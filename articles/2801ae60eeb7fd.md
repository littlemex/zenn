## はじめに

NVIDIA が公開した [NCCL Roadmap: Nov 2026 - Jan 2027 (GitHub Issue #2486)](https://github.com/NVIDIA/nccl/issues/2486) から、大規模分散学習・推論に携わるエンジニアが押さえるべきポイントを解説します。前回のロードマップの解説は「[NCCL Roadmap Aug-Oct 2026 の解説](https://zenn.dev/tosshi/articles/8d7fea5568e638)」、そこで挙げた項目の現在までの実装状況は「[NCCL 2.32.3 でロードマップはどう実装されたか](https://zenn.dev/tosshi/articles/9ab10d37f33ced)」にあります。GIN の基本は前回の解説を前提にします。

この記事では、新しい概念の GENK と Flow、AWS EFA と GIN の現状、注目機能 3 つを扱います。InfiniBand 固有の項目は扱いません。実装の状況は、2026 年 10 月 23 日に NVIDIA/nccl、aws-ofi-nccl、amazon-contributing/DeepEP、NVIDIA/nccl-extensions の公開ブランチで確かめたものです。筆者は、この記事の機能を EFA の上で動かしてはいません。NCCL は master、staging、dev の 3 本のブランチを公開していて、staging には [2.32.5-1 の版番号を付けた commit](https://github.com/NVIDIA/nccl/commit/ce64428bcceafe2ab35991f0a786679564ff1221) があります。ロードマップは「Coming Soon: NCCL 2.32 Update 1」の版番号を書いていませんが、この記事では staging のコードをその候補として読みます。

| ロードマップの項目 | 10 月 23 日時点の状態 | 実務での意味 |
|---|---|---|
| General Kernels (GENK)、Flow Device API | staging に入りました。GENK は既定では無効です | NCCL の内部と同じ部品で、自分の通信カーネルを書けます |

## GENK と Flow とは何か

### 概要

Flow は、集団通信の部品を提供する Device API です。Device API は、GPU のカーネルの中から通信を呼ぶための API で、GIN もその一部です。ロードマップは Flow を「LSA と GIN の両方で動く、高水準の Device API」と説明しています。LSA (Load/Store Accessible) は、NVLink や CUDA P2P でつながった相手の GPU のメモリに、普通の読み書きの命令で触れる通信の方式です。

GENK (General Kernels) は、NCCL が自分の Ring と Tree の集団通信を、この Flow の上で作り直したカーネルの一群です。

![staging で GENK を有効にした場合、集団通信の呼び出しをコストモデルが受け、既存のカーネル、特化した symmetric カーネル、GENK のどれかを選ぶ。GENK は Flow の上に作られ、Flow は相手ごとに LSA か GIN の接続を選ぶ。GIN の接続は strong signal を必要とし、複数ノードでは GIN Proxy の上で動く](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/2801ae60eeb7fd/zenn/articles/2801ae60eeb7fd/genk-flow.png)

図で [API] の札を付けた Flow processor、LSA connection、GIN connection は、アプリのカーネルからも呼べる Device API です。cost model、legacy kernels、specialized symmetric kernels、GENK は NCCL の中の部品です。

### なぜ重要か

前回のロードマップには「Unify legacy kernels using Device API」という項目がありました。GENK はこの項目の実体で、昔からの Ring と Tree のカーネル (図の legacy kernels) を Device API の上で作り直すものです。今回のロードマップは、選んだプラットフォームで GENK を既定にし、古いカーネルを置き換えるとしています。あわせて性能モデルを 1 つにまとめ、どの実装を選ぶかを同じ物差しで決めるとしています。

**NCCL 自身が同じ Flow で集団通信を組むので、利用者は NCCL の内部と同じ部品で自分の通信カーネルを書けます。**

GENK は、特化した symmetric カーネルより使える場所が広くなります。symmetric カーネルは、全ランクが同じ形で登録したバッファ (symmetric memory) を使う、NCCL の新しいカーネルです。staging の[カーネルの選択](https://github.com/NVIDIA/nccl/blob/af13236cbf4f03aecbb1dbfc390fb5d6166f70f1/src/sym_kernels.cc#L578-L580)には「特化したカーネルは NVLink の直結を要するが、GENK は CUDA P2P の LSA や GIN も使える」というコメントがあります。

### 構造

[Flow processor](https://github.com/NVIDIA/nccl/blob/af13236cbf4f03aecbb1dbfc390fb5d6166f70f1/src/include/nccl_device/flow.h#L15-L20) は、データの受け取り、足し合わせ、コピー、送り出しを 1 つの処理として進める部品です。CTA (GPU のスレッドブロック) のすべてのスレッドが、転送ごとに Flow を呼びます。Flow は、その中のスレッドに待つ役と送る役を割り当てます。

相手とのやり取りには、相手ごとに固定の受信バッファ (FIFO) を持つ接続を使います。受け手は、空いたバッファの数 (credit) を送り手に返します。この接続には LSA の接続と GIN の接続があり、Flow は相手ごとに実行時にどちらかを選びます。GIN の接続は、GIN の put と signal でデータを送り、相手の状態を進めます。

GENK は、この Flow の上に、Ring の 5 つの集団通信 (AllGather、ReduceScatter、Broadcast、Reduce、AllReduce) を[実装しています](https://github.com/NVIDIA/nccl/commit/c91544a4672d1854fefd9106cd5e81f5d981ff8c)。プロトコルは Simple (帯域重視)、LL (低遅延)、LL128 (LL の拡張) の 3 つです。Tree は AllReduce で、2 本の木 (double tree) を使います。GIN でつなぐ相手は、全員ではなく Ring と Tree の隣の相手だけに絞り、GIN の種類には Proxy を[指定しています](https://github.com/NVIDIA/nccl/blob/af13236cbf4f03aecbb1dbfc390fb5d6166f70f1/src/genk_runtime.cc#L171-L172)。

### staging での状態

以下は 2026 年 10 月 23 日の staging のコードから読んだもので、タグの付いたリリースで確かめたものではありません。staging の GENK は、環境変数で[有効にしたとき](https://github.com/NVIDIA/nccl/blob/af13236cbf4f03aecbb1dbfc390fb5d6166f70f1/src/sym_kernels.cc#L242)だけ選択の候補に入り、[Hopper 以降の GPU](https://github.com/NVIDIA/nccl/blob/af13236cbf4f03aecbb1dbfc390fb5d6166f70f1/src/sym_kernels.cc#L580) が要ります。

```bash
export NCCL_SYM_GENK_ENABLE=1
```

複数ノードで GENK が候補に入る[条件](https://github.com/NVIDIA/nccl/blob/af13236cbf4f03aecbb1dbfc390fb5d6166f70f1/src/sym_kernels.cc#L581-L591)は、symmetric の GIN カーネルが有効なままで、communicator のすべての相手に GIN で届き、[GIN の Proxy バックエンドがある](https://github.com/NVIDIA/nccl/blob/af13236cbf4f03aecbb1dbfc390fb5d6166f70f1/src/sym_kernels.cc#L244-L255)ことです。

GIN の signal は、受け手の側に置かれる 64 ビットの数で、put で書いたデータが届いたことを受け手に知らせます。[NCCL の文書](https://github.com/NVIDIA/nccl/blob/a6112fe8ddba871dc44d1c23111b3ae9133d2b6c/docs/userguide/source/api/device_gin.rst#L104-L106)によると、strong signal は、同じ相手への同じ context でのそれまでの put のデータもすべて見えていることを意味します。weak signal は、その signal が付いた put のデータが見えていることだけを意味します。Flow の GIN の接続は、strong signal を[必要とします](https://github.com/NVIDIA/nccl/blob/af13236cbf4f03aecbb1dbfc390fb5d6166f70f1/src/include/nccl_device/flow.h#L103)。LSA だけを使う Flow には GIN の signal は要りません。

## AWS EFA 関連アップデートと現在の課題

### EFA の 2 つの GIN の経路と signal の種類

EFA で GIN を使うときは、カーネルが必要とする signal を経路が提供するかを確かめます。EFA で使う GIN の経路として、ここでは 2 つを比べます。1 つは NCCL の GIN Proxy で、CPU のスレッドが aws-ofi-nccl の RMA の機能を通して EFA に送ります。もう 1 つは EFA GDA で、GPU のカーネルが EFA の送信キューに直接依頼を書きます。aws-ofi-nccl の文書によると、EFA GDA は `NCCL_GIN_TYPE=5` で[明示したとき](https://github.com/aws/aws-ofi-nccl/blob/d8f964011facc5afb4311bc4fa376bcbe7d2496c/doc/gin-getting-started.md#L73-L81)に使われます。同じ文書は、明示しなければ NCCL 2.31 は EFA で Proxy を使うと書いています。インスタンスやドライバなどの要件も同じ文書にあります。

2 つの経路は、提供する signal が違います。NCCL の Proxy は、strong signal と VA signal (登録した仮想アドレスに置く signal) を[使えると報告します](https://github.com/NVIDIA/nccl/blob/af13236cbf4f03aecbb1dbfc390fb5d6166f70f1/src/gin/gin_host_proxy.cc#L381-L386)。EFA GDA については、aws-ofi-nccl が strong signal も VA signal も[使えないと報告し](https://github.com/aws/aws-ofi-nccl/blob/d8f964011facc5afb4311bc4fa376bcbe7d2496c/src/rdma/gin/nccl_ofi_gin_gdaki.cpp#L1212-L1217)、NCCL の側も番号で指す indexed signal だけを[受け付けます](https://github.com/NVIDIA/nccl/blob/af13236cbf4f03aecbb1dbfc390fb5d6166f70f1/src/include/nccl_device/gin/efa_gda/gin_efa_gda.h#L461-L466)。EFA GDA の signal は、EFA の NIC が届いた書き込みを数えるカウンタで作られています。aws-ofi-nccl の[文書](https://github.com/aws/aws-ofi-nccl/blob/d8f964011facc5afb4311bc4fa376bcbe7d2496c/doc/gin-getting-started.md#L56-L69)は、signal と counter の合計が EFA のデバイスあたり 512 個までであることも、制限に挙げています。

![GIN を使う GENK と Flow は strong signal を、上流の DeepEP の ordered カーネルは strong signal と VA signal を必要とする。EFA で比べた 2 つの経路のうち、それを提供するのは NCCL の GIN Proxy で、GENK は Proxy を指定している。amazon-contributing のフォークの unordered カーネルは数える weak signal だけを求め、Proxy と EFA GDA のどちらも提供する](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/2801ae60eeb7fd/zenn/articles/2801ae60eeb7fd/efa-signals.png)

図の矢印は、使い手が必要とする signal をバックエンドが提供するかを示します。矢印はソースと文書から描いたもので、どの経路が選ばれるかや、動かした結果を示すものではありません。NCCL は、要る signal を持たないバックエンドを[選ばず](https://github.com/NVIDIA/nccl/blob/af13236cbf4f03aecbb1dbfc390fb5d6166f70f1/src/gin/gin_host.cc#L248-L258)、要件を満たすバックエンドがあればそちらを使い、無ければ失敗すると[説明しています](https://github.com/NVIDIA/nccl/blob/af13236cbf4f03aecbb1dbfc390fb5d6166f70f1/plugins/gin/README.md#L181-L182)。

GENK はそもそも Proxy を指定するので、staging のコードを読む限り、GENK が EFA の上で複数ノードの通信をするなら Proxy の経路を通ります。一方、aws-ofi-nccl の文書は、EFA GDA を使うときに symmetric の GIN カーネルを無効にするよう書いていて、この設定にすると複数ノードの GENK は候補から外れます。GENK を試す設定と EFA GDA を試す設定は、分けて考える必要があります。

### aws-ofi-nccl v1.22.0

aws-ofi-nccl の [v1.22.0](https://github.com/aws/aws-ofi-nccl/releases/tag/v1.22.0) が 2026 年 10 月 22 日 (日本時間) に出ました。v1.22.0 は NCCL 2.32.3-1 で試験された版です。EFA と GIN に関わる変更のうち、ここでは次の 3 つを取り上げます。

- 前回の実装状況の記事で書いたとおり、2026 年 9 月 25 日時点では、NCCL 2.32.3 の EFA GDA の Get に要る対応は、aws-ofi-nccl のタグの無い master にしかありませんでした。NCCL 2.32 は、EFA GDA のキューの形の番号 (backendVersion) として [2 を使います](https://github.com/NVIDIA/nccl/blob/12df1a11afad322be5a204a2db890161cbf8131d/src/gin/gin_host.cc#L25)。v1.22.0 は、backendVersion 2 への[対応](https://github.com/aws/aws-ofi-nccl/commit/452f3026990d93f329b699466e0a26a0e5545398)と、Get の完了を数える[修正](https://github.com/aws/aws-ofi-nccl/commit/d840aa1f9c3427a99d75a52e0c931cc824977049)を含む、最初のタグです。リリースノートに Get の項目はありませんが、この 2 つの commit は v1.22.0 に入っていて、1 つ前のタグの v1.21.1 には入っていません。Get の修正の説明によると、EFA GDA の Get に、利用者が完了を知るための signal や counter は付けられません。
- P6-B200 と P6-B300 で、GIN の接続の準備が失敗したり止まったりする問題が直りました。この問題は [Issue #2468](https://github.com/NVIDIA/nccl/issues/2468) に、p6-b300.48xlarge と aws-ofi-nccl 1.21.1 などの組み合わせで報告されました。Issue は、aws-ofi-nccl 側の回避策が v1.22 に入る見込みになったことを受けて、2026 年 10 月 21 日 (日本時間) に閉じられています。これらのインスタンスには NVLink のスイッチを管理するための ConnectX-7 があり、このポートはほかのノードに届きません。NCCL は、`NCCL_IB_HCA` で止めない限り、このポートで自分の GDAKI のバックエンドを初期化します。GDAKI は優先度が最も高いので既定の経路に選ばれ、一部のランクだけが失敗して全体が止まっていました。Issue が求めた、NCCL の側で全ランクがそろって別の経路に移る変更は、10 月 23 日時点の公開ブランチに見当たりません。v1.22.0 は、プラグインの初期化に成功し、利用者が `NCCL_IB_HCA` を設定していないときに、これらのインスタンスで `NCCL_IB_HCA=invalid` を[設定します](https://github.com/aws/aws-ofi-nccl/commit/a5a5737b6293e70ccc49bf5d0b957c4e80127793)。ジョブがすでに `NCCL_IB_HCA` を設定していると、この自動の設定は効きません。それより前の版では、同じ値を手で設定すると避けられると Issue に書かれています。
- Grace Blackwell で NIC が Grace の CPU に直接つながっているとき、flush の読み出しが、CPU と GPU の間の C2C の接続ではなく PCIe の経路を通っていた問題が直りました。

### NCCL 側の EFA GDA の変更

EFA GDA は signal と counter の合計がデバイスあたり 512 個までなので、signal を節約し、送る処理を軽くする変更が staging に 2 つ入っています。

1 つ目は、signal を 2 つだけ使う barrier です。barrier は、参加するランクがそろうまで待ち合わせる処理です。NCCL の既定の GIN の barrier は、2 ランク以上では、送り手のランク 1 つにつき signal を 1 つ使います。aws-ofi-nccl の文書も、EFA GDA で AlltoAll の試験をするときは、signal の数の制限のために、カーネルの CTA の数を減らすよう書いています。

![既定の barrier は 8 ランクで 8 個の signal を使い、staging の signal を節約する barrier はランク数によらず 2 個の signal を交互に使う。EFA GDA のデバイス側のコードは後者を使うが、ホストが確保する数が減るのはプラグインが API の v15 でこの barrier を希望してから。EFA GDA の signal と counter の合計はデバイスあたり 512 個まで](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/2801ae60eeb7fd/zenn/articles/2801ae60eeb7fd/barrier-slots.png)

図の 8 ランクは例で、signal の数はコードの数え方から描いたものです。新しい barrier は、2 つの数える signal を phase のビットで交互に使い、ランク数によらず 2 つで[済ませます](https://github.com/NVIDIA/nccl/blob/af13236cbf4f03aecbb1dbfc390fb5d6166f70f1/src/include/nccl_device/impl/gin_barrier__types.h#L19-L26)。EFA GDA のデバイス側のコードは、コンパイル時にこの barrier を[選びます](https://github.com/NVIDIA/nccl/blob/af13236cbf4f03aecbb1dbfc390fb5d6166f70f1/src/include/nccl_device/gin/efa_gda/gin_efa_gda.h#L1086-L1092)。ホストが確保する signal の数は、選んだバックエンドの barrier の希望から[決まります](https://github.com/NVIDIA/nccl/blob/af13236cbf4f03aecbb1dbfc390fb5d6166f70f1/src/include/dev_runtime.h#L126-L127)。この希望は、GIN のプラグインが API の v15 で報告する項目として 2026 年 10 月 3 日の [commit](https://github.com/NVIDIA/nccl/commit/4e5c1f164f2b060df5d5e5266d6e1a22bd2cd47d) で足されました。プラグインの[説明](https://github.com/NVIDIA/nccl/blob/af13236cbf4f03aecbb1dbfc390fb5d6166f70f1/plugins/gin/README.md#L170-L180)は、v14 以前のプラグインを既定の barrier とみなすと書いています。2026 年 10 月 23 日時点の aws-ofi-nccl の master は、EFA GDA の性質を GIN の API の [v14 の形](https://github.com/aws/aws-ofi-nccl/blob/d8f964011facc5afb4311bc4fa376bcbe7d2496c/src/rdma/gin/nccl_ofi_gin_gdaki.cpp#L1261)で報告しています。そのため、確保する signal が実際に減るのは、プラグインがこの希望を報告するようになってからです。

2 つ目は、1 つの送信キューに 1 つのスレッドしか書かない使い方のための、Put の専用の経路です ([PR #2478](https://github.com/NVIDIA/nccl/pull/2478))。複数のスレッドが同じキューに書く場合は、キューの位置を atomic に進め、スレッドどうしで待ち合わせる処理が要ります。書き手が 1 つと決まっていれば、この専用の経路はこれらの処理を省きます。PR は 2026 年 10 月 23 日時点で open (マージされていない) ですが、同じ題の [commit](https://github.com/NVIDIA/nccl/commit/ad35c997e6ee645a87d9617f10edf2a59877c26b) が staging に入っています。

### DeepEP と NCCL EP

DeepEP は、MoE のトークンを担当の expert に配り (dispatch)、計算結果を集める (combine) 通信のライブラリです。DeepEP は 2026 年 9 月 29 日の [V2.5](https://github.com/deepseek-ai/DeepEP/commit/def865146e95aa9ea223e277c0a8a4c6b81e5ac7) で、V1 の実装と NVSHMEM への依存をすべて取り除きました。ノードをまたぐ EP の dispatch と combine は NCCL の GIN を使い、要件は [NCCL 2.32.3 以降](https://github.com/deepseek-ai/DeepEP/blob/f6aa38fe06cd4a0489e7730365d4e0114970a2f3/README.md#L53)です。

EFA で DeepEP を動かす取り組みは、[amazon-contributing/DeepEP](https://github.com/amazon-contributing/DeepEP) のフォークにあります。EFA が使う送り方の SRD (Scalable Reliable Datagram) は届く順番を保たないので、最後の書き込みが届いても、先の書き込みが届いたとは限りません ([NCCL のソースのコメント](https://github.com/NVIDIA/nccl/blob/af13236cbf4f03aecbb1dbfc390fb5d6166f70f1/src/include/nccl_device/gin/efa_gda/gin_efa_gda.h#L625-L627))。

フォークの[カーネルの選び方の説明](https://github.com/amazon-contributing/DeepEP/blob/2a00bd88fcc69e6f9b669f5a338348e49217bf86/README.md#L403-L417)によると、ordered は、上流から来たノードをまたぐ hybrid の dispatch と combine のカーネルです。最後の signal が届いたらそれより前のデータも届いている、という前提で作られているので、strong signal と VA signal を必要とします。フォークは、ヘッダを付けた塊を送り、届いた signal の数を数えて届いた量を知る unordered のカーネルを足しました。この説明は、unordered のカーネルが GIN のバックエンドに数える signal (weak signal) だけを求めるとし、EFA ではバックエンドとして EFA GDA と CPU proxy の 2 つが使えるとしています。2026 年 10 月 23 日時点で、フォークの main は V2.5 の変更をまだ取り込んでいません。

NVIDIA の [NCCL EP](https://github.com/NVIDIA/nccl-extensions) も、MoE の dispatch と combine のライブラリです。2 つは同じ dispatch と combine を受け持つので、その段では一方を選ぶ形になると筆者は読んでいます。2 つとも NCCL の Device API と GIN の上に作られているので、NCCL とは一緒に使います。NCCL EP は NVIDIA/nccl-extensions に移っていて、2026 年 10 月 23 日時点で、NCCL の dev の nccl_ep には移転の[案内](https://github.com/NVIDIA/nccl/blob/a6112fe8ddba871dc44d1c23111b3ae9133d2b6c/contrib/nccl_ep/README.md#L1-L3)が置かれています。

## 注目機能 3 選

### CFT を使う階層型カーネル

CFT (Compute Fabric Transport) は、NCCL 2.31 で Device API に加わった通信の方式です。[NCCL の文書](https://github.com/NVIDIA/nccl/blob/a6112fe8ddba871dc44d1c23111b3ae9133d2b6c/docs/userguide/source/usage/cft.rst)によると、CFT が使えるシステムでは、CUDA が用意する fabric の logical endpoint (論理的な宛先) を、GPU のカーネルから fabric 用の命令で直接使い、put、get、足し合わせ、barrier を行えます。

ロードマップは、この CFT を使って、AllGather、ReduceScatter、AlltoAll の階層型カーネルを作るとしています。階層型は、近い GPU の間と遠い GPU の間で通信を分ける作りです。2026 年 10 月 23 日に master、staging、dev を調べた範囲では、CFT の宛先の集まりの[階層の種類](https://github.com/NVIDIA/nccl/blob/12df1a11afad322be5a204a2db890161cbf8131d/src/include/nccl_device/core.h#L82-L86)は 2.32.3 のコードに定義されていますが、それを使う集団通信のカーネルは見当たりませんでした。

:::details CFT とは
CFT が使えるのは、ハードウェア、ドライバ、CUDA が logical endpoint と fabric 用の命令に対応したシステムだけで、例の barrier のプログラムは CUDA 13.3 と SM_100 を要件に挙げています。dev では、2026 年 9 月 28 日の [commit](https://github.com/NVIDIA/nccl/commit/bac256ddb4a6c9917ef19c2ddfca98c3287d3c0f) で、CFT の宛先の集まり (CFT team) を、CUDA が報告する到達できる範囲 (clique) から作るように変わりました。10 月 23 日時点で、この commit は master と staging にはありません。

NCCL EP には、CFT の counted な書き込み (データの後に受け手のカウンタを進める書き込み) で低遅延の dispatch を送る経路が、`NCCL_EP_LL_CFT=1` で選んだときだけ使われる形で、2026 年 9 月 16 日の [commit](https://github.com/NVIDIA/nccl-extensions/commit/1cab1ed05e6781f8876b45691cd8bb7d3b671087) から main に入っています。
:::

### Determinism Guarantees: 同じ入力で同じビットを返す

ここでの決定性は、同じ入力の集団通信が、毎回ビット単位で同じ結果を返すことです。BF16 のような精度の低い型では、部分和を足す順番が変わると丸めが変わり、結果のビットが変わります。強化学習で学習側と推論側の数値のずれを追うときや、障害の調査で実行を再現したいときに、この性質が要ります。

[Issue #2360](https://github.com/NVIDIA/nccl/issues/2360) は、Hopper の NVLS で、先に作った communicator の数によって BF16 の結果が変わると報告しました。NVIDIA は、この再現例は NCCL 2.27 以降の FP32 での足し合わせで多くの場合に緩和されるが根本の修正ではない、と答えています。この Issue は 2026 年 10 月 10 日に閉じられ、そのときのコメントは、決定性の保証についての文書を外部に出す予定だと書いています。

[Issue #2479](https://github.com/NVIDIA/nccl/issues/2479) は、GB300 の NVLS の BF16 と FP16 の AllReduce と ReduceScatter で、要素の数が 4 の倍数でない場合の一部で、末尾の値が実行ごとに変わると報告しています。B300 での再現もコメントに寄せられています。この Issue には、再現した利用者が修正案の [PR #2504](https://github.com/NVIDIA/nccl/pull/2504) を出していて、2026 年 10 月 23 日時点で open です。

ロードマップは、決定性を確かめる試験の仕組みを作り、文書を公開するとしています。どの条件でどこまで同じ結果を約束するかが文書で決まれば、アルゴリズムを固定するような回避策を、根拠を持って選べるようになります。

### New Enqueue Pipeline: 呼び出しから起動までを 3 つの層に分ける

enqueue は、アプリが呼んだ集団通信や put を、カーネルやコピーの起動に変える NCCL の中の流れです。ロードマップは、これを管理 (Management)、準備 (Preparation)、スケジューリング (Scheduling) の 3 層に分け、制御の流れを簡単にし、カーネルの最適化をしやすくするとしています。

![2026 年 10 月 21 日の dev の新しい enqueue の流れ (既定では無効) では、グループの中の呼び出しは、Preparation で調整の入力を作り、すべての集団通信のアルゴリズムを選び、その結果で振り分け、バッファを登録する。Scheduling は symmetric カーネル、片側通信、コピーエンジン、既存の経路ごとにあり、それぞれの仕事を stream ごとに 1 つのキューにまとめる。communicator の作成や破棄は Management の別のキューに入る](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/2801ae60eeb7fd/zenn/articles/2801ae60eeb7fd/enqueue-layers.png)

この[枠組み](https://github.com/NVIDIA/nccl/commit/a62c20e10e69bc131876efed3fae32f100415092)は 2.31.2 から入っていますが、既定では使われません。dev では、Preparation の tuning ですべての集団通信のアルゴリズムやプロトコルを先に[選び](https://github.com/NVIDIA/nccl/commit/d348a2e8085f1e3993d65672c2bc6e7c4fc5ed1a)、classification でその結果だけを使って起動の経路を振り分ける形にしました。経路ごとのスケジューラは、それぞれの仕事を stream ごとに 1 つのキューに[まとめます](https://github.com/NVIDIA/nccl/commit/0f8accd167d01fdb0abd2684320e4df2d0be33c3)。2026 年 10 月 21 日の dev の commit では、GENK は自分の device communicator の準備が要るので、新しい symmetric のスケジューラではなく、既存の symmetric カーネルのスケジューラから[起動されます](https://github.com/NVIDIA/nccl/commit/3daa2dfd80b95ad73732ea717575a9792535807b)。

## まとめ

2026 年 10 月 23 日時点の staging には、集団通信を Device API の Flow の上で作り直した GENK が、既定では無効の形で入っています。staging のコードを読む限り、EFA の複数ノードの GENK は、strong signal を提供する Proxy の経路を使います。EFA GDA の側では、signal を節約する変更が進んでいます。
