## Device API とは何か

### NCCL の API の全体像

ロードマップの項目を説明する前に、まず背景知識として NCCL の API を整理します。NCCL の API は、Host API、Device API、plugin API の 3 つに分けられます。Host API と Device API の仕様は [NCCL の公式文書](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/api.html)にあり、この記事の表はその章立てに沿っています。plugin API は公式文書の API の章には無く、リポジトリの [plugins ディレクトリ](https://github.com/NVIDIA/nccl/tree/a6112fe8ddba871dc44d1c23111b3ae9133d2b6c/plugins)に plugin の種類ごとの説明があります。

![Host API では、CPU が ncclAllReduce を呼んで通信を NCCL に頼み、NCCL がアルゴリズムを選んで NCCL のカーネルを起動する。Device API では、CPU で window の登録と device communicator の作成を済ませたあと、利用者のカーネルが自分の計算と NCCL の通信の呼び出しを同じカーネルの中で行う。plugin API は、NCCL がネットワークなどの下の部品を呼ぶための口である](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/2801ae60eeb7fd/zenn/articles/2801ae60eeb7fd/nccl-apis.png)

| API | 何をするか | 例 |
|---|---|---|
| Host API | CPU から呼んで、communicator (通信に参加する GPU の集まり) の作成や集団通信を NCCL に頼みます。集団通信では、NCCL がアルゴリズムを選び、NCCL のカーネルを GPU で起動します。利用者の計算は別のカーネルです | [ncclCommInitRank](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/api/comms.html)、[ncclAllReduce](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/api/colls.html) |
| Device API | 利用者が書いた CUDA カーネルの中から、ほかの GPU との通信を直接呼びます (2.28 から)。計算と通信を 1 つのカーネルに入れられます。使う前の準備には Host API を使います | [GIN、LSA](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/api/device.html) |
| plugin API | NCCL のほうから呼ぶ、下の部品の差し替え口です。ネットワークへの送受信や、アルゴリズムの選択の調整などを、NCCL の外の実装に任せます | net、GIN。説明は [plugins](https://github.com/NVIDIA/nccl/tree/a6112fe8ddba871dc44d1c23111b3ae9133d2b6c/plugins) にあります。aws-ofi-nccl は EFA 用の plugin |

### 誰が NCCL を呼ぶか

NCCL を呼ぶのは、多くの場合アプリ自身ではなく、間に入るフレームワークやライブラリです。主な呼び手を、ソースで確かめた範囲で並べます。

![PyTorch の ProcessGroupNCCL と vLLM の PyNccl は Host API を直接呼び、PyTorch の nccl4py の backend は nccl4py を通して Host API を呼ぶ。PyTorch の symmetric memory の演算、DeepEP、NCCL EP は、Host API で準備したあと Device API を使う。NCCL は、NVLink には自分で届き、ネットワークには組み込みの InfiniBand などの経路か、plugin API を通した aws-ofi-nccl などで送る](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/2801ae60eeb7fd/zenn/articles/2801ae60eeb7fd/nccl-callers.png)

| 呼び手 | どう呼ぶか | 使う API |
|---|---|---|
| PyTorch の `torch.distributed` (backend `"nccl"`) | C++ の ProcessGroupNCCL が、`ncclAllReduce` などを[直接呼びます](https://github.com/pytorch/pytorch/blob/9aee436a1bfc7a0bd2c40f48f128cb185ee3d75e/torch/csrc/distributed/c10d/ProcessGroupNCCL.cpp#L4590) | Host API |
| PyTorch の backend `"nccl4py"` (`torch.distributed._nccl4py`) | Python で書いた backend が、[nccl4py を通して呼びます](https://github.com/pytorch/pytorch/blob/9aee436a1bfc7a0bd2c40f48f128cb185ee3d75e/torch/distributed/_nccl4py/backend.py#L1-L9)。`init_process_group("nccl4py")` で選びます | Host API |
| [nccl4py](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/nccl4py.html) | NVIDIA の公式の Python の bindings。Cython で libnccl を呼び、PyTorch の tensor や CuPy の配列をそのまま渡せます。実験的な CuTe DSL の部品もあります | 主に Host API |
| vLLM の PyNccl | Python の ctypes で libnccl を[読み込んで呼びます](https://github.com/vllm-project/vllm/blob/debcf228431f0b04ee8f12cfc410b0fe3c34a4f7/vllm/distributed/device_communicators/pynccl_wrapper.py#L379-L383) | Host API |
| PyTorch の symmetric memory の演算、DeepEP、NCCL EP | 自分の CUDA カーネルの中から通信を呼びます。準備には Host API で window を[登録し](https://github.com/pytorch/pytorch/blob/9aee436a1bfc7a0bd2c40f48f128cb185ee3d75e/torch/csrc/distributed/c10d/symm_mem/NCCLSymmetricMemory.cu#L198)、device communicator を[作ります](https://github.com/pytorch/pytorch/blob/9aee436a1bfc7a0bd2c40f48f128cb185ee3d75e/torch/csrc/distributed/c10d/symm_mem/ops/nccl_all_to_all_nd.cu#L179) | Device API と Host API |
| aws-ofi-nccl など | NCCL のほうから呼ばれます。NCCL が EFA などのネットワークに送るときの下の部品です。InfiniBand には NCCL に組み込みの経路もあります | plugin API |

### Device API は何のためにあるか

Host API で通信を頼むと、通信は NCCL のカーネル 1 回分の単位になり、利用者の計算とは別のカーネルになります。計算の途中で決まった相手に少しずつ送りたい場合や、計算と通信を細かく重ねたい場合には、この単位が粗すぎます。たとえば MoE のトークンの振り分けでは、どのトークンをどの GPU に送るかが計算の途中で決まります。

Device API は、利用者のカーネルの中から、ほかの GPU のメモリへ直接データを動かせるようにするための [API](https://github.com/NVIDIA/nccl/blob/a6112fe8ddba871dc44d1c23111b3ae9133d2b6c/docs/userguide/source/usage/deviceapi.rst#L5-L6) です。NCCL の [Device API の例](https://github.com/NVIDIA/nccl/blob/a6112fe8ddba871dc44d1c23111b3ae9133d2b6c/docs/examples/07_kernel_fusion/README.md#L10-L20)は、計算と通信を分けて順に行う従来のやり方に対して、カーネルの中で両方を細かく混ぜることで、待ち時間を減らし処理量を上げられると説明しています。

![利用者のカーネルからほかの GPU に届く経路ごとに、Device API の部品がある。LSA は CUDA P2P (NVLink と一部の PCIe)、Multimem は NVLink SHARP、GIN はネットワーク、CFT は CUDA の fabric に届き、reduce と copy の部品は自分では通信路を持たない。利用者は CPU で symmetric memory window を登録し、ncclDevCommCreate で device communicator を作ってから、自分のカーネルを起動する](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/2801ae60eeb7fd/zenn/articles/2801ae60eeb7fd/device-api-modules.png)

GPU のカーネルからほかの GPU に届く経路はいくつかあり、Device API は経路ごとに部品を用意しています。同じノードで NVLink や PCIe の P2P でつながった相手には、相手のメモリを普通の読み書きの命令で触れます (LSA)。NVLink のスイッチが複数の宛先への書き込みや足し合わせを引き受けられるシステムでは、Multimem を使います。ノードをまたぐ相手には、NIC を通して put や get を出します (GIN)。CFT は、相手のメモリを番地 (ポインタ) で触る代わりに、CUDA が用意する宛先の番号 (logical endpoint) とオフセットを指定して put や get を出す部品で、Blackwell 以降の GPU で使えます。これらと組み合わせて使う、足し合わせやコピーの部品 (reduce と copy) も用意されています。

GIN の仕組みは、前回の解説の「[GIN とは何か](https://zenn.dev/tosshi/articles/8d7fea5568e638#gin-(gpu-initiated-networking)-%E3%81%A8%E3%81%AF%E4%BD%95%E3%81%8B)」で説明しました。LSA は後の GENK と Flow の節で、CFT は注目機能の節で扱います。Multimem と reduce と copy の部品は、この記事では詳しく扱いません。

どの部品を使う場合も、準備は利用者が CPU で Host API を呼んで行います。通信に使うバッファを symmetric memory window として登録し、カーネルが使う資源を指定して device communicator を作り、それを渡して自分のカーネルを起動します。手順の例は [NCCL の文書](https://github.com/NVIDIA/nccl/blob/a6112fe8ddba871dc44d1c23111b3ae9133d2b6c/docs/userguide/source/usage/deviceapi.rst#L87-L125)にあります。GIN を使うカーネルは、NCCL を更新したら作り直す必要があると[文書](https://github.com/NVIDIA/nccl/blob/a6112fe8ddba871dc44d1c23111b3ae9133d2b6c/docs/userguide/source/usage/deviceapi.rst#L84-L85)は書いています。次の節からは、この Device API の上に加わる新しい部品とカーネルを見ていきます。

## GENK と Flow とは何か

:::message
GENK と Flow は、まだリリースされておらず staging にだけあるコードです。この節は staging の実装から読み取った内容で、リリースまでに変わる可能性があります。staging で試すには、ビルドのときに `SYM_GENK=1` を[指定し](https://github.com/NVIDIA/nccl/blob/26068774a52e415b3fd4494f91a3dba06f135e04/makefiles/common.mk#L30-L33)、実行のときに `NCCL_SYM_GENK_ENABLE=1` を設定する必要があります。
:::

### 概要

Flow は、前の節の LSA と GIN の上に作られた、集団通信の部品を提供する Device API です。ロードマップは Flow を「LSA と GIN の両方で動く、高水準の Device API」と説明しています。LSA は、NVLink や PCIe の P2P でつながった相手の GPU のメモリに、普通の読み書きの命令で触れる Device API の部品です。

GENK (General Kernels) は、NCCL が自分の Ring と Tree の集団通信を、この Flow の上で作り直したカーネルの一群です。Ring では AllGather、ReduceScatter、Broadcast、Reduce、AllReduce を、Tree では AllReduce を[実装しています](https://github.com/NVIDIA/nccl/commit/c91544a4672d1854fefd9106cd5e81f5d981ff8c)。

前回のロードマップには「Unify legacy kernels using Device API」という項目がありました。GENK はこの項目につながる取り組みだと筆者は読んでいて、legacy kernels (NCCL に最初からある Ring と Tree のカーネル) を Device API の上で作り直すものです。今回のロードマップは、選んだプラットフォームで GENK を既定にし、古いカーネルを置き換えるとしています。あわせて性能モデルを 1 つにまとめ、どの実装を選ぶかを同じ物差しで決めるとしています。

staging では、NCCL 自身が同じ Flow で集団通信を組んでいます。**Flow がリリースに入れば、利用者も NCCL の内部と同じ部品で通信カーネルを書けます。**

NCCL の集団通信には、GENK の前から 2 種類のカーネルがあります。

- legacy kernels: NCCL に最初からある Ring や Tree のカーネルです。経路の違いは、CPU の側が準備する [transport](https://github.com/NVIDIA/nccl/tree/26068774a52e415b3fd4494f91a3dba06f135e04/src/transport) (NVLink や PCIe の P2P、ネットワークなど) が受け持ち、ネットワークでは CPU の proxy スレッドが NIC に渡します。
- symmetric カーネル: 全ランクが同じ形で登録した[バッファ](https://github.com/NVIDIA/nccl/blob/a6112fe8ddba871dc44d1c23111b3ae9133d2b6c/docs/userguide/source/usage/bufferreg.rst#L183-L203) (symmetric memory window) を集団通信に渡したときに使える、新しいカーネルです。相手のバッファの番地が分かるので、Device API の LSA などで相手のメモリを直接読み書きします。いまあるものは、NVLink の直結を前提に、場面ごとに作り込まれています (表の「特化した symmetric カーネル」)。

GENK は、symmetric カーネルと同じ Device API の作りで、legacy kernels と同じくらい広い経路で動くものです。Ring で隣の GPU にデータを渡す場面で比べると、次のようになります。

| 隣の GPU との経路 | legacy kernels | 特化した symmetric カーネル | GENK |
|---|---|---|---|
| NVLink | 動く | 動く | 動く (LSA) |
| PCIe の P2P | 動く | 使えない | 動く (LSA) |
| 別のノード (ネットワーク) | 動く | 一部の種類だけ動く (GIN) | 動く (GIN) |

特化した symmetric カーネルは、PCIe だけでつながったノードでは候補から外れます。GENK では、隣の GPU ごとに Flow が LSA か GIN かを実行時に選ぶので、同じカーネルのまま NVLink でも PCIe でもネットワークでも動きます。staging の[カーネルの選択](https://github.com/NVIDIA/nccl/blob/26068774a52e415b3fd4494f91a3dba06f135e04/src/sym_kernels.cc#L592-L594)にも「特化したカーネルは NVLink の直結を要するが、GENK は CUDA P2P の LSA や GIN も使える」というコメントがあります。

利用者の側の例もあります。NCCL の [Device API の例](https://github.com/NVIDIA/nccl/tree/a6112fe8ddba871dc44d1c23111b3ae9133d2b6c/docs/examples/07_kernel_fusion)には、Transformer の RMSNorm の計算を ReduceScatter と AllGather の通信と 1 つのカーネルにまとめるものがあり、いまは LSA、Multimem、GIN を直接使って、受け取り、足し合わせ、送り出しを書いています。Flow は、NCCL 自身が集団通信に使うこの受け取り、足し合わせ、送り出しの部分を、部品として提供します。

NCCL の文書の Device API の章には、Flow と GENK の説明はまだありません。Flow の使い方は、ヘッダの[説明](https://github.com/NVIDIA/nccl/blob/26068774a52e415b3fd4494f91a3dba06f135e04/src/include/nccl_device/flow.h#L15-L120)にまとまっていて、[Flow processor を足した commit](https://github.com/NVIDIA/nccl/commit/11dd8fce6c8a33c1398bb9e9ea6e37532576ab04) が入口になります。GENK は、[カーネルを足した commit](https://github.com/NVIDIA/nccl/commit/c91544a4672d1854fefd9106cd5e81f5d981ff8c) と、[NCCL の選択に組み込んだ commit](https://github.com/NVIDIA/nccl/commit/21501c3746bb04fe8f35b32c5ccfa116f3a4807e) が出発点です。

![staging の NCCL を SYM_GENK=1 でビルドし、環境変数で GENK を有効にした Hopper 以降の GPU の場合、集団通信の呼び出しをコストモデルが受け、既存のカーネル、特化した symmetric カーネル、GENK のどれかを選ぶ。GENK は Flow の上に作られ、Flow は相手ごとに LSA か GIN の接続を選ぶ。GIN の接続は strong signal を必要とし、GENK は複数ノードで GIN Proxy を指定する](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/2801ae60eeb7fd/zenn/articles/2801ae60eeb7fd/genk-flow.png)

図で [API] のタグを付けた Flow processor、LSA connection、GIN connection は、アプリのカーネルからも呼べる Device API です。cost model、legacy kernels、specialized symmetric kernels、GENK は NCCL の中の部品です。

### GIN の signal とは

GIN の put は片側通信で、受け手は何も呼ばないので、データがいつ届いたかを自分では知れません。signal は、それを知らせるための、受け手の側に置かれた数です。送り手が put に signal を付けると、データが届いたあとに受け手の数が 1 増え、受け手はその数が目標に達するまで待ってから読みます。GIN の基本は、前回の解説の「[GIN とは何か](https://zenn.dev/tosshi/articles/8d7fea5568e638#gin-(gpu-initiated-networking)-%E3%81%A8%E3%81%AF%E4%BD%95%E3%81%8B)」で説明しました。

![weak signal では、put C に付けた signal が届いても、signal を付けていない put A と put B のデータはまだ届いていないかもしれない。strong signal では、同じ相手への同じ context の put A、B、C のデータがすべて読める](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/2801ae60eeb7fd/zenn/articles/2801ae60eeb7fd/signal-strong-weak.png)

signal には strong と weak の [2 種類](https://github.com/NVIDIA/nccl/blob/a6112fe8ddba871dc44d1c23111b3ae9133d2b6c/docs/userguide/source/api/device_gin.rst#L104-L106)があります。weak signal が「読んでよい」と約束するのは、その signal を付けた put のデータだけです。strong signal は、同じ相手に先に出した put のデータもすべて読めると約束するので、最後の put にだけ signal を付ければ済みます。

EFA の送り方の SRD は、書き込みが届く[順番を保ちません](https://github.com/NVIDIA/nccl/blob/26068774a52e415b3fd4494f91a3dba06f135e04/src/include/nccl_device/gin/efa_gda/gin_efa_gda.h#L625-L640)。EFA の上の経路のうち、GPU から直接送る EFA GDA が提供するのは weak signal だけです (次の節で説明します)。一方、Flow の GIN の接続は strong signal を[必要とします](https://github.com/NVIDIA/nccl/blob/26068774a52e415b3fd4494f91a3dba06f135e04/src/include/nccl_device/flow.h#L103)。

## AWS EFA 関連アップデートと現在の課題

### EFA の 2 つの GIN の経路と signal の種類

:::message
GENK と Flow の GIN の接続は strong signal を必要とします。EFA の上で strong signal を提供するのは GIN Proxy だけで、GPU から直接送る EFA GDA は weak signal しか提供しません。そのため、EFA の複数ノードで GENK を使うなら Proxy の経路になります。
:::

EFA で GIN を使うときは、カーネルが必要とする signal の種類を、使う経路が提供するかを先に確かめる必要があります。NCCL は、カーネルが求める種類の signal を提供できないバックエンドを[使わず](https://github.com/NVIDIA/nccl/blob/26068774a52e415b3fd4494f91a3dba06f135e04/src/gin/gin_host.cc#L248-L258)、提供できる別のバックエンドがあればそちらに切り替え、無ければエラーにすると[説明しています](https://github.com/NVIDIA/nccl/blob/26068774a52e415b3fd4494f91a3dba06f135e04/plugins/gin/README.md#L181-L183)。EFA で使う GIN の経路として、ここでは 2 つを比べます。1 つは NCCL の GIN Proxy で、CPU のスレッドが aws-ofi-nccl の RMA の機能を通して EFA に送ります。もう 1 つは EFA GDA で、GPU のカーネルが EFA の送信キューに直接依頼を書きます。aws-ofi-nccl の文書によると、EFA GDA は `NCCL_GIN_TYPE=5` で[明示したとき](https://github.com/aws/aws-ofi-nccl/blob/d8f964011facc5afb4311bc4fa376bcbe7d2496c/doc/gin-getting-started.md#L73-L81)に使われます。同じ文書は、明示しなければ NCCL 2.31 は EFA で Proxy を使うと書いています。インスタンスやドライバなどの要件も同じ文書にあります。

2 つの経路は、提供する signal が違います。NCCL の Proxy は、strong signal と VA signal (登録した仮想アドレスに置く signal) を[使えると報告します](https://github.com/NVIDIA/nccl/blob/26068774a52e415b3fd4494f91a3dba06f135e04/src/gin/gin_host_proxy.cc#L381-L386)。EFA GDA については、aws-ofi-nccl が strong signal も VA signal も[使えないと報告し](https://github.com/aws/aws-ofi-nccl/blob/d8f964011facc5afb4311bc4fa376bcbe7d2496c/src/rdma/gin/nccl_ofi_gin_gdaki.cpp#L1212-L1217)、NCCL の側も番号で指す indexed signal だけを[受け付けます](https://github.com/NVIDIA/nccl/blob/26068774a52e415b3fd4494f91a3dba06f135e04/src/include/nccl_device/gin/efa_gda/gin_efa_gda.h#L461-L466)。EFA GDA の signal は、EFA の NIC が届いた書き込みを数えるカウンタで作られています。aws-ofi-nccl の[文書](https://github.com/aws/aws-ofi-nccl/blob/d8f964011facc5afb4311bc4fa376bcbe7d2496c/doc/gin-getting-started.md#L56-L69)は、signal と counter の合計が EFA のデバイスあたり 512 個までであることも、制限に挙げています。

![GIN を使う GENK と Flow は strong signal を、上流の DeepEP の ordered カーネルは strong signal と VA signal を必要とする。EFA で比べた 2 つの経路のうち、それを提供するのは NCCL の GIN Proxy で、GENK は Proxy を指定している。amazon-contributing のフォークの unordered カーネルは数える weak signal だけを求め、Proxy と EFA GDA のどちらも提供する](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/2801ae60eeb7fd/zenn/articles/2801ae60eeb7fd/efa-signals.png)

図の矢印は、使い手が必要とする signal をバックエンドが提供するかを示します。矢印はソースと文書から描いたもので、どの経路が選ばれるかや、動かした結果を示すものではありません。図の DeepEP の ordered は届く順番を前提にする上流のカーネル、unordered は順番を前提にしない amazon-contributing のフォークのカーネルで、後の「DeepEP と NCCL EP」で説明します。

GENK はノードをまたぐ GIN の種類に Proxy を[指定している](https://github.com/NVIDIA/nccl/blob/26068774a52e415b3fd4494f91a3dba06f135e04/src/genk_runtime.cc#L171-L172)ので、staging のコードを読む限り、GENK が EFA の上で複数ノードの通信をするなら Proxy の経路を通ります。一方、aws-ofi-nccl の文書は、EFA GDA を使うときに symmetric の GIN カーネルを無効にするよう書いていて、この設定 (`NCCL_SYM_GIN_KERNELS_ENABLE=0`) にすると複数ノードの GENK は候補から外れます。EFA GDA を試す設定 (`NCCL_GIN_TYPE=5` と `NCCL_SYM_GIN_KERNELS_ENABLE=0`) と、GENK を試す設定 (この 2 つを既定のままにして Proxy で動かす) は、分けて考える必要があります。

:::details aws-ofi-nccl v1.22.0 で、EFA GDA の Get がタグの付いた版で使えるようになった
Get は、GPU のカーネルが、ほかの GPU のメモリの中身を、持ち主に何もさせずに読み出す操作です。たとえば、手元の番号を見て、ほかの GPU が持つ表の行を取り出すような使い方ができます。Get の意義は「[NCCL 2.32.3 でロードマップはどう実装されたか](https://zenn.dev/tosshi/articles/9ab10d37f33ced)」で説明しました。

その記事の時点では、NCCL 2.32.3 には Get が入っていましたが、aws-ofi-nccl の側の対応はタグの無い master にしかありませんでした。2026 年 10 月 22 日 (日本時間) の [v1.22.0](https://github.com/aws/aws-ofi-nccl/releases/tag/v1.22.0) は、NCCL 2.32 が使うキューの形への[対応](https://github.com/aws/aws-ofi-nccl/commit/452f3026990d93f329b699466e0a26a0e5545398)と、Get の完了を数える[修正](https://github.com/aws/aws-ofi-nccl/commit/d840aa1f9c3427a99d75a52e0c931cc824977049)を含む最初のタグです。これで、NCCL 2.32 と aws-ofi-nccl v1.22.0 という、タグの付いた版どうしで EFA GDA の Get を使えます。

ただし、Get には完了を知らせる signal や counter を付けられません。読み出しが終わったかは、出した依頼をまとめて待つ Flush で確かめます。
:::

### DeepEP と NCCL EP

DeepEP は、MoE のトークンを担当の expert に配り (dispatch)、計算結果を集める (combine) 通信のライブラリです。DeepEP は 2026 年 9 月 29 日の [V2.5](https://github.com/deepseek-ai/DeepEP/commit/def865146e95aa9ea223e277c0a8a4c6b81e5ac7) で、V1 の実装と NVSHMEM への依存をすべて取り除きました。ノードをまたぐ EP の dispatch と combine は NCCL の GIN を使い、要件は [NCCL 2.32.3 以降](https://github.com/deepseek-ai/DeepEP/blob/f6aa38fe06cd4a0489e7730365d4e0114970a2f3/README.md#L53)です。

EFA で DeepEP を動かす取り組みは、[amazon-contributing/DeepEP](https://github.com/amazon-contributing/DeepEP) のフォークにあります。EFA が使う送り方の SRD (Scalable Reliable Datagram) は届く順番を保たないので、最後の書き込みが届いても、先の書き込みが届いたとは[限りません](https://github.com/NVIDIA/nccl/blob/26068774a52e415b3fd4494f91a3dba06f135e04/src/include/nccl_device/gin/efa_gda/gin_efa_gda.h#L625-L627)。

フォークの[カーネルの選び方の説明](https://github.com/amazon-contributing/DeepEP/blob/2a00bd88fcc69e6f9b669f5a338348e49217bf86/README.md#L403-L417)によると、ordered は、上流から来たノードをまたぐ hybrid の dispatch と combine のカーネルです (`EP_HYBRID_KERNEL` で選び、direct mode には関係しません)。最後の signal が届いたらそれより前のデータも届いている、という前提で作られているので、strong signal と VA signal を必要とします。ソースと文書から読む限り、このカーネルを EFA で動かすなら Proxy の経路を通ることになり、EFA GDA は使えません。フォークは、ヘッダを付けた塊を送り、届いた signal の数を数えて届いた量を知る unordered のカーネルを足しました。この説明は、unordered のカーネルが GIN のバックエンドに数える signal (weak signal) だけを求めるとし、EFA ではバックエンドとして EFA GDA と CPU proxy の 2 つが使えるとしています。フォークの main は V2.5 の変更をまだ取り込んでいません。

NVIDIA の [NCCL EP](https://github.com/NVIDIA/nccl-extensions) も、MoE の dispatch と combine のライブラリです。2 つは同じ dispatch と combine を受け持つので、その段では一方を選ぶ形になると筆者は読んでいます。2 つとも NCCL の Device API と GIN の上に作られているので、NCCL とは一緒に使います。NCCL EP は NVIDIA/nccl-extensions に移り、NCCL の staging からは、nccl_ep と nccl_m2n のディレクトリが[消されました](https://github.com/NVIDIA/nccl/commit/26068774a52e415b3fd4494f91a3dba06f135e04)。

## 注目機能 3 選

### CFT を使う階層型カーネル

CFT (Compute Fabric Transport) は、NCCL 2.31 で Device API に加わった部品です。LSA では、カーネルのスレッドが、相手の GPU のメモリを番地で指して、普通の読み書きの命令で書きます。CFT では、CUDA 13.3 で加わった logical endpoint という仕組みを使います。NCCL は CPU の側で、宛先の番号を確保し、そこに各 GPU のバッファを[結び付けておきます](https://github.com/NVIDIA/nccl/blob/a6112fe8ddba871dc44d1c23111b3ae9133d2b6c/src/include/cudawrap.h#L176-L186)。カーネルは、送りたいデータを shared memory に置き、宛先の番号とオフセットを指定して put を出し、そのあと完了を[確かめます](https://github.com/NVIDIA/nccl/blob/a6112fe8ddba871dc44d1c23111b3ae9133d2b6c/docs/userguide/source/usage/cft.rst#L86-L107)。

CFT で届く相手の集まり (CFT team) は、CUDA が報告する「logical endpoint で届く範囲」から作られ、それが分からないときは LSA で届く範囲と同じになります。dev のソースでは、CUDA が報告する範囲は LSA の範囲の倍数でなければならず、LSA より広い範囲を 1 つの CFT team にできる[作りです](https://github.com/NVIDIA/nccl/blob/a6112fe8ddba871dc44d1c23111b3ae9133d2b6c/src/cft_dev_runtime.cc#L110-L127)。NCCL の文書は、CFT がどの物理的な経路を通るかを書いていません。NCCL EP の CFT を使う経路は、1 つの NVLink のドメインの中だけを対象にしています。

ロードマップは、この CFT を使って、AllGather、ReduceScatter、AlltoAll の階層型カーネルを作るとしています。階層型は、近い GPU の間と遠い GPU の間で通信を分ける作りで、LSA の範囲と、それより広い CFT team の範囲を使い分けることになると筆者は読んでいます。master、staging、dev を調べた範囲では、CFT の宛先の集まりの[階層の種類](https://github.com/NVIDIA/nccl/blob/12df1a11afad322be5a204a2db890161cbf8131d/src/include/nccl_device/core.h#L82-L86)は 2.32.3 のコードに定義されていますが、それを使う集団通信のカーネルは見当たりませんでした。

:::details CFT とは
CFT が使えるのは、ハードウェア、ドライバ、CUDA が logical endpoint と fabric 用の命令に対応したシステムだけで、例の barrier のプログラムは CUDA 13.3 と SM_100 を要件に挙げています。CFT team を CUDA の報告する範囲 (clique) から作る変更は、dev の [2026 年 9 月 28 日の commit](https://github.com/NVIDIA/nccl/commit/bac256ddb4a6c9917ef19c2ddfca98c3287d3c0f) で入り、master と staging にはまだありません。

NCCL EP には、CFT の counted な書き込み (データの後に受け手のカウンタを進める書き込み) で低遅延の dispatch を送る経路が、`NCCL_EP_LL_CFT=1` で選んだときだけ使われる形で、[2026 年 9 月 16 日の commit](https://github.com/NVIDIA/nccl-extensions/commit/1cab1ed05e6781f8876b45691cd8bb7d3b671087) から main に入っています。
:::

### Determinism Guarantees: 同じ入力で同じビットを返す

ここでの決定性は、同じ入力の集団通信が、毎回ビット単位で同じ結果を返すことです。BF16 のような精度の低い型では、部分和を足す順番が変わると丸めが変わり、結果のビットが変わります。前回のロードマップは、決定性の目的を、結果の再現と大規模な実行の調査をしやすくすることとしていました。たとえば、強化学習で学習側と推論側の数値のずれを追うときにも、この性質が要ります。

[Issue #2360](https://github.com/NVIDIA/nccl/issues/2360) は、Hopper の NVLS で、先に作った communicator の数を変えると BF16 の結果が変わると報告しました。同じ構成で繰り返すと結果は安定していて、実行ごとに値が変わる後の Issue #2479 とは現象が違います。NVIDIA の担当者は、この再現例は NCCL 2.27 では再現せず、2.27 以降の FP32 での足し合わせは多くの場合に緩和するが根本の修正ではないと答え、この問題は Hopper に特有だとしています。この Issue は、報告者の返事を数週間待ったあと 2026 年 10 月 10 日に閉じられ、[そのときのコメント](https://github.com/NVIDIA/nccl/issues/2360#issuecomment-6093355393)は、決定性の保証についての文書を外部に出す予定だと書いています。

[Issue #2479](https://github.com/NVIDIA/nccl/issues/2479) は、GB300 の NVLS の BF16 と FP16 の AllReduce と ReduceScatter で、要素の数が 4 の倍数でない場合の一部で、末尾の値が実行ごとに変わると報告しています (報告は NCCL 2.29.7)。B300 と NCCL 2.32.3 での再現もコメントに寄せられています。この Issue には、再現した利用者が修正案の [PR #2504](https://github.com/NVIDIA/nccl/pull/2504) を出しました。NVIDIA の担当者は、修正が効くことを確かめ、取り込みを検討するために NCCL の内部に写したと[コメントしています](https://github.com/NVIDIA/nccl/issues/2479#issuecomment-6425466179)。Issue と PR はどちらも open (マージされていない) です。

ロードマップは、決定性を確かめる試験の仕組みを作り、文書を公開するとしています。どの条件でどこまで同じ結果を約束するかが文書で決まれば、アルゴリズムを固定するような回避策を、根拠を持って選べるようになります。

### New Enqueue Pipeline: 呼び出しから起動までを 3 つの層に分ける

enqueue は、アプリが呼んだ集団通信や put を、カーネルやコピーの起動に変える NCCL の中の流れです。ロードマップは、これを管理 (Management)、準備 (Preparation)、スケジューリング (Scheduling) の 3 層に分け、制御の流れを簡単にし、カーネルの最適化をしやすくするとしています。

![dev の新しい enqueue の流れ (既定では無効) では、グループの中の呼び出しは、Preparation で調整の入力を作り、すべての集団通信のアルゴリズムを選び、その結果で振り分け、バッファを登録する。Scheduling は symmetric カーネル、片側通信、コピーエンジン、既存の symmetric カーネル (いまの GENK はここ) の経路ごとにあり、それぞれの仕事を stream ごとに 1 つのキューにまとめる。communicator の作成や破棄は Management の別のキューに入る](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/2801ae60eeb7fd/zenn/articles/2801ae60eeb7fd/enqueue-layers.png)

管理と準備の層を含む[基本の枠組み](https://github.com/NVIDIA/nccl/commit/a62c20e10e69bc131876efed3fae32f100415092)は 2.31.2 から入っていて、その時点のスケジューリングの層は既存の経路に戻すだけでした。いまの staging と dev でも、新しい流れは既定で無効です。dev では、Preparation の tuning ですべての集団通信のアルゴリズムやプロトコルを先に[選び](https://github.com/NVIDIA/nccl/commit/d348a2e8085f1e3993d65672c2bc6e7c4fc5ed1a)、classification でその結果だけを使って起動の経路を振り分ける形にしました。経路ごとのスケジューラは、それぞれの仕事を stream ごとに 1 つのキューに[まとめます](https://github.com/NVIDIA/nccl/commit/0f8accd167d01fdb0abd2684320e4df2d0be33c3)。dev の commit では、GENK は自分の device communicator の準備が要るので、新しい symmetric のスケジューラではなく、既存の symmetric カーネルのスケジューラから[起動されます](https://github.com/NVIDIA/nccl/commit/3daa2dfd80b95ad73732ea717575a9792535807b)。

## まとめ

staging には、Flow の上で作り直し、NVLink、PCIe、ネットワークのどの経路でも同じカーネルで動く GENK が入っています。EFA の複数ノードでは、strong signal を提供する Proxy の経路を通ります。
