## はじめに

Amazon FSx for Lustre の EFA 有効のファイルシステムには、クライアントから EFA と TCP の 2 つの経路があります。この記事は、EFA の経路だけが不調になったときに Lustre が TCP に切り替わるか、TCP に固定すると何を失うか、どの規模の学習まで TCP で足りるかを、公開されているソースと、東京リージョンで 2026-10-26 (JST) に行った試験から調べます。Lustre の部品と LNet の基本は、前編の「[Lustre 入門: サーバの役割とファイルの流れ、LNet の通信](https://zenn.dev/tosshi/articles/cfd989188c2509)」を前提にします。AWS のサポートに確認した内容ではありません。

## EFA を使うための条件

EFA の経路は、ファイルシステムの作成時と、クライアントの側の両方で条件を満たしたときだけ使えます。AWS の [EFA 有効のファイルシステムの文書](https://docs.aws.amazon.com/fsx/latest/LustreGuide/efa-file-systems.html) を、2026-11-26 に読み直した内容を表にします。

| 対象 | 条件 |
|---|---|
| ファイルシステム | Persistent 2 で、メタデータの設定があること。SSD か Intelligent-Tiering で、Intelligent-Tiering は 4,000 MBps 以上の 4,000 MBps 刻み。SSD で 1000 MB/s/TiB なら容量は 4,800 GiB 以上 (試験では 1,200 GiB の作成が拒否された)。EFA を有効にできるのは作成するときだけ |
| クライアント | Nitro v4 以降の EFA 対応インスタンス (trn2 を除く)。AL2023、RHEL 9.5 以降、Ubuntu 22 以降のカーネル 6.8 以降。EFA のモジュールと設定 |
| ネットワーク | ファイルシステムと同じアベイラビリティーゾーンと /16 の CIDR。EFA 対応のセキュリティグループ |
| GPUDirect Storage | P5、P5e、P5en、P6-B200、P6-B300 のクライアントと、GDS のドライバ |
| メタデータの通信 | EFA を有効にしても、常に TCP |

## kefalnd が EFA の経路を作る仕組み

EFA 向けの LND は kefalnd で、upstream の Lustre に [lnet/klnds/efalnd](https://github.com/lustre/lustre-release/tree/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd) として入っています。kefalnd は、NID の作り方と接続の確立で、TCP の経路に頼ります。次の表は、EFA の経路で、各層が何を受け持ち、失敗と再送をどこで扱い、何で相手を特定するかを示します。

| 層 | 受け持ち | 失敗と再送 | 相手の特定 |
|---|---|---|---|
| LNet | 宛先と経路の選択、health | 失敗の種類に応じて health を下げ、条件を満たすメッセージだけを再送する | NID |
| kefalnd | EFA の接続、bulk の運び方 | 送信の完了エラーなどを状態に変えて LNet に返す。bulk のメモリの登録と解除、cookie の照合をする | EFA の NID、GID と QP の番号、epoch |
| EFA の NIC (SRD) | パケットの送受信 | 失われたパケットを NIC が送り直す。ソフトウェアには、届いたか失敗の通知かが見える | GID と QP の番号 |

::::details 読んだコードのバージョン

リンクは upstream の [lustre-release 6325870](https://github.com/lustre/lustre-release/tree/6325870717c7899f1ba545493ce2a07cb3834a6b) で、2026-10-21 のタグ 2.17.60 です。FSx のクライアントは、AWS が公開する [SRPM](https://fsx-lustre-client-repo.s3.amazonaws.com/el/9/SRPMS/) の 2.15.6-1fsx31 から fsx36 に patch を `%prep` の順に当てて組み直し、`kefalnd_send`、`kefalnd_drain_ni_conns`、`lnet_find_best_ni_on_local_net` が upstream と同じ処理であることを読み比べました。試験したカーネルのモジュールが fsx のどの patch まで含むかは確かめていません。kefalnd のバージョンの文字列 1.2.6 は fsx36 の `efalnd.h` と同じです。チケットの状態は 2026-10-26 に Jira で見た値です。

### NID の作り方

kefalnd の NID のうち、アドレスが 4 バイトの small NID は、TCP の NID の IP アドレスの一部と、EFA デバイスの PCI の位置から計算で作られます。

![TCP の NID 10.0.1.20 の上位 16 ビットを捨て、下位 16 ビットの 1.20 を EFA の NID の上位に置き、EFA デバイスの PCI のバス番号 0 と devfn 248 を下位に置いて 1.20.0.248@efa になる。相手の TCP の NID は、自分の IP の上位 16 ビットと相手の EFA の NID の上位 16 ビットから作られる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/9c049a2f18444a/zenn/articles/9c049a2f18444a/nid.png)

試験では、OSS の TCP の NID の `10.0.1.20@tcp` が、[kefalnd_create_efa_nid](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd.c#L2922) の計算で `1.20.0.248@efa` になりました。OSS の PCI の値は、クライアントから見えた NID からの逆算です。クライアントは逆向きに、相手の EFA の NID と自分の IP アドレスの上位 16 ビットから、相手の TCP の NID を [求めます](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd_peerni.c#L65)。自分と相手が同じ /16 にいないと、この計算で得る IP アドレスは相手の本当の IP アドレスと一致せず、EFA の条件に同じ /16 が入っているのはこのためと考えられます。文書は理由を書いていません。

::::details NID が変わったときの不具合

サーバの PCI の位置が変わると、IP アドレスが同じでも EFA の NID は変わります。peer の NID が付け直されると、peer をまとめる検査にかかって I/O が止まる不具合が、公開チケットの [LU-20482](https://jira.whamcloud.com/browse/LU-20482) にあり、2026-10-26 の時点では Open でした。2.15.6-1fsx34 には、この検査を緩める patch が入っています。upstream の 6325870 には入っておらず、この記事の試験とは別の事象です。

::::

### 接続の確立

kefalnd は最初の送信のとき、相手の TCP の NID に LNet の ping を送って EFA の宛先を教わり、そのあと EFA の上で接続を作ります。EFA の宛先は、相手の EFA デバイスのアドレスである GID と、接続の管理に使う QP (送受信の窓口) の番号です。

![クライアントが PROBE_TCP の状態で 10.0.1.20@tcp へ LNet ping を送り、GID と CM QP を受け取って PROBE_EFA に進み、EFA で CONN_PROBE と PROBE_RESP を交わし、CONN_REQ と CONN_REQ_ACK で ESTABLISH から ACTIVE になり、最初の PUT を送る。kefalnd の接続は向きごとに 1 本で、OSS からクライアントへの接続は別に開かれる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/9c049a2f18444a/zenn/articles/9c049a2f18444a/connect.png)

自分から開く接続は、[PROBE_TCP、PROBE_EFA、ESTABLISH、ACTIVE](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd.h#L300) の順に進みます。試験の 1 回の記録では、最初の送信の要求から ACTIVE まで 3.0 ms でした。両側は epoch (NI を起動した時刻) も交換して、相手が起動し直したかを見分けます。この記録では、クライアントが開いた接続とは別に、OSS が自分からクライアントへの接続を開きました。

TCP の ping が要るのは、対応がキャッシュに無い相手との接続を新しく作るときです。つまり、対応がキャッシュに無い相手との接続を新しく作るには、TCP と EFA の両方が動いている必要があります。キャッシュに古い対応が残った場合は試していません。

### データの運び方

kefalnd は、大きなデータを、受け手が送り手のメモリを RDMA READ で読む 1 通りで運びます。RDMA READ は、相手の CPU を使わずに相手のメモリを読む操作で、読まれる側が先にメモリを登録して、鍵とアドレスを読む側に渡します。EFA の通信方式 SRD は、NIC が失われたパケットを送り直し、ソフトウェアには、届いたか、失敗が通知されたかのどちらかが見えます。

![クライアントが読むとき、OSS が PUTR_REQ で自分のメモリのアドレスと鍵を渡し、クライアントが RDMA READ で約 1 MiB ずつ読み、PUTR_DONE を返す。クライアントが書くとき、OSS が GETR_REQ を送り、クライアントが GETR_ACK でアドレスと鍵を渡し、OSS が RDMA READ で読み、GETR_DONE を返す。試験の後のクライアントのカウンタは、rdma_read_bytes の増分が 80 GiB、rdma_read_wrs が 81,921、rdma_write_wrs が 0](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/9c049a2f18444a/zenn/articles/9c049a2f18444a/bulk.png)

[メッセージの種類](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd_proto.h#L194) には RDMA READ で運ぶ PUT と GET (名前は PUTR と GETR) しかなく、RDMA WRITE で運ぶものはありません。そのため、ファイルを読むときはクライアントが OSS のメモリを読み、書くときは OSS がクライアントのメモリを読みます。試験では 4 MiB の I/O で、書き込みと読み込みを 80 GiB ずつ流しました。クライアントの `rdma_read_bytes` はちょうど 80 GiB 増えました。別に取った累計では、`rdma_read_wrs` が 81,921 回で、バイト数との比は約 1 MiB です。4 MiB の I/O が約 1 MiB ずつの RDMA READ に分かれる理由は確かめていません。`rdma_write_wrs` は 0 でした。書き込みの向きで OSS がクライアントを読むことは、コードから読んだもので、クライアントのカウンタでは確かめていません。GPU のメモリでなく、ヘッダとデータの合計が [8,900 バイト以下](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd.c#L1088) のメッセージは、RDMA を使わず 1 回で送ります。

RDMA READ だけで運ぶので、bulk ごとに、メモリの登録と解除、鍵とアドレスの受け渡し、完了を照合する番号 (cookie) の突き合わせが要ります。TCP の ksocklnd はソケットにバイト列を流すだけなので、EFA の経路は管理する状態が多く、相手と食い違う箇所も多くなります。

::::details kefalnd の最近の修正

2.15.6-1fsx35 (2026-09-10) と fsx36 (2026-10-19) に入った kefalnd の修正の多くは、この状態の管理に関するものです。[LU-20191](https://jira.whamcloud.com/browse/LU-20191) は接続の後始末を分け、[LU-20496](https://jira.whamcloud.com/browse/LU-20496) は使われていない接続だけを壊すようにし、[LU-20497](https://jira.whamcloud.com/browse/LU-20497) は古い受信の完了と応答の cookie を扱い、[LU-20655](https://jira.whamcloud.com/browse/LU-20655) は起動の失敗時の参照カウントを直し、[LU-20790](https://jira.whamcloud.com/browse/LU-20790) と [LU-20791](https://jira.whamcloud.com/browse/LU-20791) は受信バッファの漏れと接続の参照カウントを直しています。

## 失敗の伝わり方

kefalnd が失敗を LNet に返すと LNet は health を下げますが、返らない失敗があり、それが EFA から TCP へ移らない原因になり得ます。

![kefalnd が LNet に返す 4 つの状態は、いずれも health を下げる。受け手の検査で捨てられたメッセージ、200 秒以内に使われた接続で止まった送信、LNet が受信の入口で捨てたメッセージは、何も報告されず health は動かない](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/9c049a2f18444a/zenn/articles/9c049a2f18444a/failure-paths.png)

kefalnd は失敗の種類ごとに、health の何を下げるかを決めた状態を付けて LNet に返し、LNet は [lnet_health_check](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/lnet/lib-msg.c#L961) でその状態を見て、自分の NI (自分の側のネットワークの口) や相手の NI (相手が持つ NID) の health を下げ、場合によっては再送します。図の上の 4 行がこれです。LNet のメッセージを載せていない probe や接続要求の失敗は、この経路を通りません。

相手が NID を 1 つしか持たない peer では、ルータを使わない限り、相手の NI の health は更新されません。

返らない失敗は 2 種類あります。1 つは、受け手の検査に落ちたメッセージです。kefalnd は何も付けずに [捨て](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd.c#L1766)、送り手には何も返しません。宛先の epoch が違うメッセージもここで捨てられ、SRD の層では届いているので、送った側の送信は成功として完了し得ます。

もう 1 つは、止まった送信です。送信の期限は lnd_timeout (試験では 16 秒) で、これを調べる [kefalnd_drain_ni_conns](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd_connection.c#L1281) は、接続を管理するスレッドが後始末を待つ一覧に移した接続しか見ません。一覧に移るのは、非活性化された接続か、[200 秒以上使われなかった接続](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd_connection.c#L1175) です。kefalnd は送るたびに接続の最後に使った時刻を更新するので、200 秒より短い間隔で送り続ける接続では、止まった送信が期限にかかりません。TCP の ksocklnd と InfiniBand の o2iblnd は、接続の使われ方に関係なく、送信ごとの期限を調べます。これはコードを読んだ結果で、止まった送信が期限にかからなかったことは試験では観測していません。この記事の故障注入は、kefalnd の下ではなく LNet の受信の入口で捨てるもので、図の最後の行です。

::::details 送信の期限と 200 秒の根拠

peer_timeout の下限は定数 [EFALND_MIN_INIT_CONN_TIMEOUT](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd.h#L86) の 200 秒です。試験のクライアントでも、kefalnd のモジュールのパラメータの peer_timeout の 180 秒が 200 秒に引き上げられ、dmesg に `Added LNI 2.30.0.248@efa [32/8192/0/200]` と出ていました。角括弧の値は、順に peer の送信の枠、NI 全体の送信の枠、ルータ用の枠、peer_timeout です。相手から開かれた接続には、さらに [300 秒](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd_connection.c#L20) が足されます。

ksocklnd の [ksocknal_check_peer_timeouts](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/socklnd/socklnd_cb.c#L2399) と o2iblnd の [kiblnd_check_txs_locked](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/o2iblnd/o2iblnd_cb.c#L3731) が送信ごとの期限を調べる箇所です。試験でも、EFA でマウントした直後の dmesg に、ksocklnd が期限を過ぎた送信を見つけたことを示す `Total 1 stale ZC_REQs for peer_ni 10.0.1.20@tcp detected; the oldest(...) timed out 3 secs ago` が出ていました。この 1 件がどの送信かは追っていません。fsx31 の kefalnd でも、送信の期限を調べる対象は後始末の対象の接続だけで、同じ作りです。

::::

## LNet が EFA と TCP のどちらを選ぶか

LNet は送るたびに、health と優先度を決まった順で比べ、最初に差が出たところで経路を決めます。

![試験の構成では、相手のネットワークの health、相手の優先度、自分のネットワークの health は EFA と TCP で同じで、自分のネットワークの優先度で、UDSP が 0 を付けた EFA が選ばれる。EFA が選ばれ続け得る理由は 3 つある](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/9c049a2f18444a/zenn/articles/9c049a2f18444a/path-select.png)

比べる関数は [lnet_find_best_ni_on_local_net](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/lnet/lib-move.c#L2314) で、OSS あてのふつうの送信では、[次の順](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/lnet/lib-move.c#L2388) に比べます。discovery (相手の NID の一覧を問い合わせる仕組み) やルーティングには、別の選び方があります。

1. 相手のネットワークの health
2. 相手のネットワークの優先度
3. 自分のネットワークの health
4. 自分のネットワークの優先度

UDSP は、どのネットワークを優先するかを利用者が決める規則で、数値が小さいほど優先されます。AWS の EFA の設定スクリプトは EFA に優先度 0 を付け、試験の [lnetctl](https://doc.lustre.org/lustre_manual.xhtml) の `udsp show` も `src: efa`、`priority: 0` でした。health がどれも 1000 のあいだは、1 から 3 で差がつかず、4 で EFA が選ばれます。帯域の測定を終えた時点で、OSS の TCP の NID への送信は 21 件だけでした。ログには、discovery と、kefalnd の ping が出ていますが、21 件の内訳は記録していません。

TCP が選ばれるのは、1 から 3 の比較で、efa の health が tcp より下がったときです。相手の NI の health は、失敗が相手のせいとされると health_sensitivity (既定 100) だけ下がり、その相手から次に受信したときに同じだけ戻ります。EFA が選ばれ続け得る理由は、図の右の 3 つです。

A は、前の節の失敗が health に届かないことです。

B は、相手が EFA の NID を複数持つ場合です。1 つでも 1000 なら、相手の efa のネットワークの health は 1000 のままです。試験の OSS の EFA の NID は 1 つでした。

C は、health が戻ることです。health の下がった NI には、LNet が定期的に ping を送り、応答が返ると health を戻します。この仕組みを recovery と呼びます。ping の受け口のバッファが 8,900 バイト以下なら RDMA READ を通らないので、RDMA の経路だけが壊れていれば、ping の成功で health が戻り、次の bulk がまた EFA に流れることがあり得ます。コードから考えた可能性で、試験での大きさと動きは確かめていません。

ptlrpc の接続先の NID は TCP のもので、試験でも `lctl get_param osc.*.ost_conn_uuid` は `10.0.1.20@tcp` でした。張り直しても、実際の経路は LNet が同じ peer の中から選び直します。

AWS の [re:Post の記事](https://repost.aws/articles/ARbKKMiQVXQbW-7DUCQTEjqQ/troubleshooting-fsx-for-lustre-how-to-perform-efa-to-tcp-failover-for-kefalnd-abort-tx-failures) は、自動で TCP に切り替わらない理由を 4 つ挙げ、設計どおりの動きで、手動の切り替えが要るとしています。UDSP が EFA を優先度 0 に固定すること、kefalnd が失敗を health に報告しないこと、接続した後の ping が EFA だけを通ること、サーバの evict の 227 秒が切り替えより短いことです。このうち health の扱いは、この記事で読んだコードと一部が食い違います。LNet は health を優先度より先に比べ、kefalnd は LNet のメッセージを載せた送信の失敗を health に返します。re:Post の例では外向きの送信がすべて失敗する状態で、health が 1000 のままだったのは、接続を作る段階の送信が LNet のメッセージを載せていないことと矛盾しません。食い違いがどの条件とバージョンによるかは、確かめていません。

そこで、クライアントの LNet の受信の入口で、`@efa` から届くメッセージをすべて捨てる規則を入れ、256 MiB を O_DIRECT で書きました。規則は LND を通った後の [lnet_parse](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/lnet/lib-move.c#L4752) で効き、TCP の側には何もしていません。EFA の送受信の経路そのものを断つ試験ではなく、re:Post の事例の再現でもありません。標準の故障注入のうち health のエラーを注入する `-e` は、kefalnd が呼び出しを持たないので効かず、2 GiB を書いても規則に当たったメッセージは 0 件でした。

## TCP と EFA の実測

同じクライアントから TCP と EFA で測ると、TCP は 1 組のクライアントと OSS の上限で頭打ちになりました。TCP に固定したときに失うものを見るために、[fio](https://fio.readthedocs.io/) の 4 MiB の direct I/O で、c7gn.16xlarge 1 台から、OST が 1 つの PERSISTENT_2 SSD (4,800 GiB、1000 MB/s/TiB) を、TCP だけと EFA で 1 回ずつ測りました。1 本のファイルは 16 GiB、16 本のファイルはそれぞれ 4 GiB で、各読み込みの前にページキャッシュを捨てています。fio の `bw` は KiB/s なので、10 進の MB/s に直して示します。

![OST が 1 つの試験のファイルシステムで、同じ c7gn.16xlarge から測ると、TCP は 1 本と 16 本のファイルの読み書きのどれも 620 MB/s で、1 組のクライアントと OSS あたり 5 Gbps (625 MB/s) の線のすぐ下に並ぶ。EFA は 1 本の書き込み 5,576、1 本の読み込み 8,115、16 本の書き込み 4,772、16 本の読み込み 7,238 MB/s で、スループットキャパシティ 4,688 MB/s の線を超える](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/9c049a2f18444a/zenn/articles/9c049a2f18444a/tcp-vs-efa.png)

TCP は、ファイルの本数も読み書きの向きも関係なく、すべて 620.3〜620.4 MB/s (4.96 Gbps) でした。AWS の [性能の説明](https://docs.aws.amazon.com/fsx/latest/LustreGuide/performance.html#throughput-clients) は、クライアント 1 台と 1 つの OSS の間の通信を 5 Gbps (625 MB/s) に制限するとし、この注記は、EFA を有効にしていないファイルシステムと、EFA 有効のファイルシステムに ENA で接続する場合に付いています。測った値はその 99.2〜99.3 % です。OST が 1 つなので、すべての I/O が 1 つの OSS に集まりました。この上限が何で決まっているかは文書になく、ksocklnd の接続の数の設定で変わるかも試していません。ファイルシステムのスループットキャパシティは次の値で、TCP はその 13.2 % でした。

$$
\frac{4800\ \mathrm{GiB}}{1024\ \mathrm{GiB/TiB}} \times 1000\ \mathrm{MB/s/TiB} = 4687.5\ \mathrm{MB/s}
$$

EFA は、1 本のファイルの書き込みが 5,576 MB/s、読み込みが 8,115 MB/s で、TCP のそれぞれ 9.0 倍と 13.1 倍でした。16 本のファイルでは、書き込みが 4,772 MB/s、読み込みが 7,238 MB/s で、7.7 倍と 11.7 倍でした。4 つともスループットキャパシティを超えていて、理由はクライアント側の情報からは分かりません。16 本の書き込みが 1 本より低い理由も見ていません。読み込みは書いた直後に読んだので、OSS の側のキャッシュが効いた可能性があります。EFA の測定の直後に、`local_error_count` と SRD の再送のタイムアウトが累計で 1 件ずつありましたが、起きた時刻と帯域への影響は確かめていません。

4 KiB のレイテンシーは、キューの深さ 1 の同期 I/O で 20 秒ずつ測りました。書き込みの行は fsync を挟む実行の中の書き込みで、fsync の時間は含みません。

| 測定 (クライアント 1 台、OST 1 つ) | TCP の中央値 / p99 | EFA の中央値 / p99 | TCP / EFA (中央値) |
|---|---|---|---|
| 4 KiB の書き込み | 700 / 741 µs | 537 / 659 µs | 1.31 |
| fsync | 9,241 / 10,420 µs | 8,847 / 10,420 µs | 1.04 |
| 4 KiB の読み込み | 635 / 700 µs | 473 / 586 µs | 1.34 |

中央値の差は、書き込みで約 164 µs、読み込みで約 162 µs です。fsync はどちらも約 9 ms で、内訳は測っていません。多数のクライアントが同時に小さな I/O を出す条件は測っていません。

```bash
echo 3 > /proc/sys/vm/drop_caches

```

## メタデータの通信

EFA 有効のファイルシステムでも、メタデータの通信は常に TCP を通ります。AWS の [文書](https://docs.aws.amazon.com/fsx/latest/LustreGuide/efa-file-systems.html#efa-considerations) がそう書いていて、試験とも合っています。クライアントの `lnetctl peer show` で見ると、OSS の peer には `10.0.1.20@tcp` と `1.20.0.248@efa` の 2 つの NID が見え、MGS と MDS の peer には `10.0.1.40@tcp` だけが見えました。マウント時のログに `Peer 10.0.1.40@tcp has discovery disabled` と出ていて、サーバの側で discovery が無効なので、クライアントは MDS のほかの NID を知りません。

![クライアントから見ると、MGS と MDS の peer には TCP の NID の 10.0.1.40@tcp だけが見え、OSS の peer には 10.0.1.20@tcp と 1.20.0.248@efa の 2 つが見えた。MDS あての open や名前、レイアウトの問い合わせは TCP を通り、OSS あての読み書きの RPC と bulk は、送信数から見て試験では EFA を通った。試験のファイルシステムは MDT 1 つ、OST 1 つ](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/9c049a2f18444a/zenn/articles/9c049a2f18444a/metadata-nids.png)

そのため、小さなファイルを大量に作ったり開いたりする処理は、EFA を有効にしても TCP の経路を通り、1 秒に処理できる数はメタデータ IOPS に左右されます。メタデータ IOPS は、AWS の [性能の説明](https://docs.aws.amazon.com/fsx/latest/LustreGuide/performance.html#dne-metadata-performance) によると、1 IOPS あたり、1 秒にできる操作が、ファイルの作成と open と close で 2、ファイルの削除で 1、ディレクトリの作成と名前の変更で 0.1、ディレクトリの削除で 0.2 です。自動のモードでは、SSD は容量から、Intelligent-Tiering はスループットから決まり、試験の 4,800 GiB の SSD は 6,000 IOPS でした。

2026-11-05 の [発表](https://aws.amazon.com/jp/about-aws/whats-new/2026/11/amazon-fsx-for-lustre-intelligent-tiering-16x-higher-metadata-iops/) で、Intelligent-Tiering のメタデータ IOPS の上限が 12,000 から 192,000 に上がり、SSD と同じになりました。ファイルの作成は 1 IOPS あたり 2 回なので、計算の上では 192,000 IOPS で 1 秒に 38.4 万回です。これは試験の後の発表で、この記事の MDT 1 つの試験には含まれません。

![メタデータ IOPS を 12,000 より増やすと (図の /data と /ckpt は例)、MDS 0 のほかにメタデータサーバが足される。前からある /data や /ckpt は MDS 0 に残り、IOPS は増えない。増やした後に作られるメタデータは、MDS 0 を含む全部のサーバに分けられる。増やすことしかできず、増やす間隔は 6 時間以上で、増やしている間は数分使えないことがある](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/9c049a2f18444a/zenn/articles/9c049a2f18444a/metadata-scaling.png)

[メタデータの性能の管理の文書](https://docs.aws.amazon.com/fsx/latest/LustreGuide/managing-metadata-performance.html) によると、12,000 を超えて増やすと、FSx はメタデータサーバを足し、その後に作られるメタデータを全部のサーバに分けます。増やす前からあるメタデータとサブディレクトリは元のサーバに残り、IOPS は増えません。前からあるディレクトリの中に新しく作るファイルがどこに置かれるかは、文書に書かれていません。増やせるのは Lustre 2.15 の Persistent 2 で、作成時にメタデータの設定を指定したものだけです。増やすことしかできず、間隔は 6 時間以上で、増やしている間は数分使えないことがあり、その間のクライアントの操作は自動で再試行されます。2026-11-05 より前に作った Intelligent-Tiering のファイルシステムは、自分で指定するモードだけで、6,000 か 12,000 しか選べません。課金は、SSD では自動のモードの分を超えた分だけ、Intelligent-Tiering では自動のモードの分を含めた全部です。サーバを何台足すかは、文書に書かれていません。

## 学習の規模から見た必要帯域

TCP で足りるかは、ノード 1 台が必要とする帯域を、1 組のクライアントと OSS の上限で割った OSS の数で決まります。AWS の性能の説明では、クライアント 1 台の上限は、ENA で 100 Gbps (12.5 GB/s)、EFA で 700 Gbps、EFA と GDS で 1,200 Gbps で、クライアント 1 台と 1 つの OSS の間は、ENA では 5 Gbps (625 MB/s) です。

同期のチェックポイントで、ノード 1 台が必要とする帯域と OSS の数は、次の式で見積もれます。$P$ はパラメータ数、$b$ は 1 パラメータあたりのバイト数、$N$ はノード数、$T$ は保存のために止めてよい秒数です。

$$
B_\text{node} = \frac{P \times b}{N \times T}, \qquad n_\text{OSS} \ge \frac{B_\text{node}}{625\ \mathrm{MB/s}}
$$

例として、「[post-training 時代の LLM 学習の規模と効率の整理](https://zenn.dev/tosshi/articles/99375dd5ac013f)」の計画を使います。Olmo 3 の 32B を p6-b200.48xlarge の 10 台、B200 の 80 枚で 1 年かけて学習する計画で、事前学習は 5.5T トークン、約 55.3 万 B200 GPU 時間、FSx for Lustre は約 82 TiB を 250 MB/s/TiB で確保します。ファイルシステム全体の帯域は $82 \times 250 = 20{,}500$ MB/s です。次の表は、この計画の台数と容量に、この記事が置いた仮定を組み合わせた計算で、実測ではありません。トークンは 4 バイトの ID を 1 回だけ読み、チェックポイントは bf16 の重み、fp32 の master の重み、Adam の 2 つの状態で 1 パラメータあたり 14 バイト、30 分ごとに保存して同期の保存で止める時間は 1 % の 18 秒に収め、再開では各ノードが自分の分だけ読み、RL では 10 台が同時に bf16 の重みを読みます。10 台は負荷を均等に分け、他の I/O は無く、ファイルシステムはスループットキャパシティを出し続けるとします。

| # | 何を運ぶか | 計算 | ノード 1 台あたり |
|---|---|---|---|
| 1 | 事前学習のトークンを読む | 55.3 万 GPU 時間 ÷ 80 枚 = 6,912.5 時間で $5.5 \times 10^{12}$ トークンを読むと約 $2.21 \times 10^5$ トークン/秒。10 台で分け、4 バイトを掛ける | 約 88 KB/s |
| 2 | 同期のチェックポイントを保存する | $32 \times 10^9 \times 14 = 448$ GB を 18 秒で書くと全体で約 24.9 GB/s。10 台で分ける | 約 2.49 GB/s |
| 3 | 非同期のチェックポイントを保存する | 448 GB を次の保存までの 30 分で書く | 平均で約 25 MB/s |
| 4 | 障害の後に再開する | 各ノードが 44.8 GB、全体で 448 GB を 20.5 GB/s で読むと 21.9 秒 | 約 2.05 GB/s |
| 5 | RL の推論ノードへ重みを配る | bf16 の 64 GB ($32 \times 10^9 \times 2$) を 10 台が読み、640 GB を 20.5 GB/s で読むと 31.2 秒 | 約 2.05 GB/s |

![仮定から計算した、ノード 1 台が必要とする帯域は、同期のチェックポイントの保存が 2.49 GB/s で OSS が 5 つ、再開の読み込みと RL の重みの読み込みが 2.05 GB/s で OSS が 4 つ。1 組のクライアントと OSS の上限は測った値で 0.62 GB/s](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/9c049a2f18444a/zenn/articles/9c049a2f18444a/scale.png)

行 1 と 3 は、1 組の上限 625 MB/s よりずっと小さな値です。行 2、4、5 は 2 GB/s 前後で、試験の約 620 MB/s が各 OSS で同時に出るなら、そのノードのファイルが、行 2 では 5 つ以上、行 4 と 5 では 4 つ以上の OSS に均等に散っている必要があります。公称の 625 MB/s なら行 2 は 4 つで足りますが、余裕は約 0.4 % です。上限は OST ではなく OSS の単位で、1 つの OSS が複数の OST を持つこともあります。ファイルの散り方は、`lctl get_param osc.*.ost_conn_uuid` と `lfs getstripe` で見え、OSS の数は、性能の文書が案内する IP アドレスの情報で確かめてください。複数の OSS で、帯域が OSS の数に比例して伸びるかは測っていません。

行 2 は、全体で約 24.9 GB/s が要るので、スループットキャパシティの 20.5 GB/s では転送だけで約 21.9 秒かかり、18 秒の目標に届きません。この試算では、TCP か EFA かより先に、ファイルシステム全体の帯域が同期の保存の時間を決めます。試験では EFA がスループットキャパシティを超えたので、18 秒に届かないとまでは言えません。評価、ログ、データの前処理、画像や動画の入力、複数のジョブの同時実行は、この表に入っていません。

学習データの読み込みは DataLoader が先読みするので、約 160 µs のレイテンシーの差がステップの時間に出るとは考えにくいですが、測っていません。GDS で GPU のメモリと直接運ぶ I/O には、TCP は使えません。LNet は送るページが GPU のメモリかを [lnet_is_rdma_only_page](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/lnet/lnet_rdma.c#L264) で調べ、GPU のメモリなら kefalnd は、長さが 0 のものを除き、小さなメッセージでも RDMA で運びます。ノード 1 台で数十 GB/s を必要とする設計なら、ファイルシステムも 20.5 GB/s より大きな帯域で確保してください。

## TCP に固定してよいかの判断

TCP に固定してよいかは、次の 5 点で決まります。

1. GDS で GPU のメモリと直接運ぶ I/O を使わないことです。
2. EFA 有効のファイルシステムに ENA で接続するなら、ノード 1 台が必要とする帯域が、ファイルの散り方を含めて、1 組あたり 625 MB/s の上限に収まることです。ENA Express の接続の上限は確かめていません。
3. 小さな I/O のレイテンシーの差が学習に効かないことです。試験のキューの深さ 1 の 4 KiB では、中央値で 1.3 倍、約 160 µs の差でした。
4. 固定の作業のために、クライアントのマウントを外せることです。
5. 再起動の後も固定が続くことです。

次の表は、EFA (kefalnd) と TCP (ksocklnd) を比べたものです。試験の値は、クライアント 1 台、OST 1 つ、試験の I/O 以外の負荷なしの条件です。

| 観点 | EFA (kefalnd) | TCP (ksocklnd) |
|---|---|---|
| クライアント 1 台の上限 | 700 Gbps、GDS では 1,200 Gbps | 100 Gbps |
| クライアント 1 台と OSS 1 つの間 | 文書に上限の記載なし。試験では 4,772〜8,115 MB/s | EFA 無効と、EFA 有効への ENA の接続では 5 Gbps (625 MB/s)。ENA Express の接続は記載なし。試験の ENA では約 620 MB/s |
| 4 KiB の読み込みのレイテンシー (中央値) | 473 µs | 635 µs |
| 接続の作り方 | 試験の small NID では、対応がキャッシュに無いとき TCP の ping で GID を取り、EFA の上で probe と接続要求を交わす | TCP の接続を張る |
| データの運び方 | 受け手が RDMA READ で読む。GPU のメモリでなく 8,900 バイト以下なら RDMA を使わない | ソケットにバイト列を流す |
| 止まった送信の期限 | 後始末を待つ接続の、未完了の送信だけを調べる | peer ごとに送信の期限を定期的に調べる |
| クライアントの LNet で EFA の受信を捨てた試験 | health は 1000 のまま、張り直しでも EFA が選ばれ、約 890 秒 I/O が止まった | 同じ形の故障は試していない |
| GDS | 使える | 使えない |
| メタデータの通信 | TCP | TCP |

固定できたことは、`lctl list_nids` に `@efa` が出ないことと、`lnetctl peer show -v` で OSS の `@tcp` の NID の送信数が読み書きに応じて増えることで確かめられます。この記事の TCP の測定は、アンマウント、`lustre_rmmod`、tcp の NI だけで `lnetctl net add`、マウントの順の手順から始めました。EFA で動いていたクライアントを、この手順で TCP に戻す操作としては試していません。実際に使うなら、アンマウントやモジュールの停止に失敗したところで止め、再マウントの後に `lctl list_nids` と `lnetctl net show` に efa の NI が無いことと、読み書きが進むことを確かめてください。AWS の [設定の説明](https://docs.aws.amazon.com/fsx/latest/LustreGuide/configure-efa-clients.html) によると、`setup.sh` は起動のたびに EFA を設定する systemd のサービスを作ります。この記事の試験は `--configure-once` でサービスを作らずに流したので、再起動の後に固定が残るかは確かめていません。サービスの有無と状態を確かめ、起動のときに EFA が設定し直されないようにしてください。

## 止まったときの確認と対処

I/O が止まったことは health では分からないので、import の状態と、I/O が進んでいるかを見ます。次の表は、この記事の試験で見えたことを並べたもので、どれもクライアント 1 台、OST 1 つ、この記事の故障の形での結果です。

| 段階 | 見るもの、すること | この記事での確認 |
|---|---|---|
| 気づく | import の `state_history` が DISCONN と CONNECTING を繰り返す。dmesg に `Request sent has timed out for slow reply` と `Connection to ... was lost` が出る。読み書きが進まない | 試験で確認した |
| それだけでは止まっていないと言えないもの | `lnetctl peer show -v` の health。この試験では止まっている間も 1000 のままだった | この故障注入で確認した |
| 実際に通っている経路 | `lnetctl peer show -v` の、OSS の NID ごとの送信数の増え方 | 帯域の測定の後に 1 回だけ確認した |
| 止まったプロセス | timeout の SIGTERM の後と考えられる時刻にも戻らなかった。`ps` の状態は D ではなく I だった | SIGKILL は試していない |
| TCP に逃がす | マウントしたままの `lnetctl net del --net efa` (`--if` なし) では NI が残った。re:Post の手順と、止まった状態からのアンマウントは試していない | 一部だけ確認した |
| 試していない戻し方 | ノードの再起動。再起動の後に EFA が設定し直されることがあるので、AWS の設定スクリプトが作るサービスの有無と状態を確かめ、再起動の後に NI を見る | 試していない |

health を見ても止まったことは分からなかったので、I/O が進んでいるかと import の状態を、監視の処理そのものが止まらない形で見ることになります。止まった状態から戻す手順は、ノードの再起動を含めて、あらかじめ自分の環境で確かめてください。

## まとめ

EFA の経路が使えなくなったとき、LNet は health を優先度より先に比べますが、クライアントの LNet で EFA の受信を捨てた試験では、health は 1000 のまま EFA が選ばれ続け、規則を入れていた約 890 秒のあいだ I/O が止まりました。自動で TCP に移ることを前提にしないでください。TCP に固定すると、EFA 有効のファイルシステムに ENA で接続する場合、試験では、クライアント 1 台と OSS 1 つの間が約 620 MB/s で頭打ちになり、4 KiB のレイテンシーは EFA の約 1.3 倍でした。この記事の仮定の 80 枚の B200 の規模の学習では、GDS を使わず、ファイルが 5 つ以上の OSS に均等に散っていれば、1 台あたりの必要帯域は計算の上では TCP の上限に収まります。ただし同期のチェックポイントの時間は、ファイルシステム全体の帯域が先に決め、複数の OSS での帯域は測っていません。メタデータの通信は常に TCP で、その性能はメタデータ IOPS で決まり、Intelligent-Tiering でも 192,000 まで増やせるようになりました。
