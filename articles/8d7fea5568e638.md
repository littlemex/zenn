# はじめに

NVIDIA が公開した [NCCL Roadmap: Aug-Oct 2026 (GitHub Issue #2272)](https://github.com/NVIDIA/nccl/issues/2272) から、大規模分散学習・推論に携わるエンジニアが押さえるべきポイントを3カテゴリに絞って解説します。

## GIN (GPU-Initiated Networking) とは何か

### 概要

GIN は NCCL 2.28 (2025年10月) で Device API の一部として導入された通信モードの一つで、GPU カーネル内からネットワーク RDMA 操作を直接発行する仕組みです。従来の NCCL は「CPU がすべての通信をオーケストレーションする (host-initiated)」モデルでしたが、GIN はこの CPU 介在を排除し、GPU スレッドが `put` / `get` / `signal` / `flush` といった one-sided RDMA 操作をカーネルコードから直接呼び出せるようにしました。

技術的詳細は arXiv 論文 [GPU-Initiated Networking for NCCL (arXiv:2511.15076)](https://arxiv.org/abs/2511.15076) に記載されています。

https://zenn.dev/tosshi/articles/42f0ee03b328a4

### なぜ重要か

GIN が解決する問題は明確で、以下の3点に集約されます。

- MoE (Mixture-of-Experts) の動的トークンルーティングのように、計算と通信が密結合し不定形の通信パターンが発生するワークロードで、CPU プロキシのオーバーヘッドがボトルネックになります
- 小メッセージ (4-128 バイト) のレイテンシを大幅に削減します: arXiv:2511.15076 の実測では GDAKI が往復 16.7us、Proxy が 18.0us を達成しています (比較対象: NVSHMEM IBRC 16.0us、NVSHMEM IBGDA 24.3us)
- SM 占有を削減し、モデル計算に GPU リソースを還元できます

https://zenn.dev/tosshi/articles/228e4225b659f7

### アーキテクチャ: 3層構造

GIN は以下の3層で構成されます。

```
[CUDA Kernel]                    <- Device GIN API (put/get/signal/flush/wait)
      |
[GIN Backend]                    <- GDAKI (GPU->NIC 直接) or Proxy (GPU->CPU->NIC)
      |
[Network: IB/RoCE/EFA]
```

各層の役割は以下の通りです。

1. **Device GIN API**: `ncclGin` クラスが提供する CUDA デバイス関数群です。Signal (リモート通知) と Counter (ローカル完了追跡) で非同期完了を管理します
2. **GDAKI バックエンド**: GPU スレッドが RDMA WQE (Work Queue Entry) を直接構築し、NIC の doorbell レジスタに書き込みます。CPU 介在ゼロで、ConnectX-6 Dx 以降が必要です
3. **Proxy バックエンド**: GPU スレッドが 64 バイトの descriptor (宛先ハンドル、オフセット、サイズ、完了アクション等を含む) をロックフリーキューに書き込み、CPU 側の proxy スレッドがポーリングして IB verbs を発行します

### NCCL 2.31 での GIN 進化

| 機能 | 説明 |
|------|------|
| Simultaneous GIN proxy and GDAKI | 異なる communicator で Proxy と GDAKI を同時使用可能になります。ワークロード特性に応じた最適バックエンド選択が可能です |
| EFA GDA support in GIN | AWS EFA 上で GPU-initiated 通信を実現する新バックエンドです (後述) |
| GIN over Sockets | IB/RoCE 不要で TCP 経由の GIN 動作です。開発やテスト環境向けに提供されます |

## AWS EFA 関連アップデートと現在の課題

### EFA + NCCL 統合の現状

AWS EFA (Elastic Fabric Adapter) は `aws-ofi-nccl` プラグイン経由で NCCL と統合されています。libfabric の Reliable Datagram エンドポイントにマッピングし、SRD (Scalable Reliable Datagram) プロトコルで通信します。

### NCCL 2.31 の目玉: EFA GDA support in GIN

GIN に `NCCL_GIN_TYPE_EFA_GDA` という EFA 専用バックエンドが追加されます。GPU カーネルが CPU プロキシを介さず EFA 経由で直接 Put/Signal/Flush を発行可能になります。内部実装は `efa-dp-direct` ライブラリを NCCL に統合したもので、NVIDIA/nccl の PR #2273 系列で実装が入っています。

有効化条件は libfabric 2.5 以上、DMA-BUF が利用可能、EFA プロバイダ (efa/efa-direct) であることです (aws-ofi-nccl の `nccl_ofi_gin_gdaki_capable()` 実装)。実績があるのは P5en / P6-B200 / P6-B300 ですが、公式ドキュメントでのインスタンスタイプ限定の明記はまだありません。

### 現在の課題

EFA + GIN の組み合わせにはまだ解決途上の課題が複数存在します。

| 課題 | 詳細 | 出典 |
|------|------|------|
| Signal coalescing と SRD 順序保証の衝突 | GIN proxy 経路で signal coalescing 導入後、受信側で barrier タイムアウトが発生します。SRD の非順序配送が coalesced-doorbell の前提と衝突しています | [aws-ofi-nccl #1327](https://github.com/aws/aws-ofi-nccl/issues/1327) |
| GDR の PCIe 距離判定 | `ncclTopoCheckGdr()` が PCIe トポロジ距離で GDR 有効/無効を判定します。`NCCL_NET_GDR_LEVEL` の不適切な設定で意図しない無効化が発生しえます | NCCL `src/graph/paths.cc` |
| マルチレール対応の成熟度 | P5en の GPU あたり2レール構成向けに `rail = contextId % num_rails` で振り分けるロジックが入ったばかりです | [aws-ofi-nccl PR #1292](https://github.com/aws/aws-ofi-nccl/pull/1292) |
| GDAKI doorbell 競合条件 | 並行 post で submitted_count がキャッシュされハングする問題がありました。atomic load への修正で対処済みです | [NVIDIA/nccl PR #2314](https://github.com/NVIDIA/nccl/pull/2314) |

## 注目機能3選

### Cost-model rearchitecture: 「どのアルゴリズムが最速か」の予測を再設計する

NCCL は集合通信を実行する際、複数のアルゴリズム (Ring: GPU を輪っか状に接続 / Tree: ツリー構造で集約 / NVLS: NVLink ハードウェア支援) とプロトコル (Simple: 帯域重視 / LL: 低レイテンシ / LL128: LL の拡張) を持っています。通信のたびに「今のデータサイズ・GPU 数・ネットワーク構成ならどの組み合わせが最速か」を予測して自動選択する仕組みが cost-model です。

現在の cost-model は `所要時間 = レイテンシ + データサイズ / 帯域幅` をベースに、GPU 世代ごとの補正定数をハードコードしています。しかし新しい GPU (Blackwell 世代) ではこの補正が追いついていません。

具体例として [Issue #2305](https://github.com/NVIDIA/nccl/issues/2305) があります。Blackwell での ReduceScatter (全 GPU からデータを集めて分割する操作) で、NCCL が自動選択した構成は 33.12us かかりましたが、GPU のスレッドブロック (CTA) をもっと多く割り当てる構成に強制変更すると 13.84us で完了しました。2.4倍の差です。修正 PR ([#2307](https://github.com/NVIDIA/nccl/pull/2307)) は特定条件だけのピンポイント上書きで根本解決ではなく、GPU 世代が増えるたびにこうした個別対応を積む方式の限界を示しています。

NCCL 2.31 で cost-model の再設計に着手することがロードマップに明記されています。

### NCCL Notify + RAS diagnostics: 大規模クラスタの障害を自動検知・通知する

10000台以上の GPU を使う学習ジョブでハングが起きた場合、「どの GPU が止まっているか」の特定は極めて困難です。従来の `NCCL_DEBUG=INFO` は各プロセスのローカルログに過ぎず、クラスタ全体で「どのランク (= 各 GPU に割り当てられた番号) がどこで止まっているか」をグローバルに把握する仕組みではありません。

RAS (Reliability, Availability, Serviceability) は NCCL 2.24 で導入され 2.28 で機能強化された分散型の健全性監視です。各プロセスに RAS スレッドが立ち、互いに TCP で「応答があるか」「集合操作の回数がずれていないか」を監視し、`ncclras` コマンドで状態を問い合わせられます。しかし以下の既知の限界があります。

- 256 GPU 構成で PyTorch がタイムアウトを報告しても RAS は「正常」と表示するケースがあります ([#1730](https://github.com/NVIDIA/nccl/issues/1730))
- 遅延しているランクではなく、先に進んでいるランクしか報告しないため原因側を特定しにくいです ([#1911](https://github.com/NVIDIA/nccl/issues/1911))

NCCL Notify は、RAS が検知した障害をアプリケーション側に構造化イベントとしてプッシュ通知する仕組みです。わざわざポーリングしなくても障害を即座に受け取れるため、自動リカバリ (チェックポイントからの再開など) をトリガーするワークフローが組みやすくなります。

### Custom kernel hook: 自作の通信アルゴリズムを NCCL に組み込む

現在の NCCL は内蔵アルゴリズム (Ring/Tree/NVLS 等) しか使えません。しかし MoE モデル向けに特化した通信ライブラリ (DeepEP: トークンルーティング特化、NCCL-EP: NVIDIA 公式の Expert Parallelism 向けプリミティブ集) が NCCL の外で開発されており、フレームワーク側で明示的に呼び分ける必要があります。

Custom kernel hook は、ユーザーが自作した通信カーネルを NCCL に「登録」し、cost-model が実行時にそれを選択候補として扱えるようにする仕組みです。「この条件ではこの自作カーネルの方が速い」と NCCL が判断すれば自動的にそちらを使ってくれるようになります。

Q2 2026 ロードマップ ([#2090](https://github.com/NVIDIA/nccl/issues/2090)) では「Custom comms ops hook」という名称で「検討中」だったものが、Aug-Oct 2026 で「Custom kernel hook」に改称され確定ロードマップに格上げされました。「NCCL を置き換える」のではなく「NCCL を拡張する」アプローチが正式にサポートされます。

## まとめ

NCCL 2.31 以降のロードマップは、3つの大きな方向性を示しています。

1. **GPU 主導通信の完成** (GIN + EFA GDA): CPU ボトルネックの完全排除です。特に MoE ワークロードで劇的な効果があります
2. **拡張性の確保** (Custom kernel hook + Cost-model 再設計): ハードウェア世代やワークロードの多様化に耐える設計です
3. **運用性の向上** (NCCL Notify + RAS): 万単位 GPU のクラスタ運用を現実的にする可観測性です

AWS EFA ユーザーにとっては、EFA GDA による GIN サポートが最大のマイルストーンですが、SRD プロトコルとの相互作用に起因する課題がまだ解決途上である点は注視が必要です。
