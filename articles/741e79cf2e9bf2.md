## はじめに

通信のライブラリ libfabric は、通信の方式をプロバイダという部品で切り替えます。AWS のネットワークカードである EFA を使うのが efa プロバイダで、同じノードの中で共有メモリを使うのが shm プロバイダです。efa プロバイダを使うと、相手が別のノードにいるときは EFA の装置を通ってデータが届きます。ところが、この記事で調べた libfabric 2.4.0 の efa プロバイダは、相手が同じノードにいるとき、既定の設定 (`FI_EFA_ENABLE_SHM_TRANSFER=1`) では EFA の装置を使わず、shm プロバイダにデータを任せます。shm プロバイダは、1 つの登録済みの GPU のバッファを送るときなど、条件がそろうと CUDA IPC (別のプロセスの GPU のメモリを、ホストのメモリを経由せずに直接コピーできるようにする CUDA の仕組み) を選び、受け取る側が送る側の GPU のメモリを開いてコピーします。CUDA IPC を選んだあとでその準備に失敗すると、SAR という、ホストの共有メモリを経由して小分けに運ぶ方法に切り替えます。この記事では、この同じノードの中の経路を図で追います。

![左は相手が別のノードにいる場合で、EFA の装置からネットワークを通って届く。右は相手が同じノードにいる場合で、efa プロバイダは既定では shm プロバイダに任せ、FI_EFA_ENABLE_SHM_TRANSFER=0 なら EFA の装置を使う](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/741e79cf2e9bf2/zenn/articles/741e79cf2e9bf2/overview.png)
*既定では、同じノードの相手へのデータは EFA の装置を通りません*

図の左は、相手が別のノードにいる場合です。データは送る側の EFA の装置からネットワークを通り、相手の EFA の装置へ届きます。図の右は、相手が同じノードにいる場合です。efa プロバイダは相手が同じノードにいると判断すると、既定の `FI_EFA_ENABLE_SHM_TRANSFER=1` では shm プロバイダにデータを任せます。`FI_EFA_ENABLE_SHM_TRANSFER=0` のときは、同じノードの相手にも EFA の装置を使います。測った構成では、この転送が装置の RDMA の書き込み (相手の CPU を介さずに相手のメモリへ直接書く方式) として出たことを、あとの節で確かめます。

ここから、この記事で使う 3 つの言葉を、図で 1 つずつ説明します。

![送る側のプロセスは、受け取る側がホストのメモリに作った領域を開き、そこにある命令の列に書く。受け取る側はその命令を読み、送る側の領域にある応答の列に結果を返す。受け取る側の領域には SAR の中継用の領域もある](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/741e79cf2e9bf2/zenn/articles/741e79cf2e9bf2/shm-term.png)
*shm プロバイダは、ホストのメモリの領域で命令と応答を受け渡します*

shm プロバイダでは、各プロセスがホストのメモリに[自分の領域を作ります](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_util.c#L191-L250)。送る側は、相手が作った領域を `shm_open` で開いて `mmap` で自分のアドレス空間に[対応付け](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_util.c#L346-L398)、その領域にある命令の列 (command queue) に命令を書きます。受け取る側は、自分の領域に書かれた命令を読んで処理し、処理が終わったことを、送る側の領域にある応答の列 (response queue) で返します。受け取る側の領域には、あとで見る SAR で使う中継用の領域も入っています。データの中身がどう運ばれるかは、次の CUDA IPC と SAR で違います。

![送る側は自分の GPU のバッファから IPC ハンドルを作り、shm の命令に入れて渡す。受け取る側はハンドルを開き、送る側の GPU のバッファから自分の GPU のバッファへ 1 回でコピーする](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/741e79cf2e9bf2/zenn/articles/741e79cf2e9bf2/cuda-ipc-term.png)
*CUDA IPC では、受け取る側が送る側の GPU のバッファから 1 回でコピーします*

CUDA IPC (Inter-Process Communication) は、別のプロセスの GPU のメモリを使えるようにする CUDA の仕組みです。送る側は、自分の GPU のバッファから IPC ハンドルという識別子を作り、shm の命令に入れて渡します。この記事で扱う、GPU のバッファへの送信では、受け取る側がそのハンドルを開き、送る側の GPU のバッファから自分の GPU のバッファへ、1 回でコピーします。コピーをするのは、受け取る側のプロセスです。ハンドルを作る前に、送る側は `cuMemGetAddressRange` でバッファの場所を調べます。この呼び出しは、送る側のスレッドで有効な CUDA のコンテキスト (GPU ごとに作られ、その GPU で確保したメモリを管理するもの) の中でアドレスを探すので、そのコンテキストの中でバッファが見つからないとハンドルを作れません。この記事で見る失敗は、ここで起きます。手順の細かいところは「CUDA IPC による受け渡し」の節で見ます。

![SAR では、送る側が自分の GPU のバッファから受け取る側の共有メモリにある 32 KiB の中継用の領域へコピーし、受け取る側がそこから自分の GPU のバッファへコピーする。中継用の領域を使い回して全部渡るまで繰り返す](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/741e79cf2e9bf2/zenn/articles/741e79cf2e9bf2/sar-term.png)
*SAR では、ホストの共有メモリを中継して、1 かたまりにつき 2 回コピーします*

SAR (segmentation and reassembly) は、shm がデータを中継用の領域で小分けに運ぶ方法です。データの大きさや指定によって[最初から選ばれる](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_ep.c#L553-L611)こともあり、CUDA IPC を選んだあとでその準備に失敗したときの切り替え先にもなります。この記事で問題になるのは、後者の切り替えです。SAR では、データを [32 KiB](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_util.h#L165) ずつのかたまりに分け、送る側が自分の GPU のバッファから、[受け取る側の共有メモリにある中継用の領域](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_ep.c#L505-L515)へコピーします。続いて受け取る側が、そこから自分の GPU のバッファへコピーします。中継用の領域は使い回し、データが全部渡るまでこれを繰り返します。CUDA IPC なら 1 回で済むコピーが、かたまりごとに 2 回になり、そのたびにホストのメモリを経由します。手順の細かいところは「SAR」の節で見ます。

同じノードの中のこの経路で、実際に何が起きていたのかを、次の節で問題として定めます。

## 調べたケース: 同じノード内の LIBFABRIC 転送


この記事では、SGLang で disaggregated inference (分離推論) をするときに、NIXL の LIBFABRIC バックエンドを使って、同じノードにいる相手へ KV cache を送るケースを調べました。SGLang の分離推論では、入力を読む prefill と、出力のトークンを 1 つずつ作る decode を、別々のプロセスに分けて動かし、prefill は計算の途中結果である KV cache を decode へ送ります。その転送を受け持つのが、推論のプロセスのあいだでデータを転送するライブラリ NIXL です。prefill と decode は別々のノードに置くのが基本の構成なので、同じノードに置くケースは、あまり想定されていないかもしれません。今回は、このケースで何が起きるかを確かめます。

:::message
SGLang の分離構成で NIXL の LIBFABRIC バックエンドを使い、prefill と decode が同じノードにあると、KV cache は EFA の装置ではなく libfabric の shm の経路を通ります。測った構成では、この経路の転送が、shm を切ったときより大幅に遅くなりました。この記事は、その経路で何が起きているかを追います。
:::

NIXL は、転送に使うバックエンドを選べます。この記事で扱うのは LIBFABRIC のバックエンドです。EFA のあるインスタンスで efa プロバイダを使うと、送り先が同じノードにあると、KV cache は上の shm の経路を通ります。NIXL には [UCX のバックエンド](https://github.com/ai-dynamo/nixl/tree/c0a1102b94d173049a5478c23e765ba37681e2ca/src/plugins/ucx)もあります。UCX は libfabric を使わず、同じノードの相手には、UCX 自身の経路 (cuda_ipc や共有メモリなど) から選んで使います。NIXL 単体で同じノードの 2 枚の GPU のあいだに送ったときは、UCX が自分の cuda_ipc の経路を選んだことを、`UCX_PROTO_INFO=y` のログで確かめました。そのため、この記事の話は、NIXL で LIBFABRIC のバックエンドを選んだときのものです。UCX のバックエンドで同じ食い違いが起きるかどうかは、この記事では調べていません。

測った構成で 1 秒に 1 件の負荷をかけると (NIXL 1.1.0、page size 1)、SGLang 自身が記録する KV の転送の段階の時間の平均は、shm を使う既定の設定で 1,776 ms、shm を使わない設定で 196 ms でした。条件のくわしいところは「3 つの構成の比較」の節で見ます。この記事が答える問いは、次の 2 つです。

- shm の経路のどこで、何が起きているのか
- NIXL 1.4.0 と shm を使わない設定は、それぞれ何を変えるのか

結論を先に書きます。測った構成の shm の経路では、送る側と受け取る側でそれぞれ 1 か所ずつ、CUDA の呼び出しをするスレッドが、データのある GPU とは別の GPU を相手にしていました (スレッドごとの current device の食い違い)。送る側の食い違いは CUDA IPC の準備を失敗させて SAR への切り替えを起こし、NIXL 1.4.0 では起きなくなります。受け取る側の食い違いは、NIXL 1.4.0 でも残ります。shm を使わない設定にすると shm の経路そのものを使わず、測った構成では同じノードの相手への書き込みも EFA の装置を通るので、2 つの食い違いのある経路をどちらも通りません。

| 層 | 受け持ち | この記事で見るところ |
|---|---|---|
| SGLang | KV cache を持ち、転送を頼む | 転送スレッドが GPU を選ばないこと |
| NIXL (LIBFABRIC バックエンド) | 転送を libfabric の呼び出しに変える | 送る前の CUDA のコンテキスト、progress thread |
| libfabric の efa | 相手が同じノードなら shm に任せる | shm を使う設定 |
| libfabric の shm | 共有メモリで渡す | CUDA IPC と SAR |

調べた版は [SGLang 0.5.12.post1](https://github.com/sgl-project/sglang/tree/5a15cde858ea09b77116212a39356f2fc51b8584)、NIXL [1.1.0](https://github.com/ai-dynamo/nixl/tree/05e4243f5ed305a245912361ace20ba354ec0808) と [1.4.0](https://github.com/ai-dynamo/nixl/commit/c0a1102b94d173049a5478c23e765ba37681e2ca)、[libfabric 2.4.0](https://github.com/ofiwg/libfabric/tree/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8) です。測ったのは、g7.48xlarge 1 台の上で DeepSeek-V2-Lite-Chat を、prefill と decode それぞれ 2 枚の GPU に分けて (テンソル並列の TP 2) 動かした構成で、この記事の数値はすべてこの構成のものです。prefill のプロセスには `CUDA_VISIBLE_DEVICES=0,1`、decode のプロセスには `CUDA_VISIBLE_DEVICES=2,3` が設定されていて、記事の中の「0 番」「1 番」は、各プロセスから見た GPU の番号を指します。

以下では、次の「全体の地図」の節で層と経路の図を示したあと、efa から shm への受け渡し、CUDA IPC と SAR、送る側のスレッドの GPU と NIXL 1.4.0 での回避、受け取る側の progress thread、3 つの構成の比較の順に見ます。

## 全体の地図

![prefill と decode の各 TP rank が 1 つずつプロセスを持ち、NIXL と libfabric の efa を通る。相手が同じノードなら shm に、別のノードなら EFA の装置に回る](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/741e79cf2e9bf2/zenn/articles/741e79cf2e9bf2/map.png)
*同じノードの相手へのデータは、既定では EFA の装置ではなく shm プロバイダを通ります*

SGLang は TP の rank ごとに 1 つのプロセスを立て、各プロセスは自分の GPU の上に KV cache を持ちます。KV cache の転送は NIXL が受け持ち、相手が同じノードにいるか別のノードにいるかで、libfabric の中の経路が分かれます。

NIXL は書き込みに、書き込みが終わったときに受け取る側へ一緒に届く小さな値 (`FI_REMOTE_CQ_DATA`) を付けて発行します。発行に使う関数は、1.1.0 では [`fi_writedata`](https://github.com/ai-dynamo/nixl/blob/05e4243f5ed305a245912361ace20ba354ec0808/src/utils/libfabric/libfabric_rail.cpp#L1127-L1136)、1.4.0 では [`fi_writemsg`](https://github.com/ai-dynamo/nixl/blob/c0a1102b94d173049a5478c23e765ba37681e2ca/src/utils/libfabric/libfabric_rail.cpp#L1168-L1171) です。この値の有無は、あとで見る shm の経路の選び方に関わります。

## efa から shm への受け渡し

![efa プロバイダは相手が同じノードなら既定で shm に任せる。FI_EFA_ENABLE_SHM_TRANSFER=0 なら EFA の装置で RDMA の書き込みをする](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/741e79cf2e9bf2/zenn/articles/741e79cf2e9bf2/efa-shm.png)
*同じノードの相手に shm を使うかどうかは、1 つの設定で決まります*

efa プロバイダは、同じノードの相手との通信のために、shm プロバイダを中に抱えています。shm を使うかどうかは設定 `enable_shm_transfer` で決まり、[既定値は 1 です](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/efa/src/efa_env.c#L15)。環境変数 `FI_EFA_ENABLE_SHM_TRANSFER=0` で 0 にすると、[shm の経路そのものが作られません](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/efa/src/efa_shm.c#L68-L77)。

shm を切ると本当に EFA の装置を通るのかを、装置のカウンタで確かめました。`rdma_write_bytes` は、装置が RDMA の書き込み (相手の CPU を介さずに相手のメモリへ直接書く方式) で送ったバイト数のカウンタで、ホストのネットワークをそのまま使う Pod から読みました。NIXL の転送の呼び出し 17 回のあいだに、カウンタは 8,663,389,312 バイト増えました。

送るはずの KV cache の量は、1 回 254,803,968 バイト × 2 rank × 17 回 = 8,663,334,912 バイトです。2 つはほぼ一致しているので、この測定の区間では、同じノードの相手への転送が装置の RDMA の書き込みとして出たと読めます。差の 54,400 バイトの内訳は分かっていません。

## CUDA IPC による受け渡し

![送る側はバッファの先頭を調べて IPC ハンドルを作り、共有メモリの命令に入れる。受け取る側はハンドルを開いて自分のバッファへコピーし、戻ってから完了のフラグを立てる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/741e79cf2e9bf2/zenn/articles/741e79cf2e9bf2/cuda-ipc.png)
*shm の CUDA IPC では、データをコピーするのは受け取る側のプロセスです*

別のプロセスの GPU のメモリは、そのアドレスを渡されただけでは使えません。CUDA IPC は、送る側が自分の GPU のメモリから IPC ハンドルという識別子を作り、受け取る側がそのハンドルを開いて、相手のメモリを自分のプロセスから使えるようにする仕組みです。

shm には、プロセス間のメモリコピー (CMA) を使って送る側だけで書き終える速い経路もあります。ただし、`FI_REMOTE_CQ_DATA` の付いた書き込みは[この経路を使いません](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_rma.c#L335-L336)。どの方法で渡すかは [`smr_select_proto`](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_ep.c#L553-L611) が決め、送るバッファが 1 つで、登録済みの GPU のメモリにあり、相手も IPC を使えるときは、CUDA IPC を選びます。

IPC ハンドルは、確保した領域の単位で作ります。そこで送る側は、まず [`cuMemGetAddressRange`](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/src/hmem_cuda.c#L440-L458) で、転送するポインタを含む領域の先頭と長さを調べます。次にその先頭について [`cudaIpcGetMemHandle`](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/src/hmem_cuda.c#L387-L401) でハンドルを作り、ハンドルと先頭からのオフセットを、[共有メモリに置く命令に入れます](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_ep.c#L313-L342)。

libfabric では、完了を確かめる関数を呼んだときに、たまっている処理をその場で進めます。これを progress と呼びます。受け取る側は、この progress の中でハンドルを開き、開いた結果をキャッシュします。続いて、その関数を呼んだスレッドの上で `cudaMemcpy` を呼んで自分のバッファへコピーし、[コピーが戻ってから完了のフラグを立てる](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_progress.c#L522-L597)ので、送る側が完了を知るのはそのあとです。

## SAR

![SAR では、送る側が受け取る側の共有メモリにある 32 KiB の領域にコピーし、受け取る側が自分のバッファへコピーする。これを全部渡るまで繰り返す](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/741e79cf2e9bf2/zenn/articles/741e79cf2e9bf2/sar.png)
*SAR では、データがホストの共有メモリを中継して 2 回コピーされます*

CUDA IPC を選んだあとで準備に失敗すると、shm は [SAR という経路に切り替えます](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_ep.c#L701-L736)。SAR は segmentation and reassembly の略で、データを小さく分けて送り、受け取る側で組み立て直す方式です。切り替えるときの警告「unable to use IPC for msg, fallback to using SAR」は `FI_WARN_ONCE` で出るので、1 つのプロセスで 1 回しか出ません。

SAR では、受け取る側の共有メモリにある、[1 つ 32 KiB の中継用の領域](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_util.h#L165)を使います。この領域をバウンスバッファと呼びます。送る側はメッセージごとに、空いているバウンスバッファを[最大 64 個](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_util.h#L123)まで[確保し](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_ep.c#L483-L530)、相手ごとの上限がある場合はその数までにします。

そのあと、2 つの手順をメッセージの終わりまで[繰り返します](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_ep.c#L423-L481)。まず送る側が中身をコピーしてフラグを FULL にし、次に受け取る側が自分のバッファへコピーしてフラグを EMPTY に戻します。GPU のメモリのデータは、ホストの共有メモリを中継する 2 段のコピーで、1 回に最大 2 MiB (64 × 32 KiB) ずつ運ばれます。SAR になったことで時間がどれだけ増えたかは、この記事では測っていません。

## スレッドごとの current device

![TP rank 1 のプロセスでは、メインのスレッドは 1 番の GPU を向くが、転送スレッドは何も設定しないので 0 番の GPU のコンテキストで動く。0 番のコンテキストではバッファのアドレスが見つからず、SAR に落ちる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/741e79cf2e9bf2/zenn/articles/741e79cf2e9bf2/thread-device.png)
*prefill の TP rank 1 では、転送スレッドが 0 番の GPU のコンテキストのまま、1 番の GPU のデータを送ろうとします*

CUDA の runtime API は、いま使う GPU をホストのスレッドごとに覚えていて、これを current device と呼びます。`cudaSetDevice` を呼ばないスレッドでは、[0 番の GPU が既定になります](https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/multi-gpu-systems.html#device-selection)。一方、`cuMemGetAddressRange` のような driver API は、そのスレッドで有効な CUDA のコンテキスト (context) の中でアドレスを探します。コンテキストは GPU ごとに作られ、その GPU で確保したメモリを管理します。

SGLang の各プロセスのメインのスレッドは、[初期化のときに自分の GPU を選びます](https://github.com/sgl-project/sglang/blob/5a15cde858ea09b77116212a39356f2fc51b8584/python/sglang/srt/model_executor/model_runner.py#L1191)。一方、NIXL の転送を発行するスレッドは、あとから [`threading.Thread` で作られます](https://github.com/sgl-project/sglang/blob/5a15cde858ea09b77116212a39356f2fc51b8584/python/sglang/srt/disaggregation/nixl/conn.py#L291-L295)。このスレッドで動く [`transfer_worker`](https://github.com/sgl-project/sglang/blob/5a15cde858ea09b77116212a39356f2fc51b8584/python/sglang/srt/disaggregation/nixl/conn.py#L563) は、GPU を選びません。

TP rank 0 の KV cache は 0 番の GPU にあるので、たまたま向きが合います。TP rank 1 では、転送スレッドが 0 番の GPU を向いたまま、1 番の GPU にある KV cache の書き込みを発行します。0 番のコンテキストの中では 1 番の GPU のアドレスが見つからず、ハンドルを作れないと考えられます。ただし、どの呼び出しで 0 番のコンテキストが有効になったかまでは確かめていません。

NIXL 1.1.0 で shm を使ったまま、起動したばかりのエンジンに 8,192 トークンの要求を 1 つ送りました。すると prefill の TP rank 1 のプロセスから、`Failed to perform cuMemGetAddressRange: CUDA_ERROR_NOT_FOUND` の警告がちょうど 27 行、SAR への切り替えの警告が 1 行出ました。切り替えの警告は 1 回しか出ないので、この 2 つの行数から、SAR に落ちたのが 1 回だけだとは言えません。

試験のために、転送スレッドの最初で `torch.cuda.set_device(self.kv_args.gpu_id)` を呼ぶ 1 行を足しました。すると、同じ要求を送っても、続けて 1 秒に 2 件の割合で 40 件の要求を流しても、どちらの警告も出ませんでした。

2026 年 10 月 19 日に確かめた時点で、この転送スレッドについての SGLang の Issue はありません。近い修正でマージ済みの [sgl-project/sglang#38774](https://github.com/sgl-project/sglang/pull/38774) は、NIXL のバックエンドを作るスレッドで GPU を選ぶようにしたもので、main ブランチの `transfer_worker` は、まだ GPU を選んでいません。Issue は今後出す予定です。

## NIXL 1.4.0 での回避

![NIXL 1.1.0 では転送スレッドが 0 番の GPU のコンテキストのままハンドルが作れず SAR になる。NIXL 1.4.0 は送る前に登録時のコンテキストを設定し直すので、CUDA IPC になる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/741e79cf2e9bf2/zenn/articles/741e79cf2e9bf2/nixl140.png)
*NIXL 1.4.0 は、転送を発行するスレッドのコンテキストを、自分で合わせ直します*

NIXL 1.4.0 の LIBFABRIC バックエンドは、GPU のメモリから転送を発行する前に、[メモリを登録したときのコンテキストを、発行するスレッドに設定し直します](https://github.com/ai-dynamo/nixl/blob/c0a1102b94d173049a5478c23e765ba37681e2ca/src/plugins/libfabric/libfabric_backend.cpp#L1217-L1224)。ソースを読む限り、この変更は [ai-dynamo/nixl#1581](https://github.com/ai-dynamo/nixl/pull/1581) で入りました。

この動きは[既定で有効です](https://github.com/ai-dynamo/nixl/blob/c0a1102b94d173049a5478c23e765ba37681e2ca/src/plugins/libfabric/libfabric_backend.cpp#L425-L431)。ただし、登録のときに 1 つのプロセスが複数の GPU を使うと[分かった場合](https://github.com/ai-dynamo/nixl/blob/c0a1102b94d173049a5478c23e765ba37681e2ca/src/plugins/libfabric/libfabric_backend.cpp#L895-L925)は、代わりに[書き込みのたびに `cudaSetDevice` で GPU を合わせます](https://github.com/ai-dynamo/nixl/blob/c0a1102b94d173049a5478c23e765ba37681e2ca/src/plugins/libfabric/libfabric_backend.cpp#L1226-L1232)。

測った構成では、各プロセスは自分の GPU だけを登録するので、複数の GPU を使うという判定にはならず、ログの「Multi-GPU detected」は 0 行でした。働いたのは、登録時のコンテキストを設定し直す動きのほうです。これにより SGLang を直さなくても TP rank 1 でハンドルが作れるようになり、3 つの seed と 5 つのレートを組み合わせた測定を 3 回流したどれでも、`cuMemGetAddressRange` の失敗と SAR への切り替えの警告は出ませんでした。

これで直るのは送る側だけです。受け取る側のコピーをどのスレッドが実行するかには、次の節で見る progress thread が関わります。

## NIXL の progress thread

![decode のプロセスでは、NIXL の progress thread が完了を拾うループを回し、ep_mutex_ を持ったまま fi_cq_read を呼ぶ。測った構成では、shm の受け取りのコピーがこのスレッドで走っていた](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/741e79cf2e9bf2/zenn/articles/741e79cf2e9bf2/progress-thread.png)
*完了を拾うだけのはずのスレッドの中で、shm の受け取りのコピーが走ります*

progress thread は、NIXL のバックエンドの設定で有効にすると、LIBFABRIC バックエンドが[立てる裏のスレッド](https://github.com/ai-dynamo/nixl/blob/c0a1102b94d173049a5478c23e765ba37681e2ca/src/plugins/libfabric/libfabric_backend.cpp#L500-L512)です。このスレッドは完了の知らせを[拾うループを回し](https://github.com/ai-dynamo/nixl/blob/c0a1102b94d173049a5478c23e765ba37681e2ca/src/plugins/libfabric/libfabric_backend.cpp#L1840-L1860)、拾うものが無いときは一定時間待ちます。測った構成では有効でした。

ループは、完了を拾う [`fi_cq_read`](https://github.com/ai-dynamo/nixl/blob/c0a1102b94d173049a5478c23e765ba37681e2ca/src/utils/libfabric/libfabric_rail.cpp#L730-L734) を、[書き込みを発行するとき](https://github.com/ai-dynamo/nixl/blob/c0a1102b94d173049a5478c23e765ba37681e2ca/src/utils/libfabric/libfabric_rail.cpp#L1168-L1171)と同じロック `ep_mutex_` を持ったまま呼びます。このロックは、NIXL がネットワークの装置ごとに持つ通信路の単位である rail ごとにあります。

前の節で見たとおり、shm の受け取る側の処理は、完了を確かめる関数の中で進みます。そのため、完了を拾うだけに見えるこのスレッドの中で、受け取りのコピーも走ります。測った構成では、decode のプロセスで受け取ったデータをコピーする `cudaMemcpy` は、この progress thread から呼ばれていました。コードを読む限り、コピーが戻るまでは同じ rail のロックを使う書き込みや完了の読み出しが待たされるはずですが、待ちの時間は測っていません。

## progress thread が向く GPU

![decode の TP rank 1 では、progress thread が 0 番の GPU のコンテキストのまま 1 番の GPU の受け取り先へコピーし、ホストを経由する 2 段のコピーとして記録された。作った側の GPU で始める試験の変更では 1 回の直接のコピーになった](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/741e79cf2e9bf2/zenn/articles/741e79cf2e9bf2/progress-device.png)
*decode の TP rank 1 では、受け取りのコピーを実行するスレッドが別の GPU を向いています*

progress thread のループは、[CUDA のコンテキストを自分では設定しません](https://github.com/ai-dynamo/nixl/blob/c0a1102b94d173049a5478c23e765ba37681e2ca/src/plugins/libfabric/libfabric_backend.cpp#L1840-L1860)。受け取る側では、ハンドルを開く処理もコピーもこのスレッドの上で走ります。そして libfabric の [`cuda_copy_to_dev`](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/src/hmem_cuda.c#L329-L343) は、引数で受け取った GPU の番号 `device` を使わずに、呼んだスレッドのコンテキストのまま `cudaMemcpy` を呼びます。

NIXL 1.4.0 で shm を使ったまま測ると、decode の TP rank 1 の progress thread は 0 番の GPU のコンテキストで動き、記録した 4,500 回のコピーのすべてで、コピー先は 1 番の GPU でした。TP rank 0 は向きが合っていました。このとき Nsight Systems の記録では、TP rank 1 の 1 回の受け取りが、ホストのメモリを経由する 2 段のコピーになっていました。

試験のために NIXL を変えて、decode の progress thread を、それを作ったスレッドが使う GPU で始めるようにすると、受け取りは 1 回の直接のコピーになりました。要求を 1 秒に 1 件送り、KV cache の page size を 1 にした条件では、decode の 1 トークンあたりの平均時間 (mean TPOT) の、測定ごとの中央値が 19.97〜20.15 ms から 13.0〜13.4 ms に下がりました。この変更は upstream にはありません。

ただし、記録したコピーの遅れの分だけではこの差を説明できず、スレッドの向きを直すとなぜ decode のステップ全体が短くなるのかは、まだ分かっていません。NIXL には、progress thread と CUDA のコンテキストについての近い報告 [ai-dynamo/nixl#1157](https://github.com/ai-dynamo/nixl/issues/1157) があり、2026 年 2 月 3 日に、progress thread は CUDA のコンテキストを操作しないという説明とともに閉じられています。一方、この記事の測定では、shm の経路の受け取りのコピーがこのスレッドの上で呼ばれていました。NIXL 1.1.0 の受け取る側は調べていません。

## 3 つの構成の比較

![NIXL 1.1.0 と shm では送る側の SAR が残り (受け取る側は未測定)、NIXL 1.4.0 と shm では受け取る側の食い違いが残り、shm を切ると shm の経路そのものを通らない](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/741e79cf2e9bf2/zenn/articles/741e79cf2e9bf2/setups.png)
*NIXL 1.4.0 で送る側は直り、shm を切ると受け取る側の食い違いも通らなくなります*

| 構成 | 送る側 | 受け取る側 |
|---|---|---|
| NIXL 1.1.0、shm あり | prefill の TP rank 1 で SAR に落ちる | この記事では測っていない |
| NIXL 1.4.0、shm あり | CUDA IPC になる | decode の TP rank 1 で、progress thread が別の GPU を向いてコピーする |
| `FI_EFA_ENABLE_SHM_TRANSFER=0` | EFA の装置で RDMA の書き込み | shm の受け取りのコピーを通らない |

速さについて、測り方の違う 2 つの結果があります。NIXL 単体で 16 MiB を 1 回だけ送ると、装置を通る経路は 0.637 ms、CUDA IPC は 0.165 ms で、装置を通るほうが遅くなりました。一方、SGLang に 1 秒に 1 件の負荷をかけた測定 (NIXL 1.1.0、page size 1) では、SGLang が記録する KV の転送の段階の平均が、shm を切ると 1,776 ms から 196 ms に短くなりました。この shm ありの値は、prefill の TP rank 1 が SAR に落ちる構成での値で、短縮の内訳は分けて測っていません。

これは 1 ノードでの比較です。shm を切ると、同じノードの中のほかの相手への libfabric の通信も装置を通るので、`FI_EFA_ENABLE_SHM_TRANSFER=0` をどの構成でも勧めるものではありません。

## まとめ

送る側では、SGLang の転送スレッドが GPU を選ばないため、prefill の TP rank 1 の転送が SAR に落ちます。NIXL 1.4.0 では、この問題は起きません。受け取る側では、decode の TP rank 1 で、NIXL の progress thread が別の GPU を向いたままコピーし、これは NIXL 1.4.0 でも残ります。`FI_EFA_ENABLE_SHM_TRANSFER=0` で shm の経路を使わなければ、どちらの経路も通らなくなります。
