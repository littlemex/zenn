## はじめに

AWS の GPU インスタンスで EFA を使う通信ライブラリの多くは、libfabric という通信のライブラリを通して EFA を操作します。たとえば NCCL は、aws-ofi-nccl というプラグインを通して libfabric を使い、libfabric が rdma-core とドライバを通して EFA を動かします。この層の分担は「[MoE の all-to-all を支える層: DeepEP、NCCL GIN、aws-ofi-nccl、EFA](https://zenn.dev/tosshi/articles/a0f5ff21eed405)」で図にしています。この記事で扱う NIXL の LIBFABRIC バックエンドも、同じように libfabric を通して EFA を使います。

通信のライブラリ libfabric は、通信の方式をプロバイダという部品で切り替えます。AWS のネットワークカードである EFA を使うのが efa プロバイダで、同じノードの中で共有メモリを使うのが shm プロバイダです。efa プロバイダを使うと、相手が別のノードにいるときは EFA の装置を通ってデータが届きます。ところが、この記事で調べた libfabric 2.4.0 の efa プロバイダは、相手が同じノードにいるとき、既定の設定 (`FI_EFA_ENABLE_SHM_TRANSFER=1`) では EFA の装置を使わず、shm プロバイダにデータを任せます。shm プロバイダは、1 つの登録済みの GPU のバッファを送るときなど、条件がそろうと CUDA IPC を選びます。CUDA IPC は、別のプロセスの GPU のメモリを、自分のプロセスから開いてコピーできるようにする CUDA の仕組みです。このとき、受け取る側が送る側の GPU のメモリを開いてコピーします。CUDA IPC を選んだあとで、送る側がその準備に失敗すると、SAR という、ホストの共有メモリを経由して小分けに運ぶ方法に切り替えます。この記事では、この同じノードの中の経路を図で追います。

![左は相手が別のノードにいる場合で、EFA の装置からネットワークを通って届く。右は相手が同じノードにいる場合で、efa プロバイダは既定では shm プロバイダに任せ、FI_EFA_ENABLE_SHM_TRANSFER=0 なら EFA の装置を使う](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/741e79cf2e9bf2/zenn/articles/741e79cf2e9bf2/overview.png)
*既定では、同じノードの相手へのデータは EFA の装置を通りません*

図の左は、相手が別のノードにいる場合です。データは送る側の EFA の装置からネットワークを通り、相手の EFA の装置へ届きます。図の右は、相手が同じノードにいる場合です。efa プロバイダは相手が同じノードにいると判断すると、既定の `FI_EFA_ENABLE_SHM_TRANSFER=1` では shm プロバイダにデータを任せます。`FI_EFA_ENABLE_SHM_TRANSFER=0` のときは、同じノードの相手にも EFA の装置を使います。RDMA (Remote Direct Memory Access) の書き込みは、通信の装置が、相手のメモリへ直接データを書き込む操作です。測った構成では、この転送が装置の RDMA の書き込みとして出たことを、「直し方 1」の節で確かめます。

ここから、この記事で使う 3 つの言葉を、図で 1 つずつ説明します。

![送る側のプロセスは、受け取る側がホストのメモリに作った領域を開き、そこにある命令の列に書く。受け取る側はその命令を読み、送る側の領域にある応答の列に結果を返す。受け取る側の領域には SAR の中継用の領域もある](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/741e79cf2e9bf2/zenn/articles/741e79cf2e9bf2/shm-term.png)
*shm プロバイダは、ホストのメモリの領域で命令と応答を受け渡します*

shm プロバイダでは、各プロセスがホストのメモリに[自分の領域を作ります](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_util.c#L191-L250)。送る側は、相手が作った領域を `shm_open` で開いて `mmap` で自分のアドレス空間に[対応付け](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_util.c#L346-L398)、その領域にある命令の列 (command queue) に命令を書きます。受け取る側は、自分の領域に書かれた命令を読んで処理し、処理が終わったことを、送る側の領域にある応答の列 (response queue) で返します。受け取る側の領域には、あとで見る SAR で使う中継用の領域も入っています。データの中身がどう運ばれるかは、次の CUDA IPC と SAR で違います。

![送る側は自分の GPU のバッファから IPC ハンドルを作り、shm の命令に入れて渡す。受け取る側はハンドルを開き、送る側の GPU のバッファから自分の GPU のバッファへ 1 回でコピーする](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/741e79cf2e9bf2/zenn/articles/741e79cf2e9bf2/cuda-ipc-term.png)
*CUDA IPC では、受け取る側が送る側の GPU のバッファから 1 回でコピーします*

CUDA IPC (Inter-Process Communication) は、別のプロセスの GPU のメモリを使えるようにする CUDA の仕組みです。送る側は、自分の GPU のバッファから IPC ハンドルという識別子を作り、shm の命令に入れて渡します。この記事で扱う、GPU のバッファへの送信では、受け取る側がそのハンドルを開き、送る側の GPU のバッファから自分の GPU のバッファへ、1 回でコピーします。コピーをするのは、受け取る側のプロセスです。ハンドルを作る前に、送る側は `cuMemGetAddressRange` でバッファの場所を調べます。この呼び出しは、送る側のスレッドで有効な CUDA のコンテキスト (GPU ごとに作られ、その GPU で確保したメモリを管理するもの) の中でアドレスを探すので、そのコンテキストの中でバッファが見つからないとハンドルを作れません。この記事で見る失敗は、ここで起きます。手順の細かいところは「CUDA IPC による受け渡し」の節で見ます。

![SAR では、送る側が自分の GPU のバッファから受け取る側の共有メモリにある 32 KiB の中継用の領域へコピーし、受け取る側がそこから自分の GPU のバッファへコピーする。中継用の領域を使い回して全部渡るまで繰り返す](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/741e79cf2e9bf2/zenn/articles/741e79cf2e9bf2/sar-term.png)
*SAR では、ホストの共有メモリを中継して、1 かたまりにつき 2 回コピーします*

SAR (segmentation and reassembly) は、shm がデータを中継用の領域で小分けに運ぶ方法です。データの大きさや指定によって[最初から選ばれる](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_ep.c#L553-L611)こともあり、CUDA IPC を選んだあとでその準備に失敗したときの切り替え先にもなります。この記事で問題になるのは、後者の切り替えです。SAR では、データを [32 KiB](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_util.h#L165) ずつのかたまりに分け、送る側が自分の GPU のバッファから、[受け取る側の共有メモリにある中継用の領域](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_ep.c#L505-L515)へコピーします。続いて受け取る側が、そこから自分の GPU のバッファへコピーします。中継用の領域は使い回し、データが全部渡るまでこれを繰り返します。CUDA IPC なら 1 回で済むコピーが、かたまりごとに 2 回になり、そのたびにホストのメモリを経由します。手順の細かいところは「SAR」の節で見ます。

同じノードの中のこの経路で、実際に何が起きていたのかを、次の節で問題として定めます。

## 調べたケース: 同じノード内の LIBFABRIC 転送


この記事では、SGLang で disaggregated inference (分離推論) をするときに、NIXL の LIBFABRIC バックエンドを使って、同じノードにいる相手へ KV cache を送るケースを調べました。SGLang の分離推論では、入力を読む prefill と、出力のトークンを 1 つずつ作る decode を、別々のプロセスに分けて動かします。prefill は、入力の各トークンについて計算した Attention の Key と Value を KV cache として保存し、decode へ送ります。decode はそれを使って、入力を計算し直さずに続きのトークンを作ります。その転送を受け持つのが、推論のプロセスのあいだでデータを転送するライブラリ NIXL です。この記事の構成では、prefill と decode は、それぞれモデルの計算を 2 枚の GPU に分けて受け持ちます。この分け方をテンソル並列 (TP) と呼び、GPU ごとに 1 つずつあるプロセスの番号を TP rank と呼びます。prefill と decode は別々のノードに置くのが基本の構成なので、同じノードに置くケースは、あまり想定されていないかもしれません。今回は、このケースで何が起きるかを確かめます。

:::message
SGLang の分離構成で NIXL の LIBFABRIC バックエンドを使い、prefill と decode が同じノードにあると、KV cache は EFA の装置ではなく libfabric の shm の経路を通ります。測った構成では、この経路の転送が、shm を切ったときより大幅に遅くなりました。この記事は、その経路で何が起きているかを追います。
:::

NIXL は、転送に使うバックエンドを選べます。この記事で扱うのは LIBFABRIC のバックエンドです。EFA のあるインスタンスで efa プロバイダを使う場合、送り先が同じノードにあれば、KV cache は上の shm の経路を通ります。NIXL には [UCX のバックエンド](https://github.com/ai-dynamo/nixl/tree/c0a1102b94d173049a5478c23e765ba37681e2ca/src/plugins/ucx)もあります。UCX は libfabric を使わず、同じノードの相手には、UCX 自身の経路 (cuda_ipc や共有メモリなど) から選んで使います。NIXL 単体で同じノードの 2 枚の GPU のあいだに送ったときは、UCX が自分の cuda_ipc の経路を選んだことを、`UCX_PROTO_INFO=y` のログで確かめました。そのため、この記事の話は、NIXL で LIBFABRIC のバックエンドを選んだときのものです。UCX のバックエンドで同じ食い違いが起きるかどうかは、この記事では調べていません。

測った構成で 1 秒に 1 件の負荷をかけると (NIXL 1.1.0、page size 1)、SGLang 自身が記録する KV の転送の段階の時間の平均は、shm を使う既定の設定で 1,776 ms、shm を使わない設定で 196 ms でした。page size は、SGLang が KV cache を管理するページ 1 つに入るトークンの数で、この記事の数値はすべて page size 1 で測ったものです。この記事が答える問いは、次の 2 つです。

- shm の経路のどこで、何が起きているのか
- それを避ける方法は何か

測った構成の shm の経路では、prefill の TP rank 1 (送る側) で、KV cache の書き込みを発行する SGLang の転送スレッドが、データのある 1 番の GPU ではなく 0 番の GPU を向いたまま、書き込みを発行していたと考えられます。CUDA は、いま使う GPU (current device) をスレッドごとに覚えていて、転送スレッドではこれを設定していません。そのため CUDA IPC の準備に失敗し、SAR に切り替わります。転送スレッドで GPU を指定すると、この失敗は起きなくなりました。この記事では、これを「問題」と呼びます。

この問題で長くなる KV の転送の段階を短くする方法は、2 通りあります。

| 直し方 | 何を変えるか | 1 秒に 1 件の KV の転送の段階の平均 ms |
|---|---|---|
| 1. shm を使わない設定 | 同じノードの相手にも、EFA の装置で RDMA の書き込みをする。shm の経路を使わない | 196 |
| 2. NIXL 1.4.0 | shm の経路のまま、書き込みの前に、メモリを登録したときのコンテキストにスレッドを合わせる。SAR に切り替わらない | 533 |

直し方 1 は NIXL 1.1.0 で測った値です。比べる元は、NIXL 1.1.0 で shm を使う既定の設定の 1,776 ms です。どれも 1 秒に 1 件、page size 1 で、SGLang が記録する転送の段階の時間を、構成ごとに 1 回の測定で平均した値です。平均に使った SGLang の記録の数は、比べる元が 51〜59、直し方 1 が 38、直し方 2 が 34 です。

次の表は、転送に関わる層を、上から呼び出す順に並べたものです。右の列が、この記事で見るところです。

| 層 | 受け持ち | この記事で見るところ |
|---|---|---|
| SGLang | KV cache を持ち、転送を頼む | 転送スレッドが GPU を選ばないこと |
| NIXL (LIBFABRIC バックエンド) | 転送を libfabric の呼び出しに変える | 送る前の CUDA のコンテキスト |
| libfabric の efa | 相手が同じノードなら shm に任せる | shm を使う設定 |
| libfabric の shm | 共有メモリで渡す | CUDA IPC と SAR |

記事の中の「0 番」「1 番」は、各プロセスから見た GPU の番号を指します。prefill のプロセスには `CUDA_VISIBLE_DEVICES=0,1`、decode のプロセスには `CUDA_VISIBLE_DEVICES=2,3` を設定していたので、たとえば decode の「0 番」はノードの 3 枚目の GPU です。この記事の数値は、次の条件で測ったものです。

:::details 調べた条件
| 項目 | 値 |
|---|---|
| インスタンス | g7.48xlarge 1 台。Kubernetes の 1 つの Pod に prefill と decode を入れ、それぞれ 2 枚の GPU (テンソル並列の TP 2) を使う。Pod に割り当てた EFA の装置は 1 台で、prefill と decode が一緒に使う |
| モデル | DeepSeek-V2-Lite-Chat (revision `85864749cd611b4353ce1decdb286193298f64c7`) |
| SGLang | [0.5.12.post1](https://github.com/sgl-project/sglang/tree/5a15cde858ea09b77116212a39356f2fc51b8584) |
| NIXL | [1.1.0](https://github.com/ai-dynamo/nixl/tree/05e4243f5ed305a245912361ace20ba354ec0808) と [1.4.0](https://github.com/ai-dynamo/nixl/commit/c0a1102b94d173049a5478c23e765ba37681e2ca) |
| libfabric | [2.4.0](https://github.com/ofiwg/libfabric/tree/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8) |
| ルーター | sglang-router 0.3.2、`--pd-disaggregation --policy round_robin --disable-retries --request-timeout-secs 330` |

| prefill だけの引数 | `--disaggregation-mode prefill --disaggregation-bootstrap-port 8998` |
| decode だけの引数 | `--disaggregation-mode decode` |

| 要求 | 入力 8,192 トークン、出力 256 トークン。問題の警告の行は、起動したばかりのエンジンに要求を 1 つ送って数えた。転送の段階の時間は、平均して 1 秒に 1 件か 2 件の割合で 20 秒送って測った (構成ごとに 1 回)。TTFT は、同じ 1 秒に 1 件の負荷を、要求の届く間隔などをばらつかせる乱数の始まりの値 seed を 3 通りに変えて流し、合わせた |
| 測ったもの | SGLang が `--enable-metrics` で記録する段階ごとの時間 (`sglang:per_stage_req_latency_seconds` の `stage="prefill_transfer_kv_cache"`)、libfabric のログの警告の行 (`unable to use IPC for msg, fallback to using SAR`、`Failed to perform cuMemGetAddressRange`) |

問題の警告は、手を加えていない SGLang の prefill と decode のサーバーを同じノードで起動し、ルーターを PD モードで立てて、長い入力を送るだけで出ます。転送の段階の時間は、同じ長さの要求を、届く間隔をばらつかせながら平均して決まった割合で送り、測りました。

:::details 同じ構成を起動する手順
`MODEL_PATH` に、モデルを置いた場所か Hugging Face の名前を入れます。これは、上の条件の起動引数を並べたものです。このブロックは、上の条件と同じ版 (SGLang 0.5.12.post1、NIXL 1.1.0、libfabric 2.4.0) が入った、GPU 4 枚と EFA の装置 1 つを割り当てた 1 つの Pod の中で、そのまま流すと下に書いた数が出ることを、2026-10-20 に確かめています。最後の行で、起動したサーバーを止めます。

```bash
export MODEL_PATH=deepseek-ai/DeepSeek-V2-Lite-Chat
export SGLANG_DISAGGREGATION_NIXL_BACKEND=LIBFABRIC
export FI_PROVIDER=efa
export FI_EFA_USE_DEVICE_RDMA=1
export FI_LOG_LEVEL=info
COMMON="--model-path $MODEL_PATH --revision 85864749cd611b4353ce1decdb286193298f64c7 --host 127.0.0.1 --tp-size 2 --dtype bfloat16 --kv-cache-dtype bf16 --context-length 32768 --chunked-prefill-size 8192 --mem-fraction-static 0.75 --page-size 1 --enable-metrics --stream-interval 1 --disaggregation-transfer-backend nixl"
CUDA_VISIBLE_DEVICES=0,1 python3 -m sglang.launch_server $COMMON --port 30000 --disaggregation-mode prefill --disaggregation-bootstrap-port 8998 > prefill.log 2>&1 &
CUDA_VISIBLE_DEVICES=2,3 python3 -m sglang.launch_server $COMMON --port 30001 --disaggregation-mode decode > decode.log 2>&1 &
until curl -sf http://127.0.0.1:30000/health > /dev/null && curl -sf http://127.0.0.1:30001/health > /dev/null; do sleep 10; done
python3 -m sglang_router.launch_router --pd-disaggregation --prefill http://127.0.0.1:30000 8998 --decode http://127.0.0.1:30001 --host 127.0.0.1 --port 8000 --policy round_robin --disable-retries --request-timeout-secs 330 > router.log 2>&1 &
until curl -sf http://127.0.0.1:8000/health > /dev/null; do sleep 2; done
python3 -c 'import json, random, urllib.request; ids = [random.randrange(1000, 30000) for _ in range(8192)]; req = urllib.request.Request("http://127.0.0.1:8000/generate", json.dumps({"input_ids": ids, "sampling_params": {"max_new_tokens": 256, "ignore_eos": True}}).encode(), {"content-type": "application/json"}); print(json.loads(urllib.request.urlopen(req, timeout=600).read())["meta_info"]["completion_tokens"])'
grep -c "fallback to using SAR" prefill.log
grep -c "cuMemGetAddressRange" prefill.log
kill $(jobs -p)
```

このブロックを流すと、生成されたトークンの数として 256 が出て、そのあとに SAR への切り替えの警告が 1 行、`cuMemGetAddressRange` の失敗の警告が 27 行と出ました。この 1 回目の要求では、どちらも prefill の TP rank 1 のプロセスの行でした。最後の `kill` の前に、同じエンジンへ要求をさらに 4 回 (合計 5 回) 送ると、TP rank 1 の切り替えの警告は 1 行のままで、TP rank 1 の `cuMemGetAddressRange` の行は要求ごとに 27 行ずつ増えて 135 行になりました。このとき、2〜5 回目の要求のあいだに、TP rank 0 のプロセスからも `cuMemGetAddressRange` の失敗が合計 2 行、切り替えの警告が 1 行出ました。その理由は調べていません。要求を続けると、`grep -c` の数には TP rank 0 の行も入ります。shm を使わない構成を試すときは、サーバーを起動する前に `export FI_EFA_ENABLE_SHM_TRANSFER=0` を足します。足して流すと、256 のあとに 0 と 0 が出ました。
:::

## 全体像

![prefill と decode の各 TP rank が 1 つずつプロセスを持ち、NIXL と libfabric の efa を通る。相手が同じノードなら shm に、別のノードなら EFA の装置に回る](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/741e79cf2e9bf2/zenn/articles/741e79cf2e9bf2/map.png)
*同じノードの相手へのデータは、既定では EFA の装置ではなく shm プロバイダを通ります*

SGLang は TP の rank ごとに 1 つのプロセスを立て、各プロセスは自分の GPU の上に KV cache を持ちます。KV cache の転送は NIXL が受け持ち、相手が同じノードにいるか別のノードにいるかで、libfabric の中の経路が分かれます。

NIXL は書き込みに、書き込みが終わったときに受け取る側へ一緒に届く小さな値を付けて発行します。この値を付けることを示す印が、libfabric の [`FI_REMOTE_CQ_DATA`](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/include/rdma/fabric.h#L142) です。発行に使う関数は、1.1.0 では [`fi_writedata`](https://github.com/ai-dynamo/nixl/blob/05e4243f5ed305a245912361ace20ba354ec0808/src/utils/libfabric/libfabric_rail.cpp#L1127-L1136)、1.4.0 では [`fi_writemsg`](https://github.com/ai-dynamo/nixl/blob/c0a1102b94d173049a5478c23e765ba37681e2ca/src/utils/libfabric/libfabric_rail.cpp#L1168-L1171) です。この値の有無は、あとで見る shm の経路の選び方に関わります。

## efa から shm への受け渡し

![SGLang、NIXL の LIBFABRIC バックエンド、libfabric の efa プロバイダ、libfabric の shm プロバイダを段に分けた図。NIXL が FI_REMOTE_CQ_DATA を付けて書き込みを出し、efa プロバイダは相手が同じノードなら既定で shm プロバイダに任せ、shm プロバイダは CMA の速い経路を使わずに CUDA IPC か SAR で運ぶ。同じノードでないか shm を切ると EFA の装置で RDMA の書き込みになる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/741e79cf2e9bf2/zenn/articles/741e79cf2e9bf2/efa-shm.png)
*書き込みに印を付けるのは NIXL で、その印を見て経路を決めるのは libfabric です*

SGLang は KV cache の送信を NIXL に頼み、NIXL の LIBFABRIC バックエンドは、libfabric の書き込みの関数を `FI_REMOTE_CQ_DATA` の印付きで呼びます。その先の経路は libfabric が決めます。efa プロバイダは、[相手が同じノードなら shm プロバイダに任せます](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/efa/src/rdm/efa_rdm_rma.c#L599-L602)。shm プロバイダは、印が付いているので[送る側だけで書き終える速い経路を使わず](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_rma.c#L335-L336)、CUDA IPC か SAR で運びます。

efa プロバイダは、同じノードの相手との通信のために、shm プロバイダを中に抱えています。shm を使うかどうかは設定 `enable_shm_transfer` で決まり、[既定値は 1 です](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/efa/src/efa_env.c#L15)。環境変数 `FI_EFA_ENABLE_SHM_TRANSFER=0` でこれを 0 にすると、[shm の経路そのものが作られません](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/efa/src/efa_shm.c#L68-L77)。この設定を使う直し方は、「直し方 1: shm を使わない設定」の節で見ます。

## CUDA IPC による受け渡し

![CUDA IPC の 6 つの手順。送る側のスレッドが確保領域の先頭を調べて IPC ハンドルを作り、ハンドルとオフセットを入れた命令を受け取る側の命令の列に書く。受け取る側の progress がハンドルを開き、送る側の GPU のバッファから自分のバッファへ cudaMemcpy でコピーし、送る側の応答の列に完了を書く。1 で先頭が見つからないと SAR に切り替わる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/741e79cf2e9bf2/zenn/articles/741e79cf2e9bf2/cuda-ipc.gif)
*shm の CUDA IPC では、データをコピーするのは受け取る側のプロセスです*

別のプロセスの GPU のメモリは、そのアドレスを渡されただけでは使えません。CUDA IPC は、送る側が自分の GPU のメモリから IPC ハンドルという識別子を作り、受け取る側がそのハンドルを開いて、相手のメモリを自分のプロセスから使えるようにする仕組みです。

shm には、プロセス間のメモリコピー (CMA) を使って送る側だけで書き終える速い経路もあります。ただし、`FI_REMOTE_CQ_DATA` の付いた書き込みは[この経路を使いません](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_rma.c#L335-L336)。どの方法で渡すかは [`smr_select_proto`](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_ep.c#L553-L611) が決め、送るバッファが 1 つで、登録済みの GPU のメモリにあり、相手も IPC を使えるときは、CUDA IPC を選びます。

細かい手順の前に、全体の流れを書きます。データは、送る側 (prefill) の GPU にある KV cache から、受け取る側 (decode) の GPU のバッファへ流れます。コピーを実行するのは、受け取る側のプロセスです。そのための通り道は、2 つの処理でできます。送る側が自分の GPU のバッファの IPC ハンドルを作って渡す処理と、受け取る側がそのハンドルを開いて送る側のバッファを読めるようにする処理です。ハンドルや完了の知らせは、ホストの共有メモリにある命令の列と応答の列でやり取りします。

図の番号の順に、1 回の書き込みで何が起きるかを見ます。libfabric では、完了を確かめる関数を呼んだときに、たまっている処理をその場で進めます。これを progress と呼びます。

1. 送る側の転送スレッドが、[`cuMemGetAddressRange`](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/src/hmem_cuda.c#L440-L457) で、転送するポインタを含む確保領域の先頭と長さを調べます。この呼び出しは、そのスレッドでいま有効な CUDA のコンテキストの中でアドレスを探します。
2. その先頭について [`cudaIpcGetMemHandle`](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/src/hmem_cuda.c#L387-L401) で IPC ハンドルを作ります。ハンドルは確保領域の全体を指すので、転送するポインタの先頭からのずれ (オフセット) を[一緒に記録します](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_ep.c#L313-L342)。
3. 送る側は、ハンドル・オフセット・大きさを、受け取る側の領域にある命令の列で[先に確保した場所](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_rma.c#L163-L186)に書き込みます。最後に送る側が命令を確定させると、受け取る側から見えるようになります。送る側は、データそのものはコピーしません。
4. 受け取る側は progress の中でこの命令を[読み](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_progress.c#L1213-L1275)、[ハンドルを開いて](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/src/hmem_ipc_cache.c#L37-L72)、送る側の GPU のバッファを自分のプロセスから使えるようにします。開くのは [`cudaIpcOpenMemHandle`](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/src/hmem_cuda.c#L403-L421) で、開いた結果はキャッシュします。
5. 受け取る側のスレッドが、開いたアドレスにオフセットを足した場所から自分のバッファへ、`cudaMemcpy` で[コピーします](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_progress.c#L574-L578)。受け取る側は送る側の GPU のバッファから直接読み、SAR のように中継用の領域にいったん置くことはしません。
6. コピーの呼び出しが戻ってから、受け取る側は送る側の領域にある応答の列に[処理が済んだことを書き](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_progress.c#L592-L594)、送る側は自分の progress でそれを見ます。送る側の書き込みが完了するのは、このときです。

1 か 2 が失敗すると、[`smr_do_ipc`](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_ep.c#L701-L736) はこの書き込みを次の節の SAR に切り替えます。切り替えの警告は、プロセスごとに 1 回しか出ません。問題は、1 でスレッドのコンテキストの中にバッファが見つからないときに起きます。

## SAR

![SAR では、送る側が受け取る側の共有メモリにある 32 KiB の領域にコピーし、受け取る側が自分のバッファへコピーする。これを全部渡るまで繰り返す](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/741e79cf2e9bf2/zenn/articles/741e79cf2e9bf2/sar.png)
*SAR では、データがホストの共有メモリを中継して 2 回コピーされます*

CUDA IPC を選んだあとで準備に失敗すると、shm は [SAR という経路に切り替えます](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_ep.c#L701-L736)。SAR は segmentation and reassembly の略で、データを小さく分けて送り、受け取る側で組み立て直す方式です。切り替えるときの警告「unable to use IPC for msg, fallback to using SAR」は `FI_WARN_ONCE` で出るので、1 つのプロセスで 1 回しか出ません。

SAR では、受け取る側の共有メモリにある、[1 つ 32 KiB の中継用の領域](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_util.h#L165)を使います。この領域をバウンスバッファと呼びます。送る側はメッセージごとに、空いているバウンスバッファを[最大 64 個](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_util.h#L123)まで[確保し](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_ep.c#L483-L530)、相手ごとの上限がある場合はその数までにします。

そのあと、2 つの手順をメッセージの終わりまで[繰り返します](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_ep.c#L423-L481)。まず送る側が中身をコピーしてフラグを FULL にし、次に受け取る側が自分のバッファへコピーしてフラグを EMPTY に戻します。GPU のメモリのデータは、ホストの共有メモリを中継する 2 段のコピーで、1 回に最大 2 MiB (64 × 32 KiB) ずつ運ばれます。SAR に切り替わることで転送の段階がどれだけ長くなるかは、次の節で、切り替えをなくしたときの値と比べます。

## 問題: 転送スレッドが向く GPU

:::message
ここで、もとの目的に戻ります。分離推論では、prefill が作った KV cache を、decode へすばやく渡す必要があります。この受け渡しにかかる時間は、最初のトークンが出るまでの時間 (TTFT) に入るからです。問題は、この受け渡しの送る側で起きます。prefill の TP rank 1 では、転送スレッドが別の GPU を向いているため、CUDA IPC の準備に失敗し、ホストのメモリを中継する SAR に切り替わります。測った構成 (NIXL 1.1.0、shm を使う設定、page size 1、1 秒に 1 件) では、SGLang が記録する KV の転送の段階 (`prefill_transfer_kv_cache`) の平均が、そのままで 1,886 ms、転送スレッドに正しい GPU を指定する 1 行を SGLang に足すと 461 ms でした。どちらも 1 回の測定の値で、それぞれ 37 件と 39 件の平均です。1,886 ms は、「調べたケース」の節の 1,776 ms と同じ構成を別の回に測ったもので、461 ms はそれと同じ回に、SGLang に 1 行を足して測ったものです。元の構成どうしでも 1,776 ms と 1,886 ms の違いがあるので、比べるのはこの 2 つのあいだだけにします。
:::

![TP rank 1 のプロセスでは、メインのスレッドは 1 番の GPU を向くが、転送スレッドは何も設定しないので 0 番の GPU のコンテキストで動く。0 番のコンテキストではバッファのアドレスが見つからず、SAR に落ちる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/741e79cf2e9bf2/zenn/articles/741e79cf2e9bf2/thread-device.png)
*問題: prefill の TP rank 1 では、転送スレッドが 0 番の GPU のコンテキストのまま、1 番の GPU のデータを送ろうとします*

CUDA の runtime API は、いま使う GPU をホストのスレッドごとに覚えていて、これを current device と呼びます。`cudaSetDevice` を呼ばないスレッドでは、[0 番の GPU が既定になります](https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/multi-gpu-systems.html#device-selection)。一方、`cuMemGetAddressRange` のような driver API は、そのスレッドで有効な CUDA のコンテキスト (context) の中でアドレスを探します。コンテキストは GPU ごとに作られ、その GPU で確保したメモリを管理します。

SGLang の各プロセスのメインのスレッドは、[初期化のときに自分の GPU を選びます](https://github.com/sgl-project/sglang/blob/5a15cde858ea09b77116212a39356f2fc51b8584/python/sglang/srt/model_executor/model_runner.py#L1191)。一方、NIXL の転送を発行するスレッドは、あとから [`threading.Thread` で作られます](https://github.com/sgl-project/sglang/blob/5a15cde858ea09b77116212a39356f2fc51b8584/python/sglang/srt/disaggregation/nixl/conn.py#L291-L295)。このスレッドで動く [`transfer_worker`](https://github.com/sgl-project/sglang/blob/5a15cde858ea09b77116212a39356f2fc51b8584/python/sglang/srt/disaggregation/nixl/conn.py#L563) は、GPU を選びません。

TP rank 0 の KV cache は 0 番の GPU にあるので、たまたま向きが合います (ただし、上の再現の手順で要求を続けたときは、TP rank 0 からも少数の警告が出ており、その理由は調べていません)。TP rank 1 では、転送スレッドが 0 番の GPU を向いたまま、1 番の GPU にある KV cache の書き込みを発行します。0 番のコンテキストの中では 1 番の GPU のアドレスが見つからず、ハンドルを作れないと考えられます。ただし、どの呼び出しで 0 番のコンテキストが有効になったかまでは確かめていません。

NIXL 1.1.0 で shm を使ったまま、起動したばかりのエンジンに 8,192 トークンの要求を 1 つ送りました。すると prefill の TP rank 1 のプロセスから、`Failed to perform cuMemGetAddressRange: CUDA_ERROR_NOT_FOUND` の警告がちょうど 27 行、SAR への切り替えの警告が 1 行出ました。切り替えの警告は 1 回しか出ないので、この 2 つの行数から、SAR に落ちたのが 1 回だけだとは言えません。

SGLang の [`transfer_worker`](https://github.com/sgl-project/sglang/blob/5a15cde858ea09b77116212a39356f2fc51b8584/python/sglang/srt/disaggregation/nixl/conn.py#L563) の最初に、`torch.cuda.set_device(self.kv_args.gpu_id)` を呼ぶ 1 行を足すと、同じ要求を送っても、続けて 1 秒に 2 件の割合で 40 件の要求を流しても、どちらの警告も出ませんでした。

2026 年 10 月 19 日に確かめた時点で、この転送スレッドについての SGLang の Issue はありません。近い修正でマージ済みの [sgl-project/sglang#38774](https://github.com/sgl-project/sglang/pull/38774) は、NIXL のバックエンドを作るスレッドで GPU を選ぶようにしたもので、main ブランチの `transfer_worker` は、まだ GPU を選んでいません。

## 直し方 1: shm を使わない設定

直し方 1 は、SGLang のプロセスを起動する前に、環境変数 `FI_EFA_ENABLE_SHM_TRANSFER=0` を設定するものです。efa プロバイダは、同じノードの相手にも shm に任せず、EFA の装置で RDMA の書き込みをします。

この設定が効くのは、efa プロバイダの中に [shm の経路そのものが作られない](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/efa/src/efa_shm.c#L68-L77)からです。問題の失敗は、shm が CUDA IPC の準備をするときに起きるので、shm を通らなければ、その準備も SAR への切り替えも起きません。SGLang の転送スレッドが GPU を選ばないことは、この設定でも変わりません。

測った構成 (NIXL 1.1.0、page size 1、1 秒に 1 件) では、KV の転送の段階の平均は、shm を使う既定の設定の 1,776 ms から 196 ms になり、TTFT の中央値は 2,453 ms から 1,376 ms になりました。

shm を使わない設定で本当に EFA の装置を通るのかを、装置のカウンタで確かめました。`rdma_write_bytes` は、libfabric や NIXL の機能ではなく、EFA の装置が数えているカウンタです。装置が RDMA の書き込みで送ったバイト数を、Linux の EFA ドライバが[統計の項目として登録し](https://github.com/torvalds/linux/blob/v6.12/drivers/infiniband/hw/efa/efa_verbs.c#L49-L86)、カーネルの RDMA の共通部分 (RDMA core) が、それを sysfs のファイルとして[見せます](https://github.com/torvalds/linux/blob/v6.12/drivers/infiniband/core/sysfs.c#L1006-L1025)。ファイルの場所は、下の図のいちばん上に示しました。パスに `infiniband` とありますが、EFA は InfiniBand の装置ではありません。Linux の RDMA の仕組みはもともと InfiniBand のために作られたので、分類の名前が今も [`infiniband`](https://github.com/torvalds/linux/blob/v6.12/drivers/infiniband/core/device.c#L537) のままで、EFA のドライバも RDMA の装置として[ここに登録されます](https://github.com/torvalds/linux/blob/v6.12/drivers/infiniband/hw/efa/efa_main.c#L453)。このファイルは装置が書き込むものではありません。読むたびに、カーネルが EFA ドライバを通して装置にその時点の値を[問い合わせ](https://github.com/torvalds/linux/blob/v6.12/drivers/infiniband/hw/efa/efa_verbs.c#L2138-L2201)、その値を返します。ただし、前の問い合わせから約 [10 ms](https://github.com/torvalds/linux/blob/v6.12/include/rdma/ib_verbs.h#L614) 以内に読むと、[前の値をそのまま返します](https://github.com/torvalds/linux/blob/v6.12/drivers/infiniband/core/sysfs.c#L814-L827)。

![いちばん上に sysfs のファイルの場所 /sys/class/infiniband/<device>/ports/1/hw_counters/rdma_write_bytes がある。確認用の Pod がこのファイルを読むと、カーネルの RDMA core と EFA ドライバを通して EFA の装置にカウンタを問い合わせ、その時点の値が返る。測った構成のエンジンの Pod (ホストのネットワークを使わない) の中からはカウンタが見えない。shm を使わない設定では、KV cache が RDMA の書き込みで EFA の装置を通る。結果は、shm を使う設定で 0、shm を使わない設定で 8,663,389,312 バイト増え、計算した KV の量 8,663,334,912 バイトとの比は 1.0000063](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/741e79cf2e9bf2/zenn/articles/741e79cf2e9bf2/efa-counter.png)
*数えているのは EFA の装置で、EFA ドライバが登録し RDMA core が sysfs に出した値を、同じノードの別の Pod から読みました*

この記事の構成では、推論のエンジンを動かす Pod は、ホストのネットワークを使わない設定でした。この Pod の中からは、`hw_counters` のディレクトリが見えませんでした。同じノードに置いた、ホストのネットワークを使う Pod からは見えたので、その確認用の Pod から、負荷をかける前と後にすべてのカウンタを読んで差を取りました。負荷は、NIXL 1.1.0、page size 1 の構成に、平均して 1 秒に 1 件の割合で 15 秒のあいだ要求を送るものです。要求が届く間隔はばらつくため、この回は 15 件ではなく 17 件が届き、17 件すべてが完了しました。shm を使う既定の設定では、バイト数のカウンタはどれも 0 のままでした。shm を使わない設定では、`rdma_write_bytes` が 8,663,389,312 バイト増えました。

送るはずの KV cache の量は、モデルの設定から計算すると 8,663,334,912 バイトで、測った値との比は 1.0000063 です。負荷をかけない 20 秒にはカウンタが動かなかったことと合わせると、この測定の区間の KV cache の転送は、装置の RDMA の書き込みとして出たと読めます。差の 54,400 バイト (17 件で割ると 3,200 バイト) の内訳は分かっていません。

直し方 1 で問題の経路を通らないことは、実測とコードからの推論を分けて書きます。実測は 3 つです。shm を使わない設定で起動したエンジンのログには、`EFA will not use SHM for intranode communication because FI_EFA_ENABLE_SHM_TRANSFER=0` が出て、shm の行は 1 行も出ませんでした。「調べたケース」の節の「同じ構成を起動する手順」を shm を使わない設定で流すと、SAR への切り替えの警告も `cuMemGetAddressRange` の失敗の警告も 0 行でした。そして上で見たとおり、送るはずの KV cache とほぼ同じバイト数が、装置の RDMA の書き込みとして数えられました。一方、shm の経路が作られないことそのものは、上で示したコードの分岐から言えることで、shm の中を直接見て確かめたわけではありません。

:::details 測り方と計算
| 項目 | 中身 |
|---|---|
| 数えたもの | EFA の装置の `hw_counters` の全項目 (`rdma_write_bytes`、`rdma_write_recv_bytes`、`rdma_write_wrs`、`tx_bytes` など) |
| 読んだ場所 | 同じノードに置いた、ホストのネットワークを使う確認用の Pod から sysfs を読んだ |
| 負荷 | 入力 8,192 トークン・出力 256 トークンの要求を、平均 1 秒に 1 件の割合で 15 秒。届く間隔は指数分布でばらつき、この回は 17 件が届いて 17 件とも完了。NIXL 1.1.0、page size 1、TP 2 |
| 雑音の確認 | どちらの設定でも、測る直前に負荷をかけない 20 秒のあいだ、カウンタはどの項目も動かなかった |
| 送るはずの量 | 1 トークンあたり 27 層 × (512 + 64) × 2 バイト = 31,104 バイト。1 件、1 rank で × 8,192 トークン = 254,803,968 バイト。MLA の KV は 2 つの rank が同じものを送るので、× 2 rank × 17 件 = 8,663,334,912 バイト |
| 使った装置 | prefill と decode のどの rank も、Pod に割り当てた 1 台の装置を開き、その装置の中で折り返した。ノードのほかの装置のカウンタは 0。割り当てられる装置は Pod ごとに変わりうるので、ノードのすべての装置のカウンタを読んだ |
| 結果 | shm を使う既定の設定: 0。shm を使わない設定: 8,663,389,312 バイト (比 1.0000063)、RDMA の書き込みの回数 (`rdma_write_wrs`) は 17,836 回 (要求の数との対応は調べていない) |
:::

shm を使わない設定は、同じノードの中のほかの相手への libfabric の通信も装置に回すので、どの構成にも勧めるものではありません。参考として、負荷をかけずに NIXL 単体で 16 MiB を 1 回だけ送った測定では、装置を通る経路が 0.637 ms、CUDA IPC が 0.165 ms で、この 1 回の転送そのものは装置を通るほうが遅くなりました。負荷をかけた SGLang で shm を使わない設定のほうが短かった理由は、この 1 回の転送の速さでは説明できず、この記事では切り分けていません。

## 直し方 2: NIXL 1.4.0

![NIXL 1.1.0 では転送スレッドが 0 番の GPU のコンテキストのままハンドルが作れず SAR になる。NIXL 1.4.0 は送る前に登録時のコンテキストを設定し直すので、CUDA IPC になる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/741e79cf2e9bf2/zenn/articles/741e79cf2e9bf2/nixl140.png)
*直し方 2: NIXL 1.4.0 は、転送を発行するスレッドのコンテキストを、自分で合わせ直します*

NIXL 1.4.0 で問題が起きないのは、次の順に、TP rank 1 の転送スレッドが 1 番の GPU のコンテキストを向くようになるからです。

1. メモリを登録するとき、NIXL は KV cache のバッファを[持っているコンテキストを調べて](https://github.com/ai-dynamo/nixl/blob/c0a1102b94d173049a5478c23e765ba37681e2ca/src/plugins/libfabric/libfabric_backend.cpp#L225-L228)、[エンジンに 1 つ記録します](https://github.com/ai-dynamo/nixl/blob/c0a1102b94d173049a5478c23e765ba37681e2ca/src/plugins/libfabric/libfabric_backend.cpp#L254-L281)。TP rank 1 では、1 番の GPU のコンテキストです。
2. GPU のメモリから書き込みを出す前に、NIXL は、[書き込みを出すスレッドを](https://github.com/ai-dynamo/nixl/blob/c0a1102b94d173049a5478c23e765ba37681e2ca/src/plugins/libfabric/libfabric_backend.cpp#L1214-L1224)、記録したコンテキストに[切り替えます](https://github.com/ai-dynamo/nixl/blob/c0a1102b94d173049a5478c23e765ba37681e2ca/src/plugins/libfabric/libfabric_backend.cpp#L284-L290) (`cuCtxSetCurrent`)。これは既定の設定で、1 つのプロセスが 1 つの GPU だけを登録している場合の動きです。書き込みを出すのは、NIXL を呼んだ SGLang の転送スレッドです。
3. そのあと同じスレッドの上で、shm が IPC ハンドルを作る[準備の中で](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_ep.c#L313-L330)、libfabric の [`cuMemGetAddressRange`](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/src/hmem_cuda.c#L440-L457) が呼ばれます。スレッドのコンテキストが KV cache のある GPU と合っているので、測った構成では、この呼び出しが失敗しなくなりました。
4. ハンドルの準備が失敗しないので、[SAR への切り替え](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_ep.c#L722-L728)の分岐に入りません。

NIXL 1.1.0 も、登録のときに[同じようにコンテキストを記録します](https://github.com/ai-dynamo/nixl/blob/05e4243f5ed305a245912361ace20ba354ec0808/src/plugins/libfabric/libfabric_backend.cpp#L714-L724)。ただし、それを設定するのは[登録の処理の中](https://github.com/ai-dynamo/nixl/blob/05e4243f5ed305a245912361ace20ba354ec0808/src/plugins/libfabric/libfabric_backend.cpp#L767-L772)だけで、書き込みを出す前には設定し直しません。書き込みの前に設定し直す処理は、[ai-dynamo/nixl#1581](https://github.com/ai-dynamo/nixl/pull/1581) の変更に含まれています。直ったのは NIXL の側で、SGLang の転送スレッドのコードは変わっておらず、自分では GPU を指定しないままです。

この動きは[既定で有効です](https://github.com/ai-dynamo/nixl/blob/c0a1102b94d173049a5478c23e765ba37681e2ca/src/plugins/libfabric/libfabric_backend.cpp#L425-L431)。ただし、登録のときに 1 つのプロセスが複数の GPU を使うと[分かった場合](https://github.com/ai-dynamo/nixl/blob/c0a1102b94d173049a5478c23e765ba37681e2ca/src/plugins/libfabric/libfabric_backend.cpp#L895-L925)は、代わりに[書き込みのたびに `cudaSetDevice` で GPU を合わせます](https://github.com/ai-dynamo/nixl/blob/c0a1102b94d173049a5478c23e765ba37681e2ca/src/plugins/libfabric/libfabric_backend.cpp#L1226-L1232)。

測った構成では、各プロセスは自分の GPU だけを登録するので、複数の GPU を使うという判定にはならず、ログの「Multi-GPU detected」は 0 行でした。働いたのは、登録時のコンテキストを設定し直す動きのほうです。これにより、SGLang を直さなくても、TP rank 1 でハンドルを作れるようになりました。測った結果は次のとおりで、どちらもログの行の数です。NIXL 1.1.0 で shm を使う設定のまま、seed を 3 通り、1 秒あたりの要求の数を 5 通りに変えて負荷をかけたあとのログには、`cuMemGetAddressRange` の失敗の警告が 2 万行以上あり、すべて prefill の TP rank 1 から出ていました。NIXL 1.4.0 では、同じ設定で同じ 15 通りの負荷を 3 回流したあとのログに、この警告も SAR への切り替えの警告も、1 行もありませんでした。ここでは行の数どうしではなく、警告が出たか出なかったかを比べます。転送の段階の時間は、1 秒に 1 件、page size 1 で 533 ms (34 件の平均) でした。SGLang に 1 行を足した NIXL 1.1.0 の 461 ms と同じ程度ですが、別の回の 1 回ずつの測定なので、この差の大きさまでは比べられません。

ただし、直し方 2 は shm の経路そのものは使い続けます。shm の経路には、SAR とは別の遅れが残ることがあります。直し方 2 の 533 ms は直し方 1 の 196 ms より長く、その差がどこから来るかは、この記事では調べていません。

## 4 つの組み合わせの値

最後に、NIXL の版と shm の設定の 4 つの組み合わせで測った値を並べます。元の構成は NIXL 1.1.0 で shm を使う設定、直し方 1 は NIXL 1.1.0 で shm を使わない設定、直し方 2 は NIXL 1.4.0 で shm を使う設定、両方は NIXL 1.4.0 で shm を使わない設定です。どれも page size 1 です。

| 組み合わせ | 1 秒に 1 件の転送の段階の平均 ms | 1 秒に 2 件の転送の段階の平均 ms | 経路 | 1 秒に 1 件の TTFT の中央値 ms | 1 秒に 1 件の TTFT の p99 ms |
|---|---|---|---|---|---|
| 元の構成 | 1,776 | 測定中 | CUDA IPC と SAR | 2,453 | 6,294 |
| 直し方 1 | 196 | 495 | EFA | 1,376 | 3,175 |
| 直し方 2 | 533 | 664 | 測定中 | 2,410 | 4,391 |
| 両方 | 267 | 614 | 測定中 | 1,389 | 3,175 |

負荷は、平均して 1 秒に 1 件か 2 件です。転送の段階は、SGLang が記録する時間を、構成ごとに 1 回の測定で平均した値です。平均に使った記録の数は、1 秒に 1 件の各行で 34〜59、1 秒に 2 件を測った 3 行で 56〜75 です。TTFT は、要求を送ってから最初のトークンが返るまでの時間で、20 秒の負荷を 3 つの seed で流して合わせた 66 件から求めました。p99 は、遅いほうから 1% の境目の値です。66 件の p99 は最も遅い 1 件に近い値で決まるので、p99 の差は参考の値です。

経路の列は、prefill から decode へ KV cache を運んだ経路です。表の時間を測った回とは別の回で、次のように判定しました。元の構成では、rank 0 が主に CUDA IPC、rank 1 が SAR でした。SAR は、libfabric のログに出る SAR への切り替えの警告と `cuMemGetAddressRange` の失敗の警告を、どの rank のプロセスが出したかで見ました。元の構成では、どちらの警告も prefill の rank 1 から出ました。さらに、別の回に 1 秒に 0.25 件と 2 件の負荷をかけ、IPC ハンドルを作る `cudaIpcGetMemHandle` の呼び出しを eBPF の uprobe で数えると、prefill の rank 0 だけで呼ばれ、rank 1 では 1 回も呼ばれませんでした。ただし、再現の手順で同じエンジンに要求を続けたときは、rank 0 からも切り替えの警告が 1 行出ているので、rank 0 がいつも CUDA IPC だとまでは言えません。EFA は、装置のカウンタ `rdma_write_bytes` の増分を、モデルの設定から計算した KV cache の量と比べて見ました。直し方 1 では、15 秒で 17 件を送った別の回で 8,663,389,312 バイト増え、計算値との比は 1.0000063 でした。shm を使う元の構成では、増分は 0 でした。

行ごとに別の回の測定なので、近い値どうしの小さな差は比べていません。1 秒に 1 件では、転送の段階は、どちらの直し方でも元の構成より短くなりました。一方 TTFT の中央値は、shm を使わない 2 つの行で短くなり、直し方 2 では元の構成とほとんど変わりませんでした。直し方 2 で中央値が縮まらない理由は、この記事では調べていません。

## まとめ

同じノードの相手へ NIXL の LIBFABRIC バックエンドで KV cache を送ると、libfabric の efa プロバイダは、既定では shm プロバイダに任せます。測った構成では、prefill の TP rank 1 で SGLang の転送スレッドが別の GPU を向いているため、CUDA IPC の準備に失敗して SAR に切り替わっていました。転送スレッドの最初で GPU を指定する 1 行を SGLang に足すと、SAR への切り替えは起きなくなり、同じ組の測定で KV の転送の段階の平均は 1,886 ms から 461 ms になりました (NIXL 1.1.0、page size 1、1 秒に 1 件)。2026 年 10 月 19 日の時点で、この件の SGLang の Issue はありません。

SGLang を変えずに KV の転送の段階を短くする方法は 2 通りです。1 つ目は shm を使わない設定で、同じノードの相手にも EFA の装置で RDMA の書き込みをします。転送の段階は 1,776 ms から 196 ms になりました。ただし、同じノードの中のほかの libfabric の通信も装置に回るので、どの構成にも勧めるものではありません。2 つ目は NIXL 1.4.0 で、shm の経路のまま SAR への切り替えを避けます。転送の段階は 533 ms でした。
