## はじめに

GPUDirect Storage（GDS）は、ストレージから GPU のメモリへ、CPU のメモリを通さずにデータを送る NVIDIA の仕組みです。KvikIO は、GDS を Python から使うためのライブラリで、NVIDIA の RAPIDS が出しています。この記事は、[NVIDIA の解説記事](https://developer.nvidia.com/blog/how-to-read-data-into-gpu-memory-in-python-with-nvidia-gpudirect-storage/)を前提に、GDS がどの部品でできていて、直接の転送が何を条件に成り立つかを整理します。説明は資料だけでなく、ソースと実機のログでも確かめました。

| 項目 | この記事で整理すること | 実務での意味 |
|---|---|---|
| [GPU への 2 本の道](#gpu-への-2-本の道) | 消えるのは CPU のメモリでの中継です | CPU が読み込みを頼む仕事は残ります |
| [GDS の層](#gds-の層) | KvikIO、cuFile、カーネル、ドライバ、装置の受け持ちです | どこで直接の道が決まるかが分かります |
| [nvidia-fs 方式](#nvidia-fs-方式) | GDS に対応した NVMe のドライバが、宛先を GPU に差し替えます | 対応したドライバが要ります |
| [P2PDMA 方式](#p2pdma-方式) | Linux のカーネルが、装置どうしの転送を許すかを決めます | PCIe のつながり方で決まります |
| [2 段の切り替え](#2-段の切り替え) | 直接送れないと、KvikIO か cuFile が中継します | 読み込みが成功しても直接とは限りません |
| [確かめ方](#直接送れたかの確かめ方) | 回数とログで見分けます | 速さでは見分けません |
| [AWS の構成](#aws-で-gds-が使える構成) | AWS は FSx for Lustre と一部の GPU インスタンスを対応としています | p4d.24xlarge のインスタンスストアでは止まりました |

## GPU への 2 本の道

GDS が省くのは、CPU のメモリを中継に使う読み込みです。ここでのストレージは、NVMe という規格でつながる SSD です。普通に読むと、SSD がデータをまず CPU のメモリに書きます。次に、GPU を動かす NVIDIA のソフトウェアである CUDA が、そのデータを GPU のメモリへもう一度写します。GDS を使うと、SSD が GPU のメモリへ直接書き込みます。

![左は SSD が CPU のメモリに書き、CUDA が GPU へ写す普通の読み込み、右は SSD が GPU のメモリへ直接書き込む GDS の読み込み](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/3335e5d9e6ee14/zenn/articles/3335e5d9e6ee14/two-paths.png)

装置が CPU の手を借りずに、自分でメモリへデータを書き込む仕組みを DMA と呼びます。どちらの道でも、読み込みを頼み、終わりを確かめるのは CPU です。**GDS で消えるのは、CPU のメモリを通る中継です。** その分、CPU のメモリの帯域も使わずに済みます。

## GDS の層

GDS は、5 つの層のソフトウェアと、その下の SSD が、順に仕事を渡して動きます。アプリケーションが KvikIO に読み込みを頼み、KvikIO が GDS の本体である cuFile というライブラリを呼びます。cuFile とカーネルの部品が GPU のメモリを書き込み先として用意し、ファイルシステムと NVMe のドライバが SSD に命令を出し、データを実際に運ぶのは SSD です。カーネルは OS の中心で、装置を動かすプログラムです。

![アプリケーション、KvikIO、cuFile、カーネルの部品、ファイルシステムと NVMe のドライバが縦に並び、最後に SSD が GPU のメモリへ直接書き込む](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/3335e5d9e6ee14/zenn/articles/3335e5d9e6ee14/parts.png)

| 層 | 受け持ち |
|---|---|
| アプリケーション | どのファイルのどこを、GPU のどのメモリに読むかを決めます |
| KvikIO | Python から cuFile を呼ぶ窓口です。大きな読み込みを既定で 4 MiB ずつに分けて頼みます。既定の設定では、cuFile が使えないときは自分で中継して読みます |
| cuFile | GPU のメモリを読み込み先にして、カーネルに読み込みを頼みます。直接送れないと分かったときは、設定で許していれば中で中継します |
| カーネルの部品 | GPU のメモリを、読み込みの書き込み先として扱えるようにします。nvidia-fs 方式と P2PDMA 方式の 2 種類があります |
| ファイルシステムと NVMe のドライバ | ページキャッシュを通さない読み込み（O_DIRECT）の手順で、SSD に命令を出します |

カーネルの部品の 2 種類は、GPU のメモリの番地を SSD に渡す方法が違います。次の 2 節で、それぞれの流れを見ます。

## nvidia-fs 方式

通常の読み込みの経路では、ファイルシステムは書き込み先として CPU のメモリのページだけを扱います。nvidia-fs 方式は、この経路に GPU 宛ての読み込みを通す方式で、ファイルシステムには CPU のメモリのページに読むように見せかけ、最後の DMA の宛先だけを GPU のメモリに差し替えます。差し替えるのは、NVIDIA の nvidia-fs というカーネルモジュールと、GDS に対応した NVMe のドライバの組みです。カーネルモジュールは、カーネルにあとから組み込む部品です。

![cuFile が nvidia-fs に GPU のページを固定させ、データの入らない影のバッファを宛先に O_DIRECT の読み込みを流し、GDS に対応した NVMe のドライバが DMA の宛先を GPU の番地に差し替える](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/3335e5d9e6ee14/zenn/articles/3335e5d9e6ee14/nvfs-flow.png)

1. cuFile が nvidia-fs に、GPU のメモリを読み込み先として登録させます。nvidia-fs は NVIDIA のドライバの関数で GPU のページを固定し、その物理番地の一覧を持ちます（[nvfs-core.c](https://github.com/NVIDIA/gds-nvidia-fs/blob/6a65099b667e1838109952a87dcc6c9414ebf81f/src/nvfs-core.c#L1246-L1251)）。
2. nvidia-fs は、CPU のメモリに「影のバッファ」（shadow buffer）を用意し、そこを宛先にしてファイルシステムに O_DIRECT の読み込みを流します（[nvfs-core.c](https://github.com/NVIDIA/gds-nvidia-fs/blob/6a65099b667e1838109952a87dcc6c9414ebf81f/src/nvfs-core.c#L1006-L1009)）。影のバッファは見せかけの宛先で、データは入りません。
3. NVMe のドライバが DMA の宛先を作るときに nvidia-fs を呼び、影のバッファの番地を GPU のメモリの番地に差し替えます（[nvfs-dma.c](https://github.com/NVIDIA/gds-nvidia-fs/blob/6a65099b667e1838109952a87dcc6c9414ebf81f/src/nvfs-dma.c#L1411-L1462)）。
4. SSD は、その番地へ DMA で書き込みます。データは CPU のメモリを通りません。

3 の呼び出しを持つのは、GDS に対応した NVMe のドライバだけです。nvidia-fs は、NVMe のドライバが公開する登録の関数を名前で探して呼び、自分の差し替えの処理を渡します（[nvfs-mod.c](https://github.com/NVIDIA/gds-nvidia-fs/blob/6a65099b667e1838109952a87dcc6c9414ebf81f/src/nvfs-mod.c#L52-L54)）。Linux の標準の NVMe のドライバにはこの関数がなく、対応版は NVIDIA の MLNX_OFED や DOCA などで配られます（[gds-nvidia-fs の README](https://github.com/NVIDIA/gds-nvidia-fs/blob/6a65099b667e1838109952a87dcc6c9414ebf81f/README.md#L19-L25)、[GDS Overview Guide](https://docs.nvidia.com/gpudirect-storage/overview-guide/index.html)）。

## P2PDMA 方式

P2PDMA 方式は、宛先を差し替えるのではなく、GPU のメモリをはじめからカーネルのページとして登録しておく方式です。登録に使うのは、Linux に標準で入っている P2PDMA という、PCIe の装置どうしでデータを送るための仕組みです。こうすると、ファイルシステムも NVMe のドライバも、GPU のメモリをそのまま宛先として扱え、nvidia-fs も GDS 用の NVMe のドライバも要りません。cuFile は CUDA 12.8 から、この方式を NVMe で使えます。

![NVIDIA のドライバが GPU のメモリを BAR1 に固定して P2PDMA に登録し、O_DIRECT の読み込みがそのページを宛先にする。カーネルは共通の上流のブリッジ、許可されたホストブリッジ、AMD の Zen 世代以降の CPU のどれかに当たるときだけ許す](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/3335e5d9e6ee14/zenn/articles/3335e5d9e6ee14/p2pdma-flow.png)

1. NVIDIA のドライバが、GPU のメモリを装置から見える窓（BAR1）に固定で並べ、カーネルの P2PDMA に登録します。BAR1 は、PCIe の上で GPU のメモリを外から見るための番地の範囲です。この固定には、NVIDIA のオープンなドライバ 570 以降と、ドライバの設定 `RMForceStaticBar1=1;RmForceDisableIomapWC=1` が要ります（[Troubleshooting Guide の P2PDMA の節](https://docs.nvidia.com/gpudirect-storage/troubleshooting-guide/index.html)）。
2. O_DIRECT の読み込みは、登録された GPU のページを、普通のページと同じように宛先として受け取ります。
3. NVMe のドライバが DMA の宛先を作るとき、カーネルが GPU と SSD の PCIe のつながりを調べ、直接送ってよいかを決めます（[p2pdma.c の calc_map_type_and_dist](https://github.com/torvalds/linux/blob/v6.8/drivers/pci/p2pdma.c#L574-L660)）。
4. SSD は、GPU のメモリへ DMA で書き込みます。

3 の判定では、GPU と SSD が PCIe のスイッチのような共通の上流のブリッジの下にあり、その間で ACS（PCIe の通り道を見張る機能）が転送を CPU 側へ回していなければ、直接送れます。そうでない場合は、CPU 側の PCIe の入口であるホストブリッジを調べます。Linux v6.8 では、ホストブリッジの装置がカーネルの許可の一覧に載っているとき（一部の装置は、GPU と SSD が同じホストブリッジの下にあることも条件）と、CPU が AMD の Zen 世代以降のときに、送れます（[p2pdma.c の一覧](https://github.com/torvalds/linux/blob/v6.8/drivers/pci/p2pdma.c#L405-L444)）。cuFile の設定では、`properties.use_pci_p2pdma` と `block:nvme:use_pci_p2pdma` でこの方式を選びます（[Configuration Guide](https://docs.nvidia.com/gpudirect-storage/configuration-guide/index.html)）。この判定を通っても、実際の転送が成功するとは限りません。

| 条件 | nvidia-fs 方式 | P2PDMA 方式 |
|---|---|---|
| カーネルの部品 | nvidia-fs | Linux の P2PDMA（標準、カーネル 6.2 以降の Ubuntu） |
| NVMe のドライバ | GDS に対応した版 | 標準 |
| NVIDIA のドライバ | 通常の設定 | オープンなドライバ 570 以降と BAR1 を固定する設定 |
| PCIe のつながり | 直接の DMA が通ること | 共通の上流のブリッジの下で ACS が回していないか、許可されたホストブリッジか、AMD の Zen 世代以降の CPU |
| ファイルシステム | ext4 の `data=ordered` か XFS など | 同じ |

## 2 段の切り替え

直接送れないときに中継へ切り替える判定は、KvikIO と cuFile の 2 か所にあります。KvikIO はファイルを開くときに cuFile を使うかを決め、cuFile は読み込みのときに直接送るかを決めます。切り替え先は、CPU のメモリを中継する普通の読み込みです。この代わりの読み方を互換モード、英語で compatibility mode と呼びます。ファイルごとの切り替えはファイルを開くときに決まり、cuFile での読み込みが失敗したときに中継で読み直す仕組みはありません。16 KiB より小さい読み込みだけは、読み込みのたびに cuFile を通さない判定があります（[compat_mode_manager.cpp](https://github.com/rapidsai/kvikio/blob/6ddda9a1ad59e105723fab9348b3d4d262a56b76/cpp/src/compat_mode_manager.cpp#L71-L78)）。

![1 段目で KvikIO がファイルを開くときに cuFile を使うかを決め、2 段目で cuFile が直接送るか中継するかを決める。KvikIO の互換モードを切っていれば 1 段目は中継せずエラーに、cuFile が中継を許さなければ 2 段目もエラーになる。直接の転送を装置やカーネルが断った場合もエラーになる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/3335e5d9e6ee14/zenn/articles/3335e5d9e6ee14/two-stage.png)

1. KvikIO の互換モードが既定の AUTO のとき、KvikIO が cuFile を呼ぶかを決めます。cuFile のライブラリが見つからないときは、プロセスの全体で cuFile を呼びません。ファイルを O_DIRECT で開けないときや、cuFile に登録できなかったときは、そのファイルの読み込みに cuFile を使いません。どの場合も KvikIO 自身が中継して読みます。互換モードを切っていると、これらの場合は中継せずにエラーになります（[defaults.cpp](https://github.com/rapidsai/kvikio/blob/6ddda9a1ad59e105723fab9348b3d4d262a56b76/cpp/src/defaults.cpp#L193-L209)、[compat_mode_manager.cpp](https://github.com/rapidsai/kvikio/blob/6ddda9a1ad59e105723fab9348b3d4d262a56b76/cpp/src/compat_mode_manager.cpp#L40-L82)）。
2. cuFile が、直接送るかを決めます。前の 2 節の条件がそろわないと分かったとき、cuFile は中で中継して読みます。これが cuFile の互換モードで、cuFile の設定で許したときだけ働きます。直接の転送を試みて装置やカーネルが断った場合は、中継にならずにエラーになることがあります。

KvikIO が cuFile を呼んでも、2 段目で cuFile が中継することがあります。だから「cuFile を呼んだ」ことは、「GDS で直接送った」ことを意味しません。

## 直接送れたかの確かめ方

直接送れたかは、速さではなく、回数とログで確かめます。中継になっても読み込みは成功するので、速さだけでは原因を切り分けにくいからです。回数で見分けられるのは nvidia-fs 方式です。P2PDMA 方式の転送がどの回数に数えられるかは資料に書かれていないので、読み込みの結果と、cuFile とカーネルのログで確かめます。

![gdscheck で環境の対応を見て、KvikIO の互換モードを切って読み、cuFile の統計と nvidia-fs の回数を見る](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/3335e5d9e6ee14/zenn/articles/3335e5d9e6ee14/verify.png)

1. GDS に付いてくる gdscheck を `-p` を付けて動かします。NVMe と NVMe P2PDMA の行が、それぞれの方式に対応しているかを示します。Supported でも、実際の転送で断られることがあるので、次の手順でも確かめます。
2. KvikIO の互換モードを切り、cuFile の統計を取る設定で読みます。KvikIO が自分で中継した読み込みは cuFile を通らず、統計に数えられないからです。
3. 読み終わってもプログラムを残し、gds_stats で cuFile の回数を見ます。全体の回数 n のうち、cuFile が中継した回数が posix に数えられます。NVIDIA の解説記事は、残りを nvidia-fs で直接送った回数（nvfs）として見ています。nvidia-fs 自身の回数（`/proc/driver/nvidia-fs/stats` の Reads）も見られますが、中継と P2PDMA 方式の読み込みは数えません。失敗した読み込みも ok に数えられる場合があるので、io_state_err が 0 であることも合わせて見ます（[nvfs-core.c](https://github.com/NVIDIA/gds-nvidia-fs/blob/6a65099b667e1838109952a87dcc6c9414ebf81f/src/nvfs-core.c#L2079-L2113)）。

```bash
CUFILE_STATS_LEVEL=3 KVIKIO_COMPAT_MODE=off python3 -i read_with_kvikio.py
```

```bash
/usr/local/cuda/gds/tools/gds_stats -p "$(pgrep -n -f read_with_kvikio.py)" -l 3
```

断られたときは、cuFile のログとカーネルのログ（`dmesg`）に、どの層が断ったかが出ます。

:::details KvikIO の読み込みの例
NVIDIA の解説記事のコードを短くしたものです。ちょうど 1 GiB のファイルを用意してあり、CuPy という GPU の配列のライブラリが同じ大きさの書き込み先を作ります。上の 1 つ目のコマンドは、これを `read_with_kvikio.py` に保存した場合の書き方で、`-i` を付けると読み終わったあともプログラムが残ります。

```bash
dd if=/dev/urandom of=/mnt/nvme/data.bin bs=1M count=1024 oflag=direct
```

```python
import cupy as cp
import kvikio

buf = cp.empty(1 << 30, dtype=cp.uint8)
with kvikio.CuFile("/mnt/nvme/data.bin", "r") as f:
    n = f.read(buf)
assert n == buf.nbytes
```

既定では、16 KiB より小さい読み込みは cuFile を通らないので、統計を見るときは 4 KiB にそろえた大きな読み込みを使います（[file_handle.cpp](https://github.com/rapidsai/kvikio/blob/6ddda9a1ad59e105723fab9348b3d4d262a56b76/cpp/src/file_handle.cpp#L386-L392)）。NVIDIA の解説記事の環境では、1 GiB の読み込みの 256 回すべてが nvfs の側でした。
:::

## AWS で GDS が使える構成

AWS が GDS の対応を書いているのは、ネットワークの先の共有ファイルシステムを、対応する GPU インスタンスで読む構成です。共有ファイルシステムは FSx for Lustre で、EFA という AWS のネットワークの装置を有効にして作ります。この構成では、SSD の代わりに EFA が、GPU のメモリへ直接 DMA で書き込みます。GPU インスタンス側にも nvidia-fs を入れます。GPU インスタンスは、P5、P5e、P5en、P6-B200、P6-B300 です（[FSx for Lustre の EFA のページ](https://docs.aws.amazon.com/fsx/latest/LustreGuide/efa-file-systems.html)、[クライアントの設定](https://docs.aws.amazon.com/fsx/latest/LustreGuide/configure-efa-clients.html)、[AWS の ML ブログ](https://aws.amazon.com/blogs/machine-learning/accelerate-llm-model-loading-and-increase-context-windows-with-gpudirect-on-amazon-fsx-for-lustre-and-turboquant/)）。この一覧は、2026 年 11 月 8 日に確かめたものです。

![EC2 のインスタンスストアは AWS の対応の一覧になく、FSx for Lustre と P5、P5e、P5en、P6-B200、P6-B300 の組み合わせは AWS が対応を書いている](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/3335e5d9e6ee14/zenn/articles/3335e5d9e6ee14/where.png)

インスタンスに付いてくる SSD であるインスタンスストアは、この一覧にありません。[kvikio#941](https://github.com/rapidsai/kvikio/issues/941) でも、質問者が「AWS に確かめたところ、FSx for Lustre なしの GDS は EC2 では今のところ使えない」と書いて閉じています。

:::details コラム: p4d.24xlarge のインスタンスストアでは、どこで止まるか
p4d.24xlarge（A100 が 8 枚、us-east-1）のインスタンスストアで、両方の方式を前提条件までそろえて試しました。どちらも、ソフトウェアの準備は通り、別の場所で止まりました。

![nvidia-fs 方式は GPU の番地への差し替えまで進んだあと、NVMe の読み込みが「命令の中の指定が不正」で終わった。P2PDMA 方式は、カーネルがホストブリッジを許可の一覧で確かめられずに断った](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/3335e5d9e6ee14/zenn/articles/3335e5d9e6ee14/p4d-stops.png)

| 方式 | そろえた前提 | 止まった場所 | ログ |
|---|---|---|---|
| nvidia-fs 方式 | NVMe をモジュールにして組み直したカーネル 6.8.12、GDS に対応した NVMe のドライバ（DOCA の mlnx-nvme）、nvidia-fs 2.31 | 仮想マシンから見える NVMe のコントローラが、読み込みの命令に「命令の中の指定が不正」を返しました | `nvme0n1: I/O Cmd(0x2) ... I/O Error (sct 0x0 / sc 0x2)`、`nvidia-fs:read IO failed :-95` |
| P2PDMA 方式 | NVIDIA のドライバの `RMForceStaticBar1=1;RmForceDisableIomapWC=1` | カーネルの P2PDMA の判定が断りました | `cannot be used for peer-to-peer DMA as the client and provider (0000:90:1c.0) do not share an upstream bridge or whitelisted host bridge` |

nvidia-fs 方式では、gdscheck の NVMe の行は Supported になりました。nvidia-fs は GPU のページを固定し、DMA の宛先を GPU の番地に差し替えるところまで進みました。そのあと NVMe のコントローラが返した状態は、NVMe の規格の「命令の中の指定が不正」（Invalid Field in Command、sc 0x2）でした（[NVMe Base Specification 2.4](https://nvmexpress.org/wp-content/uploads/NVM-Express-Base-Specification-Revision-2.4-Ratified-2026.07.31.pdf)）。同じ SSD で宛先を CPU のメモリにすると、2.0 GiB/s で読めました。このコントローラは、仮想マシンの中から Amazon の NVMe SSD Controller として見えています。どの層がこの状態を返したかは、仮想マシンの中からは分かりません。

P2PDMA 方式でも、gdscheck の NVMe P2PDMA の行は Supported になりました。実際の読み込みでは、GPU と SSD が同じバス（0000:90）に並んでいても、カーネルが断りました。仮想マシンの中から見ると、このバスには GPU 2 枚（1c.0 と 1d.0）と SSD 2 台（1e.0 と 1f.0）の 4 つだけが並び、最初の装置は GPU です。PCIe のスイッチもホストブリッジの装置もありません。CPU は Intel の Xeon Platinum 8275CL で、AMD の特別扱いにも当たりません。カーネルは、ホストブリッジの装置を、バスの最初の装置が 00.0 の番号か Root Port のときだけ見つけます。この場合は見つからないので、許可の一覧を引けずに断ります（[p2pdma.c の pci_host_bridge_dev](https://github.com/torvalds/linux/blob/v6.8/drivers/pci/p2pdma.c#L465-L500)）。

AWS が提供するカーネル（7.0.0-1014-aws と 6.8.0-1069-aws）は、NVMe のドライバを本体に組み込んでいます（`CONFIG_NVME_CORE=y` と `CONFIG_BLK_DEV_NVME=y`）。そのため、そのままでは GDS に対応した NVMe のドライバに差し替えられず、NVMe をモジュールにしたカーネルを組み立て直しました。今回使った AMI（ami-06d20c922ee616e37）は、`GRUB_FORCE_PARTUUID` の設定で initrd を使わずに起動していたので、このカーネルではその設定を外す必要がありました。
:::

:::details コラム: 中継になったときの KvikIO の速さと CPU
同じ p4d.24xlarge の標準のカーネルで、KvikIO は cuFile の中で中継して読みました。1 回に約 100 MB の連続した範囲を 8 つ、まとめて 1 枚の GPU へ読んだ値です。比べる相手は、O_DIRECT で読み、ピン留めした CPU のメモリから 1 回で GPU へ写す読み方です。ピン留めは、OS が動かさないように固定した CPU のメモリです。

| 読み方 | 速さ | 使った CPU |
|---|---|---|
| KvikIO（cuFile の中で中継）、スレッド 1 本（既定） | 2.4 GB/s | 0.4 コア |
| KvikIO、スレッド 4 本 | 7.3 GB/s | 1.2 コア |
| KvikIO、スレッド 16 本 | 11.2 GB/s | 10.6 コア |
| 比べる相手（O_DIRECT とピン留め）、スレッド 16 本 | 12.2 GB/s | 1.5 コア |

読んだのは RAID0 にまとめた 7 台の SSD で、KvikIO は 26.10、cuFile は 1.15、KvikIO の仕事の大きさは既定の 4 MiB です。測る前にページキャッシュを捨て、5 回の慣らしのあと 100 回を、GPU への読み込みが終わるまで含めて測りました。測定は 2026 年 11 月 8 日に 1 回ずつ行いました。CPU の値は、測ったプロセスの全スレッドが使った CPU の時間を、かかった時間で割ったものです。この条件では、中継になった KvikIO はスレッドを増やすと速さが近づきますが、同じくらいの速さで CPU を約 7 倍使いました。
:::

## まとめ

GDS の直接の転送は、nvidia-fs 方式なら GDS に対応した NVMe のドライバが宛先を GPU に差し替え、P2PDMA 方式ならカーネルが PCIe のつながりを見て許すことで成り立ちます。どちらも最後は装置と PCIe のつながりが受け入れる必要があり、直接送れたかは KvikIO の互換モードを切って、読み込みの結果と回数とログで見分けます。

P2PDMA 方式の読み込みがどの回数に数えられるかと、p4d.24xlarge で NVMe のエラーを返した層は、まだ分かっていません。

| 次に確かめること | 確かめ方 |
|---|---|
| AWS が対応としている構成で、直接の読み込みになるか | P5 系と EFA を有効にした FSx for Lustre で、gds_stats とカーネルのログを見る |
| P2PDMA 方式で直接送れたときの回数の出方 | P2PDMA 方式が通る環境で、gds_stats の n と posix を見る |
