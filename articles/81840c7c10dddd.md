## はじめに

この記事は [Forward Override パターンの記事](https://zenn.dev/tosshi/articles/53cc505a8d85e2)の続きで、音声合成モデル XTTS v2 を題材に、カスタムモデルを NxD Inference に載せるときに自分で書くインタフェースと、そのときに守る決まりを図でまとめます。XTTS v2 に固有の部分と実測は、[実装編](https://zenn.dev/tosshi/articles/ffc359901ea1cc)で扱います。実装は [littlemex/samples の xttsv2-nxd-inference](https://github.com/littlemex/samples/tree/b6334caf1f46c549bb58905a7a39000d5aba5db2/ml_distributed_experiment_collection/xttsv2-nxd-inference) にあり、Neuron の無い CPU の上でも、スタブを使って動きを確かめられます。

## 3 つのインタフェース

![NeuronApplicationBase、ModelWrapper、BaseModelInstance の 3 つで、書くのは数個のメソッドだけ。compile、load、重みの分割、KV の書き戻しは NxD Inference が受け持つ](/images/81840c7c10dddd-interfaces.png)

NxD Inference は、コンパイル、ロード、推論の共通の処理を持っています。モデルごとに違う「どの nn.Module を使うか」「KV キャッシュをどこに書き戻すか」「どの形の入力でコンパイルするか」を伝えるのが、次の 3 つのインタフェースです。

| インタフェース | このサンプルで書くもの | NxD Inference が受け持つもの |
| --- | --- | --- |
| [`NeuronApplicationBase`](https://github.com/aws-neuron/neuronx-distributed-inference/blob/v0.7.14366/src/neuronx_distributed_inference/models/application_base.py) | `forward()`、`get_state_dict()`、config のクラス、Hugging Face 用の 2 つのメソッド（使わないなら 1 行） | compile、load、load_weights、Tensor Parallel の分割 |
| [`ModelWrapper`](https://github.com/aws-neuron/neuronx-distributed-inference/blob/v0.7.14366/src/neuronx_distributed_inference/models/model_wrapper.py) | `input_generator()`（コンパイルに使う入力）、`get_model_instance()`、`forward()` | バケットの管理、コンパイルの呼び出し |
| [`BaseModelInstance`](https://github.com/aws-neuron/neuronx-distributed-inference/blob/v0.7.14366/src/neuronx_distributed_inference/models/model_wrapper.py) | `load_module()`（nn.Module を作る）、`get()`（nn.Module と aliases を返す）。このサンプルは基底クラスの `__init__()` を呼ばず、`module` と `input_output_aliases` を自分で初期化する | aliases を付けたトレース、KV の書き戻し |

ModelWrapper が BaseModelInstance を作り、BaseModelInstance が nn.Module と aliases を返します。prefill と decode を別々の Application にする場合は、普通の Python のクラス（コーディネーター）を足します。コーディネーターは 2 つの Application の `compile()`、`load()`、`load_weights()` を順に呼び、`forward()` では入力の長さで 2 つを呼び分けます。自分でコンパイルするモデルは持たないので、`NeuronApplicationBase` を継承しない普通のクラスにします。prefill の KV を decode 側へ写す `sync_kv_cache_prefill_to_decode()` は、`forward()` からは呼ばれません。呼ぶ側が、prefill のあと最初の decode の前に明示的に呼びます。

## コンパイルする範囲を決める

![XTTS v2 で Neuron に載せるのは GPT デコーダだけで、前処理、出力層、HifiDecoder は CPU に残す](/images/ffc359901ea1cc-xtts-structure.png)

最初に、モデルのどこを Neuron でコンパイルし、どこを CPU に残すかを決めます。この境界の入力と出力の形が、そのまま `input_generator()` と `forward()` の仕様になるからです。XTTS v2 では、層の数 30 はそのままに幅と系列の長さを 4 分の 1 に縮めた CPU の計測で、GPT デコーダが時間の 89.8% を占めました。これは目安で、元の大きさや Trainium の上での時間の配分を測ったものではありません。そこで 30 層の GPT デコーダだけをコンパイルし、入力は埋め込み `[B, seq_len, 1024]`、出力は隠れ状態 `[B, seq_len, 1024]` にしました。範囲を決めるときは、次の 4 点を見ます。

- 全体の時間のどれだけを占めるか（実際に測って決める）
- 入力と出力の形をコンパイル時に固定できるか
- Python の分岐やループが多い処理は CPU に残せるか
- 使う演算が Neuron のコンパイラで使えるか（公式のドキュメントの Operator Support で確かめる）

## コンパイルから推論までの流れ

![compile は設定ごとに一度、load と load_weights は起動のたびに行い、自分で書く get_state_dict() はコンパイルでは形だけの仮の重み、load_weights では実際の重みを返す](/images/81840c7c10dddd-lifecycle.png)

コンパイルとロードは別のプロセスで走ることもあるので、層の数や `max_seq_len` のようなモデルの形は [`InferenceConfig`](https://github.com/aws-neuron/neuronx-distributed-inference/blob/v0.7.14366/src/neuronx_distributed_inference/models/config.py) のサブクラスに持たせ、両方に同じものを渡します。この実装では `max_seq_len` が KV キャッシュの長さで、埋め込みの入力の長さは prefill では `max_seq_len`、decode では 1、マスクはどちらも `[B, max_seq_len]` です。推論のときは、`input_generator()` が作った入力と同じ形、型、順番で渡します。`get_state_dict()` は compile と load_weights の両方から呼ばれ、コンパイルでは形だけの仮の重み（ほとんど 0 で、LayerNorm の重みは 1）を、load_weights では実際の重みを返します。compile は重みの分割の配置を決めるために重みの辞書を使うので、チェックポイントがまだ無くても正しい形の辞書が要り、実際の重みは起動のたびに load_weights が分割してデバイスに入れるからです。この切り替えはサンプル側の実装で、コーディネーターの `load_weights()` がチェックポイントのパスを config に書き込んでから、各 Application の `load_weights()` を呼びます。NxD の基底クラスはこのパスを書き込みません。Hugging Face Hub から読めるモデルなら、`load_hf_model()` を使う別の道があります。

## KV キャッシュは aliases で書き戻す

![forward() は隠れ状態と新しい KV をタプルで返し、aliases が出力の何番目をどの nn.Parameter に書き戻すかを決め、次のステップは書き戻された KV を読む。図は 30 層のうち最初の 3 層だけを描き、K は 1 番から、V は 31 番から並ぶ](/images/81840c7c10dddd-aliases-writeback.gif)

decode の各ステップで更新した KV を次のステップへ引き継ぐには、普通の PyTorch なら `forward()` の中で KV キャッシュを書き換えれば済みます。Neuron のコンパイラは `forward()` を固定のグラフにするので、この実装では新しい KV を `forward()` の戻り値のタプルに入れて返し、「何番目の出力をどのパラメータに書き戻すか」を aliases として渡します。ランタイムがそれを見て、デバイスの上の KV キャッシュに書き戻します。prefill から decode への受け渡しはこれとは別の処理で、コーディネーターが `.state` を使って写します。**KV キャッシュの持ち方は、この aliases の仕組みに合わせて決まります**。

- KV キャッシュは `nn.Parameter(requires_grad=False)` にして、モジュールのパラメータとして登録します。aliases は登録されたパラメータを書き戻す先として使うので、登録されない普通のテンソルの属性は使えません
- KV キャッシュの更新は、スライスへの代入ではなく `torch.scatter` で新しいテンソルを作ります。更新したテンソルを戻り値に入れて、aliases で書き戻すためです
- 戻り値は、隠れ状態、全層の K、全層の V の順に `(hidden_states,) + tuple(all_cache_k) + tuple(all_cache_v)` のように `+` でつなぎます。この実装は、`return a, *list_b` の形を torch.jit.script が受け付けないことを理由にしています（[modeling_gpt.py](https://github.com/littlemex/samples/blob/b6334caf1f46c549bb58905a7a39000d5aba5db2/ml_distributed_experiment_collection/xttsv2-nxd-inference/src/neuron_xttsv2/modeling_gpt.py)）
- `get()` で作る aliases の番号は、戻り値のタプルの並びと 1 つもずれてはいけません。30 層では K が 1〜30 番、V が 31〜60 番です。範囲の中で番号を取り違えると、番号の範囲だけを調べるテストでは見つからず、書き戻す先だけが狂って結果が壊れるので、各番号が指す KV まで照合します

## prefill と decode の分け方

![1 つの Application に 2 つの ModelWrapper を持たせて同じ nn.Module の KV を共有する方法と、2 つの Application に分けて KV を CPU 経由で写す方法](/images/81840c7c10dddd-prefill-decode-split.png)

バケットを使わない場合、1 つの ModelWrapper がコンパイルする入力の形は 1 つに固定されます。そのため prefill `[B, 1081, 1024]` と decode `[B, 1, 1024]` には ModelWrapper を 2 つ用意し、その置き場所に 2 つの方法があります。XTTS v2 の実装は方法 B で、prefill と decode を別々の Application にしています。

方法 A は、[Whisper の実装](https://github.com/aws-neuron/neuronx-distributed-inference/blob/v0.7.14366/src/neuronx_distributed_inference/models/whisper/modeling_whisper.py)のように 1 つの Application に 2 つの ModelWrapper を登録する方法です。同じ nn.Module の KV キャッシュを共有するので、KV を写す処理が要らず、デバイスの上の KV も 1 組で済みます。ただし、prefill と decode の区別を `self.models` に足した順番で付けるので、この順番の扱いが変わると、2 つのモデルの役割がずれます。

方法 B では、2 つの Application に名前が付き、KV の受け渡しをコーディネーターで明示的に書くので、prefill と decode を別の場所で動かす構成へ広げる余地もあります。代償は 2 つあります。KV キャッシュがデバイスの上に 2 組でき、prefill のたびに、各 rank と各層の K と V を CPU へ読み出して decode 側へ書き戻す処理を自分で書いて走らせます。0 で埋めた prefix より後ろの位置には K と V の bias から出た値が残るので、写す前にその位置を 0 にします。

## 守る決まりの一覧

この実装で守った決まりです。

| 決まり | なぜ | どうするか |
| --- | --- | --- |
| `get_state_dict()` に `cache_k` と `cache_v` を入れない | KV はランタイムが持ち、入れると重みの分割で形が合わない | `model.state_dict()` を使わず、重みだけの辞書を作る |
| Tensor Parallel のモデルで `state_dict()` をそのまま使わない | `parallel_state` が有効な間に呼ぶと分割済みの形が返り、さらに分割されて二重になる | 分割前の全体の形で辞書を作る |
| Application の `forward()` は `outputs[0]` だけを返す | nn.Module の `forward()` が返す KV は、aliases がデバイスの上に書き戻す | 呼ぶ側は隠れ状態だけを受け取る |
| load のあとは、`nxd_model` の `read_from_neuron_buffer` のような公開されていないメソッドを呼べない | TorchScript のオブジェクトになり、`@torch.jit.export` の無いメソッドは `AttributeError` になる | KV は公開されている `traced_model.nxd_model.state` から読み書きする |
| デバイスのテンソルに飛び飛びの代入をしない | XLA の制約で動かない | prefill の KV を CPU に読み出し、prefix より後ろの位置を 0 にしてから、decode 側の `.state` に `copy_()` する |
| CPU と Neuron の間で型をそろえる | bfloat16 でコンパイルしたモデルに float32 を渡すと型が合わない | 渡す前に bfloat16 に、受け取ったら float32 に戻す。位置とマスクはサンプルの入力と同じ整数の型にする |
| この 30 層の GPT は BF16 にした | FP16 では後ろの層の attention があふれ、同じトークンを繰り返した | BF16 でコンパイルし、出力を比べて確かめる |
| 1 つの形で足りるならバケットを増やさない | バケットの数だけコンパイルの時間が増える | `bucket_config = None` のままにする |

CPU との型の変換、生成の品質、音声のストリーミングは、[実装編](https://zenn.dev/tosshi/articles/ffc359901ea1cc)で扱います。

- return タプルの長さが `1 + n_layer * 2`（hidden_states + cache_k 全層 + cache_v 全層）になります


## まとめ

この XTTS v2 の実装では、3 つのインタフェースを通して、入力の形、重み、KV を書き戻す先を NxD Inference に渡しました。要点は、aliases と出力の順番をそろえること、コンパイル用の仮の重みと実際の重みを切り替えること、prefill と decode の分け方に応じて KV を共有するか写すかを決めることです。
