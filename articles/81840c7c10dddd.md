## はじめに

この記事は [Forward Override パターンの記事](https://zenn.dev/tosshi/articles/53cc505a8d85e2)の続きで、音声合成モデル XTTS v2 を題材に、カスタムモデルを NxD Inference に載せるときに自分で書くインタフェースと、そのときに守る決まりを図でまとめます。XTTS v2 に固有の部分と実測は、[実装編](https://zenn.dev/tosshi/articles/ffc359901ea1cc)で扱います。実装は [littlemex/samples の xttsv2-nxd-inference](https://github.com/littlemex/samples/tree/b6334caf1f46c549bb58905a7a39000d5aba5db2/ml_distributed_experiment_collection/xttsv2-nxd-inference) にあり、Trainium や Inferentia の無い CPU のマシンでも、スタブを使って動きを確かめられます。

## 3 つのインタフェース

![NeuronApplicationBase、ModelWrapper、BaseModelInstance の 3 つで、書くのは数個のメソッドだけ。compile、load、重みの分割、KV の書き戻しは NxD Inference が受け持つ](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/81840c7c10dddd/zenn/articles/81840c7c10dddd/interfaces.png)

NxD Inference は、コンパイル、ロード、推論の手順そのものを持っています。ただし、手順の途中で「どの形の入力でコンパイルするか」「どの nn.Module を作るか」「戻り値のどれが KV か」といった、モデルを書いた人にしか分からないことが必要になります。それを答えるのが、次の 3 つのインタフェースです。

| インタフェース | 自分で書くもの | 自分で書く理由（NxD Inference には分からないこと） |
| --- | --- | --- |
| [`NeuronApplicationBase`](https://github.com/aws-neuron/neuronx-distributed-inference/blob/v0.7.14366/src/neuronx_distributed_inference/models/application_base.py) | `forward()`、`get_state_dict()`、config のクラスと `get_config_cls()` | 呼び出しの引数の並び、チェックポイントの重みの名前と形、層の数や `max_seq_len` は、モデルごとに違う |
| [`ModelWrapper`](https://github.com/aws-neuron/neuronx-distributed-inference/blob/v0.7.14366/src/neuronx_distributed_inference/models/model_wrapper.py) | `input_generator()`、`get_model_instance()` | コンパイルに使う入力の形、型、順番は、モデルごとに違う |
| [`BaseModelInstance`](https://github.com/aws-neuron/neuronx-distributed-inference/blob/v0.7.14366/src/neuronx_distributed_inference/models/model_wrapper.py) | `load_module()`、`get()` | どの nn.Module を作るか、戻り値の何番目がどの KV かは、モデルを書いた人しか知らない |

![app.compile() は 5 段で進む。1 と 2 で Application が ModelWrapper から例の入力と BaseModelInstance を受け取り、3 と 4 で ModelBuilder が BaseModelInstance から nn.Module と aliases を受け取り、5 で例の入力を一度流してコンパイルする。重みはまだ入らない](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/81840c7c10dddd/zenn/articles/81840c7c10dddd/compile-steps.png)

`app.compile()` は、NxD が順に質問し、自分で書いたメソッドが答える形で進みます。XTTS v2 の prefill を例にすると、次のとおりです。

1. Application が ModelWrapper の `input_generator()` に「どの形の入力でコンパイルするか」を聞き、`[1, 1081, 1024]` の隠れ状態などの例の入力を受け取ります。
2. Application が ModelWrapper の `get_model_instance()` で、モデルの作り方を知っている BaseModelInstance を受け取り、例の入力と一緒に [ModelBuilder に渡します](https://github.com/aws-neuron/neuronx-distributed-inference/blob/v0.7.14366/src/neuronx_distributed_inference/models/application_base.py#L148-L182)。
3. ModelBuilder が BaseModelInstance の `load_module()` を呼び、30 層の nn.Module を作ってもらいます。
4. ModelBuilder が BaseModelInstance の `get()` を呼び、その nn.Module と、戻り値の何番目をどの KV に書き戻すかの対応表（aliases）を受け取ります。
5. ModelBuilder が例の入力を一度流して計算の道筋を記録し（トレース）、コンパイルします。[重みはこの時点では入れず](https://github.com/aws-neuron/neuronx-distributed/blob/fbac349b61a3adbb123c2983835af692840ff62f/src/neuronx_distributed/trace/model_builder.py#L871-L906)、あとで load_weights が入れます。

![推論の 1 ステップでは、1 で自分の forward() が呼ばれ、2 でコンパイル済みのモデルが NeuronCore で動き、0 番に隠れ状態、1〜30 番に新しい K、31〜60 番に新しい V を返す。3 で aliases が K と V をデバイスの上の KV キャッシュに書き戻し、4 で forward() は 0 番の隠れ状態だけを返す](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/81840c7c10dddd/zenn/articles/81840c7c10dddd/decode-step.png)

推論の 1 ステップでは、自分で書いた `forward()` がコンパイル済みのモデルを呼びます（図の 1 と 2）。戻り値は、0 番が隠れ状態、1〜30 番が新しい K、31〜60 番が新しい V です。K と V は aliases の対応表どおりにデバイスの上の KV キャッシュへ書き戻され、次のステップで読まれます（3）。そのため、`forward()` が呼び出し側に返すのは 0 番の隠れ状態だけです（4）。

## コンパイルする範囲を決める

![XTTS v2 で NeuronCore で動かすのは GPT デコーダだけで、前処理、出力層、HifiDecoder は CPU に残す](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/81840c7c10dddd/zenn/articles/81840c7c10dddd/xtts-structure.png)

最初に、モデルのどこを Neuron でコンパイルし、どこを CPU に残すかを決めます。この境界の入力と出力の形が、そのまま `input_generator()` と `forward()` の仕様になるからです。XTTS v2 では、縮めた設定の CPU の計測で時間の 89.8% を占めた 30 層の GPT デコーダだけをコンパイルし、入力は埋め込み `[B, seq_len, 1024]`、出力は隠れ状態 `[B, seq_len, 1024]` にしました。範囲は、時間を多く使う部分のうち、入力と出力の形を固定でき、使う演算を Neuron のコンパイラが扱える部分に絞ります。

## コンパイルから推論までの流れ

compile は設定ごとに一度、load と load_weights は起動のたびに行います。compile と load_weights はどちらも、最初に ModelBuilder を作るときに `get_model_instance()` と `input_generator()` を呼びます。コンパイルとロードは別のプロセスで走ることもあるので、層の数や `max_seq_len` のようなモデルの形は [`InferenceConfig`](https://github.com/aws-neuron/neuronx-distributed-inference/blob/v0.7.14366/src/neuronx_distributed_inference/models/config.py) のサブクラスに持たせ、両方に同じものを渡します。推論のときは、`input_generator()` が作った入力と同じ形、型、順番で渡します。

![get_state_dict() を呼ぶ時期は save_sharded_checkpoint で変わる。既定の False では load_weights が起動のたびに分けてデバイスに入れ、True では compile のときに分けて保存する](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/81840c7c10dddd/zenn/articles/81840c7c10dddd/state-dict.png)

`get_state_dict()` は、NxD が重みを rank ごとに分けるときに、ModelBuilder の `shard_checkpoint()` を通して呼ばれます。NxD v0.7 の既定（`save_sharded_checkpoint=False`）では、[compile は重みを入れずにトレースして保存し、分割は飛ばします](https://github.com/aws-neuron/neuronx-distributed-inference/blob/v0.7.14366/src/neuronx_distributed_inference/models/application_base.py#L240-L255)。[load_weights が起動のたびに `shard_checkpoint()` を呼び](https://github.com/aws-neuron/neuronx-distributed-inference/blob/v0.7.14366/src/neuronx_distributed_inference/models/application_base.py#L374-L414)、`get_state_dict()` が返した重みを分けてデバイスに入れます。`save_sharded_checkpoint=True` にすると、compile のときに分けた重みを保存し、load_weights はそれを読みます。

重みは Tensor Parallel で分ける前の全体の形で返します。分けた後の形で返すと、NxD がさらに分けてしまうからです。このサンプルの [`get_state_dict()`](https://github.com/littlemex/samples/blob/b6334caf1f46c549bb58905a7a39000d5aba5db2/ml_distributed_experiment_collection/xttsv2-nxd-inference/src/neuron_xttsv2/application_gpt.py) は、config にチェックポイントのパスがあれば実際の重みを、なければ同じ形の仮の重みを返し、パスはコーディネーターの `load_weights()` が書き込みます。そのため `save_sharded_checkpoint=True` で使うなら、compile の前にパスを入れておきます。パスが空のまま compile すると、仮の重みが保存されてしまいます。KV の `cache_k` と `cache_v` は aliases で更新するので、このサンプルは辞書から外しています。

## KV キャッシュは aliases で書き戻す

![nn.Parameter(requires_grad=False) の cache_k と cache_v を forward() が読み、torch.scatter で作った新しい K と V を戻り値に入れ、aliases がそれをパラメータに書き戻して次のステップに渡す](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/81840c7c10dddd/zenn/articles/81840c7c10dddd/kv-parameter.png)

decode は、毎ステップ、前のステップまでの K と V を読みます。トレースしたモデルの呼び出しをまたいで KV を残すために、NxD は aliases という仕組みを持っています。`get()` が返す aliases は、モデルのパラメータと戻り値の番号の対応表です。ModelBuilder はこれを[トレースのときにコンパイラへ渡し](https://github.com/aws-neuron/neuronx-distributed/blob/fbac349b61a3adbb123c2983835af692840ff62f/src/neuronx_distributed/trace/model_builder.py#L899-L906)、コンパイル済みのモデルは、その番号の戻り値をデバイスの上のパラメータに書き戻します。**そこで KV キャッシュを、重みと同じくデバイスに置かれるパラメータとして登録し、新しい値は戻り値で返します**。

- KV キャッシュは `nn.Parameter(requires_grad=False)` で作ります。`nn.Parameter` にすると、モデルのパラメータとして登録され、aliases の書き戻し先にできます。`requires_grad=False` は、このパラメータの勾配を計算しない指定です。KV は推論のたびに上書きするだけの入れ物なので、勾配は要りません
- このサンプルは、`torch.scatter` で指定の位置を更新した新しい K と V のテンソルを作り、戻り値に入れます。aliases が、その戻り値を次の呼び出しで使うキャッシュに書き戻します
- コンパイルする nn.Module の `forward()` は、隠れ状態、全層の K、全層の V の順に返します（[modeling_gpt.py](https://github.com/littlemex/samples/blob/b6334caf1f46c549bb58905a7a39000d5aba5db2/ml_distributed_experiment_collection/xttsv2-nxd-inference/src/neuron_xttsv2/modeling_gpt.py)）。aliases の番号はこの並びと 1 つもずれてはいけません。30 層では K が 1〜30 番、V が 31〜60 番です

![forward() は隠れ状態と新しい KV をタプルで返し、aliases が出力の何番目をどの nn.Parameter に書き戻すかを決め、次のステップは書き戻された KV を読む。図は 30 層のうち最初の 3 層だけを描き、K は 1 番から、V は 31 番から並ぶ](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/81840c7c10dddd/zenn/articles/81840c7c10dddd/aliases-writeback.gif)

## prefill と decode の分け方

![1 つの Application に 2 つの ModelWrapper を持たせて同じ nn.Module の KV を共有する方法と、2 つの Application に分けて KV を CPU 経由で写す方法](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/81840c7c10dddd/zenn/articles/81840c7c10dddd/prefill-decode-split.png)

バケットを使わない場合、1 つの ModelWrapper がコンパイルする入力の形は 1 つに固定されます。そのため prefill `[B, 1081, 1024]` と decode `[B, 1, 1024]` には ModelWrapper を 2 つ用意し、その置き場所に 2 つの方法があります。XTTS v2 の実装は方法 B で、prefill と decode を別々の Application にしています。

方法 A は、[Whisper の実装](https://github.com/aws-neuron/neuronx-distributed-inference/blob/v0.7.14366/src/neuronx_distributed_inference/models/whisper/modeling_whisper.py)のように 1 つの Application に 2 つの ModelWrapper を登録する方法です。同じ nn.Module の KV キャッシュを共有するので、KV を写す処理が要らず、デバイスの上の KV も 1 組で済みます。ただし、prefill と decode の区別を `self.models` に足した順番で付けるので、この順番の扱いが変わると、2 つのモデルの役割がずれます。

方法 B では、普通の Python のクラス（コーディネーター）が 2 つの Application を順に compile、load、load_weights し、入力の長さで呼び分けます。2 つの Application に名前が付き、KV の受け渡しを明示的に書くので、prefill と decode を別の場所で動かす構成へ広げる余地もあります。代償は 2 つあります。KV キャッシュがデバイスの上に 2 組でき、prefill のたびに、各 rank と各層の K と V を CPU へ読み出して decode 側へ書き戻す処理を自分で書いて走らせます。0 で埋めた prefix より後ろの位置には K と V の bias から出た値が残るので、写す前にその位置を 0 にします。この受け渡しの `sync_kv_cache_prefill_to_decode()` は `forward()` からは呼ばれないので、呼ぶ側が prefill のあと最初の decode の前に呼びます。

## 守る決まりの一覧

この実装で守った決まりです。

| 決まり | なぜ | どうするか |
| --- | --- | --- |
| load のあとは、`nxd_model` の `read_from_neuron_buffer` のような公開されていないメソッドを呼べない | TorchScript のオブジェクトになり、`@torch.jit.export` の無いメソッドは `AttributeError` になる | KV は公開されている `traced_model.nxd_model.state` から読み書きする |
| デバイスのテンソルに飛び飛びの代入をしない | XLA の制約で動かない | prefill の KV を CPU に読み出し、prefix より後ろの位置を 0 にしてから、decode 側の `.state` に `copy_()` する |
| CPU と Neuron の間で型をそろえる | bfloat16 でコンパイルしたモデルに float32 を渡すと型が合わない | 渡す前に bfloat16 に、受け取ったら float32 に戻す。位置とマスクはサンプルの入力と同じ整数の型にする |
| この 30 層の GPT は BF16 にした | FP16 では後ろの層の attention があふれ、同じトークンを繰り返した | BF16 でコンパイルし、出力を比べて確かめる |

CPU との型の変換、生成の品質、音声のストリーミングは、[実装編](https://zenn.dev/tosshi/articles/ffc359901ea1cc)で扱います。

このコードが確認すること

Neuron ハードウェア不要の最小スタブで 3 インタフェースの連携を再現します。`load_module()` でモデルをインスタンス化し、`get()` で aliases を構築し、`forward()` の return タプルのインデックスが aliases と一致することを assert で検証します。

- `load_module()` → `get()` の順序でフレームワークが呼ぶことにより、`get()` 時点で `self.module` が初期化済みになります

- return タプルの長さが `1 + n_layer * 2`（hidden_states + cache_k 全層 + cache_v 全層）になります

実行コマンド。

```bash
PYTHONPATH=stubs:src uv run python examples/smoke_test.py
```

## まとめ

この XTTS v2 の実装では、3 つのインタフェースを通して、入力の形、重み、KV を書き戻す先を NxD Inference に渡しました。要点は、aliases と出力の順番をそろえること、コンパイル用の仮の重みと実際の重みを切り替えること、prefill と decode の分け方に応じて KV を共有するか写すかを決めることです。
