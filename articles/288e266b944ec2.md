# はじめに

GPU のノードを複数の Pod で分けて使うとき、Pod に渡される [EFA](https://aws.amazon.com/hpc/efa/) (Elastic Fabric Adapter。インスタンスの間の、帯域が広くレイテンシーが低い通信に使う AWS のネットワークの機器) が、その Pod の GPU の近くにあるとは限りません。[p5e.48xlarge](https://aws.amazon.com/ec2/instance-types/p5/) 1 台に k3s の kubelet と従来の device plugin を入れ、GPU 1 枚と EFA 4 個を求める Pod を 8 つ作ったところ、GPU と同じ PCIe ルート (機器をつなぐ配線の根元) の EFA は 32 個中 2 個で、でたらめに配った場合と区別できませんでした。[DRA](https://kubernetes.io/docs/concepts/scheduling-eviction/dynamic-resource-allocation/) (Dynamic Resource Allocation) で「同じ PCIe ルート」という条件を付けると、32 個すべてがそろいました。1 台の中の 2 つの GPU の通信を EFA に通して各条件 1 回測ると、そろった場合は 45.81 GB/s、rank が別の NUMA (CPU とメモリの区画) の EFA を使った場合は 3.56〜4.69 GB/s でした。

この記事の前半では、GPU のスケジューリングで [Run:ai](https://run-ai-docs.nvidia.com/) が担ってきた役割を、オープンソースのスケジューラ (KAI Scheduler、Kueue) と Kubernetes の DRA でどこまで代わりにできるかを、各製品の文書から整理します。後半では、その中で DRA が効く場面を、この p5e での実測で確かめます。

# Run:ai とオープンソースの道具で何が違うか

Run:ai のスケジューラ (どの Pod をどこに置くかを決める部品) は、[KAI Scheduler](https://github.com/NVIDIA/KAI-Scheduler) としてオープンソースで公開されており、[Run:ai の文書](https://run-ai-docs.nvidia.com/saas/resources/blogs/numa-aware-scheduling-in-nvidia-run-ai)も、自身のスケジューラを KAI Scheduler の上に作ったものと説明しています。[Kueue](https://kueue.sigs.k8s.io/) はジョブを動かしてよいかを決めて待たせる仕組みで、DRA は Pod に渡す機器を 1 つずつ属性で選ぶ Kubernetes の仕組みです。KAI Scheduler は Pod をノードに置く段、Kueue はその前でジョブを始めてよいかを決める段を受け持つので役割は違いますが、待ち行列と公平な配分はどちらにもあり、この機能では重なります。次の表は、これらの受け持つ機能を各製品の文書から比べたもので、実際に組み合わせて動かしたものではありません。対応状況は 2026-11-11 から 2026-11-20 に各文書で確かめたものです。

| 機能 | Run:ai | オープンソースの道具と Kubernetes | 差 |
|---|---|---|---|
| まとめて置く (gang)、階層のある待ち行列、公平な配分 | ある | KAI Scheduler にある。Kueue にも待ち行列と公平な配分がある | ほぼ無い |
| GPU を分けたときのメモリの上限 | [ある](https://run-ai-docs.nvidia.com/self-hosted/2.24/platform-management/runai-scheduler/resource-optimization/fractions) | KAI Scheduler の [GPU sharing](https://github.com/NVIDIA/KAI-Scheduler/blob/main/docs/gpu-sharing/README.md) の HamiCore か NvFractions のモードで上限を守らせられる。NvFractions は CUDA 13.4 と gpu-fractioning operator を[組み合わせる](https://zenn.dev/tosshi/articles/95edc2cb88f57b) | ほぼ無い |
| 保証した分を超えて、空いていれば上乗せする GPU の分割 | [dynamic fractions](https://run-ai-docs.nvidia.com/self-hosted/2.24/platform-management/runai-scheduler/resource-optimization/dynamic-fractions) がある | KAI Scheduler の NvFractions は GPU メモリの request と limit を別々に指定できる | 近い機能があるが、同じ振る舞いかは文書からは分からない |
| 管理画面、利用者の区分け、ログイン連携、使用量の可視化、サポート | 製品として揃っている | 自分で組み合わせて作り、運用する | Run:ai の強み |
| 複数クラスタ | 1 つの管理画面から複数のクラスタを管理する | [MultiKueue](https://kueue.sigs.k8s.io/docs/concepts/multikueue/) が、管理用のクラスタから作業用のクラスタへジョブを振り分ける (beta) | 役割が違う |
| DRA | [クラスタの v2.25 から対応](https://run-ai-docs.nvidia.com/saas/getting-started/whats-new-for-nvidia-run-ai-saas) | Kubernetes v1.34 で [GA (一般提供)](https://kubernetes.io/docs/concepts/scheduling-eviction/dynamic-resource-allocation/) | どちらでも使える |

スケジューラの機能では、Run:ai にしかできないことは少なくなりました。Run:ai に残る強みは、管理画面、利用者の区分け、サポートが最初から揃っていることです。Kueue は Pod を作る前にジョブを止めて待たせるので、必要なときにノードを作る [Karpenter](https://karpenter.sh/) と組み合わせると、置けないジョブのためにノードが作られにくいという[性質](https://zenn.dev/tosshi/articles/e47ba6e81153c2)もあります。

DRA は Run:ai でも Kubernetes でも使えるので、対応の有無だけでは両者を区別できません。では、DRA そのものはどこで効くのでしょうか。よく聞くのは「GB200 のようなラック単位の構成では必要だが、P 系のインスタンスで 1 台をまるごと使うなら、従来の device plugin で足りる」という見方です。ノードを複数の Pod で分けたときにどうなるかを、次から測ります。

# 測った環境

p5e.48xlarge 1 台 (H200 が 8 枚、EFA が 32 個) に [k3s](https://k3s.io/) v1.37.2+k3s1 を新しく入れ、1 台だけのクラスタにしました。kubelet は k3s のもので、EKS の AL2023 の kubelet では試していません。比べたのは次の 2 つの方式です。

| 方式 | 使ったもの |
|---|---|
| device plugin | [NVIDIA device plugin](https://github.com/NVIDIA/k8s-device-plugin) (chart 0.20.1)、[EFA device plugin](https://github.com/aws/eks-charts/tree/master/stable/aws-efa-k8s-device-plugin) (chart v0.5.35、イメージ v0.5.22-eksbuild.9)。kubelet の [topology manager](https://kubernetes.io/docs/tasks/administer-cluster/topology-manager/) は `best-effort`、scope は `pod` |
| DRA | [NVIDIA DRA ドライバ](https://github.com/kubernetes-sigs/dra-driver-nvidia-gpu) 0.5.1 (GPU の割り当てのみ有効)、[DRANET](https://github.com/kubernetes-sigs/dranet) v1.4.0 |

このマシンでは、GPU 1 枚ごとに専用の PCIe ルートがあり、その下のスイッチに EFA が 4 個ずつ付いています。NUMA は 4 つあり、1 つの NUMA に GPU が 2 枚と EFA が 8 個入っています。DRA の 2 つのドライバは、どちらも各機器に `resource.kubernetes.io/pcieRoot` という共通の属性を付けて公開します。

# 割り当ての結果

GPU 1 枚と EFA 4 個の Pod を 8 つ作る場合と、GPU 4 枚と EFA 16 個の Pod を 2 つ作る場合を比べました。各 EFA は、Pod の中のどれかの GPU と同じ PCIe ルートなら「同じルート」、そうでなくてどれかの GPU と同じ NUMA なら「同じ NUMA で別ルート」、どちらでもなければ「別の NUMA」と数えました。

| 方式 | Pod | 同じルート | 同じ NUMA で別ルート | 別の NUMA |
|---|---|---|---|---|
| device plugin | 8 × (1 GPU + 4 EFA) | 2 / 32 | 8 | 22 |
| device plugin | 2 × (4 GPU + 16 EFA) | 18 / 32 | 0 | 14 |
| DRA 条件なし | 8 × (1 GPU + 4 EFA) | 0 / 32 | 0 | 32 |
| DRA の `matchAttribute` | 8 × (1 GPU + 4 EFA) | 32 / 32 | 0 | 0 |
| DRA の `matchAttribute` (GPU と EFA の組を 4 つ) | 2 × (4 GPU + 16 EFA) | 32 / 32 | 0 | 0 |

EFA を GPU と関係なく 32 個から選んだ場合、1 個の EFA が Pod の GPU と同じルートに当たる確率は、1 GPU の Pod で $4/32$、4 GPU の Pod で $16/32$ です。乱数で 20 万回配った試行では、同じルートの数が 1 GPU の Pod で 2 以下になる確率は 22%、4 GPU の Pod で 18 以上になる確率は 36% でした。**device plugin の 2 と 18 は、でたらめに配っても珍しくない値です。** そろえていないことは言えますが、でたらめより悪いとは言えません。

topology manager がそろえる単位は NUMA で、PCIe ルートではありません。そこで同じ NUMA まで広げて数えると、1 GPU の Pod は 32 個中 10 個 (同じルート 2 個と、同じ NUMA で別ルート 8 個) で、でたらめに配った場合の平均 $32 \times 8/32 = 8$ 個 (1 つの NUMA にある EFA は 8 個) と区別できませんでした。この設定では topology manager の効果は見えず、device plugin が kubelet に配置の手がかり (topology hint) を渡していたかは記録していません。

条件なしの DRA も、そろいませんでした。各 Pod に 1 つのルートの EFA 4 個をまとめて渡しましたが、どれも Pod の GPU とは別のルートでした。Pod ごとの EFA は 1 つのルートの 4 個にまとまり、Pod 1〜7 にはルートの番号順に渡っていたので、これは偶然ではなく、GPU と関係なく機器を決まった順に選んだ結果と考えられます。でたらめより悪いという意味でもありません。DRA は、条件を書いたときにそろえます。まず、DRANET が公開する機器から EFA だけを選ぶ DeviceClass を作ります。

```yaml
apiVersion: resource.k8s.io/v1
kind: DeviceClass
metadata:
  name: efa.dra.net
spec:
  selectors:
  - cel:
      expression: device.driver == "dra.net" && device.attributes["dra.net"].rdma == true && device.attributes["dra.net"].pciDevice == "Elastic Fabric Adapter (EFA)"
```

次に、GPU 1 枚と EFA 4 個を同じ `pcieRoot` から選ぶ要求を書きます。

```yaml
apiVersion: resource.k8s.io/v1
kind: ResourceClaimTemplate
metadata:
  name: gpu1-efa4-aligned
spec:
  spec:
    devices:
      requests:
      - name: gpu
        exactly: {deviceClassName: gpu.nvidia.com, count: 1}
      - name: nic
        exactly: {deviceClassName: efa.dra.net, count: 4}
      constraints:
      - requests: [gpu, nic]
        matchAttribute: resource.kubernetes.io/pcieRoot
```

GPU 4 枚の Pod では、1 つの `pcieRoot` に GPU 4 枚は入らないので、GPU 1 枚と EFA 4 個の組を 4 つ書き、組ごとに `matchAttribute` を付けました。そろえたのは GPU ごとの組で、Pod の GPU は複数の NUMA にまたがっています。

# 共有の結果

1 つの機器を複数の Pod で使えるかも試しました。

| 試したこと | 結果 |
|---|---|
| device plugin で、1 GPU と EFA 32 個の Pod を 2 つ | 2 つ目は `Insufficient vpc.amazonaws.com/efa` で割り当て待ちのまま |
| DRA で、GPU 1 枚の ResourceClaim を 2 つの Pod から参照 | 2 つとも動き、同じ GPU が見えた (同時に計算したときの干渉は見ていない) |
| DRA で、GPU 1 枚と EFA 4 個の ResourceClaim を 2 つの Pod から参照 | 2 つとも置き場所は決まったが、準備の段階で `driver only supports one pod per claim, got 2` で止まった |

DRA の仕組みは、[1 つの ResourceClaim を複数の Pod で参照すること](https://kubernetes.io/docs/concepts/scheduling-eviction/dynamic-resource-allocation/)を許しています。エラーにドライバの名前は出ませんが、EFA を含まない同じ形の要求は通ったので、EFA の共有を断ったのは DRANET だと考えられます。DRANET では RDMA の機器の共有が [Issue #63](https://github.com/kubernetes-sigs/dranet/issues/63) で検討されており、2026-11-20 の時点で open です。

# 通信の帯域

GPU と EFA の位置が通信にどれだけ効くかを、[NCCL](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/overview.html) (複数の GPU の間の通信を扱う NVIDIA のライブラリ) で測りました。1 つの Pod の中で GPU を 1 枚ずつ持つ 2 つの rank (通信に参加するプロセス) を動かし、`NCCL_P2P_DISABLE=1 NCCL_SHM_DISABLE=1 NCCL_NVLS_ENABLE=0` で、通信が必ず EFA を通るようにしました。実際の学習では同じ台の GPU どうしは NVLink でつながり、EFA は別の台との通信に使われるので、これは GPU と EFA の間の経路だけを切り出した測定です。NCCL から EFA へは [aws-ofi-nccl](https://github.com/aws/aws-ofi-nccl) を通ります。値は [nccl-tests](https://github.com/NVIDIA/nccl-tests) の all_reduce (全 rank の値を足し合わせ、結果を全 rank に配る操作) の 4 GiB での busbw (帯域の指標) で、各条件 1 回です。

図の別の NUMA の道筋は、sysfs の配線と NCCL のログの GDR の有無から描いたもので、通信の経路そのものを観測したものではありません。

表の GDR は GPUDirect RDMA (EFA が GPU のメモリを直接読み書きする仕組み) が使われたか、チャネルは NCCL が 2 つの rank の間に並べて張った通信の道筋の数で、どちらも NCCL のログから読みました。

| 条件 | GPU | rank が使った EFA | GDR | 1 rank が使った EFA の本数 | チャネル | 帯域 (busbw、4 GiB) |
|---|---|---|---|---|---|---|
| DRA で GPU と同じルートの EFA を指定 | 0、1 | それぞれ自分のルートの 4 本 | あり | 4 | 4 | 45.81 GB/s |
| device plugin の 1 回目 | 2、3 | それぞれ自分のルートの 1 本 | あり | 1 | 2 | 10.56 GB/s |
| DRA で別の NUMA の EFA を指定し、GDR を強制 | 0、1 | 別の NUMA の 4 本 | あり (強制) | 4 | 2 | 4.69 GB/s |
| DRA で同じ NUMA の別ルートを指定したが、NCCL が別の NUMA の組を選んだ | 0、2 | 別の NUMA の 4 本 | なし | 4 | 2 | 4.38 GB/s |
| DRA で別の NUMA の EFA を指定 | 0、1 | 別の NUMA の 4 本 | なし | 4 | 2 | 3.56 GB/s |

**rank が別の NUMA の EFA を使った場合、帯域は 3.56〜4.69 GB/s で、自分のルートの EFA を 4 本使えた 45.81 GB/s の約 10〜13 分の 1 でした。** GDR を強制しなかった 2 回では NCCL が自分で GDR を切り、3 回ともチャネルは 4 から 2 に減っています。GDR を強制した 1 回も 4.69 GB/s で 45.81 GB/s から大きく離れているので、GDR だけでは差を説明できません。残りが PCIe の経路によるものか、チャネル数によるものかは切り分けていません。

device plugin の 1 回目では、各 GPU に自分のルートの EFA が 1 本ずつ当たり、NCCL はその 1 本を選んで 10.56 GB/s でした。4 本の場合のほぼ 4 分の 1 ですが、チャネル数も違います。2 回目と 3 回目は、各 rank が選んだ自分のルートの EFA の組の本数が 1 本と 2 本 (3 回目は 1 本と 3 本) で食い違い、1 台の中で EFA を折り返したこの測定では、aws-ofi-nccl が `Unexpected number of remote rails for dev 0. Expected 1 but got 2` (3 回目は `got 3`) で止まりました。

# Pod に EFA を何個も見せるときの注意

1 つの Pod に 2 つの rank と EFA 8 個を入れ、両方の rank の `FI_EFA_IFACE` に 8 個すべてを並べると、どの rank がどの組を使うかは NCCL が決めます。要求 (claim) の中で「GPU 0 にはこの 4 個」と組を指定すると、その対応は ResourceClaim の割り当て結果に要求の名前ごとに残りますが、コンテナの中の NCCL には自動では渡りません。

上の表の 4.38 GB/s の行がその例です。要求では、各 GPU に同じ NUMA の別ルートの EFA を割り当てましたが、ログでは NCCL は 2 つの rank とも別の NUMA の組を選んでいました。そのため、この行は別の NUMA の場合として扱っており、同じ NUMA で別ルートの場合の帯域はこの記事の表に含まれていません。どの rank がどの EFA を使ったかは、ログの `via NET/Libfabric/<番号>` の行と、`NIC group` の行の PCI アドレスを突き合わせて確かめてください。

# まとめ

スケジューラの機能では、Run:ai とオープンソースの道具の差は小さくなりました。Run:ai に残る強みは、管理画面、利用者の区分け、サポートが最初から揃っていることです。

DRA が効くのは、ノードを分けて使い、GPU とネットワークの機器の組み合わせが通信の帯域を決める場面です。k3s の kubelet を使った今回の p5e 1 台での各条件 1 回の測定では、device plugin で Pod を分けると、GPU と同じ PCIe ルートの EFA はでたらめに配った場合と区別できない数しか渡されず、DRA の `matchAttribute` で `pcieRoot` をそろえると 32 個すべてがそろいました。EFA に通した 2 つの GPU の間の帯域は、自分のルートの EFA を 4 本使えた場合が 45.81 GB/s、1 本の場合が 10.56 GB/s、rank が別の NUMA の EFA を使った場合が 3.56〜4.69 GB/s でした。

一方で、1 つの ResourceClaim を 2 つの Pod から参照する形では、DRANET v1.4.0 は EFA を共有できませんでした。NVIDIA の DRA ドライバも、v0.5.0 で入った ConsumableShares などは[まだ alpha](https://github.com/kubernetes-sigs/dra-driver-nvidia-gpu/releases/tag/v0.5.0) です。ノードをまるごと使う Pod では EFA 32 個がすべて渡るので、位置の問題は起きにくいと考えられます。ノードを分けて使うなら、GPU と EFA の位置を DRA の `matchAttribute` でそろえるか、少なくとも NCCL のログで、各 rank が使った EFA の位置を確かめてください。
