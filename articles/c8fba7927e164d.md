## はじめに

GPU インスタンスを数十台まとめて起動しようとして、容量不足のエラーで止まった経験はないでしょうか。公式のスコアの説明ではこのエラーを InsufficientCapacityError と呼んでいますが、[EC2 のエラーコード一覧](https://docs.aws.amazon.com/AWSEC2/latest/APIReference/errors-overview.html)に載っているコードは InsufficientInstanceCapacity です。Spot には Spot placement score（SPS）という先行する仕組みがありますが、On-Demand については、起動する前に空き具合の目安を得る手段が乏しい、というのが筆者の認識でした。

EC2 Capacity Manager は、On-Demand、Spot、Capacity Reservation の使用状況を一か所で確認するための EC2 の機能です。その中の Check supportability は、起動する前に「このインスタンスタイプとこの Availability Zone（AZ）の組み合わせは、いまこの量を支えられそうか」を High、Medium、Low の 3 段階で返します。値の定義は [What the scores mean](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-score-meaning.html) にあります。On-Demand と Spot を同じ呼び方で調べられ、起動も予約もしません。評価するのは現在のキャパシティだけで、日付を指定して将来の空き具合を調べることはできません。チェック自体で費用が発生することはありませんが、使えるのは AWS Support の Unified Operations プランのお客様だけです。一次情報は AWS の [Check supportability](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-supportability.html) のページです。

この記事では、前提と制約、呼び出し方、スコアの読み方を、公式ドキュメントのリンクを添えて整理します。Spot にはこれまでも SPS という似た仕組みがあるので、その違いと、SPS を自動で追跡する AWS 公式のガイダンス実装も紹介します。さらに、この API 向けの公式の実装例があるかを調べた結果と、自分で書いたレポートスクリプトも載せます。

この機能の結果は、委託先や代理人を除く第三者に開示できない決まりがあるため、この記事には実測のスコアも、特定のインスタンスタイプや AZ に関する結果も載せていません。書いているのは、公式ドキュメント、ガイダンスの README、2026-11-05 時点で調べた結果、手元で試した API の挙動です。公式に書かれていないことは、その旨を明記します。

## 概要と使いどころ

[公式ドキュメント](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-supportability.html)によると、使うインスタンスタイプと Availability Zone の候補、それに必要な量を渡すと、候補ごとのスコアと、候補全体のスコアが返ってきます。使えるインスタンスタイプや AZ の候補を増やすべきかを、起動する前に判断するための道具です。使いどころは公式に 3 つ書かれています。

![利用の流れの図。左から、インスタンスタイプ、AZ、量、市場からなる要求、起動も予約もしない Check supportability、組み合わせごとのスコアと全体の集約スコア、の順に矢印でつながる。下に公式ドキュメントの応答例があり、c6g.xlarge と c7g.xlarge は High、m6g.xlarge は Medium、集約は High。各スコアは、棒の本数と文字でも区別できる。](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/c8fba7927e164d/zenn/articles/c8fba7927e164d/01-flow.png)
*図 1: 要求を渡すと、組み合わせごとのスコアと集約スコアが返る。応答例は公式ドキュメントのもの*

| # | 使いどころ | 公式の記述 |
|---|---|---|
| 1 | 起動を支えられるかの確認 | confirm that a launch is supportable |
| 2 | 候補の中で強い場所の発見 | find where capacity is strongest across your options |
| 3 | 起動失敗の切り分け | diagnose a launch failure |

確約はしない、という点も同じページに明記されています。チェックはある時点のキャパシティを反映したもので、キャパシティを予約せず、後の起動が成功することも保証しません。

## 前提と制約

使う前に、4 つの条件と、権限を確認します。

![使う前の 4 つの条件の図。1 サポートプランは AWS Support の Unified Operations、2 Capacity Manager はアカウントにつき 1 つの Region で有効化、3 上限は 1 時間 100 クエリと 1 リクエスト 100 組、4 結果は共有しない。下に、API は Capacity Manager を有効にした Region で呼び、調べる AZ は任意の Region でよい、と書かれている。](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/c8fba7927e164d/zenn/articles/c8fba7927e164d/02-conditions.png)
*図 2: 使う前の条件。色だけでなく、模様と番号でも区別している*

| # | 条件 | 内容 | 出典 |
|---|---|---|---|
| 1 | サポートプラン | AWS Support の [Unified Operations プラン](https://aws.amazon.com/premiumsupport/plans/unified-operations/)のお客様だけが使えます | [Check supportability](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-supportability.html) |
| 2 | Capacity Manager の有効化 | アカウント単位の Capacity Manager だけで足り、組織単位の設定は不要です | [Check supportability](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-supportability.html) |
| 3 | 呼び出しの上限 | アカウントあたり 1 時間に 100 クエリで、1 リクエストあたり最大 100 組のインスタンスタイプと AZ の組み合わせです。組織全体では 1 時間に 10,000 クエリです | [Quotas](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-check-quotas.html) |
| 4 | 結果の扱い | 結果を第三者と共有することはできません。サービス条件には、自社のために行動する委託先や代理人という例外があります | [Check supportability](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-supportability.html)、[AWS Service Terms](https://aws.amazon.com/service-terms/) |

権限については、[EnableCapacityManager](https://docs.aws.amazon.com/AWSEC2/latest/APIReference/API_EnableCapacityManager.html) の `DryRun` の説明に、権限がないと `UnauthorizedOperation` になるとあります。[AWS Service Reference](https://servicereference.us-east-1.amazonaws.com/v1/ec2/ec2.json)（2026-10-29 更新）には、EnableCapacityManager と GetCapacityManagerAttributes が IAM アクションとして載っています。GetCapacityManagerSupportabilityScores はオペレーションとして載っていますが、対応する IAM アクションは書かれていません。筆者が確認した範囲では、必要な権限は 2026-11-05 時点で公開されていません。筆者は管理者ロールで試しました。また、プランの条件を満たさないアカウントで呼んだときにどのエラーが返るかも、公式には書かれていません。エラーが出たときに、プラン、権限、Region のどれが原因かを、応答だけで判別できるとは限りません。

4 つ目の条件について、AWS Service Terms の EC2 Capacity Manager の項は、スコアなどのデータを自社の内部の容量計画とワークロード管理の目的に限って使うこと、自社のために行動する委託先や代理人を除く第三者に開示しないことを定めています。直接か間接かを問わず、類似または競合する製品やサービスの開発、改良、提供に使うことや、他者に使わせることも禁じています。AWS が違反していると合理的に判断した場合、Capacity Manager の利用が停止されることがあります。この定義は、Check supportability のスコアに限らず、Capacity Manager を通じて得られるヘッドルーム指標やしきい値などの容量に関する情報も対象にしています。これは原文の要約であり、法的な判断ではありません。ブログやスライドでの公開は第三者への開示に当たると読めるので、自分のアカウントのスコアを載せたくなったときは、先に原文を確認し、必要なら社内の法務に相談してください。

### Capacity Manager の有効化

無効なアカウントでは、まず有効にします。[EnableCapacityManager](https://docs.aws.amazon.com/AWSEC2/latest/APIReference/API_EnableCapacityManager.html) は、EC2 のキャパシティ使用状況の取り込みを始める API で、初回のデータ処理に数時間かかることがあると書かれています。有効にできる Region はアカウントにつき 1 つです（[EC2 Capacity Manager](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager.html)）。Check supportability は、その有効にした Region で呼びます（[How to check capacity](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-check-capacity.html)）。[アカウント単位の有効化のページ](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/enable-capacity-manager-account.html)によると、有効にすると 14 日分の履歴を集め、数時間かかることがあり、その間は `initial-ingestion-in-progress`、終わると `ingestion-complete` と表示されます。この処理が終わる前にチェックが使えるかどうかは、公式に書かれていません。有効化の直後にエラーや空の応答が返ったら、時間をおいて再試行してください。

```bash
export CM_REGION="ap-northeast-1"
aws sts get-caller-identity --region "$CM_REGION"
aws ec2 get-capacity-manager-attributes --region "$CM_REGION"
aws ec2 enable-capacity-manager --region "$CM_REGION"
aws ec2 get-capacity-manager-attributes --region "$CM_REGION"
```

最初の `get-caller-identity` で実行するアカウントを、最初の `get-capacity-manager-attributes` で有効化前の状態を確認します。[enable-capacity-manager](https://docs.aws.amazon.com/cli/latest/reference/ec2/enable-capacity-manager.html) が有効化で、[get-capacity-manager-attributes](https://docs.aws.amazon.com/cli/latest/reference/ec2/get-capacity-manager-attributes.html) が状態の確認です。有効化はアカウントの設定を変える操作です。公式には書かれていませんが、筆者が試した範囲では、`get-capacity-manager-attributes` は呼び出した Region の状態を返し、無効な Region では `CapacityManager.Disabled` というエラーが返りました。共有のアカウントでは、他の人が別の Region で有効にしていないかを、候補の Region それぞれで確認してください。すでに別の Region で有効なときに有効化を実行した場合の挙動は、公式に書かれていません。

## 呼び出し方

市場、必要な量、AZ の ID、インスタンスタイプを渡すと、組み合わせごとのスコアと集約スコアが返ります。コンソールからも実行できます。AWS CLI で呼ぶ場合は 2.39.1 以降が必要です（[aws-cli の変更履歴](https://github.com/aws/aws-cli/blob/v2/CHANGELOG.rst)）。次の例は [How to check capacity](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-check-capacity.html) の公式の例に、Capacity Manager を有効にした Region を指す `--region` を足したものです。3 つのインスタンスタイプを候補として、use1-az1 で On-Demand の 50 台を調べます。呼び出し先の Region と調べる AZ の Region は別でも構いません。公式は「任意の Region」と書いていますが、GovCloud や中国のような別のパーティションの AZ を指定できるかは明記されていません。

```bash
aws ec2 get-capacity-manager-supportability-scores \
    --region "$CM_REGION" \
    --market-type "on-demand" \
    --capacity-amount 50 \
    --capacity-unit "instances" \
    --capacity-availability-zone-ids '["use1-az1"]' \
    --instance-types '["c6g.xlarge", "c7g.xlarge", "m6g.xlarge"]'
```

返ってくる JSON も公式の例です。各行は 1 つの組み合わせのスコアで、`AggregateScore` は候補全体のスコアです。

```json
{
    "AggregateScore": "high",
    "CapacityManagerSupportabilityScores": [
        { "InstanceType": "c6g.xlarge", "AvailabilityZoneId": "use1-az1", "Score": "high" },
        { "InstanceType": "c7g.xlarge", "AvailabilityZoneId": "use1-az1", "Score": "high" },
        { "InstanceType": "m6g.xlarge", "AvailabilityZoneId": "use1-az1", "Score": "medium" }
    ]
}
```

パラメータは [get-capacity-manager-supportability-scores の CLI リファレンス](https://docs.aws.amazon.com/cli/latest/reference/ec2/get-capacity-manager-supportability-scores.html)に載っています。

| # | パラメータ | 内容 |
|---|---|---|
| 1 | `--market-type` | `on-demand` か `spot` を指定します |
| 2 | `--capacity-amount` | 必要な量で、1 以上の整数です。スコアはこの量に対する相対値です |
| 3 | `--capacity-unit` | 量の単位で、`instances` は台数、`vcpus` は vCPU 数です |
| 4 | `--capacity-availability-zone-ids` | 調べる AZ の ID を、最大 10 個まで指定します。別の Region の AZ も指定できます |
| 5 | `--instance-types` | 調べるインスタンスタイプを、最大 50 個まで指定します |
| 6 | `--instance-requirements-with-metadata` | 名前の代わりに vCPU やメモリなどの属性で指定します。`--instance-types` とは同時に指定できません |

タイプ数と AZ 数の積は、1 リクエストで 100 組までです。例えば 10 タイプと 3 AZ なら 30 組になります。[Quotas](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-check-quotas.html) は、1 回の問い合わせでより多くの情報を得るために、広い条件でリクエストすることを勧めています。

呼び出しの場所には決まりがあります。API は Capacity Manager を有効にした Region で呼び、1 回の呼び出しで任意の Region の AZ を調べられます。また公式は、起動のたびに呼ぶのではなく、ワークロードを計画するときや見直すときに実行することを勧めています。他の Region の起動が、Region をまたぐ呼び出しに依存しないようにするためです。AZ は名前ではなく AZ ID で指定します。`ap-northeast-1c` のような AZ 名はアカウントによって別の物理的なゾーンに対応しますが、AZ ID はどのアカウントでも同じゾーンを指します。詳しくは [Availability Zone IDs for your AWS resources](https://docs.aws.amazon.com/ram/latest/userguide/working-with-az-ids.html) を参照してください。

## スコアの読み方

スコアの定義は [What the scores mean](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-score-meaning.html) にあります。各スコアは、そのインスタンスタイプと AZ の組み合わせがいま保有しているキャパシティを、要求した量と比べた比です。

| # | スコア | 公式の意味 |
|---|---|---|
| 1 | High | 組み合わせが要求量の数倍を保有しています。進めてよい水準です |
| 2 | Medium | 組み合わせは余裕をほとんど残さず要求量を満たせます。安全というより実行可能な水準で、起動は失敗することがあります |
| 3 | Low | 組み合わせは要求量より少ないものの、一部のキャパシティは残っていると見込まれます |

![スコアの意味の模式図。High は保有量が要求の数倍、Medium は要求を満たすがほとんど余裕がない、Low は要求より少ない。横棒の長さと、棒の本数の記号で示している。下に、同じ組み合わせ、同じ時刻でも 50 台なら High、5,000 台なら Low になりうる、と書かれている。](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/c8fba7927e164d/zenn/articles/c8fba7927e164d/03-score-meaning.png)
*図 3: スコアは、保有量を要求量と比べたもの。縮尺は正確ではない*

読むときの注意が 4 つあります。

1 つ目は、スコアが要求量に対する相対値だという点です。同じ組み合わせ、同じ時刻でも、50 台なら High、5,000 台なら Low になりえます。台数を決めずにスコアだけを比べても意味がありません。

2 つ目は、どのスコアも保証ではないという点です。公式は、High でも容量不足のエラーは起こりうると明記し、重要なワークロードにはスコアに関係なく Capacity Reservation か将来日付の Capacity Reservation を使うよう勧めています。前者は [On-Demand Capacity Reservations](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-capacity-reservations.html) が該当します。公式の推奨には挙がっていませんが、GPU を期間を決めて押さえる手段として [Capacity Blocks for ML](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-capacity-blocks.html) もあります。

3 つ目は、集約スコアの意味です。応答には、組み合わせごとのスコアに加えて、候補全体の集約スコアが入ります。公式は、組み合わせごとの値が Low でも集約が High になるのは矛盾ではなく意図した動作だと説明しています。1 つの組み合わせでは要求量を支えられなくても、候補を合わせれば支えられるという意味で、柔軟性を保つ理由になります。

![組み合わせごとのスコアと集約スコアの図。3 つの組み合わせがすべて Low でも、3 つをまとめた集約スコアは High になる。下に、単独では支えられなくても、全体では支えられる、と書かれている。](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/c8fba7927e164d/zenn/articles/c8fba7927e164d/04-pair-vs-aggregate.png)
*図 4: 組み合わせごとが Low でも、集約が High になることがある*

4 つ目は、リクエストを分けたときの集約です。1 リクエストの上限は公式に 100 組と定められています。超えたときにエラーになるのか切り詰められるのかは書かれていないので、筆者は 100 組以内に収めて呼び出しを分ける前提で考えています。公式は分けた場合の集約の扱いも書いていませんが、集約は 1 リクエストの候補全体に対する値なので、複数のリクエストをまたいだ 1 つの集約は得られない、というのが筆者の解釈です。属性指定では解決後のタイプ数を事前に決められないため、100 組を超える場合の挙動は確認していません。

## スコアの使い分け

[What to do based on your score](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-score-actions.html) は、フリートの形と状況で読み方を分けています。

| # | 状況 | 見るもの | 公式が勧める行動 |
|---|---|---|---|
| 1 | 複数タイプを使えるミックスフリート | 集約スコア | High なら進めます。Auto Scaling グループ、Karpenter、EC2 Fleet といったオーケストレーターが、起動時に組み合わせへ分散します。Medium か Low なら、候補を増やすか、時間をおいて再試行します |
| 2 | 1 つのタイプしか使えない | 組み合わせごとのスコア | 最も高い組み合わせを選びます。並んだ場合は、コスト、性能、慣れで決めます |
| 3 | 起動が InsufficientCapacityError で失敗した | 同じタイプ、AZ、量で再実行したときの組み合わせごとのスコア | High なら、その組み合わせにキャパシティはあるが、要求のサイズに合わせるためにホストのリサイズが必要な状態だと説明されています。起動できる分を起動し、残りは数分おきに再試行します。Medium か Low なら空きが限られているので、High だった別の組み合わせで起動するか、タイプを増やします |

![どのスコアを読むかの図。1 複数タイプのミックスフリートは集約スコアを読み、High なら進め、Medium か Low なら組み合わせを足すか再試行する。2 タイプが 1 つだけなら組み合わせごとのスコアを読み、最も高いものを選ぶ。3 起動が失敗したら同じタイプ、AZ、量で確認し、High ならホストのリサイズが必要なので起動できる分を起動し、Medium か Low なら空きが限られるので別の High の組み合わせを使う。下に、Spot は集約スコアを読む、と書かれている。](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/c8fba7927e164d/zenn/articles/c8fba7927e164d/05-which-score.png)
*図 5: 状況ごとに読むスコアが違う*

2 行目と 3 行目は、どちらも組み合わせごとのスコアを読む使い方です。公式の説明は市場を区別していません。Spot については、すでに SPS を直接使っている場合に集約スコアを Spot の信号として読むよう公式は書いていますが、組み合わせごとの Spot の値の扱いは書かれていません。したがって、Spot でこの 2 つの使い方をする根拠は、公式にはありません。また、Spot のスコアは SPS を土台にしているため、SPS にある制約が Check supportability の Spot にも及ぶかどうかは、公式に書かれていません。Spot で 1 つか 2 つのタイプだけを調べて Low が出たときは、空きの不足と決めつけず、3 つ以上のタイプで確かめることを筆者は勧めます。ただし SPS の最小数は P、G、Trn、Inf ファミリーには適用されないので、これらのファミリーでは最小数が原因とは考えにくいです。これは筆者の注意であり、公式の記述ではありません。

3 行目の使い方は、エラーが、要求した量に対して空きが限られているためなのか、ホストのリサイズが必要なためなのかを切り分ける材料になります。

## Spot placement score という先行する仕組み

SPS は、Spot のリクエストがある Region や AZ でどれくらい成功しそうかを 1 から 10 で返す、以前からある API です。[Spot placement score](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/spot-placement-score.html) によると、スコアは推奨にすぎず、空き容量や中断リスクの保証はなく、追加の料金もかかりません。

仕組みは [How Spot placement score works](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/how-sps-works.html) と [GetSpotPlacementScores](https://docs.aws.amazon.com/AWSEC2/latest/APIReference/API_GetSpotPlacementScores.html) に書かれています。

| # | 項目 | 内容 | 出典 |
|---|---|---|---|
| 1 | スケール | 各 Region か AZ に 1 から 10 を付け、10 は成功する可能性が高いという意味です | [How Spot placement score works](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/how-sps-works.html) |
| 2 | 返る数 | 上位 10 の Region か、上位 10 の AZ です。既定は Region の一覧で、Local Zone は既定では無視されます。含めるには `IncludeLocalZones` を `true` にします | 同上 |
| 3 | 使える条件 | スコアが意味を持つのは、Spot のリクエストの構成がスコアを取ったときと同じで、`capacity-optimized` の配分戦略を使う場合です。Region のスコアは全 AZ を、AZ のスコアは単一の AZ を使うフリートを前提とし、Local Zone を含むスコアなら同じ Local Zone を使う必要があります | 同上 |
| 4 | 権限 | IAM のアクション `ec2:GetSpotPlacementScores` が書かれています。サポートプランの条件は、読んだページには出てきません | [Required permissions](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/sps-iam-permission.html) |
| 5 | 最小のタイプ数 | インスタンスタイプで指定する場合は、異なる 3 つ以上のタイプが必要で、満たさないと低いスコアが返ります。属性で指定する場合も、3 つ以上のタイプに解決される必要があります。ただし P、G、Trn、Inf ファミリーのインスタンスタイプには、この最小数は適用されません | [Spot placement score](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/spot-placement-score.html)、[How Spot placement score works](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/how-sps-works.html) |

Check supportability の Spot は、この SPS を土台にしています。[Relationship to Spot placement score](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-sps.html) によると、SPS は個々の組み合わせではなく柔軟性の全体を評価し、Spot の集約スコアが同等の指針になります。すでに SPS を直接使っている場合は、集約を Spot の信号として読むよう書かれています。組み合わせごとの Spot の値をどう扱うかは、公式に書かれていません。

2 つの仕組みは、同じ「空き具合の予測」でも対象が違います。

| # | 観点 | SPS（GetSpotPlacementScores） | Check supportability |
|---|---|---|---|
| 1 | 対象の市場 | Spot だけです | On-Demand と Spot です |
| 2 | スコアの形 | 1 から 10 の数値です | High、Medium、Low と、候補全体の集約です |
| 3 | 粒度 | Region か AZ ごとで、上位 10 件です | 指定した組み合わせごとで、1 リクエスト最大 100 組です |
| 4 | 必要な条件 | IAM 権限です | Capacity Manager の有効化と Unified Operations プランです。対応する IAM アクションは、AWS Service Reference に載っていません（2026-11-05 時点） |
| 5 | 結果の共有 | サービス条件の EC2 Capacity Manager の項の対象には含まれないと読めます。他の契約条項は確認していません | Capacity Manager を通じて得たデータとして、第三者への開示が制限されます |

## SPS を自動で追跡するガイダンス実装

SPS が返すのは取得した時点のスコアだけなので、時間の変化を見たい場合は自分で記録する必要があります。それを代わりにやってくれるのが、AWS Solutions Library の [Guidance for EC2 Spot Placement Score Tracker](https://github.com/aws-solutions-library-samples/guidance-for-ec2-spot-placement-score-tracker) です。AWS が公開する、自分のアカウントに構築して使う参考実装です。リポジトリの README とコードに基づくと、次のような構成です。

| # | 項目 | 内容 |
|---|---|---|
| 1 | 構成 | AWS CDK の Python で、Lambda、EventBridge のスケジュール、CloudWatch ダッシュボード、IAM ロールを作ります。設定ファイルとコードは、`cdk bootstrap` で用意される S3 バケットに置かれます |
| 2 | スコアの取得 | `ec2:GetSpotPlacementScores` を使います。Spot だけが対象で、On-Demand は見ません |
| 3 | 入力 | インスタンスタイプかインスタンス属性、Region のリスト、目標の容量、AZ 単位か Region 単位かを指定します。Karpenter の NodePool の YAML から要件を読む方法もあります |
| 4 | 出力 | スコアと Spot 価格を CloudWatch のカスタムメトリクスにして、ダッシュボードに時系列で表示します |
| 5 | 費用 | README は、2026 年 2 月時点の us-east-1 の既定の設定で、月額約 25.37 ドルと見積もっています。大半は CloudWatch のカスタムメトリクスの費用です |
| 6 | ライセンス | MIT-0 です |
| 7 | 導入に必要なもの | CDK、Python 3.8 以上、virtualenv、boto3、PyYAML、Docker、CDK のスタックを実行できる IAM 権限、SPS と EC2 の API を呼べる権限です |
| 8 | 実行間隔 | README の中で 5 分と 15 分の記述が混在しています |

使いどころは、Spot で GPU を回したい場合に、指定したインスタンスタイプの組と容量の構成について、Region や AZ ごとのスコアの推移を見ることです。SPS が採点するのは構成全体であり、構成の中の個々のインスタンスタイプではありません。取りやすい構成を許可リストに入れ、実際の起動は Karpenter や EC2 Fleet の配分戦略に任せる、という運用が考えられます。ただし公式は、スコアが意味を持つのは同じ構成で `capacity-optimized` を使う場合だとしています。[Karpenter の Disruption のページ](https://karpenter.sh/docs/concepts/disruption/)は、Spot から Spot への統合で、より安い Spot のインスタンスタイプを `price-capacity-optimized` で選ぶと書いています。起動時に使う配分戦略が `capacity-optimized` と異なる場合、スコアと起動結果が対応するかは、公式に書かれていません。その場合、スコアは傾向の参考にとどまる、というのが筆者の解釈です。この配分戦略は [price-capacity-optimized の紹介](https://aws.amazon.com/blogs/compute/introducing-price-capacity-optimized-allocation-strategy-for-ec2-spot-instances/)を参照してください。

注意点も書かれています。README は、SPS では新しい構成を多数投げると制限され、設定が多すぎると Lambda の実行が失敗しうると説明しています。目標の容量にも上限があります。[Spot placement score](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/spot-placement-score.html) のドキュメントによると、上限は直近の Spot の利用量に今後の増加を見込んで決まり、利用実績がなければ Spot のリクエスト上限に合わせた低い既定値になります。同じページは、意図された使い方と異なるパターンを検知すると、24 時間あたりの新しい構成の数を制限することがあると書いています。

## 自作スクリプト

自分のアカウントで回して、JSON のデータと HTML のレポートにまとめるスクリプトを書きました。コードは [distributed-ai の investigations（コミットを固定したリンク）](https://github.com/littlemex/distributed-ai/tree/02d3b810d77a345cb7259da0d49e83db7227771a/investigations/2026-11-05-ec2-capacity-supportability-report) にあります。レポートは自社の中で使う前提で、リポジトリには実行結果を含めていません。boto3 で呼ぶ部分の骨格は次のとおりです。`region_name` には、Capacity Manager を有効にした Region を指定します。

```python
import boto3

ec2 = boto3.client("ec2", region_name="ap-northeast-1")
r = ec2.get_capacity_manager_supportability_scores(
    MarketType="on-demand",
    CapacityAmount=50,
    CapacityUnit="instances",
    CapacityAvailabilityZoneIds=["use1-az1"],
    InstanceTypes=["c6g.xlarge", "c7g.xlarge", "m6g.xlarge"],
)
print(r["AggregateScore"])
for s in r["CapacityManagerSupportabilityScores"]:
    print(s["InstanceType"], s["AvailabilityZoneId"], s["Score"])
```

スクリプトは、この呼び出しを市場と台数の組み合わせごとに繰り返し、ページに必要なものをすべて JSON に書き出して、その JSON と同じ文書だけから 1 つの HTML を作ります。作るときに決めたことは次のとおりです。

![自作スクリプトの流れの図。1 送る前の確認、2 値を除いて送り直すリクエスト、3 すべてのデータを入れた JSON、4 英語と日本語の HTML、の順につながる。JSON から HTML へは、AWS を呼ばずに作り直す点線の経路がある。終了コード 0 の実行のファイルは出力先に置かれ、完了しなかった実行は別名で保存される。](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/c8fba7927e164d/zenn/articles/c8fba7927e164d/07-script.png)
*図 7: 集めてから描く流れ。失敗した実行は、正常なレポートを置き換えない*

| # | 決めたこと | 理由 |
|---|---|---|
| 1 | Capacity Manager の有効化は `--enable` を付けたときだけ行い、`--expect-account` で指定したアカウントでしか実行しません | 有効化はアカウントの設定を変えるので、意図しないアカウントで行わないためです |
| 2 | `--region` を必須にします | 既定値が間違っていると、意図しない Region で有効化してしまうためです |
| 3 | 集約スコアを 1 リクエストごとに表示します | 分割した場合に、全体を通した 1 つの集約は得られないと解釈したためです。これは筆者の解釈です |
| 4 | 応答にない組み合わせは N/A、失敗したリクエストに含まれていた組み合わせは Error、EC2 が提供していないと答えた組み合わせは Not offered と表示します。属性指定の場合は、失敗したリクエストの対象タイプを確定できないので、表の上に警告を出し、最良スコアに不完全な可能性の印を付けます | Low と区別し、失敗を低いスコアに見せないためです。応答にない理由はドキュメントに書かれていません |

| 6 | API が値を名指しで拒否したときは、その値を除いて最大 3 回まで送り直し、以後のリクエストでも避けます | 送る前に判定できない誤りで、全部がエラーになるのを防ぐためです。文言は観察に基づく仮定なので、一致しなければ送り直しません |

| 8 | Ctrl-C、SIGTERM、SIGHUP で止められたときは、一時ファイルを消して終了コード 130 で終わります | 途中の空のレポートが残って、次の実行を邪魔しないためです |

| 12 | 集めたデータは JSON ファイルに書き出し、HTML は書き出す JSON と同じ文書を解析し直して作ります。`--from-json` を使うと、API を呼ばずに HTML だけ作り直せます | 見た目や文言を直すたびに API を呼ぶと、1 時間 100 クエリの上限を使うためです。JSON があれば、ほかのツールからも同じ事実を読めます。HTML が JSON だけに依存するので、JSON に欠けがあればテストで分かります |

| 7 | 有効化の直後は `initial-ingestion-in-progress` と表示されました | 有効化のページと API リファレンスに、14 日分の履歴の収集、数時間かかること、`initial-ingestion-in-progress`、`ingestion-complete`、`ingestion-failed` の状態が書かれています | 記載済み。この間にチェックが使えるかは未記載 |

あわせて、公式の側で分かったことが 2 つあります。1 つ目は、GetCapacityManagerSupportabilityScores が EC2 の API リファレンスの目次に見当たらず、ページの Markdown 版も取得できなかった（404）ことです。この API は、ユーザーガイド、AWS CLI のリファレンス、boto3 のリファレンスで説明されています。2 つ目は、送る前の確認に使う DescribeInstanceTypeOfferings と DescribeAvailabilityZones が、ここで使う形で記載されていることです。前者は `availability-zone-id` の場所の種類と、現在の Region の AZ ID を受け付けます。後者は `zone-id` のフィルターと `AllAvailabilityZones` を受け付けます。

公式ドキュメントに書かれていないことも、はっきりさせておきます。

| # | 疑問 | 状況 |
|---|---|---|
| 1 | 別のアカウントが同じ条件で同じ時刻に呼ぶと、同じスコアになるか | 書かれていません。結果は呼び出したアカウントのものとして扱うのが安全です |
| 2 | High、Medium、Low の境界の正確な基準 | 「数倍」「余裕をほとんど残さず」以上の定義は書かれていません |
| 3 | SDK が自動で再試行したリクエストが、1 時間 100 クエリに数えられるか | 書かれていません。なお、`ThrottlingException` を SDK が自動で再試行することは、[Common Error Types](https://docs.aws.amazon.com/AWSEC2/latest/APIReference/CommonErrors.html) に書かれています |

## まとめ

Check supportability は、起動の前に、インスタンスタイプと AZ の組み合わせごとの空き具合を、要求量に対する相対値として High、Medium、Low で返す API です。使えるのは Unified Operations プランのお客様で、Capacity Manager を有効にした Region から呼び、結果は原則として第三者に開示できません。どのスコアも起動を保証せず、重要なワークロードには、スコアに関係なく Capacity Reservation か将来日付の Capacity Reservation を使うのが公式の勧めです。

ミックスフリートでは集約スコア、1 つのタイプしか使えない場合は組み合わせごとのスコア、起動失敗の後は同じ条件での再実行、と読み方を使い分けます。ただし、組み合わせごとのスコアの Spot での読み方は、公式に書かれていません。Spot は SPS が土台で、すでに SPS を直接使っている場合は、集約スコアを Spot の信号として読むよう公式は書いています。

SPS には、スコアを時系列で追う AWS Solutions Library のガイダンス実装があります。一方、Check supportability 向けの公式のサンプルアプリやガイダンス実装は、2026-11-05 時点では見つけられませんでした。公式が勧めているのは、起動のたびではなく、計画や見直しのときの実行です。この API には、アカウントあたり 1 時間 100 クエリの上限があり、結果の共有にも制限があります。スコアの根拠は、いつでも冒頭の [Check supportability](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-supportability.html) のページに戻って確認してください。
