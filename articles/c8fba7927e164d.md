## はじめに

P5 や P6 のような GPU インスタンスを、決まった期間に決まった台数だけ確実に使いたいなら、[ML 向けキャパシティブロック](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-capacity-blocks.html)（Capacity Blocks for ML）や[キャパシティ予約](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-capacity-reservations.html)（Capacity Reservation）で先に押さえるのが基本です。一方で、新しいモデルや構成をすぐに試したいときは、予約を待たずにオンデマンドやスポットで起動したくなります。そのときに知りたいのは、どのリージョンのどの AZ に、欲しい台数を支えられるだけの空きがありそうか、です。

スポットについては、起動前にリクエストの成功しやすさを 1 から 10 で返す [Spot placement score](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/spot-placement-score.html)（SPS）という API が以前からあります。[EC2 Capacity Manager](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager.html) の real-time supportability checks は、この目安をオンデマンドにも広げ、しかもインスタンスタイプと AZ の候補全体として、欲しい台数を支えられそうかを返します。ドキュメントのページ名とコンソールのボタンは Check supportability なので、この記事ではこの名前で呼びます。Check supportability は、候補の組み合わせごとのスコアと候補全体のスコアを、起動の前に High、Medium、Low の 3 段階で返し、起動も予約もしません。一次情報は [Check supportability](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-supportability.html) のページで、使い方の流れは AWS Compute Blog の[公式の紹介記事](https://aws.amazon.com/blogs/compute/plan-and-measure-ec2-flexibility-with-amazon-ec2-capacity-manager/)にもまとまっています。

チェック自体に費用はかかりません。使える条件は[前提と制約](#前提と制約)にまとめます。条件に当てはまらないアカウントでも、スポットに限れば、[SPS](#spot-placement-score) で同じ種類の目安を得られます。評価するのは現在のキャパシティだけで、日付を指定して将来の空き具合を調べることはできません。

筆者のアカウントで取得したスコアは、[結果の扱いの決まり](#前提と制約)により載せていません。載せている応答例は、公式ドキュメントのものです。

## 概要と使いどころ

Check supportability には、インスタンスタイプと AZ の候補と必要な量を[渡します](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-supportability.html)。1 つのインスタンスタイプと 1 つの AZ の組を、この記事では組み合わせ（公式の combination）と呼び、候補全体のスコアを集約スコアと呼びます。使いどころは公式に 3 つ書かれています。

| # | 使いどころ | 公式の記述 |
|---|---|---|
| 1 | 起動を支えられるかの確認 | confirm that a launch is supportable |
| 2 | 候補の中で強い場所の発見 | find where capacity is strongest across your options |
| 3 | 起動失敗の切り分け | diagnose a launch failure |

Check supportability を使えるかどうかは、サポートプランと Capacity Manager の設定で決まります。この節では、使う前の条件と、必要な権限を確認します。

| # | 条件 | 内容 | 出典 |
|---|---|---|---|
| 1 | サポートプラン | AWS Support の [Unified Operations プラン](https://aws.amazon.com/premiumsupport/plans/unified-operations/)のアカウントだけが使えます | [Check supportability](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-supportability.html) |
| 2 | Capacity Manager の有効化 | アカウントにつき 1 つのリージョンで有効にします。[AWS Organizations](https://docs.aws.amazon.com/organizations/latest/userguide/orgs_introduction.html) との連携の設定は不要です | [EC2 Capacity Manager](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager.html)、[Check supportability](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-supportability.html) |

| 4 | 結果の扱い | AWS Service Terms の第 5.9 項（EC2 Capacity Manager）は、データを自社の内部の容量計画とワークロード管理に限って使うこと、自社のために行動する委託先や代理人を除く第三者に開示しないこと、類似または競合する製品やサービスの開発や提供に使わないことを定めています。ブログやスライドへの掲載も第三者への開示に当たると読めます。これは原文の要約で、法的な判断ではありません | [Check supportability](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-supportability.html)、[AWS Service Terms](https://aws.amazon.com/service-terms/) |

AWS CLI で呼ぶ場合は、`get-capacity-manager-supportability-scores` が追加された [2.39.1](https://github.com/aws/aws-cli/blob/2.39.1/CHANGELOG.rst) 以降のバージョンに更新してください。

Check supportability の API は [`GetCapacityManagerSupportabilityScores`](https://docs.aws.amazon.com/cli/latest/reference/ec2/get-capacity-manager-supportability-scores.html) です。呼び出し元には、この API と、状態を確かめる [`GetCapacityManagerAttributes`](https://docs.aws.amazon.com/AWSEC2/latest/APIReference/API_GetCapacityManagerAttributes.html)、有効にするときの [`EnableCapacityManager`](https://docs.aws.amazon.com/AWSEC2/latest/APIReference/API_EnableCapacityManager.html) を呼べる権限が要ります。

Capacity Manager は、[アカウント単位の有効化のページ](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/enable-capacity-manager-account.html)の手順で有効にします。有効にすると 14 日分の履歴の取り込みが始まり、状態が `ingestion-complete` になるまで数時間かかることがあります。

## 呼び出し方

コンソールからも実行できます。AZ は名前ではなく AZ ID で指定します。`ap-northeast-1c` のような AZ 名と物理的なゾーンの対応はアカウントごとにランダムに決まるので、同じ AZ 名が別のゾーンを指すことがあります。AZ ID はどのアカウントでも同じゾーンを指します。詳しくは [Availability Zone IDs for your AWS resources](https://docs.aws.amazon.com/ram/latest/userguide/working-with-az-ids.html) を参照してください。例の `use1-az1` は、米国東部（バージニア北部）の AZ ID です。

API は Capacity Manager を有効にしたリージョンで呼びます。調べる AZ は別のリージョンでもよく、[公式の紹介記事](https://aws.amazon.com/blogs/compute/plan-and-measure-ec2-flexibility-with-amazon-ec2-capacity-manager/)によると、1 回のチェックに、複数のリージョンにまたがる AZ を入れられます。公式は、起動のたびに呼ぶのではなく、ワークロードを計画するときや見直すときに実行することを勧めています。他のリージョンの起動が、リージョンをまたぐ呼び出しに依存しないようにするためです。

次の例は [How to check capacity](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-check-capacity.html) の公式の例に `--region` を足したものです。3 つのインスタンスタイプを候補として、use1-az1 でオンデマンドの 50 台を調べます。

```bash
export CM_REGION="ap-northeast-1"
aws ec2 get-capacity-manager-supportability-scores \
    --region "$CM_REGION" \
    --market-type "on-demand" \
    --capacity-amount 50 \
    --capacity-unit "instances" \
    --capacity-availability-zone-ids '["use1-az1"]' \
    --instance-types '["c6g.xlarge", "c7g.xlarge", "m6g.xlarge"]'
```

返ってくる JSON の各行は 1 つの組み合わせのスコアで、`AggregateScore` は集約スコアです。

```json
{
    "AggregateScore": "high",
    "CapacityManagerSupportabilityScores": [
        { "InstanceType": "c6g.xlarge", "AvailabilityZoneId": "use1-az1", "Score": "high" },
        { "InstanceType": "c7g.xlarge", "AvailabilityZoneId": "use1-az1", "Score": "high" },
        { "InstanceType": "m6g.xlarge", "AvailabilityZoneId": "use1-az1", "Score": "medium" }
    ]
}
```

パラメータと個々の上限は、[get-capacity-manager-supportability-scores の CLI リファレンス](https://docs.aws.amazon.com/cli/latest/reference/ec2/get-capacity-manager-supportability-scores.html)の Options に載っています。

| # | パラメータ | 内容 |
|---|---|---|
| 1 | `--market-type` | `on-demand` か `spot` を指定します |
| 2 | `--capacity-amount` | 必要な量で、1 以上の整数です |
| 3 | `--capacity-unit` | 量の単位で、`instances` は台数、`vcpus` は vCPU 数です |
| 4 | `--capacity-availability-zone-ids` | 調べる AZ の ID を、最大 10 個まで指定します |
| 5 | `--instance-types` | 調べるインスタンスタイプを、最大 50 個まで指定します |
| 6 | `--instance-requirements-with-metadata` | 名前の代わりに vCPU やメモリなどの属性で指定します。`--instance-types` とは同時に指定できません |

これらの個別の上限とは別に、タイプ数と AZ 数の積が 1 リクエストで 100 個の組み合わせまで、という上限があります。例えば 10 タイプと 3 AZ なら $10 \times 3 = 30$ 個の組み合わせになります。[Quotas](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-check-quotas.html) は、1 回の問い合わせでより多くの情報を得るために、広い条件でリクエストすることを勧めています。集約スコアは 1 リクエストの候補全体に対する値なので、候補を複数のリクエストに分けると、全体を通した集約スコアは得られません。

## スコアの読み方

スコアは、組み合わせがいま保有しているキャパシティを、要求した量と比べた[比](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-score-meaning.html)です。3 段階の意味は次のとおりです。

| # | スコア | 公式の意味 |
|---|---|---|
| 1 | High | 組み合わせが要求量の数倍を保有しています。進めてよい水準です |
| 2 | Medium | 組み合わせは余裕をほとんど残さず要求量を満たせます。安全というより実行可能な水準で、起動は失敗することがあります |
| 3 | Low | 組み合わせは要求量より少ないものの、一部のキャパシティは残っていると見込まれます |

![英語の模式図。題は Held capacity relative to the request、副題は Schematic, not to scale。request と書いた縦線と、bar: held capacity という説明があり、保有量の横棒が、High（several times the request）は線を大きく超え、Medium（little to spare）はわずかに超え、Low（below the request）は線に届かない](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/c8fba7927e164d/zenn/articles/c8fba7927e164d/03-score-meaning.png)
*図 3: スコアは保有量を要求量と比べたものです。縮尺は正確ではありません*

読むときの注意が 3 つあります。

1 つ目は、スコアが要求量に対する相対値だという点です。同じ組み合わせ、同じ時刻でも、50 台なら High、5,000 台なら Low になりえます。量を決めずにスコアだけを比べても意味がありません。

2 つ目は、どのスコアも保証ではないという点です。公式は、High でも容量不足のエラーは起こりうると明記し、重要なワークロードにはスコアに関係なく、キャパシティ予約か[将来の日付のキャパシティ予約](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-reservations-create.html#create-future-cr)（Future-dated Capacity Reservation）を使うよう勧めています。後者の対象のファミリーは C、G、I、M、R、T、U、X に限られます。

3 つ目は、集約スコアの意味です。公式は、組み合わせごとの値が Low でも集約スコアが High になるのは矛盾ではなく、意図した動作だと説明しています。1 つの組み合わせでは要求量を支えられなくても、候補を合わせれば支えられるという意味で、候補を柔軟に保つ理由になります。

![英語の模式図。題は Low per combination, High in aggregate、副題は Schematic: the number of combinations is illustrative。Combination 1 から Combination 3 はどれも Low で、3 本の矢印が Aggregate score の箱に集まり、その中は High](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/c8fba7927e164d/zenn/articles/c8fba7927e164d/04-pair-vs-aggregate.png)
*図 4: 組み合わせごとが Low でも、集約スコアは High になることがあります*

## スコアの使い分け

読むスコアは、フリートが複数のインスタンスタイプを使えるか、1 つのタイプに決まっているか、すでに起動が失敗したかで[変わります](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-score-actions.html)。

| # | 状況 | 見るもの | 公式が勧める行動 |
|---|---|---|---|
| 1 | 複数のインスタンスタイプのどれで起動してもよいフリート（ミックスフリート） | 集約スコア | High なら進めます。[Auto Scaling グループ](https://docs.aws.amazon.com/autoscaling/ec2/userguide/what-is-amazon-ec2-auto-scaling.html)、[Karpenter](https://karpenter.sh/)、[EC2 Fleet](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/Fleets.html) といったオーケストレーターが、起動時に組み合わせへ分散します。Medium か Low なら、候補を増やすか、時間をおいて再試行します |
| 2 | 1 つのタイプしか使えない | 組み合わせごとのスコア | 最も高い組み合わせを選びます。並んだ場合は、コスト、性能、慣れで決めます |
| 3 | 起動が容量不足（公式の呼び名は `InsufficientCapacityError`）で失敗した | 同じ市場、タイプ、AZ、量、単位で確かめ直したときの組み合わせごとのスコア | High なら、その組み合わせにキャパシティはあるが、要求のサイズに合わせるためにホストのリサイズが必要な状態だと説明されています。起動できる分を起動し、残りは数分おきに再試行します。Medium か Low なら空きが限られているので、High だった別の組み合わせで起動するか、タイプを増やします |

![英語の図。題は Which score to read、副題は By fleet situation。1 Several types は Read the aggregate へ進み、結果は High: proceed か、Medium or Low: add options or wait。2 One type only は Read each combination へ進み、Pick the highest-scoring combination。3 Capacity error は Re-check the request へ進み、結果は High: launch, retry the rest か、Medium or Low: use another High one, or add types](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/c8fba7927e164d/zenn/articles/c8fba7927e164d/05-which-score.png)
*図 5: 状況ごとに読むスコアが違います。1 列目と 3 列目の 2 つの結果はどちらか一方で、順番ではありません*

使えるインスタンスタイプが 1 つに決まっていて、オンデマンドで起動する場合は、2 行目に当たります。そのタイプ 1 つと、複数のリージョンの AZ ID を渡し、組み合わせごとのスコアが最も高い AZ を選びます。

このページの行動の指針は、市場を区別していません。スポットについては、[Relationship to Spot placement score](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-sps.html) が、すでに SPS を直接使っている場合は集約スコアをスポットの信号として読むよう書いています。

## Spot placement score

Check supportability のスポットのスコアは、以前からある SPS を[土台にしています](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-sps.html)。SPS は、個々の組み合わせではなく、柔軟性の全体を評価します。

[Spot placement score](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/spot-placement-score.html) によると、SPS のスコアは推奨にすぎず、空き容量や中断リスクの保証はなく、追加の料金もかかりません。仕組みは [How Spot placement score works](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/how-sps-works.html) に書かれています。 スコアが意味を持つのは、スポットのリクエストの構成がスコアを取ったときと同じで、配分戦略（フリートがどのスポットプールから起動するかを決める設定）に `capacity-optimized` を使う場合です。

SPS と Check supportability の違いは次のとおりです。

| # | 観点 | SPS（GetSpotPlacementScores） | Check supportability |
|---|---|---|---|
| 1 | 粒度 | リージョンか AZ ごとで、上位 10 件です | 指定した組み合わせごとです |
| 2 | 必要な条件 | [IAM 権限](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/sps-iam-permission.html)です | [前提と制約](#前提と制約)のとおりです |

オンデマンドの空き具合は、スポットのスコアから推測せず、`--market-type on-demand` で調べてください。公式は 2 つを別の市場として扱っています。

## SPS を自動で追跡するガイダンス実装

SPS が返すのは取得した時点のスコアだけなので、時間の変化を見たい場合は自分で記録する必要があります。それを代わりにやってくれるのが、AWS Solutions Library の [Guidance for Building a Spot Placement Score Tracker Dashboard on AWS](https://aws.amazon.com/solutions/guidance/building-a-spot-placement-score-tracker-dashboard-on-aws/) で、[Spot placement score の使い方のページ](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/work-with-spot-placement-score.html)から案内されています。コードは [GitHub のリポジトリ](https://github.com/aws-solutions-library-samples/guidance-for-ec2-spot-placement-score-tracker/tree/433c22eebc26f85a84bea05cae46282ab3476888)にあります。AWS が公開する、自分のアカウントに構築して使う参考実装で、リポジトリの README とコードに基づくと、次のような構成です。

| # | 項目 | 内容 |
|---|---|---|
| 1 | 構成 | [AWS CDK](https://docs.aws.amazon.com/cdk/v2/guide/home.html) の Python で、[Lambda](https://docs.aws.amazon.com/lambda/latest/dg/welcome.html)、[EventBridge](https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-what-is.html) のスケジュール、[CloudWatch](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/WhatIsCloudWatch.html) ダッシュボード、IAM ロールを作ります。設定ファイルとコードは、`cdk bootstrap` で用意される S3 バケットに置かれます |
| 2 | スコアの取得 | `ec2:GetSpotPlacementScores` を使います。スポットだけが対象で、オンデマンドは見ません |
| 3 | 入力 | インスタンスタイプかインスタンス属性、リージョンのリスト、目標の容量、AZ 単位かリージョン単位かを指定します。Karpenter が起動するノードの条件を定める NodePool の YAML から、インスタンスの要件を読む方法もあります |
| 4 | 出力 | スコアとスポット価格を CloudWatch のカスタムメトリクスにして、ダッシュボードに時系列で表示します |
| 5 | 費用 | README は、us-east-1 の既定の設定で、月額約 25.37 ドルと見積もっています。大半は CloudWatch のカスタムメトリクスの費用です |
| 6 | ライセンス | MIT-0 です |

使いどころは、スポットで GPU インスタンスを使いたい場合に、指定したインスタンスタイプの組と容量の構成について、リージョンや AZ ごとのスコアの推移を見ることです。取りやすい構成を、Karpenter の NodePool などで起動を許すインスタンスタイプの一覧に入れ、実際の起動は Karpenter や EC2 Fleet の配分戦略に任せる、という運用が考えられます。`capacity-optimized` 以外の配分戦略を使う場合に、スコアと起動結果が対応するかは公式に書かれていないので、そのときのスコアは傾向の参考にとどまる、というのが筆者の解釈です。

注意点も書かれています。README は、SPS では新しい構成を多数投げると制限され、設定が多すぎると Lambda の実行が失敗しうると説明しています。目標の容量にも上限があります。[Spot placement score](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/spot-placement-score.html) のドキュメントによると、上限は直近のスポットの利用量に今後の増加を見込んで決まり、利用実績がなければスポットのリクエスト上限に合わせた低い既定値になります。同じページは、意図された使い方と異なるパターンを検知すると、24 時間あたりの新しい構成の数を制限することがあると書いています。

## まとめ

Check supportability を使うと、予約を待たずにオンデマンドやスポットですぐ試したいときに、どのリージョンのどの AZ を候補にするかを、起動の前に決められます。
