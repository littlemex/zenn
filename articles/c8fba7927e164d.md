## はじめに

EC2 Capacity Manager の Check supportability は、インスタンスタイプと Availability Zone（AZ）の組み合わせが、いまの空きで要求した量を支えられそうかを、起動する前に High、Medium、Low の 3 段階で返す機能です。On-Demand と Spot のどちらでも調べられ、起動も予約もしません。値の定義は [What the scores mean](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-score-meaning.html) にあり、一次情報は [Check supportability](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-supportability.html) のページです。

GPU インスタンスを数十台まとめて起動しようとして、容量不足のエラーで止まった経験はないでしょうか。Spot には、起動前にリクエストの成功しやすさを 1 から 10 で返す Spot placement score（SPS）という API が以前からありますが、On-Demand では、起動する前に空き具合の目安を得る手段が乏しい、というのが筆者の認識でした。Check supportability は、その目安を On-Demand でも与えます。

チェック自体に費用はかかりませんが、使えるのは AWS Support の有料プランの 1 つである Unified Operations プランのお客様だけです。評価するのは現在のキャパシティだけで、日付を指定して将来の空き具合を調べることはできません。

## 概要と使いどころ

[公式ドキュメント](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-supportability.html)によると、使うインスタンスタイプと Availability Zone の候補、それに必要な量を渡すと、候補ごとのスコアと、候補全体のスコアが返ってきます。この記事では、候補全体のスコアを集約スコアと呼びます。使えるインスタンスタイプや AZ の候補を増やすべきかを、起動する前に判断するための道具です。使いどころは公式に 3 つ書かれています。

| # | 使いどころ | 公式の記述 |
|---|---|---|
| 1 | 起動を支えられるかの確認 | confirm that a launch is supportable |
| 2 | 候補の中で強い場所の発見 | find where capacity is strongest across your options |
| 3 | 起動失敗の切り分け | diagnose a launch failure |

*図 1: 要求を渡すと、組み合わせごとのスコアと集約スコアが返ります。応答例は公式ドキュメントのものです*

確約はしない、という点も同じページに明記されています。チェックはある時点のキャパシティを反映したもので、キャパシティを予約せず、後の起動が成功することも保証しません。

Check supportability の API である `GetCapacityManagerSupportabilityScores` に必要な IAM 権限は、筆者が確認した範囲では、2026-11-05 時点で公開されていません。IAM アクションの一覧を機械可読の形で公開している [AWS Service Reference](https://servicereference.us-east-1.amazonaws.com/v1/ec2/ec2.json) は 2026-10-29 に更新されていて、`EnableCapacityManager` と `GetCapacityManagerAttributes` は IAM アクションとして載っていますが、このオペレーションには対応する IAM アクションがありません。筆者は管理者ロールで試しました。プランの条件を満たさないアカウントでどのエラーが返るかも、公式には書かれていません。エラーが出たときに、プラン、権限、Region のどれが原因かを、応答だけで判別できるとは限りません。

4 つ目の条件について、AWS Service Terms の EC2 Capacity Manager の項は、スコアなどのデータを自社の内部の容量計画とワークロード管理の目的に限って使うこと、自社のために行動する委託先や代理人を除く第三者に開示しないことを定めています。直接か間接かを問わず、類似または競合する製品やサービスの開発、改良、提供に使うことや、他者に使わせることも禁じています。AWS が違反していると合理的に判断した場合、Capacity Manager の利用が停止されることがあります。この定義は、Check supportability のスコアに限らず、Capacity Manager を通じて得られるヘッドルーム指標やしきい値などの容量に関する情報も対象にしています。これは原文の要約であり、法的な判断ではありません。ブログやスライドでの公開は第三者への開示に当たると読めるので、自分のアカウントのスコアを載せたくなったときは、先に原文を確認し、必要なら社内の法務に相談してください。

### Capacity Manager の有効化

無効なアカウントでは、まず有効にします。[EnableCapacityManager](https://docs.aws.amazon.com/AWSEC2/latest/APIReference/API_EnableCapacityManager.html) は、EC2 のキャパシティ使用状況の取り込みを始める API で、初回のデータ処理に数時間かかることがあると書かれています。[EC2 Capacity Manager](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager.html) によると、有効にできる Region はアカウントにつき 1 つです。[How to check capacity](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-check-capacity.html) によると、Check supportability はその有効にした Region で呼びます。[アカウント単位の有効化のページ](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/enable-capacity-manager-account.html)によると、有効にすると 14 日分の履歴を集め、数時間かかることがあり、その間は `initial-ingestion-in-progress`、終わると `ingestion-complete` と表示されます。この処理が終わる前にチェックが使えるかどうかは、公式に書かれていません。有効化の直後にエラーや空の応答が返ったら、時間をおいて再試行してください。

```bash
export CM_REGION="ap-northeast-1"
aws sts get-caller-identity --region "$CM_REGION"
aws ec2 get-capacity-manager-attributes --region "$CM_REGION"
aws ec2 enable-capacity-manager --region "$CM_REGION"
aws ec2 get-capacity-manager-attributes --region "$CM_REGION"
```

最初の `get-caller-identity` で実行するアカウントを、最初の `get-capacity-manager-attributes` で有効化前の状態を確認します。[enable-capacity-manager](https://docs.aws.amazon.com/cli/latest/reference/ec2/enable-capacity-manager.html) が有効化で、[get-capacity-manager-attributes](https://docs.aws.amazon.com/cli/latest/reference/ec2/get-capacity-manager-attributes.html) が状態の確認です。有効化はアカウントの設定を変える操作です。公式には書かれていませんが、筆者が試した範囲では、どの Region でも有効にしていないアカウントで `get-capacity-manager-attributes` を呼ぶと、`CapacityManager.Disabled` というエラーが返りました。ある Region で有効にした後は、ほかの Region から呼ぶと `CapacityManager.IncorrectRegion` が返り、メッセージに有効にしている Region の名前が含まれていました。共有のアカウントでは、有効化の前にどこかの Region でこの API を呼べば、すでに別の Region で有効かどうかが分かります。すでに別の Region で有効なときに有効化を実行した場合の挙動は、公式に書かれていません。

## 呼び出し方

市場、つまり On-Demand か Spot かと、必要な量、AZ の ID、インスタンスタイプを渡すと、組み合わせごとのスコアと集約スコアが返ります。コンソールからも実行できます。[aws-cli の変更履歴](https://github.com/aws/aws-cli/blob/v2/CHANGELOG.rst)によると、AWS CLI では 2.39.1 でこのコマンドが追加されました。次の例は [How to check capacity](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-check-capacity.html) の公式の例に、Capacity Manager を有効にした Region を指す `--region` を足したものです。3 つのインスタンスタイプを候補として、use1-az1 で On-Demand の 50 台を調べます。呼び出し先の Region と調べる AZ の Region は別でも構いません。

```bash
aws ec2 get-capacity-manager-supportability-scores \
    --region "$CM_REGION" \
    --market-type "on-demand" \
    --capacity-amount 50 \
    --capacity-unit "instances" \
    --capacity-availability-zone-ids '["use1-az1"]' \
    --instance-types '["c6g.xlarge", "c7g.xlarge", "m6g.xlarge"]'
```

返ってくる JSON も公式の例です。各行は 1 つの組み合わせのスコアで、`AggregateScore` は候補全体のスコアです。

```json
{
    "AggregateScore": "high",
    "CapacityManagerSupportabilityScores": [
        { "InstanceType": "c6g.xlarge", "AvailabilityZoneId": "use1-az1", "Score": "high" },
        { "InstanceType": "c7g.xlarge", "AvailabilityZoneId": "use1-az1", "Score": "high" },
        { "InstanceType": "m6g.xlarge", "AvailabilityZoneId": "use1-az1", "Score": "medium" }
    ]
}
```

パラメータと個々の上限は、2026-11-05 に確認した [get-capacity-manager-supportability-scores の CLI リファレンス](https://docs.aws.amazon.com/cli/latest/reference/ec2/get-capacity-manager-supportability-scores.html)の Options に載っています。

| # | パラメータ | 内容 |
|---|---|---|
| 1 | `--market-type` | `on-demand` か `spot` を指定します |
| 2 | `--capacity-amount` | 必要な量で、1 以上の整数です。スコアはこの量に対する相対値です |
| 3 | `--capacity-unit` | 量の単位で、`instances` は台数、`vcpus` は vCPU 数です |
| 4 | `--capacity-availability-zone-ids` | 調べる AZ の ID を、最大 10 個まで指定します。別の Region の AZ も指定できます |
| 5 | `--instance-types` | 調べるインスタンスタイプを、最大 50 個まで指定します |
| 6 | `--instance-requirements-with-metadata` | 名前の代わりに vCPU やメモリなどの属性で指定します。`--instance-types` とは同時に指定できません |

AZ の 10 個とタイプの 50 個という個別の上限とは別に、タイプ数と AZ 数の積が 1 リクエストで 100 組まで、という上限があります。例えば 10 タイプと 3 AZ なら 30 組になります。[Quotas](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-check-quotas.html) は、1 回の問い合わせでより多くの情報を得るために、広い条件でリクエストすることを勧めています。

呼び出しの場所には決まりがあります。API は Capacity Manager を有効にした Region で呼び、1 回の呼び出しで任意の Region の AZ を調べられます。また公式は、起動のたびに呼ぶのではなく、ワークロードを計画するときや見直すときに実行することを勧めています。他の Region の起動が、Region をまたぐ呼び出しに依存しないようにするためです。AZ は名前ではなく AZ ID で指定します。`ap-northeast-1c` のような AZ 名と物理的なゾーンの対応はアカウントごとにランダムに決まるので、同じ AZ 名が別のゾーンを指すことがあります。AZ ID はどのアカウントでも同じゾーンを指します。詳しくは [Availability Zone IDs for your AWS resources](https://docs.aws.amazon.com/ram/latest/userguide/working-with-az-ids.html) を参照してください。

## スコアの読み方

スコアの定義は [What the scores mean](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-score-meaning.html) にあります。各スコアは、そのインスタンスタイプと AZ の組み合わせがいま保有しているキャパシティを、要求した量と比べた比です。

| # | スコア | 公式の意味 |
|---|---|---|
| 1 | High | 組み合わせが要求量の数倍を保有しています。進めてよい水準です |
| 2 | Medium | 組み合わせは余裕をほとんど残さず要求量を満たせます。安全というより実行可能な水準で、起動は失敗することがあります |
| 3 | Low | 組み合わせは要求量より少ないものの、一部のキャパシティは残っていると見込まれます |

![スコアの意味の模式図。要求量を示す縦線に対して、保有量を示す横棒が、High は線を大きく超え、Medium はわずかに超え、Low は線に届かない。それぞれ、保有量が要求量の数倍、余裕がほとんどない、要求量より少ない、という意味。下に、同じ組み合わせ、同じ時刻でも、50 台なら High に、5,000 台なら Low になりうる、と書かれている。](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/c8fba7927e164d/zenn/articles/c8fba7927e164d/03-score-meaning.png)
*図 3: スコアは保有量を要求量と比べたものです。縮尺は正確ではありません*

読むときの注意が 4 つあります。

1 つ目は、スコアが要求量に対する相対値だという点です。同じ組み合わせ、同じ時刻でも、50 台なら High、5,000 台なら Low になりえます。量を決めずにスコアだけを比べても意味がありません。

2 つ目は、どのスコアも保証ではないという点です。公式は、High でも容量不足のエラーは起こりうると明記し、重要なワークロードにはスコアに関係なく Capacity Reservation か将来日付の Capacity Reservation を使うよう勧めています。前者は [On-Demand Capacity Reservations](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-capacity-reservations.html) です。後者は [Capacity Reservation の作成のページ](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-reservations-create.html#create-future-cr)によると、対象のファミリーが C、G、I、M、R、T、U、X に限られます。公式の推奨には名前が挙がっていませんが、GPU を期間を決めて押さえる手段として [Capacity Blocks for ML](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-capacity-blocks.html) もあります。

3 つ目は、集約スコアの意味です。応答には、組み合わせごとのスコアに加えて、候補全体の集約スコアが入ります。公式は、組み合わせごとの値が Low でも集約が High になるのは矛盾ではなく意図した動作だと説明しています。1 つの組み合わせでは要求量を支えられなくても、候補を合わせれば支えられるという意味で、柔軟性を保つ理由になります。

![組み合わせごとのスコアと集約スコアの模式図。3 つの組み合わせがすべて Low でも、集約スコアは High になることがある。組み合わせの数は例示で、3 つに意味はない。下に、1 つでは要求量を支えられなくても合わせれば支えられ、候補を柔軟に保つ理由になる、と書かれている。](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/c8fba7927e164d/zenn/articles/c8fba7927e164d/04-pair-vs-aggregate.png)
*図 4: 組み合わせごとが Low でも、集約スコアは High になることがあります*

4 つ目は、リクエストを分けたときの集約です。1 リクエストの上限は公式に 100 組と定められています。超えたときにエラーになるのか切り詰められるのかは書かれていないので、筆者は 100 組以内に収めて呼び出しを分ける前提で考えています。公式は分けた場合の集約の扱いも書いていませんが、集約は 1 リクエストの候補全体に対する値なので、複数のリクエストをまたいだ 1 つの集約は得られない、というのが筆者の解釈です。属性指定では解決後のタイプ数を事前に決められないため、100 組を超える場合の挙動は確認していません。

## スコアの使い分け

[What to do based on your score](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-score-actions.html) は、フリートの形と状況で読み方を分けています。

| # | 状況 | 見るもの | 公式が勧める行動 |
|---|---|---|---|
| 1 | 複数タイプを使えるミックスフリート | 集約スコア | High なら進めます。Auto Scaling グループ、Karpenter、EC2 Fleet といったオーケストレーターが、起動時に組み合わせへ分散します。Medium か Low なら、候補を増やすか、時間をおいて再試行します |
| 2 | 1 つのタイプしか使えない | 組み合わせごとのスコア | 最も高い組み合わせを選びます。並んだ場合は、コスト、性能、慣れで決めます |
| 3 | 起動が容量不足で失敗した | 同じ市場、単位、タイプ、AZ、量で確かめ直したときの組み合わせごとのスコア | High なら、その組み合わせにキャパシティはあるが、要求のサイズに合わせるためにホストのリサイズが必要な状態だと説明されています。起動できる分を起動し、残りは数分おきに再試行します。Medium か Low なら空きが限られているので、High だった別の組み合わせで起動するか、タイプを増やします |

![どのスコアを読むかの図。1 複数タイプなら集約スコアを読み、結果は、High なら進める、Medium か Low なら候補を足すか待つ、のどちらか。2 タイプが 1 つだけなら組み合わせごとを読み、最も高い組み合わせを選ぶ。3 容量不足のエラーが出たら同じ条件で確かめ直し、結果は、High なら空きはあるので起動して残りを再試行する、Medium か Low なら別の High の組み合わせを使うかタイプを増やす、のどちらか。下に、同じ条件とは市場、単位、タイプ、量、AZ をそろえることで、Spot は SPS を直接使っているなら集約スコアを読み、組み合わせごとの読み方は書かれていない、とある。](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/c8fba7927e164d/zenn/articles/c8fba7927e164d/05-which-score.png)
*図 5: 状況ごとに読むスコアが違います。1 列目と 3 列目の 2 つの結果はどちらか一方で、順番ではありません*

このページは、容量不足のエラーを `InsufficientCapacityError` と呼んでいますが、[EC2 のエラーコード一覧](https://docs.aws.amazon.com/AWSEC2/latest/APIReference/errors-overview.html)に載っているコードは `InsufficientInstanceCapacity` です。また、公式の手順はタイプ、AZ、量をそろえるとだけ書いていますが、市場と単位も失敗した要求と同じにしないと比べられない、というのが筆者の解釈です。

2 行目と 3 行目は、どちらも組み合わせごとのスコアを読む使い方です。このページの行動の指針は、市場を区別していません。一方、Spot については、[Relationship to Spot placement score](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-sps.html) が、SPS は柔軟性の全体を評価するもので、すでに SPS を直接使っている場合は集約スコアを Spot の信号として読むよう書いています。組み合わせごとの Spot の値の読み方は、どちらのページにも書かれていません。SPS の制約は、[次の節](#spot-placement-score-という先行する仕組み)で説明します。

3 行目の使い方は、エラーが、要求した量に対して空きが限られているためなのか、ホストのリサイズが必要なためなのかを切り分ける材料になります。

## Spot placement score という先行する仕組み

SPS は、Spot のリクエストがある Region や AZ でどれくらい成功しそうかを 1 から 10 で返す、以前からある API です。[Spot placement score](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/spot-placement-score.html) によると、スコアは推奨にすぎず、空き容量や中断リスクの保証はなく、追加の料金もかかりません。

仕組みは [How Spot placement score works](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/how-sps-works.html) と [GetSpotPlacementScores](https://docs.aws.amazon.com/AWSEC2/latest/APIReference/API_GetSpotPlacementScores.html) に書かれています。

| # | 項目 | 内容 | 出典 |
|---|---|---|---|
| 1 | スケール | 各 Region か AZ に 1 から 10 を付け、10 は成功する可能性が高いという意味です | [How Spot placement score works](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/how-sps-works.html) |
| 2 | 返る数 | 上位 10 の Region か、上位 10 の AZ です。既定は Region の一覧で、Local Zone は既定では無視されます。含めるには `IncludeLocalZones` を `true` にします | 同上 |
| 3 | 使える条件 | スコアが意味を持つのは、Spot のリクエストの構成がスコアを取ったときと同じで、`capacity-optimized` の配分戦略を使う場合です。Region のスコアは全 AZ を、AZ のスコアは単一の AZ を使うフリートを前提とし、Local Zone を含むスコアなら同じ Local Zone を使う必要があります | 同上 |
| 4 | 権限 | IAM のアクション `ec2:GetSpotPlacementScores` が書かれています。サポートプランの条件は、読んだページには出てきません | [Required permissions](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/sps-iam-permission.html) |
| 5 | 最小のタイプ数 | インスタンスタイプで指定する場合は、異なる 3 つ以上のタイプが必要で、満たさないと低いスコアが返ります。属性で指定する場合も、3 つ以上のタイプに解決される必要があります。ただし P、G、Trn、Inf ファミリーのインスタンスタイプには、この最小数は適用されません | [Spot placement score](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/spot-placement-score.html)、[How Spot placement score works](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/how-sps-works.html) |

Check supportability の Spot は、この SPS を土台にしています。[Relationship to Spot placement score](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-sps.html) によると、SPS は個々の組み合わせではなく柔軟性の全体を評価し、Spot の集約スコアが同等の指針になります。すでに SPS を直接使っている場合は、集約を Spot の信号として読むよう書かれています。組み合わせごとの Spot の値をどう扱うかは、公式に書かれていません。

2 つの仕組みは、同じ「空き具合の予測」でも対象が違います。

| # | 観点 | SPS（GetSpotPlacementScores） | Check supportability |
|---|---|---|---|
| 1 | 対象の市場 | Spot だけです | On-Demand と Spot です |
| 2 | スコアの形 | 1 から 10 の数値です | High、Medium、Low と、候補全体の集約です |
| 3 | 粒度 | Region か AZ ごとで、上位 10 件です | 指定した組み合わせごとで、1 リクエスト最大 100 組です |
| 4 | 必要な条件 | IAM 権限です | Capacity Manager の有効化と Unified Operations プランです。対応する IAM アクションは、AWS Service Reference に載っていません（2026-11-05 時点） |
| 5 | 結果の共有 | サービス条件の EC2 Capacity Manager の項の対象には含まれないと読めます。他の契約条項は確認していません | Capacity Manager を通じて得たデータとして、第三者への開示が制限されます |

![Spot placement score と Check supportability の比較表。Spot placement score は、市場が Spot だけ、スコアが 1 から 10、単位が Region か AZ の上位 10 件、条件が IAM 権限。Check supportability は、市場が On-Demand と Spot、スコアが High、Medium、Low と集約スコア、単位がタイプと AZ の組み合わせで 1 リクエスト 100 組まで、条件が Unified Operations と Capacity Manager。下に、Check supportability の IAM アクションは 2026-11-05 時点で未公開、とある。](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/c8fba7927e164d/zenn/articles/c8fba7927e164d/06-sps-vs-supportability.png)
*図 6: 2 つの仕組みの、公式ドキュメントにある違いです*

出典は表の上で挙げたページと、[Check supportability](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-supportability.html)、[AWS Service Terms](https://aws.amazon.com/service-terms/) です。5 行目はサービス条件の文面の読み方であり、法的な判断ではありません。Capacity Manager を通じて得た Spot のスコアは、Spot であっても開示の制限の対象に含まれると読めます。SPS の API を直接呼んだ結果を共有する場合は、ご自身でサービス条件を確認してください。

ここで、よく出る疑問に触れておきます。Spot のスコアが高ければ On-Demand も取りやすいのか、という疑問です。筆者が読んだ範囲では、SPS のページはすべて Spot のリクエストについて説明していて、On-Demand との関係は書かれていません。Capacity Manager のページも On-Demand と Spot を別の市場として扱っています。一方のスコアから他方を推測できる、という記述は見つけられませんでした。On-Demand を使うなら、On-Demand の市場で調べてください。また、Check supportability の Spot に、SPS の最小のタイプ数や目標の容量の上限が及ぶかどうかも、公式に書かれていません。

## SPS を自動で追跡するガイダンス実装

SPS が返すのは取得した時点のスコアだけなので、時間の変化を見たい場合は自分で記録する必要があります。それを代わりにやってくれるのが、AWS Solutions Library の [Guidance for EC2 Spot Placement Score Tracker](https://github.com/aws-solutions-library-samples/guidance-for-ec2-spot-placement-score-tracker) です。AWS が公開する、自分のアカウントに構築して使う参考実装です。リポジトリの README とコードに基づくと、次のような構成です。

| # | 項目 | 内容 |
|---|---|---|
| 1 | 構成 | AWS CDK の Python で、Lambda、EventBridge のスケジュール、CloudWatch ダッシュボード、IAM ロールを作ります。設定ファイルとコードは、`cdk bootstrap` で用意される S3 バケットに置かれます |
| 2 | スコアの取得 | `ec2:GetSpotPlacementScores` を使います。Spot だけが対象で、On-Demand は見ません |
| 3 | 入力 | インスタンスタイプかインスタンス属性、Region のリスト、目標の容量、AZ 単位か Region 単位かを指定します。Karpenter の NodePool の YAML から要件を読む方法もあります |
| 4 | 出力 | スコアと Spot 価格を CloudWatch のカスタムメトリクスにして、ダッシュボードに時系列で表示します |
| 5 | 費用 | README は、2026 年 2 月時点の us-east-1 の既定の設定で、月額約 25.37 ドルと見積もっています。大半は CloudWatch のカスタムメトリクスの費用です |
| 6 | ライセンス | MIT-0 です |
| 7 | 導入に必要なもの | CDK、Python 3.8 以上、virtualenv、boto3、PyYAML、Docker、CDK のスタックを実行できる IAM 権限、SPS と EC2 の API を呼べる権限です |
| 8 | 実行間隔 | README の中で 5 分と 15 分の記述が混在しています |

![つながりの図。Check supportability の Spot は Spot placement score（SPS）を土台にしていて、これを点線で示す。トラッカーは Lambda から SPS を呼び、結果を CloudWatch のメトリクスに書き、メトリクスは CloudWatch のダッシュボードに表示される。これらは実線で示す。下に、ダッシュボードは CDK で作り、トラッカーが扱うのは Spot だけ、とある。](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/c8fba7927e164d/zenn/articles/c8fba7927e164d/07-sps-connections.png)
*図 7: 点線は土台にする関係、実線は呼ぶ、書く、表示する関係です*

使いどころは、Spot で GPU を回したい場合に、指定したインスタンスタイプの組と容量の構成について、Region や AZ ごとのスコアの推移を見ることです。SPS が採点するのは構成全体であり、構成の中の個々のインスタンスタイプではありません。取りやすい構成を、Karpenter の NodePool などで起動を許すインスタンスタイプの一覧に入れ、実際の起動は Karpenter や EC2 Fleet の配分戦略に任せる、という運用が考えられます。配分戦略は、フリートがどの Spot プールから起動するかを決める設定です。公式は、スコアが意味を持つのは同じ構成で `capacity-optimized` を使う場合だとしています。一方、[Karpenter の Disruption のページ](https://karpenter.sh/docs/concepts/disruption/)は、Spot から Spot への置き換えで、より安い Spot のインスタンスタイプを `price-capacity-optimized` で選ぶと書いています。配分戦略が `capacity-optimized` と異なる場合に、スコアと起動結果が対応するかは公式に書かれていないので、スコアは傾向の参考にとどまる、というのが筆者の解釈です。`price-capacity-optimized` は [AWS Compute Blog の紹介](https://aws.amazon.com/blogs/compute/introducing-price-capacity-optimized-allocation-strategy-for-ec2-spot-instances/)で説明されています。

注意点も書かれています。README は、SPS では新しい構成を多数投げると制限され、設定が多すぎると Lambda の実行が失敗しうると説明しています。目標の容量にも上限があります。[Spot placement score](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/spot-placement-score.html) のドキュメントによると、上限は直近の Spot の利用量に今後の増加を見込んで決まり、利用実績がなければ Spot のリクエスト上限に合わせた低い既定値になります。同じページは、意図された使い方と異なるパターンを検知すると、24 時間あたりの新しい構成の数を制限することがあると書いています。

## AWS CLI だけで使うときに困ること

Check supportability は AWS CLI の 1 コマンドで呼べ、AWS CLI の `--query` と `--output text` を使えば、応答から必要な値を取り出すこともできます。それでも、何度も問い合わせて結果を判断に使おうとすると、自分で書くことになる処理があります。筆者はそれを肩代わりするコマンド `ec2-supportability` を書きました。ここでは、AWS CLI だけで使うときに自分で書くことになる処理と、このコマンドが代わりに行うことを並べ、そのあとで使い方を 3 つの場面で説明します。コードは [distributed-ai の investigations](https://github.com/littlemex/distributed-ai/tree/34b75216bd6ba60b22a21dd89480a64d2dd2d2fe/investigations/2026-11-05-ec2-capacity-supportability-report) にあり、リンクはコミットを固定しています。

| # | AWS CLI だけで使うと | ec2-supportability では |
|---|---|---|
| 1 | 頼んだ組み合わせが応答から欠けることがあります（[試して分かった挙動](#試して分かった挙動と公式の記述)の 6 行目）。欠けた組み合わせには行が無いので、頼んだ一覧と自分で突き合わせないと、欠けたことに気づきません | `--types` で指定したときは、頼んだ組み合わせすべてに行を作ります。スコアの無い行には、存在しない AZ、送っていない、提供されていない、失敗した、応答に無かった、のどれかを理由として付けます |
| 2 | 存在しないタイプや AZ ID が 1 つ混ざると、問い合わせ全体が失敗します。失敗した問い合わせが 1 時間 100 回の枠に数えられるかは、公式に書かれていません | 送る前に、EC2 の `DescribeAvailabilityZones` と `DescribeInstanceTypeOfferings` で確かめて外します。この確認は Capacity Manager の問い合わせではなく、その権限が無いときは確認を飛ばして送ります。API が値を名指しで拒否したときは、その値を外して送り直します。送り直しは 1 回の問い合わせにつき 3 回まで、`--max-calls` の残りの範囲だけです |
| 3 | 1 回の問い合わせには AZ 10 個、タイプ 50 個、組み合わせ 100 組の上限があり、超える分は自分で分けて送ります | タイプを名前で指定したときは、上限に収まるように自動で分けます。実行前に Capacity Manager への問い合わせの回数を数え、`--max-calls`（既定は 95）を超える計画なら問い合わせを 1 回も送らずに止まります。同じ時間帯にすでに使った回数と、SDK が自動で行う再試行は数えません |
| 4 | 分けて送ると、集約スコアも問い合わせごとに分かれます。まとめ方は公式に書かれていません | 集約スコアは問い合わせごとにだけ出し、1 つにまとめた値を作りません |
| 5 | 市場（On-Demand と Spot）や量を変えて調べるには、組み合わせの数だけコマンドを書きます | `--markets` と `--amounts` に並べた組み合わせを 1 回の実行で調べます。問い合わせはその組ごとに 1 回ずつ送るので、使う枠は減りません |
| 6 | `--query` は API の応答に当てるので、欠けた組み合わせは結果に現れません。シェルの変数にするには、値の引用を自分で書きます | 結果を表、JSON、タブ区切りの行、シェルの変数（`export` の行）のどれかで出します。`--query` の書き方は AWS CLI と同じ JMESPath ですが、当てる先は API の応答ではなく、行と理由を補ったこのツールのデータです。変数の値はシェル用に引用し、`PATH` のような危険な名前になるときは出さずに止まります |
| 7 | 1 回の呼び出しが失敗すれば終了コードで分かりますが、市場や量を変えて何回も呼ぶと、全体が完了したかは自分でまとめます | Capacity Manager が使えて、送る前に外した値が無く、すべての問い合わせでスコアが取れたときだけ終了コード 0、そうでなければ 3 を返します。成功した応答から組み合わせが欠けただけのときは 0 のままなので、それは行の理由で見ます |
| 8 | 応答をファイルに保存しておけば、読み直しに問い合わせは要りませんが、表や変数に直す処理は自分で書きます | `--save-json` で保存したデータから、`--from-json` で問い合わせずに、どの形でも同じ結果を出し直せます。完了しなかった実行は、保存先の正常なファイルを置き換えず、書き込めた場合は別名で保存します |
| 9 | `enable-capacity-manager` は、使っている認証情報のアカウントで実行されます。アカウントを確かめるなら、STS の呼び出しを自分で前に置きます | `--enable` は `--expect-account` と一緒のときだけ動き、呼び出し元がそのアカウントでなければ何も変えずに止まります |

AWS CLI でできないことは、ほとんどありません。差は、1 から 4 のような、自分で書くと間違えやすい処理を毎回書かずに済むことにあります。表や JSON の見た目は、使いやすさのための部分です。

### インストール

使うための条件は、[前提と制約](#前提と制約)のとおりです。AWS Support の Unified Operations プラン、1 つの Region での Capacity Manager の有効化、それに権限が要ります。権限は、送る前の確認に `ec2:DescribeAvailabilityZones` と `ec2:DescribeInstanceTypeOfferings`、状態の確認に `ec2:GetCapacityManagerAttributes`、呼び出し元の確認に `sts:GetCallerIdentity`、`--enable` を使うときは `ec2:EnableCapacityManager` を使います。スコアの取得に要る IAM アクションは、2026-11-05 時点で公開されていません。

インストールには Python 3.10 以降が要ります。リポジトリから、記事と同じコミットを指定して入れられます。PyPI には公開していません。

```bash
python3 -m pip install "ec2-supportability @ https://github.com/littlemex/distributed-ai/archive/34b75216bd6ba60b22a21dd89480a64d2dd2d2fe.zip#subdirectory=investigations/2026-11-05-ec2-capacity-supportability-report"
ec2-supportability --version
```

認証情報は、環境変数、プロファイル、インスタンスやコンテナのロールといった、AWS の通常の方法で渡します。Region は `AWS_REGION` からは読まず、`--region` か `EC2_SUPPORTABILITY_REGION` で渡します。Capacity Manager を有効にできるのは 1 アカウントにつき 1 Region だけなので、シェルにたまたま設定されていた Region で決めないためです。以下の例の `CM_REGION` は、Capacity Manager を有効にした Region です。出力例の値は公式ドキュメントの応答例のもので、表の見出しの時刻も例です。

### 場面 1: 台数を増やす前に、バッチの中で確かめる

学習ジョブの前に 50 台の On-Demand を起動するバッチで、集約スコアが High のときだけ進め、そうでなければ候補を足すか待つ、という分岐を作ります。`--output env` は結果をシェルの変数の形で出すので、`eval` でそのまま読み込めます。次の内容を `check.sh` として保存し、`bash check.sh` で実行します。

```bash
set -euo pipefail
export CM_REGION="ap-northeast-1"
if ! out="$(ec2-supportability --region "$CM_REGION" --markets on-demand --amounts 50 --azs use1-az1 --types c6g.xlarge c7g.xlarge m6g.xlarge --output env)"; then
  echo "the supportability check did not complete" >&2
  exit 1
fi
eval "$out"
if [ "$CS_AGGREGATE_ON_DEMAND_50" = high ]; then
  echo "proceed"
else
  echo "add instance types or wait"
fi
```

コマンドを `if` の条件に入れているのは、終了コードを見落とさないためです。`export X="$(...)"` と書くと、中のコマンドが失敗しても `export` の成功で上書きされます。AZ ID を 1 つ打ち間違えただけでも、その AZ は送られず、実行は完了しなかった扱い（終了コード 3）になるので、このバッチは止まります。読み込まれる変数は次のような形です。

```text
export CS_RESULT=complete
export CS_REGION=ap-northeast-1
export CS_UNIT=instances
export CS_AGGREGATE_ON_DEMAND_50=high
export CS_HIGH_ON_DEMAND_50='c6g.xlarge:use1-az1 c7g.xlarge:use1-az1'
export CS_MEDIUM_ON_DEMAND_50=m6g.xlarge:use1-az1
export CS_LOW_ON_DEMAND_50=''
```

問い合わせが上限で分かれたときは、`CS_AGGREGATE_ON_DEMAND_50` を空にして、問い合わせごとの値を `CS_AGGREGATE_ON_DEMAND_50_1` のような別の名前で出します。分けた一部を全体の値として読まないためで、このバッチは分かれたときに `else` の側へ進みます。公式は、起動のたびではなく、計画や見直しのときに呼ぶことを勧めています。1 回の実行で送る問い合わせの数と間隔によっては、1 時間 100 回の枠を圧迫するので、短い間隔で回し続ける使い方は向きません。

同じことはコンテナでもできます。次の Dockerfile でイメージを作り、認証情報と `EC2_SUPPORTABILITY_REGION` を環境変数で渡して実行します。ECS や EKS の上では、タスクや Pod のロールが認証情報を渡すので、`-e AWS_...` は要りません。

```dockerfile
FROM python:3.12-slim
RUN python3 -m pip install --no-cache-dir "ec2-supportability @ https://github.com/littlemex/distributed-ai/archive/34b75216bd6ba60b22a21dd89480a64d2dd2d2fe.zip#subdirectory=investigations/2026-11-05-ec2-capacity-supportability-report"
USER nobody
ENTRYPOINT ["ec2-supportability"]
```

```bash
docker build -t ec2-supportability .
docker run --rm -e AWS_ACCESS_KEY_ID -e AWS_SECRET_ACCESS_KEY -e AWS_SESSION_TOKEN -e EC2_SUPPORTABILITY_REGION="ap-northeast-1" ec2-supportability --markets on-demand --amounts 50 --azs use1-az1 --types c6g.xlarge c7g.xlarge m6g.xlarge --output json
```

### 場面 2: Karpenter や Auto Scaling の候補のタイプを見直す

ノードの候補に入れるインスタンスタイプを見直す場面です。候補のタイプと AZ を並べ、High になった組み合わせだけをタブ区切りで取り出します。Check supportability は 1 回の問い合わせに複数の Region の AZ を混ぜられるので、`--azs apne1-az1 use1-az1 usw2-az1` のように Region をまたいで並べても構いません。下の例は、出力の形を公式の応答例の値で示すために AZ を 1 つにしています。

```bash
export CM_REGION="ap-northeast-1"
ec2-supportability --region "$CM_REGION" --markets on-demand --amounts 50 --azs use1-az1 --types c6g.xlarge c7g.xlarge m6g.xlarge --output text --query "scores[?score=='high'].[instance_type,az_id]"
```

```text
c6g.xlarge	use1-az1
c7g.xlarge	use1-az1
```

1 行に 1 組で、見出しの行は無いので、`cut` や `awk` でそのまま候補の一覧にできます。`--query` の式は、このツールのデータの `scores` の一覧に当てます。「Low ではないもの」を取りたいときは `score!='low'` ではなく `score=='high' || score=='medium'` と書きます。スコアの無い組み合わせは `score` が `null` で、JMESPath では `null != 'low'` が真になるので、前者ではスコアの無い組み合わせまで入ってしまいます。

AZ が 10 個以内、タイプが 50 個以内、組み合わせが 100 組以内なら、市場と量の組ごとに 1 回の問い合わせで済み、集約スコアもその全部をまとめた値になります。どれかを超えると問い合わせが分かれ、集約スコアも分かれます。複数の Region をまたいで 1 つの集約スコアがほしいときは、候補をその範囲に絞ります。

### 場面 3: 容量不足で起動が失敗したあとに切り分ける

起動が容量不足で失敗したときは、[スコアの使い分け](#スコアの使い分け)の 3 行目のとおり、同じ市場、単位、タイプ、AZ、量で確かめ直します。ここでは m6g.xlarge の起動が失敗したとして、同じ AZ と量で、失敗したタイプと代わりの候補を一緒に確かめます。何も付けずに実行すると、人が読むための表が出ます。

```bash
export CM_REGION="ap-northeast-1"
ec2-supportability --region "$CM_REGION" --markets on-demand --amounts 50 --azs use1-az1 --types c6g.xlarge c7g.xlarge m6g.xlarge
```

```text
Check supportability  ap-northeast-1  2026-11-06 18:00 JST  result: complete

On-Demand, 50 instances   aggregate: High
  INSTANCE TYPE  use1-az1
  c6g.xlarge     High
  c7g.xlarge     High
  m6g.xlarge     Medium
```

失敗した組み合わせが High のとき、公式は、その組み合わせにキャパシティはあるがホストのサイズ変更が必要な状態だと説明し、起動できる分を起動して残りを数分おきに再試行するよう勧めています。Medium か Low なら、High だった別の組み合わせを使うか、タイプを増やします。この例では m6g.xlarge が Medium なので、High の c6g.xlarge か c7g.xlarge に切り替える候補になります。どのスコアも、起動の成功は保証しません。あとで見直したいときは `--html report.html` を付けると、英語と日本語を切り替えられる HTML のレポートも書きます。そのレポートも結果そのものなので、自社の中だけで扱ってください。

### 使うときの注意

結果は第三者に開示できないデータです。画面に出した結果も同じで、CI のログ、チャット、共有のダッシュボードは読める人が広がりやすい場所です。リポジトリには実行結果を含めていません。

引数の多くは `EC2_SUPPORTABILITY_REGION` のような環境変数でも渡せますが、次のものは環境変数からは受け付けません。`--enable`（アカウントの設定を変える）と `--overwrite`（ファイルを置き換える）は、コンテナの設定に一度書くとその後の全部の実行に引き継がれてしまうためです。`--query` と `--env-prefix` は、`eval` するスクリプトが受け取るものを決めるためです。`--html`、`--save-json`、`--from-json`、`--open` は、1 回の実行のファイルと動作を決めるためです。オプションの一覧、終了コード、データの形は [README](https://github.com/littlemex/distributed-ai/blob/34b75216bd6ba60b22a21dd89480a64d2dd2d2fe/investigations/2026-11-05-ec2-capacity-supportability-report/README.md) にまとめています。

## まとめ

Check supportability は、起動の前に、インスタンスタイプと AZ の組み合わせごとの空き具合を、要求量に対する相対値として High、Medium、Low で返す API です。使えるのは Unified Operations プランのお客様で、Capacity Manager を有効にした Region から呼び、結果は原則として第三者に開示できません。どのスコアも起動を保証せず、重要なワークロードには、スコアに関係なく Capacity Reservation か将来日付の Capacity Reservation を使うのが公式の勧めです。

ミックスフリートでは集約スコア、1 つのタイプしか使えない場合は組み合わせごとのスコア、容量不足で起動が失敗した後は同じ条件での確かめ直し、と読み方を使い分けます。ただし、組み合わせごとのスコアの Spot での読み方は、公式に書かれていません。Spot は SPS が土台で、すでに SPS を直接使っている場合は、集約スコアを Spot の信号として読むよう公式は書いています。

SPS には、スコアを時系列で追う AWS Solutions Library のガイダンス実装があります。一方、Check supportability 向けの公式のサンプルアプリやガイダンス実装は、2026-11-05 時点では見つけられませんでした。AWS CLI だけで使うと、応答から欠けた組み合わせを Low と取り違えたり、打ち間違い 1 つで問い合わせの枠を使ったりしやすいので、筆者はそれを肩代わりする `ec2-supportability` を書き、バッチ、候補の見直し、容量不足の切り分けの場面に組み込める形にしました。公式が勧めているのは、起動のたびではなく、計画や見直しのときの実行です。この API には、アカウントあたり 1 時間 100 クエリの上限があり、結果の共有にも制限があります。スコアの根拠は、いつでも冒頭の [Check supportability](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-manager-supportability.html) のページに戻って確認してください。
