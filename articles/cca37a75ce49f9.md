## はじめに

NCCL のリリース一覧には、NCCL4Py の版と、NCCL EP の最初の版が並んでいます。名前が似ているので、どれが何なのかが分かりにくいと思います。この記事では、3 つがそれぞれ何を受け持ち、どうつながっているかを図で見ていきます。コードには踏み込みません。

## 登場する部品

![サーバーと Linux の上に NCCL 本体が載り、その上に NCCL4Py と NCCL EP が載る](/images/cca37a75ce49f9-stack.png)

1 台の GPU サーバーの上には、次の部品が載っています。NCCL4Py と NCCL EP は、どちらも NCCL 本体のすぐ上に並びます。

| 部品 | 中身 | 入れ方 |
|---|---|---|
| NCCL 本体 | GPU どうしの通信を受け持つライブラリ | nccl4py などに CUDA 12 か 13 を指定して入れる |
| NCCL4Py | NCCL 本体を Python から呼ぶ窓口 | nccl4py を入れる |
| NCCL EP | MoE の通信を受け持つライブラリ | nccl-extensions を入れる |
| NCCL EP の Python の窓口 | NCCL EP を Python から呼ぶ窓口 | nccl-extensions を入れる |

NCCL 本体と NCCL4Py は、NVIDIA の NCCL のリポジトリで作られています。NCCL EP とその Python の窓口は、別のリポジトリで作られています。名前は nccl-extensions です。

## NCCL: GPU どうしの通信を受け持つ

![4 枚の GPU が値を出し合い、全員が合計の 10 を受け取る](/images/cca37a75ce49f9-allreduce.png)

たくさんの GPU で 1 つのモデルを学習するとき、GPU どうしで計算の結果を足し合わせます。NCCL は、この GPU 間のやり取りを速く行うためのライブラリです。図の all-reduce は代表的な操作で、参加した GPU の値をまとめ、同じ結果を全員に渡します。

PyTorch で分散学習をするとき、通信の方式に NCCL を選べます。そうすると、PyTorch の中で NCCL が動きます。そのため、NCCL を直接呼ばなくても使えます。

## MoE: トークンを担当の GPU へ送る

![4 つの GPU が、トークンを担当のエキスパートの GPU へ送り、計算し、元の GPU へ戻す](/images/cca37a75ce49f9-alltoall.gif)

MoE は、モデルの中にエキスパートと呼ぶ計算の部品をたくさん持つ形のモデルです。文章はトークンという単位に区切られ、トークンごとに使うエキスパートが選ばれます。エキスパートを複数の GPU に分けて置くこともできます。そのときは、トークンを担当の GPU へ送り、結果を元の GPU へ戻します。

送る処理を dispatch、戻す処理を combine と呼びます。図では、各トークンが 1 つのエキスパートだけを使う場合を描いています。MoE の通信を支える層は「[MoE の all-to-all を支える層](https://zenn.dev/tosshi/articles/a0f5ff21eed405)」で説明しています。

## NCCL EP: 送る所と戻す所を受け持つ

![NCCL EP が受け持つのは dispatch と combine で、エキスパートの計算はモデルのプログラムが受け持つ](/images/cca37a75ce49f9-ep-role.png)

NCCL EP の EP は、エキスパート並列 (Expert Parallelism) の略です。NCCL EP は、dispatch と combine の 2 つの操作を受け持つライブラリです。エキスパートの計算そのものは、NCCL EP ではなくモデルのプログラムが受け持ちます。

NCCL EP は、NCCL 本体の機能の上に作られています。その機能の 1 つが、GPU の計算の途中から、ほかの GPU との通信を直接始める仕組みです。

## NCCL EP の 2 つのモード

![Low-Latency モードは少ないトークンを直接送り、High-Throughput モードはたくさんのトークンをノードの中でまとめてから送る](/images/cca37a75ce49f9-modes.png)

NCCL EP には、Low-Latency と High-Throughput の 2 つのモードがあります。[NCCL EP の README](https://github.com/NVIDIA/nccl-extensions/blob/nccl-extensions-v0.1.0/nccl_ep/README.md) では、Low-Latency は待ち時間が大事な推論向けとされています。こちらは、流すトークンが少ないときに使います。High-Throughput は、学習と、推論で最初に入力をまとめて読む段階向けです。2 つは、向くトークンの量だけでなく、送り方も違います。High-Throughput は、ノードの中で一度まとめてから、ほかのノードへ送ります。

## NCCL4Py: Python から NCCL を呼ぶ窓口

![NCCL4Py は Python のプログラムから呼ばれ、NCCL 本体を呼ぶ](/images/cca37a75ce49f9-window.png)

NCCL 本体には、C 言語から呼ぶための入口があります。NCCL4Py は、その NCCL 本体を Python から呼べるようにした公式の窓口です。NCCL 2.29.2 で試験的に入り、その後は本体とは別の番号で版を重ねています。

最近の NCCL4Py の版は、それぞれ特定の版の NCCL 本体に合わせて作られています。たとえば NCCL4Py v0.6.0 は、NCCL 2.32.3 に合わせて作られています。

## nccl という名前を 2 つの配布物で分け合う

![Python の nccl という名前の下に、nccl4py と nccl-extensions がそれぞれ中身を置く](/images/cca37a75ce49f9-namespace.png)

Python では、どちらも nccl という名前で読み込みます。その下に、読み込むときの名前を 2 つの配布物が置きます。nccl4py は nccl.core を、nccl-extensions は nccl.ep を置きます。1 つの名前を複数の配布物で分け合う、Python の仕組みを使っています。

nccl-extensions は nccl4py に依存しています。そのため、入れると nccl4py も一緒に入ります。nccl.m2n は、同じ nccl-extensions に入っている NCCL M2N の窓口です。NCCL M2N は、2 つの GPU の群の間でデータを配り直す、試験的なライブラリです。学習側の GPU から推論側の GPU へ重みを送る用途があります。

## 版の組み合わせに気をつける

![CUDA 12 か 13 を指定すると nccl-extensions は NCCL 2.30.7 に固定し、一緒に選ばれる NCCL4Py v0.6.0 は NCCL 2.32.3 を基に作られている](/images/cca37a75ce49f9-versions.png)

nccl-extensions v0.1.0 が対応する NCCL 本体は、2.30.7 だけです。**CUDA 12 か 13 を指定して入れると、NCCL 本体は 2.30.7 に固定されます。** 一方、nccl-extensions は NCCL4Py の版を指定していません。新しい環境に入れると、最新の NCCL4Py が選ばれます。2026 年 10 月 1 日時点では v0.6.0 です。

NCCL4Py v0.6.0 は、NCCL 2.32.3 を基に作られています。NCCL 2.31 以降に向けて足された機能は、2.30.7 の本体では使えないと考えられます。GPU の側で動く試験的な機能は、作ったときと同じ版の NCCL を求めます。その一致は、自動では確かめられません。そうした機能を試す環境と、NCCL EP を使う環境は、分けておくのが安全です。

NCCL EP には、動くときに GPU のプログラムをその場で組み立てる処理があります。そのため、CUDA の開発道具も必要です。開発道具も、CUDA 12 か 13 かを指定した版にそろえます。配布されている NCCL4Py を入れるだけなら、この開発道具は要りません。

## NCCL4Py v0.3.1 のころといま

![v0.3.1 では nccl4py の中に nccl.ep があり、いまは nccl-extensions の中にある](/images/cca37a75ce49f9-then-now.png)

[NCCL4Py v0.3.1](https://github.com/NVIDIA/nccl/releases/tag/nccl4py-v0.3.1) には、nccl.ep と、NCCL EP のライブラリそのものが同梱されていました。ただし同梱の NCCL EP は CUDA 13 向けで、CUDA 12 の環境では自分で用意する必要がありました。

![2026 年 4 月公開の NCCL 2.30.3 に収録され、9 月に nccl-extensions から配られた](/images/cca37a75ce49f9-timeline.png)

[NCCL4Py v0.4.1](https://github.com/NVIDIA/nccl/releases/tag/nccl4py-v0.4.1) で、nccl.ep は NCCL4Py から外れました。いまは [nccl-extensions v0.1.0](https://github.com/NVIDIA/nccl-extensions/releases/tag/nccl-extensions-v0.1.0) が、NCCL EP v0.2 を配っています。nccl.ep も、こちらに入っています。v0.3.1 で nccl.ep を使っていたプログラムがあるとします。新しい NCCL4Py で動かすには、nccl-extensions も入れます。nccl.ep の使い方は変わりうると、当時から書かれていました。そのため、書き直しが要ることもあります。

v0.3.1 は、自分の中に nccl.ep を持っています。nccl-extensions は NCCL4Py の版を指定しないので、足しても v0.3.1 は残ります。すると、2 つの nccl.ep が同じ置き場所でぶつかります。v0.3.1 の環境に足すより、新しい環境を作って入れるのが確実です。

## やりたいことから選ぶ

![PyTorch の標準の学習なら PyTorch の分散機能、Python から直接なら NCCL4Py、MoE なら NCCL EP、C なら NCCL 本体](/images/cca37a75ce49f9-choose.png)

3 つは、どれか 1 つだけを選ぶ関係ではありません。自分がどの処理を直接書きたいかで、意識する相手が決まります。PyTorch で標準の分散学習をするだけなら、どれも直接は触りません。

## 各部品の受け持ち

| 部品 | 受け持ち | 使う人 |
|---|---|---|
| NCCL 本体 | GPU どうしの通信 | PyTorch などのフレームワーク、C と CUDA で書く人 |
| NCCL4Py | Python から NCCL 本体を呼ぶ | Python から NCCL を直接使う人 |
| NCCL EP | MoE の dispatch と combine | MoE の通信を組み込む人 |
| NCCL EP の Python の窓口 | Python から NCCL EP を呼ぶ。nccl-extensions が配る | Python から NCCL EP を使う人 |

## まとめ

NCCL4Py と NCCL EP は、どちらも NCCL 本体の上に載ります。Python から NCCL EP を使うときは、nccl-extensions を入れます。
