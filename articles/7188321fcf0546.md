## 推論とサービング

### SGLang-Neuron: Trainium で SGLang を動かすプラグイン

> 参照元: [Deploy frontier AI models on AWS Trainium with SGLang-Neuron](https://aws.amazon.com/blogs/machine-learning/deploy-frontier-ai-models-on-aws-trainium-with-sglang-neuron/)、[SGLang-Neuron v0.1.0: SGLang's Serving Stack on AWS Trainium](https://www.lmsys.org/blog/2026-11-12-sglang-neuron-v0.1.0/)

SGLang は、プロンプトの先頭が同じリクエストどうしで KV キャッシュを使い回す prefix cache を、RadixAttention という木の形の仕組みで持つ、オープンソースの LLM の推論エンジンです。Trainium は AWS が作った機械学習向けのチップで、その上でモデルを動かすための道具一式を Neuron SDK と呼びます。この AWS と LMSYS のブログは、RadixArk と Amazon の Annapurna Labs のチームが、SGLang の本体を書き換えずに外から差し込むプラグインとして SGLang-Neuron を公開したことを伝えるもので、AWS の記事は使い方の案内、LMSYS の記事は設計と測定の詳しい説明です。LMSYS の記事はこれを v0.1.0 と呼び、作り手に Yotta Labs も挙げています。プラグインは、Trainium を PyTorch の装置として見せる TorchNeuron の上で、ふつうの PyTorch の演算と、Neuron 向けのカーネルを書く言語の NKI で書いたカーネルを torch.compile でまとめて動かします。

:::message
**コメント**: SGLang の本体はそのままで、API サーバー、スケジューラ、radix cache、PD 分離の取り決めは SGLang の側に残し、モデルの実装、attention や MoE の NKI のカーネル、グラフの実行、KV の置き場といった Trainium に固有の部分をプラグインが持つ、という vLLM Neuron Plugin と同じ形で SGLang も使えるようになったのは待望のリリースですね。Miles など SGLang 向けの強化学習ライブラリの利用も、今後検証してみたいです。
:::

#### 参照元からの抜粋と要約

- **課題**: GPU で SGLang を使っている人が、同じ使い方のまま Trainium で推論とロールアウトの生成をしたい、という場面に向けた公開の告知です。LMSYS の記事は、10 月の closed beta で持ち込めることは示せたので、次はそれを速くすることが課題だとしています。
- **ねらい**: SGLang の使い方を変えずに Trainium を使えるようにし、Trainium への対応と SGLang の本体の開発を切り離すこと。
- **やったこと**: 記事では、SGLang-Neuron を本体の外のプラグインとして作り、`SGLANG_PLATFORM=neuron` で選べるようにしたと説明しています。PyTorch の演算と NKI のカーネルを torch.compile でまとめて動かし、PD 分離では KV キャッシュを NIXL で EFA を通して送ります。
- **結果**: 記事によると、Trainium3 の 3 台で動かした Kimi-K3 は 1 人あたり毎秒 67 トークンに届き、gpt-oss-120b では HiCache を有効にすると出力のスループットが 72〜75% 多くなりました。GPU や他の道具との比較はなく、[リポジトリ](https://github.com/sgl-project/sglang-neuron)では public preview とされています。

### Muse Spark Open の megakernel: 1 層を 1 回の起動にまとめる融合カーネル

> 参照元: [Muse Spark Open Ultrafast: Pushing beyond 1,000 Tokens per second](https://www.lmsys.org/blog/2026-11-05-muse-spark-open-ultrafast/)

Muse Spark Open は Meta が重みを公開した、全体で 816B、1 トークンあたりに使う重みが約 42B の MoE のモデルで、トークンごとに 256 の専門家のうち 8 つを選びます。SGLang はこのモデルのデコードの 1 ステップで約 1,450 個のカーネルを順に起動していて、カーネルの切れ目ごとに GPU の SM やその中のワープが手を止めるので、メモリの帯域を使い切れていませんでした。そこで、多くの演算を 1 つの常駐するカーネルにまとめ、ワープごとに役割を決めて、前の演算が終わる前から次の演算の準備を始めさせるのが megakernel です。この LMSYS のブログは、著者が SGLang のチームの立場から、Muse Spark Open の 1 層分の attention と MoE を 1 回の起動で動かす megakernel を CUDA C++ と PTX で書き、1 人のリクエストのデコードを速くした話をまとめたものです。抜粋に出てくる GB300 は NVIDIA の Blackwell の世代の GPU で、TP8 は 8 枚の GPU で重みを分けて持つテンソル並列です。投機的デコードは、小さな下書きのモデルが先に数トークンを提案し、本体のモデルがまとめて正しいか確かめることでデコードを速くする方法で、DFlash V2 はその下書きのモデルです。

:::message
**コメント**: 同じテーマの SubGPU Pipelining や、カーネルと開発の道具のテーマの GC-MoE と同じく、カーネルの切れ目の無駄をなくすために 1 つの GPU の中で役割を分けて重ねる話で、今週は同じ方向の話が 3 本そろいました。1,450 個のカーネルを 97 個にまとめて 1 ステップを 12.9 ミリ秒から 5.9 ミリ秒にした、という結果に加えて、1 つの SM の命令のキャッシュが約 128 KB しかなく 215〜314 KB の megakernel が収まらない、といった、まとめたことで初めて出てくる壁を測っているのが面白いです。ただ、いまはバッチ 1 で投機的デコードを使う場合だけに対応していて、1 人のリクエストのようなレイテンシーの厳しい設定では演算ごとに重みをどこに置くかを試して最も速い版を選んでいると書かれているので、たくさんの利用者を同時にさばく構成でどこまで効くかはまだ分かりません。重みのライセンスの条件は記事に書かれていないので、使う前に [モデルカード](https://huggingface.co/meta-models/Muse-Spark-Open-816B-A42B)で確かめたいです。コードは公開されているので、まずは命令のキャッシュの溢れが他のモデルの megakernel でも起きるかを見てみたいです。
:::

*出典: [Muse Spark Open Ultrafast](https://www.lmsys.org/blog/2026-11-05-muse-spark-open-ultrafast/) の図*

#### 参照元からの抜粋と要約

- **課題**: SGLang は Muse Spark Open のデコードの 1 ステップで約 1,450 個のカーネルを起動しており、カーネルの切れ目で SM やワープが止まり、メモリの帯域を使い切れていません。
- **ねらい**: 1 層分の attention と MoE を 1 つの megakernel にまとめ、メモリの読み出しと他の演算を細かく重ねて、GPU を休ませずに動かすこと。
- **やったこと**: 記事では、ある層の attention から次の層の qkv の射影と KV の書き込みまでを 1 回の起動で受け持つ megakernel を、本体のモデルの分だけで約 8,000 行の CUDA C++ と PTX で書いたと説明しています。GB300 の 144 個の SM それぞれに 12 のワープを置き、KV の読み込み、重みの読み込み、テンソルコアの演算、送受信などの役割をワープごとに固定しました。MoE の 2 つの行列の掛け算を両方とも N の方向で分けて持ち、1 つ目の後に FP4 の all-gather、2 つ目の後に BF16 の all-gather を置くテンソル並列に変えました。重みの先読み、命令のキャッシュの溢れへの対策、データそのものを合図に使ってメモリのフェンスを避ける同期、下書きのモデルの megakernel 化も行いました。
- **結果**: 記事によると、GB300 8 枚の TP8 で、GSM8K の 1 リクエストを投機的デコードありで流し、20 ステップの中央値をとると、デコードのスループットはこれまでの SGLang の 毎秒 517 トークンから毎秒 1,109 トークン になり、2.1 倍になりました。1 ステップの時間は 12.9 ミリ秒から 5.9 ミリ秒に、カーネルの数は 1,450 個から 97 個に減りました。下書きのモデルの 1 ステップは 1.16 ミリ秒から 0.44 ミリ秒になりました。1 ステップで 16 トークンを確かめ、平均 6.6 トークンが採用されました。GB300 の 1 つの SM の命令のキャッシュは約 128 KB で、215〜314 KB の megakernel は収まらず、100 KB のコードを単独で回すと 1 回 12.4 マイクロ秒のところ、別の 100 KB と続けて回すと 19.5 マイクロ秒かかりました。いまの megakernel はバッチ 1 で投機的デコードを使う場合だけに対応していて、この設定では 1 つのやり方がどこでも効くわけではないので、演算ごとに重みを共有メモリと L2 のどこに置くかなどを試して最も速い版を選んでいます。コードは [facebookresearch/sgl-muse-mega](https://github.com/facebookresearch/sgl-muse-mega) で公開されています。

### SGLang の unified memory: KV と状態をまとめた共有の置き場

> 参照元: [Unified Memory in SGLang: One Arena for Every Token Lifetime](https://www.lmsys.org/blog/2026-11-11-unified-memory/)

最近のモデルには、全部の文脈を見る attention の層と、直近の一定の長さだけを見るスライディングウィンドウの attention の層や、Mamba や線形の attention のように固定の大きさの状態を持ち回る層を混ぜたハイブリッドなものが増えています。前者の KV キャッシュは文脈が長くなるほど伸び続けますが、後者のウィンドウの KV や状態は 1 リクエストあたりの大きさに上限があり、2 つは同じようには伸び縮みしません。SGLang はこれまで、それぞれに別の置き場を用意し、その割合を起動時の設定で決め打ちしていたので、長い文脈が多いと一方が足りなくなり、短いリクエストが多いと他方が足りなくなり、空いているメモリがあっても別の置き場からは使えませんでした。この LMSYS のブログは、著者らがこれらを GPU のメモリの 1 つの置き場にまとめ、使う量を実行中の需要に合わせて動かす unified memory を SGLang に入れた話をまとめたものです。ここでの unified memory は、Grace Hopper の CPU と GPU の共有メモリや CUDA の Unified Memory とは別のもので、SGLang の中のメモリの置き場の作り方のことです。抜粋に出てくるアリーナは 1 つの連続した GPU のメモリの領域のことで、retraction はメモリが足りなくなったときに実行中のリクエストをいったん巻き戻して後でやり直すことです。

:::message
**コメント**: 記事が評価に使った Qwen3.5-4B や GPT-OSS-20B のようなハイブリッドなモデルが増えるなら、KV と状態の割合を決め打ちしない仕組みは、それを扱う推論エンジンでは必要になりそうだと思いました。割合を 0.1 に変えるだけでスループットが既定の割合より 12% 落ちる例を先に示してから、まとめた方式が、割合が合っている負荷ではほぼ同じで、合わない負荷では上回ることを見せる、という比べ方も分かりやすいです。リクエストを受け入れる前に、最後まで動かしたときにメモリが足りるかを先に判定し、動かしている最中にページを移すときに古いバイトを守る仕組みまで書いていて、作り込みが細かい印象です。ただ、まだ実験的な機能で、対象はハイブリッドなモデルだけで、優先度による割り込みは無効になります。測定も H200 1 枚で 2 回ずつなので、複数の GPU や PD 分離の構成での振る舞いを見たいです。
:::

#### 参照元からの抜粋と要約

- **課題**: ハイブリッドなモデルのメモリを、状態の種類ごとに起動時の固定の割合で分けると、負荷に合わない割合を選んだときにスループットが落ちたり、同時に動かせるリクエストの数が不必要に絞られたりします。適切な割合はまだ来ていない負荷に依存するので、決めるには事前の測定が要り、負荷が変わるとメモリが余ったまま使われません。
- **ねらい**: 割合を決め打ちせず 1 つのアリーナにまとめても、既定の割合の構成と同じかそれ以上の性能を保ち、割合が負荷に合わない場面でより多くのリクエストを受け入れられることを示すこと。
- **やったこと**: 記事では、全部の層の KV をトークンごとの 1 つの項目にまとめる新しい並べ方にし、全体を見る attention の KV と上限のある状態を同じアリーナの中の帯として確保したと説明しています。リクエストを受け入れる前に、最後まで動かしたときに必要なメモリが確保できるかを判定し、実行中の処理を壊さずにページを動かすために、解放したページや移したページの古いバイトをしばらく守る仕組みを入れました。`--enable-unified-memory` で有効にします。評価は H200 1 枚で、Qwen3.5-4B と GPT-OSS-20B を使い、SGLang の既定の、種類ごとに置き場を分ける構成と比べました。各条件は 2 回の平均です。
- **結果**: 記事によると、Qwen3.5-4B の入力 1,024、出力 256 トークン、同時 64 の負荷では、スループットは unified memory が毎秒 5,830 トークン、既定の構成が 5,880 トークンで、GSM8K の 200 問の正答率はどちらも 0.875 でした。GPT-OSS-20B の入力 512、出力 1,536 トークン、同時 1,024 の負荷で、既定の構成の割合を 0.1 に変えると、スループットは既定の割合の毎秒 9,030 トークンから 7,910 トークンに 12% 落ちました。同じ負荷で、既定の割合の構成が同時に動かせたのは 618 のリクエストだったのに対し、unified memory は約 1,000 を動かし、既定の割合の構成よりスループットは 14% 高く、TTFT は 43 秒から 6 秒に縮みました。Qwen3.5-4B の入力 16K、出力 4,096 トークン、同時 64 の負荷では、同時に動かせた数が既定の構成の 22 に対して 32 で、26% 速くなりました。いまは実験的な機能で、ハイブリッドなモデルだけが対象で、優先度による割り込みは無効になり、LMCache や FP4 の KV などとの組み合わせは起動時に拒否されます。使い方と設計は [SGLang のドキュメント](https://docs.sglang.io/docs/advanced_features/unified_memory)にあります。

### vLLM の DeepSeek-V4.1-Flash on Vera Rubin: 同じ対話性で GB300 の 58 倍

> 参照元: [DeepSeek-V4.1-Flash on Vera Rubin NVL72: 58x Throughput vs. GB300 NVL72 at 387 tokens/s](https://vllm.ai/blog/2026-11-12-deepseek-v41-flash-vera-rubin)

推論の性能は、1 人の利用者に毎秒何トークン返せるかという対話性と、GPU 1 枚が全体で毎秒何トークン処理できるかというスループットの、2 つの釣り合いで決まります。同じハードウェアでも、同時に受けるリクエストを増やせばスループットは上がり対話性は下がるので、2 つの構成を比べるときは同じ対話性の点どうしで比べるのが筋です。Vera Rubin NVL72 は、NVIDIA の Blackwell の次の世代の Rubin の GPU 72 枚を 1 つの NVLink でつないだラックで、1 枚の GPU の中にメモリの領域が 2 つあることや、FP8 と FP4 の新しい行列の掛け算の命令を持つことが、GB300 NVL72 との違いです。この vLLM のブログは、Inferact と vLLM のチームが、GB300 NVL72 で組んだ DeepSeek-V4.1-Flash の提供の構成を Vera Rubin NVL72 に移し、Rubin の特徴に合わせてカーネルとメモリの使い方を作り直したものです。抜粋に出てくる DEP はデータ並列の attention と専門家並列を組み合わせた構成で、DEP2 は 2 枚の GPU、DEP16 は 16 枚の GPU にまたがります。AgentX は SemiAnalysis が公開している、エージェントのコーディングの会話を再生して負荷をかけるベンチマークで、Mooncake は KV キャッシュを複数のサーバーで共有する置き場です。

:::message
**コメント**: 見出しの 58 倍は、GB300 の結果と、利用者 1 人あたり毎秒 387 トークンという同じ対話性の点どうしで比べた数字で、比べ方としては筋が通っています。ただ、58 倍には Rubin 向けにカーネルとメモリの使い方を作り直した分も入っていて、トークンにはキャッシュに当たった入力も数えているので、世代の差そのものとは読まないほうがよいと思いました。387 トークンが GB300 の曲線のどのあたりの点かによっても、倍率は大きく変わるはずです。それよりも面白かったのは、Rubin で計算が速くなった結果、1 つのラックがさばく同時のセッションが増え、GB300 のときの GPU ごとの KV の置き場とセッションを GPU に固定する割り振りでは追いつかなくなった、という話です。速いハードウェアが次はメモリと割り振りを問題にする流れで、KV の置き場をまとめて需要に合わせる点は今週の unified memory の話とも似ています。prefill の GPU の空いた HBM を共有の KV の置き場に出す仕組みはまだ実験的で、ピークの数字や 1 人向けの最速の数字には比べる相手が書かれていません。手元で Rubin を試せる見込みはまだないので、まずは GB300 の曲線の上で、対話性を変えたときに倍率がどう動くかを記事の図から読み取ってみたいです。
:::

![Vera Rubin NVL72 の GPU 1 枚あたりのスループットが、利用者 1 人あたり毎秒 387 トークンの点で、Dynamo と vLLM で動かした GB300 NVL72 の 58 倍になることを示す図](https://vllm.ai/blog-assets/figures/2026-11-12-deepseek-v41-flash-vera-rubin/hero.png?v=20261112)
*出典: [DeepSeek-V4.1-Flash on Vera Rubin NVL72](https://vllm.ai/blog/2026-11-12-deepseek-v41-flash-vera-rubin) の図*

#### 参照元からの抜粋と要約

- **課題**: GB300 NVL72 で作った DeepSeek-V4.1-Flash の prefill とデコードを分けた構成と専門家並列の構成を、Vera Rubin NVL72 に移し、Rubin の 2 つのメモリの領域、新しい行列の掛け算の命令、72 枚の NVLink のつながりを使って性能を伸ばしたいとしています。Rubin では 1 つのラックがさばく同時のセッションが大きく増え、GB300 のときの GPU ごとの CPU 側の prefix cache と、セッションを GPU に固定する割り振りでは、キャッシュが足りず、GPU の間の負荷の偏りが起きます。
- **ねらい**: GB300 の構成の形を保ったまま、カーネルとラック全体のメモリの使い方を Rubin に合わせて作り直し、スループットと対話性の曲線を押し上げること。
- **やったこと**: 記事では、GB300 で使った DEP2 の prefill、DEP16 か DEP32 のデコード、最もレイテンシーの短い TP8 のデコード の 3 つの形をそのまま使い、中のカーネルを Rubin の 2 つのメモリの領域と新しい命令に合わせて作り直したと説明しています。MoE の dispatch では、各トークンが必要とする遠くの GPU からの読み込みを、自分の GPU への書き込みより先にすべて出すようにしました。KV キャッシュを DRAM と空いた HBM まで広げた 1 つの Mooncake の置き場にまとめ、セッションを GPU に固定しない、負荷を見た割り振りに切り替えました。
- **結果**: 記事によると、Vera Rubin NVL72 の 1 ラックで SemiAnalysis AgentX を流すと、利用者 1 人あたり P90 で毎秒 387 トークンの点で、GPU 1 枚あたり毎秒 170 万トークンを処理し、これは同じ対話性の点での、Dynamo と vLLM で動かした GB300 NVL72 の 58 倍でした。ここでのトークンは、キャッシュに当たった入力、当たらなかった入力、出力をすべて合わせて数えています。同じ曲線の上の別の点として、GPU 1 枚あたりのピークの毎秒 252 万トークンと、1 人向けの最速の構成の P90 で毎秒 1,810 トークンが挙がっていますが、これらには比べる相手が書かれていません。カーネルの作り直しでは、Rubin の上の変更の前と後で比べて、32K トークンの DEP2 の prefill の 1 ステップが 28% 短くなり、8 枚にまたがる DEP8 でのデコードの MoE のカーネルが 192 マイクロ秒から 160 マイクロ秒になりました。非常に多い同時のセッションでも、prefix cache に当たる割合は 96.5〜97% を保ちました。prefill の GPU の空いた HBM を共有の置き場に出す仕組みは、まだ実験的とされています。

### Detent: カーネルの選び方の固定によるバッチ不変

> 参照元: [Detent: Batch-Invariant LLM Serving and RL Rollouts at Near-Stock Speed](https://arxiv.org/html/2611.10611)

LLM の推論エンジンは、GPU を効率よく使うために複数のリクエストをまとめたバッチで処理します。ところが、同じリクエストでも、一緒にバッチに入った他のリクエストによって出力がビット単位で変わることがあります。小数の足し算は足す順番を変えると結果がわずかに変わるので、バッチの大きさに応じて足し方の違う計算を選ぶと、結果も変わってしまうからです。評価の再現や、強化学習でロールアウトと呼ぶ「今のモデルで答えを生成する段階」を学習側で計算し直して一致させたい場面では、これが問題になります。vLLM や SGLang には、どんなバッチでも同じ結果を返すバッチ不変のモードがすでにありますが、計算ごとに 1 種類の保守的なカーネルに固定するので遅くなります。カーネルは GPU の上で動く 1 つの計算のプログラムのことです。このプレプリントは、独立研究者と Boston University、Google、Princeton University などの研究者が、カーネルそのものではなく、どのカーネルをどの設定で選ぶかの判断のほうを固定する Detent を作ったものです。抜粋に出てくる split は長い入力を分けて並列に計算し最後に足し合わせるやり方で、GRPO は同じ問題への複数の答えの報酬を比べてモデルを更新する強化学習の手法、KL はロールアウト側と学習側の確率のずれの大きさを表す量です。

:::message
**コメント**: 前号では学習側から同じ問題に取り組む TitanRL の batch-invariant モードを取り上げ、本の章 [[26/10/29:#3] 学習と推論の確率は本当に一致するか](https://zenn.dev/tosshi/books/ml-distributed-experiment-collection/viewer/exp-titanrl-batch-invariant) でも確かめました。Detent はそれを推論エンジンの側から、しかも「カーネル自体はバッチ不変でも、選び方がバッチを読んでいる」という見方で解いていて、固定する対象をカーネルから選び方に移し、固定する値をワークロードごとに測って決めると、H100 4 枚の構成で既定の構成と比べた遅さが、既存の決定的なモードの 1.67〜10.3 倍から 1.04〜1.17 倍まで縮むのが面白いと思いました。BF16 の GRPO で、既定の構成だと報酬が途中で崩れたのに Detent では崩れなかった、という結果は、学習と推論の確率のずれが実際に学習を壊すことを示す例として覚えておきたいです。ただ、カーネルの選び方を SelIR という専用の言語で書き直す手間がカーネルごとにかかり、動的な FP8 の倍率のようにバッチ全体で決まる値は対象外で、コードもプレプリントには載っていません。最速の設定は流れてくるリクエストの形で変わり、Qwen3-30B-A3B では別の形の負荷向けの設定を当てると、その負荷に合わせた設定と比べて最大 4.17 倍遅くなるとも書かれているので、本番でこの設定をどう保つかが一番の課題だと感じます。
:::

![Detent がワークロードごとに設定を決めることで、Qwen3-30B-A3B と Llama-3.1-70B のどちらでも既定の構成に近いレイテンシーでバッチ不変を保つことを示す図](https://arxiv.org/html/2611.10611v1/fig_headline.svg)
*出典: [Detent](https://arxiv.org/html/2611.10611) の Figure 1*

#### 参照元からの抜粋と要約

- **課題**: 推論エンジンは、同じバッチに乗る他のリクエストの組み合わせによって、attention の split の数とタイルの幅、MoE の融合カーネルの設定の行、TP の all-reduce のアルゴリズムを切り替えるので、カーネル自体がバッチ不変でもエンジン全体ではバッチ不変になりません。既存の決定的なモードである SGLang-Det と vLLM-Det は、計算ごとに 1 種類の保守的なカーネルに固定するため、出力トークン 1 個あたりのレイテンシーが既定の構成の 1.67〜10.3 倍になります。既定の構成では、SGLang で負荷を変えるだけで GSM8K の 1,319 問のうち 33 問の答えが変わり、学習側で計算し直したロールアウトのトークンのうちビットが一致するのは 1.0〜47.7% でした。
- **ねらい**: カーネル自体は変えずに、カーネルの選び方だけをバッチ不変にして、既定の構成に近いレイテンシーでバッチ不変を実現すること。
- **やったこと**: 著者らは、FA3 の attention、融合 MoE、all-reduce、GEMM のカーネルの選び方を SelIR という Python の一部からなる言語で書き直し、バッチに依存する入力から選択までのすべての経路を塞ぐ最小の値の組を最大流の計算で求めました。FA3 では 3 個の値を固定すればよく、MoE では設定表の行を決める 1 個の値で、バッチに依存する 16 個の選択のうち 14 個を固定できました。固定する値はワークロードごとに測って決め、カーネルの種類ごとに独立に探すことで、Qwen3-30B-A3B では 1,607,040 通りの組み合わせを 3,020 通りに減らしました。vLLM と SGLang に組み込み、Llama-3.1-70B と MoE の Qwen3-30B-A3B を H100 4 枚の TP 構成で、ShareGPT の会話と 8K トークンの arXiv の文書など 3 種類の負荷で評価しました。
- **結果**: 著者らによると、H100 4 枚で vLLM と SGLang の上の 2 つのモデルを動かしたとき、出力トークン 1 個あたりのレイテンシーは、ワークロードごとに設定を決めた Detent で既定の構成の 1.04〜1.17 倍、既存の決定的なモードで 1.67〜10.3 倍でした。GSM8K の正答率は、SGLang-Det と比べて -0.15〜+0.53 ポイントで有意な差はありませんでした。温度 1 で生成した GSM8K のロールアウト 512 件は、バッチやキャッシュの分け方を変えても 512 件すべてがビット単位で一致しました。Qi らの手順で DeepSeek-R1-Distill-Qwen-1.5B を BF16 の GRPO で学習すると、既定の構成では報酬が 299 ステップ目の 0.733 から 500 ステップ目の 0.436 に崩れましたが、Detent ではずれの KL が 600 ステップまで 0 のままで、報酬は 0.843 に達しました。かかった時間は既定の構成の 1.18 倍でした。一方で、ある負荷向けに決めた設定を別の形の負荷に当てると、その負荷に合わせた設定と比べてレイテンシーの中央値が Qwen3-30B-A3B で最大 4.17 倍、Llama-3.1-70B で最大 1.22 倍になり、B200 の上の Llama-3.1-8B では設定を決めないままだと既定の構成の最大 2.34 倍遅くなりました。著者らは、動的な FP8 の倍率のようにバッチ全体で決まる値は対象外で、バッチ不変にするにはトークンごとか固定の倍率が要るとしています。プレプリントには Detent 自身のコードの公開先は書かれていません。

### SubGPU Pipelining: 1 枚の GPU の中の流れ作業

> 参照元: [SubGPU Pipelining: Intra-GPU Fine-Grained Spatial Parallelism for LLM Inference](https://arxiv.org/html/2611.14904)

LLM が答えを 1 トークンずつ生成するデコードの段階では、1 ステップの中で正規化、attention、行列の掛け算、MoE の専門家の計算などの何十個ものカーネルを順番に呼びます。B200 のような強力な GPU では、1 つのカーネルがマイクロ秒単位で終わってしまい、起動の待ち時間が目立ったり、メモリの帯域が上限に当たって GPU の計算の部品が余ったりします。GPU の中には SM と呼ぶ計算の部品が 148 個並んでいて、ふつうはどのカーネルも全部の SM を使って 1 つずつ順に動きます。GPU を増やしても、この 1 枚の中の無駄は残ります。このプレプリントは、NVIDIA の研究者が、1 枚の GPU の中を SM のまとまりに分けて、計算の区間を流れ作業で重ねる SubGPU Pipelining を提案したものです。抜粋に出てくるマイクロバッチはバッチをさらに小さく分けたもので、Green Context は SM の一部だけを使う区画を作る CUDA の機能です。ユーザーあたりのスループットは 1 人の利用者に 1 秒あたり何トークン返せるか、GPU あたりのスループットは GPU 1 枚が 1 秒あたり全体で何トークン生成できるかを表します。

:::message
**コメント**: 並列化というと GPU を何枚にどう分けるかの話になりがちですが、これは 1 枚の GPU の中をさらに分ける話で、学習のテーマの並列化と並べると、分ける単位がどんどん細かくなっているのが面白いです。既存のカーネルには手を入れず、Green Context と CUDA Graph という CUDA の既存の仕組みで組んでいる点はよいと思いましたが、区間の切り方と SM の割り当てを決める探索のコードは見当たらないので、同じことを試すには割り当てを自分で決める必要があります。ただ、全部の SM で順に動かす方式と比べてユーザーあたりのスループットが最大 2.2 倍、GPU あたりのスループットが最大 1.9 倍という見出しの数字はシミュレーションのもので、実機は 1 枚の B200 で 32 枚構成の 1 枚分の仕事を、GPU 間の通信を見積もりの待ち時間で置き換えて再現したものです。実機では、full attention のカーネルの合計時間は延び SM の稼働率も下がっていますが、重ねた結果として、全部の SM で順に動かす場合と比べて 1 ステップは 10.33% 短くなっています。vLLM や SGLang のような実際のエンジンの中で、ほかの並列化と組み合わせたときにどこまで残るかを見たいです。
:::

![ふつうの実行ではどのカーネルも 148 個の SM を全部使って順番に動くが、SubGPU では full attention を 68 SM、残りを 80 SM に割り当てて重ねて動かす様子を比べた図](https://arxiv.org/html/2611.14904v1/figures/fig3_kernel_timeline.png)
*出典: [SubGPU Pipelining](https://arxiv.org/html/2611.14904) の Figure 6*

#### 参照元からの抜粋と要約

- **課題**: LLM のデコードは、短くメモリの読み出しに縛られがちなカーネルが何十個も連続するので、GPU の計算の部品とメモリの読み出しを一時的にしか使い切れません。GPU の間で分ける TP、DP、EP、CP、パイプライン並列のどれを使っても、この GPU 1 枚の中の無駄は解決しません。
- **ねらい**: 1 層分の計算のつながりを連続した区間に切って互いに重ならない SM のまとまりに固定し、マイクロバッチを流し込んで、必要な資源の違う区間を同時に動かすこと。
- **やったこと**: 著者らは、区間の切り方、SM の割り当て、マイクロバッチの大きさをまとめて決める最適化の問題を定式化し、出来事を順に追うシミュレータと、動的計画法で切り方の案を出してから SM を 2 つの区間の間で移し替えて磨く探索を作りました。シミュレーションでは、GPT-OSS 120B のデコードを入力の長さ 32,768 で、32 枚の B200 の構成を想定して評価しました。実機では、1 枚の B200 で 32 枚構成の 1 枚分の仕事を再現し、TensorRT-LLM の既存のカーネルを CUDA の Green Context と CUDA Graph で組み合わせて、バッチ 2,048 で測りました。GPU 間の通信は、3 マイクロ秒と転送量を 900 GB/s で割った時間を待つだけの仮のカーネルで置き換えました。
- **結果**: 著者らによると、シミュレーションでは、GPU あたりのスループットをそろえて比べると、ユーザーあたりのスループットが全部の SM で順に動かす方式の最大 2.2 倍になり、ユーザーあたりのスループットをそろえて比べると、GPU あたりのスループットが最大 1.9 倍になりました。バッチが小さすぎるときと、計算に縛られて SM を使い切っているときは差がほぼ消えました。1 枚の B200 での実機では、メモリの読み書きの帯域の平均がピークの 71.8% から 83.6% に上がり、36 層のデコードの 1 ステップが 14.970 ミリ秒から 13.424 ミリ秒へ 10.33% 短くなりました。このとき SM の稼働率は 85.9% から 71.7% に下がり、36 層の間に full attention のカーネルが動いていた時間を足し合わせると 10.957 ミリ秒から 15.345 ミリ秒に延びました。同じ設定でシミュレーションが予測した短縮は 6.6% でした。著者らは、同時に動く区間の重みや途中の値が GPU の L2 キャッシュに収まらないと利得が打ち消されうるとしています。コードの公開先は書かれていません。

### Cairn: 共有と前もった準備によるコールドスタートの短縮

> 参照元: [Fast Serverless LLM Cold Starts by Sharing and Prewarming Startup Work](https://arxiv.org/html/2611.16180)

サーバーレスの LLM の基盤では、リクエストが来たときだけ推論のプロセスを立ち上げ、使われなくなったら止めることで GPU を節約します。このとき何も動いていない状態から最初の答えを返せるまでにかかる時間をコールドスタートと呼び、これまでの研究は主に重みを速く読み込む工夫をしてきました。ところが、ServerlessLLM と vLLM を組み合わせた構成で測ると、コールドスタートは 57〜85 秒かかり、そのうち重みの読み込みは 5〜11% しかありませんでした。残りは、torch.compile によるコンパイル、KV キャッシュに使えるメモリの量を決めるメモリプロファイリング、プロセスの起動と PyTorch の読み込みなどで、どのサーバーで行っても同じ結果になるか、どのモデルかに関係なく済ませられる作業です。このプレプリントは、KAIST と SK hynix の研究者が、こうした作業をサーバーをまたいで共有し、前もって済ませておく Cairn を作ったものです。抜粋に出てくる CXL は、CPU が別の装置につながったメモリをふつうのメモリと同じ命令で読み書きできる接続の規格で、複数のサーバーで共有するメモリの置き場をメモリプールと呼びます。ウォームコンテナは、どのモデルかが決まる前に、モデルに依存しない準備だけを済ませて待っている 2 つ 1 組のプロセスで、TTFT はリクエストが届いてから最初のトークンが返るまでの時間です。

:::message
**コメント**: コールドスタートというと重みの転送の帯域の話になりがちですが、重みは 1 割程度で、残りの多くはサーバー間で結果が同じか、モデルに依存しない作業のやり直しだった、という切り分けが一番の収穫でした。共有できるもの、前もってできるもの、記録したプロセスから離せない CUDA Graph の 3 つに分ける見方は、サーバーレスに限らず、Kubernetes で推論の Pod をスケールさせるときの立ち上げの時間を見直すときにも使えそうです。ただ、共有の CXL のメモリプールは実機ではなく、1 台のホストの上の 2 台の仮想マシンでリモートの NUMA のメモリを共有させて真似したもので、GPU も RTX A6000 が 1 枚ずつです。16 台の規模の結果はシミュレーションで、GPU が埋まり切る負荷では差が縮むとも書かれています。CXL が無い環境でも、vLLM の compile のキャッシュを共有のストレージに置くだけでどこまで縮むかは、手元で確かめられそうです。
:::

#### 参照元からの抜粋と要約

- **課題**: サーバーレスの LLM の推論では、コールドスタートが長くなります。著者らが ServerlessLLM の vLLM の部分を vLLM v0.20 に移植した構成で 1B から 14B のモデルを測ると、57〜85 秒かかり、重みの読み込みはその 5〜11% でした。残りのコンパイル、メモリプロファイリング、起動の処理は、サーバー間で結果が同じか、モデルに依存しないのに、サーバーごとに毎回やり直しています。2 台のサーバーで同じモデルを立ち上げると、モデルの情報、コンパイラのキー、CUDA Graph のメモリの見積もりはバイト単位で一致し、コンパイル済みのコードと Triton のカーネルも同じでした。
- **ねらい**: サーバー間で結果が同じ作業はクラスタで一度だけ行って共有し、モデルに依存しない準備はモデルが決まる前にウォームコンテナで済ませておくことで、コールドスタートを短くすること。
- **やったこと**: 著者らは、最初にモデルを立ち上げたサーバーが、重み、コンパイルのキャッシュ、コンパイラのキー、CUDA Graph のメモリの見積もりを書き換えない項目として CXL のメモリプールに書き込み、他のサーバーはそれをその場で読む仕組みを作りました。記録したプロセスから離せない CUDA Graph の記録だけは、ふつうどおり毎回行います。モデルに依存しない準備は、CUDA をまだ初期化していないひな形のプロセスを fork して作るウォームコンテナで済ませます。評価では、1 台のホストの上の 2 台の仮想マシンに RTX A6000 を 1 枚ずつ割り当て、リモートの NUMA のメモリを共有させて 96 GB の CXL のメモリプールの代わりにしました。モデルは Llama-3.2-1B、OPT-1.3B、Qwen2.5 の 1.5B、3B、7B、14B の 6 つで、ServerlessLLM と vLLM の組み合わせと比べました。
- **結果**: 著者らによると、一度もそのモデルを動かしたことがなく、自分のチェックポイントも持たないサーバーで、コールドスタートは ServerlessLLM と vLLM の組み合わせの 57〜85 秒から 11.0〜21.0 秒になり、4.1〜5.2 倍速くなりました。同じモデルを過去に動かしてローカルにキャッシュを持つサーバーと比べても、Qwen2.5 の 3B から 14B で約 2 倍速くなりました。Azure Functions の記録に沿った 1 時間で 403 件のリクエストを 2 台で処理すると、TTFT の中央値は ServerlessLLM と vLLM の組み合わせの 32.5 秒から 11.8 秒に 64% 短くなりました。16 台で各 4 枚の GPU を想定したシミュレーションでは、1 秒あたり 3.2 件のリクエストで 300 秒を超えて時間切れになった割合が、ServerlessLLM と vLLM の組み合わせの 15.6% から 2.1% に下がりましたが、1 秒あたり 4.8 件でどちらも GPU が埋まり切ると、ServerlessLLM と vLLM の組み合わせに対する TTFT の中央値の改善は 26% に縮みました。最初に立ち上げるサーバーが共有のメモリプールへ同時に書き込むと、ディスクからの最初の読み込みは、書き込まない場合より 22〜23% 遅くなりました。コードはプレプリントの出版時に公開するとされており、いまは公開されていません。

## カーネルと開発の道具

### TLX: ワープの役割分担を書ける Triton の拡張

> 参照元: [How We Built TLX: A Hardware-Native GPU Compiler for Production ML at Scale](https://engineering.fb.com/2026/11/10/open-source/tlx-a-hardware-native-gpu-compiler-for-production-ml/)

Triton は、行列の塊をまとめて扱う書き方で GPU のカーネルを Python から書ける言語で、Meta の社内では 10 か月でカーネルの数が 3.8 倍に増え、同じ期間に 2.0 倍だった CUDA のカーネルより速く広がっています。ところが Hopper や Blackwell の GPU では、データを運ぶワープの組と計算するワープの組に仕事を分ける warp specialization、メモリの間の転送を専用に受け持つ TMA、計算の結果を置く専用のメモリの TMEM、複数のスレッドのまとまりを協調させるクラスタの実行がスループットの鍵になり、これらはカーネルの組み立て方そのものを変えます。CUDA ならこれらを書けますが手間が大きく、Triton では多くがコンパイラの裏に隠れていて、新しい GPU が出るたびにコンパイラの対応を待つことになっていました。この Meta のブログは、Meta のチームが、Triton の書き方を残したまま、ワープの組の役割分担と同期をはっきり書ける拡張の TLX を作り、本番で使った経験をまとめたものです。TLX は Triton Low-Level Extensions の略で、記事は 1 つのスレッドを単位にする CUDA と塊を単位にする Triton の間に、ワープの組を単位にする段が抜けていたとし、その段を MIMW と呼びます。抜粋に出てくる mbarrier は、ワープの組の間で準備ができたことを知らせ合う軽い同期の仕組みで、MFU は GPU が理論上出せる演算のスループットのうち実際に使えた割合です。

:::message
**コメント**: 同じテーマの GC-MoE が、warp specialization や非同期の段の重ね合わせを CuTe DSL で一から組んでいたのを見ると、それを Triton の書き方のまま書けるようにする、という TLX の狙いはよく分かります。Triton は何を計算するかを、TLX はそれをどう段取りするかを書く、という役割の分け方は、学習のテーマの SS-HSDP が計算の都合と更新の都合を分けたのと似た発想で、今週は分け方の設計の話が多いと感じました。記事の Blackwell の GEMM の例では、データを読む組、テンソルコアで計算する組、結果を書く組をそれぞれ書いていて、ふつうの Triton より段取りが見えます。CUDA で同じことを書いた場合との長さの比較は記事にはありません。ただ、スループットとレイテンシーの数字はどれも Meta の社内の事例で、GEMM や attention の形状をそろえた CUTLASS や cuBLAS との比較の表はなく、MoE の grouped GEMM の事例には数字がありません。コードは Meta の Triton のフォークにあり、本家の Triton にプラグインとして足す配り方もあるので、手元の Hopper で attention のカーネルを書いて、ふつうの Triton と比べてみたいです。
:::

![1 つのスレッドを単位にする CUDA と、塊を単位にする Triton の間に、ワープの組を単位にする段が抜けていて、TLX がそこを埋める構成図](https://engineering.fb.com/wp-content/uploads/2026/11/Meta-TLX-Figure-3.png)
*出典: [How We Built TLX](https://engineering.fb.com/2026/11/10/open-source/tlx-a-hardware-native-gpu-compiler-for-production-ml/) の図*

#### 参照元からの抜粋と要約

- **課題**: Hopper と Blackwell は、warp specialization、TMA、TMEM、クラスタの実行といった実行の段取りを求めますが、CUDA は書けても手間が大きく、Triton は生産的でも実行の構造をコンパイラの裏に隠すので、新しいハードウェアへの対応が常に遅れます。記事はこれをコンパイラが追いつく問題と呼んでいます。
- **ねらい**: Triton の生産的な書き方を保ったまま、ワープの組を実行の基本の単位として扱える段を用意し、新しいハードウェアの機能をコンパイラを待たずに使えるようにすること。
- **やったこと**: 記事では、Triton に 5 つの機能を足したと説明しています。ワープの組に送り手、計算役、後処理役などの役割を割り当てる機能、mbarrier などでワープの組の単位で同期を書く機能、TMA、非同期のテンソルコアの演算、TMEM を直接使う機能、複数のスレッドのまとまりが分散した共有メモリで協調するクラスタの実行、そしてデータの並べ方を書かなくてもコンパイラが決める機能です。対象は NVIDIA の Hopper と Blackwell、AMD の MI300 と MI350x で、本番では広告の生成モデルの GEM の学習、推薦の推論の IKBO、LLM の事前学習の MoE の grouped GEMM の 3 つに使っています。
- **結果**: 記事によると、GEM の学習では数千枚の Blackwell で合計 10 の 24 乗回程度の浮動小数点の演算を行い、学習の全体の MFU は 20〜25% でした。この数字には比べる相手が書かれていません。GEM では Blackwell で CUTLASS、CuTe DSL、TLX の 3 つを比べ、ほとんどのカーネルで生産性と性能のつり合いが最もよいのは TLX だったとしています。GEM の多くの attention の演算を 1 つのカーネルにまとめた GDPA は、まとめる前の複数のカーネルの構成と比べて、順伝播で最大 2 倍速くなりました。IKBO では、推薦のときに候補ごとに同じユーザーの特徴量を何十回も複製していた無駄をなくす中で、linear compression のカーネルに残ったボトルネックを TLX のカーネルで解き、H100 で TLX にする前のカーネルの 4 倍のスループットになりました。FlashAttention では、IKBO に合わせて共同設計したモデルで、計算が支配的な部分の正味のレイテンシーが、共同設計の前と比べて最大 3 分の 2 減りました。MoE の grouped GEMM は、大きな GPU の群れで長い期間本番で動いているとだけ書かれ、数字はありません。記事がリンクする arXiv の論文の概要によると、コードは [facebookexperimental/triton](https://github.com/facebookexperimental/triton) で公開されていて、リポジトリのライセンスは MIT です。

### LLDB で CPU と GPU を 1 つのセッションでデバッグする拡張

> 参照元: [Extending LLDB to Debug Applications That Span CPUs and GPUs](https://engineering.fb.com/2026/11/09/developer-tools/extending-lldb-to-debug-applications-that-span-cpus-and-gpus/)

いまの AI のプログラムは、高レベルのフレームワークから CPU のネイティブのコードを通って GPU のカーネルまで往復するので、不具合も CPU と GPU の境目をまたいで起きます。ところが CPU と GPU は命令の種類、レジスタ、メモリのアドレスの空間、実行のしかたが違い、GPU は CPU 側のプロセスの中のランタイムとドライバを通して動くので、ふつうのデバッガのように 1 つのプロセスを 1 つの見方で調べることができません。そこで GPU を作る会社がそれぞれ、AMD の ROCgdb や NVIDIA の CUDA-GDB のような専用のデバッガを作ってきましたが、止める位置を決めるブレークポイントや 1 行ずつ進めるステップ実行のような共通の機能まで、会社ごとに作って保守することになっていました。この Meta のブログは、Meta のチームが、LLVM のデバッガの LLDB に、特定の会社に依存しないアクセラレーターのためのプラグインの土台を作り、その大部分を LLVM の本家に取り込んだことを説明したものです。抜粋に出てくる lldb-server は、デバッグする対象のそばで動いて、プロセスの起動や停止、メモリの読み出しを LLDB の代わりに行う相棒のプロセスです。ターゲットは LLDB がデバッグする 1 つの対象のことで、upstream は本家のリポジトリへの取り込みを指します。

:::message
**コメント**: CPU と GPU を 1 つのプロセスに無理にまとめず、別々のターゲットのまま 1 つのセッションに並べ、つなぎ役をプラグインに任せる、という分け方は、推論のテーマの SGLang-Neuron が本体と Trainium の部分を分けたのとよく似ていると思いました。同じテーマの GPU のカーネルのライブラリの不具合の調査では、結果が誤りになる不具合が 17.67% あったので、CPU 側の呼び出しから GPU のカーネルの中まで同じ道具で追えるのは、こうした不具合を調べるときにありがたいはずです。本物の GPU を使わずにプラグインの流れを確かめる模擬のプラグインを LLVM のテストに入れている点も、共有の土台を保守していくための手当てとしてよいと感じました。一方で、記事に数字はなく、例は AMD の HIP のカーネル 1 つで、PyTorch や Triton のカーネルのデバッグとどうつながるかは書かれていません。記事にはリンクがありませんでしたが、LLVM のリポジトリを探すと、たとえば[プラグインの基底のクラスを足す PR](https://github.com/llvm/llvm-project/pull/198907) が見つかりました。手元では Triton のカーネルの中でブレークポイントが止まるかを、まず試してみたいです。
:::

![CPU と GPU が別々の LLDB のターゲットのままで、lldb-server の中のプラグインが CPU 側と GPU 側のデバッグを協調させる構成図](https://engineering.fb.com/wp-content/uploads/2026/11/Extending-LLDB.png)
*出典: [Extending LLDB to Debug Applications That Span CPUs and GPUs](https://engineering.fb.com/2026/11/09/developer-tools/extending-lldb-to-debug-applications-that-span-cpus-and-gpus/) の図*

#### 参照元からの抜粋と要約

- **課題**: CPU と GPU の境目をまたぐ不具合を調べたいのですが、ふつうのデバッガは 1 つのプロセスが 1 つの命令の種類と 1 つのメモリの見方を持つことを前提にしています。GPU は x86-64 のホストと違う命令を使い、何千もの実行の単位を同時に進め、CPU と同じアドレスが別の場所を指すこともあります。会社ごとの専用のデバッガは、共通の機能まで別々に作って保守しています。
- **ねらい**: LLDB の lldb-server に会社に依存しない共通のプラグインの仕組みを作り、コマンドライン、通信の取り決め、シンボルの処理、IDE との連携のような共有の部分と、ハードウェアに固有の制御を分けること。新しいハードウェアを LLDB に足す作業を、デバッガを一から作るのではなく、その会社のプラグインを書くだけで済むようにすること。
- **やったこと**: 記事では、CPU と GPU を別々の LLDB のターゲットとして表し、それぞれが自分の命令の種類、スレッド、レジスタ、アドレスの空間を持つようにしたと説明しています。プラグインは CPU 側のプロセスの中に内部のブレークポイントを置くよう LLDB に頼み、GPU のデバッグを始められる時点に来ると、その会社のデバッグの API を初期化して接続先を用意します。LLDB はそこに GPU 側の 2 つ目のターゲットを作って接続します。専用のハードウェアなしでこの流れを確かめる模擬のプラグインを作り、GPU のコアダンプを後から調べる仕組みも同じ土台に載せました。記事の時点で、lldb-server のプラグインの取り決め、プラグインの発見と初期化、実行中のイベントの協調、GPU への接続の生成のための通信、CPU と GPU のプロセスの対応づけ、複数のアドレスの空間、模擬のテストを LLVM の本家に取り込み済みで、残りも近く取り込む予定としています。
- **結果**: 記事によると、AMD の HIP で書いたベクトルの内積のカーネルで、CPU のターゲットと `amdgcn` の GPU のターゲットが一覧に並び、保留になっていたブレークポイントが GPU のモジュールの読み込みで有効になり、GPU 側のバックトレースが取れる様子を示しています。Meta の社内の、ハードウェアとソフトウェアの構成が違う複数の GPU の取り組みが、すでに同じ仕組みを使っているとしています。性能などの数字は書かれておらず、記事は個々の PR にリンクしていません。

### GPU カーネルのライブラリの不具合 300 件の分類

> 参照元: [An Empirical Study of Issues in GPU Kernel Libraries for LLM Systems](https://arxiv.org/html/2611.09280)

LLM の学習と推論のスループットは、attention や行列の掛け算を GPU の上で速く計算するカーネルのライブラリに大きく頼っていて、FlashAttention、FlashInfer、Triton、CUTLASS などがその代表です。これらのライブラリは、テンソルの形や数の形式ごとに専用に作り分けた特殊化したカーネルを、利用者の環境でコンパイルして動かすことが多く、エラーを出さずに結果だけが間違う不具合や、GPU の処理が止まったまま進まないハングが起きると、原因を追うのが難しくなります。それでも、こうした不具合がどこから来るのかを体系的に整理した研究はありませんでした。このプレプリントは、Microsoft Research Asia と Tsinghua University の研究者が、7 つのライブラリの GitHub の issue から 300 件を選び、症状、原因、直し方、テストのやり方を手作業で分類したものです。抜粋に出てくるメモリのエイリアシングは、別々であるはずの入力と出力が同じメモリを指してしまうことです。ABI はコンパイル済みのプログラムどうしをつなぐ約束事のことで、ここでの低精度は、FP16、FP8、INT8 のように、ふつうの 32 ビットより少ないビット数で数を表す形式のことです。

:::message
**コメント**: GPU のカーネルというと、計算の中身の誤りや性能の話を想像しますが、原因の 6 割がコンパイラ、ビルド、実行環境の側だったというのが一番の発見でした。症状でも、そもそもインストールや配布で失敗したものとビルドで失敗したものが合わせて半分を超えていて、GPU の上で動く前に壊れている、というのが実態に近いと感じました。前のテーマの Detent が「カーネルの選び方」に原因を置き直したのと同じく、ここでも問題はカーネル本体の外側に多い、という見方がそろってきているのが面白いです。一方で、エラーを出さずに結果だけが間違う例が 17.67% あり、FP16 の参照値と合わないのは参照側の丸めが原因だった例のように、テストの参照値そのものが怪しい場合もあると書かれています。データや分類の表の公開先は見当たらないので、自分たちが使っているカーネルの issue を同じ分類で数えてみると、どこにテストを足すべきかが見えそうです。
:::

| 症状 | 300 件のうちの件数 | 割合 |
|---|---|---|
| インストールや配布の失敗 | 82 | 27.33% |
| ビルドの失敗 | 73 | 24.33% |
| クラッシュ | 63 | 21.00% |
| エラーを出さずに誤った結果 | 53 | 17.67% |
| 性能の劣化 | 23 | 7.67% |
| ハング | 6 | 2.00% |

*出典: [An Empirical Study of Issues in GPU Kernel Libraries for LLM Systems](https://arxiv.org/html/2611.09280) の TABLE II を日本語にまとめたもの*

#### 参照元からの抜粋と要約

- **課題**: GPU のカーネルのライブラリの不具合は、エラーを出さずに結果を壊したり、GPU をハングさせたり、デプロイの食い違いを起こしたりしますが、どんな症状がどんな原因で起き、どう直され、どうテストされているかを体系的に整理した研究がありませんでした。
- **ねらい**: FlashInfer、FlashAttention、Triton、CUTLASS、DeepGEMM、xFormers、bitsandbytes の 7 つのライブラリについて、GitHub の issue を通して症状、原因、直し方、テストとデバッグのやり方を初めて体系的に整理すること。
- **やったこと**: 著者らは、2015 年 12 月から 2026 年 7 月までの issue 9,099 件を集め、失敗に関する語とラベルで 3,181 件に絞り、ライブラリごとの件数に比例して 300 件を選びました。根拠の足りない issue は、同じライブラリで作られた時刻が近い issue と入れ替えました。2 人の著者が 300 件すべてに症状を 6 分類、原因を 3 つの大分類と 15 の小分類で独立に付け、2 人の一致の度合いを表す Cohen's kappa は 0.87 でした。
- **結果**: 著者らによると、300 件のうち、原因がコンパイラとビルドの側だったのが 81 件の 27.00%、実行環境の側だったのが 100 件の 33.33% で、合わせて 181 件の 60.33% でした。カーネルのライブラリそのものの原因は 119 件の 39.67% で、個別の分類で最も多かったのはソフトウェアの組み合わせの非互換の 76 件の 25.33% でした。症状では、インストールや配布の失敗の 82 件の 27.33% とビルドの失敗の 73 件の 24.33% で半分を超えました。カーネルの特殊化が暗黙に課す制約の例として、FlashInfer のサンプリングのカーネルが入力と出力に同じ変数を渡して語彙の外の巨大なトークンの番号を返した [FlashInfer の issue](https://github.com/flashinfer-ai/flashinfer/issues/384) や、xFormers の attention が有効なキーの列の数を符号付き 16 ビットに詰めて長い文脈で NaN を返した [xFormers の issue](https://github.com/facebookresearch/xformers/issues/719) などを挙げています。テストについては、FlashAttention の勾配が FP16 の参照値とは合わず FP32 の同じ計算とは合った [FlashAttention の issue](https://github.com/Dao-AILab/flash-attention/issues/385) などの例から、低精度の数値の誤差とハードウェアに固有の失敗を見つけるには今のテストのやり方が足りないとしています。著者らは、ビルドや実行の前に GPU、ドライバ、コンパイラ、パッケージ、ABI の組み合わせを確かめる道具や、入力と環境を記録して再現したら回帰テストに変える仕組みを提案しています。データの公開先はプレプリントに書かれていません。

### GC-MoE on SM120: ワークステーションの Blackwell での MoE デコードの重ね合わせ

> 参照元: [GC-MoE on SM120: Overlapping Expert-Parallel Token Dispatch with Warp-Level FP8xFP4 Block-Scaled MMA on Consumer Blackwell](https://arxiv.org/html/2611.16219)

MoE のモデルを複数の GPU で動かすときは、専門の部品である専門家を GPU ごとに分けて持つ専門家並列がよく使われます。デコードの 1 層ごとに、トークンを担当の専門家の GPU へ送る dispatch、専門家ごとの行列の掛け算をまとめて行う grouped GEMM、結果を元の GPU へ戻して足し合わせる combine の 3 段が順番に起き、1 回に流れるトークンが少ないので、待ち時間がそのまま遅さになります。著者らの前作の GC-MoE は、この 3 段を、SM の一部だけを使う区画を作る CUDA の Green Context で SM を分け、1 つの CUDA Graph の中で重ねて動かしていて、GC は Green Context の略です。ところが前作が頼っていたデータセンター向けの Blackwell である SM100 の機能のうち、テンソルメモリ (TMEM)、2 つの CTA で協力する行列の掛け算、クラスタの中での一斉配信は、RTX PRO 5000 などのワークステーション向けの Blackwell の SM120 にはなく、GPU の間も NVLink ではなく PCIe でつながります。このプレプリントは、Alibaba の研究者が、この制約の中で同じ 3 段の重ね合わせを作り直したものです。抜粋に出てくるワープは GPU の中で 32 本のスレッドがそろって動く単位で、CTA はそのワープを束ねたスレッドのまとまり、ブロックスケールは一定の数の値ごとに倍率を共有して少ないビット数で数を表す形式のことです。

:::message
**コメント**: 推論のテーマの SubGPU Pipelining と同じく Green Context で SM を分けて段を重ねる話で、同じ週に NVIDIA と Alibaba からこの使い方が出てきたのは偶然ではない気がします。データセンター向けの Blackwell に合わせて作られた MoE のカーネルが、ワークステーション向けの Blackwell では命令の種類からして使えず、作り直しになるというのは、同じ Blackwell という名前でも中身がかなり違うことを示していて覚えておきたいです。PCIe では結果を戻す側の転送が最も大きくなるので、バイト数よりも転送の回数を減らす、という考え方も、NVLink の無い環境で MoE を動かすときの参考になりそうです。ただし評価は 8 枚の RTX PRO 5000 の 1 台だけで、複数のノードは試しておらず、バッチ 256 の GLM5.2 では Cake との差が 1.017 倍まで縮み、著者らも未解決の課題としています。コードの公開先もプレプリントには書かれていないので、PCIe の GPU で MoE を動かす機会があれば、FlashInfer のカーネルとの差を自分で見てみたいです。
:::

![GLM5.2 の形の MoE で、バッチの大きさを 1 から 256 まで変えたときのデコードのレイテンシーを、GC-MoE と、FlashInfer の CuTe DSL で書いた実装と、Cake で比べると、どのバッチでも GC-MoE が最も速いことを示す図](https://arxiv.org/html/2611.16219v1/pro5000_glm52_gc_moe.png)
*出典: [GC-MoE on SM120](https://arxiv.org/html/2611.16219) の Figure 3*

#### 参照元からの抜粋と要約

- **課題**: 専門家並列の MoE のデコードは、dispatch、grouped GEMM、combine の 3 段が 1 層ごとに順番に起き、各 GPU に同時に流れるトークンも少ないので、レイテンシーが問題になります。SM100 向けの設計をそのまま SM120 に持ち込むと、ブロックスケールのテンソルコアがワープ単位の `mma.sync` の命令でしか使えず、テンソルメモリ、2 つの CTA で協力する行列の掛け算、クラスタの中での一斉配信がなく、GPU の間が PCIe であることから、うまく動きません。PCIe では、FP8 で送った値が BF16 の部分和として 2 倍の大きさで戻ってくるので、戻りの転送が全体で最も大きくなります。
- **ねらい**: SM120 と PCIe の制約の中で、3 段を重ねて動かす利点を、設定の調整ではなく仕組みの作り直しで取り戻すこと。
- **やったこと**: 著者らは、FP4 の重みを行列の掛け算の命令の A の側に、FP8 の値を B の側に置く形でメインのループを作り直し、トークンの数に応じてタイルの形を選ぶ仕組みを入れました。dispatch では専門家ごとに準備ができ次第知らせ、同じ送り元の同じトークンを二重に読まないためのキャッシュを持ち、戻りは BF16 のまま連続した区間ごとに 1 回でまとめてコピーする専用のコピー役を置きました。カーネルは CuTe DSL で書きました。評価は PCIe でつないだ 8 枚の RTX PRO 5000 72GB で、FP8 の値と MXFP4 の重みを使い、GLM5.2 と DSV4.1-Flash の 2 つの形について、バッチを 1 から 256 まで 9 通りに変えた計 18 の条件で、FlashInfer の CuTe DSL の W4A8 MegaMoE と Cake の MegaMoE と比べました。
- **結果**: 著者らによると、18 の条件すべてで両方より速く、デコードのレイテンシーで比べた比の算術平均は、FlashInfer の CuTe DSL の実装に対して 1.522 倍、Cake に対して 1.387 倍でした。共有の専門家を一緒に計算する構成でも、Cake に対して平均 1.388 倍でした。GLM5.2 のバッチ 32 では、量子化した重みを GPU のメモリから読み出す帯域が GPU 1 枚あたり毎秒 1,145 GB で、Cake の 1.42 倍でした。一方で、GLM5.2 のバッチ 256 では Cake との差が 1.017 倍、18 マイクロ秒まで縮み、著者らは実質の引き分けで未解決の課題としています。数値の確認では 94 件の検証と 752 件の GPU ごとの確認すべてに合格し、量子化する前の BF16 の MoE と比べたコサイン類似度の最小は 0.97610、Cake の出力とのコサイン類似度の最小は 0.99999976 でした。複数のノードでの動きは試しておらず、コードの公開先は書かれていません。

### SPMW: 格子をそのまま書ける FPGA 回路のプログラミングモデル

> 参照元: [SPMW: A Grid-Based Programming Model for Scalable Accelerator Design](https://arxiv.org/html/2611.12944)

行列の掛け算のような規則正しい計算を速くする専用の回路では、同じ形の小さな計算の部品である PE を格子状に並べ、格子の上で接する PE どうしでデータを受け渡すシストリックアレイがよく使われます。FPGA の上でこうした回路を作るときは、C++ で動作を書いて回路に変換する高位合成の HLS か、回路そのものを SystemVerilog などで書く RTL が使われてきました。ところが HLS では、PE を番号付きの配列で呼び出し、並べ方や端の扱いを pragma や読み込み用の関数にばらばらに埋め込むので、どの PE も同じ形だという規則性がコンパイラに見えず、同じ PE を何度も変換し直してしまいます。このプレプリントは、Cornell University の研究者が、格子の並べ方と、接する PE どうしのつながりをプログラムの中で直接書ける SPMW というプログラミングのモデルを作ったもので、SPMW は Single Program, Multiple Connected Work Units の略です。各 PE の中身は HLS で合成し、格子とつながりは RTL として組み立て、同じ設定の PE は 1 回だけ変換して使い回します。抜粋に出てくる GEMM は行列の掛け算、FFT は信号を周波数の成分に分ける計算で、U280 は Xilinx の FPGA のボードです。

:::message
**コメント**: GPU の話ではありませんが、学習のテーマの AutoParallel と同じく、人が手で書き分けていた規則性を、ツールが理解できる形に持ち上げて自動で扱う方向の話として読みました。同じ PE は 1 回だけ変換して使い回すので、変換の時間が格子の大きさではなく PE の種類の数で決まる、というのは素直でうまい考え方だと思います。面白かったのは、5 つのコーディングエージェントに同じ 8×8 の回路を作らせると、SPMW で書かせたときの課金されたトークン数の中央値が SystemVerilog の 7.51 分の 1 だった実験で、エージェントに書かせるならどんな抽象が向いているかを測る、という評価の仕方は今後増えそうです。一方で、FPGA の配置配線にかかる時間は変わらず、最大の配列では 89.3 分のうち HLS は 2.1% にすぎないとされ、小さい配列では回路の資源が元の RTL の実装より多く、FFT では DSP を多く使います。コードは Allo のリポジトリへの取り込みが進んでいる段階なので、まずはそこで例を動かしてみたいです。
:::

![コーディングエージェントに 8×8 のシストリックアレイを作らせると、SPMW で書かせたときのトークン数の中央値は HLS や SystemVerilog で書かせたときより少ないことを示す図](https://arxiv.org/html/2611.12944v1/agent_study.svg)
*出典: [SPMW](https://arxiv.org/html/2611.12944) の Figure 14*

#### 参照元からの抜粋と要約

- **課題**: シストリックアレイのような規則正しい並列のハードウェアを作る既存のツールは、各 PE を個別の逐次のプログラムやばらばらの接続として書くので、共通の処理のパターンが見えなくなり、コンパイラが同じ処理を何度も作り直します。HLS では、PE の複製、並べ方、データの供給がコードのあちこちに散らばります。
- **ねらい**: 格子の規則性をプログラミングのモデルの中心の抽象として持ち、1 つの PE の設計を 1 回だけコンパイルして多くのハードウェアの部品に使い回せるようにすること。
- **やったこと**: 著者らは、PE の振る舞いとポート、格子の形、型の付いた接続の規則を書き分けるモデルを作り、Allo の上に実装しました。各座標について、選ばれる本体、ポートのつなぎ方、座標に依存する定数の組を特殊化のキーとして計算し、キーが同じ座標どうしは 1 つの PE の HLS の設計だけを合成して、RTL を組み立てるときに複製します。並列に動く機能のシミュレータも作りました。評価は Xilinx の U280 と Vitis、Vivado で、動作の周波数の上限は 300 MHz とし、AutoSA、Allo、手で最適化した HP-FFT、Spiral などと比べました。コーディングエージェントの実験では、Opus 5、GPT-5.6 Sol、Kimi K3、GLM-5.3、DeepSeek-V4-Pro の 5 つに、同じ仕様の 8×8 の int8 のシストリックアレイを SPMW、C++ の HLS、SystemVerilog でそれぞれ作らせ、100 万トークンなどの予算の中で課金されたトークン数を比べました。
- **結果**: 著者らによると、32×32 のシストリックアレイでの 32×32×32 の GEMM のレイテンシーは、SPMW が 280 サイクル、AutoSA が 1,222 サイクルで 4.36 倍短く、同じ設計のカーネルから RTL を作るまでの時間は、8 つ並列で 56.6 秒と、Vitis HLS を使う AutoSA の 619 倍短くなりました。複素数の FP32 の 1,024 点の FFT のレイテンシーは、HP-FFT より最大 2.65 倍短くなりました。LLaMA 3.2 1B の FFN の一部を 16×16 の小さな TPU で動かすシミュレーションは、Vitis HLS の C のシミュレーションの 35.57 秒に対して 1.93 秒で 18.4 倍速くなりました。エージェントの実験では、課金されたトークン数の中央値は SPMW が 67.1K、SystemVerilog が 503.8K で 7.51 分の 1、C++ の HLS の 300.4K と比べると 4.48 分の 1 で、仕様を満たした数は SPMW と SystemVerilog が 5 つのうち 5、HLS が 3 でした。一方で、1,024 点の FFT は HP-FFT より FF を多く、Spiral より DSP を多く使い、4×4 と 8×8 の FEATHER では元の RTL の実装より LUT が 52〜53% 多くなりました。性能のシミュレーションには対応しておらず、評価は FPGA だけで、コードは [Allo](https://github.com/cornell-zhang/allo) への取り込みを進めている段階です。

## 学習の並列化

### AutoParallel: 並列化の計画の自動探索

> 参照元: [AutoParallel: Composable, PyTorch-Native Automatic Parallelism for Production Training](https://arxiv.org/html/2611.08660)

大きなモデルを学習するときは、1 枚の GPU に載らない重みや計算を何枚もの GPU に分けて持たせます。この分け方を並列化と呼び、重みを分割して持つ FSDP、1 つの行列の計算を複数の GPU で分担するテンソル並列の TP、長い入力の列を GPU ごとに分けるコンテキスト並列の CP、モデルを前半と後半のように区切って流れ作業で計算するパイプライン並列などを組み合わせて使います。どれをどう組み合わせるかは今も専門家が手で書いていて、モデルや入力の長さや GPU の台数が変わるたびに書き直しが必要です。研究の世界では以前から自動で探す方法が提案されてきましたが、PyTorch とは別の実行環境が必要だったり、出てきた計画が読みにくかったりして、実際の学習の現場には広まりませんでした。このプレプリントは、Meta Superintelligence Labs の研究者が、PyTorch の中だけで動き、結果を普通の PyTorch のプログラムとして出す自動の計画ツール AutoParallel を作ったものです。抜粋に出てくるメッシュは GPU を格子のように並べた座標のことで、縦と横の 2 方向だけでなく、FSDP 用、TP 用、CP 用のように軸を増やした 3 次元や 4 次元のメッシュも使います。DTensor はテンソルがその格子の上でどう分割されているかを覚えている PyTorch のデータの型です。MoE は専門の部品をいくつも持ち、トークンごとに使う部品を選ぶ作りのモデルで、attention は入力のどの部分どうしが関係するかを計算する部品です。TorchTitan は Meta が公開している大規模学習の見本の実装で、比較相手はその中の専門家が手で書いた並列化のレシピです。

:::message
**コメント**: 並列化の決め方を人の手作業から自動の探索へ移そうとする流れがはっきり出てきたのは興味深いと思いました。次に紹介する SS-HSDP も、手で決め打ちしていた重みの分け方を柔軟にする方向で、向きは同じだと感じます。私が一番効いていると思ったのは、結果が独自の実行環境ではなく普通の PyTorch のプログラムとして出てくる点です。中身を人が読んで直せるなら、自動で作ったものを本番に入れる心理的なハードルがかなり下がりそうです。一方で、パイプライン並列は対象外で、MoE の振り分けや CP の attention は利用者が書いた部分をそのまま固定の条件として扱う作りなので、いちばん難しいところはまだ人の手に残っています。LLaMA 3 8B を H100 128 枚の CP 併用の 4 次元メッシュで学習した構成では、1 秒あたりのトークン数が手書きのレシピより 3.6% 少なく、著者らは CP が attention の大部分を利用者の書く部分に押し込むことを主な要因と推測しつつ、他の要因からは切り分けていないと書いています。自動で探せる範囲が CP や MoE の部分まで広がるかを見ていきたいです。
:::

#### 参照元からの抜粋と要約

- **課題**: 分散学習の並列化のレシピは専門家が手で書いていて、モデル、入力の形、ハードウェアの構成が変わるたびに調整し直す必要があります。プレプリントが引く Hugging Face の調査では、LLaMA 系のモデルで 3,306 通りの並列化の設定を最大 512 枚の H100 で試したところ約半数がメモリ不足で失敗し、費用は約 46.9 万ドルかかりました。先行する自動並列化の研究は、PyTorch とは別の実行環境に頼る、出力が読みにくい、コンパイルや、途中の計算結果を捨てて必要なときに計算し直す activation checkpointing などの本番の最適化と組み合わせにくい、という理由で手書きのレシピを置き換えられていません。
- **ねらい**: PyTorch の外の実行環境を使わずに、演算ごとの分け方を学習の計算全体で同時に探し、専門家の手書きに並ぶか上回る計画を自動で見つけること。計画は人が読んで制約を足せる形で出し、MoE や CP のような動きの決まらない部分は利用者が書いたまま組み合わせられるようにすること。
- **やったこと**: 著者らは、入力から出力を求める順伝播と、出力のずれから重みの直し方をさかのぼって求める逆伝播をまとめた計算のつながりをグラフとして取り出し、演算ごとに DTensor の規則から正しく動く分け方の候補を並べ、ハードウェアに合わせて調整した所要時間の見積もりで全体の組み合わせを選ぶ探索器を作りました。選び方の問題は、グラフの辺でつながる演算どうしの関係だけでコストが決まる形に書き直し、同じ層の繰り返しをまとめる工夫と、メッシュの軸ごとに先に解いて候補を絞る工夫で、4 次元のメッシュでも解けるようにしました。結果は DTensor の重みを持つ普通の `nn.Module` として出し、TorchTitan の GraphTrainer を通して torch.compile の Inductor でコンパイルします。動きの決まらない MoE と CP の部分は、`local_map` という仕組みで利用者が入口と出口の分け方を宣言し、探索ではその境界を固定の条件として扱います。評価は H100 で最大 128 枚、最大 4 次元のメッシュで、LLaMA 3 8B と 70B、Qwen3 32B、MuseGlimmer 30B、DeepSeek-V3 の構造に基づく 16B の MoE の計 14 構成を、TorchTitan の手書きのレシピと比べました。
- **結果**: 著者らによると、14 構成のうち 9 構成で AutoParallel が TorchTitan の手書きのレシピを上回り、残る 5 構成も差は 3.6% 以内でした。最も差が大きかったのは DeepSeek-V3 の構造に基づく 16B の MoE を H100 8 枚で学習した構成で、1 秒あたりのトークン数は手書きのレシピの 4.42 万に対して 5.23 万で、18.3% 多くなりました。下回った 5 構成は、手書きのレシピと比べた 1 秒あたりのトークン数で、LLaMA 3 8B の CP 併用の 4 次元メッシュの H100 128 枚が 3.6%、MuseGlimmer 30B の 64 枚が 3.4%、Qwen3 32B の 128 枚が 2.3%、LLaMA 3 70B の 128 枚が 1.8%、MuseGlimmer 30B の 32 枚が 0.4% 少なくなりました。LLaMA 3 8B を 32 枚で学習するとき、入力の長さ 2,048 向けに作った計画を使い回す場合と比べて、長さごとに計画を作り直すと長さ 32K で 1 秒あたりのトークン数が 51.3% 多くなりました。探索にかかる時間は、LLaMA 3 8B の 3 次元メッシュで、整数計画法で最適な組み合わせを厳密に求める方法と比べて、問題の組み立てと求解の合計でおよそ 30 倍短くなりました。厳密な方法が 1 時間で問題を組み立てきれない 4 次元メッシュでも、合計 4 分弱で解けました。パイプライン並列は対象にしていません。コードは [meta-pytorch/autoparallel](https://github.com/meta-pytorch/autoparallel) で公開されています。

### SS-HSDP: 計算の並べ方と更新の単位の分離

> 参照元: [SS-HSDP: Efficient and Flexible Sharded Data Parallelism via Runtime-Update Decoupling](https://arxiv.org/html/2611.16467)

勾配は重みをどちらに動かすかを示す値で、オプティマイザは勾配を使って重みを更新する部品です。大きなモデルの学習では、重みと勾配とオプティマイザが持つ状態を GPU ごとに分割して持たせ、計算の直前だけ集めて使う方法が広く使われていて、PyTorch では FSDP2 がその実装です。ところが最近、この分け方に 2 つの別の都合が入ってきました。1 つは、重みを 8 ビットの小さな数で持ち、一定の大きさのブロックごとに倍率を共有する MXFP8 のような形式で、ブロックの途中で分割すると、倍率を共有するブロックが分断されてしまいます。もう 1 つは、要素ごとではなく行列全体を単位に更新する Muon のようなオプティマイザで、attention の中で並んで働く小さな部品であるヘッドごとの行列のように、更新の単位になる行列が丸ごとそろっていないと更新できません。計算のほうは逆に、複数の行列を 1 つにまとめて GPU の計算に都合の良い並べ方で持ちたいので、計算の都合と更新の都合が食い違います。このプレプリントは、Tsinghua University と動画生成の Shengshu Technology の研究者が、計算に使う重みと更新に使う重みを別の物として扱い、コピーを増やさずに両方の都合を満たす仕組みを作ったものです。抜粋に出てくる MFU は、GPU が理論上出せる演算のスループットのうち実際に使えた割合で、HSDP は少数の GPU の間だけで分割し、そのグループを複製して並べることで集める通信を減らす方式です。AdamW は要素ごとに更新する標準のオプティマイザで、BF16 は 16 ビットで数を表す、MXFP8 より大きい標準的な形式です。B200 は NVIDIA の GPU の機種名です。

:::message
**コメント**: これも AutoParallel と同じく、並列化を決め打ちのレシピから柔軟なものへ移していく流れの一つだと読みました。AutoParallel は演算ごとの分け方を探すほうで、SS-HSDP は計算と更新という役割の違いで分け方を切り離すほうなので、自動化と分離が両方から進んでいるのが面白いです。プレプリントの関連研究には、DeepSeek-V4 や Kimi K3 や GLM-5 が Muon をヘッド単位で使う例が挙がっていて、行列単位の更新が実験ではなく大規模な事前学習の道具になってきたことが、この仕組みが出てきた理由だと感じます。気になるのは、主な比較で使った GPU の機種が書かれていないこと、比較相手の veScale-FSDP が著者らの作り直しであること、入力が合成データであること、そしてコードがまだ公開されていないことです。公開されたら、プレプリントが報告する Muon と AdamW の差を手元で再現し、FSDP2 でヘッド単位の Muon がそもそも組めるのかもあわせて確かめたいです。
:::

![MXFP8 での学習の MFU とピークのメモリを 4 つのモデルと 32 枚から 128 枚の GPU で比べると、SS-HSDP がどの構成でも MFU が最も高いことを示す図](https://arxiv.org/html/2611.16467v1/x5.svg)
*出典: [SS-HSDP](https://arxiv.org/html/2611.16467) の Figure 6*

#### 参照元からの抜粋と要約

- **課題**: FSDP2 などの既存の仕組みは、計算が求める重みの並べ方と、オプティマイザが求める更新の単位を同じ分割の構造に結びつけています。そのため、Muon のような行列単位の更新や MXFP8 のようなブロック単位の倍率を満たそうとすると、計算の効率か更新の柔軟さのどちらかが落ちます。Megatron-FSDP は計算の並べ方を、veScale-FSDP は更新の単位を最適化しますが、両方を同時には満たしません。
- **ねらい**: 計算に使う重みと更新に使う重みを分け、追加のデータの移動なしに両方の都合を同時に満たすこと。
- **やったこと**: 著者らは、同じメモリを形の違う複数の見方で共有する data tree と、分割の段ごとにどの断片がどの GPU にあるかを記録する shard chain を作り、計算用と更新用の重みをコピーなしで両立させました。そのうえで、同じ種類の更新や並べ替えを多くの重みでまとめて実行する工夫、通信用のバッファへの詰め直しをなくす工夫、GPU の計算ユニットを使わずに専用の転送の仕組みで通信する ZeroSM を加えました。ZeroSM では、GPU の間で足し合わせる途中の値を FP32 で持つ方式と、確率的丸めを使う BF16 で持つ方式などを選べます。社内の動画モデル 2 種、MoE の Qwen3-30B-A3B、12 層に縮めた MiMo の 4 つのモデルを 32 枚から 128 枚の GPU で学習し、FSDP2、著者らが作り直した veScale-FSDP、Megatron-FSDP と比べました。
- **結果**: 著者らによると、MXFP8 での学習では試したすべての構成で SS-HSDP の MFU が最も高く、128 枚の GPU で MiMo を学習したとき、3 つの比較相手のうち最も速いものより MFU が比率で最大 21.7% 高くなりました。同じ構成でのピークのメモリは GPU 1 枚あたり 125.0 GiB で、比較相手のうち最も少ないものより 6.2% 少なくなりました。128 枚で FSDP2 と比べると、学習のスループットは最大 1.33 倍で、メモリは最大 27.3% 少なくなりました。128 枚の GPU と BF16 での学習で、同じモデルと同じ条件の AdamW と比べた Muon の追加の負担は、社内の動画モデルのうち MoE のもので 2.5% で MFU は 30.34% から 29.60% に、Qwen3-30B-A3B で 4.1% で MFU は 27.41% から 26.34% になりました。SS-HSDP 自身の BF16 での学習と比べると、MXFP8 は MiMo で 1 秒あたりの処理量を 16.3〜18.5% 増やしましたが、Qwen3-30B-A3B では差が 1% 未満でした。ZeroSM は、12 層に縮めた MiMo を、B200 を 8 枚ずつ積んだ 8 台の計 64 枚と BF16 で、GPU あたりの仕事量を変えて学習した実験で、SS-HSDP の中の計算ユニットを使う通信と比べて、仕事量が最も小さいと処理量が 33.5% 少なく、最も大きいと 8.8% 多くなりました。主な比較の節では GPU の機種は明記されておらず、入力は合成データで、コードは将来公開予定とされています。

## 強化学習の数値

### BF16 の強化学習の遅さの原因: 丸めで消える小さな更新

> 参照元: [Closing the BF16-FP16 Convergence Speed Gap in RL Post-Training with Stochastic Rounding](https://arxiv.org/html/2611.13545)

LLM の学習では、重みの元の値を 32 ビットの FP32 で持ち、計算にはそれを 16 ビットに丸めた写しを使う混合精度がふつうで、16 ビットの形式には BF16 と FP16 があります。BF16 は FP32 と同じ広い範囲の数を表せるので値があふれにくく、事前学習では FP32 と同じように収束しますが、そのぶん細かさを表す仮数が 7 ビットしかなく、FP16 の 10 ビットより粗い刻みになります。正解かどうかを自動で判定できる課題で報酬を与える強化学習の RLVR では、学習率を 10 のマイナス 6 乗のようにとても小さくすることが多く、この条件では BF16 が同じ学習率の FP16 より収束に時間がかかります。先行研究の Qi らは BF16 の RLVR で報酬が崩れることを報告し、その原因を、ロールアウトを作る推論の側と学習の側で確率の計算がずれることだと説明していました。このプレプリントは、NVIDIA の研究者が、この収束の遅さを見つけ、そのずれを取り除いても遅さが残ることを示し、もう 1 つの原因を突き止めたものです。その原因が重みの固着で、FP32 の重みへの小さな更新が、BF16 の刻みの半分に届かないうちは最も近い値への丸めで打ち消され、BF16 の写しが変わらないまま残る現象です。抜粋に出てくる確率的丸めは、上と下の候補のどちらに丸めるかを、近さに応じた確率で選ぶ丸め方で、平均すると丸める前の値に一致します。KL ダイバージェンスは 2 つの確率の分布の違いの大きさで、ここでは学習で動いたモデルが学習前の参照のモデルからどれだけ離れたかを測るのに使います。

:::message
**コメント**: 同じ週の Detent は、Qi らの手順の BF16 の GRPO で報酬が崩れるのを、推論と学習のずれをなくして防いでいました。このプレプリントは、Qi らが報告したその崩壊が著者らの環境では vLLM の TorchInductor の最適化を有効にしたときだけ起きたとしたうえで、ずれをビット単位でなくしても BF16 が遅いことを示していて、2 本を並べると原因が少なくとも 2 層あることが見えてくるのが面白いです。学習率がとても小さいと更新が丸めで消える、というのは言われてみれば当然ですが、最初の 4 回の更新の後に変わらず残った重みの割合を BF16 と FP16 で数えて、仮数のビット数を 1 つずつ増やした擬似の形式で収束が FP16 に近づくことまで確かめている、という詰め方がよいと思いました。学習のテーマの SS-HSDP にも、GPU の間の集計を BF16 の確率的丸めで行う方式が出てきたので、低精度で集計や更新をするところで確率的丸めが標準の道具になっていく気がします。ただ、丸めのカーネル自体のコストは数字がなく、複数のモデルでの主な比較は、推論と学習の確率をビット単位でそろえた状態ではなく TorchInductor を切っただけの状態で行われています。手元の RL の基盤でも、最初の数回の更新で BF16 の重みがどれだけ変わらないかは安く数えられるので、まずそこを測ってみたいです。
:::

#### 参照元からの抜粋と要約

- **課題**: BF16 の混合精度の学習は事前学習では FP32 と同じように収束しますが、学習率が 10 のマイナス 6 乗ほどの RLVR では、同じ学習率の FP16 より多くの RL のイテレーションを要します。この差は、推論の側と学習の側の確率のずれを取り除いても残るので、これまでの説明では足りません。
- **ねらい**: 収束の遅さの原因を重みの固着として突き止め、FP16 に切り替える方法や学習率を上げる方法と比べて、参照のモデルからの離れ方を増やさずに、BF16 のまま FP16 と同じ収束の速さを得る方法を示すこと。
- **やったこと**: 著者らは、verl の上の Dr. GRPO と、ロールアウトに vLLM 0.12、学習に Hugging Face Transformers を使い、vLLM の TorchInductor の最適化を切って推論と学習のずれの影響を外しました。DeepSeek-R1-Distill-Qwen-1.5B を 1,460 問の数学の問題の MATH-1460 で学習し、最初の RL のイテレーションの 4 回の更新の後に、学習前の値のまま変わらない重みの割合を BF16 と FP16 で数えました。BF16 と同じ 8 ビットの指数のまま仮数を 8、9、10 ビットに増やした擬似の形式でも学習し、仮数を増やすほど収束が FP16 に近づき、10 ビットではほぼ一致しました。そのうえで、FP32 から BF16 の写しを作る丸めを確率的丸めに替え、DeepSeek-R1-Distill-Qwen の 1.5B と Qwen3-30B-A3B を MATH-1460 で、14B を MATH-1460 と DAPO-Math-17k で学習して比べました。
- **結果**: 著者らによると、H100 64 枚で DeepSeek-R1-1.5B を学習率 10 のマイナス 6 乗で学習すると、最初の 4 回の更新の後に変わらず残った重みは BF16 で 98.84%、FP16 で 90.79% で、FP16 は BF16 の約 8 倍の重みを動かしていました。DeepSeek-R1-1.5B と Qwen3-1.7B を MATH-1460 で学習すると、vLLM 0.12〜0.17 では BF16 の報酬が崩れましたが、TorchInductor の最適化を切ると崩壊は防げ、最適化を有効にしたときと比べた 1 ステップの時間の増加は 2% 未満でした。H100 64 枚で DeepSeek-R1-1.5B を MATH-1460 で学習し、推論と学習の確率をビット単位でそろえても、FP16 は同じ学習率の BF16 より少ないイテレーションで同じ報酬に届きました。B200 64 枚で評価した 4 つの組み合わせ、つまり 1.5B と Qwen3-30B-A3B を MATH-1460 で、14B を MATH-1460 と DAPO-Math-17k で学習したすべてで、確率的丸めを使う BF16 は、ふつうの BF16 より速く報酬が上がり、FP16 とほぼ同じ報酬の伸び方をしました。DeepSeek-R1-1.5B と MATH-1460 では、学習率を 2 倍の 2×10 のマイナス 6 乗にした BF16 も、学習率 10 のマイナス 6 乗の FP16 に近い伸び方をしましたが、平均の報酬が 0.7 を超える範囲で、参照のモデルからの KL ダイバージェンスはその FP16 の約 1.5 倍になり、学習率を変えずに確率的丸めを使う BF16 は FP16 に近いままでした。一方で、同じ 1.5B と MATH-1460 の設定で、ロールアウトの側だけに確率的丸めを使うと、報酬は FP16 よりかなり低いところで止まりました。Qwen3-30B-A3B と MATH-1460 では、確率的丸めを使う BF16 の答えが FP16 とふつうの BF16 より約 25% 短いままで、理由は分かっていません。Qwen3.5-397B-A17B のエージェントの課題での予備の実験では、FP16 は損失のスケールを 1,024 にしても頻繁にあふれました。丸めのコストの数字とコードの公開先は書かれていません。

## モデルの調整と圧縮

### 前向きの計算による削る重みの探し方

> 参照元: [Efficient LLM Adaptation with Forward-Only Passes](https://arxiv.org/html/2611.10610)

学習を終えたモデルを特定の課題向けに調整することを適応と呼び、ふつうは勾配を求める逆伝播を使って重みを更新しますが、そのぶんメモリと時間がかかります。これとは別に、LASER という先行研究が、重み行列を SVD という方法で重要度の順の成分に分け、重要度の低い成分を削ると、課題によってはかえって正答率が上がることを見つけています。ただ LASER はどの重み行列をどれだけ削るかを全部試して決めるので遅く、勾配を使って当たりをつける LASER-Grad は逆伝播のぶんメモリを食います。このプレプリントは、Lund University の研究者が、Google DeepMind の研究者の助言を受けて、逆伝播を使わずに前向きの計算だけで削る重み行列を探す方法を提案したものです。前向きの計算は入力から出力を求めるふだんの推論の計算のことで、逆伝播は出力のずれから重みの直し方をさかのぼって求める計算のことです。抜粋に出てくる角度の集中度は、ある成分が作る途中の値のベクトルがトークンどうしでどれだけ同じ向きを向いているかを、向きの近さを表すコサイン類似度の平均で測ったものです。

:::message
**コメント**: 今回の中ではインフラから一番遠い話ですが、サービングで毎日大量に回っている前向きの計算をそのままモデルの調整に使えないか、という問いの立て方が気になって入れました。逆伝播が要らないので、推論用の GPU や推論エンジンのままで調整の候補を探せるようになれば、学習用の環境を別に用意する手間が減りそうです。一方で、実験は課題ごとの検証データで候補を選んで正答率を測るもので、実際のサービングのリクエストを使ったわけではありません。GPT-J-6B では、8 つのデータセットのうち Bios Profession で正答率が LASER より 3.0 ポイント、LASER-Grad より 1.4 ポイント低く、WikidataQA でも LASER-Grad より 1.2 ポイント低く、最大 57B とされるモデルも一度に使う重みは 14B の MoE です。コードの公開先もプレプリントには書かれていないので、まずは削った後のモデルが推論エンジンでスループットや正答率をどう変えるかを見てみたいです。
:::

![重み行列を SVD で成分に分け、前向きの計算で各成分の角度の集中度を測り、散らばりを生む重み行列だけを削る手順を示す図](https://arxiv.org/html/2611.10610v1/main_camera.png)
*出典: [Efficient LLM Adaptation with Forward-Only Passes](https://arxiv.org/html/2611.10610) の Figure 1*

#### 参照元からの抜粋と要約

- **課題**: LASER が示した、重み行列の重要度の低い成分を削ると正答率が上がる現象を使って課題ごとに適応したいのですが、LASER の全部を試す探索は時間がかかり、勾配を使う LASER-Grad は逆伝播のぶんメモリと時間がかかります。
- **ねらい**: 逆伝播を使わず、前向きの計算だけで、どの重み行列を削るべきかを効率よく見つけること。
- **やったこと**: 著者らは、重み行列の出力が SVD の成分ごとの出力の和に書けることを使い、成分ごとの途中の値について、トークンどうしの向きの近さの平均を角度の集中度として測りました。重要度の低いほうの成分のうち、全体より向きを散らしている成分を多く持つ重み行列を候補として点数を付け、点数の高い候補だけを検証データで実際に削って、残す成分の割合を決めました。評価は NVIDIA A100 40GB 1 枚で、GPT-J-6B と RoBERTa を中心に、CounterFact や HotPotQA などの 8 つのデータセットで LASER と LASER-Grad と比べました。
- **結果**: 著者らによると、GPT-J-6B では、探索にかかる時間が平均で LASER の 36.7 分の 1、LASER-Grad の 18.4 分の 1 で、使うメモリは平均 11.5 GB と、LASER-Grad の 22.0 GB の約半分でした。正答率は 8 つのうち 4 つのデータセットで最も高くなりましたが、Bios Profession では 79.1% で LASER の 82.1% と LASER-Grad の 80.5% より低く、WikidataQA でも LASER-Grad よりわずかに低くなりました。RoBERTa では探索にかかる時間が平均で LASER の 26.6 分の 1 でした。LLaMA2-7B や Mistral-7B から、一度に使う重みが 14B で全体が 57B の MoE の Qwen2-57B-A14B-Instruct までの 7 つのモデルでも、Epistemic Reasoning で LASER と同等以上の正答率を、平均で LASER の 15.6 分の 1 の探索の時間で得ました。プレプリントにはコードを補足資料に含むとだけあり、公開先は書かれていません。

### 大きいモデルほど補えない圧縮の傷

> 参照元: [When Bigger Becomes Brittle: Why Compression Hurts More as Language Models Scale](https://arxiv.org/html/2611.07891)

量子化や枝刈りでモデルを軽くしたときの良し悪しは、ふつうベンチマークの点数で測ります。ところが点数に表れるのは出力に残った悪化だけで、モデルの中でどれだけ壊れ、残りの部分がそれをどれだけ補ったかは分かりません。補いが大きければ、中では大きく壊れていても点数は下がらないので、点数だけでは、壊れていないのか、壊れたが補えたのかを区別できません。このプレプリントは、IIIT-Delhi を中心とする研究者が、文章の中から答えの名前を探してくる役目の注意のヘッドを止めたときに、悪化を補いと出力に残った分に分けて測り、その割合がモデルの大きさでどう変わるかを調べたものです。注意のヘッドは attention の中で並んで働く小さな部品で、ここでの量子化は重みを少ないビット数の数で表すこと、枝刈りは部品の一部を取り除くことです。抜粋に出てくる logit はモデルが各単語に付ける点数で、ここでは正解の名前と、文中で繰り返されて紛らわしい名前の点数の差を悪化の物差しに使います。Pythia は同じデータを同じ順に同じ量だけ学習させた大きさ違いのモデルの一式で、大きさの違いだけを比べるのに使われます。

:::message
**コメント**: 同じテーマの前のプレプリントが、重みを削ると正答率が上がる場合を探していたのに対して、こちらは削ったときに大きいモデルほど傷が素通りする、という逆向きの話で、並べて読むと面白いです。小さいモデルではほぼ無害だった圧縮が、大きいモデルでは高くつくことがありうる、という著者らの示唆を、点数ではなく中で何が起きているかの測定から導いている点が気になりました。ただ、調べた能力はひな形の文で名前を当てる 1 種類だけで、量子化も 32 ビットの浮動小数点の推論の中で重みだけを 4 ビット相当に丸めた模擬で、実際の量子化のカーネルを使ったものではありません。著者らのコードの公開先も見当たりません。それでも、点数が下がらないことと中が壊れていないことは別だ、という見方は、圧縮した推論の構成を評価するときの測り方として覚えておきたいと思いました。
:::

![Pythia-410M は検索のヘッドを止めた傷のほとんどを、抑えのゆるみと残りの部品の補いと正規化の変化の合計で取り戻すが、Pythia-12B はごく一部しか取り戻せず、傷が出力に残ることを比べた図](https://arxiv.org/html/2611.07891v1/fig_repair_bands_pythia_410m_12b.svg)
*出典: [When Bigger Becomes Brittle](https://arxiv.org/html/2611.07891) の Figure 3*

#### 参照元からの抜粋と要約

- **課題**: 量子化や枝刈りの効果はベンチマークの点数、つまり出力に残った悪化だけで報告され、モデルの中でどれだけ傷つき、どれだけ補われたかが分かりません。この傷と補いのつり合いがモデルの大きさで変わるかも分かっていませんでした。
- **ねらい**: 文章の中から答えを探す役目のヘッドへの傷を例に、出力に残った悪化を補いの分と厳密に分け、その分け方が Pythia の 410M から 12B でどう変わるかを明らかにすること。
- **やったこと**: 著者らは、文中の 2 人の名前のうち繰り返されていないほうを答えさせる課題で、答えの名前に注意を向けて点数を上げるヘッドを検索のヘッドとして見つけ、その出力を 0 にしました。正解の名前と紛らわしい名前の点数の差について、各部品が直接足している量を使い、出力に残った悪化が、もとの傷から、検索のヘッドの後ろで同じ答えの名前の点数を下げるコピー抑制のヘッドの抑えがゆるんだ分、残りの部品が補った分、最後の正規化で変わった分を引いたものに一致する恒等式を組みました。Pythia の 410M、1B、1.4B、2.8B、6.9B、12B の 6 つを主に比べ、OPT の 4 つの大きさでも確かめました。さらに、検索のヘッドの重みを出力のチャンネルごとに 4 ビットの整数に丸めて戻す模擬の量子化と、ヘッドの半分を止める枝刈りでも同じ分け方をしました。計算はすべて 32 ビットの浮動小数点で行いました。
- **結果**: 著者らによると、同じ 0.5 logit の傷を与えたとき、Pythia-410M は約 0.55 logit を補って点数の差がもとより約 0.05 logit 高くなったのに対し、Pythia-12B では 0.5 logit のうち約 0.38 logit が出力に残りました。約 0.8 logit の傷をそろえて比べると、コピー抑制のヘッドの抑えがゆるんだ分を引いた後に残る傷のうち、残りの attention の部品が補った割合は、Pythia-410M で約 80%、Pythia-12B で約 9% でした。ただし Pythia-12B でも、補いに加わるヘッドの動きを止めると悪化は約 0.30 logit 増えました。4 ビットの模擬の量子化でも、出力に残った悪化をもとの傷で割った比は、Pythia で 410M の 0.55 から 12B の 0.91 に、OPT で 125M の 0.41 から 6.7B の 0.98 に上がりました。枝刈りでは、上位の検索のヘッドを多く含む止め方では大きいモデルほど補いが減りましたが、ランダムな止め方では大きさの順にきれいには並びませんでした。著者らは、調べたのはひな形の文での名前の検索だけで、コピー抑制のヘッドは量子化と枝刈りの対象から外したので、実際の量子化のカーネルがそのヘッドも傷つける場合は結果が変わりうるとしています。著者らのコードの公開先は書かれていません。

## ベクトル検索とクラスタリング

### GINGER: 粗くも細かくも使う 1 つの符号

> 参照元: [GINGER: Spicing Up Graph-Based Vector Search](https://arxiv.org/html/2611.08306)

RAG や推薦では、文章や画像を意味の近さが距離に表れる数のベクトルに変えた埋め込みを大量に持ち、問い合わせに近いベクトルを探します。全部と比べると遅いので、多少の取りこぼしを許して速く探す近似最近傍探索が使われ、その代表が、近いベクトルどうしを辺でつないだグラフをたどって探すやり方です。速く探すには、グラフをたどる間はベクトルを少ないビット数に丸めた粗い符号で比べ、最後に残った候補だけを細かい表現で並べ直します。これまでのライブラリは粗い符号と細かい表現を別々に持つか元の浮動小数点のベクトルを持ち続けるので、メモリを多く使い、グラフの辺の一覧もメモリを圧迫していました。このプレプリントは、Google Research の研究者が、1 つの符号の上位のビットを粗い比較に、残りのビットまで含めた全体を並べ直しに使う形にし、グラフも損失なく圧縮したライブラリ Ginger を作ったものです。抜粋に出てくる再現率は、本当に近い上位 10 件のうち何件を見つけられたかの割合で、QPS は 1 秒あたりに処理できる問い合わせの数です。

:::message
**コメント**: 普段の推論や学習の話とは離れますが、RAG の裏側で毎回動く部分の話です。GPU を使わず CPU の SIMD だけで、再現率 95% での QPS が 14 のデータセットのうち 13 で、データセットごとの最速の既存のライブラリの平均 1.8 倍になった点が目を引きました。上位の 4 ビットだけ読めばグラフをたどれて、続きのビットまで読めば並べ直しに使える、という符号の作り方は、別々の表現を 2 つ持つより素直で、メモリの量と読み出す量を同時に減らせるのがうまいと思います。比べ方も、データセットごとの最速の相手との比較と、1 つのライブラリに固定した比較を分けて書いていて、どちらで見ても速いと言えるようにしているのが誠実だと感じました。一方で、8 ビットの整数の BigANN では SVS のほうが 4% 速く、小さいデータセットでは索引の構築で ParlayANN に、GloVe では Faiss に負けています。コードは公開されているので、手元の RAG の埋め込みの次元と件数で、いま使っている Faiss などとメモリと QPS を比べてみたいです。
:::

![14 のデータセットの幾何平均で、Ginger が再現率 95% でのクエリのスループットが既存のライブラリより高く、MS-MARCO での索引の構築も速いことを示す図](https://arxiv.org/html/2611.08306v1/teaser.svg)
*出典: [GINGER](https://arxiv.org/html/2611.08306) の Figure 1*

#### 参照元からの抜粋と要約

- **課題**: グラフをたどる近似最近傍探索の既存のライブラリは、たどるための軽い符号と並べ直しのための細かい符号を別々に持つか、元の浮動小数点のベクトルを持ち続けるので、メモリを無駄に使います。グラフの辺の一覧もメモリを圧迫します。
- **ねらい**: 1 本の量子化の符号で粗い比較と細かい並べ直しを両立させ、グラフを損失なく圧縮して、問い合わせのスループット、メモリ、索引の構築時間の 3 つを同時に良くすること。
- **やったこと**: 著者らは、索引を作る PiPNN と量子化の TurboQuant という先行研究を土台に、TurboQuant の 4 ビットの各区間をさらに細かく分けて 10 ビットや 12 ビットの符号にし、上位の 4 ビットをグラフをたどる比較に、全体を並べ直しに使う Nested TurboQuant を作りました。グラフは頂点を並べ替えたうえで、辺の一覧をビット単位で詰める SIMD 向けの無損失圧縮の AdaptiveGap で圧縮しました。評価は Intel Xeon 6985P-C の 72 コアを 2 つ載せた CPU のマシンで、GPU は使わず、10 億件の BigANN や 768 次元から 4,096 次元の埋め込みを含む 14 のデータセットで、DiskANN、ParlayANN、SVS、Hnswlib、SymphonyQG、Faiss、ScaNN の 7 つのライブラリと比べました。
- **結果**: 著者らによると、再現率 95% での QPS は、14 のデータセットのうち 13 で、データセットごとに最も速い相手と比べて平均 1.8 倍でした。比べる相手を 1 つのライブラリに固定し、QPS と再現率の曲線の下の面積の幾何平均で比べると、どの相手に対しても少なくとも 2.3 倍で、ParlayANN に対して 2.35 倍、Faiss に対して 11.7 倍でした。高次元のデータセットでは、12 ビットの符号を使う Ginger は、メモリを最も節約する SVS と比べて再現率 95% での QPS が幾何平均で 2.9 倍で、使うメモリは SVS のほうが幾何平均で 19.8% 少なくなりました。8 ビットの符号にすると、SVS より少ないメモリで再現率 95% での QPS が平均 2.6 倍でした。Nested TurboQuant は浮動小数点に近い精度を 2.6 分の 1 のメモリで実現し、10 億件の 5 つのデータセットでの索引の構築は平均 35 分と、最も速い Faiss の平均 69 分の約 2 分の 1 でした。一方で、8 ビットの整数の BigANN では再現率 90% と 95% のどちらでも SVS が 4% 速く、とても小さいデータセットでは索引の構築で ParlayANN が最大 5.7 倍速く、GloVe では Faiss が 2.1 倍速くなりました。コードは [google/ginger](https://github.com/google/ginger) で公開されています。

### e-means: 指数移動平均による Lloyd の 10 分の 1 のエポックでの k-means の解き方

> 参照元: [e-means: outperforming k-means (in one-tenth the epochs)](https://arxiv.org/html/2611.09501)

k-means は、データの点を k 個のまとまりであるクラスタに分け、各点と、その点が属するクラスタの中心との距離の二乗の平均が小さくなるように中心を決める方法で、ベクトル検索の索引づくり、ベクトルの量子化、学習データの選別などに広く使われています。標準の解き方である Lloyd のアルゴリズムは、全部の点を最も近い中心に割り当て直してから、各中心を割り当てられた点の平均に置き直す、という 1 周を何十回も繰り返します。この 1 周がデータ全体を 1 回なめるエポックにあたり、点が 100 億件のような規模ではこの繰り返しが重くなります。データの一部であるミニバッチだけで中心を少しずつ動かす方法も昔からありますが、収束先の誤差が高く、バッチの大きさや動かす幅をデータごとに手で決める必要がありました。このプレプリントは、FAIR at Meta の研究者が、画像の生成モデルの VQ-VAE で使われてきた指数移動平均による中心の更新を k-means に持ち込み、その設定を式で決められるようにした e-means を提案したものです。指数移動平均は、新しい値を一定の割合で混ぜ、古い値ほど小さい重みで残していく平均のことで、その混ぜる割合を決めるのが減衰率です。抜粋に出てくる DINO10B は、画像を DINOv3 というモデルに通して作った 1,024 次元のベクトル 100 億件のデータセットです。

:::message
**コメント**: k-means はあまりに当たり前の道具なので、まだこんなに速くなる余地があったことにまず驚きました。深層学習で当たり前になったミニバッチ、中心を動かす幅をコサインで減らしていくやり方、スケーリング則でハイパーパラメータを決めるやり方を、そのまま古典的なアルゴリズムに持ち込んでいて、学習の側で育った道具が古い問題に戻ってくる流れが面白いです。プレプリントも IVF というクラスタに分けて探す検索の索引で評価していて、そうした索引は中で k-means を回して作るので、k-means の GPU の計算量が Faiss-GPU や Flash-KMeans と比べて約 10 分の 1 になるなら、索引の作り直しの頻度も変えられそうです。ただ、スケーリング則は DEEP という比較的高次元のデータセットで当てはめたもので、低次元で小さいデータには最適ではないと著者らも書いており、合成データの 140 の実験のうち 10 では、学習に使わない点での誤差が Lloyd に負けています。コードは Faiss の中に入っているので、手元の埋め込みで、いま使っている Faiss の k-means と時間と誤差を比べてみたいです。
:::

#### 参照元からの抜粋と要約

- **課題**: Lloyd の k-means はクラスタの質は高いのですが、エポックごとにデータ全体を走査するので重くなります。MacQueen や Sculley のミニバッチの k-means は速いのですが、収束先の誤差が高く、バッチの大きさと中心を動かす幅を問題ごとに手で決める必要があります。点がまったく割り当てられない死んだクラスタへの対処もほとんど扱われていません。
- **ねらい**: 指数移動平均による中心の更新を k-means の誤差の最小化に合わせて作り直し、バッチの大きさと減衰率を探索なしで決める式を与えて、Lloyd より少ないエポックと短い時間で同じかそれより小さい誤差に届くこと。
- **やったこと**: 著者らは、クラスタごとに点の数と点の和を指数移動平均で更新し、中心をその比として読み出す更新に、動かす幅をコサインで減らしていく工夫、点の少ないクラスタを点の多いクラスタの中心を 2 つに割って復活させる工夫、最後のエポックの割り当てで中心を平均し直す仕上げを加えました。バッチの大きさと最初に動かす幅を、点の数、クラスタの数、エポックの予算のべき乗の式で表し、DEEP のデータセットでの 75,000 回の実行に当てはめました。最も近い中心を探す計算は NVIDIA の CuTe DSL で GPU のカーネルとして書き、クラスタが非常に多い場合は中心の側に IVF の索引を作って近い中心だけを比べるようにしました。比較相手は GPU の Flash-KMeans、Faiss-GPU、cuML と、CPU の Faiss と SuperKMeans です。
- **結果**: 著者らによると、DEEP、DINO10B、SPACEV、SimSearchNet++ の 4 つのデータセットで、100 万件から 1 億件は H100 1 枚、10 億件は H100 8 枚を使い、Flash-KMeans の 25 エポック目の誤差に届くまでに e-means が要したのは 1.4〜2.6 エポックで、実時間では 9.5〜45.5 倍速くなりました。DINO10B の 100 億件全部を約 1,670 万クラスタに分ける実験では、Lloyd は 25 エポックで H100 512 枚、6,784 GPU 時間を使ったのに対し、e-means は 2.5 エポック、H100 256 枚、779 GPU 時間で Lloyd より 0.014% 小さい誤差に届きました。IVF の索引で近い中心だけを比べると、4 エポックで Lloyd より 0.212% 小さい誤差に、H100 8 枚の 43.8 GPU 時間で届きました。割り当ての距離の計算を FP8 や INT8 にしても、誤差は BF16 のときとの差が 0.13% 以内でした。著者らは、スケーリング則は比較的高次元のデータで当てはめたもので、低次元で小さいデータには最適ではないとしています。一方で、合成データの 140 の実験のうち 10 では、学習に使わない点での誤差が Lloyd の 25 エポックより大きく、高次元で小さいデータでは終盤に過学習しました。コードは [Faiss の contrib/e_means](https://github.com/facebookresearch/faiss/tree/main/contrib/e_means) で公開されています。
