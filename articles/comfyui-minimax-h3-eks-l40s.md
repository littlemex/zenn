## はじめに

動画と音声を同時に生成するオープンウェイトモデル MiniMax-H3 を、GPU を 1 枚だけ積んだノードで動かして実際に動画を 1 本生成するところまでを記録します。生成を担う拡散トランスフォーマー本体は 33B パラメータあります。33B というサイズと「動画」という重い出力から、GPU 1 枚ではとても乗らないように思えます。ところが Comfy-Org 配布版の量子化と ComfyUI の動的なモデル管理を使うと、公称 48GB VRAM の L40S 1 枚で最後まで完走できました。VRAM を超えたときのために CPU オフロードも備えていますが、今回は発動しませんでした。

題材は AWS の GPU インスタンス g6e です。g6e.2xlarge は L40S を 1 枚積み、VRAM はカタログ値 48GB、`nvidia-smi` 上の実効容量が約 45GiB、ホスト RAM が 64GB あります。以降、GPU の空き枠を語るときはこの実効約 45GiB を基準にします。この記事はアプリ側、つまりモデルと ComfyUI の話に絞ります。動かす基盤には Amazon EKS を使っていますが、クラスタの構成や再現手順は踏み込まず、必要なら [littlemex/distributed-ai](https://github.com/littlemex/distributed-ai) の README を参照してください。

実際にこの構成で生成した動画が次の GIF です。アニメ調のモンスターバトルを、映像と効果音・BGM ごと 1 パスで生成しています。

![MiniMax-H3 で生成したモンスターバトルの動画](/images/comfyui-minimax-h3-eks-l40s/battle.gif)

GIF のため無音ですが、元の mp4 には生成された効果音と BGM が同期して入っています。音声付きの元動画は [リポジトリのサンプル](https://github.com/littlemex/distributed-ai/tree/main/2026-08-comfyui-minimax-h3-g6e) から確認できます。

## MiniMax-H3 とは何か

MiniMax-H3 は、テキスト・画像・動画・音声を統合的に扱う汎用生成モデルです。最大の特徴は、動画とネイティブなステレオ音声を 1 回の forward パスで同時に生成する点にあります。効果音や音楽を後付けで合成するのではなく、映像と音を一体で生成するため、動きと音のタイミングが自然に合います。公称スペックとしては 24fps で最長 15 秒程度、解像度は 2K まで対応します。ただし本記事で実際に検証したのは 864x480 の約 5 秒という低解像度・短尺の 1 本だけです。VRAM の収支は解像度と長さに強く依存するため、後述する「48GB 1 枚で動く」という結論はこの検証範囲での話で、2K や 15 秒でも同じ枠に収まることを意味しません。「33B」は [MiniMaxAI/MiniMax-H3](https://huggingface.co/MiniMaxAI/MiniMax-H3) の公称パラメータ数で、生成を担う拡散トランスフォーマー本体を指します。この本体とは別に、プロンプトの理解には 32B のテキストエンコーダー Qwen3-VL-32B が使われます。ここで正直に断っておくと、今回動かすのは 33B のフル精度モデルそのものではなく、Comfy-Org が剪定と混合精度量子化を施した配布版です。拡散トランスフォーマーのファイルは int8 主体の混合精度で約 19.5GiB、パラメータ換算では 20B 前後まで軽量化されています。つまり「公称 33B のモデルを、実行時には 20B 相当まで絞った版で動かす」という話で、フル精度の 33B を 1 枚に載せたわけではありません。この軽量化こそが 48GB に収まる前提になっています。

ComfyUI は、このモデルをコア機能としてネイティブにサポートしています。ここが実運用の観点で重要でした。新しい動画モデルは、公式対応が入る前は第三者製のラッパーノードに依存しがちで、そうしたノードはバージョン追従が不安定です。MiniMax-H3 の場合は Comfy-Org が事前量子化済みの重みを配布しており、ComfyUI 本体がそれを直接ロードできます。第三者ノードは不要でした。

必要な重みは 4 ファイルで、合計は約 40GB です。内訳は次のとおりです。

- 拡散トランスフォーマー本体（int8 主体の混合精度、剪定済み）: 約 19.5GiB
- テキストエンコーダー（Qwen3-VL-32B、nvfp4 量子化）: 約 14.6GiB
- 動画 VAE（fp16）: 約 4.9GiB
- 音声 VAE（fp32）: 約 0.6GiB

## なぜ 48GB の GPU 1 枚で動くのか

量子化前の素朴な見積もりでは、GPU 1 枚は苦しく見えます。事実、Hugging Face のモデルカードが挙げる公式のデプロイ例は、SGLang と Ulysses 並列で GPU 4 枚を使う構成です。

鍵は 2 つあります。1 つは Comfy-Org 配布版の量子化で、拡散トランスフォーマー本体を int8、テキストエンコーダーを nvfp4 に落とすことで、両者を合わせても VRAM 実効約 45GiB の枠に収まるサイズまで小さくなっています。もう 1 つは ComfyUI の動的なモデル管理です。ComfyUI は必要になったモデルを VRAM に載せ、空きがある限りは載せたままにし、足りなくなったときに初めて CPU 側へ退避します。今回は量子化のおかげで枠に収まったので、退避を発動させずに実行できました。VRAM を超えた場合は CPU オフロードが安全弁として働き、退避先としてホスト RAM が効きます。ホスト RAM に余裕があるほどこの安全弁は強くなり、g6e.2xlarge の 64GB でも足りますが、より大きい 4xlarge の 128GB ならさらに安心です。

実機のログでこの挙動がはっきり見えました。まずテキストエンコーダーが約 15GiB を VRAM にステージしてプロンプトを埋め込みに変換し、続いて拡散トランスフォーマー本体が約 20GiB をステージしてサンプリングに入ります。サンプリング中の GPU 使用率は 100%、VRAM 使用量はピークで約 40.5GiB でした。この約 40.5GiB はテキストエンコーダーと本体の両方が VRAM に載ったままの合算に、活性値や latent 分が加わった値で、両モデルのステージ量 35GiB との差はそこから来ています。実効約 45GiB の枠に対して 約 1 割の余裕を残して収まりました。当初は VRAM の収支が最大の懸念でしたが、量子化済みモデルが枠に収まったため、オフロードの安全弁に頼らずに完走できました。

## 実機で踏んだ落とし穴

設計や事前調査をどれだけ重ねても、動かして初めて分かることがあります。今回もアプリ側で 2 つ踏みました。

1 つ目は PyTorch のバージョンです。最初のビルドでは PyTorch を 2.6.0 に固定していました。これで ComfyUI をデプロイすると、Pod が起動時に CrashLoopBackOff で落ち続けました。ログを追うと、ComfyUI v0.31.0 のネイティブな量子化演算が、カスタム演算の型注釈に `list[int]` という新しい書き方を使っており、これを PyTorch 2.6 以前の型推論が受け付けずに import 時点で例外を投げていました。ComfyUI は要件ファイルで PyTorch のバージョンを固定しておらず、十分新しいものを前提にしていたのです。修正は PyTorch を 2.8.0 に上げることでした。ただし 2.8.0 は CUDA 12.6 以降のホイールしかないため、ベースイメージも CUDA 12.6.3 に上げました。バージョンを固定していたにもかかわらず起動しなかったわけで、「固定すること」と「正しい値に固定すること」は別だという教訓でした。

2 つ目は、公式のワークフローテンプレートをそのままでは HTTP API に投げられない点です。ComfyUI の公式テンプレートは Web UI 形式で、内部にサブグラフや独自のカスタムノードを含みます。一方で `/prompt` エンドポイントが受け付けるのは、ノード ID をキーにしたフラットな API 形式です。ここで当てずっぽうにグラフを手書きすると、ノードの入力名が少し違うだけで壊れます。そこで、稼働中の ComfyUI に `/object_info` を問い合わせて全ノードの入力名を確認し、コア機能のノードだけで等価なグラフを組み直しました。解像度と長さは独自ノードに頼らず数値で直接指定しています。

## 生成してみる

ブラウザで開いた ComfyUI のワークフローが次の画面です。中央の「Image to Video (MiniMax H3)」ノードに、取得した重みのファイル名（`unet_name` や `clip_name`）や生成の長さ（`duration`）がそのまま並んでいます。

![ComfyUI 上の MiniMax-H3 ワークフロー](/images/comfyui-minimax-h3-eks-l40s/comfyui-workflow.png)

プロンプトのコツは、映像の描写と音声の指定を 1 つのブロックにまとめて書くことです。音声を同時に生成するモデルなので、最後に「Audio:」として音楽や効果音を書き足すと効きます。冒頭の GIF は、版権のあるキャラクター名を避けつつ、電気タイプ風の小動物と炎タイプ風のトカゲが岩場のアリーナで戦うアニメ調のプロンプトで生成したものです。効果音は雷のクラックルと炎のうなり、BGM は勢いのあるオーケストラ、と指定しました。出力は 864x480 の H.264 映像に AAC の音声が付いた 5.17 秒のクリップで、指定どおりバトル BGM と効果音が乗っていました。

生成にかかった時間は、モデルがノードに常駐している状態で約 4 分でした。初回はモデルのロードを含むため 10 分半かかりましたが、2 本目以降は速くなります。サンプリングは 20 ステップで、1 ステップあたり約 11.5 秒でした。

## まとめ

33B の動画生成モデル MiniMax-H3 を、GPU 1 枚で動かして動画を生成できました。要点を振り返ります。

VRAM の収支は、Comfy-Org 配布版の量子化と ComfyUI の動的なモデル管理のおかげで問題になりませんでした。量子化でテキストエンコーダーと拡散トランスフォーマー本体を合わせても枠に収まるため、両方を VRAM に載せたままでもピークは約 40.5GiB にとどまり、実効約 45GiB の L40S 1 枚で完走します。枠を超えたときの安全弁として CPU オフロードが用意され、その退避先としてホスト RAM が効きます。

そして実機で動かして初めて、PyTorch のバージョン不足による起動失敗と、ワークフローの API 形式変換という 2 つの落とし穴に気づけました。設計とレビューをどれだけ重ねても、最後は動かして確かめるのが確実です。動かす基盤の EKS 構成や、コード一式は [littlemex/distributed-ai](https://github.com/littlemex/distributed-ai) に置いてあるので、同じ構成を再現したい方は参照してください。
