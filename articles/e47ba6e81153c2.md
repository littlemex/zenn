# はじめに

この記事は、Slurm と Kubernetes のどちらかが優れていると主張するためのものではありません。両者の違いをできるだけ公平に並べたうえで、Kubernetes の上でジョブのスケジューリングがどう組み立てられているのかを整理することが目的です。

:::message
筆者は Slurm も Kubernetes もどっちも好きだにゃーん。(=´ω`;=)
:::

Kubernetes に、4 つの Pod(コンテナを動かす最小単位)からなる分散学習ジョブを投げたとします。2 つは動いたのに、残り 2 つはノード(Pod を動かすマシン)の空きが無く、いつまでも待ち続けることがあります。クラスタが壊れているわけではありません。

Slurm(HPC で広く使われるジョブスケジューラ)では、この状態はふつう起こりません。Slurm にできて、素の Kubernetes(vanilla Kubernetes、追加の仕組みを入れていない状態)にできないことを、まず 5 つ並べます。

![Slurm can start a multi-node job as one unit, hold it in a queue under a limit, backfill without delaying a big job, suspend and resume it, and use fair-share from past usage; vanilla Kubernetes binds per Pod, rejects with ResourceQuota, has no planned start, deletes Pods on suspend, and uses a fixed PriorityClass](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/e47ba6e81153c2/zenn/articles/e47ba6e81153c2/intro-slurm-vs-vanilla.png)
*5 つとも、ジョブ全体(または利用者のアカウント)を単位にした判断*

1 行目は、複数ノードのジョブを 1 つの単位として始めることです。Slurm は要求したノードと GPU がすべてそろってから、ジョブを 1 つの割り当て(allocation)として始めます([Slurm のクイックスタート](https://slurm.schedmd.com/quickstart.html))。素の Kubernetes は Pod を 1 つずつノードに置くので、一部だけ動いて残りが待つ状態が起こります。

2 行目は、上限を超えたジョブを待ち行列で待たせることです。Slurm はグループ単位の上限(GrpTRES など)を超えたジョブを、受け付けたうえで PENDING のまま待たせます([Slurm のリソース上限](https://slurm.schedmd.com/resource_limits.html))。Kubernetes の ResourceQuota は、上限を超える Pod の作成を断るだけで、順番を持った待ち行列にはなりません([ResourceQuota](https://kubernetes.io/docs/concepts/policy/resource-quotas/))。

3 行目は、大きなジョブを遅らせずに小さなジョブを先に流すこと(backfill)です。Slurm は大きなジョブの開始予定時刻を計算し、それを動かさない範囲でだけ小さなジョブを先に始めます([Slurm のスケジューリング設定](https://slurm.schedmd.com/sched_config.html))。素の Kubernetes には、ジョブ全体の開始予定時刻という考え方がありません。

4 行目は、動いているジョブを止めて、作り直さずに再開することです。Slurm の suspend はプロセスを止め、resume で同じプロセスを続けます([Slurm の preemption](https://slurm.schedmd.com/preempt.html))。Kubernetes の Job を suspend すると、動いている Pod は削除されます([Job の suspend](https://kubernetes.io/docs/concepts/workloads/controllers/job/#suspending-a-job))。

5 行目は、過去の使用量から優先度を決めることです。Slurm は設定すれば、会計記録から計算した公平配分(fair-share)を優先度に入れます([Multifactor Priority](https://slurm.schedmd.com/priority_multifactor.html))。Kubernetes の PriorityClass は、Pod ごとに決まった値を与えるだけです([Pod の優先度](https://kubernetes.io/docs/concepts/scheduling-eviction/pod-priority-preemption/))。

Slurm 側はどれも設定で有効にする機能ですが、5 つに共通するのは、判断の単位が Pod ではなくジョブ全体だという点です。この記事では、Kubernetes の上でこの「ジョブ単位の判断」を後から足す Kueue・Volcano・YuniKorn・KAI-Scheduler が、それぞれどこを受け持ち、内部がどうなっているのかを整理します。主張は公式ドキュメントで確認したものに限り、その場で出典を示します。Amazon EKS Distributed AI ワークショップの本に、ここで扱う Kueue を実際に使う章を追加したので、合わせて読むと手を動かして確かめられます。

![Kubernetes runs as separate steps: a Job object is created, Kueue holds it until admitted, the controller creates Pods, a scheduler picked per Pod places them, and kubelet runs them, while Slurm makes queueing and allocation one decision in slurmctld](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/e47ba6e81153c2/zenn/articles/e47ba6e81153c2/landscape.png)
*Kueue は 2 番目の段、Volcano・YuniKorn・KAI は 4 番目の段を受け持つ*

| 名前 | 受け持ち | 置き場所 |
|---|---|---|
| kube-scheduler | Pod を 1 つずつノードに置く | Kubernetes の素の機能 |
| Kueue | ジョブ単位で、資源の枠(quota)に収まるかを決める | kube-scheduler の手前 |
| Volcano / YuniKorn | 対象に指定した Pod の配置を、kube-scheduler の代わりに担当する | kube-scheduler と並ぶ選択肢 |

| Slurm | ノードの確保そのものがジョブの単位になっている | Kubernetes とは別の世界 |

この表の並びのまま、次の節から 1 つずつ、仕組みと内部の構成を見ていきます。

## そもそも何を決める層なのか

分散ジョブを動かす仕組みは、2 つの違う問いに答えています。1 つは「このジョブを今動かしてよいか」、もう 1 つは「どの Pod をどのノードに置くか」です。**この 2 つは別の問いで、同じ機構が両方を受け持つとは限りません**。この区別を知らないと、Kueue と Volcano を同じ種類の仕組みだと誤解してしまいます。

## gang scheduling とは何か

同期型の分散学習では、決まった数の worker がそろわないと学習が進みません。必要な数に足りないまま一部だけ動かしても、残りを待つ間、その分の資源が占有されるだけです。必要な数のタスクがそろうときだけ始め、そろわなければ始めないという考え方を、gang scheduling と呼びます。

## 素の Kubernetes: kube-scheduler の内部

![Of a 4-Pod job on a cluster with 2 GPUs, worker-0 and worker-1 are bound and wait at rendezvous while worker-2 and worker-3 stay Pending](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/e47ba6e81153c2/zenn/articles/e47ba6e81153c2/kube-scheduler-partial.png)
*kube-scheduler は、4 つ全部が置けるかを確かめずに 1 つ目を置く*

標準の kube-scheduler は、Pod を 1 つずつ見て置き場所を決めるだけです([kube-scheduler の仕組み](https://kubernetes.io/docs/concepts/scheduling-eviction/kube-scheduler/))。ジョブという単位そのものを知らないので、4 つのうち 2 つだけ動いて残り 2 つを待つ状態が、何の異常もなく起こります。

![The Job controller in kube-controller-manager creates Pods through the API server, kube-scheduler receives unscheduled Pods and writes a Binding per Pod, and kubelet runs the Pods bound to its node](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/e47ba6e81153c2/zenn/articles/e47ba6e81153c2/arch-kube-scheduler.png)
*どの部品も Pod を単位に動き、ジョブ全体をまとめて置く部品は無い*

主な登場人物は kube-controller-manager・API server・etcd・kube-scheduler・kubelet です。etcd に読み書きするのは API server だけで、他はすべて API server を経由します。kube-controller-manager の Job コントローラが Pod を作り、kube-scheduler が未配置の Pod を 1 つずつ選んでノードを決め(結果を API server に書き戻す)、kubelet が自分のノードに割り当てられた Pod を実行します。次に見る Kueue・Volcano・YuniKorn・KAI-Scheduler は、いずれもこの外側か、kube-scheduler の代わりに、ジョブ単位の扱いを持ち込む仕組みです。

## Kueue: 資源の枠で通してよいかを決める層

![With a quota of 2 GPUs, job-a is admitted while job-b and job-c stay suspended with no Pods, and each is admitted only after the previous job finishes](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/e47ba6e81153c2/zenn/articles/e47ba6e81153c2/kueue-admission.png)
*Kueue が決めるのは、ジョブが Pod を作ってよい時期*

Kueue は、ジョブが使う GPU などの資源をあらかじめ決めた枠(quota)と比べ、収まる分だけジョブ単位でまとめて通します([Kueue の概要](https://kueue.sigs.k8s.io/docs/overview/))。収まらないジョブは、Job を使う構成なら Pod を作らせずに待たせます。通した後にどのノードへ置くかは、最終的には kube-scheduler に任せますが、ResourceFlavor という設定で置き先の候補を絞り込むこともできます。さらに Topology Aware Scheduling という機能を使うと、Kueue 自身が置き先の範囲をネットワークの近さでさらに絞ります([Topology Aware Scheduling](https://kueue.sigs.k8s.io/docs/concepts/topology_aware_scheduling/))。既定では無効ですが、waitForPodsReady を有効にすると、全 Pod が Ready になるまで後続ジョブの admission を止める設定も使えます([waitForPodsReady の設定](https://kueue.sigs.k8s.io/docs/tasks/manage/setup_wait_for_pods_ready/))。間に合わなければジョブを一度取り下げ、間隔を空けながら再投入します(上限回数を設定すれば、そこで打ち切ります)。

![On EKS, the Kueue webhook sets suspend on the TrainJob, a reconciler creates a Workload that goes through LocalQueue to ClusterQueue, and on admission Kueue adds the flavor's nodeSelector and clears suspend, after which Trainer, kube-scheduler and Karpenter work as before](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/e47ba6e81153c2/zenn/articles/e47ba6e81153c2/arch-kueue-eks.png)
*Kueue はジョブを止めて印を付けるだけで、Trainer・kube-scheduler・Karpenter は変わらない*

この記事が実際に動かして確かめているのは、EKS 上でのこの構成です。Kueue は `kueue-controller-manager` という 1 つの Deployment を `kueue-system` に置きますが、CRD や webhook の設定自体はクラスタ全体に登録されます。TrainJob を作ると、webhook が `suspend: true` を付けた状態でオブジェクトを作らせます(作成そのものは止めません)。続いて同じプロセスの中のジョブ用コントローラが、対応する Workload を作ります。Workload は namespace の LocalQueue を経て ClusterQueue の枠と比べられ、収まれば ResourceFlavor の nodeSelector と tolerations を付けたうえで suspend が外れます。そこから先は普段どおりで、Trainer が JobSet を作り、JobSet と Job のコントローラが Pod を作ります。kube-scheduler は置ける Pod を bind し、置けない Pod には Unschedulable の印を付けます。Karpenter はその印を見て EC2 ノードを足し、ノードが Ready になると kube-scheduler が bind します。なお、この本の kueue.tf では、webhook が働く namespace を `managed-by-kueue=true` のラベルを付けたものだけに絞っています。この構成は、Amazon EKS Distributed AI ワークショップの本の Kueue の章でも解説を予定しています。

## Volcano と YuniKorn: 対象 Pod の配置を担当する

![YuniKorn binds placeholder Pods first and replaces them with real Pods when every task group reaches minMember, while Volcano tries every task in a session and commits, pipelines or discards against the PodGroup's minMember](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/e47ba6e81153c2/zenn/articles/e47ba6e81153c2/volcano-yunikorn.png)
*どちらも本物の Pod を置く前に、設定した最低人数でそろうかを決める*

Volcano と YuniKorn は、Kueue と違って配置そのものを担当します。対象に指定した Pod について、kube-scheduler の代わりにこちらが置き先を決めます。YuniKorn は、ジョブが要求する資源を実際に占有する身代わりの Pod(プレースホルダ)を先に置き、必要な数ぶんの席が取れてから本物の Pod に 1 つずつ差し替えます([Gang Scheduling のガイド](https://yunikorn.apache.org/docs/user_guide/gang_scheduling/))。この「必要な数」は、ジョブの全タスク数ではなく、設定した最低人数(minMember)です。既定の設定では、時間内に席がそろわないと普通の配置に戻ってしまうため、確実に全部そろえたいなら設定を変える必要があります。Volcano は、ジョブのタスクを 1 つずつ仮に割り当て、最低人数(vcjob の minAvailable。PodGroup では minMember)に届けばまとめて確定します。届かなければ割り当てを戻すか、資源が空くのを待つ状態に置きます([Volcano のコア概念](https://volcano.sh/en/docs/core_concepts/)が示す gang scheduling を、判定の仕組みに即して言い直したものです)。どちらも、複数チームが同じ資源を使うときの割り振り方(queue)を持っています。

![Volcano has an admission webhook, a controller-manager that creates the PodGroup and the Pods, a Queue object, and a scheduler whose session runs enqueue, allocate, preempt, reclaim and backfill with plugins such as gang](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/e47ba6e81153c2/zenn/articles/e47ba6e81153c2/arch-volcano.png)
*Volcano はキュー、gang、配置を自分の Pod について一通り持つ*

Volcano のサーバ側は、主に admission・controller-manager・scheduler の 3 つです([Volcano のアーキテクチャ](https://volcano.sh/en/docs/architecture/))。admission という webhook がジョブなどのリソースを検証・補完し、controller-manager が PodGroup(最低人数を含む)と、ジョブ本体の Pod を作ります。scheduler は一定周期でセッションを開き、設定ファイルに書いた順に action を実行します。enqueue は Queue の空きを見て PodGroup をスケジューリング対象に進めてよいかを決め、allocate はタスクを 1 つずつ仮に割り当てます。preempt は優先度で場所を空け、reclaim は Queue の取り分を他の Queue から取り戻し、backfill は資源量を指定しない Pod を隙間に入れます。Queue はプロセスではなく、テナントごとの重みと上限を書いたオブジェクトです。gang のプラグインが最低人数を満たせば確定、満たさなければ取り消すか、資源が空くのを待つ中間状態(pipelined)に置きます。確定した割り当ては、Volcano の scheduler 自身が API server に反映します。

![The YuniKorn admission controller fills in scheduler name and app ID on new Pods, and inside one scheduler process the shim watches the cluster, the core decides, and the shim binds Pods and creates placeholders](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/e47ba6e81153c2/zenn/articles/e47ba6e81153c2/arch-yunikorn.png)
*shim が双方向に橋渡しし、判断は core が行う*

YuniKorn の中心は Scheduler Core と Kubernetes Shim で、この 2 つは 1 つのスケジューラプロセスとして動きます([YuniKorn のアーキテクチャ](https://yunikorn.apache.org/docs/next/design/architecture))。別デプロイの admission controller が、新しい Pod に schedulerName とアプリケーション ID を付けます。gang を使うための task-group の定義自体は、利用者やジョブを作る側が annotation で与えます。Shim は Kubernetes の状態を Core に伝え、Core の判断を bind やプレースホルダ Pod の作成として Kubernetes 側に反映する、双方向の橋渡し役です。

## KAI-Scheduler: GPU の分け合いまで持つスケジューラ

KAI-Scheduler も、Volcano たちと同じ位置に立つスケジューラです。ジョブ単位で配置を担当する点は同じですが、1 枚の GPU を複数のジョブで分け合う機能も持っているのが特徴です([KAI-Scheduler の README](https://github.com/kai-scheduler/KAI-Scheduler/blob/main/README.md))。チームごとの枠を何段にも分けて持たせる機能や、動いているジョブも含めて再配置し資源の空きをまとめる機能(consolidation)も合わせ持ちます。GPU の分け合い自体は他の仕組みにもありますが、どこまで同じ条件で比べられるかは製品ごとに確認が必要です。

![In KAI-Scheduler a pod-grouper writes PodGroups, a queue controller manages hierarchical queues, the scheduler writes a BindRequest, and a separate binder Deployment performs the bind; GPU sharing uses a reservation Pod](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/e47ba6e81153c2/zenn/articles/e47ba6e81153c2/arch-kai-scheduler.png)
*配置を決める Deployment と、それを反映する Deployment が分かれている*

KAI-Scheduler では、pod-grouper という部品が PyTorchJob や JobSet などのワークロードから PodGroup を作り、API server に書き込みます。これが gang の単位になります。scheduler は階層キューや bin-packing を判断したあと、BindRequest というオブジェクトを書くだけで、実際の bind はそれを読んだ別デプロイの binder が行います。この形は、Volcano や YuniKorn のようにスケジューラのプロセス自身が bind まで行う形とは分かれています。GPU の分け合いは、Pod の annotation で要求した割合を、専用の reservation Pod が確保する方式で、メモリの分離までは既定では保証されません。

## Slurm: ジョブの単位そのものがノードの集合

![In Kubernetes a Job creates separate Pods and a group object has to be added for a scheduler to see them, while in Slurm a job is one allocation and job steps and tasks start inside it](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/e47ba6e81153c2/zenn/articles/e47ba6e81153c2/slurm-unit.png)
*Slurm は資源をジョブ単位で渡し、Kubernetes はグループの物を足してそこへ近づける*

Slurm では、1 つのジョブに N 台のノードを要求すると、その N 台分の資源がそろって初めて 1 つの割り当て(allocation)が成立します([Slurm のクイックスタート](https://slurm.schedmd.com/quickstart.html))。これは Kubernetes 系が後から足している gang scheduling と似た効果ですが、Slurm では最初からジョブの単位そのものが確保したノードの集合なので、特別な名前の機能として後から足す必要がありません。

![sbatch or salloc requests resources from slurmctld, which grants one allocation; srun inside it gets a step from slurmctld and asks the slurmd of each node to launch it, and slurmd forks slurmstepd to run the task processes](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/e47ba6e81153c2/zenn/articles/e47ba6e81153c2/arch-slurm.png)
*資源の割り当てが先に 1 回で決まり、タスクはその中で始まる*

Slurm の主な構成要素はこれらです([Slurm のアーキテクチャ概要](https://slurm.schedmd.com/overview.html))。`sbatch`/`salloc` が slurmctld に資源を要求すると、必要な分がそろって初めて 1 つの割り当て(allocation)が成立します。sbatch の場合、バッチスクリプトは割り当てられた先頭のノードで動きます。そのスクリプトや salloc のシェルの中で実行した `srun` は、slurmctld からステップの割り当てを受け、それを持って各ノードの slurmd に起動を依頼し、slurmd は slurmstepd という子プロセスを fork してタスクを実際に実行します。既定では Pod のようなコンテナ抽象を挟みませんが、job step というステップの単位自体はあります。資源確保を 1 つの要求としてまとめて扱う設計のおかげで、Kubernetes 系のように gang scheduling を後から足す必要がありません。

## Slurm と Kubernetes 系、できることの境目

ここで注意が要るのは、Slurm 自身が「gang scheduling」と呼ぶ機能は、ここまでの意味と強調点が違うという点です。Slurm の gang scheduling は、同じノードを複数のジョブで時間を分けて使う機能で、1 つのジョブに属するタスクはまとめて一団として一時停止・再開されます([Slurm の Gang Scheduling](https://slurm.schedmd.com/gang_scheduling.html))。ここまでの記事が「全部そろうまで始めない」という起動の話をしてきたのに対し、Slurm のこの機能は「始めたあとの時間の分け方」の話です。同じ言葉が違う強調点で使われている例として、ここに書き留めます。

| できること | Slurm | Kueue | Volcano / YuniKorn / KAI |
|---|---|---|---|
| 動いているジョブのプロセスを一時停止し、同じ状態で後から再開する | ◯ | ✕(Pod を削除して作り直す) | ✕(Pod を削除して作り直す) |
| 最低人数がそろう場合だけ配置を確定する | ◯(ジョブの単位そのもの) | △(quota 単位では同じ判定をするが、配置の確定自体は kube-scheduler が Pod ごとに行う。waitForPodsReady で近似) | ◯(YuniKorn は既定の Soft だとタイムアウトで通常配置に戻るため、確実にするには Hard 設定が必要) |
| 複数チームで同じ資源を分け合う枠(queue)を持つ | ◯(partition / QOS) | ◯(ClusterQueue) | ◯ |
