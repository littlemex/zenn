# はじめに

Kubernetes に、4 つの Pod(コンテナを動かす最小単位)からなる分散学習ジョブを投げたとします。2 つは動いたのに、残り 2 つはノード(Pod を動かすマシン)の空きが無く、いつまでも待ち続けることがあります。クラスタが壊れているわけではありません。

![Vanilla Kubernetes treats each of 4 Pods independently, so 2 run and 2 stay pending forever, while Slurm's job unit is the node allocation itself and prevents that from happening](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/e47ba6e81153c2/zenn/articles/e47ba6e81153c2/intro-slurm-vs-vanilla.png)
*Slurm's job unit already prevents partial allocation; vanilla Kubernetes has none*

これは Slurm だと起こりません。Slurm では、ジョブという言葉自体が「確保したノードの集合」を指すので、2 台だけ確保して残りを待つという状態そのものが存在しません。この記事では、同じ「分散ジョブを動かす」という目的のために、Kueue・Volcano・YuniKorn・KAI-Scheduler・Slurm という名前がどこを受け持っているのかを、内部の構成まで含めて整理します。主張は公式ドキュメントで確認したものに限り、その場で出典を示します。Amazon EKS Distributed AI ワークショップの本に、ここで扱う Kueue を実際に使う章を追加したので、合わせて読むと手を動かして確かめられます。

## 全体の地図

![分散学習ジョブを動かす仕組みの地図。Kubernetes の世界には kube-scheduler・Kueue・Volcano/YuniKorn・KAI-Scheduler が並び、Slurm は別の世界にある](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/e47ba6e81153c2/zenn/articles/e47ba6e81153c2/landscape.png)
*同じ「分散ジョブを動かす」にも、受け持ちが違う層がいくつも並んでいる*

| 名前 | 受け持ち | 置き場所 |
|---|---|---|
| kube-scheduler | Pod を 1 つずつノードに置く | Kubernetes の素の機能 |
| Kueue | ジョブ単位で、資源の枠(quota)に収まるかを決める | kube-scheduler の手前 |
| Volcano / YuniKorn | 対象に指定した Pod の配置を、kube-scheduler の代わりに担当する | kube-scheduler と並ぶ選択肢 |
| KAI-Scheduler | 上と同じ位置で、GPU クラスタ向けの枠組みが厚い | kube-scheduler と並ぶ選択肢 |
| Slurm | ノードの確保そのものがジョブの単位になっている | Kubernetes とは別の世界 |

この表の並びのまま、次の節から 1 つずつ、仕組みと内部の構成を見ていきます。

## そもそも何を決める層なのか

分散ジョブを動かす仕組みは、2 つの違う問いに答えています。1 つは「このジョブを今動かしてよいか」、もう 1 つは「どの Pod をどのノードに置くか」です。**この 2 つは別の問いで、同じ機構が両方を受け持つとは限りません**。この区別を知らないと、Kueue と Volcano を同じ種類の仕組みだと誤解してしまいます。

## gang scheduling とは何か

同期型の分散学習では、決まった数の worker がそろわないと学習が進みません。必要な数に足りないまま一部だけ動かしても、残りを待つ間、その分の資源が占有されるだけです。必要な数のタスクがそろうときだけ始め、そろわなければ始めないという考え方を、gang scheduling と呼びます。

## 素の Kubernetes: kube-scheduler の内部

![A distributed training job with 4 Pods: 2 run while 2 stay pending forever, because kube-scheduler judges each Pod on its own](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/e47ba6e81153c2/zenn/articles/e47ba6e81153c2/kube-scheduler-partial.png)
*kube-scheduler は 1 つの Pod ごとに判断し、ジョブ全体を見ない*

標準の kube-scheduler は、Pod を 1 つずつ見て置き場所を決めるだけです([kube-scheduler の仕組み](https://kubernetes.io/docs/concepts/scheduling-eviction/kube-scheduler/))。ジョブという単位そのものを知らないので、4 つのうち 2 つだけ動いて残り 2 つを待つ状態が、何の異常もなく起こります。

![Architecture: a Job controller creates Pods via the API server, etcd stores them, kube-scheduler watches and binds each Pod one by one, and kubelet runs the bound Pod on its node](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/e47ba6e81153c2/zenn/articles/e47ba6e81153c2/arch-kube-scheduler.png)
*どの図にもジョブという単位は出てこない。登場するのは Pod だけ*

主な登場人物は kube-controller-manager・API server・etcd・kube-scheduler・kubelet です。etcd に読み書きするのは API server だけで、他はすべて API server を経由します。kube-controller-manager の Job コントローラが Pod を作り、kube-scheduler が未配置の Pod を 1 つずつ選んでノードを決め(結果を API server に書き戻す)、kubelet が自分のノードに割り当てられた Pod を実行します。次に見る Kueue・Volcano・YuniKorn・KAI-Scheduler は、いずれもこの外側か、kube-scheduler の代わりに、ジョブ単位の扱いを持ち込む仕組みです。

## Kueue: 資源の枠で通してよいかを決める層

![Kueueが見る範囲は3つのジョブの枠だけで、どのノードに置くかやノードを増やすかは既定ではkube-schedulerとKarpenterの仕事のまま](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/e47ba6e81153c2/zenn/articles/e47ba6e81153c2/kueue-admission.png)
*Kueue は既定では、資源の枠(quota)で通してよいかを決めるだけ*

Kueue は、ジョブが使う GPU などの資源をあらかじめ決めた枠(quota)と比べ、収まる分だけジョブ単位でまとめて通します([Kueue の概要](https://kueue.sigs.k8s.io/docs/overview/))。収まらないジョブは、Job を使う構成なら Pod を作らせずに待たせます。通した後にどのノードへ置くかは、最終的には kube-scheduler に任せますが、ResourceFlavor という設定で置き先の候補を絞り込むこともできます。さらに Topology Aware Scheduling という機能を使うと、Kueue 自身が置き先の範囲をネットワークの近さでさらに絞ります([Topology Aware Scheduling](https://kueue.sigs.k8s.io/docs/concepts/topology_aware_scheduling/))。既定では無効ですが、waitForPodsReady を有効にすると、全 Pod が Ready になるまで後続ジョブの admission を止める設定も使えます([waitForPodsReady の設定](https://kueue.sigs.k8s.io/docs/tasks/manage/setup_wait_for_pods_ready/))。間に合わなければジョブを一度取り下げ、間隔を空けながら再投入します(上限回数を設定すれば、そこで打ち切ります)。

![Architecture on EKS: kueue-controller-manager runs in the kueue-system namespace, with webhook sets suspend=true then a Workload moves through LocalQueue to ClusterQueue before kube-scheduler and Karpenter place it](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/e47ba6e81153c2/zenn/articles/e47ba6e81153c2/arch-kueue-eks.png)
*Kueue admits the Workload; placement and node capacity are still EKS's own job*

この記事が実際に動かして確かめているのは、EKS 上でのこの構成です。Kueue は `kueue-controller-manager` という 1 つの Deployment を `kueue-system` に置きますが、CRD や webhook の設定自体はクラスタ全体に登録されます。TrainJob を作ると、webhook が `suspend: true` を付けた状態でオブジェクトを作らせ(作成そのものは止めません)、対応する Workload が作られます。Workload は namespace の LocalQueue を経て ClusterQueue の枠と比べられ、収まれば suspend が外れます。そこから先は普段どおり、kube-scheduler が置き場所を決め、置き場所の無い Pod に Karpenter が反応してノードを増やします。この構成は、Amazon EKS Distributed AI ワークショップの本の Kueue の章でも解説を予定しています。

## Volcano と YuniKorn: 対象 Pod の配置を担当する

![YuniKornは資源を占有する身代わりのPodを先に置いて必要な数ぶんの席が取れたら本物のPodに差し替え、Volcanoはジョブのタスクを1つずつ仮に割り当て必要な数に届かなければ割り当てを戻す](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/e47ba6e81153c2/zenn/articles/e47ba6e81153c2/volcano-yunikorn.png)
*どちらも対象 Pod には別のスケジューラが配置を決め、必要な数で成否を分ける*

Volcano と YuniKorn は、Kueue と違って配置そのものを担当します。対象に指定した Pod について、kube-scheduler の代わりにこちらが置き先を決めます。YuniKorn は、ジョブが要求する資源を実際に占有する身代わりの Pod(プレースホルダ)を先に置き、必要な数ぶんの席が取れてから本物の Pod に 1 つずつ差し替えます([Gang Scheduling のガイド](https://yunikorn.apache.org/docs/user_guide/gang_scheduling/))。この「必要な数」は、ジョブの全タスク数ではなく、設定した最低人数(minMember)です。既定の設定では、時間内に席がそろわないと普通の配置に戻ってしまうため、確実に全部そろえたいなら設定を変える必要があります。Volcano は、ジョブのタスクを 1 つずつ仮に割り当て、最低人数(minAvailable)に届けばまとめて確定します。届かなければ割り当てを戻すか、資源が空くのを待つ状態に置きます([Volcano のコア概念](https://volcano.sh/en/docs/core_concepts/)が示す gang scheduling を、判定の仕組みに即して言い直したものです)。どちらも、複数チームが同じ資源を使うときの割り振り方(queue)を持っています。

![Volcano architecture: an admission webhook validates the Job resource, a controller-manager creates the PodGroup and the Job's own Pods, and the scheduler's own session runs enqueue then allocate then the gang plugin, which commits, discards, or pipelines each attempt](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/e47ba6e81153c2/zenn/articles/e47ba6e81153c2/arch-volcano.png)
*Volcano's scheduler itself binds the Pods, gated by whether the gang is complete*

Volcano のサーバ側は、主に admission・controller-manager・scheduler の 3 つです([Volcano のアーキテクチャ](https://volcano.sh/en/docs/architecture/))。admission という webhook がジョブなどのリソースを検証・補完し、controller-manager が PodGroup(最低人数を含む)と、ジョブ本体の Pod を作ります。scheduler は一定周期で開くセッションの中で、まず enqueue が枠の空きを見て PodGroup をスケジューリング対象に進めてよいかを決め、次に allocate がタスクを 1 つずつ仮に割り当てます。gang のプラグインが最低人数を満たせば確定、満たさなければ取り消すか、資源が空くのを待つ中間状態(pipelined)に置きます。確定した割り当ては、Volcano の scheduler 自身が API server に反映します。

![Apache YuniKorn architecture: an admission controller sets schedulerName and applicationId as a separate entry point, while Scheduler Core and Kubernetes Shim run as one process, with the shim feeding cluster state in and binding or creating placeholder Pods as Core decides](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/e47ba6e81153c2/zenn/articles/e47ba6e81153c2/arch-yunikorn.png)
*the shim is the two-way bridge; admission is a separate, earlier step*

YuniKorn の中心は Scheduler Core と Kubernetes Shim で、この 2 つは 1 つのスケジューラプロセスとして動きます([YuniKorn のアーキテクチャ](https://yunikorn.apache.org/docs/next/design/architecture))。別デプロイの admission controller が、Pod に schedulerName と applicationId を付けます。gang を使うための task-group の定義自体は、利用者やジョブを作る側が annotation で与えます。Shim は Kubernetes の状態を Core に伝え、Core の判断を bind やプレースホルダ Pod の作成として Kubernetes 側に反映する、双方向の橋渡し役です。

## KAI-Scheduler: GPU の分け合いまで持つスケジューラ

KAI-Scheduler も、Volcano たちと同じ位置に立つスケジューラです。ジョブ単位で配置を担当する点は同じですが、1 枚の GPU を複数のジョブで分け合う機能も持っているのが特徴です([KAI-Scheduler の README](https://github.com/NVIDIA/KAI-Scheduler/blob/main/README.md))。チームごとの枠を何段にも分けて持たせる機能や、動いているジョブも含めて再配置し資源の空きをまとめる機能(consolidation)も合わせ持ちます。GPU の分け合い自体は他の仕組みにもありますが、どこまで同じ条件で比べられるかは製品ごとに確認が必要です。

![KAI-Scheduler architecture: a pod-grouper builds a PodGroup from workload CRDs such as TrainJob, the scheduler core runs hierarchical queues and bin-packing then files a BindRequest, a separate binder Deployment performs the actual bind, and GPU sharing works through a reservation Pod rather than a device plugin](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/e47ba6e81153c2/zenn/articles/e47ba6e81153c2/arch-kai-scheduler.png)
*the binder is a separate process here; Volcano/YuniKorn bind inside the scheduler itself*

KAI-Scheduler では、pod-grouper という部品が TrainJob・PyTorchJob などのワークロードから PodGroup を作り、これが gang の単位になります。scheduler core が階層キューや bin-packing を判断したあと、実際の bind は別デプロイの binder が担当します。scheduler は BindRequest という形で依頼を作るだけで、Volcano や YuniKorn のようにスケジューラのプロセス自身が bind まで行う形とは分かれています。GPU の分け合いは、Pod の annotation で要求した割合を、専用の reservation Pod が確保する方式で、メモリの分離までは既定では保証されません。

## Slurm: ジョブの単位そのものがノードの集合

![Kubernetes系ではジョブ=別々のPodが3つあり後から束ねる必要があるが、Slurmではジョブ=確保したノードの集合そのもので束ね直す手間が無い](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/e47ba6e81153c2/zenn/articles/e47ba6e81153c2/slurm-unit.png)
*Slurm はジョブの単位を後付けせず、確保の単位そのものに合わせている*

Slurm では、1 つのジョブに N 台のノードを要求すると、その N 台分の資源がそろって初めて 1 つの割り当て(allocation)が成立します([Slurm のクイックスタート](https://slurm.schedmd.com/quickstart.html))。これは Kubernetes 系が後から足している gang scheduling と似た効果ですが、Slurm では最初からジョブの単位そのものが確保したノードの集合なので、特別な名前の機能として後から足す必要がありません。

![Slurm architecture: slurmctld is the central manager that grants sbatch/salloc one resource allocation, srun talks to slurmd directly to launch a job step within it, and slurmd forks slurmstepd to run the task, with slurmdbd optionally recording accounting](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/e47ba6e81153c2/zenn/articles/e47ba6e81153c2/arch-slurm.png)
*the allocation is requested as one resource request, before any task launches*

Slurm の主な構成要素はこれらです([Slurm のアーキテクチャ概要](https://slurm.schedmd.com/overview.html))。`sbatch`/`salloc` が slurmctld に資源を要求すると、必要な分がそろって初めて 1 つの割り当て(allocation)が成立します。そのあと `srun` は slurmctld からステップの割り当てを受け、それを持って各ノードの slurmd に起動を依頼し、slurmd は slurmstepd という子プロセスを fork してタスクを実際に実行します。既定では Pod のようなコンテナ抽象を挟みませんが、job step というステップの単位自体はあります。資源確保を 1 つの要求としてまとめて扱う設計のおかげで、Kubernetes 系のように gang scheduling を後から足す必要がありません。

## Slurm と Kubernetes 系、できることの境目

ここで注意が要るのは、Slurm 自身が「gang scheduling」と呼ぶ機能は、ここまでの意味と強調点が違うという点です。Slurm の gang scheduling は、同じノードを複数のジョブで時間を分けて使う機能で、1 つのジョブに属するタスクはまとめて一団として一時停止・再開されます([Slurm の Gang Scheduling](https://slurm.schedmd.com/gang_scheduling.html))。ここまでの記事が「全部そろうまで始めない」という起動の話をしてきたのに対し、Slurm のこの機能は「始めたあとの時間の分け方」の話です。同じ言葉が違う強調点で使われている例として、ここに書き留めます。

| できること | Slurm | Kueue | Volcano / YuniKorn / KAI |
|---|---|---|---|
| 動いているジョブのプロセスを一時停止し、同じ状態で後から再開する | ◯ | ✕(Pod を削除して作り直す) | ✕(Pod を削除して作り直す) |
| 最低人数がそろう場合だけ配置を確定する | ◯(ジョブの単位そのもの) | △(quota 単位では同じ判定をするが、配置の確定自体は kube-scheduler が Pod ごとに行う。waitForPodsReady で近似) | ◯(YuniKorn は既定の Soft だとタイムアウトで通常配置に戻るため、確実にするには Hard 設定が必要) |
| 複数チームで同じ資源を分け合う枠(queue)を持つ | ◯(partition / QOS) | ◯(ClusterQueue) | ◯ |

この表に書いた内容は、各製品を実際に確認した時点のドキュメントに基づきます。バージョンが進むと変わる可能性があるため、最終判断は参考に挙げた一次資料の最新版で確認してください。

# まとめ

同じ「分散ジョブを動かす」でも、通してよいかだけを決める層と、配置そのものを担当する層とでは、できることと内部の構成が違います。
