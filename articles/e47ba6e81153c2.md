# はじめに

この記事は、Slurm と Kubernetes のどちらかが優れていると主張するためのものではありません。両者の違いをできるだけ公平に並べたうえで、Kubernetes の上でジョブのスケジューリングがどう組み立てられているのかを整理することが目的です。

:::message
筆者は Slurm も Kubernetes もどっちも好きだにゃーん。(=´ω`;=)
:::

Kubernetes に、4 つの Pod からなる分散学習ジョブを投げたとします。2 つは動いたのに、残り 2 つはノードに空きが無く、いつまでも Pending のまま、ということが起こり得ます。クラスタが壊れているわけではありません。

![A TrainJob's 4 Pods go through kube-scheduler one per cycle; worker-0 and worker-1 are bound to the only two GPUs and wait at rendezvous, while worker-2 and worker-3 stay Pending with no GPU left, so the job holds 2 GPUs and makes no progress](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/e47ba6e81153c2/zenn/articles/e47ba6e81153c2/intro-stuck-half-placed.png)
*kube-scheduler は Pod を 1 つずつ正しく置くが、4 つ全部が置けるかは誰も確かめない*

図のとおり、どの部品も自分の仕事を正しくこなしています。ジョブを扱うコントローラは 4 つの Pod を作り、kube-scheduler は GPU が空いているノードに Pod を 1 つずつ置きます。置けない Pod は Pending のまま待ちます。置かれた 2 つの worker は、そこで止まります。分散学習では、all-reduce のような集合通信を始める前に、全 worker が互いの居場所を確かめ合う [rendezvous](https://docs.pytorch.org/docs/stable/elastic/rendezvous.html) という集合の段階があります。4 つの GPU で学習するなら、4 つの worker が全員そろうまで、先に起動した worker はこの段階で待ち続けます。残り 2 つは Pending のままなので、全員はいつまでもそろいません。その間、置かれた 2 つは GPU を確保したまま 1 ステップも学習を進められず、設定した待ち時間を過ぎるとタイムアウトのエラーで終了します。再試行の設定によって Pod が作り直されても、空きが増えていなければ同じことを繰り返します。

問題は、4 つがそろうかをジョブ全体として判断する部品が、素の Kubernetes には無いことです。

HPC で広く使われる Slurm では、この状態はふつう起こりません。Slurm にはできて、追加の仕組みを入れていない素の Kubernetes にはできないことを、まず 5 つ並べ、D1 から D5 の ID を付けます。後の節では、各仕組みがどの ID を埋めるのかを、この ID で示します。

![Slurm can start a multi-node job as one unit, hold it in a queue under a limit, backfill without delaying a big job, suspend and resume it, and use fair-share from past usage; vanilla Kubernetes binds per Pod, rejects with ResourceQuota, has no planned start, deletes Pods on suspend, and uses a fixed PriorityClass](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/e47ba6e81153c2/zenn/articles/e47ba6e81153c2/intro-slurm-vs-vanilla.png)
*D1 から D5 は、どれもジョブ全体か利用者のアカウントを単位にした判断*

D1 は、複数ノードのジョブを 1 つの単位として始めることです。Slurm は、要求したノードと GPU がすべてそろってから、それらを 1 つの割り当てとして確保してジョブを始めます。この割り当てを [allocation](https://slurm.schedmd.com/quickstart.html) と呼びます。素の Kubernetes は Pod を 1 つずつノードに置くので、一部だけ動いて残りが待つ状態が起こります。

D2 は、上限を超えたジョブを待ち行列で待たせることです。Slurm では、アカウントごとに GPU 数などの合計に上限を設けられます。この上限の 1 つが [GrpTRES](https://slurm.schedmd.com/resource_limits.html) です。上限を超えるジョブも受け付けたうえで、PENDING のまま待たせます。Kubernetes の [ResourceQuota](https://kubernetes.io/docs/concepts/policy/resource-quotas/) は、上限を超える Pod の作成を断るだけで、順番を持った待ち行列にはなりません。

D3 は、大きなジョブを遅らせずに小さなジョブを先に流す [backfill](https://slurm.schedmd.com/sched_config.html) です。Slurm は、各ジョブに指定された実行時間の上限をもとに大きなジョブの開始予定時刻を計算し、それを動かさない範囲でだけ小さなジョブを先に始めます。素の Kubernetes には、ジョブ全体の開始予定時刻という考え方がありません。

D4 は、動いているジョブを止めて、作り直さずに再開することです。Slurm でプリエンプションの方式に [suspend](https://slurm.schedmd.com/preempt.html) を選ぶと、ジョブのプロセスは一時停止され、resume するとそのまま続きから動きます。Kubernetes の Job を [suspend](https://kubernetes.io/docs/concepts/workloads/controllers/job/#suspending-a-job) すると、動いている Pod は削除されます。

D5 は、過去の使用量から優先度を決めることです。Slurm では、設定すれば [fair-share](https://slurm.schedmd.com/priority_multifactor.html) を優先度の計算に入れられます。利用実績の記録をもとに、使いすぎた利用者の優先度を下げる仕組みです。Kubernetes の [PriorityClass](https://kubernetes.io/docs/concepts/scheduling-eviction/pod-priority-preemption/) は、Pod ごとに決まった値を与えるだけです。

Slurm 側の D1 から D5 には、設定で有効にする機能も含まれます。5 つに共通するのは、判断の単位が Pod ではなく、ジョブ全体か利用者のアカウントだという点です。このうち D3 の backfill と D5 の fair-share は製品ごとの差が大きいため、この記事では D1、D2、D4 を中心に比べます。この記事では、Kubernetes の上でこの「ジョブ単位の判断」を後から足す Kueue・Volcano・YuniKorn・KAI-Scheduler が、それぞれどこを受け持ち、内部がどうなっているのかを整理します。主張は公式ドキュメントで確認したものに限り、その場で出典を示します。[Amazon EKS Distributed AI ワークショップの本](https://zenn.dev/tosshi/books/eks-distributed-ai)に、Kueue を実際に使う章を追加しました。併せて読むと、手を動かして確かめられます。

## 全体像

![Kubernetes runs as separate steps: a Job object is created, Kueue holds it until admitted, the controller creates Pods, a scheduler picked per Pod places them, and kubelet runs them, while Slurm makes queueing and allocation one decision in slurmctld](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/e47ba6e81153c2/zenn/articles/e47ba6e81153c2/landscape.png)
*Kueue は 2 番目の段を受け持つ。Volcano・YuniKorn・KAI は 4 番目の段に入り、それぞれ待ち行列も持つ*

| 名前 | 受け持ち | 置き場所 |
|---|---|---|
| kube-scheduler | Pod を 1 つずつノードに置く | Kubernetes の素の機能 |
| Kueue | ジョブ単位で、資源の枠に収まるかを決める | kube-scheduler の手前 |
| Volcano / YuniKorn | 対象に指定した Pod の配置を、kube-scheduler の代わりに担当する | kube-scheduler と並ぶ選択肢 |
| KAI-Scheduler | 上と同じ位置で、GPU の分け合いや階層キューなど GPU クラスタ向けの機能が多い | kube-scheduler と並ぶ選択肢 |
| Slurm | ノードの確保そのものがジョブの単位になっている | Kubernetes とは別の世界 |

2 つの前提を確認したあと、この表の順に、仕組みと内部の構成を 1 つずつ見ていきます。

## そもそも何を決める層なのか

分散ジョブを動かす仕組みは、2 つの違う問いに答えています。1 つは「このジョブを今動かしてよいか」、もう 1 つは「どの Pod をどのノードに置くか」です。**この 2 つは別の問いで、同じ機構が両方を受け持つとは限りません**。この区別を知らないと、Kueue と Volcano を同じ種類の仕組みだと誤解してしまいます。前者の「動かしてよいか」の判断を、Kueue では admission と呼びます。後に出てくる Volcano の admission webhook や YuniKorn の admission controller は、Kubernetes が API へのリクエストを検証・書き換えする仕組みのことで、Kueue の admission とは別物です。

## gang scheduling とは

同期型の分散学習では、決まった数の worker がそろわないと学習が進みません。必要な数に足りないまま一部だけ動かしても、残りを待つ間、その分の資源が占有されるだけです。必要な数のタスクがそろうときだけ始め、そろわなければ始めないという考え方を、gang scheduling と呼びます。

## 素の Kubernetes の挙動

標準の [kube-scheduler](https://kubernetes.io/docs/concepts/scheduling-eviction/kube-scheduler/) は、Pod を 1 つずつ見て置き場所を決めるだけです。ジョブという単位そのものを知らないので、4 つのうち 2 つだけ動いて残り 2 つを待つ状態が、何の異常もなく起こります。これが D1 の欠けている状態です。

![The Job controller in kube-controller-manager creates Pods through the API server, kube-scheduler receives unscheduled Pods and writes a Binding per Pod, and kubelet runs the Pods bound to its node](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/e47ba6e81153c2/zenn/articles/e47ba6e81153c2/arch-kube-scheduler.png)
*どの部品も Pod を単位に動き、ジョブ全体をまとめて置く部品は無い*

kube-controller-manager の Job コントローラが Pod を作り、kube-scheduler が未配置の Pod を 1 つずつ選んでノードを決め、その結果を API server に書き戻します。kubelet は自分のノードに割り当てられた Pod を実行します。次に見る Kueue・Volcano・YuniKorn・KAI-Scheduler は、kube-scheduler の手前に置くか、kube-scheduler の代わりに使うかして、ジョブ単位の扱いを持ち込む仕組みです。

::::details 4 つの部品の役割
| 部品 | 動く場所 | 何をするか | この記事との関係 |
|---|---|---|---|
| [API server](https://kubernetes.io/docs/concepts/overview/components/#kube-apiserver) | コントロールプレーン | クラスタの状態を読み書きする唯一の窓口です。Job や Pod の定義を受け取って保存し、他の部品はすべてここを通して状態を見たり書いたりします。 | Kueue の webhook も、ここに届いた作成のリクエストに割り込んで `suspend: true` を書き加えます。 |
| [kube-controller-manager](https://kubernetes.io/docs/concepts/overview/components/#kube-controller-manager) | コントロールプレーン | 「あるべき状態」と「いまの状態」の差を埋める controller をまとめて動かすプロセスです。Job controller は、Job に書かれた数だけ Pod を作ります。 | Pod を作る数は知っていますが、その Pod が全部置けるかは確かめません。 |
| [kube-scheduler](https://kubernetes.io/docs/concepts/scheduling-eviction/kube-scheduler/) | コントロールプレーン | まだノードが決まっていない Pod を 1 つずつ取り出し、空きと条件に合うノードを選んで、結果を API server に書き戻します。 | 判断の単位が Pod 1 つなので、D1 の状態が起こります。Volcano・YuniKorn・KAI-Scheduler は、この部品の代わりに置き先を決めます。 |
| [kubelet](https://kubernetes.io/docs/concepts/overview/components/#kubelet) | 各ノード | 自分のノードに割り当てられた Pod を API server から受け取り、コンテナを起動して動かし続けます。 | 置かれた worker が rendezvous で待ち続けるのは、kubelet が起動したコンテナの中です。 |
::::

## Kueue とは

![With a quota of 2 GPUs, job-a is admitted while job-b and job-c stay suspended with no Pods, and each is admitted only after the previous job finishes](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/e47ba6e81153c2/zenn/articles/e47ba6e81153c2/kueue-admission.png)
*Kueue が決めるのは、ジョブが Pod を作ってよい時期*

[Kueue](https://kueue.sigs.k8s.io/docs/overview/) は、ジョブが要求する GPU などの資源量を、quota と呼ぶあらかじめ決めた枠と比べ、枠に収まるジョブだけを通します。収まらないジョブは、Job や TrainJob のように suspend できるものなら、Pod を作らせずに待たせます。通した後にどのノードへ置くかは kube-scheduler が決めますが、Kueue は資源の種類と配置条件を表す ResourceFlavor で、候補のノードを絞れます。

ID で言うと、Kueue が埋めるのは D2 です。上限を超えたジョブを、Pod を作らせないまま待ち行列で待たせます。D1 については、ジョブ全体の資源量を枠と照合するところまでで、各 Pod をどこに置けるかは kube-scheduler が Pod ごとに判断します。D5 は、Admission Fair Sharing を設定すれば、同じ ClusterQueue を使う LocalQueue の間で過去の使用量を数え、通す順番に入れられます。D4 は埋めません。

[Topology Aware Scheduling](https://kueue.sigs.k8s.io/docs/concepts/topology_aware_scheduling/) という機能を使うと、設定したラックやノードなどのトポロジーに沿って、Kueue が置き先の範囲を絞れます。[waitForPodsReady](https://kueue.sigs.k8s.io/docs/tasks/manage/setup_wait_for_pods_ready/) は既定では無効です。有効にすると、通したジョブの全 Pod が決めた時間内に Ready にならないとき、Kueue はそのジョブを取り下げて待ち行列に戻し、戻すたびに次に通すまでの間隔を延ばします。上限回数を設定すれば、そこで打ち切ります。さらに blockAdmission を有効にすると、先に通したジョブの全 Pod が Ready になるまで、後続のジョブを通さなくなります。ただし、どちらも先のジョブの全 Pod を同時に置けることを保証する機能ではありません。

![On EKS, the Kueue webhook sets suspend on the TrainJob, a reconciler creates a Workload that goes through LocalQueue to ClusterQueue, and on admission Kueue adds the flavor's nodeSelector and clears suspend, after which Trainer, kube-scheduler and Karpenter work as before](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/e47ba6e81153c2/zenn/articles/e47ba6e81153c2/arch-kueue-eks.png)
*Kueue はジョブを止め、通すときに nodeSelector などを足すだけで、Trainer・kube-scheduler・Karpenter は変わらない*

図は、ワークショップの本で実際に動かしている EKS 上の構成です。先に、図に出てくる Kueue の 3 つのオブジェクトを説明します。

| オブジェクト | 置き場所 | 役割 |
|---|---|---|
| LocalQueue | ジョブと同じ namespace | 利用者がジョブを投入する窓口です。ジョブは `kueue.x-k8s.io/queue-name` ラベルで、投入先の LocalQueue の名前を指定します。LocalQueue 自身は枠を持たず、どの ClusterQueue に流すかだけを決めています。 |
| ClusterQueue | クラスタ全体に 1 つずつ | GPU などの枠を持ち、通してよいかを判断します。複数の namespace の LocalQueue が、同じ ClusterQueue を共有できます。 |
| ResourceFlavor | クラスタ全体に 1 つずつ | 枠の中身がどのノードの資源かを表します。この構成では、Karpenter の NodePool の名前をノードのラベルとして持たせています。 |

Kueue の実体は `kueue-system` namespace の `kueue-controller-manager` という 1 つの Deployment で、webhook とコントローラはこのプロセスの中にあります。CRD と webhook の設定はクラスタ全体に登録されますが、本で使っている Terraform の設定ファイル kueue.tf では、webhook が働く namespace を `managed-by-kueue=true` のラベルを付けたものだけに絞っています。TrainJob を 1 つ投入すると、図の番号の順に次のことが起きます。主体は動く部品、相手はその部品が手を入れる対象です。

| 番号 | 主体 | 相手 | すること | その後の状態 |
|---|---|---|---|---|
| 1 | 利用者 | EKS の API server | `kueue.x-k8s.io/queue-name: gpu-ddp` のラベルを付けた Kubeflow Trainer の TrainJob を `kubectl apply` で送る | 作成のリクエストが API server に届く |
| 2 | Kueue の webhook | API server が保存しようとしている TrainJob | 作成を止めずに `suspend: true` を書き加える | TrainJob は止まった状態で保存され、Trainer はまだ Pod を作らない |
| 3 | kueue-controller-manager のジョブ用コントローラ | 保存された TrainJob | 必要な GPU や CPU の量をまとめた Workload を 1 つ作る | Kueue が待ち行列で扱う単位ができる |
| 4 | ClusterQueue | LocalQueue から並んだ Workload | いま使われている量に要求量を足し、ResourceFlavor ごとの枠に収まるかを判断する | 収まるか収まらないかが決まる |
| 5 | Kueue | 枠に収まった Workload の TrainJob | Workload を admitted にし、ResourceFlavor の nodeLabels を nodeSelector として、tolerations があればそれも付けて、`suspend` を外す | 収まらなければ止まったままで Pod は作られず、枠が空くのを待つ |
| 6 | Trainer と JobSet・Job のコントローラ | `suspend` が外れた TrainJob | Trainer が JobSet を作り、JobSet と Job のコントローラが Pod を作る | Pod ができ、置き先が未定のまま並ぶ |
| 7 | kube-scheduler | 置き先が未定の Pod | nodeSelector に合い、空きのあるノードに bind する。置けない Pod には Unschedulable の印を付ける | 置けた Pod は動き出し、残りは Pending のまま |
| 8 | Karpenter | Unschedulable の印が付いた Pod | 条件に合う EC2 ノードを起動する | ノードが Ready になると 7 に戻り、kube-scheduler が残りを bind する |

Kueue が手を入れるのは 2 から 5 までで、6 から 8 の Trainer・kube-scheduler・Karpenter の動き方は変わりません。止まっている TrainJob には Pod が無いので、Karpenter はそのためのノードを起動しません。この構成は、本の Kueue の章でも解説しています。

## Volcano と YuniKorn とは

![YuniKorn binds placeholder Pods first and replaces them with real Pods when every task group reaches minMember, while Volcano tries every task in a session and commits, pipelines or discards against the PodGroup's minMember](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/e47ba6e81153c2/zenn/articles/e47ba6e81153c2/volcano-yunikorn.png)
*どちらも本物の Pod を置く前に、設定した最低人数でそろうかを決める*

Volcano と YuniKorn は、Kueue と違って配置そのものを担当します。schedulerName でこれらのスケジューラを指定した Pod について、kube-scheduler の代わりに置き先を決めます。YuniKorn は、本物の Pod より先に、同じ量の資源を実際に占有する身代わりの Pod を置きます。この身代わりを[プレースホルダ](https://yunikorn.apache.org/docs/user_guide/gang_scheduling/)と呼びます。必要な数のプレースホルダが置けたら、それを本物の Pod に 1 つずつ差し替えます。「必要な数」は、ジョブの全タスク数ではなく、minMember で設定した最低人数です。既定の Soft では、時間内に最低人数がそろわないと、プレースホルダを外して普通の配置に戻ります。一部だけで動き出すのを避け、そろわなければジョブを失敗させたいなら、gangSchedulingStyle を Hard にします。Volcano は、ジョブのタスクを 1 つずつ仮に割り当て、最低人数に届けばまとめて確定します。最低人数は、Volcano の Job である vcjob では minAvailable、Pod のまとまりを表す [PodGroup](https://volcano.sh/en/docs/core_concepts/) では minMember という名前です。どちらも複数チームに資源を割り振るキューを持ちます。Volcano では Queue というオブジェクトで、YuniKorn では設定に書く階層キューです。ID で言うと、Volcano と YuniKorn は自分が配置する Pod について D1 と D2 を埋めます。ただし YuniKorn の D1 は、既定の Soft のままだと時間切れで崩れます。D4 はどちらも埋めません。

![Volcano has an admission webhook, a controller-manager that creates the PodGroup and the Pods, a Queue object, and a scheduler whose session runs enqueue, allocate, preempt, reclaim and backfill with plugins such as gang](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/e47ba6e81153c2/zenn/articles/e47ba6e81153c2/arch-volcano.png)
*Volcano はキュー、gang、配置を自分の Pod について一通り持つ*

[Volcano](https://volcano.sh/en/docs/architecture/) のサーバ側は、主に admission webhook・controller-manager・scheduler の 3 つです。admission webhook がジョブなどのリソースを検証・補完します。vcjob を使う場合は、controller-manager が最低人数を指定した PodGroup と、ジョブの Pod を作ります。scheduler は一定周期でセッションを開き、設定ファイルに書いた順に action を実行します。enqueue は Queue の空きを見て PodGroup をスケジューリング対象に進めてよいかを決め、allocate はタスクを 1 つずつ仮に割り当てます。preempt は優先度で場所を空け、reclaim は Queue の取り分を他の Queue から取り戻します。backfill は資源量を指定しない Pod を隙間に入れる機能で、Slurm の backfill とは別物です。Queue はプロセスではなく、テナントごとの重みと上限を書いたオブジェクトです。gang のプラグインは、最低人数を満たせば確定し、満たさなければ取り消すか、資源が空くのを待つ pipelined という中間状態に置きます。確定した割り当ては、Volcano の scheduler 自身が API server に反映します。

![The YuniKorn admission controller fills in scheduler name and app ID on new Pods, and inside one scheduler process the shim watches the cluster, the core decides, and the shim binds Pods and creates placeholders](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/e47ba6e81153c2/zenn/articles/e47ba6e81153c2/arch-yunikorn.png)
*shim が双方向に橋渡しし、判断は core が行う*

[YuniKorn](https://yunikorn.apache.org/docs/design/architecture/) の中心は Scheduler Core と Kubernetes Shim で、この 2 つは 1 つのスケジューラプロセスとして動きます。別の Deployment として動く admission controller が、新しい Pod に schedulerName とアプリケーション ID を付けます。gang を使うための task-group の定義自体は、利用者やジョブを作る側が annotation で与えます。Shim は Kubernetes の状態を Core に伝え、Core の判断を bind やプレースホルダ Pod の作成として Kubernetes 側に反映する、双方向の橋渡し役です。

## KAI-Scheduler とは

[KAI-Scheduler](https://github.com/kai-scheduler/KAI-Scheduler/blob/main/README.md) も、Volcano や YuniKorn と同じく、kube-scheduler の代わりに配置を担当するスケジューラです。特徴は、1 枚の GPU を複数のジョブで分け合う機能を持つことです。チームごとの枠を何段にも入れ子にできる階層キューや、動いているジョブも含めて置き直し、空きをまとまった形にする consolidation も持っています。ID で言うと、D1 と D2 を埋め、D4 は埋めない点は Volcano や YuniKorn と同じです。

![In KAI-Scheduler a pod-grouper writes PodGroups, a queue controller manages hierarchical queues, the scheduler writes a BindRequest, and a separate binder Deployment performs the bind; GPU sharing uses a reservation Pod](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/e47ba6e81153c2/zenn/articles/e47ba6e81153c2/arch-kai-scheduler.png)
*配置を決める Deployment と、それを反映する Deployment が分かれている*

KAI-Scheduler では、pod-grouper という部品が PyTorchJob や JobSet などのワークロードから KAI-Scheduler 独自の PodGroup を作り、API server に書き込みます。これが gang の単位になります。scheduler は、階層キューの取り分と、Pod をなるべく少ないノードに詰める bin-packing を考えて置き先を決めます。そのうえで書くのは BindRequest というオブジェクトだけで、実際の bind はそれを読んだ別デプロイの binder が行います。この点は、スケジューラのプロセス自身が bind まで行う Volcano や YuniKorn とは異なります。GPU を分け合うときは、既定のモードでは共有する GPU を専用の reservation Pod が押さえ、各 Pod が annotation で要求した割合はスケジューラが勘定します。このモードでは GPU メモリは分離されず、HAMi-core を使うモードを選ぶとメモリの上限がかかります。

## Slurm と Kubernetes 系の違い

表に入る前に 1 つ注意があります。Slurm が「gang scheduling」と呼ぶ機能は、ここまで使ってきた意味と強調点が違います。Slurm の [gang scheduling](https://slurm.schedmd.com/gang_scheduling.html) は、同じノードを複数のジョブで時間を分けて使う機能で、1 つのジョブに属するタスクはまとめて一時停止・再開されます。この記事がここまで「全部そろうまで始めない」という起動の話をしてきたのに対し、Slurm のこの機能は「始めたあとの時間の分け方」の話で、D4 の suspend を使って成り立っています。

| ID | できること | Slurm | Kueue | Volcano / YuniKorn / KAI |
|---|---|---|---|---|
| D1 | 最低人数がそろう場合だけ配置を確定する | ◯ [ジョブの単位そのもの](https://slurm.schedmd.com/quickstart.html) | △ ジョブ全体の資源量を [quota](https://kueue.sigs.k8s.io/docs/concepts/cluster_queue/) と照合するが、各 Pod を置けるかは kube-scheduler が個別に判断する | ◯ [Volcano の minAvailable](https://volcano.sh/en/docs/vcjob/)、[YuniKorn の task-groups](https://yunikorn.apache.org/docs/user_guide/gang_scheduling/)、[KAI の batch-min-member](https://github.com/kai-scheduler/KAI-Scheduler/blob/main/docs/batch/README.md)。ただし YuniKorn は既定の Soft だとタイムアウト後に通常配置に戻る |
| D2 | 上限を超えたジョブを待ち行列で待たせる | ◯ [アカウントごとの上限と QOS](https://slurm.schedmd.com/resource_limits.html) | ◯ [ClusterQueue の quota](https://kueue.sigs.k8s.io/docs/concepts/cluster_queue/) | ◯ [Volcano の Queue](https://volcano.sh/en/docs/queue/)、[YuniKorn のキューの上限](https://yunikorn.apache.org/docs/user_guide/queue_config)、[KAI の Queue](https://github.com/kai-scheduler/KAI-Scheduler/blob/main/docs/queues/README.md) |
| D4 | 動いているジョブのプロセスを一時停止し、同じ状態で後から再開する | ◯ [scontrol suspend と resume](https://slurm.schedmd.com/scontrol.html) | ✕ Kueue が使う [Job の suspend](https://kubernetes.io/docs/concepts/workloads/controllers/job/#suspending-a-job) は動いている Pod を削除する | ✕ Volcano の [vcctl job suspend](https://volcano.sh/en/docs/cli/) は再開時にジョブを作り直す。YuniKorn と KAI は、対応する機能を公式ドキュメントで確認できず |

この表の内容は、各製品のドキュメントを確認した時点のものです。バージョンが進むと変わる可能性があるため、最終判断は参考に挙げた一次資料の最新版で確認してください。

## Kueue の最近のアップデート

Kueue は、機能を足すマイナー版がおよそ 2 か月ごと、修正のパッチ版がおよそ毎週出ていて、2026 年 10 月 23 日の時点の最新は v0.20.3 です。ここ半年の機能追加のうち、この記事の D1 から D5 や、分散学習の運用に関わるものを 5 つ挙げます。どれも alpha か beta で、既定では無効のものが多いので、使う前に feature gate の状態を確かめてください。

| 機能 | 入った版 | 何が嬉しいか | 何に使えるか |
|---|---|---|---|
| [KueueDRADeviceFeasibility](https://github.com/kubernetes-sigs/kueue/pull/15577) | [v0.20.0](https://github.com/kubernetes-sigs/kueue/releases/tag/v0.20.0) で alpha、既定は無効 | 通す前に、ノードごとに DRA のデバイスの空きを確かめます。デバイスが足りないせいで kube-scheduler が置けないジョブのために、quota を確保してしまうことが減ります。 | DRA で GPU を要求するジョブの「通ったのに置けない」を減らす。device plugin の `nvidia.com/gpu` で要求するジョブや、CPU・メモリ・taint が原因で置けない場合は対象外。EKS で Karpenter と組むには、Karpenter 側の DRA 対応も要る |
| [DynamicQuotaOrchestration](https://github.com/kubernetes-sigs/kueue/pull/15283) | [v0.20.0](https://github.com/kubernetes-sigs/kueue/releases/tag/v0.20.0) で alpha、既定は無効 | 見つかった容量を、配下の Cohort と ClusterQueue に nominalQuota の比で配り、`status.effectiveQuotas` に書きます。nominalQuota は配分の比として人が決めますが、絶対値を容量の増減に合わせて書き換える作業は要らなくなります。 | ノード数が変わるクラスタで、ClusterQueue の枠を実際の容量に追従させる |
| [UnadmittedWorkloadsObservability](https://github.com/kubernetes-sigs/kueue/pull/12759) | [v0.19.0](https://github.com/kubernetes-sigs/kueue/releases/tag/v0.19.0) で追加、既定は無効 | 通っていないジョブについて、`WaitingForQuota` や `NoMatchingFlavor`、`ExceedsMaxQuota`、`TopologyPlacementFailed` のような理由を、Warning のイベントと、理由ごとに数えたメトリクスで出します。 | 「なぜこのジョブが待っているのか」を `kubectl get events` やダッシュボードで見分け、理由ごとにアラートを出す |
| [Concurrent Admission](https://github.com/kubernetes-sigs/kueue/pull/10610) | [v0.18.0](https://github.com/kubernetes-sigs/kueue/releases/tag/v0.18.0) で alpha、既定は無効 | リリースノートでは "migrate admitted Workloads between ResourceFlavors to chase the optimal available capacity" と説明されています。一度通したジョブを、より望ましい ResourceFlavor に空きが出たらそちらへ移します。 | 予備の ResourceFlavor で先に走らせておき、優先したい ResourceFlavor が空いたら移す。移る際に Pod が作り直されうるので、チェックポイントから再開できるジョブ向け |
| [ElasticJobsViaWorkloadSlices](https://kueue.sigs.k8s.io/docs/concepts/elastic_workload/) | [v0.18.0](https://github.com/kubernetes-sigs/kueue/releases/tag/v0.18.0) で beta に昇格 | 動いている Pod を止めずに、ジョブの Pod 数を増減できます。減らすときはその場で反映されます。増やすときは新しい大きさの Workload を作って通し、通った時点で古いものと入れ替えるので、増やす分は枠が空くまで待つことがあります。 | batch/v1 Job や RayJob、RayCluster の伸縮。ジョブ側に `kueue.x-k8s.io/elastic-job: "true"` の annotation が要る。TrainJob は対象に入っていない |

最初の 2 つは、この記事で何度か出てきた「Kueue が通しても、置けるとは限らない」という D1 の弱点のうち DRA デバイスの不足によるものと、quota の絶対値を手で決め続ける運用の負担を減らす変更です。どちらもまだ alpha なので、本番で頼る前に、自分の Kueue の版と feature gate の状態を確かめてください。

なお、DRA を使う 1 つ目の機能を EKS で活かすには、ノードを足す Karpenter も DRA の要求を理解する必要があります。Karpenter は既定では DRA の要求を無視します。NVIDIA GPU を DRA で扱う `DRANVIDIAGPU` の feature gate は、[v1.15 で alpha として入ったばかり](https://karpenter.sh/docs/reference/settings/)で既定は無効です。有効にするには `--ignore-dra-requests=false` の設定も要るので、本番で使える段階にはまだ来ていません。DRA を使う構成は、今後ワークショップの本で検証します。

# まとめ

Kueue は通してよいかだけを決めて D2 を埋め、配置は kube-scheduler に任せます。Volcano・YuniKorn・KAI-Scheduler は配置そのものを担当し、D1 と D2 を自分の Pod について埋めます。どれを選んでも、D4 のように止めたプロセスをそのまま再開することはできません。

最後に、D1 から D5 を各製品でどう指定するかを並べます。コマンドと設定名のリンク先が、それぞれの出典です。◯ は同じことができる、△ は近いが同じではない、✕ は対応する機能が無い、を表します。

| ID | 製品 | 投入・設定 | 備考 |
|---|---|---|---|
| D1 | Slurm | [`sbatch --nodes=4 --gpus-per-node=1 job.sh`](https://slurm.schedmd.com/sbatch.html) | ◯ 4 ノード分がそろってから始まる |
| D1 | Kueue | [ラベル `kueue.x-k8s.io/queue-name`](https://kueue.sigs.k8s.io/docs/tasks/run/jobs/) と [`waitForPodsReady` の `enable` と `blockAdmission`](https://kueue.sigs.k8s.io/docs/tasks/manage/setup_wait_for_pods_ready/) | △ quota の確保はジョブ単位で、Pod の配置は kube-scheduler が 1 つずつ行う |
| D1 | Volcano | [vcjob の `minAvailable`](https://volcano.sh/en/docs/vcjob/) | ◯ |
| D1 | YuniKorn | [annotation `yunikorn.apache.org/task-groups`](https://yunikorn.apache.org/docs/user_guide/gang_scheduling/) | ◯ 確実にするなら `gangSchedulingStyle=Hard` |
| D1 | KAI-Scheduler | [`schedulerName: kai-scheduler` とラベル `kai.scheduler/queue`](https://github.com/kai-scheduler/KAI-Scheduler/blob/main/docs/quickstart/README.md) | ◯ PodGroup は pod-grouper が作る。batch Job や JobSet で最低人数を決めるときは [`kai.scheduler/batch-min-member`](https://github.com/kai-scheduler/KAI-Scheduler/blob/main/docs/batch/README.md) を付ける |
| D2 | Slurm | [`sacctmgr modify account where name=team-a set GrpTRES=gres/gpu=8`](https://slurm.schedmd.com/resource_limits.html) | ◯ slurm.conf に `AccountingStorageEnforce=limits` が要る |
| D2 | Kueue | [ClusterQueue の `nominalQuota`](https://kueue.sigs.k8s.io/docs/concepts/cluster_queue/) | ◯ cohort で借りる設定にすると超えられる。超えさせないなら `borrowingLimit` も使う |
| D2 | Volcano | [Queue の `capability`](https://volcano.sh/en/docs/queue/) | ◯ |

| D3 | Slurm | [`SchedulerType=sched/backfill`](https://slurm.schedmd.com/sched_config.html) と sbatch の `--time` | ◯ 既定で有効。実行時間の上限から開始予定時刻を計算する |
| D3 | Kueue | [ClusterQueue の `queueingStrategy: BestEffortFIFO`](https://kueue.sigs.k8s.io/docs/concepts/cluster_queue/) | △ 先頭が入らないとき後ろの入るジョブを通すが、先頭の開始予定時刻は守らない |
| D3 | Volcano | [backfill action](https://volcano.sh/en/docs/actions/) | ✕ 資源量を指定しない Pod を隙間に入れる別の機能 |
| D3 | YuniKorn | 対応する機能を公式ドキュメントで確認できず | ✕ |
| D3 | KAI-Scheduler | 対応する機能を公式ドキュメントで確認できず | ✕ |
| D4 | Slurm | [`scontrol suspend 1234` と `scontrol resume 1234`](https://slurm.schedmd.com/scontrol.html) | ◯ 管理者の権限が要る |
| D4 | Kueue | 対応なし | ✕ suspend すると Pod が削除される |
| D4 | Volcano | [`vcctl job suspend` と `vcctl job resume`](https://volcano.sh/en/docs/cli/) | ✕ suspend すると Pod が削除され、resume で作り直される |
| D4 | YuniKorn | 対応なし | ✕ |
| D4 | KAI-Scheduler | 対応なし | ✕ |
| D5 | Slurm | [`PriorityType=priority/multifactor` と `PriorityWeightFairshare`](https://slurm.schedmd.com/priority_multifactor.html) | ◯ 利用実績の記録に slurmdbd を使う |

| D5 | Volcano | [`drf` と `proportion` のプラグイン](https://volcano.sh/en/docs/plugins/) | △ いま割り当てている量で配分する |

| D5 | KAI-Scheduler | [SchedulingShard の `usageDBConfig`](https://github.com/kai-scheduler/KAI-Scheduler/blob/main/docs/time-based-fairshare/README.md) | ◯ 既定では無効。Prometheus を有効にし、そこに貯めた使用量を使う |
