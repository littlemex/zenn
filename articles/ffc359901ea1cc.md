## はじめに

[前編](https://zenn.dev/tosshi/articles/81840c7c10dddd)では、NxD Inference にカスタムモデルを載せるための 3 つのインタフェースを紹介しました。この記事はその実装編で、音声合成モデル XTTS v2 を NxD Inference で動かすために何をしたのか、なぜそうする必要があったのかを、図でまとめます。実装は [littlemex/samples の xttsv2-nxd-inference](https://github.com/littlemex/samples/tree/b6334caf1f46c549bb58905a7a39000d5aba5db2/ml_distributed_experiment_collection/xttsv2-nxd-inference) にあります。

| 前編のインタフェース | 前編で作った実体 | この記事での使い方 |
| --- | --- | --- |
| nn.Module | `NeuronGPTTransformer`（30 層） | そのまま使い、GPT-2 の最終の LayerNorm はブリッジ側に置く |
| ModelWrapper | `ModelWrapperGPTPrefill` と `ModelWrapperGPTDecode` | そのまま使い、ブリッジが prefill と decode の入力を作る |
| NeuronApplicationBase | `NeuronApplicationBase` を継承した prefill と decode の Application と、それを持つ `NeuronApplicationXTTSv2GPT` | prefill の直後に、ブリッジが KV の受け渡しを呼ぶ |

この記事で新しく書いたのは、Hugging Face の `generate()` と前編の Application をつなぐブリッジのクラス `NeuronGPT2InferenceModel` です。

## XTTS v2 の構造

![XTTS v2 は参照音声と文を GPT デコーダに渡し、CPU の出力層とサンプリングで音声トークンを 1 つずつ選び、HiFi-GAN で波形にする。Neuron に載せるのは GPT デコーダだけ](/images/ffc359901ea1cc-xtts-structure.png)

XTTS v2 は、参照音声を CPU の ConditioningEncoder と PerceiverResampler で話者の条件（speaker prompt）に変え、文のトークンと並べて GPT デコーダに渡します。GPT デコーダは隠れ状態を返し、CPU の出力層とサンプリングが次の音声トークンを選び、その埋め込みを次のステップに渡します。これを EOS まで繰り返し、最後に HiFi-GAN で波形にします。[前編](https://zenn.dev/tosshi/articles/81840c7c10dddd)で見たとおり、推論の時間の大半はこの 1 トークンずつの生成に使われるので、Neuron に載せるのは 30 層の GPT デコーダだけにしました。Neuron はコンパイル時に入力の形を固定するので、系列の上限を、話者の条件に 70、文に開始と終了のトークン込みで 404、音声に同じく 607 の、合計 1081 位置に決めています。

## ブリッジで何をしているか

![Coqui TTS は generate() の前にブリッジの store_prefix_emb() で prefill を呼び、generate() からの forward() で decode を呼ぶ。KV は prefill_app から decode_app へ写す](/images/ffc359901ea1cc-bridge.png)

Coqui TTS と前編の Application をつなぐために新しく書いたのが、[`NeuronGPT2InferenceModel`](https://github.com/littlemex/samples/blob/b6334caf1f46c549bb58905a7a39000d5aba5db2/ml_distributed_experiment_collection/xttsv2-nxd-inference/src/neuron_xttsv2/neuron_xttsv2.py) というブリッジのクラスです。XTTS v2 の `synthesize()` は Hugging Face の `generate()` で生成ループを回すので、ブリッジを Hugging Face のモデルとして振る舞わせれば、ループも Coqui TTS のコードも変えずに済みます。差し込みは、XTTS v2 がもともと持っている `gpt.gpt_inference` という差し替え口にブリッジを代入するだけです（[e2e_xttsv2_neuron.py](https://github.com/littlemex/samples/blob/b6334caf1f46c549bb58905a7a39000d5aba5db2/ml_distributed_experiment_collection/xttsv2-nxd-inference/examples/e2e_xttsv2_neuron.py#L143-L156)）。

## NxD のインタフェースに合わせ込んだところ

この節では、SDK 2.28 の NxD Inference の決まりと、この実装が選んだ構成に、Hugging Face と XTTS v2 の動きをどう合わせたかをまとめます。前提として、この実装は prefill と decode を別々の Application にしています。`NeuronApplicationBase` は trace したモデルを 1 つしか持たないので、1 つの Application が持てる ModelWrapper も 1 つです。1 つの nn.Module を 2 つの形で trace して 1 つの Application にまとめる方式（Whisper の方式）なら、KV のバッファが 1 つで済み、写す処理も要りません。別々にすると KV の受け渡しが明示的になり、prefill と decode を別の場所で動かす構成へ広げる余地ができますが、今回は同じインスタンスの中で、CPU を経由して KV を写しています。

| Neuron 側の前提 | Hugging Face と XTTS v2 の動き | 合わせ方と実装の場所 |
| --- | --- | --- |
| 入力の形はコンパイル時に固定する（NxD） | 文と話者によって prefix の長さが変わる | prefill では prefix を 1081 位置まで 0 で埋め、マスクで有効な範囲を示す。decode では 1 トークンの埋め込み、書き込む位置、書き込む位置までを有効にした 1081 位置のマスクを渡す（ブリッジ） |
| KV は aliases の仕組みで NeuronCore のデバイスメモリ上で更新され、Application の `forward()` は隠れ状態だけを返す（NxD） | `generate()` は `forward()` が返した `past_key_values` を次のステップに渡す | 中身の無い `past_key_values` を返し、`prepare_inputs_for_generation()` がそれを見て最後の 1 トークンだけを渡す（ブリッジ） |
| prefill と decode は別の Application で、KV のバッファも別（この実装の構成） | `synthesize()` は `generate()` の前に prefix を処理する | prefill の KV を `.state` から CPU に読み出し、0 で埋めた位置に残る bias 由来の値を消して、decode 側へ書き込む（[`sync_kv_cache_prefill_to_decode()`](https://github.com/littlemex/samples/blob/b6334caf1f46c549bb58905a7a39000d5aba5db2/ml_distributed_experiment_collection/xttsv2-nxd-inference/src/neuron_xttsv2/application_gpt.py#L228)） |
| KV に書く位置は呼び出し側が渡す（NxD） | `generate()` の最初の呼び出しは prefix を含む全体を渡してくる | ブリッジが書き込み位置を数え、最初の呼び出しでは KV にある prefix を飛ばす（ブリッジ） |
| 重みは分割前の全体を渡すと、NxD が Tensor Parallel に分けて載せる。KV は aliases が管理する（NxD） | Coqui の GPT-2 の重みは Q、K、V が 1 つにまとまった `Conv1D` の形 | Q、K、V に分けて転置する（`state_dict.py`）。`get_state_dict()` はコンパイルのときは 0 の重みを返し、`cache_k` と `cache_v` は入れない。実際の重みはコンパイルのあとに `app.load_weights()` で prefill と decode の両方に載せる（`application_gpt.py`） |
| `NeuronGPTTransformer` は最終の LayerNorm を持たない（この実装の構成） | Coqui の GPT-2 は最終の LayerNorm を内側に持つ | GPT-2 の最終の LayerNorm（`ln_f`）を、XTTS v2 の `final_norm` と出力層の前に置き、この順で適用する（ブリッジ） |

NxD Inference は入力の形も KV キャッシュも自分で持つので、**ブリッジは Hugging Face に「キャッシュはある」とだけ伝え、KV に書く位置と生成の状態を自分で数えます**。

## 1 回の音声生成の流れ

![ブリッジは prefix を prefill_app に一度で流し、KV を CPU 経由で decode_app へ写したあと、1 ステップに 1 トークンずつ decode_app を呼ぶ](/images/ffc359901ea1cc-xtts-utterance-flow.gif)

Coqui TTS は `generate()` の前にブリッジの `store_prefix_emb()` を呼びます。`store_prefix_emb()` は、話者の条件、文、音声の開始トークンまでの prefix を `prefill_app` に一度で流して KV を作り、それを `decode_app` 側へ写します。`generate()` の最初の `forward()` は prefix を含む全体を渡してくるので、ブリッジはすでに KV にある prefix を飛ばし、その後ろの新しいトークンを 1 つずつ `decode_app` に渡します。以降のステップでは、`forward()` 1 回につき 1 トークンの埋め込みを作って `decode_app` に渡し、返ってきた隠れ状態を CPU の出力層で logits にします。EOS で止めるのは `generate()` です。`store_prefix_emb()` は、保持する prefix と書き込み位置を毎回置き直すので、発話ごとに `synthesize()` を呼べば前の発話の位置は残りません。`store_prefix_emb()` を通さずに `generate()` を直接呼ぶ場合は、書き込み位置と保持している prefix を初期値に戻してから呼びます。

::::details 重みの変換と位置の埋め込みの注意点

後で出てくる重みの注入、コンパイルの出力先、スワップの注意は、手順の中に書いています。ここでは、CPU 版の計算に合わせるときの注意だけを補います。

- 転置したあとの重みの連続化。`.contiguous()` を付けないと、重みを分割する処理の中の `view()` が失敗します
- チェックポイントの読み込み。XTTS v2 のチェックポイントには設定のオブジェクトが入っているので、`torch.load()` に `weights_only=False` が必要です
- 音声トークンの位置の埋め込み。ブリッジは KV 全体の位置ではなく、音声の列の中の位置（書き込み位置から prefix の長さを引いた値）を XTTS v2 の音声の位置の埋め込みに渡します

::::

### Procedure 4: 重みが正しく注入されているかの確認

コンパイル後、実際の重みが Neuron モデルに注入されるかを確認します。以下のスクリプトを実行し、出力の `std` の値に着目してください。

```bash
python3 - <<'EOF'
import sys, os, torch

SRC_PATH      = os.environ.get('SRC_PATH',      '/home/ubuntu/nxd-inference-xttsv2/src')
COMPILED_PATH = os.environ.get('COMPILED_PATH', '/home/ubuntu/neuron_xttsv2_compiled_bf16')
CKPT_PATH     = os.environ.get('CKPT_PATH',     '/home/ubuntu/xttsv2-model/model.pth')

sys.path.insert(0, SRC_PATH)
from neuron_xttsv2.config import XTTSv2InferenceConfig
from neuron_xttsv2.application_gpt import NeuronApplicationXTTSv2GPT
from neuronx_distributed_inference.models.config import NeuronConfig

nc  = NeuronConfig(batch_size=1, tp_degree=2, seq_len=1081, torch_dtype=torch.bfloat16)
cfg = XTTSv2InferenceConfig(neuron_config=nc)

app = NeuronApplicationXTTSv2GPT(model_path=COMPILED_PATH, config=cfg)
app.load(COMPILED_PATH, skip_warmup=True)
app.load_weights(CKPT_PATH, tp_degree=2)

h    = torch.randn(1, 1081, 1024, dtype=torch.bfloat16)
last = torch.tensor([1080], dtype=torch.int32).expand(1)
mask = torch.ones(1, 1081, dtype=torch.int32)

out  = app.prefill_app(h, last, mask)
print(f'[OK] prefill output: mean={out.mean():.4f}, std={out.std():.4f}')
EOF
```

期待される出力と解釈は以下のとおりです。

```text
[OK] prefill output: mean=1.0312, std=25.3750
```

`std` が 0.1 以下であればゼロ重みのままであり、重みのロードが失敗しています。この実行では `std` が 25.375 で、0.1 を大きく超えています。入力は乱数なので、再実行で同じ値になる必要はありません。この表示は出力が 0 のままになっていないかを見る簡単な確認で、重みが正しいことまでは、続く Procedure 5 の E2E の結果で確かめます。

:::message alert
`traced_model.load_state_dict()` を TP モデルに対して使用してはいけません。テンソルの shape 不一致が原因でサイレントにスキップされ、ゼロ重みのまま推論が走ります。重みの注入には必ず `app.load_weights()` を使用してください。これが内部で `shard_checkpoint()` を経由して `nxd_model.initialize()` を正しく呼ぶパスになっています。

### Procedure 5: E2E 推論（CPU vs Neuron 比較）

::::details torchaudio の互換性問題への対処

PyTorch 2.9 + torchaudio 2.9 の組み合わせでは、音声ファイルの読み込みに `torchcodec` が要求される場合があります。`torchcodec` が環境にない場合は以下のモンキーパッチで `soundfile` に差し替えることで回避できます。スクリプトの冒頭で適用してください。

```python
import soundfile as sf_lib
import torch
import torchaudio

def load_audio_sf(path, sr=None):
    wav, orig_sr = sf_lib.read(path, dtype='float32', always_2d=True)
    wav = torch.from_numpy(wav.T)
    if sr and sr != orig_sr:
        wav = torchaudio.functional.resample(wav, orig_sr, sr)
        orig_sr = sr
    return wav, orig_sr

torchaudio.load = load_audio_sf
```

## 結果

数値の型は BF16 にしています。FP16 でコンパイルした別の実行（trn1.2xlarge、Tensor Parallel 2）では、同じトークンを繰り返す音声になり、WER が 68.8% でした。FP16 の指数部は 5 bit で、attention の softmax の前の値が表せる範囲を超えやすいためと考えています。BF16 の指数部は FP32 と同じ 8 bit です。

次の表は、Procedure 6 の `test_long_text_script.py` を trn1.2xlarge で 1 回実行した出力から取った値です。CPU は同じインスタンスの同じスクリプトで動かし、Neuron は Tensor Parallel 2、BF16 です。WER は、Whisper large-v2 の書き起こしと参照文を、小文字にして英数字以外を除いてから比べた単語の誤り率です。RTF は音声の長さを生成にかかった時間で割った値で、CPU 比の速さは同じ入力文に対する CPU の生成時間を Neuron の生成時間で割った値です。

| テスト | 単語数 | CPU WER | Neuron WER | 音声長（CPU） | 音声長（Neuron） | CPU 時間 | Neuron 時間 | RTF | CPU 比の速さ |
|---|---|---|---|---|---|---|---|---|---|
| short | 5 | 0.0% | 0.0% | 3.10s | 3.38s | 4.2s | 1.6s | 2.12x | 2.7x |
| medium | 18 | 55.6% | 33.3% | 18.85s | 11.56s | 24.8s | 4.1s | 2.81x | 6.0x |
| long | 24 | 4.2% | 4.2% | 13.74s | 15.69s | 18.2s | 5.5s | 2.84x | 3.3x |

short と long では、CPU と Neuron の WER が一致しました。medium では、音声の長さも CPU が 18.85s、Neuron が 11.56s と違い、CPU の書き起こしには入力に無い語が続いています。この 1 回の実行では、この差が生成した音声によるものか、Whisper の書き起こしによるものかは切り分けていません。3 ケースの速さの倍率の平均は 4.0 倍です。ただし CPU と Neuron で作った音声の長さが違うので、medium の 6.0 倍には、CPU が 1.6 倍長い音声を作った分が入っています。音声 1 秒あたりの生成時間で比べると、Neuron は short で約 2.9 倍、medium で約 3.7 倍、long で約 3.8 倍速く、RTF は 2.12〜2.84 で音声の長さより 2 倍以上速く生成できています。

## まとめ

XTTS v2 を NxD Inference に載せる鍵は、生成ループを Hugging Face に任せたまま、新しいブリッジのクラスで NxD Inference の静的な形とデバイスの上の KV キャッシュに合わせ、この実装で分けた prefill と decode の間の KV の受け渡しと重みの変換を足すことでした。
