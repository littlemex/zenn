## はじめに

NCCL のリリース一覧には、NCCL4Py の版と、NCCL EP の最初の版が並んでいます。名前が似ているので、どれが何なのかが分かりにくいと思います。この記事では、3 つがそれぞれ何を受け持ち、どうつながっているかを図で見ていきます。後半の「[配布物の中身](#配布物の中身)」では、配布物の中のライブラリとソースコードを読み、それぞれのコードが何を受け持っているかを、GPU の無い機械で読み込みの動きを確かめながら整理します。

## 登場する部品

![サーバーと Linux の上に NCCL 本体が載り、その上に NCCL4Py と NCCL EP が載る](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/8195cc2bbe4888/zenn/articles/8195cc2bbe4888/stack.png)

1 台の GPU サーバーの上には、次の部品が載っています。NCCL4Py と NCCL EP は、どちらも NCCL 本体のすぐ上に並びます。

| 部品 | 中身 | 入れ方 |
|---|---|---|
| NCCL 本体 | GPU どうしの通信を受け持つライブラリ | nccl4py などに CUDA 12 か 13 を指定して入れる |
| NCCL4Py | NCCL 本体を Python から呼ぶ窓口 | nccl4py を入れる |
| NCCL EP | MoE の通信を受け持つライブラリ | nccl-extensions を入れる |
| NCCL EP の Python の窓口 | NCCL EP を Python から呼ぶ窓口 | nccl-extensions を入れる |

NCCL 本体と NCCL4Py は、NVIDIA の NCCL のリポジトリで作られています。NCCL EP とその Python の窓口は、別のリポジトリで作られています。名前は nccl-extensions です。

## NCCL: GPU どうしの通信を受け持つ

![4 枚の GPU が値を出し合い、全員が合計の 10 を受け取る](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/8195cc2bbe4888/zenn/articles/8195cc2bbe4888/allreduce.png)

たくさんの GPU で 1 つのモデルを学習するとき、GPU どうしで計算の結果を足し合わせます。NCCL は、この GPU 間のやり取りを速く行うためのライブラリです。図の all-reduce は代表的な操作で、参加した GPU の値をまとめ、同じ結果を全員に渡します。

PyTorch で分散学習をするとき、通信の方式に NCCL を選べます。そうすると、PyTorch の中で NCCL が動きます。そのため、NCCL を直接呼ばなくても使えます。

## NCCL EP: 送る所と戻す所を受け持つ

MoE でトークンを担当のエキスパートの GPU へ送る dispatch と、結果を元の GPU へ戻す combine、そしてそれを支える通信の層は「[MoE の all-to-all を支える層](https://zenn.dev/tosshi/articles/a0f5ff21eed405)」で説明しています。ここでは、その dispatch と combine を NCCL EP がどう受け持つかを見ます。

![NCCL EP が受け持つのは dispatch と combine で、エキスパートの計算はモデルのプログラムが受け持つ](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/8195cc2bbe4888/zenn/articles/8195cc2bbe4888/ep-role.png)

NCCL EP の EP は、エキスパート並列 (Expert Parallelism) の略です。NCCL EP は、dispatch と combine の 2 つの操作を受け持つライブラリです。エキスパートの計算そのものは、NCCL EP ではなくモデルのプログラムが受け持ちます。

NCCL EP は、NCCL 本体の機能の上に作られています。その機能の 1 つが、GPU の計算の途中から、ほかの GPU との通信を直接始める仕組みです。

## NCCL EP の 2 つのモード

![Low-Latency モードは少ないトークンを直接送り、High-Throughput モードはたくさんのトークンをノードの中でまとめてから送る](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/8195cc2bbe4888/zenn/articles/8195cc2bbe4888/modes.png)

NCCL EP には、Low-Latency と High-Throughput の 2 つのモードがあります。[NCCL EP の README](https://github.com/NVIDIA/nccl-extensions/blob/e57f0dad43dc1ca5bf96f09bf4075afc2eae6599/nccl_ep/README.md) では、Low-Latency は待ち時間が大事な推論向けとされています。こちらは、流すトークンが少ないときに使います。High-Throughput は、学習と、推論で最初に入力をまとめて読む段階向けです。2 つは、向くトークンの量だけでなく、送り方も違います。High-Throughput は、ノードの中で一度まとめてから、ほかのノードへ送ります。

## NCCL4Py: Python から NCCL を呼ぶ窓口

![NCCL4Py は Python のプログラムから呼ばれ、NCCL 本体を呼ぶ](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/8195cc2bbe4888/zenn/articles/8195cc2bbe4888/window.png)

NCCL 本体には、C 言語から呼ぶための入口があります。NCCL4Py は、その NCCL 本体を Python から呼べるようにした公式の窓口です。NCCL 2.29.2 で試験的に入り、その後は本体とは別の番号で版を重ねています。

最近の NCCL4Py の版は、それぞれ特定の版の NCCL 本体に合わせて作られています。たとえば NCCL4Py v0.6.0 は、NCCL 2.32.3 に合わせて作られています。

## nccl という名前を 2 つの配布物で分け合う

![Python の nccl という名前の下に、nccl4py と nccl-extensions がそれぞれ中身を置く](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/8195cc2bbe4888/zenn/articles/8195cc2bbe4888/namespace.png)

Python では、どちらも nccl という名前で読み込みます。その下に、読み込むときの名前を 2 つの配布物が置きます。nccl4py は nccl.core を、nccl-extensions は nccl.ep を置きます。1 つの名前を複数の配布物で分け合う、Python の仕組みを使っています。

nccl-extensions は nccl4py に依存しています。そのため、入れると nccl4py も一緒に入ります。nccl.m2n は、同じ nccl-extensions に入っている NCCL M2N の窓口です。NCCL M2N は、2 つの GPU の群の間でデータを配り直す、試験的なライブラリです。学習側の GPU から推論側の GPU へ重みを送る用途があります。

## 版の組み合わせに気をつける

![CUDA 12 か 13 を指定すると nccl-extensions は NCCL 2.30.7 に固定し、一緒に選ばれる NCCL4Py v0.6.0 は NCCL 2.32.3 を基に作られている](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/8195cc2bbe4888/zenn/articles/8195cc2bbe4888/versions.png)

nccl-extensions v0.1.0 が対応する NCCL 本体は、2.30.7 だけです。**CUDA 12 か 13 を指定して入れると、NCCL 本体は 2.30.7 に固定されます。** 一方、nccl-extensions は NCCL4Py の版を指定していません。新しい環境に入れると、最新の NCCL4Py が選ばれます。2026 年 10 月 19 日時点でも v0.6.0 です。

NCCL4Py v0.6.0 は、NCCL 2.32.3 を基に作られています。NCCL4Py v0.6.0 が NCCL 本体に探しに行く 93 個の関数のうち、79 個は 2.30.7 の本体にあり、残る 14 個は 2.30.7 には無く 2.32.3 にはあります。調べた本体はこの 2 つの版だけです。この組み合わせで実際に動かして確かめた結果は、後の「[配布物の中身](#配布物の中身)」で示します。

GPU の側で動く試験的な機能には、もっと厳しい条件があります。NCCL4Py の [`nccl.core.device.cute`](https://github.com/NVIDIA/nccl/blob/893470119efc83fb6ecd4f9240efcf60c0aef6a3/bindings/nccl4py/nccl/core/device/cute/__init__.py#L9-L15) は、GPU のカーネルから NCCL を使うための試験的な窓口です。その説明には、使う `libnccl_device.bc` が NCCL4Py を作ったときの NCCL と完全に同じ版でなければならず、版の確認はしない、と書かれています。`libnccl_device.bc` は `nvidia-nccl` の配布物に入っているので、`NCCL_HOME` を自分で設定していなければ、nccl-extensions が選ぶ組み合わせでは 2.30.7 のものが使われ、NCCL4Py の 2.32.3 と一致しません。そうした機能を試す環境と、NCCL EP を使う環境は、分けておくのが安全です。

nccl-extensions の main ブランチでは、この制約を緩める変更が進んでいます。[NCCL EP の README](https://github.com/NVIDIA/nccl-extensions/blob/25c0638e22132e1fc8c0648e1d52010838c3e528/nccl_ep/README.md#nccl-ep-compatibility-with-newer-nccl-runtimes) には、2.31 以降で作ったものは新しい NCCL 本体でそのまま動き、2.30.5 以上 2.31 未満で作ったものは `NCCL_DEV_API_JIT` を有効にすれば動く、と書かれました。ただし 2026 年 10 月 19 日時点ではまだリリースに入っておらず、main の[依存関係の定義](https://github.com/NVIDIA/nccl-extensions/blob/25c0638e22132e1fc8c0648e1d52010838c3e528/python/pyproject.toml#L52-L60)も NCCL 本体を 2.30.7 に固定したままです。

NCCL EP には、動くときに GPU のプログラムをその場で組み立てる処理があります。そのため、CUDA の開発道具も必要です。開発道具も、CUDA 12 か 13 かを指定した版にそろえます。配布されている NCCL4Py を入れるだけなら、この開発道具は要りません。

## NCCL4Py v0.3.1 のころといま

![v0.3.1 では nccl4py の中に nccl.ep があり、いまは nccl-extensions の中にある](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/8195cc2bbe4888/zenn/articles/8195cc2bbe4888/then-now.png)

[NCCL4Py v0.3.1](https://github.com/NVIDIA/nccl/releases/tag/nccl4py-v0.3.1) には、nccl.ep と、NCCL EP のライブラリそのものが同梱されていました。ただし同梱の NCCL EP は CUDA 13 向けで、CUDA 12 の環境では自分で用意する必要がありました。2026 年 9 月 3 日には [v0.3.1.post1](https://pypi.org/project/nccl4py/0.3.1.post1/) が PyPI に出ています。中身は v0.3.1 と同じく nccl.ep を含みます。v0.3.1 は依存する NCCL 本体の版を固定していませんでしたが、v0.3.1.post1 は 2.30.4 に固定しています。

![2026 年 4 月公開の NCCL 2.30.3 に収録され、9 月に nccl-extensions から配られた](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/8195cc2bbe4888/zenn/articles/8195cc2bbe4888/timeline.png)

[NCCL4Py v0.4.1](https://github.com/NVIDIA/nccl/releases/tag/nccl4py-v0.4.1) で、nccl.ep は NCCL4Py から外れました。いまは [nccl-extensions v0.1.0](https://github.com/NVIDIA/nccl-extensions/releases/tag/nccl-extensions-v0.1.0) が、NCCL EP v0.2 を配っています。nccl.ep も、こちらに入っています。v0.3.1 で nccl.ep を使っていたプログラムがあるとします。新しい NCCL4Py で動かすには、nccl-extensions も入れます。nccl.ep の使い方は変わりうると、当時から書かれていました。そのため、書き直しが要ることもあります。

v0.3.1 は、自分の中に nccl.ep を持っています。nccl-extensions は NCCL4Py の版を指定しないので、足しても v0.3.1 は残ります。すると、2 つの nccl.ep が同じ置き場所でぶつかります。実際に v0.3.1 の環境へ pip で `nccl-extensions[cu13]==0.1.0` を足すと、NCCL4Py は v0.3.1 のまま残り、`nccl/ep` の持ち主として 2 つの配布物が記録されました。v0.3.1.post1 の環境では結果が違い、NCCL 本体の固定が 2.30.4 と 2.30.7 でぶつかるため、pip は NCCL4Py を v0.6.0 に入れ替えました。どちらの場合も、古い環境に足すより、新しい環境を作って入れるのが確実です。

## やりたいことから選ぶ

![PyTorch の標準の学習なら PyTorch の分散機能、Python から直接なら NCCL4Py、MoE なら NCCL EP、C なら NCCL 本体](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/8195cc2bbe4888/zenn/articles/8195cc2bbe4888/choose.png)

3 つは、どれか 1 つだけを選ぶ関係ではありません。自分がどの処理を直接書きたいかで、意識する相手が決まります。PyTorch で標準の分散学習をするだけなら、どれも直接は触りません。

## 各部品の受け持ち

| 部品 | 受け持ち | 使う人 | 実体 |
|---|---|---|---|
| NCCL 本体 | GPU どうしの通信 | PyTorch などのフレームワーク、C と CUDA で書く人 | `libnccl.so.2` |
| NCCL4Py | Python から NCCL 本体を呼ぶ | Python から NCCL を直接使う人 | `nccl.core` と `nccl.bindings` |
| NCCL EP | MoE の dispatch と combine | MoE の通信を組み込む人 | `libnccl_ep.so` |
| NCCL EP の Python の窓口 | Python から NCCL EP を呼ぶ。nccl-extensions が配る | Python から NCCL EP を使う人 | `nccl.ep` と `nccl._extensions.bindings` |

## 配布物の中身

ここからは、3 つの配布物の中のコードが、それぞれ何を受け持っているかを見ます。調べたのは、nccl-extensions を CUDA 13 の指定で入れたときに選ばれる組み合わせで、NCCL4Py v0.6.0、nccl-extensions v0.1.0、nvidia-nccl-cu13 2.30.7 と、一緒に入った cuda-bindings 13.4.4、cuda-pathfinder 1.8.3 です。中身は pip の配布ファイルを展開して調べ、ソースは commit を固定したリンクで示します。

先に、この節で使う言葉を説明します。通信路は NCCL の communicator のことで、通信に参加する GPU の顔ぶれと、通信に必要な状態をまとめたものです。NCCL4Py では Python の `Communicator` として扱います。共有ライブラリは、プログラムが動くときに読み込むコンパイル済みのコードで、Linux では `.so` という名前のファイルで配られます。このうち Python の `import` で読み込める形にしたものを拡張モジュールと呼び、`nccl.cpython-312-x86_64-linux-gnu.so` のように Python の版が名前に入っています。Cython は、Python に近い書き方で C の関数を呼ぶ拡張モジュールを作る言語です。

![You、Python API、Bindings、Native、Driver の 5 段。左の列は nccl4py と nvidia-nccl、右の列は nccl-extensions。nccl.core から nccl.ep へ comm.ptr を渡し、nccl._extensions は先に nccl.bindings に libnccl を読み込ませる。Bindings から Native へは実行中に開き、libnccl_ep.so は libnccl.so.2 と libcuda.so.1 をリンクし、libnccl.so.2 は libcuda.so.1 を実行中に開く](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/8195cc2bbe4888/zenn/articles/8195cc2bbe4888/roles.png)

図の左の段の名前で見ると、You の段 (緑) は自分で書くプログラムです。Python API の段と Native の段 (青) は、使う人が呼ぶ Python の窓口と、通信を実際に行うネイティブのライブラリです。Bindings の段 (黄) は、その間を橋渡しするコードです。Driver の段 (灰) は GPU のドライバです。緑の段のほかは、どれも NVIDIA が配っています。

図の links は、そのライブラリが依存するライブラリの一覧に書かれていることを表します。この一覧は `.so` の中に書かれていて、Linux の動的リンカーが `.so` を読み込むときに一緒に探して読み込みます。破線は、一覧には書かれておらず、動いている途中で `dlopen` という関数で開くことを表します。ラベルの無い実線は、上の段のコードが下の段を呼ぶことを表します。段はコードの種類でそろえているので、NCCL EP が NCCL 本体の上に載る関係は、`libnccl_ep.so` から `libnccl.so.2` への links で表しています。

### nvidia-nccl: NCCL 本体

次の表は、nvidia-nccl-cu13 2.30.7 の配布物を調べた結果です。

| 置き場所 | 受け持ち |
|---|---|
| `nvidia/nccl/lib/libnccl.so.2` | NCCL 本体。通信路の作成と、all-reduce などの集団通信と、GPU のカーネルから通信を始める Device API。`nccl` で始まる C の関数を 83 個公開 |
| `nvidia/nccl/include/` | `nccl.h` と Device API のヘッダー。ヘッダーは、関数の名前と引数と型の宣言を書いたファイルで、C と CUDA から NCCL を使うプログラムを作るときに読む |
| `nvidia/nccl/lib/libnccl_device.bc` | Device API の GPU 側のコード。NCCL4Py の試験的な `nccl.core.device.cute` が使う |

`libnccl.so.2` の依存の一覧には、`libcuda.so.1` も CUDA のランタイムも書かれていません。GPU のドライバは、通信路を作るときなどに NCCL 本体が自分で開きます。そのため NCCL4Py は、GPU の無い機械でも読み込んで版を問い合わせられます。

| [`nccl.bindings._internal.nccl`](https://github.com/NVIDIA/nccl/blob/893470119efc83fb6ecd4f9240efcf60c0aef6a3/bindings/nccl4py/nccl/bindings/_internal/nccl_linux.pyx#L1146-L1148) | NCCL 本体を探して開き、93 個の関数の場所を集めて持つ |

`cynccl` の目的は [NCCL4Py の README](https://github.com/NVIDIA/nccl/blob/893470119efc83fb6ecd4f9240efcf60c0aef6a3/bindings/nccl4py/README.md#L37-L46) に書かれていて、Cython の拡張モジュールから Python の負担を小さくして NCCL を呼ぶための試験的な API です。`nccl.bindings.nccl`、`nccl.bindings.cynccl`、`nccl.bindings._internal.nccl` の 3 段の分け方は、NVIDIA の cuda-python の `cuda.bindings` と同じで、たとえば [nvJitLink の窓口](https://github.com/NVIDIA/cuda-python/blob/308e4e17991fa9cc8fd5d9ac76619317f948b3e6/cuda_bindings/cuda/bindings/_internal/nvjitlink_linux.pyx#L94)も同じ形をしています。

`nccl.bindings._internal.nccl` は、`import` のときではなく、最初に NCCL の関数を呼んだときに働きます。関数をまずプロセスの中にすでにあるものから探し、見つからないときに NCCL 本体のファイルを探して開きます。ファイルの探し方は [`cuda.pathfinder`](https://github.com/NVIDIA/cuda-python/blob/308e4e17991fa9cc8fd5d9ac76619317f948b3e6/cuda_pathfinder/cuda/pathfinder/_dynamic_libs/load_nvidia_dynamic_lib.py#L165-L198) に任せています。それでも見つからない関数は場所が空のまま残り、その関数を呼んだときに初めてエラーになります。

### libnccl_ep.so: EP の通信処理

`libnccl_ep.so` は、MoE の dispatch と combine を GPU のカーネルで行う NCCL EP の本体です。C の入口は [`nccl_ep.h`](https://github.com/NVIDIA/nccl-extensions/blob/e57f0dad43dc1ca5bf96f09bf4075afc2eae6599/nccl_ep/include/nccl_ep.h) にあり、調べた nccl-extensions v0.1.0 の CUDA 13 向けのものは、`ncclEp` で始まる関数を 18 個公開しています。使う順に主なものを並べます。

| 関数 | 受け持ち |

`libnccl_ep.so` の依存の一覧には `libnccl.so.2` と `libcuda.so.1` が書かれていて、NCCL 本体の関数を 18 個使います。`ncclDevCommCreate`、`ncclCommWindowRegister`、`ncclTeamLsa` のような Device API に関わる関数と、`ncclAllGather`、`ncclAllReduce` のような集団通信と、`ncclMemAlloc` などです。GPU のドライバからは、`cuModuleLoadDataEx` や `cuLaunchKernel` など、GPU のプログラムを読み込んで起動する関数を 10 個使います。dispatch と combine の中でこれらがどう使われているかまでは、この記事では読んでいません。

前半で触れた CUDA の開発道具は、カーネルの一部を初めて使うときに組み立てるためのものです。[NCCL EP の README](https://github.com/NVIDIA/nccl-extensions/blob/e57f0dad43dc1ca5bf96f09bf4075afc2eae6599/nccl_ep/README.md#L326-L331) によれば、そのために CUDA のコンパイラである `nvcc` と、カーネルと NCCL と CUDA のヘッダーと、書き込めるキャッシュのディレクトリ (既定は `/tmp/nccl_ep/jit`) が要ります。[`nccl.ep` を読み込むと](https://github.com/NVIDIA/nccl-extensions/blob/e57f0dad43dc1ca5bf96f09bf4075afc2eae6599/python/nccl/ep/__init__.py#L19-L31)、`NCCL_EP_HOME` と `NCCL_HOME` がまだ設定されていなければ、nccl-extensions と `nvidia-nccl` の場所が入ります。すでに設定している場合は、その値が使われます。

`libnccl_ep.so` は NCCL 本体を直接呼ぶので、NCCL EP の窓口は、`libnccl_ep.so` を開く前に NCCL4Py に NCCL 本体を開かせます。図の loads libnccl first の矢印がこれに当たります。理由と、確かめた結果は、後の details に置きました。

### 確かめたこと

GPU の無い x86_64 の Linux の機械に nccl-extensions の v0.1.0 を CUDA 13 の指定で入れ、2026 年 10 月 19 日に次のことを確かめました。

| 確かめたこと | 結果 |
|---|---|
| `import nccl.core` だけで NCCL 本体を読み込むか | 読み込まない。`get_version()` を呼んだ後に読み込み済み |
| NCCL4Py v0.6.0 が探す 93 個の関数は、2.30.7 の本体にあるか | 79 個がある。残る 14 個は、2.32.3 の本体にはあり、2.30.7 には無い。調べた本体はこの 2 つの版だけ |
| 2.30.7 に無い関数を呼ぶとどうなるか | `set_encryption(0)` で `FunctionNotFoundError`。`import` と `get_version()` は通る。14 個のうち呼んだのは `ncclSetEncryption` だけ |
| NCCL EP は動くか | GPU の無い機械なので、`libnccl_ep.so` を開く段階で `libcuda.so.1` が見つからずに止まる。dispatch と combine は確かめていない |

どの NCCL 本体が使われているかは、手元で次のように確かめられます。新しく作ったディレクトリ `/tmp/ncclblog` で実行しました。パスは実行した場所で変わります。

```bash
uv venv .venv --python 3.12
uv pip install --python .venv/bin/python "nccl-extensions[cu13]==0.1.0"
.venv/bin/python -c "import nccl.core; nccl.core.show_versions()"
```

```text
NCCL4Py versions
----------------
nccl4py  : 0.6.0
bindings : 2.32.3
libnccl  : 2.30.7+cuda13.3 @ /tmp/ncclblog/.venv/lib/python3.12/site-packages/nvidia/nccl/lib/libnccl.so.2
```

`bindings` は NCCL4Py を作ったときのヘッダーの版、`libnccl` は実際に読み込んだ本体の版と場所です。

:::details 読み込みの細部と、確かめた手順と出力

2.30.7 に無い 14 個は、`ncclAllReduceConfig` のように集団通信の設定 `ncclCollConfig_t` を受け取る版が 8 個、`ncclGetPeerDeviceLeInfo` のように名前が `LeInfo` で終わるものが 3 個、`ncclTeamCft` と `ncclTeamCftMultimem` の 2 個、そして `ncclSetEncryption` です。`ncclSetEncryption` は、[NCCL 2.32.3 のリリースノート](https://github.com/NVIDIA/nccl/releases/tag/v2.32.3-1)によれば、OpenSSL3 を有効にして作った NCCL で、NCCL が自分で張るソケット通信を TLS で暗号化するときに設定する API です。

NCCL EP の窓口が `libnccl_ep.so` より先に NCCL 本体を開かせる理由は、[`load_library` のコメント](https://github.com/NVIDIA/nccl-extensions/blob/e57f0dad43dc1ca5bf96f09bf4075afc2eae6599/python/nccl/_extensions/bindings/_internal/nccl_ep_linux.pyx#L354-L369)に書かれています。先に NCCL4Py に `libnccl.so.2` を開かせておけば、`libnccl_ep.so` が求める `libnccl.so.2` がファイルを探さずに見つかり、NCCL 本体を探す場所を NCCL4Py の 1 箇所にまとめられる、という理由です。

次の 2 つの言葉は、下の表で使います。`RTLD_GLOBAL` は、開いたライブラリの関数を、後から開くほかのライブラリからも使えるようにする `dlopen` の指定です。`pnccl` で始まる 82 個の関数は、NCCL の [`NCCL_API` マクロ](https://github.com/NVIDIA/nccl/blob/73cf112295c33aee2b895f329f592f2a9b4b0f97/src/include/core.h#L17-L20)が `PROFAPI` を有効にして作ったときに付ける別名で、呼び出しを外から横取りしたとき、横取りした関数の中から本物を呼ぶのに使えます。

| 確かめたこと | 結果 |
|---|---|
| 先に 2.32.3 の `libnccl.so.2` を `RTLD_GLOBAL` で開くとどうなるか | NCCL4Py は 2.30.7 ではなく、先に開いた 2.32.3 を使った。見つからない関数は 0 個になり、`set_encryption(0)` も戻った |
| `nccl.ep` から開くとき、`libnccl.so.2` を読み込み直すか | 読み込み直さない。`libnccl` と `libcuda` に絞った動的リンカーのログでは、`libnccl.so.2` の読み込みは NCCL4Py が開いた 1 回だけで、`libnccl_ep.so` の依存として新たに読み込もうとしたのは `libcuda.so.1` だった |
| NCCL 本体を開いていないプロセスで `libnccl_ep.so` だけを開くとどうなるか | `libnccl.so.2: cannot open shared object file` で失敗した |
| 差し込んだ関数から、`pnccl` の名前で NCCL 本体の関数を呼べるか | 呼べた。`ncclGetVersion` を差し込み、中から `pncclGetVersion` を呼ぶと、差し込んだ関数を通って本物の値が返った |
| cuda-python を読まずに、`libnccl.so.2` だけで通信路を作らせるとどうなるか | 動的リンカーが `libcuda.so.1` を探しに行き、`ncclCommInitRank` は 1 (`ncclUnhandledCudaError`) を返した |

NCCL4Py はまずプロセスの中にすでにある関数を探すので、別のライブラリが先に `libnccl.so.2` を `RTLD_GLOBAL` で開いていれば、それを使います。この記事で確かめたのは、この場合だけです。

手順は、uv と gcc が入った GPU の無い x86_64 の Linux で、次のスクリプトを `bash` で実行したものです。

```bash
set -e
rm -rf /tmp/ncclcheck && mkdir /tmp/ncclcheck && cd /tmp/ncclcheck
uv venv -q .venv --python 3.12
uv pip install -q --python .venv/bin/python "nccl-extensions[cu13]==0.1.0"
uv pip install -q --python .venv/bin/python --target other --no-deps "nvidia-nccl-cu13==2.32.3"
cat > check.py <<'PY'
import ctypes, os, sys
if len(sys.argv) > 1:
    ctypes.CDLL(sys.argv[1], mode=os.RTLD_NOW | os.RTLD_GLOBAL)
def loaded():
    return any(l.rstrip().endswith("libnccl.so.2") for l in open("/proc/self/maps"))
import nccl.core as nc
from nccl.bindings import nccl as B
from nccl.bindings._internal import nccl as L
print("import 直後に libnccl.so.2 を読み込み済み:", loaded())
v = nc.get_version()
print("get_version() の後に読み込み済み:", loaded())
print("bindings:", v.nccl_bindings)
print("libnccl :", v.libnccl)
ptrs = L._inspect_function_pointers()

print(f"探す関数 {len(ptrs)} 個のうち見つからないもの {len(missing)} 個:", missing)
try:
    B.set_encryption(0)
    print("set_encryption(0): 戻った")
except Exception as e:
    print("set_encryption(0):", type(e).__name__ + ":", e)
PY
echo "=== 1. nccl-extensions が入れた組み合わせのまま ==="
.venv/bin/python check.py
echo "=== 2. 先に 2.32.3 の libnccl.so.2 を RTLD_GLOBAL で開く ==="
.venv/bin/python check.py other/nvidia/nccl/lib/libnccl.so.2
echo "=== 3. nccl.ep から libnccl_ep.so を開いたときの動的リンカーのログ ==="
LD_DEBUG=files .venv/bin/python -c "import nccl.ep as ep; ep.get_lib_version()" 2>&1 | grep -E "file=lib(nccl|cuda)[^ ]* \[0\];|RuntimeError" | sed -E 's/^ *[0-9]+:\t//'
echo "=== 4. NCCL 本体を開いていないプロセスで libnccl_ep.so だけを開く ==="
.venv/bin/python -c "import ctypes, os; ctypes.CDLL('.venv/lib/python3.12/site-packages/nccl/ep/lib/cu13/libnccl_ep.so', mode=os.RTLD_NOW | os.RTLD_GLOBAL)" 2>&1 | tail -1
echo "=== 5. pncclGetVersion を呼ぶ ncclGetVersion を差し込む ==="
cat > shim.c <<'C'
#include <stdio.h>
typedef int ncclResult_t;
ncclResult_t pncclGetVersion(int* v);
ncclResult_t ncclGetVersion(int* v) {
  ncclResult_t r = pncclGetVersion(v);
  fprintf(stderr, "[shim] ncclGetVersion を横取り: 本物は %d を返した\n", *v);
  return r;
}
C
gcc -shared -fPIC -o libshim.so shim.c -L.venv/lib/python3.12/site-packages/nvidia/nccl/lib -l:libnccl.so.2 -Wl,-rpath,$PWD/.venv/lib/python3.12/site-packages/nvidia/nccl/lib
LD_PRELOAD=$PWD/libshim.so .venv/bin/python -c "import nccl.core as nc; print('libnccl:', nc.get_version().libnccl.version)"
echo "=== 6. cuda-python を読まずに libnccl.so.2 だけで通信路を作らせる ==="
cat > raw.py <<'PY'
import ctypes, os
lib = ctypes.CDLL(".venv/lib/python3.12/site-packages/nvidia/nccl/lib/libnccl.so.2", mode=os.RTLD_NOW)
class UniqueId(ctypes.Structure):
    _fields_ = [("internal", ctypes.c_char * 128)]
uid = UniqueId()
lib.ncclGetUniqueId(ctypes.byref(uid))
comm = ctypes.c_void_p()
r = lib.ncclCommInitRank(ctypes.byref(comm), 1, uid, 0)
maps = {l.split()[-1] for l in open("/proc/self/maps") if l.split()[-1].startswith("/")}
print("ncclCommInitRank の戻り値:", r)
print("cuda-python の .so を読み込み済み:", any("/cuda/" in m for m in maps))
PY
LD_DEBUG=libs .venv/bin/python raw.py 2>&1 | grep -E "find library=libcuda|^ncclCommInitRank|^cuda-python" | sed -E 's/^ *[0-9]+:\t//'
```

## まとめ

NCCL4Py と NCCL EP は、どちらも NCCL 本体の上に載り、Python から NCCL EP を使うときは nccl-extensions を入れます。NCCL4Py は NCCL 本体の通信を、`nccl.ep` は EP のグループと送り先とデータを Python から扱う窓口で、dispatch と combine の通信そのものは `libnccl_ep.so` が受け持ちます。
