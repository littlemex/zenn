## はじめに

[EKS Hybrid Nodes](https://docs.aws.amazon.com/eks/latest/userguide/hybrid-nodes-overview.html) を使うと、EKS の外で自分で用意するマシンを EKS クラスタのノードとして参加させ、AWS 側のコントロールプレーンから管理できます。この記事では、このようなマシンを BYOM (Bring Your Own Machine、持ち込みマシン) と呼びます。例えばオンプレミスのサーバーです。BYOM はこの記事での呼び方で、AWS の文書は Hybrid Nodes を bring your own infrastructure と説明しています。EKS には [EKS Capabilities](https://docs.aws.amazon.com/eks/latest/userguide/capabilities.html) という機能もあり、その 1 つとして Argo CD を AWS が運用する形で使えます。この記事では、AWS が運用するこの Argo CD を「マネージドの Argo CD」と呼びます。Hybrid ノードも EKS クラスタのノードなので、マネージドの Argo CD から EKS クラスタにデプロイすれば、原理的には Hybrid ノードにも届くはずです。これが実際に問題なく動くのかを、環境を作って確かめました。あわせて、AKS や GKE、自分で建てたクラスタのような、EKS ではない Kubernetes にもデプロイできるかを確かめました。

結論を先に表にします。デプロイできるかどうかは、マネージドの Argo CD にデプロイ先を登録できるかで決まります。自分で用意した環境は、マシンを EKS のノードとして参加させる場合と、すでに動いている Kubernetes クラスタにデプロイする場合とで、行が分かれます。表の「2 段目の Argo CD」は、マネージドの Argo CD が EKS クラスタに入れる、通常の (自分で運用する) Argo CD のことです。

| デプロイ先 | マネージドの Argo CD から | 方法 |
|---|---|---|
| EKS クラスタ | 直接デプロイできます | クラスタの ARN (AWS のリソースを一意に指す名前) で登録します |
| BYOM | 直接デプロイできます | EKS Hybrid Nodes で EKS クラスタのノードとして参加させます。今回は EC2 を BYOM として確かめました |
| EKS ではない Kubernetes (AKS、GKE、自分で建てたクラスタ) | 直接はデプロイできません | 2 段目の Argo CD を経由します。今回は k3s で確かめました |

この記事は、Argo CD と EKS の基本を知っている読者に向けて、それぞれの方法がなぜ成り立つのかと、確かめた結果を書きます。

## マネージドの Argo CD がデプロイできる相手

![マネージドの Argo CD は EKS クラスタの ARN でしかデプロイ先を使えない。EKS ではないクラスタを URL とトークンで登録すると、それを使う Application が失敗する](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cb793f2e6301ee/zenn/articles/cb793f2e6301ee/targets.png)

マネージドの Argo CD がデプロイできるのは、EKS クラスタだけです。AWS の比較の文書にも[デプロイ先は EKS クラスタの ARN だけ](https://docs.aws.amazon.com/eks/latest/userguide/argocd-comparison.html)と書かれています。マネージドの Argo CD のコントローラーは[ユーザーのクラスタの外にある AWS の基盤](https://docs.aws.amazon.com/eks/latest/userguide/capabilities-controller-logs.html)で動き、デプロイ先の EKS クラスタには、マネージドの Argo CD に渡した IAM ロールを[アクセスエントリ](https://docs.aws.amazon.com/eks/latest/userguide/argocd-register-clusters.html)に登録して入ります。

通常の Argo CD では、デプロイ先を API サーバーの URL とトークンで登録できます。登録には cluster secret (デプロイ先の接続先と認証情報を入れた Secret) を使います。同じ形の cluster secret をマネージドの Argo CD に置くと、cluster secret 自体は作れますが、それを使う Application の condition に次のエラーが出て、デプロイは始まりませんでした。

```text
Failed to load live state: failed to get cluster info for "https://10.90.0.48:6443": error getting cluster: error getting cluster RESTConfig: server should be specified as a cluster ARN
```

エラーの文言からは、RESTConfig (デプロイ先への接続の設定) を組み立てるところで、`server` が ARN でないことを理由に止まっていると読めます。EKS ではないクラスタにデプロイする方法は、後の節で説明します。

## BYOM は Hybrid Nodes で EKS のノードにする

![Argo CD が話す相手は AWS 側にある EKS の API サーバーだけで、BYOM の kubelet が自分から API サーバーにつなぎ、API サーバーからは kubelet と webhook の Pod に向かう通信がある](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cb793f2e6301ee/zenn/articles/cb793f2e6301ee/hybrid.png)

BYOM を EKS クラスタのノードにすれば、マネージドの Argo CD は、そのマシンにも EKS クラスタへのデプロイとして届けられます。そのための機能が [EKS Hybrid Nodes](https://docs.aws.amazon.com/eks/latest/userguide/hybrid-nodes-overview.html) です。コントロールプレーンは AWS 側にあり、BYOM はノードとして働くだけです。

マネージドの Argo CD は、AWS 側にある EKS の API サーバーにマニフェストを適用するだけで、BYOM のネットワークに入る必要はありません。Pod をどのノードに置くかは Kubernetes のスケジューラが決めます。Hybrid ノードには[既定で `eks.amazonaws.com/compute-type: hybrid` というラベルが付く](https://docs.aws.amazon.com/eks/latest/userguide/hybrid-nodes-add-ons.html)ので、Pod の `nodeSelector` にこのラベルを指定すれば、Pod の置き場所を BYOM に限れます。逆に、Hybrid ノードには既定の taint がないので、置き場所を指定しない Pod は BYOM にも置かれます。クラウドで動かしたい Pod には、このラベルを避ける affinity を付けるか、Hybrid ノードに taint を付けます。今回は、2 段目の Argo CD をこの affinity でクラウドのノードに限りました。今回デプロイした [podinfo の chart](https://github.com/stefanprodan/podinfo/tree/fd3a834ed8d14b80ea334cf8a2fddd4597924da6/charts/podinfo) は、Helm の値の `nodeSelector` を Pod に渡すので、[Application](https://github.com/littlemex/distributed-ai/blob/e2f5c587dbf23d9744fe6c33ea6d0b4f60263908/investigations/2026-10-29-eks-capabilities-hybrid-nodes/k8s/t1-podinfo-onprem.yaml) の値に次の 2 行を書くだけで済みました。

```yaml
nodeSelector:
  eks.amazonaws.com/compute-type: hybrid
```

通信の向きは 2 つあります。BYOM の kubelet は、自分から API サーバーに接続します。API サーバーから BYOM へ向かう通信は、[ポートの表](https://docs.aws.amazon.com/eks/latest/userguide/hybrid-nodes-networking.html)にあるとおり、kubelet の 10250 番ポートと、webhook の Pod の 2 種類です。

webhook の Pod に API サーバーが届くのは、BYOM の Pod の IP の範囲を[ルーティングできるようにした場合](https://docs.aws.amazon.com/eks/latest/userguide/hybrid-nodes-networking.html)です。そのためには、その範囲をクラスタの `RemotePodNetwork` (BYOM の Pod の IP の範囲を EKS に伝える設定)、VPC のルートテーブル、クラスタのセキュリティグループに入れ、BYOM の側のネットワークでも BGP や静的な経路でその範囲を流します。ルーティングできない場合は、webhook をクラウドのノードで動かすよう勧められています。今回は、BYOM の側の経路を、Transit Gateway と VPC のルートで置き換えました。

クラスタの API エンドポイントは、public だけか private だけにします。AWS の文書は、[public と private の併用は使えない](https://docs.aws.amazon.com/eks/latest/userguide/hybrid-nodes-cluster-create.html)としています。併用すると、VPC の外にある BYOM では API の名前が public のアドレスに解決され、[ノードが参加できないことがある](https://docs.aws.amazon.com/eks/latest/userguide/hybrid-nodes-prereqs.html)からです。同じ文書によると、public だけにすると kubelet はインターネットを通り、private だけにすると VPN や Direct Connect のような専用の経路を通ります。private だけにしても、マネージドの Argo CD は[そのクラスタにデプロイできます](https://docs.aws.amazon.com/eks/latest/userguide/argocd-register-clusters.html#_private_clusters)。

Hybrid ノードは、CNI (Pod のネットワークを作る部品) が動くまで Ready になりません。Hybrid ノードには [VPC CNI を使えず](https://docs.aws.amazon.com/eks/latest/userguide/hybrid-nodes-add-ons.html)、CNI のページでは [AWS がサポートする CNI は Cilium](https://docs.aws.amazon.com/eks/latest/userguide/hybrid-nodes-cni.html) とされています。アドオンのページは Cilium と Calico を挙げていますが、CNI のページは Calico の説明を EKS Hybrid Examples のリポジトリに移しています。サポートされる版は 1.17 系と 1.18 系で、AWS は Cilium の Helm chart を ECR Public に置いています。今回は `1.18.3-0` を使いました。この版は Linux カーネル 5.10 以上を必要とするので、Ubuntu 20.04 と RHEL 8 では AWS のサポート対象外で、その OS では 1.17 系を使います。

ノードを参加させるときに使う Systems Manager のハイブリッドアクティベーションのコードは、それを持つマシンを EKS クラスタのノードとして参加させられる認証情報です。有効期限と登録できる台数を絞って作り、配るときも秘密として扱います。

Hybrid Nodes は、BYOM の置き場所と AWS の間に[安定した接続があることを前提](https://docs.aws.amazon.com/eks/latest/userguide/hybrid-nodes-overview.html#hybrid-nodes-general)にしています。切断される、不安定、断続的、帯域が限られる環境 (DDIL) には向かないとされ、その場合は EKS Anywhere が勧められています。

## 他社のクラウドのマシンは Hybrid Nodes にできるか

他社のクラウドのマシンを Hybrid Nodes にするのは、AWS のサポートを受けられない構成です。本番で使うかどうかは、AWS の担当者に確かめてから決めるべきです。AWS の文書は、これを[サポートの対象外](https://docs.aws.amazon.com/eks/latest/userguide/hybrid-nodes-overview.html#hybrid-nodes-general)としています。

> Running EKS Hybrid Nodes on cloud infrastructure, including AWS Regions, AWS Local Zones, AWS Outposts, or in other clouds, is not supported. You will be charged the hybrid nodes fee if you run hybrid nodes on Amazon EC2 instances.

この線引きは、VM かベアメタルかでは分かれていません。同じページは、Hybrid ノードを [physical or virtual machines](https://docs.aws.amazon.com/eks/latest/userguide/hybrid-nodes-overview.html#hybrid-nodes-features) のどちらでも動かせるとしています。文書が区別しているのは、オンプレミスか、AWS を含むクラウドかだけです。Azure や Google Cloud が提供するベアメタルのサーバーも「in other clouds」に含まれると読むのが自然で、ベアメタルならサポートされるという記述はありません。

技術的に動くかどうかは、EC2 でしか確かめていません。今回の検証では、EC2 を Hybrid ノードとして参加させ、デプロイまで動きました。AWS 自身の試験も [Hybrid ノードを EC2 で作っています](https://github.com/aws/eks-hybrid/blob/ab5348b9ea98bb07f93097f07b9db48688486713/test/e2e/peered/node.go#L162)。ノードを参加させる nodeadm には、[SSM の認証情報を読むときに、EC2 の上でも EC2 のメタデータの認証情報を誤って使わない処理](https://github.com/aws/eks-hybrid/blob/ab5348b9ea98bb07f93097f07b9db48688486713/internal/ssm/credentials.go#L35-L37)があります。また、nodeadm の [commit ab5348b9](https://github.com/aws/eks-hybrid/tree/ab5348b9ea98bb07f93097f07b9db48688486713) のテストと vendor 以外の Go のコード全体を、他社のクラウドのメタデータを読むときに使う名前 (`metadata.google`、`Metadata: true`、`azure`) で検索した範囲では、他社のクラウドを見分けて拒否するコードは見つかりませんでした。Azure と Google Cloud のマシンでは試していません。

## EKS ではないクラスタには 2 段目の Argo CD を経由する

![マネージドの Argo CD が持つ 2 つの Application が EKS クラスタに通常の Argo CD とその Application を入れ、その Argo CD がスクリプトで置いたトークンで EKS ではないクラスタにデプロイする](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cb793f2e6301ee/zenn/articles/cb793f2e6301ee/two-stage.png)

AKS や GKE のように、EKS ではない Kubernetes にマネージドの Argo CD から直接はデプロイできません。それでも、何をどこにデプロイするかの書き換えはマネージドの Argo CD の Application だけで済ませたい、という場合に使える構成を確かめました。マネージドの Argo CD に、EKS クラスタの中へ通常の Argo CD を入れさせる構成です。2 段目の Argo CD は通常の Argo CD なので、デプロイ先を API サーバーの URL とトークンで登録できます。

マネージドの Argo CD には、[2 つの Application](https://github.com/littlemex/distributed-ai/blob/e2f5c587dbf23d9744fe6c33ea6d0b4f60263908/investigations/2026-10-29-eks-capabilities-hybrid-nodes/k8s/t3-tier2-argocd.yaml) を置きます。1 つは Helm chart [argo-cd 10.2.2](https://github.com/argoproj/argo-helm/tree/e510a7d9ebbc91ae681f333ba4b4041545448881/charts/argo-cd) で 2 段目の Argo CD を入れるもの、もう 1 つは Helm chart [argocd-apps 2.0.7](https://github.com/argoproj/argo-helm/tree/dfeb6aab23ceeef800236c2e3465968e6abf3717/charts/argocd-apps) で 2 段目の Argo CD が持つ Application を作るものです。2 段目が何をどこにデプロイするかは、argocd-apps の値として、マネージドの Argo CD の Application の中に書けます。そのため、今回の 2 つのデプロイ先では、デプロイする内容を変えるときに触るのはマネージドの Argo CD の Application だけで済みました。ただし、EKS ではないクラスタを 2 段目に登録する cluster secret はトークンを含むので、今回は Application に書かず、スクリプトで 2 段目の namespace に直接置きました。

2 段目の Argo CD は、マネージドの Argo CD の CRD と Application が置かれた EKS クラスタで動くので、3 つのことに気を付けます。

- Application などの CRD は、[マネージドの Argo CD を作るときに EKS が入れます](https://docs.aws.amazon.com/eks/latest/userguide/argocd-create-cli.html)。今回のログでも、2 段目を入れる前の時点で CRD `applications.argoproj.io` はすでにありました。2 段目の chart では `crds.install: false` にして入れません。
- argo-cd の chart は版ごとに CRD を同梱していて、2 段目はその CRD を入れずにマネージドの Argo CD の CRD を使うので、2 段目の Argo CD のマイナー版をマネージドの Argo CD にそろえました。今回、マネージドの Argo CD は `aws eks describe-capability` で `3.4.7-eks-1` と表示され、2 段目には Argo CD 3.4.6 を入れる chart 10.2.2 を使いました。マネージドの Argo CD は[版の更新も AWS が行う](https://docs.aws.amazon.com/eks/latest/userguide/working-with-capabilities.html)ので、`describe-capability` の版を定期的に確かめ、マイナー版が変わったら、2 段目の chart も、appVersion (chart が入れる Argo CD の版) が同じマイナー版のものに上げます。chart の版と Argo CD の版は番号が別なので、`helm search repo argo/argo-cd --versions` で対応を見て選びます。2 段目を先に新しいマイナー版へ上げると、古い CRD の上で新しいコントローラーが動くことになるので、先には上げません。
- マネージドの Argo CD は、[作るときに指定した namespace の Application だけ](https://docs.aws.amazon.com/eks/latest/userguide/argocd-comparison.html)を扱います。通常の Argo CD も、[既定では自分の namespace の Application だけ](https://argo-cd.readthedocs.io/en/release-3.4/operator-manual/app-any-namespace/)を扱います。2 段目を `argocd-edge` に入れ、マネージドの Argo CD の `argocd` と分けたので、どちらの Argo CD がどの Application を扱うかが namespace で決まり、同じ Application を 2 つの Argo CD が取り合いません。

この構成で引き受けるものは 4 つあります。

- 2 段目の Argo CD の版の更新と可用性は、利用者の責任になります。マネージドなのは 1 段目だけです。
- EKS ではないクラスタのトークンを、2 段目の Argo CD の cluster secret として管理する必要があります。今回のトークンは、k3s の ServiceAccount に結び付いた期限のない Secret です。漏れたときは k3s 側でその Secret を消して無効にし、作り直したトークンで cluster secret を書き換えます。期限のあるトークンを使うなら、期限が切れる前に書き換える仕組みが要ります。
- 2 段目の Argo CD が動く EKS クラスタから、EKS ではないクラスタの API サーバーへ通信が届く必要があります。AKS や GKE なら、API サーバーを private にしたまま VPN などで AWS の VPC とつなぐか、[AKS の authorized IP ranges](https://learn.microsoft.com/azure/aks/api-server-authorized-ip-ranges) や [GKE の authorized networks](https://cloud.google.com/kubernetes-engine/docs/how-to/authorized-networks) に、EKS クラスタから外に出るときのアドレス (この構成では NAT Gateway のアドレス) を入れることになります。後者では、同じ NAT Gateway を通るほかのワークロードからも API サーバーに届くので、API サーバー側の認証と権限で絞ることが前提になります。
- 2 段目の Argo CD の権限は、マネージドの Argo CD の権限の外にあります。

最後の権限について、今回変えた設定と、既定のまま残したものを表にまとめます。

| 対象 | 今回の設定 |
|---|---|
| 2 段目のデプロイ先 | 自分が動く EKS クラスタを [in-cluster のアドレスで使えないように](https://argo-cd.readthedocs.io/en/release-3.4/operator-manual/argocd-cm-yaml/)しました (`cluster.inClusterEnabled: "false"`) |
| k3s 向けの Application | デプロイ先を k3s の 1 つの namespace に、取得元を podinfo の chart リポジトリに限った AppProject に入れました |
| 2 段目の application-controller の EKS 側の権限 | chart の既定のままで、EKS クラスタ全体を読み書きできる ClusterRole を持ちます |
| 2 段目の画面へのログイン | chart の既定のままで、Identity Center ではなく、ローカルの admin で入ります |
| k3s 側の権限 | 短く確かめるために、2 段目が使う ServiceAccount に `cluster-admin` を与えました |
| マネージドの Argo CD の EKS 側の権限 | 短く確かめるために `AmazonEKSClusterAdminPolicy` を与えました。2 段目の chart は ClusterRole と ClusterRoleBinding を作るので、このまま 2 段構成を使う限り、マネージドの Argo CD にはそれを作れる権限が要ります |
| 2 段目の画面の admin のパスワード | Argo CD の既定のままで、起動時に作られる `argocd-edge` の Secret `argocd-initial-admin-secret` に入ります |

実運用では、残したものも絞ります。k3s 側の権限を namespace の Role に絞るなら、Role では namespace を作れないので、デプロイ先の namespace を先に作り、Application の `CreateNamespace=true` と AppProject の Namespace の許可を外したうえで、2 段目が使う ServiceAccount をその namespace の Role に結び付けます。この絞り方は、今回は確かめていません。[cluster secret の namespaces](https://argo-cd.readthedocs.io/en/release-3.4/operator-manual/declarative-setup/#clusters) は、2 段目の Argo CD が扱う namespace を限る設定で、k3s 側の権限を狭めるものではありません。

## 2 段構成のほかの方法

EKS ではないクラスタにデプロイする方法は、2 段構成だけではありません。今回確かめたのは 2 段構成だけで、ほかの方法は試していません。

| 方法 | 良いところ | 引き換えになるもの |
|---|---|---|
| 各クラスタに Argo CD か Flux を置き、それぞれが Git から取りに行く | 外から API サーバーに入る通信が要らず、トークンをクラスタの外に出しません | クラスタの数だけ Argo CD や Flux を運用し、状態を 1 か所で見るには別の仕組みが要ります |
| 中央の Argo CD と、各クラスタに置く [argocd-agent](https://github.com/argoproj-labs/argocd-agent) を組み合わせる | 各クラスタの agent が中央に接続しに行くので、API サーバーを外に開けずに中央の画面を保てます | 2026 年 10 月 29 日に EKS ユーザーガイドの Argo CD の節を見た範囲では、マネージドの Argo CD と組み合わせられるという記述はありません |
| 今回の 2 段構成 | デプロイする内容の書き換えを、トークンを除いてマネージドの Argo CD の Application にまとめられます | 2 段目の Argo CD の運用、トークンの管理、EKS から相手の API サーバーへの通信を引き受けます |

EKS ではないクラスタを [EKS Connector](https://docs.aws.amazon.com/eks/latest/userguide/eks-connector.html) で EKS に登録しても、そのクラスタに使える EKS の API は登録、一覧、参照、登録解除だけです。マネージドの Argo CD が使うアクセスエントリは設定できないので、文書の上ではデプロイ先になりません。

## 検証の結果

6 つの項目がすべて通りました。

| # | 確かめたこと | 結果 |
|---|---|---|
| T1 | マネージドの Argo CD が、BYOM に Helm chart をデプロイする | デプロイできました。2 つの Pod が BYOM の上で、BYOM の Pod の範囲 10.81.0.0/16 の IP を持って動きました。この範囲を VPC からルーティングできるようにしてあるので、AWS 側のノードの Pod から Service に送ったリクエストに、2 つのうちのどちらかの Pod が応答しました |
| T2 | EKS ではないクラスタを URL とトークンでマネージドの Argo CD に登録する | cluster secret は作れましたが、それを使う Application は前の節のエラーで止まり、k3s にデプロイ先の namespace は作られませんでした |
| T3 | 2 段目の Argo CD を経由して、k3s にデプロイする | デプロイできました。マネージドの Argo CD の 2 つの Application (2 段目を入れる `tier2-argocd` と、2 段目の Application を作る `tier2-apps`) と、2 段目の Application が、すべて Synced と Healthy になりました |
| T4 | マネージドの Argo CD の上の 2 つの Application (`podinfo-onprem` と `tier2-apps`) の値だけを変える | BYOM では 3 つ、k3s では 2 つのレプリカがすべて更新され、どの Pod も自分の IP で新しいメッセージを返しました。BYOM は 121 秒以内、k3s は 78 秒以内でした |
| T5 | k3s で Deployment を手で消す | 2 段目の Argo CD が Deployment を作り直しました。削除と作り直しの時刻の差は、秒単位の時計で 1 秒でした |
| T6 | BYOM の kubelet の接続先 | クラスタの VPC の private のアドレス 10.0.4.94 に接続しました |

T4 の秒数は、最初の値の変更から数えた上限です。2 つのデプロイ先を同じループで確かめ、1 回の確認のあとに 5 秒待ちます。1 回の確認には SSM Run Command の往復も入るので、秒数は Argo CD が反映するまでの時間そのものではありません。BYOM は 3 つの Pod を 1 つずつ SSM Run Command で確かめるので、1 回の確認に k3s より時間がかかります。そのため、2 つの秒数の差は 2 つの経路の速さの差ではありません。T5 は、削除のコマンドを出した時刻と、作り直された Deployment の作成時刻を比べたもので、どちらも k3s のマシンの時計の秒単位です。Pod が Ready になるまでの時間は含みません。T2 は、マネージドの Argo CD が出すエラーの文言で合否を決めているので、AWS が文言を変えると、拒否されていても FAIL になります。

環境は、3 つの VPC を Transit Gateway でつなぎ、AWS、BYOM の置き場所、EKS ではない Kubernetes に見立てました。BYOM 役の EC2 には instance profile を付けず、AWS への認証は Systems Manager のハイブリッドアクティベーションだけで行いました。物理サーバーを参加させるときと認証の条件をそろえるためです。EKS ではない Kubernetes は、EC2 に入れた k3s です。クラスタの API エンドポイントは private だけにしました。実際のオンプレミスでの構築とは、次の点が違います。

- 経路は Transit Gateway で、VPN や Direct Connect ではありません。
- Hybrid ノードは EC2 です。実際のサーバーでは、OS が [AWS の対応表](https://docs.aws.amazon.com/eks/latest/userguide/hybrid-nodes-os.html)に載っている必要があります。
- マネージドの Argo CD の権限は、前の節の表のとおり広く与えました。実運用での絞り方は、[最小権限の設定](https://docs.aws.amazon.com/eks/latest/userguide/argocd-register-clusters.html#_production_setup_with_least_privilege)にあります。

構築、検証、削除の手順とコードは [littlemex/distributed-ai の investigations](https://github.com/littlemex/distributed-ai/tree/e2f5c587dbf23d9744fe6c33ea6d0b4f60263908/investigations/2026-10-29-eks-capabilities-hybrid-nodes) にあります。

## まとめ

EKS Capabilities のマネージドの Argo CD は EKS クラスタにしかデプロイできませんが、BYOM は Hybrid Nodes で EKS クラスタのノードにすれば直接デプロイできることを、EC2 を BYOM として確かめました。EKS ではない Kubernetes には、マネージドの Argo CD が入れた 2 段目の Argo CD を経由してデプロイできることを k3s で確かめ、デプロイする内容は、トークンを含む cluster secret を除いて、マネージドの Argo CD の Application だけで変えられました。
