## はじめに

[EKS Hybrid Nodes](https://docs.aws.amazon.com/eks/latest/userguide/hybrid-nodes-overview.html) を使うと、EKS の外で自分で用意するマシンを EKS クラスタのノードとして参加させ、AWS 側のコントロールプレーンから管理できます。AWS の文書は、この考え方を [bring your own infrastructure](https://docs.aws.amazon.com/eks/latest/userguide/hybrid-nodes-overview.html#hybrid-nodes-features) と呼んでいます。この記事でも、このように自分で用意するマシンを BYOI (bring your own infrastructure、持ち込みのインフラ) と呼びます。例えばオンプレミスのサーバーを管理下に置けます。EKS には [EKS Capabilities](https://docs.aws.amazon.com/eks/latest/userguide/capabilities.html) という機能もあり、その 1 つとして Argo CD を AWS が運用する形で使えます。この記事では、AWS が運用するこの Argo CD を「Managed Argo CD」と呼びます。Hybrid ノードも EKS クラスタのノードなので、Managed Argo CD から EKS クラスタにデプロイすれば、原理的には Hybrid ノードにも届くはずです。これが実際に問題なく動くのかを、環境を作って確かめました。あわせて、AKS や GKE、自分で建てたクラスタのような、EKS ではない Kubernetes にもデプロイできるかを確かめました。

結論を先に表にします。デプロイできるかどうかは、Managed Argo CD にデプロイ先を登録できるかで決まります。自分で用意した環境は、マシンを EKS のノードとして参加させる場合と、すでに動いている Kubernetes クラスタにデプロイする場合とで、行が分かれます。

| デプロイ先 | Managed Argo CD からの直接デプロイ | 方法 |
|---|---|---|
| EKS クラスタ | 可 | クラスタの ARN (AWS のリソースを一意に指す名前) で登録 |
| BYOI | 可 | EKS Hybrid Nodes で EKS クラスタのノードとして参加。今回は EC2 で確認 |
| EKS ではない Kubernetes (AKS、GKE、自分で建てたクラスタ) | 不可 | EKS クラスタに置いた中継用の Argo CD を経由。今回は k3s で確認 |

この記事は、Argo CD と EKS の基本を知っている読者に向けて、それぞれの方法がなぜ成り立つのかと、確かめた結果を書きます。

## Managed Argo CD がデプロイできる相手

まず、Managed Argo CD の部品がどこにあるかを押さえます。

![Managed Argo CD のコントローラーは AWS が運用する場所にあり、利用者の EKS クラスタの API サーバーを通して、クラスタの argocd namespace にある Application と cluster secret を読み、マニフェストを適用する。利用者は Application を自分のクラスタに kubectl apply する](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cb793f2e6301ee/zenn/articles/cb793f2e6301ee/placement.png)

Managed Argo CD の部品は、2 か所に分かれています。

- 実際にデプロイの仕事をするコントローラーは、利用者の EKS クラスタの中ではなく、[AWS が運用する場所](https://docs.aws.amazon.com/eks/latest/userguide/capabilities-controller-logs.html)で動きます。利用者のノードの上には、コントローラーの Pod はありません。
- 何をどこにデプロイするかを書いた Application と、デプロイ先を書いた cluster secret (デプロイ先の情報を入れた Secret) は、利用者の EKS クラスタの `argocd` namespace に、普通の Kubernetes のオブジェクトとして置きます。

利用者は Application を自分のクラスタに `kubectl apply` するだけです。コントローラーはクラスタの API サーバーを通してそれを読み、Helm chart や Git のリポジトリから中身を取ってきて、同じ API サーバーにマニフェストを適用します。Pod がどのノードに置かれるかは、クラスタのスケジューラが決めます。

次に、デプロイ先をどう指定するかです。

![上の段は EKS クラスタの ARN で登録した場合で、Managed Argo CD が ARN でクラスタを見つけ、IAM ロールで入り、アクセスエントリがそのロールに Kubernetes の権限を与えてマニフェストが適用される。下の段は URL とトークンで登録した場合で、cluster secret は作れるが Application が止まり、相手のクラスタには何も届かない](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cb793f2e6301ee/zenn/articles/cb793f2e6301ee/register.png)

Managed Argo CD がデプロイできるのは EKS クラスタだけで、AWS の比較の文書にも[デプロイ先は EKS クラスタの ARN だけ](https://docs.aws.amazon.com/eks/latest/userguide/argocd-comparison.html)と書かれています。理由は、Managed Argo CD がデプロイ先を見つける方法と、デプロイ先に入る方法の両方が EKS の仕組みでできているからです。上の図の上の段がその流れです。

1. デプロイ先は cluster secret で登録します。Managed Argo CD では、その `server` に EKS クラスタの ARN を書きます。
2. AWS 側のコントローラーは、ARN でデプロイ先のクラスタを特定し、Managed Argo CD を作るときに渡した IAM ロールでそのクラスタの API サーバーに入ります。
3. デプロイ先の EKS クラスタでは、[アクセスエントリ](https://docs.aws.amazon.com/eks/latest/userguide/argocd-register-clusters.html) (IAM ロールに Kubernetes の権限を結び付ける EKS の設定) が、その IAM ロールに権限を与えます。
4. 権限をもらった Managed Argo CD が、マニフェストを適用します。

図の下の段は、通常の Argo CD と同じように、API サーバーの URL とトークンで登録した場合です。cluster secret はエラーなく作れます。ところが、その cluster secret を使う Application は、condition に次のエラーを出して止まり、相手のクラスタには何も届きませんでした。

```text
Failed to load live state: failed to get cluster info for "https://10.90.0.48:6443": error getting cluster: error getting cluster RESTConfig: server should be specified as a cluster ARN
```

エラーの文言からは、Managed Argo CD が `server` に ARN を求め、URL を受け付けずに止まっていると読めます。EKS ではないクラスタには ARN もアクセスエントリもないので、この流れには乗れません。EKS ではないクラスタにデプロイする方法は、後の節で説明します。

## Hybrid Nodes による BYOI の参加

![Managed Argo CD は EKS の API サーバーにマニフェストを適用し、スケジューラが Pod ごとにノードを選ぶ。nodeSelector で compute-type: hybrid を指定した Pod は BYOI に、hybrid を避ける affinity を付けた Pod はクラウドのノードに置かれる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cb793f2e6301ee/zenn/articles/cb793f2e6301ee/hybrid-deploy.png)

BYOI を EKS クラスタのノードにすれば、Managed Argo CD は、EKS クラスタへのデプロイと同じやり方で、そのマシンにもアプリを届けられます。そのための機能が [EKS Hybrid Nodes](https://docs.aws.amazon.com/eks/latest/userguide/hybrid-nodes-overview.html) です。コントロールプレーンは AWS 側にあり、BYOI はノードとして働くだけです。

Managed Argo CD は、AWS 側にある EKS の API サーバーにマニフェストを適用するだけで、BYOI のネットワークに入る必要はありません。Pod をどのノードに置くかは Kubernetes のスケジューラが決めます。Hybrid ノードには[既定で `eks.amazonaws.com/compute-type: hybrid` というラベルが付く](https://docs.aws.amazon.com/eks/latest/userguide/hybrid-nodes-add-ons.html)ので、Pod の `nodeSelector` にこのラベルを指定すれば、Pod の置き場所を BYOI に限れます。ただし、今回は Hybrid ノードに taint を付けていないので、置き場所を指定しない Pod は BYOI にも置かれることがあります。クラウドで動かしたい Pod には、このラベルを避ける affinity を付けるか、Hybrid ノードに taint を付けます。今回は、後の節で説明する中継用の Argo CD を、この affinity でクラウドのノードに限りました。今回デプロイした [podinfo の chart](https://github.com/stefanprodan/podinfo/tree/fd3a834ed8d14b80ea334cf8a2fddd4597924da6/charts/podinfo) は、Helm の値の `nodeSelector` を Pod に渡すので、`podinfo-onprem` という [Application](https://github.com/littlemex/distributed-ai/blob/ca98dda99c81cf7a3ec6d21cd9088f7724684e2f/investigations/2026-10-29-eks-capabilities-hybrid-nodes/k8s/t1-podinfo-onprem.yaml) の値に次の 2 行を書くだけで済みました。

```yaml
nodeSelector:
  eks.amazonaws.com/compute-type: hybrid
```

次に、BYOI と AWS の間の通信です。

![クラスタの VPC と BYOI のネットワークをプライベートな接続でつなぐ。kubelet は API エンドポイントの 443 番に接続し、API サーバーは kubelet の 10250 番に接続する。BYOI のノードと Pod の範囲を、EKS の RemoteNodeNetwork と RemotePodNetwork、VPC のルートテーブル、セキュリティグループ、BYOI 側の経路に入れる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cb793f2e6301ee/zenn/articles/cb793f2e6301ee/hybrid-network.png)

BYOI のマシンは、AWS 側にある EKS のコントロールプレーンと通信できなければ、ノードとして働けません。kubelet が API サーバーに接続してノードとして登録し、API サーバーもログの取得などのために kubelet に接続するからです。そのため、BYOI のネットワークとクラスタの VPC を VPN や Direct Connect のようなプライベートな接続でつなぎ、BYOI のノードと Pod の IP の範囲を EKS に登録して、ルートテーブルとセキュリティグループで必要なポートを通します。必要なポートと設定の詳細は、[AWS の文書](https://docs.aws.amazon.com/ja_jp/eks/latest/userguide/hybrid-nodes-networking.html)にまとまっています。

![EKS の RemoteNetworkConfig にオンプレミスのノードと Pod の範囲を書き、VPC のルートテーブルとオンプレミスのルートテーブルの両方に、その範囲への経路を入れる](https://docs.aws.amazon.com/ja_jp/eks/latest/userguide/images/hybrid-prereq-diagram.png)
*出典: Amazon EKS ユーザーガイド「[ハイブリッドノード用のネットワークを準備する](https://docs.aws.amazon.com/ja_jp/eks/latest/userguide/hybrid-nodes-networking.html)」、CC BY-SA 4.0*

クラスタの API エンドポイントは、インターネットに出さず private にしておくのが安全です。今回も API エンドポイントを private だけにした閉じたネットワークで検証し、Managed Argo CD からのデプロイまで動きました。BYOI の置き場所との VPN の代わりには、VPC 同士をプライベートにつなぐ Transit Gateway を使いました。private だけのクラスタでも、Managed Argo CD は[デプロイできます](https://docs.aws.amazon.com/eks/latest/userguide/argocd-register-clusters.html#_private_clusters)。

Hybrid ノードは、Pod のネットワークを作る部品である CNI が動くまで Ready になりません。Hybrid ノードには [VPC CNI を使えない](https://docs.aws.amazon.com/eks/latest/userguide/hybrid-nodes-add-ons.html)ので、Cilium などの CNI を自分で入れます。今回は、AWS が ECR Public に置いている Cilium の Helm chart を使いました。対応する CNI と版、OS ごとの制約は [CNI のページ](https://docs.aws.amazon.com/ja_jp/eks/latest/userguide/hybrid-nodes-cni.html)にあります。

## 他社クラウドのマシンと Hybrid Nodes

他社のクラウドのマシンを Hybrid Nodes にする構成は、AWS の文書で[サポートの対象外](https://docs.aws.amazon.com/eks/latest/userguide/hybrid-nodes-overview.html#hybrid-nodes-general)とされています。本番で使うかどうかは、AWS の担当者に確かめてから決めるべきです。

> Running EKS Hybrid Nodes on cloud infrastructure, including AWS Regions, AWS Local Zones, AWS Outposts, or in other clouds, is not supported. You will be charged the hybrid nodes fee if you run hybrid nodes on Amazon EC2 instances.

この線引きは、VM かベアメタルかでは分かれていません。同じページは、Hybrid ノードを [physical or virtual machines](https://docs.aws.amazon.com/eks/latest/userguide/hybrid-nodes-overview.html#hybrid-nodes-features) のどちらでも動かせるとしています。文書が区別しているのは、オンプレミスか、AWS を含むクラウドかだけです。Azure や Google Cloud が提供するベアメタルのサーバーも「in other clouds」に含まれると読むのが自然で、ベアメタルならサポートされるという記述はありません。

技術的に動くかどうかについては、Hybrid ノードを参加させるツールである [nodeadm のソース](https://github.com/aws/eks-hybrid/tree/ab5348b9ea98bb07f93097f07b9db48688486713)を見た範囲で、他社のクラウドを見分けて参加を拒否するような処理は見つかりませんでした。今回、EC2 では参加からデプロイまで動いたので、Azure や Google Cloud のマシンも、技術的にはノードとして追加できそうです。ただし、Azure と Google Cloud のマシンでは試していないので、確実に動くとは言えません。

## 中継用の Argo CD

![Managed Argo CD が持つ 2 つの Application が、EKS クラスタに中継用の Argo CD とその Application を入れ、中継用の Argo CD がスクリプトで置いたトークンで EKS ではないクラスタにデプロイする](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cb793f2e6301ee/zenn/articles/cb793f2e6301ee/two-stage.png)

AKS や GKE、自分で構築したクラスタのように、コントロールプレーンが EKS ではない Kubernetes へは、中継用の Argo CD を通してデプロイします。Managed Argo CD のデプロイ先は [EKS クラスタの ARN で指定するものだけ](https://docs.aws.amazon.com/eks/latest/userguide/argocd-comparison.html)なので、Managed Argo CD からは直接デプロイできません。そのクラスタのノードは、すでにそのクラスタのコントロールプレーンに属しています。Kubernetes のノードは 1 つのクラスタにしか参加しないので、そのままでは EKS の Hybrid ノードになれず、Managed Argo CD のデプロイ先にもなりません。

Managed Argo CD から直接デプロイしたいなら、マシンを元のクラスタから外し、Hybrid ノードとして EKS クラスタに参加させ直すことになります。ただし、AKS や GKE のノードは他社のクラウドのマシンなので、前の節のとおり Hybrid Nodes のサポート対象外です。元のクラスタをそのまま使いたい場合のために、今回は次の構成を確かめました。

1. Managed Argo CD とは別に、オープンソースの通常の Argo CD を 1 つ用意し、EKS クラスタの中で動かします。この記事では、これを「中継用の Argo CD」と呼びます。中継用の Argo CD は、AWS ではなく利用者が運用します。デプロイ先を API サーバーの URL とトークンで登録できるので、EKS ではないクラスタにもデプロイできます。
2. 中継用の Argo CD そのものも、Helm chart として配られている普通のアプリです。そのため、中継用の Argo CD を EKS クラスタに入れる作業も、Managed Argo CD のデプロイとして行えます。
3. その結果、Managed Argo CD が EKS クラスタに中継用の Argo CD を入れ、中継用の Argo CD が EKS ではないクラスタにデプロイする、という 2 段の流れになります。

Managed Argo CD には、[2 つの Application](https://github.com/littlemex/distributed-ai/blob/ca98dda99c81cf7a3ec6d21cd9088f7724684e2f/investigations/2026-10-29-eks-capabilities-hybrid-nodes/k8s/t3-tier2-argocd.yaml) を置きます。1 つは、Helm chart [argo-cd 10.2.2](https://github.com/argoproj/argo-helm/tree/e510a7d9ebbc91ae681f333ba4b4041545448881/charts/argo-cd) で中継用の Argo CD を入れる `tier2-argocd` です。もう 1 つは、Helm chart [argocd-apps 2.0.7](https://github.com/argoproj/argo-helm/tree/dfeb6aab23ceeef800236c2e3465968e6abf3717/charts/argocd-apps) で、中継用の Argo CD が持つ Application の `podinfo-other` を作る `tier2-apps` です。中継用の Argo CD が何をどこにデプロイするかは、argocd-apps の値として、Managed Argo CD の Application の中に書けます。そのため、今回の 2 つのデプロイ先では、デプロイする内容を変えるときに触るのは Managed Argo CD の Application だけで済みました。ただし、EKS ではないクラスタを中継用の Argo CD に登録する cluster secret はトークンを含むので、今回は Application に書かず、スクリプトで中継用の Argo CD の namespace に直接置きました。

中継用の Argo CD は、Managed Argo CD の CRD と Application が置かれた EKS クラスタで動くので、3 つのことに気を付けます。

- Application などの CRD は、[Managed Argo CD を作るときに EKS が入れます](https://docs.aws.amazon.com/eks/latest/userguide/argocd-create-cli.html)。今回のログでも、中継用の Argo CD を入れる前の時点で CRD `applications.argoproj.io` はすでにありました。中継用の Argo CD の chart では `crds.install: false` にして入れません。
- argo-cd の chart は版ごとに CRD を同梱していて、中継用の Argo CD はその CRD を入れずに Managed Argo CD の CRD を使うので、中継用の Argo CD のマイナー版を Managed Argo CD にそろえました。今回、Managed Argo CD は `aws eks describe-capability` で `3.4.7-eks-1` と表示され、中継用の Argo CD には Argo CD 3.4.6 を入れる chart 10.2.2 を使いました。Managed Argo CD は[版の更新も AWS が行う](https://docs.aws.amazon.com/eks/latest/userguide/working-with-capabilities.html)ので、`describe-capability` の版を定期的に確かめ、マイナー版が変わったら、中継用の Argo CD の chart も同じマイナー版の Argo CD を入れるものに上げる、という方針になります。chart が入れる Argo CD の版は chart の appVersion に書かれていて、chart の版とは番号が別です。対応は、次のコマンドで見られます。

```bash
helm repo add argo https://argoproj.github.io/argo-helm
helm search repo argo/argo-cd --versions
```

中継用の Argo CD を先に新しいマイナー版へ上げると、古い CRD の上で新しいコントローラーが動くことになるので、先には上げません。この方針は今回の版で動いたことを確かめただけで、版を上げる手順そのものは試していません。
- Managed Argo CD は、[作るときに指定した namespace の Application だけ](https://docs.aws.amazon.com/eks/latest/userguide/argocd-comparison.html)を扱います。通常の Argo CD も、[既定では自分の namespace の Application だけ](https://argo-cd.readthedocs.io/en/release-3.4/operator-manual/app-any-namespace/)を扱います。中継用の Argo CD を `argocd-edge` に入れ、Managed Argo CD の `argocd` と分けたので、どちらの Argo CD がどの Application を扱うかが namespace で決まり、同じ Application を 2 つの Argo CD が取り合いません。

この構成では、利用者が次の 4 つを引き受けます。

- 中継用の Argo CD の版の更新と可用性は、利用者の責任になります。AWS が運用するのは Managed Argo CD だけです。
- EKS ではないクラスタのトークンを、中継用の Argo CD の cluster secret として管理する必要があります。今回は、k3s の ServiceAccount に結び付けた Secret に入る、期限のないトークンを使いました。漏れたときは k3s 側でその Secret を消して無効にし、作り直したトークンで cluster secret を書き換えます。期限のあるトークンを使うなら、期限が切れる前に書き換える仕組みが要ります。
- 中継用の Argo CD が動く EKS クラスタから、EKS ではないクラスタの API サーバーへ通信が届く必要があります。AKS や GKE なら、方法は 2 つあります。1 つは、API サーバーを private にしたまま、VPN などで AWS の VPC とつなぐ方法です。今回の検証もこの形で、k3s に Transit Gateway を通る private なアドレスでつなぎました。もう 1 つは、[AKS の authorized IP ranges](https://learn.microsoft.com/azure/aks/api-server-authorized-ip-ranges) や [GKE の authorized networks](https://cloud.google.com/kubernetes-engine/docs/how-to/authorized-networks) に、EKS クラスタから外に出るときのアドレスを入れる方法です。EKS クラスタのノードが NAT Gateway から外に出る構成なら、そのアドレスは NAT Gateway のアドレスです。この方法では、同じ NAT Gateway を通るほかのワークロードからも API サーバーに届くので、API サーバー側の認証と権限で絞ることが前提になります。
- 中継用の Argo CD は、Managed Argo CD のアクセスエントリとは別に、自分の ServiceAccount に結び付いた ClusterRole で EKS クラスタを操作します。そのため、Managed Argo CD の権限を絞っても、中継用の Argo CD の権限は別に絞る必要があります。

中継構成に関わる権限について、今回の設定を表にまとめます。区分の列は、絞ったもの、既定のまま残したもの、広く与えたもののどれに当たるかを示します。

| 区分 | 対象 | 今回の設定 |
|---|---|---|
| 絞った | 中継用の Argo CD のデプロイ先 | `cluster.inClusterEnabled: "false"` で、自分が動く EKS クラスタを [in-cluster のアドレスで使えないように](https://argo-cd.readthedocs.io/en/release-3.4/operator-manual/argocd-cm-yaml/)設定 |
| 絞った | k3s 向けの Application | デプロイ先を k3s の 1 つの namespace に、取得元を podinfo の chart リポジトリに限った AppProject |
| 既定のまま | 中継用の Argo CD の application-controller の EKS 側の権限 | EKS クラスタ全体を読み書きできる ClusterRole |
| 既定のまま | 中継用の Argo CD の画面へのログイン | Identity Center ではなくローカルの admin |
| 既定のまま | 中継用の Argo CD の画面の admin のパスワード | 起動時に作られる `argocd-edge` の Secret `argocd-initial-admin-secret` に保存 |
| 広く与えた | k3s 側の権限 | 検証を短く済ませるため、中継用の Argo CD が使う ServiceAccount に `cluster-admin` |
| 広く与えた | Managed Argo CD の EKS 側の権限 | 検証を短く済ませるため `AmazonEKSClusterAdminPolicy`。中継用の Argo CD の chart が ClusterRole と ClusterRoleBinding を作るので、中継構成のままではそれを作れる権限が必要 |

実運用では、既定のまま残したものと広く与えたものも絞ります。k3s 側の権限を namespace の Role に絞るなら、Role では namespace を作れないので、デプロイ先の namespace を先に作り、Application の `CreateNamespace=true` と AppProject の Namespace の許可を外したうえで、中継用の Argo CD が使う ServiceAccount をその namespace の Role に結び付けます。この絞り方は、今回は確かめていません。[cluster secret の namespaces](https://argo-cd.readthedocs.io/en/release-3.4/operator-manual/declarative-setup/#clusters) は、中継用の Argo CD が扱う namespace を限る設定で、k3s 側の権限を狭めるものではありません。Role に絞る場合は、この設定でもデプロイ先の namespace を指定しておきます。[Argo CD の文書](https://argo-cd.readthedocs.io/en/release-3.4/operator-manual/declarative-setup/#clusters)によると、namespaces を指定すると、中継用の Argo CD はクラスタ全体のリソースを扱わなくなるからです。

## 中継構成以外の方法

EKS ではないクラスタにデプロイする方法は、中継構成だけではありません。今回確かめたのは中継構成だけで、ほかの方法は試していません。

| 方法 | 良いところ | 引き換えになるもの |
|---|---|---|
| 各クラスタに Argo CD か Flux を置き、それぞれが Git から取得 | 外から API サーバーに入る通信が不要。トークンをクラスタの外に出さない | クラスタの数だけ Argo CD や Flux を運用。状態を 1 か所で見るには別の仕組みが必要 |
| 中央の Argo CD と、各クラスタに置く [argocd-agent](https://github.com/argoproj-labs/argocd-agent) の組み合わせ | 各クラスタの agent が中央に接続するので、API サーバーを外に開けずに中央の画面を維持 | 2026 年 10 月 29 日に EKS ユーザーガイドの Argo CD の節を見た範囲では、Managed Argo CD と組み合わせられるという記述なし |
| 今回の中継構成 | デプロイする内容の書き換えを、トークンを除いて Managed Argo CD の Application に集約 | 中継用の Argo CD の運用、トークンの管理、EKS から相手の API サーバーへの通信 |

EKS ではないクラスタを [EKS Connector](https://docs.aws.amazon.com/eks/latest/userguide/eks-connector.html) で EKS に登録しても、そのクラスタに使える EKS の API は登録、一覧、参照、登録解除だけです。Managed Argo CD が使うアクセスエントリは設定できないので、文書の上ではデプロイ先になりません。

## 検証の結果

検証の環境では、3 つの VPC を Transit Gateway でつなぎ、それぞれを AWS、BYOI の置き場所、EKS ではない Kubernetes に見立てました。BYOI 役の EC2 には instance profile を付けず、AWS への認証は Systems Manager のハイブリッドアクティベーションだけで行いました。物理サーバーを参加させるときと認証の条件をそろえるためです。EKS ではない Kubernetes は、EC2 に入れた k3s です。クラスタの API エンドポイントは private だけにしました。

この環境で、次の 6 つの項目がすべて通りました。

| # | 確かめたこと | 結果 |
|---|---|---|
| T1 | Managed Argo CD から BYOI へ Helm chart をデプロイ | デプロイを確認。2 つの Pod が BYOI の上で、BYOI の Pod の範囲 10.81.0.0/16 の IP で稼働。この範囲を VPC からルーティングできるので、AWS 側のノードの Pod から Service へのリクエストに、2 つのうちどちらかの Pod が応答 |
| T2 | EKS ではないクラスタを URL とトークンで Managed Argo CD に登録 | cluster secret は作成可。それを使う Application は `server should be specified as a cluster ARN` のエラーで停止し、k3s にデプロイ先の namespace は作られないことを確認 |
| T3 | 中継用の Argo CD を経由して k3s へデプロイ | デプロイを確認。Managed Argo CD の `tier2-argocd` と `tier2-apps`、中継用の Argo CD の `podinfo-other` がすべて Synced と Healthy |
| T4 | Managed Argo CD の上の 2 つの Application (`podinfo-onprem` と `tier2-apps`) の値だけを変更 | BYOI では 3 つ、k3s では 2 つのレプリカがすべて更新され、どの Pod も自分の IP で新しいメッセージを返すことを確認。BYOI は 121 秒以内、k3s は 78 秒以内 |
| T5 | k3s で Deployment を手で削除 | 中継用の Argo CD による作り直しを確認。削除と作り直しの時刻の差は、秒単位の時計で 1 秒 |
| T6 | BYOI の kubelet の接続先 | クラスタの VPC の private のアドレス 10.0.4.94 への接続を確認 |

T4 の秒数は、最初の値の変更から数えた上限です。2 つのデプロイ先を同じループで確かめ、1 回の確認のあとに 5 秒待ちます。1 回の確認には SSM Run Command の往復も入るので、秒数は Argo CD が反映するまでの時間そのものではありません。BYOI は 3 つの Pod を 1 つずつ SSM Run Command で確かめるので、1 回の確認に k3s より時間がかかります。そのため、2 つの秒数の差は 2 つの経路の速さの差ではありません。T5 は、削除のコマンドを出した時刻と、作り直された Deployment の作成時刻を比べたもので、どちらも k3s のマシンの時計の秒単位です。Pod が Ready になるまでの時間は含みません。T2 は、Managed Argo CD が出すエラーの文言で合否を決めているので、AWS が文言を変えると、拒否されていても FAIL になります。

実際の BYOI での構築とは、次の点が違います。

- 経路は Transit Gateway で、VPN や Direct Connect ではありません。
- Hybrid ノードは EC2 です。実際のサーバーでは、OS が [AWS の対応表](https://docs.aws.amazon.com/eks/latest/userguide/hybrid-nodes-os.html)に載っている必要があります。
- EKS ではないクラスタは EC2 に入れた k3s で、AKS や GKE では試していません。
- Managed Argo CD と、k3s 側で中継用の Argo CD が使う ServiceAccount には、「中継用の Argo CD」の節の表のとおり広い権限を与えました。実運用での絞り方は、[最小権限の設定](https://docs.aws.amazon.com/eks/latest/userguide/argocd-register-clusters.html#_production_setup_with_least_privilege)にあります。

構築、検証、削除の手順とコードは [littlemex/distributed-ai の investigations](https://github.com/littlemex/distributed-ai/tree/ca98dda99c81cf7a3ec6d21cd9088f7724684e2f/investigations/2026-10-29-eks-capabilities-hybrid-nodes) にあります。

## まとめ

EKS Capabilities の Managed Argo CD は EKS クラスタにしかデプロイできませんが、BYOI を Hybrid Nodes で EKS クラスタのノードにすれば、BYOI にも直接デプロイできます。今回はこれを、AWS のサポート対象外である EC2 を BYOI に見立てて確かめました。EKS ではない Kubernetes には、Managed Argo CD が入れた中継用の Argo CD を経由してデプロイできることを k3s で確かめ、デプロイする内容は、トークンを含む cluster secret を除いて、Managed Argo CD の Application だけで変えられました。
