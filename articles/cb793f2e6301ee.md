## はじめに

[EKS Hybrid Nodes](https://docs.aws.amazon.com/ja_jp/eks/latest/userguide/hybrid-nodes-overview.html) を使うと、EKS の外で自分で用意するマシンを EKS クラスタのノードとして参加させ、AWS 側のコントロールプレーンから管理できます。AWS の文書は、この考え方を [bring your own infrastructure](https://docs.aws.amazon.com/ja_jp/eks/latest/userguide/hybrid-nodes-overview.html#hybrid-nodes-features) と呼んでいます。この記事でも、このように自分で用意するマシンを BYOI (bring your own infrastructure、持ち込みのインフラ) と呼びます。例えばオンプレミスのサーバーを管理下に置けます。EKS には [EKS Capabilities](https://docs.aws.amazon.com/ja_jp/eks/latest/userguide/capabilities.html) という機能もあり、その 1 つとして Argo CD を AWS が運用する形で使えます。この記事では、AWS が運用するこの Argo CD を「Managed Argo CD」と呼びます。Hybrid ノードも EKS クラスタのノードなので、Managed Argo CD から EKS クラスタにデプロイすれば、原理的には Hybrid ノードにも届くはずです。これが実際に問題なく動くのかを、環境を作って確かめました。あわせて、AKS や GKE、自分で建てたクラスタのような、EKS ではない Kubernetes にもデプロイできるかを確かめました。

結論を先に表にします。Managed Argo CD にデプロイ先として登録できるのは EKS クラスタだけで、BYOI には、BYOI が参加した EKS クラスタへのデプロイとして届きます。自分で用意した環境は、マシンを EKS のノードとして参加させる場合と、すでに動いている Kubernetes クラスタにデプロイする場合とで、行が分かれます。

| デプロイ先 | Managed Argo CD からの直接デプロイ | 方法 |
|---|---|---|
| EKS クラスタ | 可 | クラスタの ARN (AWS のリソースを一意に指す名前) で登録 |
| BYOI | 可 | EKS Hybrid Nodes で EKS クラスタのノードとして参加。今回は EC2 で確認 |
| EKS ではない Kubernetes (AKS、GKE、自分で建てたクラスタ) | 不可 | EKS クラスタに置いた中継用の Argo CD を経由。今回は k3s で確認 |

この記事は、Argo CD と EKS の基本を知っている読者に向けて、それぞれの方法がなぜ成り立つのかと、確かめた結果を書きます。

## Managed Argo CD がデプロイできる相手

まず、Managed Argo CD の部品がどこにあるかを押さえます。

![Managed Argo CD のコントローラーは AWS が運用する場所にあり、利用者の EKS クラスタの API サーバーを通して、クラスタの argocd namespace にある Application と cluster secret を読み、マニフェストを適用する。利用者は Application を自分のクラスタに kubectl apply する](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cb793f2e6301ee/zenn/articles/cb793f2e6301ee/placement.png)

Managed Argo CD の部品は、2 か所に分かれています。

- 実際にデプロイの仕事をするコントローラーは、利用者の EKS クラスタの中ではなく、[AWS が運用する場所](https://docs.aws.amazon.com/ja_jp/eks/latest/userguide/capabilities-controller-logs.html)で動きます。利用者のノードの上には、コントローラーの Pod はありません。
- 何をどこにデプロイするかを書いた Application と、デプロイ先を書いた Secret である cluster secret は、今回の構成では、Managed Argo CD を作った EKS クラスタの `argocd` namespace に、普通の Kubernetes のオブジェクトとして置きます。

利用者は Application を自分のクラスタに `kubectl apply` するだけです。コントローラーはクラスタの API サーバーを通してそれを読み、Helm chart や Git のリポジトリから中身を取ってきて、デプロイ先の API サーバーにマニフェストを適用します。今回はデプロイ先も同じクラスタなので、同じ API サーバーです。Pod がどのノードに置かれるかは、クラスタのスケジューラが決めます。

次に、デプロイ先をどう指定するかです。

![上の段は EKS クラスタの ARN で登録した場合で、Managed Argo CD が ARN でクラスタを見つけ、IAM ロールで入り、アクセスエントリがそのロールに Kubernetes の権限を与えてマニフェストが適用される。下の段は URL とトークンで登録した場合で、cluster secret は作れるが Application が止まり、相手のクラスタには何も届かない](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cb793f2e6301ee/zenn/articles/cb793f2e6301ee/register.png)

Managed Argo CD がデプロイできるのは EKS クラスタだけで、AWS の比較の文書にも[デプロイ先は EKS クラスタの ARN だけ](https://docs.aws.amazon.com/ja_jp/eks/latest/userguide/argocd-comparison.html)と書かれています。理由は、Managed Argo CD がデプロイ先を見つける方法と、デプロイ先に入る方法の両方が EKS の仕組みでできているからです。上の図の上の段がその流れです。

1. デプロイ先は cluster secret で登録します。Managed Argo CD では、その `server` に EKS クラスタの ARN を書きます。Managed Argo CD を作った EKS クラスタ自身も、[自動ではデプロイ先に登録されない](https://docs.aws.amazon.com/ja_jp/eks/latest/userguide/argocd-register-clusters.html)ので、同じように ARN で登録します。
2. AWS 側のコントローラーは、ARN でデプロイ先のクラスタを特定し、Managed Argo CD を作るときに渡した IAM ロールでそのクラスタの API サーバーに入ります。
3. デプロイ先の EKS クラスタでは、[アクセスエントリ](https://docs.aws.amazon.com/ja_jp/eks/latest/userguide/argocd-register-clusters.html) (IAM ロールに Kubernetes の権限を結び付ける EKS の設定) が、その IAM ロールに権限を与えます。
4. 権限をもらった Managed Argo CD が、マニフェストを適用します。

図の下の段は、通常の Argo CD と同じように、API サーバーの URL とトークンで登録した場合です。cluster secret はエラーなく作れます。ところが、その cluster secret を使う Application は、condition に次のエラーを出して止まり、相手のクラスタには何も届きませんでした。

```text
Failed to load live state: failed to get cluster info for "https://10.90.0.48:6443": error getting cluster: error getting cluster RESTConfig: server should be specified as a cluster ARN
```

エラーの文言からは、Managed Argo CD が `server` に ARN を求め、URL を受け付けずに止まっていると読めます。Managed Argo CD のデプロイ先は EKS クラスタの ARN で指定するので、EKS ではないクラスタはこの流れに乗れません。EKS ではないクラスタにデプロイする方法は、後の節で説明します。

## Hybrid Nodes による BYOI の参加

![Managed Argo CD は EKS の API サーバーにマニフェストを適用し、スケジューラが Pod ごとにノードを選ぶ。nodeSelector で compute-type: hybrid を指定した Pod は BYOI に、hybrid を避ける affinity を付けた Pod はクラウドのノードに置かれる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cb793f2e6301ee/zenn/articles/cb793f2e6301ee/hybrid-deploy.png)

BYOI を EKS クラスタのノードにすれば、Managed Argo CD は、EKS クラスタへのデプロイと同じやり方で、そのマシンにもアプリを届けられます。そのための機能が、はじめにで触れた EKS Hybrid Nodes です。コントロールプレーンは AWS 側にあり、BYOI はノードとして働くだけです。

Managed Argo CD は、AWS 側にある EKS の API サーバーにマニフェストを適用するだけで、BYOI のネットワークに入る必要はありません。Pod をどのノードに置くかは Kubernetes のスケジューラが決めます。Hybrid ノードには[既定で `eks.amazonaws.com/compute-type: hybrid` というラベルが付く](https://docs.aws.amazon.com/ja_jp/eks/latest/userguide/hybrid-nodes-add-ons.html)ので、Pod の `nodeSelector` にこのラベルを指定すれば、Pod の置き場所を BYOI に限れます。ただし、今回は Hybrid ノードに taint を付けていないので、置き場所を指定しない Pod は BYOI にも置かれることがあります。クラウドで動かしたい Pod には、このラベルを避ける affinity を付けるか、Hybrid ノードに taint を付けます。今回は、後の節で説明する中継用の Argo CD を、この affinity でクラウドのノードに限りました。今回デプロイした [podinfo の chart](https://github.com/stefanprodan/podinfo/tree/fd3a834ed8d14b80ea334cf8a2fddd4597924da6/charts/podinfo) は、Helm の値の `nodeSelector` を Pod に渡すので、`podinfo-onprem` という [Application](https://github.com/littlemex/distributed-ai/blob/ca98dda99c81cf7a3ec6d21cd9088f7724684e2f/investigations/2026-10-29-eks-capabilities-hybrid-nodes/k8s/t1-podinfo-onprem.yaml) の値に次の 2 行を書くだけで済みました。

```yaml
nodeSelector:
  eks.amazonaws.com/compute-type: hybrid
```

次に、BYOI と AWS の間の通信です。

![クラスタの VPC と BYOI のネットワークをプライベートな接続でつなぐ。kubelet は API エンドポイントの 443 番に接続し、API サーバーは kubelet の 10250 番に接続する。BYOI のノードと Pod の範囲を、EKS の RemoteNodeNetwork と RemotePodNetwork、VPC のルートテーブル、セキュリティグループ、BYOI 側の経路に入れる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cb793f2e6301ee/zenn/articles/cb793f2e6301ee/hybrid-network.png)

BYOI のマシンは、AWS 側にある EKS のコントロールプレーンと通信できなければ、ノードとして働けません。kubelet が API サーバーに接続してノードとして登録し、API サーバーもログの取得などのために kubelet に接続するからです。そのため、BYOI のネットワークとクラスタの VPC をつなぎ、BYOI のノードと Pod の IP の範囲を EKS に登録して、VPC のルートテーブルと BYOI 側のネットワークに経路を、セキュリティグループに必要なポートの許可を入れます。今回は、BYOI の Pod の IP にも VPC から届く構成にしました。必要なポートと設定の詳細は、[AWS の文書](https://docs.aws.amazon.com/ja_jp/eks/latest/userguide/hybrid-nodes-networking.html)にまとまっています。

![EKS の RemoteNetworkConfig にオンプレミスのノードと Pod の範囲を書き、VPC のルートテーブルとオンプレミスのルートテーブルの両方に、その範囲への経路を入れる](https://docs.aws.amazon.com/ja_jp/eks/latest/userguide/images/hybrid-prereq-diagram.png)
*出典: Amazon EKS ユーザーガイド「[ハイブリッドノード用のネットワークを準備する](https://docs.aws.amazon.com/ja_jp/eks/latest/userguide/hybrid-nodes-networking.html)」、CC BY-SA 4.0*

クラスタの API エンドポイントは、インターネットに出さず private にしておくのが安全です。今回も API エンドポイントを private だけにし、BYOI との経路もプライベートな接続にした構成で検証し、Managed Argo CD からのデプロイまで動きました。BYOI の置き場所との VPN の代わりには、VPC 同士をプライベートにつなぐ Transit Gateway を使いました。private だけのクラスタでも、Managed Argo CD は[デプロイできます](https://docs.aws.amazon.com/ja_jp/eks/latest/userguide/argocd-register-clusters.html#_private_clusters)。

Hybrid ノードは、Pod のネットワークを作る部品である CNI が動くまで Ready になりません。Hybrid ノードには [VPC CNI を使えない](https://docs.aws.amazon.com/ja_jp/eks/latest/userguide/hybrid-nodes-add-ons.html)ので、Cilium などの CNI を自分で入れます。今回は、AWS が ECR Public に置いている Cilium の Helm chart を使いました。対応する CNI と版、OS ごとの制約は [CNI のページ](https://docs.aws.amazon.com/ja_jp/eks/latest/userguide/hybrid-nodes-cni.html)にあります。

## 他社クラウドのマシンと Hybrid Nodes

他社のクラウドのマシンを Hybrid Nodes にする構成は、AWS の文書で[サポートの対象外](https://docs.aws.amazon.com/ja_jp/eks/latest/userguide/hybrid-nodes-overview.html#hybrid-nodes-general)とされています。本番で使うなら、AWS のサポートを受けられないことと、障害の切り分けや運用を自分たちで統制する必要があることを受け入れたうえで使うべきです。

> Running EKS Hybrid Nodes on cloud infrastructure, including AWS Regions, AWS Local Zones, AWS Outposts, or in other clouds, is not supported. You will be charged the hybrid nodes fee if you run hybrid nodes on Amazon EC2 instances.

この線引きは、VM かベアメタルかでは分かれていません。同じページは、Hybrid ノードを[物理マシンと仮想マシンのどちらでも動かせる](https://docs.aws.amazon.com/ja_jp/eks/latest/userguide/hybrid-nodes-overview.html#hybrid-nodes-features)としています。文書が区別しているのは、オンプレミスか、AWS を含むクラウドかだけです。Azure や Google Cloud が提供するベアメタルのサーバーも「in other clouds」に含まれると読むのが自然で、ベアメタルならサポートされるという記述はありません。

技術的に動くかどうかについては、Hybrid ノードを参加させるツールである [nodeadm のソース](https://github.com/aws/eks-hybrid/tree/ab5348b9ea98bb07f93097f07b9db48688486713)を見た範囲で、他社のクラウドを見分けて参加を拒否するような処理は見つかりませんでした。今回、EC2 では参加からデプロイまで動いたので、Azure や Google Cloud のマシンも、技術的にはノードとして追加できそうです。ただし、Azure と Google Cloud のマシンでは試していないので、確実に動くとは言えません。

## 中継用の Argo CD

EKS ではない Kubernetes にデプロイする方法の 1 つとして、中継用の Argo CD を経由する構成が考えられます。今回は、この構成を実際に試しました。まず、考え方の全体を示します。

![Managed Argo CD が EKS クラスタにセルフホストの中継用の Argo CD とその Application を入れ、中継用の Argo CD が API サーバーの URL とトークンで EKS ではないクラスタにデプロイする](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cb793f2e6301ee/zenn/articles/cb793f2e6301ee/relay-concept.png)

1. Managed Argo CD とは別に、オープンソースの通常の Argo CD を 1 つ用意し、EKS クラスタの中で動かします。AWS が運用するのではなく、利用者が自分で運用するセルフホストの Argo CD です。この記事では、これを「中継用の Argo CD」と呼びます。デプロイ先を API サーバーの URL とトークンで登録できるので、EKS ではないクラスタにもデプロイできます。
2. 中継用の Argo CD そのものも、Helm chart として配られている普通のアプリです。そのため、中継用の Argo CD を EKS クラスタに入れる作業も、Managed Argo CD のデプロイとして行えます。
3. その結果、Managed Argo CD が EKS クラスタに中継用の Argo CD を入れ、中継用の Argo CD が EKS ではないクラスタにデプロイする、という 2 段の流れになります。中継用の Argo CD が何をどこにデプロイするかも Managed Argo CD の Application に書けるので、デプロイする内容を変える場所は、トークンを除いて Managed Argo CD の 1 か所にまとまります。

この構成が要るのは、EKS ではないクラスタのノードが、すでにそのクラスタのコントロールプレーンに属しているからです。そのままでは EKS の Hybrid ノードになれません。Managed Argo CD から直接デプロイしたいなら、マシンを元のクラスタから外し、Hybrid ノードとして EKS クラスタに参加させ直すことになります。元のクラスタをそのまま使う場合に、中継用の Argo CD が使えます。

ここからは、中継構成を組むときに大事なネットワークと認証認可の 2 点を説明します。

ネットワークでは、中継用の Argo CD から、EKS ではないクラスタの API サーバーに届く必要があります。中継用の Argo CD は、EKS クラスタの中から相手の API サーバーを呼んでデプロイするからです。相手の API サーバーをインターネットに開くと攻撃される入口が増えるので、BYOI と同じく、VPN などのプライベートな接続でつなぐのが安全です。今回は、k3s に Transit Gateway を通る private なアドレスでつなぎました。

![Managed Argo CD は IAM ロールとアクセスエントリで EKS クラスタに入り、中継用の Argo CD は自分の ServiceAccount で EKS クラスタを操作し、cluster secret に入れたトークンで EKS ではないクラスタの API サーバーに入る](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cb793f2e6301ee/zenn/articles/cb793f2e6301ee/relay-auth.png)

認証認可では、誰がどの認証情報でどこに入るかを 3 つに分けて押さえます。

- Managed Argo CD は、IAM ロールとアクセスエントリで EKS クラスタに入ります。中継用の Argo CD の chart は ClusterRole を作るので、Managed Argo CD のアクセスエントリには、ClusterRole を作れる権限が要ります。
- 中継用の Argo CD は、EKS クラスタの中で、自分の ServiceAccount と ClusterRole で動きます。chart の既定のままでは、この ClusterRole で EKS クラスタ全体を読み書きできます。そこで、`cluster.inClusterEnabled: "false"` で既定のデプロイ先である自分の EKS クラスタを外し、AppProject で Application が指定できるデプロイ先と取得元を限ります。ただし、これらは ServiceAccount の権限そのものは狭めないので、狭めるなら ClusterRole を絞ります。Managed Argo CD の画面には IAM Identity Center で入りますが、中継用の Argo CD の画面にはローカルの admin で入ります。
- 中継用の Argo CD は、EKS ではないクラスタに、相手の ServiceAccount のトークンで入ります。トークンは cluster secret に入れ、Git には置かずに中継用の Argo CD の namespace に直接置きます。相手のクラスタで何ができるかは、そのトークンの ServiceAccount の RBAC で決まります。今回は検証を短く済ませるため `cluster-admin` を与えました。実運用で namespace の中だけに絞るなら、デプロイ先の namespace を先に作り、Role と RoleBinding で権限を与え、Application の `CreateNamespace=true` も外します。

設定としては、Managed Argo CD に 2 つの Application を置きます。`tier2-argocd` は Helm chart argo-cd で中継用の Argo CD を入れ、`tier2-apps` は Helm chart argocd-apps で、中継用の Argo CD の AppProject と Application を作ります。具体的な値は、[リポジトリの設定](https://github.com/littlemex/distributed-ai/blob/ca98dda99c81cf7a3ec6d21cd9088f7724684e2f/investigations/2026-10-29-eks-capabilities-hybrid-nodes/k8s/t3-tier2-argocd.yaml)にあります。

版の更新では、中継用の Argo CD のマイナー版を Managed Argo CD にそろえます。2 つの Argo CD は、同じクラスタの CRD を共有するからです。その CRD は [Managed Argo CD を作るときに EKS が入れ](https://docs.aws.amazon.com/ja_jp/eks/latest/userguide/argocd-create-cli.html)、[版の更新も AWS が行う](https://docs.aws.amazon.com/ja_jp/eks/latest/userguide/working-with-capabilities.html)ので、中継用の Argo CD の chart は `crds.install: false` で CRD を入れません。`aws eks describe-capability` で Managed Argo CD の版を定期的に確かめ、マイナー版が上がったら、中継用の Argo CD をあとから同じマイナー版に上げます。Helm chart argo-cd の版は Argo CD の版と別なので、chart の appVersion を見て選びます。中継用の Argo CD を先に上げると、古い CRD の上で新しいコントローラーが動くことになります。マイナー版をそろえても互換性が保証されるわけではないので、上げる前に Argo CD のリリースノートで CRD の変更を確かめます。

## まとめ

EKS Capabilities の Managed Argo CD は EKS クラスタにしかデプロイできませんが、BYOI を Hybrid Nodes で EKS クラスタのノードにすれば、BYOI にも直接デプロイできます。今回はこれを、AWS のサポート対象外である EC2 を BYOI に見立てて確かめました。EKS ではない Kubernetes には、Managed Argo CD が入れた中継用の Argo CD を経由してデプロイできることを k3s で確かめ、デプロイする内容は、トークンを含む cluster secret を除いて、Managed Argo CD の Application だけで変えられました。構築、検証、削除のコードと結果のログは、[littlemex/distributed-ai の investigations](https://github.com/littlemex/distributed-ai/tree/ca98dda99c81cf7a3ec6d21cd9088f7724684e2f/investigations/2026-10-29-eks-capabilities-hybrid-nodes) にあります。
