## はじめに

SGLang で DeepSeek 系のモデルを動かしていると、SGLang の内部に `MHA` と `MLA` という 2 種類の計算の手順があることに気づきます。`MHA` と聞くと、普通の Multi-Head Attention を使うモデルのことだと思うかもしれません。しかし DeepSeek-V2 は、MLA (Multi-head Latent Attention) という別の作りの attention を使うモデルです。SGLang の `MHA` はモデルの種類ではなく、この MLA のモデルを計算する手順の 1 つの名前です。

LLM の推論には、入力の文章をまとめて計算する prefill と、出力のトークンを 1 つずつ作る decode の 2 つの段階があります。この記事では、同じ MLA を計算する 2 つの手順と、SGLang がどちらを選ぶかの決まりを説明します。そのうえで、数トークンの cache hit で prefill 全体が遅い手順に回る例と page size による回避、死活確認の要求が起こす例外と、そこで見つかった triton の計算の無駄を紹介します。

この記事で測った条件は、SGLang 0.5.12.post1 (commit `5a15cde8`)、triton の attention のバックエンド、DeepSeek-V2-Lite-Chat、NVIDIA RTX PRO 4500 Blackwell の GPU です。モデルはテンソル並列 (モデルを複数の GPU に分けて置く方法) で 2 台の GPU に置きました。prefill と decode を別々のエンジンに分ける構成 (分離構成) で、prefill 側のエンジンの 1 台目の GPU (TP0) を測りました。時間はどれも、1 バッチの GPU の時間を CUDA のイベントで測ったもので、最初の 1 回とプロファイラを使った回は除いています。ほかのバックエンド、GPU、構成では、ここに書く数字や決まりがそのまま当てはまるとは限りません。

## MLA が KV cache に残すもの

attention は、過去のトークンを参照しながら次の計算をします。そのため、推論のエンジンは過去のトークンから計算した K (key) と V (value) を、KV cache という領域に残しておきます。普通の Multi-Head Attention では、head ごとに K と V を残すので、head の数が多いほど KV cache が大きくなります。

DeepSeek-V2 の MLA は、K と V を head ごとに残す代わりに、1 本の小さな圧縮したベクトル (latent) と、位置の情報を持つ小さな K (rope key) だけを残します。このしくみは [DeepSeek-V2 の論文](https://arxiv.org/abs/2405.04434) で提案されたものです。

![KV cache に残す値の数](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/8fc848bd0515c4/zenn/articles/8fc848bd0515c4/kv-cache.png)

DeepSeek-V2-Lite の[設定](https://huggingface.co/deepseek-ai/DeepSeek-V2-Lite-Chat/blob/85864749cd611b4353ce1decdb286193298f64c7/config.json)では、head の数が 16、latent が 512 次元、rope key が 64 次元です。1 トークン・1 層あたりに残す値は 512 + 64 = 576 個になります。比べるために、同じ head の大きさを持つ普通の Multi-Head Attention の層を考えます。K は位置の情報を持たない 128 次元と rope の 64 次元、V は 128 次元で、残す値は 5,120 個です。全部の head を 1 台の GPU に置いた場合で比べると、保存する値の数は 5,120 個から 576 個になり、約 9 分の 1 です。テンソル並列では、普通の Multi-Head Attention の K と V は head ごとに GPU に分かれますが、MLA の latent はどの GPU にも丸ごと置くので、1 台あたりの差は 9 分の 1 より縮みます。どの比も設定の値から計算したもので、実際のメモリの量を測った値ではありません。

大事なのは、この先に出てくる SGLang の `MHA` も `MLA` も、どちらもこの圧縮したベクトルを KV cache に持つ同じ MLA のモデルを計算している、という点です。

## 同じ MLA を計算する 2 つの手順

圧縮したベクトルから attention を計算する方法は、2 通りあります。どちらも数式の上では同じ attention を表し、かかる計算の量が違います。浮動小数点の計算の順序は違うので、数値が完全に一致するかどうかは確かめていません。

![MLA の 2 つの計算の手順](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/8fc848bd0515c4/zenn/articles/8fc848bd0515c4/two-procedures.png)

1 つ目は、圧縮したベクトルを head ごとの K と V に展開してから、普通の Multi-Head Attention として計算する手順です。SGLang はこの手順を `MHA` と呼んでいます。展開したあとは、十分に最適化された普通の attention の計算をそのまま使えます。その代わり、展開する対象のトークンが多いほど、展開そのものに手間がかかります。

2 つ目は、K に展開する行列 (W_UK) を query の側に、V に展開する行列 (W_UV) を出力の側に掛ける形に組み替えて、圧縮したベクトルのまま attention を計算する手順です。この記事では「吸収型の MLA」と呼びます。SGLang の名前は `MLA` です。過去のトークンを展開しなくて済む代わりに、K との内積を取るベクトルが長くなります。DeepSeek-V2-Lite の設定で数えると、`MHA` では 1 つの head の内積が 128 + 64 = 192 次元、吸収型の MLA では 512 + 64 = 576 次元です。この比較も、設定の値から数えたものです。

## prefill と decode の形

どちらの手順が有利かは、新しく計算するトークンと、参照する過去のトークンの数の関係で大きく変わります。

![prefill と decode の形の違い](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/8fc848bd0515c4/zenn/articles/8fc848bd0515c4/prefill-decode.png)

prefill では、新しいトークンが多く、使い回す過去のトークンが無いことがよくあります。この形では、展開してから普通の attention で計算する `MHA` が速くなります。過去のトークンを使わない 8,192 トークンの prefill の 1 バッチでは、時間の中央値は `MHA` で約 365 ms、同じバッチを吸収型の MLA に固定すると約 671 ms でした。測定を繰り返したときの中央値は、それぞれ 360〜369 ms と 670〜671 ms です。この差は、triton のバックエンドの、この形の prefill での値です。

decode では、新しいトークンは 1 つだけで、参照する過去のトークンが長く続きます。この形では、長い過去の分を展開しなくて済むので、吸収型の MLA が有利だと考えられます。SGLang は decode ではいつも吸収型の MLA を使います。ただし、decode での速さの比較は、この記事では測っていません。

## SGLang の切り替えの決まり

SGLang は、triton のバックエンドでは、バッチごとに[次の決まり](https://github.com/sgl-project/sglang/blob/5a15cde858ea09b77116212a39356f2fc51b8584/python/sglang/srt/models/deepseek_common/attention_backend_handler.py#L164-L178)で手順を選びます。

```python
def handle_attention_triton(attn, forward_batch):
    if is_in_piecewise_cuda_graph():
        return AttnForwardMethod.MLA
    if get_global_server_args().enable_deterministic_inference:
        return _dispatch_mla_subtype(attn, forward_batch)
    if (
        forward_batch.forward_mode.is_extend_without_speculative()
        and sum(forward_batch.extend_prefix_lens_cpu) == 0
    ):
        return AttnForwardMethod.MHA
    else:
        return _dispatch_mla_subtype(attn, forward_batch)
```

![SGLang の切り替えの決まり](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/8fc848bd0515c4/zenn/articles/8fc848bd0515c4/dispatch-rule.png)

SGLang には、以前の要求と先頭が一致する部分の KV cache を使い回す、prefix cache という機能があります。使い回せたことを cache hit、使い回せたトークンを cached prefix と呼びます。

コードの最初の 2 つの条件は、piecewise CUDA graph と決定的な推論 (deterministic inference) という特殊な設定のときのもので、どちらもいつも吸収型の MLA の系統に回ります。この記事の構成には当てはまりません。普通の場合は、次の 2 つを両方満たすバッチだけが `MHA` で計算されます。1 つは、prefill (SGLang では extend と呼びます) のバッチで、speculative decoding の検証用ではないことです。もう 1 つは、バッチ全体で足した cached prefix が 0 であることです。それ以外のバッチは、吸収型の MLA で計算されます。

吸収型の MLA には、使い回す過去のトークンを展開しなくて済む利点があります。ただし、この分岐を採用した理由を SGLang の開発者が書いた説明は見つけていません。

この決まりには、気をつける点が 2 つあります。1 つは、判定が「足した合計が 0 かどうか」だけで、使い回す長さが新しいトークンに比べて短いかどうかは見ていないことです。もう 1 つは、判定がバッチ全体で 1 回だけなので、バッチの中の 1 つの要求に cache hit があるだけで、バッチ全員が吸収型の MLA に回ることです。

## 数トークンの cache hit

長文脈のトラフィックで、この決まりのせいで、prefill のほぼ全体が吸収型の MLA に回る場面がありました。測ったトラフィックは、8,192 トークンの入力を 1 回ずつ送るものです。SGLang の内部に記録を足して調べると、既定の設定 (page size 1、prefix cache 有効) で送った 140 件のうち 138 件に cache hit があり、使い回された長さは 4〜7 トークンでした。共通していたのは入力の先頭の数トークンと考えられますが、その中身までは確かめていません。この 138 件の prefill は、すべて吸収型の MLA で計算されていました。

page size は次の節で説明します。

使い回すのは 4〜7 トークンだけなのに、cached prefix が 1 以上になるので、ほぼ 8,192 トークンの prefill 全体が吸収型の MLA に回ります。前の節の、過去のトークンを使わないバッチを手順だけ変えた比較では、約 305 ms の差がありました。この 4〜7 トークンの cache hit があるバッチに当てはめるとどれだけ遅くなるかは、直接は測っていません。

## page size という使い回しの単位

SGLang の `--page-size` は、KV cache を何トークンずつのページで扱うかを決める設定です。prefix cache も、一致した長さをページの単位に[切り下げて](https://github.com/sgl-project/sglang/blob/5a15cde858ea09b77116212a39356f2fc51b8584/python/sglang/srt/mem_cache/radix_cache.py#L147-L175)使います。triton のバックエンドでは、[指定しなければ](https://github.com/sgl-project/sglang/blob/5a15cde858ea09b77116212a39356f2fc51b8584/python/sglang/srt/server_args.py#L2949-L2954) NVIDIA の GPU で 1 トークンです。FlashMLA のように 64 や 128 のページに[固定するバックエンド](https://github.com/sgl-project/sglang/blob/5a15cde858ea09b77116212a39356f2fc51b8584/python/sglang/srt/server_args.py#L2694-L2711)もあります。

![page size と使い回しの単位](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/8fc848bd0515c4/zenn/articles/8fc848bd0515c4/page-size.png)

page size を 64 にすると、64 トークンのページが丸ごと一致しない限り、使い回しは起きません。4〜7 トークンの共通部分は 1 ページに満たないので使い回されず、cached prefix は 0 のままになり、prefill は `MHA` で計算されます。1 ページ以上の共通部分がある要求は、page size 64 でもこれまでどおり使い回され、吸収型の MLA に回ります。SGLang の内部の記録でも、page size 64 では、prefix cache の有効・無効のどちらでも、送った 140 件のどれにも cache hit がなく、すべて `MHA` で計算されていました。

その代わりに、使い回しの単位が粗くなります。1 ページに満たない共通部分は、本当に使い回したいものでも使い回されません。長い共通部分を持つ会話のトラフィックを分離構成で流し、page size 1 と 64 を比べた測定では、入力のトークンのうち使い回せた割合は、page size 1 で 81.4%、64 で 80.1% でした。この割合は、全部の要求の `cached_tokens` の合計を、入力のトークンの合計で割った値です。5 つの負荷 × 3 つの seed の 15 の組のうち 14 で、page size 64 のほうが低くなりました。ページより短い共通部分が多いトラフィックほど差が広がると考えられますが、それは測っていません。page size は、自分のトラフィックの共通部分の長さを見て選ぶ設定です。

## 死活確認が prompt を分ける例外

測ったトラフィック (共通部分が 1 ページに満たない) では、page size 64 にしても、吸収型の MLA に回る場面が 1 つ残りました。前の節の 140 件とは別に、負荷のレートを変えて長く測ったときに見つかったものです。原因は、SGLang の `/health` という死活確認です。生成を伴う `/health` は、1 トークンの小さな要求をエンジンに流して、応答が返るかを確かめます。この要求は、scheduler が死活確認の基準で「暇」と判定したときにだけ[受け付けられます](https://github.com/sgl-project/sglang/blob/5a15cde858ea09b77116212a39356f2fc51b8584/python/sglang/srt/managers/scheduler.py#L1845-L1853)。

ところがこの判定は、分離構成に特有の 2 つの待ち行列を[数えません](https://github.com/sgl-project/sglang/blob/5a15cde858ea09b77116212a39356f2fc51b8584/python/sglang/srt/managers/scheduler.py#L3295-L3330)。decode 側との接続を待つ要求 (bootstrap queue) と、KV を転送している最中の要求 (inflight queue) です。そのため、前の要求の KV の転送が残っていたり、長い入力が接続を待っていたりしても「暇」とみなされ、`/health` の要求がその入力と同じバッチに並ぶことがありました。

![死活確認が prompt を分ける様子](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/8fc848bd0515c4/zenn/articles/8fc848bd0515c4/health-split.png)

測った設定では、prefill の 1 バッチで計算できるのは 8,192 トークンまでです。これを超える分は、あとのバッチに回して分けて計算します (chunked prefill)。`/health` の要求が長い入力より先に同じバッチに入ると、`/health` が予算を [1 トークン使い](https://github.com/sgl-project/sglang/blob/5a15cde858ea09b77116212a39356f2fc51b8584/python/sglang/srt/managers/schedule_policy.py#L602)、残り 8,191 トークンはページの倍数に[切り下げられて](https://github.com/sgl-project/sglang/blob/5a15cde858ea09b77116212a39356f2fc51b8584/python/sglang/srt/managers/schedule_policy.py#L922) 8,128 トークンになります。入力の残りの 64 トークンは、あとのバッチに回ります。その 64 トークンは、前のバッチの 8,128 トークンを cached prefix として持つので、決まりのとおり、そのバッチ全体が吸収型の MLA に回ります。このバッチでは残りの 64 トークンが予算を使うので、同じバッチに入った次の 8,192 トークンの入力も 8,128 トークンで切られ、また 64 トークンが残ります。8,192 トークンの入力が待ち行列に続いている間は、新しい `/health` が無くても、吸収型の MLA のバッチが続く連鎖になります。

手を加えていないエンジンで、負荷のレートごとに 3 つの seed × 8 回ずつ測ると、この分割は 1 秒に 1 件のときに 24 回中 2 回、1 秒に 2 件のときに 24 回中 5 回 (そのうち 3 回は連鎖) 起き、0.25・0.5・4 件のときは起きませんでした。同じ seed の回は到着の並びが同じなので、24 回は互いに独立な試行ではありません。レートによって起き方が違う理由は分かっていません。

2026-10-19 に GitHub の Issue を検索したかぎりでは、この分割を報告した Issue は見つかりませんでした。死活確認に関する別の問題としては、複数のエンジンへの振り分けの状態が乱れる [#35241](https://github.com/sgl-project/sglang/issues/35241) と、時間切れのときの後始末の [#35884](https://github.com/sgl-project/sglang/issues/35884) があります。

## triton の計算の無駄

連鎖の中の、64 トークンの残りと次の入力の 8,128 トークンが同居するバッチは、測ると中央値で 1,531〜1,534 ms かかっていました。同じ 8,192 トークンの、過去のトークンを使わないバッチを吸収型の MLA に固定したときの約 671 ms の、2 倍以上です。調べると、SGLang の triton の extend attention の計算に、無駄がありました。

![連鎖のバッチで起動される計算の単位](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/8fc848bd0515c4/zenn/articles/8fc848bd0515c4/kernel-waste.png)

この計算は、バッチの中でいちばん長い列に合わせて、どの列にも同じ数の計算の単位 (query の塊) を[起動します](https://github.com/sgl-project/sglang/blob/5a15cde858ea09b77116212a39356f2fc51b8584/python/sglang/srt/layers/attention/triton_ops/extend_attention.py#L609)。この GPU と MLA の形では、1 つの塊は 32 トークンです。測った版では、自分の列の範囲を外れた塊でも途中で抜けません。起動する塊の数を計算すると、64 トークンしかない列にも、head ごと・層ごとに 8,128 ÷ 32 = 254 個の塊が起動され、そのうち 252 個は計算する行が 1 つもありません。ソースの流れを読むと、その 252 個も 8,128 トークンの cached prefix を最後まで読むので、無駄な計算になります。

範囲を外れた塊で抜ける 1 行を足して、同じ形のバッチを 1 回の実行 (88 バッチ) で測ると、中央値は 704 ms になり、約 829 ms 短くなりました。704 ms は、過去のトークンを使わないバッチを `MHA` で計算した約 365 ms の約 2 倍で、吸収型の MLA に固定した 670〜671 ms に近い値です。この 1 行を足しても、出力は変わりませんでした。連鎖のバッチと同じ形、長さを変えた 16 通り、ランダムな 40 個のバッチのすべてで、足す前と後の差の最大値は 0.0 でした。一方で、過去のトークンを使わないバッチを吸収型の MLA で計算すると、671 ms から 680 ms に少し遅くなりました。

ここまでの測定の値を、まとめて並べます。

| バッチの形 | 手順 | 1 バッチの時間 (中央値) |
|---|---|---|
| 1 つの入力、新しいトークン 8,192、cached prefix 0 | `MHA` | 360〜369 ms (繰り返した測定ごとの中央値) |
| 同じ形を吸収型の MLA に固定 | 吸収型の MLA | 670〜671 ms (同上) |
| 残りの 64 トークン (cached prefix 8,128) と次の入力の 8,128 トークン | 吸収型の MLA | 1,531〜1,534 ms (同上) |
| 同じ形、範囲外の塊で抜ける 1 行を足した計算 | 吸収型の MLA | 704 ms (1 回の実行の 88 バッチ) |

この無駄は、新しい版の SGLang では直っています。[sgl-project/sglang#32109](https://github.com/sgl-project/sglang/pull/32109) が 2026-07-23 にマージされ、extend attention の計算に同じ判定 (`if cur_block_m * BLOCK_M >= cur_seq_len_extend: return`) が入りました。測った 0.5.12.post1 の commit は 2026-05-22 のものなので、この修正より前です。この修正を含む版で、連鎖のバッチがどれだけ速くなるかは測っていません。また、この修正が直すのは計算の無駄だけで、死活確認による分割と、吸収型の MLA への切り替えそのものは変わりません。

## まとめ

1. SGLang の `MHA` と `MLA` は、どちらも MLA のモデルを計算する手順の名前です。`MHA` は圧縮したベクトルを展開して普通の Multi-Head Attention として計算し、吸収型の MLA は展開せずに計算します。
2. 新しいトークンが多い prefill では `MHA` が速く、測った 8,192 トークンの prefill の 1 バッチでは、`MHA` が約 365 ms、吸収型の MLA が約 671 ms でした。過去のトークンが長い decode では、作りから吸収型の MLA が有利と考えられますが、この記事では測っていません。
3. triton のバックエンドの SGLang は、普通の場合、バッチ全体の cached prefix が 0 のときだけ `MHA` を選びます。そのため、数トークンの cache hit でも、prefill 全体が吸収型の MLA に回ります。
4. 共通部分が 1 ページより短いトラフィックでは、page size を大きくすると短い一致が使い回されなくなり、prefill は `MHA` で計算されます。その代わり、1 ページに満たない共通部分は使い回されなくなります。
5. 死活確認の 1 トークンの要求が prompt を分けると、page size 64 でも吸収型の MLA の連鎖が起きることがあります。この連鎖で見えた triton の計算の無駄は #32109 で直っていますが、分割と吸収型の MLA への切り替えそのものは残ります。
