# はじめに

NVIDIA が 2025 年 11 月 4 日に公開した [NCCL Roadmap Q4 2025 (GitHub Issue #1896)](https://github.com/NVIDIA/nccl/issues/1896) を、2026 年 9 月に出た [NCCL v2.32.3-1](https://github.com/NVIDIA/nccl/releases/tag/v2.32.3-1) の時点から読み直します。このロードマップは v2.29 (2025 年 12 月から 2026 年 1 月) に向けた計画で、以後の 2.30、2.31、2.32 が土台にしている機能の多くがここで予告されていました。

「[NCCL Roadmap Aug-Oct 2026 の解説](https://zenn.dev/tosshi/articles/8d7fea5568e638)」は最新のロードマップを先回りして読む記事で、「[NCCL 2.32.3 でロードマップはどう実装されたか](https://zenn.dev/tosshi/articles/9ab10d37f33ced)」はその答え合わせでした。この記事は同じ答え合わせを、約 1 年前のロードマップに対して行います。計画から 1 年近くたつと、実装に降りた項目と、形を変えて降りた項目と、対応を確認できない項目がはっきり分かれます。

:::message
2026 年 10 月 1 日に NCCL のリポジトリをタイトルで検索した範囲では、公開されているロードマップは #1896 (Q4 2025)、[#1995 (Q1 2026)](https://github.com/NVIDIA/nccl/issues/1995)、[#2090 (Q2 2026)](https://github.com/NVIDIA/nccl/issues/2090)、[#2272 (Aug-Oct 2026)](https://github.com/NVIDIA/nccl/issues/2272) の 4 本で、2026 年 11 月以降の計画はまだ出ていません。
:::

# 全体像: v2.29 に予告された 10 項目

ロードマップが v2.29 に予告した 10 項目を、各版のリリースノートと v2.32.3 のソースで確かめると、次のようになります。

| ロードマップの項目 | 入った版 | 2.32.3 での状態 |
| --- | --- | --- |
| NCCL4Py (Python から NCCL を呼ぶための公式の結合層) | 2.29.2 | 実験的な扱いで入り、以後は [nccl4py](https://github.com/NVIDIA/nccl/releases/tag/nccl4py-v0.6.0) として NCCL 本体と別に版を重ねています |
| LLVM IR for Device APIs (コンパイラの中間表現での提供) | 2.29.2 | CUDA 12 と Clang 21 を用意し、`EMIT_LLVM_IR=1` でビルドすると、Device API を LLVM IR として出力できます。2.31.2 で LTO IR にも対応しました |
| Put API (ホストから出す片側通信) | 2.29.2 | `ncclPutSignal` などが入りました。後述の注目 1 です |
| Communicator Grow API | 2.29.2 | `ncclCommGrow` が入りました。後述の注目 2 です |
| Symmetric Memory Support for Network | 2.29.2 と 2.29.7 | NVLink とネットワークを組み合わせるカーネルが AllGather と ReduceScatter に入りました。後述の注目 3 です |
| Device API for LL/LL128 (小さなメッセージ向けの低遅延プロトコル) | 確認できませんでした | 2.30.3 で LL128 を使える場面は広がりましたが、これはホスト側の集団通信の話です。Device API のヘッダには LL128 が見当たらず、LL の all-to-all (`ll_a2a.h`) は 2.28.3 から存在します |
| NVLS + PAT (NVLink のスイッチ支援と、PAT という集約アルゴリズムの組み合わせ) | 2.31.2 | ノード内を NVLS、ノード間を PAT で進めるカーネルが入りました。既定では無効で、`NCCL_ALGO=PAT` か集団通信ごとの設定 (`collConfig`) で有効にします。H100 での性能低下は 2.32.3 で直りました |
| Lower Latency in Symmetric Kernels | 確認できませんでした | 2.30.3 の TMA 対応など、対称カーネルの遅延を下げる変更はあります。ただし、ロードマップが挙げた Lamport 式の初期化は中核の対称カーネル (`src/device/symmetric/`) に見当たらず、L2 のアトミック操作は調べ切れていません |
| Profiler Support for CE Collectives | 2.29.2 | Copy Engine (GPU のコピー専用回路) を使う集団通信がプロファイラから見えるようになりました |
| Support for Multi-rank GPU | 2.30.7 | MPS と MLOPart の組み合わせで、1 枚の GPU に 2 ランクまで載せられます。2.30.7 では実験的な機能として入り、2.32.3 で Rubin にも対応しました。これとは別に、2.32.3 では複数の MIG インスタンスを使う communicator にも対応しています |

10 項目のうち 8 項目は、対応する機能の追加を 2.31.2 までにリリースノートとソースの両方で確認できました。ただし、NVLS + PAT が既定で無効なように、ロードマップの説明どおりに完成したとまでは言えない項目もあります。残る 2 項目は、Device API で使える LL/LL128 の範囲の拡張と、対称カーネルの低遅延化で、今回の調査では対応する実装を特定できませんでした。

ロードマップで「検討中」だった 7 項目のうち、受信側の PXN (別の GPU の NIC を経由する送受信)、アプリに組み込める RAS の API、Endpoint API、Copy Engine を使う Send/Recv の 4 項目は、2.32.3 のソースに実装が見つかりませんでした。受信側の PXN については、ソースに [We don't support PXN on receive yet](https://github.com/NVIDIA/nccl/blob/12df1a11afad322be5a204a2db890161cbf8131d/src/transport/net.cc#L379) というコメントが残っています。RAS (障害の検知と診断の仕組み) には 2.31.2 で診断機能 (`NCCL_RUN_RAS_DIAGNOSTICS=1`) が入りましたが、RAS の関数は内部向けで、公開 API にはなっていません。残る 3 項目 (PAT のユーザーバッファ登録、Device API 向けのプロファイラ対応、対称登録していないバッファでの Copy Engine 集団通信の CUDA Graph 取り込み) は、実装の有無を判定できていません。

# AWS EFA 関連: 同じ機能でも EFA では時期と条件が違う

AWS の EFA (Elastic Fabric Adapter) は、NCCL 本体ではなく [aws-ofi-nccl](https://github.com/aws/aws-ofi-nccl) プラグインを通して NCCL とつながります。そのため NCCL のリリースノートに機能が載っても、EFA で使えるのはプラグイン側の対応がそろってからです。このロードマップの項目では、Put API と対称メモリのネットワーク対応の 2 つがこの影響を受けます。

## Put API が EFA に届くまで

2.29.2 の Put API は、ネットワーク越しの転送を CPU の代理スレッドに任せます。ただし 2.29.2 のソースでは、この代理役の送り先が NCCL 内蔵の InfiniBand 実装に固定されていました ([net.cc の該当行](https://github.com/NVIDIA/nccl/blob/ebd1e929285881cb4df02c3459588a2e12b2d8c0/src/plugin/net.cc#L355))。外部のネットワークプラグインは使われないので、ソースとリリースノートを読む限り、2.29.2 の EFA のノード間では Put API を使えなかったと考えられます。

Put API が外部のネットワークプラグインを使えるようになったのは 2.30.3 で、リリースノートに「One-sided RMA can now use an external network plugin」と書かれています。aws-ofi-nccl 側では、片側通信専用の RMA の関数表 ([ncclRmaPlugin_v14](https://github.com/aws/aws-ofi-nccl/blob/720b36298749b5c2ef21c555878f62a0ff3036e3/src/rdma/gin/nccl_ofi_gin_api.cpp#L666) と v15) を v1.21.0 から公開しています。同じ [v1.21.0](https://github.com/aws/aws-ofi-nccl/releases/tag/v1.21.0) (2026 年 8 月) のリリースノートで、aws-ofi-nccl は GIN (GPU から通信を発行する仕組み) への対応を初めて告知し、NCCL 2.31.2 と組み合わせて試験したと書いています。

まとめると、EFA で Put API をノード間に使う経路は、NCCL 側では 2.30.3 で開き、aws-ofi-nccl 側で関数表と告知がそろったのは v1.21.0 です。v1.21.0 のリリースノートが挙げる要件 (NCCL 2.31.2 以降、GDRCopy 2.5 以降) は GIN 全体の要件で、Put API だけを対象にした動作保証ではありません。v1.21.0 より前の aws-ofi-nccl と組み合わせて Put API が動くかどうかは、この記事では確かめていません。

## 対称メモリのカーネルと EFA GDA の signal

ノードをまたぐ対称メモリのカーネル (注目 3) を 2.32.3 のソースで読むと、GIN のバックエンドに strong signal と VA signal の両方を要求しています ([sym_kernels.cc](https://github.com/NVIDIA/nccl/blob/12df1a11afad322be5a204a2db890161cbf8131d/src/sym_kernels.cc#L250-L251))。signal は、受け手の GPU に「データが届いた」と知らせる数値です。[GIN のドキュメント](https://github.com/NVIDIA/nccl/blob/12df1a11afad322be5a204a2db890161cbf8131d/docs/userguide/source/api/device_gin.rst#L102-L104)によると、strong signal は 2.30.5 で weak signal と区別されたもので、同じ相手に同じ context で先に出した put のデータがすべて見えることを保証します。[VA signal](https://github.com/NVIDIA/nccl/blob/12df1a11afad322be5a204a2db890161cbf8131d/docs/userguide/source/api/device_gin.rst#L152-L153) は、あらかじめ確保した番号ではなく、登録済みの窓と位置 (仮想アドレス) で置き場所を指定する signal です。

一方、aws-ofi-nccl の EFA GDA バックエンドは、どちらの signal にも対応していないと NCCL に申告しています ([nccl_ofi_gin_gdaki.cpp](https://github.com/aws/aws-ofi-nccl/blob/2475c4c736907e68ebeadb3848f31231ee4a44d0/src/rdma/gin/nccl_ofi_gin_gdaki.cpp#L1177-L1178))。v1.21.0 のリリースノートにも「indexed signals only (not strong or VA signals)」という制限が書かれています。NCCL は、要求を満たさないバックエンドを候補から外します ([gin_host.cc](https://github.com/NVIDIA/nccl/blob/12df1a11afad322be5a204a2db890161cbf8131d/src/gin/gin_host.cc#L230-L241))。この判定を 2.32.3 のソースで追うと、EFA での結果は構成によって次のように分かれます。

| 構成 | GIN の候補になるバックエンド | ノードをまたぐ対称カーネルの準備 |
| --- | --- | --- |
| `NCCL_GIN_TYPE` を指定しない | 使えるバックエンドが順に試されます。その 1 つに、aws-ofi-nccl の RMA の関数表の上で動く NCCL 自身の CPU 代理役があります | 代理役は両方の signal に対応しているので ([gin_host_proxy.cc](https://github.com/NVIDIA/nccl/blob/12df1a11afad322be5a204a2db890161cbf8131d/src/gin/gin_host_proxy.cc#L348-L349))、条件を満たす候補になり得ます。実際にどれが選ばれるかは構成によります |
| `NCCL_GIN_TYPE=5` (EFA GDA だけを選ぶ) | EFA GDA だけです。NCCL はほかのバックエンドを最初から登録しません ([plugin/gin.cc](https://github.com/NVIDIA/nccl/blob/12df1a11afad322be5a204a2db890161cbf8131d/src/plugin/gin.cc#L143-L147)) | 条件を満たすバックエンドが残らず、準備の関数がエラーを返します。CPU の代理役へ自動で切り替わる経路はありません |

`NCCL_GIN_TYPE=5` の構成で問題が起きたときは、`NCCL_SYM_GIN_KERNELS_ENABLE=0` を設定すると、NCCL は signal の条件を課す分岐そのものを通らなくなります。この設定は、原因を切り分ける手段になります。

なお、2.32.3 のリリースノートには、AWS の EFA チームが EFA GDA に `gin.get` などを追加したことが書かれています ([PR #2382](https://github.com/NVIDIA/nccl/pull/2382)、[#2398](https://github.com/NVIDIA/nccl/pull/2398)、[#2405](https://github.com/NVIDIA/nccl/pull/2405))。ただし signal への対応はプラグインの申告で決まり、v1.21.1 の申告は strong も VA も未対応のままです。v1.21.x のリリースノートが試験対象に挙げているのも NCCL 2.31.2 で、2.32.3 ではありません。

:::message
この節の挙動はソースを読んで導いたもので、実機では確かめていません。準備のエラーが集団通信の呼び出しまで伝わるかどうか、`NCCL_SYM_GIN_KERNELS_ENABLE=0` が回避策として効くかどうかも同じです。制限が外れたかどうかは、aws-ofi-nccl の次の版のリリースノートで確かめてください。
:::

# 注目機能 3 選

## Put API: 受信の呼び出しなしで相手のメモリに書き込む

NCCL の従来の送受信 (`ncclSend` と `ncclRecv`) は、送り手と受け手の両方が呼び出しをそろえる必要がありました。[ncclPutSignal](https://github.com/NVIDIA/nccl/blob/12df1a11afad322be5a204a2db890161cbf8131d/src/nccl.h.in#L785-L787) は、相手が事前に登録したメモリの窓 (window) に、転送ごとの受信の呼び出しなしで書き込みます。この API は書き込みのあとに signal を送るので、受け手は `ncclWaitSignal` で届いたことを確かめられます。

この API は GPU のカーネルを使わず、CUDA 12.5 以降を必要とします。ノード内は Copy Engine が、ノード間は CPU の代理スレッドが転送します。そのため SM (GPU の演算器の単位) を計算に残したまま通信を進められます。ロードマップの「Zero-SM」はこの性質を指しています。

2.29.2 の時点では、CUDA Graph に取り込めないことと、通信の文脈 (context) が 1 つだけであることが制限でした。前者は 2.30.3 で解消され、後者は 2.31.2 で複数の context を使えるようになりました。[ドキュメント](https://github.com/NVIDIA/nccl/blob/12df1a11afad322be5a204a2db890161cbf8131d/docs/userguide/source/usage/p2p.rst#L121-L130)は、大きな転送を分けて context ごとに流すことを勧め、ローカルの NIC 1 枚につき 1 つ以上の context を出発点にするよう書いています。小さな転送は、context を増やすと手間の方が大きくなるので、1 つの context にとどめるよう求めています。

2.30.7 では、この片側通信の上に、SM を使わない階層型の AllGather と AllToAll が作られました。この集団通信はノード内を Copy Engine、ノード間を片側通信の代理スレッドで進め、利用者は communicator の CTA ポリシーに `NCCL_CTA_POLICY_ZERO` を指定して有効にします。ロードマップでは単独の API として予告された Put が、集団通信の部品にもなったことになります。

## Communicator Grow: 実行中のジョブにランクを足す

[ncclCommGrow](https://github.com/NVIDIA/nccl/blob/12df1a11afad322be5a204a2db890161cbf8131d/src/nccl.h.in#L356-L362) は、既存の communicator に新しいランクを加えた communicator を作ります。2.27 の `ncclCommShrink` (ランクを外す) と 2.28 の `ncclCommRevoke` (実行中の操作を止める) と組み合わせると、ノードの故障で縮めたジョブを、復旧したノードで元の大きさに戻せます。

[ドキュメントの手順](https://github.com/NVIDIA/nccl/blob/12df1a11afad322be5a204a2db890161cbf8131d/docs/userguide/source/usage/communicators.rst#L186-L277)では、既存のランクの 1 つがまとめ役になり、`ncclCommGetUniqueId` で ID を作って新しいランクだけに配ります。ドキュメントの例では、既存のランクは全員が ID を引数に渡さずに `ncclCommGrow` を呼び、元のランク番号をそのまま引き継ぎます。まとめ役が作った ID は、NCCL が内部で既存のランクの先頭と末尾に配ります ([init.cc](https://github.com/NVIDIA/nccl/blob/12df1a11afad322be5a204a2db890161cbf8131d/src/init.cc#L3737-L3748))。なお、ヘッダのコメントはまとめ役に ID を渡すよう書いており、ドキュメントの例と食い違っています。新しいランクの番号は、元の communicator の大きさから始まる値を、呼び出し側が `rank` 引数で割り当てます。

ただし、ロードマップの説明にある「通信を続けたまま (while maintaining communication)」は、元の communicator で通信しながら Grow できるという意味には受け取れません。ドキュメントは、`ncclCommGrow` を呼ぶときに元の communicator に未完了の操作を残さないよう求めています。ソースでも、新しい communicator は資源を新しく確保し、接続を作り直しています。そのため、たとえば学習ループの区切りで元の communicator の操作を終え、新しい communicator に切り替えてから、元の communicator を破棄する流れになります。ジョブ全体を再起動せずにランクを足せる点が、この API の価値です。

## Symmetric Memory for Network: NVLink とネットワークを 1 つのカーネルで進める

対称メモリ (symmetric memory) は、全ランクがバッファを窓として登録し、同じ位置を指せば相手のバッファにも届くようにする仕組みです。NVLink でつながる GPU どうしなら、GPU は相手のバッファを自分のメモリのように直接読み書きできます。2.27 で入った時点では、この NVLink の範囲でしか使えませんでした。このロードマップの項目は、その先のネットワーク越しの相手も、同じ窓を通して GIN で読み書きできるようにするものです。

2.29.2 では AllGather に、2.29.7 では ReduceScatter に、ノード内を NVLink で、ノード間を GIN で進める組み合わせのカーネルが入りました。ノード内の進め方は、AllGather が NVLS のマルチキャスト書き込み、ReduceScatter が NVLink 越しの読み出し (LSA) です。2.32.3 のソースでは、このカーネルは `ReduceScatter_RailA2A_LsaLD` や `AllGather_RailRing_LsaSTMC` のように、ノード間の方式とノード内の方式を並べた名前で登録されています ([sym_kernels.cc](https://github.com/NVIDIA/nccl/blob/12df1a11afad322be5a204a2db890161cbf8131d/src/sym_kernels.cc#L55-L57))。ノード間の転送は、NCCL が rail (各ノードの NIC を同じ系統どうしでつないだ経路) ごとに組むチームの上で行います。

このカーネルは、NVLink でつながる範囲に全ランクが収まらない場合だけ準備されます。このカーネルは対称メモリの登録と GIN を必要とし、利用者は `NCCL_SYM_GIN_KERNELS_ENABLE=0` で無効にできます。EFA では前の章で見たとおり、GIN のバックエンドの種類によって、このカーネルの条件を満たせるかどうかが変わります。

# コメント欄の話題のその後: NCCL EP

ロードマップの本文に無かった機能が、コメント欄で話題になり、その後に形になった例もあります。2026 年 1 月 21 日に、NCCL と DeepEP を組み合わせるとデバイスメモリの消費が大きいという相談があり、NVIDIA の担当者は dispatch と combine に相当する API を用意する方向で複数の取り組みを進めていると答えました。その後、NCCL EP は 2.30.3 の時点で `contrib/nccl_ep` としてリポジトリに入り、2026 年 6 月に [NCCL EP v0.1.0](https://github.com/NVIDIA/nccl/releases/tag/nccl-ep-v0.1.0) が公開されました。NCCL EP は、MoE (Mixture-of-Experts) のトークンの配送 (dispatch) と回収 (combine) を、Device API の LSA と GIN の上に実装した拡張です。v0.1.0 のリリースノートには、LL モードの Dispatch の一時バッファを、1 ランクあたりの expert 数分の 1 に縮めたことが書かれています。

# まとめ

Q4 2025 のロードマップが v2.29 に予告した 10 項目とその周辺は、v2.32.3 の時点で次の 3 つに分かれます。

- そのまま降りた項目: Put API、Communicator Grow、ネットワーク越しの対称メモリなど 8 項目は、2.31.2 までに入りました。
- 形を変えて降りた項目: Put API は単独の API にとどまらず、2.30.7 で SM を使わない階層型の集団通信の部品になりました。ロードマップ本文に無かった NCCL EP も、コメント欄で話題になったあと、2026 年 6 月に v0.1.0 が出ました。
- 対応を確認できなかった項目: Device API での LL/LL128 の拡張と、対称カーネルの低遅延化は、ロードマップの説明に対応する実装を今回の調査では特定できませんでした。

AWS EFA では、同じ機能を使えるようになる時期と条件が NVIDIA のネットワーク機器とは異なります。Put API のノード間の経路は NCCL 2.30.3 で開き、aws-ofi-nccl 側で関数表と GIN の告知がそろったのは v1.21.0 (NCCL 2.31.2 で試験) です。ネットワーク越しの対称メモリのカーネルが要求する strong signal と VA signal に、aws-ofi-nccl v1.21.1 の EFA GDA は対応していません。EFA で新しい NCCL の機能を使うときは、NCCL と aws-ofi-nccl の両方のリリースノートで、その機能が使える条件を確かめてください。
