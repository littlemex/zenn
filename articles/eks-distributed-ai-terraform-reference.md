# はじめに

NVIDIA GPU と AWS Trainium/Inferentia (Neuron) を同じ Amazon EKS クラスタに同居させ、分散学習と推論の両方を動的に回すための Terraform モジュールを作りました。この記事はその設計思想を紹介するもので、詳細なハンズオンは Zenn book『EKS で始める分散 AI 基盤』にまとめています。

ここではコードの逐条解説はしません。代わりに、なぜこの基盤を作ったのか、何が問題になるのか、どこにハマりやすいのか、そして作るときに何を考慮すべきか、という順で全体像を追います。細かい設定値やコマンドは book 側に譲ります。

対象リポジトリは [littlemex/distributed-ai の infra/eks](https://github.com/littlemex/distributed-ai/tree/main/infra/eks) です。

# 何を実現したかったのか

きっかけは強化学習 (RL) のワークロードでした。RL は大量のサンプルを生成する推論 (rollout) と、そのサンプルでモデルを更新する学習 (training) が一つのループの中で同居します。さらに実運用では、GPU で学習したいときもあれば、Trainium で推論したいときもあり、開発用の安いノードと、予約した大規模 GPU を同時に使いたいこともあります。

こうした形の違うワークロードを一つの基盤で扱いたい、というのが出発点です。分散学習だけなら Slurm (HPC で標準的なジョブスケジューラ) という選択肢もありますが、推論サービスと学習が絡み合い、宣言的にリソースを要求したり回収したりしたいワークロードでは Kubernetes の適性が高いと考え、EKS を土台にしました。

この基盤が満たすべき要求を最初に整理すると、次のようになります。

| 満たすべき要求 | なぜ必要か | この基盤での満たし方 |
|---|---|---|
| 学習と推論の混在 | RL では推論と学習が同じループに同居する | 同一クラスタに GPU プールと Neuron プールを共存させる |
| GPU/Neuron の動的確保 | 高価な資源は使うときだけ立てて即返したい | Karpenter が Pod の要求に応じてノードを起動・回収する |
| マルチノード集団通信 | 1 台に載らないモデルを複数ノードで学習する | EFA と NCCL/Neuron を単一 AZ 内で束ねる |
| 予約枠 (Capacity Block) の活用 | 大規模 GPU は予約なしでは確保が事実上困難 | 予約の購入から期限監視までをモジュールに組み込む |
| 共有ストレージ | モデルやデータを複数 Pod で共有する | Amazon EFS と Amazon FSx for Lustre を使い分ける |
| 安全な破棄 | 実験が終わったら課金を残さず消したい | 破棄順序の制御とドレイン待機で孤立ノードを防ぐ |

全体像を 1 枚にすると次の図になります。VPC の中に 2 つの AZ を張り、EKS コントロールプレーンの下で Karpenter が GPU/Neuron の NodePool を動的に起動し、共有ストレージや Capacity Block の期限監視といった周辺サービスも含めた構成です。

![EKS 分散 AI 基盤の全体アーキテクチャ](/images/books/eks-distributed-ai/arch-overview.png)

CPU、GPU、Trainium が同じクラスタに混ざり、on-demand、spot、reserved (Capacity Block) という異なる調達方法のノードが並んで動く点がこの基盤の核心です。それぞれを別々の仕組みで書くのではなく、一つの抽象で統一的に表現することを目指しました。

# インフラ層とアプリ層の境界をどこに引くか

基盤を設計するうえで最初に決めたのが、どこまでを基盤が用意し、どこからを利用者が実装するか、という責務の境界です。この線引きが曖昧だと、基盤が抱え込みすぎて硬直したり、逆に利用者が毎回インフラの面倒を見る羽目になったりします。

![インフラ層とアプリ層の責務境界](/images/books/eks-distributed-ai/infra-app-boundary.png)

境界は Kubernetes の宣言的 API に置きました。利用者は「どんな Pod をいくつ、どの GPU で動かすか」を Job や RayCluster として宣言するだけでよく、その要求を満たすためのノード起動、EFA の構成、デバイスプラグインの導入、ストレージのマウントといった機構はすべて基盤側が提供します。slime (LLM 向け RL フレームワーク) による GRPO、torchrun による DDP、vLLM による推論サービングといった「何を計算するか」は利用者の実装で、基盤はそれらが載る土台に徹します。

この境界の考え方は、スケーリングにも表れます。ノードのスケーリング (Pod の要求に応じてノードを増減させること) は Karpenter が担う基盤の責務です。一方、Pod 自体のスケーリング (HPA や KEDA によるレプリカ数の調整) はワークロードの性質に依存するアプリ層の関心事なので、この基盤の範疇には含めていません。

# 何が問題になり、どこにハマるのか

分散 AI 基盤を EKS で組むと、通常の Web アプリ向けクラスタでは出会わない問題にいくつもぶつかります。実際に手を動かして初めて分かったものを紹介します。

まず IP アドレスの枯渇です。アクセラレータノードは 1 台が消費する IP の桁が、通常の CPU ノードとは違います。主因は VPC CNI (Pod に VPC の IP を直接割り当てる EKS 標準のネットワークプラグイン) で、1 ノードに Pod 用のセカンダリ IP をあらかじめ確保するため、GPU/Neuron ノードが数台立つだけでサブネットの空きを大きく削ります。少数のノードでサブネットの IP を使い切り、新しいノードが起動できずに止まる、という事故が起きやすいのです。だからノードを置く private サブネットは大きく取る必要があります。

次に EFA が「選ばれても流れない」という厄介な失敗です。EFA のセキュリティグループは、通常の IP トラフィックとは異なる特殊な通信を許可する必要があり、これを取りこぼすと、NCCL (NVIDIA の集団通信ライブラリ) のブートストラップは成功して「EFA を選んだ」とログに出るのに、実際のデータ転送でハングします。動いているように見えて動かない、最も診断が難しい部類の障害です。

EFA の枚数そのものにも罠があります。たとえば p5en.48xlarge では物理ネットワークカードが 16 枚ありますが、1 枚はノードの IP を持つプライマリインターフェイスとして使われ、残り 15 枚は IP を消費しない EFA 専用 (interfaceType: efa-only) のインターフェイスになります。枚数はインスタンスタイプごとに異なります。Pod が要求できる EFA は物理カード数より 1 少ない値であり、IP 枯渇の主役は EFA カードではなく前述の VPC CNI です。この非対称性を知らずにカード数そのままを要求すると、Pod は永遠に起動待ちのままになります。

Capacity Block の運用も、通常の on-demand とは流れが違います。予約は前払いで確定し、購入という操作自体が Terraform の管理外で起こります。さらに予約にはいつか切れる期限があるため、期限を監視して通知する仕組みがないと、切れた瞬間にノードが失われて実験が止まります。

そして最後が破棄の難しさです。クラスタを消すとき、ノードの削除リクエストが Kubernetes に受理された時点と、実際に EC2 インスタンスが終了する時点の間には数分から十数分のギャップがあります。このギャップの間に後始末をするコントローラを先に消してしまうと、ノードが孤立して課金だけが残り続けます。さらに NAT ゲートウェイが先に消えるとコントローラが AWS の API に到達できなくなるため、VPC エンドポイント経由の通信経路を最後まで残しておく必要もあります。「作る」ことより「確実に壊す」ことのほうが、実は事故が起きやすいのです。

# 何を考慮して作るべきか

こうした問題を踏まえて、設計では次の 4 点を軸に据えました。

一つ目は、混在を一つの抽象でまとめることです。GPU と Neuron、on-demand と spot と reserved を別々の仕組みで書くと、共通のロジックを何箇所にも複製することになり、修正漏れの温床になります。プールを表す一つの設定を増やすだけで新しいアクセラレータを追加できるように、記述を統一しました。

二つ目は、間違いを機械的に弾くことです。EFA の枚数のように、間違えると症状が分かりにくいものは、人手で書かせず自動的に導出し、矛盾があれば適用の時点で止めるようにしました。「動くが遅い」「動くように見えて動かない」といった失敗を、最初から起こさせない方針です。

三つ目は、計算とストレージを単一 AZ に寄せることです。EFA の集団通信は AZ をまたげず、FSx for Lustre も単一 AZ が前提で、Capacity Block も AZ を自由には選べません。結果として、性能を出したいワークロードは自然と一つの AZ に集まります。マルチ AZ で可用性を稼ぐ通常の Web サービスとは、そもそも設計の重心が違うのです。この基盤ではノードをすべて private サブネットに置き、外部公開が必要なロードバランサだけを小さな public サブネットに載せています。全体図では作図の都合で共有ストレージを左の AZ-B に配置していますが、実際には FSx for Lustre は計算ノードと同じ AZ に作成します。EFS はマルチ AZ 対応なのでどちらの AZ からでもマウントできます。

四つ目は、確実に壊せることです。破棄の順序を制御し、ノードが完全に消えるまで後始末のコントローラを生かしておくことで、孤立ノードの課金を構造的に防ぎます。

:::message
Slurm や AWS ParallelCluster に慣れた方は、「ログインノードはどこにあるのか」と思うかもしれません。Slurm ではログインノードに SSH でログインし、そこから `sbatch` でジョブを投入するため、常時起動する公開ホストが要ります。EKS ではそうした常設のログインノードは登場しません。ジョブは `kubectl` を通じて Job や Pod として宣言的に投入するので、計算ノードに直接ログインする必要がないからです。デバッグで一時的にコンテナへ入りたいときも、SSM Session Manager や `kubectl` の機能で事足ります。この違いが、public サブネットを小さく保てる理由の一つでもあります。
:::

# 実機で確認できたこと

2026 年 7 月、us-east-2 のクラスタでスモークテストを行いました。性能測定ではなく、各パスが端から端まで通ることの確認が目的です。

| ワークロード | 環境 | 結果 |
|---|---|---|
| PyTorch DDP (gloo) | CPU プール、2 ノード | 完了。損失が減少し、共有ストレージにチェックポイントを書き込み |
| FSDP、Llama-3.2-1B | p5en.48xlarge 1 ノード (H200 x8) | 完了。約 99 TFLOPS/GPU、約 114k tokens/s。EFA トランスポート (efa-direct) を確認 |
| vLLM 推論 | H200 1 ノード | サーバーが正常稼働し、OpenAI 互換のレスポンスを確認 |
| torch-neuronx DDP | trn2.48xlarge 2 ノード (world_size=64) | 完了。all-reduce と MNIST の DDP がともに完走し、EFA (efa-direct) を確認 |

マルチノードの集団通信については、trn2.48xlarge を 2 台束ねた EFA 越しの DDP まで実機で確認できています。GPU 側のマルチノード NCCL 集団通信 (p5en を 2 台束ねる構成) は、Capacity Block の在庫確保を待って今後検証する予定です。

表中の用語について補足します。DDP/FSDP は PyTorch の分散学習方式、gloo は CPU 用の通信バックエンド、world_size は分散学習に参加するワーカーの総数、efa-direct は EFA を直接使う通信経路です。

# book で扱っていること

この記事で紹介した設計の一つひとつを、Zenn book では章ごとに手を動かしながら解説しています。VPC とネットワークの土台づくりから始まり、CPU での DDP 体験、Karpenter の導入、アクセラレータプールの設計、EFA のトポロジ、Capacity Block の運用、ワークロードの実行、監視、Neuron/Trainium への対応、共有ストレージ、そして安全な破棄まで、順を追って進める構成です。

この基盤は [awslabs/awsome-distributed-ai](https://github.com/awslabs/awsome-distributed-ai) のリファレンス実装を参考にしています。特に「public サブネットは小さく、private サブネットは大きく」というネットワークの原則はそこから学びました。既存のアプローチと優劣を競うのではなく、それらから学んだうえで、Trainium への対応など自分たちのワークロードに必要な部分を反復的に改善し続けている、というのがこの基盤の立ち位置です。

# まとめ

この基盤が目指しているのは、GPU と Neuron が混在する分散 AI 基盤を、Terraform だけで再現可能に立てて、確実に壊せるようにすることです。学習と推論の混在、動的なノード確保、マルチノードの集団通信、予約枠の活用、共有ストレージ、そして安全な破棄という、地味だが実運用で最も事故が起きやすい部分を固めることに絞りました。

コードの詳細やハンズオン手順、Capacity Block の運用ノウハウ、Neuron/Trainium 検証の進捗は Zenn book にまとめていきます。この記事が、分散 AI 基盤を自分で組んでみようとする方の見取り図になれば幸いです。
