## はじめに

この記事は、PyTorch の `forward` が AWS Trainium の実行バイナリ（NEFF）になるまでの変換を、図を中心に追います。NeuronCore は Trainium のチップの中で計算を受け持つコアです。途中で生まれる FX graph、HLO、NEFF は、どれも NeuronCore を使わずに CPU だけで作れるので、その観察の手順も載せます。各段階は次の節の図で説明し、ここでは手元に何が残るかだけを並べます。vLLM Neuron の v0.21 の変更そのものは「[vLLM Neuron プラグイン v0.21 アップデート解説](https://zenn.dev/tosshi/articles/be22d1ace136a5)」で説明しています。

| 段階 | 手元に残るもの | 実務での意味 |
|---|---|---|
| FX graph | `fxgraph.txt` | `forward` がどの演算として捕まったかを、書いたコードと見比べて確かめられる |
| HLO | `graph.hlo` | ハードウェアに依存しない演算の並びになり、ここから先は Neuron のコンパイラ `neuronx-cc` の仕事になる |
| NEFF | `graph_<hash>.neff` | 共有のキャッシュを使えば、CPU のマシンで作っておき、Trainium のマシンではコンパイルせずに読み込める |

:::message
この記事の内部フローとログは、vLLM Neuron `v0.21.0.1.0.0`（vLLM `0.21.0`、Neuron SDK `2.31.0`、neuronx-cc `2.26`）を、NeuronCore を使わない 2 つのモード（CPU モードと CPU コンパイルモード）で実際に動かして確認したものです。
:::

## 全体像: 翻訳のリレー

![PyTorch の forward は、TorchDynamo で FX graph に、torch-xla で HLO に、neuronx-cc で NEFF になる。ここまでは CPU で動き、NEFF を Neuron Runtime で NeuronCore に載せて実行するところだけ Trainium が要る。NEFF はコンパイルキャッシュに置かれ、次の起動でキャッシュにあれば再利用される](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/545d60be7314cb/zenn/articles/545d60be7314cb/compile-flow.png)

左端が普段書く `forward` で、右から 2 つ目が Trainium が直接実行できる NEFF です。右端の Neuron Runtime は、NEFF を NeuronCore に読み込んで実行するソフトウェアです。間にある FX graph と HLO は、どちらも中間表現（IR、Intermediate Representation）です。中間表現は、人が読むコードと機械が実行するバイナリの間にある、変換しやすい形式です。

**NEFF を作るところまでは CPU でできて、NeuronCore が要るのは NEFF を実行するところだけです**。公式の [CPU 開発のガイド](https://github.com/vllm-project/vllm-neuron/blob/ae6c10eff6ec748e958045241aaca0288e8ddaa8/docs/model-dev/cpu-development.md) も、CPU コンパイルモードを、Neuron のインスタンスを使わずにグラフをコンパイルし、実行はしないモードとして説明しています。この境目があるので、コンパイルを CPU のマシンに任せ、Trainium のマシンでは実行だけを行う、という分け方ができます。

## なぜグラフにするのか

GPU の PyTorch では、1 行ずつその場で演算を実行する eager 実行がふつうです。この記事で追う Trainium の経路では、`forward` をまずグラフとして受け取り、まとめて最適化してから実行します。まとめて最適化するために、まず Python の関数をグラフの形で取り出します。これがコンパイルの最初の処理で、そこから NEFF ができるまでの変換全体をコンパイルと呼びます。

## 共通の中間表現を挟む理由

![3 つのフレームワークと 3 種類のハードウェアを直接つなぐと 9 通りの変換が要るが、間に共通の中間表現を挟むと 6 通りで済む（数え方のモデル）](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/545d60be7314cb/zenn/articles/545d60be7314cb/shared-ir.png)

段階が多いのは、役割を分けるためです。フレームワークとハードウェアを直接つなぐと、組み合わせの数だけ変換が要ります。間に共通の中間表現を挟むと、フレームワーク側の開発者は共通の中間表現への変換を、ハードウェア側の開発者は共通の中間表現から実行形式への変換を作ればよくなります。この数え方では、$N$ 個のフレームワークと $M$ 種類のハードウェアをつなぐ変換の数が、$N \times M$ から $N + M$ に減ります。この記事の経路では、XLA というコンパイラが使う中間表現の HLO がこの役にあたります。[XLA](https://openxla.org/xla) は、PyTorch、TensorFlow、JAX のモデルを受け取り、GPU、CPU、機械学習のアクセラレータ向けに最適化するコンパイラです。

## FX graph と HLO: 同じ演算が姿を変える

![Tiny の forward の 3 行は、FX graph では linear、relu、add の 3 つのノードになり、HLO では dot と add、maximum、broadcast と add のような小さな演算になる。HLO では変数名 a、b は残らず、f32[2,3] のような形で追う](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/545d60be7314cb/zenn/articles/545d60be7314cb/op-relay.gif)

各段階の形を知っておくと、コンパイルで問題が起きたときに、どの変換までは期待どおりだったかを切り分けられます。例にするのは、次の極小モデル `Tiny` です。

```python
class Tiny(nn.Module):
    def __init__(self):
        super().__init__()
        self.fc = nn.Linear(4, 3)
    def forward(self, x):
        a = self.fc(x)
        b = torch.relu(a)
        return b + 1.0
```

`torch.compile` を呼ぶと、[TorchDynamo](https://docs.pytorch.org/docs/2.13/user_guide/torch_compiler/torch.compiler_dynamo_overview.html) が関数の中の演算と、演算どうしのデータの流れを取り出し、FX graph を作ります（仕組みは [PEP 523](https://peps.python.org/pep-0523/) の Frame Evaluation API を使った bytecode の解析です）。FX graph では、ノードが演算などの要素、矢印がデータの流れを表します。`Tiny` では書いた 3 行がそのまま `linear`、`relu`、`add` の 3 つの演算のノードになります。GIF は入力と出力のノードを省き、演算のノードだけを描いています。後の観察の手順では同じ計算を 1 行で書いていますが、できるノードは同じ 3 つです。演算はまだ PyTorch の語彙のままです。TorchDynamo が読み切れないコードがあるとグラフはそこで途切れ（graph break）、1 つの `forward` が複数のグラフに分かれることがあります。

次に、FX graph は torch-xla によって HLO に変換されます。HLO では、`linear` が行列積の `dot` とバイアスの `add` に、`relu` が 0 との最大値の `maximum` に置き換わり、定数は `broadcast` で形をそろえてから足されます。変数名（`a` や `b`）は残らなくなるので、HLO 以降は「どんな形のデータに、どの演算がかかるか」で追います。GIF の `f32[2,3]` は観察した出力ではなく、入力が $2 \times 4$ で `nn.Linear(4, 3)` を通るので出力が $2 \times 3$ の 32 ビット浮動小数点数になる、という形をコードから書いたものです。

## neuronx-cc の中

![neuronx-cc のログには、HLOToTensorizer、Frontend、StaticIOTranspose、WalrusDriver、NeffWrapper の順に 5 つの処理の名前が並ぶ。HLOToTensorizer の行には、hlo2penguin が HLO を penguin.py に変換する実行と、MLIR のパスの実行が出る](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/545d60be7314cb/zenn/articles/545d60be7314cb/neuronx-cc-stages.png)

HLO を NEFF にするのが、Neuron のコンパイラ `neuronx-cc` です。内部の実装は公開されていませんが、コンパイラのログには図の 5 つの処理の名前が順に出るので、HLO がどんな処理を順に通って NEFF になるかを読めます。

[MLIR](https://mlir.llvm.org/) は特定の 1 つの中間表現ではなく、用途ごとの語彙（dialect）を定義し、抽象的な表現を機械寄りの表現へ段階的に落とす（lowering）ための枠組みです。パスは、中間表現を読んで書き換える 1 つ 1 つの処理です。最初の HLOToTensorizer では、`hlo2penguin` というツールが HLO を Penguin script という内部の形式に変換し、その中で MLIR のパスが走ります。手元のログでは、ここで HLO の命令が 19 個から 14 個に減っていました。Frontend から NeffWrapper までの 4 つは、ログには名前と順番が出るだけです。

## NEFF とコンパイルキャッシュ

NEFF（Neuron Executable File Format）は、Trainium 向けの実行ファイルです。実行するときは、Neuron Runtime が NEFF を NeuronCore に読み込んで走らせます。

vLLM Neuron は、作った NEFF を `VLLM_CACHE_ROOT` の下にコンパイルキャッシュとして保存し、次の起動で設定とグラフが同じで、キャッシュにその NEFF があれば、コンパイルを省いて再利用します。初回の起動が遅く、2 回目以降が速くなるのはこのためです。公式の CPU 開発のガイドは、この性質を使う手順を紹介しています。CPU のインスタンスでは、`VLLM_NEURON_CPU_COMPILE=1` を付け、`VLLM_NEURON_REMOTE_CACHE` に NFS や FSx のような共有のファイルシステムの上のパスを指定して、NEFF を作ります。Trainium のインスタンスでは、同じ `VLLM_NEURON_REMOTE_CACHE` を指定し、`VLLM_NEURON_DISABLE_WARMUP_COMPILE=1` などでコンパイルを止めます。`VLLM_NEURON_DISABLE_WARMUP_COMPILE=1` を付けると、キャッシュに無いグラフがあったときに、その場でコンパイルする代わりに `RuntimeError` で止まります。ガイドによると、CPU コンパイルモードは投機的デコードに対応しておらず、コンパイルが通ることだけを確かめ、数値の正しさは確かめられません。

:::message
`VLLM_CACHE_ROOT` は、vLLM Neuron がコンパイルキャッシュを置く場所の設定です。vLLM を介さずに torch-neuronx や `neuronx-cc` を直接使う場合は、Neuron のコンパイラ側のキャッシュの設定（`NEURON_COMPILE_CACHE_URL` など）が関わります。
:::

## CPU だけで各段階を観察する

![CPU でコンパイルすると、compile_cache の下のハッシュ名のディレクトリに、FX graph の fxgraph.txt、HLO の graph.hlo、neuronx-cc の command.txt と log-neuron-cc.txt、NEFF の graph_<hash>.neff が残る。観察では、そのあと NEFF を NeuronCore に読み込むところでエラーが出た](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/545d60be7314cb/zenn/articles/545d60be7314cb/cpu-compile-files.png)

観察には 2 つのモードを使います。CPU モード（`VLLM_NEURON_CPU_MODE=1`）は演算を CPU で実行し、NEFF は作りません。CPU コンパイルモード（`VLLM_NEURON_CPU_COMPILE=1` と `NEURON_PLATFORM_TARGET_OVERRIDE=trn2`）はグラフを NEFF までコンパイルします。2 つは同時には有効にできません。FX graph の観察は CPU モードで、`torch.compile` に自前の backend を渡して表示するだけなので、vLLM Neuron の backend は通りません。HLO と NEFF の観察は CPU コンパイルモードで、vLLM のエンジンを使わずに `torch.compile` を直接呼びます。

CPU コンパイルモードでは、図のファイルがハッシュ名のディレクトリに残ります。`command.txt` には `neuronx-cc compile graph.hlo --framework XLA --target trn2 --output ...neff` という呼び出しがそのまま入っていて、HLO が入力で NEFF が出力であることが読めます。`log-neuron-cc.txt` には、前の節の 5 つの処理と MLIR のパスが出ます。

HLO と NEFF の観察では、成果物を保存したというログのあとに、NEFF を NeuronCore に読み込むところで、NeuronCore を確保できないというエラーが出ました。NEFF はその前に保存されています。

:::details CPU での観察の手順と出力
以下の出力は、記事の冒頭に書いた版の venv で、上から順に実行したときのものです。必要なのは、vLLM Neuron の DLAMI に付属する専用 venv だけです。以下はそのままコピー&ペーストで再現できます（1 つのシェルセッションで上から順に実行してください）。

```bash
source /opt/aws_neuronx_venv_pytorch_inference_vllm_0_21_0_1_0_0/bin/activate
export PATH="/opt/aws/neuron/bin:$PATH"
```

HLO と NEFF は、CPU コンパイルモードで作ります。パラメータと入力を `meta` デバイスに置くので、形と型だけが流れ、実データは要りません。

```bash

os.environ["VLLM_NEURON_CPU_COMPILE"] = "1"
os.environ["NEURON_PLATFORM_TARGET_OVERRIDE"] = "trn2"
os.environ["VLLM_CACHE_ROOT"] = "/tmp/artifact_demo"  # 成果物の保存先
import torch, torch.nn as nn
import vllm_neuron

class Tiny(nn.Module):
    def __init__(self):
        super().__init__()
        self.fc = nn.Linear(4, 3)
    def forward(self, x):
        return torch.relu(self.fc(x)) + 1.0

m = Tiny().eval().to("meta")               # パラメータを meta デバイスへ
cm = torch.compile(m, backend="vllm_neuron", fullgraph=True)
with torch.no_grad():
    cm(torch.randn(2, 4, device="meta"))   # 入力も meta
```

## 今後の展望: TorchNeuron

AWS は、この XLA と HLO を経由する経路とは別に、TorchNeuron という PyTorch ネイティブのバックエンドを [PyTorch Native overview](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/frameworks/torch/pytorch-native-overview.html) で紹介しています。ドキュメントは「support for eager mode for rapid iteration and experimentation」と書き、GPU と同じく 1 演算ずつその場で実行する eager モードを挙げています。`torch.compile` についても「the Neuron Backend for TorchDynamo provides native torch.compile support without using Inductor」「The Neuron backend generates Neuron IR, which may include NKI kernels passed as custom ops in the FX graphs」と書いており、FX graph から Neuron IR を作り、Neuron のコンパイラがその IR から Trainium の命令を作る経路として説明しています。内部でどの中間表現を経由するかまでは、公開情報からは分かりません。

ドキュメントには「TorchNeuron is currently only available as part of a closed Beta program」とあり、2026 年 10 月 6 日に確かめた時点では closed Beta の段階です。この記事で観察したのは、現行の XLA と HLO を経由する経路です。

## まとめ

PyTorch の `forward` は、FX graph、HLO を経て、`neuronx-cc` の中で NEFF になります。NEFF を作るところまでは CPU で再現できるので、各段階のファイルを手元で開けます。共有のキャッシュを使えば、コンパイルを Trainium のマシンから切り離すこともできます。
