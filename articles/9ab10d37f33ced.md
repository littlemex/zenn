「[NCCL Roadmap Aug-Oct 2026 の解説](https://zenn.dev/tosshi/articles/8d7fea5568e638)」で挙げた項目が、[NCCL v2.32.3-1](https://github.com/NVIDIA/nccl/releases/tag/v2.32.3-1) でどこまで実装に降りたかを整理します。GIN と EFA GDA の基本は「[MoE の all-to-all を支える層](https://zenn.dev/tosshi/articles/a0f5ff21eed405)」で図にしたので、ここでは実務で何が変わるかに絞ります。

| ロードマップの項目 | 2.32.3 での状態 | 実務での意味 |
|---|---|---|
| EFA GDA の機能を増やす | Get が入った。FlushAsync と Wait はまだ実装が終わっていない | EFA の上で、GPU が自分で Get を出せる。相手ごとの完了待ちはまだ |
| efa-dp-direct の更新 | 1.1.0 に上がり、GPU が読むキューの記述の形が変わった | aws-ofi-nccl がその形に対応している必要がある |
| GIN over Sockets | TCP の上の GIN が入った | RDMA の NIC が無い手元の GPU で GIN のカーネルを書ける |
| RAS の強化 | 集団通信の進み具合を GPU の上で数えるカウンタが入った | 止まったカーネルを見つけやすくなる |
| ロードマップの記事に無い項目 | Rubin の初期対応が入った | 性能モデルの調整は次のリリース |

## EFA GDA の Get: なぜ要るのか

![Put で頼んで返してもらうと、転送のたびに持ち主も働く。Get なら読み手だけで取り出せる](/images/9ab10d37f33ced-get-need.png)

Get は、相手の GPU のメモリから、読み手の側だけで読み出す操作です。API は [NCCL 2.30.3 から](https://github.com/NVIDIA/nccl/blob/12df1a11afad322be5a204a2db890161cbf8131d/docs/userguide/source/api/device_gin.rst#L59-L64)ありましたが、EFA GDA では使えず、[aws-ofi-nccl v1.21.0 のリリースノート](https://github.com/aws/aws-ofi-nccl/releases/tag/v1.21.0)にも「Only Put and signal operations are supported — no get or flush」と書かれていました。Flush は、自分が出した依頼が手元で終わるまで待つ操作です。Get のあとに呼ぶと、読み出したデータが自分のメモリで使えるようになるまで待ちます。Get だけがあっても、Flush が無ければ読み終わったかを確かめられません。

Get が効くのは、欲しいデータの場所を知っているのが読み手だけのときです。実例は DeepEP V2 の実験的な機能 [Engram](https://github.com/deepseek-ai/DeepEP/blob/a56d6156febcd9976e55adc85b5155bfac9f28f8/README.md) の[表引きのカーネル](https://github.com/deepseek-ai/DeepEP/blob/a56d6156febcd9976e55adc85b5155bfac9f28f8/deep_ep/include/deep_ep/impls/engram_fetch.cuh#L44-L52)で、手元の番号を見て、ほかのランクが持つ表の行を Get で取り出します。Engram については、今後のブログでより詳しく調べてみます。

**Put だけで同じことをするなら、持ち主の側にも、番号を受け取って対応する行を書き戻す処理が要ります。** Get なら、表を登録しておく準備のあとは、転送のたびに持ち主が関わらずに済みます。

## Get はどう実現されたか

![Get は Put と同じ送信キューと呼び鈴を使い、依頼の種類だけが「読む」になる](/images/9ab10d37f33ced-get-how.png)

Get は、Put がデータを送るのと同じ送信キューと呼び鈴を使います。[PR #2382](https://github.com/NVIDIA/nccl/pull/2382) によると、RDMA の読み出しと書き込みは依頼の中身の項目が同じで、違うのは依頼の種類だけです。そのため、呼び鈴を鳴らすまでの道は Put と共用です。

読んだデータは、EFA が読み手の GPU のメモリに直接書き込みます。読み手は Flush を呼んで、データが見えるようになったことを確かめます。内部では Put と共用の完了カウンタを見ています。持ち主の GPU やアプリには、転送ごとの知らせは行きません。

## efa-dp-direct: GPU と EFA の間の取り決め

![efa-dp-direct は GPU の上で依頼を組み立て、準備ではキューの記述を作る。NCCL と aws-ofi-nccl がそれぞれ取り込んでいる](/images/9ab10d37f33ced-dp-direct.png)

efa-dp-direct は、GPU から EFA を直接操作するための部品です。このソースを、[NCCL](https://github.com/NVIDIA/nccl/tree/12df1a11afad322be5a204a2db890161cbf8131d/src/transport/net_efa_gda/efa-dp-direct) と [aws-ofi-nccl](https://github.com/aws/aws-ofi-nccl/tree/63df9e4ef85c298306cac9e80bef7ac68ffec316/3rd-party/efa-gda) がそれぞれ取り込んでいます。取り込んだ版は、両者で同じとは限りません。

転送のたびには、NCCL の中で efa-dp-direct の GPU 側の部分が依頼を組み立て、呼び鈴を鳴らします。準備では、aws-ofi-nccl が efa-dp-direct を使って、GPU が読める形でキューの記述を作ります。

GPU が読むキューの記述の形が両者でずれると、GPU は間違った位置を読み書きしてしまいます。そこで NCCL は、どの形を使うかを backendVersion という番号で aws-ofi-nccl に伝えます。

2.32.3 では [PR #2398](https://github.com/NVIDIA/nccl/pull/2398) でこの形が変わり、2026 年 9 月 25 日時点で、EFA GDA の Get に必要な対応が入っているのは、まだタグの無い aws-ofi-nccl の [master](https://github.com/aws/aws-ofi-nccl/tree/63df9e4ef85c298306cac9e80bef7ac68ffec316) だけです。

## FlushAsync と Wait: 相手ごとに完了を待つ

[Flush](https://github.com/NVIDIA/nccl/blob/12df1a11afad322be5a204a2db890161cbf8131d/docs/userguide/source/api/device_gin.rst#L73-L90) が自分の出した依頼をまとめて止まって待つのに対して、FlushAsync は、1 つの相手を指定して、その終わりを止まらずに予約します。あとで Wait を呼ぶと、その相手の分が手元で終わるまで待ちます。Put の場合、手元で終わることは相手に届いたことまでは意味しません。終わった相手の分から先に使えるので、待ち時間を計算と重ねられます。Engram の表引きも、Get を出したあと相手ごとに FlushAsync を呼び、[別のカーネル](https://github.com/deepseek-ai/DeepEP/blob/a56d6156febcd9976e55adc85b5155bfac9f28f8/deep_ep/include/deep_ep/impls/engram_fetch_wait.cuh)で Wait する作りです。

EFA では同じ相手への依頼でも終わる順番が入れ替わるので、相手ごとに待つには工夫が要ります。[PR #2405](https://github.com/NVIDIA/nccl/pull/2405) で一度実装されましたが[リリース前に取り消され](https://github.com/NVIDIA/nccl/commit/78e54daaff264e7cffd6c269e64462b4459f37b7)、2.32.3 の EFA GDA ではまだ実装が終わっておらず、呼んでも何も待ちません。そのため Engram の表引きの待ち方は、EFA GDA ではまだそのまま使えません。

## TCP で GIN が動く

![GIN の依頼の出し方は 2 種類。TCP は CPU の代理役の道に新しく加わった](/images/9ab10d37f33ced-tcp-gin.png)

GIN が NIC に依頼を出す方法には、GPU が自分で頼む道と、CPU の代理役が頼む道があります。この 2 つの違いは「[MoE の all-to-all を支える層](https://zenn.dev/tosshi/articles/a0f5ff21eed405)」で説明しました。2.32.3 では、代理役の道の先に、TCP のソケットが加わりました。実体は [`rma_socket.cc`](https://github.com/NVIDIA/nccl/blob/12df1a11afad322be5a204a2db890161cbf8131d/src/transport/rma_socket.cc) です。

**これで、InfiniBand や EFA のような RDMA の NIC が無い手元の GPU でも、GDRCopy が動く環境なら、GIN を使うカーネルを書いて動作を確かめられます。** ただし、使える操作と完了の意味はバックエンドごとに違います。

TCP の GIN は、CPU から GPU のメモリを直接読み書きする GDRCopy を必要とします。GDRCopy のライブラリとドライバを入れたうえで、リリースノートの既知の問題にあるとおり、[NCCL の設定](https://github.com/NVIDIA/nccl/blob/12df1a11afad322be5a204a2db890161cbf8131d/src/init.cc#L152)で明示的に有効にします。有効でないと、[ソース](https://github.com/NVIDIA/nccl/blob/12df1a11afad322be5a204a2db890161cbf8131d/src/transport/rma_socket.cc#L30-L34)の TCP の GIN の初期化がエラーになります。

```bash
export NCCL_GDRCOPY_ENABLE=1
```

## RAS: カーネルが進んでいるかを見る

RAS には、GPU の上に置いた進み具合のカウンタを、定期的にホストへ写して見張る[仕組み](https://github.com/NVIDIA/nccl/blob/12df1a11afad322be5a204a2db890161cbf8131d/src/ras/progress_monitor.cc)が入りました。カウンタには、集団通信の種類ごとに、GPU のカーネルが終えた仕事の数と最後に終えた時刻が記録されます。たとえば、all-reduce を実行中なのに、終えた数と最後に終えた時刻がしばらく更新されなければ、その all-reduce のカーネルが止まっていると疑えます。リリースノートも「for diagnosing stalled collective kernels」と説明しています。

## Rubin: rail と plane、MPS と MLOPart

Rubin は Blackwell の次の世代の GPU です。リリースノートには、sm107 への対応とともに、ConnectX-9 の rail と plane の検出と、MPS と MLOPart の組み合わせへの対応が挙がっています。

![rail は NIC の番号でそろえたネットワーク、plane は同じ rail の中を分けた別々のネットワーク](/images/9ab10d37f33ced-rail-plane.png)

rail は、各ノードの同じ番号の NIC を同じスイッチにつなぐ作り方で、[NCCL のドキュメント](https://github.com/NVIDIA/nccl/blob/12df1a11afad322be5a204a2db890161cbf8131d/docs/userguide/source/env.rst#L152-L157)では network rail と呼ばれています。plane は、rail とは別に NIC に割り当てる、ネットワークの区分です。NCCL の[設定の例](https://github.com/NVIDIA/nccl/blob/12df1a11afad322be5a204a2db890161cbf8131d/docs/userguide/source/env.rst#L200-L202)でも、同じ rail 0 の 2 つの NIC が plane 0 と plane 1 に分かれています。NCCL の[経路探索](https://github.com/NVIDIA/nccl/blob/12df1a11afad322be5a204a2db890161cbf8131d/src/graph/search.cc#L618-L619)は、違う plane の NIC をまたいでつなぎません。リリースノートは、Rubin 対応の一部として ConnectX-9 の rail と plane の検出を挙げています。

![MPS は 1 枚の GPU を複数のプロセスで使い、MLOPart は 1 枚の GPU を複数のデバイスに分ける](/images/9ab10d37f33ced-mps-mlopart.png)

MPS は、複数のプロセスが 1 枚の GPU を同時に使うための仕組みです。MLOPart は MPS の機能で、1 枚の GPU を、それぞれ計算とメモリの資源を持つ複数の CUDA デバイスに分けます。NVIDIA の[ブログ](https://developer.nvidia.com/blog/boost-gpu-memory-performance-with-no-code-changes-using-nvidia-cuda-mps/)によると、分け目はメモリの遅延に効く境目で、Blackwell ではダイの境目です。

Rubin 向けの性能モデルの調整は 2.32.3 には入っておらず、リリースノートは「This will be part of the next release」としています。

## まとめ

2.32.3 で EFA GDA は Get まで GPU だけで出せるようになり、その土台の efa-dp-direct を通して、NCCL と aws-ofi-nccl は同じ backendVersion のキューの形に合わせる必要があります。
