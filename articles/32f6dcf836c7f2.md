## はじめに

NVIDIA の Rubin GPU は、Tensor Core の 1 クロックあたりのスループットを上げたうえで、データを運ぶ手間と、カーネルや GPU の間の待ち合わせを削る機能を足した世代です。この記事は、[NVIDIA の Rubin アーキテクチャ解説](https://developer.nvidia.com/blog/inside-nvidia-rubin-gpu-architecture-powering-the-era-of-agentic-ai/)と [vLLM の Vera Rubin NVL72 対応の報告](https://vllm.ai/blog/2026-10-09-vera-rubin-preview)の図を引用しながら、GB200 と比べて推論のどこが変わったのかに絞って読みます。prefill と decode、MoE、tensor 並列を知っている人向けに書いているので、これらの基礎は説明しません。

NVIDIA の記事は作った側の説明で、GPU とラックのそれぞれの機能が何のためにあるかを書きます。vLLM の記事は、LLM の推論を受け持つ OSS の推論エンジンである [vLLM](https://github.com/vllm-project/vllm) を Rubin で動かした側の報告で、何がそのまま動き、何を作り直し、どれだけのスループットが出たかを書いています。

比較する 2 つのラックは、36 個の Grace CPU と 72 個の Blackwell GPU を載せた [GB200 NVL72](https://www.nvidia.com/en-us/data-center/gb200-nvl72/) と、36 個の Vera CPU と 72 個の Rubin GPU を載せた [Vera Rubin NVL72](https://www.nvidia.com/en-us/data-center/vera-rubin-nvl72/) です。NVIDIA の記事は Blackwell と Blackwell Ultra を分けて書き、どのシステムと比べたかは書いていないので、NVIDIA の値を引くときは記事のとおりに Blackwell と書きます。

**token を 1 つずつ作る decode は重みと KV cache を読み続ける処理で、NVIDIA はこの段のスループットを、ピークの帯域の数字ではなくカーネルがメモリのサブシステムをどれだけ使い切れるかが決めると書いています。** Rubin の変更には、Tensor Core や softmax の計算を速くするものと、データの運びと待ち合わせを削るものの両方があり、この記事では後者を中心に読みます。

![Hopper、Blackwell、Rubin のシステムで、エージェントのスループットと interactivity の Pareto frontier を比べたグラフ](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/hopper-blackwell-rubin-throughput-interactivity-comparison.webp)
*[NVIDIA の解説](https://developer.nvidia.com/blog/inside-nvidia-rubin-gpu-architecture-powering-the-era-of-agentic-ai/)の Figure 1 から引用しました。NVIDIA が internal 2T MoE workload と書いている社内のワークロードで引いた Pareto frontier です。*

NVIDIA は本文で、Rubin GPU を Blackwell と比べて、同じエネルギーあたりのエージェントのスループットが最大 10 倍になるよう設計したと書いていて、Figure 1 はその世代の伸びを Vera Rubin プラットフォーム全体について示しています。Pareto frontier は、ユーザー 1 人あたりの 1 秒あたり token 数 (interactivity) を決めたときに出せる最大のスループットを結んだ線なので、interactivity をどこに置くかで倍率は変わります。

| 変わったところ | Blackwell 世代から Rubin へ | NVIDIA と vLLM が説明する推論での意味 |
|---|---|---|
| [チップ構成](#rubin-gpu-のチップ構成) | トランジスタが GB200 の 1 GPU の 1.6 倍に、メモリが HBM3e から HBM4 へ | 1 GPU に載るモデルと KV cache が増えます |
| [MoE の重みの指し方](#moe-の重みの指し方) | expert ごとの descriptor から、expert で共通の descriptor へ | expert が増えたときのメタデータの管理とデータの移動が軽くなります |
| [K 次元](#1-命令で処理する-k-次元を-2-倍にする) | 1 回に足し込める長さが 2 倍に (図の例では回す回数が 4 回から 2 回へ) | tensor 並列を広げたときの効率が上がります |
| [attention の中間データ](#attention-の中間データを間引く) | 中間の score を間引いて後段へ渡す使い方ができます | 長い context の softmax と 2 つ目の行列積が軽くなります |
| [カーネルのつなぎ目](#カーネルのつなぎ目の待ちを縮める) | 前の処理がまとまって終わるのを待つ形から、できた分から始める形へ | カーネルの間の空き時間が縮みます |
| [GPU 間の同期](#nvlink-の-counted-writes) | 届いたかの確認の往復から、カウンターの更新で受け手が完了を追う形へ | GPU どうしがデータを渡し合う通信の待ちが減ります |
| [メモリ帯域](#hbm4-と-locality-domain) | 8 TB/s から 22 TB/s へ (NVIDIA の記事の Blackwell との比較) | decode で重みと KV cache を読み出すのに使える帯域が上がります |
| [ラックの電力](#ラック全体で電力を平らにする) | 前の世代の平滑化に対して、蓄電で電力の尖頭を吸う Intelligent Power Smoothing が入りました | 電力の振れが小さくなり、AI factory 全体では同じ予算に置ける GPU が増えます |

*[vLLM の報告](https://vllm.ai/blog/2026-10-09-vera-rubin-preview)の Figure 2 から引用しました。vLLM はこの図の出典を NVIDIA Vera Rubin Platform としています。*

vLLM は、Vera Rubin を 5 つの rack-scale system からなるものとして紹介していて、Rubin GPU が入るのはそのうちの Vera Rubin NVL72 です。

## Rubin GPU のチップ構成

Rubin GPU は、1 つの GPU に載せる計算とメモリを増やして、モデルと KV cache を 1 GPU に収めやすくした構成です。1 枚のダイで作れる大きさには上限があるので、計算の回路は 2 枚のダイに分けて 1 つのパッケージに載せ、ダイの間を NV-HBI という高速なリンクでつないでいます。

![NVIDIA Rubin GPU のチップ構成図。Graphics Processor Cluster、HBM メモリコントローラー、L2 cache、NVLink、PCIe Gen 6 と、主な性能値が注記されている](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/nvidia-rubin-gpu-chip-architecture-1.webp)
*[NVIDIA の解説](https://developer.nvidia.com/blog/inside-nvidia-rubin-gpu-architecture-powering-the-era-of-agentic-ai/)の Figure 2 から引用しました。この図は Rubin 単体の構成で、GB200 との比較ではありません。*

GB200 からの変化で言うと、[vLLM の Figure 1](https://vllm.ai/blog/2026-10-09-vera-rubin-preview) の 1 GPU あたりの値では、トランジスタの数が 2,080 億個から 3,360 億個、HBM の容量が 186 GB から 288 GB に増えています。NVIDIA の解説が挙げる数は、トランジスタが 3,360 億個、SM が 224 個、Tensor Core が 896 個です。第 3 世代の Transformer Engine が数値形式を使い分けて、4 bit の NVFP4 で最大 50 petaflops の推論性能を出します (vLLM の Figure 1 の注記では、この 50 は sparse の値です)。重みをもっと小さく持ちたい場合に向けて、値そのものではなく代表値の表への 3 bit の番号を持つ形式も入り、NVIDIA はこの形式で MXFP8 と同じ精度まで保てると書いています。メモリは最大 288 GB の HBM4 で帯域は最大 22 TB/s、GPU の外へは NVLink 6 が NVLink Switch へ 3,600 GB/s を出します。

## MoE の重みの指し方

MoE では token ごとに使う expert が変わるので、expert の数が増えるほど、重みの置き場所を伝える descriptor の管理が重くなります。descriptor は、複雑な配置のデータをまとめて動かす TMA (Tensor Memory Accelerator) に「どこから、どんな形で読むか」を渡す指定で、Rubin はこれを、メモリ上で書き換える形から、命令の中で項目を上書きできる形に変えました。

図では、Blackwell 側は expert ごとに descriptor を 1 つ持っています。Rubin では、形が同じで置き場所だけが違う重みに共通の descriptor を 1 つ持ち、メモリ上の descriptor を書き換える代わりに、メモリのポインターや stride といった項目を TMA の命令の中で実行時に上書きします。

![Blackwell と Rubin を並べた図。Blackwell は expert ごとに MoE descriptor を持ち、Rubin は 1 つの descriptor を全 expert で共有する](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/rubin-gpu-moe-descriptor-sharing-1.webp)
*[NVIDIA の解説](https://developer.nvidia.com/blog/inside-nvidia-rubin-gpu-architecture-powering-the-era-of-agentic-ai/)の Figure 3 から引用しました。*

共通の descriptor を使えないと、expert の数を増やすほどメタデータの管理と、そのためのデータの移動が増えて、GPU の時間が推論そのもの以外に使われます。expert 数の多いモデルを選びやすくなる変更です。

## 1 命令で処理する K 次元を 2 倍にする

Rubin は、行列積で足し込む方向を 1 回の命令で 2 倍の長さまで処理できるようにして、モデルを多数の GPU に割ったときの繰り返しの回数を減らしました。足し込む方向の長さは、$C = A B$ で $A$ が $M \times K$、$B$ が $K \times N$ のときの $K$ にあたり、K 次元と呼びます。

モデルの計算を多数の GPU に割ると、1 GPU が受け持つ出力の幅 $N$ は小さくなるのに、足し込む方向の $K$ は大きいままになることがよくあります。K 次元が長いと、カーネル (GPU の上で 1 回の起動で動く計算のプログラム) は K 次元をループで分けて処理するので、ループの回数そのものが損になります。

![同じ行列積について、Rubin は 1 回に処理する K 次元を 2 倍にして 2 回の繰り返しで終わり、Blackwell は 4 回かかることを示す図](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/rubin-k-dimension-instruction-throughput-1.webp)
*[NVIDIA の解説](https://developer.nvidia.com/blog/inside-nvidia-rubin-gpu-architecture-powering-the-era-of-agentic-ai/)の Figure 4 から引用しました。*

K ループが減ると、ループの管理も Tensor Core が空く時間も減るので、prefill の行列積と decode の行列積の両方が、tensor 並列を広げた状態で効率よく動きます。

## attention の中間データを間引く

attention は、token どうしの関係を score として計算し、softmax で割合に直してから value に掛ける処理です。NVIDIA は、Rubin の新しい sparsity の機能を attention に使う方法の 1 つとして、この途中にできる score を間引いて持つやり方を挙げています。score の書き出しと保存が減り、後段の softmax と行列積で扱うデータと計算も減ります。

その流れは 3 段です。1 つめに、query と key の積を、すべての値を持つ形で計算して score を作ります。2 つめに、その score を Tensor Memory から読み出すときに 2:4 の sparse な形 (並んだ 4 つのうち 2 つを残す形) に圧縮し、残した値と、それが元はどこにあったかを示すメタデータを作ります。3 つめに、softmax は残った値だけを処理し、value との積は残った値とメタデータを使った sparse な行列積で済ませます。出力は元の dense の形式を保つので、周りのモデルのパイプラインのインターフェースを変えずに使えます。4 つのうちどの 2 つを残すかと、それが出力の品質にどう響くかは、NVIDIA の記事に書かれていません。

![すべての値を持つ行列がメタデータ付きの sparse な行列に変換され、transformer block の attention と MLP の activation に適用されることを示す図](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/nvidia-rubin-adaptive-compression-sparsity-1.webp)
*[NVIDIA の解説](https://developer.nvidia.com/blog/inside-nvidia-rubin-gpu-architecture-powering-the-era-of-agentic-ai/)の Figure 5 から引用しました。図には MLP の activation への適用も描かれていますが、この節で扱うのは attention の score の部分だけです。*

もう 1 つ、softmax に使う指数関数の、SM 1 つあたり 1 クロックあたりのスループットも上がりました。Tensor Core が速くなると、指数関数と行方向の足し込みに頼る softmax が先に詰まるからです。

| GPU | FP32 の指数関数 | BF16/FP16 の指数関数 |
|---|---|---|
| Blackwell | 1 倍 | 1 倍 |
| Blackwell Ultra | 2 倍 | 2 倍 |
| Rubin | 2 倍 | 4 倍 |

[NVIDIA の解説](https://developer.nvidia.com/blog/inside-nvidia-rubin-gpu-architecture-powering-the-era-of-agentic-ai/)の Table 1 から引用した、Blackwell を 1 としたときの、SM 1 つあたり 1 クロックあたりの比です。

## カーネルのつなぎ目の待ちを縮める

推論では、1 つのカーネルが activation を書き、次のカーネルがそれを読んで次の token の計算を進めます。Rubin は、この引き継ぎを、前のカーネルがまとまって終わるのを待つ形から、使えるデータができた分だけ始める形に変えました。

Blackwell にも、後続のカーネルを先に起動しておく programmatic dependent launch がありました。それでも後続は必要な activation が揃うまで待つことがあり、GPU の時間に空きができます。Rubin は tile (行列を小さな四角に分けた 1 つ分) の単位で依存を見るので、後続は自分が要る tile ができた時点で動き出せます。

![Blackwell と Rubin の producer と consumer の thread block の時間軸を比べた図。Rubin はデータができた分から consumer の処理を始める](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/blackwell-rubin-timelines-producer-consumer-thread-blocks-1.webp)
*[NVIDIA の解説](https://developer.nvidia.com/blog/inside-nvidia-rubin-gpu-architecture-powering-the-era-of-agentic-ai/)の Figure 6 から引用しました。上が Blackwell のまとまり単位の起動で、下が Rubin の tile 単位の起動です。*

エージェントの推論では、activation がモデルの層を順番に通るので、カーネルからカーネルへ移るときのレイテンシーが、ユーザー 1 人あたりの 1 秒あたり token 数にそのまま出ます。

## NVLink の counted writes

GPU 間の転送では、データ本体のほかに、読み出してよいことを知らせるやり取りが要ります。Rubin は counted writes という仕組みで、受け取る側の GPU が転送の完了をより効率よく追えるようにしました。

カーネルの中に通信を入れると、カーネルは CPU に制御を返さずに、計算を続けながら NVLink でほかの GPU へ書き込めます。従来の GPU 間の通信では、そのときにデータ本体のほかに調整と同期の処理が要り、通信が頻繁なときにレイテンシーを足し、NVLink の帯域を使うことがあります。図では、Blackwell 側が、書いたデータが相手から見えると保証する処理、届いたことの返事、届いたことを示す印の書き込みを使い、Rubin 側はカウンターの更新のあとに受け取る側がデータを読み出します。

![Blackwell が memory barrier、応答、atomic flag を使い、Rubin はカウンターの更新のあとに受け取る側の GPU がデータを読み出すことを並べた図](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/rubin-nvlink-communication-acceleration.webp)
*[NVIDIA の解説](https://developer.nvidia.com/blog/inside-nvidia-rubin-gpu-architecture-powering-the-era-of-agentic-ai/)の Figure 7 から引用しました。*

NVIDIA は、分散推論で通信が頻繁に起きるときに、counted writes を使った通信が同期の待ちを減らし、計算を止めずに済むと書いています。

## HBM4 と locality domain

Rubin は HBM4 で帯域の上限を上げ、vLLM は CUDA 13.4 の locality domain を使って、SM が自分に近いメモリから重みを読むようにしました。前者がハードウェアの変更、後者がソフトウェアの側の使い方です。

![Blackwell、Blackwell Ultra、Rubin のメモリ帯域を比べた棒グラフ。8 TB/s から Rubin の 22 TB/s へ上がる](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/memory-bandwidth-nvidia-rubin-gpu.webp)
*[NVIDIA の解説](https://developer.nvidia.com/blog/inside-nvidia-rubin-gpu-architecture-powering-the-era-of-agentic-ai/)の Figure 8 から引用しました。*

HBM4 は HBM3e に対してインターフェースの幅が 2 倍になりました。新しいメモリコントローラーと合わせて、NVIDIA の記事では最大 22 TB/s としていて、Blackwell と Blackwell Ultra の 8 TB/s の 2.8 倍です。1 GPU あたりに直した vLLM の値では、GB200 の 7.94 TB/s に対して 19.16 TB/s で 2.4 倍になります。容量は 1 GPU あたり最大 288 GB で、context を長くすることと、KV cache を GPU の外に出さずに同時実行数を上げることに効きます。

locality domain は、GPU の中の SM とメモリを区分に分けて、計算とデータを同じ区分に置く仕組みです。SM は自分の区分のメモリを、ほかの区分の HBM より高い帯域と低いレイテンシーで読めるので、区分ごとに 1 つのカーネルを起動して、それぞれが自分の区分だけを読むようにできます。vLLM は、NVIDIA の GPU は Ampere からメモリへのアクセスが一様ではなく、locality domain は CUDA 13.4 の機能で、今も設計と開発が続いていると書いています。

vLLM は予備的な評価として、これを MoE の decode に当てました。重みの読み出しで詰まる処理なので、expert の 2 つの全結合層 (FC1 と FC2) の重みを列の方向に半分ずつ割り、2 つの locality domain のそれぞれの SM が、自分の区分にある半分だけを読むようにしています (split-N)。入力と出力は 2 つの区分にまたがったままです。ただし vLLM は、decode では activation のメモリが比較的小さいので、その負担も小さいと説明しています。[vLLM の locality domain の評価](https://vllm.ai/blog/2026-10-09-vera-rubin-preview#locality-domain-support)では、MiniMax M3 という MoE のモデルの形で、FC1 と FC2 の forward のレイテンシーを rank あたりで測っています。token 数が小さい設定では、locality domain を使わない場合のレイテンシーに対して、平均 1.2 倍の speedup でした。routing を均した条件で、tensor 並列が 2 と 4、expert 並列が 2 と 4 でも、212 個の SM を使う backfill mode でも 200 個を使う既定の mode でも、傾向はおおむね同じで、通信の時間は含みません。精度と vLLM のバージョンは報告に書かれていません。

## ラック全体で電力を平らにする

Vera Rubin のラックは、電源に蓄電を持って電力の振れを吸い、尖頭に合わせて空けていた電力の枠を GPU に回せるようにしました。

![蓄電が電力の尖頭を吸い、空き時間の谷を埋めて、交流の入力電力を平らに保つことを示すグラフ](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/gpu-power-chart.webp)
*[NVIDIA の解説](https://developer.nvidia.com/blog/inside-nvidia-rubin-gpu-architecture-powering-the-era-of-agentic-ai/)の Figure 9 から引用しました。*

![DSX MaxLPS が無い場合の使われない容量と、同じ電力の予算で最大 40% 多い GPU を置けることを並べた図](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/power-budget-comparison-dsx-maxlps-1.webp)
*[NVIDIA の解説](https://developer.nvidia.com/blog/inside-nvidia-rubin-gpu-architecture-powering-the-era-of-agentic-ai/)の Figure 10 から引用しました。比べているのは、DSX MaxLPS を使わない場合と使う場合に同じ電力の予算で置ける GPU の数で、電力の波形ではありません。*

NVIDIA は、この Intelligent Power Smoothing が、前の世代の平滑化と比べて平均の消費電力を約 10%、50 ms の尖頭を約 20% 下げると書いています。さらに、AI factory 全体で電力を配る DSX MaxLPS を使うと、効率のよい動作点で、ワークロードの性能への影響を小さく抑えながら、使わない場合と同じ電力の予算に最大 40% 多い GPU を置けるとしています。この 40% は AI factory 全体の話で、Vera Rubin NVL72 のラック単体の値ではありません。

## vLLM が Rubin で動くまで

vLLM は、既存の実装のまま Rubin で推論を動かし始められました。[vLLM の報告](https://vllm.ai/blog/2026-10-09-vera-rubin-preview)によると、Rubin は Blackwell と同じアーキテクチャの系列で、カーネルを機械語にするときに指定する GPU の種類 (compile target) は sm107 という新しいものですが、Blackwell 系の sm100f 向けに作ったカーネルもそのまま動きます。

そのため、行列積が重い attention や MoE のカーネルは手を入れずに動き、DeepSeek、Kimi、GLM、MiniMax が Rubin で動いています。Rubin 向けに調整した attention、行列積、MoE のカーネルは、推論のカーネルを集めた [FlashInfer](https://github.com/flashinfer-ai/flashinfer) というライブラリから入ります。毎日の container は CUDA 13.4 と PyTorch 2.15 で作った `vllm/vllm-openai:cu134-nightly` として公開されています。各カーネルを有効にする指定は[vLLM の実行手順の付録](https://vllm.ai/blog/2026-10-09-vera-rubin-preview#appendix-running-vllm-on-vera-rubin-nvl72)にまとまっているので、使うときはそちらを見てください。

Rubin の公開直後から使えるものと、これから入るものの線引きも報告に書かれています。2026 年 10 月 9 日の時点で入っているカーネルには、dense の NVFP4 と MXFP4 の行列積、NVFP4 の MoE、FP8 の attention、FP8 の MSA prefill などがあります。今後の作業に挙がっているのは、counted writes を使う MoE の all-to-all (expert ごとに token を各 GPU へ配り直す通信) のカーネル、前に出てきた programmatic dependent launch (PDL) と Lamport Sync でカーネルの重ね合わせを増やすこと、MoE の層で locality domain を全面的に有効にすることなどです。この記事で説明した Rubin の機能のうち、descriptor の共有、K 次元、score の 2:4 の圧縮については、vLLM が今使っているかどうかは報告に書かれていません。

## 早期の実測値

vLLM は 2 つのベンチマークで、Rubin のスループットを前の世代のラックと比べています。vLLM は AgentX の結果を早期の評価と位置づけ、使える Vera Rubin NVL72 のノードが増えればテストを広げると書いています。

![SemiAnalysis AgentX で MiniMax M3 を動かした、vLLM on Rubin の結果のグラフ](https://vllm.ai/blog-assets/figures/2026-10-09-vera-rubin-preview/agentx-results.png)
*[vLLM の報告](https://vllm.ai/blog/2026-10-09-vera-rubin-preview)の Figure 5 から引用しました。MiniMax M3 で測った SemiAnalysis AgentX の結果です。*

1 つめは SemiAnalysis の AgentX です。MiniMax M3 を Vera Rubin NVL72 で動かし、ユーザー 1 人あたりの 1 秒あたり token 数 (interactivity) を揃えた条件で、GB200 の 1 GPU あたり最大 7.84 倍のスループットが出ました。揃えた interactivity の値、精度、GB200 側で動かしたソフトウェアとバージョンは、報告の本文に書かれていません。1 秒あたり 150 token の制約の下では GB200 と比べて 5.18 倍で、この 5.18 倍が 1 GPU あたりの値かどうかは書かれていません。2 つめは [MLPerf Inference](https://mlcommons.org/benchmarks/inference-datacenter/) v6.1 の VLM で、Qwen3-VL-235B-A22B を、vLLM を推論エンジン、[Dynamo](https://github.com/ai-dynamo/dynamo) を前段のルーターとして動かし、offline と server と interactive のシナリオを通じて GB300 NVL72 と比べて最大 3.7 倍のスループットでした。比較の相手が AgentX では GB200、MLPerf では GB300 なので、2 つの倍率を並べて比べることはできません。

## 数字の基準をそろえる

公開されている倍率は、どの単位で数えたかで変わります。vLLM の Figure 1 は、GB200 NVL72 と Vera Rubin NVL72 の仕様のページと NVIDIA の Rubin の記事をもとに、1 GPU あたりに直した値を並べているので、基準をそろえて読むのに向いています。

| 項目 | GB200 NVL72 の 1 GPU | Vera Rubin NVL72 の 1 GPU | 比 |
|---|---|---|---|
| HBM の容量 | 186 GB | 288 GB | 1.5 倍 |
| HBM の帯域 | 7.94 TB/s | 19.16 TB/s | 2.4 倍 |
| BF16 (dense) | 2.5 PFLOPS | 4.0 PFLOPS | 1.6 倍 |
| FP8 (dense) | 5.0 PFLOPS | 17.5 PFLOPS | 3.5 倍 |
| NVFP4 の学習 (dense) | 10 PFLOPS | 35 PFLOPS | 3.5 倍 |
| NVFP4 の推論 | 10 PFLOPS (dense) | 50 PFLOPS (sparse) | 5 倍 (条件が違います) |
| NVLink の双方向の帯域 | 1.8 TB/s | 3.0 TB/s | 1.7 倍 |
| トランジスタの数 | 2,080 億個 | 3,360 億個 | 1.6 倍 |

[vLLM の報告](https://vllm.ai/blog/2026-10-09-vera-rubin-preview)の Figure 1 の値から、指数関数の 2 行を除いて書き写しました。この表を読むときに気をつける点が 4 つあります。

1 つめに、NVFP4 の推論の 5 倍は、GB200 側が dense の値、Rubin 側が sparse の値です。図にも、この行だけが sparse でほかは dense だという注記が付いています。2 つめに、HBM の帯域は、Blackwell 側が 8 TB/s と 7.94 TB/s でほぼ同じで、差は Rubin 側の 22 TB/s と 19.16 TB/s にあります。NVIDIA の記事は 22 TB/s を最大の値として書き、vLLM の図のページのデータは、19.16 TB/s を $16128 \times 4.752 \times 2 / 8 = 19160$ GB/s として計算しています。3 つめに、NVLink の帯域は、NVIDIA の記事が NVLink Switch への scale-up の帯域を 3,600 GB/s と書き、vLLM の表は双方向の帯域を 1 GPU あたり 3.0 TB/s としていて、vLLM はこの 1.7 倍の帯域が collective を速くすると見込んでいます。4 つめに、SM の数は、NVIDIA の記事が Rubin GPU に 224 個を挙げ、vLLM は locality domain の実験で backfill mode なら 212 個、既定なら 200 個を使うと書いています。2 つめから 4 つめの食い違いと数え方の関係は、どちらの記事にも書かれていません。22 TB/s は NVIDIA が示す最大の値、19.16 TB/s は vLLM が spec から計算した値として区別し、2 つを混ぜて使わないでください。

倍率を引用するときは、dense か sparse か、1 GPU かラック全体か、比較の相手が GB200 か GB300 かを一緒に書いてください。どれかが抜けた倍率は、読み手が別の条件の値と取り違えます。

## まとめ

Rubin には、Tensor Core や指数関数のように計算を増やす変更と、MoE の重みの指定を共有する descriptor、必要な tile ができた分から後続を始めるカーネルの引き継ぎ、転送の完了をカウンターで受け手が追う counted writes、帯域を上げた HBM4 のように、データの運びと待ち合わせを削る変更の両方があります。推論の性能を見積もるときは演算の値だけで決めず、公開されている倍率は比較の条件と一緒に読んでください。
