## はじめに

NVIDIA の Rubin GPU は、Tensor Core の 1 クロックあたりのスループットを上げたうえで、データを運ぶ手間と、カーネル (GPU の上で 1 回の起動で動く計算のプログラム) や GPU の間の待ち合わせを削る機能を足した世代です。この記事は、[NVIDIA の Rubin アーキテクチャ解説](https://developer.nvidia.com/blog/inside-nvidia-rubin-gpu-architecture-powering-the-era-of-agentic-ai/)と [vLLM の Vera Rubin NVL72 対応の報告](https://vllm.ai/blog/2026-10-09-vera-rubin-preview)の図を引用しながら、GB200 と比べて推論のどこが変わったのかに絞って読みます。prefill と decode、MoE、tensor 並列を知っている人向けに書いているので、これらの基礎は説明しません。

NVIDIA の解説は作った側の説明で、GPU とラックのそれぞれの機能が何のためにあるかを書きます。vLLM の報告は、LLM の推論を受け持つ OSS の推論エンジンである [vLLM](https://github.com/vllm-project/vllm) を Rubin で動かした側の報告で、何がそのまま動き、何を作り直し、どれだけのスループットが出たかを書いています。

比較する 2 つのラックは、36 個の Grace CPU と 72 個の Blackwell GPU を載せた [GB200 NVL72](https://www.nvidia.com/en-us/data-center/gb200-nvl72/) と、36 個の Vera CPU と 72 個の Rubin GPU を載せた [Vera Rubin NVL72](https://www.nvidia.com/en-us/data-center/vera-rubin-nvl72/) です。NVIDIA の解説は Blackwell と Blackwell Ultra を分けて書き、どのシステムと比べたかは書いていないので、NVIDIA の値を引くときは解説のとおりに Blackwell と書きます。

decode は、token を 1 つずつ作るあいだ、重みと KV cache を読み続ける処理です。**NVIDIA は、decode がメモリのサブシステムで頭打ちになり、効くのは帯域のピークの数字ではなく、各カーネルがメモリのサブシステム全体をどれだけ効率よく使えるかだと書いています。** Rubin の変更には、Tensor Core や softmax の計算のスループットを上げるものと、データの運びと待ち合わせを削るものの両方があり、この記事では後者を中心に読みます。

![縦軸が 1 GW あたりの agent throughput (tokens per sec/GW)、横軸が agent interactivity (turns per minute per user) の Pareto frontier。Hopper NVL8 + x86、Blackwell NVL72 + x86、Rubin NVL72 + Vera の 3 本の線が並び、Rubin が 10x more agents と 2x more tool calls と注記されている](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/hopper-blackwell-rubin-throughput-interactivity-comparison.webp)
*[NVIDIA の解説](https://developer.nvidia.com/blog/inside-nvidia-rubin-gpu-architecture-powering-the-era-of-agentic-ai/)の Figure 1 から引用しました。NVIDIA が internal 2T MoE workload と書いている社内のワークロードで引いた Pareto frontier です。*

NVIDIA の解説は、Rubin GPU を Blackwell と比べて、同じエネルギーあたりのエージェントのスループットが最大 10 倍になるよう設計したと書いています。その 10 倍を示す Figure 1 は、縦軸が 1 GW あたりの token/s、横軸がユーザー 1 人あたり 1 分あたりの turn 数で、Blackwell NVL72 + x86 の線に対して Rubin NVL72 + Vera の線に 10x more agents と 2x more tool calls が注記されています。縦軸が電力で割られているのでエネルギーあたりの比較になり、Pareto frontier なので横軸のどこを見るかで倍率は変わります。

| 変わったところ | Blackwell 世代から Rubin へ | NVIDIA と vLLM が説明する推論での意味 |
|---|---|---|

| [MoE の重みの指し方](#moe-の重みの指し方) | expert ごとの descriptor から、expert で共通の descriptor へ | expert が増えたときの descriptor の管理とデータの移動が軽くなります |
| [K 次元](#1-命令あたりの-k-次元) | 1 回に足し込める長さが 2 倍に (図の例では回す回数が 4 回から 2 回へ) | tensor 並列を広げたときの効率が上がります |

| [カーネルのつなぎ目](#カーネルのつなぎ目の待ち) | 前の処理がまとまって終わるのを待つ形から、できた分から始める形へ | カーネルの間の空き時間が縮みます |
| [GPU 間の同期](#nvlink-の-counted-writes) | 届いたかの確認の往復から、カウンターの更新で受け手が完了を追う形へ | GPU どうしがデータを渡し合う通信の待ちが減ります |
| [メモリ帯域](#hbm4-と-locality-domain) | 8 TB/s から最大 22 TB/s へ (NVIDIA の解説の Blackwell との比較) | decode で重みと KV cache を読み出すのに使える帯域が上がります |
| [ラックの電力](#ラック全体の電力の平滑化) | 前の世代の平滑化から、蓄電で電力のピークを吸う Intelligent Power Smoothing へ | 電力の振れが小さくなり、AI factory 全体では同じ予算に置ける GPU が増えます |

## Rubin GPU のチップ構成

Rubin GPU は、1 つの GPU に載せる計算とメモリを増やして、モデルと KV cache を 1 GPU に収めやすくした構成です。1 枚のダイで作れる大きさには上限があるので、計算の回路は 2 枚のダイに分けて 1 つのパッケージに載せ、ダイの間を NV-HBI という高速なリンクでつないでいます。

![NVIDIA Rubin GPU のチップ構成図。Graphics Processor Cluster、HBM メモリコントローラー、L2 cache、NVLink、PCIe Gen 6 と、主な性能値が注記されている](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/nvidia-rubin-gpu-chip-architecture-1.webp)
*[NVIDIA の解説](https://developer.nvidia.com/blog/inside-nvidia-rubin-gpu-architecture-powering-the-era-of-agentic-ai/)の Figure 2 から引用しました。この図は Rubin 単体の構成で、GB200 との比較ではありません。*

GB200 からの変化で言うと、[vLLM の Figure 1](https://vllm.ai/blog/2026-10-09-vera-rubin-preview) の 1 GPU あたりの値では、トランジスタの数が 2,080 億個から 3,360 億個、HBM の容量が 186 GB から 288 GB に増えています。NVIDIA の解説が挙げる数は、トランジスタが 3,360 億個、SM が 224 個、Tensor Core が 896 個です。第 3 世代の Transformer Engine が数値形式を使い分けて、4 bit の NVFP4 で最大 50 PFLOPS の推論性能を出します (vLLM の Figure 1 の注記では、この 50 は値を間引いて持つ sparse の値で、ほかの行はすべての値を持つ dense の値です)。重みをもっと小さく持ちたい場合に向けて、値そのものではなく代表値の表への 3 bit の番号を持つ形式も入り、NVIDIA はこの形式で MXFP8 と同じ精度まで保てると書いています。メモリは最大 288 GB の HBM4 で帯域は最大 22 TB/s、GPU の外へは NVLink 6 が NVLink Switch へ 3,600 GB/s を出します。

## MoE の重みの指し方

MoE では token ごとに使う expert が変わるので、expert の数が増えるほど、重みの置き場所を伝える descriptor の管理が重くなります。descriptor は、複雑な配置のデータをまとめて動かす TMA (Tensor Memory Accelerator) に「どこから、どんな形で読むか」を渡す指定で、Rubin は、expert ごとに持っていた descriptor を、expert で共通の 1 つにできるようにしました。

図では、Blackwell 側は expert ごとに descriptor を 1 つ持っています。Rubin では、形が同じで置き場所だけが違う重みに共通の descriptor を 1 つ持ち、メモリ上の descriptor を書き換える代わりに、メモリのポインターや stride といった項目を TMA の命令の中で実行時に上書きします。

![Blackwell と Rubin を並べた図。Blackwell は expert ごとに MoE descriptor を持ち、Rubin は 1 つの descriptor を全 expert で共有する](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/rubin-gpu-moe-descriptor-sharing-1.webp)
*[NVIDIA の解説](https://developer.nvidia.com/blog/inside-nvidia-rubin-gpu-architecture-powering-the-era-of-agentic-ai/)の Figure 3 から引用しました。*

共通の descriptor を使えないと、expert の数を増やすほど descriptor の管理とデータの移動が増えて、GPU の時間が推論そのもの以外に使われます。NVIDIA は、この変更で expert の数が増えても MoE のモデルが効率よくスケールするようになると書いています。

## 1 命令あたりの K 次元

Rubin は、行列積で足し込む方向を、1 回の命令で Blackwell の 2 倍の長さまで処理できるようにして、モデルを多数の GPU に割ったときの繰り返しの回数を減らしました。足し込む方向の長さは、$C = A B$ で $A$ が $M \times K$、$B$ が $K \times N$ のときの $K$ にあたり、K 次元と呼びます。

モデルの計算を多数の GPU に割ると、1 GPU が受け持つ出力の幅 $N$ は小さくなるのに、足し込む方向の $K$ は大きいままになることがよくあります。K 次元が長いと、カーネルは K 次元をループで分けて処理するので、ループの回数そのものが損になります。

![同じ行列積について、Rubin は 1 回に処理する K 次元を 2 倍にして 2 回の繰り返しで終わり、Blackwell は 4 回かかることを示す図](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/rubin-k-dimension-instruction-throughput-1.webp)
*[NVIDIA の解説](https://developer.nvidia.com/blog/inside-nvidia-rubin-gpu-architecture-powering-the-era-of-agentic-ai/)の Figure 4 から引用しました。*

K ループが減ると、ループの管理も Tensor Core が空く時間も減るので、prefill の行列積と decode の行列積の両方が、tensor 並列を広げた状態で効率よく動きます。

## attention の score の間引き

Rubin では、attention の途中にできる score を間引いて持てるようになり、score の書き出しと保存が減って、後段の softmax と行列積で扱うデータと計算も減ります。attention は、token どうしの関係を score として計算し、softmax で割合に直してから value に掛ける処理です。NVIDIA は、この間引き方を、Rubin の新しい sparsity の機能を attention に使う方法の 1 つとして挙げています。

その流れは 3 段です。1 つめに、query と key の積を、すべての値を持つ形で計算して score を作ります。2 つめに、その score を Tensor Memory から読み出すときに構造化された 2:4 の sparse な形 (4 つ並んだ値のうち 2 つを非ゼロとして持つ形) に圧縮し、非ゼロの値と、それを使うためのメタデータを作ります。3 つめに、softmax は非ゼロの値だけを処理し、value との積は非ゼロの値とメタデータを使った sparse な行列積で済ませます。出力は元の dense の形式を保つので、周りのモデルのパイプラインのインターフェースを変えずに使えます。どの値を非ゼロとして残すかと、それが出力の品質にどう響くかは、NVIDIA の解説に書かれていません。

![すべての値を持つ行列がメタデータ付きの sparse な行列に変換され、transformer block の attention と MLP の activation に適用されることを示す図](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/nvidia-rubin-adaptive-compression-sparsity-1.webp)
*[NVIDIA の解説](https://developer.nvidia.com/blog/inside-nvidia-rubin-gpu-architecture-powering-the-era-of-agentic-ai/)の Figure 5 から引用しました。図には MLP の activation への適用も描かれていますが、この節で扱うのは attention の score の部分だけです。*

もう 1 つ、softmax に使う指数関数の、SM 1 つあたり 1 クロックあたりのスループットも上がりました。Tensor Core のスループットが上がると、指数関数と行方向の足し込みに頼る softmax がボトルネックになりうるからです。

| GPU | FP32 の指数関数 | BF16/FP16 の指数関数 |
|---|---|---|
| Blackwell | 1 倍 | 1 倍 |
| Blackwell Ultra | 2 倍 | 2 倍 |
| Rubin | 2 倍 | 4 倍 |

[NVIDIA の解説](https://developer.nvidia.com/blog/inside-nvidia-rubin-gpu-architecture-powering-the-era-of-agentic-ai/)の Table 1 から引用した、Blackwell を 1 としたときの、SM 1 つあたり 1 クロックあたりの比です。NVIDIA の解説は、この表で Blackwell、Blackwell Ultra、Rubin の 3 世代を並べています。

## カーネルのつなぎ目の待ち

推論では、1 つのカーネルが activation を書き、次のカーネルがそれを読んで次の token の計算を進めます。Rubin は、この引き継ぎを、前のカーネルのまとまりが終わるのを待つ形 (図の bulk triggering) から、使えるデータができた分だけ始める形に変えました。

Blackwell にも、後続のカーネルを先に起動しておく programmatic dependent launch がありました。それでも後続は必要な activation が揃うまで待つことがあり、GPU の時間に空きができます。Rubin は tile (行列を小さな四角に分けた 1 つ分) の単位で依存を見るので、後続は自分が要る tile ができた時点で動き出せます。

![Blackwell と Rubin の producer と consumer の thread block の時間軸を比べた図。Rubin はデータができた分から consumer の処理を始める](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/blackwell-rubin-timelines-producer-consumer-thread-blocks-1.webp)
*[NVIDIA の解説](https://developer.nvidia.com/blog/inside-nvidia-rubin-gpu-architecture-powering-the-era-of-agentic-ai/)の Figure 6 から引用しました。上が Blackwell のまとまり単位の起動で、下が Rubin の tile 単位の起動です。*

エージェントの推論では、activation がモデルの層を順番に通るので、カーネルからカーネルへ移るときのレイテンシーが、ユーザー 1 人あたりの 1 秒あたり token 数にそのまま出ます。

## NVLink の counted writes

GPU 間の転送では、データ本体のほかに、読み出してよいことを知らせるやり取りが要ります。Rubin は counted writes という仕組みで、受け取る側の GPU が転送の完了をより効率よく追えるようにしました。

カーネルの中に通信を入れると、カーネルは CPU に制御を返さずに、計算を続けながら NVLink でほかの GPU へ書き込めます。従来の GPU 間の通信では、そのときにデータ本体のほかに調整と同期の処理が要り、通信が頻繁なときにレイテンシーを足し、NVLink の帯域を使うことがあります。図では、Blackwell 側が、書いたデータが相手から見えると保証する処理、届いたことの返事、届いたことを示す印の書き込みを使い、Rubin 側はカウンターの更新のあとに受け取る側がデータを読み出します。

![Blackwell が memory barrier、応答、atomic flag を使い、Rubin はカウンターの更新のあとに受け取る側の GPU がデータを読み出すことを並べた図](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/rubin-nvlink-communication-acceleration.webp)
*[NVIDIA の解説](https://developer.nvidia.com/blog/inside-nvidia-rubin-gpu-architecture-powering-the-era-of-agentic-ai/)の Figure 7 から引用しました。*

NVIDIA は、分散推論で通信が頻繁に起きるときに、counted writes を使った通信が同期の待ちを減らし、計算を止めずに済むと書いています。

## HBM4 と locality domain

Rubin は HBM4 で帯域の上限を上げ、vLLM は CUDA 13.4 の locality domain を使って、SM が自分に近いメモリから MoE の重みを読む対応を進めています。前者がハードウェアの変更、後者がソフトウェアの側の使い方です。

![メモリ帯域の棒グラフ。Blackwell GPU (HBM3e) と Blackwell Ultra GPU (HBM3e) が 8 TB/s、Rubin GPU (HBM4) が 22 TB/s で、その間に 2.8x と注記されている](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/memory-bandwidth-nvidia-rubin-gpu.webp)
*[NVIDIA の解説](https://developer.nvidia.com/blog/inside-nvidia-rubin-gpu-architecture-powering-the-era-of-agentic-ai/)の Figure 8 から引用しました。*

HBM4 は HBM3e に対してインターフェースの幅が 2 倍になりました。新しいメモリコントローラーと合わせて、NVIDIA の解説では最大 22 TB/s としていて、Blackwell と Blackwell Ultra の 8 TB/s の 2.8 倍です。1 GPU あたりに直した vLLM の値では、GB200 の 7.94 TB/s に対して 19.16 TB/s で 2.4 倍になります。容量は 1 GPU あたり最大 288 GB で、context を長くすることと、KV cache を GPU の外に出さずに同時実行数を上げることに効きます。

locality domain は、GPU の中の SM とメモリを区分に分けて、計算とデータを同じ区分に置く仕組みです。SM は自分の区分のメモリを、ほかの区分の HBM より高い帯域と低いレイテンシーで読めるので、区分ごとに 1 つのカーネルを起動して、それぞれが自分の区分だけを読むようにできます。vLLM は、locality domain は CUDA 13.4 の機能で、今も設計と開発が続いていると書いています。

vLLM は予備的な評価として、これを MoE の decode に当てました。重みの読み出しで詰まる処理なので、expert の 2 つの全結合層 (FC1 と FC2) の重みを列の方向に半分ずつ割り、2 つの locality domain のそれぞれの SM が、自分の区分にある半分だけを読むようにしています (split-N)。入力と出力は 2 つの区分にまたがったままです。ただし vLLM は、decode では activation のメモリが比較的小さいので、2 つの区分をまたいで読み書きする負担も小さいと説明しています。[vLLM の locality domain の評価](https://vllm.ai/blog/2026-10-09-vera-rubin-preview#locality-domain-support)では、MiniMax M3 という MoE のモデルの形で、FC1 と FC2 の forward のレイテンシーを rank あたりで測り、token 数が小さい設定では locality domain 無しのレイテンシーに対して平均 1.2 倍の speedup でした。tensor 並列が 2 と 4、expert 並列が 2 と 4 でも、212 個の SM を使う backfill mode でも 200 個を使う既定の mode でも傾向はおおむね同じで、通信の時間と、重みの数値形式と vLLM のバージョンは報告にありません。SM の数が NVIDIA の解説の 224 個と違う点は[数字の基準](#数字の基準)で扱います。

## ラック全体の電力の平滑化

Vera Rubin のラックは、電源に蓄電を持って電力の振れを吸い、ピークに合わせて空けていた電力の枠を GPU に回せるようにしました。

![蓄電が電力の尖頭を吸い、空き時間の谷を埋めて、交流の入力電力を平らに保つことを示すグラフ](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/gpu-power-chart.webp)
*[NVIDIA の解説](https://developer.nvidia.com/blog/inside-nvidia-rubin-gpu-architecture-powering-the-era-of-agentic-ai/)の Figure 9 から引用しました。*

![同じ電力の予算で GPU の枠を並べた図。左は DSX MaxLPS が無い場合で Wasted AI Factory Potential と書かれた空きがあり、右は DSX MaxLPS を使う場合で +40% の GPU が足されている](https://developer-blogs.nvidia.com/wp-content/uploads/2026/07/power-budget-comparison-dsx-maxlps-1.webp)
*[NVIDIA の解説](https://developer.nvidia.com/blog/inside-nvidia-rubin-gpu-architecture-powering-the-era-of-agentic-ai/)の Figure 10 から引用しました。比べているのは、DSX MaxLPS を使わない場合と使う場合に同じ電力の予算で置ける GPU の数で、電力の波形ではありません。*

NVIDIA は、この Intelligent Power Smoothing が、平均の消費電力を前の世代の平滑化と比べて約 10% 下げ、50 ms のピークの電力を約 20% 下げると書いています。さらに、AI factory 全体で電力を配る DSX MaxLPS を使うと、効率のよい動作点で、ワークロードの性能への影響を小さく抑えながら、使わない場合と同じ電力の予算に最大 40% 多い GPU を置けるとしています。この 40% は AI factory 全体の話で、Vera Rubin NVL72 のラック単体の値ではありません。

## vLLM が Rubin で動くまで

vLLM は、Blackwell 向けに作ったカーネルを変えずに Rubin で推論を動かし始められました。CUDA 13.4 でのビルドと依存関係の更新は、別の変更として入っています。[vLLM の報告](https://vllm.ai/blog/2026-10-09-vera-rubin-preview)によると、Rubin は Blackwell と同じアーキテクチャの系列で、カーネルを機械語にするときに指定する GPU の種類 (compile target) は sm107 という新しいものですが、Blackwell 系の sm100f 向けに作ったカーネルもそのまま動きます。

そのため、行列積が重い attention や MoE のカーネルは手を入れずに動き、DeepSeek、Kimi、GLM、MiniMax が Rubin で動いています。Rubin 向けに調整した attention、行列積、MoE のカーネルは、推論のカーネルを集めた [FlashInfer](https://github.com/flashinfer-ai/flashinfer) から入ります。毎日の container は CUDA 13.4 と PyTorch 2.15 で作った `vllm/vllm-openai:cu134-nightly` で、各カーネルを有効にする指定は [vLLM の実行手順の付録](https://vllm.ai/blog/2026-10-09-vera-rubin-preview#appendix-running-vllm-on-vera-rubin-nvl72)にまとまっています。

Rubin の公開直後から使えるものと、これから入るものの線引きも報告にあります。2026 年 10 月 9 日の時点で入っているカーネルには、dense の NVFP4 と MXFP4 の行列積、NVFP4 の MoE、FP8 の attention、FP8 の MSA prefill などがあります。今後の作業に挙がっているのは、counted writes を使う MoE の all-to-all (expert ごとに token を各 GPU へ配り直す通信) のカーネル、programmatic dependent launch と Lamport Sync でカーネルの重ね合わせを増やすこと、MoE の層で locality domain を全面的に有効にすることなどです。descriptor の共有、K 次元、score の圧縮を vLLM が今使っているかどうかは、報告にありません。

## vLLM が報告した早期のスループット

vLLM は 2 つのベンチマークで、Vera Rubin NVL72 のスループットを GB200 NVL72 と GB300 NVL72 のそれぞれと比べています。vLLM は AgentX の結果を早期の評価と位置づけ、使える Vera Rubin NVL72 のノードが増えればテストを広げると書いています。

![縦軸が 1 チップあたりの token throughput (tok/s/chip)、横軸が P90 interactivity (tok/s/user) のグラフ。Vera Rubin NVL72 と GB200 NVL72 の線が並び、150 tok/s/user で 5.18 倍、430 tok/s/user あたりで 7.84 倍と注記されている](https://vllm.ai/blog-assets/figures/2026-10-09-vera-rubin-preview/agentx-results.png)
*[vLLM の報告](https://vllm.ai/blog/2026-10-09-vera-rubin-preview)の Figure 5 から引用しました。SemiAnalysis の InferenceX で MiniMax M3 428B を測った結果で、図には Vera Rubin NVL72 と GB200 NVL72 のどちらも Dynamo と vLLM で動かしたとあります。*

1 つめは SemiAnalysis の AgentX です。MiniMax M3 を Vera Rubin NVL72 で動かし、interactivity を揃えた条件 (matched interactivity) で、1 チップあたりのスループットが GB200 NVL72 と比べて最大 7.84 倍でした。図を見ると、この 7.84 倍はユーザー 1 人あたり 430 tok/s あたりの高い interactivity の点で、GB200 側は tensor 並列 8 で動かしています。ユーザー 1 人あたり 150 tok/s の制約の下では 5.18 倍です。モデルの数値形式と vLLM のバージョンは報告に書かれていません。2 つめは [MLPerf Inference](https://mlcommons.org/benchmarks/inference-datacenter/) v6.1 の VLM で、Qwen3-VL-235B-A22B を Vera Rubin NVL72 で、vLLM を推論エンジン、[Dynamo](https://github.com/ai-dynamo/dynamo) を前段のルーターとして動かし、offline と server と interactive のシナリオを通じて GB300 NVL72 と比べて最大 3.7 倍のスループットでした。比較の相手が AgentX では GB200、MLPerf では GB300 なので、2 つの倍率を並べて比べることはできません。

## 数字の基準

公開されている倍率は、どの単位で数えたかで変わります。vLLM の Figure 1 は、2 つのラックの仕様のページと NVIDIA の解説をもとに 1 GPU あたりに直した値を並べているので、基準をそろえて読むのに向いています。

| 項目 | GB200 NVL72 の 1 GPU | Vera Rubin NVL72 の 1 GPU | 比 |
|---|---|---|---|
| HBM の容量 | 186 GB | 288 GB | 1.5 倍 |
| HBM の帯域 | 7.94 TB/s | 19.16 TB/s | 2.4 倍 |
| BF16 (dense) | 2.5 PFLOPS | 4.0 PFLOPS | 1.6 倍 |
| FP8 (dense) | 5.0 PFLOPS | 17.5 PFLOPS | 3.5 倍 |
| NVFP4 の学習 (dense) | 10 PFLOPS | 35 PFLOPS | 3.5 倍 |
| NVFP4 の推論 | 10 PFLOPS (dense) | 50 PFLOPS (sparse) | 5 倍 (条件が違います) |
| NVLink の双方向の帯域 | 1.8 TB/s | 3.0 TB/s | 1.7 倍 |
| トランジスタの数 | 2,080 億個 | 3,360 億個 | 1.6 倍 |

[vLLM の報告](https://vllm.ai/blog/2026-10-09-vera-rubin-preview)の Figure 1 の値から、指数関数の 2 行を除いて書き写しました。比の列は、左の 2 列から計算して四捨五入した値です。この表を読むときに気をつける点が 4 つあります。

1 つめは、NVFP4 の推論の 5 倍です。GB200 側が dense の値、Rubin 側が sparse の値で、図にもこの行だけが例外だという印が付いています。残りの 3 つは、2 本の出典で値そのものが違う項目です。

| Rubin の 1 GPU | NVIDIA の解説 | vLLM の Figure 1 と報告 |
|---|---|---|
| HBM の帯域 | 最大 22 TB/s (Blackwell の 8 TB/s の 2.8 倍) | 19.16 TB/s (GB200 の 7.94 TB/s の 2.4 倍) |
| NVLink の帯域 | NVLink Switch への scale-up で 3,600 GB/s | 双方向で 3.0 TB/s (GB200 の 1.8 TB/s の 1.7 倍) |
| SM の数 | 224 個 | 212 個 (既定では 212 個のうち 200 個を使う) |

食い違いの理由と数え方の関係は、どちらの出典にも書かれていません。帯域なら、22 TB/s は NVIDIA が示す最大の値、19.16 TB/s は vLLM の図のデータが式で出した値 ($16128 \times 4.752 \times 2 / 8 = 19160$ GB/s、各項の意味は書かれていません) として区別し、2 つを混ぜて使わないでください。vLLM は、1.7 倍になった NVLink の帯域が、GPU どうしがデータを渡し合う通信 (collective) を速くすると見込んでいます。

倍率を引用するときは、dense か sparse か、1 GPU かラック全体か、比較の相手が GB200 か GB300 かを一緒に書いてください。どれかが抜けると、読み手は別の条件の値と取り違えます。

## まとめ

Rubin は、計算のスループットを上げる変更に加えて、データの運びと待ち合わせを削る変更を入れた世代です。推論の性能を見積もるときは PFLOPS の値だけで決めず、公開されている倍率は、dense か sparse か、1 GPU かラックか、比較の相手は何かと一緒に読んでください。
