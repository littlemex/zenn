# はじめに

Amazon EKS で、Pod ごとに専用の軽量な VM を[割り当てられるようになりました](https://aws.amazon.com/jp/about-aws/whats-new/2026/11/nitro-sandboxes-eks-ecs-ec2/)。通常の Pod はノードの Linux カーネルを共有しますが、この機能を使う Pod は Nitro Sandbox という VM の中で動き、同じノードの上にいてもカーネルを共有しません。生成 AI が書いたコードや CI のジョブ、利用者が持ち込むスクリプトのように、他人のコードを実行するサービスで、コンテナからの脱出やカーネルの不具合が同じノードの他の利用者に届かないようにするための機能です。

この記事では、仕組みと 2 つのモード isolated と confidential を整理したあと、東京リージョンの EKS で実際に動かし、ノードから何が見えて何が見えないかを確かめます。後半では、使える場所と制限、セキュリティの運用で何が変わるかをまとめます。使い方ごとの動かせる例は、AWS が[公式のサンプル集](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc)として公開しています。

また、セキュリティの運用の節では、sandbox の中を監視する手段が少なかったため筆者が個人で作った、検証用の OSS の [sandbox-guestwatch](https://github.com/littlemex/sandbox-guestwatch/tree/d87645b7190b41b9ea77db2a445821b2be4238f5) を紹介します。AWS の公式のツールやサンプルではありません。

# 通常の Pod が共有しているもの

通常の Pod は、ノードのカーネルを共有しています。コンテナは、[名前空間](https://man7.org/linux/man-pages/man7/namespaces.7.html)と [cgroup](https://man7.org/linux/man-pages/man7/cgroups.7.html) というカーネルの機能で区切られたプロセスにすぎないので、カーネルの不具合やコンテナからの脱出があると、同じノードの他の Pod にまで影響が及びます。

共有していることは [`boot_id`](https://man7.org/linux/man-pages/man5/proc_sys_kernel.5.html) で確かめられます。`boot_id` は、Linux がカーネルを起動するたびに無作為に作る ID で、同じカーネルの上の Pod どうしなら同じ値、別のカーネルなら別の値になります。同じノードの通常の Pod 2 つは `boot_id` がノードと同じで、sandbox の Pod は Pod ごとに別々でした。

![同じノードで、通常の Pod 2 つは boot_id とカーネルが同じで、sandbox の Pod 3 つはそれぞれ別の boot_id と別のカーネルを持つことを並べた図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/0ed37fa99f3fa0/zenn/articles/0ed37fa99f3fa0/shared-kernel.png)

# Nitro Sandbox の仕組み

Nitro Sandbox は、Pod 1 つに VM を 1 つ割り当て、その VM の中でコンテナを動かす仕組みです。以下、この VM を「ゲスト」とも呼びます。ノードの EC2 インスタンス自身も、[Nitro Hypervisor](https://docs.aws.amazon.com/whitepapers/latest/security-design-of-aws-nitro-system/the-nitro-system-journey.html) という AWS のハイパーバイザーの上で動く VM です。Nitro Sandbox の VM は、ノードの中に入れ子で作るのではなく、同じ Nitro Hypervisor がノードとは別の VM として[直接作ります](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing.html)。VM のメモリの仕切りは、ノードの OS ではなく Nitro Hypervisor が受け持ちます。なお Graviton5 では、Nitro Hypervisor のうち VM どうしを隔離する部分を取り出して形式検証した [Nitro Isolation Engine](https://aws.amazon.com/jp/blogs/news/ec2s-formally-verified-isolation-engine-provides-mathematical-assurance-of-virtual-machine-isolation/) が公表されていますが、Nitro Sandbox との関係は公開資料には書かれていません。

[EKS ユーザーガイドの How it works の図](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing.html)をもとに、Pod 1 つが起動するときの部品のつながりと順番を描きました。ノードの [kubelet](https://kubernetes.io/docs/reference/command-line-tools-reference/kubelet/) と [containerd](https://github.com/containerd/containerd) から順に動きます。部品を押すと受け持ちが出ます。

## 試す手順

isolated のモードなら、Pod の定義に足すのは `runtimeClassName` の 1 行です。利用者のコードを動かすなら、後の「2 つのモード」で書く理由で `automountServiceAccountToken: false` も足してください。limits だけを書くと、Kubernetes が requests にも同じ値を入れます。

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-app
spec:
  runtimeClassName: isolated-sandbox
  automountServiceAccountToken: false
  containers:
  - name: main
    image: public.ecr.aws/amazonlinux/amazonlinux:2023
    command: ["sleep", "3600"]
    resources:
      limits:
        cpu: "1"
        memory: 512Mi
```

[eksctl](https://github.com/eksctl-io/eksctl) で [Auto Mode](https://docs.aws.amazon.com/eks/latest/userguide/automode.html) のクラスタを作る例です。

```bash
export CLUSTER_NAME=sandbox-demo
export AWS_REGION=ap-northeast-1
eksctl create cluster --name "$CLUSTER_NAME" --region "$AWS_REGION" --version 1.37 --enable-auto-mode
```

上の Pod を `manifest.yaml` として保存して apply し、`boot_id` を見ます。同じノードの通常の Pod と比べるか、同じノードの sandbox の Pod 2 つで値が互いに違うことを見ると、sandbox の中で動いていると分かります。通常の Pod は別のノードに置かれることがあり、ノードが違えば `boot_id` は必ず違うので、同じノードで比べます。

```bash
kubectl apply -f manifest.yaml
kubectl wait pod/my-app --for=condition=Ready --timeout=300s
kubectl exec my-app -- cat /proc/sys/kernel/random/boot_id
```

Pod が Pending のままなら、`kubectl describe pod` のイベントと、ノードの `eks.amazonaws.com/nitro-sandbox` のラベルを見ます。動かせる場所の条件は[使える場所と制限](#使える場所と制限)にまとめました。

## Deployment と NodePool の書き方

Deployment などで Pod を作る場合は、`runtimeClassName` と `sandbox.amazonaws.com/` で始まる annotation を、Pod テンプレート `spec.template` の側に書いてください。Deployment 自身の `metadata.annotations` に書いても Pod には写されません。

この記事では、試すインスタンスタイプを固定するため、Graviton5 の m9g.xlarge だけを使う次の [NodePool](https://karpenter.sh/docs/concepts/nodepools/) を足しました。比較用の x86 の m8i.xlarge 用も同じ形です。Pod には `nodeSelector` に `pool: graviton5` を書いて、この NodePool のノードに置きました。

```yaml
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: graviton5
spec:
  template:
    metadata:
      labels:
        pool: graviton5
    spec:
      nodeClassRef:
        group: eks.amazonaws.com
        kind: NodeClass
        name: default
      requirements:
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["on-demand"]
        - key: node.kubernetes.io/instance-type
          operator: In
          values: ["m9g.xlarge"]
```

# 2 つのモード

[EKS ユーザーガイドの Modes の節](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing.html#sandboxing-modes)は、2 つのモードの違いを、何を信頼し何を守るかで定めています。下の表の 3 行目以降は、そこと [confidential の設定のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-confidential-setup.html)にある組み込みの設定の既定値です。

| 項目 | isolated-sandbox | confidential-sandbox |
|---|---|---|
| 信頼の前提 | ノードを信頼し、ゲストは信頼しない | ノードを信頼せず、ゲストだけを信頼の境界にする |
| 守るもの | 乗っ取られたワークロードから、ノードと他の Pod を守る | ノードの管理者や乗っ取られたノードから、ワークロードのデータを守る |
| Cedar policy | 無くてもよい。付けなければ、すべてを許す組み込みの既定が使われる | 必須。イメージの digest、引数、環境変数、マウントなどを固定する |
| exec と stdin | 使える | 拒否される |
| ログ | 読める | 既定では読める (拒否する設定もある) |
| コンテナの書き込み層 | 暗号化しない | VM の中で暗号化する |
| Kubernetes の ServiceAccount トークン | isolated のプロファイルで作った Cedar policy なら渡らない。Cedar policy を付けないと渡る | 渡る |

書き込み層は、イメージには無く、コンテナが動いている間に作ったり書き換えたりしたファイルが入る領域です。

:::message
ServiceAccount のトークンは、Pod の中から Kubernetes の API を呼ぶための認証情報です。公式の説明では isolated はこれを VM に渡しませんが、実機では Cedar policy を付けない Pod には渡り、それで API サーバーに認証できました。渡らなかったのは、後述の生成ツール [`eks-nitro-sandbox-genpolicy`](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-download-binaries.html) (以下 genpolicy) に `--profile isolated` を付けて作った Cedar policy を付けた Pod です。利用者のコードを動かす Pod には、どちらのモードでも `automountServiceAccountToken: false` を書いてください。
:::

## confidential で秘密を受け取る仕組み

confidential はノードを信頼しないので、秘密のデータは平文でノードを通さず、平文が現れるのはノードから読めない sandbox の VM のメモリの中だけにします。VM のメモリをノードから読めなくするのは Nitro Hypervisor の隔離で、そのうえで Nitro は、その VM が承認した Cedar policy で起動したことを証明する仕組みを提供します。

- [PCR](https://docs.aws.amazon.com/enclaves/latest/user/set-up-attestation.html) (platform configuration register) は、起動時に読み込んだものの計測値です。名前はレジスタですが CPU のレジスタではなく、Nitro Enclaves と同じく VM に付く [Nitro Secure Module](https://github.com/aws/aws-nitro-enclaves-nsm-api) というデバイス `/dev/nsm` が保持します。VM は自分の Cedar policy のハッシュを PCR17 に記録します。
- [アテステーション](https://docs.aws.amazon.com/kms/latest/developerguide/services-nitro-enclaves.html)は、PCR の値と VM の中で作った鍵の組の公開鍵に、Nitro Hypervisor が署名した文書です。[セキュリティモデルのページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-security-model.html)によると、ノードはこれを偽れません。

[KMS](https://docs.aws.amazon.com/kms/latest/developerguide/overview.html) は、アテステーションの PCR の値がキーポリシーの条件に合うときだけ、復号した平文をその公開鍵で包んで返します。包みを開ける秘密鍵は VM の中にしか無いので、途中のノードには読めません。図の上の切り替えで、承認した Pod、環境変数を 1 つ変えた Pod、同じ IAM ロールの通常の Pod の 3 つの場合を選べ、どれも実機で試した結果です。

キーポリシーの条件は、たとえば次の形です。

```json
"Condition": {
  "StringEqualsIgnoreCase": {
    "kms:RecipientAttestation:PCR17": "128d66d847a8767e70b52b23cfe1839ab55a45512e5087bc51dbc92a2d5d06d5197980ede432ee0f6b3192204dc2f5fe",
    "kms:RecipientAttestation:PCR8:ServiceName": "eks.amazonaws.com"
  }
}
```

PCR17 は Cedar policy のハッシュで、genpolicy が予測値を出します。PCR8 は、ゲストが EKS の署名したものであることを確かめる条件です。キーポリシーの書き方と注意は、[公式のサンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc/examples/confidential)を参照してください。

## Cedar policy の作り方

Cedar policy は、AWS が署名して配布している生成ツール [`eks-nitro-sandbox-genpolicy`](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-download-binaries.html) で Pod の定義から作ります。PCR17 の予測値も出るので、Pod を動かす前にキーポリシーの条件を書けます。

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-conf
spec:
  runtimeClassName: confidential-sandbox
  enableServiceLinks: false
  containers:
  - name: main
    image: public.ecr.aws/amazonlinux/amazonlinux:2023
    command: ["sleep", "3600"]
    resources:
      limits:
        cpu: "1"
        memory: 512Mi
  automountServiceAccountToken: false
```

これを `conf.yaml` として保存して次のように実行すると、Cedar policy の base64 の文字列と PCR17 の予測値が出ます。base64 の文字列を Pod の `sandbox.amazonaws.com/policy` という annotation に付けて apply します。

```bash
eks-nitro-sandbox-genpolicy --profile confidential conf.yaml
```

作るときに守ることは次の 3 つです。

- AWS の認証情報を使う Pod は、[EKS Pod Identity](https://docs.aws.amazon.com/eks/latest/userguide/pod-identities.html) なら `--with-pod-identity`、[IRSA](https://docs.aws.amazon.com/eks/latest/userguide/iam-roles-for-service-accounts.html) なら `--with-irsa` を付けてください。付けないと認証情報が渡らず、AWS の呼び出しが失敗します。
- `enableServiceLinks: false` を書いてください。書かないとツールがエラーで止まります。
- webhook がサイドカーを足すなどで定義が変わるなら、変わったあとの最終的な定義から作ってください。イメージを変えたときも、Cedar policy、キーポリシーの PCR17、Pod を作り直してください。

イメージを digest ではなく [AWS Signer](https://docs.aws.amazon.com/signer/latest/developerguide/Welcome.html) の署名で信頼して、作り直しを減らす方法もあります。今回は試していないので、[公式のサンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc/examples/confidential/signer-policy)を参照してください。

## sandbox のカーネルが止まっても、ほかの sandbox とノードは止まらない

| 項目 | 内容 |
|---|---|
| なぜ | 通常の Pod はカーネルを共有するので、1 つの Pod がカーネルを止めるとノードごと止まる。sandbox ならそれが防げるかを知りたい |
| 何を | sandbox の中でカーネルを意図的に止め、同じノードの他の sandbox とノードが動き続けるかを見た |
| 結果 | 他の sandbox 2 つもノードも止まらず、`boot_id` も変わらなかった |

## ノードから VM のメモリを読もうとすると固まる

| 項目 | 内容 |
|---|---|
| なぜ | ノードの root が、sandbox の VM のメモリを読めるかを知りたい |
| 何を | ノードの firecracker のプロセスにある、VM のメモリにあたる領域 (`/dev/nitro_enclaves` をマップした領域) を `/proc` 経由で読んだ |
| 結果 | 読み取りが 10 分経っても返らず、同じノードの通常の Pod への exec まで固まったので、ノードを作り直した |

プロセスのメモリを走査する監視エージェントをノードに入れているなら、sandbox のノードに載せる前に検証用のノードで確かめてください。

## 起動にかかる時間

| 項目 | 内容 |
|---|---|
| なぜ | sandbox は Pod ごとに VM を起動するので、Pod の起動がどれだけ遅くなるかを知りたい |
| 何を | 通常の Pod、isolated、confidential を各 10 回作り、準備完了までの時間を測った |
| 結果 | 通常の Pod が 0〜1 秒、isolated が 3〜4 秒 (中央値 3.5 秒)、confidential が 5〜8 秒 (中央値 7 秒) |

## 帯域とパケット数の上限

| 項目 | 内容 |
|---|---|
| なぜ | 既定の上限 (100 Mbps、毎秒 1,500 個) が実際にどう効き、上げるとどこまで出るかを知りたい |
| 何を | 上限の設定を変え、TCP と UDP の帯域を測った |
| 結果 | 下の表のとおり。UDP は帯域だけ上げてもパケット数の上限で止まるので、上げるときは両方を上げる。TCP はドキュメントでは帯域だけ上げても約 100 Mbps のままとされているが、1 回の測定で 750 Mbps 出た |

| sandbox の設定 | sandbox から送る TCP | sandbox が受ける TCP | sandbox から送る UDP |
|---|---|---|---|
| 既定のまま | 99.9 Mbps | 99.9 Mbps | 17.7 Mbps (毎秒約 1,580 個) |
| 帯域だけ 1G に上げる | 750 Mbps | 690 Mbps | 18.2 Mbps (毎秒約 1,620 個) |
| 帯域を 1G、パケット数を毎秒 15,000 個に上げる | 997 Mbps | 998 Mbps | 176 Mbps (毎秒約 15,700 個) |

## Pod ごとのセキュリティグループは sandbox の Pod にも効く

| 項目 | 内容 |
|---|---|
| なぜ | [Pod ごとのセキュリティグループ](https://docs.aws.amazon.com/eks/latest/userguide/auto-sgp.html)が Auto Mode でも[使えるようになった](https://aws.amazon.com/jp/about-aws/whats-new/2026/11/amazon-eks-auto-mode-security-groups-for-pods/)が、sandbox の Pod に効くかはドキュメントに書かれていない |
| 何を | 外への通信を許さないセキュリティグループを、sandbox の Pod と通常の Pod に付け、付けない sandbox の Pod と比べた |
| 結果 | 付けた 2 つの Pod は、sandbox でも通常でも外への TCP が 3 回とも止まり、名前解決だけは通った。付けない sandbox の Pod は外に届いた |

## CPU の取り分

| 項目 | 内容 |
|---|---|
| なぜ | VM にすると CPU の処理量が落ちるか、同じノードに並べたときに落ちるかを知りたい |
| 何を | 同じ CPU の処理を、通常の Pod と sandbox の Pod で、1 個と 4 個同時に回して比べた |
| 結果 | 1 個では差が測定のばらつきに収まった。4 個同時では sandbox が 3〜6% 低かった |

| ノード | 通常 1 個 | sandbox 1 個 | 通常 4 個 (合計) | sandbox 4 個 (合計) |
|---|---|---|---|---|
| m9g.xlarge | 1.00 | 0.95 | 3.94 | 3.75 |
| m8i.xlarge | 1.00 | 0.99 | 2.07 | 1.96 |

## カーネルが止まっても Pod は Running のまま

| 項目 | 内容 |
|---|---|
| なぜ | sandbox の中のカーネルが止まったとき、Kubernetes が気づいて Pod を作り直すかを知りたい |
| 何を | sandbox の中のカーネルを止め、liveness probe なし、exec の probe、HTTP の probe の 3 通りで、再起動されるかを見た |
| 結果 | Pod は `Running` で準備完了のまま残った。気づけたのは HTTP の probe だけで、約 50 秒で再起動した。probe なしは約 6 分、exec の probe は状態不明の「エラー」扱いで 471 秒経っても再起動されなかった |

ネットワークのある sandbox の Pod には HTTP の liveness probe を付けてください。公式はネットワークを切った Pod に exec の probe を勧めていますが、この止まり方は exec の probe では検知できませんでした。

# 使える場所と制限

2026 年 11 月 13 日時点のドキュメントの記載で、主な出典は [isolated の始め方のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-isolated-setup.html)と[制限事項のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-limitations.html)です。EC2 から直接使うときの direct モードは別物で、この記事の内容は当てはまりません ([EC2 のユーザーガイド](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/amazon-ec2-nitro-sandboxes.html))。

| 項目 | 対応 |
|---|---|
| EKS Auto Mode | 使える。RuntimeClass と sandbox のノードが自動で用意される |
| EC2 のノードグループ | 使える。sandbox 用の AMI、[Nitro Enclaves](https://docs.aws.amazon.com/enclaves/latest/user/nitro-enclave.html) の有効化 (`EnclaveOptions.Enabled=true`)、RuntimeClass、ノードのラベルを自分で用意する |
| Fargate、Hybrid Nodes | 使えない (Fargate は実機でも Pending のまま) |
| Kubernetes | 1.36 以降 |
| GPU などのデバイス | 使えない |
| VM の大きさ | limits ではなく、requests と RuntimeClass の上乗せ分 (isolated は 256Mi、confidential は 512Mi) で決まり、あとから変えられない。必ず requests を書く |
| `hostNetwork: true` | 起動しない |
| 1 つのノードの sandbox の数 | 個数も vCPU の合計も、ノードの vCPU の数の 5 倍まで |
| ネットワークの既定の上限 | 帯域 100 Mbps、毎秒 1,500 パケット。Pod の annotation で変える (下の一覧) |
| ネットワークを切る | `sandbox.amazonaws.com/network-isolated: "true"` で、ネットワークのデバイスが無い状態で起動する。vsock は残るので完全な遮断ではない |

| `hostPID: true`、`hostIPC: true` | 起動するが、見えるのはその VM の中だけ | 制限事項のページ、実機 |
| IMDS | リージョン、アベイラビリティーゾーンなど 5 つの項目だけ。インスタンス ID と IAM の認証情報は返らないので、AWS の認証情報は Pod Identity で渡す | 制限事項のページ、実機 |
| ユーザー名前空間 | `hostUsers: false` の Pod は起動しない。VM の中の `max_user_namespaces` は 0 で、[bubblewrap](https://github.com/containers/bubblewrap) のようなツールはそのままでは動かない | 制限事項のページ、実機 |
| ネットワークを切った Pod | ログと exec は使える。Pod Identity の認証情報、暗号化したイメージ、署名の確認、HTTP と TCP の probe、EFS と S3 Files は使えない。EBS は使える | [ネットワーク分離のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-network-isolation.html) |
| EBS のボリューム | 複数の Pod で共有できず `ReadWriteOncePod` を使う。動いている Pod のボリュームは拡張できない | 公式のサンプル |
| kubelet の CPU Manager の `static` | 効かない | 制限事項のページ |
| `kubectl port-forward` | `127.0.0.1` だけで待ち受けるサーバーには届かない | 制限事項のページ |
| `emptyDir` と書き込み層の使用量 | kubelet からは 0 に見える。上限は `ephemeral-storage` の requests と limits で決める | 制限事項のページ |
| 一部だけ暗号化したイメージ | 使えない。暗号化するなら全部の層 | 制限事項のページ |
| Ubuntu のノード | sandbox の Pod に `appArmorProfile.type: Unconfined` が要る | 公式のサンプル |
| スナップショットからの復元、ライブマイグレーション | 使えない | 制限事項のページ |

Pod ごとの既定の上限は、Pod の annotation で変えられます ([資源の上限のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-resource-isolation.html))。接続数を除いては `"disabled"` で外せますが、`"0"` を指定すると Pod が起動しません。

| 上限 | 既定 | annotation (`sandbox.amazonaws.com/` の後ろ) |
|---|---|---|
| 帯域 (受信と送信) | 100 Mbps | `ingress-bandwidth`、`egress-bandwidth` |
| パケット数 (受信と送信) | 毎秒 1,500 個 | `ingress-packets-per-second`、`egress-packets-per-second` |
| DNS | 毎秒 100 クエリ (512 まで) | `dns-packets-per-second` |
| 同時の外向き接続 | IP のファミリーごとに 4,096 (無効にはできない) | `conntrack-limit` |
| 書き込み層のディスク | 400 Mbps、1,500 IOPS | `overlay-disk-bandwidth`、`overlay-disk-iops` |
| ログ | 2 Mbps | `log-bandwidth` |
:::

# セキュリティ運用で何が変わるか

sandbox が防ぐのは、VM の中のコードがノードのカーネルやメモリに直接触ることです。テナントどうしの通信、認証情報、共有のストレージ、資源の取り合いは、別の対策で守ります。ノード側の firecracker や仮想デバイスの処理は VM から入力を受け取るので、攻撃される面として残ります。前提は、信頼できないのはコンテナの中のコードで、Pod の定義は信頼できる人が書くことです。

| 層 | sandbox で変わること |
|---|---|
| 隔離 | 境界が共有のカーネルから Nitro Hypervisor に移る |
| 監査ログ | [Kubernetes の監査ログ](https://docs.aws.amazon.com/eks/latest/userguide/control-plane-logs.html)と [CloudTrail](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-user-guide.html) はノードの外で記録されるので変わらない。どちらも VM の中で実行されたコマンドの記録ではない |
| ログとメトリクス | kubelet を通るので、[CloudWatch のエージェント](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/Container-Insights-setup-EKS-addon.html)などで集められる ([監視のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-observability.html)) |
| ノードのランタイム監視 | sandbox の中は見えない。監視のページは [GuardDuty のランタイム監視](https://docs.aws.amazon.com/guardduty/latest/ug/runtime-monitoring.html)の agent が sandbox の中を観察できないと書いており、実機でもノードから見えたのは firecracker と shim だけだった |
| Pod の中の監視 | 同じ Pod に置いた監視用のコンテナから、VM の中のプロセスやファイル、通信が見える。ただし使える道具は限られる (次の節) |
| ネットワーク | [NetworkPolicy](https://kubernetes.io/docs/concepts/services-networking/network-policies/) も [Pod ごとのセキュリティグループ](https://docs.aws.amazon.com/eks/latest/userguide/auto-sgp.html)も VM の外で効くので、sandbox の中から外せない (次の節) |

隔離と検知は別の軸の対策です。隔離は侵害が Pod の外へ広がる範囲を狭め、検知は侵害に気づくまでの時間を縮めます。sandbox は前者を強めますが、後者の代わりにはなりません。アプリの脆弱性を突かれた攻撃者は、sandbox を抜け出さなくても、Pod が正当に持つ IAM の権限、データベースへの接続、シークレットで目的を果たせるからです。

広い権限や機密データを持ち、長く動き続ける業務アプリを sandbox に載せるなら、検知の代わりになる対策を組み合わせてください。外への通信を既定で拒否する、IAM の権限を最小にして認証情報の有効期限を短くする、ルートのファイルシステムを読み取り専用にする、CloudTrail と監査ログの異常を見張る、アプリ自身に操作の記録を残させる、Pod を短い時間で作り直す、といった対策です。sandbox が最も向いているのは、利用者のコードや AI エージェントの道具の実行のように、中で動くコードを信頼できず、短い時間だけ動き、権限の小さい処理です。

## Pod の中から監視する

ノードから見えないなら、Pod の中に監視用のコンテナを置くことになります。同じ Pod に特権付きのコンテナを置き、Pod に `hostPID: true` を付けると、その VM の中のすべてのプロセスが見えます。sandbox の中の `hostPID` は、ノードではなくその VM の PID 名前空間だからです。ただし sandbox のカーネルには、多くの監視の道具が前提にする仕組みがありません。実機で調べた結果を、仕組みごとにまとめます。

| 仕組み | sandbox の中 | その仕組みに頼る道具の例 |
|---|---|---|
| カーネルの型情報 [BTF](https://docs.kernel.org/bpf/btf.html) と、kprobe、tracepoint、LSM の eBPF | 使えない | [Falco](https://github.com/falcosecurity/falco)、[Tetragon](https://github.com/cilium/tetragon) |
| audit | 使えない | [auditd](https://github.com/linux-audit/audit-userspace) |
| ノードに置く agent | 中が見えない | [GuardDuty のランタイム監視](https://docs.aws.amazon.com/guardduty/latest/ug/runtime-monitoring.html) |
| [fanotify](https://man7.org/linux/man-pages/man7/fanotify.7.html) | マウント単位の登録は失敗。登録の仕方によっては使える | [fatrace](https://github.com/martinpitt/fatrace) は失敗、[ClamAV](https://github.com/Cisco-Talos/clamav) の clamonacc は動いた |
| `/proc`、パケットの捕捉、ファイルの走査 | 使える | [osquery](https://github.com/osquery/osquery)、[Auditbeat](https://www.elastic.co/docs/reference/beats/auditbeat)、[Wazuh](https://github.com/wazuh/wazuh)、[Suricata](https://github.com/OISF/suricata) |
| proc connector、cgroup の `sock_addr` の eBPF、inotify、conntrack | 使える | 次の節の sandbox-guestwatch |

使える側の仕組みのうち、[proc connector](https://github.com/torvalds/linux/blob/v6.18/include/uapi/linux/cn_proc.h) はプロセスの実行をカーネルが知らせる仕組みで、cgroup に付ける [`sock_addr` の eBPF プログラム](https://docs.ebpf.io/linux/program-type/BPF_PROG_TYPE_CGROUP_SOCK_ADDR/)は接続と UDP の送信のたびに呼ばれ、BTF が無くても動きます。ファイルの変化は [inotify](https://man7.org/linux/man-pages/man7/inotify.7.html) が、新しい通信の宛先は [conntrack](https://conntrack-tools.netfilter.org/) が知らせます。

監視用のコンテナには特権と `hostPID: true` が要り、どちらも [Pod Security](https://kubernetes.io/docs/concepts/security/pod-security-standards/) の baseline に反するので、admission で例外を設け、requests も書いてください。監視はワークロードと同じ VM の中にいて、`hostPID` は Pod の全体に効くので、root で動くワークロードからは止められるはずです (試していません)。そのため監視は気づくための仕組みと考え、記録はすぐに VM の外へ送ってください。confidential では、その記録が信頼しないノードを通ります。別のコンテナのファイルは `/proc/<PID>/root` から見えますが、PID ごとのパスなので、コンテナが作り直されたら指し直してください。

## sandbox-guestwatch

上で動いた仕組みだけを使って、sandbox の中を記録する小さなエージェントを作り、[sandbox-guestwatch](https://github.com/littlemex/sandbox-guestwatch/tree/d87645b7190b41b9ea77db2a445821b2be4238f5) として Apache-2.0 で公開しました。筆者が個人で作った検証用の道具で、AWS の公式のツールやサンプルではなく、AWS のサポートの対象でもありません。

| 記録するもの | 使う仕組み |
|---|---|
| プログラムの実行と引数 | proc connector |
| 外への接続と UDP の送信、そのプロセス | cgroup の `connect4`、`connect6`、`sendmsg4`、`sendmsg6` の eBPF |
| ファイルの作成、書き込み、移動 | inotify |

eBPF のプログラムは Go の中で命令を組み立てるので、BTF も C のビルド環境も要りません。別のコンテナのファイルは、そのコンテナのルートを指す fd から [`openat2`](https://man7.org/linux/man-pages/man2/openat2.2.html) でたどるので、コンテナの中のシンボリックリンクにも惑わされません。ファイルは、fanotify がファイルシステム単位で登録できなかったので inotify で見ます。依存は [`cilium/ebpf`](https://github.com/cilium/ebpf) と [`golang.org/x/sys`](https://pkg.go.dev/golang.org/x/sys) の 2 つです。使うときは、[例の Pod](https://github.com/littlemex/sandbox-guestwatch/blob/d87645b7190b41b9ea77db2a445821b2be4238f5/deploy/example-pod.yaml) のようにサイドカーとして置いてください。イメージは [README](https://github.com/littlemex/sandbox-guestwatch/blob/d87645b7190b41b9ea77db2a445821b2be4238f5/README.md) の手順で自分で作ってください。

```yaml
spec:
  runtimeClassName: isolated-sandbox
  hostPID: true
  containers:
    - name: guestwatch
      image: ${GUESTWATCH_IMAGE}
      args: ["--require=exec,net,file"]
      securityContext:
        privileged: true
```

記録は 1 件 1 行の JSON で標準出力に出るので、コンテナのログを集める仕組みでそのまま集められます。規則に当たった記録には印が付きます。

```json
{"v":1,"type":"exec","container":{"id":"e4964251…"},"process":{"pid":1902,"uid":1000,"exe":"/tmp/fastcurl","cmdline":["/tmp/fastcurl","--version"]},"rules":["exec_from_temp_dir"]}
{"v":1,"type":"connect","container":{"id":"e4964251…"},"process":{"pid":1884,"comm":"bash"},"net":{"proto":"udp","dst":"192.0.2.20","port":9999,"count":499,"repeat":true}}
{"v":1,"type":"file","container":{"id":"de48706c…"},"file":{"path":"/usr/local/bin/evil","op":"create"},"rules":["write_to_binary_dir"]}
```

筆者の書いた[試験](https://github.com/littlemex/sandbox-guestwatch/blob/d87645b7190b41b9ea77db2a445821b2be4238f5/test/e2e/run.sh)を、x86 のノードの isolated の sandbox で流し、20 項目がすべて通りました。確かめたのは、`/tmp` に置いてすぐ終わる実行ファイル、500 回の UDP の送信が 1 行目と「残り 499 回」の 2 行にまとまること、IPv4 を IPv6 の形で書いた宛先、コンテナの中のシンボリックリンクの先への書き込み、`/usr/local/bin` へのディレクトリの移動、コンテナの作り直しへの追従です。

外から入る接続、raw socket、ファイルの読み取り、ファイルの記録のプロセス、エージェントが起動する前の動き、システムコール単位の記録は取れません。高い負荷のときの取りこぼしと、Graviton のノード、confidential は試していません。

## 通信を制限するときの注意

通信を制限する仕組みは 2 つあり、どちらも VM の外で効きます。NetworkPolicy はノードが強制し、[Pod ごとのセキュリティグループ](https://docs.aws.amazon.com/eks/latest/userguide/auto-sgp.html) (SecurityGroupPolicy) は Pod ごとに付く EC2 のネットワークインターフェースで通信を評価します。後者は sandbox の Pod にも効きました (実機で確かめたことの節)。ただし、図の 2〜4 の通信はどちらでも止まりません。

![sandbox の Pod の外への通信はセキュリティグループと NetworkPolicy で止まるが、CoreDNS を通る DNS、ノードと hostNetwork の Pod からの通信、kubelet の probe と Pod Identity の通信は止まらないことを示した図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/0ed37fa99f3fa0/zenn/articles/0ed37fa99f3fa0/network-rules.png)
*通信の規則が効く場所と、規則を通り抜ける通信*

Auto Mode では、NetworkPolicy は強制を有効にするまで効きません。実機でも、外への通信をすべて拒否する NetworkPolicy を入れても HTTPS は通り、次の ConfigMap を作ると、作り直した sandbox の Pod の通信が止まりました。

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: amazon-vpc-cni
  namespace: kube-system
data:
  enable-network-policy-controller: "true"
```

図の 2 のとおり、クラスタの DNS は外の名前を引くので、問い合わせの名前に載せた持ち出しは、外への通信をすべて拒否しても止まりません。利用者のコードには、ネットワークを切るか、引ける名前を絞る DNS のフィルタと `dns-packets-per-second` の引き下げを組み合わせてください。図の 3 のとおり、同じノードの `hostNetwork` の Pod からは sandbox の中のポートに届くので、VM の中のサービスにも認証を付けてください。外への通信を既定で拒否するなら、Pod Identity の認証情報の取得先 `169.254.170.23` と DNS を許してください。

[公式のサンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc)には、Pod の起動の直後に NetworkPolicy がまだ効いていない時間があった例が載っています。今回は起動直後の時間を確かめておらず、強制を有効にした後は Pod を作り直して試したので、既存の Pod に効くかも確かめていません。短い時間だけ動く処理では起動直後が実行の大半なので、通信が要らないならネットワークを切る設定を使ってください。

## 利用者のコードを実行するサービスの組み立て

Pod の定義はサービスの側で作り、利用者からはコードなどの入力だけを受け取ります。利用者が通常の Pod や特権、`hostPath` を指定できたり、exec できたりすると、境界を回り込めるからです。Pod を作る経路と変える経路は [RBAC](https://kubernetes.io/docs/reference/access-authn-authz/rbac/) で絞り、`runtimeClassName` の付け忘れなどの定義の中身は admission control で強制してください。実行環境は isolated の sandbox にし、通信が要らない処理はネットワークも切ります。中が止まっても Pod は準備完了のまま残ることがあるので、実行時間の上限、外からの死活の確認、強制的な削除と作り直しの手順も組み合わせてください。

Pod の中には、もう 1 つの閉じ込めの層も置けます。[公式のサンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc/examples/subagent-security)は、エージェントが起動する道具のプロセスを、sandbox の中で [Landlock](https://docs.kernel.org/userspace-api/landlock.html) や [seccomp](https://man7.org/linux/man-pages/man2/seccomp.2.html) でさらに絞る例を挙げています。Nitro の境界は Pod とノードの間にあり、Pod の中のプロセスどうしは分けないからです。

# 誤解しやすい点

confidential が守るのは、VM のメモリと CPU の状態、暗号化した書き込み層などです。ワークロード自身が漏らすものと、ノードが握っている入出力は守れません。[セキュリティモデルのページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-security-model.html)が挙げている例を、2 つに分けてまとめます。

| ワークロード自身が漏らすもの | 理由 |
|---|---|
| 標準出力や終了メッセージに書いた秘密 | ログを許可していれば、ノードがそのまま受け取る。終了メッセージ (`/dev/termination-log`) はログとは別の操作で、既定ではどちらのモードでも読める |
| EFS や EBS に平文で書いたデータ | ノードは同じファイルシステムをマウントでき、EBS は中身を直接読める |
| 実行時に読み込んだ信頼できないコード | 起動後に取ってきたコードは Cedar policy の固定の外にある |

| ノードができること | 理由 |
|---|---|
| 暗号化していないイメージの層を読む | 層はノードを通って VM に渡される。[イメージの暗号化](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-encrypted-images.html)をしても、manifest と設定 (`ENV` など)、Pod の定義の引数と環境変数は平文のまま |
| ConfigMap、Secret、projected volume の中身を差し替える | Cedar policy が固定するのはマウントの場所で、中身ではない。CA 証明書のような信頼の起点は、digest で固定したイメージに入れる |
| 暗号化していない通信を見たり書き換えたりする | TLS で相手の証明書を確かめ、Pod の中の通信は `localhost` ではなく `127.0.0.1` を使う (`/etc/hosts` はノードが書く) |
| EFS の接続先を差し替える | genpolicy が作る Cedar policy はファイルシステムの ID を固定しないので、`context.file_system_id` を固定する permit を書き足す |
| Pod Identity の認証情報や、[Secrets Store CSI Driver](https://secrets-store-csi-driver.sigs.k8s.io/) で渡した秘密を読む | どちらもノードを通って渡される |
| サービスを止める、時刻や DNS や配置のメタデータを偽る | ノードが提供している |

ほかに、次の点も誤解しやすい点です。

- Pod の定義は信頼する入力として扱われます。信頼できないイメージを動かす機能で、信頼できない人が書いた Pod の定義を受け付ける機能ではありません。
- KMS のキーポリシーに PCR の条件を書かなければ、計測値は記録されるだけで誰も確かめません。PCR8 の署名者の条件が示すのは EKS が署名したゲストのイメージであることで、バージョンの新しさには触れていません。
- [EKS ユーザーガイド](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing.html)によると、AWS が受け持つのは Nitro Hypervisor、sandbox の境界、ゲストのシステムイメージで、コンテナのイメージ、Cedar policy、KMS のキーポリシー、アプリケーションのコードは利用者が受け持ちます。Auto Mode を使わず自分で AMI を作るなら、ノードのカーネルやランタイムの更新も自分で行います。
- 隔離は性能の予約ではありません。vCPU は時分割で共有され、ノードの vCPU の数を超えて割り当てられます。

# まとめ

isolated なら `runtimeClassName` の 1 行と requests で Pod は専用のカーネルの VM で動き、confidential では試した 3 つの場合で KMS の復号を承認した Cedar policy の Pod だけに絞れました。一方でノードの監視からは中が見えなくなるので、osquery、Wazuh、Suricata、sandbox-guestwatch のような Pod の中で動いた道具と、監査ログ、ネットワークの記録を組み合わせる設計が要ります。
