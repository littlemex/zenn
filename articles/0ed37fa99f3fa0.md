# はじめに

Amazon EKS で、Pod ごとに専用の軽量な VM を[割り当てられるようになりました](https://aws.amazon.com/jp/about-aws/whats-new/2026/11/nitro-sandboxes-eks-ecs-ec2/)。通常の Pod はノードの Linux カーネルを共有しますが、この機能を使う Pod は Nitro Sandbox という VM の中で動き、同じノードの上にいてもカーネルを共有しません。生成 AI が書いたコードや CI のジョブ、利用者が持ち込むスクリプトのように、他人のコードを実行するサービスで、コンテナからの脱出やカーネルの不具合が同じノードの他の利用者に届かないようにするための機能です。

この記事では、仕組みと 2 つのモード isolated と confidential を整理したあと、東京リージョンの EKS で実際に動かし、ノードから何が見えて何が見えないかを確かめます。後半では、使える場所と制限、セキュリティの運用で何が変わるかをまとめ、sandbox の中を監視するために作った OSS の [sandbox-guestwatch](https://github.com/littlemex/sandbox-guestwatch/tree/d87645b7190b41b9ea77db2a445821b2be4238f5) を紹介します。使い方ごとの動かせる例は、AWS の[公式のサンプル集](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc)にまとまっています。

| 確かめたこと | 結果 | 節 |
|---|---|---|
| 同じノードの Pod どうしでカーネルが分かれるか | sandbox ごとに別のカーネルが起動していた | [カーネルとプロセス](#カーネルとプロセスが分かれている) |
| ノードの特権付きの Pod からメモリやディスクを探せるか | `/proc` から読めた範囲に、メモリの中身は無かった。書き込み層のディスクの中身は isolated では見つかり、confidential では見つからなかった | [ノードから探したもの](#ノードから探したもの) |

| ネットワークを切る設定 | VM の外とつながるネットワークインターフェースが無い状態で起動した | [ネットワークを切る](#ネットワークを切る) |

# 通常の Pod が共有しているもの

通常の Pod は、ノードのカーネルを共有しています。コンテナは、名前空間と cgroup というカーネルの機能で区切られたプロセスにすぎないので、カーネルの不具合やコンテナからの脱出があると、同じノードの他の Pod にまで影響が及びます。

共有していることは、Linux が起動のたびに振る `boot_id` で確かめられます。同じノードの通常の Pod 2 つは `boot_id` とカーネルのビルドがノードと同じで、sandbox の Pod は Pod ごとに別々でした。カーネルの版の番号はノードと同じになることもあるので、見分けるのは `boot_id` とビルドです。

![同じノードで、通常の Pod 2 つは boot_id とカーネルが同じで、sandbox の Pod 3 つはそれぞれ別の boot_id と別のカーネルを持つことを並べた図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/0ed37fa99f3fa0/zenn/articles/0ed37fa99f3fa0/shared-kernel.png)
*同じ m9g.xlarge ノードで、各 Pod の中から読んだ boot_id とカーネルの版*

# Nitro Sandbox の仕組み

Nitro Sandbox は、Pod 1 つに VM を 1 つ割り当て、その VM の中でコンテナを動かす仕組みです。以下、この VM を「ゲスト」とも呼びます。ノードの EC2 インスタンス自身も、Nitro Hypervisor という AWS のハイパーバイザーの上で動く VM です。Nitro Sandbox の VM は、ノードの中に入れ子で作るのではなく、同じ Nitro Hypervisor がノードの隣に[直接作ります](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing.html)。VM のメモリの仕切りは、ノードの OS ではなく Nitro Hypervisor が受け持ちます。なお Graviton5 では、Nitro Hypervisor のうち VM どうしを隔離する部分を取り出して形式検証した [Nitro Isolation Engine](https://aws.amazon.com/jp/blogs/news/ec2s-formally-verified-isolation-engine-provides-mathematical-assurance-of-virtual-machine-isolation/) が公表されていますが、Nitro Sandbox との関係は公開資料には書かれていません。

| 部品 | 受け持ち | 動く場所 |
|---|---|---|
| kubelet と containerd | Pod を受け取り、どのランタイムで動かすかを決める | ノード |
| containerd-shim-nitro-sandbox-v2 | Pod ごとに firecracker を起動し、VM の中の agent とやり取りする | ノード |
| firecracker | VM の起動を受け持ち、ディスクやネットワークの仮想デバイスを VM に見せる | ノード (Pod ごとに 1 つ) |
| Nitro Hypervisor | ノードが差し出したメモリと CPU で VM を作り、VM どうしとノードを隔離する | ノードの下 |
| nitro-sandbox-agent | VM の中でコンテナを起動し、Pod ごとの Cedar policy を守らせる | VM の中 |

以下、`containerd-shim-nitro-sandbox-v2` を shim、`nitro-sandbox-agent` を agent と書きます。Cedar は、AWS が公開しているアクセス制御の言語です。その Pod がどのイメージをどの引数で起動してよいか、exec やログを許すかを Cedar で書き、Pod の annotation に付けます。以下、これを policy と書き、IAM や KMS の「ポリシー」と区別します。shim と VM の間は、virtio の仮想デバイスと vsock という内部の通信経路でつながります。

Pod を 1 つ起動すると、図の番号の順に進みます。

1. Pod の定義に `runtimeClassName: isolated-sandbox` または `confidential-sandbox` が書かれています。
2. shim が firecracker を起動します。
3. Nitro Hypervisor が VM を作り、VM の中で専用のカーネルが起動します。
4. VM の中の agent が、Pod に付いた policy で、どのイメージやどの操作を許すかを確かめます。
5. コンテナが VM の中で起動します。

![ノードの上の kubelet、containerd、shim、firecracker と、その隣の Nitro Sandbox の中の agent、policy の確認、コンテナ、下の Nitro Hypervisor を、起動の順に 1 から 5 の番号で示した図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/0ed37fa99f3fa0/zenn/articles/0ed37fa99f3fa0/components.png)
*Pod が runtimeClassName を指定したときに起動する部品と、その順番*

## 試す手順

isolated のモードなら、Pod の定義に足すのは `runtimeClassName` の 1 行です。利用者のコードを動かすなら、後の「2 つのモード」で書く理由で `automountServiceAccountToken: false` も足します。limits だけを書くと、Kubernetes が requests にも同じ値を入れます。

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-app
spec:
  runtimeClassName: isolated-sandbox
  automountServiceAccountToken: false
  containers:
  - name: main
    image: public.ecr.aws/amazonlinux/amazonlinux:2023
    command: ["sleep", "3600"]
    resources:
      limits:
        cpu: "1"
        memory: 512Mi
```

Nitro Sandbox には Kubernetes 1.36 以降が要ります。[isolated の始め方のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-isolated-setup.html)は Auto Mode のクラスタを勧めています。

```bash
export CLUSTER_NAME=sandbox-demo
export AWS_REGION=ap-northeast-1
eksctl create cluster --name "$CLUSTER_NAME" --region "$AWS_REGION" --version 1.37 --enable-auto-mode
```

[公式のサンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc/examples/getting-started/hello-sandbox)によると、既定の NodePool のままでも、sandbox の Pod が来ると Auto Mode が sandbox に対応したノードを起動します。既定の NodePool は x86 なので、起動するのは x86 のノードです。今回は NodePool を足した構成で確かめました。上の Pod を `manifest.yaml` として保存して apply し、カーネルのビルドと `boot_id` を見ます。同じノードの通常の Pod と比べるか、同じノードの sandbox の Pod 2 つで値が互いに違うことを見ると、sandbox の中で動いていると分かります。通常の Pod は別のノードに置かれることがあり、ノードが違えば `boot_id` は必ず違うので、同じノードで比べます。

```bash
kubectl apply -f manifest.yaml
kubectl wait pod/my-app --for=condition=Ready --timeout=300s
kubectl exec my-app -- sh -c 'uname -rv; cat /proc/sys/kernel/random/boot_id'
```

Pod が Pending のままなら、`kubectl describe pod` のイベントと、ノードの `eks.amazonaws.com/nitro-sandbox` のラベルを見ます。動かせない場所は[使える場所と制限](#使える場所と制限)にまとめました。

## Auto Mode 以外と Deployment で使うとき

- Auto Mode を使わないノードグループでは、sandbox のランタイムを入れた AMI、起動テンプレートで Nitro Enclaves を有効にする設定 `EnclaveOptions.Enabled=true`、自分で作る RuntimeClass、ノードのラベルが要ります。Nitro Enclaves は、インスタンスからメモリと CPU を切り出して隣に隔離された環境を作る機能で、Nitro Sandbox はこれを土台にしています。
- Auto Mode の既定の NodePool `general-purpose` は x86 のインスタンスだけを使うので、Graviton で動かすには arm64 を許す NodePool を足します。
- Deployment などで Pod を作る場合は、`runtimeClassName` と `sandbox.amazonaws.com/` で始まる annotation を、Pod テンプレート `spec.template` の側に書きます。Deployment 自身の `metadata.annotations` に書いても Pod には写されません。

この記事で足した NodePool は次のとおりで、m8i 用も同じ形です。Pod の側では `nodeSelector` に `exp-pool: g5` を書きます。

```yaml
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: g5
spec:
  template:
    metadata:
      labels:
        exp-pool: g5
    spec:
      nodeClassRef:
        group: eks.amazonaws.com
        kind: NodeClass
        name: default
      requirements:
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["on-demand"]
        - key: node.kubernetes.io/instance-type
          operator: In
          values: ["m9g.xlarge"]
```

## VM の大きさは requests で決まる

sandbox の Pod には、必ず requests を書きます。VM の大きさは limits ではなく requests で決まり、メモリは起動時に全部を確保するからです。[公式のサンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc)は、requests が無くメモリが足りない Pod がログを残さずに落ちる例を挙げています。

Auto Mode のクラスタにある 2 つの RuntimeClass は、Pod 1 つごとに `eks.amazonaws.com/nitro-sandbox` という拡張リソースを 1 つ使い、メモリを isolated では 256Mi、confidential では 512Mi 余分に予約する設定でした。この上乗せ分は Pod Overhead という仕組みで、スケジューリングのときに Pod の requests に足されます。isolated の Pod の VM のメモリは、カーネルから見て、requests を書かないと約 145 MiB、requests 512Mi・limits 2Gi では約 647 MiB でした。後者は requests と上乗せ分の合計 768 MiB より約 120 MiB 少なく、前者も上乗せ分の 256 MiB より約 110 MiB 少ない値です。VM のメモリは limits の 2Gi には届きません。m9g.xlarge (4 vCPU) のノードは拡張リソースの空きを 20 と表示し、[制限事項のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-limitations.html)の「sandbox の個数はノードの vCPU の数の 5 倍まで」と一致しました。

# 2 つのモード

2 つのモードの違いは、ノードを信頼するかどうかです。isolated はノードを信頼し、怪しいワークロードからノードと他の Pod を守ります。confidential はノードを信頼せず、ノードの管理者や乗っ取られたノードからワークロードのデータを守ります。次の表は、[EKS ユーザーガイド](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing.html)と [confidential の設定のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-confidential-setup.html)にある、組み込みの設定の既定値です。

| 項目 | isolated-sandbox | confidential-sandbox |
|---|---|---|
| 信頼しないもの | Pod の中のワークロード | ノード |
| policy | 無くてもよい。付けなければ、すべてを許す組み込みの既定が使われる | 必須。イメージの digest、引数、環境変数、マウントなどを固定する |
| exec と stdin | 使える | 拒否される |
| ログ | 読める | 既定では読める (拒否する設定もある) |
| コンテナの書き込み層 | 暗号化しない | VM の中で暗号化する |
| Kubernetes の ServiceAccount トークン | isolated のプロファイルで作った policy なら渡らない。policy を付けないと渡る | 渡る |

書き込み層は、イメージには無く、コンテナが動いている間に作ったり書き換えたりしたファイルが入る領域です。

:::message
表の最後の行は実機でも確かめました。後述の生成ツール `eks-nitro-sandbox-genpolicy` (以下 genpolicy) に `--profile isolated` を付けて作った policy の Pod にはトークンが無く、policy を付けない Pod にはあり、それで API サーバーに問い合わせるとその ServiceAccount として認証されました。利用者のコードを動かす Pod では、どちらのモードでも `automountServiceAccountToken: false` を書き、admission control で強制するのが安全です。
:::

## confidential で秘密を受け取る仕組み

confidential では、秘密のデータを KMS の鍵で暗号化しておき、承認した policy で起動したことを証明できる Pod にだけ復号を許します。PCR は、起動時に読み込んだものの計測値を記録するレジスタで、VM は自分の policy のハッシュを PCR17 に記録します。アテステーションは、その計測値に Nitro が署名した文書です。[セキュリティモデルのページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-security-model.html)によると、ノードはこれを偽れません。鍵の管理者は、KMS のキーポリシーに、復号を許す条件として PCR の値を書きます。

```json
"Condition": {
  "StringEqualsIgnoreCase": {
    "kms:RecipientAttestation:PCR17": "128d66d847a8767e70b52b23cfe1839ab55a45512e5087bc51dbc92a2d5d06d5197980ede432ee0f6b3192204dc2f5fe",
    "kms:RecipientAttestation:PCR8:ServiceName": "eks.amazonaws.com"
  }
}
```

PCR17 の値は、今回の試験で genpolicy が出した予測値です。PCR8 には、ゲストの起動イメージに署名した証明書の計測値が入り、`:ServiceName` を付けると署名者のサービス名で比べられます。この条件で、「承認した policy で起動し、EKS が署名したゲストで動いていること」を求めます。PCR8 の条件は、ゲスト自体が EKS の署名したものであることを確かめる役目なので、省きません。復号の流れは、[実機の節の図](#confidential-の-policy-と-kms)で 1 歩ずつ見られます。

キーポリシーの書き方には、[公式のサンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc/examples/confidential)が挙げている注意があります。

- 既定のキーポリシーで鍵を作ると、条件を書く前から復号できるので、最初から条件付きのポリシーで作ります。
- 条件に合わないものを拒否する文は、PCR17 と PCR8 で分けます。1 つの文にまとめると、両方が合わないときにしか拒否されません。
- 鍵の管理者には `kms:Decrypt` だけでなく `kms:ReEncryptFrom` も与えません。与えると、条件の無い別の鍵で包み直せます。
- PCR8 は生の値ではなく署名者の名前で書きます。AWS が署名の証明書を入れ替えると、生の値は変わるからです。

アプリケーションの側では、KMS の鍵をエイリアスではなく ARN で指定します。リージョンなどのメタデータはノードが偽れるからです。

## policy の作り方

policy は、生成ツール `eks-nitro-sandbox-genpolicy` で Pod の定義から作ります。ツールは PCR17 の予測値も出すので、Pod を動かす前にキーポリシーの条件を書けます。ツールは AWS が署名して公開している[ランタイムの配布物](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-download-binaries.html)に入っていて、今回は署名を確かめて使いました。

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-conf
spec:
  runtimeClassName: confidential-sandbox
  enableServiceLinks: false
  containers:
  - name: main
    image: public.ecr.aws/amazonlinux/amazonlinux:2023
    command: ["sleep", "3600"]
    resources:
      limits:
        cpu: "1"
        memory: 512Mi
  automountServiceAccountToken: false
```

これを `conf.yaml` として保存して次のように実行すると、policy の base64 の文字列と PCR17 の予測値が出ます。base64 の文字列を Pod の `sandbox.amazonaws.com/policy` という annotation に付けて apply します。

```bash
eks-nitro-sandbox-genpolicy --profile confidential conf.yaml
```

policy を作るときの決まりは次のとおりです。

- Pod に IAM ロールを割り当てる EKS Pod Identity を使う Pod は、`--with-pod-identity` を付けて作ります。ServiceAccount に IAM ロールを結び付ける IRSA なら `--with-irsa` を付けます。付けないと、認証情報のファイルが無く、AWS の呼び出しが失敗します。
- `enableServiceLinks: false` を書きます。書かないと、kubelet が足す環境変数を固定できず、ツールはエラーで止まりました。`--allow-additional-env` でも回避できますが、環境変数を厳密には固定しなくなります。
- webhook などがサイドカーを足す場合は、書き換えたあとの最終的な Pod の定義から作ります。
- イメージの更新など、policy が固定している項目を変えたら、policy とキーポリシーの PCR17 と Pod を作り直します。動いている Pod の policy は変えられないので、この手順は CI/CD に組み込みます。
- 作り直しを減らしたい場合は、digest ではなく AWS Signer の署名者でイメージを信頼する policy にできます。[公式のサンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc/examples/confidential/signer-policy)によると、署名者を指定する policy と `--skip-image-ref-container` を組み合わせて digest の固定を外します。固定を外すフラグだけでは署名者の条件が入らないおそれがあるので、生成した policy に署名者の条件があることを確かめます。承認の範囲は「この署名者が署名したイメージすべて」に広がり、署名済みの古い版への差し替えも含むので、失効の管理も要ります。今回は試していません。署名の確認には Pod のロールに `signer:GetSigningProfile` と `signer:GetRevocationStatus` が要ります。

確かめたのは単体の Pod だけで、Deployment で confidential を使えるかは確かめていません。

# 実機で確かめたこと

## 環境

ノードの側から sandbox がどう見えるかを確かめるため、同じノードに `hostPID: true` を付けた特権付きの通常の Pod を置き、その中から調べました。以下、これを観察用の Pod と呼びます。特に断らない結果は m9g.xlarge のもので、確かめたのは 2026 年 11 月 10 日から 14 日です。

| 項目 | 値 |
|---|---|
| リージョン | 東京 (ap-northeast-1) |
| クラスタ | EKS Auto Mode、Kubernetes 1.37 |
| ノード | m9g.xlarge (Graviton5、4 vCPU、1 コアに 1 スレッド)、m8i.xlarge (4 vCPU、1 コアに 2 スレッド) |

Auto Mode は、通常の Pod だけのときはラベル `eks.amazonaws.com/nitro-sandbox` が `false` のノードを起動し、sandbox の Pod を作ると、`true` のノードを別に起動しました。通常の Pod は sandbox のノードにも置けるので、比較は両方を同じ sandbox のノードに並べて行いました。

## カーネルとプロセスが分かれている

sandbox の Pod 3 つと通常の Pod 2 つを置いたノードで、観察用の Pod からプロセスを一覧すると、firecracker と Pod ごとの shim が sandbox の数と同じ 3 つずつ見え、sandbox の中の `sleep` は見えませんでした。逆に sandbox の Pod に `hostPID: true` を付けると、見えたのは VM の中のプロセスだけでした。`hostNetwork: true` の Pod は `hostNetwork is not supported for nitro-sandbox pods` で起動しませんでした。どちらも[制限事項のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-limitations.html)のとおりです。

カーネルのログも分かれていました。sandbox の中でカーネルのログに書いた目印の行は、ノードのカーネルのログ 1,455 件には出ませんでした。sandbox の中でカーネルを意図的に止めても (`echo c > /proc/sysrq-trigger`)、同じノードの他の sandbox 2 つとノードは `boot_id` が変わらず、動き続けました。

## confidential の policy と KMS

confidential では、policy が固定している項目が Pod と違うと、コンテナが起動しません。同じ名前のまま引数だけを変えた Pod は、VM は起動したものの、agent が `policy denied Agent::Action::"CreateContainer"` で拒否しました。名前も変えた Pod は、その手前の `policy denied SetupSandbox` で止まりました。policy が Pod の名前も固定しているためと考えられます。

KMS は、[公式のサンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc/examples/confidential)のキーポリシーの形で確かめました。Pod Identity で割り当てる IAM ロールには IAM のポリシーを付けず、キーポリシーで、PCR17 が承認した値で PCR8 の署名者が EKS のときだけこのロールに復号を許し、それ以外を拒否しました。そのうえで、暗号文 1 つを 3 つの Pod で復号させました。図の上の切り替えで、3 つの場合を選べます。

## ネットワークを切る

[ネットワーク分離のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-network-isolation.html)によると、Pod に `sandbox.amazonaws.com/network-isolated: "true"` を付けると、VM の外とつながるネットワークインターフェースを持たない VM として起動します。

```yaml
metadata:
  annotations:
    sandbox.amazonaws.com/network-isolated: "true"
spec:
  runtimeClassName: isolated-sandbox
```

実機では、この Pod にあるのはループバックと停止中の `dummy0` だけで、外への HTTPS は名前解決で失敗し、インスタンスの情報を返す IMDS にもつながりませんでした。一方で `kubectl logs` と `kubectl exec` は使えました。これらは VM とノードの間の vsock を通るからです。ネットワーク分離のページによると、ノード側でも firecracker の vsock のソケットに触れられるプロセスなら、VM の中で待ち受けているポートに接続できるので、完全な遮断ではありません。ネットワークを切った Pod では Pod Identity の認証情報も使えないので、暗号化したイメージと AWS Signer による署名の確認も使えません。

ネットワークを切らない sandbox の IMDS は、リージョン、アベイラビリティーゾーン、パーティションを返し、インスタンス ID と IAM の認証情報は 404 でした。AWS の認証情報は Pod Identity で渡します。

## 運用で効く数字と注意

### 起動にかかる時間

Pod を作ってから準備完了になるまでの時間を、各 10 回測りました。Kubernetes の API が記録する作成時刻と準備完了の時刻の差は 1 秒刻みで、通常の Pod が 0〜1 秒、isolated が 3〜4 秒で中央値 3.5 秒、confidential が 5〜8 秒で中央値 7 秒でした。Pod は CPU 0.5・メモリ 256Mi で、イメージはノードにある状態です。ノードの起動待ちは含みません。起動待ちを避けたい場合は、先に起動しておいた sandbox を割り当てるウォームプールの[サンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc/examples/getting-started/warm-pool)があり、割り当ては 1 秒未満と書かれています。

### 既定の帯域とパケット数の上限

sandbox には、Pod ごとの帯域とパケット数に[既定の上限](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-resource-isolation.html)があり、帯域は 100 Mbps、パケット数は毎秒 1,500 個です。同じノードの通常の Pod を相手に、iperf3 で TCP を 30 秒、1,400 バイトの UDP を 300 Mbps で 20 秒送り、受信側で測りました。

| sandbox の設定 | sandbox から送る TCP | sandbox が受ける TCP | sandbox から送る UDP |
|---|---|---|---|
| 既定のまま | 99.9 Mbps | 99.9 Mbps | 17.7 Mbps (毎秒約 1,580 個) |
| 帯域だけ 1G に上げる | 750 Mbps | 690 Mbps | 18.2 Mbps (毎秒約 1,620 個) |
| 帯域を 1G、パケット数を毎秒 15,000 個に上げる | 997 Mbps | 998 Mbps | 176 Mbps (毎秒約 15,700 個) |

既定のままで負荷試験をすると、sandbox の性能ではなくこの上限を測ることになります。上げるときは、帯域とパケット数の両方を Pod の annotation で指定します。小さいパケットが多い通信は、帯域より先に毎秒 1,500 個の上限に当たるからです。annotation は Pod の作成時に一度だけ読まれます。

```yaml
metadata:
  annotations:
    sandbox.amazonaws.com/ingress-bandwidth: "1G"
    sandbox.amazonaws.com/egress-bandwidth: "1G"
    sandbox.amazonaws.com/ingress-packets-per-second: "15000"
    sandbox.amazonaws.com/egress-packets-per-second: "15000"
```

:::details 帯域だけ上げたときの TCP の結果
ドキュメントは片方だけ上げても効果はないと書き、公式のサンプルは 100 Mbps 付近のままと書いています。1,400 バイトの UDP では効果がなく 17.7 Mbps から 18.2 Mbps でしたが、同じノードの Pod どうしの TCP を 1 回測ると、帯域だけ上げても 750 Mbps 出ました。1 個あたりに直すと次のとおりです。

$$
\frac{750 \times 10^6\ \text{bit/s}}{1500\ \text{packets/s}} \div 8 \approx 62.5\ \text{KB/packet}
$$

TCP が複数のパケットを大きな単位にまとめて扱うときの大きさ (最大 64 KB) に近く、パケット数がまとめた単位で数えられているのではないかと推測しています。通信先や経路によって変わる可能性があります。
:::

### CPU の取り分

CPU を使い切る Python のループを 20 秒回し、進んだ回数を通常の Pod と sandbox の Pod で比べました。CPU は requests 0.8、limits 1 にそろえ、同じノードに 1 個または 4 個を同時に置いて、各 3 回の中央値を取っています。値は通常の Pod 1 個を 1 とした比です。

| ノード | 通常 1 個 | sandbox 1 個 | 通常 4 個 (合計) | sandbox 4 個 (合計) |
|---|---|---|---|---|
| m9g.xlarge (4 コア、1 コアに 1 スレッド) | 1.00 | 0.95 | 3.94 | 3.75 |
| m8i.xlarge (2 コア、1 コアに 2 スレッド) | 1.00 | 0.99 | 2.07 | 1.96 |

1 個のときの差は、sandbox 1 個の 3 回の値の幅 (m9g で 0.91〜1.01、m8i で 0.83〜1.00) に収まります。4 個を同時に置くと、3 回とも sandbox のほうが 3〜6% 低くなりました。m8i で 4 個の合計が約 2 倍で止まるのは、物理コアが 2 つで、2 つ目のスレッドがこの処理ではほとんど上乗せにならないためと考えられ、通常の Pod も同じです。制限事項のページは、1 コアに 2 スレッドのインスタンスでは 2 つの sandbox が同じコアを同時に使わないよう制御されると書き、CPU を 2 vCPU 単位で要求するか、Graviton のように 1 コアに 1 スレッドのインスタンスを選ぶことを勧めています。

### カーネルが止まっても Pod は「動いている」ままになる

ネットワークのある sandbox の Pod には、HTTP の liveness probe を付けておくのが安全です。sandbox の中でカーネルを止めると、Pod は `Running` で準備完了のまま残りました。

```yaml
livenessProbe:
  httpGet:
    path: /
    port: 8080
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 2
```

probe を付けない Pod は約 6 分経っても再起動されず、exec だけが返らない状態でした。同じ間隔で `cat /proc/uptime` を実行する exec の probe は、「失敗」ではなく状態不明の「エラー」になり、471 秒経っても再起動されませんでした。HTTP の probe を付けた Pod は約 50 秒で再起動し、`boot_id` も新しくなりました。ネットワーク分離のページは、HTTP と TCP の probe が使えないネットワークを切った Pod に exec の probe を勧めていますが、今回の止まり方は exec の probe では検知できませんでした。試したのはネットワークのある Pod で、切った Pod では確かめていません。

# 使える場所と制限

表の内容は、2026 年 11 月 13 日にドキュメントで確かめたものです。Nitro Sandbox は EC2 のインスタンスの機能で、ECS や EC2 から直接も使えます。[EC2 のユーザーガイド](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/amazon-ec2-nitro-sandboxes.html)によると、EC2 から直接使うときの direct モードは、ノードが VM のメモリを読めてアテステーションもない別のモードです。この記事の結果は当てはまりません。

| 項目 | 対応 | 根拠 |
|---|---|---|
| EKS Auto Mode | 使える。RuntimeClass が最初からあり、sandbox のノードも自動で起動する | [isolated の始め方のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-isolated-setup.html)、実機 |
| EC2 のマネージドノードグループ、セルフマネージドノード | 使える。AMI、起動テンプレート、RuntimeClass、ノードのラベルの用意が要る | isolated の始め方のページ |
| Hybrid Nodes (オンプレミスのサーバーを EKS につなぐ形) | 使えない。実機では試していない | Nitro Sandbox は対応する EC2 のインスタンスタイプでしか動かない ([EKS ユーザーガイド](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing.html)) |
| Fargate | 使えない | 実機では `Fargate profile ... cannot satisfy pod's node selector/affinity requirements` で Pending のままだった |
| Kubernetes の版 | 1.36 以降 | isolated の始め方のページ |
| インスタンスタイプ | Nitro Enclaves に対応するものの一部。多くのファミリーで最小のサイズと metal は対象外 | EC2 のユーザーガイド |
| Auto Mode で sandbox のノードを作らない構成 | FIPS 用、GPU や Neuron 用の AMI、複数の NUMA を持つインスタンスタイプ、未検証のインスタンスタイプ。いずれも Pod は Pending のまま | [制限事項のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-limitations.html) |
| GPU などのデバイスの受け渡し | 使えない | 制限事項のページ |

次は Pod の機能の制限です。断りの無いものは制限事項のページの記載です。

| Pod の機能 | sandbox での扱い |
|---|---|
| `hostNetwork: true` | 起動しない (実機でも確かめた) |
| `hostPID: true`、`hostIPC: true` | 起動するが、見えるのはその VM の中だけ (hostPID は実機でも確かめた) |
| ユーザー名前空間 | `hostUsers: false` の Pod は起動しない。sandbox のカーネルは `max_user_namespaces` が 0 で (実機)、bubblewrap のように中でユーザー名前空間を作るツールはそのままでは動かない |
| VM の大きさ、CPU とメモリ | requests で決まり、あとから変えられない |
| EBS のボリューム | 複数の Pod で共有できず `ReadWriteOncePod` を使う。動いている Pod のボリュームは拡張できない ([公式のサンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc)) |
| kubelet の CPU Manager の `static` | 効かない |
| `kubectl port-forward` | `127.0.0.1` だけで待ち受けるサーバーには届かない |
| `emptyDir` と書き込み層の使用量 | kubelet からは 0 に見える。上限は `ephemeral-storage` の requests と limits で決める |
| 一部だけ暗号化したイメージ | 使えない。暗号化するなら全部の層 |
| 1 つのノードの sandbox の数 | 個数も vCPU の合計も、ノードの vCPU の数の 5 倍まで |
| ネットワークを切った Pod | Pod Identity の認証情報、暗号化したイメージ、署名の確認、HTTP と TCP の probe、EFS と S3 Files が使えない。EBS は使える |
| Ubuntu のノード | sandbox の Pod に `appArmorProfile.type: Unconfined` が要る (公式のサンプル) |
| スナップショットからの復元、ライブマイグレーション | 使えない |

Pod ごとの既定の上限は、[資源の上限のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-resource-isolation.html)のとおり Pod の annotation で変えられます。接続数を除いては `"disabled"` で外せますが、`"0"` を指定すると Pod が起動しません。

| 上限 | 既定 | annotation (`sandbox.amazonaws.com/` の後ろ) |
|---|---|---|
| 帯域 (受信と送信) | 100 Mbps | `ingress-bandwidth`、`egress-bandwidth` |
| パケット数 (受信と送信) | 毎秒 1,500 個 | `ingress-packets-per-second`、`egress-packets-per-second` |
| DNS | 毎秒 100 クエリ (512 まで) | `dns-packets-per-second` |
| 同時の外向き接続 | IP のファミリーごとに 4,096 (無効にはできない) | `conntrack-limit` |
| 書き込み層のディスク | 400 Mbps、1,500 IOPS | `overlay-disk-bandwidth`、`overlay-disk-iops` |
| ログ | 2 Mbps | `log-bandwidth` |

# セキュリティ運用で何が変わるか

sandbox が防ぐのは、VM の中のコードがノードのカーネルやメモリに直接触ることです。テナントどうしの通信、認証情報、共有のストレージ、資源の取り合いは、別の対策で守ります。ノード側の firecracker や仮想デバイスの処理は VM から入力を受け取るので、攻撃される面として残ります。前提は、信頼できないのはコンテナの中のコードで、Pod の定義は信頼できる人が書くことです。

| 層 | sandbox で変わること |
|---|---|
| 隔離 | 境界が共有のカーネルから Nitro Hypervisor に移る。実機で確かめたのは障害の封じ込めで、sandbox のカーネルを止めても隣の sandbox とノードは動き続けた。脱出への強さは試していない |
| 監査ログ | Kubernetes の監査ログと CloudTrail はノードの外で記録されるので変わらない。どちらも VM の中で実行されたコマンドの記録ではない |
| ログとメトリクス | kubelet を通るので、CloudWatch のエージェントなどで集められる ([監視のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-observability.html)) |
| ノードのランタイム監視 | sandbox の中は見えない。監視のページは GuardDuty のランタイム監視の agent が sandbox の中を観察できないと書いており、実機でもノードから見えたのは firecracker と shim だけだった |
| Pod の中の監視 | 同じ Pod に置いた監視用のコンテナから、VM の中のプロセスやファイル、通信が見える。ただし使える道具は限られる (次の節) |
| ネットワーク | NetworkPolicy やセキュリティグループはノードの側で効くので、sandbox の中から外せない。Auto Mode では強制を有効にする設定が要る |

隔離と検知は別の軸の対策です。隔離は侵害が Pod の外へ広がる範囲を狭め、検知は侵害に気づくまでの時間を縮めます。sandbox は前者を強めますが、後者の代わりにはなりません。アプリの脆弱性を突かれた攻撃者は、sandbox を抜け出さなくても、Pod が正当に持つ IAM の権限、データベースへの接続、シークレットで目的を果たせるからです。

広い権限や機密データを持ち、長く動き続ける業務アプリを sandbox に載せるなら、検知の代わりになる対策を組み合わせます。外への通信を既定で拒否する、IAM の権限を最小にして認証情報の有効期限を短くする、ルートのファイルシステムを読み取り専用にする、CloudTrail と監査ログの異常を見張る、アプリ自身に操作の記録を残させる、Pod を短い時間で作り直す、といった対策です。sandbox が最も向いているのは、利用者のコードや AI エージェントの道具の実行のように、中は乗っ取られる前提で、短い時間だけ動き、権限の小さい処理です。

Falco、Tetragon、auditd が動かないのは、sandbox のカーネルに、カーネルの型情報である BTF や、それらが前提にする eBPF と audit の仕組みが無いからです。一方で、次の仕組みは使えました。

- proc connector は、プロセスの実行をカーネルが知らせる仕組みです。
- cgroup に付ける `sock_addr` の eBPF プログラムは、接続と UDP の送信のたびに呼ばれ、BTF が無くても動きます。
- inotify は、ファイルの変化を知らせる仕組みです。
- conntrack は新しい通信の宛先を、perf のタスクイベントは実行されたプログラムの名前を知らせます。

fatrace による fanotify の登録は、`/` でも `/tmp` のマウント単位でも `Operation not supported` で失敗しました。clamonacc の fanotify は知らせを受け取れたので、登録の仕方によっては使えます。

監視用のコンテナを置くときの注意は次のとおりです。

- 監視用のコンテナには特権と `hostPID: true` が要り、Pod ごとに入れます。どちらも Pod Security の baseline に反するので、admission で例外を設けます。requests も書き、VM のメモリを見込んでおきます。
- 特権の影響はその VM の中にとどまると考えられますが、試してはいません。持たせた認証情報やマウント、送信先は VM の外に届き、仮想デバイスへの入力も増えるので、最小限にします。
- `hostPID` は Pod の全体に効くので、root で動くワークロードは監視のプロセスを止められるはずです (試してはいません)。攻撃を防ぐ仕組みではなく気づくための仕組みなので、結果はすぐに VM の外へ送ります。ネットワークを切った Pod では、送る経路が標準出力のログ (既定で 2 Mbps) や EBS に限られます。
- confidential では、標準出力に出した記録は信頼しないノードを通ります。
- 別のコンテナのファイルは `/proc/<PID>/root` から見えますが、PID ごとのパスなので、コンテナが作り直されたら指し直します。
- 確かめたのは x86 のノードだけです。

## sandbox-guestwatch

上で動いた仕組みだけを使って、sandbox の中を記録する小さなエージェントを作り、[sandbox-guestwatch](https://github.com/littlemex/sandbox-guestwatch/tree/d87645b7190b41b9ea77db2a445821b2be4238f5) として Apache-2.0 で公開しました。検証用の道具で、AWS のプロジェクトではありません。

| 記録するもの | 使う仕組み |
|---|---|
| プログラムの実行と引数 | proc connector |
| 外への接続と UDP の送信、そのプロセス | cgroup の `connect4`、`connect6`、`sendmsg4`、`sendmsg6` の eBPF |
| ファイルの作成、書き込み、移動 | inotify |

eBPF のプログラムは Go の中で命令を組み立てるので、BTF も C のビルド環境も要りません。別のコンテナのファイルは、そのコンテナのルートを指す fd から `openat2` でたどるので、コンテナの中のシンボリックリンクにも惑わされません。ファイルは、fanotify がファイルシステム単位で登録できなかったので inotify で見ます。依存は `cilium/ebpf` と `golang.org/x/sys` の 2 つです。使うときは、[例の Pod](https://github.com/littlemex/sandbox-guestwatch/blob/d87645b7190b41b9ea77db2a445821b2be4238f5/deploy/example-pod.yaml) のようにサイドカーとして置きます。イメージは [README](https://github.com/littlemex/sandbox-guestwatch/blob/d87645b7190b41b9ea77db2a445821b2be4238f5/README.md) の手順で自分で作ります。

```yaml
spec:
  runtimeClassName: isolated-sandbox
  hostPID: true
  containers:
    - name: guestwatch
      image: ${GUESTWATCH_IMAGE}
      args: ["--require=exec,net,file"]
      securityContext:
        privileged: true
```

記録は 1 件 1 行の JSON で標準出力に出るので、コンテナのログを集める仕組みでそのまま集められます。規則に当たった記録には印が付きます。

```json
{"v":1,"type":"exec","container":{"id":"e4964251…"},"process":{"pid":1902,"uid":1000,"exe":"/tmp/fastcurl","cmdline":["/tmp/fastcurl","--version"]},"rules":["exec_from_temp_dir"]}
{"v":1,"type":"connect","container":{"id":"e4964251…"},"process":{"pid":1884,"comm":"bash"},"net":{"proto":"udp","dst":"192.0.2.20","port":9999,"count":499,"repeat":true}}
{"v":1,"type":"file","container":{"id":"de48706c…"},"file":{"path":"/usr/local/bin/evil","op":"create"},"rules":["write_to_binary_dir"]}
```

筆者の書いた[試験](https://github.com/littlemex/sandbox-guestwatch/blob/d87645b7190b41b9ea77db2a445821b2be4238f5/test/e2e/run.sh)を、x86 のノードの isolated の sandbox で流し、20 項目がすべて通りました。確かめたのは次の動きです。

- `/tmp` に置いてすぐ終わる実行ファイル
- 500 回の UDP の送信が、1 行目と「残り 499 回」の 2 行にまとまること
- IPv4 を IPv6 の形で書いた宛先
- コンテナの中のシンボリックリンクの先への書き込み
- `/usr/local/bin` へのディレクトリの移動と、コンテナの作り直しへの追従

外から入る接続、raw socket、ファイルの読み取り、ファイルの記録のプロセス、エージェントが起動する前の動き、システムコール単位の記録は取れません。高い負荷のときの取りこぼしと、Graviton のノード、confidential は試していません。

## NetworkPolicy の注意

- Auto Mode では、NetworkPolicy は強制を有効にするまで効きません。実機でも、外への通信をすべて拒否する NetworkPolicy を入れても HTTPS は通り、次の ConfigMap を作ると、作り直した sandbox の Pod の通信が止まりました。

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: amazon-vpc-cni
  namespace: kube-system
data:
  enable-network-policy-controller: "true"
```

- Pod と自分のノードの間の通信は、NetworkPolicy ではどちらの向きも止められません。同じノードの `hostNetwork` の Pod から sandbox の中のポートに届くので、VM の中のサービスにも認証を付けます。[公式のサンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc)によると、sandbox の IMDS は VM の中で応答するので、NetworkPolicy の対象外です。
- 公式のサンプルには、Pod の起動の直後に NetworkPolicy がまだ効いていない時間があった例が載っています。今回は起動直後の時間を確かめておらず、強制を有効にした後は Pod を作り直して試したので、既存の Pod に効くかも確かめていません。短い時間だけ動く処理では起動直後が実行の大半なので、通信が要らないならネットワークを切る設定を使います。
- 外への通信を既定で拒否するなら、Pod Identity の認証情報の取得先 `169.254.170.23` と DNS を許します。許す相手をクラスタの DNS に絞っても、クラスタの DNS は外の名前を引くので、問い合わせに載せた持ち出しは止まりません。利用者のコードには、ネットワークを切るか、引ける名前を絞る DNS のフィルタと `dns-packets-per-second` の引き下げを組み合わせます。

## 利用者のコードを実行するサービスの組み立て

利用者から受け取るのはコードなどの限られた入力だけにし、Pod の定義はサービスの側で作ります。通常の Pod を作れたり、特権や `hostNetwork`、`hostPath` を指定できたり、既存の Pod に exec できたりすると、sandbox の境界を回り込めるからです。Pod を作る経路と変える経路は RBAC で絞り、`runtimeClassName` の付け忘れなどの定義の中身は admission control で強制します。実行環境は isolated の sandbox にし、通信が要らない処理はネットワークも切ります。中が止まっても Pod は準備完了のまま残ることがあるので、実行時間の上限、外からの死活の確認、強制的な削除と作り直しの手順も組み合わせます。

Pod の中には、もう 1 つの閉じ込めの層も置けます。[公式のサンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc/examples/subagent-security)は、エージェントが起動する道具のプロセスを、sandbox の中で Landlock や seccomp でさらに絞る例を挙げています。Nitro の境界は Pod とノードの間にあり、Pod の中のプロセスどうしは分けないからです。

# 誤解しやすい点

confidential が守るのは、VM のメモリと CPU の状態、暗号化した書き込み層などです。ワークロード自身が漏らすものと、ノードが握っている入出力は守れません。[セキュリティモデルのページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-security-model.html)が挙げている例を、2 つに分けてまとめます。

| ワークロード自身が漏らすもの | 理由 |
|---|---|
| 標準出力や終了メッセージに書いた秘密 | ログを許可していれば、ノードがそのまま受け取る。終了メッセージ (`/dev/termination-log`) はログとは別の操作で、既定ではどちらのモードでも読める |
| EFS や EBS に平文で書いたデータ | ノードは同じファイルシステムをマウントでき、EBS は中身を直接読める |
| 実行時に読み込んだ信頼できないコード | 起動後に取ってきたコードは policy の固定の外にある |

| ノードができること | 理由 |
|---|---|
| 暗号化していないイメージの層を読む | 層はノードを通って VM に渡される。[イメージの暗号化](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-encrypted-images.html)をしても、manifest と設定 (`ENV` など)、Pod の定義の引数と環境変数は平文のまま |
| ConfigMap、Secret、projected volume の中身を差し替える | policy が固定するのはマウントの場所で、中身ではない。CA 証明書のような信頼の起点は、digest で固定したイメージに入れる |
| 暗号化していない通信を見たり書き換えたりする | TLS で相手の証明書を確かめ、Pod の中の通信は `localhost` ではなく `127.0.0.1` を使う (`/etc/hosts` はノードが書く) |
| EFS の接続先を差し替える | genpolicy が作る policy はファイルシステムの ID を固定しないので、`context.file_system_id` を固定する permit を書き足す |
| Pod Identity の認証情報や、Secrets Store CSI Driver で渡した秘密を読む | どちらもノードを通って渡される |
| サービスを止める、時刻や DNS や配置のメタデータを偽る | ノードが提供している |

ほかに、次の点も誤解しやすいので書いておきます。

- Pod の定義は信頼する入力として扱われます。信頼できないイメージを動かす機能で、信頼できない人が書いた Pod の定義を受け付ける機能ではありません。
- KMS のキーポリシーに PCR の条件を書かなければ、計測値は記録されるだけで誰も確かめません。PCR8 の署名者の条件が示すのは EKS が署名したゲストのイメージであることで、版の新しさには触れていません。
- [EKS ユーザーガイド](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing.html)によると、AWS が受け持つのは Nitro Hypervisor、sandbox の境界、ゲストのシステムイメージで、コンテナのイメージ、policy、KMS のキーポリシー、アプリケーションのコードは利用者が受け持ちます。Auto Mode を使わず自分で AMI を作るなら、ノードのカーネルやランタイムの更新も自分で行います。
- 隔離は性能の予約ではありません。vCPU は時分割で共有され、ノードの vCPU の数の 5 倍まで割り当てられます。

# まとめ

isolated なら `runtimeClassName` の 1 行と requests で Pod は専用のカーネルの VM で動き、ノードの特権付きの Pod が `/proc` から読めた範囲にメモリの中身は無く、confidential では試した 3 つの場合で KMS の復号を承認した policy の Pod だけに絞れました。一方でノードの監視からは中が見えなくなるので、osquery、Wazuh、Suricata、sandbox-guestwatch のような Pod の中で動いた道具と、監査ログ、ネットワークの記録を組み合わせる設計が要り、確かめていない主な点を次の表に残します。

| 項目 | 内容 |
|---|---|
| メモリを読む別の方法 | `/proc` と共有領域を探す以外の方法で、ノードからゲストのメモリに届くか |
| ボリューム | EBS と EFS を sandbox から使ったときの性能と、confidential での扱い |
| 暗号化したイメージ | イメージの層を暗号化し、sandbox の中で KMS を使って復号する機能 |
| パケット数の数え方 | TCP で帯域だけ上げたときに 750 Mbps 出た理由 |
| ネットワークの性能 | 上限を外したときの帯域とレイテンシー、ノードの外への TCP |
| vsock の通信経路 | ネットワークを切った Pod に、ノードの root が vsock から実際に接続できるか |
| ほかの死活の確認 | TCP の probe、アプリケーションだけが固まった場合、ネットワークを切った Pod での検知、Service の振り分け先に残るか |
| confidential の更新 | ローリング更新で新旧の PCR17 が並ぶときのキーポリシーと、Deployment での policy の扱い |
| 起動時間 | sandbox のノードが無い状態からの時間と、Pod の大きさとの関係 |
| 書き込み層の暗号 | 暗号の方式と、改ざんや巻き戻しへの強さ |
| Hybrid Nodes | 実機での確認 |
| GuardDuty の検知 | 新しい実行ファイルやリバースシェルなどのプロセスの検知 (通常の Pod でも出ず比べられなかった)、ノードの名前解決を通らない DoH などの問い合わせ |
| Graviton での Pod の中の監視 | arm64 の sandbox で、上の道具と sandbox-guestwatch が同じように動くか |
| ノード側の部品の権限 | firecracker と shim が動く uid、seccomp、capability |
| Nitro Isolation Engine | Nitro Sandbox の隔離に関わっているか |
