# はじめに

Amazon EKS で、Pod ごとに専用の軽量な VM を[割り当てられるようになりました](https://aws.amazon.com/jp/about-aws/whats-new/2026/11/nitro-sandboxes-eks-ecs-ec2/)。通常の Pod はノードの Linux カーネルを共有しますが、この機能を使う Pod は Nitro Sandbox という VM の中で動き、同じノードの上にいてもカーネルを共有しません。

Linux カーネルの脆弱性は毎年のように見つかります。生成 AI が書いたコード、CI のジョブ、利用者が持ち込むスクリプトのように、他人のコードをそのまま実行するサービスでは、コンテナからの脱出やカーネルの不具合が、同じノードの他の利用者にまで届くことが心配になります。Nitro Sandbox は、Pod どうしを隔てる仕切りを、共有の Linux カーネルからハイパーバイザーに移す機能です。

AWS は、AI のエージェント、CI のジョブ、ストレージ、機密データの保護などの使い方を、そのまま動かせる形でまとめた[公式のサンプル集](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc)も公開しています。この記事では、まず仕組みと 2 つのモード（isolated と confidential）を整理し、次に東京リージョンの EKS で実際に動かして、ノードの側から何が見えて何が見えないかを確かめた結果を書きます。続けて使える場所と制限をまとめます。隔離と監視の組み合わせがセキュリティの運用でどう変わるかを整理し、ハイパーバイザーのうち隔離を受け持つ部分を形式検証した Nitro Isolation Engine との関係を見たうえで、最後に誤解しやすい点をまとめます。

| 確かめたこと | 結果 | 節 |
|---|---|---|
| 同じノードの Pod どうしでカーネルが分かれるか | sandbox ごとに別のカーネルが起動していた | [カーネルとプロセス](#カーネルとプロセスが分かれている) |
| ノードの root からメモリやディスクを探せるか | `/proc` 経由で読めた範囲に、メモリの中身は無かった。書き込み層のディスクの中身は isolated では見つかり、confidential では見つからなかった | [ノードから探したもの](#ノードの-root-から探したもの) |
| confidential の policy と KMS | 中身を 1 か所変えた Pod には、KMS が復号を許さなかった | [policy と KMS](#confidential-の-policy-と-kms) |
| ネットワークを切る設定 | VM の外とつながるネットワークインターフェースが無い状態で起動した | [ネットワークを切る](#ネットワークを切る) |
| ノードからのプロセスの見え方 | ノードからは sandbox の中のプロセスが見えなかった。同じ Pod の中に置いた監視用のコンテナからは見えた | [セキュリティ運用で何が変わるか](#セキュリティ運用で何が変わるか) |
| 使える場所 | EKS では Auto Mode と EC2 のノードグループだけ。Fargate では sandbox の Pod が Pending のままだった | [使える場所と制限](#使える場所と制限) |
| 運用で効く数字 | 起動は isolated で 3〜4 秒、confidential で 5〜8 秒（CPU 0.5・メモリ 256Mi の Pod、イメージはノードにある状態）。既定の帯域は 100 Mbps。sandbox のカーネルを止めた試験では、exec の liveness probe では気づけず、HTTP の probe で気づけた | [運用で効く数字と注意](#運用で効く数字と注意) |

# 通常の Pod が共有しているもの

通常の Pod は、ノードのカーネルを共有しています。コンテナは、カーネルの機能（プロセスから見える範囲を区切る名前空間と、資源の使用量を区切る cgroup）で区切られたプロセスにすぎません。そのため、カーネルの不具合やコンテナからの脱出（コンテナの中のプロセスが区切りを越えてノードを操作すること）があると、同じノードの他の Pod にまで影響が及びます。

カーネルを共有していることは、Pod の中から確かめられます。Linux は起動のたびに `boot_id` という ID を振ります。同じノードに置いた通常の Pod 2 つでは、`boot_id` が同じでした（11 月 10 日、図の値）。11 月 13 日に同じ並びを作り直してノードの上でも読むと、通常の Pod 2 つの `boot_id` とカーネルのビルドはノードの値と一致しました。sandbox の Pod は、どちらの日も `boot_id` が Pod ごとに別々でした。この環境ではカーネルの版もノードと違いましたが、版は同じになることもあるので、見分けるのは `boot_id` とカーネルのビルドです。

![同じノードで、通常の Pod 2 つは boot_id とカーネルが同じで、sandbox の Pod 3 つはそれぞれ別の boot_id と別のカーネルを持つことを並べた図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/0ed37fa99f3fa0/zenn/articles/0ed37fa99f3fa0/shared-kernel.png)
*同じ m9g.xlarge ノードで、各 Pod の中から読んだ boot_id とカーネルの版（版は同じになることもあるので、見分けるのは boot_id とビルド）*

# Nitro Sandbox の仕組み

Nitro Sandbox は、Pod 1 つに VM を 1 つ割り当て、その VM の中でコンテナを動かす仕組みです。ノード（EC2 インスタンス）自身も、Nitro Hypervisor という AWS のハイパーバイザーの上で動く VM です。Nitro Sandbox の VM は、ノードの中に入れ子で作るのではなく、同じ Nitro Hypervisor がノードの隣に[直接作ります](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing.html)。そのため、VM のメモリの仕切りはノードの OS ではなく Nitro Hypervisor が受け持ちます。以下、この VM を「ゲスト」とも呼びます。

登場する部品の受け持ちは次のとおりです。

| 部品 | 受け持ち | 動く場所 |
|---|---|---|
| kubelet と containerd | Pod を受け取り、どのランタイムで動かすかを決める | ノード |
| containerd-shim-nitro-sandbox-v2 | Pod ごとに firecracker を起動し、VM の中の agent とやり取りする | ノード |
| firecracker | AWS が公開している VM の管理プログラム。VM の起動を受け持ち、ディスクやネットワークの仮想デバイスを VM に見せる | ノード（Pod ごとに 1 つ） |
| Nitro Hypervisor | ノードが差し出したメモリと CPU で VM を作り、VM どうしとノードを隔離する | ノードの下（ノード自身もこの上で動く） |
| nitro-sandbox-agent | VM の中の自分の containerd でコンテナを起動し、Pod ごとの Cedar policy を守らせる | VM の中 |

Cedar は、AWS が公開しているアクセス制御の言語です。Nitro Sandbox では、その Pod がどのイメージをどの引数で起動してよいか、exec やログを許すかを Cedar で書き、Pod の annotation に付けます。以下、これを policy と書き、IAM や KMS の「ポリシー」と区別します。shim と VM の間は、virtio という仮想デバイスの規格と vsock という内部の通信経路でつながります。firecracker の役割は、[EC2 のユーザーガイド](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/amazon-ec2-nitro-sandboxes.html)に書かれています。

Pod を 1 つ起動すると、次の順で進みます。番号は図の番号と同じです。

1. Pod の定義に `runtimeClassName: isolated-sandbox`（または `confidential-sandbox`）が書かれています。
2. shim が firecracker を起動します。
3. Nitro Hypervisor が、ノードが差し出したメモリから VM を作り、VM の中で専用のカーネルが起動します。
4. VM の中の agent が、Pod に付いた policy で、どのイメージやどの操作を許すかを確かめます。
5. コンテナが VM の中で起動します。

![ノードの上の kubelet、containerd、shim、firecracker と、その隣の Nitro Sandbox の中の agent、policy の確認、コンテナ、下の Nitro Hypervisor を、起動の順に 1 から 5 の番号で示した図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/0ed37fa99f3fa0/zenn/articles/0ed37fa99f3fa0/components.png)
*Pod が runtimeClassName を指定したときに起動する部品と、その順番*

## 試す手順

isolated のモードなら、Pod の定義に足すのは `runtimeClassName` の 1 行です。利用者のコードを動かすなら、後の「2 つのモード」で書く理由で `automountServiceAccountToken: false` も足します。

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-app
spec:
  runtimeClassName: isolated-sandbox
  automountServiceAccountToken: false
  containers:
  - name: main
    image: public.ecr.aws/amazonlinux/amazonlinux:2023
    command: ["sleep", "3600"]
    resources:
      limits:
        cpu: "1"
        memory: 512Mi
```

Nitro Sandbox には Kubernetes 1.36 以降が要ります。[isolated の始め方のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-isolated-setup.html)は、Auto Mode のクラスタを使う方法を勧めていて、eksctl なら版を明示して作ります。

```bash
export CLUSTER_NAME=sandbox-demo
export AWS_REGION=ap-northeast-1
eksctl create cluster --name "$CLUSTER_NAME" --region "$AWS_REGION" --version 1.37 --enable-auto-mode
```

[公式のサンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc/examples/getting-started/hello-sandbox)によると、既定の NodePool のままでも、sandbox の Pod が来ると Auto Mode が sandbox に対応したノードを起動します（"Auto Mode brings up a sandbox-capable node if none is available"）。既定の NodePool は x86 なので、このとき起動するのは x86 のノードです。今回は NodePool を足した構成で確かめました。Pod が Pending のままなら、`kubectl describe pod` のイベントと、ノードの `eks.amazonaws.com/nitro-sandbox` のラベルを見ます。

上の Pod を `manifest.yaml` として保存して apply し、Pod の中の `boot_id` とカーネルのビルドを見ます。通常の Pod で同じコマンドを実行した値と違えば、sandbox の中で動いています。カーネルの版の番号はノードと同じになることもあるので（[公式のサンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc)にその例があります）、`uname -r` ではなく、ビルドの番号と日時まで出す `uname -rv` で比べます。

```bash
kubectl apply -f manifest.yaml
kubectl wait pod/my-app --for=condition=Ready --timeout=300s
kubectl exec my-app -- sh -c 'uname -rv; cat /proc/sys/kernel/random/boot_id'
```

動かせる場所には制限があります。Fargate や Hybrid Nodes では使えず、Auto Mode でも構成によっては sandbox のノードが作られません。詳しくは[使える場所と制限](#使える場所と制限)にまとめました。

## Auto Mode 以外と Deployment で使うとき

- Auto Mode を使わないノードグループでは、sandbox のランタイムを入れた AMI と、起動テンプレートで Nitro Enclaves を有効にする設定 `EnclaveOptions.Enabled=true` が要ります。Nitro Enclaves は、インスタンスからメモリと CPU を切り出してインスタンスの隣に隔離された環境を作る機能で、Nitro Sandbox はこれを土台にしています。RuntimeClass も最初からは無いので自分で作り、ノードには sandbox 用のラベルを付けます。Ubuntu のノードの例では、ラベルが 2 つ要り、Cilium で kube-proxy を置き換えるなら追加の設定も要ります。詳しくは[公式のサンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc)を参照してください。
- Auto Mode の既定の NodePool `general-purpose` は x86 のインスタンスだけを使います。今回のクラスタの設定と[公式のサンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc)で確認しました。Graviton で動かすには、arm64 を許す NodePool を足します。
- Deployment などで Pod を作る場合は、`runtimeClassName` と、この記事で後に出てくる `sandbox.amazonaws.com/` で始まる annotation を、Pod テンプレート `spec.template` の側に書きます。Deployment 自身の `metadata.annotations` に書いても Pod には写されず、何も起きません。confidential の policy を Deployment で使えるかは確かめていません。詳しくは「policy の作り方」の末尾を参照してください。

この記事で足した NodePool は次のとおりです（m8i も同じ形）。Pod の側では `nodeSelector` に `exp-pool: g5` を書いて、このノードに置きます。

```yaml
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: g5
spec:
  template:
    metadata:
      labels:
        exp-pool: g5
    spec:
      nodeClassRef:
        group: eks.amazonaws.com
        kind: NodeClass
        name: default
      requirements:
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["on-demand"]
        - key: node.kubernetes.io/instance-type
          operator: In
          values: ["m9g.xlarge"]
```

## VM の大きさは requests で決まる

sandbox の Pod には、必ず requests を書きます。VM の大きさは Pod の limits には左右されず、requests をもとに決まり、メモリは起動時に全部を確保するからです。実機では、VM のメモリは requests に RuntimeClass の上乗せ分を足した量に近く、そこからカーネルの取り分が引かれた値に見えました。上乗せ分は isolated では 256Mi で、次の段落で説明します。requests を書かない Pod の VM のメモリは、カーネルから見て約 145 MiB（公式のサンプルでは約 130 MiB）でした。要求 512Mi・上限 2Gi の Pod では、カーネルから見て約 647 MiB でした。[公式のサンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc)は、requests が無くメモリが足りない Pod が、ログを残さずに落ちる例を挙げています。「試す手順」の例のように limits だけを書いた場合は、Kubernetes が requests にも同じ値を入れます。

EKS Auto Mode のクラスタには、2 つの RuntimeClass が最初からあります。中身を見ると、Pod 1 つごとに `eks.amazonaws.com/nitro-sandbox` という拡張リソースを 1 つ使い、メモリを isolated では 256Mi、confidential では 512Mi 余分に予約する設定でした。この上乗せ分は、Kubernetes の Pod Overhead の仕組みで、スケジューリングのときに Pod の要求に足して数えられます。m9g.xlarge（4 vCPU）のノードは、拡張リソースの空きを 20 と表示しました。[制限事項のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-limitations.html)の「sandbox の個数はノードの vCPU の数の 5 倍まで」と一致します。

# 2 つのモード

2 つのモードの違いは、ノードを信頼するかどうかです。isolated はノードを信頼し、怪しいワークロードからノードと他の Pod を守ります。confidential はノードを信頼せず、ノードの管理者や乗っ取られたノードからワークロードのデータを守ります。次の表は、[EKS ユーザーガイド](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing.html)と [confidential の設定のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-confidential-setup.html)にある、組み込みの設定の既定値の整理です。policy を生成するときの指定で、exec を一部だけ許したり、digest の固定を署名の確認に置き換えたりもできます。実機で確かめた結果は、後の節に書きます。

| 項目 | isolated-sandbox | confidential-sandbox |
|---|---|---|
| 信頼しないもの | Pod の中のワークロード | ノード |
| policy | 無くてもよい。付けなければ、すべてを許す組み込みの既定が使われる。[confidential の設定のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-confidential-setup.html)を参照 | 必須。中身から計算した識別子であるイメージの digest、引数、環境変数、マウントなどを固定する |
| exec と stdin | 使える | 拒否される |
| ログ | 読める | 既定では読める（拒否する設定もある） |
| コンテナの書き込み層（イメージには無く、コンテナが動いている間に作ったり書き換えたりしたファイルが入る領域） | 暗号化しない | VM の中で暗号化する |
| Kubernetes の ServiceAccount トークン | isolated のプロファイルで作った policy なら渡らない。policy を付けないと渡る（下の注意） | 渡る |

:::message
isolated の Pod に policy を付けないと、ServiceAccount トークンが VM の中に渡ります。[EKS ユーザーガイド](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing.html)は、isolated ではトークンを「VM の中に複製しない」と書いています。実機でも、`--profile isolated` で作った policy を付けた Pod にはトークンがありませんでした。一方、policy を付けない Pod ではすべてを許す既定が使われ、`/var/run/secrets/kubernetes.io/serviceaccount/token` があり、それを使って API サーバーに問い合わせると、その Pod の ServiceAccount として認証されました（権限を与えていないので、操作は 403 で拒否されました）。利用者のコードを動かす Pod では、policy を付けるか、`automountServiceAccountToken: false` を書きます。
:::

## confidential で秘密を受け取る仕組み

confidential では、秘密のデータを KMS（AWS の鍵の管理サービス）の鍵で暗号化しておき、承認した policy で起動したことを証明できる Pod にだけ、復号を許します。受け持ちは次のとおりです。

| 登場するもの | 受け持ち |
|---|---|
| 鍵の管理者 | 復号を許す条件を、KMS のキーポリシー（その鍵を誰がどう使えるかの規則）に書く |
| sandbox の VM | 起動時に、自分の policy のハッシュなどを PCR というレジスタに記録する。ノードは、この記録とアテステーションを偽れない（[セキュリティモデルのページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-security-model.html)） |
| Nitro | VM の記録に署名した文書（アテステーション）を作る |
| KMS | アテステーションの署名と記録を確かめ、キーポリシーの条件に合うときだけ復号する |

許可の文の条件の部分は、たとえば次の形です。PCR17 の値は、今回の試験で genpolicy が出した予測値です。

```json
"Condition": {
  "StringEqualsIgnoreCase": {
    "kms:RecipientAttestation:PCR17": "128d66d847a8767e70b52b23cfe1839ab55a45512e5087bc51dbc92a2d5d06d5197980ede432ee0f6b3192204dc2f5fe",
    "kms:RecipientAttestation:PCR8:ServiceName": "eks.amazonaws.com"
  }
}
```

流れは次のとおりです。

1. 準備として、鍵の管理者がキーポリシーに条件を書きます。PCR17 には policy のハッシュが、PCR8 にはゲストの起動イメージに署名した証明書の計測値が入ります。PCR8 は `:ServiceName` を付けると証明書に記録されたサービス名で比べられるので、「PCR17 が承認した値で、PCR8 の署名者が `eks.amazonaws.com`（EKS の Nitro Sandbox）であること」を条件にします。
2. VM は起動時に、Pod の policy のハッシュを PCR17 に書き込みます。
3. VM の中のプログラムは、鍵の組を作り、その公開鍵と PCR の値に Nitro の署名を付けたアテステーションを、KMS への復号の依頼に添えます。
4. KMS は条件に合えば、平文をそのまま返さず、その公開鍵で包んで返します。途中を通るノードには読めません。policy を変えた Pod は PCR17 が変わるので、復号できません。

キーポリシーの書き方には、[公式のサンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc/examples/confidential)が挙げている注意があります。

- KMS の鍵は、既定のキーポリシーで作ると条件を書く前から復号できる状態になるので、最初から条件付きのポリシーで作ります。
- 条件に合わないものを拒否する文は、PCR17 と PCR8 で分けます。1 つの文にまとめると、両方が合わないときにしか拒否されません。
- 鍵の管理者には `kms:Decrypt` だけでなく `kms:ReEncryptFrom` も与えません。与えると、条件の無い別の鍵で包み直せます。
- 条件には PCR8 の生の値ではなく、署名者の名前（`PCR8:ServiceName`）を書きます。AWS が署名の証明書を入れ替えると、生の値は変わるからです。

アプリケーションの側では、KMS の鍵をエイリアスではなく ARN で指定します。リージョンなどのメタデータはノードが偽れるので、どのリージョンのどの鍵を使うかは ARN で固定します（[セキュリティモデルのページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-security-model.html)）。

## policy の作り方

policy は、生成ツール `eks-nitro-sandbox-genpolicy` で Pod の定義から作ります。ツールは PCR17 の予測値も出力するので、Pod を動かす前にキーポリシーの条件を書けます。ツールは、AWS が署名して公開している[ランタイムの配布物](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-download-binaries.html)に入っていて、今回はこのページからダウンロードし、署名を確かめて使いました。confidential の Pod は、たとえば次のように書きます。

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-conf
spec:
  runtimeClassName: confidential-sandbox
  enableServiceLinks: false
  containers:
  - name: main
    image: public.ecr.aws/amazonlinux/amazonlinux:2023
    command: ["sleep", "3600"]
    resources:
      limits:
        cpu: "1"
        memory: 512Mi
```

これを `conf.yaml` として保存し、次のように実行すると、policy の base64 の文字列と PCR17 の予測値が出力されます。base64 の文字列を Pod の `sandbox.amazonaws.com/policy` という annotation に付けて apply します。

```bash
eks-nitro-sandbox-genpolicy --profile confidential conf.yaml
```

policy を作るときの決まりは次のとおりです。

- Pod Identity で AWS の認証情報を使う Pod は `--with-pod-identity` を付けて作ります（IRSA なら `--with-irsa`）。付けないと、Pod は起動しても認証情報のファイルが無く、AWS の呼び出しが失敗します。今回の KMS の試験も、このフラグを付けて作りました。
- `enableServiceLinks: false` を書きます。書かないと、kubelet が足す環境変数を固定できないため、ツールはエラーで止まりました。`--allow-additional-env` で回避することもできますが、その場合は環境変数を厳密には固定しません。
- サイドカーを足す webhook（Pod の作成時に定義を書き換える仕組み）などが書き換えたあとの、最終的な Pod の定義から作ります。
- イメージの更新など、policy が固定している項目を変えたら、policy とキーポリシーの PCR17 の条件を作り直し、Pod も作り直します（動いている Pod の policy の annotation は変えられません）。この手順は CI/CD に組み込みます。
- 作り直しを減らしたい場合は、イメージを digest ではなく AWS Signer の署名者で信頼する policy にします。署名者の指定に加えて `--skip-image-ref-container` で digest の固定を外します。イメージだけを更新するなら policy は変わらず、PCR17 も変わりません。ただし、承認の範囲は「このイメージ」から「この署名者が署名したイメージすべて」に広がるので、署名の権限と、古い版の失効も管理します。署名の確認には、Pod のロールに `signer:GetSigningProfile` と `signer:GetRevocationStatus` という AWS Signer の 2 つの権限が要り、確かめられないと起動を拒否します。詳しくは[公式のサンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc/examples/confidential/signer-policy)を参照してください。

Deployment で confidential を使えるかは確かめていません。今回確かめたのは単体の Pod だけで、名前と引数を変えた Pod は `SetupSandbox` で拒否されました（[confidential の policy と KMS](#confidential-の-policy-と-kms)）。

今回使った組み込みの `confidential` のプロファイルは、VM の中の agent がそのまま受け付けました（同じ定義から作り直しても、PCR17 は同じ値になりました）。[公式のサンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc)には、プレビューの時点のゲストでは受け付けられず、項目を減らしたプロファイルを使ったという記載があり、ツールの公開の配布もプレビューの時点では無かったと書かれています。

# 実機で確かめたこと

## 環境

ノードの側から sandbox がどう見えるかを確かめるため、同じノードに特権付きの通常 Pod（`hostPID: true`、以下「観察用の Pod」）を置き、その中から調べました。クラスタは EKS Auto Mode で、Graviton5 の m9g.xlarge と、比較用に x86 の m8i.xlarge だけを使う NodePool を足しています。特に断らない結果は m9g.xlarge のものです。確かめたのは 2026 年 11 月 10 日から 13 日です。

| 項目 | 値 |
|---|---|
| リージョン | 東京（ap-northeast-1） |
| クラスタ | EKS Auto Mode、Kubernetes 1.37 |
| ノード | m9g.xlarge（Graviton5、4 vCPU、1 コアに 1 スレッド）、m8i.xlarge（4 vCPU、1 コアに 2 スレッド） |
| ノードの OS | Bottlerocket（EKS Auto、Standard）2026.10.31、containerd 2.2.9 |
| ノードのカーネル | 6.18.56 |
| sandbox のカーネル | 6.18.54 |
| コンテナのイメージ | `public.ecr.aws/amazonlinux/amazonlinux:2023` ほか |

今回の Auto Mode は、最初に通常の Pod だけを作ったときには sandbox に対応しないノード（`eks.amazonaws.com/nitro-sandbox=false`）を起動し、sandbox の Pod を作ると、別に対応したノード（`true`）を起動しました。通常の Pod は sandbox のノードにも置けて、この記事の比較は、通常の Pod と sandbox の Pod を同じ sandbox のノードに並べて行っています。

## カーネルとプロセスが分かれている

sandbox の Pod は、ノードのカーネルの上で動くプロセスではなくなります。sandbox の Pod 3 つと通常の Pod 2 つを置いたノードで、観察用の Pod からプロセスを一覧すると、firecracker と Pod ごとの shim が sandbox の数と同じ 3 つずつ見えました（ほかに全体で共通の shim が 1 つ）。`sleep` は、観察用の Pod 自身のものを除くと通常の Pod の 2 つだけが見え、sandbox の中で動いている `sleep` は見えませんでした。

sandbox の Pod の中からノードのプロセスが見えるかも確かめました。sandbox の Pod に `hostPID: true` を付けると、見えたのは VM の中の init、agent、自分の `sleep` などで、ノードのプロセスは見えませんでした。`hostNetwork: true` の Pod は、`hostNetwork is not supported for nitro-sandbox pods` というエラーで起動しませんでした。hostPID と hostNetwork の結果は、どちらも[制限事項のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-limitations.html)の記載どおりです。

カーネルのログも分かれていました。特権付きの sandbox の中でカーネルのログに目印の行を書き込むと、sandbox の中の `dmesg` には出て、ノードのカーネルのログ 1,455 件には出ませんでした。さらに、sandbox の中でカーネルを意図的に止めても（`echo c > /proc/sysrq-trigger`）、同じノードの他の sandbox 2 つとノードは `boot_id` が変わらず、そのまま動き続けました。

## ノードの root から探したもの

ノードの root（観察用の Pod）が `/proc` からプロセスのメモリを探しても、読めた範囲に sandbox のメモリの中身はありませんでした。コンテナの書き込み層のディスクの中身は、isolated では見つかり、confidential では見つかりませんでした。

確かめ方は、目印の文字列を Pod の中でメモリとディスクに大量に書き、観察用の Pod から探すというものです。目印は、Pod の定義に書いた元の文字列（種）を、Pod の中で SHA-256 にかけて作ります。Pod の定義はノードにも届くので、種をそのまま目印にすると、ノードが持っている定義の写しを見つけてしまうからです。ハッシュにした目印は、Pod の中で計算されるまでどこにも現れません。

![通常の Pod、isolated、confidential の 3 列で、プロセス、メモリ、ディスク、カーネルのログのそれぞれをノードから見つけられたかを並べた図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/0ed37fa99f3fa0/zenn/articles/0ed37fa99f3fa0/node-read.png)
*ノードの root から、Pod の中で作った目印（図の marker）を探した結果*

メモリは、通常の Pod なら簡単に読めました。観察用の Pod から、通常の Pod のシェルのメモリを探すと、目印が 129,072 回見つかりました。sandbox では、ノード上でメモリを読めたプロセスを全部探しても、目印は 0 回でした。isolated の試験では 36 プロセスの 3,162 MiB、confidential の試験では 32 プロセスの 3,209 MiB を探しました。デバイスをマップした領域はこの走査から外し、そのうち読める共有領域だけを別に探しました（次の段落）。isolated では、sandbox の中のメモリ上のファイル（tmpfs）に目印が 516,222 行あることも、Pod の中から確かめています。exec を拒否する confidential では中から数えられないので、目印を書き終えたあとに出すログの行で、書き込みが済んだことを確かめました。

firecracker の中を見ると、VM のメモリにあたると考えられる大きな領域は `/dev/nitro_enclaves` をマップしたもので、読み書きの権限がありません（`---s`）。仮想デバイスとのやり取りに使う読める共有領域も探しました。大きさは sandbox 1 つあたり約 62 MiB です。11 月 10 日の走査で確かめられたのは confidential の目印の Pod の分で、目印はありませんでした。isolated については、11 月 13 日に、目印を書いた isolated の Pod を作り直して同じ走査をすると、その Pod の firecracker の共有領域にも、読めるプロセスのメモリ全体（32 プロセスの 3,274 MiB）にも、目印は 0 回でした。

:::message alert
同じことを試すときは、捨ててよいノードで行ってください。VM のメモリにあたる領域を `/proc` から無理に読もうとした 1 回目の試みでは、読み取りが 10 分経っても返らず、同じノードの通常の Pod への exec まで固まったので、ノードを作り直しました（再現は試していません）。プロセスのメモリを走査するような監視エージェントをノードに入れている場合も、sandbox のノードに載せる前に検証用のノードで確かめておくと安全です。
:::

ディスクでは、2 つのモードの差がはっきり出ました。確かめたのは平文の目印が見つかるかどうかで、暗号の方式や改ざんへの強さは確かめていません。起動時に 16 MiB 分の目印をファイルに書く Pod を作ると、isolated では、ノード上にあるその Pod の書き込み層の実体のファイル `overlay.img` から目印が 258,111 回見つかりました。これは 16 MiB を 1 行 65 バイトで割った行数と同じで、書いた量のすべてです。confidential では 0 回でした。isolated は書き込み層を暗号化しないので、ノードからディスクの中身が読めます。ノードを信頼する isolated の前提のとおりです。一方、confidential の Pod に付けた policy そのものは保存していませんが、同じ定義から作り直した policy は、書き込み層の暗号化（`integrity-memory`）を要求していました。

[セキュリティモデルのページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-security-model.html)は、「ノードはゲストのメモリを読み書きできない」と書いています。今回の結果はこれと矛盾しません。

## confidential の policy と KMS

この節では 2 つのことを確かめます。1 つ目は、policy と食い違う Pod はコンテナが起動しないこと、2 つ目は、起動できる Pod でも、KMS が承認していない policy なら秘密を復号できないことです。

confidential では、policy が固定している項目（イメージの digest、引数、環境変数、マウントなど）が Pod と違うと、コンテナが起動しません。名前を変えたときの挙動と分けるため、まず名前は同じにして確かめました。policy を生成したあと、同じ名前のまま引数だけを変えた Pod を作ると、VM は起動したものの、VM の中の agent が `policy denied Agent::Action::"CreateContainer"` でコンテナの起動を拒否しました。名前と引数の両方を変えた Pod は、その手前の `policy denied SetupSandbox` で止まりました。policy が Pod の名前（hostname）も固定しているためと考えられます。動いている Pod への `kubectl exec` は `policy denied Agent::Action::"Exec"` で拒否され、ログは読めました。

KMS の側は、[公式のサンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc/examples/confidential)のキーポリシーの形をそのまま使って確かめました。Pod に EKS Pod Identity（Pod ごとに IAM ロールを割り当てる EKS の機能）で割り当てる IAM ロールには、IAM のポリシーを 1 つも付けません。キーポリシーには、PCR17 が承認した policy の値で、かつ PCR8 の署名者が EKS のときだけ、このロールに復号を許すと書きます。それ以外の復号は、誰からのものでも拒否します。そのうえで、暗号文 1 つを 3 つの Pod で復号させました。

![genpolicy が出した PCR17 の予測値を KMS のキーポリシーに書き、承認した Pod、環境変数を変えた Pod、同じロールの通常の Pod の 3 つが復号を試した結果を並べた図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/0ed37fa99f3fa0/zenn/articles/0ed37fa99f3fa0/attestation.png)
*PCR17 の条件を書いたキーポリシーと、3 つの Pod の復号の結果*

承認した Pod は復号に成功し、平文のハッシュも一致しました。環境変数を 1 つだけ変え、その定義から正しく作り直した policy を付けた Pod は、`AccessDeniedException` で拒否されました。genpolicy が出した PCR17 の予測値は、承認した Pod と別の値になっていました。同じロールを使う通常の Pod も拒否されました。通常の Pod には、アテステーションを作るデバイス（`/dev/nsm`）がありません（isolated の Pod にはありましたが、isolated の Pod で復号を試してはいません）。ロールの認証情報を持っているだけでは復号できず、承認した policy の計測値を KMS に示して初めて復号できる、という形を実際に確かめられました。PCR17 が固定するのは policy で、policy が許すイメージの中で動くコードが安全かどうかまでは保証しません。秘密を扱う処理と、利用者から受け取った任意のコードは、同じ VM に置かないようにします。なお、PCR の条件を書いたキーポリシーでも、キーポリシーを書き換えられる鍵の管理者は残ります。信頼しないのはノードであって、鍵の管理者ではありません。

## ネットワークを切る

Pod に `sandbox.amazonaws.com/network-isolated: "true"` を付けると、VM の外とつながるネットワークインターフェースを持たない VM として起動します（[ネットワーク分離のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-network-isolation.html)）。通信を遮るのではなく、インターフェースそのものが無い状態です。

```yaml
metadata:
  annotations:
    sandbox.amazonaws.com/network-isolated: "true"
spec:
  runtimeClassName: isolated-sandbox
```

実機では、この Pod にあるのはループバックと停止中の `dummy0` だけで、経路表は空でした。外への HTTPS は名前解決の段階で失敗し、インスタンスメタデータ（IMDS、EC2 がインスタンスの情報を返す仕組み）にもつながりませんでした。一方で `kubectl logs` と `kubectl exec` は使えました。ログや exec は、VM とノードの間の vsock という別の通信経路を通るからです。ネットワーク分離のページによると、この vsock は VM の中のどのプロセスも使え、ノード側でも firecracker の vsock のソケットに触れられるプロセスなら、VM の中で待ち受けているポートに接続できます。完全な遮断ではありません。また、ネットワークを切った Pod では Pod Identity の認証情報も使えないので、KMS を使う暗号化したイメージや、AWS Signer による署名の確認も使えません。

ネットワークを切らない sandbox から IMDS に問い合わせると、リージョン、アベイラビリティーゾーン、パーティションは返り、インスタンス ID と IAM の認証情報は 404 でした。制限事項のページも、sandbox の IMDS が返すのはリージョン、アベイラビリティーゾーン、その ID、サービスのドメイン、パーティションの 5 つだけで（今回確かめたのはそのうち 3 つ）、AWS の認証情報は Pod Identity で渡すと書いています。

## 運用で効く数字と注意

sandbox で測った、起動の時間、通信の上限、CPU の取り分、障害の見え方を順に書きます。既存の Pod を移すときに引っかかる機能の一覧は、次の節の[使える場所と制限](#使える場所と制限)にまとめました。

### 起動にかかる時間

Pod を作ってから準備完了になるまでの時間を、各 10 回測りました。Kubernetes の API が Pod に記録する作成時刻と準備完了の時刻の差は、1 秒刻みで、通常の Pod が 0〜1 秒、isolated が 3〜4 秒（中央値 3.5 秒）、confidential が 5〜8 秒（中央値 7 秒）でした。Pod の CPU の要求は 0.5、メモリは 256Mi です。イメージはノードにある状態で、ノードの起動待ちは含みません。[公式のサンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc)には、kubectl の往復を含めて測った 3.2〜3.7 秒という値と、条件の書かれていない約 5〜6 秒という値、m5a.xlarge の上の CPU 1・メモリ 2 GiB の Pod で 19 秒という値（大半が sandbox の作成とゲストの起動と説明されている）が載っています。Pod の大きさと起動時間の関係は、今回は確かめていません。起動待ちを避けたい場合は、先に起動しておいた sandbox を割り当てるウォームプールの[サンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc/examples/getting-started/warm-pool)があり、割り当ては 1 秒未満と書かれています。手元の kubectl から測った待ち時間は、東京との往復の揺れが大きく、通常の Pod と isolated の差を見分けられなかったので使っていません。

### 既定の帯域とパケット数の上限

sandbox には、Pod ごとの帯域とパケット数に[既定の上限](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-resource-isolation.html)があります。帯域は 100 Mbps、パケット数は毎秒 1,500 個です。同じノードの通常の Pod を相手に、Alpine 3.20 の iperf3 で測ると、次のようになりました。TCP は送信と受信をそれぞれ 30 秒、UDP は 1,400 バイトのパケットを 300 Mbps で 20 秒送り、受信側で測った値です。

| sandbox の設定 | TCP 送信 | TCP 受信 | UDP 送信 |
|---|---|---|---|
| 既定のまま | 99.9 Mbps | 99.9 Mbps | 17.7 Mbps（毎秒約 1,580 個） |
| 帯域だけ 1G に上げる | 750 Mbps | 690 Mbps | 18.2 Mbps（毎秒約 1,620 個） |
| 帯域を 1G、パケット数を毎秒 15,000 個に上げる | 997 Mbps | 998 Mbps | 176 Mbps（毎秒約 15,700 個） |

帯域だけ上げた TCP の 750 Mbps は、同じノードの Pod どうしで 1 回測った値です。ドキュメントと公式のサンプルは、この場合を約 100 Mbps と書いていて、今回の結果と違います（下の折りたたみ）。既定のままで負荷試験をすると、sandbox の性能ではなく、この上限を測ることになります。上げるときは、帯域とパケット数の両方を Pod の annotation で指定します。小さな RPC のように小さいパケットが多い通信は、帯域より先に毎秒 1,500 個の上限に当たるからです。DNS には別に毎秒 100 クエリの上限があります。annotation は Pod の作成時に一度だけ読まれます。

```yaml
metadata:
  annotations:
    sandbox.amazonaws.com/ingress-bandwidth: "1G"
    sandbox.amazonaws.com/egress-bandwidth: "1G"
    sandbox.amazonaws.com/ingress-packets-per-second: "15000"
    sandbox.amazonaws.com/egress-packets-per-second: "15000"
```

:::details 帯域だけ上げたときの TCP の結果
ドキュメントは「片方だけ上げても効果はない」と書き、9,001 バイトの MTU で毎秒 1,500 個なら約 102 Mbps になると書いています（単純に掛け算すると約 108 Mbps）。1,400 バイトの UDP ではそのとおりでしたが、TCP では帯域だけ上げても 750 Mbps 出ました。1 個あたりの大きさに直すと次のとおりです。

$$
\frac{750 \times 10^6\ \text{bit/s}}{1500\ \text{packets/s}} \div 8 \approx 62.5\ \text{KB/packet}
$$

これは、TCP が複数のパケットを大きな単位にまとめて扱うときの大きさ（最大 64 KB）に近い値です。パケット数が、MTU の大きさのパケットではなく、まとめた単位で数えられているのではないかと推測しています。なお、[公式のサンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc)は、帯域だけ上げた場合の値を 100 Mbps 付近と書いています。今回の同じノードの Pod どうしの TCP の測定はそうなりませんでしたが、通信先や経路によって変わる可能性があります。
:::

### CPU の取り分

CPU を使い切る処理では、sandbox の Pod は通常の Pod とほぼ同じスループットで動きました。1 コアに 2 スレッドの x86 のインスタンスでは、4 個を同時に置くと 1 個あたりの処理量が約半分になりましたが、これは通常の Pod でも同じでした。

測り方は次のとおりです。CPU を使い切る Python のループを 20 秒回し、その間に進んだ回数を、通常の Pod と sandbox の Pod で比べました。各 Pod の CPU は要求 0.8、上限 1 にそろえ、同じノードに 1 個または 4 個を同時に置いて、各 3 回の中央値を取っています。値は、同じノードの通常の Pod 1 個の回数を 1 とした比です。

| ノード | 通常 1 個 | sandbox 1 個 | 通常 4 個（合計） | sandbox 4 個（合計） |
|---|---|---|---|---|
| m9g.xlarge（4 コア、1 コアに 1 スレッド） | 1.00 | 0.95 | 3.94 | 3.75 |
| m8i.xlarge（2 コア、1 コアに 2 スレッド） | 1.00 | 0.99 | 2.07 | 1.96 |

1 個のときの差は、m9g で 5%、m8i で 1% です。これは sandbox 1 個の 3 回の値の幅（m9g で 0.91〜1.01、m8i で 0.83〜1.00）に収まります。4 個を同時に置いたときは、3 回とも sandbox のほうが 3〜6% 低くなりました。中央値どうしでは約 5% の差です。m8i では、4 個の合計が通常の Pod 1 個の約 2 倍（通常の Pod で 2.07、sandbox で 1.96）で、どちらも同じ傾向です。物理コアが 2 つで、この処理では 1 コアの 2 つ目のスレッドがほとんど上乗せにならないためと考えられます。制限事項のページは、1 コアに 2 スレッドのインスタンスでは、2 つの sandbox が同じコアのスレッドを同時に使わないように制御されるので、sandbox が使える計算量はおよそ物理コアの数までになると書いています。この処理は通常の Pod でも物理コア 2 つ分で上限になるので、その制御の影響はこの測定には表れません。同じページは、sandbox の CPU を 2 vCPU 単位で要求するか、Graviton のように 1 コアに 1 スレッドのインスタンスを選ぶことを勧めています。

### カーネルが止まっても Pod は「動いている」ままになる

ネットワークのある sandbox の Pod には、HTTP の liveness probe を付けておくのが安全です。sandbox の中でカーネルを止めると、Kubernetes 上の Pod は `Running` で準備完了のまま残りました。試した 3 通り（probe なし、exec、HTTP）のうち、検知できたのは HTTP の probe だけでした。検知できた HTTP の probe は、次の設定です。exec の probe も、同じ間隔で `cat /proc/uptime` を実行する形で試しました。

```yaml
livenessProbe:
  httpGet:
    path: /
    port: 8080
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 2
```

probe を付けない Pod では、約 6 分経っても再起動されず、exec だけが返らない状態でした。exec の liveness probe を付けても、probe は「失敗」ではなく「エラー」（状態不明という扱い）になり、約 8 分、471 秒経っても再起動されませんでした。HTTP の liveness probe を付けた Pod では、約 50 秒で再起動して準備完了に戻り、`boot_id` も新しくなりました。準備完了のまま残る間は、Service の振り分け先からも外れないと考えられます（確かめてはいません）。ネットワークを切った Pod では HTTP と TCP の probe が使えず、ネットワーク分離のページは exec の probe を勧めていますが、ネットワークのある Pod で試した今回の止まり方は、exec の probe では検知できませんでした。ネットワークを切った Pod でも同じかは確かめていません。

# 使える場所と制限

表の内容は、2026 年 11 月 13 日にドキュメントで確かめたものです。Nitro Sandbox は EC2 のインスタンスの機能で、EKS のほかに ECS や EC2 から直接も使えます。この記事の isolated と confidential は EKS の RuntimeClass のモードで、EC2 から直接使うときのモードである confidential と direct とは別です。EC2 の direct モードでは、ノードが VM のメモリを読めて、アテステーションもありません。詳しくは[EC2 のユーザーガイド](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/amazon-ec2-nitro-sandboxes.html)を参照してください。この記事の結果を direct モードに当てはめることはできません。EKS で使えるのは、EC2 のインスタンスで動くノード（Auto Mode、マネージドノードグループ、セルフマネージドノード）だけです。Pod の機能にも、通常の Pod と違う制限がいくつもあります。導入を決める前に確かめる点を、まず動かせる場所、次に Pod の機能の順にまとめます。

| 動かせる場所 | 使えるか | 根拠 |
|---|---|---|
| EKS Auto Mode | 使える。RuntimeClass が最初からあり、sandbox のノードも自動で起動する | [isolated の始め方のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-isolated-setup.html)、実機 |
| EC2 のマネージドノードグループ、セルフマネージドノード | 使える。sandbox のランタイムを入れた AMI、起動テンプレートで Nitro Enclaves を有効にする設定、RuntimeClass の作成、ノードのラベルが要る | isolated の始め方のページ |
| Hybrid Nodes（オンプレミスのサーバーを EKS につなぐ形） | 使えない。ドキュメントの記載からの判断で、実機では試していない | Nitro Sandbox は対応する EC2 のインスタンスタイプでしか動かない。[EKS ユーザーガイド](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing.html)を参照 |
| Fargate | 使えない | 実機では、sandbox の Pod は `Fargate profile ... cannot satisfy pod's node selector/affinity requirements` で Pending のままだった。同じプロファイルの通常の Pod は動いた |
| Kubernetes の版 | 1.36 以降 | isolated の始め方のページ |
| インスタンスタイプ | Nitro Enclaves に対応するものの一部。多くのファミリーで最小のサイズと metal は対象外 | [EC2 のユーザーガイド](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/amazon-ec2-nitro-sandboxes.html) |
| Auto Mode で sandbox のノードを作らない構成 | FIPS 用の AMI、GPU や Neuron 用の AMI、複数の NUMA を持つインスタンスタイプ、まだ検証されていないインスタンスタイプ。発表の時点では r5a、r5ad、m5ad も一時的に対象外。いずれも Pod は Pending のまま | [制限事項のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-limitations.html) |
| GPU などのデバイスの受け渡し | 使えない | 制限事項のページ |

次は、Pod の機能の制限です。特に断りの無いものは制限事項のページの記載で、ほかのページの記載や実機で確かめたものはそう書いています。

| Pod の機能 | sandbox での扱い |
|---|---|
| `hostNetwork: true` | 起動しない（実機でも確かめた） |
| `hostPID: true`、`hostIPC: true` | 起動するが、見えるのはその VM の中だけ（hostPID は実機でも確かめた） |
| ユーザー名前空間（`hostUsers: false`） | sandbox の Pod では起動しない（制限事項のページは isolated-sandbox のノードと書いている） |
| VM の中のユーザー名前空間 | sandbox のカーネルは `max_user_namespaces` が 0（実機で確かめた）。[公式のサンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc)によると、bubblewrap のように中でユーザー名前空間を作るツールはそのままでは動かない |
| VM の大きさ | requests で決まり、あとから変えられない。requests が無いと小さい既定の大きさになる（実機で約 145 MiB） |
| EBS のボリューム | 1 つのボリュームを複数の Pod で共有できない。`ReadWriteOncePod` を使う。動いている Pod のボリュームは拡張できない。1 つの PVC は 1 つの Pod の中の 1 つのコンテナにだけ、1 つのパスでマウントする（[公式のサンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc)） |
| CPU とメモリのその場での変更 | できない。作り直す |
| kubelet の CPU Manager の `static` | 効かない |
| `kubectl port-forward` | `127.0.0.1` だけで待ち受けるサーバーには届かない |
| `emptyDir` と書き込み層の使用量 | kubelet からは 0 に見える。上限は `ephemeral-storage` の requests と limits で決める |
| IMDS | リージョンなど 5 つの項目だけ。IAM の認証情報は返らない（実機でも確かめた） |
| 一部だけ暗号化したイメージ | 使えない。暗号化するなら全部の層 |
| Pod ごとの既定の上限 | 下の表 |
| 1 つのノードの sandbox の数 | 個数も vCPU の合計も、ノードの vCPU の数の 5 倍まで。CPU をオーバーコミットするインスタンスタイプでは個数の上限が半分 |
| 1 コアに 2 スレッドのインスタンス | 2 つの sandbox が同じコアを同時に使わないように制御され、使える計算量はおよそ物理コアの数まで |
| ネットワークを切った Pod | Pod Identity の認証情報、暗号化したイメージ、AWS Signer による署名の確認が使えない。HTTP と TCP の probe も使えない。EFS と S3 Files はマウントできないが、EBS は使える（公式のサンプル）。参照: [ネットワーク分離のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-network-isolation.html)、[confidential の設定のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-confidential-setup.html) |
| ノードに置くランタイム監視 | sandbox の中は見えない。[監視のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-observability.html)の記載で、実機でも確かめた。詳しくは[セキュリティ運用で何が変わるか](#セキュリティ運用で何が変わるか)を参照 |
| Ubuntu のノード | sandbox の Pod に `appArmorProfile.type: Unconfined` が要る（[公式のサンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc)。AppArmor の無い Amazon Linux 2023 のノードでは要らない） |
| スナップショットからの復元、ライブマイグレーション | 使えない（制限事項のページ） |

Pod ごとの既定の上限は、Pod の annotation で変えられます。詳しくは[資源の上限のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-resource-isolation.html)を参照してください。接続数を除いては `"disabled"` で外せますが、`"0"` を指定すると Pod が起動しません。

| 上限 | 既定 | annotation（`sandbox.amazonaws.com/` の後ろ） |
|---|---|---|
| 帯域（受信と送信） | 100 Mbps | `ingress-bandwidth`、`egress-bandwidth` |
| パケット数（受信と送信） | 毎秒 1,500 個 | `ingress-packets-per-second`、`egress-packets-per-second` |
| DNS | 毎秒 100 クエリ（512 まで。公式のサンプルによると IP のファミリーごと） | `dns-packets-per-second` |
| 同時の外向き接続 | IP のファミリーごとに 4,096（64〜65,536、無効にはできない） | `conntrack-limit` |
| 書き込み層のディスク | 400 Mbps、1,500 IOPS | `overlay-disk-bandwidth`、`overlay-disk-iops` |
| ログ | 2 Mbps | `log-bandwidth` |

# セキュリティ運用で何が変わるか

Nitro Sandbox は、コンテナの中のコードがカーネルの脆弱性やコンテナからの脱出を使っても、被害がノードと他の Pod に及ぶリスクを下げます。一方、sandbox にすると、ノードに置いたランタイム監視（動いているプロセスやシステムコールを見張る仕組み）からは、sandbox の中が見えなくなります。

sandbox が防ぐのは、VM の中のコードがノードのカーネルやメモリに直接触ることです。テナントどうしの通信、認証情報、共有のストレージ、資源の取り合いは、別の対策で守ります。ノード側の firecracker や仮想デバイスの処理は、VM の中から入力を受け取るので、攻撃される面として残ります。前提は、信頼できないのはコンテナの中のコードで、Pod の定義は信頼できる人が書くことです。守りと見張りのそれぞれで何が変わるかを、層ごとに整理します。

| 層 | 受け持ち | sandbox で変わること |
|---|---|---|
| 隔離 | コンテナからの脱出やカーネルの不具合を、他の Pod とノードに広げない | 境界が共有のカーネルから Nitro Hypervisor に移る。実機では、特権付きのコンテナで sandbox のカーネルを止めても、隣の sandbox とノードはそのまま動いた |
| 監査ログ | Kubernetes の監査ログで誰が何を作ったか、CloudTrail で AWS の API の呼び出しを記録する | ノードの外で記録される仕組みなので、sandbox にしても記録する場所は変わらない。ただし、どちらも VM の中で実行されたコマンドの記録ではない |
| ログとメトリクス | コンテナのログと使用量を集める | kubelet を通るので、CloudWatch のエージェントなどで集められる（[監視のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-observability.html)） |
| ノードのランタイム監視 | ノードのプロセスや cgroup を見張る | sandbox の中は見えない。監視のページは、GuardDuty のランタイム監視のエージェントが sandbox の中の動きを観察できないと書いている。実機でも、ノード側からは sandbox の中のワークロードのプロセスと agent が見つからず、見えたのは firecracker と shim だけだった。GuardDuty の Runtime Monitoring を有効にして試すと、既知の不正な宛先への名前の問い合わせは、通常の Pod では Pod の名前と `curl` というプロセス名つきで検知された。sandbox の Pod からの同じ問い合わせは、ノードで名前解決を中継する `coredns` と `systemd-resolved` の名義でだけ記録され、どの Pod が問い合わせたかは残らなかった |
| Pod の中の監視 | その VM の中の動きを見張る | 同じ Pod に特権付きで `hostPID: true` の監視用コンテナを置くと、その VM のカーネルの上のワークロードのプロセスの一覧が見えた。Falco、Tetragon、auditd は sandbox の中で動かなかったが、Linux に標準の別の仕組みや、Wazuh、Suricata、osquery では、別のコンテナでのプログラムの実行、ファイルの変化、通信が見えた。詳しくは表の下に書く |
| ネットワーク | 通信先を制限する、通信を記録する | NetworkPolicy やセキュリティグループはノードの側で効くので、sandbox の中から外せない。Auto Mode では NetworkPolicy の強制を有効にする設定が要る（表の下） |

隔離と検知は別の軸の対策です。隔離は侵害が Pod の外へ広がる範囲を狭め、検知は侵害に気づくまでの時間を縮めます。sandbox は前者を強めますが、後者の代わりにはなりません。たとえばアプリの脆弱性を突かれてコードを実行されても、攻撃者は sandbox を抜け出す必要がありません。Pod が正当に持つ IAM の権限、データベースへの接続、シークレットだけで目的を果たせるからです。今回の実機の範囲では、sandbox の中で何が実行されたかは、ノードからは記録できませんでした。Pod の中に監視用のコンテナを置けば一部は記録できます。ただし、Falco や Tetragon のようにシステムコールを見張る製品は動かず、使えるのは Wazuh、Suricata、osquery のように、ファイルの変化、通信、プロセスの一覧を見る製品です。

広い権限や機密データを持つ長く動き続ける業務アプリを sandbox に載せるなら、検知の代わりになる対策を組み合わせます。外への通信を既定で拒否すること、IAM の権限を最小にして認証情報の有効期限を短くすること、ルートのファイルシステムを読み取り専用にすること、CloudTrail と監査ログの異常を見張ること、アプリ自身に操作の記録を残させること、Pod を短い時間で作り直すことです。sandbox が最も向いているのは、利用者のコードや AI エージェントの道具の実行のように、中は乗っ取られる前提で、短い時間だけ動き、権限の小さい処理です。

NetworkPolicy を使うときは、次の点に気をつけます。

- Auto Mode では、NetworkPolicy は強制を有効にするまで効きません。実機でも、外への通信をすべて拒否する NetworkPolicy を入れても HTTPS は通り、次の ConfigMap を作ると、作り直した sandbox の Pod の通信が止まりました。

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: amazon-vpc-cni
  namespace: kube-system
data:
  enable-network-policy-controller: "true"
```

- NetworkPolicy を書いても、Pod と自分のノードの間の通信は、どちらの向きも止められません。同じノードの `hostNetwork` の Pod からは、sandbox の中で待ち受けているポートに届くので、VM の中のサービスにも認証を付けます。sandbox の IMDS は VM の中で応答するので、NetworkPolicy の対象外です（[公式のサンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc)）。
- [公式のサンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/blob/43aa7c77150e4a1c456663448b5a7a0180c075fc/examples/confidential/encrypted-image/README.md)には、Pod の起動の直後に NetworkPolicy がまだ効いていない時間があった例が載っています（"a probe in its first seconds can run before the policy is in force"）。今回の試験は、強制を有効にした後に作り直した Pod の、起動から時間が経った時点の通信を見たもので、起動直後の時間は確かめていません。起動直後の通信も止めたい処理では、この点を自分の環境で確かめます。
- 外への通信を既定で拒否するなら、Pod Identity の認証情報の取得先 `169.254.170.23` と DNS を許す必要があります。DNS の 53 番を広く開けると、DNS を使ってデータを持ち出せるので、許す相手はクラスタの DNS に絞ります。名前で許可する書き方（`domainNames`）は、同じアドレスで動く別の名前にも届きます（[公式のサンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc)）。
- 通信が要らない処理はネットワークを切った sandbox で動かせますが、vsock の経路は残ります。

利用者のコードを実行するサービスなら、次のような組み合わせが考えられます。利用者から受け取るのはコードなどの限られた入力だけにし、Pod の定義はサービスの側で作ります。通常の Pod を作れたり、特権や `hostNetwork`、`hostPath` を指定できたり、既存の Pod に exec できたりすると、sandbox の境界を回り込めます。そこで、Pod を作る経路と変える経路をすべて RBAC（Kubernetes の権限の仕組み）で絞ります。`runtimeClassName` の付け忘れなど、Pod の定義の中身の制約は、admission control（Pod の作成時に定義を検査して拒否する仕組み）で強制します。実行環境は isolated の sandbox にし、通信が要らない処理はネットワークも切ります。監査ログとネットワークの記録は引き続き取りますが、VM の中で完結する不正な処理はそこには現れません。ノードに置いていたランタイム監視の代わりにはなりません。同じ Pod に監視用のコンテナを入れれば、後で書くように、プログラムの実行と通信は記録できます。それでも既存の監視製品のようには使えないので、監査ログ、ネットワーク、アプリのログを軸にします。実機で見たとおり、中が止まっても Pod は準備完了のまま残ることがあるので、実行時間の上限、外からの死活の確認、強制的な削除と作り直しの手順も組み合わせます。

Pod の中には、監視だけでなく、もう 1 つの閉じ込めの層も置けます。[公式のサンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc/examples/subagent-security)は、エージェントが起動する道具のプロセスを、sandbox の中で Landlock や seccomp、bubblewrap などでさらに絞る例を挙げています。Landlock と seccomp は特権が要りませんが、bubblewrap はユーザー名前空間が要るので、特権付きの init コンテナでゲストの設定を上げていて、サンプル自身もこの構成を本番の基準にしないよう書いています。どの方法も、通信の制限やデータの持ち出しの対策にはなりません。Nitro の境界は Pod とノードの間にあり、Pod の中のプロセスどうしは分けないからです。

Pod の中に監視を入れるときの注意は次のとおりです。

- sandbox のカーネルには、eBPF の監視ツールの多くが前提にする BTF というカーネルの型情報 `/sys/kernel/btf/vmlinux` がありませんでした。ノードのカーネルにはあります。eBPF は、カーネルの中で小さなプログラムを動かして監視する仕組みです。実際に Falco と Tetragon を isolated の sandbox の中で特権付きで動かすと、どちらも起動できませんでした。Tetragon は BTF が見つからない時点で止まり、Falco は BTF を前提にしない modern eBPF のドライバでも `prog 'BPF_TRACE_RAW_TP' is not supported` というエラーで止まります。`bpftool feature probe kernel` で調べると、`kprobe`、`tracepoint`、`raw_tracepoint`、`tracing`、`lsm` の種類の eBPF プログラムが使えないという判定でした。eBPF ではない昔からの Linux の audit の仕組みも、`auditd` が `Operation not permitted` で起動できず、使えませんでした。BTF を用意するだけでは直りません。カーネルモジュールの読み込みは仕組みとしては許されていましたが、Falco のカーネルモジュールが使う tracepoint の登録関数がカーネルに無いので、この方法でも Falco は動かないと考えられます。
- 一方で、Linux に標準で入っている別の仕組みは動きました。特権付きの監視用コンテナと、特権の無い uid 1000 のワークロードのコンテナを同じ Pod に置き、Pod に `hostPID: true` を付けて確かめた結果が次の表です。確かめたのは x86 のノードで、Graviton では試していません。

| 仕組み | 使ったコマンド | ワークロードのコンテナについて見えたもの | 見えないもの |
|---|---|---|---|
| proc connector | `nsenter -t 1 -n forkstat -e exec` | 実行されたプログラムと引数のすべて。`cp /bin/true /tmp/wl_evil` や `curl ... http://example.com` | ファイルと通信。VM の最初の network namespace に入らないと、何も届かなかった |
| perf のタスクイベント | `perf record -e dummy -a` | 実行されたプログラムの名前と、読み込まれた実行ファイルとライブラリのパス | 引数、ファイル、通信 |
| conntrack | `conntrack -E -e NEW` | 新しい通信の宛先の IP アドレスとポート | どのプロセスの通信か |
| cgroup の eBPF | `cgroup/connect4` のプログラムを `/sys/fs/cgroup` に付ける | `connect` の呼び出しを数えられた。BTF が無いという警告は出るが動く | プログラムを自分で書く必要がある |
| inotify | `inotifywait -m -r /etc /tmp` | ファイルの作成、変更、`/etc/shadow` を開いたこと | どのプロセスか |
| fanotify | `fatrace` | 何も取れない。`Operation not supported` で登録できなかった | すべて |

- 有名な OSS の製品も、同じ構成で試しました。結果は次のとおりです。どれも 1 つの構成で 1 回ずつ試した結果です。

| 製品 | 試した機能 | 結果 |
|---|---|---|
| Wazuh 4.14 | ファイルの変化をその場で見張る FIM。監視先は `/proc/<ワークロードの PID>/root/tmp` | 動いた。ワークロードのコンテナで作ったファイルの追加と変更が、その場で警告になった |
| Suricata 7.0 | Pod のネットワークインターフェースを流れる通信の検査 | 動いた。自分で書いたルールで、不正な宛先への名前の問い合わせと、特定の宛先への HTTP を検知した。標準のルールの検知力は試していない |
| osquery 5.24 | プロセスと通信の一覧 | 動いた。`/tmp` に置いて動かした実行ファイルのパス、引数、uid、通信先が見えた。一覧を定期的に読む方式なので、すぐ終わるプロセスは見逃しうる |
| osquery 5.24 | ファイルの変化の記録 `file_events` | 監視先を `/proc/<PID>/root/...` で指定すると、監視用コンテナ自身のパスに置き換えられて何も取れない。`nsenter` でワークロードのマウント名前空間に入れて起動すると動いた |
| osquery 5.24 | プロセスの実行の記録 `process_events` | 動かない。Linux の audit の仕組みが使えないため |
| Auditbeat 9.5 | ファイルの変化の記録 `file_integrity` | osquery と同じで、`nsenter` でワークロードのマウント名前空間に入れて起動したときだけ動いた |
| ClamAV 1.5 | `clamscan` による手動の検査 | 動いた。ワークロードのコンテナに置いたテスト用のウイルスのファイル EICAR を検出した |
| ClamAV 1.5 | `clamonacc` によるアクセス時の検査 | 検出しない。アクセスの知らせは届くが、ワークロードのコンテナの中のパスを、監視用コンテナの側で開こうとして失敗する |

- 使うときの注意をまとめます。
  - `/proc/<PID>/root` は PID ごとのパスなので、ワークロードのコンテナが作り直されると、監視先を指し直す必要があります。
  - `nsenter` で入れる方法は、ほかのライブラリに頼らない単体の実行ファイルでしか使えず、壊れやすいやり方です。
  - ここで動いたのは、プロセスの一覧、ファイルの変化、通信の検査です。システムコール単位で記録する EDR のような監視は、この記事の範囲では動きませんでした。
  - 監視用のコンテナには特権と `hostPID: true` が要り、Pod ごとに入れます。ワークロードと同じ VM の中にいるので、VM の中で root を取られれば、監視も止められる位置にあります。これは攻撃を防ぐ仕組みではなく、気づくための仕組みです。
  - 確かめたのは x86 のノードだけで、Graviton では試していません。
- 監視用のコンテナにも requests を書き、VM のメモリを見込んでおきます。
- 監視用のコンテナに特権を与えても、カーネルへの影響はその VM の中にとどまります。ただし、持たせた認証情報やマウント、送信先は VM の外に届くので、最小限にします。特権を与えたコンテナには、コンテナランタイムの既定の seccomp も効きません（[公式のサンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc)）。
- 監視の結果は、すぐに VM の外へ送ります。ワークロードと同じ VM の中にあるので、VM のカーネルが乗っ取られれば消されたり書き換えられたりし得るからです。ネットワークを切った Pod では、送る経路が標準出力のログ（既定で 2 Mbps の上限がある）や EBS のボリュームなどに限られます。

Nitro Sandbox は AWS の Nitro の上でしか使えません。オンプレミスでも、コンテナにホストのカーネルを直接使わせない仕組みで同じ考え方を取れますが、境界の作り方や監視のしかたは仕組みごとに違うので、同じようには扱えません。

# Nitro Isolation Engine との関係

Nitro Isolation Engine は、Graviton5 の Nitro Hypervisor のうち、VM どうしを隔離する部分だけを取り出した部品です。VM の作成、vCPU、メモリの管理について、正しく隔離することが数学的な証明を機械で検査する形式検証で示されています（範囲は後に書きます）。[解説ブログ](https://aws.amazon.com/jp/blogs/news/ec2s-formally-verified-isolation-engine-provides-mathematical-assurance-of-virtual-machine-isolation/)によると、最初に使われたのは 2026 年 6 月に提供が始まった Graviton5 の M9g と M9gd です。ただし、Nitro Sandbox がこの形式検証の保証を受けるかは、公開資料からは分かりません。この節は Graviton5 で sandbox を使う人向けの背景で、読み飛ばしても前の節までの結論は変わりません。以下では、[ホワイトペーパー](https://d1.awsstatic.com/onedam/marketing-channels/website/aws/en_US/whitepapers/compliance/nitro-isolation-engine-whitepaper.pdf)と[解説ブログ](https://aws.amazon.com/jp/blogs/news/ec2s-formally-verified-isolation-engine-provides-mathematical-assurance-of-virtual-machine-isolation/)をもとに、何が検証されたのかと、Nitro Sandbox との関係を書きます。

## 何を分けたのか

それまでの Nitro Hypervisor は、隔離の仕組みと運用の判断を 1 つのプログラムで受け持っていました。隔離の仕組みはページテーブルや CPU の状態の管理、運用の判断はスケジューリングやデバイスのエミュレーションです。このままでは大きすぎて、正しさを証明できません。そこで、ページテーブル、CPU の状態の保存、デバイスが読み書きできるメモリを制限する IOMMU といった仕組みだけを Isolation Engine に移し、ハイパーバイザー用の特権レベルである EL2（Arm の CPU の権限の段階）で動かしました。残りの Nitro Hypervisor は一段下の EL1 に降り、ゲストの状態に触るときは、必ず Isolation Engine の限られた API（ハイパーコール）を通します。

![左に、隔離の仕組みと運用の判断を 1 つで受け持つ以前の Nitro Hypervisor、右に、EL2 の Isolation Engine と、EL1 に降りてハイパーコールで依頼する Nitro Hypervisor を並べた図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/0ed37fa99f3fa0/zenn/articles/0ed37fa99f3fa0/isolation-engine.png)
*ホワイトペーパーの説明をもとにした、Isolation Engine の導入前と導入後*

Isolation Engine が守る約束には、たとえば次のものがあります。

- 物理メモリの 1 ページは、いつでもただ 1 つの主体（ゲスト、Isolation Engine、Nitro Hypervisor のどれか）が持ちます。
- ページの持ち主が変わるときは、新しい持ち主が触る前に中身をゼロで消します。
- ゲストの情報を Nitro Hypervisor に渡してよいのは、あらかじめ列挙した場面だけです。たとえば、ゲストが割り当てのないアドレスに書き込んで処理が止まったときは、その理由と書き込み先と値だけを渡します。

## 機密性をどう証明したか

証明したのは、「ゲストのメモリやレジスタに何が入っていても、あらかじめ列挙した受け渡しを除けば、ゲストの外から見える結果は変わらない」という性質で、非干渉性（noninterference）と呼びます。外から見える結果が中身によって変わらなければ、外からは中身を推測できない、という考え方です。ここで外から見る側にあたるのは、権限を下げた Nitro Hypervisor や他のゲストです。形式的には、見る側から区別できない 2 つの状態から同じ操作を 1 つ進めても、結果の 2 つの状態がやはり区別できない、という形で書きます。

解説ブログは、これを公開レジスタと非公開レジスタを 1 つずつ持つマシンで説明しています。図は、その例に、漏らさない操作の場合を筆者が書き足したものです。観察者に見えるのは公開レジスタだけなので、非公開レジスタだけが違う 2 台のマシン A と B は区別できません。公開レジスタに 1 を入れるだけの操作なら、操作のあとも区別できません。一方、非公開レジスタの値で分岐して公開レジスタに 1 を入れる操作では、操作のあとの公開レジスタが食い違い、観察者は非公開の値を知ってしまいます。

![公開レジスタだけが見える観察者に対して、非公開の値に関係なく公開レジスタを 1 にする操作は区別がつかないままで、非公開の値で分岐する操作は区別がついてしまうことを並べた図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/0ed37fa99f3fa0/zenn/articles/0ed37fa99f3fa0/noninterference.png)
*解説ブログの例（右）と、筆者が書き足した漏らさない操作（中央）*

Isolation Engine の証明は、検証の対象の操作について、列挙した受け渡しを除けば、観察者から見える結果が図の中央と同じく非公開の値によらないことを示しています。前の節の「持ち主が変わるときはページを消す」も、この性質を満たすための約束の 1 つです。証明は Isabelle/HOL という定理証明支援系で機械的に検査されており、解説ブログによると、モデルと証明を合わせた分量は約 33 万行です。

## 証明の範囲

ホワイトペーパーは、証明が及ばない範囲も明記しています。

- 現時点の対象は、VM の作成と設定、vCPU の管理、メモリの管理の 3 つです。I/O デバイスの管理と、ライブアップデートやライブマイグレーションは対象に挙げられていません。
- 証明しているのは Rust の実装を形式化したモデルで、Rust からモデルへの翻訳は手作業です。複数の CPU が同時に動く場合は、ロックの規律で逐次の実行に置き換えられることを前提にしています。
- キャッシュの時間差などを使うサイドチャネル攻撃は対象外です。ゲストの秘密を必要な短い間しか Isolation Engine の手の届く所に置かない secret hiding や、投機実行を止める命令、ゲストどうしで L1 キャッシュを共有しないことなど、別の対策で緩和します。
- Rust のコンパイラや CPU のハードウェアが仕様どおりに動くことは前提です。

## Nitro Sandbox との関係

Nitro Sandbox の公開ドキュメントは、Isolation Engine に触れていません。ホワイトペーパーも Nitro Sandbox には触れていません。今回の実機でも、Isolation Engine が sandbox の隔離に関わっているかを外から観察する方法はありませんでした。ホワイトペーパーによると、Graviton5 では、ゲストを作る判断は Nitro Hypervisor が行い、実際にゲストを作って管理する操作は Isolation Engine だけが行えます。m9g の上の sandbox もそれを経由すると考えるのは自然ですが、資料にそう書かれているわけではありません。Isolation Engine の検証結果を、Nitro Sandbox 全体の検証済みの保証として扱うことはできません。言えるのは、Graviton5 の Nitro Hypervisor のうち隔離を受け持つ部分が、「証明の範囲」に挙げた 3 つの対象について形式検証されている、ということまでで、それが sandbox の隔離に使われているかは資料に書かれていません。

# 誤解しやすい点

confidential が守るのは、VM のメモリと CPU の状態、暗号化した書き込み層などで、ワークロード自身が漏らすものと、ノードが握っている入出力は守れません。この節では、その守れないものを先に、両方のモードに共通する誤解を後にまとめます。[セキュリティモデルのページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-security-model.html)は、その例を具体的に挙げています。まず、ワークロード自身が漏らすものです。

| ワークロード自身が漏らすもの | 理由 |
|---|---|
| 標準出力や終了メッセージに書いた秘密 | ログを許可していれば、ノードがそのまま受け取る。終了メッセージ（`/dev/termination-log`）は、標準出力のログとは別の policy の操作で、既定ではどちらのモードでも読める |
| EFS や EBS に平文で書いたデータ | ノードは同じファイルシステムを自分の権限でマウントでき、EBS は中身を直接読める |
| 実行時に読み込んだ信頼できないコード | 起動後に取ってきたコードは policy の固定の外にある |

次に、ノードができることです。

| ノードができること | 理由 |
|---|---|
| 暗号化していないイメージの層を読む | イメージの層はノードを通って VM に渡される。中身を隠すには[イメージの暗号化](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-encrypted-images.html)が要るが、暗号化されるのは層だけで、イメージの manifest と設定（`ENV` など）、Pod の定義の引数と環境変数は平文のまま。秘密はここに置かない |
| ConfigMap、Secret、projected volume の中身を差し替える | policy が固定するのはマウントの場所で、中身ではない。CA 証明書のような信頼の起点は、digest で固定したイメージに入れる |
| 暗号化していない通信を見たり書き換えたりする | NetworkPolicy やセキュリティグループもノードの側で効く。TLS で相手の証明書を確かめ、Pod の中の通信は `localhost` ではなく `127.0.0.1` を使う（`/etc/hosts` はノードが書く） |
| EFS の接続先を差し替える | マウントは Pod ではなく EFS CSI ドライバーの IAM の主体で行われる。genpolicy が作る policy はファイルシステムの ID を固定しないので、confidential では `context.file_system_id` を固定する permit を自分で書き足す |
| Pod Identity の認証情報で読めるものを読む | ノードはそのノードの Pod の認証情報を発行できる |
| Secrets Store CSI Driver（Secrets Manager などの秘密をファイルとして Pod に渡す仕組み）で渡した秘密を読む | ノードを通って渡される |
| サービスを止める | VM を止めたり、CPU やネットワークを絞ったりできる |
| 時刻、DNS、配置のメタデータを偽る | ノードが提供している |

ほかにも、次の点は誤解しやすいので書いておきます。

- Pod の定義は、信頼する入力として扱われます。信頼できないイメージを動かすための機能で、信頼できない人が書いた Pod の定義を受け付けるための機能ではありません。sandbox の Pod を作ったり変えたりできる人を RBAC で絞り、Pod の中身の制約は admission control で強制します。
- KMS のキーポリシーに PCR の条件を書かなければ、計測値は記録されるだけで、誰も確かめません。PCR17 だけでなく、PCR8 の署名者の条件も要ります。ドキュメントによると、PCR8 の署名者の条件が示すのは、ゲストのイメージを EKS が署名したことです。イメージの版の新しさには触れていないので、古い版を除きたいなら、システムイメージを計測する PCR0 の固定も考えられます（筆者の考えで、PCR0 を固定すると AWS がゲストのイメージを更新するたびにキーポリシーを直すことになります）。
- AWS が受け持つのは Nitro Hypervisor、sandbox の境界、ゲストのシステムイメージで、コンテナのイメージ、policy、KMS のキーポリシー、アプリケーションのコードは利用者が受け持ちます。詳しくは[EKS ユーザーガイド](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing.html)を参照してください。Auto Mode を使わず自分で AMI を作る場合は、ノードのカーネルやランタイムの更新も自分で行うことになります。[公式のサンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc/examples/setup/ubuntu-ami)には、動いているノードにはセキュリティの修正が入らないという注意があります。
- 隔離は性能の予約ではありません。vCPU は時分割で共有され、ノードの vCPU の数を超えて割り当てることもできます（上限は 5 倍）。

# まとめ

isolated なら `runtimeClassName` を 1 行足し、requests を書いておけば、Pod は専用のカーネルを持つ VM の中で動き、ノードの root が `/proc` から読めた範囲にはメモリの中身がありませんでした。confidential では、policy を生成して annotation に付けると、書き込み層に書いた平文の目印もノードから見つからなくなり（ログは既定ではノードに見える）、KMS のキーポリシーに PCR の条件を書くと、承認した policy の計測値を示した Pod だけが復号できました。一方で、ノードに置いたランタイム監視からは sandbox の中が見えなくなるので、監視は監査ログとネットワークの記録を軸にする設計が要ります。Pod の中では、Falco、Tetragon、auditd は動きませんでしたが、Pod の中に監視用のコンテナを置くと、Wazuh のファイルの監視、Suricata の通信の検査、osquery のプロセスの一覧は動きました。GuardDuty の Runtime Monitoring では、sandbox の Pod の問い合わせはノードの名前解決の名義でだけ記録され、どの Pod からかは分かりませんでした。既定の帯域の上限や、sandbox のカーネルを止めた試験で exec の liveness probe では気づけなかったことなど、通常の Pod とは違う運用上の注意もあります。

確かめていない主なことは次のとおりです。

| 項目 | 内容 |
|---|---|
| メモリを読む別の方法 | `/proc` と共有領域を探す以外の方法で、ノードからゲストのメモリに届くか |
| ボリューム | EBS と EFS を sandbox から使ったときの性能と、confidential での扱い |
| 暗号化したイメージ | イメージの層を暗号化し、sandbox の中で KMS を使って復号する機能 |
| パケット数の数え方 | TCP で帯域だけ上げたときに 750 Mbps 出た理由 |
| 2 スレッドのコアの制御 | 1 コアに 2 スレッドのインスタンスで、sandbox どうしが同じコアを使わない制御の影響 |
| ネットワークの性能 | 上限を外したときの帯域とレイテンシーが、通常の Pod とどれだけ違うか。ノードの外への TCP で、帯域だけ上げたときにどうなるか |
| vsock の通信経路 | ネットワークを切った Pod に、ノードの root が vsock から実際に接続できるか（ドキュメントでは接続できるとされている） |
| ほかの死活の確認 | TCP の probe や、アプリケーションだけが固まった場合の検知。ネットワークを切った Pod で使える検知の方法。カーネルが止まった Pod が Service の振り分け先に残るか |
| confidential の更新 | ローリング更新で新旧の PCR17 が並ぶときのキーポリシーの書き方と、Deployment が作る名前の変わる Pod での policy の扱い |
| 起動時間 | sandbox のノードが無い状態から最初の Pod が準備完了になるまでの時間と、Pod の大きさとの関係 |
| 書き込み層の暗号 | 暗号の方式と、改ざんや巻き戻しへの強さ（今回は平文の目印の有無だけ） |
| Hybrid Nodes | 実機での確認 |
| GuardDuty の検知 | 新しい実行ファイルの実行やリバースシェルなど、プロセスについての検知。今回は通常の Pod でも検知が出ず、比べられなかった。ノードの名前解決を通らない DoH などの問い合わせ |
| Isolation Engine | Nitro Sandbox の隔離に Isolation Engine が関わっているか |
