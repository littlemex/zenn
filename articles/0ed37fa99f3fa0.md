# はじめに

Amazon EKS で、Pod ごとに専用の軽量な VM を[割り当てられるようになりました](https://aws.amazon.com/jp/about-aws/whats-new/2026/11/nitro-sandboxes-eks-ecs-ec2/)。通常の Pod はノードの Linux カーネルを共有しますが、この機能を使う Pod は Nitro Sandbox という VM の中で動き、同じノードの上にいてもカーネルを共有しません。対応するノードがあれば、isolated のモードは Pod の定義に `runtimeClassName` を 1 行足すだけで使えます。

Linux カーネルの脆弱性は毎年のように見つかります。生成 AI が書いたコード、CI のジョブ、利用者が持ち込むスクリプトのように、他人のコードをそのまま実行するサービスでは、コンテナからの脱出やカーネルの不具合が、同じノードの他の利用者にまで届くことが心配になります。Nitro Sandbox は、この境界を共有のカーネルからハイパーバイザーに移す機能です。

AWS は、AI のエージェント、CI のジョブ、ストレージ、confidential などの使い方を、そのまま動かせる形でまとめた[公式のサンプル集](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc)も公開しています。この記事は、それとは別に、ノードの側から何が見えて何が見えないかを確かめることに絞ります。

この記事では、まず仕組みと 2 つのモード（isolated と confidential）を整理し、次に東京リージョンの EKS で実際に動かして、ノードの側から何が見えて何が見えないかを確かめた結果を書きます。そのうえで、隔離と監視の組み合わせがセキュリティの運用でどう変わるかを整理し、最後に、Graviton5 で使われている Nitro Isolation Engine（ハイパーバイザーのうち隔離を受け持つ部分を形式検証したもの）との関係を整理します。

| 確かめたこと | 結果 | 節 |
|---|---|---|
| 同じノードの Pod どうしでカーネルが分かれるか | sandbox ごとに別のカーネルが起動していた | [カーネルとプロセス](#カーネルとプロセスが分かれている) |
| ノードの root からメモリやディスクを探せるか | `/proc` 経由で読めた範囲に、メモリの中身は無かった。書き込み層のディスクの中身は isolated では見つかり、confidential では見つからなかった | [ノードから探したもの](#ノードの-root-から探したもの) |
| confidential の policy と KMS | 中身を 1 か所変えた Pod には、KMS が復号を許さなかった | [policy と KMS](#confidential-の-policy-と-kms) |
| ネットワークを切る設定 | VM の外とつながるネットワークインターフェースが無い状態で起動した | [ネットワークを切る](#ネットワークを切る) |
| ランタイム監視 | ノードからは sandbox の中のプロセスが見えなかった。同じ Pod の中に置いた監視用のコンテナからは見えた | [セキュリティ運用で何が変わるか](#セキュリティ運用で何が変わるか) |
| 使える場所 | EKS では Auto Mode と EC2 のノードグループだけ。Fargate では sandbox の Pod が Pending のままだった | [使える場所と制限](#使える場所と制限) |
| 運用で効く数字 | 起動は isolated で 3〜4 秒、confidential で 5〜8 秒。既定の帯域は 100 Mbps。カーネルが止まっても exec の probe では気づけなかった | [運用で効く数字と注意](#運用で効く数字と注意) |

# 通常の Pod が共有しているもの

通常の Pod は、ノードのカーネルを共有しています。コンテナは、カーネルの機能（プロセスから見える範囲を区切る名前空間と、資源の使用量を区切る cgroup）で区切られたプロセスにすぎません。そのため、カーネルの不具合やコンテナからの脱出があると、同じノードの他の Pod にまで影響が及びます。生成 AI が書いたコードや、他社のコードを同じノードで動かすときに気になるのはこの点です。

カーネルを共有していることは、Pod の中から確かめられます。Linux は起動のたびに `boot_id` という ID を振ります。同じノードに置いた通常の Pod 2 つでは、`boot_id` もカーネルの版も同じで、どちらもノードのカーネルの値です。sandbox を使った Pod 3 つでは、`boot_id` が 3 つとも別々でした。この環境ではカーネルの版もノードと違いましたが、版は同じになることもあるので、見分けるのは `boot_id` とカーネルのビルドです。

![同じノードで、通常の Pod 2 つは boot_id とカーネルの版が同じで、sandbox の Pod 3 つはそれぞれ別の boot_id と別のカーネルを持つことを並べた図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/0ed37fa99f3fa0/zenn/articles/0ed37fa99f3fa0/shared-kernel.png)
*同じ m9g.xlarge ノードで、各 Pod の中から読んだ boot_id とカーネルの版*

# Nitro Sandbox の仕組み

Nitro Sandbox は、Pod 1 つに VM を 1 つ割り当て、その VM の中でコンテナを動かす仕組みです。ノード（EC2 インスタンス）自身も、Nitro Hypervisor という AWS のハイパーバイザーの上で動く VM です。Nitro Sandbox の VM は、ノードの中に入れ子で作るのではなく、同じ Nitro Hypervisor がノードの隣に[直接作ります](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing.html)。そのため、VM のメモリの仕切りはノードの OS ではなく Nitro Hypervisor が受け持ちます。以下、この VM を「ゲスト」とも呼びます。

登場する部品の受け持ちは次のとおりです。

| 部品 | 受け持ち | 動く場所 |
|---|---|---|
| kubelet と containerd | Pod を受け取り、どのランタイムで動かすかを決める | ノード |
| containerd-shim-nitro-sandbox-v2 | Pod ごとに firecracker を起動し、VM の中の agent とやり取りする | ノード |
| firecracker | AWS が公開している VM の管理プログラム。VM の起動を受け持ち、ディスクやネットワークの仮想デバイスを VM に見せる | ノード（Pod ごとに 1 つ） |
| Nitro Hypervisor | ノードが差し出したメモリと CPU で VM を作り、VM どうしとノードを隔離する | ノードの下（ノード自身もこの上で動く） |
| nitro-sandbox-agent | VM の中の自分の containerd でコンテナを起動し、Pod ごとの Cedar policy を守らせる | VM の中 |

Cedar は、AWS が公開しているアクセス制御の言語です。Nitro Sandbox では、その Pod がどのイメージをどの引数で起動してよいか、exec やログを許すかを Cedar で書き、Pod の annotation に付けます。以下、これを policy と書き、IAM や KMS の「ポリシー」と区別します。shim と VM の間は、virtio という仮想デバイスの規格と vsock という内部の通信経路でつながります。firecracker の役割は、[EC2 のユーザーガイド](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/amazon-ec2-nitro-sandboxes.html)に書かれています。

Pod を 1 つ起動すると、次の順で進みます。番号は図の番号と同じです。

1. Pod の定義に `runtimeClassName: isolated-sandbox`（または `confidential-sandbox`）が書かれています。
2. shim が firecracker を起動します。
3. Nitro Hypervisor が、ノードが差し出したメモリから VM を作り、VM の中で専用のカーネルが起動します。
4. VM の中の agent が、Pod に付いた policy で、どのイメージやどの操作を許すかを確かめます。
5. コンテナが VM の中で起動します。

![ノードの上の kubelet、containerd、shim、firecracker と、その隣の Nitro Sandbox の中の agent、policy の確認、コンテナ、下の Nitro Hypervisor を、起動の順に 1 から 5 の番号で示した図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/0ed37fa99f3fa0/zenn/articles/0ed37fa99f3fa0/components.png)
*Pod が runtimeClassName を指定したときに起動する部品と、その順番*

isolated のモードなら、Pod の定義に足すのは 1 行です。この例は limits だけを書いていて、その場合 Kubernetes は requests にも同じ値を入れます。

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-app
spec:
  runtimeClassName: isolated-sandbox
  containers:
  - name: main
    image: public.ecr.aws/amazonlinux/amazonlinux:2023
    command: ["sleep", "3600"]
    resources:
      limits:
        cpu: "1"
        memory: 512Mi
```

ただし、動かせる場所には制限があります。Fargate や Hybrid Nodes では使えず、Auto Mode でも構成によっては sandbox のノードが作られません。詳しくは[使える場所と制限](#使える場所と制限)にまとめました。

試す手順は次のとおりです。Nitro Sandbox には Kubernetes 1.36 以降が要ります。[isolated の始め方のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-isolated-setup.html)は、Auto Mode のクラスタを使う方法を勧めていて、eksctl なら版を明示して作ります。

```bash
eksctl create cluster --name sandbox-demo --region ap-northeast-1 --version 1.37 --enable-auto-mode
```

上の Pod を `manifest.yaml` として保存して apply し、Pod の中の `boot_id` とカーネルのビルドを見ます。通常の Pod で同じコマンドを実行した値と違えば、sandbox の中で動いています。カーネルの版の番号はノードと同じになることもあるので（公式のサンプルにその例があります）、`uname -r` ではなく、ビルドの番号と日時まで出す `uname -rv` で比べます。

```bash
kubectl apply -f manifest.yaml
kubectl wait pod/my-app --for=condition=Ready --timeout=300s
kubectl exec my-app -- sh -c 'uname -rv; cat /proc/sys/kernel/random/boot_id'
```

Auto Mode を使わないノードグループでは、sandbox のランタイムを入れた AMI と、起動テンプレートで Nitro Enclaves を有効にする設定（`EnclaveOptions.Enabled=true`）が要ります。Auto Mode の既定の NodePool（`general-purpose`）は x86 のインスタンスだけを使うので、Graviton で動かすには、arm64 を許す NodePool を足します。この記事でも、m9g と m8i にインスタンスタイプを固定した NodePool を足しています。Deployment などで Pod を作る場合は、`runtimeClassName` と、この記事に出てくる `sandbox.amazonaws.com/` で始まる annotation を、Pod テンプレート（`spec.template`）の側に書きます。Deployment 自身の `metadata.annotations` に書いても Pod には写されず、何も起きません。

EKS Auto Mode のクラスタには、2 つの RuntimeClass が最初からあります。中身を見ると、Pod 1 つごとに `eks.amazonaws.com/nitro-sandbox` という拡張リソースを 1 つ使い、メモリを isolated では 256Mi、confidential では 512Mi 余分に予約する設定でした。この上乗せ分は、Kubernetes の Pod Overhead の仕組みで、スケジューリングのときに Pod の要求に足して数えられます。VM の大きさは、Pod の limits ではなく requests で決まり、メモリは起動時に全部を確保します。実機では、requests を書かない Pod の VM のメモリは約 145 MiB、要求 512Mi・上限 2Gi の Pod は約 647 MiB でした（どちらもカーネルから見た量）。公式のサンプルは、requests が無くメモリが足りない Pod が、ログを残さずに落ちる例を挙げています。sandbox の Pod には、必ず requests を書きます。1 つのノードに置ける sandbox には、[制限事項のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-limitations.html)によると 2 つの上限があります。sandbox の個数はノードの vCPU の数の 5 倍まで、sandbox に割り当てる vCPU の合計もノードの vCPU の数の 5 倍までです。m9g.xlarge（4 vCPU）のノードは、拡張リソースの空きを 20 と表示し、個数の上限と一致しました。

# 2 つのモード

2 つのモードの違いは、ノードを信頼するかどうかです。isolated はノードを信頼し、怪しいワークロードからノードと他の Pod を守ります。confidential はノードを信頼せず、ノードの管理者や乗っ取られたノードからワークロードのデータを守ります。次の表は、[EKS ユーザーガイド](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing.html)と[confidential の設定のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-confidential-setup.html)にある、組み込みの設定の既定値の整理です。policy を生成するときの指定で、exec を一部だけ許したり、digest の固定を署名の確認に置き換えたりもできます。実機で確かめた結果は、後の節に書きます。

| 項目 | isolated-sandbox | confidential-sandbox |
|---|---|---|
| 信頼しないもの | Pod の中のワークロード | ノード |
| policy | 無くてもよい。付けなければ、すべてを許す組み込みの既定が使われる（[confidential の設定のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-confidential-setup.html)） | 必須。イメージの digest（中身から計算した識別子）、引数、環境変数、マウントなどを固定する |
| exec と stdin | 使える | 拒否される |
| ログ | 読める | 既定では読める（拒否する設定もある） |
| コンテナの書き込み層 | 暗号化しない | VM の中で暗号化する |
| Kubernetes の ServiceAccount トークン | [EKS ユーザーガイド](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing.html)は「VM の中に複製しない」と書くが、実機では渡っていた（下の注） | 渡す（同じページ） |

ServiceAccount トークンについては、ドキュメントの記載と実機の結果が違いました（公式のサンプルにも、`automountServiceAccountToken: false` を書かないとトークンが sandbox に入るという記載があります）。policy を付けない isolated の Pod の中に `/var/run/secrets/kubernetes.io/serviceaccount/token` があり、それを使って API サーバーに問い合わせると、その Pod の ServiceAccount として認証されました（権限を与えていないので、操作は 403 で拒否）。利用者のコードを動かす Pod では、ServiceAccount に権限を与えないうえで、`automountServiceAccountToken: false` を書いてトークンを渡さないようにします。

confidential で秘密のデータを受け取る仕組みは、次のとおりです。

1. VM は起動時に、Pod の policy のハッシュを PCR17 に書き込みます。PCR は、あとから書き換えられない計測値のレジスタです。
2. PCR8 には、ゲストの起動イメージに署名した者の情報が入ります。EKS の Nitro Sandbox が署名したイメージなら、署名者は `eks.amazonaws.com` です。
3. VM の中のプログラムは、使い捨ての鍵の組を作り、その公開鍵と PCR の値に Nitro の署名を付けた文書（アテステーション）を作って、KMS への復号の依頼に添えます。KMS は平文をそのまま返さず、その公開鍵で包んで返すので、途中を通るノードには読めません。
4. KMS のキーポリシーに、PCR17 と PCR8 の条件を書いておきます。policy を変えた Pod は PCR17 が変わるので、そのキーで暗号化したデータを復号できません。

キーポリシーの書き方には、[公式のサンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc/examples/confidential)が挙げている注意があります。KMS のキーは、既定のキーポリシーで作ると条件を書く前から復号できる状態になるので、最初から条件付きのポリシーで作ります。拒否の文は PCR17 と PCR8 で分けます（1 つの文にまとめると、両方が合わないときにしか拒否されない）。キーの管理者には `kms:Decrypt` だけでなく `kms:ReEncryptFrom` も与えません（与えると、条件の無い別のキーで包み直せる）。今回の検証は、この形のサンプルのキーポリシーをそのまま使っています。

policy の生成ツール `eks-nitro-sandbox-genpolicy` は、Pod の定義から policy を作り、PCR17 の予測値も出力します。ツールは、AWS が署名して公開している[ランタイムの配布物](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-download-binaries.html)に入っています（今回はこのページからダウンロードし、署名を確かめて使いました。公式のサンプルには、プレビューの時点では公開の配布が無かったという記載があります）。confidential の Pod は、たとえば次のように書きます。

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-conf
spec:
  runtimeClassName: confidential-sandbox
  enableServiceLinks: false
  containers:
  - name: main
    image: public.ecr.aws/amazonlinux/amazonlinux:2023
    command: ["sleep", "3600"]
    resources:
      limits:
        cpu: "1"
        memory: 512Mi
```

これを `conf.yaml` として保存し、次のように実行すると、policy の base64 の文字列と PCR17 の予測値が出力されます。base64 の文字列を Pod の `sandbox.amazonaws.com/policy` という annotation に付けて apply します。

```bash
eks-nitro-sandbox-genpolicy --profile confidential conf.yaml
```

`enableServiceLinks: false` を指定していない Pod では、kubelet が足す環境変数を固定できないため、ツールはエラーで止まりました。policy は、サイドカーを足す webhook などが書き換えたあとの、最終的な Pod の定義から作ります。イメージの更新など、policy が固定している項目を変えるたびに、policy と KMS の PCR17 の条件も作り直すので、この手順は CI/CD に組み込むことになります。動いている Pod の policy の annotation は変えられないので、新しい policy は Pod を作り直して反映します。イメージを digest ではなく AWS Signer の署名者で信頼する policy にすると、イメージを更新しても policy を作り直さずに済み、PCR17 も変わりません（[公式のサンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc/examples/confidential/signer-policy)）。今回使った組み込みの `confidential` のプロファイルは、この環境では受け付けられました。公式のサンプルには、プレビューの時点のゲストでは受け付けられず、項目を減らしたプロファイルを使ったという記載があります。

# 使える場所と制限

Nitro Sandbox は EC2 のインスタンスの機能で、EKS のほかに ECS や EC2 から直接も使えます。EKS で使えるのは、EC2 のインスタンスで動くノード（Auto Mode、マネージドノードグループ、セルフマネージドノード）だけです。Pod の機能にも、通常の Pod と違う制限がいくつもあります。導入を決める前に確かめる点を、まず動かせる場所、次に Pod の機能の順にまとめます。

| 動かせる場所 | 使えるか | 根拠 |
|---|---|---|
| EKS Auto Mode | 使える。RuntimeClass が最初からあり、sandbox のノードも自動で起動する | [isolated の始め方のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-isolated-setup.html)、実機 |
| EC2 のマネージドノードグループ、セルフマネージドノード | 使える。sandbox のランタイムを入れた AMI と、起動テンプレートで Nitro Enclaves を有効にする設定が要る | isolated の始め方のページ |
| Hybrid Nodes（オンプレミスのサーバーを EKS につなぐ形） | 使えない | Nitro Sandbox は対応する EC2 のインスタンスタイプでしか動かない（[EKS ユーザーガイド](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing.html)） |
| Fargate | 使えない | 実機では、sandbox の Pod は `Fargate profile ... cannot satisfy pod's node selector/affinity requirements` で Pending のままだった。同じプロファイルの通常の Pod は動いた |
| Kubernetes の版 | 1.36 以降 | isolated の始め方のページ |
| インスタンスタイプ | Nitro Enclaves に対応するものの一部。多くのファミリーで最小のサイズと metal は対象外 | [EC2 のユーザーガイド](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/amazon-ec2-nitro-sandboxes.html) |
| Auto Mode で sandbox のノードを作らない構成 | FIPS 用の AMI、GPU や Neuron 用の AMI、複数の NUMA を持つインスタンスタイプ、まだ検証されていないインスタンスタイプ。発表の時点では r5a、r5ad、m5ad も一時的に対象外。いずれも Pod は Pending のまま | [制限事項のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-limitations.html) |
| GPU などのデバイスの受け渡し | 発表の時点では使えない | 制限事項のページ |

次は、Pod の機能の制限です。特に断りの無いものは制限事項のページの記載で、ほかのページの記載や実機で確かめたものはそう書いています。

| Pod の機能 | sandbox での扱い |
|---|---|
| `hostNetwork: true` | 起動しない（実機でも確かめた） |
| `hostPID: true`、`hostIPC: true` | 起動するが、見えるのはその VM の中だけ（hostPID は実機でも確かめた） |
| ユーザー名前空間（`hostUsers: false`） | isolated のノードでは起動しない |
| VM の中のユーザー名前空間 | sandbox のカーネルは `max_user_namespaces` が 0（実機で確かめた）。公式のサンプルによると、bubblewrap のように中でユーザー名前空間を作るツールはそのままでは動かない |
| VM の大きさ | requests で決まり、あとから変えられない。requests が無いと小さい既定の大きさになる（実機で約 145 MiB） |
| EBS のボリューム | 1 つのボリュームを複数の Pod で共有できない（`ReadWriteOncePod` を使う）。動いている Pod のボリュームは拡張できない。1 つの PVC を同じ Pod の中で別々のパスにマウントできない（公式のサンプル） |
| CPU とメモリのその場での変更 | できない。作り直す |
| kubelet の CPU Manager の `static` | 効かない |
| `kubectl port-forward` | `127.0.0.1` だけで待ち受けるサーバーには届かない |
| `emptyDir` と書き込み層の使用量 | kubelet からは 0 に見える。上限は `ephemeral-storage` の requests と limits で決める |
| IMDS | リージョンなど 5 つの項目だけ。IAM の認証情報は返らない（実機でも確かめた） |
| 一部だけ暗号化したイメージ | 使えない。暗号化するなら全部の層 |
| Pod ごとの既定の上限 | 帯域 100 Mbps、パケット毎秒 1,500 個、DNS 毎秒 100 クエリ、同時の外向き接続が IP のファミリーごとに 4,096（64〜65,536 の範囲で変えられるが、無効にはできない）、書き込み層のディスク 400 Mbps と 1,500 IOPS、ログ 2 Mbps。接続数以外は `"disabled"` で外せて、`"0"` を指定すると Pod が起動しない（[資源の上限のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-resource-isolation.html)） |
| 1 つのノードの sandbox の数 | 個数も vCPU の合計も、ノードの vCPU の数の 5 倍まで。CPU をオーバーコミットするインスタンスタイプでは個数の上限が半分 |
| 1 コアに 2 スレッドのインスタンス | 2 つの sandbox が同じコアを同時に使わないように制御され、使える計算量はおよそ物理コアの数まで |
| ネットワークを切った Pod | Pod Identity の認証情報、暗号化したイメージ、AWS Signer による署名の確認が使えない。HTTP と TCP の probe も使えない。EFS と S3 Files はマウントできないが、EBS は使える（公式のサンプル）（[ネットワーク分離のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-network-isolation.html)、[confidential の設定のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-confidential-setup.html)） |
| ノードに置くランタイム監視 | sandbox の中は見えない（[監視のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-observability.html)、実機でも確かめた。[セキュリティ運用で何が変わるか](#セキュリティ運用で何が変わるか)） |
| Ubuntu のノード | sandbox の Pod に `appArmorProfile.type: Unconfined` が要る（公式のサンプル。AppArmor の無い Amazon Linux 2023 のノードでは要らない） |
| スナップショットからの復元、ライブマイグレーション | 使えない（制限事項のページ） |

# 実機で確かめたこと

## 環境

ノードの側から sandbox がどう見えるかを確かめるため、同じノードに特権付きの通常 Pod（`hostPID: true`、以下「観察用の Pod」）を置き、その中から調べました。クラスタは EKS Auto Mode で、Graviton5 の m9g.xlarge と、比較用に x86 の m8i.xlarge だけを使う NodePool を足しています。特に断らない結果は m9g.xlarge のものです。確かめたのは 2026 年 11 月 10 日から 13 日です。

| 項目 | 値 |
|---|---|
| リージョン | 東京（ap-northeast-1） |
| クラスタ | EKS Auto Mode、Kubernetes 1.37 |
| ノード | m9g.xlarge（Graviton5、4 vCPU、1 コアに 1 スレッド）、m8i.xlarge（4 vCPU、1 コアに 2 スレッド） |
| ノードのカーネル | 6.18.56 |
| sandbox のカーネル | 6.18.54 |
| コンテナのイメージ | `public.ecr.aws/amazonlinux/amazonlinux:2023` ほか |

今回の Auto Mode は、sandbox の Pod が来たときに sandbox に対応したノードを起動しました。通常の Pod のために先に起動したノードには `eks.amazonaws.com/nitro-sandbox=false` のラベルが付き、sandbox の Pod はそこに置かれませんでした。逆に、sandbox のノードには通常の Pod も載ります。

## カーネルとプロセスが分かれている

sandbox の Pod は、ノードのカーネルの上で動くプロセスではなくなります。sandbox の Pod 3 つと通常の Pod 2 つを置いたノードで、観察用の Pod からプロセスを一覧すると、firecracker と Pod ごとの shim が sandbox の数と同じ 3 つずつ見えました（ほかに全体で共通の shim が 1 つ）。`sleep` は、観察用の Pod 自身のものを除くと通常の Pod の 2 つだけが見え、sandbox の中で動いている `sleep` は見えませんでした。

逆向きも確かめました。sandbox の Pod に `hostPID: true` を付けると、見えたのは VM の中の init、agent、自分の `sleep` などで、ノードのプロセスは見えませんでした。`hostNetwork: true` の Pod は、`hostNetwork is not supported for nitro-sandbox pods` というエラーで起動しませんでした。どちらも[制限事項のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-limitations.html)の記載どおりです。

カーネルのログも分かれていました。特権付きの sandbox の中でカーネルのログに目印の行を書き込むと、sandbox の中の `dmesg` には出て、ノードのカーネルのログ 1,455 件には出ませんでした。さらに、sandbox の中でカーネルを意図的に止めても（`echo c > /proc/sysrq-trigger`）、同じノードの他の sandbox 2 つとノードは `boot_id` が変わらず、そのまま動き続けました。

## ノードの root から探したもの

ノードの root になって `/proc` からプロセスのメモリを探しても、読めた範囲に sandbox のメモリの中身はありませんでした。コンテナの書き込み層のディスクの中身は、isolated では見つかり、confidential では見つかりませんでした。

確かめ方は、目印の文字列を Pod の中でメモリとディスクに大量に書き、観察用の Pod から探すというものです。目印は、Pod の定義に書いた元の文字列（種）を、Pod の中で SHA-256 にかけて作ります。Pod の定義はノードにも届くので、種をそのまま目印にすると、ノードが持っている定義の写しを見つけてしまうからです。ハッシュにした目印は、Pod の中で計算されるまでどこにも現れません。

![通常の Pod、isolated、confidential の 3 列で、プロセス、メモリ、ディスク、カーネルのログのそれぞれをノードから見つけられたかを並べた図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/0ed37fa99f3fa0/zenn/articles/0ed37fa99f3fa0/node-read.png)
*ノードの root から、Pod の中で作った目印（図の marker）を探した結果*

メモリは、通常の Pod なら簡単に読めました。観察用の Pod から、通常の Pod のシェルのメモリを探すと、目印が 129,072 回見つかりました。sandbox では、ノード上でメモリを読めたプロセスを全部探しても（isolated の試験では 36 プロセスの 3,162 MiB、confidential の試験では 32 プロセスの 3,209 MiB）、目印は 0 回でした。デバイスをマップした領域は、次に書く理由でこの走査から外し、別に調べています。isolated では、sandbox の中のメモリ上のファイル（tmpfs）に目印が 516,222 行あることも、Pod の中から確かめています。exec を拒否する confidential では中から数えられないので、目印を書き終えたあとに出すログの行で、書き込みが済んだことを確かめました。

firecracker の中を見ると、VM のメモリにあたる領域は `/dev/nitro_enclaves` をマップしたもので、読み書きの権限がありません（`---s`）。仮想デバイスとのやり取りに使う読める共有領域（sandbox 1 つあたり約 62 MiB）も探しましたが、目印はありませんでした。なお、VM のメモリにあたる領域を `/proc` から無理に読もうとした 1 回目の試みでは、読み取りが 10 分経っても返らず、同じノードの通常の Pod への exec まで固まったので、ノードを作り直しました（再現は試していません）。試すときは捨ててよいノードで行い、プロセスのメモリを走査するような監視エージェントをノードに入れている場合も、sandbox のノードに載せる前に検証用のノードで確かめておくと安全です。

ディスクでは、2 つのモードの差がはっきり出ました。起動時に 16 MiB 分の目印をファイルに書く Pod を作ると、isolated ではノード上の `overlay.img` から目印が 258,111 回（書いた量のすべて）見つかり、confidential では 0 回でした。isolated は書き込み層を暗号化しないので、ノードからディスクの中身が読めます。ノードを信頼する isolated の前提のとおりです。

[セキュリティモデルのページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-security-model.html)は、「ノードはゲストのメモリを読み書きできない」と書いています。今回の結果はこれと矛盾しません。

## confidential の policy と KMS

confidential では、policy が固定している項目（イメージの digest、引数、環境変数、マウントなど）が Pod と違うと、コンテナが起動しません。policy を生成したあと、同じ名前のまま引数だけを変えた Pod を作ると、VM は起動したものの、VM の中の agent が `policy denied Agent::Action::"CreateContainer"` でコンテナの起動を拒否しました。名前と引数の両方を変えた Pod は、その手前の `policy denied SetupSandbox` で止まりました。動いている Pod への `kubectl exec` は `policy denied Agent::Action::"Exec"` で拒否され、ログは読めました。

KMS の側は、[公式サンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc/examples/confidential)のキーポリシーの形をそのまま使って確かめました。Pod のロールには IAM のポリシーを 1 つも付けません。キーポリシーには、PCR17 が承認した policy の値で、かつ PCR8 の署名者が EKS のときだけ、このロールに復号を許すと書きます。それ以外の復号は、誰からのものでも拒否します。そのうえで、暗号文 1 つを 3 つの Pod で復号させました。

![genpolicy が出した PCR17 の予測値を KMS のキーポリシーに書き、承認した Pod、環境変数を変えた Pod、同じロールの通常の Pod の 3 つが復号を試した結果を並べた図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/0ed37fa99f3fa0/zenn/articles/0ed37fa99f3fa0/attestation.png)
*PCR17 の条件を書いたキーポリシーと、3 つの Pod の復号の結果*

承認した Pod は復号に成功し、平文のハッシュも一致しました。環境変数を 1 つだけ変え、その定義から正しく作り直した policy を付けた Pod は、`AccessDeniedException` で拒否されました。genpolicy が出した PCR17 の予測値は、承認した Pod と別の値になっていました。同じロールを使う通常の Pod も拒否されました。通常の Pod には、アテステーションを作るデバイス（`/dev/nsm`）がありません。ロールの認証情報を持っているだけでは復号できず、承認した policy の計測値を KMS に示して初めて復号できる、という形を実際に確かめられました。なお、この形でもキーポリシーを書き換えられるキーの管理者は残ります。信頼しないのはノードであって、キーの管理者ではありません。

## ネットワークを切る

Pod に `sandbox.amazonaws.com/network-isolated: "true"` を付けると、VM の外とつながるネットワークインターフェースを持たない VM として起動します（[ネットワーク分離のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-network-isolation.html)）。通信を遮るのではなく、インターフェースそのものが無い状態です。

```yaml
metadata:
  annotations:
    sandbox.amazonaws.com/network-isolated: "true"
spec:
  runtimeClassName: isolated-sandbox
```

実機では、この Pod にあるのはループバックと停止中の `dummy0` だけで、経路表は空でした。外への HTTPS は名前解決の段階で失敗し、インスタンスメタデータ（IMDS、EC2 がインスタンスの情報を返す仕組み）にもつながりませんでした。一方で `kubectl logs` と `kubectl exec` は使えました。ログや exec は、VM とノードの間の vsock という別の通信経路を通るからです。ネットワーク分離のページによると、この vsock は VM の中のどのプロセスも使え、ノード側でも firecracker の vsock のソケットに触れる root のプロセスなら、VM の中で待ち受けているポートに接続できます。完全な遮断ではありません。また、ネットワークを切った Pod では EKS Pod Identity（Pod ごとに IAM ロールを割り当てる EKS の機能）の認証情報も使えないので、KMS を使う暗号化したイメージや、AWS Signer による署名の確認も使えません。

ネットワークを切らない sandbox から IMDS に問い合わせると、リージョン、アベイラビリティーゾーン、パーティションは返り、インスタンス ID と IAM の認証情報は 404 でした。制限事項のページも、sandbox の IMDS が返すのはリージョン、アベイラビリティーゾーン、その ID、サービスのドメイン、パーティションの 5 つだけで（今回確かめたのはそのうち 3 つ）、AWS の認証情報は Pod Identity で渡すと書いています。

## 運用で効く数字と注意

既存の Pod を移すときに引っかかる機能の一覧は、[使える場所と制限](#使える場所と制限)にまとめました。ここでは、実機で測った数字と、運用で気をつける点を書きます。

### 起動にかかる時間

Pod を作ってから準備完了になるまでの時間を、各 10 回測りました。Kubernetes の API が Pod に記録する作成時刻と準備完了の時刻（1 秒刻み）の差は、通常の Pod が 0〜1 秒、isolated が 3〜4 秒（中央値 3.5 秒）、confidential が 5〜8 秒（中央値 7 秒）でした。Pod の CPU の要求は 0.5、メモリは 256Mi です。イメージはノードにある状態で、ノードの起動待ちは含みません。公式のサンプルには、kubectl の往復を含めて測った 3.2〜3.7 秒という値と、条件の書かれていない約 5〜6 秒という値、CPU 1・メモリ 2 GiB の Pod で 19 秒という値が載っています。起動待ちを避けたい場合は、先に起動しておいた sandbox を割り当てるウォームプールの[サンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc/examples/getting-started/warm-pool)があり、割り当ては 1 秒未満と書かれています。手元の kubectl から測った待ち時間は、東京との往復の揺れが大きく、通常の Pod と isolated の差を見分けられなかったので使っていません。

### 既定の帯域とパケット数の上限

sandbox には、Pod ごとの帯域とパケット数に[既定の上限](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-resource-isolation.html)があります。帯域は 100 Mbps、パケット数は毎秒 1,500 個です。同じノードの通常の Pod を相手に、Alpine 3.20 の iperf3 で測ると、次のようになりました。TCP は送信と受信をそれぞれ 30 秒、UDP は 1,400 バイトのパケットで毎秒 300 Mbit を 20 秒送り、受信側で測った値です。

| sandbox の設定 | TCP 送信 | TCP 受信 | UDP 送信 |
|---|---|---|---|
| 既定のまま | 99.9 Mbps | 99.9 Mbps | 17.7 Mbps（毎秒約 1,580 個） |
| 帯域だけ 1G に上げる | 750 Mbps | 690 Mbps | 18.2 Mbps（毎秒約 1,620 個） |
| 帯域を 1G、パケット数を毎秒 15,000 個に上げる | 997 Mbps | 998 Mbps | 176 Mbps（毎秒約 15,700 個） |

既定のままで負荷試験をすると、sandbox の性能ではなく、この上限を測ることになります。上げるには、帯域とパケット数の両方を Pod の annotation で指定します。annotation は Pod の作成時に一度だけ読まれます。

```yaml
metadata:
  annotations:
    sandbox.amazonaws.com/ingress-bandwidth: "1G"
    sandbox.amazonaws.com/egress-bandwidth: "1G"
    sandbox.amazonaws.com/ingress-packets-per-second: "15000"
    sandbox.amazonaws.com/egress-packets-per-second: "15000"
```

ドキュメントは「片方だけ上げても効果はない」と書き、9,001 バイトの MTU で毎秒 1,500 個なら約 102 Mbps になるという計算を添えています。1,400 バイトの UDP ではそのとおりでしたが、TCP では帯域だけ上げても 750 Mbps 出ました。1 個あたりの大きさに直すと次のとおりです。

$$
\frac{750 \times 10^6\ \text{bit/s}}{1500\ \text{packets/s}} \div 8 \approx 62.5\ \text{KB/packet}
$$

これは、TCP が複数のパケットを大きな単位にまとめて扱うときの大きさ（最大 64 KB）に近い値です。パケット数が、MTU の大きさのパケットではなく、まとめた単位で数えられているのではないかと推測しています。いずれにしても、小さな RPC のように小さいパケットが多い通信は、帯域より先に毎秒 1,500 個の上限に当たるので、帯域と一緒にパケット数も上げます。DNS には別に毎秒 100 クエリの上限があります。なお、公式のサンプルは、帯域だけ上げても 100 Mbit/s 付近で頭打ちになると書いています。今回の同じノードの Pod どうしの TCP の測定はそうなりませんでしたが、通信先や経路によって変わる可能性があります。

### CPU の取り分

CPU を使い切る処理では、sandbox の Pod は通常の Pod とほぼ同じスループットで動きました。1 コアに 2 スレッドの x86 のインスタンスでは、4 個を同時に置くと 1 個あたりの処理量が約半分になりましたが、これは通常の Pod でも同じでした。

測り方は次のとおりです。CPU を使い切る Python のループを 20 秒回し、その間に進んだ回数を、通常の Pod と sandbox の Pod で比べました。各 Pod の CPU は要求 0.8、上限 1 にそろえ、同じノードに 1 個または 4 個を同時に置いて、各 3 回の中央値を取っています。値は、同じノードの通常の Pod 1 個の回数を 1 とした比です。

| ノード | 通常 1 個 | sandbox 1 個 | 通常 4 個（合計） | sandbox 4 個（合計） |
|---|---|---|---|---|
| m9g.xlarge（4 コア、1 コアに 1 スレッド） | 1.00 | 0.95 | 3.94 | 3.75 |
| m8i.xlarge（2 コア、1 コアに 2 スレッド） | 1.00 | 0.99 | 2.07 | 1.96 |

sandbox と通常の Pod の差は 1〜5% でした。m8i では、4 個の合計が通常の Pod 1 個の約 2 倍（通常の Pod で 2.07、sandbox で 1.96）で、どちらも同じ傾向です。物理コアが 2 つで、この処理では 1 コアの 2 つ目のスレッドがほとんど上乗せにならないためです。制限事項のページは、1 コアに 2 スレッドのインスタンスでは、2 つの sandbox が同じコアのスレッドを同時に使わないように制御されるので、sandbox が使える計算量はおよそ物理コアの数までになると書いています。この処理は通常の Pod でも物理コア 2 つ分で上限になるので、その制御の影響はこの測定には表れません。同じページは、sandbox の CPU を 2 vCPU 単位で要求するか、Graviton のように 1 コアに 1 スレッドのインスタンスを選ぶことを勧めています。

### カーネルが止まっても Pod は「動いている」ままになる

ネットワークのある sandbox の Pod には、HTTP の liveness probe を付けておくのが安全です。sandbox の中でカーネルを止めると、Kubernetes 上の Pod は `Running` で準備完了のまま残りました。試した 3 通り（probe なし、exec、HTTP）のうち、検知できたのは HTTP の probe だけでした。probe はどれも `periodSeconds: 5`、`timeoutSeconds: 2`、`failureThreshold: 2` で試しています。

詳しく書きます。probe を付けない Pod では、約 6 分経っても再起動されず、exec だけが返らない状態でした。exec の liveness probe を付けても、probe は「失敗」ではなく「エラー（状態不明）」として扱われ、約 8 分（471 秒）経っても再起動されませんでした。HTTP の liveness probe を付けた Pod では、約 50 秒で再起動して準備完了に戻り、`boot_id` も新しくなりました。今回の止め方では、HTTP の probe なら検知できたことになります。準備完了のまま残る間は、Service の振り分け先からも外れないと考えられます（確かめてはいません）。ネットワークを切った Pod では HTTP と TCP の probe が使えず、ネットワーク分離のページは exec の probe を勧めていますが、今回のような止まり方は exec の probe では検知できませんでした。

# セキュリティ運用で何が変わるか

Nitro Sandbox は、コンテナの中のコードがカーネルの脆弱性やコンテナからの脱出を使っても、被害がノードと他の Pod に及ぶリスクを下げます。前提は、信頼できないのはコンテナの中のコードで、Pod の定義は信頼できる人が書くことです。その代わり、ノードに置いたランタイム監視（動いているプロセスやシステムコールを見張る仕組み）からは、sandbox の中が見えなくなります。守りと見張りのそれぞれで何が変わるかを、層ごとに整理します。

| 層 | 受け持ち | sandbox で変わること |
|---|---|---|
| 隔離 | コンテナからの脱出やカーネルの不具合を、他の Pod とノードに広げない | 境界が共有のカーネルから Nitro Hypervisor に移る。実機では、特権付きのコンテナで sandbox のカーネルを止めても、隣の sandbox とノードはそのまま動いた |
| 監査ログ | Kubernetes の監査ログで誰が何を作ったか、CloudTrail で AWS の API の呼び出しを記録する | ノードの外で記録される仕組みなので、sandbox にしても記録する場所は変わらない。ただし、どちらも VM の中で実行されたコマンドの記録ではない |
| ログとメトリクス | コンテナのログと使用量を集める | kubelet を通るので、CloudWatch のエージェントなどで集められる（[監視のページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-observability.html)） |
| ノードのランタイム監視 | ノードのプロセスや cgroup を見張る | sandbox の中は見えない。監視のページは、GuardDuty のランタイム監視のエージェントが sandbox の中の動きを観察できないと書いている。実機でも、ノード側からは sandbox の中のワークロードのプロセスと agent が見つからず、見えたのは firecracker と shim だけだった。同じノードの通常の Pod とノード自身は引き続き見える |
| Pod の中の監視 | その VM の中の動きを見張る | 同じ Pod に特権付きで `hostPID: true` の監視用コンテナを置くと、その VM のカーネルの上のワークロードのプロセスが見えた |
| ネットワーク | 通信先を制限する、通信を記録する | NetworkPolicy やセキュリティグループはノードの側で効くので、sandbox の中から外せない。ただし、Auto Mode では、NetworkPolicy は強制を有効にするまで効かない。実機でも、既定で拒否する NetworkPolicy を入れても外への HTTPS は通り、`kube-system` に `amazon-vpc-cni` の ConfigMap（`enable-network-policy-controller: "true"`）を作ると、新しい sandbox の Pod の通信が止まった。また、Pod は自分のノードには常に届き、sandbox の IMDS は VM の中で応答するのでポリシーの対象外。既定で拒否するなら、Pod Identity の認証情報の取得先（`169.254.170.23`）と DNS を許す必要がある（公式のサンプル）。通信が要らない処理はネットワークを切った sandbox で動かせるが、vsock の経路は残る |

利用者のコードを実行するサービスなら、次のような組み合わせが考えられます。利用者から受け取るのはコードなどの限られた入力だけにし、Pod の定義はサービスの側で作ります。sandbox の Pod を作れる人は RBAC で絞り、定義の制約は admission control で強制します。実行環境は isolated の sandbox にし、通信が要らない処理はネットワークも切ります。監査ログとネットワークの記録は引き続き取りますが、VM の中で完結する不正な処理はそこには現れません。ノードに置いていたランタイム監視の代わりにはならないので、VM の中の振る舞いを見たい場合は、監視用のコンテナを同じ Pod に入れます。実機で見たとおり、中が止まっても Pod は動いているように見えることがあるので、実行時間の上限と、外からの死活の確認も組み合わせます。

Pod の中には、監視だけでなく、もう 1 つの閉じ込めの層も置けます。[公式のサンプル](https://github.com/aws-samples/sample-eks-nitro-sandbox/tree/43aa7c77150e4a1c456663448b5a7a0180c075fc/examples/subagent-security)は、エージェントが起動する道具のプロセスを、sandbox の中で Landlock や seccomp、bubblewrap などでさらに絞る例を挙げています。Nitro の境界は Pod とノードの間にあり、Pod の中のプロセスどうしは分けないからです。

Pod の中に監視を入れるときは、2 点に気をつけます。1 つ目は、sandbox のカーネルには、多くの eBPF（カーネルの中で小さなプログラムを動かして監視する仕組み）の監視ツールが前提にする BTF（カーネルの型情報、`/sys/kernel/btf/vmlinux`）がありませんでした。ノードのカーネルにはあります。そうしたツールが sandbox の中でそのまま動くかは確かめていません。監視用のコンテナにも requests を書き、VM のメモリを見込んでおきます。2 つ目は、監視用のコンテナに特権を与えても、カーネルへの影響はその VM の中にとどまりますが、監視用のコンテナに持たせた認証情報やマウント、送信先は VM の外に届きます。これらは最小限にします。特権を与えたコンテナには、コンテナランタイムの既定の seccomp も効きません（公式のサンプル）。また、監視の結果もワークロードと同じ VM の中にあるので、VM のカーネルが乗っ取られれば、消されたり書き換えられたりし得ます。結果はすぐに VM の外へ送る設計にします。ネットワークを切った Pod では、外へ送る経路が標準出力のログ（既定で 2 Mbps の上限がある）や EBS のボリュームなどに限られます。

Nitro Sandbox は AWS の Nitro の上でしか使えません。オンプレミスでも同じ考え方を取りたい場合は、コンテナにホストのカーネルを直接使わせないという同じ目的の OSS として、Pod ごとに軽量な VM を割り当てる Kata Containers や、ユーザー空間でカーネルの役割を受け持つ gVisor があります。境界の作り方や監視のしかたはそれぞれ違うので、同じようには扱えません。

# Nitro Isolation Engine との関係

Nitro Isolation Engine は、sandbox を作る Nitro Hypervisor のうち、VM どうしを隔離する部分だけを取り出した部品で、正しく隔離することが形式検証（数学的な証明を機械で検査する方法）で示されています。Graviton5 のインスタンスで使われていますが、Nitro Sandbox がこの検証の保証を受けると書いた資料はありません。以下は、[ホワイトペーパー](https://d1.awsstatic.com/onedam/marketing-channels/website/aws/en_US/whitepapers/compliance/nitro-isolation-engine-whitepaper.pdf)と[解説ブログ](https://aws.amazon.com/jp/blogs/news/ec2s-formally-verified-isolation-engine-provides-mathematical-assurance-of-virtual-machine-isolation/)をもとに、何が検証されたのかと、Nitro Sandbox との関係を書きます。

## 何を分けたのか

それまでの Nitro Hypervisor は、隔離の仕組み（ページテーブルや CPU の状態の管理）と、運用の判断（スケジューリングやデバイスのエミュレーション）を 1 つのプログラムで受け持っていました。このままでは大きすぎて、正しさを証明できません。そこで、仕組み（ページテーブル、CPU の状態の保存、デバイスが読み書きできるメモリを制限する IOMMU）だけを Isolation Engine に移し、ハイパーバイザー用の特権レベルである EL2（Arm の CPU の権限の段階）で動かしました。残りの Nitro Hypervisor は一段下の EL1 に降り、ゲストの状態に触るときは、必ず Isolation Engine の限られた API（ハイパーコール）を通します。

![左に、隔離の仕組みと運用の判断を 1 つで受け持つ以前の Nitro Hypervisor、右に、EL2 の Isolation Engine と、EL1 に降りてハイパーコールで依頼する Nitro Hypervisor を並べた図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/0ed37fa99f3fa0/zenn/articles/0ed37fa99f3fa0/isolation-engine.png)
*ホワイトペーパーの説明をもとにした、Isolation Engine の導入前と導入後*

Isolation Engine が守る約束には、たとえば次のものがあります。

- 物理メモリの 1 ページは、いつでもただ 1 つの主体（ゲスト、Isolation Engine、Nitro Hypervisor のどれか）が持ちます。
- ページの持ち主が変わるときは、新しい持ち主が触る前に中身をゼロで消します。
- ゲストの情報を Nitro Hypervisor に渡してよいのは、あらかじめ列挙した場面だけです。たとえば、ゲストが割り当てのないアドレスに書き込んで処理が止まったときは、その理由と書き込み先と値だけを渡します。

## 機密性をどう証明したか

証明したのは、「ゲストのメモリやレジスタに何が入っていても、あらかじめ列挙した受け渡しを除けば、ゲストの外から見える結果は変わらない」という性質で、非干渉性（noninterference）と呼びます。ここで外から見る側にあたるのは、権限を下げた Nitro Hypervisor や他のゲストです。形式的には、見る側から区別できない 2 つの状態から同じ操作を 1 つ進めても、結果の 2 つの状態がやはり区別できない、という形で書きます。

解説ブログは、これを公開レジスタと非公開レジスタを 1 つずつ持つマシンで説明しています。図は、その例に、漏らさない操作の場合を筆者が書き足したものです。観察者に見えるのは公開レジスタだけなので、非公開レジスタだけが違う 2 台のマシン A と B は区別できません。公開レジスタに 1 を入れるだけの操作なら、操作のあとも区別できません。一方、非公開レジスタの値で分岐して公開レジスタに 1 を入れる操作では、操作のあとの公開レジスタが食い違い、観察者は非公開の値を知ってしまいます。

![公開レジスタだけが見える観察者に対して、非公開の値に関係なく公開レジスタを 1 にする操作は区別がつかないままで、非公開の値で分岐する操作は区別がついてしまうことを並べた図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/0ed37fa99f3fa0/zenn/articles/0ed37fa99f3fa0/noninterference.png)
*解説ブログの例（右）と、筆者が書き足した漏らさない操作（中央）*

Isolation Engine の証明は、対象のすべての操作が、どんな状態から始めても図の真ん中の形になることを示しています。前の節の「持ち主が変わるときはページを消す」も、この性質を満たすための約束の 1 つです。証明は Isabelle/HOL という定理証明支援系で機械的に検査されており、ホワイトペーパーによると、モデルと証明を合わせた分量は約 33 万行です。

## 証明の範囲

ホワイトペーパーは、証明が及ばない範囲も明記しています。

- 現時点の対象は、VM の作成と設定、vCPU の管理、メモリの管理の 3 つです。I/O デバイスの管理と、ライブアップデートやライブマイグレーションは対象に挙げられていません。
- 証明しているのは Rust の実装を形式化したモデルで、Rust からモデルへの翻訳は手作業です。複数の CPU が同時に動く場合は、ロックの規律で逐次の実行に置き換えられることを前提にしています。
- キャッシュの時間差などを使うサイドチャネル攻撃は対象外です。ゲストの秘密を必要な短い間しか Isolation Engine の手の届く所に置かない secret hiding という別の対策で緩和します。
- Rust のコンパイラや CPU のハードウェアが仕様どおりに動くことは前提です。

解説ブログによると、Isolation Engine を最初に使ったインスタンスは、2026 年 6 月に提供が始まった M9g と M9gd です。

## Nitro Sandbox との関係

Nitro Sandbox の公開ドキュメントは、Isolation Engine に触れていません。ホワイトペーパーも Nitro Sandbox には触れていません。今回の実機でも、Isolation Engine が sandbox の隔離に関わっているかを外から観察する方法はありませんでした。ホワイトペーパーによると、Graviton5 では Isolation Engine だけがゲストを直接作れます。m9g の上の sandbox もそれを経由すると考えるのは自然ですが、資料にそう書かれているわけではありません。言えるのは、sandbox を作る Nitro Hypervisor のうち、VM どうしを隔離する部分が、Graviton5 では上の範囲で形式検証されている、ということまでです。

# 誤解しやすい点

confidential が守るのは、VM のメモリと CPU の状態、暗号化した書き込み層などです。ワークロード自身が漏らすものと、ノードが握っている入出力は守れません。[セキュリティモデルのページ](https://docs.aws.amazon.com/eks/latest/userguide/sandboxing-security-model.html)は、その例を具体的に挙げています。まず、ワークロード自身が漏らすものです。

| ワークロード自身が漏らすもの | 理由 |
|---|---|
| 標準出力に書いた秘密 | ログを許可していれば、ノードがそのまま受け取る |
| EFS や EBS に平文で書いたデータ | ノードは同じファイルシステムを自分の権限でマウントでき、EBS は中身を直接読める |
| 実行時に読み込んだ信頼できないコード | 起動後に取ってきたコードは policy の固定の外にある |

次に、ノードができることです。

| ノードができること | 理由 |
|---|---|
| 暗号化していないイメージの層を読む | イメージの層はノードを通って VM に渡される。中身を隠すにはイメージの暗号化が要る |
| ConfigMap、Secret、projected volume の中身を差し替える | policy が固定するのはマウントの場所で、中身ではない。CA 証明書のような信頼の起点は、digest で固定したイメージに入れる |
| 暗号化していない通信を見たり書き換えたりする | NetworkPolicy やセキュリティグループもノードの側で効く。TLS で相手の証明書を確かめ、Pod の中の通信は `localhost` ではなく `127.0.0.1` を使う（`/etc/hosts` はノードが書く） |
| EFS の接続先を差し替える | マウントは Pod ではなく EFS CSI ドライバーの IAM の主体で行われる。confidential では policy でファイルシステムの ID を固定する |
| Pod Identity の認証情報で読めるものを読む | ノードはそのノードの Pod の認証情報を発行できる |
| Secrets Store CSI Driver（Secrets Manager などの秘密をファイルとして Pod に渡す仕組み）で渡した秘密を読む | ノードを通って渡される |
| サービスを止める | VM を止めたり、CPU やネットワークを絞ったりできる |
| 時刻、DNS、配置のメタデータを偽る | ノードが提供している |

ほかにも、次の点は誤解しやすいので書いておきます。

- Pod の定義は、信頼する入力として扱われます。信頼できないイメージを動かすための機能で、信頼できない人が書いた Pod の定義を受け付けるための機能ではありません。sandbox の Pod を作ったり変えたりできる人を RBAC で絞り、Pod の中身の制約は admission control で強制します。
- KMS のキーポリシーに PCR の条件を書かなければ、計測値は記録されるだけで、誰も確かめません。PCR17 だけでなく、PCR8 の署名者の条件も要ります。
- 隔離は性能の予約ではありません。vCPU は時分割で共有され、合計で物理の vCPU を超えて割り当てられます。

# まとめ

isolated なら `runtimeClassName` を 1 行足すだけで、Pod は専用のカーネルを持つ VM の中で動き、ノードの root が `/proc` から読めた範囲にはメモリの中身がありませんでした。confidential では、policy を生成して annotation に付けると書き込み層のディスクの中身も見えなくなり、KMS のキーポリシーに PCR の条件を書くと、承認した policy の計測値を示した Pod だけが復号できました。一方で、ノードに置いたランタイム監視からは sandbox の中が見えなくなるので、監視は監査ログとネットワークの記録を軸にし、中の振る舞いは Pod の中で見張る設計が要ります。既定の帯域の上限や、カーネルが止まったときに exec の probe で気づけないことなど、通常の Pod とは違う運用上の注意もあります。

確かめていないことは次のとおりです。

| 項目 | 内容 |
|---|---|
| メモリを読む別の方法 | `/proc` と共有領域を探す以外の方法で、ノードからゲストのメモリに届くか |
| ボリューム | EBS と EFS を sandbox から使ったときの性能と、confidential での扱い |
| 暗号化したイメージ | イメージの層を暗号化し、sandbox の中で KMS を使って復号する機能 |
| パケット数の数え方 | TCP で帯域だけ上げたときに 750 Mbps 出た理由 |
| ServiceAccount トークン | ドキュメントの記載と実機の結果が違った理由 |
| 2 スレッドのコアの制御 | 1 コアに 2 スレッドのインスタンスで、sandbox どうしが同じコアを使わない制御の影響 |
| ネットワークの性能 | 上限を外したときの帯域とレイテンシーが、通常の Pod とどれだけ違うか。ノードの外への TCP で、帯域だけ上げたときにどうなるか |
| vsock の通信経路 | ネットワークを切った Pod に、ノードの root が vsock から実際に接続できるか（ドキュメントでは接続できるとされている） |
| ほかの死活の確認 | TCP の probe や、アプリケーションだけが固まった場合の検知。ネットワークを切った Pod で使える検知の方法。カーネルが止まった Pod が Service の振り分け先に残るか |
| confidential の更新 | ローリング更新で新旧の PCR17 が並ぶときのキーポリシーの書き方と、Deployment が作る名前の変わる Pod での policy の扱い |
| ノードを含む起動時間 | sandbox のノードが無い状態から最初の Pod が準備完了になるまでの時間 |
| Pod の中の eBPF の監視 | BTF の無い sandbox のカーネルで、eBPF を使う監視ツールが動くか |
| GuardDuty の検知 | GuardDuty が sandbox の Pod について何を検知できるか（今回は有効にしていない） |
| Isolation Engine | Nitro Sandbox の隔離に Isolation Engine が関わっているか |
