# はじめに

答えの型が決まった分類のような仕事では、大きなモデルにしばらく答えさせ、その答えで小さなモデルを鍛えると、小さなモデルでも近い精度が出ることがあります。大きなモデルの答えで小さなモデルを鍛えることを蒸留と呼びます。難しいのは鍛えることよりも、いつ切り替えてよいかを決めることです。点数を一度測って良さそうだから切り替える、というやり方では、選ぶのに使ったデータでたまたま良く見えただけかもしれません。

この記事では、筆者が作っている [tierbook](https://github.com/littlemex/tierbook/tree/36ea5132afeb84266b8ddf860eda27c3aa68a691) という OSS で、この切り替えの判断を試した結果を紹介します。先生役の大きなモデルが答えた記録から安い生徒を育て、生徒が統計的な証明書を得たときだけ仕事を渡し、依頼をどのモデルに送るかを決めるルーターで実際に振り分けを確かめました。

結果を先に書くと、パラメータ数 8 億 (0.8B) の小さな LLM を生徒にして CPU で動かす前提で値段を付けると、最低の正解率 0.80 では、受理 1 件あたりの費用が先生の 0.30 倍で合格しました。1,200 件での正解率は先生が 0.896、この生徒が 0.873 です。最低の正解率は最初 0.85 と宣言し、0.80 は実験の途中で足した値です。0.85 では、先生へ回す組み合わせが 2 回目の判定で先生の 0.41 倍で合格しましたが、仮の合格として扱っています。

この 0.30 倍は、16 問ずつまとめて処理し、常に全力で動かし、学習の費用を 100 万件で割る前提の値で、1 問ずつ処理するなら 0.43 倍です。その代わり、レイテンシーは先生の中央値 45.2 ms に対して、1 問ずつで約 0.28 秒、16 問ずつでは 1 回の処理に約 2.9 秒かかります。同じ作り方の生徒を GPU の vLLM で動かした構成は、OpenAI の API と同じ形式で依頼を受けるルーター (以下、OpenAI 互換のルーター) から呼べることを通し試験で確かめました。

ただし、ルーターに実際に依頼を流す通し試験をしたのは、その GPU の構成と、LightGBM の生徒を使った構成の 2 つです。CPU 版をルーターの後ろで動かす仕組みは、16 問をまとめる部分を含めてまだ作っていません。CPU 版の判定は、GPU で答えさせた記録に CPU の値段を付けたものです。精度と処理件数は実際に測った値で、費用はそれに料金と前提を掛けて計算した値です。費用に入れた項目と入れていない項目は「費用の内訳」の節にまとめます。

# tierbook の仕組み

tierbook は、採点済みの記録から、利用者が決めた最低の正解率を満たす中で一番安いモデルをタスクの種類ごとに決め、その決定をルーターの設定に書き出すツールです。依頼を受けて振り分けるのはルーター、答えるのは先生と生徒で、tierbook 自身は依頼の経路に入りません。

部品はどれも他にあります。安いモデルに先に答えさせ、点数がしきい値に届かなければ高いモデルに回す cascade は、既存の研究と製品にあります。[FrugalGPT](https://arxiv.org/abs/2305.05176) (Chen ら、2023 年) は別に学習した採点モデルの点数を、[AutoMix](https://arxiv.org/abs/2310.12963) (Aggarwal ら、2023 年) は小さいモデル自身による答えの検証を、[vLLM Semantic Router](https://github.com/vllm-project/semantic-router) の confidence 機能は答えの logprob を使います。この記事の生み出す版の cascade は 3 つ目と同じ logprob の方式で、確かめたのは 2026 年 11 月の開発版です。依頼と応答の記録から小さなモデルをファインチューニングするサービスには [OpenPipe](https://openpipe.ai/) などがあり、答えを採点して点数を集め、基準と比べる道具には [Braintrust](https://www.braintrust.dev/) や [Langfuse](https://langfuse.com/) などがあります。

合格の決まりも新しいものではありません。データの一部で候補と順番を決め、残りのデータで固定した順に検定する考え方は、[Learn then Test](https://arxiv.org/abs/2110.01052) (Angelopoulos ら、2021 年) と、それを複数の指標の両立に使った [Pareto Testing](https://arxiv.org/abs/2210.07913) (Laufer-Goldshtein ら、2022 年) にあります。これらの研究は件数が少なくても成り立つ検定を使いますが、tierbook は近似である Wilson の区間を使うので、保証はおよその値です。

tierbook はこれらを置き換えません。蒸留は学習の仕組みが、採点は利用者の採点器が、振り分けはルーターが受け持ち、tierbook はその間で、どの担当に切り替えてよいかの判定と、料金を測定から分けて計算し直すことと、ルーターの設定の書き出しを受け持ちます。

この記事で使う言葉を先に決めておきます。

- 担当は、仕事を任せる先の候補で、tierbook では arm と呼びます。単独のモデルのほか、生徒が先に答えて自信が足りなければ先生に回す組み合わせも、1 つの担当として扱います。
- 受理は、担当の答えを、利用者が用意した採点器が良しとすることです。今回の採点器は「データセットの正解ラベルと一致するか」なので、受理率は正解率と同じ意味になります。
- 合格ラインは、利用者が宣言する最低の受理率で、tierbook では floor と呼びます。
- 信頼下限は、測った受理率から統計的に言える「少なくともこれ以上」という値です。件数が少ないほど、測った受理率より低くなります。tierbook は、二項分布の信頼区間の求め方の 1 つである Wilson の区間の下端を使います。
- α は、信頼区間が本当の受理率を外す確率です。tierbook の区間は両側で、下に外れる確率と上に外れる確率が α の半分ずつです。
- 証明書は、選ぶのに使っていないデータ (後で述べる「確かめる半分」) で信頼下限が合格ライン以上になった、という判定の記録です。tierbook は certified と表示します。
- 受理 1 件あたりの費用は、1 回答えさせる費用を受理率で割った値です。

ここまでの言葉を使うと、全体の流れは次の図の 1〜6 になります。1 で先生が答えた記録をため、2 で生徒を鍛え、3 で担当を宣言し、4 で証明書を出し、5 でルーターの設定に書き出し、6 でルーターで流した結果を drift という機能で照らし合わせます。今回の実験では、LightGBM の生徒と読む版の 0.8B について、1 から 4 までを 1,000 件ずつ 9 区切り分くり返しました。cascade、固定順の検定、生み出す版の判定は 9 区切り目の記録だけで行い、5 と 6 は 2 つの経路で 1 回ずつ行いました。左端の帯は受け持ちを表し、1 は先生、2 は生徒、3・4・6 は tierbook、5 はルーターです。左下の箱は利用者が宣言する値で、後の表にまとめます。

![tierbook の流れ。1 先生が答える、2 生徒が学ぶ、3 担当を宣言する、4 証明書を出す、5 ルーターに書き出す、6 成績を見張るの順に進み、1 から 4 は次の 1,000 件でくり返す。合格ライン、α、しきい値などは利用者が宣言する](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/a2a7df365ee71e/zenn/articles/a2a7df365ee71e/loop.png)

決め方は次のとおりです。採点済みの記録を、問題のハッシュで「選ぶ半分」と「確かめる半分」に分けます。選ぶ半分で、信頼下限が合格ライン以上の担当のうち受理 1 件あたりの費用が一番安いものを選び、確かめる半分でも信頼下限が合格ライン以上のときだけ合格とします。費用はその日の料金表から計算し直すので、値段が変わったときは測り直さずに割り当てを引き直せます。

本当の受理率が合格ラインに届かない担当を誤って合格させるのは、信頼区間の下端が本当の受理率より上に来てしまったときだけです。その確率は 1 回の判定あたり、多くてもおよそ α の半分です。α が 0.05 なら約 0.025 で、Wilson の区間は近似なので、この確率もおよそです。

合格を左右する値には既定値がなく、すべて宣言します。今回の宣言は次のとおりです。drift の結果の読み方は「ルーターでの通し試験」の節で説明します。

| 項目 | 今回の値 |
|---|---|
| 信頼下限の求め方 | Wilson の区間の下端 |
| α | 0.05 (後で述べる 2 回目の判定だけ 0.025) |
| 確かめる半分の割合 | 0.5 |
| 確かめる半分で調べる担当の数 | 最初は 1 で、一番安い担当だけを調べました。固定順の検定を入れた後は、選ぶ半分の候補を全部調べました |
| 合格ライン | 最初は 0.85 です。精度をどこまで譲るかを比べるため、途中から 0.80 と 0.75 でも同じ記録を判定しました |
| 記録の無い問題の扱い | 受理しなかったものとして数えます |
| 先生と学習にかかった費用 | 100 万件の依頼で回収する前提で割り振ります |

# 実験の設定

実験は 2026 年 11 月 9 日から 10 日に行い、料金は 11 月 9 日に AWS の料金表から引いた値です。題材は、金融ニュースの見出しを bearish・bullish・neutral の 3 つに分ける感情分類です。データセットには MIT ライセンスの [zeroshot/twitter-financial-news-sentiment](https://huggingface.co/datasets/zeroshot/twitter-financial-news-sentiment) を使い、次のように分けました。

| 使い道 | 件数 | 中身 |
|---|---|---|
| 学習 | 1,000 件ずつ 9 区切り | 学習用の分割から順に流し、区切りごとに生徒を鍛え直して判定し直しました。記録がたまっていく様子を模しています |
| しきい値と学習方法の選択 | 300 件 | tierbook の合格判定には一度も使っていません |
| 合格判定 | 1,200 件 | 選ぶ半分と確かめる半分が約 600 件ずつです。最後の判定だけ 588 件を足して 1,788 件にし、確かめる半分は 887 件になりました |
| ルーターでの通し試験 | 経路ごとに 300 件 | 学習にも選択にも合格判定にも使っていない問題です |

合格判定用の 1,200 件のうち 66% が neutral なので、常に neutral と答えるだけで正解率は 0.659 になります。正解ラベルはありますが、正解が無い仕事での学習を模すため、合格判定に出した生徒の学習には先生の答えだけを使いました。正解ラベルは、合格判定の採点と、学習方法としきい値を選ぶ 300 件の採点に使っています。正解ラベルを 5% 混ぜる学習も試しましたが、採用していません。

先生は [Prismyra](https://github.com/littlemex/Prismyra) の判断用のモデル `littlemex/prismyra-decision-35b-a3b-fp8` です。Prismyra も筆者の OSS で、判断用のモデルと、その答えで小さな生徒を育てて自信のある問題だけ生徒に答えさせる振り分け役をまとめたものです。この記事で先生と呼ぶのは判断用のモデルのほうです。Prismyra にも、生徒を使ってよいかを先生の答えとの一致で決める独自の基準があります。tierbook の証明書は、採点器が受理する割合を、選ぶのに使っていないデータで見る点が違います。今回の実験のために Prismyra に足した、自信度で振り分ける場合の基準と OpenAI 互換のエンドポイントは、2026 年 11 月 11 日に Prismyra の main に取り込みました。このモデルはパラメータ数が全体で 350 億 (35B) あり、トークンごとに一部の重みだけを使う MoE という作りで、1 回に使うのは 30 億 (3B) 分です。重みを 8 ビットの fp8 に量子化し、NVIDIA L40S 1 枚で動かしました。

# 生徒の育て方

生徒は 2 種類を育てました。決定木を積み重ねる軽い分類器の LightGBM と、パラメータ数 8 億の LLM (0.8B) です。0.8B は学習のさせ方で「読む版」と「生み出す版」に分かれ、OpenAI 互換のルーターで使えるのは生み出す版だけです。

LightGBM の生徒は、Prismyra の標準の入力である単語の出現を数えた特徴量では、正解率が 0.71 前後で頭打ちでした。入力を文章の埋め込みに替えると、合格判定用の 1,200 件で 0.81 まで上がりました。埋め込みは、`BAAI/bge-small-en-v1.5` などのモデルで文章の意味を数字の並びに変えたものです。

それより大きく伸びたのは、0.8B の `Qwen/Qwen3.5-0.8B` を先生の答えで学習させたことです。9 区切り目までに先生が答えた 9,000 件のうち 8,100 件で学習させると、1,200 件での正解率が先生の 0.896 に対して 0.885 になりました。

0.8B では、学習のさせ方そのものにも大事な違いがありました。この記事では 2 つを区別します。

- 読む版は、3 つのラベルの語の点数 (logit) どうしを比べるだけの学習をしたものです。答えるときも、3 つの点数のうち一番高いものを読みます。指示文を付けた標準の入力 (1 件約 68 トークン) と、見出しだけの入力 (約 37 トークン) の 2 通りで学習させ、上の 0.885 は標準の指示文のほうです。
- 生み出す版は、全語彙に対して「ラベルの語と終わりの記号」を生み出す形で、見出しだけの入力で学習させたものです。1,200 件での正解率は 0.873 でした。

読む版に文章を生み出させると、「1111」のような意味のない出力になりました。全語彙の中でラベルの語を上に出すことを学んでいないからです。生み出す版だけがルーターで使えるのは、OpenAI 互換のルーターがモデルに文章を生み出させて使うからです。

# cascade としきい値

生徒が自信のあるときだけ答え、迷ったら先生に回すやり方を、tierbook では cascade として宣言します。`candidates.json` に次のように書きます。

```json
"student-or-teacher": {"cascade": {"primary": "student", "fallback": "teacher", "threshold": 0.98, "on_no_score": "fallback"}}
```

`threshold` は、生徒の答えの自信度がこの値以上なら生徒の答えを使う、という境目です。自信度はモデルが自分の答えをどれだけ確からしいと見ているかの値で、統計の信頼下限とは別物です。`on_no_score` は、自信度が記録されていない答えをどう扱うかの指定です。自信度の計算は生徒の種類で違います。LightGBM は分類器が出すラベルの確率、読む版は 3 つのラベルの点数から求めた確率、生み出す版はルーターと同じ logprob の平均から求めた値です。しきい値の数字は、種類をまたいで比べられません。tierbook は生徒と先生それぞれが実際に答えた記録から cascade の答えを組み立て、両方が使った分を足して値段を付けます。

## しきい値は合格判定に使わないデータで決める

しきい値は、合格判定に使わない 300 件で先に 1 つに決めてから、担当として宣言します。規則は、300 件での信頼下限が合格ライン以上になる中で一番安いしきい値を選び、無ければ信頼下限が一番高いものを選ぶ、というものです。ただし、この 300 件では 0.50〜0.99 のどのしきい値でも cascade の正解率が 0.84〜0.85 で、しきい値の優劣は見分けられませんでした。合格ライン 0.85 では信頼下限が合格ライン以上になるしきい値が無く、信頼下限が一番高いものを選んでいます。

こう決めたのは、しきい値の候補をそのまま担当として並べると、候補を増やすほど、たまたま良く見える安い担当が選ばれやすくなるからです。その担当は確かめる半分で落ちやすく、誤って合格させる確率は増えませんが、合格できる担当を取りこぼします。実際に 0.50 から 0.99 までの 9 つのしきい値を 2 種類の生徒に掛けて 18 の担当を足すと、合格ライン 0.85 で選ぶ半分を通る担当は 37 に増えましたが、選ぶ半分で一番安かったのは足す前と同じ生徒単独で、cascade は 1 つも合格になりませんでした。しきい値を別のデータで決めるという方針は、Hamel Husain さんらの記事「[How To Use Decision Models for Evals](https://hamel.dev/blog/posts/decision-model-evals/)」の指摘に沿っています。この記事は、点数の既定のしきい値には根拠が無く、結果を報告しないデータで決めるべきだと述べています。候補を増やすと取りこぼしやすくなるという点は仕組みからの筆者の見立てで、今回の実験で直接確かめたものではありません。

## 確かめる半分では高い順に調べる

前の節で cascade が 1 つも合格にならなかった直接の原因は、選ぶ半分で一番安い担当だけを確かめる半分で調べていたことです。安い担当がぎりぎり選ぶ半分を通ると、少し高いけれど確かめる半分でも合格する担当が隠れてしまいます。

そこで、固定順の検定 (fixed sequence procedure) と呼ばれる方法を入れました。選ぶ半分だけで安い担当をいくつか並べ、確かめる半分では高いほうから順に調べ、最初に落ちたところで止めます。合格した中で一番安い担当を採用します。調べる順番は、確かめる半分のデータを見る前に、選ぶ半分だけで決めます。そのため、調べる担当を増やしても、合格ラインに届かない担当を 1 つでも誤って合格させる確率は、多くても 1 回の判定と同じです。代わりに、高いほうが落ちると、それより安い担当は調べられません。この形は、前に挙げた Learn then Test や Pareto Testing と同じ考え方です。

合格ライン 0.85 での実際の例を次の表に示します。このとき並べた担当はほかにもありますが、表には先生と、選ぶ半分で安かった 3 つだけを載せています。

| 担当 | 選ぶ半分の信頼下限 | 確かめる半分の信頼下限 | 受理 100 万件あたりの費用 | 高い順に確かめた結果 |
|---|---|---|---|---|
| Prismyra (先生) | 0.877 | 0.860 | $46.9 | 選ぶ半分で、より安く信頼下限の高い担当に負けて候補から外れました |
| 読む版 (見出しだけを入力) から先生へ回す cascade | 0.879 | 0.853 | $17.2 | 合格し、これを採用しました |
| 読む版 (標準の指示文) 単独 | 0.868 | 0.838 | $14.1 | 不合格で、ここで止めました |
| 読む版 (見出しだけを入力) 単独 | 0.856 | 0.823 | $9.0 | 前の段で止まったので、この手順では調べません。0.823 は、以前のやり方でこの担当だけを調べたときの値です |

以前のやり方では、一番安い「読む版 (見出しだけを入力) 単独」だけを調べて落ち、先生の 37% の費用で済む cascade を見落としていました。

# 合格判定の結果

担当によって、どの仕組みから呼べるか (以下、経路) が違います。読む版は、ラベルの点数を読む専用の仕組みからしか呼べません。生み出す版は vLLM Semantic Router から呼べます。LightGBM の生徒は、Prismyra の振り分け役から呼べます。tierbook は合格ラインごとに一番安い合格者を選びますが、次の表には、合格ライン 0.85 と 0.80 のそれぞれで、経路ごとの合格者を並べました。この表で、生徒を使う担当のうち OpenAI 互換のルーターから呼べるのは 3 行目だけです。cascade の行の比は、先生の GPU の空き時間を他の仕事が使い切る前提の値で、先生の GPU を cascade だけのために動かす場合は、先生単独より高くなります。生徒を CPU で動かした場合の行は、α と件数が違うので「CPU 版での再判定」の節の表に分けます。費用は受理 100 万件あたりで、先生の値段との比を添えています。

| # | 合格ライン | 担当 | しきい値 | 確かめる半分の信頼下限 | 受理 100 万件あたりの費用 | 先生との比 | 動かせる経路 |
|---|---|---|---|---|---|---|---|
| 1 | 0.85 | Prismyra (先生) | なし | 0.860 | $46.9 | 1 | OpenAI 互換のエンドポイント |
| 2 | 0.85 | 読む版 (見出しだけを入力) から先生へ回す cascade | 0.98 | 0.853 | $17.2 | 0.37 | ラベルの点数を読む専用の仕組み |
| 3 | 0.85 | 生み出す版から先生へ回す cascade、生徒は GPU | 0.98 | 0.851 | $46.5 | 0.99 | vLLM Semantic Router |
| 4 | 0.80 | Prismyra の振り分け役 (LightGBM の生徒から先生へ回す) | 0.8 | 0.834 | $9.4 | 0.20 | Prismyra の振り分け役 |
| 5 | 0.80 | 読む版 (見出しだけを入力) | なし | 0.823 | $9.0 | 0.19 | ラベルの点数を読む専用の仕組み |

ルーターでの通し試験に使ったのは 3 行目と 4 行目です。合格ライン 0.75 では、LightGBM の生徒単独が受理 100 万件あたり $0.99、先生の約 47 分の 1 で合格しました。この費用の半分近くは先生が答えを付けた費用の割り振りで、残りは CPU での埋め込みの計算です。

表全体にかかる注意は 3 つです。

- 合格判定用の 1,200 件は、学習方法やしきい値を比べた回を含め、何度も判定に使いました。毎回、選ぶ半分と確かめる半分に分けていますが、分け方は毎回同じで、同じデータを見ながら手順を変えています。どの行も、事前に決めた 1 回だけの判定より弱い証明書です。
- 誤って合格させる確率が多くてもおよそ α の半分というのは、合格ラインと担当の組 1 つごとの話で、表全体のどこかに誤りが混じる確率ではありません。
- 合格ライン 0.85 の行は、信頼下限と合格ラインの差が 0.001〜0.010 しかありません。Wilson の区間は近似なので、正確な方法に替えると不合格になる行がありえます。

行ごとの注記は次のとおりです。

- 2 行目は、cascade が確かめる半分で合格ラインを超えているのを見た後に、固定順の検定を足して同じ記録を判定し直した合格です。
- 3 行目は、全担当を並べた判定では選ばれず、その結果を見た後に、候補を vLLM Semantic Router で動かせる担当に絞って判定し直した合格です。生徒にも GPU の値段が付いたため、先生とほぼ同じ費用になっています。生徒の GPU での処理件数は 1 時間 109,908 件です。先生の処理件数は 8 件を並行して流して測りましたが、生徒も同じ条件で測ったかは記録で確かめられないので、3 行目の費用は目安です。
- 4 行目は 6 区切り目までの記録で鍛えた LightGBM の生徒を、Prismyra の固定のしきい値 0.8 で判定した値です。9 区切り目では、合格ライン 0.80 でこの振り分け役より安い担当が合格しています。

# ルーターでの通し試験

合格させただけでは仕事は渡せないので、2 つの経路で実際にルーターを動かし、合格判定に使っていない 300 件ずつを流しました。実際の利用者からの依頼ではなく、同じデータセットの問題を流した試験なので、問題の傾向の変化は見ていません。

流した結果は drift で照らし合わせます。drift には流した依頼の答えを採点した記録が要るので、正解が無い仕事では、採点の手段と費用を別に用意する必要があります。結果は 3 通りです。新しい結果の信頼下限が合格ライン以上なら confirmed、信頼区間が合格ラインをまたいでいれば consistent、信頼区間全体が合格ラインを下回れば contradicted です。consistent は、食い違うとは言えないが、合格ラインを超えるとまでは確かめられていない状態です。その幅は広く、300 件で合格ライン 0.85 の場合、受理が 243〜267 件のあいだはすべて consistent になり、contradicted になるのは 242 件以下のときです。小さな劣化は、この件数では見つかりません。

## Prismyra の振り分け役

1 つ目は表の 4 行目の Prismyra 自身の振り分け役です。tierbook から Prismyra の設定に書き出して起動しました。300 件のうち生徒が 203 件を中央値 13.8 ms で答え、残り 97 件を先生が中央値 45.2 ms で答えました。300 件中 263 件が受理され、信頼下限 0.835 が合格ライン 0.80 以上だったので、drift の結果は confirmed でした。

## vLLM Semantic Router

2 つ目は表の 3 行目で、vLLM Semantic Router を使いました。構成と結果は次の図のとおりです。ルーターは依頼をまず 0.8B の生徒に送り、生徒の答えの自信度が 0.98 に足りない依頼だけを Prismyra に回します。

![vLLM Semantic Router が 0.8B の生徒の答えの自信度を見て、0.98 以上ならその答えを返し、足りなければ Prismyra に回す構成。300 件の通し試験では生徒が 269 件、先生が 31 件に答え、267 件が受理され、合格ライン 0.85 に対する drift の結果は consistent](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/a2a7df365ee71e/zenn/articles/a2a7df365ee71e/serving.png)

ルーターは、モデルの答えのトークンごとの確からしさの対数である logprob から自信度を計算します。ここで大事なのは、合格判定に使った自信度と、ルーターが計算する自信度が同じであることです。違う値で合格させた証明書は、ルーターでは意味を持ちません。そこで、使った開発版のルーターの[ソース](https://github.com/vllm-project/semantic-router/blob/37bdd814a71f5c4a490abbc2b2abd80e2e3493b2/src/semantic-router/pkg/looper/confidence.go#L404-L417)で、自信度の式を確かめました。答えのトークンの logprob の平均を $\bar{\ell}$ とすると、自信度は次の値です。

$$
\min\left(1,\ \max\left(0,\ \frac{\bar{\ell} + 3}{3}\right)\right)
$$

次に、GPU 上の vLLM 0.27.1 で動かした生み出す版の答えを、この式と、ルーターが送るのと同じ依頼の形で記録し直しました。しきい値は 300 件の選択用データで 0.98 に決め、先生へ回す cascade を合格ライン 0.85 で判定して合格させ、`export-policy --target vsr --cascade-confidence avg_logprob` で書き出しました。tierbook は、自信度の計算方法が宣言されない限り cascade を書き出しません。

ルーターで流した 300 件では、ルーターが生徒に任せた 269 件と先生に回した 31 件が、記録した自信度から予測した振り分けと 300 件すべてで一致しました。同じ式と同じ入力なので一致するはずのものですが、式や依頼の形が食い違っていればここで見つかります。受理は 300 件中 267 件で、信頼下限 0.8495 は合格ライン 0.85 をわずかに下回り、drift の結果は consistent でした。267 件は、consistent になる範囲 (243〜267 件) の上端です。この件数では、成績が合格ラインを少し上回る程度の担当は confirmed になりにくいです。この経路で確かめられたのは、合格判定どおりに振り分けることまでです。

# CPU でのスループットの改善

3 行目の生徒は GPU の値段で先生とほぼ同じ費用だったので、生み出す版を CPU で動かして値段を下げました。見出しだけを入力し (1 件約 37 トークン) ラベル 1 語を出す処理を 200 件で測ると、処理の仕方を変えて 1 時間あたりの処理件数は 7,105 件から 19,612 件になり、値段にはこの値を使いました。入力が長い仕事や、長時間流したときの値は測っていません。tierbook は、自前で動かすモデルの値段を、時間料金を実測した 1 時間あたりの処理件数で割って付けるので、スループットを上げれば値段が下がり、値段が変わったときと同じように割り当てが変わります。CPU は AWS の Arm 系 CPU である Graviton4 の c8g.xlarge (4 コア、4 スレッド) で、PyTorch 2.15 で動かしました。

| 生み出す版の処理の仕方 | 1 時間あたりの件数 |
|---|---|
| 8 問ずつまとめて処理 | 7,105 件 |
| 1 問ずつ処理 | 12,918 件 |
| 出力層の行数を 16 の倍数にそろえ、出力層を最後の位置だけ計算して 8 問ずつ処理 | 19,488 件 |
| 同じ工夫で 16 問ずつ処理 | 19,612 件 |

最初は 8 問ずつにすると、スループットが 1 問ずつより低くなりました。調べると、出力層の計算で、まとめた 8 問分の 8 行と全語彙の行列を掛ける計算だけ、CPU の行列計算ライブラリ oneDNN が極端に遅い方法を選んでいました。1 回 871 ms かかり、16 行なら 52 ms です。行数をそろえるために足した行は計算後に捨てるので、答えは変わりません。19,612 件は最初の 7,105 件の 2.76 倍、1 問ずつの 12,918 件の 1.52 倍です。

その代わり、レイテンシーは長くなります。先生は通し試験で中央値 45.2 ms でしたが、CPU の生徒は 1 問ずつで約 0.28 秒、16 問ずつでは 1 回の処理に約 2.9 秒で、16 問がそろうまでの待ち時間がこれに加わります。cascade で先生に回る依頼は、生徒の時間のあとに先生の時間がかかります。16 問をまとめる仕組みはルーターの後ろにまだ置いておらず、件数と値段だけを測りました。

生み出す版は、読む版で先に試した 2 つの工夫も使っています。重みを 16 ビットの浮動小数点数 bf16 にすることと、このモデルが使う linear attention の一種である Gated DeltaNet の計算を一括の解法に置き換えることです。見出しだけを入力にした読む版は、これらの工夫に、ラベル 3 語の点数だけを最後の位置で計算することと 8 問ずつの処理を加えて、1 時間 27,848 件になりました。「合格判定の結果」の表の 5 行目の値段はこの値から付けています。この読む版のラベルは、GPU で動かしたときと 200 件中 199 件で一致しました。工夫の中身は[実験の記録](https://github.com/littlemex/tierbook/blob/36ea5132afeb84266b8ddf860eda27c3aa68a691/docs/verify/v0.5.0-distillation-loop.md#round-6-tune-how-the-08b-is-served-not-what-it-answers)にあります。

生み出す版は、上の表のどの段でも、答えのラベルが GPU で動かしたときと 200 件すべてで一致することを確かめてから値段に使いました。ルーターが生徒に任せるかどうかの判断は、しきい値 0.98 で 200 件中 199 件が一致し、自信度の差は最大 0.0276 でした。合格ライン 0.85 の cascade が使うしきい値 0.99 では、1 問ずつと 8 問ずつの測定で 200 件すべて一致しましたが、値段に使った 16 問ずつの測定では確かめていません。

# CPU 版での再判定

CPU の値段で判定し直すと、合格ライン 0.80 では生み出す版の生徒単独が先生の 0.30 倍の費用で合格しました。合格ライン 0.85 では、先生へ回す cascade が 1 回目はわずかに届かず、問題を足した 2 回目の判定で 0.41 倍で合格しました。次の表は 2 回目の判定の値で、α は 0.025、確かめる半分は 887 件です。「合格判定の結果」の表の行とは条件が違うので、信頼下限をそのまま比べることはできません。なお、合格ライン 0.80 の生徒単独は、1 回目の判定 (α 0.05、1,200 件) でもすでに先生の 0.30 倍で合格しています。後で書く 2 回目の判定の弱い点は、合格ライン 0.85 の cascade の行だけに当てはまります。先生との比は、同じ回の先生の値段 (受理 100 万件あたり $46.7) に対するものです。

| 合格ライン | 担当 | しきい値 | 確かめる半分の信頼下限 | 受理 100 万件あたりの費用 | 先生との比 | 動かせる経路 |
|---|---|---|---|---|---|---|
| 0.85 | 生み出す版から先生へ回す cascade、生徒は CPU | 0.99 | 0.8515 | $19.1 | 0.41 | vLLM Semantic Router (CPU 版は未接続) |
| 0.80 | 生み出す版、CPU | なし | 0.825 | $13.9 | 0.30 | vLLM Semantic Router (CPU 版は未接続) |

合格判定には、同じ手順と乱数の種で学習し直した生み出す版を GPU の vLLM で答えさせた記録を使い、値段だけを CPU の測定から付けました。つまり、この表の証明書は GPU で答えさせた記録に対するものです。前の節で確かめた 200 件すべての一致から言えるのは、CPU と GPU の答えの食い違いがおよそ 2% 以下ということまでです。0.85 の cascade の信頼下限と合格ラインの差 0.0015 はこれより小さいので、この合格は、CPU で答えさせた記録で判定し直すまで仮のものです。しきい値は、学習し直したモデルについて同じ 300 件と同じ規則で決め直し、合格ライン 0.85 では 0.99 になりました。学習し直したのは通し試験に使ったモデルの重みを保存していなかったためで、学習は完全には再現しないため、新しいモデルの答えが元のモデルと一致したのは 93.4% の問題でした。値段の付け方と前提は、次の「費用の内訳」の節にまとめます。

2 回目の判定の経緯は次のとおりです。合格ライン 0.85 では、1 回目の判定で cascade の信頼下限が 0.849 で、わずかに届きませんでした。そこで、まだどこにも使っていなかった 588 件を合格判定の問題に足し、この判定だけ α を 0.025 に下げて改めて判定しました。

この 2 回目の判定には弱い点があります。1 回目は α が 0.05、2 回目は 0.025 なので、1 回あたりの上限であるおよそ α の半分を足すと、2 回のどちらかで誤って合格させる確率は、多くても次の値です。

$$
\frac{0.05}{2} + \frac{0.025}{2} = 0.0375
$$

1 回だけ判定した場合のおよそ 0.025 より大きくなります。これはこの 2 回だけを数えた値で、同じ 1,200 件を以前の回で学習方法やしきい値の比較に使った分は入っていません。この足し算が成り立つのは 2 回で止めた場合だけで、合格するまで問題を足し続けるやり方には当てはまりません。また、2 回目を見ると決めたのは 1 回目の結果を見た後です。信頼下限と合格ラインの差も 0.0015 しかないので、この結果は今回の記録の中で一番弱い証明書として扱っています。

# 費用の内訳

CPU の生徒の値段は、次のように付けました。c8g.xlarge の時間料金 $0.20 を 1 時間の処理件数 19,612 件で割ると、推論の費用は 100 万件あたり $10.2 です。先生が 9,000 件に答えを付けた費用 $0.37 と、L40S での 1,203 秒の学習の費用 $1.27 は、9 区切り目の学習 1 回分です。区切りごとの鍛え直し、合格判定用と選択用の問題に先生が答えた費用、採用しなかった学習の費用は入れていません。合計 $1.64 を、生徒が今後答える依頼の数として宣言した 100 万件で割ると、推論と同じ単位で依頼 100 万件あたり $1.6 です。丸める前の値で足すと依頼 100 万件あたり約 $11.85 で、記録では $11.9 と表示しています。生徒単独の値段は、これを受理率で割った値です。cascade の値段は、これに先生へ回した問題の分の先生の費用を足してから受理率で割っています。100 万件という前提が小さくなるほど、また 100 万件に届く前に鍛え直すほど、割り振る分が大きくなり、生徒は高くなります。1 問ずつ処理すると、生徒単独は受理 100 万件あたり $20.0、先生の 0.43 倍です。

費用に入れたのは、モデルを動かすインスタンスの時間料金と、先生のラベル付けと学習 1 回分だけです。ルーター自体の計算資源、止まらないように複数台を置く分、依頼が来ない待ち時間、drift のための採点の費用は入れていません。

CPU で動かしても、0.8B の生み出す版の費用は先生の 0.30〜0.41 倍までしか下がりませんでした。料金はどれも ap-northeast-1 のオンデマンドです。先生の GPU は、L40S を 4 枚積んだ g6e.12xlarge ($15.22/h) の 1/4 として 1 時間 $3.80 とし、残りの 3 枚も使われている前提です。これは c8g.xlarge の $0.20 の 19 倍です。しかし、8 件を並行して流した測定で先生は 1 時間に 91,367 件をこなし、生徒の 19,612 件の 4.7 倍です。先生の処理件数はこの 1 条件で測った値で、生徒のように処理の仕方を調整した値ではありません。並行数を上げて先生のスループットが伸びれば、0.30 倍という比はその分だけ大きくなります。先生は全体が大きくても、1 回に使う重みは 3B 分です。今回の測定で CPU の費用が先生を大きく下回ったのは、LightGBM の生徒でした。ただし合格できたのは合格ライン 0.75 までで、そのときの費用が先生の約 47 分の 1 でした。

この比較は、GPU も CPU も常に全力で動いている前提です。依頼が少なく 1 割しか動いていなければ、先生も CPU の生徒も 1 件あたりの費用は 10 倍になります。依頼が毎時 1.2 万件ほどまでなら生徒は c8g.xlarge 1 台で足り、$0.20/h の CPU と $3.80/h の GPU を動かし続ける費用の比べ合いになります。cascade では、生徒が答えられない問題のために先生の GPU も動かし続ける必要があります。先生の GPU を cascade だけのために動かすと、GPU の $3.80/h はそのままで CPU の費用が加わるので、先生単独より高くなります。cascade の 0.37〜0.41 倍になるのは、先生の GPU の空き時間を他の仕事が使い切る場合だけです。

# 限界

まだ示していないことは次のとおりです。

- 1 回の実験は数百〜数千件です。蒸留は 3 ラベルの簡単な分類 1 つだけで、採点に判定役のモデルが要るような自由記述の生成は試していません。
- 正解が無い仕事を模したのは学習だけで、採点には正解ラベルを使っています。クラスごとの正解率は見ていません。
- 証明書が保証するのは、利用者の採点器が受理する割合です。採点器が正しいかどうかは保証しません。採点器がモデルの場合、その誤りは証明書にそのまま入ります。
- 保証が及ぶのは、合格判定と同じような問題が来る場合だけです。タスクの種類を取り違えて届いた依頼は、証明書の外にあります。
- 正解ラベルや先生の答えで小さな分類用のエンコーダーを直接学習させる定番のやり方とは、比べていません。0.8B の LLM を選んだのは、OpenAI 互換のルーターでそのまま使えるからです。
- cascade の自信度は、生徒自身が出す確率や logprob から計算する方式だけを試しました。FrugalGPT のように採点モデルを別に学習する方式や、AutoMix のように生徒に自分の答えを検証させる方式とは、比べていません。
- 点数を一度測って切り替える素朴なやり方と比べて、証明書が誤った切り替えを何件防いだかは、まだ測っていません。
- 先生の Prismyra も tierbook も筆者の OSS で、第三者による再現はまだありません。

# まとめ

安い生徒に仕事を渡す判断を、選ぶのに使っていないデータでの信頼下限で決め、合格したものだけをルーターの設定に書き出し、ルーターで流した結果も合格判定と照らし合わせる流れを試しました。OpenAI 互換のルーターで使える 0.8B の生み出す版は、16 問ずつまとめて CPU で常に全力で動かす前提で、合格ライン 0.80 なら先生の 0.30 倍の費用で合格しました。その代わり、レイテンシーは先生より長くなります。この合格は同じ合格判定用のデータを繰り返し使った上での判定で、CPU 版のルーターでの通し試験はまだです。合格判定と通し試験の結果は[実験の記録](https://github.com/littlemex/tierbook/blob/36ea5132afeb84266b8ddf860eda27c3aa68a691/docs/verify/v0.5.0-distillation-loop.md)に残しています。料金と先生の処理件数は「費用の内訳」の節に書いた値です。
