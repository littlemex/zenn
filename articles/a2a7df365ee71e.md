# はじめに

:::message
今回は完全に趣味ブログですにゃ。趣味では数理統計とかモデル開発に興味があるけど、クソ雑魚ですにゃ。
:::

この取り組みの出発点は、セルフホストの LLM でどんな価値を出せるかを探ることです。大きな GPU インスタンスは趣味用では気軽に使えないので、NVIDIA L40S を 4 枚積んだ g6e.12xlarge 程度の規模で、いろいろと趣味の実験を回しています。2026 年 9 月 15 日に TypeSafe AI の Jev が登場しました。Jev は、文書を読んで型の決まった質問に確率つきで答える判断用モデル (decision model) です。LLM から文章を生み出す decode の部分を外し、出力の head を少し変えればすぐに同じものが作れそうだと思い、2 週間後には強化学習まで終えたモデル [Prismyra](https://github.com/littlemex/Prismyra) を、サービングエンジンも含めて自作して Hugging Face に公開しました。セルフホストの価値を模索することは、LLM の API を否定するものではありません。データポイントなしにセルフホストを使うべきではない、あるいはユースケースが分からない、という立場とは違って、筆者は自分でデータポイントを集めながらその価値を探っています。

筆者が模索しているのは、パラメータの規模が大きくなっても、こうしたモデル開発やサービングエンジンの層から自分で作っていくことに意味があるかどうかです。実際に今回、自作した分類モデルの Prismyra を先生にして、蒸留の仕組みがうまく働くケースを見つけました。生徒への入力を文章の埋め込みに替える、つまり Amazon Bedrock などで使う LLM の API では **レスポンスに出てこない情報** を使って、LightGBM や `Qwen/Qwen3.5-0.8B` の生徒を裏側で育て、仕事を切り替える仕組みです。

この先に考えているのは、運用 (Ops) の形です。セルフホストの大きな LLM は先生として置いておき、ある程度定型の仕事では、そのワークロードに合わせて、LLM に処理を頼む実際のリクエストと、それに対するレスポンスの記録を取りながら、蒸留と学習を回して安い生徒を鍛えます。この仕組みが回って、性能と精度を保ちながら費用を下げていければ、大きなセルフホストへの投資に見合う効果が得られるのではないかと思っています。ただ、まだいろいろ試している途中で、本当にそうなるかは分かりません。

今回の記事で扱うのは、その一歩目です。生徒を育てることより難しいのは、いつ切り替えてよいかの判断です。そこで筆者の OSS の [tierbook](https://github.com/littlemex/tierbook/tree/56506022d7338a9b6146ace3ce8a76f2bb7d2cb2) で、生徒を選ぶのに使っていないデータで正解率を測り、その **信頼下限** (ばらつきを見込んだ低めの見積もり) が、利用者が決める最低の正解率である **合格ライン** を上回るかで判定しました。

結果は次の図のとおりです。CPU で動かす前提の生徒単独は、正解率 0.873 (先生は 0.896) で合格ライン 0.80 の判定に合格し、採点で正しいとされた答え 1 件あたりの費用である **受理 1 件あたりの費用** は、計算上、先生の 0.30 倍でした。青の網目が合格した担当、灰色が先生です。

![先生 (Teacher) は受理 100 万件あたり $46.7、正解率 0.896。先生へ回す cascade は $19.1 (0.41 倍)、正解率 0.878 (確かめる半分 887 件) で合格ライン 0.85 に合格。CPU の生徒単独は $13.9 (0.30 倍)、正解率 0.873 で合格ライン 0.80 に合格。GPU で答えさせた記録に 16 問ずつ・常に全力の CPU の値段を付けた計算値](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/a2a7df365ee71e/zenn/articles/a2a7df365ee71e/headline.png)

0.30 倍は、GPU で答えさせた記録に CPU の値段を付けた計算値で、16 問ずつまとめて常に全力で動かす前提です。CPU 版の生徒はまだルーターを通した試験をしておらず、レスポンスも先生より遅くなります。合格判定も同じデータを何度も使っているので、証明としては弱いものです。詳しくは後の節で書きます。

# tierbook の仕組み

tierbook は、採点済みの記録から、利用者が決めた最低の正解率を満たす中で一番安いモデルをタスクの種類ごとに決め、その決定をルーターの設定に書き出すツールです。リクエストを受けて振り分けるのはルーター、答えるのは先生と生徒で、tierbook 自身は、LLM へのリクエストが流れる経路には入りません。

リクエストの経路と、記録と設定の流れを次の図に示します。太い実線がリクエストの経路で、Client からのリクエストを Router が Student (CPU) か Teacher (GPU) に送ります。破線が記録と設定の流れで、答えの記録 (Answer records) を利用者の採点器 (Grader) が採点し、tierbook が candidates.json と declarations.json と合わせて判定 (derive / certify / drift) し、結果の policy.json をルーターの設定として書き出します。

![tierbook の構成。リクエストは Client から Router を通って Student (CPU) か Teacher (GPU) に届く。答えの記録を Grader が採点し、tierbook が candidates.json と declarations.json と合わせて判定し、policy.json をルーターの設定として書き出す。tierbook はリクエストの経路に入らない](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/a2a7df365ee71e/zenn/articles/a2a7df365ee71e/architecture.png)

部品はどれもすでに他にあります。安いモデルに先に答えさせ、点数がしきい値に届かなければ高いモデルに回す cascade は、既存の研究と製品にあります。[FrugalGPT](https://arxiv.org/abs/2305.05176) (Chen ら、2023 年) は別に学習した採点モデルの点数を、[AutoMix](https://arxiv.org/abs/2310.12963) (Aggarwal ら、2023 年) は小さいモデル自身による答えの検証を、[vLLM Semantic Router](https://github.com/vllm-project/semantic-router) の confidence 機能は答えの logprob を使います。この記事の生み出す版の cascade は 3 つ目と同じ logprob の方式です。リクエストとレスポンスの記録から小さなモデルをファインチューニングするサービスには [OpenPipe](https://openpipe.ai/) などがあり、答えを採点して点数を集め、基準と比べる道具には [Braintrust](https://www.braintrust.dev/) や [Langfuse](https://langfuse.com/) などがあります。

合格の決まりも新しいものではありません。データの一部で候補と順番を決め、残りのデータで固定した順に検定する考え方は、[Learn then Test](https://arxiv.org/abs/2110.01052) (Angelopoulos ら、2021 年) と、それを複数の指標の両立に使った [Pareto Testing](https://arxiv.org/abs/2210.07913) (Laufer-Goldshtein ら、2022 年) にあります。これらの研究は件数が少なくても成り立つ検定を使いますが、tierbook は近似である Wilson の区間を使うので、保証はおよその値です。

**tierbook はこれらを置き換えません**。蒸留は学習の仕組みが、採点は利用者の採点器が、振り分けはルーターが受け持ち、tierbook はその間で、どの担当に切り替えてよいかの判定と、料金を測定から分けて計算し直すことと、ルーターの設定の書き出しを受け持ちます。

tierbook では、仕事を任せる先の候補を **担当** (arm) と呼びます。単独のモデルのほか、生徒が先に答えて自信が足りなければ先生に回す組み合わせも、1 つの担当です。全体の流れは次の図の 1〜6 になります。1 で先生が答えた記録をため、2 で生徒を鍛え、3 で担当を宣言し、4 で証明書を出し、5 でルーターの設定に書き出し、6 でルーターで流した結果を drift という機能で照らし合わせます。

![tierbook の流れ (The tierbook loop)。1 先生が答える (Teacher answers)、2 生徒が学ぶ (Student trains)、3 担当を宣言する (Declare arms)、4 合格判定 (Certify)、5 ルーターに書き出す (Export to router)、6 drift の確認 (Drift check) の順に進み、記録がたまると 1 に戻ってくり返す。利用者が宣言するのは floor、alpha、held-out share、rungs to test、threshold、requests to amortise over](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/a2a7df365ee71e/zenn/articles/a2a7df365ee71e/loop.png)

tierbook がどの担当に仕事を渡すかの決め方は次のとおりです。考え方は 1 つで、合格ラインを満たすと統計的に言える担当のうち、一番安いものに渡します。そのために、精度の測り方、費用の測り方、選び方と確かめ方の 3 つを決めています。

1 つ目は精度の測り方です。担当の答えを利用者の採点器が良しとすることを **受理** (accepted) と呼びます。今回の採点器は「データセットの正解ラベルと一致するか」なので、受理率は正解率と同じ意味です。測った受理率は、どの問題がたまたま含まれたかによってぶれます。そこで、測った受理率から「少なくともこれ以上」と言える値である信頼下限 (lower bound、図では LB) を使い、これが合格ライン (tierbook では floor) 以上かで判定します。件数が少ないほど、信頼下限は測った受理率より低くなります。tierbook は、二項分布の信頼区間の求め方の 1 つである **Wilson の区間** の下端を使います。

2 つ目は費用の測り方です。担当ごとに 1 回答えさせる費用が違い、しかも答えのうち受理されるのは一部なので、使える答え 1 件を得るのにかかる費用で比べます。これが受理 1 件あたりの費用で、1 回答えさせる費用を受理率で割った値です。たとえば先生は 1 回答えさせるのに 100 万回あたり $41.6 かかり、受理率が 0.892 なので、受理 100 万件あたりでは $46.7 になります。1 回答えさせる費用は、API で呼ぶモデルならその料金、自前で動かすモデルなら時間料金を 1 時間に答えられる件数で割った値です。料金は料金表として測定の記録とは別に持ち、判定のたびに計算し直すので、値段が変わったときは測り直さずに選び直せます。

3 つ目は選び方と確かめ方です。同じデータで一番良く見える担当を選び、同じデータで合格させると、たまたま良く見えただけの担当が選ばれやすくなります。そこで、採点済みの記録を「選ぶ半分」と「確かめる半分」に分けます。どちらに入れるかは、問題の ID から計算したハッシュ値で決めます。ハッシュ値は結果を見る前に決まり、何度計算しても同じ問題は同じ側に入るので、都合の良い分け方を後から選ぶことができません。選ぶ半分では、信頼下限が合格ライン以上の担当のうち受理 1 件あたりの費用が一番安いものを選び、確かめる半分でも信頼下限が合格ライン以上のときだけ合格とします。この判定の記録を **証明書** と呼び、tierbook は合格を certified、届かないものを unconfirmed と表示します。

この選び方と確かめ方を次の図に示します。左の Scored records が採点済みの記録で、Split by hash(item) で 2 つに分け、上の Selection half で選び、下の Held-out half で確かめます。図の 1,200 items と約 600 件ずつの件数、alpha 0.05 は今回の実験の値です。

![採点済みの記録 1,200 件をハッシュで選ぶ半分と確かめる半分に分け、選ぶ半分で信頼下限が合格ライン以上の一番安い担当を選び、確かめる半分でも信頼下限が合格ライン以上なら certified、届かなければ unconfirmed](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/a2a7df365ee71e/zenn/articles/a2a7df365ee71e/split.png)

信頼区間が本当の受理率を外す確率を **α** と書きます。この関係を、本当の受理率 p がちょうど合格ライン f にある担当で次の図に示します。誤って合格させうる担当の中で、一番合格しやすい場合です。測った受理率 p-hat は p のまわりにばらつき、tierbook の区間は両側なので、外れる確率 α は左右の裾 (黄の格子) に半分ずつ分かれます。

![本当の受理率 p が合格ライン f = 0.85 にちょうどある担当を 600 件で測ったときの、測った受理率のばらつき (標準誤差 0.0146)。両側の裾にそれぞれ alpha/2 = 0.025 があり、右の裾では区間の下端が p を上回って誤って合格し、左の裾では区間の上端が p を下回る](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/a2a7df365ee71e/zenn/articles/a2a7df365ee71e/interval.png)

誤って合格させるのは右の裾、つまり測った受理率がたまたま高く出て、区間の下端が p を上回ったときだけです。そのため、その確率は 1 回の判定あたり多くてもおよそ α の半分で、α が 0.05 なら約 0.025 です。Wilson の区間は近似なので、この確率もおよそです。

合格を左右する値には既定値がなく、すべて宣言します。今回の宣言は次のとおりです。drift の結果の読み方は「ルーターでの通し試験」の節で説明します。

| 項目 | 今回の値 |
|---|---|
| 信頼下限の求め方 | Wilson の区間の下端 |
| α | 0.05 (後で述べる 2 回目の判定だけ 0.025) |
| 確かめる半分の割合 (held-out share) | 0.5 |
| 確かめる半分で調べる担当の数 (rungs to test) | 最初は 1 で、一番安い担当だけを調べました。固定順の検定を入れた後は、選ぶ半分の候補を全部調べました |
| 合格ライン | 最初は 0.85 です。精度をどこまで譲るかを比べるため、途中から 0.80 と 0.75 でも同じ記録を判定しました |
| 記録の無い問題の扱い | 受理しなかったものとして数えます |
| 先生と学習にかかった費用 (requests to amortise over) | 100 万件のリクエストで回収する前提で割り振ります |

# 実験の設定

題材は、金融ニュースの見出しを bearish・bullish・neutral の 3 つに分ける感情分類です。データセットには MIT ライセンスの [zeroshot/twitter-financial-news-sentiment](https://huggingface.co/datasets/zeroshot/twitter-financial-news-sentiment) を使い、次のように分けました。

| 使い道 | 件数 | 中身 |
|---|---|---|
| 学習 | 1,000 件ずつ 9 区切り | 学習用の分割から順に流し、区切りごとに生徒を鍛え直して判定し直しました。記録がたまっていく様子を模しています |
| しきい値と学習方法の選択 | 300 件 | tierbook の合格判定には一度も使っていません |
| 合格判定 | 1,200 件 | 選ぶ半分と確かめる半分が約 600 件ずつです。最後の判定だけ 588 件を足して 1,788 件にし、確かめる半分は 887 件になりました |
| ルーターでの通し試験 | 経路ごとに 300 件 | 学習にも選択にも合格判定にも使っていない問題です |

合格判定用の 1,200 件のうち 66% が neutral なので、常に neutral と答えるだけで正解率は 0.659 になります。正解ラベルはありますが、正解が無い仕事での学習を模すため、合格判定に出した生徒の学習には先生の答えだけを使いました。正解ラベルは、合格判定の採点と、学習方法としきい値を選ぶ 300 件の採点に使っています。

先生は [Prismyra](https://github.com/littlemex/Prismyra) の判断用のモデル [littlemex/prismyra-decision-35b-a3b-fp8](https://huggingface.co/littlemex/prismyra-decision-35b-a3b-fp8) です。Prismyra も筆者の OSS で、判断用のモデルに加えて、その答えで LightGBM などの小さな生徒を育て、生徒が自信のある問題から生徒に切り替えていく仕組み (`prismyra.learn`) を持っています。この記事で先生と呼ぶのは判断用のモデルのほうです。Prismyra にも、生徒を使ってよいかを先生の答えとの一致で決める独自の基準があります。tierbook の証明書は、採点器が受理する割合を、選ぶのに使っていないデータで見る点が違います。また、Prismyra の `prismyra.learn` は判断用モデル専用の仕組みですが、tierbook は LLM や VLM などモデルの種類に依存しません。答えの記録と、その採点と、料金があれば、どの担当にも同じ判定を当てられます。元のモデルは [Qwen/Qwen3.6-35B-A3B-FP8](https://huggingface.co/Qwen/Qwen3.6-35B-A3B-FP8) で、g6e.12xlarge に積んだ NVIDIA L40S 4 枚のうち 1 枚で動かしました。L40S 1 枚の g6e.xlarge に相当する規模です。

# 生徒の育て方

生徒は 2 種類を育てました。決定木を積み重ねる軽い分類器の LightGBM と、パラメータ数 8 億の LLM (0.8B) です。

LightGBM の生徒は、Prismyra の標準の入力である単語の出現を数えた特徴量では、正解率が 0.71 前後で頭打ちでした。そこで、生徒の入力を文章の埋め込みに替えました。埋め込みは、`BAAI/bge-small-en-v1.5` などの小さなモデルで文章の意味を数字の並びに変えたものです。これで、合格判定用の 1,200 件での正解率が 0.81 まで上がりました。

ここが、LLM の API ではできないことです。Prismyra はサービングエンジンごと自作しているので、届いたリクエストの文章から埋め込みを計算し、先生の答えと一緒に記録し、その記録で生徒を学習させ、自信のある問題から生徒に切り替える、という一連の処理をサーバーの中に足せます。Amazon Bedrock などの LLM の API では、受け取れるのはレスポンスだけで、API の中にこうした処理を足すことはできません。同じことをするには、API の外に記録と学習と振り分けの仕組みを別に作る必要があります。

それより大きく伸びたのは、0.8B の `Qwen/Qwen3.5-0.8B` を先生の答えで学習させたことです。9 区切り目までに先生が答えた 9,000 件のうち 8,100 件で学習させると、1,200 件での正解率が先生の 0.896 に対して 0.885 になりました。

0.8B では、学習のさせ方そのものにも大事な違いがありました。この記事では 2 つを区別します。

- 読む版は、3 つのラベルの語の点数 (logit) どうしを比べるだけの学習をしたものです。答えるときも、3 つの点数のうち一番高いものを読みます。指示文を付けた標準の入力と、見出しだけの入力の 2 通りで学習させ、上の 0.885 は標準の指示文のほうです。
- 生み出す版は、全語彙に対して「ラベルの語と終わりの記号」を生み出す形で、見出しだけの入力で学習させたものです。1,200 件での正解率は 0.873 でした。

2 つの学習のさせ方の違いを次の図に示します。左が読む版 (Read-out)、右が生み出す版 (Generating) です。

![0.8B の生徒の 2 つの学習方法。読む版 (Read-out) は 3 つのラベルの logit の交差エントロピーで学習し argmax で答え、正解率 0.885 (標準の指示文)。生み出す版 (Generating) は全語彙の次トークン予測でラベルと終わりの記号を学習し、OpenAI 互換のルーターから呼べ、正解率 0.873](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/a2a7df365ee71e/zenn/articles/a2a7df365ee71e/students.png)

読む版に文章を生み出させると、「1111」のような意味のない出力になりました。全語彙の中でラベルの語を上に出すことを学んでいないからです。生み出す版だけがルーターで使えるのは、OpenAI 互換のルーターがモデルに文章を生み出させて使うからです。

# cascade としきい値

生徒が自信のあるときだけ答え、迷ったら先生に回すやり方を、tierbook では cascade として宣言します。`candidates.json` に次のように書きます。

```json
"student-or-teacher": {"cascade": {"primary": "student", "fallback": "teacher", "threshold": 0.98, "on_no_score": "fallback"}}
```

`threshold` は、生徒の答えの自信度がこの値以上なら生徒の答えを使う、という境目です。自信度はモデルが自分の答えをどれだけ確からしいと見ているかの値で、統計の信頼下限とは別物です。`on_no_score` は、自信度が記録されていない答えをどう扱うかの指定です。自信度の計算は生徒の種類で違います。LightGBM は分類器が出すラベルの確率、読む版は 3 つのラベルの点数から求めた確率、生み出す版はルーターと同じ logprob の平均から求めた値です。しきい値の数字は、種類をまたいで比べられません。tierbook は生徒と先生それぞれが実際に答えた記録から cascade の答えを組み立て、両方が使った分を足して値段を付けます。

## しきい値は合格判定に使わないデータで決める

しきい値は、合格判定に使わない 300 件で先に 1 つに決めてから、担当として宣言します。規則は、300 件での信頼下限が合格ライン以上になる中で一番安いしきい値を選び、無ければ信頼下限が一番高いものを選ぶ、というものです。ただし、この 300 件では 0.50〜0.99 のどのしきい値でも cascade の正解率が 0.84〜0.85 で、しきい値の優劣は見分けられませんでした。合格ライン 0.85 では信頼下限が合格ライン以上になるしきい値が無く、信頼下限が一番高いものを選んでいます。

こう決めたのは、しきい値の候補をそのまま担当として並べると、候補を増やすほど、たまたま良く見える安い担当が選ばれやすくなるからです。その担当は確かめる半分で落ちやすく、誤って合格させる確率は増えませんが、合格できる担当を取りこぼします。実際に 0.50 から 0.99 までの 9 つのしきい値を 2 種類の生徒に掛けて 18 の担当を足すと、合格ライン 0.85 で選ぶ半分を通る担当は 37 に増えましたが、選ぶ半分で一番安かったのは足す前と同じ生徒単独で、cascade は 1 つも合格になりませんでした。しきい値を別のデータで決めるという方針は、Hamel Husain さんらの記事「[How To Use Decision Models for Evals](https://hamel.dev/blog/posts/decision-model-evals/)」の指摘に沿っています。この記事は、点数の既定のしきい値には根拠が無く、結果を報告しないデータで決めるべきだと述べています。候補を増やすと取りこぼしやすくなるという点は仕組みからの筆者の見立てで、今回の実験で直接確かめたものではありません。

## 確かめる半分では高い順に調べる

前の節で cascade が 1 つも合格にならなかった直接の原因は、選ぶ半分で一番安い担当だけを確かめる半分で調べていたことです。安い担当がぎりぎり選ぶ半分を通ると、少し高いけれど確かめる半分でも合格する担当が隠れてしまいます。

そこで、固定順の検定 (fixed sequence procedure) と呼ばれる方法を入れました。tierbook ではこの並びを ladder、並べた担当の 1 つずつを rung と呼びます。選ぶ半分だけで安い担当をいくつか並べ、確かめる半分では高いほうから順に調べ、最初に落ちたところで止めます。合格した中で一番安い担当を採用します。調べる順番は、確かめる半分のデータを見る前に、選ぶ半分だけで決めます。そのため、調べる担当を増やしても、合格ラインに届かない担当を 1 つでも誤って合格させる確率は、多くても 1 回の判定と同じです。代わりに、高いほうが落ちると、それより安い担当は調べられません。この形は、前に挙げた Learn then Test や Pareto Testing と同じ考え方です。誤って合格させる確率が増えない理由は、次の「判定の数理」の節で式で示します。

合格ライン 0.85 での実際の例を次の図に示します。このとき並べた担当はほかにもありますが、図には先生 (Teacher) と、選ぶ半分で安かった 3 つだけを載せています。Selection LB は選ぶ半分の信頼下限、Held-out LB は確かめる半分の信頼下限で、一番下の担当の値を括弧に入れているのは、この手順では調べず、以前のやり方でこの担当だけを調べたときの値だからです。先生の dropped at selection は、選ぶ半分で、より安くて信頼下限も高い担当があったために調べる順番から外れたという意味です。図では cascade の 0.879 が先生の 0.877 を上回っています。Result の 1 と 2 は、確かめる半分で調べた順番です。cascade (Read-out cascade) が合格し、次に安い Read-out alone, full prompt が落ちたのでそこで止め、cascade を採用しました。

# 判定の数理

ここまで言葉で書いた判定を、式で確かめます。この節で扱うのは、受理率の信頼下限の求め方、それで合格させたときに誤る確率、半分に分ける理由、固定順の検定、2 回目の判定、drift、費用の式です。

## 受理率を二項分布で表す

合格判定の問題が、これから届くリクエストと同じ母集団から、互いに独立に無作為に取り出されたとみなします。その母集団で、ある担当の答えが受理される割合を $p$ とします。$p$ がこの担当の本当の受理率で、知りたいのに直接は見えない値です。$n$ 件の問題のうち受理が $X$ 件なら、$X$ は二項分布に従います。

$$
X \sim \mathrm{Binomial}(n, p), \qquad \hat{p} = \frac{X}{n}
$$

$\hat{p}$ は測った受理率で、平均は $p$、分散は $p(1-p)/n$ です。偶然の出どころは、どの問題が抜き取られたかです。この前提は、限界の節の「合格判定と同じような問題が来る場合だけ」と同じものです。

## Wilson の区間

$n$ が十分に大きいとき、中心極限定理から、次の量はおよそ標準正規分布に従います。

$$
Z = \frac{\hat{p} - p}{\sqrt{p(1-p)/n}} \approx \mathcal{N}(0, 1)
$$

標準正規分布の累積分布関数を $\Phi$ として、$z = \Phi^{-1}(1 - \alpha/2)$ とします。$\alpha = 0.05$ なら $z \approx 1.960$、$\alpha = 0.025$ なら $z \approx 2.241$ です。このとき $|Z| \le z$ となる確率がおよそ $1 - \alpha$ です。

$|Z| \le z$ を $p$ について解きます。両辺を 2 乗すると $p$ の 2 次不等式になります。

$$
(\hat{p} - p)^2 \le \frac{z^2}{n}\, p(1-p)
$$

これを満たす $p$ の範囲の両端が、Wilson の区間の下端 $L$ と上端 $U$ です。

$$
L,\ U = \frac{\hat{p} + \dfrac{z^2}{2n} \mp z\sqrt{\dfrac{\hat{p}(1-\hat{p})}{n} + \dfrac{z^2}{4n^2}}}{1 + \dfrac{z^2}{n}}
$$

$p(1-p)$ に先に $\hat{p}$ を入れてから解く Wald の区間 $\hat{p} \pm z\sqrt{\hat{p}(1-\hat{p})/n}$ と違い、$p$ のまま解くので、$\hat{p}$ が 1 に近いときも区間が 1 を越えません。ただし正規近似に頼るので、下端 $L$ が $p$ を上回る確率と、上端 $U$ が $p$ を下回る確率は、それぞれおよそ $\alpha/2$ で、ちょうど等しいわけではありません。

## 誤って合格させる確率

合格ラインを $f$ とし、tierbook は $L \ge f$ のときに合格させます。上の 2 次不等式の境目を $p = f$ で考えると、$L \ge f$ は次と同じです。

$$
\hat{p} \ge f + z\sqrt{\frac{f(1-f)}{n}}
$$

つまり判定は「受理 $X$ が、$n$ と $f$ と $\alpha$ で決まる件数 $x^*$ 以上か」という形になります。本当の受理率が $p < f$ の担当では、$X$ が $x^*$ 以上になる確率は $p = f$ の場合より小さいので、誤って合格させる確率は次の値で抑えられます。

$$
\Pr_p\left(X \ge x^*\right) \le \Pr_f\left(X \ge x^*\right) = \sum_{k = x^*}^{n} \binom{n}{k} f^k (1-f)^{n-k}
$$

右辺は近似なしに計算できます。確かめる半分が 600 件、$\alpha = 0.05$、$f = 0.85$ では $x^* = 528$ で、右辺は 0.0204 です。887 件、$\alpha = 0.025$ では $x^* = 778$ で 0.0119 です。どちらも、正規近似で見積もった $\alpha/2$ (0.025 と 0.0125) を下回ります。$p$ が $f$ より大きく下にあるほど、この確率はさらに小さくなります。

## 半分に分ける理由

$K$ 個の担当の測定値 $\hat{p}_1, \dots, \hat{p}_K$ から良く見えるものを選ぶと、選んだ担当の測定値は本当の値より上に出やすくなります。一番大きな測定値の平均は、一番大きな本当の値以上だからです。

$$
\mathbb{E}\left[\max_k \hat{p}_k\right] \ge \max_k \mathbb{E}\left[\hat{p}_k\right] = \max_k p_k
$$

誤って合格させる確率で言うと、$K$ 個の担当がすべて合格ラインのすぐ下にあるとき、同じデータで $L_k \ge f$ となる担当が 1 つでも出る確率は、後で使うブールの不等式で最大およそ $K\alpha/2$ まで大きくなりえます。tierbook はその中から一番安いものを選ぶので、選ぶのに使ったデータの $L$ で合格させると、選んだ担当が合格ラインに届かない確率は $\alpha/2$ では抑えられません。

そこで、問題をハッシュで 2 つに分け、選ぶ半分で担当 $\hat{a}$ を選びます。分け方は結果を見る前に決まっているので、確かめる半分の記録は $\hat{a}$ の選び方と独立で、確かめる半分では $\hat{a}$ を固定した 1 回の判定になり、上の評価が成り立ちます。ただし、これは候補と手順を、確かめる半分の結果を一度も見ずに決めた場合に限ります。今回は同じ分け方で手順を変えながら何度も判定したので、「合格判定の結果」の節に書いたとおり、この評価より弱い保証です。

## 固定順の検定

合格ラインを $f$、担当 $a$ の確かめる半分での Wilson の下端を $L_a$ と書きます。選ぶ半分の記録を $S$ とし、$S$ だけを使って、調べる担当の順番 $a_1, a_2, \dots, a_m$ を高いものから安いものへ決めます。担当 $a_k$ について、「本当の受理率が合格ラインに届かない」という仮説を $p_{a_k} < f$ とします。確かめる半分で $k = 1, 2, \dots$ の順に $L_{a_k} \ge f$ かを調べ、合格したら次へ進み、最初に落ちたところで止めます。採用するのは、最後に合格した担当、つまり合格した中で一番安い担当です。

合格ラインに届かない担当を 1 つでも誤って合格させる事象を $E$ とします。順番の中で、本当に合格ラインに届かない担当のうち最初のものを $a_j$ とします。$a_j$ より後の担当を調べるには、$a_j$ で合格する必要があります。$a_j$ より前で止まれば、誤った合格は起きません。したがって $E$ が起きるのは $a_j$ を誤って合格させたときだけです。順番と $j$ は $S$ だけで決まり、確かめる半分は $S$ と独立なので、$S$ を固定すると次が成り立ちます。

$$
\Pr(E \mid S) \le \Pr\left(L_{a_j} \ge f \mid S\right) \le \Pr_f\left(X \ge x^*\right)
$$

右辺は前の小節の値 (確かめる半分が 600 件、$\alpha = 0.05$ で 0.0204) で、$S$ について平均しても同じ上限です。合格ラインに届かない担当が順番の中に無いときは $\Pr(E \mid S) = 0$ です。そのため、調べる担当をいくつ並べても、誤って合格させる確率は 1 回の判定と同じ上限に収まります。

## 2 回目の判定

1 回目の判定で誤って合格させる事象を $E_1$、2 回目を $E_2$ とします。2 つの事象が互いに依存していても、どちらかが起きる確率は、それぞれの確率の和を超えません。これはブールの不等式と呼ばれ、Bonferroni の補正の根拠です。正確な二項分布の値を使うと、次のようになります。

$$
\Pr(E_1 \cup E_2) \le \Pr(E_1) + \Pr(E_2) \le 0.0204 + 0.0119 = 0.0323
$$

正規近似の $\alpha/2$ で見積もると $0.05/2 + 0.025/2 = 0.0375$ で、正確な値はこれより小さくなります。2 回目は 1 回目の約 600 件を含むので $E_1$ と $E_2$ は強く依存し、実際の確率はこの上限よりさらに小さいはずです。ただし、この上限が言えるのは判定を 2 回で止め、2 回目の件数と $\alpha$ を 1 回目の結果に合わせて調整していない場合です。合格するまで問題を足し続けると、足すたびに右辺に項が増えます。今回は 2 回目を行うこと自体を 1 回目の結果を見てから決めたので、事前に決めた手順に対する保証より弱くなります。

数字で確かめます。2 回目の判定では、確かめる半分の $n = 887$ 件のうち cascade の受理が $X = 779$ 件で、$\hat{p} = 0.8782$ です。$\alpha = 0.025$ から $z = 2.2414$ で、Wilson の下端は $L = 0.8515$ になり、合格ライン 0.85 以上です。受理が 778 件なら $L = 0.8503$ でまだ合格ですが、777 件なら $L = 0.8490$ で不合格です。$x^* = 778$ なので、887 件中 2 件の違いで結果が変わる、ぎりぎりの合格です。

## drift の判定

通し試験の $n = 300$ 件に、$\alpha = 0.05$ の Wilson の区間 $[L, U]$ を当てます。$L \ge f$ なら confirmed、$L < f \le U$ なら consistent、$U < f$ なら contradicted です。合格ライン $f = 0.85$ では、受理 $X = 268$ 件で $L = 0.8533$ となり confirmed ですが、$X = 267$ 件では $L = 0.8495$ で consistent です。contradicted になるのは $X \le 242$ 件のときで、本当の受理率がちょうど 0.85 の担当がたまたま contradicted になる確率は、二項分布で 0.0244 です。243 件から 267 件までの 25 件分が consistent の幅なので、300 件では、本当の受理率が合格ラインの前後数ポイントにある担当を見分けられません。この範囲を次の図に示します。

![drift の判定の 3 つの範囲 (300 件、合格ライン 0.85、alpha 0.05)。受理 242 件以下は contradicted、243〜267 件は consistent、268 件以上は confirmed。vLLM Semantic Router の通し試験の 267 件は consistent の上端](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/a2a7df365ee71e/zenn/articles/a2a7df365ee71e/drift.png)

CPU と GPU の答えの一致にも同じ道具を使えます。200 件で食い違いが 0 件のとき、食い違う確率の Wilson の上端は $\alpha = 0.05$ で 0.0188 です。食い違いが本当は 2% 近くあっても、200 件では 0 件と出ることがあります。

## 費用の式

自前で動かす担当の 1 回あたりの費用は、時間料金 $h$ を 1 時間の処理件数 $T$ で割ったものに、先生の答えと学習にかかった費用 $C$ を宣言したリクエストの数 $N$ で割り振ったものを足した値です。

$$
c = \frac{h}{T} + \frac{C}{N}
$$

CPU の生徒は $h = 0.20012$ ドル/時、$T = 19{,}612$ 件/時、$C = 1.646$ ドル (丸める前の値)、$N = 10^6$ 件で、生徒の 1 回あたりの費用は $c_s \approx 1.185 \times 10^{-5}$ ドルです。受理率 $r$ の担当の受理 1 件あたりの費用は $c / r$ です。cascade では、生徒は全件に答え、そのうち割合 $q$ を先生に回すので、先生の 1 回あたりの費用を $c_t$ とすると、受理 1 件あたりの費用は次の値です。

$$
\frac{c_s + q\, c_t}{r}
$$

先生は $c_t = 3.804 / 91{,}367 \approx 4.16 \times 10^{-5}$ ドルです。2 回目の判定の cascade では $r = 0.878$ で、受理 100 万件あたり \$19.1 から逆算すると $q \approx 0.12$、つまり確かめる半分の約 12% が先生に回っています。$q\,c_t$ は分子の約 3 割 ($c_s$ の約 0.4 倍) を占め、受理率が同じなら、$q$ が 1 ポイント増えるごとに cascade の費用は約 2.5% 増えます。

ルーターでの通し試験に使ったのは 3 行目と 4 行目です。合格ライン 0.75 では、LightGBM の生徒単独が受理 100 万件あたり $0.99、先生の約 47 分の 1 で合格しました。この費用の半分近くは先生が答えを付けた費用の割り振りで、残りは CPU での埋め込みの計算です。

表全体にかかる注意は 3 つです。

- 合格判定用の 1,200 件は、学習方法やしきい値を比べた回を含め、何度も判定に使いました。毎回、選ぶ半分と確かめる半分に分けていますが、分け方は毎回同じで、同じデータを見ながら手順を変えています。どの行も、事前に決めた 1 回だけの判定より弱い証明書です。
- 誤って合格させる確率が多くてもおよそ α の半分というのは、合格ラインと担当の組 1 つごとの話で、表全体のどこかに誤りが混じる確率ではありません。
- 合格ライン 0.85 の行は、信頼下限と合格ラインの差が 0.001〜0.010 しかありません。Wilson の区間は近似なので、正確な方法に替えると不合格になる行がありえます。

行ごとの注記は次のとおりです。

- 2 行目は、cascade が確かめる半分で合格ラインを超えているのを見た後に、固定順の検定を足して同じ記録を判定し直した合格です。
- 3 行目は、全担当を並べた判定では選ばれず、その結果を見た後に、候補を vLLM Semantic Router で動かせる担当に絞って判定し直した合格です。生徒にも GPU の値段が付いたため、先生とほぼ同じ費用になっています。生徒の GPU での処理件数は 1 時間 109,908 件です。先生の処理件数は 8 件を並行して流して測りましたが、生徒も同じ条件で測ったかは記録で確かめられないので、3 行目の費用は目安です。
- 4 行目は 6 区切り目までの記録で鍛えた LightGBM の生徒を、Prismyra の固定のしきい値 0.8 で判定した値です。9 区切り目では、合格ライン 0.80 でこの振り分け役より安い担当が合格しています。

# ルーターでの通し試験

合格させただけでは仕事は渡せないので、2 つの経路で実際にルーターを動かし、合格判定に使っていない 300 件ずつを流しました。実際の利用者からのリクエストではなく、同じデータセットの問題を流した試験なので、問題の傾向の変化は見ていません。

流した結果は drift で照らし合わせます。drift には流したリクエストの答えを採点した記録が要るので、正解が無い仕事では、採点の手段と費用を別に用意する必要があります。結果は 3 通りです。新しい結果の信頼下限が合格ライン以上なら confirmed、信頼区間が合格ラインをまたいでいれば consistent、信頼区間全体が合格ラインを下回れば contradicted です。consistent は、食い違うとは言えないが、合格ラインを超えるとまでは確かめられていない状態です。その幅は広く、300 件で合格ライン 0.85 の場合、受理が 243〜267 件のあいだはすべて consistent になり、contradicted になるのは 242 件以下のときです。小さな劣化は、この件数では見つかりません。

## Prismyra の振り分け役

1 つ目は表の 4 行目の Prismyra 自身の振り分け役です。tierbook から Prismyra の設定に書き出して起動しました。300 件のうち生徒が 203 件を中央値 13.8 ms で答え、残り 97 件を先生が中央値 45.2 ms で答えました。300 件中 263 件が受理され、信頼下限 0.835 が合格ライン 0.80 以上だったので、drift の結果は confirmed でした。

## vLLM Semantic Router

2 つ目は表の 3 行目で、vLLM Semantic Router を使いました。構成と結果は次の図のとおりです。ルーターの confidence looper は、1 で 300 件すべてをまず 0.8B の生徒に送り、2 で生徒の答えの自信度 (conf) が 0.98 に足りない 31 件だけを Prismyra に回します (破線の矢印)。右の Result の route match 300/300 は、この振り分けが記録からの予測と全件で一致したことを表します。

![vLLM Semantic Router の通し試験 300 件。confidence looper が全件をまず 0.8B の生徒に送り、自信度 0.98 未満の 31 件を Prismyra に回す。生徒 269 件、先生 31 件、受理 267 件、振り分けの一致 300/300、合格ライン 0.85 に対して drift は consistent](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/a2a7df365ee71e/zenn/articles/a2a7df365ee71e/serving.png)

ルーターは、モデルの答えのトークンごとの確からしさの対数である logprob から自信度を計算します。ここで大事なのは、合格判定に使った自信度と、ルーターが計算する自信度が同じであることです。違う値で合格させた証明書は、ルーターでは意味を持ちません。そこで、使った開発版のルーターの[ソース](https://github.com/vllm-project/semantic-router/blob/37bdd814a71f5c4a490abbc2b2abd80e2e3493b2/src/semantic-router/pkg/looper/confidence.go#L404-L417)で、自信度の式を確かめました。答えのトークンの logprob の平均を $\bar{\ell}$ とすると、自信度は次の値です。

$$
\min\left(1,\ \max\left(0,\ \frac{\bar{\ell} + 3}{3}\right)\right)
$$

次に、GPU 上の vLLM で動かした生み出す版の答えを、この式と、ルーターが送るのと同じリクエストの形で記録し直しました。しきい値は 300 件の選択用データで 0.98 に決め、先生へ回す cascade を合格ライン 0.85 で判定して合格させ、`export-policy --target vsr --cascade-confidence avg_logprob` で書き出しました。tierbook は、自信度の計算方法が宣言されない限り cascade を書き出しません。

ルーターで流した 300 件では、ルーターが生徒に任せた 269 件と先生に回した 31 件が、記録した自信度から予測した振り分けと 300 件すべてで一致しました。同じ式と同じ入力なので一致するはずのものですが、式やリクエストの形が食い違っていればここで見つかります。受理は 300 件中 267 件で、信頼下限 0.8495 は合格ライン 0.85 をわずかに下回り、drift の結果は consistent でした。267 件は、consistent になる範囲 (243〜267 件) の上端です。この件数では、成績が合格ラインを少し上回る程度の担当は confirmed になりにくいです。この経路で確かめられたのは、合格判定どおりに振り分けることまでです。

# CPU でのスループットの改善

3 行目の生徒は GPU の値段で先生とほぼ同じ費用だったので、生み出す版を CPU で動かして値段を下げました。見出しだけを入力してラベル 1 語を出す処理を 200 件で測ると、処理の仕方を変えて 1 時間あたりの処理件数は 7,105 件から 19,612 件になり、値段にはこの値を使いました。入力が長い仕事や、長時間流したときの値は測っていません。tierbook は、自前で動かすモデルの値段を、時間料金を実測した 1 時間あたりの処理件数で割って付けるので、スループットを上げれば値段が下がり、値段が変わったときと同じように割り当てが変わります。CPU は AWS の Arm 系 CPU である Graviton4 の c8g.xlarge で、PyTorch で動かしました。

処理の仕方ごとの 1 時間あたりの件数を次の図に示します。batch はまとめて処理する問題数、padded head は出力層の行数を 16 の倍数にそろえたことを表し、値段に使ったのは青の網目の行です。

![c8g.xlarge での生み出す版の 1 時間あたりの件数。8 問ずつ 7,105、1 問ずつ 12,918、出力層の行数をそろえて 8 問ずつ 19,488、16 問ずつ 19,612 (値段に使用)](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/a2a7df365ee71e/zenn/articles/a2a7df365ee71e/throughput.png)

最初は 8 問ずつにすると、スループットが 1 問ずつより低くなりました。調べると、出力層の計算で、まとめた 8 問分の 8 行と全語彙の行列を掛ける計算だけ、CPU の行列計算ライブラリ oneDNN が極端に遅い方法を選んでいました。1 回 871 ms かかり、16 行なら 52 ms です。行数をそろえるために足した行は計算後に捨てるので、答えは変わりません。19,612 件は最初の 7,105 件の 2.76 倍、1 問ずつの 12,918 件の 1.52 倍です。

その代わり、レイテンシーは長くなります。先生は通し試験で中央値 45.2 ms でしたが、CPU の生徒は 1 問ずつで約 0.28 秒、16 問ずつでは 1 回の処理に約 2.9 秒で、16 問がそろうまでの待ち時間がこれに加わります。cascade で先生に回るリクエストは、生徒の時間のあとに先生の時間がかかります。16 問をまとめる仕組みはルーターの後ろにまだ置いておらず、件数と値段だけを測りました。

生み出す版は、読む版で先に試した 2 つの工夫も使っています。重みを 16 ビットの浮動小数点数 bf16 にすることと、このモデルが使う linear attention の一種である Gated DeltaNet の計算を一括の解法に置き換えることです。見出しだけを入力にした読む版は、これらの工夫に、ラベル 3 語の点数だけを最後の位置で計算することと 8 問ずつの処理を加えて、1 時間 27,848 件になりました。「合格判定の結果」の表の 5 行目の値段はこの値から付けています。この読む版のラベルは、GPU で動かしたときと 200 件中 199 件で一致しました。工夫の中身は[実験の記録](https://github.com/littlemex/tierbook/blob/56506022d7338a9b6146ace3ce8a76f2bb7d2cb2/docs/verify/v0.5.0-distillation-loop.md#round-6-tune-how-the-08b-is-served-not-what-it-answers)にあります。

生み出す版は、上の表のどの段でも、答えのラベルが GPU で動かしたときと 200 件すべてで一致することを確かめてから値段に使いました。ルーターが生徒に任せるかどうかの判断は、しきい値 0.98 で 200 件中 199 件が一致し、自信度の差は最大 0.0276 でした。合格ライン 0.85 の cascade が使うしきい値 0.99 では、1 問ずつと 8 問ずつの測定で 200 件すべて一致しましたが、値段に使った 16 問ずつの測定では確かめていません。

# CPU 版での再判定

CPU の値段で判定し直すと、合格ライン 0.80 では生み出す版の生徒単独が先生の 0.30 倍の費用で合格しました。合格ライン 0.85 では、先生へ回す cascade が 1 回目はわずかに届かず、問題を足した 2 回目の判定で 0.41 倍で合格しました。次の表は 2 回目の判定の値で、α は 0.025、確かめる半分は 887 件です。「合格判定の結果」の表の行とは条件が違うので、信頼下限をそのまま比べることはできません。なお、合格ライン 0.80 の生徒単独は、1 回目の判定 (α 0.05、1,200 件) でもすでに先生の 0.30 倍で合格しています。後で書く 2 回目の判定の弱い点は、合格ライン 0.85 の cascade の行だけに当てはまります。先生との比は、同じ回の先生の値段 (受理 100 万件あたり $46.7) に対するものです。

| 合格ライン | 担当 | しきい値 | 確かめる半分の信頼下限 | 受理 100 万件あたりの費用 | 先生との比 | 動かせる経路 |
|---|---|---|---|---|---|---|
| 0.85 | 生み出す版から先生へ回す cascade、生徒は CPU | 0.99 | 0.8515 | $19.1 | 0.41 | vLLM Semantic Router (CPU 版は未接続) |
| 0.80 | 生み出す版、CPU | なし | 0.825 | $13.9 | 0.30 | vLLM Semantic Router (CPU 版は未接続) |

合格判定には、同じ手順と乱数の種で学習し直した生み出す版を GPU の vLLM で答えさせた記録を使い、値段だけを CPU の測定から付けました。つまり、この表の証明書は GPU で答えさせた記録に対するものです。前の節で確かめた 200 件すべての一致から言えるのは、CPU と GPU の答えの食い違いがおよそ 2% 以下ということまでです。0.85 の cascade の信頼下限と合格ラインの差 0.0015 はこれより小さいので、この合格は、CPU で答えさせた記録で判定し直すまで仮のものです。しきい値は、学習し直したモデルについて同じ 300 件と同じ規則で決め直し、合格ライン 0.85 では 0.99 になりました。学習し直したのは通し試験に使ったモデルの重みを保存していなかったためで、学習は完全には再現しないため、新しいモデルの答えが元のモデルと一致したのは 93.4% の問題でした。値段の付け方と前提は、次の「費用の内訳」の節にまとめます。

2 回目の判定の経緯は次のとおりです。合格ライン 0.85 では、1 回目の判定で cascade の信頼下限が 0.849 で、わずかに届きませんでした。そこで、まだどこにも使っていなかった 588 件を合格判定の問題に足し、この判定だけ α を 0.025 に下げて改めて判定しました。

この 2 回目の判定には弱い点があります。1 回目は α が 0.05、2 回目は 0.025 なので、1 回あたりの上限であるおよそ α の半分を足すと、2 回のどちらかで誤って合格させる確率は、多くても次の値です。

$$
\frac{0.05}{2} + \frac{0.025}{2} = 0.0375
$$

1 回だけ判定した場合のおよそ 0.025 より大きくなります。これはこの 2 回だけを数えた値で、同じ 1,200 件を以前の回で学習方法やしきい値の比較に使った分は入っていません。この足し算が成り立つのは 2 回で止めた場合だけで、合格するまで問題を足し続けるやり方には当てはまりません。また、2 回目を見ると決めたのは 1 回目の結果を見た後です。信頼下限と合格ラインの差も 0.0015 しかないので、この結果は今回の記録の中で一番弱い証明書として扱っています。

# 費用の内訳

CPU の生徒の値段は、次のように付けました。c8g.xlarge の時間料金 $0.20 を 1 時間の処理件数 19,612 件で割ると、推論の費用は 100 万件あたり $10.2 です。先生が 9,000 件に答えを付けた費用 $0.37 と、L40S での 1,203 秒の学習の費用 $1.27 は、9 区切り目の学習 1 回分です。区切りごとの鍛え直し、合格判定用と選択用の問題に先生が答えた費用、採用しなかった学習の費用は入れていません。合計 $1.646 (丸める前の値) を、生徒が今後答えるリクエストの数として宣言した 100 万件で割ると、推論と同じ単位でリクエスト 100 万件あたり $1.6 です。丸める前の値で足すとリクエスト 100 万件あたり約 $11.85 で、記録では $11.9 と表示しています。生徒単独の値段は、これを受理率で割った値です。cascade の値段は、これに先生へ回した問題の分の先生の費用を足してから受理率で割っています。100 万件という前提が小さくなるほど、また 100 万件に届く前に鍛え直すほど、割り振る分が大きくなり、生徒は高くなります。1 問ずつ処理すると、1 回目の判定 (確かめる半分が約 600 件) の値で、生徒単独は受理 100 万件あたり $20.0、先生 ($46.9) の 0.43 倍です。

2 回目の判定 (second look) での受理 100 万件あたりの費用を次の図に示します。各合格ラインで採用された担当は青の網目です。teaching は、先生のラベル付けと学習の費用を 100 万件に割り振った分です。

![2 回目の判定 (確かめる半分 887 件) での受理 100 万件あたりの費用の計算値。先生単独 $46.7、CPU の生徒から先生へ回す cascade (合格ライン 0.85) $19.1 で 0.41 倍、CPU の生徒単独 (合格ライン 0.80) $13.9 で 0.30 倍。GPU で答えさせた記録に CPU の値段を付け、16 問ずつ処理し、常に全力で動かし、先生の GPU を他の仕事と分け合う前提](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/a2a7df365ee71e/zenn/articles/a2a7df365ee71e/cost.png)

費用に入れたのは、モデルを動かすインスタンスの時間料金と、先生のラベル付けと学習 1 回分だけです。ルーター自体の計算資源、止まらないように複数台を置く分、リクエストが来ない待ち時間、drift のための採点の費用は入れていません。

CPU で動かしても、0.8B の生み出す版の費用は先生の 0.30〜0.41 倍までしか下がりませんでした。先生の GPU は、L40S を 4 枚積んだ g6e.12xlarge の 1/4 として 1 時間 $3.80 とし、残りの 3 枚も使われている前提です。これは c8g.xlarge の $0.20 の 19 倍です。しかし、8 件を並行して流した測定で先生は 1 時間に 91,367 件をこなし、生徒の 19,612 件の 4.7 倍です。先生の処理件数はこの 1 条件で測った値で、生徒のように処理の仕方を調整した値ではありません。並行数を上げて先生のスループットが伸びれば、0.30 倍という比はその分だけ大きくなります。先生は全体が大きくても、1 回に使う重みは 3B 分です。今回の測定で CPU の費用が先生を大きく下回ったのは、LightGBM の生徒でした。ただし合格できたのは合格ライン 0.75 までで、そのときの費用が先生の約 47 分の 1 でした。

この比較は、GPU も CPU も常に全力で動いている前提です。リクエストが少なく 1 割しか動いていなければ、先生も CPU の生徒も 1 件あたりの費用は 10 倍になります。リクエストが毎時 1.2 万件ほどまでなら生徒は c8g.xlarge 1 台で足り、$0.20/h の CPU と $3.80/h の GPU を動かし続ける費用の比べ合いになります。cascade では、生徒が答えられない問題のために先生の GPU も動かし続ける必要があります。先生の GPU を cascade だけのために動かすと、GPU の $3.80/h はそのままで CPU の費用が加わるので、先生単独より高くなります。cascade の 0.37〜0.41 倍になるのは、先生の GPU の空き時間を他の仕事が使い切る場合だけです。

# 限界

まだ示していないことは次のとおりです。

- 1 回の実験は数百〜数千件です。蒸留は 3 ラベルの簡単な分類 1 つだけで、採点に判定役のモデルが要るような自由記述の生成は試していません。
- 正解が無い仕事を模したのは学習だけで、採点には正解ラベルを使っています。クラスごとの正解率は見ていません。
- 証明書が保証するのは、利用者の採点器が受理する割合です。採点器が正しいかどうかは保証しません。採点器がモデルの場合、その誤りは証明書にそのまま入ります。
- 保証が及ぶのは、合格判定と同じような問題が来る場合だけです。タスクの種類を取り違えて届いたリクエストは、証明書の外にあります。
- 正解ラベルや先生の答えで小さな分類用のエンコーダーを直接学習させる定番のやり方とは、比べていません。0.8B の LLM を選んだのは、OpenAI 互換のルーターでそのまま使えるからです。
- cascade の自信度は、生徒自身が出す確率や logprob から計算する方式だけを試しました。FrugalGPT のように採点モデルを別に学習する方式や、AutoMix のように生徒に自分の答えを検証させる方式とは、比べていません。
- 点数を一度測って切り替える素朴なやり方と比べて、証明書が誤った切り替えを何件防いだかは、まだ測っていません。
- 先生の Prismyra も tierbook も筆者の OSS で、第三者による再現はまだありません。

# まとめ

安い生徒に仕事を渡す判断を、選ぶのに使っていないデータでの信頼下限で決め、合格したものだけをルーターの設定に書き出し、ルーターで流した結果も合格判定と照らし合わせる流れを試しました。OpenAI 互換のルーターで使える 0.8B の生み出す版は、16 問ずつまとめて CPU で常に全力で動かす前提で、合格ライン 0.80 なら先生の 0.30 倍の費用で合格しました。その代わり、レイテンシーは先生より長くなります。この合格は同じ合格判定用のデータを繰り返し使った上での判定で、CPU 版のルーターでの通し試験はまだです。合格判定と通し試験の結果は[実験の記録](https://github.com/littlemex/tierbook/blob/56506022d7338a9b6146ace3ce8a76f2bb7d2cb2/docs/verify/v0.5.0-distillation-loop.md)に残しています。料金と先生の処理件数は「費用の内訳」の節に書いた値です。

:::details 実験の条件
- 実験の日時は 2026 年 11 月 9 日から 10 日です。料金は 11 月 9 日に AWS の Price List API から引いた、ap-northeast-1 のオンデマンドの値です。
- 先生は [littlemex/prismyra-decision-35b-a3b-fp8](https://huggingface.co/littlemex/prismyra-decision-35b-a3b-fp8) を L40S 1 枚で動かしました。値段は g6e.12xlarge ($15.22/h、L40S 4 枚) の 1/4 として $3.80/h、処理件数は 8 件を並行して流して測った 1 時間 91,367 件です。
- GPU で動かした生徒は vLLM 0.27.1 で配信しました。
- CPU の生徒は c8g.xlarge (4 コア、4 スレッド、$0.20012/h) で、PyTorch 2.15、bf16 の重みで動かしました。
- 入力の長さは、標準の指示文で 1 件約 68 トークン、見出しだけで約 37 トークンです。
- 0.8B の学習は L40S 1 枚で、AdamW、学習率 2e-5、バッチ 32、2 エポック、乱数の種 0 です。生み出す版の学習は 1,203 秒でした。
- vLLM Semantic Router は開発版 0.5.0.dev20261105131819 (commit 37bdd81) を使いました。
:::
