## はじめに

にゃーん。最初にお断りしておくと、私は事前学習も事後学習も自分で回したことがなく、実体験としてのデータは持っていません。RL のフレームワークを AWS で動かす参照実装の整備はしていますが、モデルを育てる規模の学習ではありません。この記事の数字は、公開された技術報告の値と、そこから式で計算した試算だけでできています。どの数字がどちらなのかは、そのつど書きます。

AWS の 3 人の著者が Hugging Face に書いた「[Building Blocks for Foundation Model Training and Inference on AWS](https://huggingface.co/blog/amazon/foundation-model-building-blocks)」は、冒頭で「スケーリングはもはや 1 本の曲線ではない」と書いています。NVIDIA が「[one to three scaling laws](https://blogs.nvidia.com/blog/ai-scaling-laws/)」と呼ぶ整理を引き、事前学習に加えて、SFT や RL による post-training と、推論時の計算量でも性能が伸びるという見方です。この記事では、そのうち post-training が加わったことで GPU 台数の見積もりがどう変わるかを整理し、最後に 100B 級のモデルを AWS で学習するときの構成の判断軸を表にまとめます。以下、このブログを Building Blocks と呼びます。

| よく置かれる前提 | いまの状態 | 実務での意味 |
|---|---|---|
| 計算量はほぼ事前学習で決まる | DeepSeek の報告では post-training が事前学習の 0.19 % から 10 % 超へ増え、RL に事前学習より多くの GPU を確保した例も出ている | post-training の台数と予算を別に見積もる |
| 世代を変えたときの台数は、ピーク性能の比でおおよそ決まる | 事前学習なら step 時間の内訳から一次試算を式で出せる | p5en 8 台の 64 枚の H200 を B200 に置き換えると、試算では p6-b200 が 4〜6 台になる |
| MFU は構成で決まる | RL では回答の長さ、HBM に同時に置ける生成中の系列の数、環境を動かす CPU の待ちで動き、学習の途中でも変わる | RL は pilot で測らないと台数が決まらない |

## 3 本のスケーリング則

![3 本のスケーリング則は、伸ばすものとスループットを決めるものが違い、土台は共通である](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/99375dd5ac013f/zenn/articles/99375dd5ac013f/three-scaling-laws.png)

事前学習では、パラメータ数 $N$ とトークン数 $D$ を増やすと損失が下がります。その関係と計算量の式 $C \approx 6ND$ は「[Scaling Laws を丁寧に読む](https://littlemex.github.io/explainers/paper-scaling-laws.html)」で整理しました。post-training で伸ばすのは SFT のデータと RL に使う計算量で、推論時の計算量で伸ばすのは、1 つの回答に使うトークン数や、並列に作って比べる回答の本数です。

Building Blocks は、3 つとも密に結合した GPU、広帯域で低遅延のネットワーク、スケールする分散ストレージを必要とし、違いは主に負荷の形とスケジューリングだと結んでいます。台数の見積もりで効いてくるのは、図の中段、つまりスループットを何が決めるかの違いです。中段の KV seats は HBM に同時に置ける生成中の系列の数で、RL の節で扱います。

## 事前学習のスループット

![事前学習では構成を決めると step 時間が安定し、GPU 時間が式で決まる。MFU の低下はそのまま GPU 時間の増加になる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/99375dd5ac013f/zenn/articles/99375dd5ac013f/pretraining-throughput.png)

事前学習の 1 step は、同じ段階の中ではほぼ同じ形の計算です。ここで recompute は、逆伝播で使う activation を保存せずに計算し直してメモリを空ける手法です。並列化の構成、dtype、recompute の範囲を決めて学習が安定すれば、step 時間はあまり動きません。系列長やデータの配合を変える段階に移ると内訳が変わり、MoE では expert への振り分けの偏りでも揺れるので、見積もりは段階ごとに分けます。そのうえで、必要な GPU 時間は次の式で概算できます。$P$ は GPU 1 枚のピーク性能で単位は FLOP/s、MFU は学習が動いている間に理論ピークのうち実際に学習に使えた割合、$A$ は故障からの復旧や checkpoint の保存で止まった時間を除いた、学習が進んでいた時間の割合です。

$$
\text{GPU 時間} = \frac{C}{3600 \cdot P \cdot \text{MFU} \cdot A}, \qquad C \approx 6 N_\text{active} D
$$

GPU の時間単価が同じなら、MFU や $A$ が下がった分だけ費用が増えます。MFU が 35 % から 34 % に 1 ポイント落ちると、GPU 時間は 35/34 倍、つまり 2.9 % 増えます。後の節で試算する 100B 級の事前学習の約 58 万 GPU 時間に当てると約 1.7 万 GPU 時間で、512 枚のクラスタの約 1.4 日分に当たります。$A$ については、[Llama 3](https://arxiv.org/abs/2407.21783) の 405B の学習で 54 日間に 466 回の中断があり、有効な学習時間は 90 % を超えたと報告されています。同じ報告は、H100 の 8K〜16K 枚で bf16 の MFU が 38〜43 % だったとしています。MoE でも、[ERNIE 4.5](https://ernie.baidu.com/blog/publication/ERNIE_Technical_Report.pdf) は最大のモデルの事前学習で MFU 47 % を報告しています。FP8 の混合精度で学習しており、分母の dtype は書かれていません。FP8 で数えた例では、[PLaMo-100B](https://arxiv.org/abs/2410.07563) が H100 の FP8 ピークの約 27 % です。[Nemotron-4 340B](https://arxiv.org/abs/2406.11704) も H100 を 1,536 枚から 6,144 枚へ増やす間に 42.4 % から 41.0 %、[MegaScale](https://arxiv.org/abs/2402.15627) は 175B の dense で 12,288 枚の 55.2 % を報告しており、大規模な dense の事前学習で実際に出ている値の目安になります。

step 時間、フレームワークが出す実効 TFLOP/s から求めた MFU、DCGM の Tensor Core の稼働率、計算と重ならない通信、中断と再開の時間を常に監視するのはこのためです。DCGM の GPU 使用率は kernel が 1 つでも動いていれば 100 % になるので、MFU の代わりにはなりません。Building Blocks も、DCGM-Exporter と Prometheus、Grafana による監視を基本の構成に挙げています。

![H100、H800、H200 で学習した 23 のモデルは、ほとんどが bf16 ピークの 10〜40 % の線の間に並ぶ](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/99375dd5ac013f/zenn/articles/99375dd5ac013f/compute-vs-gpu-hours.png)

公開値からも、この式でどのくらいの効率だったかを逆算できます。上の図は、H100、H800、H200 で学習し、トークン数と GPU 時間の両方を公開している 23 のモデルを並べたものです。点線は bf16 のピークの 10 %、20 %、40 % で学習した場合の GPU 時間で、ほとんどのモデルがこの間に入ります。次の表は $6 N_\text{active} D$ だけを数え、attention の計算量を入れていません。報告された GPU 時間に中断が含まれていれば、値は MFU と $A$ の積に対応します。どこまで含むかは報告ごとに違うので、目安として読んでください。

| モデル | 総 / active パラメータ | トークン | GPU 時間 | $6N_\text{active}D$ の bf16 ピーク比 |
|---|---|---|---|---|
| [Llama 4 Scout](https://huggingface.co/meta-llama/Llama-4-Scout-17B-16E) | 109B / 17B | 約 40T | H100 5.0M | 22.9 % |
| [Llama 4 Maverick](https://huggingface.co/meta-llama/Llama-4-Maverick-17B-128E) | 400B / 17B | 約 22T | H100 2.38M | 26.5 % |
| [DeepSeek-V3](https://arxiv.org/abs/2412.19437) | 671B / 37B | 14.8T | H800 2.664M | 34.6 % |

H800 の bf16 dense のピークは H100 と同じ 0.9895 PFLOP/s として計算しました。DeepSeek-V3 は行列積の大半を FP8 で計算しているので、FP8 のピークで割ると 17.3 % になります。同じ学習でも、分母の dtype の選び方で値が 2 倍違います。[Llama 4 の発表](https://ai.meta.com/blog/llama-4-multimodal-intelligence/)も Behemoth の事前学習で FP8 を使ったと述べており、Scout と Maverick の値も bf16 の実効率とは限りません。3 行は分母を bf16 にそろえた換算値として並べられるだけで、bf16 の実測 MFU として引けるのは、Llama 3 の 38〜43 % や Nemotron-4 の 41〜42 % のような報告値です。attention の計算量も小さくありません。causal mask で半分だけ数えても、次の節で扱う GLM-4.5-Air の 46 層、96 ヘッドの形では、系列長 4K で $6N$ の約 2 割、32K では $6N$ の 1.5 倍になります。MFU を比べるときは、FLOP の数え方と分母の dtype をそろえる必要があります。

## 世代変更の見積もり: H200 から B200

![H200 から B200 では、演算、HBM 帯域、NVLink はそれぞれ違う倍率で速くなるが、1 台あたりの EFA の帯域と待ち時間はほぼ変わらない。数字は単純なモデルから出したもの](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/99375dd5ac013f/zenn/articles/99375dd5ac013f/h200-to-b200.png)

事前学習なら、世代を変えたときの台数も一次試算を式で出せます。新しい GPU 1 枚が現行の何倍の仕事をするかを実効倍率 $S$ とすると、必要な GPU は現行の GPU 数を $S$ で割った数です。$S$ は、現行の step 時間を区間 $i$ ごとの割合 $f_i$ に分け、それぞれの区間が新しい GPU で何倍速くなるか $r_i$ を当てて合成します。$\eta$ は新しい世代でのソフトウェアの成熟度で、ここでは 0.95 と置きます。現行の step 時間を基準にした比で考えるので、現行の MFU の値そのものは要りません。

$$
S = \frac{\eta}{\sum_i f_i / r_i}, \qquad \text{必要 GPU} = \frac{\text{現行 GPU}}{S}, \qquad k = \frac{S}{r_\text{peak}}
$$

$k$ は、ピーク比 $r_\text{peak}$ のうち実際に生きる割合で、ここでは移送係数と呼びます。$k = 1$ ならピーク比どおりで、小さいほどピーク比から目減りします。この式は、各区間が直列に並び、台数を減らしても並列化の次元や GPU 1 枚あたりの micro-batch を据え置けることを仮定しています。並列化の次元とは、行列積を分ける TP、層を分ける PP、expert を分ける EP、データを分ける DP のことです。たとえば下の表に出てくる 35 GPU や 39 GPU では、TP、PP、EP、DP の積で割り切れる構成がほとんど組めません。実際には 32 や 40 のような候補ごとに構成を組み直し、その構成で $f_i$ を測り直して確かめます。

$f_i$ の通信には、profiler で計算と重なっていないと確かめた分だけを入れます。演算が速くなると、現行では計算の裏に隠れていた通信が新しい世代では表に出るので、この式は楽観側に外れやすく、通信の $f_i$ は多めに置くのが安全です。待ちは、データの読み込み、ホストとの同期、遅い GPU を待つ時間のことです。PP の bubble は演算に比例して縮むので演算に含め、checkpoint の保存による停止は step の外の $A$ に含めます。

NVIDIA のデータシートと [P5](https://aws.amazon.com/ec2/instance-types/p5/)、[P6](https://aws.amazon.com/ec2/instance-types/p6/) の製品ページから、p5en.48xlarge の H200 と p6-b200.48xlarge の B200 を比べると次のようになります。Building Blocks の表は B200 の帯域を 8 TB/s としていますが、これは GB200 の値で、8 GPU のサーバーに載る B200 のデータシートの値は 7.7 TB/s です。

| 項目 | H200 | B200 | 比 |
|---|---|---|---|
| bf16 dense ピーク | 0.9895 PFLOP/s | 2.25 PFLOP/s | 2.27 |
| HBM 容量 | 141 GB | 180 GB | 1.28 |
| HBM 帯域 | 4.8 TB/s | 7.7 TB/s | 1.60 |
| NVLink、GPU 1 枚あたり | 900 GB/s | 1.8 TB/s | 2.0 |
| EFA、1 台あたり | 3,200 Gbps、第 3 世代 | 3,200 Gbps、EFAv4 | 1.0 |

EFA の第 3 世代は H200 のうち p5en だけで、同じ H200 の p5e は p5 と同じ第 2 世代です。演算は 2.27 倍になる一方で、HBM 帯域は 1.60 倍にとどまります。演算律速と帯域律速の境目になる算術強度は、ピーク値から計算すると H200 の 206 FLOP/byte から B200 の 292 FLOP/byte へ上がり、同じ算術強度で動く区間は B200 のほうが帯域の制約を受けやすくなります。ノード間の帯域は 1 台あたり同じで、Building Blocks によれば EFAv4 で集団通信の性能が EFAv3 より 18 % 上がります。

現行が p5en の 8 台、64 GPU だとして、4 通りの内訳を当てると次のようになります。内訳は例として置いた値です。各区間の倍率は、演算 2.27、HBM 1.60、ノード間通信 1.0、待ち 1.0 と置き、必要 GPU を 8 で割って切り上げたものを台数としました。ノード間通信は保守的に 1.0 としましたが、18 % の改善を当てて 1.18 にしても台数は変わりません。

| 現行の step 時間の内訳 | $k$ | 必要 GPU | 台数 |
|---|---|---|---|
| すべて演算律速 | 0.95 | 30 | 4 |
| 演算 80 %、HBM 10 %、ノード間通信 5 %、待ち 5 % | 0.81 | 35 | 5 |
| 演算 60 %、HBM 25 %、ノード間通信 10 %、待ち 5 % | 0.73 | 39 | 5 |
| 演算 50 %、HBM 20 %、ノード間通信 25 %、待ち 5 % | 0.65 | 44 | 6 |

ピーク比だけで割ると $8 / 2.27 \approx 3.5$ なので 4 台ですが、内訳によっては 6 台まで増えます。ノード間の通信がほとんど速くならないので、ほかの区間が速くなるほど step に占める通信の割合が大きくなるからです。同じ負荷で H200 と B200 を比べた公開値は、[MLPerf Training v6.0](https://mlcommons.org/2026/06/mlperf-training-v6-0/) にあります。SXM 型の H200 と B200 を 16 枚どうしで比べると、Llama 3.1 8B の事前学習で 2.34 倍（Cisco の H200 と HPE の B200）、Llama 2 70B の LoRA で 1.96 倍（Krai の H200 と HPE の B200）でした。結果の表から私が計算した値で、LoRA の 2 つは global batch の大きさも違います。提出した会社とソフトウェアの版が違い、精度も結果の表からはわからないので、目安として読んでください。8 枚の提出の H200 は電力と帯域を絞った NVL 型で、p5en の H200 とは別物です。もう 1 つの近い実測として、NVIDIA の [Megatron Bridge の性能表](https://docs.nvidia.com/nemo/megatron-bridge/latest/performance-summary-archive.html) では、FP8 の TFLOP/s/GPU が H100 から B200 で Llama 3.1 405B は 822 から 1,667 の 2.03 倍、DeepSeek-V3 は 338 から 557 の 1.65 倍です。GPU 枚数も構成も違う測定ですが、FP8 のピーク比 2.27 で割ると dense が約 0.89、MoE が約 0.73 で、上の表の幅に収まります。$\eta = 0.95$ も実測ではない仮定で、感度を見るために 3 行目の内訳で $\eta = 0.8$ と置くと 46 GPU、6 台になります。NVLink の 2.0 倍は、ノードの中の通信が計算と重なるとしてこの 4 例では区間に分けていません。

もう 1 つ見落としやすいのが HBM の総量です。4 台に減らすと 5,728 GB になり、現行の 9,024 GB の 63 % です。容量に余裕のない構成では TP や recompute を増やす必要が出て、$k$ がさらに下がります。H100 から B300 への置き換えでは、p6-b300 の製品ページの 1 台 2,144 GB から HBM の容量が 1 枚あたり約 3.35 倍、帯域が 2.30 倍、EFA が 1 台あたり 2 倍に増えます。帯域と通信が演算の伸びに近いので $k$ は高めに出て、同じ式でも逆に recompute を外せる余地が生まれます。移行元と移行先の組み合わせで、効く項が入れ替わります。段階による違いもあります。継続事前学習で系列長を伸ばすなら attention の割合が上がるので $f_i$ を測り直し、SFT はジョブが短く起動や checkpoint の固定費の割合が大きいので、実質的に $\eta$ を下げて見ます。最後は、台数にインスタンスの時間単価を掛けた費用で比べます。

## アーキテクチャの影響

$f_i$ と $r_i$ のどちらも、モデルのアーキテクチャに強く左右されます。効き方が大きいのは、MoE がどれだけ疎か、そして attention が 1 トークンあたり何バイトの KV キャッシュを持つかの 2 点です。次の表は、各モデルの config から bf16 で計算した、全層の合計の値です。

| モデル | 総 / active | expert 数 / 選ぶ数 | attention | KV、1 トークン | 32K トークンの 1 本 |
|---|---|---|---|---|---|
| [GLM-4.5-Air](https://huggingface.co/zai-org/GLM-4.5-Air) | 106B / 12B | 128 / 8 | GQA、46 層 | 184 KiB | 5.75 GiB |
| [gpt-oss-120b](https://huggingface.co/openai/gpt-oss-120b) | 117B / 5.1B | 128 / 4 | GQA、36 層の半分が sliding window | 36 KiB | 1.13 GiB |
| [DeepSeek-V3](https://huggingface.co/deepseek-ai/DeepSeek-V3) | 671B / 37B | 256 / 8 | MLA、61 層 | 68.6 KiB | 2.14 GiB |
| [Llama 3.1 70B](https://arxiv.org/abs/2407.21783) | 70B / 70B | dense | GQA、80 層 | 320 KiB | 10.0 GiB |

gpt-oss-120b の 36 KiB は全体を見る 18 層の分で、128 トークンの窓だけを見る残りの 18 層は、系列の長さによらず 1 本あたり 4.5 MiB で一定です。

bf16 の行列積では、重み 1 要素の 2 バイトを読むたびにトークン 1 つにつき 2 FLOP を計算するので、算術強度はおよそ同時に流すトークン数に等しくなります。MoE では、expert 1 つに流れるトークンが「選ぶ数 / expert 数」に細り、GLM-4.5-Air なら $8/128 = 1/16$ です。トークンが expert に均等に振り分けられるとすると、B200 の境目の 292 FLOP/byte に届くには、expert 1 つあたり約 292 トークン、16 倍して 1 回の行列積に約 4,700 トークンが要ります。事前学習の大きな micro-batch ならこれに近づけますが、生成では 1 step に各系列が 1 トークンずつしか進まないので、まず届きません。そのため rollout の expert の計算は帯域律速になり、$r_i$ は演算比の 2.27 より帯域比の 1.60 に近くなります。KV のサイズは、次の節で扱う rollout の同時系列数を決めます。attention の方式ごとの違いは「[Attention の系譜](https://littlemex.github.io/explainers/attention-series-index.html)」にまとめています。

MoE は事前学習でも効率が落ちやすく、[MegaScale-MoE](https://arxiv.org/abs/2505.11432) は 352B の MoE を H800 の 1,440 枚で MFU 27.9〜32.5 % と報告しています。GPU と規模は違いますが、同じ組織が 175B の dense で報告した 55〜65 % の約半分です。

事前学習では、アーキテクチャの影響は現行の $f_i$ を測った時点で数字に入り、同じ段階の中ではあまり変わりません。RL ではそうはいきません。

## RL: rollout と trainer

![RL の 1 step では、rollout が時間の大半を使い、trainer が計算量の大半を使う。内訳は学習の途中でも動く](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/99375dd5ac013f/zenn/articles/99375dd5ac013f/rl-step.png)

RL の 1 step には、性質の違う 2 つの仕事が入ります。rollout は推論エンジンで回答を生成します。trainer は、回答に付いた報酬から勾配を計算して重みを更新します。更新した重みを rollout 側へ配るのが重み同期です。仕組みは「[分散 RL post-training の通信プリミティブ入門](https://zenn.dev/tosshi/articles/1f6589ff93dca7)」で図にしました。

rollout と trainer の置き方には 2 通りあります。同じ GPU を交互に使う colocated では、HBM の分け方と切り替えの時間が制約になります。重み同期は同じ GPU の上のコピーで済む部分が多い一方、trainer が FSDP などで重みをノードをまたいで分けていれば、推論エンジンに渡す前の all-gather は EFA を通ります。別の GPU に分ける disaggregated では、重み同期がノード間の EFA を通り、同期の待ちも入ります。[Qwen3.5](https://qwen.ai/blog?id=qwen3.5) は学習と推論を完全に分けた構成を採っています。重み同期の実測は短く、[Kimi K2](https://arxiv.org/abs/2507.20534) は 1 兆パラメータ全体の更新を 30 秒未満、[LlamaRL](https://arxiv.org/abs/2505.24034) は 405B で 2.31 秒、[Laminar](https://arxiv.org/abs/2510.12633) は 72B を 128 台へ 1.6 秒未満で配っています。非同期にすれば両者を重ねられ、[INTELLECT-3](https://www.primeintellect.ai/blog/intellect-3) は非同期の方式だけを使い、常に数 step だけ古い重みで生成しています。その代わり、古い重みで作ったデータで学ぶことになるので、学習の質も見る必要が出ます。[Magistral](https://arxiv.org/abs/2506.10910) は何 step 古い重みまで許すかに上限を置き、[AReaL](https://arxiv.org/abs/2505.24298) は同じ GPU 数の同期型より最大 2.77 倍速く、推論と学習の GPU を 75 対 25 に分けたときが 50 対 50 より速かったと報告しています。

まず、計算量の割合と時間の割合が一致しません。trainer は、rollout が作ったトークン列の確率を、更新前の重みで計算し直してから学習する構成が多く見られます。推論エンジンが返す確率と trainer の計算では数値が少しずれるので、更新の幅を決める比には trainer 側の値を使うためです。生成したトークンについて、この再計算の $2N$、rollout の $2N$、学習の $6N$ だけを 1 回ずつ数える単純なモデルでは、rollout は計算量の約 20 % です。prompt のトークンは再計算と学習にはかかり生成にはかからないので、prompt が長いほどこの割合は下がります。KL 正則化のために学習前の重みを固定した参照モデルの forward や、複数回の更新を足しても下がります。[INTELLECT-2](https://arxiv.org/abs/2505.07291) は学習と推論の FLOP の比を 4.5 倍と報告しており、rollout が約 18 % にあたるので、この単純なモデルと近い値です。

ところが [Seer](https://arxiv.org/abs/2511.14617) の Table 1 では、Moonlight、Qwen2-VL-72B、Kimi-K2 の 3 つの RL の負荷で、rollout が 1 回の反復の 63〜87 % の時間を占めています。

![rollout が RL の step の時間に占める割合は、システムによって 22 % から 90 % まで散らばる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/99375dd5ac013f/zenn/articles/99375dd5ac013f/rollout-share.png)

この割合はシステムの作りでも大きく変わります。上の図は、論文と技術報告の 14 のシステムの値を並べたものです。rollout 以外の計算を並行して動かす [ReaL](https://arxiv.org/abs/2406.14088) の計算値では、探索した配置で 25.5〜48 %、ヒューリスティックな配置で最大 57.2 %、短い回答の設定では [DistFlow](https://arxiv.org/abs/2507.13833) が 31.8 %、比較対象の verl が 21.9 % です。図の OpenRLHF の 90 % は、特定の実験ではなく論文の導入部の一般的な記述です。完全に非同期にした [MiMo-V2.6](https://arxiv.org/abs/2610.11959) は、RL の時間を rollout 43.8 %、学習 43.5 %、採点 12.7 % と報告しています。1 トークンずつ進む decode は、毎回重みと KV を HBM から読み出すので、計算量のわりに時間がかかります。ただし、ツールの出力を長く読み込む agentic な負荷では prefill の計算量が大きくなり、この部分は演算律速なので世代の差がそのまま効きます。rollout の中でも prefill と decode は分けて測ります。

次に、時間の多くが裾にあります。同じ論文は、メモリが厳しい負荷では最後の 10 % のリクエストが全体の時間の最大 50 % を使うと報告しています。裾では同時に動く系列が少なく、GPU は帯域も演算も使い切れません。この区間は世代を変えても、1 系列の生成速度の分しか速くなりません。裾の大きさは、回答の長さの上限、未完の系列を次の step に持ち越す partial rollout、非同期の度合い、Seer のような長さを予測するスケジューリングで変わるので、pilot ではこれらを本番の値に固定して測ります。DeepSeek は [R1 の補足資料](https://www.nature.com/articles/s41586-025-09422-z)で、rollout に自分自身の予測ヘッドを使った投機的デコードを入れ、最も長いサンプルが終わるまでの時間を縮めたと書いています。

さらに、この内訳は学習の途中で動きます。[DeepSeek-R1](https://arxiv.org/abs/2501.12948) の報告では、R1-Zero の回答の平均長は RL の進行とともに伸び続けました。回答が伸びれば rollout の割合が増え、KV が膨らんで同時に置ける系列が減り、裾も伸びます。事前学習の $f_i$ が構成でほぼ決まるのに対し、RL の $f_i$ は方策の振る舞いでも動きます。

同時に置ける系列の数も、世代の比較を変えます。以下ではこれを座席数と呼びます。GLM-4.5-Air の bf16 の重みは約 212 GB です。これを 1 台の 8 GPU に均等に分けて置き、1 台の HBM の 90 % から重みを引いた残りをすべて KV に使い、全系列が 32K トークンに達したとして、容量の上での最悪の値を計算すると次のとおりです。PagedAttention は実際の長さの分しか KV を取らないので、回答が短いうちは座席はこれより多くなります。HBM の容量は AWS の製品ページの 1 台あたりの値で、p5en が 1,128 GB、p6-b200 が 1,432 GB、p6-b300 が 2,144 GB です。Building Blocks の表は B300 を 1 枚 288 GB としていますが、p6-b300 の製品ページの値は 1 枚あたり約 268 GB です。

| 1 台 | bf16 で KV に使える HBM | bf16 の座席数 | 重みと KV を FP8 にした座席数 | bf16 の H200 比 | FP8 の H200 比 |
|---|---|---|---|---|---|
| p5en、H200 | 803 GB | 130 | 294 | 1.0 | 1.0 |
| p6-b200、B200 | 1,077 GB | 174 | 383 | 1.34 | 1.30 |
| p6-b300、B300 | 1,718 GB | 278 | 590 | 2.14 | 2.01 |

[GLM-4.5](https://arxiv.org/abs/2508.06471) の報告は、学習を bf16、rollout を FP8 で行っています。FP8 の列は、重みに加えて KV も FP8 にしたと仮定した私の試算です。FP8 にすると座席はどの世代でも約 2.2 倍に増えますが、世代間の比はほとんど変わりません。

rollout が新しい世代で何倍速くなるかは、何が 1 step の時間を決めるかで変わります。重みと KV の読み出しが支配的なら、同じ batch でも帯域比の 1.60 倍に近く、座席が増えた分 batch を大きくできればそれ以上になります。一方、同時に動く系列が少なく、sampler や CPU 側の処理で step の時間に下限が付く区間では、帯域の伸びは効かず、同時に進められる系列の数、つまり座席比の 1.34 倍が目安になります。B300 は座席が約 2 倍になり、EFA も 1 台あたり 6,400 Gbps と 2 倍なので、重みの読み出しが支配的な短い回答や重み同期では B200 より有利になり得ます。B300 の帯域は B200 と同じなので、32K に近い長い回答で KV の読み出しが支配的な区間では、差は小さくなります。

これらを先ほどの式に当てはめると、たとえば次の内訳と倍率になります。倍率はどれも仮定です。

| 区間 | $f_i$ | $r_i$ | 置いた理由 |
|---|---|---|---|
| rollout の大部分 | 45 % | 1.60、または 1.34 | 帯域律速なら帯域比、step に下限が付くなら座席比 |
| 裾 | 25 % | 1.60 | 1 系列の帯域比 |
| 確率の再計算と学習 | 20 % | 2.0 | 事前学習の 2 行目の内訳を $\eta$ を除いて合成した $1.94$ と同じ程度 |
| 重み同期 | 5 % | 1.5 | EFA の 1.0 と NVLink の 2.0 の間。実測は数秒から 30 秒未満 |
| 報酬と環境 | 5 % | 1.0 | GPU の外の時間。agentic な負荷の公開値は無く、次の節のとおり設計で大きく変わる |

rollout の大部分を帯域比で置くと $k$ は 0.67、座席比で置くと 0.62 になり、どちらも 64 GPU の置き換えに 6 台 48 GPU が要ります。ただ、この数字に頼ることはできません。どちらの倍率が効くかは負荷によって違い、内訳そのものが学習中に動くので、どの時点の内訳を使うかで答えが変わるからです。

ここで pilot と呼んでいるのは、本番と同じモデル、回答長の上限、配置で、数十から数百 step だけ回す試験です。数百 step では学習の後半の長い回答には届かないので、pilot の初期の内訳をそのまま使うと、学習が進むほど rollout の割合が増えて見積もりが外れます。そこで、回答長の上限を本番の値に固定して全系列が上限に達したときの座席数と裾を最悪値として測るか、前回の学習から後半の回答長の分布を借りて rollout だけを再現します。RL の台数は、**後半の内訳を pilot でこのように見積もってから決める**しかありません。学習と推論の数値の食い違いについては「[RL ポストトレーニングが静かに壊れるとき](https://zenn.dev/tosshi/articles/5fc9e8dc7f2ae3)」で扱いました。

## RL の台数は事前学習より減らせるか

RL の MFU が低いなら、GPU が余っているので台数を減らせる、と考えたくなります。ここで「減らせる」には 2 つの意味があります。同じスループットをより少ない GPU で出せるかと、総計算量が小さいので少ない GPU で足りるかです。公開された資料を並べると、どちらもそう単純ではありません。

まず、MFU が低いのは演算が遊んでいるということで、メモリまで余っているとは限りません。[Olmo 3](https://arxiv.org/abs/2512.13961) は、A100 の 2 ノードで推論側だけを測った小さなベンチマークで、MFU 1.01 % のときに HBM 帯域の利用率が 43.2 % だったと報告しています。帯域は演算よりはるかによく使われ、HBM の容量は KV で埋まります。colocated の構成では、[DeepSeek-R1](https://www.nature.com/articles/s41586-025-09422-z) や [Llama-Nemotron Ultra](https://arxiv.org/abs/2505.00949) のように、推論エンジンの KV と学習の重みや optimizer の状態を同じ HBM の上で入れ替えながら使っています。GPU を減らすと座席が減り、rollout と裾が延び、この入れ替えも苦しくなります。

次に、trainer の台数には下限があります。optimizer の状態はモデルの大きさで決まり、台数を減らすほど 1 枚あたりの負担が増えます。[Kimi K2](https://arxiv.org/abs/2507.20534) は、1 兆パラメータの bf16 の重みと FP32 の勾配のバッファだけで 256 枚の並列のグループに約 6 TB を置き、学習ノードが 32 台のような小さい構成では optimizer の状態の一部を CPU のメモリへ退避すると書いています。退避すれば動きますが、その分 step は遅くなります。

公開例では、RL に使った GPU の枚数も期間も事前学習より小さいことが多く、DeepSeek は事前学習の 2,048 枚、約 54 日に対して R1 の RL が 512 枚、約 12 日です。Olmo 3 は最大 1,024 枚で約 47 日の事前学習に対して、RL が 224 枚で初回の約 5 日と追加の 21 日です。GPU 時間で見ると事前学習の約 5〜11 % です。逆の例もあり、[Reflection AI の Beam](https://www.reflection.ai/beam) は事前学習を GB300 の 6,144 枚で 4 週間未満、RL を GB300 の 1 万 500 枚で 4 週間行っています。RL に確保した GPU 時間が事前学習を上回る例です。

増やす方向にも上限があります。[ROLL Flash](https://arxiv.org/abs/2510.11345) は、学習側を 16 枚に固定して推論側を変えた比較で、推論 24 枚が最も速く、32 枚に増やすと生成中に計算資源が大きく遊ぶと報告しています。配分の比は、[AReaL](https://arxiv.org/abs/2505.24298) で推論と学習が 75 対 25、INTELLECT-3 で 44 対 16 ノード、Olmo 3 の 32B で 20 対 8 ノードと、推論側を 2.5〜3 倍にする例が並びます。一方、[Tülu 3](https://arxiv.org/abs/2411.15124) の 405B は推論を重みを載せる最小の 16 枚にとどめ、残りの 240 枚を学習に回しています。推論側の枚数がスループットで決まるか、重みを載せる最小の構成で決まるかで、比は 1 対 15 から 3 対 1 まで変わります。

公開例で RL の枚数が事前学習より少ないのは、総計算量が小さいからで、MFU が低いからではありません。1 枚あたりの効率を落とさずに台数を減らせるのは、HBM の容量に余裕があり回答が短く裾が小さい負荷か、推論側の枚数が重みを載せる最小の構成で決まっている負荷です。台数を減らせば、同じ仕事には長い期間がかかります。一方、回答が長く KV で座席が埋まる負荷や、モデルが大きく optimizer の状態が下限を決める負荷では、減らすと遅くなるので、FP8 の rollout、投機的デコード、KV の量子化、非同期化のように同じ台数のスループットを上げる手段を先に検討します。

## CPU と環境の時間

agentic な RL では、GPU の外で動く環境の比重が増えています。モデルがコードを実行し、ツールを呼び、テストを回すたびに、CPU の上のサンドボックスが結果を返すまで、その系列の生成は止まります。[Kimi K2](https://arxiv.org/abs/2507.20534) は Kubernetes の上で 1 万を超えるサンドボックスを同時に動かし、[Qwen3-Coder](https://qwenlm.github.io/blog/qwen3-coder/) は 2 万の独立した環境を並列に動かしたと報告しています。[LongCat-Flash-Thinking-2601](https://arxiv.org/abs/2601.16725) は 3 万 2,000 の環境を同時に動かし、[Reflection AI の Beam](https://www.reflection.ai/beam) は同時に最大 17 万のサンドボックスを動かしています。累計の数では、Beam が学習と採点で約 13 億のサンドボックスを使い、[Kimi K3](https://github.com/MoonshotAI/Kimi-K3/blob/main/k3_tech_report.pdf) が学習と評価の間に約 5,122 万個を作り、サンドボックスは寿命の最大 98 % をモデルの推論の結果を待って止まっていたと書いています。環境が GPU を待つ時間も長いということです。どれも CPU のコア数と GPU の比は公開しておらず、DeepSeek-V4.1-Flash がノードあたり 2,500 を超えるコンテナの密度とスケジューリングの方法を書いているのが近い例です。

環境の待ちが GPU をどれだけ遊ばせるかを直接測った公開値は少なく、[SkyRL-Agent](https://arxiv.org/abs/2511.16108) がその 1 つです。H100 の 16 枚で SWE の agent を学習し、まとめて待つ方式ではサンドボックスの初期化と報酬の計算の間に GPU の利用率が大きく落ち、生成と環境を流れ作業で重ねる方式では約 90 % で安定し、1.55 倍速くなりました。環境の待ちに直接対応する実測はこの 1.55 倍で、生成と学習を完全に非同期にした [AReaL](https://arxiv.org/abs/2505.24298) は最大 2.77 倍です。同じ GPU でも、待ちの扱い方で step の時間は大きく変わります。

報酬の作り方でも CPU の量は変わります。[SWE-RL](https://arxiv.org/abs/2502.18449) はコードを実行せず、正解との差分の似ている度合いを報酬にして、サンドボックスを使わずに済ませています。実行して検証する方式は報酬の信頼性が高い代わりに、CPU とコンテナの数がそのまま必要な資源になります。

前の節の表では報酬と環境を 5 %、倍率 1.0 と置きましたが、agentic な負荷でこれを裏付ける公開値はありません。GPU を新しい世代にしてもこの区間は速くならないので、GPU の台数を減らすほど step に占める割合は大きくなります。台数を見積もるときは、GPU とは別に、同時に動かすサンドボックスの数と 1 回の実行にかかる CPU 時間を pilot で測ります。p5en、p6-b200、p6-b300 は 1 台に 192 vCPU を持ちます。[MiniMax-M2](https://arxiv.org/abs/2605.26494) が評価の設定で使った 1 サンドボックス 8 vCPU を、学習時の値ではないことを承知で当てると、1 万のサンドボックスには 8 万 vCPU が要り、p6-b200 の 64 台が持つ 12,288 vCPU の約 6.5 倍です。このため、GPU のノードとは別に CPU のノードグループを用意する構成になります。

| [Reflection AI Beam](https://www.reflection.ai/beam) | 501B / 23B の RL を GB300 1 万 500 枚で 4 週間 | 1 万 500 枚を 4 週間確保したとすると約 7.06M | 事前学習の 6,144 枚、4 週間未満を上回る |
| [Llama-Nemotron Ultra](https://arxiv.org/abs/2505.00949) | 253B の dense の RL を H100 576 枚で。学習と生成の並列化がともに 576 枚に一致する構成 | 約 140K、報告値 | 事前学習は元の Llama の分 |
| [Tülu 3](https://arxiv.org/abs/2411.15124) | 405B の RLVR を H100 256 枚で 46 時間 | 約 11.8K、枚数と時間の報告値からの計算値 | 事前学習は元の Llama の分 |
| [INTELLECT-3](https://www.primeintellect.ai/blog/intellect-3) | GLM-4.5-Air base からの SFT と RL。クラスタは H200 512 枚で 2 か月、RL はそのうち 480 枚 | 2 か月を 60 日とし、512 枚を確保し続けたと仮定すると約 737K | 仮定を置いた試算で約 55 % |

INTELLECT-3 の 737K は、複数の実験を含めてクラスタを確保していた時間の換算で、実際に学習が進んでいた時間ではありません。技術報告によれば、RL には 60 ノードの 480 枚を使い、学習に 16 ノード、推論に 44 ノードを割り当てました。推論側が約 2.75 倍で、rollout が時間の大半を占めることがそのまま配分に出ています。比べる相手の GLM-4.5-Air の事前学習は、GPU の種類が公開されておらず、論文の要旨も 23T トークンの多段学習を GLM-4.5 について書いていて、Air の値は分けて書いていません。Air も 23T で学習し、H800 相当で MFU 35 % だったと仮定すると、約 1.33M GPU 時間になります。H200 と H800 は bf16 のピークが同じなので GPU 時間で並べましたが、この 55 % は仮定どうしの比で、実際の計算量の比でもその上限でもありません。post-training の予算が事前学習の数十 % に届くこともあり得る、というシナリオとして読んでください。

RL の計算量にもスケーリング則が見つかりつつあります。[The Art of Scaling Reinforcement Learning Compute for LLMs](https://arxiv.org/abs/2510.13786) は 40 万 GPU 時間を超える実験で、RL の計算量と性能の関係がシグモイドの曲線に乗り、小さな実験から 10 万 GPU 時間の 1 本の学習を外挿できたと報告しています。到達点はレシピで決まり、損失の集計や正規化、カリキュラム、off-policy の方式は主に到達までの効率を変えるとしています。この曲線の横軸は GPU 時間なので、同じレシピでも GPU の世代が変われば 1 GPU 時間でできる仕事の量が変わり、そこに前の節の $k$ の問題がそのまま残ります。

この報告と前の節から、RL で曲線に沿って計算量を伸ばすために守ることを並べると次のようになります。

1 と 3〜5 は ScaleRL と各社の報告に根拠があり、2 は世代をまたいで比べるための私の補足です。

1. 小さい学習でレシピを固め、曲線を当てはめてから規模を伸ばします。途中でレシピを変えると、到達点の違う別の曲線に乗り換えることになります。
2. 横軸を GPU 時間だけにせず、生成したトークン数と FLOP も記録します。世代や台数を変えても、曲線を比べられます。
3. 非同期にするなら、何 step 古い重みまで許すかを決めて記録します。
4. 回答長の上限、partial rollout、非同期の設定を、pilot と本番でそろえます。
5. rollout の時間の割合、最後の 10 % のリクエストの時間、座席の使用率、GPU 1 枚あたりの生成トークン数、環境の待ちの時間、学習と推論の確率のずれを、事前学習の MFU と同じように常に監視します。確率のずれは [MiniMax-M1](https://arxiv.org/abs/2506.13585) が実測しており、最後の出力層を FP32 にして学習と推論の確率の相関を 0.9 台から 0.99 台に上げています。

## 事前学習と RL の比較

ここまでの数字を、事前学習と RL で並べます。RL の MFU を公開した例は少なく、私が調べた RL のシステム論文と技術報告の 21 本には MFU の値がなく、数少ない実測は [Olmo 3](https://arxiv.org/abs/2512.13961) の RL です。A100 の 2 ノードで学習 1 ノード、推論 1 ノードに分けて推論側だけを測った小さなベンチマークで、改善の前後で MFU が 0.30 % から 1.01 %、HBM 帯域の利用率が 12.9 % から 43.2 % です。論文は推論のノードを学習の 8 倍以上にするのが典型だと書いていますが、本番の 32B の RL は推論 20 ノード、学習 8 ノードでした。下の表の試算は、colocated の同期型で、trainer の区間の MFU を 35 %、rollout を計算量の 20 %、残りの時間を trainer が使うと置いたものです。

| 項目 | 事前学習 | RL の post-training |
|---|---|---|
| MFU | Llama 3 405B で 38〜43 %、Nemotron-4 340B で 41〜42 %、ERNIE 4.5 の MoE で 47 %（分母の dtype は非公開）、報告値 | Olmo 3 のベンチマークの推論側で 0.30〜1.01 %、報告値。単純なモデルの試算では step 全体で約 6〜16 % |
| H200 から B200 の $k$ | 0.65〜0.95、試算 | 0.62〜0.67、試算 |
| 何で動くか | 並列化の構成、dtype、学習の段階 | 回答長、座席数、裾、非同期の度合い、環境の待ち |
| 見積もり方 | 式と、現行のジョブで測った $f_i$ | pilot で見積もった学習の後半の $f_i$ |

Olmo 3 の値は小さなベンチマークの推論側の値なので直接は比べられませんが、単純なモデルの試算より 1 桁低く、RL の MFU を事前学習の感覚で見積もると大きく外れうることを示唆しています。100B 前後の gpt-oss-120b は 2.1M H100 時間を[公開](https://arxiv.org/abs/2508.10925)していますが、トークン数は数兆としか書かれていないので MFU は出せません。事前学習の側でも MFU を割合で公開するモデルは少なく、[Granite 3.0](https://github.com/ibm-granite/granite-3.0-language-models/blob/main/paper.pdf) のように GPU 時間を公開しているモデルから $6N_\text{active}D$ で計算すると、dense は 19.7〜26.3 %、小さな MoE は 9.5〜10.1 % です。

## 100B クラスのデータ量の目安

![LLM のパラメータ数と事前学習のトークン数。100B 級の MoE は 15〜40T トークンに集まる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/99375dd5ac013f/zenn/articles/99375dd5ac013f/params-vs-tokens.png)

上の図は、一次資料から集めた 156 のモデルと、Epoch AI のデータベースの 81 のモデルを、総パラメータ数と事前学習のトークン数で並べたものです。縦軸の容量は 1 トークンを約 4 バイトのテキストとして換算した値で、言語とトークナイザーで変わります。100B 級の MoE は 15〜40T トークン、つまりフィルタ後のテキストで約 60〜160 TB に集まっています。PB の桁になるのはフィルタ前のウェブのデータで、学習に入る量はその一部です。

![active パラメータあたりのトークン数は 2023 年以降に 100 を超え、MoE では 1,000 前後に並ぶ](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/99375dd5ac013f/zenn/articles/99375dd5ac013f/tokens-per-param-by-date.png)

公開値から、各段階の量の目安を並べます。100B 前後のモデルでも各段階の量がそろって公開されているわけではないので、SFT と RL はより大きいモデルの値も参考に入れています。

| 段階 | 量の単位 | 公開例 |
|---|---|---|
| 事前学習 | トークン | Llama 4 Scout で約 40T、総パラメータあたり約 370 トークン。GLM-4.5 の 23T を Air にも当てはめると約 220 トークン |
| SFT | サンプル数 | DeepSeek-V3 で 150 万件、DeepSeek-R1 で約 80 万件、Tülu 3 で約 94 万件 |
| RL | GPU 時間 | 1 万〜数十万 GPU 時間が多く、最大の公開例は数百万 GPU 時間（Reflection AI Beam、確保の換算値） |

事前学習のトークン数は、Chinchilla の目安である 1 パラメータあたり 20 トークンを大きく超えています。Llama 3 は 8B から 405B まで約 15T トークンで学習しており、405B は 15.6T と明記されています。8B は Chinchilla の最適量の約 94〜97 倍です。MoE の active パラメータあたりで見ると、Scout で約 2,350、Air に 23T を当てはめた場合で約 1,900 トークンです。これはスケーリング則の最適点ではなく、推論の費用まで考えて小さなモデルを長く学習させた結果です。

指針としてまとめると、100B 級の MoE を一から事前学習するなら、15〜40T トークンが公開例の帯で、20T を超える例が多くなっています。SFT は数十万から百万件の桁で、Tülu 3 は約 94 万件ですが、100B 級そのものの公開値は見つけられていません。技術報告に RL の記述が無い例もあり、560B の MoE の [LongCat-Flash](https://arxiv.org/abs/2509.01322) の報告は SFT とデータ合成が中心です。RL は 14 万〜74 万 GPU 時間の値が並び、512 枚なら約 11〜60 日に当たります。一方で Tülu 3 の 405B の RLVR は約 1.2 万 GPU 時間で、RL の規模はレシピによって 1 桁以上変わります。ただし学習に使った時間とクラスタを確保していた時間が混ざっているので、幅の上の側は多めに出ています。継続事前学習では、[Llama 3.3 Swallow 70B](https://aws.amazon.com/blogs/machine-learning/training-llama-3-3-swallow-a-japanese-sovereign-llm-on-amazon-sagemaker-hyperpod/) が SageMaker HyperPod の p5.48xlarge 32 台、H100 の 256 枚で、314B トークンを 16 日 6 時間かけて学習しています。

前の節で H800 相当の 1.33M GPU 時間とした GLM-4.5-Air の形の計算量 $6 \times 12 \times 10^9 \times 23 \times 10^{12} \approx 1.66 \times 10^{24}$ FLOP は、B200 では次のようになります。attention を除き、中断の無い $A = 1$ の理想で計算すると、MFU 35 % なら約 58 万 GPU 時間で、p6-b200 64 台の 512 枚なら約 48 日です。MFU が 30 % なら 56 日、40 % なら 42 日です。長い系列の段階があればその分の attention が加わり、中断があればさらに延びます。

この記事は LLM に絞っています。動画や世界モデルでは、学習データを時間数や本数で報告するのが普通で、[NVIDIA Cosmos](https://arxiv.org/abs/2501.03575) は 1 万枚の H100 で 3 か月、[TwelveLabs](https://www.twelvelabs.io/blog/dankim-marengo-research-interview) は扱う映像のデータが数 PB の規模だとインタビューで述べており、データの前処理とストレージの比重が LLM よりずっと大きくなります。

RL の量は、トークン数ではなく、プロンプト数、1 つのプロンプトから作る回答の数、回答の長さ、step 数の積で決まります。この積が生成するトークンの総量を決め、計算量では小さい rollout が、同期型の構成では時間の大半を占めます。事前学習の式のように GPU 時間へ直す前に、pilot で rollout の時間を測ることになります。

## 100B 級の構成の判断軸

100B 級のモデルを AWS で学習するおすすめの構成を聞かれたら、まず次の軸を確かめます。軸どうしが絡み合うので、1 本の流れ図にはせず、台数を決める軸と、基盤を決める軸に分けて表にします。

台数を決める軸は次のとおりです。

| 判断軸 | 選択肢 | どう決めるか | 詳しく |
|---|---|---|---|
| 出発点 | 一から学習、公開された base から継続事前学習、公開された base から SFT と RL だけ | 一から学習するなら事前学習の式が予算の大半を決める。公開された base から SFT と RL だけを行うなら事前学習の行は飛ばし、RL の pilot が台数を決める | この記事の post-training の計算量の節 |
| 学習の段階 | 事前学習、継続事前学習、SFT、RL | 事前学習と継続事前学習は、トークン予算から式で台数を出す。SFT も同じ式で、ジョブが短く padding と packing の無駄が効く。RL は pilot が先 | この記事の前半 |
| モデルの形 | dense、MoE | MoE は、EP の all-to-all を NVLink の中に収められるかで選ぶ。8 GPU の p6-b200 や p6-b300 か、最大 72 GPU が 1 つの NVLink ドメインでつながる P6e-GB200 UltraServer か | [MoE の all-to-all を支える層](https://zenn.dev/tosshi/articles/a0f5ff21eed405) |
| 学習の状態の総量 | 総パラメータ数で決まる | bf16 の重みと勾配、fp32 の master と Adam の 2 つの状態をすべて GPU に置くと 1 パラメータ約 16 バイト。100B で約 1.6 TB を HBM の総量の下限の目安にし、activation は別に足す | [Building Blocks](https://huggingface.co/blog/amazon/foundation-model-building-blocks) の FSDP2 |
| 系列長と回答長 | 数 K、32K 以上 | 長いほど attention の計算量と KV が増え、1 台 2,144 GB の p6-b300 が効く | [Attention の系譜](https://littlemex.github.io/explainers/attention-series-index.html) |
| dtype | bf16、FP8、FP4 | 安定して回るレシピの dtype のピークで割る。rollout だけ FP8 にする構成もある | [GLM-4.5](https://arxiv.org/abs/2508.06471) |
| 納期と予算 | 期間、GPU 時間 | 必要 GPU は GPU 時間を納期の時間で割り、8 で割って台数にする。[Capacity Blocks for ML](https://aws.amazon.com/ec2/capacityblocks/) は 1〜64 台を最長 6 か月、最大 8 週間前まで予約できるので、最適な台数が単価だけでなく予約の単位でも変わる | この記事の事前学習の節 |

基盤を決める軸は次のとおりです。

| 判断軸 | 選択肢 | どう決めるか | 詳しく |
|---|---|---|---|
| 運用の基盤 | Slurm、Kubernetes | チームが運用できる方を選ぶ。どちらでも RL のフレームワークは動く | 次の節 |
| 障害への備え | 学習の長さと規模 | 数百 GPU で数週間なら $A$ が費用を左右する。HyperPod の自動再開や、障害時に残りのノードから状態を組み直す checkpointless training、空いた資源に合わせて規模を変える elastic training を検討する | [Building Blocks](https://huggingface.co/blog/amazon/foundation-model-building-blocks) |
| RL の配置 | colocated、disaggregated、非同期 | rollout と trainer の比率と、重み同期が NVLink と EFA のどちらを通るかで決める | [通信プリミティブ入門](https://zenn.dev/tosshi/articles/1f6589ff93dca7) |
| 報酬と環境 | 数式の検証、コードの実行、ツールを使う agent、実行しない報酬 | 実行して検証するなら、同時に動かすサンドボックスの数と CPU 時間を pilot で測り、GPU と別の CPU のノードグループを用意する。公開例では同時に 1 万から十数万の環境がある | この記事の CPU の節 |
| ストレージ | データ量、checkpoint の大きさ | 100B で optimizer の状態まで残す checkpoint は、勾配を除いて約 1.4 TB になる。FSx for Lustre で読み書きし、S3 に残す | [Building Blocks](https://huggingface.co/blog/amazon/foundation-model-building-blocks) |

確かめる順は、出発点と段階、総パラメータ数から HBM の下限、MoE なら NVLink の範囲、納期から台数、運用の基盤です。2 つの例に当てはめると次のようになります。どちらも、この記事の試算を当てた一例です。

- GLM-4.5-Air と同じ形の 106B の MoE を一から 23T トークン学習する場合は、事前学習の式が台数を決めます。試算では MFU 35 % のとき、p6-b200 の 64 台、512 枚で約 48 日です。基盤は HyperPod の Slurm か AWS PCS に FSx for Lustre を組み合わせ、自動再開で $A$ を守ります。
- 公開された 106B の base に SFT と RL をかける場合は、事前学習の行は要りません。公開例の INTELLECT-3 は、実験を含めて H200 の 512 枚を 2 か月確保し、RL にはそのうち 480 枚を使いました。rollout は座席数を見て p6-b300 も候補にし、EKS と KubeRay の上で slime や verl の pilot から始めます。

## AWS での構成

![RL の post-training は、Slurm でも Kubernetes でも、Ray の上で同じフレームワークを動かせる。土台のインスタンス、EFA、ストレージは共通である](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/99375dd5ac013f/zenn/articles/99375dd5ac013f/rl-on-aws.png)

事前学習は、Slurm のジョブとして Megatron Core や NeMo を動かすのが素直な構成です。AWS では [AWS ParallelCluster](https://github.com/awslabs/awsome-distributed-ai/tree/240279b4a8f9c12297c72ef1bee37ad3a2558884/architectures/aws-parallelcluster)、[AWS PCS](https://github.com/awslabs/awsome-distributed-ai/tree/240279b4a8f9c12297c72ef1bee37ad3a2558884/architectures/aws-pcs)、Amazon SageMaker HyperPod の Slurm がその受け皿になり、HyperPod はノードの健全性の監視とジョブの自動再開を持っています。事前学習の費用は止まっていた時間にも比例して増えるので、自動再開は $A$ を上げる手段として効きます。

RL の post-training では、[slime](https://github.com/THUDM/slime)、[miles](https://github.com/radixark/miles)、[NeMo RL](https://github.com/NVIDIA-NeMo/RL)、[verl](https://github.com/volcengine/verl) のどれも Ray で rollout と trainer を配置します。Slurm の環境でも、ジョブの中で Ray を起動すれば同じフレームワークが動き、たとえば NeMo RL は Slurm の上で Ray のクラスタを立てる手順を[文書](https://github.com/NVIDIA-NeMo/RL/blob/main/docs/cluster.md)にしています。Amazon EKS や HyperPod の EKS では KubeRay で Ray のクラスタを作り、Kueue や KAI Scheduler で複数ノードのジョブをまとめて受け入れます。[awsome-distributed-ai](https://github.com/awslabs/awsome-distributed-ai/tree/240279b4a8f9c12297c72ef1bee37ad3a2558884/examples/training) には、EKS と KubeRay で動かす [slime](https://github.com/awslabs/awsome-distributed-ai/tree/240279b4a8f9c12297c72ef1bee37ad3a2558884/examples/training/slime) と [miles](https://github.com/awslabs/awsome-distributed-ai/tree/240279b4a8f9c12297c72ef1bee37ad3a2558884/examples/training/miles)、Kubernetes 向けの [NeMo RL](https://github.com/awslabs/awsome-distributed-ai/tree/240279b4a8f9c12297c72ef1bee37ad3a2558884/examples/training/nemo-rl)、Kubernetes と HyperPod の EKS 向けの [verl](https://github.com/awslabs/awsome-distributed-ai/tree/240279b4a8f9c12297c72ef1bee37ad3a2558884/examples/training/verl) の参照実装があります。

どちらの道でも、RL で台数の見積もりに効くのは rollout と trainer の置き方です。disaggregated にすれば rollout と trainer を別のノードグループに置けるので、座席数が効く rollout を HBM の大きい p6-b300 に、trainer を別の世代に、という組み合わせも構成の上では選べます。そのとき重み同期は EFA を通るので、ノード間の帯域が step 時間の一部になります。B200 で事前学習した公開例として、[A.X K2](https://arxiv.org/abs/2608.30181) は 688B / 33B の MoE を B200 の 512 枚で約 70 日学習しています。段階で世代を分けた例として、[Arcee Trinity Large](https://www.arcee.ai/blog/trinity-large-thinking) は事前学習を B300 の 2,048 枚、post-training を H100 の 1,152 枚で行っています。

状況ごとの構成をまとめると次のとおりです。

## まとめ

事前学習は step 時間の内訳から台数を式で一次試算でき、H200 の 64 枚は B200 の 4〜6 台に置き換わる見込みで、100B 級なら 20〜40T トークンを Slurm 系の基盤で回しながら MFU と中断の時間を監視するのが仕事になります。RL の post-training は事前学習とは別に、レシピによって 1 万から数十万、最大では数百万 GPU 時間に及ぶ予算と、環境を動かす CPU の資源を立て、rollout の座席数、回答長の変化、環境の待ちで内訳が動くので、Slurm と Ray か EKS と KubeRay の上で、pilot で学習の後半の内訳を見積もってから台数を決めるのが現実的です。
