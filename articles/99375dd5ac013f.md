# はじめに

にゃーん。

:::message
この記事は、post-training の時代に LLM の学習がどのくらいの規模と計算効率で行われているのかに個人的に興味があり、主に自分向けに整理したものです。私は超大規模な事前学習も事後学習も自分で回したことがなく、その規模の実体験としてのデータは持っていません。この記事の数字は、公開された技術報告の値と、そこから式で計算した試算だけでできています。どの数字がどちらなのかは、そのつど書きます。
:::

AWS の 3 人の著者が Hugging Face に書いた「[Building Blocks for Foundation Model Training and Inference on AWS](https://huggingface.co/blog/amazon/foundation-model-building-blocks)」は、基盤モデルの学習と推論に要る部品を、下の層から順に整理したブログです。以下、このブログを Building Blocks と呼びます。Building Blocks は冒頭で、NVIDIA が「[one to three scaling laws](https://blogs.nvidia.com/blog/ai-scaling-laws/)」と呼ぶ整理を引き、LLM の性能は事前学習だけでなく、SFT や RL による post-training と、推論時の計算量でも伸びると書いています。AWS で学習と推論を動かすためのインスタンス、ネットワーク、ストレージ、クラスタの管理、ソフトウェアの構成も、Building Blocks に幅広く整理されています。Building Blocks で扱っている内容は、この記事では改めて解説しません。Building Blocks は網羅的かつ過不足なくまとまっているので、読んで前提知識をそろえてから本記事を読み進めてください。

スケーリング則が 1 本から 3 本になった中で、最近の LLM の学習が、どのくらいの規模 (GPU の枚数と GPU 時間)、どのくらいの MFU (Model FLOPs Utilization、GPU のピーク性能のうちモデルの計算に使えた割合)、どのくらいのトークン数で行われているのかを、この記事では公開された資料から整理します。ここでの学習には、RL の中で回答を生成する推論も含めます。公開された GPU 時間は GPU の世代がばらばらなので、世代の違いをそろえて比べる考え方も合わせて整理します。最後に、post-training では GPU だけでなく CPU も重要になっていることを整理します。扱う問いは次の 5 つです。

1. 最近の LLM の事前学習は、何トークンで行われているか
2. 事前学習は、どのくらいの MFU で動いているか
3. post-training は、どのくらいの規模と効率で動いているか
4. 世代の違う GPU の値は、どうそろえて比べるか
5. agentic な RL では、サンドボックスを動かす CPU が GPU に対してどのくらい要るか

集計に使ったデータとスクリプトは [GitHub](https://github.com/littlemex/distributed-ai/tree/main/investigations/2026-10-17-llm-training-compute-survey) に置いてあり、記事の数値とグラフはそこから再現できます。

# 3 本のスケーリング則

![3 本のスケーリング則は、性能を伸ばすために増やすものと、学習や推論のスループットを決める要因が違い、GPU、ネットワーク、ストレージという基盤は共通です](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/99375dd5ac013f/zenn/articles/99375dd5ac013f/three-scaling-laws.png)

事前学習では、パラメータ数 $N$ とトークン数 $D$ を増やすと損失が下がります。この関係は [Kaplan ら](https://arxiv.org/abs/2001.08361) と [Chinchilla](https://arxiv.org/abs/2203.15556) の論文が示しました。事前学習の計算量の数え方も Kaplan らの論文にあり、1 トークンあたり約 $6N$ FLOP として、学習全体を $C = 6NBS$ と書いています。$B$ は 1 batch のトークン数、$S$ は step 数で、$B \times S$ が学習したトークン数 $D$ にあたるので、$C \approx 6ND$ FLOP になります。Chinchilla の論文も同じ近似を使っています。

:::details 計算量が 6ND になる理由

重みの行列 $W$ を入力 $x$ に掛ける $y = Wx$ では、重み 1 つにつき掛け算と足し算を 1 回ずつ行うので、1 トークンあたり $2N$ FLOP かかります。これが forward の分です。

backward では、同じ大きさの行列積を 2 回行います。1 回は前の層へ勾配を返すための $\partial L / \partial x = W^\top \, \partial L / \partial y$ で、もう 1 回は重みの勾配を求める $\partial L / \partial W = \partial L / \partial y \, x^\top$ です。どちらも $2N$ FLOP なので、backward は $4N$ FLOP になります。

合わせて 1 トークンあたり $2N + 4N = 6N$ FLOP で、$D$ トークンを学習すると $6ND$ FLOP です。この数え方には、系列長に比例して増える attention の $QK^\top$ と重み付き和の計算、embedding の参照、正規化などが入っていません。全層の activation を recompute すると forward をもう 1 回行うので、GPU が実際に実行する計算は約 $8ND$ に増えます。MFU は $6ND$ のようなモデルの計算量を分子に、GPU の実行時間とピーク性能を分母にして数える効率で、recompute の分まで含めて数える効率は HFU (Hardware FLOPs Utilization) と呼んで区別します。

:::

post-training には、お手本の回答で学ぶ教師ありの微調整（SFT）と、生成した回答への報酬で重みを更新する RL があります。post-training で性能を伸ばすために増やすのは、SFT に使うデータの量と、RL に使う計算量です。推論時の計算量で性能を伸ばすために増やすのは、1 つの回答に使うトークン数や、並列に作って比べる回答の本数です。Building Blocks は、3 つの伸ばし方の違いは、主に GPU にかかる負荷の形とスケジューリングだとしています。図の中段の KV seats は、HBM に同時に置ける生成中の系列の数のことで、本文では座席数と呼びます。問い 3 の節で回答が伸びると座席数が減ることに触れ、問い 4 の節で世代による座席数の違いを計算します。

# 最近の LLM の事前学習は、何トークンで行われているか

この節は問い 1 を扱います。

![LLM のパラメータ数と事前学習のトークン数。大きいモデルほど多くのトークンで学習され、総パラメータ 100B 以上では中央値 20T です](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/99375dd5ac013f/zenn/articles/99375dd5ac013f/params-vs-tokens.png)

上の図は、一次資料から集めた 155 のモデルと、Epoch AI のデータベースのモデルか、アーキテクチャが dense か MoE か不明なモデルの 81 を、総パラメータ数と事前学習のトークン数で並べたものです。縦軸に添えた容量の目安は、1 トークンを約 4 バイトのテキストとして換算した参考値で、言語とトークナイザーで変わります。一次資料の 155 モデルを総パラメータの大きさで分けると、事前学習のトークン数は次のとおりです。

| 総パラメータ | モデル数 | 中央値 | 四分位の範囲 | 2025 年以降のモデルの中央値 |
|---|---|---|---|---|
| 10B 未満 | 60 | 6.0T | 2.5〜11T | 5.0T、14 モデル |
| 10〜100B | 54 | 8.2T | 2.1〜15T | 12T、19 モデル |
| 100B 以上 | 41 | 20T | 12〜29T | 24T、19 モデル |

一次資料の 155 モデルのうちリリースの年が記録されている 103 モデルで分けると、事前学習のトークン数の中央値は、2023 年の 1.45T、2024 年の 4.5T、2025 年の 13T、2026 年の 24.4T と、前年の 1.9〜3.1 倍ずつ増えています。事前学習のデータは、ウェブなどから集めた生のデータから、重複した文書、品質の低い文書、対象外の言語の文書を取り除いて作ります。この記事でいうフィルタ後のテキストは、こうして取り除いたあとの、学習に使うと決めたテキストのことです。トークン数をテキストの容量に直すには、1 トークンが平均で何バイトの文字にあたるかを掛けます。英語の文章では 1 トークンがおよそ 4 バイトにあたり、この値は言語とトークナイザーで変わります。総パラメータ 100B 以上の中央値の 20T トークンに 4 バイトを掛けると、約 80 TB です。これは学習で読んだ延べの量で、同じデータを複数回読んだ分も含むので、フィルタ後のテキストの大きさはこれ以下です。取り除く前の生のデータの大きさは、延べの量からは決まりませんが、たとえば [FineWeb](https://arxiv.org/abs/2406.17557) は、Common Crawl の 96 回分の収集データを絞り込んで 15T トークンのデータセットを作っています。学習データが PB の規模だと言われるのは、この絞り込む前のデータを指す場合です。

![active パラメータあたりのトークン数は 2023 年以降に 100 を超え、MoE では 1,000 前後に並びます](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/99375dd5ac013f/zenn/articles/99375dd5ac013f/tokens-per-param-by-date.png)

1 トークンの計算に使うパラメータを active パラメータと呼びます。MoE では選ばれた expert に加えて attention など毎回使う層の分も数え、dense では総パラメータと同じです。2025 年以降のモデルのうち active パラメータがわかる 48 モデルでは、active パラメータあたりの事前学習のトークン数の中央値は 745 で、Chinchilla の論文が dense のモデルで計算量に対して最適とした 1 パラメータあたり約 20 トークンの約 37 倍です。[Llama 3](https://arxiv.org/abs/2407.21783) は 8B から 405B まで約 15T トークンで学習しており、論文は推論の費用を考えて小さなモデルを最適な量より長く学習したと明言しています。

最適な量より長く学習すると、同じ損失に届くまでの計算量は、最適な配分で学習した場合より多くかかります。[Besiroglu ら](https://arxiv.org/abs/2404.10102)が Chinchilla の損失の当てはめ式を推定し直した式を使い、一次資料の dense の 68 モデルについて、実際に使った計算量と、当てはめ式が予測する同じ損失に最適な配分で届く計算量を比べました。モデルごとに求めたこの比は、中央値で 2.6 倍、四分位の範囲で 1.6〜4.1 倍で、68 モデルのうち 65 モデルは、同じ計算量で最適になる大きさよりモデルが小さい側にありました。この倍率は、モデルを最適より小さくした代わりに、事前学習で多く払っている計算量の目安です。当てはめ式は Chinchilla の論文の学習データで求めたものなので、学習データやアーキテクチャの違う最近のモデルでは、損失そのものではなく配分のずれの目安として読みます。

![MoE のモデルが 1 トークンの計算に使うパラメータの割合は、2024 年の中央値 24.2 % から 2026 年の 5.5 % へ下がっています](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/99375dd5ac013f/zenn/articles/99375dd5ac013f/moe-active-share-by-year.png)

パラメータあたりのトークン数が増える一方で、MoE のモデルでは、総パラメータのうち 1 トークンの計算に使う割合の年ごとの中央値が下がっています。事前学習のトークン数を公開している一次資料の MoE のモデルで、active パラメータを総パラメータで割った値の中央値は、2024 年の 24.2 % (5 モデル、四分位の範囲 13.4〜24.6 %)、2025 年の 9.7 % (12 モデル、5.1〜16.2 %)、2026 年の 5.5 % (14 モデル、4.6〜10.0 %) です。トークン数を公開していないモデルは入っていません。2024 年は 5 モデルだけで、2025 年と 2026 年の四分位の範囲も重なるので、確かに言えるのは、active の割合が 1 割を切る MoE が増えたことまでです。active パラメータの数え方は、embedding を含めるかどうかなどでモデルごとに少し違います。

# 事前学習は、どのくらいの MFU で動いているか

この節は問い 2 を扱います。

![事前学習では構成を決めると step 時間が安定し、GPU 時間が式で決まります。MFU の低下はそのまま GPU 時間の増加になります](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/99375dd5ac013f/zenn/articles/99375dd5ac013f/pretraining-throughput.png)

事前学習の 1 step は、系列長やバッチの構成を変えない同じ段階の中では、ほぼ同じ形の計算です。並列化の構成、dtype、recompute の範囲、系列長、バッチの大きさを決めて学習が安定すれば、step 時間はあまり動きません。そのため、事前学習に要る GPU 時間 $H$ は次の式で概算できます。

$$
H = \frac{6 N_\text{active} D}{3600 \cdot P \cdot \text{MFU} \cdot A}
$$

$P$ は GPU 1 枚のピーク性能で、単位は FLOP/s です。本来の $P$ は、学習が行列積に使う精度のピークで、FP8 で学習するなら FP8 のピークを使います。ただ、MFU を報告している論文の多くが bf16 の dense のピークを分母にしているので、この記事では公開値と比べられるように、$P$ を bf16 の dense のピークにそろえて扱います。dense は、データシートの見出しにある 2:4 の構造化 sparsity を使った場合の値ではない、という意味です。MFU は、学習が動いている間に、$6ND$ のようなモデルの計算量を基準として、GPU が理論ピークのうち学習の計算に使えた割合です。$A$ は、GPU を確保していた全体の時間のうち、故障からの復旧や checkpoint の保存で止まった時間を除いた、学習が進んでいた時間の割合です。GPU の時間単価が同じなら、MFU や $A$ が下がった分だけ事前学習の費用が増えます。たとえば MFU が 35 % から 34 % に 1 ポイント落ちると、$H$ は $35/34$ 倍、つまり 2.9 % 増えます。[Llama 3](https://arxiv.org/abs/2407.21783) の 405B の事前学習を分析した 54 日間の期間に 466 回の中断があり、$A$ は 90 % を超えたと報告されています。Blackwell 世代でも、GB300 を 6,144 枚使った [Reflection AI の Beam](https://reflection.ai/blog/introducing-beam) は、学習が進んだ時間の割合を 92.3 % と報告しており、世代による大きな差は公開値からは見えません。学習を運用するチームが、step 時間、実効の TFLOP/s から求めた MFU、計算と重ならない通信、中断と再開の時間を常に監視するのは、どれもこの式の分母を直接動かすからです。

![H100、H800、H200 で学習した 21 のモデルは、ほとんどが bf16 ピークの 10〜40 % の線の間に並びます](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/99375dd5ac013f/zenn/articles/99375dd5ac013f/compute-vs-gpu-hours.png)

公開された値からも、事前学習の効率を逆算できます。上の図は、H100、H800、H200 で学習し、トークン数と GPU 時間の両方を公開している 21 のモデルを並べたものです。PFLOP/s は 1 秒間に何千兆回の計算ができるかを表す単位で、1 PFLOP/s は 1 秒に $10^{15}$ 回です。H100 は bf16 の行列積を最大で 1 秒に約 989.5 兆回、つまり 0.9895 PFLOP/s 計算できます。H800 と H200 は H100 と同じ Hopper 世代のチップで、メモリや GPU 間の接続は違いますが、行列積の最大の速さは同じなので、3 つとも 0.9895 PFLOP/s として扱います。図の破線は、GPU がこの最大の速さの 10 %、20 %、40 % で計算し続けたとしたら、横軸の計算量を終えるのに何 GPU 時間かかるかを引いた線です。たとえば DeepSeek-V3 の計算量 $6 N_\text{active} D = 6 \times 37\text{B} \times 14.8\text{T} \approx 3.3 \times 10^{24}$ FLOP は、最大の速さの 40 % で計算し続けると約 231 万 GPU 時間、20 % なら約 461 万 GPU 時間かかります。報告値の 266 万 GPU 時間はその間にあるので、点は 20 % と 40 % の破線の間、約 35 % の位置に描かれます。点が上の破線に近いほど、同じ計算量に多くの GPU 時間を使った、つまり効率が低かったことを表します。21 モデルの $6 N_\text{active} D$ を GPU 時間と bf16 ピークで割った値は、中央値 23.9 %、四分位の範囲 14.9〜26.5 % でした。この値は attention の計算量を含まないので、attention を含めて数えた報告 MFU より低めに出ます。また、報告された GPU 時間が中断を含む場合は、$\text{MFU} \cdot A$ に対応する分だけさらに低めに出ます。

MFU を直接報告した大規模な事前学習の値は、21 モデルの逆算値の中央値 23.9 % より高く並びます。H100 で bf16 の例では、Llama 3 の 405B が 38〜43 %、[Nemotron-4 340B](https://arxiv.org/abs/2406.11704) が H100 を 1,536 枚から 6,144 枚へ増やす間に 42.4 % から 41.0 % でした。[MegaScale](https://arxiv.org/abs/2402.15627) は 175B の dense のモデルを 12,288 枚の GPU で学習し、MFU 55.2 % を報告しています。MoE では、[ERNIE 4.5](https://ernie.baidu.com/blog/publication/ERNIE_Technical_Report.pdf) が最大のモデルの事前学習で MFU 47 % を報告していますが、FP8 の混合精度で学習しており、MFU の分母の dtype は書かれていません。[MegaScale-MoE](https://arxiv.org/abs/2505.11432) は 352B の MoE を H800 の 1,440 枚で学習し、MFU 27.9〜32.5 % でした。

MFU は、FLOP の数え方と分母の dtype で値が大きく変わります。[DeepSeek-V3](https://arxiv.org/abs/2412.19437) は 37B / 671B のモデルを 14.8T トークンで、H800 の 2,664K GPU 時間で学習しました。この値から $6 N_\text{active} D$ を bf16 のピークで割ると 34.6 % ですが、DeepSeek-V3 は行列積の大半を FP8 で計算しているので、FP8 のピークで割ると 17.3 % です。attention の計算量も小さくなく、GLM-4.5-Air の 46 層、96 ヘッドの形では、causal mask で半分だけ数えても、系列長 4K で $6N_\text{active}$ の約 2 割、32K では $6N_\text{active}$ の 1.5 倍になります。

自分たちの環境で MFU を実測しておくと、GPU 時間と費用を上の式で見積もれるようになります。また、世代の違う GPU に移るときの見積もりにも使えます。問い 4 の節で扱うように、新しい世代でどれだけ速くなるかは、演算、HBM の帯域、通信のどれに時間を使っているかで決まります。今の世代で MFU と step 時間の内訳を測っておけば、ピーク性能の比だけで見積もるよりも根拠のある GPU 時間を出せます。学習中に MFU が下がったときは、設定の誤りや調子の悪いノードに早く気づく手がかりにもなります。

## 計算量の規模

post-training に使った GPU 時間や費用が、事前学習の GPU 時間や費用に比べて誤差とは言えない大きさになった例が出ています。

![公開資料から集めた post-training の GPU 時間は、報告値と確保時間からの換算値を合わせて数千から数百万まで 3 桁にわたります](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/99375dd5ac013f/zenn/articles/99375dd5ac013f/rl-gpu-hours.png)

次の表の GPU 時間には、報告値と、私が報告の枚数と期間から換算した値が混ざっています。報告値にも、学習に使った時間と、実験を含めてクラスタを確保していた時間の 2 種類があるので、値どうしを学習の計算量として直接は比べられません。

| モデル | 公開された内容 | post-training の GPU 時間 | 報告か換算か | 事前学習との比 |

| [DeepSeek-V3](https://arxiv.org/abs/2412.19437) | post-training の GPU 時間 | H800 で 5K | 報告 | 事前学習の GPU 時間の 0.19 % |

post-training と事前学習の規模の比を出せるのは 5 例 (DeepSeek-V3、DeepSeek-R1、DeepSeek-V3.2、Olmo 3、Beam) で、比の定義は GPU 時間か費用か、報告値か換算値か、下限かが例ごとに違います。値は 0.19 %、約 5 %、10 % 超 (V3.2)、約 12 % (Olmo 3)、170 % 超 (Beam) で、V3.2 の値は下限なので並びは確定しませんが、真ん中は V3.2 の 10 % 超か Olmo 3 の約 12 % で、どちらも 1 割前後です。DeepSeek の 3 つの報告 (V3 の 0.19 %、R1 の約 5 %、V3.2 の 10 % 超) は分子と分母の定義がそれぞれ違い、V3 の値は同じ base から作った R1 の RL を含まないので、ここから時間とともに増えたとは読めません。それでも、同じ組織の報告の中に、post-training の費用が事前学習の 1 割を超えた例が出ています。学習時間の報告値とクラスタの確保時間からの換算値を混ぜた上の図の 10 例では、RL の GPU 時間は中央値約 11 万 GPU 時間、範囲 3 千〜706 万 GPU 時間です。SFT のデータの量は、数十万から百万件の桁で、推論の能力を蒸留で移す例では DeepSeek-V3 が 150 万件、DeepSeek-R1 が約 80 万件、一般的な指示チューニングの例では [Tülu 3](https://arxiv.org/abs/2411.15124) が約 94 万件です。ごく少量のデータで微調整する例には、[LIMA](https://arxiv.org/abs/2305.11206) や [s1](https://arxiv.org/abs/2501.19393) のように 1,000 件程度のものもあります。

RL の計算量と性能の関係にも、スケーリング則が見つかりつつあります。[The Art of Scaling Reinforcement Learning Compute for LLMs](https://arxiv.org/abs/2510.13786) は 40 万 GPU 時間を超える実験で、RL の計算量と性能の関係がシグモイドの曲線に乗り、小さな実験から 10 万 GPU 時間の 1 本の学習の性能を外挿できたと報告しています。性能の到達点はレシピで決まり、損失の集計や正規化、カリキュラム、off-policy の方式は、主に到達までの効率を変えるとしています。この論文が示す RL の計算量と性能の曲線は、横軸が GB200 の GPU 時間なので、GPU の世代が変われば、1 GPU 時間でできる仕事の量も変わります。そのため、問い 4 の節で扱う世代のそろえ方がここでも要ります。

## RL の時間の内訳

![RL の 1 step では、rollout が計算量の割合より長い時間を使い、trainer が計算量の大半を使います。内訳は構成と学習の進み方で動きます](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/99375dd5ac013f/zenn/articles/99375dd5ac013f/rl-step.png)

RL の 1 step には、性質の違う 2 つの主な仕事が入ります。rollout は、推論エンジンで回答を生成する仕事です。trainer は、回答に付いた報酬から勾配を計算して重みを更新する仕事です。trainer が更新した重みを rollout 側へ配る処理を、重み同期と呼びます。仕組みは「[分散 RL post-training の通信プリミティブ入門](https://zenn.dev/tosshi/articles/1f6589ff93dca7)」で図にしました。

rollout が RL の 1 step に占める割合は、計算量で数えた場合と時間で数えた場合で大きく違います。計算量で数えると、生成したトークンに対して、active パラメータを $N$ として、rollout の $2N$、trainer が学習の前に古い重みで確率を計算し直す $2N$、学習の $6N$ がかかるので、rollout は計算量の約 20 % です。この数え方には、プロンプトの処理、attention、参照モデルや報酬モデルの計算が入っていません。[INTELLECT-2](https://arxiv.org/abs/2505.07291) も学習と推論の FLOP の比を 4.5 倍と報告しており、rollout は計算量の約 18 % にあたります。

![rollout が RL の step の時間に占める割合は、実測では 22〜87 % に散らばり、論文の一般的な記述では 90 % 以上とするものもあります](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/99375dd5ac013f/zenn/articles/99375dd5ac013f/rollout-share.png)

一方、時間で数えた rollout の割合は、上の図の実測の 10 の設定で中央値 68.5 %、範囲 22〜87 % でした。同期の方式では step の経過時間に対する割合、非同期の方式では処理ごとの時間の内訳で、分母はそろっていません。[Seer](https://arxiv.org/abs/2511.14617) は、Moonlight、Qwen2-VL-72B、Kimi-K2 の 3 つの RL の負荷で rollout が反復の時間の 63〜87 % を占めたと報告しています。短い回答の設定では、[DistFlow](https://arxiv.org/abs/2507.13833) が 31.8 %、比較の相手の verl が 21.9 % です。完全に非同期にした [MiMo-V2.6](https://arxiv.org/abs/2610.11959) の Pro は、RL の時間を rollout 43.8 %、学習 43.5 %、採点 12.7 % と報告しています。図の白抜きの点は、rollout の時間比率について論文の導入部などにある一般的な記述や、その上限と下限です。decode は 1 回に各系列を 1 トークンずつしか進めないのに、その 1 回ごとに重みと KV を HBM から読み出すので、trainer の行列積と比べて計算量のわりに時間がかかります。

rollout の時間は、最後まで終わらない少数の長い回答にも引っ張られます。Seer は、メモリが厳しい負荷では、最後の 10 % のリクエストが rollout の時間の最大 50 % を使うと報告しています。さらに、回答の長さは学習の途中で伸びます。[DeepSeek-R1](https://arxiv.org/abs/2501.12948) の報告では、R1-Zero の回答の平均長は RL の進行とともに伸び続けました。回答が伸びれば rollout と trainer の処理はどちらも増え、KV が膨らんで同時に置ける系列が減るので、rollout の割合は増えやすくなります。事前学習の時間の内訳が構成でほぼ決まるのに対し、RL の時間の内訳は、回答の長さという学習中の方策の振る舞いでも動きます。

## RL の MFU と GPU の枚数

私が調べた RL のシステム論文と技術報告の 21 本には、RL 全体の MFU の値がありませんでした。推論側だけの実測なら [Olmo 3](https://arxiv.org/abs/2512.13961) にあり、A100 の 2 ノードを学習 1 ノード、推論 1 ノードに分けた小さなベンチマークの推論側で、MFU が 1.01 %、HBM 帯域の利用率が 43.2 % でした。この測定では、演算のピークに対する利用率は低くても、HBM の帯域の利用率はそれより高くなっています。Olmo 3 の本番の 32B の RL は、推論に H100 の 20 ノード、学習に 8 ノードを使い、学習側は時間の 75 % を rollout のデータを待って過ごしたと書いています。

RL に使う GPU の枚数は、事前学習と比べて少ない例も多い例もあります。事前学習と RL の両方の枚数を公開している 4 例で、RL と事前学習の枚数の比は中央値 0.41、範囲 0.22〜1.71 でした。DeepSeek は事前学習が 2,048 枚、R1 の RL が 512 枚で、Olmo 3 は事前学習が最大 1,024 枚、RL が 224 枚です。[Arcee AI の Trinity Large Thinking](https://www.arcee.ai/blog/trinity-large-thinking) は、事前学習は Trinity Large と共通の B300 の 2,048 枚で、post-training の RL は H100 の 1,152 枚です。Beam は事前学習が 6,144 枚、RL が 1 万 500 枚です。推論と学習の GPU の配分は、[AReaL](https://arxiv.org/abs/2505.24298) で 75 対 25、INTELLECT-3 で 44 対 16 ノード、Olmo 3 で 20 対 8 ノードと、推論側を 2.5〜3 倍にする例が並びます。同じモデルの RL を、事前学習と同じ枚数で回した場合と少ない枚数で回した場合とで、学習の期間や到達する性能を比べた公開値は見つかりませんでした。

# 世代の違う GPU の値は、どうそろえて比べるか

この節は問い 4 を扱います。

## 実効倍率と移送係数

![H200 から B200 では、演算、HBM 帯域、NVLink はそれぞれ違う倍率で速くなるが、1 台あたりの EFA の帯域と待ち時間はほぼ変わりません。数字は単純なモデルから出したものです](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/99375dd5ac013f/zenn/articles/99375dd5ac013f/h200-to-b200.png)

公開された GPU 時間は、H100、H800、H200、B200、GB300 など、さまざまな世代の GPU で測られています。世代の違う値を比べたり、ある世代の値から別の世代の GPU 時間を見積もったりするには、新しい世代の GPU 1 枚が古い世代の GPU 1 枚の何倍の仕事をするかを表す実効倍率 $S$ が要ります。$S$ は、古い世代の step 時間を、演算・HBM 帯域・通信・待ちなど何に律速されているかで区分 $i$ に分け、その割合を $f_i$、それぞれの区分が新しい世代で何倍速くなるかを $r_i$ として合成します。

![H200 の 1 step を 100 として中身に分け、それぞれを B200 での速くなり方で割ると、合計は 60 になります。B200 は 1.66 倍速く、カタログのピーク比 2.27 倍のうち 73 % が実際に生きます](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/99375dd5ac013f/zenn/articles/99375dd5ac013f/speedup-walkthrough.png)

上の図は、H200 の 1 step の時間を 100 として、その中身を演算 60、メモリの読み出し 25、ノード間の通信 10、待ち 5 に分けた例です。B200 では演算が 2.27 倍速くなるので 60 が 26 に、メモリの読み出しは 1.60 倍速くなるので 25 が 16 に縮みますが、通信と待ちは速くならないので 10 と 5 のままです。合計は 57 で、新しい世代ではソフトウェアがまだこなれていない分を 0.95 として割ると 60 になります。つまり B200 は H200 の 100 ÷ 60 = 1.66 倍速く、これが $S$ です。カタログのピーク比 2.27 倍のうち実際に生きる割合は 1.66 ÷ 2.27 = 0.73 で、これが $k$ です。H200 で 100 万 GPU 時間かかった学習は、B200 では 100 万 ÷ 1.66 で約 60 万 GPU 時間になります。同じ計算を式で書くと次のとおりです。

$$
S = \frac{\eta}{\sum_i f_i / r_i}, \qquad k = \frac{S}{r_\text{peak}}, \qquad H_\text{新} = \frac{H_\text{旧}}{S} = \frac{H_\text{旧}}{r_\text{peak} \cdot k}
$$

$\eta$ は、古い世代と比べた新しい世代でのソフトウェアの成熟度で、根拠のない仮の値としてここでは 0.95 と置きます。$r_\text{peak}$ は新しい世代と古い世代の bf16 dense のピーク性能の比で、$k$ はそのピーク比のうち実際に生きる割合です。この記事では $k$ を移送係数と呼びます。$k = 1$ ならピーク比どおりに速くなり、$k$ が小さいほどピーク比から目減りします。$k$ が 1 を超える場合は、ピーク比より速くなります。$f_i$ の通信には、計算と重ならない分だけを入れます。演算が速くなると、古い世代で計算の裏に隠れていた通信が新しい世代では表に出るので、この式は楽観側に外れやすくなります。

NVIDIA のデータシートと [P5](https://aws.amazon.com/ec2/instance-types/p5/)、[P6](https://aws.amazon.com/ec2/instance-types/p6/) の製品ページから、p5en.48xlarge の H200 と p6-b200.48xlarge の B200 を比べると次のようになります。

| 項目 | H200 | B200 | B200 の H200 に対する比 |
|---|---|---|---|
| bf16 dense のピーク | 0.9895 PFLOP/s | 2.25 PFLOP/s | 2.27 |
| HBM の容量、データシート | 141 GB | 180 GB | 1.28 |
| HBM の帯域 | 4.8 TB/s | 7.7 TB/s | 1.60 |
| NVLink、GPU 1 枚あたり | 900 GB/s | 1.8 TB/s | 2.0 |
| EFA、1 台あたり | 3,200 Gbps、第 3 世代 | 3,200 Gbps、EFAv4 | 1.0 |

B200 の演算は H200 の 2.27 倍になる一方で、HBM の帯域は 1.60 倍にとどまります。演算律速と帯域律速の境目になる算術強度は、ピーク値から計算すると H200 の 206 FLOP/byte から B200 の 292 FLOP/byte へ上がるので、同じ算術強度で動く区間は B200 のほうが帯域の制約を受けやすくなります。Building Blocks の表は B200 の帯域を 8 TB/s としていますが、これは GB200 の値で、8 GPU のサーバーに載る B200 のデータシートの値は 7.7 TB/s です。

p5en の 8 台、64 GPU の事前学習を p6-b200 に置き換える場合に、例として 4 通りの内訳を当てると次のようになります。各区間の倍率は、演算 2.27、HBM 1.60、ノード間通信 (EFA) 1.0、データの読み込みや同期などの待ち 1.0 と置き、ノード内の NVLink の通信は計算と重なるとみなして区間に入れていません。

| p5en の step 時間の内訳 | $k$ | 同じ期間で終えるのに要る B200 | p6-b200 の台数 |
|---|---|---|---|
| すべて演算律速 | 0.95 | 30 枚 | 4 |
| 演算 80 %、HBM 10 %、ノード間通信 5 %、待ち 5 % | 0.81 | 35 枚 | 5 |
| 演算 60 %、HBM 25 %、ノード間通信 10 %、待ち 5 % | 0.73 | 39 枚 | 5 |
| 演算 50 %、HBM 20 %、ノード間通信 25 %、待ち 5 % | 0.65 | 44 枚 | 6 |

実測からも $k$ を出せます。[MLPerf Training v6.0](https://mlcommons.org/2026/06/mlperf-training-v6-0/) の結果の表で SXM 型の H200 と B200 を 16 枚どうしで比べると、B200 は H200 より Llama 3.1 8B の事前学習で 2.34 倍、Llama 2 70B の LoRA で 1.96 倍速く終わっています。NVIDIA の [Megatron Bridge の性能表](https://docs.nvidia.com/nemo/megatron-bridge/latest/performance-summary-archive.html)では、FP8 の TFLOP/s/GPU が H100 から B200 で Llama 3.1 405B は 2.03 倍、DeepSeek-V3 は 1.65 倍です。この 4 つをピーク比 2.27 (H100 と H200 は bf16 のピークが同じ) で割った $k$ は、中央値 0.88、範囲 0.73〜1.03 でした。提出した会社、ソフトウェアの版、GPU の枚数がそれぞれ違う測定なので、目安として使います。

## アーキテクチャと座席数

$f_i$ と $r_i$ は、モデルのアーキテクチャにも左右されます。影響が大きいのは、MoE で 1 トークンが使う expert の割合と、attention が 1 トークンあたりに持つ KV キャッシュの大きさです。GQA と MLA は、通常の multi-head attention と比べて 1 トークンあたりに保持する KV を小さくする方式で、sliding window は直近の一定の長さだけを見る方式です。次の表は、各モデルの config から bf16 で計算した、全層の合計の KV の大きさです。

| モデル | 総 / active | expert 数 / 選ぶ数 | attention | KV、1 トークン | 32K トークンの 1 本 |
|---|---|---|---|---|---|
| [GLM-4.5-Air](https://huggingface.co/zai-org/GLM-4.5-Air) | 106B / 12B | 128 / 8 | GQA、46 層 | 184 KiB | 5.75 GiB |
| [gpt-oss-120b](https://huggingface.co/openai/gpt-oss-120b) | 117B / 5.1B | 128 / 4 | GQA、36 層の半分が sliding window | 36 KiB | 1.13 GiB |
| [DeepSeek-V3](https://huggingface.co/deepseek-ai/DeepSeek-V3) | 671B / 37B | 256 / 8 | MLA、61 層 | 68.6 KiB | 2.14 GiB |
| [Llama 3.1 70B](https://arxiv.org/abs/2407.21783) | 70B / 70B | dense | GQA、80 層 | 320 KiB | 10.0 GiB |

MoE では、expert 1 つの行列積に流れるトークンは、層に入るトークン全体の「選ぶ数 / expert 数」に細ります。GLM-4.5-Air なら $8/128 = 1/16$ なので、B200 の境目の 292 FLOP/byte に届くには、1 回の expert の行列積に約 292 トークン、MoE 層全体ではその 16 倍の約 4,700 トークンをまとめる必要があります。事前学習の大きな micro-batch なら約 4,700 トークンに近づけますが、rollout の decode では 1 回の forward で各系列が 1 トークンずつしか進みません。そのため、MoE 層に入るトークン数は同時に生成している系列の数とほぼ同じになり、後の表の座席数 (1 台 130〜590) ではまず届きません。そのため、decode が中心で座席数がこの程度という仮定では、rollout の expert の計算は帯域律速に近く、rollout の $r_i$ は演算の比の 2.27 より帯域の比の 1.60 に近いと考えられます。prefill が多い局面や回答の短い負荷では、この見方は当てはまりません。

rollout の速さは、HBM に同時に置ける生成中の系列の数、この記事でいう座席数にも左右されます。GLM-4.5-Air の bf16 の重み約 212 GB を 1 台の 8 GPU に均等に分けて置き、1 台の HBM の 90 % から重みを引いた残りをすべて KV に使い、全系列が 32K トークンに達したとして計算すると、座席数は次のとおりです。HBM の容量は AWS の製品ページの 1 台あたりの値です。

| 1 台 | KV に使える HBM | bf16 の座席数 | 重みと KV を FP8 にした座席数 | bf16 の座席数の H200 に対する比 |
|---|---|---|---|---|
| p5en、H200 8 枚 | 803 GB | 130 | 294 | 1.0 |
| p6-b200、B200 8 枚 | 1,077 GB | 174 | 383 | 1.34 |
| p6-b300、B300 8 枚 | 1,718 GB | 278 | 590 | 2.14 |

座席数は HBM の容量から重みの分を引いた残りで決まり、上の表の計算では B200 の座席数は H200 の 1.34 倍です。decode の 1 step の速さは帯域の比の 1.60 倍に近づいても、同時に生成できる系列の数は 1.34 倍しか増えません。rollout の大部分の倍率を帯域の比の 1.60 か座席数の比の 1.34、遅い回答の裾の倍率を帯域の比の 1.60、確率の再計算と学習の倍率を 2.0、重み同期の倍率を 1.5、報酬と環境の倍率を 1.0 と置きます。RL の step 時間の内訳を rollout の大部分 45 %、遅い回答の裾 25 %、確率の再計算と学習 20 %、重み同期 5 %、報酬と環境 5 % とすると、RL の $k$ は 0.62〜0.67 で、事前学習の仮定の例の 0.65〜0.95 の下端と同じくらい、実測の中央値 0.88 よりは低めに出ます。RL の時間の内訳は学習中に動くので、この $k$ は学習のどの時点の内訳を使うかでも変わります。

# agentic な RL では、サンドボックスを動かす CPU が GPU に対してどのくらい要るか

この節は問い 5 を扱います。

agentic な RL では、GPU の外で動く環境の比重が増えています。RL の中でモデルがコードを実行し、ツールを呼び、テストを回すたびに、CPU の上のサンドボックスが結果を返すまで、その系列の生成は止まります。公開された 4 例では、サンドボックスと環境を同じ数として数え、Kimi K2 の「1 万を超える」を 1 万として数えると、同時に動かす数は中央値約 2.6 万、範囲 1 万〜17 万でした。[Kimi K2](https://arxiv.org/abs/2507.20534) は Kubernetes の上で 1 万を超えるサンドボックスを同時に動かし、[Qwen3-Coder](https://qwenlm.github.io/blog/qwen3-coder/) は 2 万の環境、[LongCat-Flash-Thinking-2601](https://arxiv.org/abs/2601.16725) は 3 万 2,000 の環境を並列に動かしたと報告しています。[Reflection AI の Beam](https://www.reflection.ai/beam) は、GB300 の 1 万 500 枚の RL で、同時に最大 17 万のサンドボックスを動かしました。どの例も、CPU のコア数と GPU の比は公開していません。近い開示として、[DeepSeek-V4.1-Flash](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash) の技術報告は、サンドボックスを GPU の学習のノードの外に置き、1 ノードあたり 2,500 を超えるコンテナを動かせたと書いています。

サンドボックスの結果を他の系列の生成で隠せない場合、その待ち時間は GPU の効率を直接下げます。[SkyRL-Agent](https://arxiv.org/abs/2511.16108) は H100 の 16 枚で SWE の agent を学習し、回答の生成と環境の実行をまとめて待つ方式ではサンドボックスの初期化と報酬の計算の間に GPU の利用率が大きく落ち、生成と環境を流れ作業で重ねる方式では利用率が約 90 % で安定して 1.55 倍速くなったと報告しています。逆に、環境が GPU を待つ時間も長く、[Kimi K3](https://github.com/MoonshotAI/Kimi-K3/blob/main/k3_tech_report.pdf) は、サンドボックスを [Firecracker](https://firecracker-microvm.github.io/) の microVM (軽量の仮想マシン) として動かし、モデルの推論の結果を待つ時間がサンドボックスの寿命の最大 98 % になり得るので、その間はサンドボックスを一時停止して CPU とメモリを使わないようにしています。報酬の作り方でも CPU の量は変わり、[SWE-RL](https://arxiv.org/abs/2502.18449) はコードを実行せず、正解との差分の似ている度合いを報酬にして、サンドボックスを使わずに済ませています。

Firecracker は AWS が開発したオープンソースの仮想化技術で、Amazon EKS でも、EC2 のベアメタルのインスタンスをワーカーノードにして Kata Containers を使うと、Pod を Firecracker の microVM として動かせます ([AWS のブログ](https://aws.amazon.com/blogs/containers/enhancing-kubernetes-workload-isolation-and-security-using-kata-containers/))。agentic な RL では、GPU のノードで学習と推論を回しながら、CPU のノードで数万のサンドボックスを立ち上げ、止め、再開します。同じ Kubernetes のクラスタの中で、GPU と CPU に資源を柔軟に割り当てられることも、RL の時代には大事になっています。

CPU とサンドボックスの構成を変えずに GPU だけを新しい世代にしても、CPU の上の環境の時間は速くなりません。環境の処理が GPU の処理と重ならない場合、GPU の区間が縮むほど、RL の step 時間に占める環境の割合は大きくなります。

# 3 本のスケーリング則のもとで自社の学習の資源を見積もる

スケーリング則が 3 本になると、自社で学習を計画するときに見積もるものも増えます。事前学習の GPU に加えて、post-training の GPU、世代の違う GPU への換算、RL のサンドボックスを動かす CPU まで要ります。ここでは、ここまでに整理した公開値を仮の値として、この 4 つを順に見積もる手順を示します。値は自社のモデルと学習の条件に置き換えて使ってください。

## 事前学習の GPU 時間と枚数

事前学習の GPU 時間 $H_\text{pre}$ と、期間 $T$ 時間で終えるのに要る GPU の枚数 $G$ は、次の式で見積もります。枚数を変えても GPU 1 枚あたりの効率が変わらないと仮定した概算です。$E$ は MFU と $A$ の積で、問い 2 の節の 21 モデルの中央値 0.24 か、大規模な学習の MFU の報告値 0.40 前後に $A$ の 0.9 を掛けた 0.36 を仮に置きます。0.24 は H100、H800、H200 の公開値から逆算した値で、B200 で測った値ではありません。

$$
H_\text{pre} = \frac{6 N_\text{active} D}{3600 \cdot P \cdot E}, \qquad G = \frac{H_\text{pre}}{T}
$$

例として、総パラメータが 100B 以上、active パラメータが 20B の MoE のモデルを考え、active パラメータ $N_\text{active} = 20 \times 10^9$、トークン数 $D = 20 \times 10^{12}$ を置きます。$D$ は、問い 1 の節の総パラメータ 100B 以上の中央値です。GPU を B200 として $P = 2.25 \times 10^{15}$、期間を 60 日として $T = 1{,}440$ 時間とすると、次のようになります。

| $E$ | $H_\text{pre}$ | $G$ | 8 枚の台数 |
|---|---|---|---|
| 0.24、21 モデルの中央値 | 約 123 万 GPU 時間 | 約 857 枚 | 108 台 |
| 0.36、大規模な学習の MFU 0.40 に $A = 0.9$ を掛けた値 | 約 82 万 GPU 時間 | 約 572 枚 | 72 台 |

## post-training の GPU 時間

post-training の GPU 時間 $H_\text{post}$ は、事前学習の GPU 時間に比 $\rho$ を掛けて見積もります。

$$
H_\text{post} = \rho \cdot H_\text{pre}
$$

$\rho$ に、仮の値として 0.10 を置きます。問い 3 の節の 5 例の真ん中は 1 割前後ですが、定義の違う値の並びで、GPU 時間の比として測った値ではありません。$\rho = 0.10$ とすると、上の例の $E = 0.24$ では $H_\text{post}$ は B200 で約 12 万 GPU 時間です。公開された RL の GPU 時間の中央値の約 11 万 GPU 時間 (おもに H800 や H100 の値) と桁は重なりますが、$\rho$ を仮に選んでいるので、見積もりの確かめにはなりません。公開例の比は、定義が違うまま 0.0019 から 170 % 超まで広がります。見積もりの区間ではありませんが、$\rho$ の置き方でどれだけ動くかを見るために $\rho = 0.0019$ を置くと $H_\text{post}$ は約 2 千 GPU 時間、1.7 を置くと約 210 万 GPU 時間で、3 桁違います。

## 世代をまたいだ換算

古い世代の GPU で測った GPU 時間 $H_\text{旧}$ を、新しい世代の GPU 時間に直すには、問い 4 の節の式を使います。

$$
H_\text{新} = \frac{H_\text{旧}}{r_\text{peak} \cdot k}
$$

H200 で 100 万 GPU 時間かかった学習を B200 に直す場合、$r_\text{peak} = 2.27$ と、実測から出した $k$ の中央値 0.88 を置くと約 50 万 GPU 時間です。$k$ の範囲 0.73〜1.03 を置くと、約 43 万〜60 万 GPU 時間になります。同じ 100 万 GPU 時間が RL だった場合は、仮定した時間内訳からの試算の $k$ の 0.62〜0.67 を置くと、約 66 万〜71 万 GPU 時間です。

## RL の CPU

RL で同時に動かすサンドボックスの数 $S$ と、必要な vCPU の数 $V$ は、次の式で見積もります。

$$
S = s \cdot G_\text{RL}, \qquad V = S \cdot c, \qquad G_\text{CPU} = \frac{V}{v}
$$

$G_\text{RL}$ は RL に使う GPU の枚数、$s$ は GPU 1 枚あたりの同時のサンドボックスの数、$c$ はサンドボックス 1 つあたりの vCPU、$v$ は CPU のインスタンス 1 台あたりの vCPU、$G_\text{CPU}$ は必要な CPU のインスタンスの台数です。GPU の枚数と同時サンドボックスの最大数の両方を公開しているのは Beam だけで、$s = 170{,}000 / 10{,}500 \approx 16$ です。$c$ には、[MiniMax-M2](https://arxiv.org/abs/2605.26494) が Terminal-Bench 2.0 の評価でサンドボックス 1 つに割り当てた 8 vCPU を置きます。どちらも 1 例だけの値で、8 vCPU は RL ではなく評価のときの割り当てなので、桁を見るための仮の値です。RL に GPU を $G_\text{RL} = 512$ 枚使い、$v = 192$ とすると、$S$ は約 8,200、$V$ は約 6 万 5,500 vCPU、CPU のインスタンスは約 341 台です。GPU の 8 枚のインスタンスの 64 台より、CPU のインスタンスの台数のほうが 5 倍以上多くなります。

# まとめ

はじめにの 5 つの問いに、公開値の統計で答えます。

| 問い | 答え |
|---|---|
| 事前学習のトークン数 | 総パラメータ 100B 以上で中央値 20T。2025 年以降のモデルは active パラメータあたり中央値 745 トークンで、Chinchilla の目安の約 37 倍 |
| 事前学習の MFU | H100、H800、H200 の 21 モデルの逆算値で中央値 23.9 %。大規模な学習の報告値は dense で 38〜55 % |
| post-training の規模 | 事前学習との比は定義の違う 5 例で真ん中が 1 割前後。RL の GPU 時間は中央値約 11 万。rollout は時間の中央値 68.5 % を占める |
| 世代のそろえ方 | ピーク比に移送係数 $k$ を掛ける。H200 から B200 への実測の $k$ は中央値 0.88 |
| RL の CPU | 同時のサンドボックスは中央値約 2.6 万。CPU と GPU の比の公開値はなく、仮の値の試算では CPU のインスタンスが GPU のインスタンスの 5 倍以上 |
