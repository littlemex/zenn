## はじめに

「[NCCL 2.32.3 でロードマップはどう実装されたか](https://zenn.dev/tosshi/articles/9ab10d37f33ced)」で、NCCL が MPS と MLOPart の組み合わせに対応したことに触れました。MPS そのものは新しい機能ではなく、今の vLLM でも試せます。Databricks は「[NVIDIA MPS で小規模 LLM をスケールする](https://www.databricks.com/jp/blog/scaling-small-llms-nvidia-mps)」で、H100 の上で 3B 未満のモデルなら MPS で 50% を超えてスループットが伸びたと報告しています。

この記事では、家庭用の RTX 4090 と同じ 24 GB のメモリを持つ L4 1 枚で、別の GPU と別の負荷のもとで MPS の効果を確かめます。Databricks の測定は、短い文脈とバッチサイズ 1024 などの条件つきです。今回の条件での答えは、次のとおりです。

| 問い | L4、同じモデル 2 つ、CUDA graph ありでの答え |
|---|---|
| 2 つのエンジンを載せるなら、MPS を使うほうが速いか | 速い。MPS 無しの時間分割より 11〜15% 速い |
| 同じ負荷を 1 つのエンジンで受けるのと、2 つに分けるのとではどちらが速いか | 1 つのほうが速い。MPS で 2 つに分けても、1 つの 0.60〜0.88 倍だった |

## MPS 無しの共有: GPU は時間分割で使う

![MPS 無しでは違うプロセスのカーネルは同時に走れない。MPS なら空いた SM に相手のカーネルが入る](/images/f4f81e1c20106d-timeline.png)

1 枚の GPU を 2 つのプロセスで使うと、ふつうは時間分割で動きます。つまり、プロセスが順番に GPU を使います。NVIDIA の [MPS のドキュメント](https://docs.nvidia.com/deploy/mps/architecture.html)は「Work launched to the compute engine from work queues belonging to different CUDA contexts cannot execute concurrently」と書いています。プロセスごとに別の CUDA のコンテキストを持つので、片方のカーネルが SM の一部しか使わなくても、残りの SM をもう片方が使えません。

MPS は、この制約を外すための仕組みです。違うプロセスのカーネルが同じ時間に別の SM で走れるので、1 つのプロセスでは埋まらない GPU の空きを、もう 1 つのプロセスが使えます。

## MPS の仕組み

![MPS は制御デーモンとサーバとクライアントの 3 つでできている。クライアントは仕事を GPU に直接出す](/images/f4f81e1c20106d-arch.png)

MPS は 3 つの部品でできています。

- **制御デーモン**の `nvidia-cuda-mps-control` は、MPS のサーバを立ち上げ、クライアントの接続を受け付けます。
- **サーバ**の `nvidia-cuda-mps-server` は、クライアントが共有する GPU の資源を取りまとめます。
- **クライアント**は、CUDA を使うふつうのプロセスです。CUDA のライブラリ libcuda が、制御デーモンが動いていると自動で MPS のクライアントとしてふるまいます。vLLM のコードは何も変えなくて済みます。

部品どうしは、[既定では](https://docs.nvidia.com/deploy/mps/appendix-environment-variables.html) `/tmp/nvidia-mps` に置いた名前付きパイプと UNIX ソケットでつながります。今回の測定でも、制御デーモンのログに次の行が残っていました。1 つ目のエンジンのプロセスが来たときに制御デーモンがサーバを立ち上げ、40 秒後に別のプロセスが同じサーバにつながっています。スクリプトは 2 つのエンジンを 40 秒ほどずらして起動しているので、2 つ目のエンジンだと見ています。

```text
[Control  1768] NEW CLIENT 1806 from user 0: Server is not ready, push client to pending list
[Control  1836] Starting new server 1836 for user 0
[Control  1768] NEW SERVER 1836: Ready
...
[Control  1768] NEW CLIENT 1983 from user 0: Server already exists
```

Volta 以降の GPU では、クライアントはサーバを経由せずに、仕事を GPU に直接出します。ドキュメントには「MPS clients submit work directly to the GPU without passing through the MPS server」とあり、サーバが受け持つのは、同時に動かすために共有が要る残りの資源だけです。また「Each MPS client owns its own GPU address space」とあり、クライアントはそれぞれ自分のアドレス空間を持つので、相手のメモリを読み書きできません。

**ただし、障害は切り離しきれません。** ドキュメントは「a fatal fault from one client may bring down a different user's client that shares any GPU with the faulting client」と書いています。別のユーザーのクライアントまで止まりうるので、同じサーバを共有する今回のようなエンジンどうしは、1 つの故障にほかも巻き込まれる前提で使うのが安全です。

クライアントが使えるスレッドの割合は `CUDA_MPS_ACTIVE_THREAD_PERCENTAGE` で、CUDA で確保できる GPU メモリの上限は `CUDA_MPS_PINNED_DEVICE_MEM_LIMIT` で制限できます。どちらも上限であり、SM やメモリを物理的に分ける設定ではありません。

## 測り方

測定は [mps_bench.sh](https://github.com/littlemex/distributed-ai/tree/d2c78ff01c6ac99662c4958403b7342a8b8efe3f/2026-09-25-mps-small-llm-vllm) の 1 本のスクリプトで行いました。Volta 以降の GPU が 1 枚あり、NVIDIA のドライバと vLLM が入っていて、モデルを 2 つ載せられるメモリがあれば、どこでも動きます。

| モード | エンジンの数 | GPU の分け方 |
|---|---|---|
| single | 1 | vLLM の `gpu-memory-utilization` を 0.84 にした 1 つのエンジン |
| timeslice | 2 | MPS 無し。0.42 ずつの 2 つのエンジンで、GPU は時間分割で動く |
| mps | 2 | 制御デーモンを立ててから、同じ 2 つのエンジンを載せる |

どのモードにも、1 つの負荷生成器から同じリクエストの並びを流します。同時に流すリクエストは合計で 16 と 128 の 2 通りで、2 つのエンジンには半分ずつ配ります。入力は 512 トークン、出力は 128 トークンです。決まった数のリクエストを流し切るまでの時間でスループットを計算し、各条件を 3 回測りました。MPS のときは、制御デーモンを次のように立てて止めます。

```bash
nvidia-cuda-mps-control -d
```

```bash
echo quit | nvidia-cuda-mps-control
```

スクリプトは、MPS のときに全エンジンがクライアントとして登録されたことを確かめ、MPS 無しのときに制御デーモンが動いていないことを確かめます。最初の試しでは、前の測定の制御デーモンが残っていて、MPS 無しのつもりの測定が MPS の上で走っていたからです。

## 結果

![CUDA graph ありでは、2 つのエンジンは 1 つのエンジンに届かず、MPS は時間分割より 11〜15% 速い](/images/f4f81e1c20106d-results.png)

図の左の 6 組は、CUDA graph ありの 3 つのモデルを、同時に流すリクエスト 16 と 128 で測ったものです。この 6 組すべてで、MPS は時間分割より 11〜15% 速く出ました。一方で、同じ負荷を 2 つのエンジンに分けると、1 つのエンジンの 0.60〜0.88 倍に落ちました。このとき 1 つのエンジンでも、GPU でカーネルが走っていた時間の割合は 98〜100% でした。

図の右の 2 組は、Qwen2.5-0.5B-Instruct の CUDA graph を切り、1 つのエンジンの GPU に空きを作って測ったものです。同時に流すリクエストが 16 のとき、1 つのエンジンでカーネルが走っていた時間の割合は 44% に下がりました。2 つに分けると、MPS で 0.98 倍と 1.01 倍、時間分割で 0.96 倍と 0.88 倍で、1 つのエンジンとの差はほとんど無くなりました。

3 回の測定のばらつきは、どの条件も平均の 1% 未満です。

## いつ MPS を使うか

今回の L4 では、同じ負荷を 2 つのエンジンに分けて、1 つよりはっきり速くなる場面はありませんでした。一方で、1 枚の GPU に複数のエンジンを載せるなら、MPS は時間分割より速く出ました。

## まとめ

MPS は 1 枚の GPU を複数のプロセスで同時に使う仕組みで、今回の L4 では CUDA graph ありなら時間分割より 11〜15% 速かったものの、同じ負荷を 2 つに分けて 1 つのエンジンをはっきり超えることはありませんでした。
