## はじめに

[SkyPilot v0.14.0](https://github.com/skypilot-org/skypilot/releases/tag/v0.14.0) が 2026 年 10 月 6 日に出ました。この記事では、SkyPilot がそもそも何をする道具なのかを押さえたうえで、v0.14.0 の機能と性能に関わる変更を、実務の目で整理します。

| v0.14.0 の項目 | 何が変わったか | 実務での意味 |
|---|---|---|
| [動的なジョブグループ](#動的なジョブグループ) | 動いているグループの中から、ジョブを足せるようになった | 統合モードのリモートの API サーバーなら、学習を止めずに、チェックポイントごとの評価をグループの一部として足せる |
| [グループ内の通信の保証](#グループ内の通信の保証) | 既定で、タスクどうしが通信できる形で置けないと、投げた時点で失敗するようになった（`inter_connection: false` で外せる） | 通信できないまま学習が始まる事故を、投げた時点かネットワークの準備の時点で止められる |
| [AWS Neuron への対応](#aws-neuron-への対応) | Kubernetes の上で Trainium と Inferentia のノードに Pod を置けるようになった | デバイスプラグインとラベルを用意した EKS で、Neuron SDK の入ったイメージを指定すれば、Trainium のノードを GPU と同じ `--gpus` の書き方で頼める |
| [EFA の改善](#efa-の改善) | `network_tier: best` のジョブで、複数ノードを 1 つの AZ にまとめ、`kubernetes.autoscaler` を設定したクラスタではアクセラレータのノードが 0 台でも EFA の数を決めるようになった | NCCL を使う複数ノードの学習が、気づかないまま TCP に落ちにくくなる |
| [Kueue との連携の改善](#kueue-との連携の改善) | Kueue の受け入れ待ちを、確保のタイムアウトに数えなくなった | 確保のタイムアウトと、受け入れ待ちの上限（既定 24 時間、プールのワーカーは既定で無期限）を別々に決められる |
| [複数ユーザーでの実行](#複数ユーザーでの実行) | Slurm で、ユーザーごとの Unix アカウントでジョブを出せるようになった | 設定で有効にすれば、Slurm 側で設定した利用量の記録や割り当ての方針を、人を区別して適用できる |
| [コンテナクラスタの停止と再開](#コンテナクラスタの停止と再開) | Slurm のコンテナのクラスタを止めて、あとで再開できるようになった | 割り当てを手放しても、コンテナに入れたパッケージやファイルを残したまま再開できる |

## SkyPilot とは何か

### 1 つの書き方で複数の基盤に投げる

![1 つのタスクの YAML から、Kubernetes、Slurm、クラウドの VM のどれにでも同じ書き方で投げられる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/c11cbe23729078/zenn/articles/c11cbe23729078/overview.png)

組織で複数のプロジェクトを進めていると、GPU の確保の難しさやコストとの兼ね合いから、複数のクラウドプロバイダ、オーケストレーター、リージョンを併用することがあります。Kubernetes や Slurm のクラスタは、それぞれ別々に構築して立ち上げます。AWS の場合は、[クラスタを構築するリファレンスのテンプレート](https://github.com/awslabs/awsome-distributed-ai/tree/3a1002576ccef26e66ba714303b10ccdaa645691/architectures)が awsome-distributed-ai にあります。対象は SageMaker HyperPod、Amazon EKS、Slurm を使う AWS Parallel Computing Service（AWS PCS）などです。基盤ごとに、ジョブの書き方も、空きの探し方も、止まったときの立て直し方も違います。

SkyPilot は、こうして別々に立てたクラスタやクラウドの VM に、統一的にジョブを投げるための道具だと理解すればよいです。クラウドの VM の場合は、SkyPilot がインスタンスを自分で作ります。投げる先の例として、SkyPilot のドキュメントは [`network_tier` の説明](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/docs/source/reference/yaml-spec.rst#L596-L613)で、HyperPod の EKS のクラスタを Kubernetes として、HyperPod の Slurm のクラスタを Slurm として挙げ、GKE や CoreWeave などの Kubernetes のクラスタも並べています。AWS PCS については、2026 年 10 月 31 日に v0.14.0 のドキュメントを検索して記述が見つからず、筆者も PCS のクラスタに投げることは確かめていません。

**SkyPilot は、どの基盤でも同じ 1 つのタスクの書き方で、計算資源の確保からジョブの実行と後片付けまでを受け持つ道具です**。[カリフォルニア大学バークレー校の研究室](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/docs/source/sky-computing.rst#L80-L86)から生まれたオープンソースのソフトウェアで、[ライセンス](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/LICENSE)は Apache 2.0 です。

タスクは、必要な資源、準備のコマンド、実行のコマンドを YAML に書いたものです。

```yaml
resources:
  accelerators: H100:8
workdir: .
setup: pip install -r requirements.txt
run: python train.py
```

これを `requirements.txt` と `train.py` のあるディレクトリに `task.yaml` として保存し、`sky launch task.yaml` を実行すると、SkyPilot は条件を満たす基盤と場所を探して計算資源を確保します。確保に失敗したら、別の場所で[やり直します](https://docs.skypilot.co/en/latest/examples/auto-failover.html)。[README](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/README.md) のとおり、計算資源はすべて利用者自身のクラウドのアカウントやクラスタの中に作られます。

`sky launch` は対話的に使う開発用のクラスタを、`sky serve` は推論のエンドポイントを作ります。`sky jobs launch` で投げた[マネージドジョブ](https://docs.skypilot.co/en/latest/examples/managed-jobs.html)は、スポットインスタンスの回収やノードの故障が起きると、資源を確保し直して実行し直します。途中から続けるには、アプリケーションがチェックポイントを保存して読み込む必要があります。`sky` コマンドは [API サーバー](https://docs.skypilot.co/en/latest/reference/api-server/api-server.html)に依頼を送ります。1 人で使うときは手元に API サーバーが自動で立ち、チームで使うときはリモートに 1 つ立てて共有します。

### Kubernetes や Slurm との関係

SkyPilot は、Kubernetes や Slurm を置き換えません。Kubernetes の上では、資源の要求と置き場所の条件を書いた Pod の定義を作って Kubernetes の API サーバーに出し、置くノードは Kubernetes のスケジューラが決めます。Slurm の上では `sbatch` と `srun` でジョブを出し、割り当ては Slurm が決めます。

### Kueue との関係

[Kueue](https://kueue.sigs.k8s.io/) は、Kubernetes のクラスタの中でジョブを待ち行列に並べ、割り当て枠や優先度に従って、受け入れるか、待たせるか、優先度の高いジョブのために追い出すかを決める仕組みです。1 つのクラスタの中で使う場合、SkyPilot と Kueue は受け持つ段が違うので、置き換えではなく重ねて使います。SkyPilot はどのクラスタやクラウドに置くかを選び、Kueue は選ばれたクラスタの中でいつ受け入れるかを決め、置くノードは Kubernetes のスケジューラが決めます。

組み合わせるときは、SkyPilot が Pod を作る名前空間に、ClusterQueue を参照する [LocalQueue](https://kueue.sigs.k8s.io/docs/concepts/local_queue/) を用意し、その名前を SkyPilot の設定の [`kubernetes.kueue.local_queue_name`](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/docs/source/reference/config.rst#L2013-L2018) に書きます。すると SkyPilot は、作る Pod に[待ち行列の名前と Pod のグループの名前のラベル](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/sky/templates/kubernetes-ray.yml.j2#L306-L309)と、[グループの Pod の数の annotation](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/sky/templates/kubernetes-ray.yml.j2#L328-L330) を付けます。複数ノードのタスクの Pod は、1 つのグループとしてまとめて受け入れられます。SkyPilot はタスクの計算資源を Pod として作るので、Kueue の側で[Pod をそのまま扱う設定](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/docs/source/reference/kubernetes/examples/kueue-example.rst#L38-L42)を有効にしておきます。v0.14.0 での受け入れ待ちの扱いの変更は、[Kueue との連携の改善](#kueue-との連携の改善)で説明します。

Kueue には、複数のクラスタにジョブを振り分ける [MultiKueue](https://kueue.sigs.k8s.io/docs/concepts/multikueue/) もあります。管理側のクラスタで枠を確保したジョブを各クラスタに写し、最初に受け入れたクラスタで動かす仕組みで、どのクラスタで動かすかを決めるので、この段では SkyPilot と受け持ちが重なります。SkyPilot の [Kueue の例](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/docs/source/reference/kubernetes/examples/kueue-example.rst#L359)は MultiKueue を参考の資料に挙げていますが、組み合わせる手順は載せていません（2026 年 10 月 29 日に v0.14.0 のドキュメントで確認）。

## ジョブグループのアップデート

### 動的なジョブグループ

![統合モードのリモートの API サーバーでは、グループの中のタスクが sky jobs launch で足したジョブは、グループの下に並び、グループと一緒に取り消される](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/c11cbe23729078/zenn/articles/c11cbe23729078/job-group-dynamic.png)

[ジョブグループ](https://docs.skypilot.co/en/latest/examples/job-groups.html)は、学習と報酬の計算のように資源の違う複数のタスクを同時に動かし、1 つの単位として管理する仕組みです。v0.13.0 のドキュメントには動的なタスクが無く、グループのタスクは投げる時点の YAML で決まります。

v0.14.0 では、グループの中のタスクが `sky jobs launch` を呼ぶと、そのジョブは自動でグループの[動的なタスク](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/docs/source/examples/job-groups.rst#L392-L412)になります。動的なタスクは `sky jobs queue` でグループの下に番号付きで並び、グループを取り消すと一緒に取り消されます。置き場所はグループと別に決まり、動的なタスクが失敗してもグループは失敗しません。

primary のタスク（図の `[P]`）がすべて終わると、それ以外の auxiliary のタスクは `termination_delay` の猶予のあとに止められ、そこでグループが終わります。グループが終わった時点でまだ動いている動的なタスクは、取り消されます。図の例では、チェックポイントを見張って評価を投げる見張り役を primary にし、見張り役が自分の投げた評価の終わりを待ってから終わるようにしています。この待ちを書かないか、見張り役を auxiliary にすると、動いている評価はグループと一緒に取り消されます。

この機能には、条件が 2 つあります。1 つは、マネージドジョブを[統合モード（consolidation mode）](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/docs/source/examples/job-groups.rst#L477-L482)で動かすリモートの API サーバーです。統合モードは、API サーバー自身がマネージドジョブを管理する形で、リモートの API サーバーの既定です。もう 1 つは、そのタスクが API サーバーに接続できることで、認証情報をタスクに渡すために[サービスアカウント](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/docs/source/examples/managed-jobs.rst#L676-L682)を有効にしておく必要があります。統合モードでない環境では、グループの中から投げたジョブは、グループに属さない普通のジョブになります。

### グループ内の通信の保証

ジョブグループの既定では、グループの YAML に書いたタスクを 1 つの Kubernetes クラスタにまとめて置き、互いのホスト名で通信できるようにつなぎます。v0.14.0 からは、このまとめた置き方ができないとき、SkyPilot は[投げた時点でグループを失敗にします](https://github.com/skypilot-org/skypilot/pull/10297)。タスクどうしのネットワークの準備に失敗した場合も、ジョブは失敗します。これまでのように、黙って別々のクラスタに分かれて置かれることはありません。前の節の動的なタスクは置き場所が別に決まり、グループのホスト名では呼べないので、この保証の対象外です。

別々のクラスタやクラウドに分けて置いてよいなら、グループに `inter_connection: false` を書きます。この場合、タスクどうしをつなぐ仕組みは用意されません。

## Kubernetes 関連のアップデート

### AWS Neuron への対応

![Trainium2:16 を頼むと、SkyPilot は Pod に資源の要求、ノードの指定、toleration の 3 つを足す。デバイスプラグインとラベルはクラスタの側で用意する](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/c11cbe23729078/zenn/articles/c11cbe23729078/neuron-pod.png)

SkyPilot は、少なくとも 2025 年 7 月の [v0.10.0](https://github.com/skypilot-org/skypilot/blob/61fc313fd82ea4770be02f568f826e797abb0e58/sky/clouds/aws.py#L277-L279) から、AWS の VM として Trainium と Inferentia を扱えます。v0.14.0 では、[Neuron に対応させた PR](https://github.com/skypilot-org/skypilot/pull/10169) で、Kubernetes の上でも扱えるようになりました。この PR は 2026 年 7 月 21 日にマージされ、v0.14.0 のタグに入っています（2026 年 10 月 24 日に確認）。

EKS の側に、Neuron 用の AMI で起動するノード、アクセラレータを Kubernetes の資源として見せる [Neuron のデバイスプラグイン](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/deploy/eks/index.html)、アクセラレータの種類を表すノードのラベルを用意しておくと、SkyPilot は Pod に次の 3 つを足します。

- 資源の要求: Trainium、Trainium2、Inferentia、Inferentia2 を頼むと、GPU の資源名の代わりに `aws.amazon.com/neuron` で[要求します](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/sky/clouds/kubernetes.py#L811-L814)。`Trainium2:16` の 16 はチップの数です。v0.14.0 の[一覧](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/sky/provision/kubernetes/utils.py#L299-L302)に Trainium3 はまだありません。
- ノードの指定: Karpenter がノードに付ける `karpenter.k8s.aws/instance-accelerator-name`（trn2.48xlarge では `trainium2`）を[読み](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/sky/provision/kubernetes/utils.py#L937-L982)、nodeAffinity に書きます。ノードが 0 台から増える場合は、SkyPilot の設定に `kubernetes.autoscaler: karpenter` を書いておきます。Karpenter を使わない場合は、ノードに [`skypilot.co/accelerator`](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/sky/provision/kubernetes/utils.py#L633-L668) のラベルを小文字の値で付けます。
- toleration: Neuron のノードに付けた `aws.amazon.com/neuron` の NoSchedule の taint を[許します](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/sky/provision/kubernetes/instance.py#L2465-L2476)。

Kubernetes の既定のコンテナイメージは、Neuron の Pod でも [GPU 用のもの](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/sky/clouds/kubernetes.py#L779)で、Neuron SDK は入っていません。そのため、`image_id` で Neuron SDK の入ったイメージを指定します。この節の動きは、2026 年 10 月 24 日に PyPI の skypilot 0.14.0 とソースで確かめましたが、実機の EKS での `sky launch` はまだ確かめていません。


:::

Trainium の上で動かすコードの側では、v0.14.0 のあとの 2026 年 10 月 20 日に、[TorchNeuron](https://pytorch.org/blog/introducing-torchneuron-native-pytorch-backend-for-aws-trainium/) が公開ベータになりました。TorchNeuron は、PyTorch の外からデバイスを足す PrivateUse1 という仕組みで、Trainium2 と Trainium3 を `neuron` デバイスとして登録する backend です。ブログの学習の例では、変更は `model.to('neuron')` の 1 か所です。TorchNeuron は eager と `torch.compile(backend="neuron")` に対応し、DDP、FSDP2、テンソル並列、パイプライン並列も使えます。ネイティブの変換が無い演算子や動的な形のように、最初のリリースでは対応していないものもあります。学習では、普段の PyTorch のコードを SkyPilot のタスクの `run` にそのまま書ける場面が増えると筆者は見ています。

推論について、ブログは LLM の配信に [vLLM Neuron plugin](https://github.com/vllm-project/vllm-neuron) を挙げ、Neuron の推論のスタックも TorchNeuron と同じ `torch.compile` の対応の上に作られていると書いています。いまの LLM の推論では vLLM Neuron plugin を使うのが現実的で、カーネルの最適化が進み、普段の PyTorch のモデルの実装のままで推論の性能が出る範囲が広がれば、学習と同じように使いやすくなると筆者は見ています。TorchNeuron と SkyPilot の組み合わせは、まだ確かめていません。

### EFA の改善

EFA は Elastic Fabric Adapter の略で、AWS のノードどうしを高速につなぐネットワークのインタフェースです。タスクの `resources:` の下に `network_tier: best` を書くと、SkyPilot は AWS の EKS で、Pod に EFA の要求を足そうとします。条件に合うノードが `vpc.amazonaws.com/efa` の資源を公開していれば、要求する数は次の式で決まります。

$$
\text{要求する EFA の数} = \max\left(1,\ \left\lfloor \frac{\text{頼んだデバイスの数}}{\text{ノードのデバイスの数}} \times \text{ノードの EFA の数} \right\rfloor\right)
$$

[この計算](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/sky/clouds/kubernetes.py#L1918-L1934)は、要求したアクセラレータの資源の名前で数えます。たとえば [trn2.48xlarge](https://karpenter.sh/docs/reference/instance-types/) はデバイスと EFA を 16 ずつ公開するので、`Trainium2:8` を頼めば EFA は 8 になります。

v0.14.0 では、この仕組みに 2 つの改善が入りました。1 つ目は、[アクセラレータのノードが 0 台でも数を決める](https://github.com/skypilot-org/skypilot/pull/10053)ことです。これまでは動いているノードを調べて数を決めていたので、Karpenter などでノードを 0 台から増やすクラスタでは数が決まらず、EFA を要求しないまま Pod が作られることがありました。そうなると、NCCL の通信は気づかないまま TCP に落ちます。v0.14.0 からは、設定に `kubernetes.autoscaler` があり、クラスタに AWS のノードが 1 台でもあれば、SkyPilot のカタログにあるインスタンスの EFA の数から、[同じ割合で数を決めます](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/sky/clouds/kubernetes.py#L2027-L2034)。カタログでも数が決まらなければ、これまでどおり EFA なしの Pod になります。

2 つ目は、[複数ノードの EFA のジョブを 1 つの AZ にまとめる](https://github.com/skypilot-org/skypilot/pull/10054)ことです。EFA の通信は 1 つの AZ の中で組むので、ノードが別々の AZ に散ると EFA でつながりません。v0.14.0 からは、AWS の EFA の環境で複数ノードの `network_tier: best` のジョブに、[同じ AZ に集まる podAffinity](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/sky/templates/kubernetes-ray.yml.j2#L460-L472) を足します。最初の Pod が置かれた AZ に、残りの Pod が続きます。この条件は必須なので、その AZ に空きが無ければ、Pod は TCP に落ちて動き出すのではなく、待ちの状態で止まります。

どちらも Pod の資源の要求と置き場所の改善で、アプリケーションが EFA を使うかは、イメージの中の通信ライブラリの設定で決まります。SkyPilot の EFA の処理は、ソースのコメントを見るかぎり、NVIDIA の GPU 向けの通信ライブラリである NCCL を念頭に書かれています。Neuron の通信が割り当てた EFA を使うかは、確かめていません。

### Kueue との連携の改善

Kueue は、Kubernetes のジョブを待ち行列に並べ、割り当て枠に空きができたものから受け入れる仕組みです。受け入れ待ちの Pod には scheduling gate という印が付き、スケジューラに載りません。

これまでも、Kueue の待ち行列を設定した場合は、確保のタイムアウトの既定を 24 時間に延ばしていました。ただし、`provision_timeout` を明示すると、その値が受け入れ待ちにも効いていました。確保の遅れを見張るつもりで短い値を書くと、待ち行列が混んでいるだけのジョブまで捨てられていました。v0.14.0 からは、対象の Pod のどれかが待っている間は[確保の時計を止め](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/sky/provision/kubernetes/instance.py#L1081-L1096)、すべてが受け入れられてから数え始めます。受け入れ待ちそのものの上限は `kubernetes.kueue.admission_timeout` で別に決まり、[既定は 24 時間](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/sky/provision/kubernetes/instance.py#L65-L76)、`-1` で無期限です。この変更は [PR #10252](https://github.com/skypilot-org/skypilot/pull/10252) で 2026 年 7 月 28 日にマージされました。

あわせて、ジョブを流すワーカーを並べておくプールが、Kueue の割り当て枠に当たったときの[動きも直りました](https://github.com/skypilot-org/skypilot/pull/10718)。Kueue が優先度の高いジョブのためにワーカーを追い出すと、SkyPilot はスポットでないワーカーも外して置き直します。プールのワーカーは、上限を書かなければ受け入れを無期限に待ちます。

## Slurm 関連のアップデート

### 複数ユーザーでの実行

![既定の submit_as_user: false では全員が SSH ユーザーとしてジョブを出し、true にすると SSH ユーザーから sudo で各ユーザーの Unix アカウントに切り替える](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/c11cbe23729078/zenn/articles/c11cbe23729078/slurm-multi-user.png)

1 つの API サーバーで Slurm のクラスタを分け合うと、既定ではどのユーザーのジョブも、`~/.slurm/config` に書いた 1 つの SSH ユーザーとして出されます。Slurm の利用量の記録（accounting）、公平な割り当て（fairshare）、ファイルの権限は、Slurm 側の設定に従ってユーザーごとに効くので、全員が同じ 1 人に見えます。共通のアカウントで運用するなら、既定の `submit_as_user: false` のままで構いません。

v0.14.0 では、API サーバーが読む SkyPilot の設定で [`slurm.submit_as_user`](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/docs/source/reference/config.rst#L2382-L2411) を有効にできます。すると SkyPilot は、まず SSH ユーザーで接続し、そのあと確保、`srun`、ファイルの転送、取り消しを、依頼した人の Unix アカウントとして行います。アカウント名は、既定ではメールアドレスの `@` より前の部分で、`username_map` で個別に対応を書けます。この設定はタスクやクライアントの設定では上書きできません。次の例は、Slurm のクラスタに `jdoe` の Unix アカウントがあることを前提にしています。

```yaml
slurm:
  submit_as_user: true
  username_map:
    jane.doe@example.com: jdoe
```

そのためには、SSH ユーザーが root であるか、対象のユーザーとして `/bin/bash` をパスワードなしの sudo で動かせる必要があります。SkyPilot はこのシェルの中でスクリプトの実行や rsync を行うので、コマンドごとには絞れず、切り替え先の権限がそのまま SSH ユーザーに渡ります。[ドキュメント](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/docs/source/reference/config.rst#L2412-L2436)は、切り替え先を sudo や Slurm の管理権限を持たない専用グループのアカウントに限り、そのグループにだけ `requiretty` を外す設定例を載せています。対象のアカウントが無いか権限が足りないとき、SkyPilot はその操作を失敗させ、SSH ユーザーには戻りません。

新しい `slurm.quota` は、`queue` を `sbatch` の `--qos` に、`account` を `--account` に渡す設定で、ワークスペースごとに変えられます。この `--account` は Slurm の利用量を付ける先の単位で、Unix のアカウントとは別のものです。

### コンテナクラスタの停止と再開

Slurm の上で Pyxis を使うコンテナのクラスタは、[`sky stop` と `sky start` に対応しました](https://github.com/skypilot-org/skypilot/pull/10544)。止めるときは、各ノードのコンテナのファイルシステムを共有のストレージに写してから割り当てを手放し、再開するときは新しい割り当てに書き戻します。入れたパッケージやファイルを残したまま、Slurm のノードを他の人に返せます。残るのはファイルシステムで、動いていたプロセスは止めた時点で終わるので、計算を途中から続けるにはチェックポイントが要ります。

あわせて、一定時間使われていないクラスタを同じ手順で止める [autostop](https://github.com/skypilot-org/skypilot/pull/10645) と、ホストのパスを[マウントする設定](https://github.com/skypilot-org/skypilot/pull/10438)も入りました。

## アップグレードの前に確かめること

[リリースノート](https://github.com/skypilot-org/skypilot/releases/tag/v0.14.0)の破壊的変更のうち、タスクや設定の書き換えが要る主なものを並べます。API の認可が厳しくなった変更などの残りは、リリースノートを見てください。

| 変わったこと | 必要な対応 | 書く場所 |
|---|---|---|
| SkyPilot は conda を既定では入れない。Kubernetes の既定のイメージは、システムの Python と `~/sky-user-env` の仮想環境を持つ | setup で `conda activate` を使うなら、`provision.install_conda: true` を書く。入るのは Miniforge で、チャネルは conda-forge だけ | SkyPilot の設定 |
| ジョブグループのタスクを互いに通信できる形で置けないと、投げた時点で失敗する。ネットワークの準備の失敗もジョブの失敗になる | 別々のクラスタやクラウドに置いてよければ、グループに `inter_connection: false` を書く。タスクどうしをつなぐ仕組みは用意されなくなる | ジョブグループの YAML の先頭 |
| `user` の権限のユーザーは、API サーバーの設定を読めない | 読ませたいなら `rbac.restrict_config_to_admins: false` を書く | API サーバーの設定 |
| Kubernetes の一時領域の大きさは `ephemeral_storage` ではなく `disk_size` で書く | `disk_size` に書き換える | タスクの `resources` |

## まとめ

v0.14.0 では、ジョブグループに、動いているグループへジョブを足す機能と既定で有効な通信の保証が入りました。Kubernetes には Neuron への対応と、EKS の EFA と Kueue の改善が入り、Slurm にはユーザーごとの実行とコンテナの停止と再開が入りました。
