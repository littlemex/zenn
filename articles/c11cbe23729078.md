## はじめに

[SkyPilot v0.14.0](https://github.com/skypilot-org/skypilot/releases/tag/v0.14.0) が 2026 年 10 月 6 日（日本時間）に出ました。この記事では、SkyPilot がそもそも何をする道具なのかを押さえたうえで、v0.14.0 の変更を実務の目で整理します。中でも詳しく見るのは、Kubernetes の上で AWS Trainium と Inferentia を扱えるようになった変更です。Trainium と Inferentia は AWS の機械学習向けのアクセラレータで、Neuron SDK で動かします。SkyPilot のリリースノートは、この 2 つを Neuron のアクセラレータと呼んでいます。

| v0.14.0 の項目 | 何が変わったか | 実務での意味 |
|---|---|---|
| Kubernetes での AWS Neuron | Trainium と Inferentia のノードに Pod を置けるようになった | EKS の Trainium のノードを、GPU と同じ `--gpus` の書き方で頼める。イメージは利用者が Neuron SDK の入ったものを指定する |
| 動的なジョブグループ | 動いているグループの中から、ジョブを足せるようになった | 統合モードのリモートの API サーバーなら、学習を止めずに、チェックポイントごとの評価をグループの一部として足せる |
| 複数ユーザーの Slurm | ユーザーごとの Unix アカウントでジョブを出せるようになった | 設定で有効にすれば、Slurm 側で設定した利用量の記録と公平な割り当てが、人ごとに効く |
| 非公開ワークスペースの読み取り | メンバー以外にも、読み取り専用で見せられるようになった | 他のチームの実験の様子を、変更させずに共有できる |
| ジョブが動かない理由の表示 | 待っている理由が一覧に出るようになった | 「なぜ始まらないのか」の手がかりを、ログを掘る前に得られる |

## SkyPilot とは

![1 つのタスクの YAML から、Kubernetes、Slurm、クラウドの VM のどれにでも同じ書き方で投げられる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/c11cbe23729078/zenn/articles/c11cbe23729078/overview.png)

AI の計算資源は、AWS の Kubernetes サービスである EKS、Slurm のクラスタ、クラウドの VM のように散らばっていることが多いです。基盤ごとに、ジョブの書き方も、空きの探し方も、止まったときの立て直し方も違います。

**SkyPilot は、どの基盤でも同じ 1 つのタスクの書き方で、計算資源の確保からジョブの実行と後片付けまでを受け持つ道具です**。 [カリフォルニア大学バークレー校の研究室](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/docs/source/sky-computing.rst#L80-L86)から生まれたオープンソースのソフトウェアで、[ライセンス](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/LICENSE)は Apache 2.0 です。

タスクは、必要な資源、準備のコマンド、実行のコマンドを YAML に書いたものです。

```yaml
resources:
  accelerators: H100:8
workdir: .
setup: pip install -r requirements.txt
run: python train.py
```

これを `requirements.txt` と `train.py` のあるディレクトリに `task.yaml` として保存し、`sky launch task.yaml` を実行すると、SkyPilot は条件を満たす基盤と場所を探して計算資源を確保します。確保に失敗したら、別の場所で[やり直します](https://docs.skypilot.co/en/latest/examples/auto-failover.html)。[README](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/README.md) のとおり、計算資源はすべて利用者自身のクラウドのアカウントやクラスタの中に作られます。

`sky launch` は対話的に使う開発用のクラスタを、`sky serve` は推論のエンドポイントを作ります。`sky jobs launch` で投げた[マネージドジョブ](https://docs.skypilot.co/en/latest/examples/managed-jobs.html)は、スポットインスタンスの回収やノードの故障が起きると、資源を確保し直して実行し直します。途中から続けるには、アプリケーションがチェックポイントを保存して読み込む必要があります。`sky` コマンドは [API サーバー](https://docs.skypilot.co/en/latest/reference/api-server/api-server.html)に依頼を送ります。1 人で使うときは手元に API サーバーが自動で立ち、チームで使うときはリモートに 1 つ立てて共有します。

## Kubernetes や Slurm との関係

SkyPilot は、Kubernetes や Slurm を置き換えません。Kubernetes の上では、資源の要求と置き場所の条件を書いた Pod の定義を作って Kubernetes の API サーバーに出し、置くノードは Kubernetes のスケジューラが決めます。Slurm の上では `sbatch` と `srun` でジョブを出し、割り当ては Slurm が決めます。待ち行列の Kueue を使う場合は、SkyPilot が Pod に[待ち行列の名前](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/docs/source/reference/config.rst#L98-L99)を付け、受け入れるかは Kueue が決めます。

## Trainium: Kubernetes 経由の対応が要る理由

![Trainium を使う方法は 2 つ。VM として使う方法は v0.10.0 にもあり、Kubernetes 経由の方法が v0.14.0 で加わった](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/c11cbe23729078/zenn/articles/c11cbe23729078/neuron-paths.png)

SkyPilot は、少なくとも 2025 年 7 月の [v0.10.0](https://github.com/skypilot-org/skypilot/blob/61fc313fd82ea4770be02f568f826e797abb0e58/sky/clouds/aws.py#L277-L279) から、AWS の VM として Trainium と Inferentia を扱えます。v0.14.0 では、アクセラレータの名前が Trainium か Inferentia で始まると、SkyPilot は GPU 用ではなく [Neuron 用のマシンイメージ](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/sky/clouds/aws.py#L464-L467)で起動します。この方法では、SkyPilot がインスタンスを自分で作ります。

一方で、Trainium のノードを EKS のクラスタに置き、チームで分け合う使い方もあります。この形では、SkyPilot は既にあるクラスタに Pod を置きます。ところが [Neuron に対応させた PR](https://github.com/skypilot-org/skypilot/pull/10169) の説明によると、v0.14.0 より前の Kubernetes 対応が標準で認識する資源は、NVIDIA と AMD の GPU と Google の TPU だけでした。そのため、Trainium のノードがあっても、SkyPilot は Neuron のデバイスを要求する Pod を作れませんでした。2026 年 10 月 24 日に確かめたところ、この PR は 2026 年 7 月 21 日にマージされ、v0.14.0 のタグに入っています。

## Trainium: Pod に足されるもの

![Trainium2:16 を頼むと、SkyPilot は Pod に資源の要求、ノードの指定、toleration の 3 つを足す。デバイスプラグインとラベルはクラスタの側で用意する](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/c11cbe23729078/zenn/articles/c11cbe23729078/neuron-pod.png)

v0.14.0 では、EKS の Trainium のノードを、GPU のノードと同じ頼み方で使えます。リリースノートの例は `sky launch --gpus Trainium2:16 --infra k8s` です。ただし、この例のままでは GPU 用の既定のイメージで Pod が作られるので、実際には後の節のとおり Neuron SDK の入ったイメージを指定します。

SkyPilot が受け持つのは、Neuron を要求する Pod を作って Kubernetes に出すところです。EKS の側には、Neuron 用の AMI で起動するノード、ノードのアクセラレータを Kubernetes の資源として見せる [Neuron のデバイスプラグイン](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/deploy/eks/index.html)、アクセラレータの種類を表すノードのラベル（後述）を先に用意します。そのうえで、SkyPilot は Pod の定義に次の 3 つを足します。

1 つ目は資源の要求です。Neuron のデバイスプラグインは、Trainium と Inferentia を `aws.amazon.com/neuron` という名前の資源として公開します。SkyPilot は、頼まれたアクセラレータが [Trainium、Trainium2、Inferentia、Inferentia2 のどれか](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/sky/provision/kubernetes/utils.py#L299-L302)なら、GPU の資源名の代わりに[この資源名で要求します](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/sky/clouds/kubernetes.py#L811-L814)。v0.14.0 のこの一覧には、Trainium3 はまだ入っていません。

2 つ目はノードの指定です。ノードを需要に応じて増やす Karpenter は、Trainium のノードに `karpenter.k8s.aws/instance-accelerator-name` というラベルを付けます。[Karpenter の表](https://karpenter.sh/docs/reference/instance-types/)では、trn2.48xlarge の値は `trainium2` です。SkyPilot は[このラベルを読めるようになり](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/sky/provision/kubernetes/utils.py#L937-L982)、Pod の nodeAffinity、つまり置くノードをラベルで絞る条件に、この値を書きます。

ノードがまだ無く、Karpenter がこれから作る場合もあります。このときは、タスクの YAML ではなく SkyPilot の設定ファイルの `kubernetes:` の下に `autoscaler: karpenter` を書いておきます。すると SkyPilot は、ノードを見ずに、[Karpenter のラベルと `trainium2` の値](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/sky/provision/kubernetes/utils.py#L2811-L2837)を nodeAffinity に書きます。Karpenter を使わない場合は、SkyPilot 自身のラベル [`skypilot.co/accelerator`](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/sky/provision/kubernetes/utils.py#L633-L668) に、`trainium2` のような小文字の値を自分で付けます。`Trainium2` のように大文字を含む値は、SkyPilot の検査で拒まれます。

3 つ目は toleration です。taint はノードに付ける「この条件の Pod しか載せない」という印で、toleration はその taint を許す Pod 側の設定です。Neuron のノードには、Neuron を使わない Pod が載らないよう、`aws.amazon.com/neuron` の taint が付けられていることがあります。SkyPilot は、Neuron を要求する Pod に、このキーの NoSchedule を許す [toleration を足します](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/sky/provision/kubernetes/instance.py#L2465-L2476)。

さらに、タスクの `resources:` の下に `network_tier: best` を書くと、SkyPilot は EFA の要求も足そうとします。EFA は Elastic Fabric Adapter の略で、AWS のノードどうしを高速につなぐネットワークのインタフェースです。条件に合うノードが EFA を公開していれば、要求する数は次の式で決まります。

$$
\text{要求する EFA の数} = \max\left(1,\ \left\lfloor \frac{\text{頼んだデバイスの数}}{\text{ノードのデバイスの数}} \times \text{ノードの EFA の数} \right\rfloor\right)
$$

[この計算](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/sky/clouds/kubernetes.py#L1918-L1934)は要求した資源の名前で数えるので、Neuron にもそのまま効きます。trn2.48xlarge は Neuron を 16、EFA を 16 持つ機種なので、EFA のデバイスプラグインが入ったノードで 16 デバイスを全部頼めば、EFA も 16 になります。条件に合うノードがまだ無い場合は、設定に `kubernetes.autoscaler` があり、クラスタに AWS のノードが 1 台でもあれば、[インスタンスの一覧から EFA の数を引こうとします](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/sky/clouds/kubernetes.py#L2027-L2034)。どちらの方法でも数が決まらなければ、SkyPilot はエラーにせず EFA なしの Pod を作ります。

## Trainium: 使うときの注意

`Trainium2:16` の 16 は、Neuron デバイス、つまりチップの数です。チップの中の計算コアは NeuronCore と呼ばれ、trn2.48xlarge は 16 個のデバイスと 128 個の NeuronCore を公開します。SkyPilot が要求するのは、デバイスの側だけです。

Kubernetes の既定のコンテナイメージは、Neuron の Pod でも [GPU 用のもの](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/sky/clouds/kubernetes.py#L779)です。このイメージは CUDA のランタイムのイメージを土台にしていて、[Dockerfile](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/Dockerfile_k8s_gpu) のどこでも Neuron SDK を入れていません。VM として使う場合と違い、Kubernetes 経由では Neuron 用の既定のイメージがまだ無いので、Neuron SDK の入ったイメージを自分で指定します。独自のイメージには[条件が 2 つ](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/docs/source/reference/kubernetes/kubernetes-getting-started.rst#L203-L206)あります。Debian 系で apt が使えることと、既定のユーザーが root であるか、パスワードなしで sudo できることです。

次の YAML は、[Neuron の Deep Learning Containers](https://github.com/aws-neuron/deep-learning-containers) のうち、2026 年 10 月 24 日に README の表の先頭にあった Neuron SDK 2.30.0 のイメージを指定する例です。

```yaml
resources:
  infra: k8s
  accelerators: Trainium2:16
  image_id: docker:public.ecr.aws/neuron/pytorch-training-neuronx:2.9.0-neuronx-py312-sdk2.30.0-ubuntu24.04
```

これを `trainium2.yaml` として保存し、次のように渡します。

```bash
sky launch trainium2.yaml
```

この節と前の節のうち、名前の判定、Karpenter のラベルのキーと値、小文字の検査、扱う taint のキーは、2026 年 10 月 24 日に PyPI の skypilot 0.14.0 で関数を呼んで確かめました。Pod への書き込み、EFA の数の計算、既定のイメージの選択は、同じ日に v0.14.0 のソースを読んで確かめました。上の YAML は、`sky.Task.from_yaml` で読み込めることと、指定したイメージのタグが公開されていることまでを確かめました。このイメージの既定のユーザーが root かどうかと、`sky launch` での実機の EKS での動作は、まだ確かめていません。SkyPilot の EFA の処理は、ソースのコメントを見るかぎり、NVIDIA の GPU 向けの通信ライブラリである NCCL を念頭に書かれています。Neuron の通信が割り当てた EFA を実際に使うかも、確かめていません。

## 動的なジョブグループ: 要る理由

[ジョブグループ](https://docs.skypilot.co/en/latest/examples/job-groups.html)は、学習と報酬の計算のように資源の違う複数のタスクを同時に動かし、1 つの単位として管理する仕組みです。v0.13.0 のドキュメントには動的なタスクが無く、グループのタスクは投げる時点の YAML で決まります。チェックポイントごとの評価は、グループとは別のジョブとして管理することになります。

## 動的なジョブグループ: 仕組み

![統合モードのリモートの API サーバーでは、グループの中のタスクが sky jobs launch で足したジョブは、グループの下に並び、グループと一緒に取り消される](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/c11cbe23729078/zenn/articles/c11cbe23729078/job-group-dynamic.png)

v0.14.0 では、グループの中のタスクが `sky jobs launch` を呼ぶと、そのジョブは自動でグループの[動的なタスク](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/docs/source/examples/job-groups.rst#L392-L412)になります。動的なタスクは `sky jobs queue` でグループの下に番号付きで並び、グループを取り消すと一緒に取り消されます。置き場所はグループと別に決まり、動的なタスクが失敗してもグループは失敗しません。

primary のタスク（図の `[P]`）がすべて終わると、それ以外の auxiliary のタスクは `termination_delay` の猶予のあとに止められ、そこでグループが終わります。グループが終わった時点でまだ動いている動的なタスクは、取り消されます。図の例では、チェックポイントを見張って評価を投げる見張り役を primary にし、見張り役が自分の投げた評価の終わりを待ってから終わるようにしています。この待ちを書かないか、見張り役を auxiliary にすると、動いている評価はグループと一緒に取り消されます。

この機能には、条件が 2 つあります。1 つは、マネージドジョブを[統合モード（consolidation mode）](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/docs/source/examples/job-groups.rst#L477-L482)で動かすリモートの API サーバーです。統合モードは、API サーバー自身がマネージドジョブを管理する形で、リモートの API サーバーの既定です。もう 1 つは、そのタスクが API サーバーに接続できることで、認証情報をタスクに渡すために[サービスアカウント](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/docs/source/examples/managed-jobs.rst#L676-L682)を有効にしておく必要があります。統合モードでない環境では、グループの中から投げたジョブは、グループに属さない普通のジョブになります。

## 複数ユーザーの Slurm: 人ごとのアカウントで出す

![既定の submit_as_user: false では全員が SSH ユーザーとしてジョブを出し、true にすると SSH ユーザーから sudo で各ユーザーの Unix アカウントに切り替える](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/c11cbe23729078/zenn/articles/c11cbe23729078/slurm-multi-user.png)

1 つの API サーバーで Slurm のクラスタを分け合うと、既定ではどのユーザーのジョブも、`~/.slurm/config` に書いた 1 つの SSH ユーザーとして出されます。Slurm の利用量の記録（accounting）、公平な割り当て（fairshare）、ファイルの権限は Unix のユーザーごとに効くので、全員が同じ 1 人に見えます。共通のアカウントで運用するなら、既定の `submit_as_user: false` のままで構いません。

v0.14.0 では、API サーバーが読む SkyPilot の設定で [`slurm.submit_as_user`](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/docs/source/reference/config.rst#L2382-L2411) を有効にできます。すると SkyPilot は、まず SSH ユーザーで接続し、そのあと確保、`srun`、ファイルの転送、取り消しを、依頼した人の Unix アカウントとして行います。アカウント名は、既定ではメールアドレスの `@` より前の部分で、`username_map` で個別に対応を書けます。この設定はタスクやクライアントの設定では上書きできません。次の例は、Slurm のクラスタに `jdoe` の Unix アカウントがあることを前提にしています。

```yaml
slurm:
  submit_as_user: true
  username_map:
    jane.doe@example.com: jdoe
```

そのためには、SSH ユーザーが root であるか、対象のユーザーとして `/bin/bash` をパスワードなしの sudo で動かせる必要があります。SkyPilot はこのシェルの中でスクリプトの実行や rsync を行うので、コマンドごとには絞れず、切り替え先の権限がそのまま SSH ユーザーに渡ります。ドキュメントは、切り替え先を sudo や Slurm の管理権限を持たない専用グループのアカウントに限る設定例を載せています。SkyPilot は端末を割り当てずに SSH 越しに sudo を呼ぶので、sudo の設定で `requiretty` が全体に効いていると操作が失敗します。対象のグループにだけ `!requiretty` を書く例も、[ドキュメント](https://github.com/skypilot-org/skypilot/blob/7b62fd814e21aa9ab17d0c60c10ffb6f6aa1250e/docs/source/reference/config.rst#L2412-L2436)にあります。対象のアカウントが無いか権限が足りないとき、SkyPilot はその操作を失敗させ、SSH ユーザーには戻りません。

新しい `slurm.quota` は、`queue` を `sbatch` の `--qos` に、`account` を `--account` に渡す設定で、ワークスペースごとに変えられます。この `--account` は Slurm の利用量を付ける先の単位で、Unix のアカウントとは別のものです。

## 運用の見通しを良くする変更

ユーザーと資源をまとめる区画であるワークスペースは、非公開でも、API サーバーの設定でそのワークスペースに `read_access: all` を書けば、メンバー以外にクラスタ、マネージドジョブ、ログを読み取り専用で見せられるようになりました。`sky jobs queue -v` は、待っているマネージドジョブについて、Slurm の待ちの理由や Kubernetes でのイメージの取得といった、起動の最新の状況を表示します。

## アップグレードの前に確かめること

[リリースノート](https://github.com/skypilot-org/skypilot/releases/tag/v0.14.0)の破壊的変更のうち、タスクや設定の書き換えが要る主なものを並べます。API の認可が厳しくなった変更などの残りは、リリースノートを見てください。

| 変わったこと | 必要な対応 | 書く場所 |
|---|---|---|
| SkyPilot は conda を既定では入れない。Kubernetes の既定のイメージは、システムの Python と `~/sky-user-env` の仮想環境を持つ | setup で `conda activate` を使うなら、`provision.install_conda: true` を書く。入るのは Miniforge で、チャネルは conda-forge だけ | SkyPilot の設定 |
| ジョブグループのタスクを互いに通信できる形で置けないと、投げた時点で失敗する。ネットワークの準備の失敗もジョブの失敗になる | 別々のクラスタやクラウドに置いてよければ、グループに `inter_connection: false` を書く。タスクどうしをつなぐ仕組みは用意されなくなる | ジョブグループの YAML の先頭 |
| `user` の権限のユーザーは、API サーバーの設定を読めない | 読ませたいなら `rbac.restrict_config_to_admins: false` を書く | API サーバーの設定 |
| Kubernetes の一時領域の大きさは `ephemeral_storage` ではなく `disk_size` で書く | `disk_size` に書き換える | タスクの `resources` |

## まとめ

SkyPilot は、Kubernetes、Slurm、クラウドの VM の上に同じ書き方の層をかぶせる道具で、v0.14.0 ではその層が Trainium と Inferentia の Kubernetes のノードまで届きました。ただし Kubernetes 経由では、Neuron SDK の入ったコンテナイメージを自分で指定します。
