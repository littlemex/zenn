# はじめに

vLLM のブログで [Decode Context Parallelism（DCP）](https://vllm.ai/blog/2026-08-07-decode-context-parallelism) という並列化の効果が紹介されていました。長いコンテキストを高スループットで捌くための工夫です。

> vLLM ブログより

![](https://vllm.ai/blog-assets/figures/2026-07-27-decode-context-parallelism/figure-5.png)

ちなみに Context Parallelism 自体は新しい技術ではなく、以前からある Parallelism の一種です。

この記事では、DCP を理解する前提として並列化の全体像を GPU への割り当てで整理し、そのうえで MoE（Mixture of Experts）、DCP、P/D Disaggregated Inference（Prefill/Decode 分離）、AFD（Attention-FFN Disaggregation）の 4 つが概念上どういう関係にあるのかを星取表で示します。TP や EP との関係にも触れ、この4つは互いに直交しているのか、について整理します。特定のフレームワーク実装の対応状況ではなく、概念レベルで捉えることを目的にしています。

# 結論として 4 つは直交

先に結論だけ置きます。MoE、DCP、P/D 分離、AFD は、どれも他の技術を前提にしているわけではなく、対ごとに見て直交（独立に組み合わせられる）しています。

| 技術 | MoE | DCP | P/D | AFD |
|---|---|---|---|---|
| MoE | - | 直交 | 直交 | 相乗 |
| DCP | 直交 | - | 相乗 | 相乗 |
| P/D | 直交 | 相乗 | - | 直交 |
| AFD | 相乗 | 相乗 | 直交 | - |

表の言葉の意味は次のとおりです。**直交**は互いに独立で自由に併用できる関係、**相乗**は独立でありながら組み合わせると特に効果が高い関係を指します。このあと TP と EP を加えたときに出てくる **依存**は片方がもう片方を前提とする関係、**入れ子**は概念は別だが実装上は片方の中に定義される関係です。

なぜこう言えるのかを、並列化の基礎から順に見ていきます。

# 並列化は GPU に何が載るかで理解

並列化の種類は名前だけ覚えると混乱しますが、例として 4 つの GPU があったときに「GPU 0 から 3 に何が載るか」を見ると一気に整理できます。分割する対象が、重みなのか、バッチなのか、シーケンスなのか、expert なのかで種類が決まります。次の図は、その「GPU 0 から 3 に何が載るか」を並列化ごとに並べたものです。

![並列化ごとの GPU への割り当て](/images/45a492721a6235-fig-parallelism.png)

- **TP（Tensor 並列）**: 1 枚に載らない大きな重みを分割します。どの GPU も同じトークンを見ます。
- **DP（Data 並列）**: 重みを全複製し、リクエストを GPU ごとに分けて、スループットを最大で台数分近くまで伸ばします。
- **CP（Context 並列）**: 「シーケンスの 4 分の 1 が 1 GPU に載る」形で、トークン位置の方向にシーケンスを分割します。
- **EP（Expert 並列）**: MoE を構成する小さな FFN である expert を GPU に配ります。
- **SP（Sequence 並列）**: LayerNorm や Dropout 周りの activation をシーケンス方向に分割してメモリを削ります。CP とは別物で、単独では使わず TP と同じ GPU グループの中で TP と組み合わせて使います。

ここで大事なのは、これらが「何を分割するか」という別々の軸に乗っている点です。重みを割る TP と、シーケンスを割る CP は、同時に使えます。つまり並列化どうしは基本的に掛け合わせられます。

# FFN の分割は Dense と MoE で別物

並列化の中でいちばん混乱しやすいのが、FFN と MoE と EP の関係です。ここは分けて理解する価値があります。次の図で、Dense の FFN と MoE の FFN が、それぞれどう分割されるのかを見比べてください。

![FFN の分割は Dense と MoE で別物になる](/images/45a492721a6235-fig-ffn-moe.png)

Dense な FFN は大きな重み行列で、これを分割するときは TP を使います。FFN は 2 つの行列積からなり、1 つ目を列方向、2 つ目を行方向に分割すると、途中の中間結果は通信なしで受け渡せて、最後に 1 回だけ all-reduce で合算できます。どの GPU も全トークンを部分的に計算する点が特徴です。

一方 MoE の FFN は、独立した複数の expert の集まりです。これを分割するのが EP で、expert を丸ごと GPU に配置します。トークンは router（トークンごとにどの expert を使うか選ぶ機構）が選んだ expert を持つ GPU にだけ送られ（all-to-all 通信）、全部の GPU を通るわけではありません。

つまり同じ「FFN の分割」でも、Dense なら TP、MoE なら EP と手段が変わります。EP は MoE という構造があって初めて成立するので、EP だけは MoE に依存します。これが後半の星取表で EP と MoE を「依存」とした理由です。ちなみに EP と TP も直交します。

# 推論サービスで GPU プールを分離する 2 つの軸

ここまでが 1 台のプールの中の話でした。実際の LLM 推論サービスは、GPU プールそのものを分けて役割を持たせます。分け方には直交する 2 つの軸があります。

1 つはフェーズで分ける P/D Disaggregated Inference（Prefill/Decode 分離）です。入力全体を一括で処理する Prefill は計算が重く（compute-bound）、1 トークンずつ生成する Decode はメモリ帯域が効きます（memory-bound）。性質が違うので、別々の GPU プールに分けてそれぞれ最適化します。

もう 1 つはモジュールで分ける AFD（Attention-FFN Disaggregation）です。Attention は KV キャッシュ（過去トークンの Key と Value を保存しておく領域）を読むメモリ律速の処理、FFN や MoE は行列積が重い処理なので、これも別々のプールに分けられます。次の図は、8 GPU を P/D 分離と AFD の 2 つの軸で割り当てた例です。

![実デプロイ例として P/D 分離と AFD で 8 GPU を割り当てる](/images/45a492721a6235-fig-deploy.png)

この 2 軸は独立です。図では Prefill プール（GPU 0 から 3）で入力を処理し、KV キャッシュを Decode プール（GPU 4 から 7）へ転送します。この転送の境目が P/D 分離です。Decode プールの中はさらに AFD で Attention サブプールと FFN サブプールに分かれ、層ごとに activation を往復させます。Attention サブプールでは後述する DCP で KV を分割し、FFN サブプールでは EP で expert を分割します。1 枚の図の中に、これまで出てきた並列化が自然に収まっていますね。

なお AFD は decode 専用の技術ではありません。原理的には Prefill 側でも Attention と FFN を分離できます。これまで実運用で主に Decode 側がターゲットにされているのは、Prefill が Attention も FFN も計算律速で、層ごとに activation を往復させる通信コストに見合いにくいと考えられるからです。もっとも最近は Prefill 側でも Attention と FFN の処理を切り分けてスケジューリングする FlowPrefill のような取り組みも登場しており、AFD を Prefill に広げる方向はありえます。

# DCP は decode の KV をシーケンス方向に分割

ようやく本題の DCP です。DCP が解こうとする問題は、TP だけでは KV キャッシュが複製されてしまうことにあります。

TP は KV キャッシュを attention head の単位で分割します。ところが KV head の数より TP の並列度が大きくなると、それ以上は分割できず、同じ KV を複数の GPU が重複して持つことになります。とくに KV を 1 つの潜在ベクトルに圧縮する MLA（Multi-head Latent Attention）では、KV が全 head で共有されます。そのため分割の余地がなく、TP が 2 以上になると全 GPU に複製されます。KV head を複数の Query head で共有する GQA（Grouped Query Attention）でも、TP 並列度が KV head 数を超えた分は複製になります。長いコンテキストほど KV キャッシュは巨大なので、複製はメモリを圧迫し、同時に捌けるリクエスト数を下げてしまいます。

![](https://vllm.ai/blog-assets/figures/2026-07-27-decode-context-parallelism/kv-parallelism-overview.svg)

DCP は KV を head ではなくシーケンス（トークン位置）の方向に分割します。20 万トークンのリクエストを 4 GPU で分けるなら、概念としては GPU 0 が前半、GPU 1 が後半、というふうにトークン位置で区切るイメージです。実際の vLLM 実装では、新しく生成されるトークンの KV が特定の GPU に偏らないよう、KV ブロックを GPU 間で交互に（インターリーブして）割り当てます。decode 時は各 GPU が完全なクエリと自分の担当区間の KV で attention を計算し、部分結果を online-softmax（log-sum-exp を使って部分結果を正しく合算する手法）でまとめます。これにより KV の複製がなくなり、メモリに余裕が生まれて同時実行数を伸ばせます。

vLLM ブログの計測では、8 枚の B200 で Kimi K2.6 を動かした場合に、TP ベースラインが同時実行 64 で 1 GPU あたり約 1,863 tok/s（KV メモリ使用率 100%）で頭打ちになるのに対し、DCP は同時実行 512 で 1 GPU あたり 6,091 tok/s に到達し、KV 使用率は 82% に留まったと報告されています。ポイントは速度そのものではなく、KV 複製の解消で同時実行数の上限が伸びる点です。同時実行数が違えばレイテンシの条件も変わるので、その前提で読んでください。

DCP は TP の弱点（KV 複製）を補う関係にありますが、掛け算で並列度が増える意味での直交ではありません。vLLM の実装では、DCP は TP グループ内の GPU を再利用して KV を分割するため、GPU を新たに足すわけではなく、TP の中に入れ子で定義されます。後半の星取表で DCP と TP を「入れ子」としたのはこのためです。

# 4技術は直交しているのか

ここまでの内容を踏まえて、最初の問いに戻ります。MoE、DCP、P/D 分離、AFD は直交しているのかという問いです。TP と EP も加えた全体像を、あらためて星取表で示します。

| 技術 | MoE | DCP | P/D | AFD | TP | EP |
|---|---|---|---|---|---|---|
| MoE | - | 直交 | 直交 | 相乗 | 直交 | 依存 |
| DCP | 直交 | - | 相乗 | 相乗 | 入れ子 | 直交 |
| P/D | 直交 | 相乗 | - | 直交 | 直交 | 直交 |
| AFD | 相乗 | 相乗 | 直交 | - | 直交 | 相乗 |
| TP | 直交 | 入れ子 | 直交 | 直交 | - | 直交 |
| EP | 依存 | 直交 | 直交 | 相乗 | 直交 | - |

MoE と DCP は直交です。MoE は FFN の構造の話、DCP は Attention 側の KV 分割の話で、無関係な別軸です。ただし DCP の主な適用先である MLA を採用するモデル（DeepSeek 系など）は MoE でもあることが多く、現実には共起しやすい点は補足しておきます。

DCP と P/D 分離、DCP と AFD はいずれも相乗です。DCP は decode の Attention を軽くする技術なので、P/D 分離が用意する decode 専用プールや、AFD が用意する Attention 専用プールと組み合わせると素直に効きます。

MoE と AFD、EP と AFD も相乗です。AFD で切り出した FFN プールを expert 並列にする動機がまさに MoE だからです。AFD 自体は Dense モデルにも定義できますが、MoE と組んだときに価値が大きくなります。

P/D 分離と AFD は直交です。片方はフェーズ（時間）で分け、もう片方はモジュール（機能）で分ける、異なる軸の分割なので、両方同時に適用できます。図で見たとおり、Decode プールをさらに AFD で割ることができます。

例外は 2 つだけです。EP は MoE がなければ成立しないので MoE に依存します。DCP は概念としては TP と別ですが、実装上は TP の中に入れ子で定義されます。この 2 点を除けば、4 つの技術は互いに直交していて、自由に組み合わせられます。

最後に注意点を 1 つ挙げます。概念上の直交は「実装で無料に合成できる」ことを意味しません。通信コストは非対称で、AFD は層ごとに activation を往復させるため頻度が高く、TP は層ごとの all-reduce、DCP は decode ステップごとの結果合算、P/D 分離は頻度こそリクエストあたり 1 回ですが転送量はコンテキスト長に比例して大きい、というように性質が違います。どの推論エンジンがどの組み合わせをサポートしているかも、また別の問題です。

調べた限りまだ SGLang は AFD に正式に対応していないようです。vLLM は正式に対応しており P/D 分離、MoE などと組み合わせることができそうなので今後フル構成を検証してみたいと思います。

# まとめ

DCP は decode 時の KV キャッシュをシーケンス方向に分割し、TP では避けられない KV 複製を解消して長いコンテキストの同時実行数を伸ばす並列化です。並列化は「GPU に何が載るか」で捉えると整理しやすく、TP は重み、DP はバッチ、CP と DCP はシーケンス、EP は expert を分割します。FFN の分割は Dense なら TP、MoE なら EP と手段が変わります。

推論サービスはフェーズで分ける P/D 分離と、モジュールで分ける AFD という直交する 2 軸でプールを構成でき、その中で TP や DCP や EP を使います。MoE、DCP、P/D 分離、AFD の 4 つは、EP が MoE に依存する点と DCP が実装上 TP に入れ子である点を除けば、互いに直交していて理論的には自由に組み合わせられます。
