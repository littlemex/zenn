## はじめに

vLLM のブログで [Decode Context Parallelism（DCP）](https://vllm.ai/blog/2026-08-07-decode-context-parallelism)が紹介されました。DCP は、長いコンテキストのリクエストを多数同時に処理するための並列化です。この記事では、並列化を GPU に何が載るかで整理してから DCP を説明し、MoE、DCP、P/D 分離、AFD の 4 つがどう組み合わさるかを表にまとめます。特定のフレームワークの対応状況ではなく、仕組みの関係を見るのが目的です。

## 全体の地図

先に結論を示します。MoE は FFN の構造を扱い、DCP は decode の KV キャッシュ（過去の token の Key と Value を保存しておく領域）の分け方を扱います。P/D 分離はフェーズで、AFD はモジュールで GPU のプールを分けます。扱う対象か分ける軸が違うので、4 つは仕組みの上で組み合わせを考えられます。TP と EP を加えると、EP は MoE を前提にし、vLLM で PCP（Prefill Context Parallelism）を使わない場合の DCP は TP の GPU のグループを使います。まず、それぞれが何を分けるかを一覧にします。

| 名前 | 分けるもの | 主に効く場面 |
|---|---|---|
| TP（Tensor 並列） | 重み | 1 枚に載らない重み |
| DP（Data 並列） | リクエスト | スループット |
| CP（Context 並列） | シーケンス | 長い入力 |
| EP（Expert 並列） | MoE の expert | MoE の FFN |
| SP（Sequence 並列） | TP の中の activation | activation のメモリ |
| P/D 分離 | prefill と decode の GPU | フェーズの性質の違い |
| AFD | Attention と FFN の GPU | decode の FFN の効率 |
| DCP | decode の KV キャッシュ | 長いコンテキストの同時実行数 |

## 並列化は GPU に何が載るかで見る

![4 つの GPU に、TP は重みの断片、DP は全部の重みと別々のリクエスト、CP はシーケンスの 4 分の 1、EP は expert を 1 つずつ、SP は TP の重みの断片と activation の 4 分の 1 を載せる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/45a492721a6235/zenn/articles/45a492721a6235/parallelism-map.png)

図は、4 つの GPU にそれぞれ何が載るかを、並列化ごとに並べたものです。TP は重みを分け、どの GPU も同じ token を見ます。DP は重みを全部複製し、GPU ごとに別のリクエストを処理します。CP は token の位置でシーケンスを分けます。EP は MoE の expert（小さな FFN）を GPU に配ります。SP は CP とは別物です。activation は、各層が計算して次の層へ渡す中間の値で、token ごとに 1 本のベクトルがあります。重みと違って入力ごとに作られ、token の数に比例して大きくなります。SP は、LayerNorm や Dropout のまわりの activation をシーケンスの方向に分けます。[Korthikanti らの論文](https://arxiv.org/abs/2205.05198)のとおり、SP は TP と同じ GPU のグループの中で TP と組み合わせて使います。

分けるものが違う並列化どうしは、同じモデルの中で組み合わせる構成を考えられます。たとえば重みを分ける TP と、シーケンスを分ける CP は同時に使えます。ただし、必要な GPU のグループや並列度、通信は方式と実装で決まります。

## FFN を分ける 2 つの単位: 重みの TP と expert の EP

![左は Dense の FFN を TP で分け、全部の GPU が全部の token の一部を計算して all-reduce で足す。右は MoE の FFN を EP で分け、router が選んだ expert の GPU にだけ token を送り、all-to-all で戻す](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/45a492721a6235/zenn/articles/45a492721a6235/ffn-tp-ep.gif)

Dense の FFN は大きな重み行列なので、TP で分けます。[Megatron-LM](https://arxiv.org/abs/1909.08053) の分け方では、1 つ目の行列を列で、2 つ目の行列を行で分けます。途中の結果は通信せずに次の行列へ渡せて、最後に 1 回の all-reduce で足し合わせます。どの GPU も、全部の token の一部を計算します。

MoE の FFN は、独立した expert の集まりです。EP は expert を丸ごと GPU に置きます。router（token ごとに使う expert を選ぶ部品）が選んだ expert の GPU にだけ token を送り、計算した結果を元の GPU に戻します。この通信を all-to-all と呼びます。EP は MoE の構造があって初めて成り立つので、EP は MoE に依存します。MoE でも、expert をどの GPU に置くかという EP の選択と、各 expert の重みをどう分けるかという TP の選択は別です。

## GPU のプールを分ける 2 つの軸

![8 つの GPU を prefill のプールと decode のプールに分け、decode のプールをさらに Attention の sub-pool（DCP で KV を 2 つに分ける）と FFN の sub-pool（EP で expert を 2 つずつ置く）に分ける。KV は prefill から decode へ 1 回だけ渡し、activation は層ごとに往復する](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/45a492721a6235/zenn/articles/45a492721a6235/pd-afd-deploy.png)

ここまでは、GPU のプールが 1 つの場合の話でした。推論サービスでは、プールそのものを役割ごとに分けます。分け方には 2 つの軸があります。上の図は、説明のために筆者が描いた構成です。prefill に GPU 0〜3、decode に GPU 4〜7 を割り当て、decode をさらに Attention と FFN に分けています。Attention の sub-pool では、後の節で説明する DCP で KV キャッシュを GPU 4 と GPU 5 に半分ずつ置きます。FFN の sub-pool では、EP で expert を GPU 6 と GPU 7 に 2 つずつ置きます。

1 つはフェーズで分ける P/D 分離です。入力をまとめて処理する prefill と、1 token ずつ生成する decode を、別々の GPU に置きます。[Splitwise](https://arxiv.org/abs/2311.18677) は、評価した推論で prefill を計算律速（compute-intensive）、decode をメモリ律速（memory-intensive）と特徴づけました。そのうえで、2 つのフェーズを別々のマシンに置きました。[DistServe](https://arxiv.org/abs/2401.09670) は、2 つのフェーズを同じ GPU で混ぜると互いに干渉することを示し、分けて置く方式を提案しました。

もう 1 つはモジュールで分ける AFD（Attention-FFN Disaggregation）です。AFD は、同じ層の Attention と FFN を別々の sub-pool に置きます。[MegaScale-Infer](https://arxiv.org/abs/2504.02263) は、MoE では token ごとに一部の expert しか使わないため、推論では FFN が計算律速からメモリ律速に変わると述べています。その結果、GPU の使用率が下がるとしています。

![prefill のプールが作った KV を decode の Attention の sub-pool に 1 回渡し、その後は層ごとに activation が Attention の sub-pool と FFN の sub-pool を往復する](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/45a492721a6235/zenn/articles/45a492721a6235/afd-layers.gif)

P/D 分離は、KV キャッシュをリクエストごとに 1 回渡します。AFD は、層ごとに activation を往復させます。ここで往復するのは、Attention の出力として FFN に渡す token ごとのベクトルと、FFN の出力として次の層の Attention に戻すベクトルです。上の GIF の 4 層は、往復を見せるために筆者が決めた数です。MegaScale-Infer は、層の中の Attention と FFN を分け、両者を別々に増減できるようにしました。さらに、バッチを micro-batch に分けて両者の間を往復させる ping-pong pipeline で、GPU の使用率を上げる方式を示しました。[Step-3](https://arxiv.org/abs/2507.19427) も、decode のコストを下げる仕組みとして AFD を使っています。

AFD は原理的には prefill にも定義できます。ここで紹介した MegaScale-Infer と Step-3 は、decode の効率を主な対象にしています。

## KV head が足りないと TP では KV が複製される

![MLA を TP=4 で動かすと 1 つの latent KV が 4 つの GPU に複製され、KV head が 2 つの GQA を TP=4 で動かすと各 head が 2 つずつ複製される。MLA を DCP=4、interleave が 1 で動かすと、各 GPU が token の 4 分の 1 を 4 つおきに持つ](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/45a492721a6235/zenn/articles/45a492721a6235/kv-duplication.png)

ここから DCP です。DCP が解く問題は、TP だけでは KV キャッシュが複製されることです。

KV head は、Key と Value のテンソルを 1 組ずつ持つ attention の計算の単位です。TP は KV キャッシュを KV head の単位で分けます。[GQA](https://arxiv.org/abs/2305.13245)（Grouped-Query Attention）は複数の query head で 1 つの KV head を共有するので、KV head の数は少なくなります。TP の並列度が KV head の数を超えると、それ以上は分けられず、同じ KV head を複数の GPU が持ちます。[DeepSeek-V2](https://arxiv.org/abs/2405.04434) が導入した MLA（Multi-head Latent Attention）は、KV キャッシュを 1 つの latent ベクトルに圧縮し、すべての query head で共有します。KV head が実質 1 つなので、TP の全部の GPU に同じ KV キャッシュが複製されます。長いコンテキストほど KV キャッシュは大きいので、複製がメモリを圧迫し、同時に処理できるリクエストの数を減らします。図の GQA は KV head が 2 つで TP=4 の例で、各 KV head は $4 / 2 = 2$ 個ずつ複製されます。

## DCP: KV を token の位置で分ける

![新しい token の query を全部の GPU に集め、各 GPU が自分の持つ KV だけで attention を計算し、部分結果を LSE で重み付けして足し、新しい token の KV を GPU 12 mod 4 = 0 に足す](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/45a492721a6235/zenn/articles/45a492721a6235/dcp-decode.gif)

**DCP は、KV キャッシュを head ではなく token の位置で分け、各 GPU が自分の持つ token の KV だけを読むようにします**。vLLM ブログの説明では、標準の DCP は、decode の 1 ステップごとに、各層で次の 3 つを行います。上の GIF の場面 1〜3 が、この 3 つに対応します。

1. query の all-gather: 各 GPU が計算した query の一部を all-gather で集め、全部の GPU が新しい token の query をそろえます。decode では query が 1 token 分なので、この通信は小さく済みます。
2. 自分の KV での attention の計算: 各 GPU は、集めた query と自分の KV で attention を計算します。
3. 部分結果の合算: 各 GPU の部分結果と LSE（log-sum-exp、softmax の分母の対数）を集め、LSE で重みを補正して足し合わせます。ブログはこの合わせ方を online-softmax trick と呼んでいます。softmax の正規化を 1 回の走査で求める方法は [Milakov と Gimelshein](https://arxiv.org/abs/1805.02867) が提案しました。

[ブログが説明する標準の手順](https://vllm.ai/blog/2026-08-07-decode-context-parallelism)では、all-gather と reduce-scatter で部分結果を合わせ、各 GPU に担当する head の出力を返します。GIF の場面 3 は合算を 1 つにまとめて描き、出力の配り方は省いています。

ブログは説明として、20 万 token を 4 つの GPU に 5 万 token ずつ区切って置く例を挙げています。vLLM の実際の置き方は設定で変わります。GIF の場面 4 と、前の節の図にある DCP の列は、コードの定義から描いたものです。描いた設定は、DCP の並列度が 4、[cp_kv_cache_interleave_size](https://github.com/vllm-project/vllm/blob/c41b2639e29c3bc01add1d34bef3032a6d9d8aca/vllm/config/parallel.py#L414) が 1 の場合です。この場合、token $i$ の KV は GPU $i \bmod 4$ に置かれ、token 12 の KV は GPU 0 に入ります。新しく生成した token の KV が順番に別の GPU へ入るので、特定の GPU に偏りません。

vLLM では、PCP を使わない場合、DCP は TP のグループにある GPU をそのまま使います（[parallel.py の定義](https://github.com/vllm-project/vllm/blob/c41b2639e29c3bc01add1d34bef3032a6d9d8aca/vllm/config/parallel.py#L380)）。DCP のために新しい GPU は足しません。そのため、この場合の DCP は TP の中に入れ子で定義されます。

DCP と AFD は、FFN をどの GPU で計算するかが違います。[vLLM ブログ](https://vllm.ai/blog/2026-08-07-decode-context-parallelism)の構成では、Attention で KV キャッシュを分担した同じ GPU が、続く FFN の計算にも使われます。AFD は、Attention と FFN を別々の GPU のプールに置きます。

DCP の並列度には、モデルの種類ごとに条件があります。条件は [vLLM ブログ](https://vllm.ai/blog/2026-08-07-decode-context-parallelism)にあります。$\text{TP}$ と $\text{DCP}$ は並列度、$H$ は KV head の数です。

| モデル | 条件 | ブログの例 |
|---|---|---|
| MLA | $\text{TP} \ge \text{DCP}$ かつ $\text{TP} \bmod \text{DCP} = 0$ | DeepSeek-R1 を TP=8、DCP=8 |
| GQA | 複製の数 $R = \lfloor \text{TP} / H \rfloor$ について、$R \ge \text{DCP}$ かつ $R \bmod \text{DCP} = 0$ | Qwen3-235B（$H = 4$）を TP=8 にすると複製は $8 / 4 = 2$ で、DCP は 2 まで |

## vLLM の計測

![vLLM のブログの報告値で、TP は同時実行数 64 で KV キャッシュのメモリ使用率が 100% になり、そのときの 1 GPU あたりのスループットが約 1,863 tok/s で、DCP は同時実行数 512 で 1 GPU あたり 6,091 tok/s、KV キャッシュのメモリ使用率は 82% だった](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/45a492721a6235/zenn/articles/45a492721a6235/vllm-result.png)

[vLLM のブログ](https://vllm.ai/blog/2026-08-07-decode-context-parallelism)の計測の条件は次のとおりです。

| 項目 | 値 |
|---|---|
| GPU | B200 × 8（1 ノード） |
| モデル | Kimi K2.6（NVFP4） |
| 入力と出力 | 入力は中央値で約 67k token、出力は約 400 token（agentic な長いコンテキストの trace） |
| 同時実行 | 16 から 512 |

DCP は、計測した同時実行数の上限である 512 で 1 GPU あたり 6,091 tok/s に達し、そのときの KV キャッシュのメモリ使用率は 82% でした。TP だけの構成は同時実行数 64 で KV キャッシュのメモリ使用率が 100% に達し、そのときの 1 GPU あたりのスループットは約 1,863 tok/s でした。図の値はブログの報告値で、筆者は再現していません。

ブログは、DCP で GPU あたりの KV キャッシュの量が減り、より多くのリクエストを載せられることを、この差の主な理由として説明しています。この計測だけでは、計算の時間と通信の時間がそれぞれどれだけ効いたかは分かりません。また 2 つの値は、同時実行数が 64 と 512 という違う条件で測ったもので、1 リクエストあたりの待ち時間の条件も違います。

## 4 つの技術の関係

次の表は、筆者が仕組みの関係を整理したもので、実装の対応表ではありません。DCP と TP の入れ子は、vLLM で PCP を使わない場合の関係です。

| 技術 | MoE | DCP | P/D | AFD | TP | EP |
|---|---|---|---|---|---|---|
| MoE | - | 直交 | 直交 | 相乗 | 直交 | 依存 |
| DCP | 直交 | - | 相乗 | 相乗 | 入れ子 | 直交 |
| P/D | 直交 | 相乗 | - | 直交 | 直交 | 直交 |
| AFD | 相乗 | 相乗 | 直交 | - | 直交 | 相乗 |
| TP | 直交 | 入れ子 | 直交 | 直交 | - | 直交 |
| EP | 依存 | 直交 | 直交 | 相乗 | 直交 | - |

表の言葉の意味は次のとおりです。

| 言葉 | 意味 |
|---|---|
| 直交 | 分ける対象か役割が違い、片方がもう片方の成り立つ条件ではない |
| 相乗 | 直交のうち、組み合わせる動機が特に強い |
| 依存 | 片方がもう片方を前提にする |
| 入れ子 | 仕組みは別でも、実装では片方の中に定義される |

MoE と DCP は直交です。MoE は FFN の構造、DCP は Attention の KV キャッシュの分け方の話です。一方で、DCP がよく効く MLA と MoE は、同じモデルに一緒に現れることがあります。[DeepSeek-V2](https://arxiv.org/abs/2405.04434) は MLA と MoE の両方を採用しています。

DCP と P/D 分離、DCP と AFD は相乗です。DCP は decode の KV キャッシュを分けて、メモリに余裕を作ります。そのため、P/D 分離が作る decode のプールや、AFD が作る Attention の sub-pool で DCP を使う構成が考えられます。効果は、通信と、各プールに資源をどう配るかで変わります。ここで引いた資料は、この組み合わせによる性能の向上を示していません。表で DCP に付けた相乗は、組み合わせる動機の強さを表します。

MoE と AFD、EP と AFD も相乗です。AFD は Dense の FFN と Attention を分ける構成にも定義できるので、MoE を前提にしません。MoE と組み合わせると、分けた FFN の sub-pool に expert を置けます。「GPU のプールを分ける 2 つの軸」の節で紹介した MegaScale-Infer が、この組み合わせで GPU の使用率を上げた例です。表の相乗は、このように配置と通信を設計した場合の関係です。

P/D 分離と AFD は直交です。フェーズで分ける軸とモジュールで分ける軸なので、仕組みの上では両方を同時に使う構成を描けます。

本文で触れていない直交の欄は、分ける単位が違い、片方がもう片方の条件にならないことを表します。MoE と TP、TP と EP が直交なのは、FFN の節で見たとおり、expert の置き方と重みの分け方が別の選択だからです。P/D 分離と EP が直交なのは、P/D 分離がフェーズの置き場所を決め、EP が各フェーズで使う expert の置き場所を決めるからです。DCP と EP が直交なのは、KV キャッシュを token の位置で分ける操作と、expert を置く操作が互いに依存しないからです。「GPU のプールを分ける 2 つの軸」の節の構成図は、この 2 つを AFD で分けた別々の sub-pool に置いた例で、同じ GPU のグループでの併用やそのコストを示したものではありません。

表で直交と相乗以外にした関係は 2 つです。EP は MoE を前提にします。また vLLM で PCP を使わない場合、DCP は TP のグループの中に定義されます。

ただし、仕組みの上で組み合わせられることは、実装で追加のコストなしに組み合わせられることを意味しません。通信の頻度と量が違うからです。AFD は層ごとに activation を往復させ、TP は層ごとに all-reduce をします。DCP は decode の 1 ステップの中で、Attention の層ごとに query を集め、部分結果を合わせます。P/D 分離はリクエストごとに 1 回ですが、コンテキストの長さに比例した量の KV キャッシュを送ります。

## まとめ

DCP は、decode の KV キャッシュを token の位置で分ける並列化です。MLA と、TP の並列度が KV head の数を超える GQA では、TP だけだと KV キャッシュが複製されます。DCP はこの複製を減らし、長いコンテキストのリクエストをより多く同時に処理できるようにします。TP と EP を加えた関係の表のうち、直交と相乗以外の関係は 2 つです。EP は MoE を前提にし（依存）、vLLM で PCP を使わない場合は DCP が TP のグループの中に定義されます（入れ子）。
