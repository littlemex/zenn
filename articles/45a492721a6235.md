# はじめに

vLLM のブログで [Decode Context Parallelism（DCP）](https://vllm.ai/blog/2026-08-07-decode-context-parallelism) という新しい並列化が紹介されました。長いコンテキストを高スループットで捌くための工夫ですが、読み進めると MoE や P/D 分離、AFD といった用語が次々に出てきて、初学者にはそれぞれがどう関係するのか分かりづらいです。

この記事では、DCP を理解する前提として並列化の全体像を GPU への割り当てで整理し、そのうえで MoE、DCP、P/D Disaggregated Inference、AFD（Attention-FFN Disaggregation）の4つが概念上どういう関係にあるのかを星取表で示します。TP や EP との関係にも触れ、最後に「この4つは互いに直交しているのか」という問いに答えます。実装の細部ではなく、概念のレベルで捉えることを目的にしています。

# 結論を先に示すと4つは直交しています

先に結論だけ置きます。MoE、DCP、P/D 分離、AFD は、どれも他の技術を前提にしているわけではなく、対ごとに見て直交（独立に組み合わせられる）しています。TP と EP を加えても、EP だけが MoE を前提にする例外です。

| 技術 | MoE | DCP | P/D | AFD | TP | EP |
|---|---|---|---|---|---|---|
| MoE | 同一 | 直交 | 直交 | 相乗 | 直交 | 依存 |
| DCP | 直交 | 同一 | 相乗 | 相乗 | 入れ子 | 直交 |
| P/D | 直交 | 相乗 | 同一 | 直交 | 直交 | 直交 |
| AFD | 相乗 | 相乗 | 直交 | 同一 | 直交 | 相乗 |
| TP | 直交 | 入れ子 | 直交 | 直交 | 同一 | 直交 |
| EP | 依存 | 直交 | 直交 | 相乗 | 直交 | 同一 |

表の言葉の意味は次のとおりです。「直交」は互いに独立で自由に併用できる関係、「相乗」は独立でありながら組み合わせると特に効果が高い関係、「依存」は片方がもう片方を前提とする関係、「入れ子」は概念は別だが実装上は片方の中に定義される関係を指します。

なぜこう言えるのかを、並列化の基礎から順に見ていきます。

# 並列化はGPUに何が載るかで理解できます

並列化の種類は名前だけ覚えると混乱しますが、「GPU 0 から 3 に何が載るか」を見ると一気に整理できます。分割する対象が、重みなのか、バッチなのか、シーケンスなのか、expert なのかで種類が決まります。

![並列化を GPU アロケーションで理解する](/images/45a492721a6235-fig-parallelism.png)

TP（Tensor 並列）は 1 枚に載らない大きな重みを分割し、どの GPU も同じトークンを見ます。DP（データ並列）は逆に重みを全複製し、リクエストを GPU ごとに分けてスループットを台数分に伸ばします。CP（Context 並列）は、まさに「シーケンスの 4 分の 1 が 1 GPU に載る」形で、トークン位置の方向にシーケンスを分割します。EP（Expert 並列）は MoE の expert を GPU に配ります。SP（Sequence 並列）は Megatron が使う手法で、LayerNorm や Dropout 周りの activation をシーケンス方向に分割してメモリを削るもので、CP とは別物です。

ここで大事なのは、これらが「何を分割するか」という別々の軸に乗っている点です。重みを割る TP と、シーケンスを割る CP は、同時に使えます。だから並列化どうしは基本的に掛け合わせられます。

# FFNの分割はDenseとMoEで別物になります

並列化の中で初学者がいちばん混乱しやすいのが、FFN と MoE と EP の関係です。ここは分けて理解する価値があります。

![FFN の分割は Dense と MoE で別物になる](/images/45a492721a6235-fig-ffn-moe.png)

Dense な FFN は 1 つの大きな重み行列です。これを分割するときは TP を使い、行列を列で 4 分割して各 GPU に配ります。どの GPU も全トークンを部分的に計算し、最後に all-reduce で合算します。

一方 MoE の FFN は、独立した複数の expert（小さな FFN）の集まりです。これを分割するのが EP で、expert を丸ごと GPU に配置します。トークンは router が選んだ expert を持つ GPU にだけ送られ（all-to-all 通信）、全部の GPU を通るわけではありません。

つまり同じ「FFN の分割」でも、Dense なら TP、MoE なら EP と手段が変わります。EP は MoE という構造があって初めて成立するので、EP だけは MoE に依存します。これが星取表で EP と MoE を「依存」とした理由です。

# 推論は2つの軸で切り分けられます

ここまでが 1 台のプールの中の話でした。実際の LLM 推論サービスは、GPU プールそのものを分けて役割を持たせます。分け方には直交する 2 つの軸があります。

1 つはフェーズで分ける P/D Disaggregated Inference（Prefill/Decode 分離）です。入力全体を一括で処理する Prefill は計算が重く（compute-bound）、1 トークンずつ生成する Decode はメモリ帯域が効きます（memory-bound）。性質が違うので、別々の GPU プールに分けてそれぞれ最適化します。

もう 1 つはモジュールで分ける AFD（Attention-FFN Disaggregation）です。Attention は KV キャッシュを読むメモリ律速の処理、FFN や MoE は行列積が重い処理なので、これも別々のプールに分けられます。

![実デプロイ例として P/D 分離と AFD で 8 GPU を割り当てる](/images/45a492721a6235-fig-deploy.png)

この 2 軸は独立です。図では Prefill プール（GPU 0 から 3）で入力を処理し、KV キャッシュを Decode プール（GPU 4 から 7）へ転送します。この転送の境目が P/D 分離です。Decode プールの中はさらに AFD で Attention サブプールと FFN サブプールに分かれ、層ごとに activation を往復させます。Attention サブプールでは後述する DCP で KV を分割し、FFN サブプールでは EP で expert を分割します。1 枚の図の中に、これまで出てきた並列化が自然に収まっている点に注目してください。

なお AFD は decode 専用の技術ではありません。原理的には Prefill 側でも Attention と FFN を分離できます。これまで実運用で主に Decode 側で使われてきたのは、Prefill が Attention も FFN も計算律速で、層ごとに activation を往復させる通信コストに見合いにくいと考えられてきたためです。もっとも最近は Prefill 側でも Attention と FFN の処理を切り分けてスケジューリングする FlowPrefill のような取り組みも登場しており、AFD を Prefill に広げる方向は活発に研究されています。

# DCPはdecodeのKVをシーケンス方向に分割します

ようやく本題の DCP です。DCP が解こうとする問題は、TP だけでは KV キャッシュが複製されてしまうことにあります。

TP は KV キャッシュを attention head の単位で分割します。ところが head 数より TP の並列度が大きくなると、それ以上は分割できず、同じ KV を複数の GPU が重複して持つことになります。とくに KV を 1 つの潜在ベクトルに圧縮する MLA（Multi-head Latent Attention）や、KV head が少ない GQA で TP 並列度が head 数を超える場合に、この複製が起きます。長いコンテキストほど KV キャッシュは巨大なので、複製はメモリを圧迫し、同時に捌けるリクエスト数を下げてしまいます。

DCP は KV を head ではなくシーケンス（トークン位置）の方向に分割します。20 万トークンのリクエストを 4 GPU で分けるなら、GPU 0 が先頭から 5 万、GPU 1 が次の 5 万、という具合です。decode 時は各 GPU が完全なクエリと自分の担当区間の KV でattention を計算し、部分結果を online-softmax（LSE の再重み付け）で合算します。これにより KV の複製がなくなり、メモリに余裕が生まれて同時実行数を伸ばせます。

vLLM ブログの計測では、8 枚の B200 で Kimi K2.6 を動かした場合に、TP ベースラインが同時実行 64 で 1 GPU あたり約 1,863 tok/s（KV メモリ使用率 100 パーセント）で頭打ちになるのに対し、DCP は同時実行 512 で 1 GPU あたり 6,091 tok/s に到達し、KV 使用率は 82 パーセントに留まったと報告されています。これは引用であり、筆者が再現した数値ではありません。

DCP は TP の弱点（KV 複製）を補う関係にありますが、掛け算で並列度が増える意味での直交ではありません。vLLM の実装では、DCP は TP グループ内の GPU を再利用して KV を分割するため、GPU を新たに足すわけではなく、TP の中に入れ子で定義されます。星取表で DCP と TP を「入れ子」としたのはこのためです。

# 4技術は直交しているのか

ここまでの内容を踏まえて、最初の問いに戻ります。MoE、DCP、P/D 分離、AFD は直交しているのかという問いです。

MoE と DCP は直交です。MoE は FFN の構造の話、DCP は Attention 側の KV 分割の話で、無関係な別軸です。ただし DCP の主な適用先である MLA を採用するモデル（DeepSeek 系など）は MoE でもあることが多く、現実には共起しやすい点は補足しておきます。

DCP と P/D 分離、DCP と AFD はいずれも相乗です。DCP は decode の Attention を軽くする技術なので、P/D 分離が用意する decode 専用プールや、AFD が用意する Attention 専用プールと組み合わせると素直に効きます。

MoE と AFD、EP と AFD も相乗です。AFD で切り出した FFN プールを expert 並列にする動機がまさに MoE だからです。AFD 自体は Dense モデルにも定義できますが、MoE と組んだときに価値が大きくなります。

P/D 分離と AFD は直交です。片方はフェーズ（時間）で分け、もう片方はモジュール（機能）で分ける、異なる軸の分割なので、両方同時に適用できます。図で見たとおり、Decode プールをさらに AFD で割ることができます。

例外は 2 つだけです。EP は MoE がなければ成立しないので MoE に依存します。DCP は概念としては TP と別ですが、実装上は TP の中に入れ子で定義されます。この 2 点を除けば、4 つの技術は互いに直交していて、自由に組み合わせられます。

最後に注意点を 1 つ挙げます。概念上の直交は「実装で無料に合成できる」ことを意味しません。通信コストは非対称で、AFD は層ごとに activation を往復させるため頻度が高く、TP は層ごとの all-reduce、DCP は decode ステップごとの結果合算、P/D 分離はリクエストあたり 1 回の KV 転送、というように性質が違います。どの推論エンジンがどの組み合わせをサポートしているかも、また別の問題です。

# まとめ

DCP は decode 時の KV キャッシュをシーケンス方向に分割し、TP では避けられない KV 複製を解消して長いコンテキストの同時実行数を伸ばす並列化です。並列化は「GPU に何が載るか」で捉えると整理しやすく、TP は重み、DP はバッチ、CP と DCP はシーケンス、EP は expert を分割します。FFN の分割は Dense なら TP、MoE なら EP と手段が変わります。

推論サービスはフェーズで分ける P/D 分離と、モジュールで分ける AFD という直交する 2 軸でプールを構成でき、その中で TP や DCP や EP を使います。MoE、DCP、P/D 分離、AFD の 4 つは、EP が MoE に依存する点と DCP が実装上 TP に入れ子である点を除けば、互いに直交していて自由に組み合わせられます。まずはこの見取り図を持っておくと、[vLLM の DCP ブログ](https://vllm.ai/blog/2026-08-07-decode-context-parallelism)も読み進めやすくなるはずです。
