# はじめに

NVIDIA GPU と AWS Trainium を同じ Amazon EKS クラスタに同居させ、分散学習と推論を動的に回す基盤を Terraform で構築しました。その手順を Zenn book にまとめています。無料で全章公開しています。

https://zenn.dev/littlemex/books/eks-distributed-ai

分散学習を Kubernetes で回す構成例そのものは、AWS 公式の [awslabs/awsome-distributed-ai](https://github.com/awslabs/awsome-distributed-ai) をはじめいくつも公開されています。ただしそれらは動く構成を示すもので、その設定を外すと何が起きるのかは書かれていません。この book が残そうとしたのはそちらです。設定を 1 つ間違えたときにどんな症状が出て、どこを見れば原因に辿り着けるのか、という対応関係を実機で踏んだ形で書いています。

この記事は book の短い紹介です。コードの解説はせず、なぜこの基盤が必要だったのか、何が難しかったのかだけをお伝えします。

# 誰向けで、何ができるようになるのか

Terraform と Kubernetes の基本操作を知っている方を想定しています。ML の知識は前提にしていません。

Basic01 から Basic11 まで進めると、GPU と Trainium のノードを要求に応じて起動・回収するクラスタが手に入ります。その上で 2 ノードにまたがる分散学習 (DDP) と vLLM による推論サービングが動き、GPU メトリクスが Grafana で見え、最後に課金を残さず破棄できる状態になります。

一方で扱っていないこともあります。本番運用のマルチテナンシー、gang scheduling を要する大規模ジョブのスケジューリング設計、そして強化学習のループそのものは範囲外です。この book が用意するのはそれらを載せる土台までです。

費用について先に書いておきます。Basic02 までは GPU を使わないので、CPU ノード数台分の数百円規模で試せます。GPU を使う Basic04 以降は、GPU インスタンスの単価がそのままかかります。Capacity Block を扱う Basic05 は予約の前払いが必要で、インスタンスタイプによって数百ドルから数千ドルの規模になります。ここは無理に実機で追わず、読むだけでも設計は掴めるように書きました。

# なぜ Amazon EKS を選んだのか

分散学習の基盤というと、まず Slurm ベースの HPC クラスタが思い浮かびます。大きな学習ジョブを 1 本、長時間流す用途では Slurm は非常に強力です。

出発点になったのは LLM 向けの強化学習でした。GRPO のような強化学習アルゴリズムは、現在のポリシーで大量のサンプルを生成する rollout のフェーズと、そのサンプルでモデルを更新する学習のフェーズをループで回します。どちらもスループット重視ですが、動くソフトウェアは推論エンジンと学習フレームワークで別物です。しかも両者の間で重みを同期し続けます。ここに低レイテンシの推論サービングまで同じ基盤で動かしたい、という要求が加わります。

つまり、性質の異なる複数のワークロードが同じクラスタに同居し、それぞれが必要なときだけ資源を掴んで返す、という形になります。Kubernetes を選んだのは、推論サーバーを Deployment、学習ジョブを Job や TrainJob として、常駐するものと使い捨てるものを同じ宣言的 API で扱えるからです。加えて Karpenter によるノードの動的確保、Kubeflow Trainer による分散学習、Prometheus による可観測性といった周辺のエコシステムがそのまま使えます。

# 実際に組んでみて難しかったこと

設計方針が決まっても、手を動かすと通常の Web アプリ向けクラスタでは出会わない問題に次々ぶつかります。性質の違うものを 3 つ挙げます。

## 動いているように見えて動かない

いちばん厄介なのがこの類です。EFA (Elastic Fabric Adapter) のセキュリティグループ設定を取りこぼすと、NCCL (GPU 間の集合通信ライブラリ) のブートストラップは成功して「EFA を選んだ」とログに出るのに、実際のデータ転送でハングします。ログが正常を報告するので、切り分けの入口が見つかりません。

似た形の罠は他にもありました。セキュリティグループの既定値が原因で、ポート 80 のような低いポートで listen する Pod への通信が、別ノードからだけ落ちるケースです。同じノードで動く kubelet の readiness probe はセキュリティグループを通らないので成功し続け、Pod は Ready に見えたままになります。この 2 つは症状も原因も違いますが、「ログと実態が食い違う」という点だけが共通しています。book では、この種の問題をどのログのどの行から辿ったのかを書いています。

## 数え方を間違えると永遠に起動しない

EFA では、インスタンスの物理ネットワークカードの枚数と、Pod が要求できる EFA の枚数が一致しないことがあります。この基盤はカード 0 番をノードの IP 用に残す構成を採っているため、p5en.48xlarge の 16 枚に対して Pod が要求できるのは 15 枚です。ここを 16 と書くと Pod は永遠に Pending のままになります。

重要なのは、この数がインスタンスタイプと構成の両方に依存することです。普遍的な計算式があるわけではないので、この book では枚数を Terraform の output として算出し、ノードの `allocatable` を実際に読んで確認する手順を入れました。同種の話として VPC CNI による IP 消費もあり、こちらはサブネットを大きく取ることで回避しています。

## 消したつもりで課金が続く

高額なリソースを扱う基盤では、破棄が構築と同じくらい重要になります。難しいのは、Kubernetes オブジェクトの削除と、コントローラが管理する EC2 インスタンスの終了が非同期であることです。破棄順序を誤って Karpenter を先に消すと、ノードを終了させる主体がいなくなり、インスタンスだけが取り残されて課金が続きます。

この落とし穴は 1 つではありませんでした。たとえば Ingress を削除してから Application Load Balancer が実際に消えるまでの待ち時間を、当初は 20 秒の固定値にしていました。実測ではロードバランサの削除に数分かかり、その間にコントローラを破棄してしまうため、ロードバランサが取り残されます。しかもその ENI がサブネットを掴んで離さず、破棄全体が 18 分待たされた末に失敗しました。固定時間の待ちをやめ、実際に消えたことをポーリングで確認する形に直しています。book では、この手の失敗を実測値とともに残しました。

# Trainium も同じ枠組みに乗せる

GPU と Trainium を同じクラスタで扱うのがこの基盤の特徴です。設計としては、両者を「taint の key が違うだけの同じ形のノード」として 1 つの型で表現し、`device_plugin` に `nvidia` か `neuron` を書くだけでどちらのプールも作れるようにしました。GPU 専用の分岐は書いていません。

Trainium 側は trn2.48xlarge を 2 台束ねた EFA 越しのマルチノード DDP まで実機で確認しています。この過程では、ノード側のドライバとコンテナ内の Neuron ランタイムのバージョン差に起因する、エラーメッセージから原因が読み取れない失敗も踏みました。そのあたりも症状と原因の対応で書いています。

# GPU を使わずに分散学習を体験する章

いきなり GPU に進まなくてもよいように、Basic02 は GPU を一切使いません。CPU ノードの上で MNIST の DDP (PyTorch の分散データ並列) を動かし、複数プロセスが勾配を共有して 1 つのモデルを学習する様子を確認します。

ここでは `torchrun` と Kubeflow Trainer v2 の TrainJob という 2 つの起動方法を比べ、単一ノード内の並列と複数ノードへの分散がどう違うのかを押さえます。共有ストレージの PVC を意図的に削除して、静的にプロビジョニングされた PersistentVolume が二度と bind できなくなる状態を再現し、そこから復旧する手順も体験します。高額な資源に進む前に、こうした Kubernetes 側の癖をわずかなコストで踏んでおける章にしました。

:::message alert
この book が構築する Amazon EKS クラスタ・GPU/Trainium ノード・NAT ゲートウェイ・Amazon FSx などは、起動している間 AWS 利用料金が発生します。実験が終わったら必ず破棄してください。
:::

# おわりに

この book がカバーするのは、基盤の構築と単一クラスタでの分散学習・推論の疎通確認までです。本番運用のマルチテナンシーやスケジューリング設計は扱っていません。インスタンスタイプや載せるアプリケーションによって、手を入れるべき部分も残っています。

一方で、EFA の設定漏れ、EFA 枚数の数え方、破棄順序といった落とし穴については、症状と原因の対応を実機で確認した形で残しました。同じ構成を組む方の時間を確実に節約できると思います。
