## はじめに

分離推論は、プロンプトを読む prefill と、出力を 1 トークンずつ作る decode を、別の GPU のインスタンスで動かす構成です。prefill は、プロンプトの各トークンについて attention の key と value を計算し、KV キャッシュとして GPU メモリに置きます。decode はこれを毎ステップ読むので、KV キャッシュが decode の GPU メモリに届くまで、最初のトークンを出せません。この転送の時間は、TTFT、つまり最初のトークンが出るまでの時間に足されます。

vLLM では、KV キャッシュの転送をコネクタと呼ぶ部品が受け持ちます。その下で、[NIXL](https://github.com/ai-dynamo/nixl) というライブラリが 2 つのプロセスのメモリの間でデータを運びます。vLLM の公式ブログは 2026 年 10 月 14 日に、prefill が decode へ書き込む [push 型の NIXL コネクタ](https://vllm.ai/blog/2026-10-14-nixl-push-connector)を紹介しました。ブログの測定では、Qwen3-32B に毎秒 8 リクエスト、入力 16,000 トークンを流したとき、decode が取りに行く従来の pull 型と比べて、TTFT が 1,744 ms から約 540 ms に縮んでいます。

ただ、push と pull の話には、別々の問いが混ざりがちです。SGLang も、NIXL か Mooncake で転送するときは prefill が書き込む方式ですが、vLLM と違って、プロンプトを区切って計算するたびに、出来た分の KV を送れます。また、同じ書き込みの操作でも、EC2 のインスタンスタイプや、同じノードの中か外かによって、ネットワークの上のやりとりが変わります。この記事では、KV の転送を 3 つの問いに分けて push と pull の得失を整理し、vLLM と SGLang の実装を並べます。そのうえで、NIXL の読み出しと書き込みの違いを実装で確かめます。

RDMA の one-sided の操作、GPU メモリの NIC への登録、GPUDirect RDMA、EFA の SRD は「[GPUDirect RDMA 入門](https://zenn.dev/tosshi/articles/42f0ee03b328a4)」で説明しています。同じノードの GPU どうしで共有メモリを通してデータを写す仕組みは「[EFA の同じノード内の GPU 間通信](https://zenn.dev/tosshi/articles/741e79cf2e9bf2)」で説明しています。この記事ではこの 2 つを前提にします。

## KV の転送を 3 つの問いに分ける

KV の転送では、router がリクエストを prefill と decode に届け、prefill が KV を作り、NIXL が KV を decode の GPU メモリへ運びます。この転送の性質は、誰が転送を始めるか、いつから送るか、どの経路で運ぶか、の 3 つの問いへの答えで決まります。

## 誰が転送を始めるか

pull は、decode が prefill の GPU メモリを読みに行く方式です。push は、prefill が decode の GPU メモリに書き込む方式です。push と pull が決めるのは転送を始める側だけで、decode をいつ選ぶかや受け取り先をいつ確保するかは別に決められますが、vLLM のブログが比べた 2 つの構成では、これらの時点も一緒に変わります。

*出典: [vLLM Blog, "NIXL Push Connector"](https://vllm.ai/blog/2026-10-14-nixl-push-connector) の Timing Comparison の図*

上の段の pull では、prefill の計算の後に、router の中継、decode の確保と準備、READ が一列に並びます。下の段の push では、それらが prefill の計算と同時に進み、prefill の後に残るのは WRITE だけです。

TPOT は、出力を 1 トークン作るのにかかる時間です。ブログは、入力 16,000 トークン、毎秒 4〜8 リクエストの条件で、TPOT が pull の約 10.4 ms から push の約 7 ms に縮んだと報告しています。decode は、動いている全リクエストの次のトークンを、1 回のステップでまとめて計算します。vLLM の pull 型では、[このステップの初めに READ を出す処理](https://github.com/vllm-project/vllm/blob/955f85be04b6250d26e6915e26bdf6720fbc8258/vllm/distributed/kv_transfer/kv_connector/v1/nixl/pull_worker.py#L49-L108)が入ります。push 型では、push に関わる NIXL の操作を[専用のスレッド](https://github.com/vllm-project/vllm/blob/955f85be04b6250d26e6915e26bdf6720fbc8258/vllm/distributed/kv_transfer/kv_connector/v1/nixl/push_worker.py#L1-L40)が受け持ち、prefill 側では WRITE を出し、decode 側では登録を送ります。ブログは、転送の準備を decode の生成の流れから外したことを、TPOT が縮んだ理由に挙げています。

ブログの値は、p5en.48xlarge を prefill と decode に 1 台ずつ、テンソル並列 8、bfloat16、NIXL の LIBFABRIC バックエンド、出力 128 トークンで測ったものです。入力は 1,000〜16,000 トークン、負荷は毎秒 1〜8 リクエストの範囲で変えています。この記事の筆者が測った値ではありません。

## push と pull の得失

push は、decode の登録が prefill の計算の間に済めば、prefill の後に要る準備を減らせます。その代わり、送り先の decode を prefill の前に決め、prefill の間も decode のメモリを確保しておく必要があります。ブログ自身も、prefill の後に負荷を見て decode を選びたい場合は pull が向くと書いています。次の表は、vLLM のブログが比べた構成での得失です。

| 観点 | pull | push |
|---|---|---|
| prefill の後に並ぶ仕事 | 在りかの中継、decode の確保、READ | 登録が先に届いていれば WRITE だけ |
| decode を選ぶ時点 | prefill が終わってから選ぶこともできる | prefill を始める時点で決める |
| decode のメモリ | 転送の直前に確保する | prefill の間ずっと確保したまま待つ |
| prefill のメモリ | decode が読み終えて知らせてくるまで残す | 自分が出した書き込みが終わるまで残す |
| 転送を出す場所 | decode。vLLM では生成と同じステップの中で出す | prefill。vLLM では専用のスレッドで出す |

pull では、decode が来ないまま prefill に KV が残り続けないよう、vLLM は既定で 30 秒の期限を付けて KV を残し、decode からの合図で期限を延ばします。詳しくは [vLLM の設計文書](https://github.com/vllm-project/vllm/blob/955f85be04b6250d26e6915e26bdf6720fbc8258/docs/design/nixl_kv_cache_lease.md)にあります。

push で decode のメモリを長く押さえる問題に対して、SGLang は decode がブロックを確保する時点を選べるようにしています。[既定](https://github.com/sgl-project/sglang/blob/0de06898bdb266e8164d3cf84bf8e3c71092cc93/python/sglang/srt/arg_groups/fields/disagg.py#L59-L64)では、decode は prefill の終わりを待たずに確保します。設定で、prefill が終わるまで KV を prefill に残し、その後で decode が確保するようにも変えられます。後者では decode のメモリが空く代わりに、次の節のチャンクごとの送信ができなくなります。

前のチャンクの転送が次のチャンクの計算の間に終われば、最初のトークンの前に残るのは、最後のチャンクの転送だけになります。図の箱の長さは考え方を示すためのもので、計算と転送の時間の比は、モデル、入力の長さ、経路によって変わります。

| 送り始める単位 | 計算の裏に隠せるもの | 要るもの |
|---|---|---|
| prefill の全体 | 無い | 送る時点で decode の受け取り先が分かっていること。router が prefill の後で decode に送る構成でも使える |
| チャンク | 最後のチャンク以外の転送 | prefill の計算の間に受け取り先が届いていること。チャンクごとの転送と、その完了の管理 |
| 層 | 最後の層以外の転送 | チャンクの場合と同じ条件に加え、層ごとの転送と完了の管理。転送の回数が最も多い |

細かく送ると転送を計算に重ねやすくなりますが、転送と通知の回数も増えます。途中から送るには、prefill の計算の間に prefill と decode が互いの相手を知っている必要があるので、router が prefill の後で decode にリクエストを送る構成では、全部終わってから送るしかありません。

## vLLM と SGLang の実装の現状

vLLM の NIXL コネクタは、pull と push のどちらでも、prefill の計算が終わってから KV を送ります。SGLang は KV の転送に使うライブラリを選べ、NIXL か、KV の転送や保存を受け持つ別のライブラリの [Mooncake](https://github.com/kvcache-ai/Mooncake) を選んだときは push を使います。そのとき SGLang は、decode の受け取り先が先に届いていれば、計算済みのチャンクから送ります。

次の表は 2026 年 11 月 27 日に各リポジトリの main で確かめたものです。取り込み済みは、リンク先の固定した commit に実装が含まれることを指します。

| 方式 | vLLM | SGLang で NIXL か Mooncake を選んだとき |
|---|---|---|
| pull、全部終わってから | 取り込み済み。NixlConnector の既定 | 無い。どちらも prefill が書き込む |
| push、全部終わってから | 取り込み済み。NixlPushConnector と、Mooncake のコネクタ | 取り込み済み。decode の確保を prefill の後にする設定のとき |
| push、チャンクごと | 取り込み前。提案と PR が進行中 | 取り込み済み。既定の設定で、decode の受け取り先が届いていれば |
| 層ごと | コネクタの仕組みに層ごとに呼ばれる関数があり、[LMCache](https://github.com/LMCache/LMCache) のコネクタがそれを実装している | 無い。全部の層の KV をまとめて 1 回の転送で出す |

vLLM は 1 層を計算するたびにコネクタの関数を呼びますが、NixlConnector は[この関数で何もしません](https://github.com/vllm-project/vllm/blob/955f85be04b6250d26e6915e26bdf6720fbc8258/vllm/distributed/kv_transfer/kv_connector/v1/nixl/connector.py#L323-L335)。push 型も、リクエストの prefill が終わった時点で送り始めます。NixlPushConnector は [PR #35264](https://github.com/vllm-project/vllm/pull/35264) で取り込まれました。チャンクごとの push は、[RFC #67207](https://github.com/vllm-project/vllm/issues/67207) と、それを設定で選べるようにする [PR #67203](https://github.com/vllm-project/vllm/pull/67203) が取り込み前の段階にあります。

PR #67203 は、同じノードの 2 枚の H100 を prefill と decode に 1 枚ずつ使い、NIC の RDMA を折り返す形でつないで、Qwen3-8B で 3 つの方式を比べています。EFA で 2 台をつないだ値ではありません。prefill が終わってから最初のトークンまでの時間の中央値は、入力 16,000 トークンで pull が 206〜210 ms、全部終わってから送る push が 342〜377 ms、チャンクごとの push が 99〜102 ms でした。入力 32,000 トークンでは、それぞれ 345〜353 ms、282〜359 ms、79〜82 ms です。この条件では、全部終わってから送る push が 16,000 トークンで pull より長くなっていて、push の効果は構成によって変わります。どれも取り込み前の PR が報告した値です。

SGLang の prefill は、チャンクを計算し終えるたびに、[decode の受け取り先が届いていればその分を送ります](https://github.com/sgl-project/sglang/blob/0de06898bdb266e8164d3cf84bf8e3c71092cc93/python/sglang/srt/disaggregation/prefill.py#L1414-L1420)。転送には NIXL の [WRITE だけを使います](https://github.com/sgl-project/sglang/blob/0de06898bdb266e8164d3cf84bf8e3c71092cc93/python/sglang/srt/disaggregation/nixl/conn.py#L2491-L2496)。SGLang の router は、リクエストを見分ける番号を作り、[prefill 向けと decode 向けのリクエストに付けて](https://github.com/sgl-project/sglang/blob/0de06898bdb266e8164d3cf84bf8e3c71092cc93/sgl-router/src/proxy/grpc.rs#L213-L231)、2 つのプロセスへ[同時に送ります](https://github.com/sgl-project/sglang/blob/0de06898bdb266e8164d3cf84bf8e3c71092cc93/sgl-router/src/server/routes/chat/forward.rs#L833-L879)。decode は、prefill が持つ bootstrap server という窓口で prefill の接続先を調べ、受け取り先のブロックの番号を、メッセージを送るライブラリの ZMQ で [prefill に送ります](https://github.com/sgl-project/sglang/blob/0de06898bdb266e8164d3cf84bf8e3c71092cc93/python/sglang/srt/disaggregation/nixl/conn.py#L3660-L3700)。転送の完了も、NIXL の仕組みではなく、[ZMQ のメッセージで decode に伝えます](https://github.com/sgl-project/sglang/blob/0de06898bdb266e8164d3cf84bf8e3c71092cc93/python/sglang/srt/disaggregation/common/conn.py#L1122-L1171)。

::::details NIXL の LIBFABRIC バックエンドを選ぶ設定

vLLM では、prefill と decode の両方で `--kv-transfer-config` を設定し、その中の `kv_connector_extra_config` の `backends` を `["LIBFABRIC"]` にします。既定は `["UCX"]` です。設定の例は [vLLM の NIXL コネクタの文書](https://github.com/vllm-project/vllm/blob/955f85be04b6250d26e6915e26bdf6720fbc8258/docs/features/nixl_connector_usage.md#L39-L54)にあります。

vLLM で push 型を選ぶ方法は 2 つあります。`kv_connector` を `NixlPushConnector` にする方法と、`kv_connector` を `NixlConnector` にしたまま [`kv_connector_extra_config` の `transfer_mode` を `push` にする方法](https://github.com/vllm-project/vllm/blob/955f85be04b6250d26e6915e26bdf6720fbc8258/vllm/distributed/kv_transfer/kv_connector/factory.py#L134-L140)です。

SGLang では、`--disaggregation-transfer-backend nixl` を指定します。そのうえで、環境変数 `SGLANG_DISAGGREGATION_NIXL_BACKEND` を `LIBFABRIC` にします。既定は `UCX` です。

## llm-d での扱い

[llm-d](https://github.com/llm-d/llm-d) は、Kubernetes の上で vLLM や SGLang の prefill と decode を並べ、リクエストの振り分けを受け持つ OSS です。NIXL を使う構成では、llm-d は vLLM を pull、SGLang を push で動かしています。違いは、decode の Pod に同居する routing sidecar というプロセスが、prefill と decode にリクエストを出す順番に表れます。

llm-d の router は、[リクエストを prefill と decode の Pod に 1 回ずつ割り当てます](https://github.com/llm-d/llm-d/blob/9059ad4050a3e1713d14b954685dac87cfe932cc/guides/pd-disaggregation/README.md#L14)。vLLM のときの sidecar は、[先に prefill にリクエストを送ります](https://github.com/llm-d/llm-d/blob/9059ad4050a3e1713d14b954685dac87cfe932cc/docs/operations/disaggregation/vllm.md#L26-L45)。prefill の応答には KV の在りかが入っていて、sidecar はそれを付けて decode に送ります。SGLang のときの sidecar は、[1 つの番号を両方のリクエストに付け](https://github.com/llm-d/llm-d/blob/9059ad4050a3e1713d14b954685dac87cfe932cc/docs/operations/disaggregation/sglang.md#L57-L68)、prefill へのリクエストを裏で出しながら、decode へのリクエストを同時に出します。llm-d では pull でも decode が先に決まっているので、pull の「prefill の後に decode を選べる」という利点は使っていません。

vLLM の push 型を llm-d で使えるようにする提案は、[issue #2720](https://github.com/llm-d/llm-d/issues/2720) で議論中です。issue は、sidecar が vLLM のときも prefill と decode へ同時に送る必要があると書き、さらに、decode が prefill の終わる前に、prefill の NIXL に接続するための名前とアドレスをどう知るかを未解決の点に挙げています。vLLM の公式の router は、すでに [push 型に対応しています](https://github.com/vllm-project/router/pull/187)。

## NIXL の READ と WRITE を libfabric の実装で見る

NIXL の READ と WRITE は、相手のアプリケーションが受信の処理を呼ばなくても進む one-sided の操作で、READ が get、WRITE が put に当たります。EFA のデバイスがその操作を持つ経路では、デバイスの RDMA read と RDMA write として動き、データの移動に相手の CPU は関わりません。その経路での 2 つの違いは、データの移動そのものではなく、相手が「届いた」「読まれた」といつ知るかにあります。

アプリケーションが呼ぶ NIXL の API は、READ か WRITE かを変えずにバックエンドに渡します。向きはどちらも呼んだ側から見て決まっていて、READ は相手のメモリを自分のメモリに読み、WRITE は自分のメモリを相手のメモリに書きます。libfabric は、終わった操作を完了キューという列に積み、NIXL はこの列を読んで操作が終わったことを知ります。NIXL の通知は、READ や WRITE に添えて相手のアプリケーションへ渡す短いメッセージで、vLLM はこれで転送の終わりを知ります。

READ では、NIXL の LIBFABRIC バックエンドが [libfabric の fi_read を呼びます](https://github.com/ai-dynamo/nixl/blob/27542ee6592a2c712bfc387cab82a93653c594d8/src/utils/libfabric/libfabric_rail.cpp#L1622-L1703)。RDMA read の完了は、読んだ側の完了キューにしか上がりません。読まれた側の prefill は何も知らないので、呼び出し側が通知を付けて READ を出したとき、NIXL は読み終えたのを確かめてから、[通知を別のメッセージとして送ります](https://github.com/ai-dynamo/nixl/blob/27542ee6592a2c712bfc387cab82a93653c594d8/src/plugins/libfabric/libfabric_backend.cpp#L1733-L1743)。vLLM の pull 型は、この通知を受けて prefill のブロックを解放します。

WRITE では、NIXL の LIBFABRIC バックエンドが、通知の有無にかかわらず [immediate data を付けた fi_writemsg を呼びます](https://github.com/ai-dynamo/nixl/blob/27542ee6592a2c712bfc387cab82a93653c594d8/src/utils/libfabric/libfabric_rail.cpp#L1524-L1620)。immediate data は、書き込みと一緒に相手に届く小さな値で、NIXL はここに転送の番号を入れます。書き込みが届くと、書かれた側の完了キューにも、この値の入った項目が上がります。通知を付けた WRITE では、[書き込みを出した直後に、何回書くかを添えて通知が送られます](https://github.com/ai-dynamo/nixl/blob/27542ee6592a2c712bfc387cab82a93653c594d8/src/plugins/libfabric/libfabric_backend.cpp#L1665-L1678)。decode の NIXL は、届いた書き込みを送り手と転送の番号の組ごとに数え、[数がそろい、通知も届いたときだけ、通知をアプリケーションに渡します](https://github.com/ai-dynamo/nixl/blob/27542ee6592a2c712bfc387cab82a93653c594d8/src/plugins/libfabric/libfabric_backend.cpp#L2252-L2300)。

**WRITE の通知を書き終わりを待たずに出せるのは、書き込みそのものが書かれた側の完了キューに到着の記録を残し、decode の NIXL がそれを数えられるからです。** 通知と書き込みは別々に流れ、書き込みは複数の EFA のデバイスに分かれることもあり、EFA の SRD は届く順番を保証しません。どちらが先に着いても正しく終わるように、通知が先に着いたときは、数がそろうまで NIXL が通知を止めておきます。ここまでは NIXL の LIBFABRIC バックエンドの動きで、SGLang は「vLLM と SGLang の実装の現状」の節で見たとおり、NIXL の通知を使いません。

NIXL は、EFA のデバイスが複数あるとき、128 KiB 以上の領域を[複数のデバイスに分けて](https://github.com/ai-dynamo/nixl/blob/27542ee6592a2c712bfc387cab82a93653c594d8/src/utils/libfabric/libfabric_rail_manager.cpp#L425-L445)並行に出します。128 KiB に満たない領域は、WRITE では続けて出す複数の領域を 1 つのデバイスにまとめ、READ では領域ごとにデバイスを順に替えて出します。

## 経路で READ と WRITE の中身が変わる

NIXL が同じ READ や WRITE を出しても、libfabric のどの provider が受け持つかと、EFA のデバイスがその操作を持つかで、ネットワークの上のやりとりが変わります。provider は、libfabric の下で実際の送受信を受け持つドライバです。EFA には efa provider を使い、efa provider は相手が同じノードにいると分かると、送受信を shm provider に回します。EFA などの RDMA のデバイスが見つからないとき、NIXL は [tcp provider か sockets provider に切り替えます](https://github.com/ai-dynamo/nixl/blob/27542ee6592a2c712bfc387cab82a93653c594d8/src/utils/libfabric/libfabric_topology.cpp#L236-L256)。

次の表は、データを運ぶ操作だけを並べたものです。大きい転送の分割と、前の節の通知は含みません。

| 経路 | READ | WRITE |
|---|---|---|
| 2 台の間、EFA が RDMA read と RDMA write を持つ。p5、p5e、p5en、p6-b200 など | 両側で NIC がその側の GPU メモリに直接触れられれば、デバイスの RDMA read | 下の本文の条件がそろえば、immediate data 付きのデバイスの RDMA write。そろわなければ次の行と同じ模倣 |
| 2 台の間、EFA が RDMA write を持たない。p4d、p4de | 同じ条件で、デバイスの RDMA read | 送受信のメッセージで模倣する。候補の 1 つは、書かれる側が RDMA read で取りに来る方式 |
| 同じノード、shm provider | immediate data が付かないので、ほかの条件がそろえば、相手のメモリから直接写す経路を使える | immediate data が付くので、直接写す経路を使えず、相手のプロセスが要求を受け取って写す |
| tcp provider | 要求のメッセージと、データを積んだ応答のメッセージ | データを積んだ 1 つのメッセージ |

どのインスタンスが RDMA read と RDMA write を持つかは、[EFA の文書の対応表](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/efa.html#efa-instance-types)にあります。efa provider が[書き込みをデバイスの RDMA write で出す](https://github.com/ofiwg/libfabric/blob/1a2262446b3e92072e746082ecc4e67e3dbba7d1/prov/efa/src/rdm/efa_rdm_rma.h#L55-L92)には、両側の EFA が RDMA write を持ち、両側で NIC がその側の GPU メモリに直接触れられる必要があります。immediate data を付けた書き込みでは、さらに 2 つの条件が加わります。1 回の書き込みが連続した 1 つの領域であることと、受信の用意なしに書き込みを受ける機能への対応が両側でそろっていることです。NIXL は 1 回の書き込みを 1 つの領域で出すので、1 つ目は満たします。2 つ目がそろわない原因として、libfabric は両側の efa ドライバ、libfabric、rdma-core のバージョンの食い違いを挙げているので、prefill と decode でこれらをそろえてください。

RDMA write を持たない p4d では、[模倣の候補](https://github.com/ofiwg/libfabric/blob/1a2262446b3e92072e746082ecc4e67e3dbba7d1/prov/efa/src/rdm/efa_rdm_proto.c#L125-L137)の 1 つに、書く側が書き込みの依頼だけを送り、[書かれる側が RDMA read でデータを取りに来る方式](https://github.com/ofiwg/libfabric/blob/1a2262446b3e92072e746082ecc4e67e3dbba7d1/prov/efa/src/rdm/protocols/efa_rdm_proto_longread_write.c)があります。この方式が選ばれると、アプリケーションから見れば push でも、ネットワークの上では decode が prefill から読む動きになります。

同じノードの場合、shm provider は [immediate data 付きの RMA を、相手のメモリに直接写す経路から外します](https://github.com/ofiwg/libfabric/blob/1a2262446b3e92072e746082ecc4e67e3dbba7d1/prov/shm/src/smr_rma.c#L107-L120)。NIXL の WRITE は常に immediate data を付けるので、同じノードでの push は、相手のプロセスが要求を受け取って写す経路で運ばれます。GPU メモリどうしのときに shm の中で何が起きるかと、同じノードでも EFA のデバイスを通す設定は、「[EFA の同じノード内の GPU 間通信](https://zenn.dev/tosshi/articles/741e79cf2e9bf2)」で説明しています。

tcp provider では、[READ は要求と応答の 2 つのメッセージ](https://github.com/ofiwg/libfabric/blob/1a2262446b3e92072e746082ecc4e67e3dbba7d1/prov/tcp/src/xnet_rma.c#L52-L83)になり、[WRITE は宛先と immediate data とデータを 1 つのメッセージに積みます](https://github.com/ofiwg/libfabric/blob/1a2262446b3e92072e746082ecc4e67e3dbba7d1/prov/tcp/src/xnet_rma.c#L202-L276)。ここでのメッセージは tcp provider の中のメッセージの数で、TCP のパケットの数ではありません。

## まとめ

KV の転送を、誰が始めるか、いつから送るか、どの経路で運ぶかの 3 つに分けました。vLLM の push 型は、decode が先に登録しておくことで、prefill の後の準備を減らしました。SGLang の NIXL と Mooncake の転送と、vLLM の進行中の PR は、prefill の途中から送ることで、転送そのものを計算の裏に隠します。NIXL の LIBFABRIC バックエンドは、WRITE の通知を書き終わりの前に送れます。decode の NIXL が書き込みの到着を数え、そろってから通知をアプリケーションに渡すからです。
