## はじめに

Turing のインフラチームが公開した「[Full-Managed のその奥は？ FSx for Lustre の I/O 問題を AWS と一緒に切り分ける](https://zenn.dev/turing_motors/articles/hyperpod-again-part1-efa-lustre)」は、Amazon FSx for Lustre の LNet-over-EFA の経路で障害が 4 回続き、最後はクライアントを TCP に固定した経緯を、観測とともに記録しています。その記事によると、8 月に Turing が確かめた際、AWS の担当者は、当時の構成では EFA から TCP へ自動では切り替わらないと答えています。この記事では、EFA の経路が使えなくなっても TCP に移らない仕組みと、TCP で足りなくなる条件を、FSx for Lustre のクライアントのソースと、東京リージョンに立てた EFA 有効のファイルシステムでの試験から説明します。

扱う問いと、読む実装と、答える節は次のとおりです。

| 問い | 読む実装 | 節 |
|---|---|---|
| Lustre で NCCL に当たる層は何か | LNet と LND の構成 | Lustre の通信層 |
| EFA の NID と接続は何に依存するか | `kefalnd_create_efa_nid`、`kefalnd_find_remote_peer_ni` | NID の作り方、接続の確立 |
| bulk はどう運ばれるか | PUTR と GETR のメッセージ | データの運び方 |
| 失敗は LNet にどう届くか | `kefalnd_tx_complete`、`kefalnd_drain_ni_conns`、受信の検査 | 失敗の伝わり方 |
| なぜ TCP に移らないのか | `lnet_find_best_ni_on_local_net`、health の更新 | LNet の経路選択、EFA で受け取れないクライアント |
| TCP ではどこで足りなくなるか | AWS の性能の表、試験の測定 | TCP と EFA の実測、学習の規模から見た必要帯域 |
| Turing の各事象は実装のどこに当たるか | 上のすべて | Turing の事象との対応 |

EFA や Lustre そのものの説明は省きます。コードの引用は、upstream の [lustre-release の 6325870](https://github.com/lustre/lustre-release/tree/6325870717c7899f1ba545493ce2a07cb3834a6b) (2026-10-21 のタグ 2.17.60、2026-10-26 に取得) に固定したリンクで示します。FSx のクライアントの配布版は、AWS が公開する [SRPM](https://fsx-lustre-client-repo.s3.amazonaws.com/el/9/SRPMS/) の 2.15.6-1fsx31 から fsx36 です。筆者はこの SRPM に patch を `%prep` の順に当てて組み直し、この記事で引く関数が同じ処理であることを読み比べました。版で違う箇所は、その場で書きます。

試験の環境は次のとおりです。試験は 2026-10-26 (JST) に行い、ファイルシステムとクライアントは試験の後に消しました。かかった費用は、オンデマンドの単価と使った時間からの見積もりで約 9 ドルです。

| 項目 | 値 |
|---|---|
| ファイルシステム | FSx for Lustre PERSISTENT_2、SSD、4,800 GiB、1000 MB/s/TiB、EFA 有効、メタデータは AUTOMATIC。`lfs df` では OST 1 つ、MDT 1 つ |
| クライアント | c7gn.16xlarge 1 台 (EFA 1 枚、200 Gbps)、ファイルシステムと同じ AZ |
| OS とモジュール | Amazon Linux 2023、カーネル 6.18.56。kefalnd 1.2.6 と Lustre 2.15.6 のモジュールはカーネルのパッケージに入っていて (kefalnd の版 1.2.6 は fsx36 の `efalnd.h` と同じ)、AWS のスクリプトが入れたのは `lustre-client-2.15.6-35.amzn2023` (lctl や lnetctl) と EFA のユーザー空間の部品 |
| EFA の設定 | AWS の [configure-efa-fsx-lustre-client](https://docs.aws.amazon.com/fsx/latest/LustreGuide/configure-efa-clients.html) の `setup.sh --configure-once` |
| 負荷 | 試験の I/O 以外のワークロードは流していない。FSx のサーバの内部の負荷は観測していない |

## Turing で起きたこと

Turing の記事から、この記事で扱う事象を抜き出します。Turing の記事自身が、4 回の障害が同じ仕組みで起きたとは確認できていないと書いている点に注意してください。

| 時期 | Turing の観測と AWS の回答 | この記事で見る節 |
|---|---|---|
| 6/14 | スループットの大幅な低下、EFA の再送タイムアウトの急増、LNet の TX completion error と GDS の読み込み失敗。AWS はホストやネットワーク機器の一時的な劣化を第一仮説とした (確定ではない) | 失敗の伝わり方 |
| 6/29 | 書き込みが詰まった。EFA の再送タイムアウトが 5 分あたり約 30 件から 88〜95 件に増えたが、RPC のタイムアウトと再送は 0 | 失敗の伝わり方 |
| 7/7〜7/9 | OSS の EFA の NID が変わった (原因は未確認)。ノードの作り直しでエラーは収まったが、古い peer 情報が残って I/O が止まり続け、7/9 に気づいた。AWS と確認して `lnetctl peer del` で再検出させ、数秒で再接続した | NID の作り方 |
| 7/13 | 複数のクライアントが同時にタイムアウトし、大半は約 15 分で回復、一部では古い peer 情報が残って接続が復旧しなかった。作り直したノードでも起きたので、クライアントを TCP に固定した | LNet の経路選択 |
| 7/20〜 | TCP 化の後、小さなファイルの読み書きが EIO で失敗し、ジョブの失敗の約 2 秒前に OST からの client eviction が記録された。7/23 の再現試験では、特定のノードペアと 3 つの OST の組み合わせで、初回の書き込み処理 (open/truncate、書き込み、同期) が 180〜185 秒止まり、別のノードペアでは再現しなかった。8/7 の AWS の回答では、事象は当初の OSS に限らず、サーバ側の LNet/EFA の peer discovery が主な調査対象になった | Turing の事象との対応 |

## Lustre の通信層

Lustre で NCCL に当たるのは LNet と、その下に差し込む LND (Lustre Network Driver) です。NCCL が集団通信を差し替え可能な net plugin に流すように、LNet は Lustre の RPC と大きなデータ (bulk) を、ネットワークごとの LND に流します。TCP には ksocklnd、InfiniBand には o2iblnd、EFA には kefalnd があります。kefalnd は [LU-18977](https://jira.whamcloud.com/browse/LU-18977) で upstream に入り、[lnet/klnds/efalnd](https://github.com/lustre/lustre-release/tree/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd) にあります。

| 項目 | NCCL | LNet |
|---|---|---|
| 運ぶもの | GPU 間の集団通信のデータ | Lustre の RPC と bulk (ファイルのデータ) |
| 動く場所 | ユーザー空間 | カーネル |
| ネットワークを差し替える部品 | net plugin (aws-ofi-nccl) | LND (kefalnd、ksocklnd、o2iblnd) |
| EFA の使い方 | libfabric の efa provider からユーザー空間の verbs で使う | カーネルの ib_verbs で SRD の QP を直接使う |
| 複数の経路の扱い | 複数の NIC にチャネルを分ける | Multi-Rail: 送るたびに相手の NI を選び、NI ごとの health で避ける |
| 失敗の扱い | 既定では、通信のエラーでコミュニケータを止める | LNet が再送し、ptlrpc が再接続とリカバリをする |

次の図は、1 枚の EFA の上で NCCL と Lustre がそれぞれどの部品を通るかを、試験のファイルシステムの NID とあわせて示します。

![NCCL の部品 (aws-ofi-nccl、libfabric、ユーザー空間の verbs) と Lustre のクライアントの部品 (llite、osc/mdc、ptlrpc、LNet、kefalnd) は別々で、共有するのは efa.ko と EFA デバイスだけ。Lustre の LNet は ksocklnd から TCP にも出られる。試験のファイルシステムの OSS は EFA と TCP の両方の NID を持ち、MGS と MDS は TCP の NID だけを持つ](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/5a792cff5d5f61/zenn/articles/5a792cff5d5f61/stacks.png)

NCCL と Lustre は efa.ko と EFA デバイスだけを共有し、それより上の部品を共有しません。kefalnd は libfabric を使わず、カーネルの verbs で SRD の QP に [送信の要求](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd.h#L266) を積みます。Turing の記事の「NCCL が通っても、Lustre の経路が正常とは限らない」は、この構造から言えます。NCCL の試験が確かめるのは EFA のデバイスと libfabric の経路までで、kefalnd の接続の状態や LNet の経路選択は確かめません。

試験のファイルシステムでは、OSS は `172.31.20.3@tcp` と `20.3.0.248@efa` の 2 つの NID を持ち、MGS と MDS は `172.31.22.230@tcp` だけを持っていました。マウント時の discovery のログには `Peer 172.31.22.230@tcp has discovery disabled` と出て、`mdc.*.mds_conn_uuid` は `172.31.22.230@tcp` でした。この構成では、メタデータの操作は EFA を有効にしても TCP を通り、EFA を通るのは OSS との RPC と bulk です。MDT が多い大きなファイルシステムでも同じかは確かめていません。

## kefalnd の実装

### NID の作り方

kefalnd の small NID (4 バイトの NID) は [kefalnd_create_efa_nid](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd.c#L2922) で作られます。次の図は、試験の OSS の NID がどう組み立てられているかを示します。

![TCP の NID 172.31.20.3 の上位 16 ビット 172.31 を捨て、下位 16 ビットの 20.3 を EFA の NID の上位に置き、EFA デバイスの PCI のバス番号 0 と devfn 248 を下位に置いて 20.3.0.248@efa になる。相手の TCP の NID は、自分の IP の上位 16 ビットと相手の EFA の NID の上位 16 ビットから作られる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/5a792cff5d5f61/zenn/articles/5a792cff5d5f61/nid.png)

```c
		pci_dev = to_pci_dev(efa_dev->ib_dev->dev.parent);
		addr = (__swab32(efa_dev->ifip) & 0xffff) << 16;
		addr = addr | ((pci_dev->bus->number & 0xff) << 8);
		addr = addr | (pci_dev->devfn & 0xff);
```

試験では、クライアントの `172.31.28.45@tcp` が `28.45.0.248@efa` に、OSS の `172.31.20.3@tcp` が `20.3.0.248@efa` になりました。NID の下位はホストの中で EFA が挿さった PCI の位置です。サーバの EFA の PCI の位置が変われば、IP が同じでも EFA の NID は変わります。Turing の 7/7 に OSS の EFA の NID が変わったこと (元の記事では原因は未確認) は、この作り方と矛盾しません。

逆向きの対応は [efa_nid_to_tcp_nid](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd_peerni.c#L65) が作ります。相手の TCP の NID を、自分の IP の上位 16 ビットと、相手の EFA の NID の上位 16 ビットからつなぎ合わせます。自分と相手が同じ /16 にいないと、この計算は別のホストを指します。AWS は EFA 有効のファイルシステムに、クライアントと同じ AZ と同じ /16 を [求めています](https://docs.aws.amazon.com/fsx/latest/LustreGuide/efa-file-systems.html)。ドキュメントは理由を書いていませんが、small NID ではこの計算がその条件を必要とします。large NID (16 バイト) は GID と接続用の QP の番号から作られ、この節の話は当てはまりません。

### 接続の確立

kefalnd が EFA で最初のメッセージを送るには、相手の EFA の GID と、接続用の QP (図の CM QP) の番号が要ります。[kefalnd_find_remote_peer_ni](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd_peerni.c#L210) は、その対応表をまず手元のキャッシュから探し、無ければ上の計算で作った相手の TCP の NID に [LNet の ping](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd_peerni.c#L251) を打って取り寄せます。その後、両側の kefalnd は EFA の上で probe と接続要求を交わし、相手の epoch を覚えます。epoch は NI を起動したときの [時刻](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd.c#L3239) です。

次の図は、試験でクライアントが最初に OSS へ送ったときの接続の確立を、マウント時に `lctl set_param debug=+net` で取ったクライアントのログの時刻とともに示します。1 回の記録で、最初の送信の要求から ACTIVE まで 3.0 ms、最初の PUT の完了まで 3.5 ms でした。

![クライアントが PROBE_TCP の状態で 172.31.20.3@tcp へ LNet ping を送り、GID と CM QP を受け取って PROBE_EFA に進み、EFA で CONN_PROBE と PROBE_RESP を交わし、CONN_REQ と CONN_REQ_ACK で ESTABLISH から ACTIVE になり、最初の PUT を送る。kefalnd の接続は向きごとに 1 本で、OSS からクライアントへの接続は別に開かれる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/5a792cff5d5f61/zenn/articles/5a792cff5d5f61/connect.png)

EFA の経路は TCP の経路に依存しています。対応表がキャッシュに無いとき、EFA の接続を作るには、相手の TCP の NID に ping が届き、相手の LNet がその NID で応答する必要があります。TCP だけの経路は、TCP が動けば使えます。EFA の経路は、TCP と EFA の両方が動き、さらに双方の NID と epoch の対応が正しく保たれて初めて使えます。キャッシュに古い対応が残った場合に何が起きるかは、この記事では試していません。

### データの運び方

kefalnd が bulk を運ぶ方法は、受け手が送り手のメモリを RDMA READ で読む 1 通りだけです。[メッセージの種類](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd_proto.h#L194) には READ の版の PUT と GET しかなく、RDMA WRITE はありません。ヘッダとデータを合わせて [8,900 バイト以下](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd.c#L1088) に収まるメッセージは、RDMA を使わずに IMMEDIATE として EFA で 1 回で送ります。

次の図は、ファイルの読み込みと書き込みのそれぞれで、どちらが RDMA READ を出し、どの制御メッセージを交わすかを示します。

![クライアントが読むとき、OSS が PUTR_REQ で自分のメモリのアドレスと鍵を渡し、クライアントが RDMA READ で約 1 MiB ずつ読み、PUTR_DONE を返す。クライアントが書くとき、OSS が GETR_REQ を送り、クライアントが GETR_ACK でアドレスと鍵を渡し、OSS が RDMA READ で読み、GETR_DONE を返す。試験の後のクライアントのカウンタは、rdma_read_bytes の増分が 80 GiB、rdma_read_resp_bytes が同じ値、rdma_write_wrs が 0](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/5a792cff5d5f61/zenn/articles/5a792cff5d5f61/bulk.png)

Lustre の bulk の読み込みは OSS からクライアントへの PUT で、書き込みは OSS がクライアントから取る GET です。kefalnd ではどちらの向きも受け手が読みにいくので、ファイルを読むときはクライアントが OSS のメモリを読み、ファイルを書くときは OSS がクライアントのメモリを読みます。試験では 4 MiB の I/O で、書き込みと読み込みをそれぞれ 80 GiB 流しました。試験の前後で、クライアントの `/sys/class/infiniband/efa_0/ports/1/hw_counters` の `rdma_read_bytes` は 8,276 から 85,899,354,196 に増え、増分はちょうど 80 GiB でした。このカウンタはクライアントが読んだ量です。クライアントが OSS に読まれた量を数える `rdma_read_resp_bytes` は試験の前の値を記録していませんが、試験の後は 85,899,354,196 で、`rdma_read_bytes` と同じ値でした。`rdma_write_wrs` は 0 でした。`rdma_read_wrs` は 81,921 回なので、クライアントが出した RDMA READ は平均で約 1 MiB です。後で述べる 4 KiB の遅延の試験の I/O は IMMEDIATE で運ばれるはずで、RDMA の量がちょうど 80 GiB だったこととも合いますが、メッセージの種類を記録したわけではありません。

この運び方では、1 回の bulk ごとにメモリの登録 (FRWR の REG_MR) と解除、鍵とアドレスの受け渡し、完了を知らせる cookie の照合が要ります。TCP の ksocklnd は、ソケットにバイト列を流すだけです。EFA の経路では、こうした状態の数が多く、相手と食い違う箇所も多くなります。2.15.6-1fsx35 と fsx36 に入った kefalnd の修正の多くは、この状態の管理に関するものです。[LU-20191](https://jira.whamcloud.com/browse/LU-20191) は接続の後始末を分け、[LU-20496](https://jira.whamcloud.com/browse/LU-20496) は使われていない接続だけを壊すようにし、[LU-20497](https://jira.whamcloud.com/browse/LU-20497) は古い受信完了と応答の cookie を扱い、[LU-20655](https://jira.whamcloud.com/browse/LU-20655) は起動の失敗時の参照カウントを直し、[LU-20790](https://jira.whamcloud.com/browse/LU-20790) と [LU-20791](https://jira.whamcloud.com/browse/LU-20791) は受信バッファの漏れと接続の参照カウントを直しています。Turing の記事は当時の版を書いていません。FSx のリポジトリでは、2.15.6-1fsx30 が 2026-05-05、fsx31 が 05-19、fsx32 が 06-22、fsx33 が 08-05、fsx34 が 09-01 に公開され、これらの kefalnd の修正はどれも fsx35 以降に入っています。

### 失敗の伝わり方

kefalnd は、失敗の種類ごとに、LNet の health の何を下げるかを決めた状態を付けて LNet に返します。LNet は [lnet_health_check](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/lnet/lib-msg.c#L961) でその状態を見て、相手の peer NI の health と自分の NI の health を下げ、場合によっては再送します。

| 失敗 | kefalnd が付ける状態 | LNet がすること |
|---|---|---|
| 送信の完了がエラーで返る | [REMOTE_DROPPED](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd.c#L1585)。自分から開いた接続なら非活性化する | 相手の peer NI の health を下げ、再送を試みる |
| メモリの登録 (REG_MR) の完了がエラーで返る | [LOCAL_DROPPED](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd.c#L1576) | 自分の NI の health を下げる |
| 送った後、決まった時間内に完了しない | NETWORK_TIMEOUT。ただし調べるのは後始末の列に入った接続だけ | 相手の peer NI と自分の NI の health を下げ、[再送はしない](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/lnet/lib-msg.c#L1033) |
| 受信したメッセージの検査に落ちる | 何も付けずに [捨てる](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd.c#L1766)。送り手には何も返さない | 何もしない |

3 行目の限定が、この記事の中心です。送信の期限を調べる [kefalnd_drain_ni_conns](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd_connection.c#L1281) は、接続管理のスレッドが後始末の列に移した接続だけを見ます。列に移るのは、非活性化された接続か、[peer_timeout の間使われなかった接続](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd_connection.c#L1175) です。peer_timeout は [最低 200 秒](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd.h#L86) で、試験のクライアントでもモジュールのパラメータの 180 が引き上げられ、EFA の NI は dmesg に `Added LNI 28.45.0.248@efa [32/8192/0/200]` と出て 200 秒でした。相手から開かれた接続には、さらに [300 秒](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd_connection.c#L20) が足されます。

一方、kefalnd は送るたびに [kefalnd_get_or_init_conn](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd.c#L1057) で接続を引き、そのたびに接続の [最後に使った時刻を更新](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd_connection.c#L604) します。上の層が 200 秒より短い間隔で送り続ける接続は、使われていることになり、後始末の列に移りません。その接続で完了を待ったまま止まった送信は、非活性化されない限り、kefalnd の期限にかかりません。ksocklnd の [ksocknal_check_peer_timeouts](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/socklnd/socklnd_cb.c#L2399) と o2iblnd の [kiblnd_check_txs_locked](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/o2iblnd/o2iblnd_cb.c#L3731) は、接続が使われているかに関係なく、送信ごとの期限を定期的に調べます。試験の dmesg にも、ksocklnd 側の `Total 1 stale ZC_REQs for peer_ni 172.31.20.3@tcp detected; the oldest(...) timed out 3 secs ago` が出ていました。fsx31 の kefalnd でも、送信の期限を調べるのは後始末の対象の接続だけで、同じ作りです。この節はコードを読んだ結果で、止まった送信が実際に期限にかからなかったことは、試験では観測していません。

4 行目の検査には、宛先の epoch が自分の epoch と違うメッセージを捨てる処理が含まれます。相手の NI が起動し直して epoch が変わったのに、こちらが古い epoch で送り続ける場合がこれに当たります。SRD の層では届いているので、送り手の送信は成功で終わります。

LND の検査とは別に、LNet が受け取りを拒んだメッセージもあります。この場合、kefalnd は相手の bulk の要求には、[PUTR_DONE](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd.c#L1230) か [NACK](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd.c#L1297) に `-ENODATA` を載せて返します。IMMEDIATE のメッセージには何も返しません。

最後に、LNet の標準の故障注入のうち、health のエラーを注入する仕組みは kefalnd では働きません。`lctl net_drop_add -e <health error>` は、LND が送信の前に [lnet_send_error_simulation](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/socklnd/socklnd_cb.c#L458) を呼ぶことで効きます。これを呼ぶのは ksocklnd と [o2iblnd](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/o2iblnd/o2iblnd_cb.c#L1042) で、kefalnd は fsx31 から fsx36 のどの版でも呼びません。試験でも、`lctl net_drop_add -s '*@efa' -d '*@efa' -r 1 -e remote_dropped` を入れて 2 GiB を書いた間、規則に当たったメッセージは 0 件で、書き込みは 2.1 秒で終わりました。この手順のスクリプトは、debug ログから health のエラーの注入の行を数える箇所で、1 行も無かったために失敗として終わっています。EFA の経路で health が下がる動きは、この標準の道具では試せません。

## LNet の経路選択

LNet は送るたびに、相手の peer のどのネットワークのどの NI へ、自分のどの NI から出すかを選びます。ネットワークを選ぶ [lnet_find_best_ni_on_local_net](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/lnet/lib-move.c#L2314) は、候補を次の順に [比べます](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/lnet/lib-move.c#L2388)。fsx31 と fsx36 の LNet も同じ順です。

| 順 | 比べるもの | 試験の構成での値 |
|---|---|---|
| 1 | 相手のネットワーク (peer net) の health | tcp も efa も 1000 |
| 2 | 相手のネットワークの優先度 | 設定なし |
| 3 | 自分のネットワークの health | tcp も efa も 1000 |
| 4 | 自分のネットワークの優先度 | AWS のスクリプトが入れる UDSP で efa が 0 |
| 5 | 相手のネットワークの順番の番号 | |
| 6 | 自分のネットワークの順番の番号 (round robin) | |

AWS の設定スクリプトを流した後の `lnetctl udsp show` は `src: efa`、`priority: 0` でした。health がすべて等しいあいだは 4 番目で efa が勝ち、OSS との RPC と bulk は EFA を通ります。試験でも、OSS の TCP の NID に送られたのは、discovery と kefalnd の ping の 21 件だけでした。peer net の health は、その中の peer NI の health の [最大値](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/include/linux/lnet/lib-lnet.h#L1129) です。peer NI の health は、失敗が相手のせいとされたときに [health_sensitivity だけ下がり](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/lnet/lib-msg.c#L578)、その peer NI からメッセージを [受け取るたびに同じだけ戻ります](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/lnet/lib-msg.c#L994)。health_sensitivity の既定は 100 で、試験のクライアントでも 100 でした。相手の peer が NI を 1 つしか持たないときは、相手の health の処理そのものを [行いません](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/lnet/lib-msg.c#L944)。

コードの順では health が UDSP の優先度より先に比べられるので、相手の EFA の health が下がれば、TCP が選ばれる道はあります。試験の OSS のように EFA の NID が 1 つの相手で、LNet のメッセージを載せた送信の完了エラーが 1 回 health に反映され、回復する前に次の送信の選択が行われれば、efa の peer net は 900、tcp は 1000 となり、コード上は TCP が選ばれます。この遷移は、上の故障注入の制約で実機では試せていません。

その一方で、この構成で EFA が選ばれ続ける要因は、コードの中に 3 つあります。どれも TCP に移るための必要条件ではなく、比較が EFA に有利なまま残る理由です。

1. 失敗が health に届かない。受け手の検査で捨てられたメッセージと、使われ続ける接続で止まった送信は、kefalnd の層では health を下げません。LNet には ACK や REPLY の応答を待つ仕組み (`response_tracking`) もあり、これが効くメッセージなら別に health を下げますが、Lustre の RPC の経路でどこまで効くかは確かめていません。
2. 下がっても最大値で打ち消される。相手が EFA の NID を複数持つなら、1 つでも 1000 の NI が残る限り efa の peer net は 1000 です。試験の OSS は EFA の NID を 1 つだけ持っていました。大きな構成のサーバがいくつ持つかは確かめていません。
3. 下がっても戻る。LNet は health の下がった peer NI を recovery の列に入れて ping を送り、応答を受け取れば health を戻します。小さな ping は IMMEDIATE で運ばれ、RDMA READ を通りません。RDMA の経路だけが壊れているなら、ping の成功で health が戻り、次の bulk がまた EFA に流れることがあり得ます。recovery の ping が実際にどの NI を通り、この故障の形で成功するかは確かめていません。

[re:Post の記事](https://repost.aws/articles/ARbKKMiQVXQbW-7DUCQTEjqQ/troubleshooting-fsx-for-lustre-how-to-perform-efa-to-tcp-failover-for-kefalnd-abort-tx-failures) は、自動で切り替わらない理由として 4 つを挙げています。(1) UDSP が EFA を優先度 0 に固定し、UDSP が有効なあいだ LNet は TCP を選ばない、(2) kefalnd は失敗を LNet の health に伝えず、EFA の NI の health は 1000 のまま、(3) 接続した後の ping は EFA だけを通る、(4) health が下がりきる前に、サーバが 227 秒でクライアントを evict する、です。(3) はこの記事の 3 番目の要因と同じ方向で、(4) は health の低下が選択に効くより先に上の層がクライアントを evict するという、別の時間の制約です。(2) は、送信の完了エラー (REMOTE_DROPPED) で自分の NI の health が下がらない点と、受け手で捨てられたメッセージや止まった送信が health に届かない点で、上のコードと一致します。コード上は、health が UDSP の優先度より先に比べられ、LNet のメッセージを載せた送信が完了エラーで返れば相手の peer NI の health が下がるので、この点は (1) と (2) の一般的な書き方とは違います。ただし re:Post が示すログは CONN_PROBE の完了エラーと `0.0.0.0@efa` 宛ての `kefalnd_abort_tx` で、接続を作る段階の失敗です。この形の失敗が LNet の health に届くかは、この記事では確かめていません。

Lustre の上の層も、この選択を変えられません。ptlrpc の import が持つ接続先は TCP の NID で、試験でも `osc.*.ost_conn_uuid` は `172.31.20.3@tcp` でした。ptlrpc がタイムアウトして再接続するときも、この NID を LNet に渡し、LNet が同じ peer の中から EFA の NI を選び直します。

### EFA で受け取れないクライアント

Turing の 7/13 に何の失敗が起きたかは、元の記事からは分かりません。ここでは、AWS が答えた「自動では切り替わらない」ことを、EFA の経路だけが使えない状態で確かめます。クライアントの LNet の受信の入口に、EFA から届くメッセージをすべて捨てる規則を入れました。この規則は、LND を通った後の [lnet_parse](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/lnet/lib-move.c#L4752) で効く、LND によらない故障注入です。前の節のとおり、このときクライアントの kefalnd は、OSS の bulk の要求には `-ENODATA` の完了を返し、IMMEDIATE のメッセージは黙って捨てます。kefalnd 自身が epoch の不一致で捨てる場合とは、捨てる層も、OSS が受け取る知らせも違います。TCP の経路には何もしていません。

次の図は、この規則を入れた後にクライアントのログで観測した順番を示します。

## TCP と EFA の実測

### 帯域

帯域は fio の 4 MiB の direct I/O で測りました。1 本のファイルは 16 GiB、16 本のファイルはそれぞれ 4 GiB で、各読み込みの前にクライアントのページキャッシュを捨てています。fio の JSON の `bw` は KiB/s なので、10 進の MB/s に直して示します。次の図は、OST が 1 つの試験のファイルシステムに対して、同じクライアントから TCP だけと EFA で測った帯域を並べたものです。

![OST が 1 つの試験のファイルシステムで、同じ c7gn.16xlarge から測ると、TCP は 1 本と 16 本のファイルの読み書きのどれも 620 MB/s で、1 組のクライアントと OSS あたり 5 Gbps (625 MB/s) の線のすぐ下に並ぶ。EFA は 5,576、8,115、4,772、7,238 MB/s で、申込みの帯域 4,688 MB/s の線を超える](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/5a792cff5d5f61/zenn/articles/5a792cff5d5f61/tcp-vs-efa.png)

TCP では、ファイルの本数も読み書きの向きも関係なく、すべての測定が 620.3〜620.4 MB/s (4.96 Gbps) でした。AWS の [性能の説明](https://docs.aws.amazon.com/fsx/latest/LustreGuide/performance.html) には、EFA を有効にしていないファイルシステムと、EFA 有効のファイルシステムに ENA で接続する場合について、クライアント 1 台と 1 つの OSS の間の通信は 5 Gbps に制限されるとあります。測った値は、この 625 MB/s の 99.3 % です。このファイルシステムの OST は 1 つなので、すべての I/O が 1 つの OSS に集まり、この上限がクライアント 1 台の上限になりました。申込みの帯域は次の値です。

$$
\frac{4800\ \mathrm{GiB}}{1024\ \mathrm{GiB/TiB}} \times 1000\ \mathrm{MB/s/TiB} = 4687.5\ \mathrm{MB/s}
$$

クライアントの NIC は 200 Gbps なので、TCP のクライアント 1 台が使えた帯域は、申込みの帯域の 13.2 % で、NIC ではなく 1 組あたりの上限で決まっていました。

EFA では、1 本のファイルの書き込みが 5,576 MB/s、読み込みが 8,115 MB/s で、TCP のそれぞれ 9.0 倍と 13.1 倍でした。EFA の 4 つの測定はどれも申込みの帯域を超えています。EFA の測定を終えた時点の累計で、LNet の `local_error_count` が 1 件、EFA の `retrans_timeout_events` が 1 件ありました。帯域への影響は確かめていません。読み込みでは OSS 側のキャッシュから返った分があると考えられますが、書き込みも含めて、超えた理由は確かめていません。

### 4 KiB の遅延

4 KiB の遅延は、キューの深さ 1 の同期 I/O で 20 秒ずつ測りました。表の値は fio の JSON の、書き込みが `write.clat_ns`、fsync が `sync.lat_ns`、読み込みが `read.clat_ns` の百分位です。

| 測定 (クライアント 1 台、OST 1 つ) | TCP の中央値 / p99 | EFA の中央値 / p99 | TCP / EFA (中央値) |
|---|---|---|---|
| 4 KiB の書き込み | 700 / 741 µs | 537 / 659 µs | 1.30 |
| fsync | 9,241 / 10,420 µs | 8,847 / 10,420 µs | 1.04 |
| 4 KiB の読み込み | 635 / 700 µs | 473 / 586 µs | 1.34 |

キューの深さ 1 の 4 KiB では、中央値の TCP / EFA の比は、書き込みで 1.30、読み込みで 1.34 でした。fsync の中央値はどちらも約 9 ms で、比は 1.04 です。fsync の内訳は測っていません。re:Post の記事は、TCP では小さな I/O の遅延が 3〜5 倍になると書いていますが、この構成ではその差は出ませんでした。多数のクライアントが同時に小さな I/O を出す条件では測っていません。CPU の使用率も mpstat で取りましたが、測定の区間と fio の区間がそろっていなかったので、比較は控えます。

## 学習の規模から見た必要帯域

TCP で足りるかは、ノード 1 台が必要とする帯域と、TCP の上限の比で決まります。AWS の性能の説明では、EFA を使わない TCP のクライアント 1 台の上限は 100 Gbps (12.5 GB/s) で、クライアント 1 台と 1 つの OSS の間は 5 Gbps (625 MB/s) です。

必要な帯域は、「[post-training 時代の LLM 学習の規模と効率の整理](https://zenn.dev/tosshi/articles/99375dd5ac013f)」の計画から見積もります。この計画は、Olmo 3 の 32B を p6-b200.48xlarge の 10 台、B200 の 80 枚で 1 年かけて学習するものです。事前学習は 5.5T トークンで約 55.3 万 B200 GPU 時間と見積もられ、FSx for Lustre には約 82 TiB を 250 MB/s/TiB で確保するとしています。計画全体では GPU 時間が約 11 % 足りず、トークン数を減らすなどの調整が検討されていますが、以下では調整前の値を使います。ファイルシステム全体の帯域は $82 \times 250 = 20{,}500\ \mathrm{MB/s}$、つまり 20.5 GB/s です。

以下は、この計画の台数、GPU 時間、FSx の容量と帯域に、この記事が置いた仮定を組み合わせた試算で、実測ではありません。仮定は、1 トークンを 4 バイトの ID で 1 回だけ読むこと、チェックポイントに bf16 の重みと fp32 の master の重みと Adam の 2 つの状態が入って 1 パラメータあたり 14 バイトになること、30 分ごとに保存すること、同期の保存で止める時間を 1 % に収めること、RL では 10 台が同時に bf16 の重みを読むこと、の 5 つです。どの行も、10 台が均等に負荷を分け、他の I/O が無く、ファイルシステムが申込みの帯域を出し続ける場合の値です。

| # | 何を運ぶか | 計算 | ノード 1 台あたり | TCP の上限との比べ |
|---|---|---|---|---|
| 1 | 事前学習のトークン | $5.5 \times 10^{12} / (6912.5\ \mathrm{h} \times 3600) \approx 2.21 \times 10^5$ トークン/s を 10 台で分け、4 バイトを掛ける | 約 88 KB/s | 12.5 GB/s の約 14 万分の 1 |
| 2 | 同期のチェックポイントの保存 | $32 \times 10^9 \times 14 = 448\ \mathrm{GB}$ を 18 秒で書く。全体で 24.9 GB/s | 約 2.49 GB/s | 12.5 GB/s には収まる。公称の 625 MB/s では OSS 4 つで 2.50 GB/s となり余裕は 0.4 %、試験で測った 620 MB/s では 4 つで 2.48 GB/s となり届かないので、OSS が 5 つ以上要る |
| 3 | 非同期のチェックポイントの保存 | 448 GB を次の保存までの 30 分で書く | 約 25 MB/s | 十分に収まる |
| 4 | 障害の後の再開の読み込み | 448 GB を 20.5 GB/s で読むと 21.9 秒 | 約 2.05 GB/s | OSS が 4 つ以上要る |
| 5 | RL の推論ノードへの重みの配布 | 64 GB を 10 台が読むと 640 GB、20.5 GB/s で 31.2 秒 | 約 2.05 GB/s | OSS が 4 つ以上要る。64 GB の 1 本のファイルが OST 1 つにあると、TCP では 1 台が 102.4 秒かかる |

この表の負荷に限れば、ノード 1 台の帯域で TCP が足りなくなる行はありません。最も大きい #2 でも 2.49 GB/s で、TCP の合計の 12.5 GB/s の約 5 分の 1 です。#2 では、ファイルシステム全体の 20.5 GB/s が先に壁になり、18 秒の目標は TCP でも EFA でも届きません。同期の保存の 18 秒には、データの転送のほかにシリアライズや close も入るので、実際にはさらに厳しくなります。

TCP で問題になるのは、ノードの帯域ではなく、1 組のクライアントと OSS あたりの 625 MB/s です。#2、#4、#5 の 2 GB/s 前後を TCP で出すには、そのノードが読み書きするファイルが 4 つ、#2 では 5 つ以上の OSS に散っている必要があります。上限は OST ではなく OSS の単位で、1 つの OSS が複数の OST を持つこともあるので、OST の数だけでは判断できません。AWS は、OSS の数をファイルシステムの IP アドレスの数から確かめるよう案内しています。逆に、試験のように OSS が少ないファイルシステムや、大きな 1 本のファイルを OST 1 つに置く形 (`lfs setstripe -c 1` や既定の配置) では、ファイルシステム全体に帯域があっても、TCP のクライアント 1 台はその一部しか使えません。Turing の記事は、TCP 化の後の読み込みのバーストで約 2 GB/s を観測し、実際のワークロードでは性能の問題は表面化しなかったと書いています。Turing の環境の OST は 8 で、OSS の数は書かれていませんが、OSS が 4 つ以上で読み込みがそれらに散っていれば、この見積もりと矛盾しません。Turing の記事も書いているとおり、読み込みの実測はチェックポイントの書き込みの性能を保証しません。

表には、評価、ログ、データの前処理、画像や動画のようなマルチモーダルの入力、複数のジョブの同時実行の負荷が入っていません。Turing の記事でも、EFA で接続していた当時に、2 人以上の同時実行でファイルシステム全体の 125 MB/s/TiB が上限になっています。こうした負荷を足すと必要な帯域は上がるので、TCP で足りるかは実際の負荷を測って決めます。

AWS の性能の表で 5 Gbps の注記が付いていないのは、EFA 有効のファイルシステムに [ENA Express](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ena-express.html) で接続する行 (100 Gbps) です。この行が 1 組あたりの上限を受けないのかはドキュメントに明記されておらず、この記事でも試していません。

遅延が効く場面は、この計画の中には見当たりません。学習データの読み込みは DataLoader が先読みするので、1 ms 未満の差がステップの時間に出るとは考えにくいですが、測ってはいません。メタデータの操作は、試験の構成では EFA を有効にしても TCP を通ります。同期の書き込みでは fsync の約 9 ms が支配的で、TCP と EFA の中央値の比は 1.04 でした。

TCP では済まないのは、GPUDirect Storage (GDS) を使う場合です。AWS は GDS を、EFA 有効のファイルシステムと EFA を持つ NVIDIA の GPU インスタンスの組み合わせで提供していて、その組み合わせのクライアント 1 台の最大を [性能の説明](https://docs.aws.amazon.com/fsx/latest/LustreGuide/performance.html) で 1,200 Gbps としています。LNet は送るページが GPU のメモリかを [lnet_is_rdma_only_page](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/lnet/lnet_rdma.c#L264) で調べ、GPU のメモリなら kefalnd は小さなメッセージでも RDMA で運びます。チェックポイントを GPU のメモリから直接書く構成のように、ノード 1 台で数十 GB/s を必要とする設計を取るなら、TCP は選べません。その場合は、ファイルシステム自体も、この計画の 20.5 GB/s より大きな帯域で確保する必要があります。

## Turing の事象との対応

| 事象 | 実装で対応し得る箇所 | 確かめられたこと |
|---|---|---|
| NCCL は基準を満たすのに、LNet に TX completion error が出る | NCCL と kefalnd は efa.ko と EFA デバイスより上の部品を共有しない | 構造はコードで確かめた |
| 6/29、EFA の再送タイムアウトが増えても、RPC のタイムアウトと再送は 0 | kefalnd は送信の完了の状態だけを見る。EFA の再送が NIC の中で最終的に成功すれば、kefalnd にも LNet にも失敗として届かず、RPC の再送は増えない | kefalnd が完了の状態だけを見ることはコードで確かめた。NIC の中の再送の動きは確かめていない。Turing の記録の再送タイムアウトが最終的に成功したかは元の記事から分からない |
| 7/7〜7/9、OSS の EFA の NID が変わり、古い peer 情報で I/O が止まった | NID は PCI の位置を含む。変わった NID を既存の peer に統合するとき、[LOCK_PRIMARY の検査](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/lnet/peer.c#L1992) が両方の peer を BAD_CONFIG にする ([LU-20482](https://jira.whamcloud.com/browse/LU-20482)) | 2.15.6-1fsx34 の patch が [この検査を緩める](https://review.whamcloud.com/c/fs/lustre-release/+/67268) ことをソースで確かめた。upstream の 6325870 には入っていない。Turing の環境で BAD_CONFIG が起きたか、修正で解消したかは分からない |
| 7/13、自動で TCP に移らない | UDSP で efa が優先され、health に届かない失敗では選び直しが起きない。下がっても最大値で打ち消されるか、小さな ping の成功で戻り得る | クライアントの受信の入口で捨てた場合に、TCP に移らず止まり続けることを実機で確かめた。7/13 にどの種類の失敗が起きたかは元の記事から分からない。6/14 の TX completion error が LNet のメッセージを載せた送信のものなら health を下げる経路で、接続の確立の段階のものなら届かない可能性がある。どちらだったかは元の記事から分からず、実機でも試せていない |
| 7/20 以降、TCP 化の後も特定のノードペアと OST で 180〜185 秒止まり、eviction が出た | クライアントを TCP にしても、FSx のサーバは EFA の構成のままで、サーバ側の LNet と kefalnd の状態はクライアントから見えない | AWS の 8 月の回答と同じ範囲で、根本原因は分からない |

最後の行は、この記事の範囲でも説明できません。re:Post の記事も、クライアントの EFA を止めた後に、サーバ側に古い EFA の peer の NID が残り得るとしています。2.15.6-1fsx32 と fsx33 に入った LDLM のロックの返却の修正 ([LU-16285](https://jira.whamcloud.com/browse/LU-16285)、[LU-18229](https://jira.whamcloud.com/browse/LU-18229)、[LU-18602](https://jira.whamcloud.com/browse/LU-18602)) が関係するかも、サーバの記録が無いと確かめられません。

## まとめ

LNet は health を UDSP の優先度より先に比べますが、kefalnd は受け手で捨てたメッセージや使われ続ける接続で止まった送信を health に伝えず、試験ではクライアントが EFA で受け取れなくなっても health は 1000 のままで、TCP の経路が生きたまま 915 秒 EFA を選び続けました。TCP の上限は 1 組のクライアントと OSS あたり 5 Gbps で、OSS が少ないファイルシステム、大きな 1 本のファイル、GDS では足りませんが、80 枚の B200 の規模の学習の机上の試算では、ファイルが 5 つ以上の OSS に散っていれば、ノード 1 台の必要帯域は TCP の上限に収まります。
