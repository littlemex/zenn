## はじめに

Amazon FSx for Lustre のクライアントは、EFA 有効のファイルシステムに EFA と TCP の両方の経路を持てます。EFA は帯域が大きい一方、仕組みが TCP より複雑で、EFA の経路だけが不調になったときにクライアントがどう振る舞うかは、文書からは読み取りにくい部分です。運用の中で、クライアントの EFA を止めて TCP に固定するかを検討する場面もあります。そのとき知りたいのは、次の 3 つです。

1. EFA の経路が使えなくなったとき、Lustre は自動で TCP に移るのでしょうか。
2. TCP に固定すると、帯域と遅延の何を失うのでしょうか。
3. どの規模の学習までなら TCP で足りるのでしょうか。

先に答えを短く書きます。1 つ目の答えは、自動で TCP に移ることを前提にしない、です。コードを読むと、送信の失敗で health が下がった直後に限って TCP が選ばれる道はありますが、health は相手からの次の受信で戻るので、その時間は短いと考えられ、この記事ではその道を実機で確かめられていません。一方、自分の送信は成功として完了し、相手からの応答や要求が自分の側で届かない、または届いても捨てられる故障では、クライアントの LNet には失敗が返らないので、EFA を選び続け得ます。この記事の試験はこの形で、クライアントの受信の側で EFA から届くメッセージをすべて捨てると、TCP の側には何もしていないのに、故障を入れていた約 890 秒のあいだ、クライアントの LNet は EFA を選び続け、I/O は止まったままでした。AWS の re:Post にも、EFA のエラーが出ても自動では切り替わらない例が載っています。2 つ目は、試験の構成 (EFA 有効のファイルシステムに ENA で接続) では、TCP のクライアント 1 台と 1 つの OSS の間が約 620 MB/s で頭打ちになったことで、これは同じ条件で測った EFA の約 1/8〜1/13 でした。3 つ目は、ノード 1 台が必要とする帯域と、そのノードのファイルが散っている OSS の数で決まります。GPUDirect Storage を使う場合は、TCP は選べません。

この記事は、この 3 つを、FSx for Lustre のクライアントの公開ソースと、東京リージョンに立てた EFA 有効のファイルシステムでの試験から説明します。最初に Lustre の通信の仕組みを基礎から説明するので、Lustre の通信層を知らなくても読めます。EFA と GPU の学習の基本は知っているものとします。

## Lustre の通信の基礎

Lustre は、ファイルの中身と、ファイルの名前や置き場所の情報を、別々のサーバに置く並列ファイルシステムです。名前、権限、ファイルの中身がどこにあるかといった情報をメタデータと呼び、MDS (メタデータサーバ) が MDT という記憶領域に持ちます。ファイルの中身は OSS (オブジェクトストレージサーバ) が OST という記憶領域に持ちます。1 本のファイルを複数の OST に分けて置くこともでき、これをストライプと呼びます。もう 1 つ、MGS がファイルシステムの構成をクライアントに配ります。FSx for Lustre では、これらのサーバは AWS が運用していて、利用者が知っているのはファイルシステムの DNS 名とマウントの名前です。

クライアントとサーバの間のやりとりは 2 種類です。1 つは、要求を送って応答を受け取る小さなやりとりで、RPC と呼びます。ファイルを開く、ロックを取る、読み書きを依頼する、といった操作が RPC です。もう 1 つは、ファイルの中身そのもののような大きなデータで、bulk と呼びます。次の図は、クライアントの中の層と、クライアントが各サーバと何をやりとりするかを示します。

![クライアントの中は、アプリケーション、llite、mdc と osc、ptlrpc、LNet、LND の順に重なり、すべてのやりとりは LND から出入りする。クライアントはマウントで MGS から構成を受け取り、ファイルを開くときやメタデータのロックを取るときは MDS に RPC を送り、読み書きとファイルの中身の範囲のロックでは OSS に RPC を送る。ファイルの中身 (bulk) は、読み込みでは OSS からクライアントへ、書き込みではクライアントから OSS へ流れる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/5a792cff5d5f61/zenn/articles/5a792cff5d5f61/basics.png)

クライアントがファイルを読むときは、まず MDS に RPC を送ってファイルを開き、中身がどの OST にあるかを教わります。名前や属性のロックは MDS から、ファイルの中身の範囲のロック (extent lock) はその OST から取ります。次に、その OST を持つ OSS に読み込みの RPC を送り、OSS がファイルの中身を bulk としてクライアントに送り返します。書き込みでは、クライアントが OSS に書き込みの RPC を送り、OSS がクライアントから中身を bulk として取りにきます。

クライアントの中の層は、上から次の役割を持ちます。llite はアプリケーションから見えるファイルシステムで、mdc と osc はそれぞれ MDS と OSS への要求を組み立てます。ptlrpc は RPC を送って応答を待ち、応答が来なければサーバとの接続を張り直します。ptlrpc が持つ、ターゲット (OST や MDT) ごとの接続の状態を import と呼び、正常なら FULL、張り直している間は CONNECTING になります。その下の LNet が、どの宛先にどのネットワークで送るかを決め、最後の LND (Lustre Network Driver) が、ネットワークの種類ごとに実際の送受信をします。

この記事に出てくる LNet の言葉を、まとめておきます。

| 言葉 | 意味 | 試験での例 |
|---|---|---|
| NID | LNet の中のアドレス。`アドレス@ネットワーク` の形 | `10.0.1.20@tcp`、`1.20.0.248@efa` |
| LND | ネットワークの種類ごとの送受信のドライバ | TCP は ksocklnd、EFA は kefalnd |
| NI | 自分の側の、1 つのネットワークの口 | クライアントの `2.30.0.248@efa` |
| peer と peer NI | 通信相手のホストと、相手が持つ NID の 1 つ | OSS が tcp と efa の 2 つの peer NI を持つ |
| peer net | 相手が持つ peer NI のうち、同じネットワーク (tcp や efa) に属するもののまとまり | OSS の efa の peer net |
| Multi-Rail | 1 台が複数の NID を持ち、送るたびに使う口を選ぶ仕組み | OSS の tcp と efa |
| discovery | 相手が持つ NID の一覧を問い合わせて、1 つの peer にまとめる仕組み | マウントの直後に動く |
| PUT と GET | LNet が運ぶメッセージの 2 種類。PUT は送り手が相手にデータを送り込み、GET は相手のデータを取りにいく。GET の応答が REPLY、PUT の受け取りの確認が ACK | ファイルの読み込みの bulk は OSS からの PUT、書き込みの bulk は OSS からの GET |
| health | NI と peer NI ごとの調子を表す 0〜1000 の点数。失敗の種類に応じて下がり、自分の NI は送受信の成功で、peer NI はその相手からの受信で戻る。経路を選ぶときは、peer net の中の peer NI の最大値を、そのネットワークの health として使う | 試験では常に 1000 |
| recovery | health が下がった NI に LNet が定期的に ping を送り、応答で health を戻す仕組み | |
| UDSP | どのネットワークを優先するかの規則。優先度は数値が小さいほど高い | AWS のスクリプトが efa を優先度 0 にする |

EFA の側の言葉も短く書いておきます。SRD は EFA の通信方式で、NIC が失われたパケットを送り直します。ソフトウェアから見ると、送ったものは届くか、失敗が通知されるかのどちらかです。QP は送受信の窓口で、GID は EFA デバイスのアドレスです。RDMA READ は、相手の CPU を使わずに相手のメモリを読む操作で、読まれる側が事前にメモリを登録し、その鍵とアドレスを読む側に渡しておく必要があります。最後に、Lustre のサーバは、応答しないクライアントを一定時間で切り離すことがあり、これを evict と呼びます。evict されたクライアントのロックや途中の要求は捨てられ、クライアントは接続し直します。

## LNet と NCCL

Lustre で NCCL に当たるのは、前の節の LNet と LND です。NCCL が集団通信を差し替え可能な net plugin に流すように、LNet は Lustre の RPC と bulk を、ネットワークごとの LND に流します。TCP には ksocklnd、InfiniBand には o2iblnd、EFA には kefalnd があります。kefalnd は Lustre の課題管理 (Whamcloud の Jira) のチケット [LU-18977](https://jira.whamcloud.com/browse/LU-18977) で upstream に入り、[lnet/klnds/efalnd](https://github.com/lustre/lustre-release/tree/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd) にあります。この記事に出てくる `LU-` で始まる番号は、どれもこの Jira のチケットです。

| 項目 | NCCL | LNet |
|---|---|---|
| 運ぶもの | GPU 間の集団通信のデータ | Lustre の RPC と bulk |
| 動く場所 | ユーザー空間 | カーネル |
| ネットワークを差し替える部品 | net plugin (aws-ofi-nccl) | LND (kefalnd、ksocklnd、o2iblnd) |
| EFA の使い方 | libfabric の efa provider から、ユーザー空間の verbs で使う | カーネルの ib_verbs で SRD の QP を直接使う |
| 複数の経路の扱い | 複数の NIC にチャネルを分ける | Multi-Rail: 送るたびに相手の NI を選び、health で避ける |
| 失敗の扱い | 通信のエラーをアプリケーションに返す | LNet は失敗の種類に応じて health を下げ、条件を満たすメッセージだけを再送する。ptlrpc は RPC のタイムアウトで接続を張り直す |

次の図は、1 枚の EFA の上で NCCL と Lustre がそれぞれどの部品を通るかを、試験のファイルシステムの NID とあわせて示します。

![NCCL の部品 (aws-ofi-nccl、libfabric、ユーザー空間の verbs) と Lustre のクライアントの部品 (llite、osc/mdc、ptlrpc、LNet、kefalnd) は別々で、共有するのはカーネルの RDMA の共通部分、efa.ko、EFA デバイスだけ。Lustre の LNet は ksocklnd から TCP にも出られる。試験のファイルシステムでは、クライアントから見た OSS は EFA と TCP の両方の NID を持ち、MGS と MDS は TCP の NID だけを持っていた](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/5a792cff5d5f61/zenn/articles/5a792cff5d5f61/stacks.png)

NCCL と Lustre が共有するのは、カーネルの RDMA の共通部分 (ib_core)、efa.ko、EFA デバイスで、それより上の部品は共有しません。kefalnd は libfabric を使わず、カーネルの verbs で SRD の QP に [送信の要求](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd.h#L266) を積みます。そのため、NCCL のテストが通っても、Lustre の EFA の経路が正常とは限りません。NCCL のテストが確かめるのは EFA のデバイスと libfabric の経路までで、kefalnd の接続の状態や LNet の経路選択は確かめません。

試験のファイルシステムでは、クライアントの `lnetctl peer show` で見た OSS の peer は `10.0.1.20@tcp` と `1.20.0.248@efa` の 2 つの NID を持ち、MGS と MDS の peer は `10.0.1.40@tcp` だけを持っていました。マウント時の discovery のログにも `Peer 10.0.1.40@tcp has discovery disabled` と出ていました。MDS が TCP の NID しか見せていないので、この構成ではメタデータの操作は EFA を有効にしても TCP を通り、EFA を通るのは OSS との RPC と bulk です。MDT が多い大きなファイルシステムでも同じかは確かめていません。

## kefalnd の実装

この節では、EFA の経路が何に依存しているかを、kefalnd の NID の作り方、接続の作り方、データの運び方、失敗の伝え方の順に見ます。

### NID の作り方

LNet の NID には、アドレスの部分が 4 バイトの small NID と、16 バイトの large NID があります。`1.20.0.248@efa` のような形は small NID で、kefalnd の small NID は [kefalnd_create_efa_nid](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd.c#L2922) で作られます。次の図の上の段は、試験の OSS の NID がどう組み立てられているかを、下の段は、その逆に EFA の NID から相手の TCP の NID を求める計算を示します。OSS の PCI の値は、クライアントから見えた NID から逆算したもので、OSS で測ったものではありません。

![TCP の NID 10.0.1.20 の上位 16 ビットを捨て、下位 16 ビットの 1.20 を EFA の NID の上位に置き、EFA デバイスの PCI のバス番号 0 と devfn 248 を下位に置いて 1.20.0.248@efa になる。相手の TCP の NID は、自分の IP の上位 16 ビットと相手の EFA の NID の上位 16 ビットから作られる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/5a792cff5d5f61/zenn/articles/5a792cff5d5f61/nid.png)

```c
		pci_dev = to_pci_dev(efa_dev->ib_dev->dev.parent);
		addr = (__swab32(efa_dev->ifip) & 0xffff) << 16;
		addr = addr | ((pci_dev->bus->number & 0xff) << 8);
		addr = addr | (pci_dev->devfn & 0xff);
```

`ifip` は TCP の口の IPv4 アドレスで、`__swab32` でバイトの順を入れ替えた後の下位 16 ビットが、アドレスの後ろ半分 (図の `1.20`) に当たります。試験では、クライアントの `10.0.2.30@tcp` が `2.30.0.248@efa` に、OSS の `10.0.1.20@tcp` が `1.20.0.248@efa` になり、この読み方と合っていました。NID の下位は、ホストの中で EFA が挿さった PCI の位置です。サーバの EFA の PCI の位置が変われば、IP が同じでも EFA の NID は変わります。

NID が変わることには、公開されている不具合が 1 つ関係します。LNet は discovery で受け取った NID を 1 つの peer にまとめます。公開チケットの [LU-20482](https://jira.whamcloud.com/browse/LU-20482) は、peer の NID の 1 つが付け直されると、peer をまとめるときの [検査](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/lnet/peer.c#L1992) にかかって I/O が止まる不具合として登録されていて、2026-10-26 の時点では Open でした。2.15.6-1fsx34 には、同じ検査を緩める patch (`Lnet: Allow peer merge when lp_merge_primary_nid is set`) が入っています。patch の説明では、ホストの復旧などで EFA の PCI の位置が変わってサーバの EFA の NID が変わると、両方の peer が BAD_CONFIG になって EFA でサーバと通信できなくなる、としています。upstream の 6325870 には、この変更はまだ入っていません。これは公開されているチケットと patch の話で、この記事の試験とは別の事象です。

逆向きの計算は [efa_nid_to_tcp_nid](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd_peerni.c#L65) がします。相手の TCP の NID を、自分の IP の上位 16 ビットと、相手の EFA の NID の上位 16 ビットからつなぎ合わせます。自分と相手が同じ /16 にいないと、この計算は別のホストを指します。AWS は EFA 有効のファイルシステムに、クライアントと同じ AZ と同じ /16 を [求めています](https://docs.aws.amazon.com/fsx/latest/LustreGuide/efa-file-systems.html)。文書は理由を書いていませんが、small NID ではこの計算がその条件を必要とします。同じ文書は、EFA で接続するクライアントを、trn2 を除く Nitro v4 以降の EFA 対応インスタンスとし、EFA を有効にするかはファイルシステムを作るときにしか選べないとしています。large NID は GID と接続用の QP の番号と QKEY から作られ、この節の話は当てはまりません。

### 接続の確立

kefalnd が EFA で最初のメッセージを送るには、相手の EFA の GID と、接続を管理するための QP の番号が要ります。この QP を、以下では CM QP と呼びます。[kefalnd_find_remote_peer_ni](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd_peerni.c#L210) は、その対応を手元のキャッシュから探し、無ければ、上の計算で作った相手の TCP の NID に [LNet の ping](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd_peerni.c#L251) を打ちます。ping の応答には相手の NID の一覧と、NID ごとの付加情報が載っていて、kefalnd はそこから EFA の NID に対応する GID と CM QP の番号を取り出します。下のログの `Found 1 mappings` がこの部分です。

その後、両側の kefalnd は EFA の上で probe と接続要求を交わし、相手の epoch を覚えます。epoch は NI を起動したときの [時刻](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd.c#L3239) で、相手の NI が起動し直したかを見分けるのに使います。後で見るとおり、宛先の epoch が合わないメッセージは受け手で捨てられます。

接続は INACTIVE、PROBE_TCP、PROBE_EFA、ESTABLISH、ACTIVE の順に状態が進みます。次の図は、試験でクライアントが最初に OSS へ送ったときの接続の確立を、マウント時に `lctl set_param debug=+net` で取ったクライアントのログの時刻とともに示します。図は流れを、下の折り畳みのログは時刻を見るためのものです。1 回の記録で、最初の送信の要求から ACTIVE まで 3.0 ms、最初の PUT の完了まで 3.5 ms でした。最初の PUT は、この接続を作るきっかけになった送信で、接続が ACTIVE になってから送られます。

ここから分かるのは、EFA の経路が TCP の経路に依存していることです。対応がキャッシュに無いとき、EFA の接続を作るには、相手の TCP の NID に ping が届き、相手の LNet がその NID で応答する必要があります。TCP だけの経路は、TCP が動けば使えます。EFA の経路は、TCP と EFA の両方が動き、さらに双方の NID と epoch の対応が正しく保たれて初めて使えます。キャッシュに古い対応が残った場合に何が起きるかは、この記事では試していません。

### データの運び方

kefalnd が bulk を運ぶ方法は、受け手が送り手のメモリを RDMA READ で読む 1 通りだけです。[メッセージの種類](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd_proto.h#L194) には、RDMA READ で運ぶ版の PUT と GET しかなく、それぞれ PUTR と GETR という名前です。末尾の R が READ を表し、RDMA WRITE で運ぶ版はありません。ヘッダとデータを合わせて [8,900 バイト以下](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd.c#L1088) に収まるメッセージは、RDMA を使わずに IMMEDIATE として EFA で 1 回で送ります。

次の図は、ファイルの読み込みと書き込みのそれぞれで、どちらが RDMA READ を出し、どの制御メッセージを交わすかを示します。図の左は読み込み (OSS からクライアントへの PUT) で、右は書き込み (OSS がクライアントから取る GET) です。

![クライアントが読むとき、OSS が PUTR_REQ で自分のメモリのアドレスと鍵を渡し、クライアントが RDMA READ で約 1 MiB ずつ読み、PUTR_DONE を返す。クライアントが書くとき、OSS が GETR_REQ を送り、クライアントが GETR_ACK でアドレスと鍵を渡し、OSS が RDMA READ で読み、GETR_DONE を返す。試験の後のクライアントのカウンタは、rdma_read_bytes の増分が 80 GiB、rdma_read_wrs が 81,921、rdma_write_wrs が 0](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/5a792cff5d5f61/zenn/articles/5a792cff5d5f61/bulk.png)

kefalnd ではどちらの向きも受け手が読みにいくので、ファイルを読むときはクライアントが OSS のメモリを読み、ファイルを書くときは OSS がクライアントのメモリを読みます。試験では、4 MiB の I/O で書き込みと読み込みをそれぞれ 80 GiB 流しました。帯域と遅延の測定をすべて流した前後で、クライアントの `/sys/class/infiniband/efa_0/ports/1/hw_counters` の `rdma_read_bytes` は 8,276 から 85,899,354,196 に増え、増分はちょうど 80 GiB で、読み込んだファイルの量と同じでした。別に取った累計では、`rdma_read_wrs` が 81,921 回、`rdma_write_wrs` が 0 で、累計のバイト数と回数の比は約 1 MiB です。`rdma_read_wrs` の測定前の値は記録していないので、測定の区間だけの平均ではありません。書き込みの向きで OSS がクライアントを読んでいることは、コードから読んだもので、クライアントのカウンタでは確かめていません。同じ区間の 4 KiB の遅延の測定の I/O は 8,900 バイト以下なので IMMEDIATE で運ばれるはずで、RDMA の量がちょうど 80 GiB だったこととも合いますが、メッセージの種類を記録したわけではありません。

この運び方では、1 回の bulk ごとに、読まれる側のメモリの登録と解除、鍵とアドレスの受け渡し、どの bulk が終わったかを照合するための番号 (cookie) の突き合わせが要ります。メモリの登録には、verbs の FRWR という、その都度 QP に登録の要求を積む方式を使います。TCP の ksocklnd は、ソケットにバイト列を流すだけです。EFA の経路では、こうした状態の数が多く、相手と食い違う箇所も多くなります。2.15.6-1fsx35 と fsx36 に入った kefalnd の修正の多くは、この状態の管理に関するものです。[LU-20191](https://jira.whamcloud.com/browse/LU-20191) は接続の後始末を分け、[LU-20496](https://jira.whamcloud.com/browse/LU-20496) は使われていない接続だけを壊すようにし、[LU-20497](https://jira.whamcloud.com/browse/LU-20497) は古い受信の完了と応答の cookie を扱い、[LU-20655](https://jira.whamcloud.com/browse/LU-20655) は起動の失敗時の参照カウントを直し、[LU-20790](https://jira.whamcloud.com/browse/LU-20790) と [LU-20791](https://jira.whamcloud.com/browse/LU-20791) は受信バッファの漏れと接続の参照カウントを直しています。FSx のリポジトリでは fsx35 が 2026-09-10、fsx36 が 10-19 に公開されていて、kefalnd はいまも修正が続いている部品です。

### 失敗の伝わり方

kefalnd の接続には、使われている状態と、閉じて資源を返す処理 (以下、後始末) を待つ状態があります。接続を管理するスレッドが、閉じると決めた接続 (非活性化された接続) や、長く使われていない接続を、約 5 秒ごとの見回りで後始末を待つ一覧に移します。そのうえで、kefalnd は、失敗の種類ごとに、health の何を下げるかを決めた状態を付けて LNet に返します。LNet は [lnet_health_check](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/lnet/lib-msg.c#L961) でその状態を見て、相手の peer NI の health と自分の NI の health を下げ、場合によっては再送します。

| 失敗 | kefalnd が付ける状態 | LNet がすること |
|---|---|---|
| 送信の完了がエラーで返る | [REMOTE_DROPPED](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd.c#L1585)。自分から開いた接続なら非活性化する | 相手の peer NI の health を下げ、再送を試みる |
| メモリの登録の完了がエラーで返る | [LOCAL_DROPPED](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd.c#L1576) | 自分の NI の health を下げ、条件によって再送する |
| 送った後、決まった時間内に完了しない | NETWORK_TIMEOUT。ただし、調べるのは後始末を待つ接続の一覧に入った接続だけ | 相手の peer NI と自分の NI の health を下げ、[再送はしない](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/lnet/lib-msg.c#L1033) |
| 受信したメッセージの検査に落ちる | 何も付けずに [捨てる](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd.c#L1766)。送り手には何も返さない | 何もしない |

「送った後、決まった時間内に完了しない」の行の限定が、この記事の中心の 1 つです。送信の期限を調べる [kefalnd_drain_ni_conns](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd_connection.c#L1281) は、接続を管理するスレッドが後始末を待つ一覧に移した接続だけを見ます。一覧に移るのは、非活性化された接続か、[peer_timeout の間使われなかった接続](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd_connection.c#L1175) です。peer_timeout の下限は定数 [EFALND_MIN_INIT_CONN_TIMEOUT](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd.h#L86) の 200 秒です。試験のクライアントでもモジュールのパラメータの 180 秒が 200 秒に引き上げられ、dmesg には `Added LNI 2.30.0.248@efa [32/8192/0/200]` と出ていました。角括弧の値は、順に peer の送信の枠、NI 全体の送信の枠、ルータ用の枠、peer_timeout です。相手から開かれた接続には、さらに [300 秒](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd_connection.c#L20) が足されます。

一方、kefalnd は送るたびに [kefalnd_get_or_init_conn](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd.c#L1057) で接続を引き、そのたびに接続の [最後に使った時刻を更新](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd_connection.c#L550) します。上の層が 200 秒より短い間隔で送り続ける接続は、使われていることになり、後始末の一覧に移りません。その接続で完了を待ったまま止まった送信は、非活性化されない限り、kefalnd の期限にかかりません。ksocklnd の [ksocknal_check_peer_timeouts](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/socklnd/socklnd_cb.c#L2399) と o2iblnd の [kiblnd_check_txs_locked](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/o2iblnd/o2iblnd_cb.c#L3731) は、接続が使われているかに関係なく、送信ごとの期限を定期的に調べます。試験でも、EFA でマウントした直後の dmesg に、ksocklnd が期限を過ぎた送信の要求を見つけたことを示す `Total 1 stale ZC_REQs for peer_ni 10.0.1.20@tcp detected; the oldest(...) timed out 3 secs ago` が出ていました。fsx31 の kefalnd でも、送信の期限を調べるのは後始末の対象の接続だけで、同じ作りです。この段落はコードを読んだ結果で、止まった送信が実際に期限にかからなかったことは、試験では観測していません。

「受信したメッセージの検査に落ちる」の行には、宛先の epoch が自分の epoch と違うメッセージを捨てる処理が含まれます。相手の NI が起動し直して epoch が変わったのに、こちらが古い epoch で送り続ける場合がこれに当たります。SRD の層では届いているので、その EFA の送信は成功として完了し得ます。そのメッセージを載せた LNet の要求や RPC が最終的にどうなるかは別で、この形の故障は試していません。

LND の検査とは別に、LNet が受け取りを拒むメッセージもあります。後の試験で使う、受信の入口でメッセージを捨てる故障注入がこれに当たります。コード上、この場合の kefalnd は相手の bulk の要求には、[PUTR_DONE](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd.c#L1230) か [NACK](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd/efalnd.c#L1297) に `-ENODATA` を載せて返し、IMMEDIATE のメッセージには何も返しません。次の節の試験で、各要求がこの分岐を通ったかと、OSS が完了を受け取ったかは記録していません。

最後に、LNet の標準の故障注入 `lctl net_drop_add` には 2 つの使い方があります。`-e` を付けない使い方は受信側の LNet で効くので、LND に関係なく働き、次の節の試験はこちらを使います。`-e` を付けて health のエラーを注入する使い方は、kefalnd では働きません。`-e` は、LND が送信の前に [lnet_send_error_simulation](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/socklnd/socklnd_cb.c#L458) を呼ぶことで効きます。これを呼ぶのは ksocklnd と [o2iblnd](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/o2iblnd/o2iblnd_cb.c#L1042) で、kefalnd は fsx31 から fsx36 のどの版でも呼びません。試験でも、`lctl net_drop_add -s '*@efa' -d '*@efa' -r 1 -e remote_dropped` を入れて 2 GiB を書いた間、規則に当たったメッセージは 0 件で、書き込みは 2.1 秒で終わりました。この確認に使った筆者の試験のスクリプトは、debug ログから注入の記録を数える箇所で、記録が 1 行も無かったために失敗として終わっています。EFA の経路で health が下がる動きは、この標準の道具では試せません。

## LNet の経路選択

LNet は送るたびに、相手の peer のどのネットワークのどの NI へ、自分のどの NI から出すかを選びます。ネットワークを選ぶ [lnet_find_best_ni_on_local_net](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/lnet/lib-move.c#L2314) は、候補を次の順に [比べます](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/lnet/lib-move.c#L2388)。上の行で差がつけば、そこで決まります。fsx31 と fsx36 の LNet も同じ順です。

| 順 | 比べるもの | 試験の構成での値 |
|---|---|---|
| 1 | 相手のネットワーク (peer net) の health | tcp も efa も 1000 |
| 2 | 相手のネットワークの優先度 | 設定なし |
| 3 | 自分のネットワークの health | tcp も efa も 1000 |
| 4 | 自分のネットワークの優先度 | UDSP で efa が 0、tcp は設定なし |
| 5 | 相手のネットワークの順番の番号 | 4 番目で決まるので比べない |
| 6 | 自分のネットワークの順番の番号 (round robin) | 4 番目で決まるので比べない |

AWS の設定スクリプトを流した後の `lnetctl udsp show` は `src: efa`、`priority: 0` でした。UDSP の優先度は数値が小さいほど高いので、health がすべて等しいあいだは 4 番目の比較で efa が勝ち、OSS との RPC と bulk は EFA を通ります。試験でも、帯域の測定を終えた時点の `lnetctl peer show -v` で、OSS の TCP の NID への送信は 21 件だけでした。discovery と kefalnd の ping の分と考えられます。

peer net の health は、その中の peer NI の health の [最大値](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/include/linux/lnet/lib-lnet.h#L1129) です。peer NI の health は、失敗が相手のせいとされたときに [health_sensitivity だけ下がり](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/lnet/lib-msg.c#L578)、その peer NI からメッセージを [受け取るたびに同じだけ戻ります](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/lnet/lib-msg.c#L994)。health_sensitivity の既定は 100 で、試験のクライアントでも 100 でした。相手の peer が NID を全部で 1 つしか持たないときは、ルータやルーティングを有効にしている場合を除いて、相手の health の処理そのものを [行いません](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/lnet/lib-msg.c#L944)。試験の OSS は tcp と efa の 2 つを持つので、この条件には当たりません。

コードの順では health が UDSP の優先度より先に比べられるので、相手の efa の peer net の health が下がるか、自分の efa のネットワークの health が下がれば、TCP が選ばれる道はあります。自分の側が下がるのは、たとえばメモリの登録の失敗 (LOCAL_DROPPED) のときです。ここで言う失敗は、LNet から渡された RPC や bulk を載せた送信の失敗です。kefalnd が接続を作るために自分で送る probe や接続要求は、LNet のメッセージを載せていません。試験の OSS のように EFA の NID が 1 つの相手で、LNet のメッセージを載せた送信の完了エラーが 1 回 health に反映され、回復する前に次の送信の選択が行われれば、efa の peer net は 900、tcp は 1000 となり、コード上は TCP が選ばれます。この遷移は、前の節で書いた故障注入の制約のため、実機では試せていません。

その一方で、EFA が選ばれ続け得る要因が、コードの中に 3 つあります。どれも TCP に移るための必要条件ではなく、比較が EFA に有利なまま残り得る理由です。3 つの確かさは同じではないので、それぞれに書き添えます。

1. 失敗が health に届かないことがあります。kefalnd の受信の検査で捨てたメッセージは、その受信の処理からは health を下げません。使われ続けて非活性化されない接続では、止まった送信が後始末の期限の検査に進まない可能性があります。どちらもコードを読んだ結果で、ほかの経路で health が下がることまで無いとは言えません。次の節の試験は、kefalnd の受信の検査ではなく LNet の受信の入口で捨てる故障で、そこでも health は下がりませんでした。LNet には ACK や REPLY を待つ仕組み (`response_tracking`) もあり、これが効くメッセージなら別に health を下げますが、試験の 400 秒の間に health は動かず、Lustre の RPC の経路でどこまで効くかは確かめていません。
2. 下がっても最大値で打ち消されることがあります。相手が EFA の NID を複数持つなら、1 つでも 1000 の NI が残る限り efa の peer net は 1000 で、ネットワークの比較では TCP より不利になりません。試験の OSS は EFA の NID を 1 つだけ持っていたので、この要因は試験には当てはまりません。大きな構成のサーバがいくつ持つかは確かめていません。
3. 下がっても戻る可能性があります。LNet は health の下がった peer NI を recovery の列に入れて ping を送り、応答を受け取れば health を戻します。小さな ping は IMMEDIATE で運ばれ、RDMA READ を通りません。RDMA の経路だけが壊れているなら、ping の成功で health が戻り、次の bulk がまた EFA に流れることがあり得ます。これはコードから考えた可能性で、recovery の ping が実際にどの NI を通り、この形の故障で成功するかは確かめていません。

AWS の [re:Post の記事](https://repost.aws/articles/ARbKKMiQVXQbW-7DUCQTEjqQ/troubleshooting-fsx-for-lustre-how-to-perform-efa-to-tcp-failover-for-kefalnd-abort-tx-failures) は、自動で TCP に切り替わらない理由として次の 4 つを挙げ、これは設計どおりの動きで、手動の切り替えが要るとしています。(1) UDSP が efa を優先度 0 に固定し、UDSP が有効な間 LNet は TCP を選ばない。(2) kefalnd は失敗を LNet の health の仕組みに報告せず、`kefalnd_abort_tx` の失敗が続いても EFA の NI の health は 1000 のまま。(3) 接続した後の ping は EFA だけを通り、TCP はマウントのときのやりとりにしか使われない。(4) サーバの evict の 227 秒は、LNet が health を下げて切り替えるまでの時間より短い。re:Post が例として示しているのは、サーバ側に出る CONN_PROBE の完了エラー (サーバがクライアントの EFA の NID に届かないことを示す status 15) と、再接続の間にクライアントに出る `0.0.0.0@efa` 宛ての `kefalnd_abort_tx` で、re:Post は、相手の EFA のアドレスを解決できず、外向きの I/O がすべて失敗する状態としています。また re:Post は、Multi-Rail が 16 本の EFA の NID を束ねて帯域を出す設計だとも書いています。

この記事で読んだ版の公開ソースからは、これと並べて次のことが読めます。ネットワークの比較では health が UDSP の優先度より先に比べられます。kefalnd は、LNet のメッセージを載せた送信の完了エラーに REMOTE_DROPPED、メモリの登録の失敗に LOCAL_DROPPED を付けて LNet に返します。一方、接続を作る段階の送信は LNet のメッセージを載せていないので、re:Post が観察した `abort_tx` の最中に health が 1000 のままだったことは、このコードの読みとも矛盾しません。re:Post の例のような故障で health がどう動くか、health が下がって TCP に移る遷移が実際に起きるかは、この記事では確かめていません。

Lustre の上の層も、この選択を変えられません。ptlrpc の import が持つ接続先は TCP の NID で、試験でも `lctl get_param osc.*.ost_conn_uuid` は `10.0.1.20@tcp` でした。ptlrpc がタイムアウトして接続を張り直すときも、この NID を LNet に渡し、LNet が同じ peer の中から EFA の NI を選び直します。次の節の試験の条件では、実際にそうなりました。import の接続先の NID が `@tcp` であっても、実際に通る経路は LNet が決めます。

まとめると、TCP に移るには、相手の efa の peer net の health が tcp より下がるか、相手の側の health が同じで自分の efa のネットワークの health が tcp より下がった状態で、次の送信の選択が行われる必要があります。上の 3 つの要因はそれを妨げ得る条件で、ptlrpc が張り直しても経路は LNet が選び直すので、上の層は助けになりません。

### EFA で受け取れないクライアント

ここでは、EFA の経路だけが使えない状態を作り、Lustre が TCP に移るかを確かめます。クライアントの LNet の受信の入口に、EFA から届くメッセージをすべて捨てる規則を入れました。この規則は、LND を通った後の [lnet_parse](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/lnet/lib-move.c#L4752) で効く、`-e` を付けない LND によらない故障注入です。「失敗の伝わり方」の節のとおり、このときクライアントの kefalnd は、OSS の bulk の要求には `-ENODATA` の完了を返し、IMMEDIATE のメッセージは黙って捨てます。kefalnd 自身が epoch の不一致で捨てる場合とは、捨てる層も、OSS が受け取る知らせも違います。TCP の側には故障を入れていません。ただし、故障を入れている間に OSS への TCP の疎通を別に確かめたわけではありません。

次の図は、この規則を入れた後にクライアントのログで観測した順番を示します。

![クライアントの LNet が @efa から届くメッセージをすべて捨てると、クライアントが持つ OSS の peer の health は tcp も efa も 1000 のまま、ptlrpc は 10.0.1.20@tcp へ接続を張り直し、LNet は 1.20.0.248@efa を選び直して、OSS からの応答はまた @efa で届いて捨てられる。規則を入れていた約 890 秒のあいだ書き込みは終わらず、NIC 全体の送信量は 10 秒目から 400 秒目までで約 0.3 MB で、張り直しの間隔は約 35 秒、40 秒、45 秒と延びた](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/5a792cff5d5f61/zenn/articles/5a792cff5d5f61/stall.png)

試験のコマンドは次の 2 行です。

```bash
lctl net_drop_add -s '*@efa' -d '*@efa' -r 1
timeout 420 dd if=/dev/zero of=/fsx/f/c bs=4M count=64 oflag=direct status=none
```

256 MiB の書き込みは、規則を入れていた約 890 秒のあいだ戻りませんでした。この長さは筆者が規則を外した時刻で決まったもので、仕組みが決める値ではありません。外さなければ止まり続けたと考えられますが、確かめていません。規則を外してから約 25 秒後に dd が戻り、dd の経過時間は 914.6 秒、終了コードは `timeout` が打ち切ったことを示す 124 でした。

止まっている間に `ps` で見ると、dd は Lustre のクライアントの I/O の完了を待つ関数 `cl_sync_io_wait` で待ち、timeout は `sigsuspend` で待っていました。経過時間が 420 秒を過ぎていたので、timeout は SIGTERM を送った後だったと考えられ、止まった dd は SIGTERM では戻りませんでした。SIGKILL は試していません。同じ時点の `lctl net_drop_list` では、規則に当たったメッセージは 39 件で、OSS からの PUT が 18 件、GET が 21 件でした。書き込みの試験なので、PUT は OSS からの RPC の応答など、GET は OSS が bulk を取りに来る要求に当たると考えられますが、個々のメッセージの中身は記録していません。

10 秒目から 400 秒目まで 10 秒ごとに取った OSS の peer の health は、tcp も efa も 1000 のまま動きませんでした。同じ区間で、クライアントの NIC 全体の送信バイト数は 305,957 バイトしか増えておらず、書き込みが TCP に移って進んだ形跡はありません。このカウンタは TCP だけの量ではなく、NIC 全体の量です。LNet のログでは、ptlrpc が `connect to NID 10.0.1.20@tcp` で張り直しを試みるたびに、LNet が `sd_best_lpni = 1.20.0.248@efa` を選び、張り直しの間隔は `increasing latency to 35s`、`40s`、`45s` と延び、ログの時刻で約 35 秒、40 秒、45 秒でした。debug ログに残ったのはこの範囲で、その後の import の `state_history` では、約 56 秒ごとに DISCONN と CONNECTING を繰り返していました。記録した dmesg の範囲に evict の行はありませんでした。

health が 1000 のままだったのは、クライアントからの送信が成功として完了し、クライアントの kefalnd に health を下げる失敗が返らなかったためと考えられます。この区間の送信の完了の記録は取っておらず、OSS が受け取った `-ENODATA` をどう扱ったかも観測していません。応答が戻らないことで health を下げる `response_tracking` の対象になったメッセージや、その動きは記録していないので、この結果だけでは、この仕組みが働かなかったとまでは言えません。

規則を外した後は、5 秒ごとの確認で、20 秒後はまだ CONNECTING、25 秒後には import の状態が FULL に戻っていました。もう 1 回、同じ規則で 90 秒止めてから、マウントしたまま `lnetctl net del --net efa` を打ちましたが、`lnetctl net show` には efa の NI が残ったままでした。終了コードとエラーの出力は記録していません。その後に規則を外すと dd は終わり、この間の NIC 全体の送信量は、ログの MB の単位の表示で 0 でした。マウントしたまま EFA の NI を外して TCP に逃がすことは、この操作ではできませんでした。re:Post の記事の切り替えの手順は、アンマウントと `lctl network down` の後に `lnetctl net del --net efa --if <interface>` を打つもので、この試験の操作とは違い、この記事では試していません。I/O が止まった状態からアンマウントできるかも確かめていないので、ノードの再起動を含めた戻し方は、あらかじめ自分の環境で確かめておく必要があります。

::::details 故障注入の間のログ (クライアント)

## TCP と EFA の実測

### 帯域

帯域は fio の 4 MiB の direct I/O で測りました。1 本のファイルは 16 GiB、16 本のファイルはそれぞれ 4 GiB で、各読み込みの前にクライアントのページキャッシュを捨てています。fio の JSON の `bw` は KiB/s なので、10 進の MB/s に直して示します。次の図は、OST が 1 つの試験のファイルシステムに対して、同じクライアントから TCP だけと EFA で測った帯域を並べたものです。

![OST が 1 つの試験のファイルシステムで、同じ c7gn.16xlarge から測ると、TCP は 1 本と 16 本のファイルの読み書きのどれも 620 MB/s で、1 組のクライアントと OSS あたり 5 Gbps (625 MB/s) の線のすぐ下に並ぶ。EFA は 1 本の書き込み 5,576、1 本の読み込み 8,115、16 本の書き込み 4,772、16 本の読み込み 7,238 MB/s で、申込みの帯域 4,688 MB/s の線を超える](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/5a792cff5d5f61/zenn/articles/5a792cff5d5f61/tcp-vs-efa.png)

TCP では、ファイルの本数も読み書きの向きも関係なく、すべての測定が 620.3〜620.4 MB/s (4.96 Gbps) でした。AWS の [性能の説明](https://docs.aws.amazon.com/fsx/latest/LustreGuide/performance.html) では、クライアント 1 台と 1 つの OSS の間の通信は 5 Gbps に制限されるとされ、この注記が付いているのは、EFA を有効にしていないファイルシステムの行と、EFA 有効のファイルシステムに ENA で接続する行です。試験の接続は後者に当たり、測った値は 625 MB/s の 99.2〜99.3 % でした。このファイルシステムの OST は 1 つなので、すべての I/O が 1 つの OSS に集まり、文書の上限に近い値になりました。サーバ側の状態は観測していないので、この上限だけが律速したかは確かめていません。申込みの帯域は次の値です。

$$
\frac{4800\ \mathrm{GiB}}{1024\ \mathrm{GiB/TiB}} \times 1000\ \mathrm{MB/s/TiB} = 4687.5\ \mathrm{MB/s}
$$

TCP のクライアント 1 台で得られた帯域は申込みの帯域の 13.2 % で、クライアントの NIC の 200 Gbps よりずっと小さな値でした。

EFA では、1 本のファイルの書き込みが 5,576 MB/s、読み込みが 8,115 MB/s、16 本のファイルの書き込みが 4,772 MB/s、読み込みが 7,238 MB/s で、1 本のファイルでは TCP のそれぞれ 9.0 倍と 13.1 倍でした。EFA の 4 つの測定はどれも申込みの帯域を超えていて、超えた理由は、この試験で取ったクライアント側の情報からは分かりません。EFA の測定の直後の `lnetctl stats show` では、`local_error_count` が累計で 1 件でした。別に取った EFA の hw_counters では、SRD の再送のタイムアウト `retrans_timeout_events` が累計で 1 件でした。どちらも起きた時刻と帯域への影響は確かめていません。

### 4 KiB の遅延

4 KiB の遅延は、キューの深さ 1 の同期 I/O で 20 秒ずつ測りました。表の値は fio の JSON の、書き込みが `write.clat_ns`、fsync が `sync.lat_ns`、読み込みが `read.clat_ns` の百分位です。書き込みの行は fsync を挟む実行の中の書き込みの時間で、fsync の時間は含みません。比は丸める前の中央値から計算しています。

| 測定 (クライアント 1 台、OST 1 つ) | TCP の中央値 / p99 | EFA の中央値 / p99 | TCP / EFA (中央値) |
|---|---|---|---|
| 4 KiB の書き込み | 700 / 741 µs | 537 / 659 µs | 1.31 |
| fsync | 9,241 / 10,420 µs | 8,847 / 10,420 µs | 1.04 |
| 4 KiB の読み込み | 635 / 700 µs | 473 / 586 µs | 1.34 |

キューの深さ 1 の 4 KiB では、中央値の TCP / EFA の比は、書き込みで 1.31、読み込みで 1.34 でした。差は書き込みで約 164 µs、読み込みで約 162 µs です。fsync の中央値はどちらも約 9 ms で、比は 1.04 です。fsync の内訳は測っていません。fsync の p99 が TCP と EFA で同じ値なのは、fio が百分位を遅延のヒストグラムの区切りの値で返すためと考えられます。多数のクライアントが同時に小さな I/O を出す条件では測っていないので、その条件での差はこの測定からは分かりません。CPU の使用率も mpstat で取りましたが、測定の区間と fio の区間がそろっていなかったので、比較は控えます。

## 学習の規模から見た必要帯域

TCP で足りるかは、ノード 1 台が必要とする帯域と、TCP の上限の比で決まります。AWS の性能の説明では、クライアント 1 台の上限は、EFA を使わない TCP で 100 Gbps (12.5 GB/s)、EFA で 700 Gbps、EFA と GPUDirect Storage で 1,200 Gbps です。TCP のクライアント 1 台と 1 つの OSS の間は、前の節のとおり 5 Gbps (625 MB/s) です。

同期のチェックポイントで、ノード 1 台が必要とする帯域と、そのために要る OSS の数は、次の式で見積もれます。$P$ はパラメータ数、$b$ は 1 パラメータあたりのバイト数、$N$ はノード数、$T$ は保存のために止めてよい秒数です。

$$
B_\text{node} = \frac{P \times b}{N \times T}, \qquad n_\text{OSS} \ge \frac{B_\text{node}}{625\ \mathrm{MB/s}}
$$

例として、「[post-training 時代の LLM 学習の規模と効率の整理](https://zenn.dev/tosshi/articles/99375dd5ac013f)」の計画を使います。この計画は、Olmo 3 の 32B を p6-b200.48xlarge の 10 台、B200 の 80 枚で 1 年かけて学習するものです。事前学習は 5.5T トークンで約 55.3 万 B200 GPU 時間と見積もられ、FSx for Lustre には約 82 TiB を 250 MB/s/TiB で確保するとしています。計画全体では GPU 時間が約 11 % 足りず、トークン数を減らすなどの調整が検討されていますが、以下では調整前の値を使います。ファイルシステム全体の帯域は $82 \times 250 = 20{,}500\ \mathrm{MB/s}$、つまり 20.5 GB/s です。

以下は、この計画の台数、GPU 時間、FSx の容量と帯域に、この記事が置いた仮定を組み合わせた試算で、実測ではありません。仮定は次の 5 つです。

- 1 トークンを 4 バイトの ID で 1 回だけ読みます。
- チェックポイントには bf16 の重み、fp32 の master の重み、Adam の 2 つの状態が入り、1 パラメータあたり 14 バイトになります。
- 30 分ごとに保存し、同期の保存で止める時間を 1 %、つまり 18 秒に収めます。
- 再開のときは、各ノードがチェックポイントのうち自分の分だけを読みます。
- RL では、10 台が同時に bf16 の重みを読みます。

どの行も、10 台が均等に負荷を分け、他の I/O が無く、ファイルシステムが申込みの帯域を出し続ける場合の値です。

| # | 何を運ぶか | 計算 | ノード 1 台あたり | TCP の上限との比べ |
|---|---|---|---|---|
| 1 | 事前学習のトークン | 55.3 万 GPU 時間を 80 枚で割った 6,912.5 時間で $5.5 \times 10^{12}$ トークンを読むと、約 $2.21 \times 10^5$ トークン/s。10 台で分け、4 バイトを掛ける | 約 88 KB/s | 12.5 GB/s の約 14 万分の 1 |
| 2 | 同期のチェックポイントの保存 | $32 \times 10^9 \times 14 = 448\ \mathrm{GB}$ を、30 分の 1 % の 18 秒で書く。全体で $448 / 18 \approx 24.9\ \mathrm{GB/s}$ | 約 2.49 GB/s | 12.5 GB/s には収まる。公称の 625 MB/s を足し合わせると、OSS 4 つで $4 \times 0.625 = 2.50\ \mathrm{GB/s}$ となり余裕は約 0.4 %。試験で測った約 620 MB/s が各 OSS で同時に出ると仮定すると、4 つでは $2.48\ \mathrm{GB/s}$ で届かず、5 つ以上要る。複数の OSS での帯域は測っていない |
| 3 | 非同期のチェックポイントの保存 | 448 GB を次の保存までの 30 分で書く | 平均で約 25 MB/s | 平均では十分に収まる。書き出しの瞬間の帯域は別に見る |
| 4 | 障害の後の再開の読み込み | 各ノードが 44.8 GB ずつ、全体で 448 GB を 20.5 GB/s で読むと 21.9 秒 | 約 2.05 GB/s | OSS が 4 つ以上要る。各ノードが全体を読む形なら、総量が 10 倍になる |
| 5 | RL の推論ノードへの重みの配布 | bf16 の 64 GB ($32 \times 10^9 \times 2$) を 10 台が読むと 640 GB、20.5 GB/s で 31.2 秒 | 約 2.05 GB/s | OSS が 4 つ以上要る。64 GB の 1 本のファイルが OST 1 つにあると、TCP では 1 台が 102.4 秒かかる |

この表の負荷に限れば、ノード 1 台の帯域で TCP の合計の上限を超える行はありません。最も大きい #2 でも 2.49 GB/s で、12.5 GB/s の約 5 分の 1 です。ただし #2 では、申込みの帯域の 20.5 GB/s を全体の持続帯域と置くと、448 GB を書くだけで約 21.9 秒かかり、18 秒の目標に届きません。試験では EFA が申込みの帯域を超えたので、申込みの帯域が厳密な上限とは言えず、実機で 18 秒に届かないとまでは言えません。同期の保存の 18 秒には、データの転送のほかにシリアライズや close も入るので、実際にはさらに厳しくなります。この試算では、TCP か EFA かより先に、ファイルシステム全体の帯域が同期のチェックポイントの時間を決めます。

TCP で問題になるのは、ノードの帯域ではなく、EFA 有効のファイルシステムに ENA で接続する場合の、1 組のクライアントと OSS あたりの 625 MB/s です。#2、#4、#5 の 2 GB/s 前後を TCP で出すには、そのノードが読み書きするファイルが 4 つ、#2 では 5 つ以上の OSS に均等に散っている必要があります。上限は OST ではなく OSS の単位で、1 つの OSS が複数の OST を持つこともあるので、OST の数だけでは判断できません。クライアントからは、`lctl get_param osc.*.ost_conn_uuid` で OST ごとの接続先の NID が、`lfs getstripe` でファイルがどの OST にあるかが見えます。異なる OSS に散っているかと OSS の数は、AWS の性能の説明が案内しているとおり、ファイルシステムの IP アドレスの情報もあわせて確かめます。複数の OSS に散らしたときに、OSS の数に比例して帯域が伸びるかは、この記事では測っていません。逆に、試験のように OSS が少ないファイルシステムや、大きな 1 本のファイルを OST 1 つに置く形では、ファイルシステム全体に帯域があっても、TCP のクライアント 1 台はその一部しか使えません。

表には、評価、ログ、データの前処理、画像や動画のようなマルチモーダルの入力、複数のジョブの同時実行の負荷が入っていません。こうした負荷を足すと必要な帯域は上がるので、TCP で足りるかは実際の負荷を測って決めます。

AWS の性能の表で 5 Gbps の注記が付いていない行のうち、TCP で接続するのは、EFA 有効のファイルシステムに [ENA Express](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ena-express.html) で接続する行 (100 Gbps) です。この行が 1 組あたりの上限を受けないのかは文書に書かれておらず、この記事でも試していません。

遅延が効く場面は、この計画の中には見当たりません。学習データの読み込みは DataLoader が先読みするので、試験で見た 160 µs 前後の差がステップの時間に出るとは考えにくいですが、測ってはいません。メタデータの操作は、試験の構成では EFA を有効にしても TCP を通ります。同期の書き込みでは fsync の約 9 ms が支配的で、TCP と EFA の中央値の比は 1.04 でした。

GPUDirect Storage (GDS) を使う場合は、TCP は選べません。GDS は GPU のメモリとストレージの間で、CPU のメモリを通さずにデータを運ぶ仕組みです。AWS は GDS を、EFA 有効のファイルシステムと EFA を持つ NVIDIA の GPU インスタンスの組み合わせで提供しています。LNet は送るページが GPU のメモリかを [lnet_is_rdma_only_page](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/lnet/lnet_rdma.c#L264) で調べ、GPU のメモリなら kefalnd は小さなメッセージでも RDMA で運びます。チェックポイントを GPU のメモリから直接書く構成のように、ノード 1 台で数十 GB/s を必要とする設計を取るなら、ファイルシステム自体も、この計画の 20.5 GB/s より大きな帯域で確保する必要があります。

## EFA と TCP の比較

ここまでの結果を、EFA (kefalnd) と TCP (ksocklnd) の比較としてまとめます。根拠の列の「文書」は AWS の公開文書、「コード」は公開ソースを読んだ結果、「実測」はこの記事の試験の値で、試験はクライアント 1 台、OST 1 つ、試験の I/O 以外の負荷なしの条件です。

| 観点 | EFA (kefalnd) | TCP (ksocklnd) | 根拠 |
|---|---|---|---|
| クライアント 1 台の上限 | 700 Gbps、GDS を使うと 1,200 Gbps | 100 Gbps | 文書 |
| クライアント 1 台と OSS 1 つの間 | 上限の記載なし。試験では 4,772〜8,115 MB/s | EFA 無効のファイルシステムと、EFA 有効のファイルシステムへの ENA での接続で 5 Gbps (625 MB/s)。ENA Express での接続は記載なし。試験 (ENA) では約 620 MB/s | 文書、実測 |
| 4 KiB の読み込みの遅延 (中央値) | 473 µs | 635 µs | 実測 |
| 接続の作り方 | TCP の ping で相手の GID を取り、EFA の上で probe と接続要求を交わす | TCP の接続を張る | コード |
| データの運び方 | 受け手が RDMA READ で読む。GPU のメモリでなければ、ヘッダとデータの合計が 8,900 バイト以下のものは IMMEDIATE で送る。GPU のメモリなら小さくても RDMA を使う | ソケットにバイト列を流す | コード |
| 止まった送信の期限の確かめ方 | 後始末を待つ接続の、未完了の送信を調べる | peer ごとに送信の期限を定期的に調べ、試験でも期限切れの送信の検出がログに出た。対象となる送信の種類のすべては確かめていない | コード、ログ |
| health に届かない可能性のある失敗 | kefalnd の受信の検査で捨てたメッセージ。使われ続ける接続で止まった送信 | この記事では調べていない | コード |
| クライアントの LNet で EFA の受信を捨てた試験 | health は 1000 のままで、張り直しでも EFA が選ばれ、規則を入れていた約 890 秒 I/O が止まった | TCP だけの構成で同じ形の故障は試していない | EFA は実測 |
| EFA に固有の条件 | trn2 を除く Nitro v4 以降の EFA 対応インスタンス、ファイルシステムと同じ AZ と /16、EFA のモジュールと NI の設定。EFA を有効にするかはファイルシステムの作成時に決める | 左の条件は TCP での接続には要らない。TCP の接続そのものの設定と疎通は要る | 文書、試験の手順 |
| GPUDirect Storage | 使える | 使えない | 文書 |
| メタデータの通信 | 試験では MDS の peer に TCP の NID だけが見えていたので、メタデータの通信は TCP を通ると判断した。個々の操作の経路は記録していない | TCP | 接続先と peer の実測からの推論 |

TCP に固定してよいかは、次の 3 点で決まります。

1. GDS を使わないことです。
2. ノード 1 台が必要とする帯域が、ファイルの散り方を含めて、1 組あたり 625 MB/s の上限に収まることです。前の節の試算では、ファイルが 5 つ以上の OSS に均等に散っていれば、80 枚の B200 の規模の学習の 1 台あたりの必要帯域は計算上収まりましたが、複数の OSS での帯域は測っておらず、同期のチェックポイントの時間はファイルシステム全体の帯域で先に決まりました。
3. 小さな I/O の遅延の差が学習に効かないことです。試験のキューの深さ 1 の 4 KiB では、中央値の差は 1.3 倍、約 160 µs でした。
4. 固定の作業のために、クライアントのマウントを外せることです。この記事で試した手順はアンマウントから始まるので、そのクライアントのジョブは止まります。
5. 再起動の後も固定が続くことです。次の段落のとおり、AWS の設定スクリプトが作るサービスが起動のたびに EFA を設定し直すことがあります。

固定できたことは、`lctl list_nids` に `@efa` が出ないことと、`lnetctl peer show -v` で OSS の `@tcp` の NID の送信数が読み書きに応じて増えることで確かめられます。

TCP に固定する手順として、この記事で試したのは、正常にアンマウントできる状態からの、アンマウント、`lustre_rmmod`、tcp の NI だけで `lnetctl net add`、再マウントの順です (「構成と手順」の折り畳み)。そこに載せたコマンドは試験のためにアンマウントの失敗を無視していますが、実際に使うなら、アンマウントやモジュールの停止に失敗したところで止め、再マウントの後に `lctl list_nids` と `lnetctl net show` に efa の NI が無いことと、読み書きが進むことを確かめてください。AWS の [EFA のクライアントの設定の説明](https://docs.aws.amazon.com/fsx/latest/LustreGuide/configure-efa-clients.html) によると、`setup.sh` は起動のたびに EFA を設定する systemd のサービスを作ります。この記事の試験は `--configure-once` を付けてサービスを作らずに流したので、TCP に固定した状態が再起動の後も残るかは、そのサービスの扱いによります。恒久的に TCP に固定するなら、そのサービスの有無と状態を確かめ、起動のときに EFA が設定し直されないようにしたうえで、再起動の後にも NI と読み書きを確かめる必要があります。再起動の後の状態は、この記事では確かめていません。

EFA を使い続ける場合、この記事の試験の形の故障では、Lustre は自動で TCP に移りませんでした。一般に、監視では接続の状態だけでなく、実際の I/O が進んでいるかも見る必要があります。試験では、import の `state_history` が DISCONN と CONNECTING を繰り返し、同じ間に dd の書き込みは進まず、dd は SIGTERM でも戻りませんでした。ファイルシステムに問い合わせる診断のコマンドは、同じように止まる可能性を考えて、監視の処理を塞がない形で実行するのが安全です。どの指標と時間で切り替えを判断するかは、環境で確かめて決めてください。TCP に固定したときのジョブの時間や費用への影響は、この記事では見積もっていません。

## 止まったときの確認と対処

この記事の試験で見えたことを、I/O が止まったときに何を見て何をするかの形で並べます。どれもクライアント 1 台、OST 1 つ、この記事の故障の形での結果で、ほかの故障の形でも同じとは限りません。

| 段階 | 見るもの、すること | この記事での確認 |
|---|---|---|
| 気づく | import の `state_history` が DISCONN と CONNECTING を繰り返す。dmesg に `Request sent has timed out for slow reply` と `Connection to ... was lost` が出る。読み書きが進まない | 試験で確認した |
| 気づくのに使えないもの | `lnetctl peer show -v` の health。止まっている間も 1000 のままだった。NCCL のテストの成否も、Lustre の経路とは別 | 試験で確認した |
| 実際に通っている経路 | `lnetctl peer show -v` の、OSS の NID ごとの送信数の増え方 | 帯域の測定の後に 1 回だけ確認した |
| 止まったプロセス | SIGTERM では戻らなかった | SIGKILL は試していない |
| TCP に逃がす | マウントしたままの `lnetctl net del --net efa` (`--if` なし) では NI が残った。re:Post の手順と、止まった状態からのアンマウントは試していない | 一部だけ確認した |
| 最後の手段 | ノードの再起動。再起動の後に EFA が設定し直されるかは、AWS の設定スクリプトが作るサービスの有無で決まる | 試していない |

試験では health の値は止まっている間も変わらなかったので、health を見ても止まったことは分かりませんでした。I/O が進んでいるかと import の状態を、監視の処理そのものが止まらない形で見ることになります。止まった状態から戻す手順は、ノードの再起動を含めて、あらかじめ自分の環境で確かめておく必要があります。

## まとめ

公開ソースを読む限り、LNet は health を UDSP の優先度より先に比べる一方、kefalnd が health に伝えない失敗があり、試験ではクライアントの LNet で EFA の受信を捨てると、health は 1000 のまま、規則を入れていた約 890 秒のあいだ EFA が選ばれ続けて I/O が止まりました。EFA 有効のファイルシステムに ENA で接続した TCP は、クライアント 1 台と OSS 1 つの間が約 620 MB/s で頭打ちになり、GDS を使わず、ファイルが十分な数の OSS に散っていれば、80 枚の B200 の規模の学習の 1 台あたりの必要帯域は、計算の上では TCP の上限に収まります。
