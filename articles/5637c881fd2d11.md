## はじめに

Engram は、直前の数トークンの並びから表の行を決めて読み、読んだ値を隠れ状態に足す部品です。仕組みは「[小さな GPT で Engram を試す](https://zenn.dev/tosshi/articles/35ef2467d84b63)」で、実際の値を使って追いました。この表は大きくなります。DeepSeek-V4.1-Flash の[公式の推論コードの設定](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash/blob/2cba9e42aa026125f3ed06c6d98c1db82f7ca027/inference/config.json)では、表は 2 か所にあり、行は合わせて約 7.68 億、1 行は 256 個の値です。8 ビットの浮動小数点数である FP8 で数えると約 196 GB になり、GPU のメモリに置くと、モデルのほかの重みに使える場所がその分減ります。

読む行は入力のトークンだけで決まるので、表を CPU 側のメモリに置いておき、必要な行だけを計算の前に取り寄せることができます。[論文](https://arxiv.org/abs/2601.07372)の 6.4 節は、1,000 億個のパラメータの表をすべて CPU 側のメモリに置き、最初のブロックの計算と重ねて PCIe で取り寄せる実験を報告しています。表を足さないモデルと比べたスループットの低下は、NVIDIA の H800 で最大 2.8% でした。8B のモデルで、1 秒あたり 6,315.52 トークンが 6,140.02 トークンになった値です。

取り寄せ方には 2 通りあります。GPU が CPU 側のメモリを直接読む方法と、CPU が行を集めて GPU に送る方法です。論文には、CPU 側が行を先に取り出して送るとあり、筆者はこれを後者と読みました。前者は CPU の手を借りずに済みますが、どちらが速いかは論文からは分かりません。そこでこの記事では、GPU を 1 枚積んだ 1 台のマシンで、2 つの方法の速さを比べました。

結論を先に書きます。**一度に 64 MiB 分の行を読む場合、GPU が直接読む方法は、表が 256 MiB と 512 MiB のときは 50.7〜50.8 GB/s でした。表が 1 GiB 以上では遅くなり、16 GiB では 10.0 GB/s でした。CPU が集めて送る方法は、256 MiB の表での 24.0 GB/s から 16 GiB の表での 20.7 GB/s へ、約 14% 下がっただけでした。** 遅くなるのは表の大きさそのものではなく、行が散らばるアドレスの範囲が広いときでした。 一方、一度に読むのが 256 行、64 KiB と少ない場合は、256 MiB から 16 GiB のどの表でも、GPU が直接読むほうが速い結果でした。

:::message alert
**この記事の数は、特に断らない限り、筆者が AWS の仮想マシン 1 台で測った値です。**
:::

## 表の行を CPU 側のメモリから読む 2 つの方法

![左が CPU 側、中央が PCIe、右が GPU。上の段が方法 A で、GPU のカーネルが CPU 側のメモリの表から行を 16 バイトずつ PCIe 越しに読み、GPU のメモリに置く。下の段が方法 B で、CPU のコアが表から行を集めて送る前に行を並べておくメモリに並べ、1 回のコピーで GPU に送る。decode では行の番号が GPU の側にあるので、方法 B では番号を CPU に戻す。方法 A は実線、方法 B は破線の矢印](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/5637c881fd2d11/zenn/articles/5637c881fd2d11/host-two-ways.png)

図の上の段の**方法 A** では、GPU が CPU 側のメモリを直接読みます。表を置いたメモリを、GPU からもアドレスで読めるように登録しておきます。カーネルは、GPU の上で多数のスレッドが並列に実行する関数です。カーネルの各スレッドが行の中身を 16 バイトずつ PCIe を通して読み出し、GPU のメモリに書きます。CPU のコアは行を集めません。

下の段の**方法 B** では、CPU のコアが表から行を集めて 1 か所に並べます。PCIe を通るのは、それを GPU に送る 1 回のコピーだけです。そのかわり、CPU は読む行の番号を先に知っている必要があります。入力の文章をまとめて処理する段階を prefill、1 トークンずつ生成する段階を decode と呼びます。prefill では、CPU も入力のトークンを持っているので、番号を自分で計算できます。decode では、次のトークンを決めるのは GPU です。そのため、GPU で計算した行の番号を、いったん CPU に戻してから集めます。

入力の中のトークン 1 個分の場所を、位置と呼びます。どちらの方法でも、1 つの位置で読むのは 16 行です。この記事のモデルの表では、1 行が 64 個の float32 で、256 バイトです。

## 測り方

使ったのは、AWS の EC2 で借りられる仮想マシンの g7.2xlarge です。GPU は RTX PRO 4500 Blackwell Server Edition です。GPU のメモリは 32 GiB で、PCIe Gen 5 の 16 レーンでつながります。CPU は Xeon 6975P-C の 8 vCPU で、CPU 側のメモリは 32 GiB です。表の大きさは MiB と GiB で、速さは 10 進の GB/s で書きます。CPU 側のメモリから GPU へ 256 MiB を 1 回で連続コピーすると 56.5 GB/s で、この記事ではこれを、このマシンの PCIe で送れる速さの目安として使います。

方法 A では、GPU の各スレッドが行を 16 バイトずつ読むカーネルを CUDA で書きました。方法 B では、CPU の 8 個のスレッドが PyTorch の index_select で行を集めて固定したメモリに並べ、1 回のコピーで GPU に送ります。固定したメモリは、OS が場所を動かさないようにしたメモリです。

まず、2 つの方法が正しい行を読めていることを確かめました。使ったのは前の記事で学習したモデルの 1 つ（seed 1337）の表で、1,049,422 行、約 256 MiB です。どちらの方法でも、読んだ行の値と、モデルの出力のロジットは、GPU のメモリに置いた表から読んだ場合とビット単位で一致しました。ロジットは、確率に直す前の出力の値です。読む行を 1 つずらすと一致しなくなることも確かめています。

速さは、乱数で埋めた 256 MiB から 16 GiB の表で測りました。読む行は、呼び出しのたびに表全体から乱数で選び直します。Engram の行の番号も、ハッシュで表全体に散らばります。論文の 2.5 節によると、実際の文章ではよく出る並びに読み出しが偏りますが、偏りが速さをどう変えるかは、この記事では測っていません。

:::details 測り方の細かい条件
- 1 回の呼び出しの前後で GPU の処理が終わるのを待ち、その間の時間を測りました。20 回の中央値で、その前の 3 回は数えていません
- 方法 B の時間には、CPU が行を集める時間と、GPU へのコピーが終わるまでの時間を含みます。行の番号は CPU が先に持っている場合で測り、GPU から番号を戻す時間は含みません
- 表の大きさを変える測定では、方法 A の表を cudaHostAlloc で確保しました。cudaHostAlloc は、固定したメモリを確保する CUDA の関数です
- GPU のメモリに置いた表は、同じ 16,384 位置分の読み出しで、16 GiB でも 303 GB/s でした
:::

## 分かったこと: 行が広い範囲に散らばると、GPU が直接読む方法は遅くなる

![横は CPU 側のメモリに置いた表の大きさで 256 MiB から 16 GiB、縦は 16,384 位置分の 64 MiB を一度に読む速さ。方法 A は丸と実線で、256 MiB と 512 MiB で 50.7 と 50.8 GB/s、1 GiB で 25.9、2 GiB で 18.3、16 GiB で 10.0 GB/s。方法 B は四角と破線で、24.0 から 20.7 GB/s へゆるやかに下がる。1 GiB と 2 GiB の間で方法 B が上になる。点線は連続コピーの 56.5 GB/s](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/5637c881fd2d11/zenn/articles/5637c881fd2d11/host-bandwidth.png)

図は、16,384 位置分の 262,144 行、64 MiB を一度に読む速さです。読む行は表全体から選ぶので、表の大きさが、そのまま行が散らばる範囲になります。方法 A は、表が 256 MiB と 512 MiB のときは 50.7 GB/s と 50.8 GB/s で、連続コピーの 56.5 GB/s の約 9 割でした。1 GiB では 25.9 GB/s、16 GiB では 10.0 GB/s まで落ちます。方法 B は、256 MiB の表での 24.0 GB/s から、16 GiB の表での 20.7 GB/s へ、約 14% 下がっただけでした。表が 1 GiB と 2 GiB の間で、方法 B のほうが速くなります。

一度に読む量を 4 分の 1 の 4,096 位置分に減らすと、方法 B のほうが速かった 4 GiB 以上の表では、方法 A との差が縮まります。これは 512 トークンの入力 8 本を prefill する量にあたります。16 GiB の表で、方法 A は 1,191 µs で 14.1 GB/s、方法 B は 1,030 µs で 16.3 GB/s でした。

読む行がもっと少ないと、方法 A のほうが速くなります。16 位置分は、16 本の入力を 1 トークンずつ decode するときに 1 回で読む量にあたります。16 位置分の 256 行を 16 GiB の表から読むと、方法 A は 19.2 µs、方法 B は CPU が番号を先に持っている場合でも 36.6 µs かかりました。256 MiB から 16 GiB のどの表でも、方法 A は 15.9〜19.2 µs、方法 B は 30.7〜37.0 µs でした。GPU のメモリに置いた表から同じ 16 位置分を読んでも、どの表でも 12.4〜13.9 µs、16 GiB の表では 13.4 µs かかります。読む量が 64 KiB と小さいので、時間の大半を占めるのは PCIe で運ぶ時間ではなく、呼び出し 1 回ごとにかかる固定の時間だと筆者は考えています。番号を GPU から CPU に戻すと、方法 B にはさらに約 10.5 µs が加わります。この値は、モデルの表から 16 位置分を読んだときの、番号を戻す場合の 38.3 µs と、戻さない場合の 27.8 µs の差です。

### 遅くなるのは、行が散らばる範囲が広いとき

![8 GiB の表で、方法 A が 262,144 行を読む速さ。横は行と行の間隔と、行が散らばる範囲。間隔 256 B から 2 KiB、範囲 64 MiB から 512 MiB までは 50.4 から 50.5 GB/s で、間隔 4 KiB、範囲 1 GiB で 25.9、8 KiB で 18.5、16 KiB、範囲 4 GiB で 15.3 GB/s](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/5637c881fd2d11/zenn/articles/5637c881fd2d11/host-span.png)

方法 A が遅くなる理由を調べるため、8 GiB の表の中で、読む行の数を 262,144 行に固定し、行と行の間隔を 256 バイトから 16 KiB まで変えました。この測定の表は、mmap で確保して cudaHostRegister で登録したものです。読むバイト数はどれも 64 MiB で、行が散らばる範囲が 64 MiB から 4 GiB まで広がります。

間隔が 2 KiB までは、範囲は 512 MiB 以下で、速さは 50.4〜50.5 GB/s のままでした。間隔が 4 KiB になると範囲は 1 GiB で、速さは 25.9 GB/s に落ちました。間隔が 16 KiB では範囲は 4 GiB で、15.3 GB/s でした。

ページは、OS がメモリを管理する単位で、ここでは 4 KiB です。間隔が 4 KiB 以上のとき、行はすべて別々のページに入るので、読むページの数は 262,144 個で同じです。それでも速さは 25.9、18.5、15.3 GB/s と違うので、ページの数では説明できません。行を乱数で選んだ前の図でも、1 GiB、2 GiB、4 GiB の表で 25.9、18.3、15.3 GB/s でした。行の並べ方が違っても範囲が同じなら速さがほぼそろうので、行の数が同じなら、速さは行が散らばる範囲とともに変わると言えます。ただし範囲だけで決まるわけではなく、同じ 16 GiB の表でも、一度に読むのが 65,536 行なら 14.1 GB/s、262,144 行なら 10.0 GB/s でした。また、どの間隔でも読むのは同じ 262,144 行、64 MiB なので、CPU のキャッシュにあふれたかどうかでも、間隔による違いは説明できません。

原因の候補として、ページの大きさ、メモリの確保の仕方、IOMMU の設定の 3 つを変えて測りました。transparent huge page と hugetlbfs は、どちらも Linux で 2 MiB のページを使う仕組みです。mmap は OS からメモリを確保する関数で、cudaHostRegister は確保済みのメモリを固定して GPU から読めるように登録する CUDA の関数です。DeepEP は、DeepSeek が公開している通信ライブラリです。IOMMU は、GPU のような装置が使うアドレスを実際のメモリの場所に変換するハードウェアの仕組みで、変換の表は OS が設定します。この比較は、同じ行を毎回読む測り方で行いました。8 GiB の表での方法 A の速さは、どれを変えても 12.3〜12.4 GB/s で、1 GiB の表でも 25.6〜26.2 GB/s に収まりました。

| 変えたもの | 試したもの |
|---|---|
| CPU 側のメモリのページの大きさ | 4 KiB、2 MiB（transparent huge page と、8 GiB までの hugetlbfs） |
| メモリの確保の仕方 | cudaHostAlloc、mmap と cudaHostRegister、cuMemCreate で CPU 側に 2 MiB 単位で確保（[DeepEP が Engram の表を CPU 側に置くときの形](https://github.com/deepseek-ai/DeepEP/blob/a56d6156febcd9976e55adc85b5155bfac9f28f8/csrc/kernels/backend/symmetric.hpp#L33-L34)） |
| 仮想マシンの中の OS の IOMMU の設定 | アドレスを変換する既定の設定と、変換しない iommu=pt。起動時のログで、既定の種類が Translated から Passthrough に変わることを確かめた。256 MiB、1 GiB、8 GiB の表で比べた |

ここからは筆者の解釈です。GPU が CPU 側のメモリを読むときには、どこかでアドレスが変換されていて、変換の結果を覚えておける量に限りがあると考えています。行が散らばる範囲が 512 MiB までは覚えた結果を使い回せ、1 GiB 以上では変換のやり直しが増える、と考えると、512 MiB と 1 GiB の間で速さが変わることを説明できます。この考えを確かめる測定はしていません。g7.2xlarge は仮想マシンなので、変換しているのが GPU の側か、仮想マシンを動かしている外側の層かは、この 1 台の測定では分かりませんでした。

## まとめ

GPU が CPU 側のメモリを直接読む方法と、CPU が集めて送る方法を、1 台の g7.2xlarge で比べました。測ったのは 16 GiB までの表で、読む行を表全体から一様な乱数で選んだ場合の、行を取り寄せる時間です。一度に 16,384 位置分を読むと、表が 256 MiB と 512 MiB のときは、GPU が直接読む方法が 50.7〜50.8 GB/s で、CPU が集める方法の 23.2〜24.0 GB/s の約 2 倍でした。16 GiB の表では、GPU が直接読む方法は 10.0 GB/s に落ち、20.7 GB/s の CPU が集める方法が約 2 倍速くなりました。GPU が直接読む方法は、行が散らばる範囲が 512 MiB までは遅くならず、1 GiB 以上で遅くなりました。その間は測っていません。一度に 16 位置分を読む場合は、16 GiB の表でも、GPU が直接読む方法が 19.2 µs で、CPU が集める方法の 36.6 µs のほぼ半分の時間で済みました。約 196 GB の表や、推論全体のスループットでどうなるかは測っていません。

今後は、ほかのマシンのメモリにある表を、GPU からネットワーク越しに読む形も試したいと考えています。[DeepEP](https://github.com/deepseek-ai/DeepEP) は、Engram の表をこの形で引きます。[実験のコードと結果](https://github.com/littlemex/zenmai-lab/tree/ac61d16/experiments/2026-11-19-engram-host-table)は公開しています。
