## はじめに

Engram は、直前の数トークンの並びから表の行を決めて読み、読んだ値を隠れ状態に足す部品です。仕組みは「[小さな GPT で Engram を試す](https://zenn.dev/tosshi/articles/35ef2467d84b63)」で、実際の値を使って追いました。この表は大きくなります。DeepSeek-V4.1-Flash の[公式の推論コードの設定](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash/blob/2cba9e42aa026125f3ed06c6d98c1db82f7ca027/inference/config.json)では、表は 2 か所にあり、行は合わせて約 7.68 億、1 行は 256 個の値です。8 ビットの浮動小数点数である FP8 で数えると $7.68 \times 10^8 \times 256\ \mathrm{B} \approx 196\ \mathrm{GB}$ で、この記事で使う 32 GiB の GPU のメモリには載りません。

読む行はトークンの番号だけで決まるので、表を CPU 側のメモリに置き、必要な行だけを計算の前に運ぶことができます。[論文](https://arxiv.org/abs/2601.07372)の 6.4 節は、1,000 億個のパラメータの表をすべて CPU 側のメモリに置き、最初のブロックの計算と重ねて PCIe で運ぶ実験を報告しています。PCIe は、CPU 側と GPU をつなぐ接続の規格です。ブロックは、モデルの中で同じ形の計算をくり返す 1 段分です。表を足さないモデルと比べたスループットの低下は、NVIDIA の H800 で最大 2.8% でした。

![左に CPU 側のメモリの Engram の表と、32 GiB の GPU のメモリ。右に V4.1-Flash の計算の順で、埋め込み、ブロック 0、Engram の層 1、ブロック 1 から 13、Engram の層 14。トークンの番号から行の番号がブロックの計算の前に決まり、行は PCIe を通って 2 つの Engram の層に届く。層 1 の猶予は埋め込みとブロック 0、層 14 の猶予は埋め込みとブロック 0 から 13 の計算の時間。](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/5637c881fd2d11/zenn/articles/5637c881fd2d11/engram-slack.png)

表引きそのものは行を運ぶだけで、計算をほとんどしません。そのため表を CPU 側に置くと、表引きの時間は行を運ぶ時間でほぼ決まります。この記事では、行の番号が決まってから、その行を使う Engram の層に着くまでの計算の時間を**猶予**と呼びます。V4.1-Flash の 1 か所目の Engram の層の猶予は、埋め込みとブロック 0 の計算だけです。行を運ぶ時間が猶予に収まり、しかもブロックの計算が使う GPU の資源を奪わなければ、入力から出力までの計算の時間は、表を GPU のメモリに置いた場合から延びません。これを、表引きが**隠れる**と呼びます。

表が大きくなったとき、行を運ぶスループットがどう落ちるか、そして猶予に隠れるかを、この記事では考えます。そのためにまず、表の行を運ぶ既存の実装である DeepEP の状況を整理します。DeepEP はこの記事のマシンでは使えないので、筆者が 2 つの読み方を書き、GPU 1 台で測りました。GPU が CPU 側のメモリを直接読むと、16 GiB までの表で、行が散らばる範囲が 1 GiB 以上でスループットが落ちました。猶予に収まる量でも、直接読むと計算の時間が 1.5〜2.9% 延び、隠れませんでした。

:::message alert
**この記事の数は、特に断らない限り、筆者が AWS の仮想マシン 1 台で測った値です。**
:::

## 表の行を運ぶ既存の実装

Engram の表の行を GPU の外から運ぶ実装は、DeepSeek が公開している通信ライブラリの [DeepEP](https://github.com/deepseek-ai/DeepEP) にすでにあります。この節では、DeepEP の表引きがこの記事のマシンで使えるかを整理します。DeepEP は [NCCL](https://github.com/NVIDIA/nccl) の [GIN](https://github.com/NVIDIA/nccl/blob/ad2d192c1f/docs/userguide/source/api/device_gin.rst) で行を読みます。NCCL は複数の GPU の間の通信を受け持つ NVIDIA のライブラリで、GIN は GPU のカーネルから直接ネットワークの通信を出す仕組みです。カーネルは、GPU の上で多数のスレッドが並列に実行する関数です。GIN の get は、相手が登録したメモリから、読み手の側だけの操作でデータを読み出します。

![左が読み手の GPU、右が行の持ち主で、読み手自身も持ち主になる。読み手の engram_fetch カーネルが、行の番号から行ごとに get を出す。get は GDAKI なら GPU が NIC に、Proxy なら CPU のスレッドが依頼し、持ち主の CPU 側のメモリにある表の行を NIC が読むか CPU が送って、読み手の GPU のメモリに置く。持ち主の GPU は何もしない。完了は相手ごとの flush_async と、別のカーネルの wait で確かめる。本文の FlushAsync と Wait にあたる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/5637c881fd2d11/zenn/articles/5637c881fd2d11/deepep-get.png)

DeepEP は、この表引きを[「0 SM Engram (with RDMA)」という実験的な機能](https://github.com/deepseek-ai/DeepEP/blob/a56d6156febcd9976e55adc85b5155bfac9f28f8/README.md#L23-L31)として挙げています。NIC は、マシンをネットワークにつなぐ装置です。RDMA は、相手の CPU を介さずに相手のメモリを直接読み書きする通信の方式です。SM は Streaming Multiprocessor の略で、GPU の中でカーネルのスレッドを実行する装置です。筆者は 0 SM を、get を出し終えてから行が届くまでの間は SM を使わないという意味だと読んでいます。get を出すカーネルと、完了を待つカーネルは SM の上で動きます。

読み手のカーネルは、行の番号から、持ち主と、持ち主の表の中での場所を計算し、[行ごとに get を出します](https://github.com/deepseek-ai/DeepEP/blob/93eb6eb238127e96c6d7a4a625a6dad158348509/deep_ep/include/deep_ep/impls/engram/engram_fetch.cuh#L114-L129)。自分が持つ行も同じように get で読み、同じマシンのメモリを直接読む分岐はありません。get を運ぶのは GIN のバックエンドで、GDAKI では GPU が NIC に直接依頼を出し、Proxy では CPU のスレッドが代わりに依頼を出します。読み終わりは、相手ごとに完了を予約する FlushAsync と、別のカーネルで完了を待つ Wait で確かめます。

バックエンドごとに、DeepEP の Engram に要る機能がそろっているかを、動かさずにソースだけで確かめました。GDAKI が使えるのは NVIDIA の ConnectX の NIC で、EFA GDA は AWS の [EFA](https://aws.amazon.com/hpc/efa/) という NIC の経路です。DMA-BUF は、装置の間でメモリを共有するための Linux の仕組みです。

| GIN のバックエンド | get | 相手ごとの完了待ち | DeepEP の Engram で使えるか |
|---|---|---|---|
| GDAKI | あります | [FlushAsync と Wait の実装があります](https://github.com/NVIDIA/nccl/blob/ad2d192c1f/src/include/nccl_device/gin/gdaki/gin_gdaki.h#L495-L530) | 機能はそろっています。93eb6eb2 の DeepEP の EngramBuffer は、[このバックエンドだけを登録します](https://github.com/deepseek-ai/DeepEP/blob/93eb6eb238127e96c6d7a4a625a6dad158348509/deep_ep/buffers/engram.py#L80-L82) |
| EFA GDA | あります | [FlushAsync と Wait が何もせずに戻ります](https://github.com/NVIDIA/nccl/blob/ad2d192c1f/src/include/nccl_device/gin/efa_gda/gin_efa_gda.h#L1011-L1045) | DeepEP の待ち方のままでは、行が届く前に読むおそれがあると筆者は考えています。93eb6eb2 の DeepEP はこのバックエンドを登録しません |
| Proxy の TCP | あります | [FlushAsync と Wait の実装があります](https://github.com/NVIDIA/nccl/blob/ad2d192c1f/src/include/nccl_device/gin/proxy/gin_proxy.h#L375-L404) | 93eb6eb2 の DeepEP はこのバックエンドを登録しません。登録しても、CPU 側と GPU のメモリにまたがる範囲の登録は、[DMA-BUF を求める検査](https://github.com/NVIDIA/nccl/blob/ad2d192c1f/src/gin/gin_host.cc#L611-L621)で断られます |

この記事で使う [g7.2xlarge](https://aws.amazon.com/ec2/instance-types/g7/) には、ConnectX の NIC も EFA もありません。残る TCP の経路も、DeepEP がこのバックエンドを登録しないことと、DMA-BUF を求める検査で断られることの 2 つの理由で使えないので、このマシンでは DeepEP の Engram の表引きを動かせません。動いたとしても、自分の持つ行も get で読むので、1 台の中で CPU 側のメモリを読むスループットそのものは測れません。そこで、1 台の中で CPU 側のメモリから行を読む方法を自分で書きました。

:::details 確かめたバージョン
2026 年 11 月 19 日に、NCCL の [v2.32.6-1](https://github.com/NVIDIA/nccl/releases/tag/v2.32.6-1)（ad2d192c1f）と、同じ日に見た staging と dev のブランチ、DeepEP の 93eb6eb2 を読みました。EFA GDA の FlushAsync と Wait は、staging と dev でも何もせずに戻ります。経緯は「[NCCL 2.32.3 でロードマップはどう実装されたか](https://zenn.dev/tosshi/articles/9ab10d37f33ced)」に書きました。
:::

## 自作した 2 つの読み方

方法 A は CPU のコアを使わない代わりに SM を使い、方法 B は SM で行を集めない代わりに CPU のコアを使います。

![左が CPU 側、中央が PCIe、右が GPU。上の段が方法 A で、SM の上で動く GPU のカーネルが CPU 側のメモリの表から行を読み、GPU のメモリに置く。下の段が方法 B で、CPU のコアが表から行を集め、固定したメモリに並べてから、1 回のコピーで GPU に送る。decode では行の番号が GPU の側にあるので、方法 B では番号を CPU に戻す。方法 B のコピーは一般にコピーエンジンが運ぶ。方法 A は実線、方法 B は破線の矢印](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/5637c881fd2d11/zenn/articles/5637c881fd2d11/host-two-ways.png)

**方法 A** では、GPU が CPU 側のメモリを直接読みます。固定したメモリは、OS が場所を動かさないようにしたメモリです。表を置く CPU 側のメモリを [cudaHostAlloc](https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__MEMORY.html) で、GPU からも読めるように対応付けた固定したメモリとして確保し、GPU から見たアドレスを cudaHostGetDevicePointer で取ります。そのアドレスを、[行を集めるカーネル](https://github.com/littlemex/zenmai-lab/blob/d5d3f3c/experiments/2026-11-19-engram-host-table/engram_host_table.py#L33-L41)に渡します。カーネルの各スレッドは行の中身を 16 バイトずつ読み、読み出しは PCIe を通ります。

```cpp
__global__ void gather_rows(const float4* table, const int64_t* rows, float4* out, int64_t n, int vec_per_row) {
  for (int64_t i = blockIdx.x * (int64_t)blockDim.x + threadIdx.x; i < n * vec_per_row; i += (int64_t)gridDim.x * blockDim.x)
    out[i] = table[rows[i / vec_per_row] * vec_per_row + i % vec_per_row];
}
```

**方法 B** では、CPU の 8 個のスレッドが PyTorch の [index_select](https://docs.pytorch.org/docs/stable/generated/torch.index_select.html) で表から行を集めて固定したメモリに並べ、1 回のコピーで GPU に送ります。このコピーでは、方法 A と違い、行を集めるカーネルを SM の上で動かしません。そのかわり、読む行の番号を CPU が先に知っている必要があります。入力の文章をまとめて処理する prefill では、CPU も入力のトークンを持っているので、番号を自分で計算できます。1 トークンずつ生成する decode では、次のトークンを決めるのは GPU なので、GPU で計算した行の番号をいったん CPU に戻してから集めます。

前の記事で学習した小さな GPT を、この記事のモデルと呼びます。入力の中のトークン 1 個分の場所を、位置と呼びます。この記事のモデルの表では 1 つの位置で 16 行を読み、1 行は 64 個の float32 で 256 バイトです。確認には、この記事のモデルの表を 1 つ使いました。1,049,422 行で、約 256 MiB です。どちらの方法でも、読んだ行の値と出力のロジットは、GPU のメモリに置いた表から読んだ場合とビット単位で一致しました。ロジットは、確率に直す前の出力の値です。読む行を 1 つずらすと一致しなくなることも確かめました。

## 測った結果

:::details 測った環境と条件
- AWS の g7.2xlarge 1 台です。GPU は RTX PRO 4500 Blackwell Server Edition で、メモリは 32 GiB、PCIe Gen 5 の 16 レーンでつながります。CPU は Xeon 6975P-C の 8 vCPU で、CPU 側のメモリは 32 GiB です
- PyTorch 2.14.1+cu130、カーネルのコンパイルに使った nvcc 13.2、ドライバ 595.91.07、Linux 7.0.0-1014-aws です
- 1 回の呼び出しの前後で GPU の処理が終わるのを待ち、その間の時間を測りました。読み出しは 20 回、この記事のモデルの prefill は 50 回の中央値です
- 表の大きさを変える測定での方法 B の時間は、CPU が行を集める時間と、GPU へのコピーが終わるまでの時間を含みます。番号は CPU が先に持っている場合で測りました
- 表の大きさを変える測定では、方法 A の表を cudaHostAlloc で確保しました
- 表の大きさは MiB と GiB、スループットは 10 進の GB/s で書きます
- 比べる目安は、CPU 側のメモリから GPU へ 256 MiB を 1 回で連続コピーしたときの 56.5 GB/s です。GPU のメモリに置いた表は、16 GiB でも 303 GB/s でした
- 16 位置分を読む時間は、256 MiB から 16 GiB のどの表でも、方法 A が 15.9〜19.2 µs、方法 B が 30.7〜37.0 µs で、GPU のメモリに置いた表でも 12.4〜13.9 µs でした
:::

### 行が広い範囲に散らばると、方法 A のスループットは落ちる

![横は CPU 側のメモリに置いた表の大きさで 256 MiB から 16 GiB、縦は 16,384 位置分の 64 MiB を一度に読むスループット。方法 A は丸と実線で、256 MiB と 512 MiB で 50.7 と 50.8 GB/s、1 GiB で 25.9、2 GiB で 18.3、16 GiB で 10.0 GB/s。方法 B は四角と破線で、24.0 から 20.7 GB/s へゆるやかに下がる。1 GiB と 2 GiB の間で方法 B が上になる。点線は連続コピーの 56.5 GB/s](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/5637c881fd2d11/zenn/articles/5637c881fd2d11/host-bandwidth.png)

乱数で埋めた 256 MiB から 16 GiB の表で、呼び出しのたびに表全体から乱数で選んだ 16,384 位置分の行を読みました。読む量は 64 MiB です。Engram の行の番号もハッシュで表全体に散らばるので、表の大きさがそのまま行が散らばる範囲になります。方法 A は、表が 512 MiB までは 50.7〜50.8 GB/s でしたが、1 GiB で 25.9 GB/s、16 GiB で 10.0 GB/s に落ちました。方法 B は 24.0 GB/s から 20.7 GB/s へ下がっただけで、表が 2 GiB 以上では方法 A を上回りました。

![8 GiB の表で、方法 A が 262,144 行を読むスループット。横は行と行の間隔と、行が散らばる範囲。間隔 256 B から 2 KiB、範囲 64 MiB から 512 MiB までは 50.4 から 50.5 GB/s で、間隔 4 KiB、範囲 1 GiB で 25.9、8 KiB で 18.5、16 KiB、範囲 4 GiB で 15.3 GB/s](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/5637c881fd2d11/zenn/articles/5637c881fd2d11/host-span.png)

8 GiB の表で、読む行の数を 262,144 行に固定し、行と行の間隔だけを 256 バイトから 16 KiB まで変えました。この表は mmap で確保し、cudaHostRegister で固定して GPU から読めるようにしたものです。行が散らばる範囲が 512 MiB までは 50.4〜50.5 GB/s のままで、1 GiB で 25.9 GB/s、4 GiB で 15.3 GB/s でした。ページは、OS がメモリを管理する単位です。間隔が 4 KiB 以上では、行はすべて別々の 4 KiB のページに入り、ページの数は同じなのにスループットは落ち続けます。GPU が CPU 側のメモリを読むときのアドレスの変換に、結果を覚えておける量の限りがあると考えると説明できます。これは筆者の推測で、変換が GPU の側か仮想マシンの外側かは、この 1 台では区別できません。

:::details 変えてもスループットが変わらなかったもの
同じ行を毎回読む測り方で、8 GiB の表での方法 A は、どれを変えても 12.3〜12.4 GB/s でした。transparent huge page と hugetlbfs は、どちらも Linux で 2 MiB のページを使う仕組みです。NUMA ノードは、CPU とそれに近いメモリのまとまりです。IOMMU は、装置が使うアドレスを実際のメモリの場所に変換するハードウェアです。

| 変えたもの | 試したもの |
|---|---|
| CPU 側のページの大きさ | 4 KiB と、2 MiB（transparent huge page と、8 GiB までの hugetlbfs） |
| メモリの確保の仕方 | cudaHostAlloc、mmap と cudaHostRegister、DeepEP が Engram の表を CPU 側に置くときと[同じ API](https://github.com/deepseek-ai/DeepEP/blob/a56d6156febcd9976e55adc85b5155bfac9f28f8/csrc/kernels/backend/symmetric.hpp#L33-L34) の [cuMemCreate](https://docs.nvidia.com/cuda/cuda-driver-api/group__CUDA__VA.html) で、CPU 側の NUMA ノードに 2 MiB 単位で確保 |
| OS の IOMMU の設定 | 既定の Translated と iommu=pt。256 MiB、1 GiB、8 GiB の表で、方法 A は 50.7〜50.8、25.6〜26.2、12.3〜12.4 GB/s で、変える前とほぼ同じでした |

変えたのは CPU 側の OS のページです。2 MiB のような大きい単位で数えると、行が触れる単位の数は散らばる範囲に比例するので、大きい単位の変換の数で決まる可能性は、この測定では除けません。この仮想マシンの中には IOMMU の装置が見えないので、OS の IOMMU の設定は GPU の読み出しの経路に効いていないと筆者は見ています。方法 A では CPU のコアがデータを読まないので、CPU のキャッシュの大きさで決まるとも考えにくいと見ています。
:::

### 猶予に収まっても、方法 A では隠れなかった

![この記事のモデルで 8 本 × 512 トークンの prefill を bfloat16 で流したときの時間。埋め込みとブロック 0 が 481 µs、方法 A で行を読むだけなら 342 µs。表を GPU のメモリに置いた場合と比べた forward の増え方は、必要になってから読むと 272 µs で 2.5%、別の stream で先に読むと 315 µs で 2.9%、読み出しのカーネルを 16 個のスレッドブロックに絞った別の回の測定で、先に読むと 167 µs で 1.5%、その回の基準は別](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/5637c881fd2d11/zenn/articles/5637c881fd2d11/host-overlap.png)

512 トークンの入力 8 本、$8 \times 512 = 4096$ 位置を、この記事のモデルで prefill しました。計算の形式は、16 ビットの浮動小数点数の bfloat16 です。表は約 256 MiB で、方法 A のスループットが落ちない大きさです。Engram の層はブロック 1 の手前にあるので、猶予は埋め込みとブロック 0 の 481 µs です。方法 A で行を読むだけなら 342 µs で、猶予に収まります。forward は、入力から出力までを 1 回計算することです。stream は GPU に順番に仕事を流す列で、列が違う仕事は GPU に空きがあれば並んで動きます。カーネルは、スレッドをスレッドブロックというまとまりに分けて実行します。

それでも forward は、表を GPU のメモリに置いた場合より長くなりました。行を必要になってから読むと 272 µs、2.5%、別の stream で先に読み始めても 315 µs、2.9% の増加です。forward が長くなったのは、読み出しを待つスレッドブロックが SM に残り、SM が同時に実行できるスレッドブロックの数を使うので、ブロック 0 のカーネルが入る余地が減ったためだと筆者は推測しています。読み出しのカーネルを 16 個のスレッドブロックに絞った別の回の測定では、先に読み始めた場合の増加は 167 µs、1.5% で、同じ回に必要になってから読んだ場合の 297 µs、2.7% より約 130 µs 短くなりました。絞っても、読むだけの時間は 342 µs から 359 µs に延びただけです。2 回の測定の間で基準の forward は約 36 µs ずれたので、これより小さい差は区別できません。

方法 B は、番号を GPU から戻して集め、送り終えるまでが単独で 943 µs で、猶予に収まりません。CPU が自分で番号を計算した場合、forward は表を GPU のメモリに置いた場合より 665 µs、6.1% 長くなりました。CPU のスレッドで先に読み始めると、829 µs、7.6% とさらに長くなりました。行を集める処理が 8 vCPU をすべて使うので、GPU に仕事を出すスレッドと CPU を取り合った可能性があります。方法 B の時間は CPU が行を集める時間を含むので、この結果からコピーで運ぶ時間だけを取り出すことはできません。

## V4.1-Flash の大きさの表をどう扱うか

ここからは、測定をもとにした筆者の考察です。GPU 1 台で測った範囲では、運ぶ量の合計は問題になりません。問題になるのは、1 ステップで運ぶ時間を、SM や CPU のコアを奪わずに猶予に重ねられるかです。ここでは、1 回の forward を 1 ステップと呼びます。

### 運ぶ量の合計

V4.1-Flash は 1 つの位置で、2 か所の Engram の層それぞれで 24 行を読みます。2-gram から 4-gram の 3 種類の並びを、それぞれ 8 個のヘッドに分けて引くためで、ヘッドごとに 1 行を読みます。1 行は FP8 の値 256 バイトなので、1 トークンあたり、値だけで $2 \times 24 \times 256\ \mathrm{B} = 12\ \mathrm{KiB}$ です。仮に 1 台の GPU が 1 秒に 1 万トークンを処理すると、運ぶ量は $12\ \mathrm{KiB} \times 10^4 \approx 123\ \mathrm{MB/s}$ で、16 GiB の表での方法 A の 10.0 GB/s でも、1 秒のうち約 1.2% の時間で運べます。1 万トークンという仮定は、論文の表 4 が H800 で報告する、4B と 8B のモデルの 1 秒あたり約 6,100〜9,000 トークンを目安に置いた値で、V4.1-Flash の実測ではありません。

### 1 ステップで運ぶ時間と猶予

512 トークンの入力 8 本の prefill で、V4.1-Flash の 1 か所の Engram の層が読むのは $4096 \times 24 \times 256\ \mathrm{B} = 24\ \mathrm{MiB}$ です。この記事で測ったスループットを当てはめると、次のようになります。16 GiB の表のスループットの幅は、4,096 位置分と 16,384 位置分を読んだときの値です。

| 読み方と条件 | スループット | 24 MiB を運ぶ時間 |
|---|---|---|
| 方法 A、行が 512 MiB 以内に収まる | 50.7 GB/s | 約 0.5 ms |
| 方法 A、16 GiB の表全体に散らばる | 10.0〜14.1 GB/s | 約 1.8〜2.5 ms |
| 方法 B、16 GiB の表 | 16.3〜20.7 GB/s | 約 1.2〜1.5 ms |

方法 A のスループットは 16 GiB でもまだ落ちているので、約 98 GB の層の表ではもっと長くなるかもしれません。これが猶予に収まるかは、V4.1-Flash のブロック 1 個の計算時間で決まります。

prefill では、行の番号は入力が届いた時点で 2 か所とも決まるので、前のバッチの計算の間に読み始めれば、猶予を 1 回の forward より長く取れます。decode では、行の番号は直前のトークンが決まるまで分からず、1 か所目の層の猶予は埋め込みとブロック 0 だけです。同時に decode する入力が増えると差も開き、256 位置分では、256 MiB から 16 GiB の表で、方法 A が 34.7〜87.6 µs、GPU のメモリに置いた表が 13.9〜18.4 µs でした。V4.1-Flash は 1 位置で 24 行を 2 か所で読むので、表引きの呼び出しは 1 ステップに 2 回になります。

### まだ試していない扱い方の案

| 条件 | この記事で測ったこと | 扱い方の案 |
|---|---|---|
| 運ぶスループットを落とさない | 方法 A は、行が散らばる範囲が 1 GiB 以上で落ち、16 GiB で 10.0 GB/s でした | よく読む行を狭い範囲にまとめます。行の番号はハッシュで決まるので、番号から置き場所への対応表が要ります。論文の 2.5 節は、よく出る埋め込みを GPU のメモリか CPU 側のメモリに、残りを SSD に置く階層を挙げています |
| 計算の資源を奪わない | 方法 A は、先に読んだ場合の増加が 315 µs で、16 個のスレッドブロックに絞った別の回では 167 µs でした。2 つの回の基準は約 36 µs ずれています | 方法 A のカーネルのスレッドブロックを減らします。DeepEP のように NIC に運ばせる get を使います。方法 B は、集める CPU のコアを増やします |
| 猶予の短い場所を避ける | 1 か所目の層の猶予は、埋め込みとブロック 0 だけでした | GPU のメモリに置く行は、浅い層のよく読む行を優先します。V4.1-Flash の層 1 の表は丸ごとでは約 98 GB で、全部は置けません |

この仮想マシン 1 台では、8 GiB の表でも、読む行が 512 MiB 以内に収まれば、方法 A は 50.4〜50.5 GB/s のままでした。そのため筆者は、行の置き場所を、表の大きさだけでなく、1 ステップで読む行が実際に散らばる範囲と、その行の猶予の 2 つで決めるのがよいと考えています。

## まとめ

DeepEP の Engram は、GIN の get で行を読みます。2026 年 11 月 19 日の時点で、93eb6eb2 の DeepEP は GDAKI だけを登録し、NCCL の EFA の経路では相手ごとの完了待ちが何もせずに戻り、TCP の経路では CPU 側と GPU のメモリにまたがる範囲の登録が断られます。そこで、ConnectX の NIC も EFA も無い 1 台の g7.2xlarge で、GPU が CPU 側のメモリを直接読む方法 A と、CPU が集めて送る方法 B を自分で書いて比べました。

16,384 位置分を一度に読むと、方法 A は、行が散らばる範囲が 512 MiB までは 50.7〜50.8 GB/s で方法 B の約 2 倍でした。1 GiB 以上では落ち、16 GiB では 10.0 GB/s と方法 B の約半分でした。この記事のモデルの prefill では、方法 A の読み出しは猶予に収まっても、forward を表を GPU のメモリに置いた場合より 2.5〜2.9% 長くしました。読み出しのカーネルを 16 個のスレッドブロックに絞り、別の stream で先に読み始めた場合は 1.5% で、絞っても必要になってから読んだ場合は 2.7% でした。大きな表では、運ぶ量の合計より、1 ステップで運ぶ時間を計算の資源を奪わずに猶予に重ねられるかが効いてくる、というのが筆者の考えです。

今後は、表を何台かに分けて、公開されているバージョンの DeepEP の get で読み、そのスループットを測りたいと考えています。[実験のコードと結果](https://github.com/littlemex/zenmai-lab/tree/d5d3f3c/experiments/2026-11-19-engram-host-table)は公開しています。
