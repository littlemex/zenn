## はじめに

Engram は、直前の数トークンの並びから表の行を決めて読み、読んだ値を隠れ状態に足す部品です。仕組みは「[小さな GPT で Engram を試す](https://zenn.dev/tosshi/articles/35ef2467d84b63)」で、実際の値を使って追いました。この表は大きくなります。DeepSeek-V4.1-Flash の[公式の推論コードの設定](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash/blob/2cba9e42aa026125f3ed06c6d98c1db82f7ca027/inference/config.json)では、表は 2 か所にあり、行は合わせて約 7.68 億、1 行は 256 個の値です。8 ビットの浮動小数点数である FP8 で数えると約 196 GB になり、この記事で使う GPU のメモリの 32 GiB には、とても載りません。

読む行は入力のトークンだけで決まるので、表を CPU 側のメモリに置いておき、必要な行だけを計算の前に取り寄せることができます。[論文](https://arxiv.org/abs/2601.07372)の 6.4 節は、1,000 億個のパラメータの表をすべて CPU 側のメモリに置き、最初のブロックの計算と重ねて PCIe で取り寄せる実験を報告しています。PCIe は、CPU 側と GPU をつなぐ接続の規格です。ブロックは、モデルの中で同じ形の計算をくり返す 1 段分です。表を足さないモデルと比べたスループットの低下は、NVIDIA の H800 で最大 2.8% でした。8B のモデルで、1 秒あたり 6,315.52 トークンが 6,140.02 トークンになった値です。

表引きそのものは、行を運ぶだけで計算をほとんどしません。そのため表を CPU 側に置いたときの表引きの時間は、行を運ぶ時間でほぼ決まります。運ぶ時間は、運ぶバイト数をそのとき出る速さで割った時間と、呼び出し 1 回ごとにかかる固定の時間の和です。表が大きくなったときに問題になるのは、運ぶ速さがどう落ちるかと、運ぶ時間を前のブロックの計算に重ねて隠し切れるかの 2 つです。この記事では、まず表の行を運ぶ既存の実装の状況を整理します。次に、それを使わずに自作した 2 つの読み方とその測定を説明し、最後に、この 2 つの問いについて考えます。

:::message alert
**この記事の数は、特に断らない限り、筆者が AWS の仮想マシン 1 台で測った値です。**
:::

## 表の行を取り寄せる既存の実装

### NCCL の GIN と DeepEP の Engram

NCCL は、複数の GPU の間の通信を受け持つ NVIDIA のライブラリです。GIN は、GPU のカーネルから直接ネットワークの通信を出せる、NCCL の仕組みです。カーネルは、GPU の上で多数のスレッドが並列に実行する関数です。GIN の get は、相手が登録したメモリから、読み手の側だけの操作でデータを読み出す操作です。GIN の基本は「[MoE の all-to-all を支える層](https://zenn.dev/tosshi/articles/a0f5ff21eed405)」で説明しました。

![左が読み手の GPU、右が行の持ち主で、読み手自身も持ち主になる。読み手の engram_fetch カーネルが、行の番号から行ごとに get を出す。get は GDAKI なら GPU が NIC に、Proxy なら CPU のスレッドが依頼し、持ち主の CPU 側のメモリにある表の行を NIC が読むか CPU が送って、読み手の GPU のメモリに置く。持ち主の GPU は何もしない。完了は相手ごとの flush_async と、別のカーネルの wait で確かめる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/5637c881fd2d11/zenn/articles/5637c881fd2d11/deepep-get.png)

DeepSeek が公開している通信ライブラリの [DeepEP](https://github.com/deepseek-ai/DeepEP) は、この get で Engram の表を引きます。NIC は、マシンをネットワークにつなぐ装置です。RDMA は、相手の CPU を介さずに相手のメモリを直接読み書きする通信の方式です。SM は Streaming Multiprocessor の略で、GPU の中でカーネルのスレッドを実行する装置です。DeepEP の [README](https://github.com/deepseek-ai/DeepEP/blob/a56d6156febcd9976e55adc85b5155bfac9f28f8/README.md#L23-L31) では、Engram の表引きは「0 SM Engram (with RDMA)」という実験的な機能です。筆者は 0 SM を、行を運ぶ間に SM を使わないという意味だと読んでいます。表は各ランクが CPU 側のメモリに分けて持ちます。ランクは、分散して動かすプロセスに付けた番号です。読み手のカーネルは、[行の番号から持ち主と位置を計算し](https://github.com/deepseek-ai/DeepEP/blob/93eb6eb238127e96c6d7a4a625a6dad158348509/deep_ep/include/deep_ep/impls/engram/engram_fetch.cuh#L114-L129)、行ごとに get を出します。自分が持つ行も同じように get で読み、同じマシンのメモリを直接読む分岐はありません。get を実際に運ぶのは GIN のバックエンドです。GDAKI では GPU が NIC に直接依頼を出し、Proxy では CPU のスレッドが依頼を代わりに出します。get の間、持ち主の GPU は何もしません。読み終わりは、相手ごとに完了を予約する FlushAsync と、別のカーネルでその完了を待つ Wait で確かめます。

### 経路ごとの今の状況

GIN のバックエンドごとに、DeepEP の Engram の表引きに要る機能がそろっているかを、2026 年 11 月 19 日の時点で公開されている版のソースで確かめました。どれも筆者は動かしておらず、ソースを読んだ結果です。InfiniBand と RoCE は、RDMA に使うネットワークの規格です。EFA は Elastic Fabric Adapter の略で、AWS が仮想マシンに提供する高速な NIC です。window は、GIN で相手から読み書きできるように登録したメモリの範囲です。DMA-BUF は、装置の間でメモリを共有するための Linux の仕組みです。NCCL は 11 月 9 日の [v2.32.6-1](https://github.com/NVIDIA/nccl/releases/tag/v2.32.6-1) と、その後の staging と dev のブランチです。

| GIN のバックエンド | get | 相手ごとの完了待ち | DeepEP の Engram で使えるか |
|---|---|---|---|
| GDAKI（InfiniBand や RoCE の NIC） | ある | [ある](https://github.com/NVIDIA/nccl/blob/ad2d192c1f/src/include/nccl_device/gin/gdaki/gin_gdaki.h#L495-L530) | 機能はそろっている。最新の DeepEP の EngramBuffer は、[このバックエンドだけを登録する](https://github.com/deepseek-ai/DeepEP/blob/93eb6eb238127e96c6d7a4a625a6dad158348509/deep_ep/buffers/engram.py#L80-L82) |
| EFA GDA（AWS の EFA） | 2.32.3 から。aws-ofi-nccl は v1.22.0 から | [中身が空のまま](https://github.com/NVIDIA/nccl/blob/ad2d192c1f/src/include/nccl_device/gin/efa_gda/gin_efa_gda.h#L1011-L1045)。v2.32.6-1、staging、dev のどれでも同じ | 使えない。完了待ちが何もせずに戻るので、行が届く前に読んでしまうおそれがあると筆者は考えている。最新の DeepEP はこのバックエンドを登録しない |
| Proxy の TCP（RMA_SOCKET_PROXY） | 2.32.3 から | [ある](https://github.com/NVIDIA/nccl/blob/ad2d192c1f/src/include/nccl_device/gin/proxy/gin_proxy.h#L375-L404) | 複数の物理的な区画にまたがる window の登録が、[DMA-BUF を求める検査](https://github.com/NVIDIA/nccl/blob/ad2d192c1f/src/gin/gin_host.cc#L611-L621)で断られる。CPU 側と GPU のメモリを 1 つの window に並べる DeepEP の表はこの形になる。v2.32.6-1 でも同じ |

TCP の経路は、筆者が NCCL を 3 か所直すと、AWS のフォークの DeepEP で 2 台が動き、表を分けて引いた結果がビット単位で一致しました。ただしこの修正は公開していません。この記事で使う g7.2xlarge には、InfiniBand の NIC も EFA もありません。そのため GDAKI と EFA GDA は選べず、残る TCP の経路は、公開されている版では window の登録で断られます。したがって、公開されている版のままでは、このマシンで DeepEP の Engram の表引きを動かせません。また DeepEP は、自分の持つ行も GIN の get で読むので、動いたとしても、1 台の中で CPU 側のメモリを読む速さそのものは測れません。そこでこの記事では、1 台の中で CPU 側のメモリから行を読む方法を自分で書き、その速さを測りました。

## 自作した 2 つの読み方

![左が CPU 側、中央が PCIe、右が GPU。上の段が方法 A で、GPU のカーネルが CPU 側のメモリの表から行を 16 バイトずつ PCIe 越しに読み、GPU のメモリに置く。下の段が方法 B で、CPU のコアが表から行を集めて送る前に行を並べておくメモリに並べ、1 回のコピーで GPU に送る。decode では行の番号が GPU の側にあるので、方法 B では番号を CPU に戻す。方法 A のカーネルは SM の上で動き、方法 B のコピーはコピーエンジンが運ぶ。方法 A は実線、方法 B は破線の矢印](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/5637c881fd2d11/zenn/articles/5637c881fd2d11/host-two-ways.png)

図の上の段の**方法 A** では、GPU が CPU 側のメモリを直接読みます。表を置く CPU 側のメモリを `cudaHostAlloc` に `cudaHostAllocMapped` を付けて確保し、GPU からもアドレスで読めるようにします。`cudaHostGetDevicePointer` で GPU から見たアドレスを得て、そのアドレスを、行を集めるカーネルに渡します。カーネルの各スレッドは行の中身を 16 バイトずつ読むので、256 バイトの 1 行は 16 個のスレッドで読みます。読み出しは PCIe を通り、結果は GPU のメモリに書かれます。CPU のコアは行を集めませんが、カーネルは GPU の SM の上で動きます。

```cpp
__global__ void gather_rows(const float4* table, const int64_t* rows, float4* out, int64_t n, int vec_per_row) {
  for (int64_t i = blockIdx.x * (int64_t)blockDim.x + threadIdx.x; i < n * vec_per_row; i += (int64_t)gridDim.x * blockDim.x)
    out[i] = table[rows[i / vec_per_row] * vec_per_row + i % vec_per_row];
}
```

下の段の**方法 B** では、CPU の 8 個のスレッドが PyTorch の index_select で表から行を集め、固定したメモリに並べます。固定したメモリは、OS が場所を動かさないようにしたメモリです。それを 1 回のコピーで GPU に送ります。このコピーは GPU のコピーエンジンが運ぶので、SM を使いません。コピーエンジンは、GPU の中でデータの転送だけを受け持つ装置です。そのかわり、CPU は読む行の番号を先に知っている必要があります。入力の文章をまとめて処理する段階を prefill、1 トークンずつ生成する段階を decode と呼びます。prefill では、CPU も入力のトークンを持っているので、番号を自分で計算できます。decode では、次のトークンを決めるのは GPU です。そのため、GPU で計算した行の番号を、いったん CPU に戻してから集めます。

入力の中のトークン 1 個分の場所を、位置と呼びます。この記事のモデルの表では、1 つの位置で 16 行を読み、1 行は 64 個の float32 で 256 バイトです。2 つの方法が正しい行を読めていることは、前の記事で学習したモデルの 1 つ（seed 1337）の表で確かめました。表は 1,049,422 行、約 256 MiB です。どちらの方法でも、読んだ行の値と、モデルの出力のロジットは、GPU のメモリに置いた表から読んだ場合とビット単位で一致しました。ロジットは、確率に直す前の出力の値です。読む行を 1 つずらすと一致しなくなることも確かめています。

## 測った結果

使ったのは、AWS の EC2 で借りられる仮想マシンの g7.2xlarge です。GPU は RTX PRO 4500 Blackwell Server Edition です。GPU のメモリは 32 GiB で、PCIe Gen 5 の 16 レーンでつながります。CPU は Xeon 6975P-C の 8 vCPU で、CPU 側のメモリは 32 GiB です。表の大きさは MiB と GiB で、速さは 10 進の GB/s で書きます。CPU 側のメモリから GPU へ 256 MiB を 1 回で連続コピーすると 56.5 GB/s で、この記事ではこれを、このマシンの PCIe で送れる速さの目安として使います。

速さは、乱数で埋めた 256 MiB から 16 GiB の表で測りました。読む行は、呼び出しのたびに表全体から乱数で選び直します。Engram の行の番号も、ハッシュで表全体に散らばります。論文の 2.5 節によると、実際の文章ではよく出る並びに読み出しが偏りますが、偏りが速さをどう変えるかは、この記事では測っていません。

:::details 測り方の細かい条件
- 1 回の呼び出しの前後で GPU の処理が終わるのを待ち、その間の時間を測りました。20 回の中央値で、その前の 3 回は数えていません
- 方法 B の時間には、CPU が行を集める時間と、GPU へのコピーが終わるまでの時間を含みます。行の番号は CPU が先に持っている場合で測り、GPU から番号を戻す時間は含みません
- 表の大きさを変える測定では、方法 A の表を cudaHostAlloc で確保しました
- GPU のメモリに置いた表は、同じ 16,384 位置分の読み出しで、16 GiB でも 303 GB/s でした
- モデルの prefill の時間は、50 回の中央値です
:::

### 行が広い範囲に散らばると、方法 A は遅くなる

![横は CPU 側のメモリに置いた表の大きさで 256 MiB から 16 GiB、縦は 16,384 位置分の 64 MiB を一度に読む速さ。方法 A は丸と実線で、256 MiB と 512 MiB で 50.7 と 50.8 GB/s、1 GiB で 25.9、2 GiB で 18.3、16 GiB で 10.0 GB/s。方法 B は四角と破線で、24.0 から 20.7 GB/s へゆるやかに下がる。1 GiB と 2 GiB の間で方法 B が上になる。点線は連続コピーの 56.5 GB/s](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/5637c881fd2d11/zenn/articles/5637c881fd2d11/host-bandwidth.png)

図は、16,384 位置分の 262,144 行、64 MiB を一度に読む速さです。読む行は表全体から選ぶので、表の大きさが、そのまま行が散らばる範囲になります。方法 A は、表が 256 MiB と 512 MiB のときは 50.7 GB/s と 50.8 GB/s で、連続コピーの 56.5 GB/s の約 9 割でした。1 GiB では 25.9 GB/s、16 GiB では 10.0 GB/s まで落ちます。方法 B は、256 MiB の表での 24.0 GB/s から、16 GiB の表での 20.7 GB/s へ、約 14% 下がっただけでした。表が 1 GiB と 2 GiB の間で、方法 B のほうが速くなります。

読む行が少ないと、方法 A のほうが速くなります。16 位置分は、16 本の入力を 1 トークンずつ decode するときに 1 回で読む量にあたります。16 位置分の 256 行を 16 GiB の表から読むと、方法 A は 19.2 µs、方法 B は CPU が番号を先に持っている場合でも 36.6 µs かかりました。GPU のメモリに置いた表から同じ 16 位置分を読んでも、どの表でも 12.4〜13.9 µs かかります。読む量が 64 KiB と小さいので、時間の大半を占めるのは PCIe で運ぶ時間ではなく、呼び出し 1 回ごとにかかる固定の時間だと筆者は考えています。番号を GPU から CPU に戻すと、方法 B にはさらに約 10.5 µs が加わります。この値は、モデルの表から 16 位置分を読んだときの、番号を戻す場合の 38.3 µs と、戻さない場合の 27.8 µs の差です。

![8 GiB の表で、方法 A が 262,144 行を読む速さ。横は行と行の間隔と、行が散らばる範囲。間隔 256 B から 2 KiB、範囲 64 MiB から 512 MiB までは 50.4 から 50.5 GB/s で、間隔 4 KiB、範囲 1 GiB で 25.9、8 KiB で 18.5、16 KiB、範囲 4 GiB で 15.3 GB/s](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/5637c881fd2d11/zenn/articles/5637c881fd2d11/host-span.png)

方法 A が遅くなる理由を調べるため、8 GiB の表の中で、読む行の数を 262,144 行に固定し、行と行の間隔を 256 バイトから 16 KiB まで変えました。この測定の表は、mmap で確保して cudaHostRegister で登録したものです。mmap は OS からメモリを確保する関数で、cudaHostRegister は確保済みのメモリを固定して GPU から読めるように登録する CUDA の関数です。読むバイト数はどれも 64 MiB で、行が散らばる範囲が 64 MiB から 4 GiB まで広がります。間隔が 2 KiB までは、範囲は 512 MiB 以下で、速さは 50.4〜50.5 GB/s のままでした。間隔が 4 KiB になると範囲は 1 GiB で 25.9 GB/s、16 KiB では範囲は 4 GiB で 15.3 GB/s でした。

ページは、OS がメモリを管理する単位で、ここでは 4 KiB です。間隔が 4 KiB 以上のとき、行はすべて別々のページに入るので、読むページの数は 262,144 個で同じです。それでも速さは 25.9、18.5、15.3 GB/s と違うので、ページの数では説明できません。行を 4 KiB のページ 1 つに 1 行ずつ置いても、詰めて置いても、65,536 行を読む速さは 47.7 GB/s と 48.1 GB/s で、ほぼ同じでした。行の数が同じなら、速さは行が散らばる範囲とともに変わります。L3 キャッシュは、CPU が最近使ったデータを置く、CPU の中のメモリです。このマシンの CPU の L3 キャッシュは 480 MiB で、速さが変わる境に近い大きさです。ただし、どの間隔でも読むのは同じ 64 MiB なので、読む量がキャッシュに収まるかどうかでは、間隔による違いを説明できません。

IOMMU は、GPU のような装置が使うアドレスを、実際のメモリの場所に変換するハードウェアの仕組みです。ページの大きさ、メモリの確保の仕方、IOMMU の設定を変えても、方法 A の速さは変わりませんでした。

:::details 変えても速さが変わらなかったもの
ほかに、ページの大きさ、メモリの確保の仕方、IOMMU の設定を変えて測りました。transparent huge page と hugetlbfs は、どちらも Linux で 2 MiB のページを使う仕組みです。IOMMU の変換の表は OS が設定します。NUMA ノードは、CPU とそれに近いメモリのまとまりです。この比較は、同じ行を毎回読む測り方で行いました。8 GiB の表での方法 A の速さは、どれを変えても 12.3〜12.4 GB/s で、1 GiB の表でも 25.6〜26.2 GB/s に収まりました。

| 変えたもの | 試したもの |
|---|---|
| CPU 側のメモリのページの大きさ | 4 KiB、2 MiB（transparent huge page と、8 GiB までの hugetlbfs） |
| メモリの確保の仕方 | cudaHostAlloc、mmap と cudaHostRegister、cuMemCreate で CPU 側の NUMA ノードに確保（[DeepEP が Engram の表を CPU 側に置くときと同じ API](https://github.com/deepseek-ai/DeepEP/blob/a56d6156febcd9976e55adc85b5155bfac9f28f8/csrc/kernels/backend/symmetric.hpp#L33-L34)。確保の単位は 2 MiB だった） |
| 仮想マシンの中の OS の IOMMU の設定 | アドレスを変換する既定の設定と、変換しない iommu=pt。起動時のログで、既定の種類が Translated から Passthrough に変わることを確かめた。256 MiB、1 GiB、8 GiB の表で比べた |
:::

ここからは筆者の解釈です。GPU が CPU 側のメモリを読むときには、どこかでアドレスが変換されていて、変換の結果を覚えておける量に限りがあると考えています。行が散らばる範囲が 512 MiB までは覚えた結果を使い回せ、1 GiB 以上では変換のやり直しが増える、と考えると、512 MiB と 1 GiB の間で速さが変わることを説明できます。この考えを確かめる測定はしていません。g7.2xlarge は仮想マシンなので、変換しているのが GPU の側か、仮想マシンを動かしている外側の層かは、この 1 台の測定では分かりませんでした。

### 読む時間が収まるだけでは、forward は短くならなかった

![この記事のモデルで 8 本 × 512 トークンの prefill を bfloat16 で流したときの時間。埋め込みとブロック 0 が 481 µs、方法 A で行を読むだけなら 342 µs。表を GPU のメモリに置いた場合と比べた forward の増え方は、必要になってから読むと 272 µs で 2.5%、別の stream で先に読むと 315 µs で 2.9%、読み出しのカーネルを 16 個のスレッドブロックに絞った別の回の測定で、先に読むと 167 µs で 1.5%、その回の基準は別](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/5637c881fd2d11/zenn/articles/5637c881fd2d11/host-overlap.png)

最後に、この記事のモデルで、8 本 × 512 トークンの prefill を bfloat16 で流しました。bfloat16 は、16 ビットの浮動小数点数の形式の 1 つです。この表は約 256 MiB で、方法 A が速い範囲に収まります。Engram の層はブロック 1 の手前にあるので、行を運ぶ時間を重ねられるのは、埋め込みとブロック 0 の 481 µs の間です。方法 A で行を読むだけなら 342 µs なので、時間の上ではこの間に収まります。この記事では、先に読み始めたときの forward の増え方が、必要になってから読んだときより小さくなることを、隠れたと呼びます。forward は、入力から出力までを 1 回計算することです。

行を必要になってから読むと、表を GPU のメモリに置いた場合より、forward 全体が 272 µs、2.5% 長くなりました。読み出しを別の stream で先に始め、ブロック 0 と並べて動かしても、増え方は 315 µs、2.9% で、短くなりませんでした。stream は、GPU に順番に仕事を流す列で、列が違えば並べて動かせます。カーネルはスレッドをまとまりに分けて実行し、このまとまりをスレッドブロックと呼びます。読み出しのカーネルを 16 個のスレッドブロックに絞って測り直すと、先に読み始めた場合の増え方は 167 µs、1.5% でした。同じ測り直しの中で、必要になってから読んだ場合は 297 µs、2.7% なので、この回では先に読み始めたほうが約 130 µs 短くなりました。2 回の測定の間で、表を GPU のメモリに置いた場合の forward は 10,885 µs と 10,921 µs で、約 36 µs 違ったので、数十 µs の差は測定のばらつきと区別できませんが、130 µs はそれより大きい差です。すべての SM を使う 1 回目で短くならなかったのは、方法 A の読み出しが読み終わりを待つ間も SM を使い続け、ブロック 0 の計算と SM を取り合ったためだと筆者は考えています。16 個に絞った条件の測定は、この 1 回分だけです。

SM を使わない方法 B も、隠れませんでした。方法 B は、番号を GPU から CPU に戻す場合、行を集めて GPU に送り終えるまでが単独で 943 µs かかり、481 µs の間に収まりません。番号を CPU が先に持っている場合の単独の時間は、このモデルでは測っていませんが、乱数で埋めた 256 MiB の表では、同じ 4,096 位置分で 893 µs でした。forward 全体は、CPU が自分で番号を計算して必要になってから読むと 665 µs、6.1% 長くなり、CPU のスレッドで先に読み始めても 829 µs、7.6% 長くなりました。なお論文の 2.8% は表を足さないモデルとの比較で、この記事の値は表を GPU のメモリに置いた場合との比較です。モデルも GPU も違うので、2 つの値は直接は比べられません。

## 大規模になったときにどう扱うか

ここからは、測定をもとにした筆者の考察です。先に結論を書きます。大きな表で問題になるのは、PCIe で運べる量の合計ではありません。1 ステップの中で行を運ぶ時間を、前の計算に、計算の資源を奪わずに重ねられるかどうかです。

### 運ぶ量の合計は問題になりにくい

V4.1-Flash は 1 つの位置で、2 か所の Engram の層それぞれで 24 行を読みます。2-gram から 4-gram の 3 種類の並びを、それぞれ 8 個のヘッドに分けて引くためです。ヘッドは、1 つの並びから引く行を分ける単位で、ヘッドごとに 1 行を読みます。1 行は FP8 の値 256 バイトなので、1 トークンあたり値だけで 12 KiB です。速さに、16,384 位置分を一度に読む測定の中で最も遅い、16 GiB の表での方法 A の 10.0 GB/s を仮に使うと、1 秒あたり約 81 万トークン分を運べます。一度に読む量が少ないと固定の時間が効いて速さはこれより下がるので、これはまとめて読む場合の見積もりです。論文の表 4 の値は、4B と 8B のモデルを H800 で動かしたときの 1 秒あたり約 6,100〜9,000 トークンです。V4.1-Flash の値ではありませんが、仮に 1 万トークンとしても、運ぶ量は約 123 MB/s です。そのため、合計が PCIe を使い切ることは考えにくいと筆者は見ています。ただし速さは 16 GiB でもまだ下がっていて、約 196 GB の表での値は測っていません。

### 1 ステップで運ぶ時間を、前の計算に重ねられるか

問題になるのは、1 ステップの中で運ぶ時間です。8 本 × 512 トークンの prefill では、V4.1-Flash の 1 か所の Engram の層が読むのは 4,096 位置 × 24 行 × 256 バイトで、24 MiB です。方法 A の測定値を当てはめると、50.7 GB/s なら約 0.5 ms、10.0 GB/s なら約 2.5 ms かかります。V4.1-Flash は Engram の層を 1 と 14 に置いているので、1 か所目の前にはブロック 0 しかなく、2 か所目の前には 14 個のブロックがあります。V4.1-Flash のブロック 1 個の計算時間は測っていないので、この時間が隠れるかどうかは、この記事からは言えません。

隠すには、時間が収まるだけでは足りないことも分かりました。この記事のモデルでは、方法 A の読み出しは時間の上では収まるのに、すべての SM を使うと forward は短くならず、16 個のスレッドブロックに絞った測り直しで増え方が 297 µs から 167 µs に縮みました。SM を使わない方法 B は、CPU で集める時間が長すぎました。1 か所目の層のように前の計算が短い場所ほど、この 2 つの条件はきつくなります。

HBM は GPU に載っているメモリ、DRAM は CPU 側の主記憶、NVMe は SSD をつなぐ規格です。

| 条件 | この記事で測ったこと | 扱い方の案（この記事では試していない） |
|---|---|---|
| 運ぶ速さを落とさない | 方法 A は、行が散らばる範囲が 512 MiB までは 50 GB/s 台で、1 GiB 以上で落ち、16 GiB で 10.0 GB/s | よく読む行を速い場所にまとめ、読む範囲を狭める。論文の 2.5 節は、よく出る埋め込みを HBM か CPU 側の DRAM に、残りを NVMe に置く階層を挙げている |
| 計算の資源を奪わない | 方法 A は SM を取り合ったと見られ、スレッドブロックを 16 個に絞ると増え方が小さくなった | DeepEP のように NIC に読ませる get か、コピーエンジンだけで運ぶ形にする。方法 B のように CPU で集める部分が遅いと、SM を使わなくても間に合わない |
| 前の計算が短い場所を避ける | この記事のモデルでは、Engram の層の前には、埋め込みとブロック 0 の 481 µs しかなかった | GPU のメモリに置く行は、浅い層のよく読む行を優先する。V4.1-Flash の層 1 の表は丸ごとでは約 98 GB あり、全部は置けない |

8 GiB の表でも、読む行が 512 MiB 以内に収まれば、方法 A は 50.4〜50.5 GB/s のままでした。そのため筆者は、行の置き場所を、表の大きさだけでなく 2 つの量で決めるべきだと考えています。1 ステップで読む行が実際に散らばる範囲と、その行が必要になるまでに残っている計算の時間です。

decode では、1 ステップで読む行が少なくなります。16 位置分では、方法 A は 15.9〜19.2 µs で、表を GPU のメモリに置いた場合の 12.4〜13.9 µs との差は約 2〜6 µs でした。decode の 1 ステップの時間は測っていないので、この差が問題になるかは分かりません。

## まとめ

2026 年 11 月 19 日の時点で、最新の DeepEP の Engram は GIN の GDAKI に固定されています。NCCL の側でも、EFA の経路では相手ごとの完了待ちが空のままで、TCP の経路では window の登録が断られます。そこで、RDMA の NIC の無い 1 台の g7.2xlarge で、GPU が CPU 側のメモリを直接読む方法と、CPU が集めて送る方法を自分で書いて比べました。

測ったのは 16 GiB までの表で、読む行を表全体から一様な乱数で選んだ場合の、行を運ぶ時間です。一度に 16,384 位置分を読むと、表が 256 MiB と 512 MiB のときは、GPU が直接読む方法が 50.7〜50.8 GB/s で、CPU が集める方法の 23.2〜24.0 GB/s の約 2 倍でした。16 GiB の表では、GPU が直接読む方法は 10.0 GB/s に落ち、20.7 GB/s の CPU が集める方法が約 2 倍速くなりました。GPU が直接読む方法は、行が散らばる範囲が 512 MiB までは遅くならず、1 GiB 以上で遅くなりました。その間は測っていません。モデルの prefill では、GPU が直接読む方法は forward を 2.5〜2.9% 長くし、すべての SM を使う読み出しでは、先に読み始めても短くなりませんでした。筆者は SM の取り合いが原因だと考えています。読み出しのカーネルを 16 個のスレッドブロックに絞った測り直しでは、先に読み始めると増え方が 2.7% から 1.5% に縮みました。CPU が集める方法では 6.1〜7.6% 長くなりました。

考察では、運ぶ量の合計は PCIe の速さに対して小さく、問題は 1 ステップの中で運ぶ時間を、計算の資源を奪わずに前の計算に重ねられるかだと見積もりました。よく読む行を読む範囲の狭い場所にまとめる案と、SM を使わない運び方の案を挙げましたが、この記事では試していません。

今後は、表を何台かに分けて、公開されている版の DeepEP の get で読み、その速さを測りたいと考えています。[実験のコードと結果](https://github.com/littlemex/zenmai-lab/tree/d5d3f3c/experiments/2026-11-19-engram-host-table)は公開しています。
