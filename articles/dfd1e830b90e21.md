## はじめに

GPU の高速化の記事、たとえば LMSYS の「[Muse Spark Open Ultrafast](https://www.lmsys.org/blog/2026-11-05-muse-spark-open-ultrafast/)」は、大きいモデル向けのコードを「8000 lines of CUDA + PTX」と書き、インライン PTX の行を載せています。そうした記事は、PTX が実行ファイルのどこに置かれ、誰が PTX を GPU の機械語に変えるのかを知っていると読みやすくなります。[PTX (Parallel Thread Execution)](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/cuda-platform.html#parallel-thread-execution-ptx) は NVIDIA の GPU 向けの仮想の命令セットで、実際の GPU の機械語より一段上にある、テキストで読み書きできるアセンブリ言語です。**実行ファイルに PTX を入れておくと、ビルドしたあとに出た GPU でも、実行ファイルを作り直さずに[動かせます](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/cuda-platform.html#ptx-compatibility)。** この記事は、CUDA C++ で書いた小さなカーネル (GPU で動かす関数) が GPU で動くまでに、何が作られ、何が働くのかを、実際に動かして追います。この記事に出てくるファイルと入れ物は次のとおりです。

| 出てくるもの | どこにあるか | 何であるか |
|---|---|---|
| [SASS](#同じ足し算を-ptx-と-sass-で見る) | cubin というファイル (`vadd.sm_89.cubin`) の中 | GPU が直接実行する機械語。実行時のコンパイルが要らない |
| [PTX](#同じ足し算を-ptx-と-sass-で見る) | `vadd.ptx`、実行ファイルの中 | SASS より一段上の命令。使える cubin が無いときに、NVIDIA ドライバーが実行時に SASS へ変える |
| [fatbin](#実行ファイルの中の-fatbin) | 実行ファイルの中の `.nv_fatbin` というセクション | cubin と PTX を一緒に入れる入れ物 |

:::message
この記事の出力と時間は、[Amazon EKS](https://aws.amazon.com/eks/) の Pod で [`nvidia/cuda:13.0.2-devel-ubuntu24.04`](https://hub.docker.com/r/nvidia/cuda) のコンテナを動かして取ったものです。GPU は g6.xlarge の NVIDIA L4 1 枚 (compute capability 8.9)、NVIDIA ドライバーは 580.178.04、nvcc は 13.0.88 です。測定と文書の参照は 2026 年 11 月 23 日で、参照した CUDA Programming Guide は v13.5 です。

## 作る側の CUDA Toolkit と動かす側の NVIDIA ドライバー

![nvcc は vadd.cu を cicc で PTX に、ptxas で sm_89 の cubin に変え、両方を fatbin として実行ファイルに入れる。動かすときは CPU 側のコードから CUDA Runtime、libcuda.so.1、OS カーネル内のドライバーを通って GPU に届き、使える cubin が無いときだけ libcuda.so.1 が JIT コンパイラで PTX を SASS にして compute cache に置く](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/dfd1e830b90e21/zenn/articles/dfd1e830b90e21/compile-and-run.png)

カーネルが GPU で動くまでには、[CUDA Toolkit と NVIDIA ドライバー](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/cuda-platform.html#cuda-toolkit-and-nvidia-driver)という 2 つの製品が関わります。CUDA Toolkit は GPU を使うソフトウェアを書き、ビルドし、解析するためのライブラリとヘッダーとツールの集まりで、NVIDIA ドライバーは GPU にとっての OS にあたるソフトウェアで、GPU を使うマシンの OS に入れてあります。2 つの製品は別々に入れるもので、バージョンも別に上がります。次の表の `libcuda.so.1` が、図の CUDA Driver です。以下、単に「ドライバー」と書いたら NVIDIA ドライバーを指します。

| 名前 | どちらの製品か | 受け持ち |
|---|---|---|
| [nvcc](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html) | CUDA Toolkit | ビルドのとき、カーネルを PTX と cubin に変えて実行ファイルに入れる |
| CUDA Runtime | CUDA Toolkit (実行ファイルの中に入る) | 動かすとき、`<<<...>>>` やメモリの確保を `libcuda.so.1` の呼び出しに変える |
| `libcuda.so.1` | NVIDIA ドライバー | 動かすとき、cubin を選ぶか PTX をコンパイルし、GPU でカーネルを起動する |

例に使うのは、2 つの配列を足すだけのカーネルで、1 スレッドが 1 要素を受け持ちます。

```cpp
__global__ void vadd(const float* a, const float* b, float* c, int n) {
  int i = blockIdx.x * blockDim.x + threadIdx.x;
  if (i < n) c[i] = a[i] + b[i];
}
```

GPU は SM (streaming multiprocessor) という単位でスレッドを実行します。GPU ごとに、使える機能を表す [compute capability](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/cuda-platform.html#compute-capability-and-streaming-multiprocessor-versions) という番号があり、L4 は 8.9 です。この番号は名前にも使われ、8.9 の GPU 向けの cubin は `sm_89` (SM のバージョン)、8.9 の機能を前提にした PTX は `compute_89` と書きます。

図の上の段で、nvcc は cicc で `vadd.cu` の中のカーネルを PTX に変え、ptxas で PTX を L4 が直接実行する機械語 (SASS) に変えます。SASS を入れたバイナリのファイルを cubin と呼び、`-arch=sm_89` の指定では、nvcc は cubin と PTX をまとめて実行ファイルに入れます。下の段で、CPU 側のコード (図の host code) が実行ファイルの中の CUDA Runtime を呼び、CUDA Runtime が `libcuda.so.1` を呼び、`libcuda.so.1` が cubin を GPU に読み込みます。使える cubin が無いときは、`libcuda.so.1` が JIT コンパイラのライブラリ (`libnvidia-ptxjitcompiler.so.1`) で PTX をその場で SASS にコンパイルし、結果を compute cache (`~/.nv/ComputeCache`) に置きます。`libcuda.so.1` は、デバイスファイル (`/dev/nvidia*`) を通して、OS のカーネルの中で動くドライバーの部分と話します。

## nvcc が呼ぶ段階

nvcc は、1 つの `.cu` ファイルを CPU 側のコードと GPU 側のコードに分け、GPU 側だけを PTX、cubin、fatbin (cubin と PTX をまとめる入れ物) の順に変えて、最後に CPU 側のオブジェクトに埋め込みます。nvcc は、この段階ごとに別のコマンドを順に呼びます。`nvcc --dryrun` を付けると、呼ぶ予定のコマンドが実行されずに順に表示されるので、この順番を確かめられます。`vadd.cu` を `-arch=sm_89` でビルドするときの順番は次のとおりです。

| 順 | 呼ばれるもの | 受け持ち | 入力 | 出力 |
|---|---|---|---|---|
| 1 | `gcc` (前処理) と `cudafe++` | CPU 側のコードを取り出す | `vadd.cu` を前処理した `vadd.cpp4.ii` | `vadd.cudafe1.cpp` |
| 2 | `gcc` (前処理) と `cicc` | カーネルを PTX に変える | `vadd.cu` を前処理した `vadd.cpp1.ii` | `vadd.ptx` |
| 3 | `ptxas` | PTX を sm_89 の SASS に変え、cubin にする | `vadd.ptx` | `vadd.sm_89.cubin` |
| 4 | `fatbinary` | cubin と PTX を fatbin にまとめる | cubin と PTX | `vadd.fatbin.c` (fatbin を C の配列にしたもの) |
| 5 | `gcc` | CPU 側をコンパイルし、fatbin を取り込む | `vadd.cudafe1.cpp` | `vadd.o` |
| 6 | `nvlink`、`fatbinary`、`gcc`、`g++` | リンクの段の小さな cubin を足し、実行ファイルにする | `vadd.o` | 実行ファイル `vadd` |

`--keep` を付けると、途中のファイルが消されずに残ります。

## 同じ足し算を PTX と SASS で見る

PTX と SASS は、同じカーネルを表す 2 通りの命令の列です。PTX は compute capability が同じか高い GPU に向けて使える仮想の命令で cicc が作り、SASS は 1 つの SM のバージョン向けの命令で ptxas が PTX から作ります。まず PTX を見ます。`vadd.ptx` はテキストのファイル (全体で 1202 バイト) で、カーネルの本体は次のように書かれています。

```text
.version 9.0
.target sm_89
...
	ld.param.u64 	%rd1, [_Z4vaddPKfS0_Pfi_param_0];
	...
	mov.u32 	%r3, %ctaid.x;
	mov.u32 	%r4, %ntid.x;
	mov.u32 	%r5, %tid.x;
	mad.lo.s32 	%r1, %r3, %r4, %r5;
	setp.ge.s32 	%p1, %r1, %r2;
	@%p1 bra 	$L__BB0_2;
	...
	mul.wide.s32 	%rd5, %r1, 4;
	add.s64 	%rd6, %rd4, %rd5;
	...
	ld.global.f32 	%f1, [%rd8];
	ld.global.f32 	%f2, [%rd6];
	add.f32 	%f3, %f2, %f1;
	...
	st.global.f32 	[%rd10], %f3;
$L__BB0_2:
	ret;
```

`%ctaid.x`、`%ntid.x`、`%tid.x` は、CUDA C++ の `blockIdx.x`、`blockDim.x`、`threadIdx.x` にあたる特殊なレジスタです。`%r1` や `%f1` は型の付いた仮想のレジスタで、本物のレジスタへの割り当ては後の段に任されています。先頭の `.version 9.0` は PTX の命令セットの仕様 (PTX ISA) のバージョンで、`.target sm_89` は、この PTX が compute capability 8.9 の GPU の機能を前提にしていることを表します。

同じカーネルを [`cuobjdump`](https://docs.nvidia.com/cuda/cuda-binary-utilities/index.html) の `-sass` で実行ファイルから取り出すと、ptxas が作った SASS が見えます。

```text
...
S2R R6, SR_CTAID.X ;
S2R R3, SR_TID.X ;
IMAD R6, R6, c[0x0][0x0], R3 ;
ISETP.GE.AND P0, PT, R6, c[0x0][0x178], PT ;
@P0 EXIT ;
...
IMAD.WIDE R4, R6, R7, c[0x0][0x168] ;
IMAD.WIDE R2, R6.reuse, R7.reuse, c[0x0][0x160] ;
LDG.E R4, [R4.64] ;
LDG.E R3, [R2.64] ;
IMAD.WIDE R6, R6, R7, c[0x0][0x170] ;
FADD R9, R4, R3 ;
STG.E [R6.64], R9 ;
EXIT ;
...
```

PTX の `mad.lo.s32` が `IMAD` に、`ld.global.f32` が `LDG.E` に、`add.f32` が `FADD` に対応しています。並べて読み取れる違いは 4 つです。レジスタは `R3`、`R6` のような番号になります。カーネルの引数は、PTX にあった読み出しの命令 (`ld.param`) が無くなり、`c[0x0][0x160]` のような定数の領域から直接読まれています。`%ntid.x` を読む命令も無くなり、`IMAD` の引数の `c[0x0][0x0]` になっています。添字を 4 倍してアドレスに足す 2 つの命令 (`mul.wide.s32` と `add.s64`) は、`IMAD.WIDE` の 1 命令にまとまっています。どの命令を選び、どのレジスタに割り当てるかを決めるのが ptxas です。

## 実行ファイルの中の fatbin

fatbin は、複数の cubin と PTX を 1 つにまとめる入れ物で、nvcc が実行ファイルの ELF の `.nv_fatbin` というセクションに埋め込みます。CUDA Programming Guide によると、プログラムを動かすときには、fatbin の中から[その GPU に最も合うものが使われます](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/cuda-platform.html#cubins-and-fatbins)。nvcc の [`--gpu-architecture`](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html#gpu-architecture-arch) の説明では、`-arch=sm_89` は `--gpu-architecture=compute_89 --gpu-code=sm_89,compute_89` と同じ意味で、sm_89 の cubin と compute_89 の PTX の 2 つを入れる指定です。`cuobjdump --list-elf --list-ptx vadd` で実行ファイルの中を見ると、その 2 つが入っていました。

```text
ELF file    1: vadd.1.sm_89.cubin
ELF file    2: vadd.2.sm_89.cubin
PTX file    1: vadd.1.sm_89.ptx
```

`ELF file` の行が cubin、`PTX file` の行が PTX です。`ELF file` が 2 つ見えるのは、リンクの段で作られる小さな cubin が加わるためです。`cuobjdump` の一覧では、PTX にも `sm_89` の名前が付いて表示されます。fatbin に何を入れるかは nvcc の `-gencode` でも指定でき、`code=` に `sm_XX` を書くと cubin が、`compute_XX` を書くと PTX が入ります。

CUDA C++ の `<<<...>>>` は C++ の文法ではないので、nvcc が CUDA Runtime を呼ぶコードに書き換えます。CUDA Runtime はその呼び出しを `libcuda.so.1` の呼び出しに変え、`libcuda.so.1` がコンテキストを作り、カーネルのコードを読み込み、GPU でカーネルを起動します。CUDA Programming Guide も、CUDA Runtime API は、ドライバーが公開する [Driver API の上に作られている](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/cuda-platform.html#cuda-runtime-api-and-cuda-driver-api)、と書いています。

nvcc は、`<<<...>>>` の呼び出しを、グリッドとブロックの大きさを CUDA Runtime に渡す関数と、カーネルの代わりに呼ばれる関数 (stub) の呼び出しに書き換えます。`--keep` で残った `vadd.cudafe1.stub.c` を読むと、stub はカーネルの 4 つの引数を並べて、マクロ `__cudaLaunch` を呼んでいました。このマクロは CUDA Runtime の `cudaLaunchKernel` を呼びます (図の 4)。`vadd.cudafe1.stub.c` には、`main()` より前に動く初期化の関数もあり、埋め込まれた fatbin を CUDA Runtime に登録します (図の 1)。

`ldd vadd` で調べると、表示されたのは `libstdc++`、`libc` などだけで、`libcudart.so` も `libcuda.so` もありませんでした。nvcc は CUDA Runtime を[既定で静的にリンク](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html#cudart-none-shared-static-hybrid-cudart)するので、CUDA Runtime は実行ファイルの中に入っています。`libcuda.so.1` は、`strace` でファイルを開く呼び出しを見ると、実行中に `/usr/lib64/libcuda.so.1` として開かれていました。デバイスファイル (`/dev/nvidiactl`、`/dev/nvidia0`、`/dev/nvidia-uvm`) も開かれていました。

### 最初の呼び出しと最初の起動にかかる時間

測った 3 つの区間の中では、最初の CUDA の呼び出しがほとんどを占めます。sm_89 の cubin だけを入れた実行ファイル (`-gencode arch=compute_89,code=sm_89`) を 10 回動かした中央値で、最初の CUDA の呼び出しの `cudaFree(0)` が返るまで (図の 2〜3) が 137 ms (133〜148 ms)、カーネルの最初の起動 (図の 4〜5) が 0.141 ms、2 回目の起動 (図の 6〜7) が 0.013 ms でした。起動の時間は、要素数 $2^{20}$、1 ブロック 256 スレッドのカーネルの終わりを待つまでを含みます。

既定の [lazy loading](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/lazy-loading.html) では、モジュール (カーネルを含む GPU のコードのまとまり) は、そのカーネルを最初に起動するときに読み込まれます。sm_89 の cubin だけの実行ファイルに [`CUDA_MODULE_LOADING=EAGER`](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/environment-variables.html#cuda-module-loading) を付けて読み込みを先に済ませると、最初の起動は 0.141 ms から 0.114 ms になりました (どちらも 10 回の中央値)。

試した 3 通り (cubin だけ、PTX だけ、sm_89 の cubin と PTX の両方) では、ドライバーは、fatbin の中に動かす GPU で使える cubin があればそれを読み込み、無いときに PTX をその GPU の SASS にコンパイルしました。実行時のこのコンパイルを JIT (just-in-time) コンパイルと呼びます。fatbin に PTX が入っていれば、JIT によって、[ビルドした時点に無かった GPU でも実行ファイルが動きます](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/cuda-platform.html#just-in-time-compilation)が、最初の起動はその分だけ長くなります。

fatbin の中身だけを変えた 4 つの実行ファイルを作り、動いた 3 つを L4 で 10 回ずつ動かしました。時間は中央値で、括弧の中は最小と最大です。compute cache (ドライバーが JIT の結果を置くキャッシュ) ありの行だけは、キャッシュを空にして 10 回動かしたうちの 2〜10 回目の値です。

| fatbin の中身 | 結果 | 最初の起動 |
|---|---|---|
| sm_89 の cubin | 動く | 0.141 ms (0.130〜0.143) |
| sm_80 の cubin | 動く | 0.138 ms (0.132〜0.144) |
| compute_80 の PTX だけ (compute cache なし) | 動く | 10.50 ms (10.35〜11.48) |
| compute_80 の PTX だけ (compute cache あり) | 動く | 0.185 ms (0.177〜0.204) |
| sm_90 の cubin | `no kernel image is available for execution on the device` | 起動に失敗したので値なし |

sm_80 の cubin が 8.9 の L4 で動き、sm_90 の cubin が動かないのは、[バイナリの互換](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/cuda-platform.html#binary-compatibility)の決まりのとおりです。cubin は、compute capability のメジャーが同じで、マイナーが同じか大きい GPU でだけ動きます。compute capability 10.0 以降の cubin は、同じ GPU ファミリーの中で作った先と違う GPU に読み込むと、ドライバーが実行時に、cubin をその GPU のアーキテクチャに[結び付け直す (off-target finalization)](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/cuda-platform.html#binary-finalization)ので、sm_80 と sm_89 の時間が近かったのは 9.x までの cubin の結果です。

PTX だけの実行ファイルでは、最初の起動が、sm_89 の cubin の実行ファイルより約 10.4 ms 長くなりました。`strace` で見ると、PTX だけの実行ファイル (compute cache なし) では `libnvidia-ptxjitcompiler.so.1` が開かれていて、sm_89 の cubin だけの実行ファイルと、cubin と PTX の両方を持つ `vadd` (`-arch=sm_89` で作ったもの) では開かれていませんでした。ドライバーは [JIT の結果を compute cache に置き、次の実行ではコンパイルを繰り返しません](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/cuda-platform.html#just-in-time-compilation)。`~/.nv/ComputeCache` は 12KB になり、2 回目からの最初の起動が表の 4 行目です。compute cache を使わないときは、環境変数 [`CUDA_CACHE_DISABLE=1`](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/environment-variables.html#cuda-cache-disable) を付けて測っています。約 10 ms は、カーネルが 1 つだけの小さな PTX を、プロセスの中で最初に JIT したときの値で、JIT コンパイラのライブラリを開く時間とコンパイルの時間は分けていません。

compute cache を使わない設定のまま、lazy loading を切る `CUDA_MODULE_LOADING=EAGER` を付けると、時間のかかる場所が、カーネルの最初の起動から、最初の CUDA の呼び出しの `cudaFree(0)` に移りました。PTX だけの実行ファイルで、`cudaFree(0)` は 138.8 ms から 146.6 ms に伸び、最初の起動は 10.50 ms から 0.111 ms に縮みました (どれも 10 回の中央値)。JIT にかかる時間はなくならず、かかる場所が移ったと読み取れます。

実行ファイルに PTX が入っていて、その JIT コンパイルが働くことは、[環境変数の説明](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/environment-variables.html#cuda-force-ptx-jit-and-cuda-force-jit)にあるとおり、`CUDA_FORCE_PTX_JIT=1` を付けると手元の GPU で確かめられます。`CUDA_FORCE_PTX_JIT=1` は、fatbin に cubin があっても PTX を JIT コンパイルさせます。`-arch=sm_89` で作った実行ファイルに、compute cache を使わない設定と一緒に付けると、最初の起動は 10.45 ms (10 回の中央値) になり、sm_89 の cubin しか無い実行ファイルに付けると `no kernel image` で失敗しました。

## ドライバーに PTX を直接渡す

`libcuda.so.1` が公開する関数の集まりを Driver API と呼び、CUDA Runtime を通さずにプログラムから直接呼べます。Driver API を使うと、PTX のテキストや cubin のファイルをそのままドライバーに渡せるので、読み込みの呼び出しにかかる時間を、カーネルの起動と分けて測れます。[`cuModuleLoadData`](https://docs.nvidia.com/cuda/cuda-driver-api/group__CUDA__MODULE.html) にファイルの中身を渡すと、ドライバーはそれが PTX のテキストか cubin かを見分けて読み込みます。`--keep` で残った `vadd.ptx` と `vadd.sm_89.cubin` を、それぞれ渡して 10 回ずつ時間を測りました。

| 渡したもの | `cuModuleLoadData` の時間 | 結果 |
|---|---|---|
| `vadd.ptx` (compute cache なし) | 10.67 ms (10.48〜10.89) | 動く |
| `vadd.sm_89.cubin` | 0.03 ms (0.03〜0.05) | 動く |
| `.version` を 99.9 に書き換えた PTX | 測っていない | `CUDA_ERROR_UNSUPPORTED_PTX_VERSION` |
| `.target` を sm_90 に書き換えた PTX | 測っていない | `CUDA_ERROR_INVALID_PTX` |

`vadd.ptx` を渡したときの約 10.7 ms は、PTX だけの実行ファイル (compute_80 の PTX) で最初の起動が長くなった約 10.4 ms に近い値です。Driver API では、この時間は `cuModuleLoadData` の呼び出しの中でかかっていました。cubin の時間は `cuModuleLoadData` が返るまでで、既定の lazy loading では、[この時点でモジュールが GPU に読み込まれているとは限りません](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/environment-variables.html#cuda-module-loading)。

表の下の 2 行は、ドライバーが PTX を受け付ける条件を示しています。3 行目の条件は PTX ISA のバージョンです。[PTX ISA の文書の表](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#release-notes)では、PTX ISA 9.0 は CUDA 13.0 とドライバー r580 に、PTX ISA 9.1 は CUDA 13.1 とドライバー r590 に対応するので、ドライバー 580.178.04 が `.version 99.9` を断った結果と合わせると、ドライバーより新しい Toolkit で作った PTX も断られることがあると考えられます。4 行目の条件は `.target` です。[PTX の互換](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/cuda-platform.html#ptx-compatibility)は、PTX の compute capability と同じか高い GPU に向かってだけあります。

ドライバーに渡す PTX は、nvcc で作ったものに限りません。[NVRTC](https://docs.nvidia.com/cuda/nvrtc/index.html) という CUDA Toolkit のライブラリを使うと、プログラムの実行中に CUDA C++ の文字列を PTX にコンパイルできます。試すと、4 行のカーネルが 872 バイトの PTX になり、`cuModuleLoadData` で読み込んで正しく動きました。CUDA Programming Guide は、[ほかの言語のコンパイラも PTX を中間表現として作り](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/cuda-platform.html#parallel-thread-execution-ptx)、NVIDIA のコンパイルの道具で GPU のコードにできる、と書いています。

## インライン PTX で PTX を手で書く

[インライン PTX](https://docs.nvidia.com/cuda/inline-ptx-assembly/index.html) は、CUDA C++ のコードの中に PTX の命令を直接書く方法で、CUDA C++ の普通の書き方では出せない命令やレジスタを使うときに使います。`asm volatile("...")` の文字列の中に PTX を書きます。CUDA Programming Guide は、PTX でアプリケーションを[直接書ける](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/cuda-platform.html#parallel-thread-execution-ptx)と書く一方、GPU のバイナリを手で作ったり書き換えたりすることは[サポートしない](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/cuda-platform.html#binary-compatibility)と書いています。LMSYS の記事には、カーネルの中で時刻を記録するマクロの部品として、`%globaltimer` を読む次の 1 行が載っています。

```cpp
asm volatile("mov.u64 %0, %%globaltimer;" : "=l"(t) :: "memory");
```

`%globaltimer` は、ナノ秒の時刻を返す PTX の特殊なレジスタです。`%0` は 1 つ目のオペランドの場所です。`"=l"(t)` は、そこに 64 ビットのレジスタを当て、命令のあとでその値を C++ の変数 `t` に入れる、という指定です。`%%` は、文字列の中で `%` そのものを書くための書き方です。

試しに、4 つのブロックに、それぞれ 20 万、40 万、60 万、80 万クロック以上の空回りをさせ、`%globaltimer` で前後の時刻を読みました。1 つ目のブロックは 200,058 クロックが 98,144 ns で、1 ns あたり 2.04 クロックになり (4 つのブロックで 2.03〜2.04)、`nvidia-smi` が示す SM の最大クロック 2,040 MHz に近い値でした。

インライン PTX の文字列は、`%0` がレジスタの名前に、`%%` が `%` に置き換わって、`timer.ptx` に `mov.u64 %rd10, %globaltimer;` として入り、ptxas によって SASS の `CS2R R4, SR_GLOBALTIMERLO` になりました。書いた PTX がどの SASS になるかは、ビルドのときは ptxas が、JIT のときはドライバーの JIT コンパイラが決めます。なお、[PTX ISA の文書](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#special-registers-globaltimer)は、`%globaltimer` を NVIDIA の道具向けのレジスタとし、振る舞いは target によって違い、将来の GPU で変わるか無くなることがあり、別の target に JIT コンパイルされたときの値は決まっていない、と書いています。

## LMSYS の記事を読み直す

LMSYS の記事が PTX の名前で書いている操作は、CUDA C++ の中にインライン PTX で書いて nvcc でビルドすれば、この記事で動かした `%globaltimer` と同じく、普通の CUDA C++ から作られた PTX と同じ道を通ります。その PTX は、ビルドのときに ptxas で SASS になって cubin として fatbin に入るか、PTX のまま fatbin に入って実行時にドライバーの JIT で SASS になります。次の表は、LMSYS の記事が PTX の名前で書いている操作と、書き方を示していない操作に分けて、PTX との関係を並べたものです。

| LMSYS の記事の中の操作 | LMSYS の記事の説明 | PTX との関係 |
|---|---|---|
| `%globaltimer` | カーネルの中で時刻を記録するマクロの部品 | インライン PTX で読む。この記事の実験と同じ書き方 |
| `fence.release.sys` など | system スコープで release する | PTX の [`fence`](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#parallel-synchronization-and-communication-instructions-membar) と [`st`](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#data-movement-and-conversion-instructions-st) の命令。LMSYS の記事は、GB300 では、試した system スコープの release (`fence.release.sys`、`fence.acq_rel.sys`、`st.release.sys` のフラグ) がどれも同じ重いバリア `MEMBAR.ALL.SYS` にコンパイルされたと書いている |
| evict-first のキャッシュの指定 | 重みの読み込みが、L2 キャッシュに残したいデータを押し出さないようにする | LMSYS の記事は evict-first の書き方を示していない (別の箇所に `load_evict_last(...)` という関数の呼び出しはある)。PTX では、読み込みの命令 [`ld`](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#data-movement-and-conversion-instructions-ld) に `.L2::evict_first` を付けて指定できる (sm_100 以上、PTX ISA 8.8 以上) |
| mbarrier | 共有メモリに置くハードウェアのカウンター | LMSYS の記事は PTX の命令を示していない。PTX には [`mbarrier`](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#parallel-synchronization-and-communication-instructions-mbarrier) の命令がある |

NVRTC で、実行中に CUDA C++ の文字列を PTX にしてから読み込むプログラムです。

```bash
cat > nvrtc.cpp << 'EOF'
// Compile CUDA C++ to PTX inside the program with NVRTC, then hand the PTX to the driver.
#include <cstdio>
#include <string>
#include <chrono>
#include <nvrtc.h>
#include <cuda.h>

static const char* src = R"(
extern "C" __global__ void scale(float* x, float k, int n) {
  int i = blockIdx.x * blockDim.x + threadIdx.x;
  if (i < n) x[i] *= k;
})";

int main() {
  auto t0 = std::chrono::steady_clock::now();
  nvrtcProgram prog;
  nvrtcCreateProgram(&prog, src, "scale.cu", 0, nullptr, nullptr);
  const char* opts[] = { "--gpu-architecture=compute_89" };
  nvrtcResult r = nvrtcCompileProgram(prog, 1, opts);
  size_t sz; nvrtcGetPTXSize(prog, &sz);
  std::string ptx(sz, '\0'); nvrtcGetPTX(prog, ptx.data());
  printf("nvrtc=%s ptx_bytes=%zu nvrtc_ms=%.2f\n", nvrtcGetErrorString(r), sz,
         std::chrono::duration<double, std::milli>(std::chrono::steady_clock::now() - t0).count());

  CUdevice dev; CUcontext ctx; CUmodule mod; CUfunction fn;
  cuInit(0); cuDeviceGet(&dev, 0); cuCtxCreate(&ctx, nullptr, 0, dev);
  CUresult cr = cuModuleLoadData(&mod, ptx.c_str());
  cuModuleGetFunction(&fn, mod, "scale");
  const int n = 1024; CUdeviceptr x; cuMemAlloc(&x, n * 4);
  float h[n]; for (int i = 0; i < n; i++) h[i] = i;
  cuMemcpyHtoD(x, h, n * 4);
  float k = 10.0f; int nn = n; void* args[] = { &x, &k, &nn };
  cuLaunchKernel(fn, 4, 1, 1, 256, 1, 1, 0, nullptr, args, nullptr);
  cuCtxSynchronize(); cuMemcpyDtoH(h, x, n * 4);
  printf("module_load=%d x[7]=%.0f expected=70\n", (int)cr, h[7]);
  return 0;
}
EOF
```

インライン PTX で `%globaltimer` と `%smid` を読むプログラムです。

```bash
cat > timer.cu << 'EOF'
// Inline PTX: read special registers that CUDA C++ has no name for.
#include <cstdio>
#include <cuda_runtime.h>

__device__ __forceinline__ unsigned long long globaltimer() {
  unsigned long long t;
  asm volatile("mov.u64 %0, %%globaltimer;" : "=l"(t) :: "memory");
  return t;
}
__device__ __forceinline__ unsigned smid() {
  unsigned s;
  asm volatile("mov.u32 %0, %%smid;" : "=r"(s));
  return s;
}

// Each block spins for (block + 1) * 200,000 SM cycles and records how long that took in nanoseconds.
__global__ void stamp(unsigned long long* ns, long long* cyc, unsigned* sm) {
  if (threadIdx.x != 0) return;
  unsigned long long t0 = globaltimer();
  long long c0 = clock64();
  while (clock64() - c0 < (blockIdx.x + 1) * 200000LL) { }
  long long c1 = clock64();
  ns[blockIdx.x] = globaltimer() - t0;
  cyc[blockIdx.x] = c1 - c0;
  sm[blockIdx.x] = smid();
}

int main() {
  const int blocks = 4;
  unsigned long long* ns; long long* cyc; unsigned* sm;
  cudaMallocManaged(&ns, blocks * sizeof(*ns));
  cudaMallocManaged(&cyc, blocks * sizeof(*cyc));
  cudaMallocManaged(&sm, blocks * sizeof(*sm));
  stamp<<<blocks, 32>>>(ns, cyc, sm);
  cudaDeviceSynchronize();
  for (int i = 0; i < blocks; i++)
    printf("block=%d sm=%u cycles=%lld ns=%llu ghz=%.2f\n", i, sm[i], cyc[i], ns[i], (double)cyc[i] / ns[i]);
  cudaDeviceProp p; cudaGetDeviceProperties(&p, 0);
  printf("sm_count=%d warp_size=%d\n", p.multiProcessorCount, p.warpSize);
  return 0;
}
EOF
```

## まとめ

PTX は、`-arch=sm_89` のビルドでは cubin と一緒に fatbin に入って実行ファイルの中に置かれ、ビルドのときは ptxas が、実行時に使える cubin が無いときは `libcuda.so.1` が JIT コンパイラで、PTX を GPU の機械語 (SASS) に変えます。インライン PTX で手で書いた命令も、普通の CUDA C++ から作られた PTX と同じこの道を通って SASS になります。
