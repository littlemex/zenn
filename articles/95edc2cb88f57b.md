## 学習フレームワーク

### torchtitan の 1 年: TitanRL と FlexShard

> 参照元: [TorchTitan Update: New SOTA Models, Performance at Scale, TitanRL](https://pytorch.org/blog/torchtitan-update-new-sota-models-performance-at-scale-titanrl/)

torchtitan はこの 1 年で、新しいモデルへの対応だけでなく、RL による事後学習や、大きな規模での性能、障害に備えた保存の仕組みまで手を広げてきました。RL は、モデルの出力に点数を付け、その点数を手がかりにモデルを直していく学習の方法で、言語モデルの事後学習の中心になっています。RL では文章を作る推論側と、モデルを直す学習側が別々の実装になっていることが多く、同じトークンの確率が両者で少しずれる問題が知られています。また、数百から数千の GPU で学習すると、途中経過を保存するチェックポイントのたびに全員で待ち合わせる時間が無視できなくなります。この Meta の PyTorch チームのブログは、こうした課題に対する 1 年分の更新をまとめたもので、学習から推論まで同じモデル定義を使う TitanRL、新しい最適化手法 Muon に合わせて重みの分け方を変えられる FlexShard、待ち合わせを減らした新しいチェックポイントが柱です。抜粋に出てくる FSDP は PyTorch の標準のデータ並列で、データ並列はデータを分けて同時に学習する方法です。NCCL は GPU どうしの通信ライブラリ、MXFP8 は 8 ビットで数を表す形式、DCPv1 は従来のチェックポイントの仕組みです。分散処理に参加する 1 つ 1 つのプロセスはランクと呼ばれます。

:::message
**コメント**: 一番気になったのは、事前学習、RL による事後学習、vLLM での推論まで同じモデル定義を使う TitanRL の設計です。モデルの実装が 2 つに分かれていると確率のずれの原因を追いにくいので、batch-invariant mode は、ずれの原因が自分の変更かどうかを見分ける道具になりそうです。チェックポイントの待ち合わせを減らす仕組みは、プロセスの数が増えるほど効くので、もっと大きな規模での数字を見てみたいです。FlexShard は、Muon のような新しい最適化手法に合わせて重みの分け方を変えられる点が気になるので、ちゃんと学ぼうと思います。
:::

![事前学習、事後学習、vLLM での推論が 1 つのモデル定義を共有する TitanRL の構成図](https://pytorch.org/wp-content/uploads/2026/10/one_model_definition-scaled.png)
*出典: [TorchTitan Update](https://pytorch.org/blog/torchtitan-update-new-sota-models-performance-at-scale-titanrl/) の図*

#### 参照元からの抜粋と要約

- **課題**: 大きな MoE モデルを 1 つのコードで学習したい人には、4 つの悩みがありました。新しいモデルへの対応に手間がかかること、RL で学習用と推論用の実装が分かれていてずれに気づきにくいこと、通信と計算を重ねる工夫がモデルごとにばらばらなこと、ランクの数が多いとチェックポイントの保存と読み込みに時間がかかることです。
- **ねらい**: 小さく拡張しやすい形を保ったまま、モデル、RL、性能、通信、チェックポイントをまとめて改善すること。
- **やったこと**: 記事では、Qwen3.5、Kimi K3、DeepSeek-V4 などを、torchtitan の並列化の仕組み全体に組み込みました。RL の TitanRL と、データ並列の新しいライブラリ FlexShard を入れています。新しい torch_checkpointing は、最初の保存の前に 1 回だけ情報を共有し、その後の保存では軽い待ち合わせだけで済ませます。PyTorch 2.14 で選べるようになった NCCL の新しい実装も試しています。
- **結果**: 記事によると、GB300 を 256 基使った DeepSeek-V3 671B の学習は、MXFP8 で GPU 1 基あたり毎秒 5,324 トークンでした。FlexShard を使うと、H100 256 基の DeepSeek-V3 で、Muon の重みの更新にかかる時間が FSDP だけの実装と比べて最大 79% 短くなりました。これは学習 1 ステップ全体の時間ではありません。H100 512 基の DeepSeek-V3 671B では、チェックポイントの書き込みが従来の DCPv1 の平均 384.4 秒から 13.1 秒に、分け方を変えない読み込みが 194.7 秒から 79 秒に縮みました。

## データの読み込みとクラスタの運用

### GPUDirect Storage: Python からの直接の読み込み

> 参照元: [How to Read Data into GPU Memory in Python with NVIDIA GPUDirect Storage](https://developer.nvidia.com/blog/how-to-read-data-into-gpu-memory-in-python-with-nvidia-gpudirect-storage/)

GPU の計算が速くなるにつれて、学習データやチェックポイントを GPU に運ぶ時間が目立つようになってきました。普通の読み込みでは、ストレージから一度 CPU のメモリに置いてから GPU に写すので、その分の時間と CPU の手間がかかります。GPUDirect Storage は、ストレージから GPU のメモリへ CPU のメモリを経由せずにデータを運ぶ NVIDIA の仕組みで、アプリケーションからの主な入口は C 言語の cuFile です。KvikIO は cuFile を Python と C++ から使いやすくしたライブラリで、GPU 向けのデータ処理ライブラリ cuDF の読み込みにも使われています。この NVIDIA のブログは、KvikIO で GPU へ読み込み、本当に直接の経路を通ったかを cuFile の統計で確かめる手順を示しています。

:::message
**コメント**: この記事で役に立つのは、経路の選択が 2 段階に分かれているという指摘です。KvikIO が cuFile を呼んでいても、cuFile が CPU を経由する互換の経路を選んでいることがあり、cuFile が呼ばれたことは速い経路を通った証拠になりません。Python から GPU へ直接読む使い方は増えると見ているので、この確かめ方は覚えておきたいです。AWS の場合は、私の理解では、p 系のインスタンスで FSx for Lustre を使うケースでしか GDS は使えない認識です。今後は、そもそも GDS が裏側でどう実装されているのかを深掘りしたいです。
:::

![KvikIO の読み込みで、ホストメモリを経由する経路と、ストレージから GPU メモリへ直接届く経路を比べた図](https://developer-blogs.nvidia.com/wp-content/uploads/2026/10/execution-flow-nvidia-kvikio.webp)
*出典: [How to Read Data into GPU Memory in Python with NVIDIA GPUDirect Storage](https://developer.nvidia.com/blog/how-to-read-data-into-gpu-memory-in-python-with-nvidia-gpudirect-storage/) の図*

#### 参照元からの抜粋と要約

- **課題**: AI の開発者の多くは Python を使いますが、GPUDirect Storage を使う主な入口は C 言語の cuFile でした。速い経路を本当に通ったかを確かめる方法も分かりにくい状態でした。
- **ねらい**: KvikIO で GPU メモリへ読み込み、cuFile の統計で通った経路を確かめる手順を示すこと。
- **やったこと**: 記事では、H100、CUDA 13.3、cuFile 1.18、ext4 のローカル NVMe の環境で、1 GiB のファイルを GPU のバッファに読み込みました。cuFile の統計を細かく取る設定を入れ、gds_stats で経路ごとの回数を数えています。環境変数を切り替えて、直接の経路、cuFile の互換の経路、KvikIO 自身の CPU 経由の経路の 3 つを再現しました。
- **結果**: 記事によると、既定の設定では、1 GiB が 4 MiB ずつ 256 回に分かれて読まれ、256 回すべてが直接の経路を通りました。cuFile の互換の経路を強制すると、同じ読み込みが互換の経路の回数として数えられました。cuFile の中でさらに処理が分かれる条件も、設定の値ごとに説明しています。

### CUDA 13.4: メモリ上限付きの GPU の共有

> 参照元: [Memory-Enforced GPU Sharing in Kubernetes with NVIDIA CUDA 13.4](https://developer.nvidia.com/blog/memory-enforced-gpu-sharing-in-kubernetes-with-nvidia-cuda-13-4/)

多くの推論や開発のジョブは、GPU 1 台の計算とメモリを使い切りません。1 台の GPU を複数のジョブで分け合う方法には、ハードウェアで区切る MIG、時間で順番に使う time-slicing、計算ユニットの SM を同時に分け合う sm-sharing があります。このうち time-slicing には、ジョブごとの GPU メモリの上限を守らせる仕組みがなく、1 つのジョブがメモリを使いすぎると他のジョブがメモリを確保できなくなるおそれがありました。CUDA 13.4 は、この上限を CUDA 自身が守る機能を入れました。この NVIDIA のブログは、その機能を Kubernetes から使うためのオペレーター、つまり Kubernetes の上で決まった作業を自動でこなす常駐のプログラムを紹介しています。Kubernetes でプログラムを動かす入れ物である Pod に、設定のメモ書きにあたるアノテーションを書くだけで、メモリの量と分け方を指定できます。

:::message
**コメント**: メモリの上限を CUDA 自身が守るようになったことで、time-slicing で同じ GPU に載せたジョブ同士がメモリを取り合う心配が減るのはありがたいです。ただ、エラーが他のジョブに広がるかどうかは別の話で、sm-sharing では全員が 1 つのエラーの範囲を共有する点は気をつけたいです。B300 のようにメモリが大きい GPU が増えるほど、小さな推論や開発のジョブを詰めて載せる使い方が広がりそうです。ただ、正直なところ挙動が全然ピンとこないので、これもいろいろと制約をかけてみたりして検証してみたいと思います。
:::

![time-slicing は GPU を使う時間を分け、sm-sharing は GPU の計算ユニットである SM を分けることを比べた図](https://developer-blogs.nvidia.com/wp-content/uploads/2026/10/image1-12-625x648-png.webp)
*出典: [Memory-Enforced GPU Sharing in Kubernetes with NVIDIA CUDA 13.4](https://developer.nvidia.com/blog/memory-enforced-gpu-sharing-in-kubernetes-with-nvidia-cuda-13-4/) の図*

#### 参照元からの抜粋と要約

- **課題**: 多くの AI のジョブは GPU 1 台を使い切りません。1 つのジョブに GPU を 1 台ずつ渡すと、残りの容量が遊びます。CUDA 13.4 でメモリの上限を守る機能が入りましたが、Kubernetes からそれを使う仕組みがありませんでした。
- **ねらい**: ノードの上で、CUDA のメモリ上限と計算の分け方をジョブごとに設定し、使った量を数える仕組みを作ること。
- **やったこと**: 記事では、gpu-fractioning というオープンソースのオペレーターを公開しました。KAI Scheduler v0.18.0 には NvFractions という共有の方式を足しました。スケジューラが決めた GPU とメモリの量を Pod のアノテーションに書き、オペレーターがそれを読んで上限を設定します。
- **結果**: 記事によると、オペレーターと対応する CUDA を入れておけば、Pod のアノテーションで、保証するメモリの量と、空いていれば伸ばせる上限を指定できるようになりました。計算の分け方は time-slicing と sm-sharing から選べ、複数の GPU にまたがる割り当ても指定できます。sm-sharing は全員が 1 つのエラーの範囲を共有するので、信頼できるジョブ同士で使うように書かれています。性能の数字は記事にありません。

## 分散推論の通信

### INC-MoE: スイッチで流す MoE の通信

> 参照元: [INC-MoE: Overlapping In-Network Collectives and Expert Computation for Expert-Parallel Mixture-of-Experts Inference](https://arxiv.org/html/2610.36339)

MoE のモデルが大きくなると、expert を 1 台の GPU に収められず、複数のノードに分けて置く expert 並列が必要になります。expert 並列では、層ごとにトークンを各 expert へ配り、計算の結果を集める通信が要り、ノードの間の帯域はノードの中より細いので、この通信が処理を頼んでから結果が返るまでの待ち時間、つまりレイテンシーを大きく左右します。これに対し、ネットワークの機械であるスイッチの中で配り直しや足し算をしてしまう in-network computing という考え方があり、NVIDIA の SHARP などで実用になっています。このプレプリントは、Huawei の研究者が、MoE の推論で使う 2 つの通信 AllGather と ReduceScatter をスイッチに任せて同時に流し、expert の計算とも重ねる INC-MoE を提案したものです。評価は、入力の文章をまとめて読み込む prefill の段階で行われています。抜粋に出てくるスレッドブロックは GPU などの上で一緒に動く処理のまとまりで、RoCE は Ethernet の上で RDMA という直接のメモリ転送を使う方式です。コサイン類似度は 2 つのベクトルの向きがどれだけそろっているかを表す値で、1.0 なら向きが完全にそろっています。decode は prefill のあと 1 トークンずつ出していく段階です。

:::message
**コメント**: MoE の all-to-all 通信をスイッチにやらせる、というアイデアは少し気になりました。というのも、読んでいて、京や富岳で使われた富士通の Tofu インターコネクトのバリア同期のインタフェースを思い出しました。Tofu には、集団通信をネットワーク側のハードウェアで処理する Tofu Barrier Interface という仕組みがあります。[Tofu: Interconnect for the K computer](http://web.archive.org/web/20201101145337/https://www.fujitsu.com/global/documents/about/resources/publications/fstj/archives/vol48-3/paper05.pdf) によると、この仕組みが受け持つのは Barrier、Broadcast、Reduce、AllReduce の 4 つで、扱えるのは 64 ビットの値 1 つだけです。受け取ったデータも送るデータもメインメモリを通らないので、レイテンシーが小さく、OS の割り込みの影響も受けにくいと書かれています。京の MPI の測定では、この仕組みを使った Barrier と AllReduce が 9,216 ノードまでほとんど遅くならず、ソフトウェアでの実装より安定していました。詳しくは [MPI Library and Low-Level Communication on the K computer](http://web.archive.org/web/20200720193348/https://www.fujitsu.com/global/documents/about/resources/publications/fstj/archives/vol48-3/paper11.pdf) にあります。一方で、ReduceScatter や AllGather はこの仕組みの対象ではなく、ソフトウェアで実装されています。ノード間の転送は、宛先のメモリのアドレスを指定して読み書きする RDMA で、ノードをまたいで 1 つのアドレス空間を共有する形でもありません。同期や小さな値の集計をネットワークに任せる Tofu と、MoE の大きなデータの配り直しをスイッチに任せる INC-MoE は、通信をネットワーク側に寄せる点では同じ方向を向いていて、扱う量が違うと理解しました。INC-MoE が一番近い先行研究として挙げているのは、スイッチの中で配り直しと足し算を動的に行う DySHARP です。気になるのは、評価のスイッチが本物ではなく、アクセラレータで真似たものである点で、実機のスイッチでどうなるかを見たいです。
:::

![トークンを帯に分け、AllGather、expert の計算、ReduceScatter を専用のスレッドブロックで同時に進める INC-MoE の全体図](https://arxiv.org/html/2610.36339v1/enhanced_pipeline_bands.png)
*出典: [INC-MoE](https://arxiv.org/html/2610.36339) の Figure 3*

#### 参照元からの抜粋と要約

- **課題**: 対象にする vLLM の既定の方式では、トークンを配る側を AllGather、結果を集める側を ReduceScatter という通信で行います。ノードの間の帯域はノードの中より細いので、この通信が層のレイテンシーを決めていました。
- **ねらい**: 2 つの通信をスイッチに任せ、同時に流して回線の行きと帰りの両方を使い、expert の計算とも重ねて、通信を待つ時間を減らすこと。
- **やったこと**: 著者らは、トークンを帯と呼ぶ小さな束に分け、配る係、計算する係、集める係のスレッドブロックが 1 つのカーネルの中で同時に動くようにしました。vLLM の MoE 層と差し替えて使えます。実験では 4 台のアクセラレータをそれぞれ 1 ノードに見立て、5 台目のアクセラレータでスイッチを真似ました。つなぎ方は RoCE で、スイッチへの 400 Gbps のリンクを 4 台で共有しています。
- **結果**: 著者らによると、OLMoE-1B-7B の prefill を 4 つの expert 並列で動かすと、最初のトークンが出るまでのレイテンシーは、vLLM の既定のリング型の通信と比べて、アクセラレータ 1 台あたりの入力が合計 24K トークンのときに 20.2%、126K トークンのときに 33.1% 短くなりました。スループットは、同じ比較で 25.3% から 49.5% 上がりました。各層の出力は、既定の方式とのコサイン類似度が 1.0 と報告されています。decode と大きな MoE モデルでの評価はありません。

## カーネルと数値

### softmax と cross-entropy の丸めの不具合

> 参照元: [A Fix for Softmax and Cross-Entropy](https://arxiv.org/html/2610.31642)

言語モデルの学習は、モデルの出力を足して 1 になる確率に直す softmax と、その確率から誤差を出す cross-entropy の上で動いています。どちらも桁があふれないよう、最大値を引いてから計算するのが標準の書き方で、それで数値の問題は片付いたと考えられてきました。一方、学習では計算を速くするために 16 ビットの bf16 のような少ないビットで数を表すことが増え、丸めの誤差が大きくなっています。誤差を減らすために重みを動かす向きと量を勾配と呼び、この勾配が丸めで崩れると学習がおかしくなります。このプレプリントは、Google DeepMind の研究者が、標準の書き方にまだ残る 2 つの丸めの不具合を指摘し、書き直し方を示したものです。大きなモデルを先生役にして小さなモデルにまねさせる蒸留でも、影響を調べています。抜粋に出てくる fp32 と fp64 は、32 ビットと 64 ビットで数を表す形式です。KL は教師と生徒が出す確率の分布がどれだけ違うかを表す値で、0 なら同じです。weight decay は、重みが大きくなりすぎないよう少しずつ小さくする工夫で、Adam の ε は割り算が 0 で壊れないように足す小さな定数です。

:::message
**コメント**: 気になるのは 2 つ目の Softmax Cancellation で、bf16 で on-policy の蒸留や RL をするときに、気づかないまま効いているかもしれません。RL の TIS への影響も考えましたが、気になったのは TIS の測定自体のずれです。学習側と推論側の確率はほぼ同じなので、その差には bf16 の丸めの雑音が混ざっているかもしれません。確信度の高いトークンでの方策の勾配や、参照モデルへの KL の罰則など、RL への影響は大きそうに感じました。
:::

![正解の候補と他の候補の出力の差が大きくなると、標準の実装では正解側の勾配が bf16 で約 5.5、fp32 で約 16.6 を境に 0 へ落ちることを示す図](https://arxiv.org/html/2610.31642v3/paper_fig1a_hard_cliff.png)
*出典: [A Fix for Softmax and Cross-Entropy](https://arxiv.org/html/2610.31642) の Figure 1 の a*

#### 参照元からの抜粋と要約

- **課題**: softmax と cross-entropy の標準の実装には、数の丸めによる 2 つの不具合がありました。1 つ目の Softmax Collapse は、正解の出力が他の出力より大きく離れたとき、つまりモデルが強く確信したときに起きます。標準の実装は最大値を引いてから計算するので、その差が bf16 で約 5.5、fp32 で約 16.6 を超えると、正解側の勾配だけが 0 に丸められ、他の出力の勾配は残ります。本来 0 になるはずの勾配の合計が、これで 0 でなくなります。2 つ目の Softmax Cancellation は蒸留で起きます。蒸留では、生徒の確率から教師の確率を引いたものが勾配になります。学習が進んで生徒の出力が教師の出力とほぼ同じになると、ほぼ同じ 2 つの数の引き算になって丸めの誤差だけが残り、本来 0 に下がるはずの勾配が雑音の高さで止まります。
- **ねらい**: 計算の途中で高い精度の型に変換せずに、丸めに強い softplus、expm1、log1p という関数だけで書き直すこと。
- **やったこと**: 著者らは、JAX で修正版を書きました。足し算の余りを当てる小さな課題で、bf16、fp32、fp64 と、最適化手法 Adam の小さな定数 ε の値をいくつか変えて標準の実装と比べています。教師の重みで始めた生徒の蒸留でも比べ、既存の対策の Zero-sum Projection と StableMax とも比べました。
- **結果**: 著者らによると、足し算の余りを当てる課題では、修正版は試したすべての精度と ε の設定でテストの正解率が 98.9% 以上になり、損失が急に跳ねる現象も消えました。weight decay を外した別の課題では、標準の実装の正解率が学習の途中で 61% から 23% に急に下がったのに対し、修正版は 85% まで上がりました。蒸留では、標準の実装が bf16 で生徒を教師からずらしたのに対し、修正版はすべての精度で KL を 0、正解率を 100% に保ちました。

### logsumexp のカーネル融合

> 参照元: [Speeding up Log-Sum-Exp: Kernel Fusion at the Memory Wall, Integer Arithmetic at the Compute Wall](https://arxiv.org/html/2610.33647)

logsumexp は、たくさんの数の指数の和の対数を、桁があふれないように出す計算です。言語モデルでは、語彙全体からトークンの確率を出すたびに使われ、語彙が大きいほど計算の量も増えます。GPU の上の計算は、カーネルと呼ぶ小さなプログラムを順に起動して進み、カーネルが分かれるたびに GPU のメモリへの読み書きと起動の手間がかかります。カーネル融合は、いくつかのカーネルを 1 つにまとめてこの手間を減らす工夫です。このプレプリントは、Aalto University と NVIDIA などの研究者が、logsumexp を 1 つのカーネルにまとめた FuseLSE と、特殊な関数を速く計算する回路のない CPU 向けに整数の計算で近似する IntLSE を作り、人の評価で言語モデルを直す RLHF などの使い道で効果を測ったものです。抜粋に出てくる確率的サーキットは確率を組み合わせた計算の図で、粒子フィルターはたくさんの候補から状態を推定する方法です。どちらも logsumexp を多く使います。

:::message
**コメント**: PyTorch の torch.logsumexp が 9 個の小さなカーネルに分かれているとは知りませんでした。torch.compile がカーネルをまとめた場合よりもさらに速いという点は、コンパイラ任せにせず手で書く価値がまだあることを示していると思います。RL の対数確率の計算に差し込んで、学習 1 ステップ全体がどれだけ縮むかを試したいです。
:::

![入力の大きさごとに、GPU と CPU での logsumexp の 1 回あたりの時間と誤差を、torch と FuseLSE と IntLSE で比べた図](https://arxiv.org/html/2610.33647v3/fig_microbenchmark.svg)
*出典: [Speeding up Log-Sum-Exp](https://arxiv.org/html/2610.33647) の Figure 3*

#### 参照元からの抜粋と要約

- **課題**: PyTorch の実装は GPU で 9 個のカーネルに分かれ、そのたびに GPU のメモリへの読み書きとカーネルの起動が起きていました。大きな入力では、同じ大きさの torch.sum より約 6 倍遅い状態でした。
- **ねらい**: 1 回の読み込みで済む 1 つのカーネル FuseLSE と、特殊な関数を速く計算する回路がない CPU 向けに、整数の計算で近似する IntLSE を作ること。
- **やったこと**: 著者らは、V100 の GPU と Xeon Gold 6134 の CPU で、1 回あたりのレイテンシーを入力の大きさを変えて測りました。V100、H100、H200、B300 では、torch.compile や JAX の XLA がカーネルをまとめた場合とも比べています。さらに、RLHF でトークンの確率を出す計算、確率的サーキットの推論、粒子フィルターの 3 つの使い道でも測りました。
- **結果**: 著者らによると、V100 では torch.logsumexp と比べて、要素数 1,024 以下で約 10〜11 倍、8,192 以上で約 6 倍速くなりました。4 種類の GPU で、torch.compile や JAX の XLA がカーネルをまとめた場合と比べても 1.8〜2.1 倍速い結果です。CPU では、近似の誤差を許す IntLSE が FuseLSE より 3〜6 倍速く、粒子フィルターでは torch より 2.8〜5.2 倍速くなりました。IntLSE の誤差は広い入力の範囲で 0.2% 未満ですが、入力の範囲によっては CPU で torch より遅い場合もあります。コードは [GitHub](https://github.com/lingyunyao/fuselse) で公開されています。

## モデルの構造

### Merlin: 平均とばらつきで選ぶ線形 attention の記憶

> 参照元: [Multi-State Linear Attention with Generalized Second-Order Routing](https://arxiv.org/html/2610.37645)

attention は、文章のどのトークンに注目するかを決める計算で、注目する側を query、注目される側を key と呼びます。普通の attention は、読んだトークンの key と value を KV キャッシュとしてすべて残すので、文章が長いほどメモリと計算が増えます。線形 attention や Mamba のような状態空間モデルは、その代わりに決まった大きさの状態を持つので、計算が文脈の長さに比例するだけで済みますが、1 つの状態に全部を詰めるので長い文脈では情報が落ちます。そこで、文脈を区間に分けて区間ごとに状態を持ち、読むときに区間を選ぶ方法が出てきました。このプレプリントは、Princeton University の研究者が、どの区間を読むかを key の平均だけでなくばらつきからも決める Merlin を提案したものです。

:::message
**コメント**: 推論の基盤から見ると、決まった大きさの状態で済む構造はメモリの見積もりが変わる点が大事です。区間を増やせば保存する量も増えるので、少ない区間で同じ精度を出せる選び方には価値があると思います。試したのは 1.3B 以下の小さなモデルだけなので、大きなモデルでも同じ傾向になるかは気になります。
:::

![文脈を区間に分け、各区間の記憶と key の平均とばらつきを持ち、query がそれらから区間ごとの重みを決める Merlin の全体図](https://arxiv.org/html/2610.37645v1/gram_main_diagram_v2.png)
*出典: [Multi-State Linear Attention with Generalized Second-Order Routing](https://arxiv.org/html/2610.37645) の Figure 2*

#### 参照元からの抜粋と要約

- **課題**: 区間ごとに記憶を分ける方法では、区間の結果をまとめる重みを、位置か key の平均との近さだけで決めていました。query と key がどれだけ鋭く合うかという、ばらつきの情報は使われていませんでした。
- **ねらい**: 平均に加えてばらつきの情報も使い、区間の重みを決めること。
- **やったこと**: 著者らは、区間を選ぶために、記憶の読み書きとは別の小さな key と query を作りました。各区間について、key の平均と、key の成分を組み合わせて掛けた値の平均を保存します。この 2 つから、query との合い方の平均とばらつきを求め、学習で決まる割合で混ぜて重みにしています。Gated DeltaNet の 1.3B と Mamba-2 の 780M を区間に分ける形に直し、長い文脈の評価で比べました。
- **結果**: 著者らによると、RULER の検索と質問の課題で、Gated DeltaNet の平均点は 62.7 となり、key の平均だけで決める方法の 57.9 を上回りました。Mamba-2 では 76.2 となり、同じ方法の 71.2 と比べて 7.0% 高い結果です。LongBench では、同じ方法と比べて Gated DeltaNet で 13.5%、Mamba-2 で 12.0% 高くなりました。区間を短くして 4 倍のメモリを使う比較対象も上回っています。

### 拡散言語モデルの作り方

> 参照元: [How To Build A Modern Diffusion Language Model](https://arxiv.org/html/2610.33391)

今の多くの言語モデルは、トークンを左から 1 つずつ出す自己回帰型で、n 個のトークンを出すのにモデルを n 回呼びます。拡散言語モデルは、全部を隠した文から始めて、何回かの書き直しで全部の位置を同時に埋めていく言語モデルで、画像の生成で使われてきた拡散モデルの考え方を文章に持ち込んだものです。長い出力はブロックに分けて順に作る方式が主流で、確定した前のブロックの KV キャッシュは使い回せます。ここ 2 年で、Google の Gemma Diffusion や NVIDIA の Nemotron Diffusion のように、大きな組織が数十億から数百億パラメータの規模で出すようになりました。このプレプリントは、Cornell University の研究者が、拡散言語モデルを作る部品と、実際のモデルがそれをどう組み合わせているかを解説したもので、新しい実験ではなく、これまでの研究の整理です。抜粋に出てくる perplexity は次のトークンの当てやすさの指標で、MAUVE は作った文の自然さの指標です。

:::message
**コメント**: 推論の回数が出力の長さではなく、書き直しの回数とブロックの数で決まるので、推論エンジンのバッチの組み方は今とは別の考え方になりそうです。SGLang が LLaDA 2.0 に対応したときの動きは、私が以前書いた「[SGLang で Diffusion LLM をサポート](https://zenn.dev/tosshi/articles/067d4c912c98d6)」で検証しました。大きな組織が本気で出してきたので、推論基盤でも一度は向き合う形式になりそうです。
:::

![自己回帰型は 1 回に 1 トークンを左から出し、拡散型は全部を隠した列から数回の書き直しで全位置を同時に埋めることを比べた図](https://arxiv.org/html/2610.33391v1/figures/ar-diffusion-comparison.png)
*出典: [How To Build A Modern Diffusion Language Model](https://arxiv.org/html/2610.33391) の Figure 1*

#### 参照元からの抜粋と要約

- **課題**: 自己回帰型は GPU の並列性を使い切れず、一度出したトークンを後から直すこともできません。
- **ねらい**: 隠した列から全体を同時に書き直していく拡散言語モデルについて、基本から最新の部品までを 1 本にまとめること。
- **やったこと**: 著者らは、トークンを隠して当てる基本の拡散から始めて、長さを変えられるブロック単位の生成、確定したトークンを戻して直す再マスク、速く出すための選び方、出力の誘導、重い部分を 1 回だけ動かす構造、学習の方法を順に説明しています。LLaDA、Gemma Diffusion、Nemotron Diffusion がどの部品を組み合わせているかも表で比べています。
- **結果**: 著者らによると、拡散言語モデルは 2 年で、研究の試作から商用のモデルまで進みました。LLaDA は 8B、Nemotron Diffusion は 35B まで大きくなっています。紹介されている先行研究では、商用の Mercury が普通の GPU でユーザー 1 人あたり毎秒 1,200 トークンを超えると報告されています。別の先行研究では、再マスクを使うと MAUVE が 1,024 回の書き直しで 0.40、4,096 回で 0.66 になり、自己回帰型の 0.76 に近づきました。一方で、perplexity で同じ値に届くまでに自己回帰型の 16 倍の計算が要ったという報告も引用されています。

### EmbeddingGemma 2: 文、画像、音声の共通の空間

> 参照元: [EmbeddingGemma 2: Unified and Efficient Multimodal Representations](https://arxiv.org/html/2610.37364)

埋め込みモデルは、文や画像を、意味が近いほど近くなる数の並びに直すモデルです。質問に関係する資料を検索して、それを手がかりに言語モデルに答えさせる RAG では、この埋め込みで資料を探します。これまで音声や画像を検索するには、文字に起こしたり説明文を付けたりしてから文の埋め込みを作ることが多く、そのための別のモデルが必要でした。このプレプリントは、Google が、文、画像、音声、動画とその組み合わせを 1 つの空間に置く 7 億 4,400 万パラメータの埋め込みモデル EmbeddingGemma 2 を発表したものです。数を少ないビットで表してメモリを減らす量子化をかけた版もあり、スマートフォンの上で動かすことも想定しています。重みは Hugging Face の [google/embeddinggemma-2](https://huggingface.co/google/embeddinggemma-2) で公開されていて、モデルカードのライセンスは Apache 2.0 です。抜粋に出てくる MTEB は、埋め込みモデルの性能を多くの課題でまとめて測る評価です。

:::message
**コメント**: 文、画像、音声、動画を 1 つの埋め込みモデルで同じ空間に置けるのは、RAG の基盤から見ると大きいです。文字起こしや説明文を付けるための別のモデルが要らなくなれば、索引を作る流れがかなり単純になります。端末の上で動かす使い方も考えられそうです。英語の文の評価では前の版から少し下がっている点は覚えておきます。
:::

![文、画像、動画、音声と、それらの組み合わせを 1 つの意味のそろったベクトル空間に置く EmbeddingGemma 2 の概念図](https://arxiv.org/html/2610.37364v1/diagram.png)
*出典: [EmbeddingGemma 2](https://arxiv.org/html/2610.37364) の Figure 1*

#### 参照元からの抜粋と要約

- **課題**: 文の埋め込みモデルで音声や画像を扱うには、文字起こしや説明文を付ける別の道具が必要で、細かい情報も落ちます。画像と文を扱う既存のモデルは混ざった入力が苦手で、大きな言語モデルを使う埋め込みは重すぎて速く動かせません。
- **ねらい**: 小さいのに、どの組み合わせの入力でも 1 つの空間に置ける埋め込みモデルを作ること。
- **やったこと**: 著者らは、Gemma 4 を土台に、画像と音声の入口を付けた 7 億 4,400 万パラメータのモデルを作りました。このうち文の部分は 2 億 7,100 万パラメータです。文だけの学習から始めて、画像や音声を混ぜた学習へ 3 段階で進め、Gemini Embedding 2 から蒸留しています。学習に使ったのは約 2 兆 9,000 億トークンです。
- **結果**: 著者らによると、コードの評価である MTEB のコード部門では、文の部分で、約 28 倍大きい首位のモデルとの差が 2 点以内でした。画像と動画と文書の画像の評価では、10 億パラメータ未満のモデルの中で 2 つの集計の両方で最高でした。音声でも、10 億パラメータ未満のモデルの中で複数の課題で最高でした。ただし、すべての評価で首位というわけではありません。

## 理論

### key と query の似方から見た KV キャッシュ圧縮の限界

> 参照元: [Attention under Bounded Key–Query Similarity: Space Complexity and Transformer Anisotropy](https://arxiv.org/html/2610.35020)

長い文脈を扱う推論では、KV キャッシュがメモリの大半を占めるので、残すトークンを選んで間引いたり、少ないビットで表す量子化をしたりして小さくする方法が多く提案されています。どこまで小さくできるかには理論上の下限がありますが、これまでの下限は query と key がぴったり重なる最悪の場合を使って証明されていて、実際のモデルには当てはまりにくいものでした。2 つのベクトルの向きがどれだけそろっているかを表すコサイン類似度で見ると、実際のモデルの key と query は小さい範囲に集まることが知られています。このプレプリントは、MIT と EPFL の研究者が、この測った事実を前提に入れて、圧縮の上限と下限を出し直した理論の研究です。

:::message
**コメント**: query を見る前に残す key を選ぶという条件では、一様にランダムに間引くだけで理論上ほぼ最適になる場合が多いという結論は、実務の感覚からすると意外でした。KV キャッシュを捨てる方式を比べるとき、一様な間引きを強い比較対象として入れるべきだと感じました。ただし、生成の品質で一様な間引きが常に一番という意味ではなく、attention の重みを見て残すものを選ぶ SnapKV や H2O、量子化は、この下限の対象の外です。
:::

![Llama 3.1、Qwen3、Ministral 3 の 8B モデルで測った key と query の類似度の範囲を、一様な間引きが最適な領域と重要度で選ぶべき領域の図に重ねた散布図](https://arxiv.org/html/2610.35020v1/ab_p0_1_scatter.svg)
*出典: [Attention under Bounded Key–Query Similarity](https://arxiv.org/html/2610.35020) の Figure 3*

#### 参照元からの抜粋と要約

- **課題**: KV キャッシュの圧縮の理論上の下限は、query と key が強く似る最悪の場合を使って証明されていました。実際のモデルの値を当てはめても、どこまでメモリを減らせるかの役に立つ目安が得られませんでした。
- **ねらい**: key と query のコサイン類似度がある小さな範囲に収まるという、測った事実を前提に入れて、圧縮の上限と下限を出し直すこと。
- **やったこと**: 著者らは、類似度の範囲によって、一様に間引くのが最適な領域と、重要なものを選んで残すのが最適な領域に分けて、それぞれでほぼ一致する上限と下限を証明しました。Llama 3.1、Qwen3、Ministral 3 の 8B モデルで、LongBench v2、InfiniteBench、SCBench の入力を 8K から 256K の長さで与え、4 つの層で類似度の範囲を測りました。
- **結果**: 著者らによると、測った範囲の多くは、一様な間引きが最適な領域の中か、その近くに入りました。下限の証明に使った難しい例の形も、実際のモデルで見える key と query の偏り方と性質が似ていました。

### Muon の更新が Hessian に合う理由

> 参照元: [How Does Orthogonalization Adapt to the Neural Network Hessian Structure?](https://arxiv.org/html/2610.28975)

学習でモデルの重みをどう動かすかを決めるのが最適化手法で、長く AdamW が標準でした。Muon は、勾配を縦と横に数を並べた表、つまり行列として扱い、どの向きにも同じ強さで伸びる形にそろえる直交化という操作をしてから重みを更新する手法で、大きなモデルの学習で使われ始めています。最適化の理論では、重みを少し動かしたときに誤差の増え方がどう変わるかを表す Hessian という行列の形に合わせて更新すると効率がよいことが知られています。ニューラルネットワークの Hessian は、表の左上から右下へ並ぶ対角のブロックに値が集まる形をしています。このプレプリントは、Dartmouth College と Meta の研究者が、Muon の更新がこの形に合う理由の一部を、初期化の時点で証明したものです。抜粋に出てくる自己外積は、ベクトルや行列をそれ自身と掛け合わせて作る行列で、期待値はたくさん試したときの平均の値です。

:::message
**コメント**: 上の torchtitan の FlexShard のように、分散の仕方まで Muon に合わせる動きが出ています。行列を丸ごと 1 つのプロセスに持たせるなど、基盤側の作りを変えるだけの価値があるのかを考えるには、なぜ効くのかの理解が要ります。証明は単純な 4 つのモデルの初期化の時点に限られていて、学習が進んだ後も同じ形が続くかは、これからの課題だと思います。
:::

![初期化時の Transformer の重み行列で、Hessian は対角のブロックに、momentum の自己外積は対角に値が集中していることを並べたヒートマップ](https://arxiv.org/html/2610.28975v1/fig1_9263.png)
*出典: [How Does Orthogonalization Adapt to the Neural Network Hessian Structure?](https://arxiv.org/html/2610.28975) の Figure 1*

#### 参照元からの抜粋と要約

- **課題**: Muon は多くの課題で AdamW を上回りますが、Muon の更新がなぜ Hessian の形に合うのかは説明されていませんでした。
- **ねらい**: Muon が暗に使っている前処理が Hessian の形に合うのは、勾配の自己外積の期待値が対角に集まるからだと、数式で示すこと。
- **やったこと**: 著者らは、行列分解、深い線形ネットワーク、2 層の ReLU ネットワーク、1 層の線形 attention の 4 つのモデルで、ランダムな初期化の時点の勾配の自己外積の期待値を計算しました。隠れ層の幅を広げたときに、対角と対角以外の値がどの速さで大きくなるかを証明しています。Qwen3.5-0.8B-Base、Granite-4.0-1B-Base、Llama-3.2-1B でも、ランダムな初期化を 25 回、FineWeb-Edu の 64 個の入力列で確かめました。
- **結果**: 著者らによると、4 つのモデルのすべてで、幅が広いほど対角の値が対角以外の値を引き離すことが、計算と実験の両方で確かめられました。線形 attention の Q、K、V では、この期待値の対角以外の値がちょうど 0 になります。

### スケーリング則の当てはめの曖昧さ

> 参照元: [Ambiguous Fits: The Rashomon Effect and Challenges in Scaling Law Estimation](https://arxiv.org/html/2610.34514)

スケーリング則は、モデルの大きさや計算量と性能の関係を表す式で、どの大きさのモデルにどれだけ計算を使うかを決めるのに使われます。小さなモデルをいくつか学習して点を取り、べき乗の式を当てはめて、もっと大きな規模の性能を予測します。測った範囲の外側を式で予測することを外挿と呼び、外挿の結果で数百万ドル規模の学習の計画が決まることもあります。当てはめには、Chinchilla の論文で使われた方法 3 が広く使われてきましたが、その答えが本当に一番よい当てはめかは確かめられていませんでした。このプレプリントは、University of Cambridge と Google DeepMind の研究者が、当てはめの曖昧さを保証付きの探索で洗い出したものです。

:::message
**コメント**: 人工的に作った合成データの例ですが、誤差がほぼ同じ 2 つの当てはめが、300 倍先の規模で必要な計算量について 74.6 倍違う答えを出すという結果には、ぞっとしました。1 本の線だけで計算の予算を決める危うさは伝わるので、スケーリング則の数字を引用するときは、誤差の近い当てはめが示す予測の幅も一緒に見たいです。ただし、保証付きの探索そのものにも時間がかかるので、その見積もりも要ります。
:::

![合成データで、当てはめの誤差がほぼ同じ 2 本の線が、学習した範囲の先で大きく離れていく様子と、最適から 1% 以内の当てはめ全部の予測が入る帯を示す図](https://arxiv.org/html/2610.34514v1/scaling_law_nonidentifiability.svg)
*出典: [Ambiguous Fits](https://arxiv.org/html/2610.34514) の Figure 1*

#### 参照元からの抜粋と要約

- **課題**: スケーリング則の最後の段階である、べき乗の式をデータに当てはめる作業は、決まった初期値から局所的に探すやり方に頼っていました。一番よい答えに近い保証はなく、誤差がほぼ同じで外挿が大きく違う当てはめがあることも見過ごされていました。
- **ねらい**: 決めた式と探索の範囲の中で、誤差が最良から指定した幅以内であることを保証付きで見つけ、誤差の近い当てはめの集まりと、その予測の幅も求めること。
- **やったこと**: 著者らは、式の変数を、範囲ごとに損失の上限と下限を安く計算できる形に直しました。その上で、範囲を分けながら見込みのない範囲を捨てていく分枝限定法の手順を 3 つ作りました。合成データと、文献から取った実際のスケーリングの 4 つの系列で、Chinchilla の方法 3 と比べています。
- **結果**: 著者らによると、実際の 4 つの系列で、Chinchilla の方法 3 の当てはめは、一番小さい損失を 2% から 180% 上回っていました。初期値の格子を細かくしても、よくなるとは限りませんでした。合成データでは、誤差が最適から 1% 以内と保証された 2 つの当てはめが、学習した範囲の 300 倍の規模で目標の損失に届く計算量を 74.6 倍違って予測しました。一方、実データの 5 つの変数の式では、予測の幅を厳密に求める計算が今の計算予算に収まらず、局所的な探索で代用しています。この幅は、将来の実測値が入ることを保証するものではありません。
