## 学習フレームワーク

### torchtitan on Trainium: 3 通りの Qwen3 学習

torchtitan は、PyTorch だけで大きなモデルを分散して学習するための、Meta が作っているフレームワークです。Trainium は AWS が作っている学習用のチップで、これまでは XLA というコンパイラを経由して PyTorch のモデルを動かすのが普通でした。TorchNeuron は、Trainium を PyTorch の device としてそのまま登録する仕組みで、GPU と同じ書き方で Trainium を使えるようにします。この記事は、その上で torchtitan を動かし、Qwen3 を 3 通りの方法で学習する手順を示した AWS のブログです。3 つ目の方法では MoE を扱います。MoE は、expert と呼ぶ小さなネットワークをたくさん持ち、トークンごとに一部の expert だけを使うモデルの作り方です。トークンは、モデルが文章を扱うときの単位で、単語や文字のかけらにあたります。NKI は、Trainium 向けのカーネル、つまりチップの上で動く小さなプログラムを自分で書くための仕組みです。損失は、モデルの答えが正解からどれだけ外れているかを表す数で、小さいほどよい値です。

:::message
コメント: 学習側にとっての一番のメリットは、Native PyTorch に対応したことで、PyTorch で書かれた新しいモデルがそのまま Trainium で動きやすくなったことだと思います。Qwen3-4B の 2 つの方法では、モデルを書き直さずに設定の切り替えだけで動いています。今後は、vLLM や SGLang の Trainium 向けのバックエンドも Native PyTorch に差し変わり、推論でも Trainium がスムーズに動くようになることを期待しています。ただ、GPU でも同じですが、特に推論ではカーネルを書かないと性能は上がりません。そこは利用者や開発者のコミュニティで盛り上げていくところだと思います。
:::

![公開済みの重みから始めた学習で最初の損失が 6.54 になり、書き出した重みを読み戻したときに不足や余分なキーが出なかったことを示す端末の出力](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/20/ML-22120-1.png)
*出典: [Train Qwen3 on AWS Trainium with torchtitan](https://aws.amazon.com/jp/blogs/machine-learning/train-qwen3-on-aws-trainium-with-torchtitan/) の図*

#### 参照元からの抜粋と要約

- **課題**: Trainium で新しいモデルを学習したい人は、GPU で使い慣れた PyTorch と torchtitan の手順を変えずに使いたいと考えています。そのためには、公開済みの重みの読み書き、torchtitan 自身のモデル実装、MoE を速く動かすカーネルの 3 つが必要でした。
- **ねらい**: 設定だけを切り替えて、3 通りの学習を同じ torchrun の起動コマンドで動かすこと。
- **やったこと**: trn2.48xlarge 1 台で、公開済みの Qwen3-4B-Instruct-2507 を 2 通りの方法で学習しました。1 つは Hugging Face Transformers v5 のモデル定義を使う方法で、もう 1 つは torchtitan 自身の Qwen3 実装を使う方法です。3 つ目の方法では、Qwen3-30B-A3B を 4 層と 64 個の expert に縮めて 1 台に収め、MoE 層を NKI で書いたカーネルで動かしました。自作のカーネルを登録する手順も、トークンの位置の情報を埋め込む RoPE を例に示しています。
- **結果**: 公開済みの重みから始めた最初のステップの損失は 6.54 で、ランダムな重みから始めた 12.43 より低くなりました。書き出した重みを読み戻すと、埋め込みと重みを共有する lm_head.weight を除いて、足りないキーも余分なキーもありませんでした。自作の RoPE カーネルは、float32 で PyTorch の標準実装と最大の差が 0.0 で一致しました。

### torchtitan の 1 年: TitanRL と FlexShard

これは、torchtitan のこの 1 年の更新を Meta の PyTorch チームがまとめたブログです。RL は、モデルの出力に点数を付け、その点数を手がかりにモデルを直していく学習の方法で、言語モデルの事後学習でよく使われます。RL では、文章を作る推論側と、モデルを直す学習側が別々の実装になっていることが多く、同じトークンの確率が両者で少しずれる問題が知られています。チェックポイントは、学習の途中経過を保存したもので、障害から再開するときに使います。分散処理に参加する 1 つ 1 つのプロセスをランクと呼びます。FSDP は PyTorch の標準のデータ並列で、データ並列はデータを分けて同時に学習する方法です。NCCL は GPU どうしの通信ライブラリで、MXFP8 は 8 ビットで数を表す形式です。Muon は、勾配の行列をそろえてから重みを更新する新しい最適化手法です。

:::message
コメント: 一番気になったのは、事前学習、RL による事後学習、vLLM での推論まで同じモデル定義を使う TitanRL の設計です。モデルの実装が 2 つに分かれていると、確率のずれの原因を追いにくくなります。対応する on-policy の構成では、batch-invariant mode によって学習側と生成側の対数確率がビット単位で一致すると書かれていて、ずれの原因が自分の変更かどうかを見分ける道具になりそうです。チェックポイントの保存で学習が止まる時間は、H100 512 基の DeepSeek-V3 671B で平均 841.2 ms から 34.1 ms に縮んでいます。ランクが増えるほど待ち合わせの負担は大きくなるので、もっと大きな規模ほど効きそうです。性能の数字は Meta の社内クラスタでの測定で、他のフレームワークとの速度の比較はありません。Megatron との比較は損失の曲線だけです。
:::

![事前学習、事後学習、vLLM での推論が 1 つのモデル定義を共有する TitanRL の構成図](https://pytorch.org/wp-content/uploads/2026/10/one_model_definition-scaled.png)
*出典: [TorchTitan Update](https://pytorch.org/blog/torchtitan-update-new-sota-models-performance-at-scale-titanrl/) の図*

#### 参照元からの抜粋と要約

- **課題**: 大きな MoE モデルを 1 つのコードで学習したい人には、4 つの悩みがありました。新しいモデルへの対応に手間がかかること、RL で学習用と推論用の実装が分かれていてずれに気づきにくいこと、通信と計算を重ねる工夫がモデルごとにばらばらなこと、ランクの数が多いとチェックポイントの保存と読み込みに時間がかかることです。
- **ねらい**: 小さく拡張しやすい形を保ったまま、モデル、RL、性能、通信、チェックポイントをまとめて改善すること。
- **やったこと**: Qwen3.5、Kimi K3、DeepSeek-V4 などを、torchtitan の並列化の仕組み全体に組み込みました。RL の TitanRL と、データ並列の新しいライブラリ FlexShard を入れています。新しい torch_checkpointing は、最初の保存の前に 1 回だけ情報を共有し、その後の保存では軽い待ち合わせだけで済ませます。PyTorch 2.14 で選べるようになった NCCL の新しい実装も試しています。
- **結果**: GB300 を 256 基使った DeepSeek-V3 671B の学習は、MXFP8 で GPU 1 基あたり毎秒 5,324 トークンでした。FlexShard を使うと、H100 256 基の DeepSeek-V3 で、Muon の重みの更新にかかる時間が FSDP だけの実装と比べて最大 79% 短くなりました。これは学習 1 ステップ全体の時間ではありません。H100 512 基の DeepSeek-V3 671B では、チェックポイントの書き込みが従来の DCPv1 の平均 384.4 秒から 13.1 秒に、分け方を変えない読み込みが 194.7 秒から 79 秒に縮みました。

## データの読み込みとクラスタの運用

### GPUDirect Storage: Python からの直接の読み込み

GPUDirect Storage は、ストレージから GPU のメモリへ、CPU のメモリを経由せずにデータを運ぶ NVIDIA の仕組みです。アプリケーションからこの仕組みを使う主な入口は、C 言語の cuFile というライブラリです。KvikIO は、その cuFile を Python と C++ から使いやすくした NVIDIA のライブラリで、GPU 向けのデータ処理ライブラリ cuDF の読み込みにも使われています。この記事は、KvikIO で GPU のメモリへ読み込み、本当に直接の経路を通ったかを cuFile の統計で確かめる手順を示した NVIDIA のブログです。

:::message
コメント: この記事で役に立つのは、経路の選択が 2 段階に分かれているという指摘です。KvikIO が cuFile を呼んだとしても、cuFile が CPU を経由する互換の経路を選んでいることがあります。cuFile が呼ばれたことは、速い経路を通った証拠になりません。cuDF の読み込みも KvikIO を通るので、Python から GPU へ直接読む使い方は増えると見ています。記事の検証はローカルの NVMe で、読み込みのスループットの数字はありません。共有のファイルシステムでも同じ確かめ方が使えるかは、まとめの表に入れました。
:::

![KvikIO の読み込みで、ホストメモリを経由する経路と、ストレージから GPU メモリへ直接届く経路を比べた図](https://developer-blogs.nvidia.com/wp-content/uploads/2026/10/execution-flow-nvidia-kvikio.webp)
*出典: [How to Read Data into GPU Memory in Python with NVIDIA GPUDirect Storage](https://developer.nvidia.com/blog/how-to-read-data-into-gpu-memory-in-python-with-nvidia-gpudirect-storage/) の図*

#### 参照元からの抜粋と要約

- **課題**: AI の開発者の多くは Python を使いますが、GPUDirect Storage を使う主な入口は C 言語の cuFile でした。速い経路を本当に通ったかを確かめる方法も分かりにくい状態でした。
- **ねらい**: KvikIO で GPU メモリへ読み込み、cuFile の統計で通った経路を確かめる手順を示すこと。
- **やったこと**: H100、CUDA 13.3、cuFile 1.18、ext4 のローカル NVMe の環境で、1 GiB のファイルを GPU のバッファに読み込みました。cuFile の統計を細かく取る設定を入れ、gds_stats で経路ごとの回数を数えています。環境変数を切り替えて、直接の経路、cuFile の互換の経路、KvikIO 自身の CPU 経由の経路の 3 つを再現しました。
- **結果**: 既定の設定では、1 GiB が 4 MiB ずつ 256 回に分かれて読まれ、256 回すべてが直接の経路を通りました。cuFile の互換の経路を強制すると、同じ読み込みが互換の経路の回数として数えられました。cuFile の中でさらに処理が分かれる条件も、設定の値ごとに説明しています。

### Mission Control 2.5: Kubernetes での自動復旧

Mission Control は、NVIDIA の GPU クラスタを監視して運用するためのソフトウェアです。Kubernetes は、たくさんのコンピュータの上でプログラムを動かして管理する仕組みで、スケジューラは、どのジョブをどのコンピュータで動かすかを決める係です。ノードは GPU を積んだ 1 台のコンピュータを指します。Slurm はスーパーコンピュータで広く使われるジョブの管理ソフトで、Run:ai は NVIDIA の Kubernetes 向けのスケジューラです。この記事は、これまで Slurm のジョブ向けだった障害からの自動復旧を、Run:ai が配置する Kubernetes のジョブにも広げたことを説明する NVIDIA のブログです。

:::message
コメント: 参考にしたいのは、ジョブの配置、ジョブの復旧、ハードウェアの復旧の 3 つの受け持ちを分けた設計です。ジョブの復旧はハードウェアの直し方を知らなくてよく、ハードウェアの復旧は学習フレームワークを知らなくて済みます。AWS でも、ジョブの再開を受け持つ SageMaker HyperPod の自動再開や、ノードの修理を受け持つ EKS のノードの自動修復があり、同じ分け方で考える参考になりそうです。ただし、2 つの仕組みが同じ障害に同時に反応したときにどうなるかは、組み合わせごとに確かめる必要があります。記事には、復旧にかかる時間が何秒減ったかという数字はありません。
:::

![Kubernetes のスケジューラ、ジョブの自動復旧、ハードウェアの自動復旧の 3 つが連携する構成図](https://developer-blogs.nvidia.com/wp-content/uploads/2026/09/image2-19.webp)
*出典: [How NVIDIA Mission Control 2.5 Brings Autonomous Recovery to Kubernetes](https://developer.nvidia.com/blog/how-nvidia-mission-control-2-5-brings-autonomous-recovery-to-kubernetes/) の図*

#### 参照元からの抜粋と要約

- **課題**: 数百ノードで何週間も学習を続けると、GPU の故障、ソフトウェアの一時的な失敗、ネットワークのタイムアウトが避けられません。人が手で直すやり方は、この規模では追いつきません。これまでの自動復旧は Slurm のジョブにしか使えませんでした。
- **ねらい**: 同じ自動復旧を、Run:ai が配置する Kubernetes のジョブにも使えるようにすること。
- **やったこと**: スケジューラ、ジョブの自動復旧、ハードウェアの自動復旧の 3 つに分けて組みました。GPU が壊れたときは、ジョブを健全なノードで再開する作業と、壊れたノードを外して診断する作業を並行して進めます。ソフトウェアの一時的な失敗では、ハードウェアには手を出さずにジョブだけを再試行します。故障の前触れが見えたノードは、ジョブが来る前に割り当ての対象から外します。
- **結果**: Mission Control 2.5 として公開され、Slurm と Kubernetes で同じ復旧の考え方が使えるようになりました。AI でネットワークの異常を見つける機能はベータ版です。

### CUDA 13.4: メモリ上限付きの GPU の共有

1 台の GPU を複数のジョブで分け合う方法には、ハードウェアで区切る MIG、時間で順番に使う time-slicing、計算ユニットの SM を同時に分け合う sm-sharing があります。これまでの time-slicing には、ジョブごとの GPU メモリの上限を守らせる仕組みがありませんでした。CUDA 13.4 は、この上限を CUDA 自身が守る機能を入れました。Kubernetes で動かすプログラムの入れ物を Pod と呼び、アノテーションは Pod の設定に付けるメモ書きのような項目です。オペレーターは、Kubernetes の上で決まった作業を自動でこなす常駐のプログラムです。この記事は、CUDA 13.4 の機能を Pod のアノテーションで指定できるようにするオペレーターを紹介する NVIDIA のブログです。

:::message
コメント: これまでの time-slicing では、ある Pod がメモリを使いすぎると、同じ GPU の他の Pod がメモリを確保できなくなるおそれがありました。CUDA 13.4 ではメモリの上限を CUDA 自身が守るので、この心配が減ります。上限を超えた確保は、その Pod の側で失敗します。ただし、エラーが他の Pod に広がるかどうかは別の話で、sm-sharing では全員が 1 つのエラーの範囲を共有します。B300 のようにメモリが大きい GPU が増えるほど、小さな推論や開発のジョブを詰めて載せる使い方が広がりそうです。
:::

![time-slicing は GPU を使う時間を分け、sm-sharing は GPU の計算ユニットである SM を分けることを比べた図](https://developer-blogs.nvidia.com/wp-content/uploads/2026/10/image1-12-625x648-png.webp)
*出典: [Memory-Enforced GPU Sharing in Kubernetes with NVIDIA CUDA 13.4](https://developer.nvidia.com/blog/memory-enforced-gpu-sharing-in-kubernetes-with-nvidia-cuda-13-4/) の図*

#### 参照元からの抜粋と要約

- **課題**: 多くの AI のジョブは GPU 1 台を使い切りません。1 つのジョブに GPU を 1 台ずつ渡すと、残りの容量が遊びます。CUDA 13.4 でメモリの上限を守る機能が入りましたが、Kubernetes からそれを使う仕組みがありませんでした。
- **ねらい**: ノードの上で、CUDA のメモリ上限と計算の分け方をジョブごとに設定し、使った量を数える仕組みを作ること。
- **やったこと**: gpu-fractioning というオープンソースのオペレーターを公開しました。KAI Scheduler v0.18.0 には NvFractions という共有の方式を足しました。スケジューラが決めた GPU とメモリの量を Pod のアノテーションに書き、オペレーターがそれを読んで上限を設定します。
- **結果**: オペレーターと対応する CUDA を入れておけば、Pod のアノテーションで、保証するメモリの量と、空いていれば伸ばせる上限を指定できるようになりました。計算の分け方は time-slicing と sm-sharing から選べ、複数の GPU にまたがる割り当ても指定できます。sm-sharing は全員が 1 つのエラーの範囲を共有するので、信頼できるジョブ同士で使うように書かれています。性能の数字は記事にありません。

## 分散推論の通信

### INC-MoE: スイッチで流す MoE の通信

MoE の expert を複数のノードに分けて置く方法を expert 並列と呼びます。expert 並列では、層ごとにトークンを各 expert へ配り、結果を集める通信が要ります。スイッチは、ノードどうしをつなぐネットワークの機械です。スイッチの中で配り直しや足し算をする考え方は in-network computing と呼ばれ、NVIDIA の SHARP などで実用になっています。レイテンシーは処理を頼んでから結果が返るまでの待ち時間で、スループットは 1 秒あたりに処理できる量です。スレッドブロックは、GPU などの上で一緒に動く処理のまとまりです。コサイン類似度は 2 つのベクトルの向きがどれだけそろっているかを表す値で、1.0 なら向きが完全にそろっています。prefill は入力の文章をまとめて読み込む最初の段階で、decode はそのあと 1 トークンずつ出していく段階です。このプレプリントは、MoE の推論で必要な通信をスイッチに任せ、expert の計算とも重ねる方式を Huawei の研究者が提案したものです。

:::message
コメント: MoE をノードをまたいで推論すると、層ごとの通信がレイテンシーの大半を占めることがあると、このプレプリントは指摘しています。その通信をスイッチに任せる方向は、今後のネットワーク機器の選び方に関わるので気になりました。最初は Tofu と同じかと思いましたが、別物でした。EuroSys 2019 の [Tofu](https://doi.org/10.1145/3302424.3303953) は学習のための計算グラフの分け方を自動で探すコンパイラで、INC-MoE は引用もしていません。富士通の [Tofu インターコネクト](https://doi.org/10.1109/MM.2011.98) も集団通信をネットワーク側で助ける点は近そうですが、細かい仕組みはまだ確かめていないので、まとめの表に入れました。一番近い先行研究として挙げられているのは、スイッチの中で配り直しと足し算を動的に行う DySHARP です。気になるのは、評価のスイッチが本物ではなく、アクセラレータで真似たものである点です。
:::

![トークンを帯に分け、AllGather、expert の計算、ReduceScatter を専用のスレッドブロックで同時に進める INC-MoE の全体図](https://arxiv.org/html/2610.36339v1/enhanced_pipeline_bands.png)
*出典: [INC-MoE](https://arxiv.org/html/2610.36339) の Figure 3*

#### 参照元からの抜粋と要約

- **課題**: 対象にする vLLM の既定の方式では、トークンを配る側を AllGather、結果を集める側を ReduceScatter という通信で行います。ノードの間の帯域はノードの中より細いので、この通信が層のレイテンシーを決めていました。
- **ねらい**: 2 つの通信をスイッチに任せ、同時に流して回線の行きと帰りの両方を使い、expert の計算とも重ねて、通信を待つ時間を減らすこと。
- **やったこと**: トークンを帯と呼ぶ小さな束に分け、配る係、計算する係、集める係のスレッドブロックが 1 つのカーネルの中で同時に動くようにしました。vLLM の MoE 層と差し替えて使えます。実験では 4 台のアクセラレータをそれぞれ 1 ノードに見立て、5 台目のアクセラレータでスイッチを真似ました。つなぎ方は RoCE で、スイッチへの 400 Gbps のリンクを 4 台で共有しています。
- **結果**: OLMoE-1B-7B の prefill を 4 つの expert 並列で動かすと、最初のトークンが出るまでのレイテンシーは、vLLM の既定のリング型の通信と比べて、アクセラレータ 1 台あたりの入力が合計 24K トークンのときに 20.2%、126K トークンのときに 33.1% 短くなりました。スループットは、同じ比較で 25.3% から 49.5% 上がりました。各層の出力は、既定の方式とのコサイン類似度が 1.0 と報告されています。decode と大きな MoE モデルでの評価はありません。

## カーネルと数値

### softmax と cross-entropy の丸めの不具合

softmax は、モデルの出力を足して 1 になる確率に直す計算で、cross-entropy はその確率から学習の誤差を出す計算です。勾配は、誤差を減らすために重みをどの向きにどれだけ動かすかを決める量です。bf16 は 16 ビット、fp32 は 32 ビットで数を表す形式で、ビット数が少ないほど丸めの誤差が大きくなります。蒸留は、大きなモデルを先生役の教師にして、生徒の小さなモデルにその答え方をまねさせる学習の方法です。KL は、教師と生徒が出す確率の分布がどれだけ違うかを表す値で、0 なら同じです。weight decay は、重みが大きくなりすぎないよう少しずつ小さくする工夫です。このプレプリントは、softmax と cross-entropy の標準の実装に残る丸めの不具合を、Google DeepMind の研究者が指摘して直したものです。

:::message
コメント: softmax は最大値を引いておけば安全だと思っていたので、その先に丸めの不具合が 2 つ残っているという指摘に驚きました。気になるのは 2 つ目の Softmax Cancellation です。教師と生徒の出力が近い蒸留では、本来 0 に近づくべき勾配が雑音の高さで止まります。bf16 で on-policy の蒸留や RL をするときに、気づかないまま効いているかもしれません。著者自身は、ここまで極端な状況は普通の大規模な学習では多くないと書いています。最後の訂正には、掲載したコードがマスクに使う負の無限大を含む入力で NaN を出す不具合があったと書かれているので、試すときは訂正後のコードを使います。
:::

![正解の候補と他の候補の出力の差が大きくなると、標準の実装では正解側の勾配が bf16 で約 5.5、fp32 で約 16.6 を境に 0 へ落ちることを示す図](https://arxiv.org/html/2610.31642v3/paper_fig1a_hard_cliff.png)
*出典: [A Fix for Softmax and Cross-Entropy](https://arxiv.org/html/2610.31642) の Figure 1 の a*

#### 参照元からの抜粋と要約

- **課題**: softmax と cross-entropy の標準の実装には、数の丸めによる 2 つの不具合がありました。1 つは Softmax Collapse で、モデルが強く確信すると正解側の勾配だけが 0 に丸められ、他の勾配とのつり合いが崩れます。図では、出力の差が bf16 で約 5.5、fp32 で約 16.6 を超えると、この丸めが起きています。もう 1 つは Softmax Cancellation で、教師と生徒が近いと勾配が 0 まで下がらず雑音が残ります。
- **ねらい**: 計算の途中で高い精度の型に変換せずに、丸めに強い softplus、expm1、log1p という関数だけで書き直すこと。
- **やったこと**: JAX で修正版を書きました。足し算の余りを当てる小さな課題で、bf16、fp32、fp64 と、最適化手法 Adam の小さな定数 ε の値をいくつか変えて標準の実装と比べています。教師の重みで始めた生徒の蒸留でも比べ、既存の対策の Zero-sum Projection と StableMax とも比べました。
- **結果**: 足し算の余りを当てる課題では、修正版は試したすべての精度と ε の設定でテストの正解率が 98.9% 以上になり、損失が急に跳ねる現象も消えました。weight decay を外した別の課題では、標準の実装の正解率が学習の途中で 61% から 23% に急に下がったのに対し、修正版は 85% まで上がりました。蒸留では、標準の実装が bf16 で生徒を教師からずらしたのに対し、修正版はすべての精度で KL を 0、正解率を 100% に保ちました。

### logsumexp のカーネル融合

logsumexp は、たくさんの数の指数の和の対数を、桁があふれないように出す計算です。言語モデルでは、語彙全体からトークンの確率を出すところで使われます。RLHF は、人の評価をもとに言語モデルを直す RL の一種です。確率的サーキットは確率を組み合わせた計算の図で、粒子フィルターはたくさんの候補から状態を推定する方法です。どちらも logsumexp を多く使います。カーネル融合は、いくつかの小さなカーネルを 1 つにまとめ、メモリへの読み書きと起動の回数を減らす工夫です。このプレプリントは、Aalto University と NVIDIA などの研究者が、logsumexp を 1 つのカーネルにまとめて速くしたものです。

:::message
コメント: logsumexp は、RL で語彙全体からトークンの対数確率を出すところに出てきます。V100 で調べた例では、PyTorch の torch.logsumexp が 9 個の小さなカーネルに分かれていて、これは知りませんでした。torch.compile がカーネルをまとめた場合よりも、さらに 1.8 倍から 2.1 倍速くなっています。RL の対数確率の計算に差し込んで、学習 1 ステップ全体がどれだけ縮むかを試したいです。
:::

![入力の大きさごとに、GPU と CPU での logsumexp の 1 回あたりの時間と誤差を、torch と FuseLSE と IntLSE で比べた図](https://arxiv.org/html/2610.33647v3/fig_microbenchmark.svg)
*出典: [Speeding up Log-Sum-Exp](https://arxiv.org/html/2610.33647) の Figure 3*

#### 参照元からの抜粋と要約

- **課題**: PyTorch の実装は GPU で 9 個のカーネルに分かれ、そのたびに GPU のメモリへの読み書きとカーネルの起動が起きていました。大きな入力では、同じ大きさの torch.sum より約 6 倍遅い状態でした。
- **ねらい**: 1 回の読み込みで済む 1 つのカーネル FuseLSE と、特殊な関数を速く計算する回路がない CPU 向けに、整数の計算で近似する IntLSE を作ること。
- **やったこと**: V100 の GPU と Xeon Gold 6134 の CPU で、1 回あたりのレイテンシーを入力の大きさを変えて測りました。V100、H100、H200、B300 では、torch.compile や JAX の XLA がカーネルをまとめた場合とも比べています。さらに、RLHF でトークンの確率を出す計算、確率的サーキットの推論、粒子フィルターの 3 つの使い道でも測りました。
- **結果**: V100 では torch.logsumexp と比べて、要素数 1,024 以下で約 10〜11 倍、8,192 以上で約 6 倍速くなりました。4 種類の GPU で、torch.compile や JAX の XLA がカーネルをまとめた場合と比べても 1.8〜2.1 倍速い結果です。CPU では、近似の誤差を許す IntLSE が FuseLSE より 3〜6 倍速く、粒子フィルターでは torch より 2.8〜5.2 倍速くなりました。IntLSE の誤差は広い入力の範囲で 0.2% 未満ですが、入力の範囲によっては CPU で torch より遅い場合もあります。コードは [GitHub](https://github.com/lingyunyao/fuselse) で公開されています。

## モデルの構造

### Merlin: 平均とばらつきで選ぶ線形 attention の記憶

attention は、文章のどのトークンに注目するかを決める計算で、注目する側のベクトルを query、注目される側を key と呼びます。KV キャッシュは、言語モデルが文章を作るときに、それまでに読んだトークンの key と value をとっておくメモリで、文章が長いほど大きくなります。線形 attention や Mamba のような状態空間モデルは、KV キャッシュの代わりに決まった大きさの状態を持つので、計算量とメモリが文脈の長さに比例するだけで済みます。その代わり、1 つの状態に全部を詰めるので、長い文脈では情報が落ちます。そこで、文脈を区間に分けて区間ごとに状態を持つ方法が出てきました。このプレプリントは、Princeton University の研究者が、どの区間の状態を読むかを key の平均とばらつきから決める Merlin を提案したものです。

:::message
コメント: 推論の基盤から見ると、決まった大きさの状態で済む構造はメモリの見積もりが変わる点が大事です。ただ、区間を増やせば保存する量も増えるので、どの区間を読むかの選び方が効いてきます。4 倍のメモリを使う比較対象を上回ったという結果は、状態の大きさとのトレードオフで効いてきそうです。試したのは 1.3B 以下の小さなモデルだけなので、大きなモデルでも同じ傾向になるかは気になります。
:::

![文脈を区間に分け、各区間の記憶と key の平均とばらつきを持ち、query がそれらから区間ごとの重みを決める Merlin の全体図](https://arxiv.org/html/2610.37645v1/gram_main_diagram_v2.png)
*出典: [Multi-State Linear Attention with Generalized Second-Order Routing](https://arxiv.org/html/2610.37645) の Figure 2*

#### 参照元からの抜粋と要約

- **課題**: 区間ごとに記憶を分ける方法では、区間の結果をまとめる重みを、位置か key の平均との近さだけで決めていました。query と key がどれだけ鋭く合うかという、ばらつきの情報は使われていませんでした。
- **ねらい**: 平均に加えてばらつきの情報も使い、区間の重みを決めること。
- **やったこと**: 区間を選ぶために、記憶の読み書きとは別の小さな key と query を作りました。各区間について、key の平均と、key の成分を組み合わせて掛けた値の平均を保存します。この 2 つから、query との合い方の平均とばらつきを求め、学習で決まる割合で混ぜて重みにしています。Gated DeltaNet の 1.3B と Mamba-2 の 780M を区間に分ける形に直し、長い文脈の評価で比べました。
- **結果**: RULER の検索と質問の課題で、Gated DeltaNet の平均点は 62.7 となり、key の平均だけで決める方法の 57.9 を上回りました。Mamba-2 では 76.2 となり、同じ方法の 71.2 と比べて 7.0% 高い結果です。LongBench では、同じ方法と比べて Gated DeltaNet で 13.5%、Mamba-2 で 12.0% 高くなりました。区間を短くして 4 倍のメモリを使う比較対象も上回っています。

### 拡散言語モデルの作り方

今の多くの言語モデルは、トークンを左から 1 つずつ出す自己回帰型で、n 個のトークンを出すのにモデルを n 回呼びます。拡散言語モデルは、全部を隠した文から始めて、何回かの書き直しで全部の位置を同時に埋めていく言語モデルです。長い出力は、ブロックに分けて順に作る方式が主流で、ブロックの中では書き直しを重ねて全部の位置を埋めます。ブロック単位の方式では、確定した前のブロックの KV キャッシュを使い回せます。perplexity は次のトークンの当てやすさの指標で、MAUVE は作った文の自然さの指標です。このプレプリントは、Cornell University の研究者が、拡散言語モデルを作る部品と、実際のモデルがそれをどう組み合わせているかを解説したもので、新しい実験ではなく、これまでの研究の整理です。

:::message
コメント: 推論の回数が書き直しの回数とブロックの数で決まるので、推論エンジンのバッチの組み方は今とは別の考え方になりそうです。SGLang が LLaDA 2.0 に対応したときの動きは、私が以前書いた「[SGLang で Diffusion LLM をサポート](https://zenn.dev/tosshi/articles/067d4c912c98d6)」で検証しました。Gemma Diffusion や Nemotron Diffusion のように大きな組織が数十億から数百億パラメータの規模で出してきたので、推論基盤でも一度は向き合う形式になりそうです。
:::

![自己回帰型は 1 回に 1 トークンを左から出し、拡散型は全部を隠した列から数回の書き直しで全位置を同時に埋めることを比べた図](https://arxiv.org/html/2610.33391v1/figures/ar-diffusion-comparison.png)
*出典: [How To Build A Modern Diffusion Language Model](https://arxiv.org/html/2610.33391) の Figure 1*

#### 参照元からの抜粋と要約

- **課題**: 自己回帰型は GPU の並列性を使い切れず、一度出したトークンを後から直すこともできません。
- **ねらい**: 隠した列から全体を同時に書き直していく拡散言語モデルについて、基本から最新の部品までを 1 本にまとめること。
- **やったこと**: トークンを隠して当てる基本の拡散から始めて、長さを変えられるブロック単位の生成、確定したトークンを戻して直す再マスク、速く出すための選び方、出力の誘導、重い部分を 1 回だけ動かす構造、学習の方法を順に説明しています。LLaDA、Gemma Diffusion、Nemotron Diffusion がどの部品を組み合わせているかも表で比べています。
- **結果**: 拡散言語モデルは 2 年で、研究の試作から商用のモデルまで進みました。LLaDA は 8B、Nemotron Diffusion は 35B まで大きくなっています。紹介されている先行研究では、商用の Mercury が普通の GPU でユーザー 1 人あたり毎秒 1,200 トークンを超えると報告されています。別の先行研究では、再マスクを使うと MAUVE が 1,024 回の書き直しで 0.40、4,096 回で 0.66 になり、自己回帰型の 0.76 に近づきました。一方で、perplexity で同じ値に届くまでに自己回帰型の 16 倍の計算が要ったという報告も引用されています。

### EmbeddingGemma 2: 文、画像、音声の共通の空間

埋め込みモデルは、文や画像を、意味が近いほど近くなる数の並びに直すモデルです。RAG は、質問に関係する資料を埋め込みで検索して、それを手がかりに言語モデルに答えさせる仕組みです。これまで音声や画像を検索するには、文字に起こしたり説明文を付けたりしてから文の埋め込みを作ることが多くありました。量子化は、数を少ないビット数で表してメモリを減らす方法で、int4 は 4 ビットの整数です。このプレプリントは、Google が、文、画像、音声、動画を 1 つの空間に置く 7 億 4,400 万パラメータの埋め込みモデル EmbeddingGemma 2 を発表したものです。

:::message
コメント: 文、画像、音声、動画を 1 つの埋め込みモデルで同じ空間に置けるのは、RAG の基盤から見ると大きいです。文字起こしや説明文を付けるための別のモデルが要らなくなります。文の部分を int4 にし、画像と音声の部分にも別の量子化をかけた版があり、Pixel 11 Pro の上で全部の入力を扱う構成のピークメモリは 567MB でした。端末の上で動かす使い方も考えられます。英語の文の評価では前の版から少し下がっている点は覚えておきます。
:::

![文、画像、動画、音声と、それらの組み合わせを 1 つの意味のそろったベクトル空間に置く EmbeddingGemma 2 の概念図](https://arxiv.org/html/2610.37364v1/diagram.png)
*出典: [EmbeddingGemma 2](https://arxiv.org/html/2610.37364) の Figure 1*

#### 参照元からの抜粋と要約

- **課題**: 文の埋め込みモデルで音声や画像を扱うには、文字起こしや説明文を付ける別の道具が必要で、細かい情報も落ちます。画像と文を扱う既存のモデルは混ざった入力が苦手で、大きな言語モデルを使う埋め込みは重すぎて速く動かせません。
- **ねらい**: 小さいのに、どの組み合わせの入力でも 1 つの空間に置ける埋め込みモデルを作ること。
- **やったこと**: Gemma 4 を土台に、画像と音声の入口を付けた 7 億 4,400 万パラメータのモデルを作りました。このうち文の部分は 2 億 7,100 万パラメータです。文だけの学習から始めて、画像や音声を混ぜた学習へ 3 段階で進め、Gemini Embedding 2 から蒸留しています。学習に使ったのは約 2 兆 9,000 億トークンです。
- **結果**: コードの評価である MTEB のコード部門では、文の部分で、約 28 倍大きい首位のモデルとの差が 2 点以内でした。画像と動画と文書の画像の評価では、10 億パラメータ未満のモデルの中で 2 つの集計の両方で最高でした。音声でも、10 億パラメータ未満のモデルの中で複数の課題で最高でした。ただし、すべての評価で首位というわけではありません。

## 理論

### key と query の似方から見た KV キャッシュ圧縮の限界

KV キャッシュを小さくする方法には、残すトークンを選んで間引く方法、数を少ないビットで表す量子化などがあります。どこまで小さくできるかには理論上の下限があり、これまでの下限は query と key がぴったり重なる最悪の場合を使って証明されていました。コサイン類似度は、2 つのベクトルの向きがどれだけそろっているかを表す値で、1 なら同じ向き、0 なら直角です。実際のモデルでは、key と query のコサイン類似度が小さい範囲に集まることが知られています。このプレプリントは、MIT と EPFL の研究者が、この測った事実を前提に入れて下限を出し直した理論の研究です。

:::message
コメント: query を見る前に残す key を選ぶという条件では、測った範囲の多くで、一様にランダムに間引くだけで理論上ほぼ最適になると示されています。KV キャッシュを捨てる方式を比べるとき、一様な間引きを強い比較対象として入れるべきだと感じました。ただし、生成の品質で一様な間引きが常に一番という意味ではありません。attention の重みを見て残すものを選ぶ SnapKV や H2O、量子化は、この下限の対象の外です。
:::

![Llama 3.1、Qwen3、Ministral 3 の 8B モデルで測った key と query の類似度の範囲を、一様な間引きが最適な領域と重要度で選ぶべき領域の図に重ねた散布図](https://arxiv.org/html/2610.35020v1/ab_p0_1_scatter.svg)
*出典: [Attention under Bounded Key–Query Similarity](https://arxiv.org/html/2610.35020) の Figure 3*

#### 参照元からの抜粋と要約

- **課題**: KV キャッシュの圧縮の理論上の下限は、query と key が強く似る最悪の場合を使って証明されていました。実際のモデルの値を当てはめても、どこまでメモリを減らせるかの役に立つ目安が得られませんでした。
- **ねらい**: key と query のコサイン類似度がある小さな範囲に収まるという、測った事実を前提に入れて、圧縮の上限と下限を出し直すこと。
- **やったこと**: 類似度の範囲によって、一様に間引くのが最適な領域と、重要なものを選んで残すのが最適な領域に分けて、それぞれでほぼ一致する上限と下限を証明しました。Llama 3.1、Qwen3、Ministral 3 の 8B モデルで、LongBench v2、InfiniteBench、SCBench の入力を 8K から 256K の長さで与え、4 つの層で類似度の範囲を測りました。
- **結果**: 測った範囲の多くは、一様な間引きが最適な領域の中か、その近くに入りました。下限の証明に使った難しい例の形も、実際のモデルで見える key と query の偏り方と性質が似ていました。

### Muon の更新が Hessian に合う理由

行列は、数を縦と横に並べた表で、対角は表の左上から右下へ並ぶ位置です。Muon は、勾配の行列を、どの向きにも同じ強さで伸びる形にそろえる直交化という操作をしてから重みを更新する最適化手法で、大きなモデルの学習で使われ始めています。Hessian は、重みを少し動かしたときに誤差の増え方がどう変わるかを表す行列で、ニューラルネットワークでは対角のブロックに値が集まる形をしていることが知られていました。自己外積は、ベクトルや行列をそれ自身と掛け合わせて作る行列です。このプレプリントは、Dartmouth College と Meta の研究者が、Muon の更新が Hessian の形に合う理由の一部を、初期化の時点で証明したものです。

:::message
コメント: 上の torchtitan の FlexShard のように、分散の仕方まで Muon に合わせる動きが出ています。行列を丸ごと 1 つのランクに持たせるなど、基盤側の作りを変えるだけの価値があるのかを考えるには、なぜ効くのかの理解が要ります。証明は単純な 4 つのモデルの初期化の時点に限られていて、学習が進んだ後も同じ形が続くかは、これからの課題です。
:::

![初期化時の Transformer の重み行列で、Hessian は対角のブロックに、momentum の自己外積は対角に値が集中していることを並べたヒートマップ](https://arxiv.org/html/2610.28975v1/fig1_9263.png)
*出典: [How Does Orthogonalization Adapt to the Neural Network Hessian Structure?](https://arxiv.org/html/2610.28975) の Figure 1*

#### 参照元からの抜粋と要約

- **課題**: Muon は多くの課題で AdamW を上回りますが、Muon の更新がなぜ Hessian の形に合うのかは説明されていませんでした。
- **ねらい**: Muon が暗に使っている前処理が Hessian の形に合うのは、勾配の自己外積の期待値が対角に集まるからだと、数式で示すこと。
- **やったこと**: 行列分解、深い線形ネットワーク、2 層の ReLU ネットワーク、1 層の線形 attention の 4 つのモデルで、ランダムな初期化の時点の勾配の自己外積の期待値を計算しました。隠れ層の幅を広げたときに、対角と対角以外の値がどの速さで大きくなるかを証明しています。Qwen3.5-0.8B-Base、Granite-4.0-1B-Base、Llama-3.2-1B でも、ランダムな初期化を 25 回、FineWeb-Edu の 64 個の入力列で確かめました。
- **結果**: 4 つのモデルのすべてで、幅が広いほど対角の値が対角以外の値を引き離すことが、計算と実験の両方で確かめられました。線形 attention の Q、K、V では、この期待値の対角以外の値がちょうど 0 になります。

### スケーリング則の当てはめの曖昧さ

スケーリング則は、モデルの大きさや計算量と性能の関係を表す式で、どの大きさのモデルにどれだけ計算を使うかの判断に使われます。小さなモデルをいくつか学習して点を取り、べき乗の式を当てはめて、もっと大きな規模の性能を予測します。測った範囲の外側を式で予測することを外挿と呼びます。Chinchilla の方法 3 は、この当てはめで広く使われてきたやり方です。このプレプリントは、University of Cambridge と Google DeepMind の研究者が、当てはめの曖昧さを保証付きの探索で洗い出したものです。

:::message
コメント: 人工的に作った合成データの例ですが、誤差がほぼ同じ 2 つの当てはめが、300 倍先の規模で必要な計算量について 74.6 倍違う答えを出すという結果には、ぞっとしました。実データの 4 つの系列でも、保証は付かない探索ですが、誤差が同じ程度の当てはめの間で計算効率の予測が 14 倍から 146 倍違う例が示されています。1 本の線だけで計算の予算を決める危うさは伝わります。スケーリング則の数字を引用するときは、誤差の近い当てはめが示す予測の幅も一緒に見たいです。ただし、保証付きの探索そのものにも時間がかかるので、その見積もりも要ります。
:::

![合成データで、当てはめの誤差がほぼ同じ 2 本の線が、学習した範囲の先で大きく離れていく様子と、最適から 1% 以内の当てはめ全部の予測が入る帯を示す図](https://arxiv.org/html/2610.34514v1/scaling_law_nonidentifiability.svg)
*出典: [Ambiguous Fits](https://arxiv.org/html/2610.34514) の Figure 1*

#### 参照元からの抜粋と要約

- **課題**: スケーリング則の最後の段階である、べき乗の式をデータに当てはめる作業は、決まった初期値から局所的に探すやり方に頼っていました。一番よい答えに近い保証はなく、誤差がほぼ同じで外挿が大きく違う当てはめがあることも見過ごされていました。
- **ねらい**: 決めた式と探索の範囲の中で、誤差が最良から指定した幅以内であることを保証付きで見つけ、誤差の近い当てはめの集まりと、その予測の幅も求めること。
- **やったこと**: 式の変数を、範囲ごとに損失の上限と下限を安く計算できる形に直しました。その上で、範囲を分けながら見込みのない範囲を捨てていく分枝限定法の手順を 3 つ作りました。合成データと、文献から取った実際のスケーリングの 4 つの系列で、Chinchilla の方法 3 と比べています。
- **結果**: 実際の 4 つの系列で、Chinchilla の方法 3 の当てはめは、一番小さい損失を 2% から 180% 上回っていました。初期値の格子を細かくしても、よくなるとは限りませんでした。合成データでは、誤差が最適から 1% 以内と保証された 2 つの当てはめが、学習した範囲の 300 倍の規模で目標の損失に届く計算量を 74.6 倍違って予測しました。一方、実データの 5 つの変数の式では、予測の幅を厳密に求める計算が今の計算予算に収まらず、局所的な探索で代用しています。この幅は、将来の実測値が入ることを保証するものではありません。
