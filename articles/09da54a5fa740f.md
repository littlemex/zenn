## はじめに

:::message
この記事は、仕組みの理解を助けるために書いたものです。実際に組む前には、専門家のレビューを受け、自分の環境で入念に検証してください。内容に誤りを見つけたら、コメントで教えていただけるとうれしいです。

この記事では、一例として Microsoft Entra ID を使って整理します。Amazon Cognito などほかのサービスでは、それぞれ違いがあるので、各サービスの資料を確かめてください。この記事は概念的な整理であり、個々のサービスで何ができて何ができないかを確約するものではありません。
:::

AI エージェントに MCP で SaaS をつなぐと、利用者がそれぞれ自分の鍵を AI エージェントに登録しがちです。MCP サーバーは、MCP で呼べるツールを公開するサーバーです。Amazon Bedrock AgentCore は、AI エージェントの入口や鍵を AWS 側で預かるサービスの集まりで、この記事では AgentCore と書きます。この記事では、社内の MCP サーバーの入口と SaaS の鍵を AgentCore に集める形を、図を中心に見ていきます。

この記事では、社員が Devin、Claude Code、Kiro のような Coding Agent を使う場面を想定します。この記事で AI エージェントと呼ぶのは、MCP で SaaS につなぐ側の Coding Agent です。AI エージェントが Entra ID からトークンを取り、更新しながら Gateway に見せ続けられるなら、ここで見る構成はどの AI エージェントにも当てはまります。それぞれの AI エージェントの設定方法は、AI エージェントの提供元の資料で確かめてください。内容は 2026 年 10 月 17 日時点の公開情報にもとづいています。

## 2 種類の認証情報

この記事には、認証情報が 2 種類出てきます。1 つ目は SaaS の鍵で、GitHub などの SaaS が発行する API キーやアクセストークンです。どちらも、SaaS が呼び出しを受け付けるときに確かめる文字列です。2 つ目は Gateway 用のアクセストークンで、利用者が会社の Microsoft Entra ID にサインインすると発行されます。Microsoft Entra ID は、社員のサインインを受け持つ Microsoft のサービスです。

この記事が目指すのは、SaaS の鍵を利用者の手元からなくし、ふだんは Gateway 用のアクセストークンだけで SaaS を使える形です。Gateway は、このあと出てくる AgentCore Gateway という入口のことです。OAuth は、アプリに API を使う権限を渡すための決まりです。利用者ごとの OAuth を使う SaaS では、SaaS のトークンが有効なあいだは、最初の 1 回だけ SaaS の同意画面を通ります。

## 問題設定

![利用者ごとに自分の鍵が AI エージェントに登録され、SaaS へ直接つながっている図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/09da54a5fa740f/zenn/articles/09da54a5fa740f/now.png)

問題は、社員が Coding Agent に、会社の管理の外で勝手に MCP サーバーをつないで使っていることです。社員は SaaS で自分の鍵を発行し、自分の AI エージェントに登録します。**鍵が利用者の手元に散らばるほど、会社が止めたり入れ替えたりできない場所が増えます**。退職や漏えいのとき、会社がすぐに鍵を止めるのは難しくなります。鍵の入れ替えも利用者まかせになります。どの操作が誰の鍵で行われたかを、会社として一元的に確かめるのも難しくなります。

## 目指す形

![AI エージェントは SaaS の鍵を持たず、入口の Gateway を通って SaaS を使う図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/09da54a5fa740f/zenn/articles/09da54a5fa740f/target.png)

目指すのは、AI エージェントが SaaS の鍵を持たない形です。AI エージェントの MCP の接続先を、AgentCore Gateway の 1 本にそろえます。SaaS の鍵は、AgentCore Identity という保管庫に預けます。Gateway は送り先ごとに決めた認証方式で、Identity に預けた鍵を使って送り先を呼びます。送り先は、SaaS が公開する MCP サーバーなどです。利用者は Entra ID でサインインし、Gateway 用のアクセストークンだけを持ちます。

こうすると、Gateway を通る呼び出しでは、SaaS の鍵の管理を Identity に集められます。

## 通行証のたとえ: 誰が何をするか

![ビルの受付の 7 つの仕事と、それを受け持つサービスの対応の図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/09da54a5fa740f/zenn/articles/09da54a5fa740f/roles.png)

この先の認証と認可の説明で、誰が何をしているかを整理するために、会社のビルにたとえてみます。社員はふだん社員証でビルに入れます。ただし機密エリアには、許可を受けた人だけが通行証を持って入れます。

このビルの社員は、Devin や Claude Code のような AI エージェントを、自分の代理人として使っています。社員は機密エリアの用事を代理人に頼み、代理人が社員の代わりに機密エリアへ行きます。代理人が入るには、その代理人用の通行証が要ります。通行証には、誰の代理か、どの代理人か、行き先はどこかが書かれています。1 人の社員が 3 つの AI エージェントを使うなら、通行証も AI エージェントごとに別々に出ます。

社員証は社員本人が使うもので、代理人には渡しません。代理人が持ち歩くのは通行証だけです。たとえと実体の対応は次のとおりです。

| たとえ | 実体 |
|---|---|
| 社員 | 利用者 |
| 社員証 | 利用者の Entra ID へのサインイン |
| 代理人 | Devin などの AI エージェント |
| 通行証 | Gateway 用のアクセストークン |
| 機密エリアの受付 | Gateway |
| 発行所 | Entra ID の認可サーバー |

認可サーバーは、アクセストークンを発行するサーバーです。

発行所は、代理人に通行証を出す前に 2 つの名簿を確かめます。1 つ目は「社員の名簿」で、代理を頼んだ本人が社員かどうかを、社員証で確かめます。2 つ目は「アプリの名簿」で、代理人として来た AI エージェントが、会社の認めたものかどうかを確かめます。社員がサインインできても、代理人の AI エージェントがアプリの名簿に載っていなければ、通行証は出ません。

| 名簿 | 確かめること | 実体 | 載せる方法 |
|---|---|---|---|
| 社員の名簿 | 代理を頼んだ本人は社員か | Entra ID の利用者の一覧 | 会社の管理者が登録する |
| アプリの名簿 | 代理人として来た AI エージェントは会社が認めたものか | Entra ID のアプリ登録 | 管理者が前もって登録する。AI エージェントが自分で登録を依頼する方式もあるが、受け付けるかは認可サーバーによる |

通行証の出し方の細かな仕組みは、認可サーバーと AI エージェントの組み合わせで変わります。たとえば、アプリの名簿に載る方法には、管理者が前もって登録する方法と、AI エージェントが自分で登録を頼む方法があります。認可サーバーが受け付ける方法と、AI エージェントが使える方法が合わないと、AI エージェントは名簿に載れず、通行証をもらう手前で止まります。通行証の宛先の書き方や、期限が来たときのもらい直し方も、同じように組み合わせ次第で合わないことがあります。どこで止まりやすいかと、その直し方は、あとの節で順に見ます。

機密エリアの受付で通行証を照合するのは Gateway です。Gateway の先で呼べる 1 つ 1 つの機能を、MCP ではツールと呼びます。機密エリアの中で入ってよい部屋、つまり Gateway で呼んでよいツールを決めるのは Policy in AgentCore です。金庫、つまり SaaS の鍵の保管庫は Identity です。出入りの記録は、AWS への操作を記録する AWS CloudTrail が受け持ちます。以下では、たとえの言葉には実体の名前を添えて書きます。

たとえの言葉のまま、実際の部品のつながりと流れを 1 枚にすると次のようになります。

![Entra ID の発行所と 2 つの名簿、受付の Gateway、Policy、金庫の Identity、SaaS、記録帳の CloudTrail のつながりと、社員がサインインしてから記録までの 8 段の流れの図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/09da54a5fa740f/zenn/articles/09da54a5fa740f/analogy-arch.png)

まず社員が社員証で Entra ID にサインインし、代理人の AI エージェントが自分用の通行証をもらいます。発行所は、社員の名簿とアプリの名簿の両方を確かめてから通行証を出します。AI エージェントは通行証を Gateway に見せて呼び出します。Gateway は Policy で入ってよい部屋かを判定し、Identity から金庫の鍵を受け取ります。Gateway はその鍵で SaaS の MCP サーバーを呼び、CloudTrail が呼び出しを記録します。以降の節は、この 1 枚の各部分を詳しく見ていきます。

## AI エージェントの条件: トークンを取って見せ続ける

![AI エージェントが通行証をもらって Gateway に見せ続ける 6 段の流れと、止まりやすい 3 つの場所の図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/09da54a5fa740f/zenn/articles/09da54a5fa740f/tooljob.png)

この形が成り立つには、代理人の AI エージェントが通行証、つまり Gateway 用のアクセストークンをもらい、受付、つまり Gateway に見せ続けられないといけません。AI エージェントは利用者を Entra ID のサインイン画面に案内し、発行されたトークンを受け取ります。Gateway を呼ぶたびにトークンを見せ、期限が来る前にもらい直します。

止まりやすい場所は 3 つあります。A は、AI エージェントが自分を Entra ID のアプリ登録に載せられない場所です。B は、トークンに書かれた宛先が Gateway の照合の条件と合わない場所です。C は、期限の前にトークンを更新できない場所です。どれか 1 つでも止まると、利用者は Gateway を通れず、SaaS を使えません。

## 実際の決まり

たとえの各場面は、OAuth の決まりの組み合わせで実現されています。MCP の認可の全体は「[MCP の認可の仕様（2026-07-28 版）](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)」に書かれています。次の表は、この版の仕様が参照する決まりを、たとえの場面ごとに並べたものです。表で案内と呼ぶものは、サーバーが自分の情報を置く決まった URL で、英語で metadata と呼ばれます。Entra ID とお使いの AI エージェントがどの決まりに対応するかは、それぞれの提供元の資料で確かめてください。

| たとえ | 実際にやること | 決まり |
|---|---|---|
| 受付の案内を読む | AI エージェントは Gateway の案内から、使う認可サーバーを見つける | [RFC 9728](https://www.rfc-editor.org/rfc/rfc9728) |
| 発行所の案内を読む | AI エージェントは認可サーバーの案内から、サインインとトークンの窓口を調べる | [RFC 8414](https://www.rfc-editor.org/rfc/rfc8414)、[OpenID Connect Discovery](https://openid.net/specs/openid-connect-discovery-1_0.html) |
| アプリの名簿に載る | AI エージェントが client ID を手に入れる。方法は事前登録、CIMD、DCR の 3 つ | [CIMD](https://datatracker.ietf.org/doc/draft-ietf-oauth-client-id-metadata-document/)、[RFC 7591](https://www.rfc-editor.org/rfc/rfc7591) |
| 社員証でサインインして通行証をもらう | サインイン後に受け取る一時的な番号、つまり認可コードを、アクセストークンに引き換える | [OAuth 2.1](https://datatracker.ietf.org/doc/draft-ietf-oauth-v2-1/)、[RFC 7636](https://www.rfc-editor.org/rfc/rfc7636) |
| 行き先を伝える | トークンを使う先を、認可サーバーに伝える | [RFC 8707](https://www.rfc-editor.org/rfc/rfc8707) |
| 通行証を見せる | 呼び出しのヘッダーにトークンを付ける | [RFC 6750](https://www.rfc-editor.org/rfc/rfc6750) |
| 期限の前にもらい直す | リフレッシュトークンという別の認証情報が出ている場合は、それで新しいトークンをもらう | [OAuth 2.1](https://datatracker.ietf.org/doc/draft-ietf-oauth-v2-1/) |

client ID は、認可サーバーがアプリを見分けるための番号です。CIMD は、英語で Client ID Metadata Documents の略です。AI エージェントの情報を置いた URL を client ID として使う方式で、決まりはまだ草案の段階です。DCR は、英語で Dynamic Client Registration の略です。AI エージェントが認可サーバーに登録を依頼する方式で、RFC 7591 で決まっています。MCP の仕様の [2026-07-28 版の変更点](https://modelcontextprotocol.io/specification/2026-07-28/changelog)で、DCR は非推奨になりました。置き換え先は CIMD です。CIMD に対応しない認可サーバーのために、DCR は互換用に残っています。Entra ID とお使いの AI エージェントがどの方式に対応するかは、それぞれの提供元の資料で確かめてください。

## 部品の組み合わせ

![どの AI エージェントも Gateway につなぎ、Gateway が Identity から鍵を受け取って SaaS を呼ぶ推奨構成の図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/09da54a5fa740f/zenn/articles/09da54a5fa740f/arch.png)

推奨する構成では、どの AI エージェントも MCP の接続先を Gateway だけにします。Gateway には、受け付けるトークンの条件を設定します。Entra ID のトークンで受け付ける場合、発行元は Entra ID の発見用の URL として設定します。そのうえで、宛先、アプリ、権限のうち確かめたい項目を[受け付け時の確認](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/inbound-jwt-authorizer.html)に入れます。

Gateway で呼べるツールは、[Policy in AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy.html) を設定すると絞れます。Policy は、Cedar という言語で規則を書く仕組みです。規則には、利用者のトークンに入った部署や権限などの項目を条件として使えます。例は公式サンプル「[02-policy](https://github.com/awslabs/agentcore-samples/tree/abab3d8beb684c79fc827a95a2d015e44e76dbbc/01-features/07-centralize-and-govern-your-ai-infrastructure/02-policy)」にあります。SaaS を呼ぶときの鍵の使い方は、Gateway の送り先ごとに[認証方式](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-outbound-auth.html)を選び、Identity に登録した鍵を指定します。

GitHub は、GitHub が公開している [MCP サーバー](https://github.com/github/github-mcp-server/blob/main/docs/remote-server.md)を Gateway の送り先にする形から試すのが手軽です。利用者ごとの OAuth で送り先にする手順は、AWS の公式サンプル「[authorization-code-flow の github](https://github.com/awslabs/agentcore-samples/tree/abab3d8beb684c79fc827a95a2d015e44e76dbbc/01-features/07-centralize-and-govern-your-ai-infrastructure/01-gateway/01-attach-targets/mcp/mcp-servers/01-configure-auth/authorization-code-flow/github)」にあります。Entra ID で受け付け、利用者ごとの OAuth で送り先を呼ぶまでの全体は、公式サンプル「[05-entraid-3lo-gateway](https://github.com/awslabs/agentcore-samples/tree/abab3d8beb684c79fc827a95a2d015e44e76dbbc/06-workshops/02-AgentCore-gateway/04-integration/05-entraid-3lo-gateway)」で動かせます。

## 1 回の呼び出し

![Entra ID でサインインしてから、データイベントを有効にした場合に CloudTrail が呼び出しを記録するまでの 6 段の流れの図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/09da54a5fa740f/zenn/articles/09da54a5fa740f/flow.png)

最初に利用者が Entra ID でサインインし、AI エージェントが Gateway 用のアクセストークンを受け取ります。サインインは毎回ではなく、トークンが使えるあいだは省けます。そのあとの呼び出しは、次の順に進みます。AI エージェントがトークンを付けて Gateway を呼びます。Gateway はトークンを確かめ、Policy を設定していれば呼んでよいツールかを判定します。Gateway は Identity に預けた鍵を使って送り先を呼び、結果を返します。設定していれば、この呼び出しを CloudTrail が記録します。

## 記録: CloudTrail のデータイベント

データイベントは、個々の呼び出しを 1 件ずつ記録する種類のログです。[CloudTrail のデータイベント](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/enabling-cloudtrail-data-event-logging.html)を有効にすると、対象の Gateway への呼び出しを記録できます。データイベントは明示的に有効にする必要があり、[料金](https://aws.amazon.com/cloudtrail/pricing/)がかかります。設定の例は、公式サンプル「[gateway-observability](https://github.com/awslabs/agentcore-samples/tree/abab3d8beb684c79fc827a95a2d015e44e76dbbc/01-features/07-centralize-and-govern-your-ai-infrastructure/01-gateway/04-advanced-concepts/gateway-observability)」にあります。記録に含まれる項目は CloudTrail の資料で確かめてください。記録されるのは Gateway への呼び出しなので、SaaS の中で何が起きたかは SaaS 側の記録で確かめます。

## 鍵の登録の単位

![社内利用なら SaaS ごとに 1 つ、他社に提供するなら会社ごとに分ける場合がある、という比較の図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/09da54a5fa740f/zenn/articles/09da54a5fa740f/cred.png)

Identity には、SaaS への接続の設定を credential provider として登録します。OAuth の場合、credential provider が持つのは SaaS に作った OAuth アプリの設定です。OAuth アプリは、SaaS から許可をもらうために SaaS に登録するアプリの設定です。利用者ごとのトークンは、Identity の中の金庫である [token vault](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/key-features-and-benefits.html) が保管します。たとえば 10 人が同じ OAuth アプリに同意しても、credential provider は 1 つで、トークンは 10 人分が別々に保管されます。

社内で使うなら、まずは SaaS ごとに 1 つから始められます。本番と検証を分ける場合や、権限の違う鍵を分ける場合は、その数だけ作ります。この記事が想定するのは、この社内で使う場合です。一方、自社が SaaS を提供する企業で、顧客企業ごとの区画、つまりテナントごとに別の OAuth アプリや鍵が要るなら、テナントごとに credential provider を作る必要があるかもしれません。作れる数には[上限](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/bedrock-agentcore-limits.html)があります。2026 年 10 月 17 日時点の上限は、1 アカウント 1 リージョンあたり種類ごとに 50 個です。上限は申請で増やせます。

## 鍵の入れ替えと停止

![利用者ごとの鍵は同意から取り消しまで、共有の API キーは発行から無効化までの 4 段の図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/09da54a5fa740f/zenn/articles/09da54a5fa740f/rotation.png)

Identity は鍵を預かって渡す役目です。鍵の止め方と入れ替え方は、Identity だけでは完結しないので、SaaS ごとに手順を決めます。

OAuth に対応する SaaS では、会社が承認した OAuth アプリを使います。利用者は最初に SaaS の同意画面で同意し、得られたトークンを Identity が預かります。本人の権限で操作されるので、SaaS 側の記録で本人を見分けやすくなります。退職のときは、Entra ID で利用者を止めることに加えて、SaaS 側の同意やトークンも取り消します。同意の画面を利用者に出す窓口は、公式サンプル「[consent portal](https://github.com/awslabs/agentcore-samples/tree/abab3d8beb684c79fc827a95a2d015e44e76dbbc/01-features/05-authenticate-and-authorize/07-consent-portal-auth-code-flow-targets)」で試せます。

API キーしか使えない SaaS では、会社で発行した鍵を Identity に預けます。AWS Secrets Manager は、鍵を預けて取り出す AWS のサービスです。API キーの credential provider は、[Secrets Manager に置いた鍵](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/resource-providers.html)を使えます。Secrets Manager の[入れ替えの仕組み](https://docs.aws.amazon.com/secretsmanager/latest/userguide/rotating-secrets.html)で、入れ替えを定期的に動かせます。ただし、SaaS で新しい鍵を発行し、古い鍵を無効にする処理は、SaaS ごとに作る必要があります。

## 直接の接続: 抜け道の狭め方

![AI エージェントが Gateway を通らず個人の鍵で SaaS に直接つなぐ抜け道と、AI エージェント側と SaaS 側の狭め方の図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/09da54a5fa740f/zenn/articles/09da54a5fa740f/guard.png)

Gateway を用意しても、利用者が個人の鍵で SaaS に直接つなげる道が残ると、鍵は 1 か所にまとまりません。管理の外でつないだ MCP サーバーが AI エージェントにとってなぜ危ないかは、「[コーディングエージェントとプロンプトインジェクション](https://zenn.dev/tosshi/articles/0f467b2807e1fc)」も参考にしてください。AI エージェント側では、管理者が MCP の接続先を Gateway だけに絞れるかを、提供元に確かめます。個人がその設定を変えられないかも確かめます。たとえば Kiro の企業向けの機能では、管理者が許可する MCP サーバーの一覧を用意できます。[Kiro の MCP の管理の資料](https://kiro.dev/docs/enterprise/governance/mcp/)によると、その設定を使う Kiro は、一覧にある MCP サーバーにだけつなげます。一覧にはリモートの MCP サーバーの URL も書けるので、Gateway の URL だけを載せれば、接続先を Gateway に絞れます。[Kiro のブログ](https://kiro.dev/blog/enterprise-governance-mcp-and-models/)では、一覧から外れた MCP サーバーは止められ、利用者が追加し直すこともできないと説明されています。ただし、この制限が効くサインインの方法には条件があり、端末の管理者権限を持つ利用者は回避できる場合があると資料に書かれています。対象の版と条件は、Kiro の資料で確かめてください。SaaS 側では、個人で発行した鍵を制限します。GitHub なら、組織の設定で[個人用アクセストークンからの利用を制限](https://docs.github.com/en/organizations/managing-programmatic-access-to-your-organization/setting-a-personal-access-token-policy-for-your-organization)できます。

利用者の端末で動く AI エージェントでは、端末のコマンドから直接つなぐ道を、AI エージェントの設定だけでは閉じきれないことがあります。その場合も、個人の鍵の制限は SaaS 側で行います。端末側の制御は、社内の端末管理の方針に従います。

## Agent Registry: 任意の社内の案内板

![Agent Registry にレコードを登録して承認し、利用者が検索して見つけた MCP サーバーを Gateway を通して呼ぶ図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/09da54a5fa740f/zenn/articles/09da54a5fa740f/registry.png)

[AWS Agent Registry](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/registry.html) は、承認した MCP サーバーやエージェント、スキルを社内で探せるようにする案内板です。ひとことで言えば、社員の AI エージェントが使ってよい MCP サーバーと、その先にある SaaS などの一覧です。ここまでの構成に Registry は必須ではありません。使ってよい MCP サーバーを全社で検索できるようにしたいときに足します。

管理者が Gateway につないだ MCP サーバーなどをレコードとして登録すると、レコードは[下書き、承認待ち、承認済みと進みます](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/registry-record-lifecycle.html)。承認済みのレコードだけが検索に出ます。承認待ちになったことは、出来事を別の仕組みに知らせる Amazon EventBridge で通知できます。Registry は、登録した MCP サーバーの URL から中身を[取り込めます](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/registry-sync-records.html)。その MCP サーバーが OAuth で守られているなら、取り込みに Identity の credential provider を使います。取り込みの例は、公式サンプル「[registry-synchronize-mcpserver](https://github.com/awslabs/agentcore-samples/tree/abab3d8beb684c79fc827a95a2d015e44e76dbbc/01-features/07-centralize-and-govern-your-ai-infrastructure/03-registry/03-advanced/registry-synchronize-mcpserver)」にあります。

Registry 自身も [MCP の窓口](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/registry.html)を持ちますが、それは案内板の中を探すためのものです。Registry は SaaS の鍵を預からず、SaaS への呼び出しも中継しません。利用者は Registry で使える MCP サーバーを見つけ、実際の呼び出しは Gateway を通します。

## つながらないときの切り分け

![止まった場所から、足りないものと直し方を 3 行でたどる図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/09da54a5fa740f/zenn/articles/09da54a5fa740f/triage.png)

最初に確かめたいのは、お使いの AI エージェントが Entra ID のトークンを取り、更新しながら Gateway を呼べるかです。ここが通らないと、この構成は成り立ちません。止まったときは、止まった場所を手がかりに調べ始めます。症状は調べ始める場所の目安で、原因を決めつけるものではありません。エラーの表示とログで、実際に止まった処理を確かめます。

サインイン画面が出ないなら、まず A を調べます。401 は、認証が通らなかったことを表す応答の番号です。サインインできたのに Gateway が 401 を返すなら、トークンの有無と期限を確かめたうえで B を調べます。最初は動くのにトークンの期限のころに止まるなら、C を調べます。A には直し方が 2 つあり、次の 2 節で接続図とともに見ます。B と C は、そのあとで要点だけ触れます。

## A の直し方 1: Entra ID にアプリを前もって登録する

![直す前は AI エージェントが自分を Entra ID のアプリ登録に載せようとして止まり、直した後は管理者が載せた client ID でサインインする接続図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/09da54a5fa740f/zenn/articles/09da54a5fa740f/wire-a1.png)

A の 1 つ目の直し方は、事前登録です。A は、AI エージェントが自分を Entra ID のアプリ登録に載せられずに止まる場合です。Entra ID がどの登録方式を受け付けるかは、Microsoft の資料で確かめてください。AI エージェントに client ID を入れる欄があるなら、いちばん簡単なのは事前登録です。管理者が AI エージェント用のアプリを Entra ID に登録し、もらった client ID を AI エージェントに設定します。

あわせて、Gateway 用の権限を公開するアプリを決めます。AI エージェントのアプリと同じにしても、分けても構いません。公式サンプルの [05-entraid-3lo-gateway](https://github.com/awslabs/agentcore-samples/tree/abab3d8beb684c79fc827a95a2d015e44e76dbbc/06-workshops/02-AgentCore-gateway/04-integration/05-entraid-3lo-gateway) は、同じ 1 つのアプリで組んでいます。このアプリが Gateway 用の権限を公開します。Gateway の許可する宛先には、このアプリの client ID が入っています。

:::details 事前登録の手順
1. AI エージェントの提供元に、client ID を入れる欄と、サインインのあとに戻る先の URL を確かめます。
2. Entra ID に AI エージェントが使うアプリを登録し、戻る先の URL を入れて、client ID を控えます。
3. Gateway 用の権限を公開するアプリで、権限を公開します。アプリを分ける場合は、AI エージェントのアプリがその権限を頼めるようにします。
4. 控えた client ID を、AI エージェントの管理画面に入れます。
5. Gateway の受け付け時の確認で、許可する宛先に、権限を公開したアプリの client ID を入れます。

この手順は、公式サンプルの準備用スクリプトと AWS の資料にもとづく流れです。この記事では、Entra ID の画面で実際に通した記録は載せていません。

サインイン画面が出て、サインインのあとに Gateway の先のツールを呼べれば直っています。値の入れ方は「[AgentCore と Entra ID の連携](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity-idp-microsoft.html)」にあります。
:::

## A の直し方 2: 自動登録の依頼に応える中継サーバー

![自動登録の依頼に登録済みの client ID を返す中継サーバーを Gateway の手前に置き、AI エージェントが Entra ID でサインインする接続図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/09da54a5fa740f/zenn/articles/09da54a5fa740f/wire-a2.png)

MCP の認証と認可の仕様では、AI エージェント、認可サーバー、MCP サーバーが、決まった手順でやり取りすることになっています。ところが、使う AI エージェントと Entra ID と MCP サーバーの組み合わせによっては、どれかが仕様の一部に対応していないことがあります。中継サーバーは、その足りない部分を間に立って補う部品です。この記事の構成では、MCP サーバーにあたるのは Gateway です。

A の 2 つ目の直し方は、中継サーバーを Gateway の手前に置く形です。AI エージェントが自動登録しかできず、client ID を入れる欄がない場合に使います。この組み合わせで足りないのは、AI エージェントが自動登録を頼んでも、Entra ID がそれを受け付けないことです。中継サーバーは Entra ID の代わりに自動登録の依頼を受け、管理者が前もって Entra ID に登録した client ID を返します。サインインとトークンの発行は、そのあとも Entra ID が行います。

トークンを出すのは Entra ID のままなので、Gateway の受け付け時の確認は変えずに済みます。中継サーバーは、Amazon API Gateway と AWS Lambda で作れます。実装は AWS の公式サンプル「[05-entraid-3lo-gateway](https://github.com/awslabs/agentcore-samples/tree/abab3d8beb684c79fc827a95a2d015e44e76dbbc/06-workshops/02-AgentCore-gateway/04-integration/05-entraid-3lo-gateway)」にあります。中継サーバーは自分たちで作って運用する部品なので、お使いの AI エージェントで登録とその後のサインインが通るかを確かめてください。

:::details 中継サーバーが取り次ぐ処理の詳細
![AI エージェントの接続先を中継サーバーにし、中継サーバーが案内、登録、サインイン、戻り、トークン、MCP の 6 つを Entra ID と Gateway に取り次ぐ図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/09da54a5fa740f/zenn/articles/09da54a5fa740f/relay-arch.png)

公式サンプルのコードの説明によると、Entra ID だけでは足りないのは次の 3 点です。1 つ目に、Entra ID は自動登録の依頼を受け付けません。2 つ目に、AI エージェントが付けてくる宛先の指定を、Entra ID はエラーにします。宛先の指定は、RFC 8707 の resource という項目です。3 つ目に、サインインのあとの戻り先は、Entra ID に前もって登録したものしか使えません。

そこで、AI エージェントの MCP の接続先を中継サーバーにします。中継サーバーは、次の 6 つを順に取り次ぎます。

1. 案内: AI エージェントがメタデータを問い合わせると、中継サーバーは自分を認可サーバーとして案内します。
2. 登録: 自動登録の依頼には、前もって Entra ID に登録した client ID を返します。
3. サインイン: サインインの依頼から宛先の指定を外し、Gateway 用の権限を足します。戻り先を中継サーバー自身に替えて、Entra ID へ送ります。
4. 戻り: Entra ID から中継サーバーに戻ってきたら、AI エージェントの元の戻り先へ返します。
5. トークン: トークンの依頼も同じように直して Entra ID へ送り、トークンに引き換えます。
6. MCP: MCP の呼び出しは、Entra ID のトークンを付けたまま Gateway へ渡します。

公式サンプルでは、この 6 つを [1 つの Lambda](https://github.com/awslabs/agentcore-samples/blob/abab3d8beb684c79fc827a95a2d015e44e76dbbc/06-workshops/02-AgentCore-gateway/04-integration/05-entraid-3lo-gateway/lambda/mcp_proxy_lambda.py) が受け持っています。このサンプルの中継サーバーは、前もって登録した client ID を返す互換用のもので、DCR の登録を本当に代わりに行うものではありません。Entra ID の最新の対応は、Microsoft の資料で確かめてください。

VS Code から Gateway につなぐ公式サンプル「[03-ide-gateway-tool](https://github.com/awslabs/agentcore-samples/tree/abab3d8beb684c79fc827a95a2d015e44e76dbbc/06-workshops/02-AgentCore-gateway/04-integration/03-ide-gateway-tool)」も、API Gateway と Lambda の中継サーバーを置きます。こちらは受け付けが、AWS が提供する利用者のサインインのサービスである Amazon Cognito です。この中継サーバーは、メタデータとサインイン後の戻り先を受け持ちます。AI エージェントが CIMD を使う場合の中継サーバーは、これらのサンプルにはありません。
:::

## B と C: ほかに止まりやすい場所

A のほかにも、止まりやすい場所が 2 つあります。どちらも、組む前に気をつけておきたい点です。

B は、サインインはできたのに Gateway が 401 を返す場合です。トークンに書かれた宛先や権限が、Gateway の受け付け時の確認の条件と合っていないことがあります。Entra ID のアプリの設定と Gateway の設定を見比べてください。値の入れ方は「[AgentCore と Entra ID の連携](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity-idp-microsoft.html)」と「[受け付け時の確認](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/inbound-jwt-authorizer.html)」にあります。

C は、最初は動くのに、トークンの期限のころに止まる場合です。AI エージェントが、期限の前に新しいトークンをもらえていないことがあります。更新に対応しているかは、AI エージェントの提供元に確かめてください。

## 部品ごとの受け持ち

| 部品 | 受け持つこと | 設定する人 |
|---|---|---|
| Entra ID | 利用者の一覧、アプリ登録、トークンの発行 | 自社の Entra ID の管理者 |
| AgentCore Gateway | MCP の入口、トークンの確認、送り先への中継 | 自社の AWS の管理者 |
| Policy in AgentCore | Gateway で呼べるツールの判定。Policy を設定した場合に働く | 自社の AWS の管理者 |
| AgentCore Identity | SaaS の接続の設定と、鍵やトークンの保管 | 自社の AWS の管理者 |
| AWS Agent Registry | 使ってよい MCP サーバーなどの案内板。全社で検索したい場合に足す | 自社の AWS の管理者 |
| 中継サーバー | 自動登録の依頼への応答。AI エージェントが DCR だけに対応するときに置く | 自社の AWS の管理者 |
| AI エージェント | トークンの取得、提示、更新。接続先の制限 | AI エージェントの提供元に確認 |
| SaaS | 個人で発行した鍵の制限、同意の取り消し | SaaS の管理者 |

## まとめ

AI エージェントが Entra ID のトークンを取って更新できるなら、MCP の接続先を Gateway の 1 本にそろえられます。SaaS の鍵を Identity に預けると、Gateway を通る呼び出しの鍵の管理を 1 か所に集められます。
