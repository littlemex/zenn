## はじめに

:::message
この記事は、仕組みの理解を助けるために書いたものです。実際に組む前には、専門家のレビューを受け、自分の環境で入念に検証してください。内容に誤りを見つけたら、コメントで教えていただけるとうれしいです。

この記事では、一例として Microsoft Entra ID を使って整理します。Amazon Cognito などほかのサービスでは、それぞれ違いがあるので、各サービスの資料を確かめてください。この記事は概念的な整理であり、個々のサービスで何ができて何ができないかを確約するものではありません。
:::

AI エージェントのツールに MCP で SaaS をつなぐと、利用者がそれぞれ自分の鍵をツールに登録しがちです。MCP サーバーは、MCP で呼べる操作を公開するサーバーです。Amazon Bedrock AgentCore は、AI エージェントの入口や鍵を AWS 側で預かるサービスの集まりで、この記事では AgentCore と書きます。この記事では、社内の MCP サーバーの入口と SaaS の鍵を AgentCore に集める形を、図を中心に見ていきます。

この記事では、MCP でつなぐ側のアプリを「ツール」と呼びます。Devin、Claude Code、Kiro、社内で作るエージェントなどがツールにあたります。ツールが Entra ID からトークンを取り、更新しながら Gateway に見せ続けられるなら、ここで見る構成はどのツールにも当てはまります。それぞれのツールの設定方法は、ツールの提供元の資料で確かめてください。内容は 2026 年 10 月 17 日時点の公開情報にもとづいています。

## 2 種類の認証情報

この記事には、認証情報が 2 種類出てきます。1 つ目は SaaS の鍵で、GitHub などの SaaS が発行する API キーやアクセストークンです。どちらも、SaaS が呼び出しを受け付けるときに確かめる文字列です。2 つ目は Gateway 用のアクセストークンで、利用者が会社の Microsoft Entra ID にサインインすると発行されます。Microsoft Entra ID は、社員のサインインを受け持つ Microsoft のサービスです。

この記事が目指すのは、SaaS の鍵を利用者の手元からなくし、ふだんは Gateway 用のアクセストークンだけで SaaS を使える形です。Gateway は、このあと出てくる AgentCore Gateway という入口のことです。OAuth は、アプリに API を使う権限を渡すための決まりです。利用者ごとの OAuth を使う SaaS では、SaaS のトークンが有効なあいだは、最初の 1 回だけ SaaS の同意画面を通ります。

## 問題設定

![利用者ごとに自分の鍵がツールに登録され、SaaS へ直接つながっている図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/09da54a5fa740f/zenn/articles/09da54a5fa740f/now.png)

利用者は SaaS で自分の鍵を発行し、自分のツールに登録します。**鍵が利用者の手元に散らばるほど、会社が止めたり入れ替えたりできない場所が増えます**。退職や漏えいのとき、会社がすぐに鍵を止めるのは難しくなります。鍵の入れ替えも利用者まかせになります。どの操作が誰の鍵で行われたかを、会社として一元的に確かめるのも難しくなります。

## 目指す形

![ツールは SaaS の鍵を持たず、入口の Gateway を通って SaaS を使う図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/09da54a5fa740f/zenn/articles/09da54a5fa740f/target.png)

目指すのは、ツールが SaaS の鍵を持たない形です。ツールの MCP の接続先を、AgentCore Gateway の 1 本にそろえます。SaaS の鍵は、AgentCore Identity という保管庫に預けます。Gateway は送り先ごとに決めた認証方式で、Identity に預けた鍵を使って送り先を呼びます。送り先は、SaaS が公開する MCP サーバーなどです。利用者は Entra ID でサインインし、Gateway 用のアクセストークンだけを持ちます。

こうすると、Gateway を通る呼び出しでは、SaaS の鍵の管理を Identity に集められます。

## 通行証のたとえ: 誰が何をするか

![ビルの受付の 7 つの仕事と、それを受け持つサービスの対応の図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/09da54a5fa740f/zenn/articles/09da54a5fa740f/roles.png)

この先の認証と認可の説明で、誰が何をしているかを整理するために、会社のビルの通行証にたとえてみます。Gateway が受付で、Gateway 用のアクセストークンが社員証にあたります。社員の名簿は Entra ID の利用者の一覧で、社員証をもらえるアプリの名簿は Entra ID のアプリ登録です。社員証を出す発行所は、Entra ID の認可サーバーです。認可サーバーは、アクセストークンを発行するサーバーです。

受付で社員証を照合するのは Gateway です。Gateway の先で呼べる 1 つ 1 つの機能を、MCP では tool と呼びます。この記事では、つなぐ側のツールと区別して「操作」と書きます。入ってよい部屋、つまり Gateway で呼んでよい操作を決めるのは Policy in AgentCore です。金庫、つまり SaaS の鍵の保管庫は Identity です。出入りの記録は、AWS への操作を記録する AWS CloudTrail が受け持ちます。以下では、たとえの言葉には実体の名前を添えて書きます。

## ツールの条件: トークンを取って見せ続ける

![ツールが社員証をもらって Gateway に見せ続ける 6 段の流れと、止まりやすい 3 つの場所の図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/09da54a5fa740f/zenn/articles/09da54a5fa740f/tooljob.png)

この形が成り立つには、ツールが社員証、つまり Gateway 用のアクセストークンをもらい、受付、つまり Gateway に見せ続けられないといけません。ツールは利用者を Entra ID のサインイン画面に案内し、発行されたトークンを受け取ります。Gateway を呼ぶたびにトークンを見せ、期限が来る前にもらい直します。

止まりやすい場所は 3 つあります。A は、ツールが自分を Entra ID のアプリ登録に載せられない場所です。B は、期限の前にトークンを更新できない場所です。C は、トークンに書かれた宛先が Gateway の照合の条件と合わない場所です。どれか 1 つでも止まると、利用者は Gateway を通れず、SaaS を使えません。

## 実際の決まり

たとえの各場面は、OAuth の決まりの組み合わせで実現されています。MCP の認可の全体は「[MCP の認可の仕様（2026-07-28 版）](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)」に書かれています。次の表は、この版の仕様が参照する決まりを、たとえの場面ごとに並べたものです。表で案内と呼ぶものは、サーバーが自分の情報を置く決まった URL で、英語で metadata と呼ばれます。Entra ID とお使いのツールがどの決まりに対応するかは、それぞれの提供元の資料で確かめてください。

| たとえ | 実際にやること | 決まり |
|---|---|---|
| 受付の案内を読む | ツールは Gateway の案内から、使う認可サーバーを見つける | [RFC 9728](https://www.rfc-editor.org/rfc/rfc9728) |
| 発行所の案内を読む | ツールは認可サーバーの案内から、サインインとトークンの窓口を調べる | [RFC 8414](https://www.rfc-editor.org/rfc/rfc8414)、[OpenID Connect Discovery](https://openid.net/specs/openid-connect-discovery-1_0.html) |
| アプリの名簿に載る | ツールが client ID を手に入れる。方法は事前登録、CIMD、DCR の 3 つ | [CIMD](https://datatracker.ietf.org/doc/draft-ietf-oauth-client-id-metadata-document/)、[RFC 7591](https://www.rfc-editor.org/rfc/rfc7591) |
| サインインして社員証をもらう | サインイン後に受け取る一時的な番号、つまり認可コードを、アクセストークンに引き換える | [OAuth 2.1](https://datatracker.ietf.org/doc/draft-ietf-oauth-v2-1/)、[RFC 7636](https://www.rfc-editor.org/rfc/rfc7636) |
| 行き先を伝える | トークンを使う先を、認可サーバーに伝える | [RFC 8707](https://www.rfc-editor.org/rfc/rfc8707) |
| 社員証を見せる | 呼び出しのヘッダーにトークンを付ける | [RFC 6750](https://www.rfc-editor.org/rfc/rfc6750) |
| 期限の前にもらい直す | リフレッシュトークンという別の認証情報が出ている場合は、それで新しいトークンをもらう | [OAuth 2.1](https://datatracker.ietf.org/doc/draft-ietf-oauth-v2-1/) |

client ID は、認可サーバーがアプリを見分けるための番号です。CIMD は、英語で Client ID Metadata Documents の略です。ツールの情報を置いた URL を client ID として使う方式で、決まりはまだ草案の段階です。DCR は、英語で Dynamic Client Registration の略です。ツールが認可サーバーに登録を依頼する方式で、RFC 7591 で決まっています。MCP の仕様の [2026-07-28 版の変更点](https://modelcontextprotocol.io/specification/2026-07-28/changelog)で、DCR は非推奨になりました。置き換え先は CIMD です。CIMD に対応しない認可サーバーのために、DCR は互換用に残っています。Entra ID とお使いのツールがどの方式に対応するかは、それぞれの提供元の資料で確かめてください。

## 部品の組み合わせ

![どのツールも Gateway につなぎ、Gateway が Identity から鍵を受け取って SaaS を呼ぶ推奨構成の図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/09da54a5fa740f/zenn/articles/09da54a5fa740f/arch.png)

推奨する構成では、どのツールも MCP の接続先を Gateway だけにします。Gateway には、受け付けるトークンの条件を設定します。Entra ID のトークンで受け付ける場合、発行元は Entra ID の発見用の URL として設定します。そのうえで、宛先、アプリ、権限のうち確かめたい項目を[受け付け時の確認](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/inbound-jwt-authorizer.html)に入れます。

Gateway で呼べる操作は、[Policy in AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy.html) を設定すると絞れます。Policy は、Cedar という言葉で規則を書く仕組みです。規則には、利用者のトークンに入った部署や権限などの項目を条件として使えます。例は公式サンプル「[02-policy](https://github.com/awslabs/agentcore-samples/tree/abab3d8beb684c79fc827a95a2d015e44e76dbbc/01-features/07-centralize-and-govern-your-ai-infrastructure/02-policy)」にあります。SaaS を呼ぶときの鍵の使い方は、Gateway の送り先ごとに[認証方式](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-outbound-auth.html)を選び、Identity に登録した鍵を指定します。

GitHub は、GitHub が公開している [MCP サーバー](https://github.com/github/github-mcp-server/blob/main/docs/remote-server.md)を Gateway の送り先にする形から試すのが手軽です。利用者ごとの OAuth で送り先にする手順は、AWS の公式サンプル「[authorization-code-flow の github](https://github.com/awslabs/agentcore-samples/tree/abab3d8beb684c79fc827a95a2d015e44e76dbbc/01-features/07-centralize-and-govern-your-ai-infrastructure/01-gateway/01-attach-targets/mcp/mcp-servers/01-configure-auth/authorization-code-flow/github)」にあります。Entra ID で受け付け、利用者ごとの OAuth で送り先を呼ぶまでの全体は、公式サンプル「[05-entraid-3lo-gateway](https://github.com/awslabs/agentcore-samples/tree/abab3d8beb684c79fc827a95a2d015e44e76dbbc/06-workshops/02-AgentCore-gateway/04-integration/05-entraid-3lo-gateway)」で動かせます。

## 1 回の呼び出し

![Entra ID でサインインしてから、データイベントを有効にした場合に CloudTrail が呼び出しを記録するまでの 6 段の流れの図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/09da54a5fa740f/zenn/articles/09da54a5fa740f/flow.png)

最初に利用者が Entra ID でサインインし、ツールが Gateway 用のアクセストークンを受け取ります。サインインは毎回ではなく、トークンが使えるあいだは省けます。そのあとの呼び出しは、次の順に進みます。ツールがトークンを付けて Gateway を呼びます。Gateway はトークンを確かめ、Policy を設定していれば呼んでよい操作かを判定します。Gateway は Identity に預けた鍵を使って送り先を呼び、結果を返します。設定していれば、この呼び出しを CloudTrail が記録します。

## 記録: CloudTrail のデータイベント

データイベントは、個々の呼び出しを 1 件ずつ記録する種類のログです。[CloudTrail のデータイベント](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/enabling-cloudtrail-data-event-logging.html)を有効にすると、対象の Gateway への呼び出しを記録できます。データイベントは明示的に有効にする必要があり、[料金](https://aws.amazon.com/cloudtrail/pricing/)がかかります。設定の例は、公式サンプル「[gateway-observability](https://github.com/awslabs/agentcore-samples/tree/abab3d8beb684c79fc827a95a2d015e44e76dbbc/01-features/07-centralize-and-govern-your-ai-infrastructure/01-gateway/04-advanced-concepts/gateway-observability)」にあります。記録に含まれる項目は CloudTrail の資料で確かめてください。記録されるのは Gateway への呼び出しなので、SaaS の中で何が起きたかは SaaS 側の記録で確かめます。

## 鍵の登録の単位

![社内利用なら SaaS ごとに 1 つ、他社に提供するなら会社ごとに分ける場合がある、という比較の図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/09da54a5fa740f/zenn/articles/09da54a5fa740f/cred.png)

Identity には、SaaS への接続の設定を credential provider として登録します。OAuth の場合、credential provider が持つのは SaaS に作った OAuth アプリの設定です。OAuth アプリは、SaaS から許可をもらうために SaaS に登録するアプリの設定です。利用者ごとのトークンは、Identity の中の金庫である [token vault](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/key-features-and-benefits.html) が保管します。たとえば 10 人が同じ OAuth アプリに同意しても、credential provider は 1 つで、トークンは 10 人分が別々に保管されます。

社内で使うなら、まずは SaaS ごとに 1 つから始められます。本番と検証を分ける場合や、権限の違う鍵を分ける場合は、その数だけ作ります。複数の会社に提供するサービスで、会社ごとに別の OAuth アプリや鍵が要る SaaS なら、会社ごとに分けます。作れる数には[上限](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/bedrock-agentcore-limits.html)があります。2026 年 10 月 17 日時点の上限は、1 アカウント 1 リージョンあたり種類ごとに 50 個です。上限は申請で増やせます。

## 鍵の入れ替えと停止

![利用者ごとの鍵は同意から取り消しまで、共有の API キーは発行から無効化までの 4 段の図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/09da54a5fa740f/zenn/articles/09da54a5fa740f/rotation.png)

Identity は鍵を預かって渡す役目です。鍵の止め方と入れ替え方は、Identity だけでは完結しないので、SaaS ごとに手順を決めます。

OAuth に対応する SaaS では、会社が承認した OAuth アプリを使います。利用者は最初に SaaS の同意画面で同意し、得られたトークンを Identity が預かります。本人の権限で操作されるので、SaaS 側の記録で本人を見分けやすくなります。退職のときは、Entra ID で利用者を止めることに加えて、SaaS 側の同意やトークンも取り消します。同意の画面を利用者に出す窓口は、公式サンプル「[consent portal](https://github.com/awslabs/agentcore-samples/tree/abab3d8beb684c79fc827a95a2d015e44e76dbbc/01-features/05-authenticate-and-authorize/07-consent-portal-auth-code-flow-targets)」で試せます。

API キーしか使えない SaaS では、会社で発行した鍵を Identity に預けます。AWS Secrets Manager は、鍵を預けて取り出す AWS のサービスです。API キーの credential provider は、[Secrets Manager に置いた鍵](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/resource-providers.html)を使えます。Secrets Manager の[入れ替えの仕組み](https://docs.aws.amazon.com/secretsmanager/latest/userguide/rotating-secrets.html)で、入れ替えを定期的に動かせます。ただし、SaaS で新しい鍵を発行し、古い鍵を無効にする処理は、SaaS ごとに作る必要があります。

## 直接の接続: 抜け道の狭め方

![ツールが Gateway を通らず個人の鍵で SaaS に直接つなぐ抜け道と、ツール側と SaaS 側の狭め方の図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/09da54a5fa740f/zenn/articles/09da54a5fa740f/guard.png)

Gateway を用意しても、利用者が個人の鍵で SaaS に直接つなげる道が残ると、鍵は 1 か所にまとまりません。ツール側では、管理者が MCP の接続先を Gateway だけに絞れるかを、提供元に確かめます。個人がその設定を変えられないかも確かめます。SaaS 側では、個人で発行した鍵を制限します。GitHub なら、組織の設定で[個人用アクセストークンからの利用を制限](https://docs.github.com/en/organizations/managing-programmatic-access-to-your-organization/setting-a-personal-access-token-policy-for-your-organization)できます。

利用者の端末で動くツールでは、端末のコマンドから直接つなぐ道を、ツールの設定だけでは閉じきれないことがあります。その場合も、個人の鍵の制限は SaaS 側で行います。端末側の制御は、社内の端末管理の方針に従います。

## Agent Registry: 任意の目録

![Agent Registry にレコードを登録して承認し、利用者が検索して見つけた入口を Gateway で呼ぶ図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/09da54a5fa740f/zenn/articles/09da54a5fa740f/registry.png)

[AWS Agent Registry](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/registry.html) は、承認した MCP サーバーやエージェント、スキルを社内で探せるようにする目録です。ここまでの構成に Registry は必須ではありません。承認した入口を全社で検索できるようにしたいときに足します。

管理者が Gateway などの入口をレコードとして登録すると、レコードは[下書き、承認待ち、承認済みと進みます](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/registry-record-lifecycle.html)。承認済みのレコードだけが検索に出ます。承認待ちになったことは、出来事を別の仕組みに知らせる Amazon EventBridge で通知できます。Registry は、登録した入口の URL から中身を[取り込めます](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/registry-sync-records.html)。入口が OAuth で守られているなら、取り込みに Identity の credential provider を使います。取り込みの例は、公式サンプル「[registry-synchronize-mcpserver](https://github.com/awslabs/agentcore-samples/tree/abab3d8beb684c79fc827a95a2d015e44e76dbbc/01-features/07-centralize-and-govern-your-ai-infrastructure/03-registry/03-advanced/registry-synchronize-mcpserver)」にあります。

Registry 自身も [MCP の窓口](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/registry.html)を持ちますが、それは目録を探すためのものです。Registry は SaaS の鍵を預からず、SaaS への呼び出しも中継しません。利用者は Registry で入口を見つけ、実際の呼び出しは Gateway を通します。

## つながらないときの切り分け

![止まった場所から、足りないものと直し方を 3 行でたどる図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/09da54a5fa740f/zenn/articles/09da54a5fa740f/triage.png)

最初に確かめたいのは、お使いのツールが Entra ID のトークンを取り、更新しながら Gateway を呼べるかです。ここが通らないと、この構成は成り立ちません。止まったときは、止まった場所を手がかりに調べ始めます。症状は調べ始める場所の目安で、原因を決めつけるものではありません。エラーの表示とログで、実際に止まった処理を確かめます。

サインイン画面が出ないなら、まず A を調べます。401 は、認証が通らなかったことを表す応答の番号です。サインインできたのに Gateway が 401 を返すなら、トークンの有無と期限を確かめたうえで C を調べます。最初は動くのにトークンの期限のころに止まるなら、B を調べます。A には直し方が 2 つあります。以下の 4 節で、それぞれの直し方を接続図で見ます。

## A の直し方 1: Entra ID にアプリを前もって登録する

![直す前はツールが自分を Entra ID のアプリ登録に載せようとして止まり、直した後は管理者が載せた client ID でサインインする接続図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/09da54a5fa740f/zenn/articles/09da54a5fa740f/wire-a1.png)

A の 1 つ目の直し方は、事前登録です。A は、ツールが自分を Entra ID のアプリ登録に載せられずに止まる場合です。Entra ID がどの登録方式を受け付けるかは、Microsoft の資料で確かめてください。ツールに client ID を入れる欄があるなら、いちばん簡単なのは事前登録です。管理者がツール用のアプリを Entra ID に登録し、もらった client ID をツールに設定します。

あわせて、Gateway 用の権限を公開するアプリを決めます。ツールのアプリと同じにしても、分けても構いません。公式サンプルの [05-entraid-3lo-gateway](https://github.com/awslabs/agentcore-samples/tree/abab3d8beb684c79fc827a95a2d015e44e76dbbc/06-workshops/02-AgentCore-gateway/04-integration/05-entraid-3lo-gateway) は、同じ 1 つのアプリで組んでいます。このアプリが Gateway 用の権限を公開します。Gateway の許可する宛先には、このアプリの client ID が入っています。

:::details 事前登録の手順
1. ツールの提供元に、client ID を入れる欄と、サインインのあとに戻る先の URL を確かめます。
2. Entra ID にツールが使うアプリを登録し、戻る先の URL を入れて、client ID を控えます。
3. Gateway 用の権限を公開するアプリで、権限を公開します。アプリを分ける場合は、ツールのアプリがその権限を頼めるようにします。
4. 控えた client ID を、ツールの管理画面に入れます。
5. Gateway の受け付け時の確認で、許可する宛先に、権限を公開したアプリの client ID を入れます。

この手順は、公式サンプルの準備用スクリプトと AWS の資料にもとづく流れです。この記事では、Entra ID の画面で実際に通した記録は載せていません。

サインイン画面が出て、サインインのあとに Gateway の先の操作を呼べれば直っています。値の入れ方は「[AgentCore と Entra ID の連携](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity-idp-microsoft.html)」にあります。
:::

## A の直し方 2: 自動登録の依頼に応える中継

![自動登録の依頼に登録済みの client ID を返す中継を Gateway の手前に置き、ツールが Entra ID でサインインする接続図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/09da54a5fa740f/zenn/articles/09da54a5fa740f/wire-a2.png)

A の 2 つ目の直し方は、自動登録の依頼に応える中継を、Gateway の手前に置く形です。ツールが DCR しかできず、client ID を入れる欄がない場合に使います。中継は、HTTP の窓口を作る Amazon API Gateway と、小さな処理を動かす AWS Lambda で作れます。ツールが Gateway のメタデータと認可サーバーのメタデータを問い合わせると、中継は Entra ID の場所を答えます。ツールが DCR で登録を依頼すると、管理者が前もって Entra ID に登録した client ID を返します。

トークンを出すのは Entra ID のままなので、Gateway の受け付け時の確認は変えずに済みます。この形は AWS の公式サンプル「[05-entraid-3lo-gateway](https://github.com/awslabs/agentcore-samples/tree/abab3d8beb684c79fc827a95a2d015e44e76dbbc/06-workshops/02-AgentCore-gateway/04-integration/05-entraid-3lo-gateway)」に実装があり、登録の依頼に答える処理は、[中継の Lambda](https://github.com/awslabs/agentcore-samples/blob/abab3d8beb684c79fc827a95a2d015e44e76dbbc/06-workshops/02-AgentCore-gateway/04-integration/05-entraid-3lo-gateway/lambda/mcp_proxy_lambda.py) にあります。VS Code から Gateway につなぐ公式サンプル「[03-ide-gateway-tool](https://github.com/awslabs/agentcore-samples/tree/abab3d8beb684c79fc827a95a2d015e44e76dbbc/06-workshops/02-AgentCore-gateway/04-integration/03-ide-gateway-tool)」も API Gateway と Lambda の中継を置きます。こちらは受け付けが Amazon Cognito です。Cognito は、AWS が提供する利用者のサインインのサービスです。この中継は、メタデータとサインイン後の戻り先を受け持ちます。

このサンプルの中継は、前もって登録した client ID を返す互換用の中継です。DCR の登録を本当に代わりに行うものではありません。お使いのツールで、登録の応答とその後のサインインが通るかを確かめてください。中継は、自分たちで作って運用する部品です。ツールが CIMD を使う場合の中継は、これらのサンプルにはありません。

## C の直し方: トークンと Gateway の条件をそろえる

![直す前はトークンの宛先が Gateway の条件と合わず 401 になり、直した後は宛先と権限がそろって呼び出しが通る接続図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/09da54a5fa740f/zenn/articles/09da54a5fa740f/wire-c.png)

C は、サインインはできたのに Gateway が 401 を返す場合です。401 の原因は宛先だけではありません。まず、トークンが呼び出しに付いているかと、期限が切れていないかを確かめます。そのうえで、ツールが受け取ったトークンの中身を読み、発行元、宛先、権限の値を控えます。

宛先に入っていてほしいのは、Gateway 用の権限を公開したアプリの ID です。別の値が入っている場合は、ツールが Gateway 用の権限を頼めていない可能性があります。Entra ID のトークンの中身の決まりは、Microsoft の資料で確かめてください。この記事で発行元と呼ぶ項目は英語で issuer、宛先は audience、権限は scope です。Entra ID のアプリの設定と Gateway の受け付け時の確認を、次の表のように 1 対 1 でそろえます。

| Entra ID の設定 | トークンの中身 | Gateway の受け付け時の確認 |
|---|---|---|
| 権限を公開したアプリで、v2.0 のトークンを出す | 発行元 | v2.0 の発見用の URL。そこに書かれた発行元と、トークンの発行元が一致すること |
| 権限を公開したアプリを登録する | 宛先 | 許可する宛先に、そのアプリの ID |
| そのアプリで Gateway 用の権限を公開する | 権限 | 許可する権限に、公開した権限 |

:::details C の設定の名前
- AWS の「[AgentCore と Entra ID の連携](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity-idp-microsoft.html)」では、権限を公開したアプリの manifest で `accessTokenAcceptedVersion=2` にして、v2.0 のトークンを出す手順になっています。
- 発行元は `iss`、宛先は `aud`、権限は `scp` という項目に入ります。
- Gateway 側の発見用の URL は discovery URL、許可する宛先は allowed audiences、許可する権限は allowed scopes という名前です。

値の入れ方は「[AgentCore と Entra ID の連携](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity-idp-microsoft.html)」と「[受け付け時の確認](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/inbound-jwt-authorizer.html)」にあります。200 が返っても、MCP の応答の中身で操作が成功したかを確かめます。断られた呼び出しの有無は、[Gateway のメトリクスとログ](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability-gateway-metrics.html)でも確かめられます。
:::

## B の直し方: 期限の前にトークンをもらい直す

![直す前は期限でトークンが切れて止まり、直した後はリフレッシュトークンで新しいトークンをもらって呼び続ける接続図](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/09da54a5fa740f/zenn/articles/09da54a5fa740f/wire-b.png)

B は、最初は動くのに、トークンの期限のころに止まる場合です。止まった時刻と、トークンに書かれた期限の時刻を比べると確かめられます。よくある原因は、ツールが期限の前に新しいトークンをもらえていないことです。リフレッシュトークンが出ていない場合や、失効した場合もあります。ここで更新するのは、Entra ID が出す Gateway 用のトークンです。Identity が預かる SaaS 用のトークンとは別なので、どちらで止まったかをログで切り分けます。

リフレッシュトークンで更新できるかは、ツールの作りと Entra ID 側の条件で決まります。ツールが更新に対応するかは、提供元に確かめます。リフレッシュトークンが出る条件は、Microsoft の資料で確かめます。ツールが更新に対応していなければ、そのツールを Gateway の対象から外すか、期限ごとにサインインし直す運用にするかを決めます。トークンの期限を長くして逃げると、漏れたときに使われる時間も長くなります。期限の長さは、Microsoft の資料と社内の基準で決めます。

## 部品ごとの受け持ち

| 部品 | 受け持つこと | 設定する人 |
|---|---|---|
| Entra ID | 利用者の一覧、アプリ登録、トークンの発行 | 自社の Entra ID の管理者 |
| AgentCore Gateway | MCP の入口、トークンの確認、送り先への中継 | 自社の AWS の管理者 |
| Policy in AgentCore | Gateway で呼べる操作の判定。Policy を設定した場合に働く | 自社の AWS の管理者 |
| AgentCore Identity | SaaS の接続の設定と、鍵やトークンの保管 | 自社の AWS の管理者 |
| AWS Agent Registry | 承認した入口の目録。全社で検索したい場合に足す | 自社の AWS の管理者 |
| 中継 | 自動登録の依頼への応答。ツールが DCR だけに対応するときに置く | 自社の AWS の管理者 |
| ツール | トークンの取得、提示、更新。接続先の制限 | ツールの提供元に確認 |
| SaaS | 個人で発行した鍵の制限、同意の取り消し | SaaS の管理者 |

## まとめ

ツールが Entra ID のトークンを取って更新できるなら、MCP の接続先を Gateway の 1 本にそろえられます。SaaS の鍵を Identity に預けると、Gateway を通る呼び出しの鍵の管理を 1 か所に集められます。
