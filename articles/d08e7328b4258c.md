## はじめに

音声合成モデル XTTS v2 の中心は、GPT-2 と同じ形の 30 層のデコーダです。このデコーダは、話者の特徴と文の埋め込みを前に置き、音声トークンを 1 つずつ作ります。この記事では、このデコーダを vllm-neuron 向けのモデルとして書き、Trainium2 の実機で vLLM のエンジンから音声トークンを作るまでに、何を書き、どこで何が壊れたかをまとめます。

結果を先に書きます。1 つの文と 1 つの参照音声で確かめたところ、vLLM のエンジンの `llm.generate()` で実機が作った音声トークンの系列は、CPU の bf16 で作った系列と 1 つ残らず同じで、そこから作った音声の単語の誤り率（WER）は CPU と同じ 8.3% でした。そのために、層の実装と bf16 で 6 つ、prefill の注意の入力で 1 つ、エンジンが渡す値に合わせて 2 つの直しをモデルに入れ、インストール済みの vllm-neuron には 1 行のパッチを当てています。

比べる相手は、同じデコーダを NxD Inference で載せた実装です。NxD Inference での仕組みは「[NxD Inference にカスタムモデルを統合するための事前知識](https://zenn.dev/tosshi/articles/81840c7c10dddd)」と「[XTTS v2 を NxD Inference で動かす](https://zenn.dev/tosshi/articles/ffc359901ea1cc)」で、XTTS v2 の全体の構造は「[XTTS v2 を AWS Neuron で動かす](https://zenn.dev/tosshi/articles/53cc505a8d85e2)」で説明しています。どちらの実装も、Trainium に載せるのは GPT デコーダだけです。話者の特徴を作る前処理、文のトークン化、波形を作る HifiDecoder は CPU で、Coqui TTS の実装をそのまま使います。

## 誰が何を書くか

![NxD Inference 版では generate() の橋渡しのクラス、prefill と decode の 2 つの Application、層の計算を自分で書く。vllm-neuron 版では生成のループとページ単位の KV キャッシュの領域を vLLM が受け持ち、prefill と decode の分岐、KV の書き込みと読み出し、層の計算、decode のマスクを自分で書き、prefill の注意には NKI の flash_attention を使う](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/d08e7328b4258c/zenn/articles/d08e7328b4258c/who-writes-what.png)

vllm-neuron では、リクエストの管理と生成のループを vLLM が受け持ちます。そのため、NxD Inference 版で書いた 2 つの仕組みが要りません。1 つは、Hugging Face の `generate()` に生成のループを任せるための橋渡しのクラスです。もう 1 つは、prefill と decode を別々の Application に分け、KV を CPU 経由で写す処理です。

vllm-neuron 版で自分で書くのは、次のものです。

- `attn_metadata` を見て prefill と decode を分ける、1 つのモデルの `forward()`
- vLLM がページ単位で用意した KV キャッシュの領域への書き込み（scatter）と、block table に沿った読み出し（gather）
- q、k、v、o の射影、MLP、LayerNorm、音声トークンと音声の位置の埋め込み、decode の注意のマスク
- 重みの変換。チェックポイントの attention と MLP の Conv1D の重みを `nn.Linear` 用に転置し、1 つにまとまった `c_attn` を q、k、v に分ける

vllm-neuron が用意する部品で、改造せずに使えたのは、prefill の注意を計算する NKI のカーネル `NF.flash_attention` と、`is_token_ids` が False の位置を `prompt_embeds` の行で置き換え、True の位置はトークンの埋め込みのままにする `NF.merge_prompt_embeds` です。ただし `NF.flash_attention` に渡す K と V は、KV キャッシュに書き込んだあとに読み戻したものにします（後の節）。話者の特徴と文の埋め込みは、vLLM の `prompt_embeds` として渡します。

## モデルとコンパイルで直した 6 つの問題

| # | 実装の注意点 | 必要な処理 |
| --- | --- | --- |
| 1 | KV キャッシュに書くとき、書き込み先の index はヘッドの順に並び、書き込む値はトークンの順に並んでいた | 値もヘッドの順に並べる |
| 2 | `NF.gen_attention_decode_mask` は、生成中のトークンの K と V を末尾の位置に置く `NF.attention_decode` と組で使う前提で、末尾の位置を常に有効にする | 実際の位置から自分でマスクを作る（2 行） |
| 3 | 最後の LayerNorm が、GPT-2 本体の `ln_f` のほかに、XTTS v2 独自の `final_norm` の 2 つある | `ln_f` のあとに `final_norm` を通してから出力の層に渡す |
| 4 | チェックポイントには GPT-2 本体のトークンと位置の埋め込み（`wte`、`wpe`）が無く、位置の埋め込みは文用（404 行）と音声用（608 行）の 2 つの表で、それぞれ 0 から数え直す | 音声トークンには、音声の中での位置で音声用の表を引く |
| 5 | `gelu(x, approximate="tanh")` が、Neuron の torch バックエンドで `TypeError: apply() takes no keyword arguments` になる | tanh 近似の式を掛け算と `tanh` で書く |
| 6 | bf16 の decode で、マスクを Python の `0.0` と `-1e9` から作ると fp32 のテンソルになり、足した scores と softmax の出力も fp32 に上がって、bf16 の V との `torch.matmul` が型の違いで止まる | 行列積の前に softmax の出力を `v_ctx.dtype` に戻す |

KV キャッシュの読み書きは、同じ入力を一度の prefill で処理した場合と、prefill のあとに 1 トークンずつ decode した場合の logits を比べて確かめます。1 と 2 は例外にならず、logits がずれるだけなので、この比べ方でないと見つかりません。2 のように組で使う前提の部品は、片方だけを借りると、自分のキャッシュの決まりと合わなくなります。3 と 4 は、本物のチェックポイントを読み込んだ Hugging Face の `GPT2Model` を独立の参照にして、同じ入力の logits を比べて確かめました。

5 の原因は、PyTorch がこの呼び出しの `approximate` をキーワード引数の形にそろえ、Neuron の torch バックエンドがそれを、キーワード引数を受け取れない `torch.autograd.Function.apply()` にそのまま渡すことです。呼び出し方を位置引数に変えても避けられません。

```python
hidden_states = 0.5 * x * (1.0 + torch.tanh(0.7978845608028654 * (x + 0.044715 * x * x * x)))
```

## prefill の注意は、書き込んだキャッシュから読む

![prefill で、射影の直後の k と v を KV キャッシュへの書き込みと flash_attention の両方に使うと、30 層の出力の CPU との cosine 類似度は 0.814 で、最初のトークンは 1023 になる。書き込んだあとのキャッシュから k と v を読み戻して flash_attention に渡すと 0.999988 で、最初のトークンは CPU と同じ 225。decode は flash_attention を使わない](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/d08e7328b4258c/zenn/articles/d08e7328b4258c/prefill-readback.png)

**今回の XTTS v2 の注意の部品では、射影の直後の K と V を、KV キャッシュへの書き込み（scatter）と `NF.flash_attention` の両方にそのまま渡すと、モデル全体を 1 回の `torch.compile` でコンパイルしたとき、実機で注意の結果が大きくずれます**。30 層を通した出力の CPU（fp32）との cosine 類似度（ベクトルの向きの近さで、1 に近いほど近い）は 0.814 で、最初に生成するトークンは CPU の 225 ではなく 1023 になります。CPU で bf16 にしただけでは、このずれは起きません。CPU の bf16 と fp32 では、30 層のどの層でも隠れ状態の cosine 類似度は 0.99995 以上です。

正しい結果になったのは、書き込んだあとの KV キャッシュから K と V を読み戻し、それを `NF.flash_attention` に渡す書き方です。モデル全体を 1 回の `torch.compile` でコンパイルしたまま、30 層の出力の cosine 類似度は 0.999988、最初のトークンは 225 になりました。K と V を `clone()` で写す方法や、書き込みを注意の後ろへ並べ替える方法のように、値を変えない操作を足すだけでは直りません。

この組み合わせは、学習済みの重みを使わない注意の部品（16 ヘッド、ヘッドの次元 64、69 トークン）でも再現します（書き込みあり 0.9375、読み戻しにすると 0.999995）。この部品では、K と V の射影を 2 回別々に計算する方法と、ヘッドを 2 倍に複製してから計算する方法でも 0.999995 に戻りましたが、どちらも計算が増えるので、30 層では読み戻しだけを使っています。vllm-neuron に同梱された `llama3` を、ヘッドの数とヘッドの次元を同じにした 2 層の乱数の重みで作り、エンジン経由で 32 トークンのプロンプトを 1 つ流すと、GQA のあり、なしのどちらでも最初のトークンは CPU と同じでした。`llama3` は RoPE を `qkv_proj` のカーネルの中で計算します。この違い、層の数の違い、そのほかの違いのどれが効いているかは、切り分けていません。コンパイラの中で何が起きているかは、まだ調べていません。

decode の注意は、`NF.flash_attention` ではなく、キャッシュから block table に沿って読み出して softmax を取る手書きの計算なので、この問題は起きません。

## エンジンが渡す 3 つの入力と、モデル側の合わせ方

![エンジンは、手書きの生成ループとは違うものを渡す。prompt_is_token_ids はインストール済みの plugin が落とし、前置きがトークン 0 の埋め込みに置き換わる。位置は系列全体の番号で、最初の音声トークンは 69。この検証で受け取った block table は [1, 2, 3, -1] で、block 0 は予約され、-1 は「ブロック無し」を表す。それぞれ、plugin への 1 行のパッチ、is_token_ids の累積和から音声の中での位置を求める直し、-1 を 0 に丸めて block_table[0] を基準にマスクを作る直しで対処する](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/d08e7328b4258c/zenn/articles/d08e7328b4258c/engine-inputs.png)

vLLM のエンジンは、次の 3 つの入力をモデルに渡します。どれも、合わせないと生成が壊れます。

1. リクエストの状態への `prompt_is_token_ids` の受け渡し。インストール済みの vllm-neuron の `neuron_model_runner.py` は、リクエストの状態（`CachedRequestState`）を作るときに、元にした vLLM の `gpu_model_runner.py` にある `prompt_is_token_ids=new_req_data.prompt_is_token_ids` の 1 行を持っていません。そのため、どの位置も「トークン ID」として扱われ、前置きの埋め込みが、トークン 0 の埋め込みに置き換わります。この検証では、インストール済みの plugin にこの 1 行を足すパッチを当てました。
2. エンジンが渡す位置の数え方。位置は系列全体の番号で来ます。XTTS v2 の音声の位置の表は、音声の中で 0 から数えます。エンジンが最初の音声トークンに渡す位置は、前置き 69 トークンの後ろの 69 です。CPU だけで試しても、位置を 69 にすると最初のトークンが 225 から 144 に変わりました。prefill では `cumsum(is_token_ids) - 1` を 0 で下限を切って音声の中での位置にし、前置きの長さを覚えておき、decode では渡された位置からその長さを引きます。この覚え方は 1 つのリクエストを前提にしているので、`max_num_seqs=1` でだけ正しく動きます。
3. エンジンが割り当てる block table。block 0 は予約されていて、本物のリクエストには割り当てられません。この検証の decode で受け取った block table は `[1, 2, 3, -1]`（`block_size=32`）で、使っていない欄は -1 です。そのまま `k_cache[block_table]` で読むと、-1 は PyTorch の負の index として、KV キャッシュの領域の最後のブロックを指します。また、decode のマスクを `slot_mapping` から作ると、読み出した文脈の先頭が block 0 でない分（この検証では 32 スロット）だけ有効な範囲が後ろへ広がり、-1 が指す無関係なブロックまで読みます。直す前の生成は、225 を 100 回繰り返しました。-1 を 0（予約された空のブロック）に丸めてから読み、マスクは `block_table[0]` の先頭のスロットを基準に作ります。

エンジンに渡す前置きの最後には、音声の開始のトークン（1024）を本物のトークンとして足し、`prompt_token_ids` を `[0] * 69 + [1024]`、`prompt_is_token_ids` を `[False] * 69 + [True]` にします。`prompt_embeds` は `prompt_token_ids` と同じ長さが要るので、最後の 1 行は使われない 0 で埋めます。

## vLLM のエンジンに載せる設定

モデルを `ModelRegistry.register_model` で、設定のクラスを `AutoConfig.register` で登録し、`enable_prompt_embeds=True` を付けた `LLM()` を作ります。モデルのディレクトリでは、変換した重み、`config.json` の `torch_dtype`、`LLM(dtype=...)` をすべて bf16 にそろえます（そろえないと `q_proj` で `mat1 and mat2 must have the same dtype` になります）。`config.json` には `"vocab_size": 1026` も書きます（`NeuronModelRunner` が直接読みます）。そのうえで、実機で `llm.generate()` を動かすには、次の設定が要りました。

| 起きたこと | この検証での対処 |
| --- | --- |
| on-device sampling（実機の上でトークンまで選ぶ機能）が既定のまま有効だと、runner は CPU のサンプラーを使わず、このモデルの `forward()` が返す bf16 の logits を選び終えたトークン ID として扱い、`Got unsupported ScalarType BFloat16` で止まる | `additional_config={"neuron_config": {"on_device_sampling_config": None}}` |
| 非同期のスケジューリングは既定で有効で、on-device sampling を無効にすると `On-device sampling must be enabled for async execution` で止まる | `async_scheduling=False` |
| エンジンが複数のプロセスで動くので、`NEURON_RT_VISIBLE_CORES` が設定されていると起動時に止まる | `NEURON_RT_VISIBLE_CORES` を解除し、`NEURON_VISIBLE_DEVICES=0` を設定する |
| EFA の無いインスタンスで、起動時の EFA の検出が失敗する | `NEURON_SKIP_EFA_AFFINITY=1` |
| 実機では `enforce_eager=True` を使えない | `enforce_eager=False` |
| 起動時に入力の形の組み合わせを先にコンパイルしておく処理で、`neuronx-cc compilation failed with 70` になる | `VLLM_NEURON_DEBUG_MODE=1` でこの処理を飛ばす。この変数は `torch.compile` の `fullgraph` も切るデバッグ用の設定で、エンジン経由の結果はこの設定で測った。status 70 の原因はまだ調べていない |
| vLLM は既定で、使えるデバイスのメモリのほぼすべてを KV キャッシュに割り当てようとする。論理 NeuronCore 1 つ（trn2.3xlarge は LNC=2）に対応する約 24GB の HBM のうち 23.4GB がテンソルで埋まり、出力の 113 MiB を確保できずに `nrt_tensor_allocate status=4` になる | `gpu_memory_utilization=0.2` |

生成は、検証のスクリプトの設定で `max_num_seqs=1`、`tensor_parallel_size=1`、`max_model_len=170`、`max_tokens=100`、`temperature=0.0`、`stop_token_ids=[1025]` にして行いました。

## 結果

本物の参照音声（XTTS-v2 に付いている `samples/en_sample.wav`）と文 "The quick brown fox jumps over the lazy dog near the riverbank." を使い、話者の特徴 32 トークンと文 37 トークンの、合わせて 69 トークンを前に置いて、貪欲法（毎回いちばん確率の高いトークンを選ぶ方法）で生成しました。3 つの列は、同じ参照音声と文を使った別々の実行です。CPU の 2 列は CPU の eager 実行です。実機の列は、この記事のすべての直しを入れたモデルを、trn2.3xlarge で改造していない `llm.generate()` から、前の節の設定で動かした値です。

波形を作る処理は、どの列も CPU で行いました。開始と終わりのトークンを除いた音声コードを m1 から mK として、`[前置き, 開始のトークン, m1, ..., m(K-1)]` を CPU のデコーダにもう一度通し（teacher forcing）、K 個の位置の `final_norm` のあとの隠れ状態を取り出します。それを話者の埋め込みと一緒に CPU の HifiDecoder に渡して、24kHz の波形にしました。WER は、Whisper の `base.en` の文字起こしと正解の文を、小文字にして句読点を除いてから `jiwer` で計算しました。

| 項目 | CPU（fp32） | CPU（bf16） | Trainium2（vLLM のエンジン、bf16） |
| --- | --- | --- | --- |
| 系列の長さ（開始と終わりのトークンを含む） | 77 | 76 | 76 |
| 最初に生成したトークン | 225 | 225 | 225 |
| CPU（bf16）の系列との一致 | 4 つ目で分かれる | ― | すべて同じ |
| WER | 8.3% | 8.3% | 8.3% |
| 文字起こし | "Quick brown fox jumps over the lazy dog near the riverbank." | 同じ | 同じ |

3 つとも、12 語のうち抜けたのは同じ "The" の 1 語でした。CPU fp32 の列は、開始のトークンを含めて 4 つ目で 487 を選び、CPU bf16 と実機は 299 を選びます。この文と参照音声では、実機でエンジンを通した系列が CPU の bf16 の系列と 1 つ残らず同じでした。エンジン経由の速さは測っていません。

## まとめ

trn2.3xlarge と Neuron SDK 2.32.0 の DLC イメージで、`tensor_parallel_size=1`、`max_num_seqs=1` の場合に、XTTS v2 の GPT デコーダを vllm-neuron のモデルとして書くと、改造していない `llm.generate()` から、1 つの文と 1 つの参照音声で CPU の bf16 と同じ系列と同じ WER 8.3% の音声ができました。そのために、prefill の注意には書き込んだキャッシュから読み戻した K と V を渡し、モデルをエンジンが渡す位置と block table に合わせ、インストール済みの vllm-neuron の `neuron_model_runner.py` に 1 行のパッチを当てています。
