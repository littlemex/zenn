## はじめに

音声合成モデル XTTS v2 の中核には、GPT-2 と同じ構造を持つ 30 層のデコーダが入っています。音声合成の「次の音声トークンを予測する」部分を、素の GPT-2 ブロックが担っているということです。この記事では、その GPT デコーダを AWS の Trainium2 チップに移植する作業を、vllm-neuron という移植先を使って実機で最後までやってみた記録を残します。

比較対象は、同じモデルを NxD Inference という別の移植手段で Trainium に載せた既存の実装です。NxD Inference 版は trn1 上で静的な系列長 1081 に固定してコンパイルし、Hugging Face の generate API をそのまま使うために `NeuronGPT2InferenceModel` という橋渡し用のクラスを自分で書いていました。今回は同じモデルを vllm-neuron 側の仕組みに乗せたときに、何を書かずに済み、何を自分の手で書く必要があったのか、そして実機でどんなバグに当たったのかを、実際に打ったコマンドと出力だけを使って説明します。

検証に使ったのは ap-southeast-4 (Melbourne) の EKS 上の trn2.3xlarge インスタンス 1 台です。Capacity Block という時間貸しの仕組みで確保した 1 台だけなので、他のプロジェクトのノードに影響しないよう名前空間とノード選択を分離した上で作業しました。

## XTTS v2 の GPT デコーダはどういうものか

XTTS v2 は、参照音声から取った「声の特徴」(conditioning latent) と、読み上げたいテキストの埋め込みを前置きにして、そこから音声トークン (mel token) を 1 つずつ自己回帰的に生成していくモデルです。生成された音声トークン列は、最後に HiFi-GAN 系のボコーダー (HifiDecoder) に通して波形に変換されます。

今回移植した GPT デコーダ部分の仕様は次の通りです。

- 隠れ次元 1024、注意ヘッド数 16、層数 30 の GPT-2 ブロックそのもの
- 音声トークンの語彙数は 1026 個 (1024 が開始トークン、1025 が終了トークン)
- テキストトークナイザーや参照音声の条件づけエンコーダ、ボコーダーは対象外で、GPT デコーダだけを Trainium に載せる

この最後の点が重要です。テキストのトークン化や条件づけ latent の計算、波形生成は CPU 側でそのまま real な coqui-tts の実装を使い、Trainium に載せるのは「次の音声トークンを予測する」計算だけに絞っています。NxD Inference 版の既存実装も同じ切り方をしているので、比較の土台は揃っています。

## vllm-neuron に移植するとは、具体的に何をすることか

vllm-neuron は vLLM という推論エンジンの Trainium 版バックエンドです。新しいモデルを載せるには、HuggingFace 形式の `config.json` と重みファイルを渡すと、`forward()` が呼ばれて次トークンの確率が返ってくる、という形にモデルクラスを書く必要があります。vLLM 側はリクエストのスケジューリングや KV キャッシュのページング管理を全部やってくれるので、モデル作者が書くのは「このモデル固有の計算」だけです。

NxD Inference 版と比べて、何を書かずに済んだかを並べると次のようになります。

| | NxD Inference 版 (既存) | vllm-neuron 版 (今回) |
|---|---|---|
| generate API との橋渡し | `NeuronGPT2InferenceModel` を自分で書き、ダミーの `past_key_values` を仕込んで generate ループに割り込む | 不要。`prompt_embeds` と `is_token_ids` は vLLM がリクエスト単位で持っている概念で、ページング KV キャッシュもそのまま使える |
| prefill と decode の分離 | 2 つの別アプリケーションに分け、KV を CPU 経由で受け渡す | 1 つのモデルの中で `attn_metadata` を見て分岐するだけ |
| 系列長 | 1081 固定でコンパイル | 固定長を強制されない (ただし本番の vLLM エンジンが使うバケット分割は今回検証していません) |

一方で、vllm-neuron の「自分の演算子を書く自由」は諸刃の剣でもありました。これは後述するバグの原因にもなっています。

## 実機で見つけた本物のバグ

ここからは実際に手で触って見つけた問題を順番に説明します。すべて実際のコマンドとエラーメッセージをもとにしています。

### バグ 1 KV キャッシュへの書き込み順序が入れ替わっていた

Prefill (最初の長い入力をまとめて処理する) と、decode (1 トークンずつ生成する) を同じ 1 回の推論として一発で計算した場合と、prefill してから decode を繰り返した場合で、本来は同じロジットが出るはずです。これを比較する回帰テストを書いたところ、2 つが一致しませんでした。

原因は KV キャッシュへの書き込みコードにありました。キャッシュのインデックスは「ヘッド番号を外側、トークン位置を内側」にして並べて作っていたのに、書き込む値 (`k`, `v` テンソル) は「トークン位置を外側」にして並び替えてしまっていたため、ヘッド数とトークン数が異なるときにキャッシュの違う場所に値が書き込まれていました。1 回の prefill だけの推論では自分の計算結果をそのまま使うのでこのズレは見えず、後で decode がそのキャッシュを読みに来たときだけ症状が出る、という見つけにくいバグでした。

### バグ 2 decode 用マスク関数が前提にしている KV レイアウトが違っていた

バグ1を直したあとも、prefill と decode を分けた結果が完全には一致しませんでした (コサイン類似度 0.9998 まで近づくものの、わずかにずれる)。

vllm-neuron には decode 時の注意マスクを作る `gen_attention_decode_mask` という関数が用意されています。これを使っていたのですが、位置を変えて出力を調べてみると、本来無効であるはずのインデックスが常に有効扱いになっていました。関数のコードを読むと、この関数は「生成中のトークン自身の K/V を、キャッシュの一番最後のスロットに書く」という別の関数 (`attention_decode`) とペアで使うことを前提にしており、そのペア用に「末尾のスロットは常に有効」という上書きが入っていました。今回の実装は K/V を実際のスロット番号にそのまま書いているので、このペアの前提と噛み合わず、キャッシュの末尾に残っていたゴミを常に見てしまっていたのです。

教訓は、「ペアになっている演算子の片方だけを借りて、自分のキャッシュ規約と組み合わせる」のは危険だということです。修正は、既知の位置情報から自分でマスクを組み立てる 2 行のコードに置き換えることでした。

### バグ 3、4 本物の重みを読み込んで初めてアーキテクチャの誤りが見つかった

ランダムな重みでのテストが全部通ったあと、公開されている `coqui/XTTS-v2` の本物のチェックポイントを読み込んでみました。すると、2 つの思い込みが誤っていたことが判明しました。

1 つ目は、最終層の正規化 (LayerNorm) が 1 つしかないと思っていたのに、本物のチェックポイントには GPT-2 本体の `ln_f` に加えて、XTTS 独自の `final_norm` という 2 つ目の LayerNorm が存在していました。ランダム初期化の重みで試していたときは「1 つの LayerNorm っぽい何か」で押し通せてしまい、見た目には問題が分からなかったのです。本物の、別々に学習された重みが入って初めて、2 つの LayerNorm の値が食い違っていることに気づけました。

2 つ目は、位置埋め込みの持ち方です。GPT-2 本体が持っている絶対位置埋め込みテーブルをそのまま使っていると思い込んでいたのですが、実際のチェックポイントには GPT-2 本体の `wte`/`wpe` キーが一切存在しませんでした。XTTS の実装では、GPT-2 本体の埋め込みを削除し、代わりにテキスト用とメル (音声) 用、それぞれ別のローカルな (0 から数え直す) 位置埋め込みテーブルを使っています。これに合わせて実装を直しました。

### バグ 5 コンパイラ自体に gelu のキーワード引数を扱えないバグがあった

本物の 30 層モデルを初めて実機でコンパイルしようとしたところ、`apply() takes no keyword arguments` という謎のエラーで落ちました。デフォルトのエラーハンドラがプロセスを `sys.exit()` してしまうため、本当のスタックトレースを見るためにエラー処理部分を一時的にパッチして調べたところ、原因は GELU 活性化関数 (tanh 近似) にありました。

:::details 実際に出たエラー
```
FATAL: apply() takes no keyword arguments
...
File ".../libtorch_neuronx_lite/xla_impl/base.py", line 167, in wrapper
    return custom_call_cls.apply(*args, **kwargs)
File ".../torch/autograd/function.py", line 596, in apply
    return super().apply(*args, **kwargs)
TypeError: apply() takes no keyword arguments
```
:::

PyTorch の FX トレーサーは `gelu(x, approximate="tanh")` という呼び方を、呼び出し方 (位置引数かキーワード引数か) に関係なく、内部的にキーワード引数の形へ正規化してしまいます。ところが Neuron 側のコンパイラバックエンドは、そのキーワード引数をそのまま `torch.autograd.Function.apply()` に渡そうとし、`apply()` はキーワード引数を受け取れないという PyTorch 自体の制約に引っかかってクラッシュしていました。これはモデル作者側の書き方では避けられない、インストールされていたコンパイラのバグです。

回避策は単純で、`gelu` のカスタム演算子を使わず、tanh 近似の数式をそのまま四則演算と `tanh` だけで書き直すことでした。CPU 上で元の `gelu` と完全に一致することを確認してから、実機側でもこの書き直した式を使っています。

```python
hidden_states = 0.5 * x * (1.0 + torch.tanh(
    0.7978845608028654 * (x + 0.044715 * x * x * x)
))
```

## 実機の精度のずれを調べる

30 層すべてを本物の重みで動かし、実機 (device) と CPU の出力を比べると、コサイン類似度は 0.976 ほどで、最も確率が高いトークン (argmax) も一致しませんでした。最初に立てた仮説は、「CPU 側は float32 で計算していて、device 側は暗黙に bf16 で計算しているから、比較の前提が揃っていないだけではないか」というものでした。

これを確かめるため、CPU 側と device 側、両方を bf16 で宣言してから比べ直しました。

```
pair                                  max_abs_diff       cosine  argmax_a  argmax_b  match
ref_fp32_vs_port_cpu_fp32             7.629395e-06   1.00000012       225       225    YES
ref_bf16_vs_port_cpu_bf16             1.093750e-01   0.99995363       225       225    YES
ref_bf16_vs_port_dev_bf16             3.531250e+00   0.97915316       225      1023     NO
```

CPU 側だけで比べると float32 でも bf16 でも、独立に実装した参照コードとこの移植版はほぼ完全に一致します。ところが bf16 同士で device と CPU を比べても、ずれの大きさは変わりませんでした。つまり、「比較の精度を揃えれば消えるはずのずれ」という最初の仮説は誤りだったことになります。

続けて 2 つの可能性を実機で潰しました。1 つは、コンパイラの `--auto-cast` オプション (精度を自動で変える設定) が原因ではないか、というものです。小さい 2 層モデルで `none`/`all`/デフォルトの 3 通りを試しましたが、結果はほとんど変わりませんでした。もう 1 つは、device 側の出力が入力を無視した「壊れた」値を返しているだけではないか、というものです。3 つの異なる入力を device に渡したところ、それぞれ違う argmax (225、323、1023) が返ってきて、出力の値も入力ごとに自然に変化していました。device はちゃんと入力に応じた計算をしている、ということです。

結論として、このずれの正体はこの検証の範囲では特定できませんでした。ただ、ずれの大きさが層数とともに大きくなること (2 層では コサイン類似度 0.998、30 層では 0.976-0.979)、そして上に挙げた 3 つの可能性をどれも実機で確認して除外できたことから、「Trainium2 の行列演算エンジンが、宣言した dtype に関係なく内部的に低い精度で計算している」という仮説は依然として最も有力ですが、これは実際にコンパイル済みの計算グラフ (HLO) を覗いて確認したわけではないので、仮説のままです。この調査には「同じ穴を 2 時間以上掘らない」という時間の制約を設けており、今回はここで切り上げています。

## 本物の声と本物のテキストで、実際に生成してみる

ここまでのテストはすべて、条件づけ latent の部分をランダムなノイズやゼロで置き換えていました。実際に意味のある音声が出るかを確かめるには、本物の参照音声から取った条件づけ latent と、本物のテキスト埋め込みが必要です。

coqui-tts の実装をそのまま使えば、本物の `ConditioningEncoder` と `PerceiverResampler` を手で再実装する必要はありません。ただし coqui-tts は依存ライブラリのバージョンがかなり特殊 (`transformers` の特定の範囲、`torchcodec` が必要など) なので、Trainium 側の torch 環境を壊さないよう、別の仮想環境を切って coqui-tts をインストールしました。

coqui/XTTS-v2 のリポジトリに同梱されている公式のサンプル音声 `samples/en_sample.wav` を参照音声として使い、本物の `get_conditioning_latents()` で 32 トークン分の条件づけ latent を取得しました。読み上げるテキストには "The quick brown fox jumps over the lazy dog near the riverbank." を選び、本物のトークナイザーとテキスト埋め込みの重みで 37 トークンの埋め込みを作りました。合わせて 69 トークンの前置きです。

この本物の前置きを使って、CPU と実機それぞれで貪欲法 (argmax) による自己回帰生成を実行しました。

```
CPU: 77 トークンを 2.73 秒で生成 (prefill 122.0ms, decode 平均 34.6ms/トークン)
生成列: [1024, 225, 373, 487, 82, 623, ... , 1006, 1025]
```

CPU 側は 77 トークンを生成した時点で、終了トークン (1025) に自然に到達して止まりました。これは、prefill、decode、KV キャッシュの成長、注意マスク、終了判定という移植版の仕組み全体が、1 回の forward だけでなく複数ステップにわたって正しく動いていることの、最も強い証拠です。

一方、実機側は最初の 1 トークン目から CPU と結果が分かれ、その後は同じトークン (1011) を繰り返すだけになり、200 トークンの上限まで終了トークンに到達しませんでした。前の節で見た精度のずれが、自己回帰のループの中で毎ステップ積み重なり、最終的に発散してしまったと考えられます。

:::details 実機側の生成列 (最初の数十トークンのみ抜粋)
```
[1024, 1023, 235, 977, 1000, 1011, 1011, 1011, 1011, 1011, 1011, ...(以下 1011 の繰り返し)]
```
:::

## 生成した音声トークンを波形にして、文字起こしで答え合わせする

CPU 側で生成できた 77 トークンの音声トークン列を、実際の音声に変換してみます。ここで 1 つ注意が必要でした。coqui-tts のボコーダー (HifiDecoder) は、生成された音声トークンの ID をそのまま受け取るのではなく、GPT デコーダの最終 LayerNorm (`final_norm`) を通した後の隠れ状態 (latent) を受け取る設計になっています。そこで、CPU で生成した音声トークン列をもう一度、今度は teacher forcing (正解を入力に使う) で forward に通し、`final_norm` 直後の隠れ状態を 75 個取り出しました。

```
gpt_latents shape: torch.Size([75, 1024])
```

これを本物の `HifiDecoder` に通すと、3.48 秒の波形 (24kHz) が得られました。

```
wav shape: torch.Size([83456]) duration: 3.48 秒
```

この波形を Whisper (`base.en`) で文字起こしして、元のテキストと比較しました。

```
文字起こし: "Quick brown fox jumps over the lazy dog near the riverbank."
正解テキスト: "The quick brown fox jumps over the lazy dog near the riverbank."
WER (単語誤り率): 8.3%
```

12 単語のうち 1 単語 ("The") が欠落しただけで、残りは完全に一致しました。これは、本物の参照音声の条件づけから、本物のテキスト、この移植版自身の CPU 上での推論、本物のボコーダー、本物の Whisper での文字起こしまで、すべて実際に動かして得られた結果です。

参考として、NxD Inference 版が報告している WER は BF16 で 12.5%、FP16 では精度が崩れて 68.8% でした。今回得られた 8.3% という数字はこれより低いものの、これは CPU 上での推論結果であり、NxD Inference 版の数字は Trainium 実機上での数字です。使っている文章も声も違うため、ハードウェアを揃えた公平な比較にはなっていません。あくまで「実際に動かして測った数字」として記録しています。device 側は前節の通り生成が崩れてしまったため、device 側の WER は今回測定できていません。

## vLLM の推論エンジンに実際に registry してみる

ここまでのテストはすべて、モデルの `forward()` を直接呼び出すレベルの検証でした。実際の vLLM の `LLM()` エンジンに登録して、スケジューラやリクエスト管理を含めた本番相当の経路で動かせるかどうかも試しています。

`ModelRegistry.register_model` でモデルクラスを登録し、`LLM(model=MODEL_DIR, dtype="bfloat16", enable_prompt_embeds=True, ...)` を呼び出すところまでは進めましたが、途中で 3 つの実際の問題に当たりました。

1 つ目は、重みの dtype とエンジンに指定した dtype が噛み合っていないという問題です。`config.json` には `float32` と書きつつ、重みファイルの dtype を変えずに bf16 のエンジンへ渡したため、自分のモデルコードの中の `q_proj` で `mat1 and mat2 must have the same dtype` というエラーになりました。モデル用のディレクトリを作るスクリプト側で、重みを `config.json` の dtype に合わせてキャストするよう修正しました。

2 つ目は、vLLM 側のモデルランナーが `hf_config.vocab_size` という属性を直接読みに来るという問題です。今回使っていた簡易な設定クラスはこの属性を持っていなかったため、`AttributeError` になりました。`config.json` に `vocab_size` を追加して解決しています。

3 つ目は、この 2 つを直した後に起きたものです。`llm.generate()` を呼び出すと、実際にエンジンのスケジューラを通って本物の forward 呼び出しが実行されました (自分のモデルコードに仕込んだデバッグ出力が、実際の bf16 テンソルとともに発火したことで確認できます)。しかし、その後 vLLM-neuron 側の汎用的な出力パース処理 (`_parse_rejection_sampling_output`) の中で、`output_token_ids.cpu().numpy()` が `TypeError: Got unsupported ScalarType BFloat16` で落ちました。これは個々のモデルの実装に依存しない、エンジン側の共通コードの中で起きている問題です。numpy には bf16 の型が存在しないため、本来は整数のトークン ID のはずのテンソルが bf16 のまま流れてきてしまっているようでした。

このエンジン側の問題は、モデルの `forward()` を直す範囲では解決できないため、今回はここで検証を止めています。モデル登録、エンジンの構築、スケジューラを通した本物の forward 呼び出しまでは実機で確認できましたが、`generate()` を最後まで通すことはできませんでした。

## 到達した点と、到達しなかった点のまとめ

実際に実機で確認できたことは次の通りです。

- 本物の重みで CPU 上では、独立に実装した参照コードと完全に近い精度で一致すること (float32、bf16 のどちらでも)
- 実機 (Trainium2) で 30 層モデルのコンパイルと forward 実行ができること
- 本物の条件づけ latent と本物のテキストから、CPU 上で意味のある音声トークン列を自己回帰生成でき、終了トークンまで自然に到達すること
- その音声トークン列を本物のボコーダーで波形にし、Whisper での文字起こしによる WER が 8.3% であること
- vLLM の `LLM()` エンジンに登録し、スケジューラを通した本物の forward 呼び出しまで到達すること

今回のセッションで到達しなかったことは次の通りです。

- 実機と CPU の精度のずれの正確な原因 (コンパイル済み計算グラフの中身までは覗いていません)
- 実機側での、崩れずに終了トークンまで到達する自己回帰生成 (精度のずれが自己回帰のループで積み重なり、途中で崩れてしまいました)

## まとめ

XTTS v2 の GPT デコーダを vllm-neuron に移植する作業では、vLLM 側がリクエスト管理と KV キャッシュのページングを担ってくれる分、HuggingFace の generate API 向けの橋渡しコードや、prefill/decode を分けた別アプリケーション、CPU 経由の KV 受け渡しといった、NxD Inference 版で必要だった仕組みを書かずに済みました。その代わり、用意されている演算子を自分のキャッシュ規約と組み合わせる際の前提のズレ (decode マスク)、本物の重みを読んで初めて見える構造の誤り (2 つ目の LayerNorm、ローカルな位置埋め込み)、インストールされていたコンパイラ自体のバグ (gelu のキーワード引数) という、実機で手を動かさないと見つからない問題にいくつも当たりました。

本物の参照音声と本物のテキストを使った CPU 上での生成は、終了トークンまで自然に到達し、文字起こしの単語誤り率は 8.3% でした。一方で実機側は精度のずれが自己回帰生成の中で積み重なり、崩れてしまいました。この精度のずれの正体の特定と、vLLM エンジンでの生成を最後まで通すことは、次の検証に引き継ぐ課題として残っています。
