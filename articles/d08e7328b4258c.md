## はじめに

音声合成モデル XTTS v2 の中核には、GPT-2 と同じ構造を持つ 30 層のデコーダが入っています。音声合成の「次の音声トークンを予測する」部分を、素の GPT-2 ブロックが担っているということです。この記事では、その GPT デコーダを AWS の Trainium2 チップに移植する作業を、vllm-neuron という移植先を使って実機で最後までやってみた記録を残します。

比較対象は、同じモデルを NxD Inference という別の移植手段で Trainium に載せた既存の実装です。NxD Inference 版は trn1 上で静的な系列長 1081 に固定してコンパイルし、Hugging Face の generate API をそのまま使うために `NeuronGPT2InferenceModel` という橋渡し用のクラスを自分で書いていました。今回は同じモデルを vllm-neuron 側の仕組みに乗せたときに、何を書かずに済み、何を自分の手で書く必要があったのか、そして実機でどんなバグに当たったのかを、実際に打ったコマンドと出力だけを使って説明します。

検証に使ったのは ap-southeast-4 (Melbourne) の EKS 上の trn2.3xlarge インスタンス 1 台です。Capacity Block という時間貸しの仕組みで確保した 1 台だけなので、他のプロジェクトのノードに影響しないよう名前空間とノード選択を分離した上で作業しました。

## XTTS v2 の GPT デコーダはどういうものか

XTTS v2 は、参照音声から取った「声の特徴」(conditioning latent) と、読み上げたいテキストの埋め込みを前置きにして、そこから音声トークン (mel token) を 1 つずつ自己回帰的に生成していくモデルです。生成された音声トークン列は、最後に HiFi-GAN 系のボコーダー (HifiDecoder) に通して波形に変換されます。

今回移植した GPT デコーダ部分の仕様は次の通りです。

- 隠れ次元 1024、注意ヘッド数 16、層数 30 の GPT-2 ブロックそのもの
- 音声トークンの語彙数は 1026 個 (1024 が開始トークン、1025 が終了トークン)
- テキストトークナイザーや参照音声の条件づけエンコーダ、ボコーダーは対象外で、GPT デコーダだけを Trainium に載せる

この最後の点が重要です。テキストのトークン化や条件づけ latent の計算、波形生成は CPU 側でそのまま real な coqui-tts の実装を使い、Trainium に載せるのは「次の音声トークンを予測する」計算だけに絞っています。NxD Inference 版の既存実装も同じ切り方をしているので、比較の土台は揃っています。

## vllm-neuron に移植するとは、具体的に何をすることか

vllm-neuron は vLLM という推論エンジンの Trainium 版バックエンドです。新しいモデルを載せるには、HuggingFace 形式の `config.json` と重みファイルを渡すと、`forward()` が呼ばれて次トークンの確率が返ってくる、という形にモデルクラスを書く必要があります。vLLM 側はリクエストのスケジューリングや KV キャッシュのページング管理を全部やってくれるので、モデル作者が書くのは「このモデル固有の計算」だけです。

NxD Inference 版と比べて、何を書かずに済んだかを並べると次のようになります。

| | NxD Inference 版 (既存) | vllm-neuron 版 (今回) |
|---|---|---|
| generate API との橋渡し | `NeuronGPT2InferenceModel` を自分で書き、ダミーの `past_key_values` を仕込んで generate ループに割り込む | 不要。`prompt_embeds` と `is_token_ids` は vLLM がリクエスト単位で持っている概念で、ページング KV キャッシュもそのまま使える |
| prefill と decode の分離 | 2 つの別アプリケーションに分け、KV を CPU 経由で受け渡す | 1 つのモデルの中で `attn_metadata` を見て分岐するだけ |
| 系列長 | 1081 固定でコンパイル | 固定長を強制されない (ただし本番の vLLM エンジンが使うバケット分割は今回検証していません) |

一方で、vllm-neuron の「自分の演算子を書く自由」は諸刃の剣でもありました。これは後述するバグの原因にもなっています。

## 実機で見つけた本物のバグ

ここからは実際に手で触って見つけた問題を順番に説明します。すべて実際のコマンドとエラーメッセージをもとにしています。

### バグ 1 KV キャッシュへの書き込み順序が入れ替わっていた

Prefill (最初の長い入力をまとめて処理する) と、decode (1 トークンずつ生成する) を同じ 1 回の推論として一発で計算した場合と、prefill してから decode を繰り返した場合で、本来は同じロジットが出るはずです。これを比較する回帰テストを書いたところ、2 つが一致しませんでした。

原因は KV キャッシュへの書き込みコードにありました。キャッシュのインデックスは「ヘッド番号を外側、トークン位置を内側」にして並べて作っていたのに、書き込む値 (`k`, `v` テンソル) は「トークン位置を外側」にして並び替えてしまっていたため、ヘッド数とトークン数が異なるときにキャッシュの違う場所に値が書き込まれていました。1 回の prefill だけの推論では自分の計算結果をそのまま使うのでこのズレは見えず、後で decode がそのキャッシュを読みに来たときだけ症状が出る、という見つけにくいバグでした。

### バグ 2 decode 用マスク関数が前提にしている KV レイアウトが違っていた

バグ1を直したあとも、prefill と decode を分けた結果が完全には一致しませんでした (コサイン類似度 0.9998 まで近づくものの、わずかにずれる)。

vllm-neuron には decode 時の注意マスクを作る `gen_attention_decode_mask` という関数が用意されています。これを使っていたのですが、位置を変えて出力を調べてみると、本来無効であるはずのインデックスが常に有効扱いになっていました。関数のコードを読むと、この関数は「生成中のトークン自身の K/V を、キャッシュの一番最後のスロットに書く」という別の関数 (`attention_decode`) とペアで使うことを前提にしており、そのペア用に「末尾のスロットは常に有効」という上書きが入っていました。今回の実装は K/V を実際のスロット番号にそのまま書いているので、このペアの前提と噛み合わず、キャッシュの末尾に残っていたゴミを常に見てしまっていたのです。

教訓は、「ペアになっている演算子の片方だけを借りて、自分のキャッシュ規約と組み合わせる」のは危険だということです。修正は、既知の位置情報から自分でマスクを組み立てる 2 行のコードに置き換えることでした。

### バグ 3、4 本物の重みを読み込んで初めてアーキテクチャの誤りが見つかった

ランダムな重みでのテストが全部通ったあと、公開されている `coqui/XTTS-v2` の本物のチェックポイントを読み込んでみました。すると、2 つの思い込みが誤っていたことが判明しました。

1 つ目は、最終層の正規化 (LayerNorm) が 1 つしかないと思っていたのに、本物のチェックポイントには GPT-2 本体の `ln_f` に加えて、XTTS 独自の `final_norm` という 2 つ目の LayerNorm が存在していました。ランダム初期化の重みで試していたときは「1 つの LayerNorm っぽい何か」で押し通せてしまい、見た目には問題が分からなかったのです。本物の、別々に学習された重みが入って初めて、2 つの LayerNorm の値が食い違っていることに気づけました。

2 つ目は、位置埋め込みの持ち方です。GPT-2 本体が持っている絶対位置埋め込みテーブルをそのまま使っていると思い込んでいたのですが、実際のチェックポイントには GPT-2 本体の `wte`/`wpe` キーが一切存在しませんでした。XTTS の実装では、GPT-2 本体の埋め込みを削除し、代わりにテキスト用とメル (音声) 用、それぞれ別のローカルな (0 から数え直す) 位置埋め込みテーブルを使っています。これに合わせて実装を直しました。

### バグ 5 コンパイラ自体に gelu のキーワード引数を扱えないバグがあった

本物の 30 層モデルを初めて実機でコンパイルしようとしたところ、`apply() takes no keyword arguments` という謎のエラーで落ちました。デフォルトのエラーハンドラがプロセスを `sys.exit()` してしまうため、本当のスタックトレースを見るためにエラー処理部分を一時的にパッチして調べたところ、原因は GELU 活性化関数 (tanh 近似) にありました。

:::details 実際に出たエラー
```
FATAL: apply() takes no keyword arguments
...
File ".../libtorch_neuronx_lite/xla_impl/base.py", line 167, in wrapper
    return custom_call_cls.apply(*args, **kwargs)
File ".../torch/autograd/function.py", line 596, in apply
    return super().apply(*args, **kwargs)
TypeError: apply() takes no keyword arguments
```
:::

PyTorch の FX トレーサーは `gelu(x, approximate="tanh")` という呼び方を、呼び出し方 (位置引数かキーワード引数か) に関係なく、内部的にキーワード引数の形へ正規化してしまいます。ところが Neuron 側のコンパイラバックエンドは、そのキーワード引数をそのまま `torch.autograd.Function.apply()` に渡そうとし、`apply()` はキーワード引数を受け取れないという PyTorch 自体の制約に引っかかってクラッシュしていました。これはモデル作者側の書き方では避けられない、インストールされていたコンパイラのバグです。

回避策は単純で、`gelu` のカスタム演算子を使わず、tanh 近似の数式をそのまま四則演算と `tanh` だけで書き直すことでした。CPU 上で元の `gelu` と完全に一致することを確認してから、実機側でもこの書き直した式を使っています。

```python
hidden_states = 0.5 * x * (1.0 + torch.tanh(
    0.7978845608028654 * (x + 0.044715 * x * x * x)
))
```

## 実機の精度のずれを調べる

30 層すべてを本物の重みで動かし、実機 (device) と CPU の出力を比べると、コサイン類似度は 0.976 ほどで、最も確率が高いトークン (argmax) も一致しませんでした。最初に立てた仮説は、「CPU 側は float32 で計算していて、device 側は暗黙に bf16 で計算しているから、比較の前提が揃っていないだけではないか」というものでした。

これを確かめるため、CPU 側と device 側、両方を bf16 で宣言してから比べ直しました。

```
pair                                  max_abs_diff       cosine  argmax_a  argmax_b  match
ref_fp32_vs_port_cpu_fp32             7.629395e-06   1.00000012       225       225    YES
ref_bf16_vs_port_cpu_bf16             1.093750e-01   0.99995363       225       225    YES
ref_bf16_vs_port_dev_bf16             3.531250e+00   0.97915316       225      1023     NO
```

CPU 側だけで比べると float32 でも bf16 でも、独立に実装した参照コードとこの移植版はほぼ完全に一致します。ところが bf16 同士で device と CPU を比べても、ずれの大きさは変わりませんでした。つまり、「比較の精度を揃えれば消えるはずのずれ」という最初の仮説は誤りだったことになります。

続けて 2 つの可能性を実機で潰しました。1 つは、コンパイラの `--auto-cast` オプション (精度を自動で変える設定) が原因ではないか、というものです。小さい 2 層モデルで `none`/`all`/デフォルトの 3 通りを試しましたが、結果はほとんど変わりませんでした。もう 1 つは、device 側の出力が入力を無視した「壊れた」値を返しているだけではないか、というものです。3 つの異なる入力を device に渡したところ、それぞれ違う argmax (225、323、1023) が返ってきて、出力の値も入力ごとに自然に変化していました。device はちゃんと入力に応じた計算をしている、ということです。

### どの演算がずれを生んでいるのか、1 つずつ切り分ける

30 層まとめて比べるだけでは「どこかで何かがずれている」ことしか分かりません。そこで、GPT ブロックの中の演算 (LayerNorm、注意機構、出力の射影、残差の足し算、MLP) を 1 つずつ取り出し、CPU で計算した「正解」の入力をそのまま device に渡して、その演算 1 回分だけの device と CPU の違いを測りました。前の層のズレを持ち込まないようにする工夫です。

```
注意機構 (NF.flash_attention) だけ:        コサイン類似度 0.9999971 〜 1.0000006 (ほぼ完全一致)
LayerNorm だけ:                            コサイン類似度 0.9999934 〜 0.9999966
出力の射影 (o_proj) だけ:                   コサイン類似度 0.9999970 〜 1.0000066
残差の足し算だけ (大きい値 + 小さい値):      誤差 0 (device と CPU で完全に同じビット列)
MLP (fc→GELU→proj) だけ:                   コサイン類似度 0.9999763 〜 0.9999970
```

どの演算も、1 つだけ取り出すと device と CPU のずれは bf16 (16 bit の浮動小数点) というデータ形式そのものが持つ普通の丸め誤差の範囲 (1% 未満) に収まっていました。この時点では「どこか 1 か所に単独のバグがあるわけではなく、小さなずれが積み重なっているだけだ」という結論に見えました。残差を高精度 (fp32) に保つ対策も試しましたが効果はなく、ここまでの調査は「これはこの移植版、このチェックポイント、この bf16 という精度、このコンパイラの組み合わせに内在する、直せない積み重なり誤差だ」という結論でいったん切り上げていました。

### その結論は誤りでした

この後の継続作業で、上の結論は誤りだったと分かりました。きっかけは、同じ Trainium2 上で別のモデル (NemotronH) を vllm-neuron に移植した際に、見た目は「コンパイラのバグ」や「bf16 の丸め誤差」に見えた崩れが、実際には移植側のコードの中の本物のバグ 3 つだった、という経験でした。「精度の性質」で片付ける前に、自分のコードのバグを疑い切る必要があるという教訓です。

同じ目で見直すと、1 つ大きな見落としがありました。「注意機構だけを取り出す」実験は、q/k/v を手で取り出して `NF.flash_attention` を直接呼ぶ、という測り方をしていました。これは KV キャッシュへの書き込み (`_write_kv_cache`) と、出力の射影 (`o_proj`) の両方を素通りしています。モデルが実際に呼んでいる経路、つまり `attn.forward()` そのものは、1 度も単独で測っていなかったのです。

まず CPU 側だけで、bf16 と fp32 を比べ直しました。device を完全に外した比較です。

```
30 層通した forward:  fp32 argmax=225  bf16 argmax=225  コサイン類似度=0.999962  一致
全 30 層の隠れ状態のコサイン類似度: 0.9999563 〜 0.9999938 (どの層でも 0.99995 を下回らない)
CPU bf16 での自己回帰生成: 76 トークンで終了トークンに到達
CPU bf16 の WER = 8.3% (CPU fp32 の 8.3% と文字起こし・欠落単語ともに完全一致)
```

CPU だけで比べると、bf16 は device で報告されていたようなずれを一切再現しません。「bf16 という精度そのもの」と「device での実行」は別の話だと、ここで切り離せました。

次に、層 0 の中の 6 つの演算を、CPU の正解値を注入せず、device が実際に計算した値をそのまま次の演算に渡してつなぎ、各段階で CPU の正解と比べました。

```
段階       コサイン類似度   (ln1 の次、attn でいきなり崩れる)
ln1        0.99999428
attn       0.73812622   ← ここで崩壊。層 0 の、上流のずれが一切無い状態で
add1       0.97290587
```

LayerNorm の直後まではコサイン類似度 0.999994 とほぼ完璧なのに、注意機構 (`attn`) を 1 回通すだけでコサイン類似度 0.738 まで落ちていました。これは層 0 の、入力が CPU と device でほぼ同一な状態での結果です。

これを 3 パターンの比較で確認しました。(1) モデルが実際に呼ぶ `attn.forward()` そのもの (KV キャッシュへの書き込み → 注意機構 → 出力射影を 1 つの `torch.compile` 呼び出しにまとめたもの)、(2) 同じものだが KV キャッシュへの書き込みをダミー関数に差し替えて何もしないようにしたもの、(3) 注意機構と出力射影だけを、KV キャッシュへの書き込みを一切経由せず、別々にコンパイルした関数として呼んだもの、の 3 つです。

```
(1) 実際の経路 (KV キャッシュ書き込みあり):              コサイン類似度 0.738172
(2) 同じだが KV キャッシュ書き込みを無効化:              コサイン類似度 0.999997
(3) 注意機構 + 出力射影のみ、書き込みを一切経由しない:    コサイン類似度 0.999997
```

KV キャッシュへの書き込みを外すだけで、コサイン類似度が 0.738 から 0.999997 まで回復しました。30 層すべて、本物の前置きを使った forward でも同じことを確認しました。

```
CPU (fp32) の正解:                        argmax=225
今まで通り (KV キャッシュ書き込みあり):      argmax=1023  コサイン類似度=0.813963
KV キャッシュ書き込みを無効化 (確認用):      argmax=225   コサイン類似度=0.999988
```

**この 1 つの問題が、これまで「bf16 の積み重なり誤差」と呼んでいたものの正体でした。** KV キャッシュへの書き込み (`index_put_` によるスキャッタ書き込み) と、注意機構の NKI カーネル呼び出し (`NF.flash_attention`) が同じ 1 つのコンパイル済み計算グラフの中に入っていると、実機上でカーネルの計算結果そのものが壊れる、というバグです。これまでの「注意機構だけを取り出す」実験は、たまたまこの書き込みを経由しない測り方をしていたため、このバグを一度も見ていませんでした。

### 直せたのか

結論から言うと、原因は特定でき、動く回避策も見つかりましたが、実際の vLLM エンジンがモデルを呼ぶ標準的な方法 (モデル全体を 1 回の `torch.compile()` でまとめてコンパイルする) の中では、まだ使えません。試して効果が無かった方法を含めて記録します。

モデル全体を 1 つの `torch.compile()` でまとめる、という条件のもとで試して、どれも効果が無かったものです。

- `index_put_` (インプレースの書き込み) を `index_put` (新しいテンソルを返す書き込み) に変える: 結果はビット単位で変わらず
- 書き込みのコードを、注意機構の呼び出しより後ろに移動する: 結果はビット単位で変わらず (コンパイラ側のスケジューラが、ソースコード上の順序を尊重していないようでした)
- 書き込み部分だけを別の `torch.compile()` 関数にあらかじめコンパイルしておき、それを呼び出す: 効果なし (外側の `torch.compile()` が、呼び出し先の中身をそのまま自分のグラフに展開してしまうため)
- `torch._dynamo.graph_break()` で計算グラフを強制的に 2 つに分割する: そもそも実行できず、グラフの間をつなぐ普通の Python コードが device 上のテンソルに対してエラーになる
- 書き込みを `torch.library.custom_op` として登録し、コンパイラに「これは不透明な操作だ」と伝える: インプレースの形は明示的に拒否され、新しいテンソルを返す形にしても結果は変わらず

一方で、効果があったのは、書き込みの処理を**完全に別の、トップレベルの `torch.compile()` 呼び出し**にする方法でした。(1) LayerNorm → q/k/v の射影 → 注意機構 → 出力射影 → 残差の足し算、を 1 つのコンパイル (KV キャッシュへの書き込みを含まない)、(2) KV キャッシュへの書き込みだけを、別の 1 つのコンパイル、(3) 2 つ目の LayerNorm → MLP → 残差の足し算、をさらに別の 1 つのコンパイル、という 3 つに分けて手でつなぐと、キャッシュへの書き込みは実際に行われたまま (読み返して確認済み)、コサイン類似度は 0.999997 まで回復しました。

ただし、この方法は呼び出す側が複数のトップレベルの `torch.compile()` 呼び出しを自分で組み立てる必要があり、実際の vLLM エンジンが行う「モデル全体を 1 回の `torch.compile()` でまとめる」という標準的な呼び方の中では、そのままでは使えません。Neuron SDK のコンパイラ自体の修正か、vllm-neuron 側が 1 モデルに対して複数のトップレベルのコンパイル領域を許すようになるかのいずれかが必要です。

## 本物の声と本物のテキストで、実際に生成してみる

ここまでのテストはすべて、条件づけ latent の部分をランダムなノイズやゼロで置き換えていました。実際に意味のある音声が出るかを確かめるには、本物の参照音声から取った条件づけ latent と、本物のテキスト埋め込みが必要です。

coqui-tts の実装をそのまま使えば、本物の `ConditioningEncoder` と `PerceiverResampler` を手で再実装する必要はありません。ただし coqui-tts は依存ライブラリのバージョンがかなり特殊 (`transformers` の特定の範囲、`torchcodec` が必要など) なので、Trainium 側の torch 環境を壊さないよう、別の仮想環境を切って coqui-tts をインストールしました。

coqui/XTTS-v2 のリポジトリに同梱されている公式のサンプル音声 `samples/en_sample.wav` を参照音声として使い、本物の `get_conditioning_latents()` で 32 トークン分の条件づけ latent を取得しました。読み上げるテキストには "The quick brown fox jumps over the lazy dog near the riverbank." を選び、本物のトークナイザーとテキスト埋め込みの重みで 37 トークンの埋め込みを作りました。合わせて 69 トークンの前置きです。

この本物の前置きを使って、CPU と実機それぞれで貪欲法 (argmax) による自己回帰生成を実行しました。

```
CPU: 77 トークンを 2.73 秒で生成 (prefill 122.0ms, decode 平均 34.6ms/トークン)
生成列: [1024, 225, 373, 487, 82, 623, ... , 1006, 1025]
```

CPU 側は 77 トークンを生成した時点で、終了トークン (1025) に自然に到達して止まりました。これは、prefill、decode、KV キャッシュの成長、注意マスク、終了判定という移植版の仕組み全体が、1 回の forward だけでなく複数ステップにわたって正しく動いていることの、最も強い証拠です。

これに対して、前の節で見つけた KV キャッシュ書き込みのバグを直す前の実機側は、最初の 1 トークン目から CPU と結果が分かれ、その後は同じトークン (1011) を繰り返すだけになり、200 トークンの上限まで終了トークンに到達しませんでした。

:::details 直す前の実機側の生成列 (最初の数十トークンのみ抜粋)
```
[1024, 1023, 235, 977, 1000, 1011, 1011, 1011, 1011, 1011, 1011, ...(以下 1011 の繰り返し)]
```
:::

### 直したあとの実機側の生成

前の節で見つけた回避策 (prefill の部分だけ、KV キャッシュへの書き込みを別のトップレベルの `torch.compile()` 呼び出しに分ける) を使って、同じ本物の前置きで実機側の生成をやり直しました。decode の部分は注意機構の NKI カーネルを使わないため、このバグの影響を受けず、今まで通りの呼び方で問題ありません。

```
CPU (fp32):            77 トークン、終了トークンに到達
実機 (直した prefill):  76 トークン、終了トークンに到達
  1 トークン目の argmax: 実機=225, CPU=225  (直す前は実機=1023 でした)
生成列: [1024, 225, 373, 299, 82, 623, 41, 110, 110, 366, 299, 584, 49, 49, 358, 352,
         83, 196, 640, 288, 288, 59, 578, 225, 825, 110, 454, 277, 49, 323, 323, 453,
         454, 20, 323, 323, 53, 323, 323, 323, 69, 323, 323, 277, 396, 4, 336, 92,
         273, 323, 323, 323, 323, 323, 644, 453, 266, 323, 11, 323, 11, 53, 323, 423,
         53, 53, 793, 53, 313, 313, 11, 92, 707, 977, 1006, 1025]
```

実機側の 1 トークン目が、CPU と完全に一致する 225 になりました。生成列全体も、CPU とは 3 トークン目のあとから少しずれますが (CPU は `487`、実機は `299`)、これは前の節で CPU 単体の bf16 で測った、ごく普通の丸め誤差による分かれ方と同じ性質のものです (CPU 側の bf16 版も、同じ場所で同じ `299` に分かれていました)。もはや 1 トークンに崩壊して止まらなくなる、という device 特有の壊れ方ではありません。

## 生成した音声トークンを波形にして、文字起こしで答え合わせする

CPU 側で生成できた 77 トークンと、直したあとの実機側で生成できた 76 トークンの、両方の音声トークン列を、実際の音声に変換してみます。ここで 1 つ注意が必要でした。coqui-tts のボコーダー (HifiDecoder) は、生成された音声トークンの ID をそのまま受け取るのではなく、GPT デコーダの最終 LayerNorm (`final_norm`) を通した後の隠れ状態 (latent) を受け取る設計になっています。そこで、生成した音声トークン列をもう一度、今度は teacher forcing (正解を入力に使う) で forward に通し、`final_norm` 直後の隠れ状態を取り出しました。

```
CPU 側の gpt_latents shape:   torch.Size([75, 1024])
実機側の gpt_latents shape:   torch.Size([74, 1024])
```

これを本物の `HifiDecoder` に通すと、どちらも 3.4 秒前後の波形 (24kHz) が得られました。この波形を Whisper (`base.en`) で文字起こしして、元のテキストと比較しました。

```
CPU (fp32) の文字起こし: "Quick brown fox jumps over the lazy dog near the riverbank."
実機 (直したあと) の文字起こし: "Quick brown fox jumps over the lazy dog near the riverbank."
正解テキスト: "The quick brown fox jumps over the lazy dog near the riverbank."
CPU の WER: 8.3%
実機の WER: 8.3%
```

**実機側の WER は、CPU 側と完全に同じ 8.3% でした。** 12 単語のうち 1 単語 ("The") が欠落しただけで、残りは完全に一致しています。しかも欠落している単語まで CPU と同じです。これは、本物の参照音声の条件づけから、本物のテキスト、実機 (Trainium2) 上でのバグを直した推論、本物のボコーダー、本物の Whisper での文字起こしまで、すべて実際に動かして得られた結果です。

参考として、NxD Inference 版が報告している WER は BF16 で 12.5%、FP16 では精度が崩れて 68.8% でした。今回得られた 8.3% という数字はこれより低いものの、使っている文章も声も違うため、公平な比較にはなっていません。あくまで「実際に動かして測った数字」として記録しています。

## vLLM の推論エンジンに実際に registry してみる

ここまでのテストはすべて、モデルの `forward()` を直接呼び出すレベルの検証でした。実際の vLLM の `LLM()` エンジンに登録して、スケジューラやリクエスト管理を含めた本番相当の経路で動かせるかどうかも試しています。

`ModelRegistry.register_model` でモデルクラスを登録し、`LLM(model=MODEL_DIR, dtype="bfloat16", enable_prompt_embeds=True, ...)` を呼び出すところまでは進めましたが、途中で 3 つの実際の問題に当たりました。

1 つ目は、重みの dtype とエンジンに指定した dtype が噛み合っていないという問題です。`config.json` には `float32` と書きつつ、重みファイルの dtype を変えずに bf16 のエンジンへ渡したため、自分のモデルコードの中の `q_proj` で `mat1 and mat2 must have the same dtype` というエラーになりました。モデル用のディレクトリを作るスクリプト側で、重みを `config.json` の dtype に合わせてキャストするよう修正しました。

2 つ目は、vLLM 側のモデルランナーが `hf_config.vocab_size` という属性を直接読みに来るという問題です。今回使っていた簡易な設定クラスはこの属性を持っていなかったため、`AttributeError` になりました。`config.json` に `vocab_size` を追加して解決しています。

3 つ目は、この 2 つを直した後に起きたものです。`llm.generate()` を呼び出すと、実際にエンジンのスケジューラを通って本物の forward 呼び出しが実行されました (自分のモデルコードに仕込んだデバッグ出力が、実際の bf16 テンソルとともに発火したことで確認できます)。しかし、その後 vLLM-neuron 側の汎用的な出力パース処理 (`_parse_rejection_sampling_output`) の中で、`output_token_ids.cpu().numpy()` が `TypeError: Got unsupported ScalarType BFloat16` で落ちました。これは個々のモデルの実装に依存しない、エンジン側の共通コードの中で起きている問題です。numpy には bf16 の型が存在しないため、本来は整数のトークン ID のはずのテンソルが bf16 のまま流れてきてしまっているようでした。

このエンジン側の問題は、モデルの `forward()` を直す範囲では解決できないため、前回の検証はここで止まっていました。今回の継続作業では、この問題の原因を特定し、本物の実機 (前回は CPU モードでの検証でした) で `LLM()` をさらに先に進めました。

原因は、vllm-neuron の「on-device sampling (ODS)」という設定でした。エンジンの追加設定に `on_device_sampling_config` というキーを明示的に指定しない限り、既定で ODS が有効になります。ODS が有効だと、エンジンは「モデル自身が device 上でサンプリングまで済ませ、トークン ID を返してくる」ものとして扱い、CPU 側の通常のサンプリング処理をスキップします。今回のモデルの `forward()` はサンプリング前のロジット (bf16) を返すだけなので、エンジンはそのロジットをすでに整数のトークン ID であるかのように扱って `numpy()` 変換しようとし、bf16 を扱えずに落ちていた、というのが真相でした。

```python
additional_config={"neuron_config": {"on_device_sampling_config": None}}
```

この設定を明示的に渡すことで ODS を無効化できます。しかしこれで終わりではなく、本物の実機で `LLM()` を構築しようとすると、さらに 4 つの実機特有の問題に次々と当たりました。

1. 実機ではエンジンが複数プロセスで動くため、`NEURON_RT_VISIBLE_CORES` という環境変数ではなく `NEURON_VISIBLE_DEVICES` を使うようにというエラー。
2. 使用したインスタンス (trn2.3xlarge) には EFA (ネットワーク高速化機能) が無いため、起動時の EFA 検出処理が失敗するというエラー。`NEURON_SKIP_EFA_AFFINITY=1` という、エラーメッセージ自身が教えてくれる回避策がありました。
3. エンジンの非同期スケジューリング機能は on-device sampling が有効であることを前提にしている、というエラー。これは手順 0 で ODS を無効化したことと正面から矛盾するため、`async_scheduling=False` を明示的に渡して非同期スケジューリング自体を無効化しました。
4. 実機では `enforce_eager=True` (都度計算するモード) がまだサポートされていない、というエラー。`enforce_eager=False` にして、エンジン自身のコンパイル処理に任せる必要がありました。

この 4 つをすべて解決した上で、ようやくエンジン独自の「事前ウォームアップコンパイル」の処理まで到達しました。しかしここで、`neuronx-cc` という Neuron 専用コンパイラ自体が `neuronx-cc compilation failed with 70` というエラーで失敗しました。これは、これまでの検証で何度も使ってきた `torch.compile(backend="neuron_libtorch")` の経路とは別の、エンジンが内部的に使っているコンパイル経路で起きている問題です。実際のコンパイラのログファイルを今回の作業時間内では見つけられず、ここで検証を止めています。

## 到達した点と、到達しなかった点のまとめ

実際に実機で確認できたことは次の通りです。

- 本物の重みで CPU 上では、独立に実装した参照コードと完全に近い精度で一致すること (float32、bf16 のどちらでも)
- 実機 (Trainium2) で 30 層モデルのコンパイルと forward 実行ができること
- 本物の条件づけ latent と本物のテキストから、CPU 上で意味のある音声トークン列を自己回帰生成でき、終了トークンまで自然に到達すること
- CPU 側の WER が 8.3% であること (bf16 でも float32 でも同じ)
- vLLM の `LLM()` エンジンに登録し、スケジューラを通した本物の forward 呼び出しまで到達すること
- 当初「bf16 の積み重なり誤差」に見えた実機と CPU のずれが、実際には KV キャッシュへの書き込みと注意機構の NKI カーネル呼び出しを同じコンパイル済みグラフに入れたときだけ起きる、実在する 1 つのバグだったこと
- そのバグの回避策 (prefill の該当部分を複数のトップレベルの `torch.compile()` 呼び出しに分ける) を見つけ、実際に動かして確認したこと
- その回避策を使って実機側で終了トークンまで到達する自己回帰生成ができ、文字起こしによる WER が **8.3%** (CPU と完全に同じ) であったこと
- `LLM()` エンジンを実機の本番相当の経路に近づけるため、5 つの実機特有の設定問題を特定して回避したこと

今回のセッションで到達しなかったことは次の通りです。

- 見つけた回避策を、実際の vLLM エンジンの標準的な呼び方 (モデル全体を 1 回の `torch.compile()` でまとめる方式) の中で使えるようにすること。これには Neuron SDK 側のコンパイラ修正か、vllm-neuron 側の対応が必要です
- `llm.generate()` を実際のエンジン経由で最後まで完走させること (今回の WER 8.3% は、モデルを手で直接呼び出す検証コードによるものです)
- コンパイル済み計算グラフ (HLO) の中身を命令レベルで覗き、コンパイラのスケジューラが具体的に何を間違えているかを特定すること
- `neuronx-cc` コンパイラの `status 70` エラーの具体的な原因 (今回見つけたバグと同じ根っこかどうかは未確認です)
- 実機側の自己回帰生成の速度の最適化 (今回の回避策はトップレベルの `torch.compile()` 呼び出しを 1 層あたり 3 つに分けており、1 層あたり 1 回だった元の呼び方より明らかに遅くなっています。速度の最適化は今回のスコープ外としました)

## まとめ

XTTS v2 の GPT デコーダを vllm-neuron に移植する作業では、vLLM 側がリクエスト管理と KV キャッシュのページングを担ってくれる分、HuggingFace の generate API 向けの橋渡しコードや、prefill/decode を分けた別アプリケーション、CPU 経由の KV 受け渡しといった、NxD Inference 版で必要だった仕組みを書かずに済みました。その代わり、用意されている演算子を自分のキャッシュ規約と組み合わせる際の前提のズレ (decode マスク)、本物の重みを読んで初めて見える構造の誤り (2 つ目の LayerNorm、ローカルな位置埋め込み)、インストールされていたコンパイラ自体のバグ (gelu のキーワード引数)、エンジン側の設定の既定値が本物の実機では噛み合わない問題 (on-device sampling、非同期スケジューリングなど) という、実機で手を動かさないと見つからない問題にいくつも当たりました。

最も大きな教訓は、実機と CPU の出力のずれを「bf16 という精度につきものの、仕方のないずれ」と結論づけてしまったことそのものでした。CPU だけで bf16 と float32 を比べ直すと、そのずれは一切再現しません。実際の原因は、KV キャッシュへの書き込みと注意機構のカーネル呼び出しを同じコンパイル済みグラフに入れたときだけ実機上で起きる、1 つの具体的なバグでした。これを回避する方法を見つけて適用したところ、実機側の自己回帰生成は CPU と同じように終了トークンまで自然に到達し、文字起こしによる単語誤り率は CPU とまったく同じ 8.3% になりました。精度の問題に見えるものを「仕方のない丸め誤差」で片付ける前に、実際にコードの中のどの部分が疑わしいかを 1 つずつ機械的に切り分けることの大切さを、あらためて示す結果になりました。残った課題は、この回避策を実際の vLLM エンジンの標準的な呼び方の中でも使えるようにすることです。
