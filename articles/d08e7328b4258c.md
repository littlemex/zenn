## はじめに

音声合成モデル XTTS v2 の中心は、GPT-2 と同じ形の 30 層のデコーダです。このデコーダは、話者の特徴と文の埋め込みを前に置き、音声トークンを 1 つずつ作ります。この記事では、このデコーダを vllm-neuron 向けのモデルとして書き、Trainium2 の実機で音声トークンを作るまでに、何を書き、どこで何が壊れたかをまとめます。

結果を先に書きます。1 つの文と 1 つの参照音声で確かめたところ、prefill を複数のコンパイル済みの呼び出しに分けて自分で呼ぶと、実機で作った音声トークンからできた音声の単語の誤り率（WER）は、CPU と同じ 8.3% でした。vLLM のエンジン経由の `llm.generate()` も最後まで返りますが、同じトークンを繰り返すので、エンジン経由の WER はまだ測れていません。

比べる相手は、同じデコーダを NxD Inference で載せた実装です。NxD Inference での仕組みは「[NxD Inference にカスタムモデルを統合するための事前知識](https://zenn.dev/tosshi/articles/81840c7c10dddd)」と「[XTTS v2 を NxD Inference で動かす](https://zenn.dev/tosshi/articles/ffc359901ea1cc)」で、XTTS v2 の全体の構造は「[XTTS v2 を AWS Neuron で動かす](https://zenn.dev/tosshi/articles/53cc505a8d85e2)」で説明しています。どちらの実装も、Trainium に載せるのは GPT デコーダだけです。話者の特徴を作る前処理、文のトークン化、波形を作る HifiDecoder は CPU で、Coqui TTS の実装をそのまま使います。

## 誰が何を書くか

![vLLM のエンジンに登録する場合の分担。NxD Inference 版では generate() の橋渡しのクラス、prefill と decode の 2 つの Application、層の計算を自分で書く。vllm-neuron 版では生成のループとページ単位の KV キャッシュの領域を vLLM が受け持ち、prefill と decode の分岐、KV の書き込みと読み出し、層の計算、decode のマスクを自分で書き、prefill の注意には NKI の flash_attention を使う](/images/d08e7328b4258c-who-writes-what.png)

この図は、vLLM のエンジン（`llm.generate()`）にモデルを登録する場合の分担です。結果の節の WER 8.3% は、生成のループと 1 ブロックの KV キャッシュを自分で用意した手動のドライバで出しています。vllm-neuron では、リクエストの管理と生成のループを vLLM が受け持ちます。そのため、NxD Inference 版で書いた 2 つの仕組みが要りません。1 つは、Hugging Face の `generate()` に生成のループを任せるための橋渡しのクラスです。もう 1 つは、prefill と decode を別々の Application に分け、KV を CPU 経由で写す処理です。

vllm-neuron 版で自分で書くのは、次のものです。

- `attn_metadata` を見て prefill と decode を分ける、1 つのモデルの `forward()`
- vLLM がページ単位で用意した KV キャッシュの領域への書き込み（scatter）と、block table に沿った読み出し（gather）
- q、k、v、o の射影、MLP、LayerNorm、音声トークンと音声の位置の埋め込み、decode の注意のマスク
- 重みの変換。チェックポイントの attention と MLP の Conv1D の重みを `nn.Linear` 用に転置し、1 つにまとまった `c_attn` を q、k、v に分ける

vllm-neuron が用意する部品で、そのまま使えたのは、prefill の注意を計算する NKI のカーネル `NF.flash_attention` と、話者と文の埋め込みを音声トークンの埋め込みと並べる `NF.merge_prompt_embeds` です。話者の特徴と文の埋め込みは、vLLM の `prompt_embeds` として渡します。

## モデルとコンパイルで直した 6 つの問題

| # | 実装の注意点 | 必要な処理 |
| --- | --- | --- |
| 1 | KV キャッシュに書くとき、書き込み先の index はヘッドの順に並び、書き込む値はトークンの順に並んでいた | 値もヘッドの順に並べる |
| 2 | `NF.gen_attention_decode_mask` は、生成中のトークンの K と V を末尾の位置に置く `NF.attention_decode` と組で使う前提で、末尾の位置を常に有効にする | 実際の位置から自分でマスクを作る（2 行） |
| 3 | 最後の LayerNorm が、GPT-2 本体の `ln_f` のほかに、XTTS v2 独自の `final_norm` の 2 つある | `ln_f` のあとに `final_norm` を通してから出力の層に渡す |
| 4 | チェックポイントには GPT-2 本体のトークンと位置の埋め込み（`wte`、`wpe`）が無く、位置の埋め込みは文用（404 行）と音声用（608 行）の 2 つの表で、それぞれ 0 から数え直す | 音声トークンには、音声の中での位置で音声用の表を引く |
| 5 | `gelu(x, approximate="tanh")` が、Neuron の torch バックエンドで `TypeError: apply() takes no keyword arguments` になる | tanh 近似の式を掛け算と `tanh` で書く |
| 6 | bf16 の decode では、加算するマスクのせいで softmax の出力が fp32 になり、bf16 の V との行列積が型の違いで止まる | 行列積の前に softmax の出力を `v_ctx.dtype` に戻す |

1 は、1 回の prefill の中では手元の K と V で注意を計算するので、出力に現れません。同じ入力を、一度の prefill と、prefill のあとの 1 トークンずつの decode で処理して、logits が一致するかを比べるテストで見つかります。2 のように組で使う前提の部品は、片方だけを借りると、自分のキャッシュの決まりと合わなくなります。3 と 4 は、本物のチェックポイントを読み込んだ Hugging Face の `GPT2Model` を独立の参照にして、同じ入力の logits を比べて確かめました。

5 の原因は、PyTorch がこの呼び出しの `approximate` をキーワード引数の形にそろえ、Neuron の torch バックエンドがそれを、キーワード引数を受け取れない `torch.autograd.Function.apply()` にそのまま渡すことです。呼び出し方を位置引数に変えても避けられません。

```python
hidden_states = 0.5 * x * (1.0 + torch.tanh(0.7978845608028654 * (x + 0.044715 * x * x * x)))
```

## prefill の注意の結果が壊れる組み合わせ

![今回の XTTS v2 の注意の部品と SDK 2.32 では、prefill で q k v の射影、KV への書き込み、flash_attention、o_proj を 1 つの torch.compile にまとめると、層 0 の注意の出力の CPU との cosine 類似度は 0.738。KV への書き込みを別の torch.compile にし、層を 3 つの呼び出しに分けると 0.999997。decode は flash_attention を使わない](/images/d08e7328b4258c-prefill-split.png)

CPU で bf16 と fp32 を比べると、30 層のどの層でも隠れ状態の cosine 類似度（ベクトルの向きの近さで、1 に近いほど近い）は 0.99995 以上です。一方、実機で 1 つのグラフにまとめたモデルでは、生成が最初のトークンから崩れて同じトークンを繰り返します。CPU で bf16 にしただけでは、この崩れは起きません。

層 0 の LayerNorm の出力を入力にして、注意の部品を実機で 1 回呼ぶと、CPU との cosine 類似度は 0.738 でした。**今回の XTTS v2 の注意の部品では、KV キャッシュへの書き込み（`index_put_`）と `NF.flash_attention` を 1 つの `torch.compile` のグラフに入れると、実機で注意の結果が大きくずれます**。書き込みを止めると 0.999997 に戻ります。

この組み合わせは、学習済みの重みを使わない注意の部品（16 ヘッド、ヘッドの次元 64、69 トークン）でも再現します（書き込みあり 0.9375、書き込みなし 0.999995）。射影の層を含まない、4 ヘッド、18 トークンの素の tensor に `index_put` で書き込み、`NF.flash_attention` を呼ぶだけの組み合わせでは再現しません（0.999996）。射影の層とヘッドやトークンの数のどちらが効いているかは、切り分けていません。コンパイラの中で何が起きているかは、まだ調べていません。

正しい結果になったのは、prefill の各層を、次の 3 つの別々の `torch.compile` の呼び出しに分け、呼ぶ側から順に呼ぶ方法です。

1. `ln_1`、q k v の射影、`NF.flash_attention`、`o_proj`、残差の足し算
2. KV キャッシュへの書き込み
3. `ln_2`、MLP、残差の足し算

この境界は、モデルを呼ぶ側で作ります。モデルの中で書き込みだけを先にコンパイルしておいても、外側でモデル全体をコンパイルすると同じグラフに取り込まれます。1 つのグラフの中で書き込みを後ろへ並べ替える方法や、K と V を `clone()` で別の tensor にする方法も効きません。1 層を 1 つの `torch.compile` にする分け方では、30 層の cosine 類似度は 0.813 で、モデル全体を 1 つのグラフにしたときの 0.814 とほぼ同じです。

動作を確かめた手動のドライバは、3 つの範囲をそれぞれ `backend="neuron_libtorch", fullgraph=False` でコンパイルします。30 層を別々にコンパイルするので `torch._dynamo.config.recompile_limit = 256` にし、実行のキューがあふれないように、層ごとに結果を CPU に読み戻して同期します。

decode の注意は、`NF.flash_attention` ではなく、キャッシュから読み出して softmax を取る手書きの計算なので、この問題は起きません。decode は 1 層ずつの呼び出しのまま生成しました。

## 結果

本物の参照音声（XTTS-v2 に付いている `samples/en_sample.wav`）と文 "The quick brown fox jumps over the lazy dog near the riverbank." を使い、話者の特徴 32 トークンと文 37 トークンの、合わせて 69 トークンを前に置いて、貪欲法（毎回いちばん確率の高いトークンを選ぶ方法）で生成しました。3 つの列は、同じ参照音声と文を使った別々の実行です。実機の列は、前の節の分け方で prefill を呼んだ手動のドライバの値で、vLLM のエンジンは通していません。

波形を作る処理は、どの列も CPU で行いました。開始と終わりのトークンを除いた音声コードを m1 から mK として、`[前置き, 開始のトークン, m1, ..., m(K-1)]` を CPU のデコーダにもう一度通し（teacher forcing）、K 個の位置の `final_norm` のあとの隠れ状態を取り出します。それを話者の埋め込みと一緒に CPU の HifiDecoder に渡して、24kHz の波形にしました。WER は、Whisper の `base.en` の文字起こしと正解の文を、小文字にして句読点を除いてから `jiwer` で計算しました。

| 項目 | CPU（fp32） | CPU（bf16） | Trainium2（手動のドライバ、prefill を分割） |
| --- | --- | --- | --- |
| 系列の長さ（開始と終わりのトークンを含む） | 77 | 76 | 76 |
| 最初に生成したトークン | 225 | 225 | 225（分割しない 1 つのグラフでは 1023） |
| WER | 8.3% | 8.3% | 8.3% |
| 文字起こし | "Quick brown fox jumps over the lazy dog near the riverbank." | 同じ | 同じ |

3 つとも、12 語のうち抜けたのは同じ "The" の 1 語でした。実機と CPU fp32 の列は、開始のトークンを含めて 4 つ目で分かれ、CPU fp32 は 487、実機と CPU bf16 は 299 を選びます。

手動のドライバの decode は 892.9 ms/トークンでした。正しさを確かめるための層ごとの呼び出しと同期を含む値なので、速さの比較には使えません。参考として、書き込みが同じグラフにあり出力が CPU と合わない構成では、30 層の初回のコンパイルが 52.04 秒（キャッシュを使うとコンパイルと最初の呼び出しで 5.2 秒）、乱数の前置き 12 トークンと音声 6 トークンの forward が平均 10.52 ms でした。

参考として、「[XTTS v2 を NxD Inference で動かす](https://zenn.dev/tosshi/articles/ffc359901ea1cc)」の実装は、trn1.2xlarge の BF16 で WER 12.5% です。インスタンスも文も声も違うので、この 8.3% と比べられません。

## vLLM のエンジンで残る壁

モデルを `ModelRegistry.register_model` で、設定のクラスを `AutoConfig.register` で登録し、`enable_prompt_embeds=True` を付けた `LLM()` を作ります。モデルのディレクトリでは、変換した重み、`config.json` の `torch_dtype`、`LLM(dtype=...)` をすべて bf16 にそろえます（そろえないと `q_proj` で `mat1 and mat2 must have the same dtype` になります）。`config.json` には `"vocab_size": 1026` も書きます（`NeuronModelRunner` が直接読みます）。そのうえで、実機で `llm.generate()` を最後まで動かすには、次の設定が要りました。

| 起きたこと | この検証での対処 |
| --- | --- |
| on-device sampling（実機の上でトークンまで選ぶ機能）が既定で有効で、モデルが返す bf16 の logits をトークン ID として扱い、`Got unsupported ScalarType BFloat16` で止まる | `additional_config={"neuron_config": {"on_device_sampling_config": None}}` |
| 非同期のスケジューリングは on-device sampling を前提にしている | `async_scheduling=False` |
| 複数のプロセスで動くので、見せる NeuronCore の指定の環境変数が違う | `NEURON_RT_VISIBLE_CORES` の代わりに `NEURON_VISIBLE_DEVICES` |
| EFA の無いインスタンスで、起動時の EFA の検出が失敗する | `NEURON_SKIP_EFA_AFFINITY=1` |
| 実機では `enforce_eager=True` を使えない | `enforce_eager=False` |
| 起動時に入力の形の組み合わせを先にコンパイルしておく処理で、`neuronx-cc compilation failed with 70` になる | `VLLM_NEURON_DEBUG_MODE=1` でこの処理を飛ばす。この変数は `torch.compile` の `fullgraph` も切るデバッグ用の設定で、status 70 の原因はまだ調べていない |
| vLLM は既定で、使えるデバイスのメモリのほぼすべてを KV キャッシュに割り当てようとする。論理 NeuronCore 1 つ（trn2.3xlarge は LNC=2）に対応する約 24GB の HBM のうち 23.4GB がテンソルで埋まり、出力の 113 MiB を確保できずに `nrt_tensor_allocate status=4` になる | `gpu_memory_utilization=0.2` |

これで `llm.generate()` は最後まで返るようになりました。ただしエンジンはモデル全体を 1 つの `torch.compile` でコンパイルするので、前の節の分け方を持ち込めません。69 トークンの前置きを渡し、`max_tokens=100`、`max_model_len=128` で生成すると、トークン 1003 を繰り返し、終わりのトークンを出さないまま 63 トークンで止まりました。ログには `max_model_len` に達したと出ますが、69 と 63 を足すと 128 を超えるので、エンジンが前置きをどう数えたかは確かめていません。エンジン経由の WER は、このため測れていません。エンジンの中で同じ結果を得るには、`index_put_` と `NF.flash_attention` が 1 つのグラフにあっても注意の結果が正しくなるように SDK 側で直すか、vllm-neuron から複数のコンパイルの範囲を呼べるようにする必要があります。

## まとめ

trn2.3xlarge と Neuron SDK 2.32.0 の DLC イメージでは、今回の XTTS v2 の注意の部品で、prefill の各層を注意の本体、KV の書き込み、MLP の 3 つの `torch.compile` の呼び出しに分けて手動のドライバから順に呼ぶと、1 つの文と 1 つの参照音声で、実機で作った音声トークンから CPU と同じ WER 8.3% の音声ができました。vLLM のエンジンはモデル全体を 1 つのグラフにするので、エンジン経由で同じ結果を得るには、SDK か vllm-neuron 側の対応が要ります。
