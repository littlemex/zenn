## はじめに

この記事は、[NVSHMEM](https://developer.nvidia.com/nvshmem) の最小のプログラムを 1 本、行の順に読みます。読むのは、各 GPU が自分の番号を隣の GPU のメモリに書き込むリング通信で、AWS の `p4d.24xlarge`（A100 × 8）の上で、NVIDIA HPC SDK 24.5 のコンテナに同梱の NVSHMEM（`comm_libs/12.4/nvshmem`）を使って動作を確かめたものです。コードの各行が NVSHMEM の仕様のどの約束の上で動いているかを、[NVSHMEM の API ドキュメント](https://docs.nvidia.com/nvshmem/api/latest/index.html)の最新版（2026 年 10 月 6 日に参照）の記述と照らして説明します。動かした版と参照した仕様の版は同じとは限りません。

| コードの行 | 仕様で確かめること | 節 |
|---|---|---|
| `nvshmem_init`、`cudaSetDevice` | GPU を選ぶ順番 | 初期化と GPU の選択 |
| `nvshmem_malloc` | 全 PE が呼ぶ集団操作で、出口にバリアがある | 対称ヒープの確保 |
| `nvshmem_int_p` | 届く前に戻ることがある | カーネルの中の put |
| `cudaDeviceSynchronize`、`nvshmem_barrier_all` | CPU 側のバリアがどの操作を順序づけるか | 完了の待ち方 |
| `cudaMemcpy`、`nvshmem_free`、`nvshmem_finalize` | 解放と終了も集団操作で、バリアを含む | 結果の読み出しと後片付け |
| `nvshmrun` | ノードの中とノードの間の通信路 | 通信路 |
| `nvcc -rdc=true` | デバイス側のライブラリをリンクする | ビルドと実行 |

## PGAS と対称ヒープ

![3 つの PE がそれぞれ GPU のメモリを持ち、その中の対称ヒープに nvshmem_malloc で確保した dst が並ぶ。put と get は、自分の dst の対称アドレスと相手の PE の番号で、相手の dst を指す](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/228e4225b659f7/zenn/articles/228e4225b659f7/pgas.png)

NVSHMEM は、CPU 向けの通信の標準である OpenSHMEM の API を、NVIDIA の GPU のクラスタ向けに実装したライブラリです（[Introduction](https://docs.nvidia.com/nvshmem/api/latest/introduction.html)）。[製品ページ](https://developer.nvidia.com/nvshmem)は、複数の GPU のメモリにまたがるグローバルなアドレス空間を作ると説明しています。このような形を PGAS（Partitioned Global Address Space、分割されたグローバルアドレス空間）と呼びます。対称ヒープの上のオブジェクトは、どの PE のものも対称アドレスと PE の番号で指せますが、実体は GPU ごとに分かれていて、自分の GPU のメモリは速く読み書きでき、ほかの GPU のメモリには転送が要ります。全 PE が同じ呼び出しで確保するので、put は相手のアドレスではなく相手の PE の番号を指定します。

| 用語 | 意味 |
|---|---|
| PE（Processing Element） | 並列に動く単位。この記事では 1 PE が 1 GPU を使う。MPI のランクにあたる |
| put / get | 相手の PE のメモリに書き込む操作と、相手の PE のメモリから読み出す操作 |
| 片側通信（one-sided、RMA） | 送り手が相手の PE、アドレス、データを指定するだけで転送を始められ、相手の PE は受け取りの処理をしない通信。届いたことを確かめるには別の待ち方が要る。RMA は Remote Memory Access の略 |
| 対称ヒープ（symmetric heap） | `nvshmem_malloc` が確保する領域。全 PE が同じ引数で呼ぶと、戻り値の対称アドレスで、どの PE の同じオブジェクトも指せる |

## カーネルから通信を出す

![CPU が通信を指揮する場合は、カーネルが終わってから CPU が MPI で送り、転送のあとに CPU が次のカーネルを起動するので、やり取りのたびに CPU に戻る。NVSHMEM ではカーネルの中で計算の途中に nvshmem_int_p で転送を始めるので、やり取りのたびに CPU に戻らない](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/228e4225b659f7/zenn/articles/228e4225b659f7/who-starts.png)

[製品ページ](https://developer.nvidia.com/nvshmem)は、MPI のような従来の通信のモデルは CPU がデータの転送を指揮するのに対し、NVSHMEM は GPU が始める非同期の転送を使い、CPU と GPU の間の同期のオーバーヘッドをなくす、と説明しています。ここで比べる MPI と CUDA の書き方では、カーネルが計算を終えて CPU に制御が戻り、CPU が送り、通信が終わってから CPU が次のカーネルを起動します。製品ページは、通信と計算を 1 つの長く動くカーネルに入れられることで、strong scaling（問題の大きさを固定して GPU を増やしたときの速度の伸び）を制限するオーバーヘッドが減るとも書いています。

| 技術 | 通信の主導 | 通信の形 | 主な使いどころ |
|---|---|---|---|
| NVSHMEM | GPU | 片側（put / get）と集団通信 | 細かく頻繁な GPU 間の通信、PGAS が活きる場面 |
| NCCL | CPU が起動し、GPU が実行 | 集団通信が中心（all-reduce など） | 深層学習の勾配の集約 |
| MPI（+ CUDA / GPUDirect） | CPU | 両側（send / recv）、片側、集団通信 | HPC 全般 |

表は、それぞれの得意な使い方を筆者が整理したものです。GPUDirect RDMA は、この表のライブラリと並ぶ選択肢ではなく、GPU のメモリを CPU を経由せずにネットワーク越しに読み書きする土台の技術です（RDMA は Remote Direct Memory Access の略）。

## コードの流れ

![4 つの PE で、1 で各 PE がノードの中の同じ番号の GPU を選び、2 で全 PE に dst が確保され、3 でカーネルが自分の番号を次の PE の dst に put し、最後の PE 3 は PE 0 に折り返す。4 で全 PE がそろうまで待ち、5 で dst を CPU に写して表示する](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/228e4225b659f7/zenn/articles/228e4225b659f7/ring-put.gif)

GIF は PE が 4 つの場合で、実際に動かしたのは 2 PE と 8 PE です。GIF の値は実行の出力ではなく、コードから書いたものです。各 PE は自分の番号を次の PE の `dst` に書き込み、最後の PE は 0 番に折り返します。そのため PE $k$ の `dst` には、PE $(k - 1) \bmod 4$ の番号が入ります。場面 3 の矢印は put を出したところです。場面 5 で各 PE の `dst` に描く値は、`p4d` で観察した出力と同じ形の期待値で、場面 4 の待ち方が仕様の上でこの到着を約束するわけではありません（後の「完了の待ち方」で説明します）。以下が動作を確かめたコード `ring.cu` の全体です。後の「ビルドと実行」で起動するコンテナの中で、この内容を `/tmp/ring.cu` に保存し、`cd /tmp` してからビルドします（実行ログでは `cat > /tmp/ring.cu <<'EOF'` で作っています）。

```cuda
#include <stdio.h>
#include "nvshmem.h"    // NVSHMEM 本体の API
#include "nvshmemx.h"   // NVSHMEMX_TEAM_NODE などの拡張 API

// 各 GPU（PE）が、自分の番号を「隣の PE」のメモリに put で書き込むカーネル
__global__ void ring_put(int *dst) {
    int mype = nvshmem_my_pe();        // 自分の PE 番号
    int npes = nvshmem_n_pes();        // PE の総数
    int peer = (mype + 1) % npes;      // 隣（次）の PE（最後は 0 に折り返す）

    // 自分の番号 mype を、隣の PE の dst に書き込む（片側通信の put）
    // _p は put の意味で、int 1 個を相手のメモリに書き込む
    nvshmem_int_p(dst, mype, peer);
}

int main(void) {
    nvshmem_init();                                  // 初期化

    int mype      = nvshmem_my_pe();                 // 全 GPU 通しの番号（グローバル PE 番号）
    int mype_node = nvshmem_team_my_pe(NVSHMEMX_TEAM_NODE);
                                                     // ノード内での番号（= 使う GPU の番号）
    cudaSetDevice(mype_node);                        // その番号の GPU を選ぶ

    // 対称ヒープ上にメモリを確保（全 PE が同じアドレスで持つ）
    int *dst = (int *)nvshmem_malloc(sizeof(int));

    ring_put<<<1, 1>>>(dst);                         // カーネル起動（put を発行）
    cudaDeviceSynchronize();                         // カーネル完了を待つ
    nvshmem_barrier_all();                           // 全 PE の put 完了を保証（ホスト側バリア）

    // 結果を CPU 側にコピーして表示
    int value;
    cudaMemcpy(&value, dst, sizeof(int), cudaMemcpyDeviceToHost);
    printf("PE %d は、隣の PE から %d を受け取りました\n", mype, value);

    nvshmem_free(dst);                               // 後片付け
    nvshmem_finalize();
    return 0;
}
```

### 初期化と GPU の選択

[`nvshmem_init()`](https://docs.nvidia.com/nvshmem/api/latest/gen/api/setup.html) は、ほかの NVSHMEM の関数より前に全 PE が呼ぶ集団操作で、初期化に失敗するとプログラムは 0 以外の値で終了します。初期化のあと、`nvshmem_my_pe()` は全 PE を通した番号を、`nvshmem_team_my_pe(NVSHMEMX_TEAM_NODE)` は同じノードの中での番号を返します。1 ノードに 8 GPU があり 8 PE で動かす場合、ノードの中の番号は 0〜7 なので、それをそのまま `cudaSetDevice` に渡すと PE ごとに別の GPU を使えます。公式の [Using NVSHMEM](https://docs.nvidia.com/nvshmem/api/latest/using.html) は「The device must be set before you allocate memory or launch a kernel」と書いており、`cudaSetDevice` が `nvshmem_malloc` より前にあるのはこのためです。

### 対称ヒープの確保

[`nvshmem_malloc`](https://docs.nvidia.com/nvshmem/api/latest/gen/api/memory.html) は、全 PE の参加が要る集団操作です。仕様は、全 PE が同じ引数で呼ぶことを利用者の責任としていて、引数が違うときの動作は未定義です。戻り値は対称アドレスで、put の宛先（get なら読み出し元）には、自分の `dst` の対称アドレスと相手の PE の番号を渡します。そのため `ring_put` には `dst` だけを渡し、カーネルの中で `nvshmem_int_p` に宛先の `dst` と相手の `peer` と送る値 `mype` を渡せばよく、相手のアドレスを問い合わせる処理がありません。コードのコメントには「全 PE が同じアドレスで持つ」とありますが、仕様が言っているのは、戻り値の対称アドレスでどの PE の同じオブジェクトも指せることまでで、各 PE のポインタの値が同じかどうかは書かれていません。

もう 1 つ大事なのは、`nvshmem_malloc` が出口でバリアと同じ働きをする処理を呼ぶことです。仕様は、これによって「the memory on other PEs can be used as soon as the local PE returns」と書いています。このコードで確保の直後にカーネルを起動し、隣の PE の `dst` に書き込んでよいのは、この約束があるからです。

### カーネルの中の put

`ring_put<<<1, 1>>>(dst)` は、1 ブロック 1 スレッドでカーネルを起動します。カーネルの中で `peer = (mype + 1) % npes` を計算し、[`nvshmem_int_p`](https://docs.nvidia.com/nvshmem/api/latest/gen/api/rma.html) で自分の番号を `peer` の `dst` に書き込みます。`_p` の付く関数は、基本の型の値 1 つを送る、遅延の小さい put です。仕様は、この関数が転送を始めたあと、データが相手に届く前に戻ることがあると書いています。つまり `nvshmem_int_p` から戻っただけでは、隣の PE の `dst` にまだ値が入っていないことがあります。

### 完了の待ち方

![GPU の上では nvshmem_int_p が put を始め、届く前に戻ることがある。仕様が GPU 側の put に求めるのは、GPU 側の nvshmem_quiet とカーネルの終了で、CPU 側の cudaDeviceSynchronize はカーネルの終了を待ち、nvshmem_barrier_all は CPU が出した操作を順序づける。公式の最初の例は、カーネルと同じストリームで nvshmemx_barrier_all_on_stream を呼ぶ](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/228e4225b659f7/zenn/articles/228e4225b659f7/completion.png)

このコードは、カーネルのあとに CPU 側で `cudaDeviceSynchronize()` と `nvshmem_barrier_all()` を呼び、コメントに「全 PE の put 完了を保証」と書いています。[`nvshmem_barrier_all`](https://docs.nvidia.com/nvshmem/api/latest/gen/api/collectives.html) は、全 PE が呼ぶまで待ち、その前に出した put などの完了を保証するバリアです。ただし仕様の注記は、CPU と GPU のそれぞれで呼んだ順序づけの操作は、それぞれ CPU と GPU から出した通信だけを順序づける、と書いています。CPU から GPU 側の操作の完了を確かめるには、GPU 側で quiet（それまでに出した put を完了させる操作）を行い、その put を出したカーネルの終了を `cudaDeviceSynchronize` などで待つか、ストリームに乗せた quiet（stream-based quiet）を使います。ストリームに乗せた quiet はストリームの順番の中で完了を保証するものなので、CPU が値を読む前には、そのストリームの完了も待ちます。

図の破線の枠の `nvshmem_quiet()` は、`ring.cu` にはありません。このコードのカーネルには quiet が無いので、CPU 側のバリアがカーネルの put の完了まで保証するとは、仕様からは言えません。`p4d` の NVLink の上で 2 PE と 8 PE を 1 回ずつ実行した範囲では、後の「実行」の節のとおり期待した値が届きました。公式の [Using NVSHMEM](https://docs.nvidia.com/nvshmem/api/latest/using.html) の最初の例は、同じリング通信を次のように書いています。

```cuda
simple_shift<<<1, 1, 0, stream>>>(destination);
nvshmemx_barrier_all_on_stream(stream);
cudaMemcpyAsync(&msg, destination, sizeof(int), cudaMemcpyDeviceToHost, stream);
cudaStreamSynchronize(stream);
```

Using NVSHMEM の説明文は、カーネルをストリームに非同期に起動し、そのあと同じストリームでバリアを呼んで、すべての更新が終わったことを保証する、と書いています。この例のカーネルにも quiet はありません。`nvshmemx_barrier_all_on_stream` がストリームに乗せた quiet と同じ働きを含むかは、`nvshmem_barrier_all` の注記には書かれていません。CPU で値を読むのは、同じストリームでコピーを入れ、`cudaStreamSynchronize` でストリームの完了を待ったあとです。この記事のコードは、公式の例と違い、既定のストリームと CPU 側の同期とバリアを使っています。上の 4 行は公式の例からの引用で、筆者は動作を確かめていません。

### 結果の読み出しと後片付け

バリアのあと、`cudaMemcpy` で自分の GPU の `dst` を CPU のメモリに写し、`printf` で表示します。CPU に写すのは表示のためで、put は GPU から出しています。表示の時点で値が届いていたことは、`p4d` での実行の出力で確かめたことです。[`nvshmem_free`](https://docs.nvidia.com/nvshmem/api/latest/gen/api/memory.html) も集団操作で、入口でバリアと同じ働きをする処理を呼ぶので、全 PE が `nvshmem_free` に着いてから解放されます。最後の `nvshmem_finalize()` も全 PE が呼ぶ集団操作で、仕様は、中に暗黙のグローバルなバリアがあり、未完了の通信を完了させると書いています。この「未完了の通信」が GPU から出した put を含むかは書かれていません。

## 通信路

![ノードの中では GPU どうしが NVLink か PCIe の P2P でつながる必要があり、p4d では 56 ペアのすべてで P2P が使え、g4dn では 12 ペアのどれも使えず初期化で終了した。ノードの間の通信路は NVSHMEM_REMOTE_TRANSPORT で選ばれ、既定は ibrc で、EFA には libfabric と efa の指定が要る。p4d では ibrc の初期化に失敗したという警告が出た](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/228e4225b659f7/zenn/articles/228e4225b659f7/transports.png)

この記事のノードの中の実行では、GPU どうしが P2P（NVLink か PCIe の P2P）でアクセスできる必要がありました。筆者が AWS の 2 種類のインスタンスで確かめた結果は次のとおりです。

| 環境 | GPU 間の接続 | P2P でアクセスできるペア | 複数 PE のデモ |
|---|---|---|---|
| `g4dn.12xlarge`（T4 × 4） | PCIe、NVLink なし | 0 / 12 | 動かない |
| `p4d.24xlarge`（A100 × 8） | NVLink + NVSwitch | 56 / 56 | 動く |

`g4dn.12xlarge` では `cudaDeviceCanAccessPeer` が全ペアで 0 を返し、NVSHMEM の初期化が `Peer GPU 1 is not accessible, exiting` で終了しました。ある PE が P2P でつながっているかは、プログラムの中で `nvshmem_ptr` が NULL 以外を返すか、その PE が `NVSHMEM_TEAM_SHARED` に入っているかで確かめられます（[FAQ](https://docs.nvidia.com/nvshmem/api/latest/faq.html)）。

ノードの間の通信路は、環境変数 `NVSHMEM_REMOTE_TRANSPORT` で選びます（[環境変数の一覧](https://docs.nvidia.com/nvshmem/api/latest/gen/env.html)）。既定は `ibrc` で、選択肢には `libfabric` があり、libfabric の provider を選ぶ `NVSHMEM_LIBFABRIC_PROVIDER` の選択肢に `efa` があります（既定は `cxi`）。AWS の EFA でノードの間を通信するときは、この 2 つで libfabric と efa を選ぶことになります。筆者はノードの間の通信は試していません。実行ログの `WARN: init failed for remote transport: ibrc` は、既定の `ibrc` の初期化に失敗したという警告です。FAQ は、InfiniBand の NIC が無いホストでも P2P の環境での動作は変わらないと書いていて、後の「実行」の節の `p4d` の実行でも期待した値が得られました。

## ビルドと実行

### 環境の準備

NVSHMEM と `nvcc` とランチャが入っている NVIDIA HPC SDK のコンテナを使います（Docker と NVIDIA Container Toolkit が入っている前提です）。タグは古くなることがあるので、最新は [NGC](https://catalog.ngc.nvidia.com) で確かめてください。

```bash
docker run --gpus all -it --rm --shm-size=8g --ipc=host \
  nvcr.io/nvidia/nvhpc:24.5-devel-cuda12.4-ubuntu22.04 bash
```

:::message
`--shm-size=8g --ipc=host` を付けないと、筆者の環境では PE が 4 つ以上（`-np 4` 以上）のときに `Bus error (signal 7)` で落ちました。`--shm-size` はコンテナの `/dev/shm` の大きさを決める指定で（[docker container run](https://docs.docker.com/reference/cli/docker/container/run/)）、この 2 つを付けると落ちなくなりました。
:::

コンテナの中で `NVSHMEM_HOME` を決めます。HPC SDK 24.5 では次のパスが NVSHMEM の本体です。`find` で探すと cuFFTMp 向けの別のコピーを拾うことがあるので、HPC SDK の決まった配置からパスを組み立てています。`VER` にはインストール先のディレクトリ名が、`CUDAVER` には CUDA の版が入り、実行ログでは `VER` が `2024`、`CUDAVER` が `12.4` でした。

```bash
HPCSDK=/opt/nvidia/hpc_sdk/Linux_x86_64
VER=$(ls $HPCSDK | sort -V | tail -1)
CUDAVER=$(ls $HPCSDK/$VER/comm_libs | grep -E '^[0-9]+\.[0-9]+$' | tail -1)
export NVSHMEM_HOME=$HPCSDK/$VER/comm_libs/$CUDAVER/nvshmem
ls $NVSHMEM_HOME/include/nvshmem.h && echo "NVSHMEM_HOME=$NVSHMEM_HOME"
```

### ビルド

![ring.cu のカーネルの部分は、静的ライブラリ libnvshmem_device.a のデバイスコードとデバイスリンクで結び付けられ、これに -rdc=true が要る。ホストの部分は libnvshmem_host.so とリンクされる。-gencode は GPU の世代に合わせる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/228e4225b659f7/zenn/articles/228e4225b659f7/build.png)

[Using NVSHMEM](https://docs.nvidia.com/nvshmem/api/latest/using.html) によると、NVSHMEM は共有ライブラリの `libnvshmem_host.so` と、静的ライブラリの `libnvshmem_device.a` の 2 つでできていて、ホストの API だけを使う場合もデバイスの API だけを使う場合も、両方をリンクする必要があります。公式のビルドの例は `-rdc=true` を付けています。`-rdc=true` は、デバイスコードを別のファイルのデバイスコードとリンクできる形でコンパイルする nvcc の指定です（[nvcc のドキュメント](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html)）。カーネルの中で呼ぶ `nvshmem_int_p` のようなデバイスの API は `libnvshmem_device.a` の側にあるので、`ring.cu` のカーネルとそれを結び付けるデバイスリンクのために付けます。

```bash
nvcc -rdc=true -ccbin g++ \
  -gencode=arch=compute_80,code=sm_80 \
  -I $NVSHMEM_HOME/include \
  ring.cu -o ring \
  -L $NVSHMEM_HOME/lib -lnvshmem_host -lnvshmem_device
```

:::message
`arch=compute_80,code=sm_80` は、A100 の世代（compute capability 8.0）向けのコードだけを作る指定です。ほかの世代の GPU で動かすときは値を合わせてください。手元の GPU の値は `nvidia-smi --query-gpu=compute_cap --format=csv` で確かめられ、世代ごとの値は [CUDA GPUs](https://developer.nvidia.com/cuda-gpus) に一覧があります。
:::

### 実行

NVSHMEM に付属するランチャ `nvshmrun` に、PE の数（使う GPU の数）を `-np` で渡します。HPC SDK のコンテナの素の状態では、筆者の環境では `nvshmrun` に実行権限が無く、依存する `libpciaccess0` も入っていませんでした。動かないときは、コンテナの中で次の準備を一度だけ行います。最後の行が、2 GPU でのリング通信の実行です（GPU の P2P が使える環境が要ります）。

```bash
apt-get update && apt-get install -y libpciaccess0
chmod +x $NVSHMEM_HOME/bin/nvshmrun.hydra $NVSHMEM_HOME/bin/hydra_*
export PATH=$NVSHMEM_HOME/bin:$PATH

nvshmrun -np 2 ./ring
```

`p4d`（A100 × 8）での出力の抜粋です（下の実行ログと同じ実行で、`WARN` の行を省いています）。PE の順番は前後することがあります。

```text
PE 0 は、隣の PE から 1 を受け取りました
PE 1 は、隣の PE から 0 を受け取りました
```

PE 0 には PE 1 が番号 `1` を書き込み、PE 1 には PE 0 が `0` を書き込みました。8 GPU で実行すると、各 PE が 1 つ前の PE の番号を受け取ります。次の出力は、同じ実行ログに残っている別の 8 PE の実行の抜粋で、PE の番号順に並べ、途中を省いています。全 8 行は実行ログにあります。

```bash
nvshmrun -np 8 ./ring
```

```text
PE 0 は、隣の PE から 7 を受け取りました
PE 1 は、隣の PE から 0 を受け取りました
PE 2 は、隣の PE から 1 を受け取りました
...
PE 7 は、隣の PE から 6 を受け取りました
```

GPU が 1 台しかない環境では、1 つの PE で起動を確かめられます。隣が自分自身なので、出力は次のようになるはずです（この実行はログに残っていません）。

```bash
nvshmrun -np 1 ./ring
```

```text
PE 0 は、隣の PE から 0 を受け取りました
```

## まとめ

NVSHMEM では、全 PE が同じ引数で確保した対称ヒープの上の変数を、自分の対称アドレスと相手の PE の番号で指定して、カーネルの中から直接書き込めます。カーネルが出した put の完了を CPU から確かめるには、仕様は GPU 側の quiet とカーネルの終了、またはストリームに乗せた quiet を求めていて、quiet を持たないこの記事のコードは、`p4d` の NVLink の上で 2 PE と 8 PE を 1 回ずつ実行した範囲では期待した値を返しました。
