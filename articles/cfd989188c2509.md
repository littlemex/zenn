## はじめに

[Lustre](https://doc.lustre.org/lustre_manual.xhtml#understandinglustre.components) は、たくさんのクライアント (Lustre のファイルを読み書きするコンピュータ) が同じファイルシステムに同時に読み書きするための、並列ファイルシステムです。ファイルの中身を複数のサーバに分けて置けるので、全体の帯域を伸ばせます。HPC (高性能計算) の大きなクラスタで使われてきました。この記事では、Lustre の部品と、部品の間をつなぐ通信層の [LNet](https://doc.lustre.org/lustre_manual.xhtml#understandinglustrenetworking) を、図で見ていきます。

特定のクラウドサービスの運用や設定には踏み込みません。ネットワークの種類の例として、AWS の高速なネットワークインターフェースである [EFA](https://aws.amazon.com/hpc/efa/) の名前が出てきます。続きの記事では、この記事の知識を使って、AWS のマネージドな Lustre である [FSx for Lustre](https://aws.amazon.com/fsx/lustre/) で、EFA と TCP を実測とあわせて比べます。

## 全体像

![クライアントが LNet を通って MGS、MDS と MDT、OSS と OST の 3 種類のサーバと話す。メタデータと構成の情報は両方向に、ファイルの中身は OSS とクライアントの間を流れる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/overview.png)

Lustre は、ファイルの名前や置き場所を持つサーバと、ファイルの中身を持つサーバを分けたファイルシステムです。クライアントは、名前や置き場所を MDS に問い合わせ、ファイルの中身は MDS を通さずに OSS と直接やりとりします。

| 部品 | 受け持ち | 持つもの |
|---|---|---|
| クライアント | ファイルシステムをマウントして、アプリケーションに普通のファイルシステムとして見せる | 自分のディスクは要らない |
| [MGS](https://doc.lustre.org/lustre_manual.xhtml#understandinglustre.components) (管理サーバ) | ファイルシステムの構成を、サーバとクライアントに渡す。MDS と同じ機械に置くこともできる | 構成の情報 |
| [MDS](https://doc.lustre.org/lustre_manual.xhtml#understandinglustre.components) (メタデータサーバ) と MDT (その記憶領域) | 名前、ディレクトリ、権限、中身の置き場所の問い合わせに答える | メタデータ |
| [OSS](https://doc.lustre.org/lustre_manual.xhtml#understandinglustre.components) (オブジェクトストレージサーバ) と OST (その記憶領域) | ファイルの中身の読み書きに答える。1 台の OSS は、ふつう 2〜8 個の OST を受け持つ | ファイルの中身 |
| LNet | クライアントとサーバをつなぐ通信層 | 宛先を表す NID (「NID」の節) |

サーバの機械を MDS や OSS と呼び、その機械が受け持つ記憶領域を MDT や OST と呼びます。

## メタデータとファイルの中身

![ファイル result.bin の MDT の記録は、持ち主や権限とレイアウトを持ち、レイアウトが OST 0、OST 2、OST 5 の object を指す](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/record-and-contents.png)

通常のファイルは、MDT にあるメタデータの記録と、OST にある object (OST がファイルの中身を持つ単位) の 2 つで表されます。持ち主、権限、時刻のような情報をメタデータと呼び、MDT が持ちます。ファイルの名前は、親のディレクトリの中の項目として MDT にあり、この記録を指します。

MDT の記録には、中身がどの OST のどの object にあるかを示すレイアウトも入っています。この記事では、中身を OST に置く場合を扱います。小さなファイルの中身を MDT に置く [DoM](https://doc.lustre.org/lustre_manual.xhtml#dataonmdt) (Data on MDT) という使い方もあります。

MDS は中身の置き場所 (レイアウト) を伝え、OSS は中身そのものを送ります。読む前にクライアントが OSS から得るロックは、「ロック」の節で説明します。

名前の問い合わせと中身の読み書きを別のサーバに分けているので、**DoM を使わない場合、中身の転送に MDS は出てきません**。そのため OSS と OST を増やすと、クライアント、ネットワーク、ディスクが詰まらない範囲で、全体の帯域を伸ばせます。ただし、すでにあるファイルの置き場所は、OST を足しても自動では広がりません。1 本のファイルの帯域は、そのファイルが使う OST の数にも左右されます。

書き込みも、レイアウトを受け取り、OSS からロックを得てから OSS とやりとりする点は、読み込みと同じです。

## 複数の MDT

![ルートと /projA が MDT 0 に、/projB が MDT 1 にあり、ストライプしたディレクトリ /projC の中身は MDT 1 と MDT 2 に分かれている。クライアントからは 1 つの木に見える](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/dne.png)

MDT が 1 つだけだと、名前に関する操作がその MDT に集まります。そこで Lustre は、ディレクトリツリーの一部を別々の MDT に置けます。この仕組みを [DNE](https://doc.lustre.org/lustre_manual.xhtml#DNE) (Distributed Namespace Environment、名前空間の分散) と呼びます。ルートのディレクトリは、最初の MDT にあります。

1 つのディレクトリの中身を、複数の MDT に分けることもできます。これを[ストライプしたディレクトリ](https://doc.lustre.org/lustre_manual.xhtml#stripeddirectory)と呼びます。どちらの場合も、クライアントの中の [LMV](https://github.com/lustre/lustre-release/tree/6325870717c7899f1ba545493ce2a07cb3834a6b/lustre/lmv) という部品が各 MDT の答えをまとめるので、アプリケーションからは 1 つのディレクトリツリーに見えます。

複数のクライアントが同じファイルを読み書きしても、それぞれの手元のデータが食い違わないように、サーバがロックを貸し出します。この仕組みを [LDLM](https://doc.lustre.org/lustre_manual.xhtml#ldlm) (分散ロックマネージャ) と呼びます。OSS はファイルの中身のロックをデータの範囲ごとに貸し出し、MDS はメタデータのロックを貸し出します。ロックを持つクライアントは、その範囲のデータを手元にためて (キャッシュして) おけます。持ち主は、ロックを返す前に、ためていたデータを書き戻します。

持ち主が決まった時間内にロックを返さないとき、サーバは、その MDT や OST について、クライアントを切り離します。これを [evict](https://doc.lustre.org/lustre_manual.xhtml#clientevictions) と呼びます。切り離されたクライアントは、その MDT や OST から借りていたロックがすべて無効になり、そこ向けにためていたデータのうち、まだサーバに書いていないものは失われることがあります。ロックを返さないことのほか、クライアントからの要求も生存確認の知らせも決まった時間届かないことも、evict の理由になります。

## NID

![10.0.1.20@tcp0 という NID は、アドレス 10.0.1.20 と、LNet のネットワーク名 tcp0 を @ でつないだもの。1 台のサーバが複数の NID を持てる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/nid.png)

[NID](https://doc.lustre.org/lustre_manual.xhtml#understandinglustrenetworking) (network identifier) は、LNet が宛先を表すのに使うアドレスで、ネットワークインターフェースのアドレスと LNet のネットワーク名を @ でつないだものです。たとえば `10.0.1.20@tcp0` です。図の値は説明用の例です。TCP や InfiniBand では、アドレスの部分に IP アドレスを使います。ネットワーク名は、LND (「LND」の節) の種類に番号を付けたもので、tcp0 は TCP、o2ib0 や o2ib1 は InfiniBand のネットワークを表します。

1 台のサーバは、複数の NID を持てます。LNet は、NID の一覧をまだ知らない相手へ最初に送るときに、LNet の ping を送って一覧を受け取ります。この動きを [discovery](https://doc.lustre.org/lustre_manual.xhtml#lnet_config.dynamic_discovery) と呼びます。

## LND: ネットワークごとのドライバ

![LNet の下に、TCP 向けの ksocklnd、InfiniBand 向けの ko2iblnd、AWS の EFA 向けの kefalnd が並ぶ](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/lnet-lnd.png)

LND (Lustre network driver) は、ネットワークごとの送受信を受け持つドライバです。LND がネットワークごとの違いを受け持つので、LNet より上の層は、TCP、InfiniBand、EFA を同じ呼び出し方で使えます。TCP には [ksocklnd](https://github.com/lustre/lustre-release/tree/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/socklnd)、InfiniBand には [ko2iblnd](https://github.com/lustre/lustre-release/tree/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/o2iblnd)、EFA には [kefalnd](https://github.com/lustre/lustre-release/tree/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd) があり、どれも upstream のソースに入っています。

LNet は、接続を持たず、届くことを保証しません。ただし、待っている ACK や REPLY (「LNet のメッセージ」の節) が時間内に来なければ、失敗として扱います。失敗したときの各層の動きは、「層ごとの受け持ち」の節にまとめます。

## LNet のメッセージ

![PUT は始める側がデータを相手に送り込み、求められたときだけ ACK が返る。GET は始める側が要求を送ると、データを載せた REPLY が返る](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/messages.png)

LNet は、データを相手に送り込む PUT と、相手から取ってくる GET の 2 つで、データを動かします。PUT では、始める側が求めたときだけ、受け取りの確認の ACK が返ります。GET では、始める側が欲しいものを伝える要求を送り、相手がデータを載せた REPLY を返します。

RPC の要求と応答は、どちらも PUT で運ばれます。REPLY は GET への返事で、RPC の応答とは別のものです。bulk も PUT と GET でできていて、読み込みでは OSS が PUT で送り込み、書き込みでは OSS が GET で取りに来ます。メッセージの型は、TCP の LND が接続を始める手続きに使う HELLO を含めて、[5 つ](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/include/uapi/linux/lnet/lnet-idl.h#L79)が定義されています。

[Multi-Rail](https://doc.lustre.org/lustre_manual.xhtml#mroverview) は、1 台が複数の NID を持つとき、メッセージごとに送る側と受ける側の NID の組を選ぶ仕組みです。複数のネットワークカードを使い分け、調子の悪い NID を避けて送れます。双方が使える NID と、相手が Multi-Rail に対応しているかで、候補が決まります。

候補から選ぶときに最初に比べるのが、NID の調子を表す 0 から 1000 の数の [health](https://doc.lustre.org/lustre_manual.xhtml#mrhealth) で、最も高い NID が選ばれます。失敗で health が下がった NID は、より health の高い NID がほかにある間、ふつうの送信には選ばれません。下がった NID は、回復の ping が成功すると health が戻ります。図は、既定の設定で NID B が 2 回失敗した場合の説明用の例です。

## ルーター

![tcp0 のクライアントが、tcp0 と o2ib0 の両方に NID を持つ LNet ルーターを通って、o2ib0 の OSS と MDS に届く](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/router.png)

違う LNet のネットワークにいる相手とは、[LNet ルーター](https://doc.lustre.org/lustre_manual.xhtml#managinglnet.configuringroutes)を通って通信します。ルーターは、2 つのネットワークのそれぞれに NID を持ち、ルーターとして動くように設定された機械で、片方で受け取ったメッセージを、もう片方へ転送します。たとえば、TCP のクライアントが、InfiniBand 側にあるサーバの NID に向けて送ると、ルーターが間を取り持ちます。LNet のルーティングは、IP のルーティングとは別のものです。

クライアントは、サーバの再起動や接続の切れ目のあとも作業を続けられるように、MDT や OST ごとに接続の状態を持ちます。これを [import](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lustre/include/lustre_import.h#L67) と呼び、ptlrpc が管理します。

サーバがこのクライアントとの接続の情報をまだ持っていれば、import は RECOVER を経て FULL (ふつうにつながっている状態) に戻ります。再起動したサーバが[復旧](https://doc.lustre.org/lustre_manual.xhtml#lustrerecovery)を受け付けている間に接続し直したときは、クライアントが要求とロックを送り直してから戻ります。サーバがクライアントを切り離していたときは、[EVICTED を通ります](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lustre/ptlrpc/import.c#L1341-L1394)。接続し直している間、新しい要求は待たされることがあります。evict された場合は、その間に進んでいた操作は失敗します。

import は ptlrpc が持つ MDT や OST との接続の状態で、NID ごとの調子は LNet の health が持ちます。そのため、接続が切れたとみなした状態 (DISCON) は、特定の NID が壊れたことを意味しません。

## 層ごとの受け持ち

失敗は、層ごとに別のものとして見つかり、別々に扱われます。LND と LNet は通信の失敗を、ptlrpc は要求の時間切れと接続を、LDLM はロックを返さないクライアントを扱います。evict はサーバが決めることで、LNet の health が下がることとは別です。

| 層 | 受け持ち | 失敗したとき |
|---|---|---|
| LND | ネットワークごとの送受信 | 送受信の失敗を LNet に伝える |
| LNet | 宛先の NID と、通る経路の選択 | health を下げて、ほかの NID を選びやすくする。失敗の種類によっては再送し、再送しきれなければ上の層へ失敗を伝える |
| ptlrpc | RPC の送受信、応答の待ち、接続の張り直し | 要求が時間内に終わらないと、接続を張り直す |
| LDLM | ロックの貸し出し | ロックを返さないクライアントを evict する |

## まとめ

Lustre は、名前の問い合わせと中身の読み書きを別のサーバに分けます。DoM を使わない場合、ファイルの中身は MDS を通らずに OSS とやりとりするので、クライアント、ネットワーク、ディスクが詰まらない範囲で、OSS と OST を増やすと帯域を伸ばせます。その通信は LNet が NID と LND で支え、失敗は health と import の状態に現れます。
