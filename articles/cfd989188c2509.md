## はじめに

[Lustre](https://doc.lustre.org/lustre_manual.xhtml#understandinglustre.components) は、たくさんのクライアントが同じファイルシステムに同時に読み書きするための、並列ファイルシステムです。ファイルの中身を複数のサーバに分けて置けるので、全体の帯域を伸ばせます。HPC の大きなクラスタで使われてきました。LLM の学習でも、多くの GPU のノードが学習データを同時に読み、チェックポイントを同時に書き出す置き場所として使われます。この記事では、Lustre の部品と、部品の間をつなぐ通信層の [LNet](https://doc.lustre.org/lustre_manual.xhtml#understandinglustrenetworking) を、図で見ていきます。特定のクラウドサービスには踏み込みません。

## 全体像

![クライアントが LNet を通って MGS、MDS と MDT、OSS と OST の 3 種類のサーバと話す。メタデータと構成の情報は両方向に、ファイルの中身は OSS とクライアントの間を流れる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/overview.png)

Lustre は、ファイルの名前や置き場所を持つサーバと、ファイルの中身を持つサーバを分けたファイルシステムです。クライアントは、名前や置き場所を MDS に問い合わせ、ファイルの中身は、ふつう MDS を通さずに OSS と直接やりとりします。

| 部品 | 受け持ち | 持つもの |
|---|---|---|
| クライアント | ファイルシステムをマウントして、アプリケーションに普通のファイルシステムとして見せる | 自分のディスクは要らない |
| [MGS](https://doc.lustre.org/lustre_manual.xhtml#understandinglustre.components) (管理サーバ) | ファイルシステムの構成を、サーバとクライアントに渡す。MDS と同じ機械に置くこともできる | 構成の情報 |
| [MDS](https://doc.lustre.org/lustre_manual.xhtml#understandinglustre.components) (メタデータサーバ) と MDT (その記憶領域) | 名前、ディレクトリ、権限、中身の置き場所の問い合わせに答える | メタデータ |
| [OSS](https://doc.lustre.org/lustre_manual.xhtml#understandinglustre.components) (オブジェクトストレージサーバ) と OST (その記憶領域) | ファイルの中身の読み書きに答える。1 台の OSS は、ふつう 2〜8 個の OST を受け持つ | ファイルの中身 |
| LNet | クライアントとサーバをつなぐ通信層 | 宛先を表す NID (問い 3) |

サーバの機械を MDS や OSS と呼び、その機械が受け持つ記憶領域を MDT や OST と呼びます。

## メタデータとファイルの中身

![ファイル result.bin の MDT の記録は、持ち主や権限とレイアウトを持ち、レイアウトが OST 0、OST 2、OST 5 の object を指す](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/record-and-contents.png)

通常のファイルは、MDT にあるメタデータの記録と、OST にある object (OST がファイルの中身を持つ単位) の 2 つで表されます。持ち主、権限、時刻のような情報をメタデータと呼び、MDT が持ちます。ファイルの名前は、親のディレクトリの中の項目として MDT にあり、この記録を指します。

MDT の記録には、中身がどの OST のどの object にあるかを示すレイアウトも入っています。この記事では、中身を OST に置く場合を扱います。小さなファイルの中身を MDT に置く [DoM](https://doc.lustre.org/lustre_manual.xhtml#dataonmdt) (Data on MDT) という使い方もあります。

ストライプは、1 本のファイルを一定の大きさの塊に分けて、複数の OST に順番に置く方法です。1 本のファイルを、1 つの OST の帯域や容量を超えて読み書きするために使います。OST が別々の OSS にあれば、読み書きが複数の OSS に分かれるので、1 台の OSS あたりのネットワーク帯域は、ファイル全体で欲しい帯域より小さくて済みます。塊の大きさをストライプサイズ、塊を配る object の数をストライプ数と呼びます。図の例では、ストライプ数が 3 なら塊を OST 0、2、5 に順に置き、1 なら全部を OST 0 に置いています。OST 0 に入った塊 1、4、7 が、前の節の図の「OST 0 の object」の中身です。

MDS は中身の置き場所 (レイアウト) を伝え、OSS は中身そのものを送ります。読む前にクライアントが OSS から得るロックは、「ロック」の節で説明します。

名前の問い合わせと中身の読み書きを別のサーバに分けているので、**DoM を使わない場合、中身の転送に MDS は出てきません**。そのため OSS と OST を増やすと、クライアント、ネットワーク、ディスクが詰まらない範囲で、全体の帯域を伸ばせます。ただし、すでにあるファイルの置き場所は、OST を足しても自動では広がりません。1 本のファイルの帯域は、そのファイルが使う OST の数にも左右されます。

書き込みも、レイアウトを受け取り、OSS からロックを得てから OSS とやりとりする点は、読み込みと同じです。

## 複数の MDT

![ルートと /projA が MDT 0 に、/projB が MDT 1 にあり、ストライプしたディレクトリ /projC の中身は MDT 1 と MDT 2 に分かれている。クライアントからは 1 つの木に見える](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/dne.png)

MDT が 1 つだけだと、名前に関する操作がその MDT に集まります。そこで Lustre は、ディレクトリツリーの一部を別々の MDT に置けます。この仕組みを [DNE](https://doc.lustre.org/lustre_manual.xhtml#DNE) (Distributed Namespace Environment、名前空間の分散) と呼びます。ルートのディレクトリは、最初の MDT にあります。

1 つのディレクトリの中身を、複数の MDT に分けることもできます。これを[ストライプしたディレクトリ](https://doc.lustre.org/lustre_manual.xhtml#stripeddirectory)と呼びます。どちらの場合も、クライアントの中の [LMV](https://github.com/lustre/lustre-release/tree/6325870717c7899f1ba545493ce2a07cb3834a6b/lustre/lmv) という部品が各 MDT の答えをまとめるので、アプリケーションからは 1 つのディレクトリツリーに見えます。

複数のクライアントが同じファイルを読み書きしても、それぞれの手元のデータが食い違わないように、サーバがロックを貸し出します。この仕組みを [LDLM](https://doc.lustre.org/lustre_manual.xhtml#ldlm) (分散ロックマネージャ) と呼びます。OSS はファイルの中身のロックをデータの範囲ごとに貸し出し、MDS はメタデータのロックを別に貸し出します。図は、中身のロックだけを描いたものです。ロックを持つクライアントは、その範囲のデータを手元にためて (キャッシュして) おけます。持ち主は、ロックを返す前に、ためていたデータを書き戻します。

持ち主が決まった時間内にロックを返さないとき、サーバは、その MDT や OST について、クライアントを切り離します。これを [evict](https://doc.lustre.org/lustre_manual.xhtml#clientevictions) と呼びます。切り離されたクライアントは、その MDT や OST から借りていたロックがすべて無効になり、そこ向けにためていたデータのうち、まだサーバに書いていないものは失われることがあります。ロックを返さないことのほか、クライアントからの要求も生存確認の知らせも決まった時間届かないことも、evict の理由になります。

## クライアントの中の層

クライアントの中の Lustre は、役割の違う層を重ねて、アプリケーションの読み書きをネットワークのメッセージに変えます。

:::message
**プロトコルの読み方**

層を重ねたプロトコルは、どの層にも同じ 4 つの問いを当てると読めます。

1. 何を運び、上の層の何を包むか
2. 何を受け持ち、失われたものをどこで送り直すか
3. どの ID で相手やものを指すか
4. どんな状態を、両端の機械と途中のどちらで持つか

この節は、この番号の順に Lustre の層を見ます。
:::

:::details コラム: 送り直しと状態をどこに置くか

送り直しと状態の置き場所には、インターネットの設計で議論されてきた考え方があり、Lustre の層もその考え方で読めます。

[End-to-End Arguments in System Design](https://web.mit.edu/Saltzer/www/publications/endtoend/endtoend.pdf) は、Saltzer らが 1984 年に書いた論文です。例として、ファイルを別の機械へ確実に写す話を挙げます。途中のネットワークがどれだけ確実に運んでも、ディスクから読む途中や書く途中で壊れることがあるので、最後は両端のアプリケーションが写した結果を確かめるしかありません。下の層の送り直しは、確かめ直しの回数を減らす性能のための補助だ、というのが論文の主張です。Lustre では、TCP の層や InfiniBand のネットワークカードが送り直しても、要求が実行されたかは ptlrpc の応答で、ディスクに確定したかはサーバが返す確定済みの transno で、ptlrpc が確かめます。

[The Design Philosophy of the DARPA Internet Protocols](http://ccr.sigcomm.org/archive/1995/jan95/ccr-9501-clark.pdf) は、Clark が 1988 年にインターネットの設計の優先順位をまとめた論文です。通信の状態を途中のゲートウェイではなく、それを使う端の機械に置き、その機械が失われたときにだけ状態も失われるようにします。これを fate-sharing と呼びます。途中の機械が止まっても、端の状態は残るので通信を続けられます。Lustre でも、送り直しに必要な要求はクライアントの ptlrpc が持ち、途中の LNet ルーターはやりとりの状態を持ちません。サーバが再起動したときは、サーバはディスクの記録と、クライアントが送り直す要求 (replay) から状態を作り直します。

[RFC 3439](https://www.rfc-editor.org/rfc/rfc3439) は、Bush と Meyer が 2002 年にインターネットの設計の指針をまとめた文書です。その 3 節「Layering Considered Harmful」は、層を厳密に分けると、誤りの制御のような同じ機能が複数の層に重なり、下の層が最適化に使いたい情報も隠れると指摘します。Lustre でも送り直しは TCP、LNet、ptlrpc に重なっています。一方で LND は送受信の失敗を LNet に伝え、LNet はそれを health に反映して送り先の NID を選び直します。層の境目を越えて情報を渡すことで、重なりの弊害を減らしている例です。
:::

### 1. 何を運び、何を包むか

![TCP で動かすとき、外側から Ethernet、IP、TCP、ksocklnd、LNet、ptlrpc の順にヘッダが付いて入れ子になる。llite、mdc、osc は自分のヘッダを持たず、操作を ptlrpc の要求の中身として渡す。bulk のデータは ptlrpc のヘッダを持たない別の LNet のメッセージになる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/protocol-stack.png)

問い 1 の答えは、層の入れ子 (カプセル化) で表せます。カプセル化は、上の層のメッセージ全体を、下の層が自分のヘッダを付けて中身として包むことです。TCP で動かすときは、外側から Ethernet、IP、TCP、ksocklnd、LNet、ptlrpc の順に入れ子になります。図は TCP の場合です。Lustre は TCP だけでなく InfiniBand や AWS の EFA の上でも動き、そのときは LND から下が、それぞれのネットワークの仕組みに置き換わります。TCP から見ると LNet も ptlrpc も TCP に載せて運ぶデータで、LNet は、その上に作られた IP に似た独自のネットワーク層だといえます。

ヘッダを持つのは ptlrpc から下の層です。[llite](https://github.com/lustre/lustre-release/tree/6325870717c7899f1ba545493ce2a07cb3834a6b/lustre/llite)、[mdc](https://github.com/lustre/lustre-release/tree/6325870717c7899f1ba545493ce2a07cb3834a6b/lustre/mdc)、[osc](https://github.com/lustre/lustre-release/tree/6325870717c7899f1ba545493ce2a07cb3834a6b/lustre/osc) は自分のヘッダを持たず、どの FID のどこを読むかのような操作を、ptlrpc の要求の中身として渡します。ファイルの中身はふつう要求に入らず、bulk という別の LNet のメッセージで運ばれます。小さな読み書きでは、中身を要求や応答に入れて運ぶこともあります (short I/O)。図の LNet のヘッダにある portal の番号と match bits は、受け手が届いたデータを入れるバッファを選ぶための値です。portal は受け口の番号で、match bits はその受け口の中で、どのバッファに入れるかを選ぶ 64 ビットの値です。

### 2. 何を受け持ち、どこで送り直すか

問い 2 の答えを、層ごとに並べます。

| 層 | 受け持ち | 失敗と送り直し |
|---|---|---|
| llite、mdc、osc | ファイルの操作を、どの MDT や OST に何を頼むかの要求に変える。mdc は MDT ごと、osc は OST ごとにあり、LMV と [LOV](https://github.com/lustre/lustre-release/tree/6325870717c7899f1ba545493ce2a07cb3834a6b/lustre/lov) がまとめる | 自分では送り直さない。直らなかった失敗を、アプリケーションにエラーとして返す |
| LDLM | ロックの貸し出しと回収 | 復旧のときは、借りているロックをサーバに伝え直す。ロックを返さないクライアントを切り離す (evict) |
| [ptlrpc](https://github.com/lustre/lustre-release/tree/6325870717c7899f1ba545493ce2a07cb3834a6b/lustre/ptlrpc) | 要求と応答の組 (RPC) を管理する | 応答が時間内に来なければ接続を張り直し、同じ番号に送り直しの印を付けて送る (resend)。サーバの再起動のあとは、応答済みでまだ確定していない要求を、変更の順番に再実行させる (replay)。番号は問い 3 で見る |
| LNet | NID で宛先を表し、経路と NID の組を選ぶ | 届くことは保証しない。LND が返した失敗の種類によっては、NID の組を選び直して送り直す。待っている ACK や REPLY の時間切れでは送り直さず、失敗を上へ返す |
| LND | ネットワークの種類ごとの送受信 | ksocklnd は送り直しを TCP に任せ、切れた接続を張り直す。ko2iblnd が使う InfiniBand の RC の接続と、kefalnd が使う EFA の SRD では、ネットワークカードが送り直す |
| TCP、InfiniBand の RC、EFA の SRD | 確実に届ける。TCP と RC は順番も守るが、SRD は守らない | 失われたデータを送り直す |
| IP、Ethernet | 相手の機械まで、また同じネットワークの機械どうしで届ける | 送り直さない。壊れたフレームは捨てる |

Lustre の RPC (Remote Procedure Call) は、操作を 1 つの要求のメッセージにして MDS や OSS に送り、サーバがその操作を実行して応答のメッセージを返す、要求と応答の組です。

![LNet の下に、TCP 向けの ksocklnd、InfiniBand 向けの ko2iblnd、AWS の EFA 向けの kefalnd が並ぶ](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/lnet-lnd.png)

LND (Lustre network driver) は、ネットワークの種類ごとにあります。TCP には [ksocklnd](https://github.com/lustre/lustre-release/tree/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/socklnd)、InfiniBand には [ko2iblnd](https://github.com/lustre/lustre-release/tree/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/o2iblnd)、AWS の [EFA](https://aws.amazon.com/hpc/efa/) には [kefalnd](https://github.com/lustre/lustre-release/tree/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/efalnd) があります。ko2iblnd は TCP/IP の層を使わず、相手を IP アドレスで探したあと、小さいメッセージは InfiniBand の SEND で、大きいデータは [RDMA で送ります](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds/o2iblnd/o2iblnd_cb.c#L463-L490)。kefalnd が使う EFA の [SRD](https://www.amazon.science/publications/a-cloud-optimized-transport-protocol-for-elastic-and-scalable-hpc) (Scalable Reliable Datagram) は、ネットワークカードの中で送り直しをしますが、パケットを多くの経路に散らすので順番は守りません。LND がネットワークごとの違いを受け持つので、LNet より上の層は、ネットワークの種類によらず同じ呼び出し方で LNet を使えます。

![tcp0 のクライアントが、tcp0 と o2ib0 の両方に NID を持つ LNet ルーターを通って、o2ib0 の OSS と MDS に届く](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/router.png)

違う LNet のネットワークにいる相手とは、[LNet ルーター](https://doc.lustre.org/lustre_manual.xhtml#managinglnet.configuringroutes)を通って通信します。ルーターは、2 つのネットワークのそれぞれに NID を持ち、ルーターとして動くように設定された機械で、片方で受け取った LNet のメッセージを、もう片方へ転送します。LNet のルーティングは、IP のルーティングとは別に動きます。

### 3. どの ID で何を指すか

問い 3 の答えです。各層は、別々の ID で相手やものを指します。

![10.0.1.20@tcp0 という NID は、アドレス 10.0.1.20 と、LNet のネットワーク名 tcp0 を @ でつないだもの。1 台のサーバが複数の NID を持てる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/nid.png)

| ID | 使う層 | 指すもの |
|---|---|---|
| [FID](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/include/uapi/linux/lustre/lustre_user.h#L362) (File Identifier) | Lustre 全体 | ファイルシステムの中の 1 つのファイルや object。sequence の番号と、その中の番号の組で、sequence ごとに置かれるサーバが決まる |
| MDT や OST の番号 | Lustre 全体 | ファイルシステムの中の 1 つの MDT や OST。レイアウトは、OST の番号と object の組で中身の置き場所を表す |
| ロックのハンドル | LDLM | 貸し出された 1 つのロック。ロックの対象には、FID をもとにした名前が付く |
| [XID](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lustre/ptlrpc/client.c#L3692) | ptlrpc | クライアントが出した 1 つの要求。送り直し (resend) も同じ番号なので、サーバは同じ要求の 2 回目だと分かる |
| [transno](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lustre/ptlrpc/client.c#L1736-L1740) | ptlrpc | サーバが変更に付ける順番。応答済みでまだ確定していない要求を、再起動のあとこの順に再実行させる (replay)。サーバは確定した最大の transno を応答で返し、クライアントはそこまでの要求を捨てる |
| NID と portal の番号と match bits | LNet | NID は 1 つのネットワークインターフェース。portal の番号と match bits は、受け手のどのバッファに入れるか |

[NID](https://doc.lustre.org/lustre_manual.xhtml#understandinglustrenetworking) (network identifier) は、`10.0.1.20@tcp0` のように、アドレスと LNet のネットワーク名を @ でつないだものです。図の値は説明用の例です。ネットワーク名は LND の種類に番号を付けたもので、tcp0 は TCP、o2ib0 や o2ib1 は InfiniBand のネットワークを表します。1 台のサーバは複数の NID を持てます。LNet は、NID の一覧をまだ知らない相手へ最初に送るときに、LNet の ping を送って一覧を受け取ります。この動きを [discovery](https://doc.lustre.org/lustre_manual.xhtml#lnet_config.dynamic_discovery) と呼びます。

ptlrpc から見ると、やりとりは要求と応答の組と、ファイルの中身を動かす bulk の 2 つです。ただし ptlrpc は自分ではデータを動かさず、どちらも下の LNet の PUT と GET で実現しています。

![PUT は始める側がデータを相手に送り込み、求められたときだけ ACK が返る。GET は始める側が要求を送ると、データを載せた REPLY が返る](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/messages.png)

PUT は、送り手が相手のバッファにデータを送り込み、送り手が求めたときだけ ACK が返ります。GET は、相手のバッファからデータを取ってきて、データは REPLY に載って返ります。受け手は、届いたメッセージの portal の番号と match bits を、あらかじめ登録したバッファと照らし合わせて、データの置き場所を決めます。置き場所を match bits で決めるので、Lustre はメッセージの届く順番に頼りません。順番を守らない SRD の上でも動ける理由の 1 つで、ptlrpc も応答は match bits で選び、replay はサーバが transno の順に並べます。

| ptlrpc から見えるもの | LNet での実現 | match bits |
|---|---|---|
| 要求 | クライアントが、サーバの要求用の portal へ PUT する。サーバは match bits を照合せず、空いているバッファに受ける | XID (照合には使わない) |
| 応答 | サーバが、クライアントが先に登録した応答用のバッファへ PUT する | XID、または送り直しのたびに取り直す番号 |
| bulk の読み込み | OSS が、クライアントが登録したバッファへ [PUT で送り込む](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lustre/target/tgt_handler.c#L2506-L2509) | 要求に書いた bulk の match bits |
| bulk の書き込み | OSS が、クライアントが登録したバッファから [GET で取りに来る](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lustre/target/tgt_handler.c#L2957-L2960) | 要求に書いた bulk の match bits |

bulk は、ptlrpc の層では大きなデータの転送に見えます。その実体は、クライアントが要求を送る前に LNet にバッファを登録し、その match bits を要求に書いて OSS に知らせ、OSS がそのバッファに向けて PUT や GET を出すことです。bulk の match bits は [送り直しのたびに取り直す](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lustre/ptlrpc/client.c#L3705)ので、前の試みのデータが新しいバッファに入ることはありません。

### 4. どんな状態をどこで持つか

問い 4 の答えです。

| 層 | 持つ状態 |
|---|---|
| LDLM | 貸し出したロックと借りたロック |
| ptlrpc | MDT や OST との論理的な接続の状態 (import)、応答を待っている要求、サーバのディスクにまだ確定していない変更の要求。サーバ側は、クライアントごとに export を持つ |
| LNet | 相手と、その NID の一覧、NID ごとの health、送信の枠 (credits)、経路の表。接続は持たない |
| ksocklnd | 相手ごとの TCP の接続 |

[import](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lustre/include/lustre_import.h#L67) は、クライアントがサーバの再起動や接続の切れ目のあとも作業を続けられるように持つ、MDT や OST ごとの接続の状態です。サーバがこのクライアントとの接続の情報をまだ持っていれば、import は RECOVER を経て FULL (ふつうにつながっている状態) に戻ります。再起動したサーバが[復旧](https://doc.lustre.org/lustre_manual.xhtml#lustrerecovery)を受け付けている間に接続し直したときは、クライアントが要求とロックを送り直してから戻ります。サーバがクライアントを切り離していたときは、[EVICTED を通ります](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lustre/ptlrpc/import.c#L1341-L1394)。evict された場合、その間に進んでいた操作は失敗します。

import は ptlrpc が持つ状態で、NID ごとの調子は LNet の health が持ちます。そのため、接続が切れたとみなした状態 (DISCON) は、特定の NID が壊れたことを意味しません。


## まとめ

Lustre は、名前の問い合わせと中身の読み書きを別のサーバに分けます。DoM を使わない場合、ファイルの中身は MDS を通らずに OSS とやりとりするので、クライアント、ネットワーク、ディスクが詰まらない範囲で、OSS と OST を増やすと帯域を伸ばせます。その通信は、ptlrpc が要求と応答の組とやり直しの状態を受け持ち、LNet が NID と match bits で宛先とバッファを決め、LND がネットワークごとの送受信を受け持つ、という層の重なりでできています。
