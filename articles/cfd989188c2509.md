## はじめに

Lustre は、たくさんのクライアントが同じファイルシステムに同時に読み書きするための、並列ファイルシステムです。クライアントは、Lustre のファイルを読み書きするコンピュータのことです。並列ファイルシステムは、ファイルの中身を複数のサーバに分けて置き、多くのクライアントが同時に高速に読み書きできるようにした仕組みです。HPC (高性能計算) の大きなクラスタで使われてきました。この記事では、Lustre の部品と、部品の間をつなぐ通信層の LNet を、図で見ていきます。

特定のクラウドサービスの運用や設定には踏み込みません。ネットワークの種類の例として、AWS の EFA の名前が出てきます。続きの記事で、この記事の知識を使って、FSx for Lustre の EFA と TCP を実測とあわせて比べます。

## 全体像

![クライアントが LNet のネットワークを通って、MGS、MDS と MDT、OSS と OST の 3 種類のサーバと話す。ファイルの中身は OST にある](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/overview.png)

Lustre は、ファイルの名前や置き場所を持つサーバと、ファイルの中身を持つサーバを分けたファイルシステムです。クライアントは、その両方のサーバと話します。

| 部品 | 受け持ち | 持つもの |
|---|---|---|
| クライアント | ファイルシステムをマウントして、アプリケーションに見せる | 自分のディスクは要らない |
| MGS (管理サーバ) | ファイルシステムの構成を、サーバとクライアントに渡す | 構成の情報 |
| MDS (メタデータサーバ) と MDT (メタデータの記憶領域) | 名前、ディレクトリ、権限、中身の置き場所の問い合わせに答える | メタデータ |
| OSS (オブジェクトストレージサーバ) と OST (その記憶領域) | ファイルの中身の読み書きに答える | ファイルの中身 |
| LNet | クライアントとサーバをつなぐ通信層 | 宛先を表す NID (あとの節で説明) |

サーバの機械を MDS や OSS と呼び、その機械が受け持つ記憶領域を MDT や OST と呼びます。マニュアルでは、1 台の OSS が受け持つ OST は典型的に数個 (1〜8 個程度) とされています。MGS は MDS と同じ機械に置くこともできます。MDS、MDT、OSS、OST の名前は、この記事の最後まで使います。この表は [Lustre のマニュアル](https://doc.lustre.org/lustre_manual.xhtml) の説明をもとにしています。

## メタデータとファイルの中身

![ファイル result.bin の記録は MDT にあり、その中のレイアウトが、中身を持つ OST 1、OST 4、OST 7 の object を指す](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/record-and-contents.png)

通常のファイルは、MDT にある記録と、OST にある中身の 2 つで表されます。名前、親のディレクトリ、持ち主、権限のような情報をメタデータと呼び、MDT が持ちます。

MDT の記録には、中身がどの OST にあるかを示すレイアウトも入っています。OST の側では、ファイルの中身を object という単位で持ちます。通常のファイルは、1 つ以上の object を持ちます。次の節のストライプ数が 2 以上なら、object は別々の OST に置かれます。

## ストライプ

![9 個の 1 MiB の塊を持つファイルが、OST 1、OST 4、OST 7 に順番に配られる。1、4、7 番目が OST 1 に、2、5、8 番目が OST 4 に、3、6、9 番目が OST 7 に入る](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/striping.png)

ストライプは、1 本のファイルを一定の大きさの塊に分けて、複数の OST に順番に置く方法です。塊の大きさをストライプサイズ、置く OST の数をストライプ数と呼びます。

既定のストライプサイズは 1 MiB で、既定のストライプ数は 1 です。図は、ストライプ数を 3 に変えた例です。図の OST 1 に入った塊 1、4、7 は、前の節の図で「OST 1 の object」と描いたものの中身です。どちらもファイルごと、ディレクトリごと、ファイルシステムごとに変えられます。1 本のファイルへの帯域が 1 つの OST の帯域を超えたいときや、1 つの OST の空き容量に収まらない大きなファイルを置くときに、ストライプ数を増やします。

## ファイルを読む流れ

![クライアントが MDS に open を送ってレイアウトを受け取り、3 つの OSS に読み込みの要求を並行して送ると、各 OSS からファイルの中身が返ってくる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/read-flow.png)

MDS はファイルの中身の置き場所を伝え、OSS は中身そのものを送ります。この役割の分担が、読む流れの形を決めます。クライアントは次の順に動きます。

1. MDS に、ファイルを開く要求を送ります。
2. MDS が、レイアウトを返します。
3. レイアウトにある OST を持つ OSS から、読む範囲のロックを得ます。ロックは次々節で説明します。
4. 読む範囲が複数の OST にまたがるときは、複数の OSS に読み込みの要求を並行して送ります。
5. 各 OSS が、ファイルの中身を返します。

**名前の問い合わせと中身の読み書きを別のサーバに分けているので、中身の転送に MDS は出てきません。** そのため OSS と OST を増やすと、ネットワークやディスクが詰まらない範囲で、全体の帯域を伸ばせます。ファイルシステム全体の帯域は、OSS 側のネットワーク帯域と、OST のディスク帯域のうち、小さいほうで決まります。1 本のファイルの帯域は、そのファイルが使う OST の数にも左右されます。

書き込みも、レイアウトを受け取り、OSS からロックを得てから OSS とやりとりする点は、読み込みと同じです。

## 複数の MDT

![ルートと /projA が MDT 0 に、/projB が MDT 1 に、/projC が MDT 2 にある。クライアントからは 1 つの木に見える](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/dne.png)

MDT が 1 つだけだと、名前に関する操作がその MDT に集まります。そこで Lustre は、ディレクトリの木を複数の MDT に分けられます。この仕組みを DNE (Distributed Namespace、名前空間の分散) と呼びます。ルートのディレクトリは、最初の MDT にあります。

1 つのディレクトリの中身を、複数の MDT に分けることもできます。これをストライプしたディレクトリと呼びます。どちらの場合も、クライアントの中の LMV という部品 (複数の MDT をまとめる部分) が各 MDT の答えをまとめるので、アプリケーションからは 1 つの木に見えます。

## ロック

![クライアント A が書き込みのロックを取り、クライアント B が同じ範囲の読み込みのロックを求めると、OSS が A にロックを返すよう求め、A が書き戻して手放した後で B に貸し出す](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/locks.png)

複数のクライアントが同じファイルを読み書きしても、内容が食い違わないように、サーバがロックを貸し出します。この仕組みを LDLM (分散ロックマネージャ) と呼びます。ロックはデータの範囲ごとに取り、ロックを持つクライアントは、その範囲のデータを手元にためておけます。

別のクライアントが、今のロックと両立しない種類のロック (たとえば、書き込みのロックがある範囲への読み込みのロック) を求めると、ロックを貸し出している OSS は今の持ち主に、ロックを返すよう求めます。持ち主は、ためていたデータをサーバに書き戻してから、ロックを手放したことをサーバに伝えます。サーバはそれを受けて、待っていたクライアントにロックを貸し出したことを知らせます。待っていたクライアントは、その知らせを受けてから読み書きを始めます。

持ち主が決まった時間内に答えないとき、サーバはそのクライアントを切り離します。これを evict と呼びます。切り離されたクライアントは、持っていたロックがすべて無効になり、手元にためていた情報とデータも無効になります。ロックを返す要求への無応答のほか、サーバの要求に時間内に答えないことや、クライアントが決まった時間内にサーバへ生存確認の ping を送らないことも、evict の理由になります。ただし、サーバがどのクライアントからも RPC を受け取っていないときは、ping が来なくても evict しません。この ping は、あとに出てくる LNet の ping とは別のものです。

## クライアントの中の層

![アプリケーションの下に、llite、lmv と mdc、lov と osc、ptlrpc、LNet、LND、ネットワークカードが順に重なる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/client-layers.png)

クライアントの Lustre のソフトウェアは、層になっています。llite は、Linux から見て普通のファイルシステムに見える部分です。その下の mdc と osc が、MDT 向けと OST 向けの要求を組み立てます。osc は OST ごとに 1 つあり、ストライプの全体は LOV という部品がまとめます。mdc は MDT ごとに 1 つあり、複数の MDT は LMV がまとめます。ロックを扱う LDLM は図には描いていませんが、mdc と osc のそばで要求にかかわります。

ptlrpc は、要求を送って応答を待ち、応答が来なければサーバとの接続を張り直します。RPC は Remote Procedure Call の略で、離れた機械に仕事を頼む呼び出しのことです。その下の LNet が、宛先と通る経路を決めます。一番下の LND が、ネットワークの種類に合わせて、実際の送受信をします。

## RPC と bulk

![読み込みでは、クライアントが読み込みの RPC を送ると OSS がデータをクライアントのバッファに送り込み、最後に応答の RPC を返す。書き込みでは、クライアントが書き込みの RPC を送ると OSS がデータを取りに来て、最後に応答の RPC を返す](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/rpc-bulk.png)

クライアントとサーバのやりとりは、2 種類に分かれます。1 つは、要求を送って応答を受け取る小さなやりとりで、RPC と呼びます。もう 1 つは、ファイルの中身のような大きなデータの移動で、bulk と呼びます。

ふつうの大きな読み書きでは、次のようになります。読み込みでは、クライアントがデータを受けるバッファを用意して、読み込みの RPC を送ります。OSS はそのバッファにデータを送り込み、最後に応答の RPC を返します。書き込みでは、クライアントが書き込みの RPC を送って、送るデータの場所を教えます。OSS はそこへデータを取りに来て、最後に応答の RPC を返します。どちらも、データを動かす側は OSS です。小さな I/O では bulk を使わず、データを RPC に載せる場合もあります。[クライアント側の準備](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lustre/osc/osc_request.c#L1786) と、[OSS 側の読み込み](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lustre/target/tgt_handler.c#L2506-L2509)、[書き込み](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lustre/target/tgt_handler.c#L2957-L2960) の処理で確かめられます。

## NID

![10.0.1.20@tcp0 という NID は、IP アドレス 10.0.1.20 と、LNet のネットワーク名 tcp0 を @ でつないだもの。1 台のサーバが複数の NID を持てる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/nid.png)

NID は、LNet が宛先を表すのに使うアドレスです。ネットワークインターフェースのアドレスと、LNet のネットワーク名を、@ でつなぎます。TCP や InfiniBand では、アドレスの部分に IP アドレスを使います。たとえば `10.0.1.20@tcp0` のような形で、図の値は説明用の例です。ネットワーク名は、LND (次の節) の種類に番号を付けたもので、tcp0 は TCP、o2ib0 や o2ib1 は InfiniBand のネットワークを表します。

1 台のサーバは、複数の NID を持てます。相手が Multi-Rail (あとの節) に対応していれば、LNet は、メッセージごとに、その中から 1 つを選びます。相手が持つ NID の一覧は、最初のメッセージを送るときに、LNet が相手に LNet の ping を送って教えてもらいます。この動きは既定で有効で、lnetctl で切ることもできます。

## LND: ネットワークごとのドライバ

![LNet の下に、TCP 向けの ksocklnd、InfiniBand 向けの o2iblnd、AWS の EFA 向けの kefalnd などの LND が並ぶ](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/lnet-lnd.png)

LNet 自体は、ネットワークの種類を知りません。ネットワークごとの送受信は、LND というドライバが受け持ちます。TCP には ksocklnd、InfiniBand には o2iblnd があります。EFA 向けの kefalnd (ソースのディレクトリ名は efalnd) も、[upstream のソース](https://github.com/lustre/lustre-release/tree/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds) に入っています。

LNet の層は、接続を持たず、非同期で、データが届いたかを確かめません。LND の層は、接続を持ち、ふつうは届いたかを確かめます。LND が送受信の失敗を見つけると、LNet に伝えます。LNet は、これと、経路が見つからない、期待した応答が時間内に来ない、といった自分で見つけた失敗をもとに、NID の調子を表す数 (health、あとの節) を下げます。失敗の種類によっては、LNet がメッセージを再送し、再送しきれないときに上の層へ失敗を伝えます。上の層は、ネットワークが変わっても同じ形で LNet を使えます。

## LNet のメッセージ

![PUT は送り手がデータを相手に送り込み、求められたときだけ ACK が返る。GET は要求を送ると、データを載せた REPLY が返る](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/messages.png)

LNet が運ぶメッセージは、PUT、ACK、GET、REPLY、HELLO の 5 種類で、基本は PUT と GET です。PUT は、送り手が相手にデータを送り込みます。送り手が求めたときだけ、受け取りの確認の ACK が返ります。GET は、欲しいものを書いた要求を送ると、データを載せた REPLY が返ります。

「RPC と bulk」の節の bulk は、この 2 つでできています。読み込みでは OSS が PUT でデータを送り込み、書き込みでは OSS が GET でデータを取りに来ます。HELLO は、TCP の LND が接続を始めるときに使います。[メッセージの種類](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/include/uapi/linux/lnet/lnet-idl.h#L79) は、ソースで確かめられます。

## Multi-Rail と health

![クライアントの 2 つの NID とサーバの 2 つの NID の組み合わせが経路の候補で、LNet がそのうち 1 つを選ぶ。NID の health は 1000 から始まり、失敗で 900 に下がり、LNet の ping が成功するたびに 1 ずつ戻る](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/multirail-health.png)

1 台が複数の NID を持つとき、LNet は、メッセージごとに、送る側と受ける側の NID の組を選びます。双方が使える NID と、相手が Multi-Rail に対応しているかなどに応じて、候補が決まります。この仕組みを Multi-Rail と呼びます。NID の一覧は候補を示すだけで、実際にどの組が通ったかは、メッセージごとに別に決まります。選ぶときの手がかりの 1 つが、health です。

health は、NID ごとの調子を表す 0 から 1000 の数です。最初は 1000 で、失敗すると下がります。既定では 1 回の失敗で 100 下がります (数値は既定の設定の場合)。使える NID が複数あるとき、数が低い NID は選ばれにくくなります。下がった NID には、LNet が既定で 1 秒ごとに ping を送って調子を確かめます。ping が 1 回成功するたびに、数は 1 ずつ戻ります。自分の NID の失敗と、相手の NID の失敗は、分けて数えます。health のほかに、ユーザーが決める優先度の規則もあり、UDSP (User Defined Selection Policy) と呼びます。続きの記事で、この優先度が出てきます。[マニュアルの LNet Health](https://doc.lustre.org/lustre_manual.xhtml) に、失敗の種類ごとの扱いが書かれています。

## ルーター

![tcp0 のクライアントが、2 つのネットワークに NID を持つ LNet ルーターを通って、o2ib0 の OSS と MDS に届く](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/router.png)

違う LNet のネットワークにいる相手とは、LNet ルーターを通って通信します。ルーターは、2 つのネットワークのそれぞれに NID を持つ機械で、片方で受け取ったメッセージを、もう片方へ転送します。たとえば、TCP のクライアントが、InfiniBand 側にあるサーバの NID に向けて送ると、ルーターが間を取り持ちます。LNet のルーティングは、IP のルーティングとは別のものです。

## 接続の状態と復旧

![import の状態は FULL、DISCON、CONNECTING、RECOVER の順に進んで FULL に戻る。サーバが復旧中なら REPLAY、REPLAY_LOCKS、REPLAY_WAIT を通り、サーバがクライアントを忘れていたら EVICTED を通る](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/import-states.png)

クライアントは、MDT や OST ごとに接続の状態を持っていて、これを import と呼びます。ptlrpc が管理します。主な状態を、普段の FULL (つながっている) から順に説明します。ほかに NEW、CLOSED、IDLE などの状態もあります。要求が時間内に終わらないと DISCON (切れた) になり、ptlrpc がサーバに接続し直します。この間は CONNECTING (接続中) です。

サーバがクライアントを覚えていれば、状態は RECOVER に進み、FULL に戻ります。サーバが再起動して復旧中なら、REPLAY でサーバが応答したもののディスクに書き終えていなかった要求を送り直し、REPLAY_LOCKS でロックを伝え直し、REPLAY_WAIT でサーバの復旧が終わるのを待ってから、RECOVER に進みます。サーバがクライアントを忘れていた場合、クライアントは多くの場合、接続し直したときに、自分が切り離されていたと知ります。状態は EVICTED になり、ロックと手元の情報を無効にしてから、RECOVER に進みます。接続し直している間、新しい要求は待たされることがあります。ただし evict された場合、その間に進んでいた操作は失敗します。

import の状態は ptlrpc の接続の状態で、LNet の NID の health とは別の層の情報です。DISCON になったからといって、特定の NID が壊れたとも、別の経路に切り替わったともいえません。health が下がることや再接続は、それだけでは evict を意味しません。evict は、サーバがクライアントを切り離す出来事です。[状態の一覧](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lustre/include/lustre_import.h#L67) と [遷移の処理](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lustre/ptlrpc/import.c#L1341-L1394) は、ソースで確かめられます。

## 層ごとの受け持ち

1 つの RPC が失敗したときは、下の層から順に次のように進みます。LND が送受信の失敗を見つけて LNet に伝え、LNet が health を下げて、必要なら再送します。それでも応答が時間内に届かないと、ptlrpc が import を DISCON にして接続を張り直します。サーバが待ちきれずにクライアントを切り離していれば、再接続のときに EVICTED を通ります。

| 層 | 受け持ち | 失敗したとき |
|---|---|---|
| ptlrpc | RPC の送受信、応答の待ち、接続の張り直し | 要求が時間内に終わらないと、接続を張り直す |
| LDLM | ロックの貸し出し | 返事をしないクライアントを evict する |
| LNet | 宛先の NID と、通る経路の選択 | health を下げて、ほかの NID を選びやすくする。失敗の種類によっては再送し、再送しきれなければ上の層へ失敗を伝える |
| LND | ネットワークごとの送受信 | 送受信の失敗を LNet に伝える |

## まとめ

Lustre は、名前の問い合わせと中身の読み書きを別のサーバに分け、クライアントが OSS と直接話すので、OSS と OST を増やすと帯域を伸ばせます。その通信は、LNet が NID と LND で支え、失敗は health と import の状態に現れます。
