## はじめに

Lustre は、たくさんのクライアントが同じファイルシステムに同時に読み書きするための、並列ファイルシステムです。ファイルの中身を複数のサーバに分けて置き、多くのクライアントが同時に高速に読み書きできるようにしています。HPC (高性能計算) の大きなクラスタで使われてきました。この記事では、Lustre の部品と、部品の間をつなぐ通信層の LNet を、図で見ていきます。

特定のクラウドサービスの運用や設定には踏み込みません。ネットワークの種類の例として、AWS の EFA の名前が出てきます。続きの記事で、この記事の知識を使って、FSx for Lustre の EFA と TCP を実測とあわせて比べます。

:::message
この記事の動く図 (右上に「Stop」「EN」「日本語」があるもの) は、押したり切り替えたりできます。図の中の箱やラベルを押すと、その用語の基本の説明が図の下に出ます (出典があれば添えます)。動く図で扱う用語の基本の説明は、本文では省いています。「EN」と「日本語」で図の言語を切り替えられます。「Stop」を押すと動きが止まり、すべての要素を描き込んだ静止画になります。もう一度押すと、また動きます。図をスクリーンショットで残すときにお使いください。
:::

## 全体像

![クライアントが LNet を通って MGS、MDS と MDT、OSS と OST の 3 種類のサーバと話す。メタデータと構成の情報は両方向に、ファイルの中身は OSS とクライアントの間を流れる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/overview.png)

Lustre は、ファイルの名前や置き場所を持つサーバと、ファイルの中身を持つサーバを分けたファイルシステムです。クライアントは、その両方のサーバと、MDS を通さずに直接話します。

| 部品 | 受け持ち | 持つもの |
|---|---|---|
| クライアント | ファイルシステムをマウントして、アプリケーションに普通のファイルシステムとして見せる | 自分のディスクは要らない |
| MGS (管理サーバ) | ファイルシステムの構成を、サーバとクライアントに渡す。MDS と同じ機械に置くこともできる | 構成の情報 |
| MDS (メタデータサーバ) と MDT (その記憶領域) | 名前、ディレクトリ、権限、中身の置き場所の問い合わせに答える | メタデータ |
| OSS (オブジェクトストレージサーバ) と OST (その記憶領域) | ファイルの中身の読み書きに答える。1 台の OSS は典型的に 2〜8 個の OST を受け持つ | ファイルの中身 |
| LNet | クライアントとサーバをつなぐ通信層 | 宛先を表す NID (あとの節で説明) |

サーバの機械を MDS や OSS と呼び、その機械が受け持つ記憶領域を MDT や OST と呼びます。MDS、MDT、OSS、OST の名前は、この記事の最後まで使います。この表は [Lustre のマニュアル](https://doc.lustre.org/lustre_manual.xhtml) の説明をもとにしています。

## メタデータとファイルの中身

![ファイル result.bin の MDT の記録は、持ち主や権限とレイアウトを持ち、レイアウトが OST 0、OST 2、OST 5 の object を指す](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/record-and-contents.png)

通常のファイルは、MDT にあるメタデータの記録と、OST にある object の 2 つで表されます (小さなファイルの中身を MDT に置く DoM を使わない場合)。持ち主、権限、時刻のような情報をメタデータと呼び、MDT が持ちます。ファイルの名前は、親のディレクトリの中の項目として MDT にあり、この記録を指します。

MDT の記録には、中身がどの OST のどの object にあるかを示すレイアウトも入っています。object は、OST がファイルの中身を持つ単位です。次の節のストライプ数が 2 以上なら、object はふつう別々の OST に置かれます (overstriping では 1 つの OST に複数置けます)。

MDS は中身の置き場所を伝え、OSS は中身そのものを送ります。クライアントは MDS からレイアウトを受け取り、OSS から読む範囲のロックを得てから、各 OSS に並行して読み込みを頼みます。図の「次へ」で 1 つずつ進められます。ロックは「ロック」の節で説明します。

**名前の問い合わせと中身の読み書きを別のサーバに分けているので、中身の転送に MDS は出てきません** (小さなファイルの中身を MDT に置く DoM を使わない場合)。そのため OSS と OST を増やすと、ネットワークやディスクが詰まらない範囲で、全体の帯域を伸ばせます。ファイルシステム全体の帯域の主な上限は、OSS 側のネットワーク帯域と、OST のディスク帯域のうち、小さいほうです。1 本のファイルの帯域は、そのファイルが使う OST の数にも左右されます。

書き込みも、レイアウトを受け取り、OSS からロックを得てから OSS とやりとりする点は、読み込みと同じです。

## 複数の MDT

![ルートと /projA が MDT 0 に、/projB が MDT 1 にあり、ストライプしたディレクトリ /projC の中身は MDT 1 と MDT 2 に分かれている。クライアントからは 1 つの木に見える](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/dne.png)

MDT が 1 つだけだと、名前に関する操作がその MDT に集まります。そこで Lustre は、ディレクトリの木の部分を別々の MDT に置けます。この仕組みを DNE (Distributed Namespace Environment、名前空間の分散) と呼びます。ルートのディレクトリは、最初の MDT にあります。

1 つのディレクトリの中身を、複数の MDT に分けることもできます。これをストライプしたディレクトリと呼びます。どちらの場合も、クライアントの中の LMV という部品が各 MDT の答えをまとめるので、アプリケーションからは 1 つの木に見えます。

複数のクライアントが同じファイルを読み書きしても、内容が食い違わないように、サーバがロックを貸し出します。この仕組みを LDLM (分散ロックマネージャ) と呼びます。ロックはデータの範囲ごとに取り、ロックを持つクライアントは、その範囲のデータを手元にためておけます。両立しない種類のロックを別のクライアントが求めると、サーバは今の持ち主にロックを返すよう求め、持ち主はためていたデータを書き戻してから返します。図で 1 つずつ追えます。

持ち主が決まった時間内にロックを返さないとき、サーバは、その MDT や OST について、クライアントを切り離します。これを evict と呼びます。切り離されたクライアントは、その MDT や OST から借りていたロックがすべて無効になり、そこ向けに手元にためていた情報とデータも無効になります。ロックを返す要求への無応答のほか、サーバの要求に時間内に答えないことや、クライアントから要求も生存確認の ping も決まった時間届かないことも、evict の理由になります。ただし、サーバがどのクライアントからも要求を受け取っていないときは、ping が来なくても evict しません。この ping は、あとに出てくる LNet の ping とは別のものです。

## クライアントの中の層

![クライアントの中は、上からアプリケーション、llite、横に並んだ LMV と mdc および LOV と osc、ptlrpc、LNet、LND、ネットワークカードの層になっている](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/client-layers.png)

クライアントの Lustre のソフトウェアは、層になっています。llite は、Linux から見て普通のファイルシステムに見える部分です。その下で、メタデータの要求は mdc が、ファイルの中身の要求は osc が組み立てます。mdc は MDT ごとに 1 つあり、複数の MDT は LMV がまとめます。osc は OST ごとに 1 つあり、ストライプの全体は LOV がまとめます。ロックを扱う LDLM は図には描いていませんが、mdc と osc のそばで要求にかかわります。

ptlrpc は、要求を送って応答を待ち、応答が来なければ再送したり、サーバとの接続を張り直したりします。RPC は Remote Procedure Call の略で、離れた機械に仕事を頼む呼び出しのことです。その下の LNet が、送る側と受ける側の NID の組と、通る経路を決めます。一番下の LND が、ネットワークの種類に合わせて、実際の送受信をします。

## NID

![10.0.1.20@tcp0 という NID は、アドレス 10.0.1.20 と、LNet のネットワーク名 tcp0 を @ でつないだもの。1 台のサーバが複数の NID を持てる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/nid.png)

NID は、LNet が宛先を表すのに使うアドレスです。ネットワークインターフェースのアドレスと、LNet のネットワーク名を、@ でつなぎます。TCP や InfiniBand では、アドレスの部分に IP アドレスを使います。たとえば `10.0.1.20@tcp0` のような形で、図の値は説明用の例です。ネットワーク名は、LND (次の節) の種類に番号を付けたもので、tcp0 は TCP、o2ib0 や o2ib1 は InfiniBand のネットワークを表します。

1 台のサーバは、複数の NID を持てます。相手が Multi-Rail (あとの節) に対応していれば、LNet は、メッセージごとに、その中から 1 つを選びます。相手が持つ NID の一覧は、まだ知らない相手へ最初に送るときに、LNet が相手に LNet の ping を送って教えてもらいます。この動き (discovery) は既定で有効で、lnetctl で切ることもできます。

## LND: ネットワークごとのドライバ

![LNet の下に、TCP 向けの ksocklnd、InfiniBand 向けの ko2iblnd、AWS の EFA 向けの kefalnd が並ぶ](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/lnet-lnd.png)

LNet は、宛先の NID と経路を選びます。ネットワークごとの送受信のやり方は、LND というドライバが受け持ちます。TCP には ksocklnd、InfiniBand には ko2iblnd (ソースのディレクトリ名は o2iblnd) があります。EFA 向けの kefalnd (ソースのディレクトリ名は efalnd) も、[upstream のソース](https://github.com/lustre/lustre-release/tree/6325870717c7899f1ba545493ce2a07cb3834a6b/lnet/klnds) に入っています。そのため上の層は、ネットワークの種類によらず同じ呼び出し方で LNet を使えます。

LNet の層は、接続を持たず、非同期で、届くことを保証しません。ただし、待っている ACK や REPLY が時間内に来なければ、失敗として扱います。LND が送受信の失敗を見つけると、LNet に伝えます。LNet は、これと自分で見つけた失敗をもとに、NID の調子を表す health という数 (「Multi-Rail と health」の節) を下げます。失敗の種類によっては、LNet がメッセージを再送し、再送しきれないときに上の層へ失敗を伝えます。

## LNet のメッセージ

![PUT は始める側がデータを相手に送り込み、求められたときだけ ACK が返る。GET は始める側が要求を送ると、データを載せた REPLY が返る](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/messages.png)

LNet のメッセージの型は、PUT、ACK、GET、REPLY、HELLO の 5 つが定義されていて、基本は PUT と GET です。PUT は、始める側が相手にデータを送り込みます。始める側が求めたときだけ、受け取りの確認の ACK が返ります。GET は、欲しいものを伝える要求を送ると、データを載せた REPLY が返ります。

RPC の要求と応答も、どちらも PUT で運ばれます。REPLY は GET への返事で、RPC の応答とは別のものです。「RPC と bulk」の節の bulk もこの 2 つでできていて、読み込みでは OSS が PUT を、書き込みでは OSS が GET を使います。HELLO は、TCP の LND が接続を始める手続きに使います。[メッセージの種類](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/include/uapi/linux/lnet/lnet-idl.h#L79) は、ソースで確かめられます。

## ルーター

![tcp0 のクライアントが、tcp0 と o2ib0 の両方に NID を持つ LNet ルーターを通って、o2ib0 の OSS と MDS に届く](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/cfd989188c2509/zenn/articles/cfd989188c2509/router.png)

違う LNet のネットワークにいる相手とは、LNet ルーターを通って通信します。ルーターは、2 つのネットワークのそれぞれに NID を持つ機械で、片方で受け取ったメッセージを、もう片方へ転送します。たとえば、TCP のクライアントが、InfiniBand 側にあるサーバの NID に向けて送ると、ルーターが間を取り持ちます。LNet のルーティングは、IP のルーティングとは別のものです。

クライアントは、MDT や OST ごとに接続の状態を持っていて、これを import と呼びます。ptlrpc が管理します。サーバがクライアントを覚えていれば、ふつうにつながっている状態 (FULL) にすぐ戻り、再起動していれば要求とロックを送り直してから戻り、切り離していれば EVICTED を通ります。接続し直している間、新しい要求は待たされることがあります。ただし evict された場合、その間に進んでいた操作は失敗します。

import の状態は ptlrpc の接続の状態で、LNet の NID の health とは別の層の情報です。接続が切れたとみなした状態 (DISCON) になったからといって、特定の NID が壊れたとも、別の経路に切り替わったともいえません。health が下がることや再接続は、それだけでは「ロック」の節で見た evict を意味しません。[状態の一覧](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lustre/include/lustre_import.h#L67) と [遷移の処理](https://github.com/lustre/lustre-release/blob/6325870717c7899f1ba545493ce2a07cb3834a6b/lustre/ptlrpc/import.c#L1341-L1394) は、ソースで確かめられます。

## 層ごとの受け持ち

1 つの RPC が失敗したときは、下の層から順に次のように進みます。LND が送受信の失敗を見つけて LNet に伝え、LNet が health を下げて、必要なら再送します。それでも応答が時間内に届かないと、ptlrpc が import を DISCON にして接続を張り直します。サーバが待ちきれずにクライアントを切り離していれば、再接続のときに EVICTED を通ります。

| 層 | 受け持ち | 失敗したとき |
|---|---|---|
| ptlrpc | RPC の送受信、応答の待ち、接続の張り直し | 要求が時間内に終わらないと、接続を張り直す |
| LDLM | ロックの貸し出し | 返事をしないクライアントを evict する |
| LNet | 宛先の NID と、通る経路の選択 | health を下げて、ほかの NID を選びやすくする。失敗の種類によっては再送し、再送しきれなければ上の層へ失敗を伝える |
| LND | ネットワークごとの送受信 | 送受信の失敗を LNet に伝える |

## まとめ

Lustre は、名前の問い合わせと中身の読み書きを別のサーバに分け、クライアントが OSS と直接話すので、OSS と OST を増やすと帯域を伸ばせます。その通信は、LNet が NID と LND で支え、失敗は health と import の状態に現れます。
