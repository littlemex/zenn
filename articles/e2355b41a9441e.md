# はじめに

Turing の [S3 データストリーミングの記事](https://zenn.dev/turing_motors/articles/c06193d7988fee) は、学習データを [Amazon FSx for Lustre](https://aws.amazon.com/fsx/lustre/) に置く代わりに [Amazon S3](https://aws.amazon.com/s3/) から直接読み、学習に使えるデータの量をクラスタのストレージ容量から切り離した話です。記事によると、S3 はノードを増やすほど帯域が伸びます。一方で、1 回の読み出しのレイテンシーは中央値で約 140 ms あり、Lustre の約 20 倍です。このレイテンシーを先読みで隠すことが、設計の中心でした。

この記事では、同じ形の読み方を、AWS が公開している [S3 Connector for PyTorch](https://github.com/awslabs/s3-connector-for-pytorch) で [Amazon EKS](https://aws.amazon.com/eks/) の上に組んで測りました。動画のファイルからフレームの範囲だけを読み、7 台のカメラの分をそろえて 1 サンプルにする読み方です。分かったことは次の 3 つです。

1. S3 Connector for PyTorch は、S3 から 1 本 1 本の GET を流す部品です。次のサンプルを先に読む仕組みは持たず、それは [PyTorch](https://pytorch.org/) の DataLoader が受け持ちます。どのバイト範囲を読むかは、自分で書く Dataset が受け持ちます。
2. 3 MiB の GET 1 回に約 125 ms かかるので、決めるべきは同時に走らせる GET の数です。1 バッチ 56 本の GET を 1 本ずつ送ると 7.55 秒かかり (c6in.32xlarge 1 台、3 MiB の範囲)、`__getitems__` で全部を同時に送ると 0.23 秒で済みました。
3. S3 の手前にも詰まる場所があります。DataLoader の worker が `bytearray` を返すと、学習のプロセスへ渡すところで 1 ステップが 391 ms に延びました。tensor で返すと 121 ms で、S3 を使わない対照でも同じ差が出ました。

最後に、S3 Connector for PyTorch に足せそうな機能を、ソースと issue から整理します。

# S3 Connector for PyTorch の受け持ち

S3 Connector for PyTorch は、PyTorch から S3 のオブジェクトを読み書きするライブラリです。Python の API の下で、[AWS Common Runtime (CRT)](https://docs.aws.amazon.com/sdkref/latest/guide/common-runtime.html) を使う Rust のクライアントが動きます。CRT は、大きな GET を part (既定で 8 MiB) に分けて並列に取ってきます。ライブラリには、データセットの型 (`S3MapDataset`、`S3IterableDataset`) と、チェックポイントの保存と読み込みと、読み方を選ぶ [`S3ReaderConstructor`](https://github.com/awslabs/s3-connector-for-pytorch/blob/c4f482629523d8fd2ec6080f70bda5966f90d89a/s3torchconnector/src/s3torchconnector/s3reader/constructor.py#L128-L251) があります。読み方は 3 つです。`sequential` はオブジェクト全体をバッファに読みます。`range_based` は読み出しのたびに必要な範囲を GET し、既定では 8 MiB のバッファで同じオブジェクトの続きを先に取ります。`dcp_optimized` はチェックポイントの読み込み用です。

このライブラリは、次のサンプルを自分から取りに行きません。[`S3MapDataset.__getitem__`](https://github.com/awslabs/s3-connector-for-pytorch/blob/c4f482629523d8fd2ec6080f70bda5966f90d89a/s3torchconnector/src/s3torchconnector/s3map_dataset.py#L164-L165) は呼ばれたときに読むだけです。サンプルをまたぐ先読みは、[DataLoader](https://docs.pytorch.org/docs/stable/data.html) の worker (次のバッチを別のプロセスで用意する仕組み) と、worker ごとに先に用意するバッチの数 `prefetch_factor` に任せています。シャッフルについても、メンテナは [issue #247](https://github.com/awslabs/s3-connector-for-pytorch/issues/247) で、ライブラリには組み込まず PyTorch の道具と組み合わせるよう案内しています。S3 から読む部品と、いつ何を読むかを決める部品を分けた設計です。

![学習のループ、DataLoader、自分の Dataset、S3 Connector for PyTorch、AWS CRT、Amazon S3 を上から順に積んだ図。サンプルをまたぐ先読みは DataLoader、範囲の並列は Dataset が受け持つ](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/e2355b41a9441e/zenn/articles/e2355b41a9441e/layers.png)

この記事の読み方では、1 サンプルが、7 個のオブジェクトのそれぞれ一部です。この形をそのまま表す型は S3 Connector for PyTorch に無いので、Dataset の中で `S3Client.get_object` に `range_based` の reader を渡して範囲を読みます。

```python
from s3torchconnector import S3ClientConfig, S3ReaderConstructor
from s3torchconnector._s3client import S3Client

client = S3Client("ap-northeast-1", s3client_config=S3ClientConfig(throughput_target_gbps=200 / 16))
reader_ctor = S3ReaderConstructor.range_based(buffer_size=0)

def read_range(info, offset, view):
    reader = client.get_object(BUCKET, info.key, object_info=info, reader_constructor=reader_ctor)
    reader.seek(offset)
    return reader.readinto(view)
```

`throughput_target_gbps` は、CRT が接続の数を決めるときの目標のスループットです。ここではノードの 200 Gbps を、同じノードで動かすプロセスの数 (この例では 16) で割って渡しています。`buffer_size=0` にしたのは、読む範囲が 3 MiB と決まっているからです。既定の 8 MiB のバッファのままだと、3 MiB を読むたびに 8 MiB を取ってきます。`object_info` には、最初に `list_objects` で取ったオブジェクトの情報を渡します。渡さないと、[範囲を読む前に大きさを知るための HEAD](https://github.com/awslabs/s3-connector-for-pytorch/blob/c4f482629523d8fd2ec6080f70bda5966f90d89a/s3torchconnector/src/s3torchconnector/_s3client/_s3client.py#L158-L161) が毎回 1 本増えます。

# 測ったこと

Turing の記事と同じく、GPU は使わず、S3 から読む部分だけを測りました。学習の計算は、1 ステップ 100 ms の `sleep` で置き換えています。

| 項目 | 内容 |
|---|---|
| ノード | [c6in.32xlarge](https://aws.amazon.com/ec2/instance-types/c6i/) (128 vCPU、ネットワーク 200 Gbps)。1 台、スケールの測定だけ 3 台 |
| クラスタ | Amazon EKS 1.35、東京リージョン (ap-northeast-1)。S3 へは VPC のゲートウェイエンドポイント経由 |
| データ | 1 個 256 MiB のオブジェクト 8,000 個、合計 2,000 GiB (約 2.1 TB)。各オブジェクトは、同じ 8 MiB の乱数のブロックを 32 回並べたもので、オブジェクトごとに先頭 16 バイトだけが違う。動画ではない |
| 読み方 | ランダムなオブジェクトのランダムな位置 (4 KiB 境界) から、範囲を指定して読む。既定は 3 MiB |
| 1 サンプル | 7 本の範囲 (7 台のカメラの想定)。1 バッチは 8 サンプルで、56 本の GET |
| ソフトウェア | Python 3.12、s3torchconnector 1.5.0、PyTorch 2.15.0 (CPU 向けのビルド)、[boto3](https://github.com/boto/boto3) 1.44.4、[NumPy](https://numpy.org/) 2.5.5 |

測定のスクリプトは筆者が書いたもので、次の details に全文と、各コマンドの出力を載せています。表の p90 と p99 は、レイテンシーの短い方から並べて 90% と 99% の位置の値です。

```python
"""Does starting many GetObject streams before consuming any of them overlap their latency?"""
import os, random, time, json
from s3torchconnector import S3ClientConfig
from s3torchconnector._s3client import S3Client
B = os.environ["BUCKET"]; P = os.environ.get("PREFIX", "big/")
c = S3Client("ap-northeast-1", s3client_config=S3ClientConfig(throughput_target_gbps=100))
infos = [o for page in c.list_objects(B, P) for o in page.object_info]
rnd = random.Random(int(time.time()))
SZ = 3 * 1024 * 1024
def pts(n):
    return [(i.key, o) for i in rnd.sample(infos, n) for o in [rnd.randrange(0, (i.size - SZ) // 4096) * 4096]]
def serial(n):
    t = time.perf_counter()
    for k, o in pts(n):
        b"".join(c._client.get_object(B, k, o, o + SZ))
    return time.perf_counter() - t
def started_first(n):
    t = time.perf_counter()
    streams = [c._client.get_object(B, k, o, o + SZ) for k, o in pts(n)]
    for s in streams:
        b"".join(s)
    return time.perf_counter() - t
out = {}
for n in (1, 7, 56):
    for f in (serial, started_first):
        xs = sorted(f(n) for _ in range(15))
        out[f"{f.__name__}-{n}"] = round(xs[len(xs) // 2] * 1e3, 1)
        print(f.__name__, n, "median ms", out[f"{f.__name__}-{n}"], flush=True)
print(json.dumps(out))
```

`bench.py`

```python
"""S3 read benchmark for s3torchconnector, modelled on video-frame range reads.

Modes (all write a JSON result to s3://$BUCKET/results/<run>/<mode>-<host>.json):
  gen     create NOBJ objects of OBJ_MIB MiB under data/
  range   random range GETs: latency (TTFB/TTLB) and node throughput at a given concurrency
  seq     whole-object reads with the sequential reader (CRT splits into parallel part GETs)
  sample  one "sample" = CAMS range GETs issued together; latency of the slowest one
  train   a training loop that consumes batches of samples through a DataLoader; data wait time
"""
import argparse
import concurrent.futures as cf
import json
import multiprocessing as mp
import os
import random
import resource
import socket
import threading
import time
import zlib

from s3torchconnector import S3ClientConfig, S3ReaderConstructor
from s3torchconnector._s3client import S3Client

MiB = 1024 * 1024
REGION = os.environ.get("AWS_REGION", "ap-northeast-1")
BUCKET = os.environ["BUCKET"]
PREFIX = os.environ.get("PREFIX", "data/")


def cpu_seconds():
    r = resource.getrusage(resource.RUSAGE_SELF)
    return r.ru_utime + r.ru_stime


def make_client(gbps, part_mib=8):
    return S3Client(REGION, s3client_config=S3ClientConfig(throughput_target_gbps=gbps, part_size=part_mib * MiB))


def list_objects(client):
    infos = []
    for page in client.list_objects(BUCKET, PREFIX):
        infos.extend(page.object_info)
    infos.sort(key=lambda o: o.key)
    return infos


# ---------- one range read, two clients ----------

class ConnRange:
    """Public path: S3Client.get_object + range_based reader, buffer off, object_info known (no HEAD)."""

    def __init__(self, gbps, part_mib):
        self.c = make_client(gbps, part_mib)
        self.rc = S3ReaderConstructor.range_based(buffer_size=0)

    def read(self, info, off, n, buf):
        t0 = time.perf_counter()
        r = self.c.get_object(BUCKET, info.key, object_info=info, reader_constructor=self.rc)
        r.seek(off)
        got = r.readinto(memoryview(buf)[:n])
        t1 = time.perf_counter()
        return t1 - t0, None, got


class BotoRange:
    def __init__(self, gbps, part_mib):
        import boto3
        from botocore.config import Config
        self.c = boto3.client("s3", region_name=REGION, config=Config(max_pool_connections=256))

    def read(self, info, off, n, buf):
        t0 = time.perf_counter()
        resp = self.c.get_object(Bucket=BUCKET, Key=info.key, Range=f"bytes={off}-{off + n - 1}")
        body = resp["Body"]
        first = body.read(64 * 1024)
        t_first = time.perf_counter()
        rest = body.read()
        t1 = time.perf_counter()
        return t1 - t0, t_first - t0, len(first) + len(rest)


CLIENTS = {"conn": ConnRange, "boto3": BotoRange}


# ---------- range / sample workers (one process, many threads) ----------

def _range_worker(args):
    (wid, client_name, sizes, threads, duration, gbps, part_mib, cams, seed) = args
    rnd = random.Random(seed)
    client = CLIENTS[client_name](gbps, part_mib)
    infos = list_objects(make_client(1)) if client_name == "boto3" else list_objects(client.c)
    size = sizes
    lat, ttfb, nbytes = [], [], [0]
    lock = threading.Lock()
    stop_at = time.perf_counter() + duration
    pool = cf.ThreadPoolExecutor(max_workers=cams) if cams > 1 else None

    def one(buf):
        info = rnd.choice(infos)
        off = rnd.randrange(0, (info.size - size) // 4096) * 4096
        return client.read(info, off, size, buf)

    def loop():
        bufs = [bytearray(size) for _ in range(cams)]
        while time.perf_counter() < stop_at:
            if cams == 1:
                dt, fb, got = one(bufs[0])
                with lock:
                    lat.append(dt); nbytes[0] += got
                    if fb is not None:
                        ttfb.append(fb)
            else:
                t0 = time.perf_counter()
                futs = [pool.submit(one, bufs[i]) for i in range(cams)]
                got = sum(f.result()[2] for f in futs)
                with lock:
                    lat.append(time.perf_counter() - t0); nbytes[0] += got

    c0, w0 = cpu_seconds(), time.perf_counter()
    ts = [threading.Thread(target=loop) for _ in range(threads)]
    [t.start() for t in ts]
    [t.join() for t in ts]
    return {"lat": lat, "ttfb": ttfb, "bytes": nbytes[0], "cpu": cpu_seconds() - c0, "wall": time.perf_counter() - w0}


def pct(xs, q):
    if not xs:
        return None
    xs = sorted(xs)
    return xs[min(len(xs) - 1, int(q * len(xs)))]


def summarize(parts, wall):
    lat = [x for p in parts for x in p["lat"]]
    ttfb = [x for p in parts for x in p["ttfb"]]
    b = sum(p["bytes"] for p in parts)
    cpu = sum(p["cpu"] for p in parts)
    return {
        "ops": len(lat), "gbytes_per_s": b / wall / 1e9, "bytes": b, "wall": wall,
        "p50_ms": pct(lat, .5) * 1e3, "p90_ms": pct(lat, .9) * 1e3, "p99_ms": pct(lat, .99) * 1e3,
        "ttfb_p50_ms": pct(ttfb, .5) * 1e3 if ttfb else None,
        "ttfb_p99_ms": pct(ttfb, .99) * 1e3 if ttfb else None,
        "cpu_s_per_gb": cpu / (b / 1e9) if b else None,
        "lat_sample_ms": [round(x * 1e3, 2) for x in random.Random(0).sample(lat, min(len(lat), 5000))],
    }


def run_parallel(worker, a, procs, extra):
    ctx = mp.get_context("spawn")
    t0 = time.perf_counter()
    with ctx.Pool(procs) as pool:
        # the seed mixes in the host, so pods started in the same second on different nodes read different places
        base = zlib.crc32(socket.gethostname().encode()) ^ time.time_ns()
        parts = pool.map(worker, [(i, *extra, base + 1000 * i) for i in range(procs)])
    return parts, time.perf_counter() - t0


def mode_range(a):
    out = []
    for size_kib in a.sizes:
        for conc in a.conc:
            procs = min(a.procs, conc)
            threads = max(1, conc // procs)
            gbps = a.gbps / procs
            parts, wall = run_parallel(_range_worker, a, procs,
                                       (a.client, size_kib * 1024, threads, a.duration, gbps, a.part_mib, a.cams))
            wall = max(p["wall"] for p in parts)
            s = summarize(parts, wall)
            s.update(size_kib=size_kib, conc=procs * threads, procs=procs, client=a.client, cams=a.cams,
                     gbps_target=a.gbps, part_mib=a.part_mib)
            print(json.dumps({k: v for k, v in s.items() if k != "lat_sample_ms"}), flush=True)
            out.append(s)
    return out


# ---------- sequential whole-object reads ----------

def _seq_worker(args):
    (wid, threads, duration, gbps, part_mib, seed) = args
    rnd = random.Random(seed)
    c = make_client(gbps, part_mib)
    infos = list_objects(c)
    rc = S3ReaderConstructor.sequential()
    lat, nbytes, lock = [], [0], threading.Lock()
    stop_at = time.perf_counter() + duration

    def loop():
        buf = bytearray(max(i.size for i in infos))
        while time.perf_counter() < stop_at:
            info = rnd.choice(infos)
            t0 = time.perf_counter()
            r = c.get_object(BUCKET, info.key, object_info=info, reader_constructor=rc)
            got = r.readinto(memoryview(buf)[:info.size])
            with lock:
                lat.append(time.perf_counter() - t0); nbytes[0] += got

    c0, w0 = cpu_seconds(), time.perf_counter()
    ts = [threading.Thread(target=loop) for _ in range(threads)]
    [t.start() for t in ts]
    [t.join() for t in ts]

class ClipDataset:
    """Map-style dataset: sample i = CAMS byte ranges (one per camera clip) of FRAME_KIB each.

    fetch: 'serial' reads the CAMS ranges one after another, 'parallel' issues them together.
    """

    def __init__(self, n, cams, frame_kib, fetch, gbps, seed=0, out="bytes"):
        self.n, self.cams, self.size, self.fetch, self.gbps, self.seed = n, cams, frame_kib * 1024, fetch, gbps, seed
        self.out = out  # "bytes": bytearray (pickled through the worker pipe), "shm": uint8 tensor in shared memory
        self.client = None

    def _buf(self):
        if self.out in ("shm", "tensor"):
            import torch
            t = torch.empty(self.size, dtype=torch.uint8)
            if self.out == "shm":
                t = t.share_memory_()
            return t, memoryview(t.numpy())
        b = bytearray(self.size)
        return b, b

    def _init(self):
        if self.client is None:
            self.client = ConnRange(self.gbps, 8)
            self.infos = list_objects(self.client.c)
            self.pool = cf.ThreadPoolExecutor(max_workers=self.cams * 16)

    def __len__(self):
        return self.n

    def ranges(self, i):
        rnd = random.Random(self.seed * 1_000_003 + i)
        out = []
        for _ in range(self.cams):
            info = rnd.choice(self.infos)
            off = rnd.randrange(0, (info.size - self.size) // 4096) * 4096
            out.append((info, off))
        return out

    def __getitem__(self, i):
        if self.fetch == "none":
            pairs = [self._buf() for _ in range(self.cams)]
            for _, v in pairs:
                v[:] = b"\x01" * self.size
            return [p[0] for p in pairs]
        self._init()
        rs = self.ranges(i)
        pairs = [self._buf() for _ in rs]
        if self.fetch == "parallel":
            futs = [self.pool.submit(self.client.read, info, off, self.size, pairs[j][1]) for j, (info, off) in enumerate(rs)]
            [f.result() for f in futs]
        else:
            for j, (info, off) in enumerate(rs):
                self.client.read(info, off, self.size, pairs[j][1])
        return [p[0] for p in pairs]


class BatchClipDataset(ClipDataset):
    """Same samples, but the DataLoader hands over a whole batch of indices via __getitems__
    and every range of every sample in the batch is issued together."""

    def __getitems__(self, idxs):
        if self.fetch == "none":
            return [self.__getitem__(i) for i in idxs]
        self._init()
        jobs = [(k, info, off) for k, i in enumerate(idxs) for info, off in self.ranges(i)]
        out = [[] for _ in idxs]
        pairs = [self._buf() for _ in jobs]
        futs = [self.pool.submit(self.client.read, info, off, self.size, pairs[j][1]) for j, (_, info, off) in enumerate(jobs)]
        [f.result() for f in futs]
        for j, (k, _, _) in enumerate(jobs):
            out[k].append(pairs[j][0])
        return out

    return batch


def mode_train(a):
    import torch
    from torch.utils.data import DataLoader
    out = []
    for cfg in a.train_cfgs:
        workers, pf, fetch, *rest = cfg.split(":")
        outk = rest[0] if rest else "bytes"
        workers, pf = int(workers), int(pf)
        cls = BatchClipDataset if fetch in ("batch",) else ClipDataset
        ds = cls(10**7, a.cams, a.frame_kib, fetch, a.gbps / max(1, workers), out=outk)
        kw = dict(batch_size=a.batch, num_workers=workers, collate_fn=collate, shuffle=True)
        if workers > 0:
            kw.update(prefetch_factor=pf, persistent_workers=True, multiprocessing_context="spawn")
        dl = DataLoader(ds, **kw)
        it = iter(dl)
        next(it)  # warm-up: worker start, client creation, listing
        waits, steps, nbytes, marks, post, slept = [], 0, 0, [], [], []
        t_start = time.perf_counter()
        while steps < a.steps:
            t0 = time.perf_counter()
            marks.append(t0)
            batch = next(it)
            waits.append(time.perf_counter() - t0)
            t1 = time.perf_counter()
            nbytes += sum(len(b) for s in batch for b in s)
            del batch
            t2 = time.perf_counter()
            time.sleep(a.step_ms / 1e3)  # stands in for decode + GPU step
            post.append(t2 - t1); slept.append(time.perf_counter() - t2)
            steps += 1
            if steps % 10 == 0:
                print(f"[progress] {cfg} step {steps} wait_last {waits[-1]*1e3:.0f} ms", flush=True)
        t_end = time.perf_counter()
        wall = t_end - t_start
        del it, dl
        r = {"cfg": cfg, "out": outk, "workers": workers, "prefetch_factor": pf, "fetch": fetch, "batch": a.batch,
             "cams": a.cams, "frame_kib": a.frame_kib, "step_ms": a.step_ms, "steps": steps, "wall": wall,
             "ideal_wall": steps * a.step_ms / 1e3, "wait_total_s": sum(waits),
             "wait_frac": sum(waits) / wall, "wait_p50_ms": pct(waits, .5) * 1e3, "wait_p99_ms": pct(waits, .99) * 1e3,
             "gbytes_per_s": nbytes / wall / 1e9}
        skip = min(a.skip, steps // 2)  # steady state: drop the pipeline fill at the start
        sw = sum(waits[skip:]); swall = t_end - marks[skip]
        r.update(post_p50_ms=pct(post[skip:], .5) * 1e3, post_p99_ms=pct(post[skip:], .99) * 1e3,
                 sleep_p50_ms=pct(slept[skip:], .5) * 1e3, sleep_p99_ms=pct(slept[skip:], .99) * 1e3)
        r.update(skip=skip, steady_wait_frac=sw / swall, steady_step_ms=swall / (steps - skip) * 1e3,
                 steady_wait_p50_ms=pct(waits[skip:], .5) * 1e3, steady_wait_p99_ms=pct(waits[skip:], .99) * 1e3)
        print(json.dumps(r), flush=True)
        out.append(r)
    return out
```

# 1 回の GET のレイテンシー

1 回の GET は、読む量が 64 KiB でも約 90 ms かかりました。8 個のプロセスがそれぞれ GET を 1 本ずつ送り続け、20 秒間測った結果です。

| 読む量 | S3 Connector for PyTorch の中央値 / p99 | boto3 の中央値 / p99 | 1 GB を読むのに使った CPU 時間 (Connector / boto3) |
|---|---|---|---|
| 64 KiB | 91 ms / 145 ms | 93 ms / 152 ms | 6.8 秒 / 25.3 秒 |
| 1 MiB | 104 ms / 202 ms | 101 ms / 209 ms | 1.7 秒 / 2.7 秒 |
| 3 MiB | 124 ms / 237 ms | 129 ms / 266 ms | 1.6 秒 / 2.3 秒 |

3 MiB の中央値 124 ms は、Turing の記事の約 140 ms と近い値です。レイテンシーは S3 Connector for PyTorch と boto3 でほぼ同じで、違いは CPU 時間に出ました。64 KiB では、S3 Connector for PyTorch の CPU 時間は boto3 の 27%、3 MiB では 70% でした。書き込んだ直後の 100 GiB のデータで先に同じ測定をしたときは、3 MiB の中央値が S3 Connector for PyTorch で 162 ms、boto3 で 134 ms でした。測る時間とデータによる違いは、クライアントによる違いより大きく出ました。

このレイテンシーは、データの量にも左右されました。3 MiB を 256 本のスレッドで読むと、100 GiB のデータでは中央値 58 ms で 12.3 GB/s 出ましたが、2,000 GiB のデータでは中央値 132 ms で 5.4 GB/s でした。100 GiB のデータから boto3 で 60 か所を選び、64 KiB ずつ 3 周読みました。中央値は、1 周目の 87 ms から、2 周目に 45 ms、3 周目に 29 ms へ縮みました。同じ 64 KiB を繰り返し読むと 25 ms でした。ベンチマークのデータが小さいと同じ場所を何度も読むので、レイテンシーが短く出ます。この記事でデータを 2,000 GiB にしたのはそのためです。

# 1 台のノードで出るスループット

レイテンシーが変わらないなら、スループットは同時に走っている GET の数で決まります。同時に走らせる GET の数 $N$ は、欲しいスループット $B$、1 本の平均のレイテンシー $L$、1 本の大きさ $S$ から次の式で決まります。

$$
N = \frac{B \, L}{S}
$$

中央値ではなく平均を使うのは、長くかかる GET の分だけ、1 本のスレッドが次の GET を送れない時間が延びるからです。

| 同時に GET を送るスレッドの数 | スループット | 中央値 / p99 |
|---|---|---|
| 192 | 4.2 GB/s | 126 ms / 250 ms |
| 480 | 10.8 GB/s | 125 ms / 250 ms |
| 960 | 15.5 GB/s | 147 ms / 808 ms |

どれも 3 MiB の範囲を、96 個のプロセスで、それぞれ 2〜10 本のスレッドを動かして 15 秒ずつ読んだ結果です。192 本と 480 本では、スレッド 1 本あたり 22 MB/s 出ました。3 MiB を 22 MB/s で読むので、1 本の平均のレイテンシーは約 140 ms です。この $L$ で計算すると、10 GB/s には約 450 本が要ります。中央値の 125 ms で計算すると約 400 本になり、少し足りません。

480 本から 960 本に増やすと、スループットは 480 本のときの 10.8 GB/s と比べて 1.4 倍の 15.5 GB/s になり、p99 は 250 ms と比べて 3.2 倍の 808 ms になりました。1 台ではこのあたりで止まります。オブジェクト全体を `sequential` で読んでも 14.0 GB/s でした。`throughput_target_gbps` を 800 に上げ、64 個のプロセスの合わせて 1,024 本のスレッドで範囲を読むと 15.3 GB/s でした。`sequential` では、800 で 12.8 GB/s、3,200 で 13.0 GB/s でした。200 Gbps のノードのうち、約 120 Gbps です。

止まる場所は、この測定では特定できていません。[ネットワークの受信の上限を超えた回数](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/monitoring-network-performance-ena.html) (`bw_in_allowance_exceeded`) は、ノードを起動してからすべての測定を終えるまでの累計で 0 でした。CPU の使用率は、`sequential` を 64 本で読んで 14.5 GB/s 出ていた回で 59%、範囲を 960 本で読んで 12.8 GB/s 出ていた別の回で 72% で、CPU が上限でないとは言い切れません。ENI は、インスタンスに付ける仮想のネットワークインターフェイスです。c6in.32xlarge で 200 Gbps を出すには、[2 枚のネットワークカードにそれぞれ ENI を付ける](https://docs.aws.amazon.com/ec2/latest/instancetypes/co.html#co_network)必要があります。ENI が 1 つなら最大 170 Gbps で、この測定のノードは 1 枚目のカードの ENI だけを使っていました。2 枚目のカードに ENI を付けた測定はしていません。Turing の記事は、200 Gbps の GPU ノード 1 台で 23.9 GB/s と書いています。

ノードを増やすと、合計のスループットはノードの数に比例して伸びました。

| ノード数 | 合計のスループット | 各ノードの中央値 | 各ノードの p99 |
|---|---|---|---|
| 1 | 14.5 GB/s | 161 ms | 797 ms |
| 2 (1 回目) | 30.2 GB/s | 137 ms、148 ms | 949 ms、836 ms |
| 2 (2 回目) | 28.7 GB/s | 149 ms、155 ms | 853 ms、820 ms |
| 3 | 44.9 GB/s | 125〜152 ms | 813〜1,059 ms |

各ノードで 960 本ずつ、30 秒間、同じバケットの同じ prefix から読みました。乱数の種にホスト名を混ぜ、ノードごとに別の場所を読ませています。3 台のときは毎秒約 1.4 万本の GET です。ノードが増えると中央値がやや下がり、p99 は延びています。この測定の前に、データ全体を何度も読んでいるので、読んだことのある場所を読み直した GET が中央値に混ざっている可能性があります。

# 7 台のカメラをそろえる

1 サンプルは 7 本の GET がそろって初めて使えるので、そのレイテンシーは 7 本の中で一番長くかかった 1 本で決まります。7 本を同時に送る 1 サンプルを 8 つ並行して 20 秒間読むと、1 サンプルのレイテンシーの中央値は 205 ms でした。1 本だけのときの 124 ms と比べて 1.65 倍で、1 本だけのときの p90 (204 ms) とほぼ同じ値です。Turing の記事の「7 台同時で約 230 ms」と近い値でした。

1 本ずつ送ると 7.55 秒、1 サンプルの 7 本ずつ同時に送ると 1.52 秒、56 本を全部同時に送ると 0.23 秒でした。全部同時は、1 本ずつと比べて 33 分の 1 です。差は、順に待つ GET の回数 (56 回、8 回、1 回) の差です。

全部を同時に送る方法では、DataLoader から [バッチ分の番号をまとめて受け取る `__getitems__`](https://docs.pytorch.org/docs/stable/data.html) を使いました。次のコードは、details の `bench.py` の `BatchClipDataset` から測定用の部分を削ったものです。

```python
class BatchClipDataset(torch.utils.data.Dataset):
    def __getitems__(self, indices):
        jobs = [(k, info, off) for k, i in enumerate(indices) for info, off in self.ranges(i)]
        bufs = [torch.empty(FRAME_BYTES, dtype=torch.uint8) for _ in jobs]
        futures = [self.pool.submit(read_range, info, off, memoryview(b.numpy()))
                   for b, (_, info, off) in zip(bufs, jobs)]
        for f in futures:
            f.result()
        samples = [[] for _ in indices]
        for b, (k, _, _) in zip(bufs, jobs):
            samples[k].append(b)
        return samples
```

GET を同時に走らせるために、スレッドのプールを使っています。`range_based` の reader は `readinto` を呼んだときに GET を送り、その中で [Rust 側の `get_object` が、呼んだスレッドで応答を待ちます](https://github.com/awslabs/s3-connector-for-pytorch/blob/c4f482629523d8fd2ec6080f70bda5966f90d89a/s3torchconnectorclient/rust/src/mountpoint_s3_client_inner.rs#L71-L79)。S3 Connector for PyTorch の下の層を直接呼び、1 つのスレッドで 7 本の読み出しを先に始めてから中身を受け取る書き方も試しました。7 本で 917 ms かかり、1 本ずつ読んだとき (938 ms) とほとんど変わりませんでした。別々の範囲を同時に読むには、スレッドかプロセスを分けてください。

# DataLoader の worker と、もう 1 つの詰まり

DataLoader の worker は、学習のプロセスとは別のプロセスで次のバッチを先に用意し、S3 のレイテンシーを隠します。必要な worker の数は、おおよそ「1 バッチを取る時間 ÷ 1 ステップの時間」です。1 ステップ 0.1 秒に対して、1 本ずつ読むなら $7.55 \div 0.1$ で約 76、1 サンプルの 7 本を同時に読むなら $1.52 \div 0.1$ で約 15、バッチ全部を同時に読むなら $0.23 \div 0.1$ で約 2.3 です。実際に足りたのは、下の表のとおり、1 本ずつで 64、7 本ずつで 16、全部同時で 4 でした。全部同時は 2 では足りず、worker の中では 1 バッチを取るのに worker を使わないときより長くかかっています (2 つで 1 ステップ 174 ms から逆算すると、1 バッチ約 0.35 秒)。この目安は出発点にして、worker の数を変えて測ってください。

worker の数のほかに、もう 1 つ詰まる場所がありました。worker を 4 つにして Dataset から `bytearray` を返すと、1 ステップは 391 ms で、worker を使わないとき (433 ms) とほとんど変わりませんでした。S3 を使わず、同じ量の `bytearray` をメモリの中で作って返すだけの対照でも 385 ms で、tensor で返すと 121 ms でした。この対照で 1 バッチを作る時間は、1 つのプロセスで 191 ms なので、worker 4 つなら 1 秒に約 21 バッチを作れます。作る側は詰まりの原因ではなく、詰まっていたのは worker から学習のプロセスへデータを渡すところです。DataLoader は、worker が返したものを pickle (Python のオブジェクトをバイト列に直す仕組み) にしてプロセスの間で送ります。tensor は [`torch.multiprocessing` が共有メモリに置き、受け取る側には共有メモリの場所だけを送ります](https://docs.pytorch.org/docs/stable/multiprocessing.html)。

| worker の数 | 1 バッチの読み方 | worker が返す型 | 1 ステップの時間 | 待ちの平均 / p99 |
|---|---|---|---|---|
| 0 (学習のプロセスで読む) | バッチ全部を同時 | `bytearray` | 433 ms | 326 ms / 484 ms |
| 4 | バッチ全部を同時 | `bytearray` | 391 ms | 281 ms / 579 ms |
| 4 | S3 を使わない対照 | `bytearray` | 385 ms | 275 ms / 823 ms |
| 4 | S3 を使わない対照 | tensor | 121 ms | 10 ms / 10 ms |
| 2 | バッチ全部を同時 | tensor | 174 ms | 62 ms / 222 ms |
| 4 | バッチ全部を同時 | tensor | 121 ms | 10 ms / 19 ms |
| 16 | 1 サンプルの 7 本を同時 | tensor | 122 ms | 11 ms / 95 ms |
| 16 | 1 本ずつ | tensor | 529 ms | 418 ms / 5,113 ms |
| 64 | 1 本ずつ | tensor | 126 ms | 15 ms / 617 ms |

1 ステップの時間は、次のバッチを待つ時間と、学習の計算の代わりの 100 ms と、受け取ったバッチを手放す約 10 ms の合計です。待ちは `next(iter)` が返るまでの時間で、待ちが長いステップと 0 のステップが交互に来る設定もあるので、平均で示しました。300 ステップのうち、worker が最初のバッチをそろえるまでの 100 ステップを除いて数えました。`prefetch_factor` はどれも 2 です。tensor の行のうち対照以外は、共有メモリに置く `share_memory_()` を先に呼んだ tensor で測りました (呼ばない tensor でも、worker 4 つ、バッチ全部を同時で 122 ms と同じでした)。

tensor の受け渡しには `/dev/shm` を使うので、次の節の表のとおり大きさを確かめてください。

# 使うときの前提と制限

S3 Connector for PyTorch でこの読み方を組むときに、判断を変える項目は次の 5 つです。

| 対象 | どう制限されるか | どうするか |
|---|---|---|
| `S3Client` | [`_s3client` という内部のモジュール](https://github.com/awslabs/s3-connector-for-pytorch/tree/c4f482629523d8fd2ec6080f70bda5966f90d89a/s3torchconnector/src/s3torchconnector/_s3client)にあり、公開の API として約束されていない | s3torchconnector のバージョンを固定する |
| 1 サンプルが複数のオブジェクトの一部になる読み方 | それを表すデータセットの型が無い | 範囲の計算は自分の Dataset に書く |
| 1 つのスレッドの中の GET | 応答を待ってから次に進むので、別々の範囲の GET は重ならない | スレッドのプールか、DataLoader の worker で並列にする |
| worker から学習のプロセスへの受け渡し | `bytearray` は pickle で送られ、この測定では 1 ステップが 391 ms になった | tensor で返す |
| `/dev/shm` | tensor は `/dev/shm` に置かれる。この測定のコンテナでは既定が 64 MiB で、worker が `No space left on device` で止まった | 少なくとも「worker の数 × `prefetch_factor` × 1 バッチの大きさ」(worker 4 つなら $4 \times 2 \times 168$ MiB で約 1.3 GiB) を確保する。この測定では、メモリを使う `emptyDir` を 64 GiB で `/dev/shm` に付けた |

# S3 Connector for PyTorch に足せそうなもの

S3 Connector for PyTorch の受け持ち (S3 から効率よく読むこと) に入りそうな機能が 2 つあります。バイト範囲の計算は動画の形式によるのでアプリの仕事として、サンプルをまたぐ先読みは DataLoader の仕事として、外に残ります。

1 つ目は、複数の範囲を 1 回の呼び出しで同時に読む API です。今は、別々の範囲を同時に読むと、範囲の数だけ Python のスレッドが要ります。Rust の側で複数の GET を同時に始めて待てば、Python のスレッドは 1 つで済みます。Rust 側の `get_object` には、呼んだスレッドで待たずに結果を後で受け取る形 (future) にできないか、という [TODO](https://github.com/awslabs/s3-connector-for-pytorch/blob/c4f482629523d8fd2ec6080f70bda5966f90d89a/s3torchconnectorclient/rust/src/mountpoint_s3_client_inner.rs#L74) が残っています。[チェックポイントの読み込みを、範囲の同時読みで短くする提案 (issue #375)](https://github.com/awslabs/s3-connector-for-pytorch/issues/375) も、同じ部品を必要とします。なお、960 本のスレッドで読んだときは 1 GB あたりの CPU 時間が 5.8 秒で、8 本のときの 1.6 秒の 3.6 倍でした。これがスレッドの数によるのか、スループットが上限に近づいたことによるのかは、この測定では分けられていません。

2 つ目は、`S3MapDataset` に `__getitems__` を持たせ、バッチの中のオブジェクトを同時に読むことです。DataLoader の先読みとは重ならず、PyTorch の Dataset の約束の範囲に収まります。

どちらも、まだ issue も PR も出していない筆者の案です。このリポジトリの[貢献の手引き](https://github.com/awslabs/s3-connector-for-pytorch/blob/c4f482629523d8fd2ec6080f70bda5966f90d89a/CONTRIBUTING.md)は、大きな変更を PR の前に issue で相談するよう求めています。issue #375 は、2026-11-17 に open でした。

# まとめ

S3 から学習データを直接読むとき、S3 Connector for PyTorch が受け持つのは 1 本 1 本の GET を流すことです。64 KiB の読み出しでは、boto3 の 27% の CPU 時間で済みました。GPU を待たせないための設計は自分の側に残ります。この測定で決めたことは次のとおりです。

| # | 決めること | この測定での値 |
|---|---|---|
| 1 | 同時に走らせる GET の数 $N = BL/S$ | 3 MiB で 10 GB/s なら、実測の平均のレイテンシーから計算して約 450 本 |
| 2 | 1 バッチの GET をまとめて送る (`__getitems__`) | 1 バッチ 7.55 秒が 0.23 秒に |
| 3 | worker から返すのは tensor にする | 1 バッチ 168 MiB、worker 4 つで、1 ステップ 391 ms が 121 ms に |
| 4 | 1 台で足りなければノードを増やす | c6in.32xlarge 1 台 (ENI 1 つ) で約 15 GB/s、3 台で 44.9 GB/s |
| 5 | ベンチマークのデータは、読む量より十分に大きくする | 3 MiB を 256 本で読むと、中央値が 2,000 GiB で 132 ms、100 GiB で 58 ms |
