## はじめに

2026 年 10 月 22 日に、LMSYS が [SGLang の Trainium 対応のベータ](https://www.lmsys.org/blog/2026-10-22-sglang-trainium-beta)を発表しました。vLLM には [vLLM Neuron プラグイン](https://github.com/vllm-project/vllm-neuron/blob/a080ebf48074048abd9574a3cb5a3ee9068a4958/README.md) (以下 vllm-neuron) があり、2026 年 10 月 20 日に[コミュニティからモデルの寄稿を受け付ける仕組み](https://github.com/vllm-project/vllm-neuron/pull/63)が入りました。Neuron は Trainium 向けの AWS の SDK とコンパイラです。NKI (Neuron Kernel Interface) は、Trainium のカーネルを Python で書くための仕組みです。AWS の Neuron チームは、NKI で書いたカーネルを [NKI Library](https://github.com/aws-neuron/nki-library/blob/ad2f1b921d8e5949fa3b9a186e5f9130269353dc/README.md) (以下 nkilib) として公開しています。カーネルは、アクセラレータの上で 1 つ、またはまとめた複数の演算を実行するプログラムです。

ここで気になるのは、nkilib、vllm-neuron、SGLang、寄稿者の手元のそれぞれで同じ演算のカーネルが書かれ、食い違っていくことです。この記事では、GPU の vLLM と SGLang がこの問題をどう扱っているかをソースで確かめます。そのうえで、Trainium で足りない仕組みを、RFC (設計の提案の文書) として出すことを提案します。内容は 2026 年 10 月 31 日時点のもので、コードへのリンクは確認したときのコミットに固定しています。

| 疑問 | GPU での事実 | Trainium での筆者の見立て |
|---|---|---|
| エンジンやモデルごとに差分は出るか | 出ることがあります。カーネルが違うと足し算の順番が変わり、ビットが変わりえます | エンジンをまたぐビット一致は前提にせず、何と比べてどこまで許すかを決めます |
| 1 モデルに 1 つのカーネルになるか | なりません。1 つの演算に多くの実装の候補があり、新しいモデルはハードごとの実装も持ちます | 段階、テンソルの形、重みの形式、チップの世代ごとに複数のカーネルが並ぶのは自然です |
| 寄稿をどう受け付けるか | 置き場所の決まりに加えて、モデルやハードごとの担当者と、実績を積んだ人がレビューする役割が文書になっています | 置き場所と Neuron チームのレビューはあります。nkilib へ変更が届く経路の見通しと、コミュニティのレビュアーの役割は文書になっていないので、RFC として提案します |

## コードはどこに置かれているか

![vllm-neuron の中に公式のモデル、寄稿のモデル、共有の演算があり、その下に nkilib がある。SGLang のプラグインは発表にリポジトリへのリンクが無い](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/686da5f92f511f/zenn/articles/686da5f92f511f/places.png)

vllm-neuron では、公式のモデルが [vllm_neuron/model/](https://github.com/vllm-project/vllm-neuron/tree/a080ebf48074048abd9574a3cb5a3ee9068a4958/vllm_neuron/model) に、寄稿のモデルが [contrib/models/](https://github.com/vllm-project/vllm-neuron/tree/a080ebf48074048abd9574a3cb5a3ee9068a4958/contrib/models) に置かれます。モデル間で共有する演算は [functional/](https://github.com/vllm-project/vllm-neuron/tree/a080ebf48074048abd9574a3cb5a3ee9068a4958/vllm_neuron/functional) にあり、`__init__.py` を除く 50 のファイルのうち 36 に、[MoE の prefill](https://github.com/vllm-project/vllm-neuron/blob/a080ebf48074048abd9574a3cb5a3ee9068a4958/vllm_neuron/functional/moe/moe_cte.py#L5-L12) のように nkilib の import 文があります。プラグインが自分で書いた NKI カーネルは [_kernels/](https://github.com/vllm-project/vllm-neuron/blob/a080ebf48074048abd9574a3cb5a3ee9068a4958/vllm_neuron/_kernels/__init__.py#L1-L17) にあり、`qwen3_32b_sp` や `glm_5_3` のようにモデルの名前の付いたものもあります。

nkilib には、[コンパイラに同梱された版と、pip で入れる版](https://github.com/aws-neuron/nki-library/blob/ad2f1b921d8e5949fa3b9a186e5f9130269353dc/README.md#L76-L108)があります。同梱の版は、そのコンパイラで確かめられています。pip の版を入れると、通常はそちらが優先されます。pip の版は最新のコンパイラで動くとは限らず、README はコンパイラの版に対応するブランチから始めるよう勧めています。

プラグインには、nkilib から写したカーネルもあります。Qwen3-32B 向けの QKV のカーネルのファイルは、[nkilib の版を写して手を加えた](https://github.com/vllm-project/vllm-neuron/blob/a080ebf48074048abd9574a3cb5a3ee9068a4958/vllm_neuron/_kernels/qwen3_32b_sp/qwen3_32b_qkv_tkg_projection_mxfp_preloaded.py#L1-L9)と冒頭に記しています。[vendored_kernels/](https://github.com/vllm-project/vllm-neuron/blob/a080ebf48074048abd9574a3cb5a3ee9068a4958/vllm_neuron/functional/vendored_kernels/__init__.py#L1-L8) には、依存先のイメージにまだ入っていない版のカーネルが写されていて、上流の版が入ったら消すとされています。

SGLang の発表は、プラグインが TorchNeuron の上に作られたと述べています。TorchNeuron は Trainium 向けの PyTorch のバックエンドで、発表によると SGLang のモデルの部品と中心の抽象は大きく変えずに Trainium に移せました。独自のカーネルには NKI を使います。発表にはリポジトリへのリンクが無いので、この記事ではプラグインの中身には踏み込みません。

## GPU では、エンジンがカーネルを選ぶ

![vLLM と SGLang では、モデルのコードが演算の層や入り口を呼び、どのカーネルで実行するかはエンジンが条件から選ぶ](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/686da5f92f511f/zenn/articles/686da5f92f511f/gpu-select.png)

vLLM のモデル追加のガイドは、[契約が合う限り Attention や MoE などの共有の層を使う](https://github.com/vllm-project/vllm/blob/d0d3005affa38e16dbd60092f0af4e314743d586/docs/contributing/model/basic.md#L80-L88)よう求めています。契約は、層が受け取る入力と返す出力の約束です。共有の層を使う場合、どのカーネルで実行するかはエンジンが決めます。

層の下には多くの候補があります。attention のバックエンドの一覧には、使わないことを表す NO_ATTENTION なども含めて [52 個の名前](https://github.com/vllm-project/vllm/blob/d0d3005affa38e16dbd60092f0af4e314743d586/vllm/v1/attention/backends/registry.py#L34-L251)が並びます。MoE の実装を集めた [experts/](https://github.com/vllm-project/vllm/tree/d0d3005affa38e16dbd60092f0af4e314743d586/vllm/model_executor/layers/fused_moe/experts) には、`__init__.py` を除いて 40 のファイルがあります。FP8 の MoE では、[プラットフォームや設定に応じて候補の優先順位](https://github.com/vllm-project/vllm/blob/d0d3005affa38e16dbd60092f0af4e314743d586/vllm/model_executor/layers/fused_moe/oracle/fp8.py#L83-L150)が決まります。

SGLang は、呼び出せるカーネルの公開の入り口として [sglang.kernels](https://github.com/sgl-project/sglang/blob/b572b8ea827fc236786cf64d025337f60895d16d/python/sglang/kernels/README.md#L1-L12) を用意しています。ここに登録する 1 つの実装は [KernelSpec](https://github.com/sgl-project/sglang/blob/b572b8ea827fc236786cf64d025337f60895d16d/python/sglang/kernels/spec.py#L203-L215) で表され、[動ける装置の条件](https://github.com/sgl-project/sglang/blob/b572b8ea827fc236786cf64d025337f60895d16d/python/sglang/kernels/spec.py#L126-L137)を持てます。AMD の GPU 向けのカーネル集 aiter や、Huawei の Ascend 向けの torch_npu も、[実装の出どころの 1 つ](https://github.com/sgl-project/sglang/blob/b572b8ea827fc236786cf64d025337f60895d16d/python/sglang/kernels/spec.py#L29-L54)として区別されます。

## GPU では、モデルのコードはエンジンごと、さらにハードごとに分かれる

SGLang の新しいモデルのガイドには、[vLLM のモデルを SGLang に移す手順](https://github.com/sgl-project/sglang/blob/b572b8ea827fc236786cf64d025337f60895d16d/docs/docs/supported-models/support_new_models.mdx#L86-L105)があります。SGLang は vLLM のインタフェースと一部の層を引き継いでいるので、移すのは易しいと書かれています。そのうえで、最後は SGLang の部品だけで動くよう求めています。同じモデルのコードが、vLLM と SGLang に別々にある前提です。カーネルは共通のライブラリからも取り、2 つのエンジンはどちらも CUDA 向けに FlashInfer に依存しています。版はそれぞれが [vLLM は 0.7.2.post1](https://github.com/vllm-project/vllm/blob/d0d3005affa38e16dbd60092f0af4e314743d586/requirements/cuda.txt#L13)、[SGLang は 0.7.2](https://github.com/sgl-project/sglang/blob/b572b8ea827fc236786cf64d025337f60895d16d/python/pyproject.toml#L41) に固定しています。

同じエンジンの中でも、新しいモデルはハードごとに分かれています。vLLM は[新しいモデルを vllm/models/<model>/ に置き](https://github.com/vllm-project/vllm/blob/d0d3005affa38e16dbd60092f0af4e314743d586/docs/contributing/labels.md#L71-L73)ます。たとえば [DeepSeek V4 のフォルダ](https://github.com/vllm-project/vllm/tree/d0d3005affa38e16dbd60092f0af4e314743d586/vllm/models/deepseek_v4)には、共通のコードと、nvidia、amd、cpu、xpu のフォルダが並びます。NVIDIA 向けのフォルダには、DeepGEMM を使う処理など、そのモデルとそのハードのための実装が置かれています。共有の層とエンジンの選択だけでは足りない部分を、モデルとハードの組で持つ形です。

正しさを確かめる方法として、2 つのガイドはどちらも Hugging Face Transformers との比較を案内しています。vLLM のガイドで必須なのはダミーの重みで初期化できるテストで、[Transformers との出力の比較](https://github.com/vllm-project/vllm/blob/d0d3005affa38e16dbd60092f0af4e314743d586/docs/contributing/model/tests.md#L5-L36)は任意です。SGLang のガイドは、[Transformers と比べたベンチマークの結果を PR に書く](https://github.com/sgl-project/sglang/blob/b572b8ea827fc236786cf64d025337f60895d16d/docs/docs/supported-models/support_new_models.mdx#L49-L84)よう求めています。

vllm-neuron も、モデルの実装をプラグインの中に持ちます。Llama 3 の実装が vLLM から読み込むのは、[テンソル並列のグループと 1 つのインタフェース](https://github.com/vllm-project/vllm-neuron/blob/a080ebf48074048abd9574a3cb5a3ee9068a4958/vllm_neuron/model/llama3/model.py#L25-L29)です。層の計算は functional と nkilib から取り、プラグインの[モデルの契約](https://github.com/vllm-project/vllm-neuron/blob/a080ebf48074048abd9574a3cb5a3ee9068a4958/contrib/README.md#L195-L212)に合わせて書かれています。

## GPU でも差分は出うる

同じモデルと同じ重みでも、カーネルが違えば結果のビットが変わることがあります。浮動小数点の足し算は順番で結果が変わり、足す順番はカーネルの作りで決まるからです。Thinking Machines の「[Defeating Nondeterminism in LLM Inference](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/)」は、推論サービスの出力が揺れる主な原因を、負荷によって一緒に処理するリクエストの数が変わることだとしています。

vLLM には、一緒に処理するリクエストの構成によらない結果を目指す [VLLM_BATCH_INVARIANT](https://github.com/vllm-project/vllm/blob/d0d3005affa38e16dbd60092f0af4e314743d586/vllm/envs.py#L642-L644) があり、compute capability 9.0 以上の NVIDIA GPU が必要です。SGLang には、Thinking Machines の実装を[もとにした](https://github.com/sgl-project/sglang/blob/b572b8ea827fc236786cf64d025337f60895d16d/python/sglang/srt/batch_invariant_ops/__init__.py#L1) batch_invariant_ops があります。どちらも 1 つのエンジンの中での揺れへの対策で、エンジンやハードウェアをまたいでビットをそろえるものではありません。

Neuron の中でも、実装はすでに意図して分かれています。nkilib の GPT-OSS 向けの decode のカーネルの 1 つは、依存するライブラリのコードごと写した、別に保守するコード一式です。その [README](https://github.com/aws-neuron/nki-library/blob/ad2f1b921d8e5949fa3b9a186e5f9130269353dc/src/nkilib_src/nkilib/models/gpt_oss/README.md#L1-L27) は、GPT-OSS 向けの調整を、他のモデルが使う共通のカーネルから隔離するためにわざと分けたと述べ、attention の実装が共通の版と違うことも書いています。実装が分かれた以上、同じ計算の順番やビット一致は、確かめずには前提にできません。

## 1 モデルに 1 つのカーネルにはならない

![GPT-OSS には、段階ごと、decode のカーネル一式ごと、重みの形式と目的ごとに別のコードがある](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/686da5f92f511f/zenn/articles/686da5f92f511f/neuron-variants.png)

推論には、入力をまとめて処理する prefill と、1 トークンずつ作る decode の 2 つの段階があります。nkilib の attention は、Context Encoding の略で prefill 向けの [attention_cte](https://github.com/aws-neuron/nki-library/blob/ad2f1b921d8e5949fa3b9a186e5f9130269353dc/src/nkilib_src/nkilib/core/attention/attention_cte.py) と、Token Generation の略で decode 向けの [attention_tkg](https://github.com/aws-neuron/nki-library/blob/ad2f1b921d8e5949fa3b9a186e5f9130269353dc/src/nkilib_src/nkilib/core/attention/attention_tkg.py) に大きく分かれ、それぞれに派生もあります。GPT-OSS では、さらに [decode 向けのカーネル一式が 3 つ](https://github.com/aws-neuron/nki-library/tree/ad2f1b921d8e5949fa3b9a186e5f9130269353dc/src/nkilib_src/nkilib/models/gpt_oss)並び、vllm-neuron のモデルも [BF16 向け、MXFP4 向け、MXFP4 の性能向けの 3 つの実装](https://github.com/vllm-project/vllm-neuron/tree/a080ebf48074048abd9574a3cb5a3ee9068a4958/vllm_neuron/model/gpt_oss)を持ちます。

チップの世代の違いには、世代専用のカーネルを置く例と、1 つのカーネルの中で分岐する例があります。Trainium3 向けの FlashAttention-2 は、[Trn3 の B1 という版のチップでしか動きません](https://github.com/aws-neuron/nki-library/blob/ad2f1b921d8e5949fa3b9a186e5f9130269353dc/src/nkilib_src/nkilib/experimental/attention/flash_attention2_trn3/flash_attention_2.py#L104-L107)。一方、多くのカーネルは、コンパイルするときに NeuronCore の世代を調べて分岐します。Trn2 は gen3、Trn3 は gen4 です。MX 形式の重みを使う MoE の decode は、[Trn3 より前の世代では止まります](https://github.com/aws-neuron/nki-library/blob/ad2f1b921d8e5949fa3b9a186e5f9130269353dc/src/nkilib_src/nkilib/core/moe/moe_tkg/moe_tkg.py#L457-L460)。decode の attention は、[K を読む DMA をまとめる数の上限を Trn3 では 64、Trn2 では 32](https://github.com/aws-neuron/nki-library/blob/ad2f1b921d8e5949fa3b9a186e5f9130269353dc/src/nkilib_src/nkilib/core/attention/attention_tkg.py#L2288-L2298) にしていて、Trn2 で大きくまとめると多いバッチで遅くなるとコメントにあります。prefill 向けの QKV のカーネルは、Trn2 の命令でも使える活性化のスカラーのバイアスを、[Trn2 ではコンパイラの事情で精度が落ちるため使っていません](https://github.com/aws-neuron/nki-library/blob/ad2f1b921d8e5949fa3b9a186e5f9130269353dc/src/nkilib_src/nkilib/core/qkv/qkv_cte.py#L88-L94)。同じカーネルでも世代によって通る経路と速さが変わるので、測った結果には、インスタンスの種類も書く必要があります。筆者は、カーネルの本数をモデルの数から見積もることはできないと考えます。

## 部品の誤差は FP32 を基準に比べる

![FP32 の CPU の結果を基準に、BF16 の CPU と BF16 の Neuron の誤差を比べ、分布の条件と入力ごとの条件の両方で合否を決める](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/686da5f92f511f/zenn/articles/686da5f92f511f/three-way.png)

差分が出る前提に立つなら、何と比べるかが大事です。vllm-neuron の[部品のテストの指針](https://github.com/vllm-project/vllm-neuron/blob/a080ebf48074048abd9574a3cb5a3ee9068a4958/docs/design/accuracy/module_test_guidelines.md#L58-L83)は、同じ入力を FP32 の CPU、BF16 の CPU、BF16 の Neuron で計算し、FP32 の結果からの 2 つの誤差を比べます。3 つの結果を使うので、指針はこれを three-way の比較と呼んでいます。

[合格の条件](https://github.com/vllm-project/vllm-neuron/blob/a080ebf48074048abd9574a3cb5a3ee9068a4958/docs/design/accuracy/module_test_guidelines.md#L105-L134)は 2 つで、両方を満たす必要があります。1 つ目は全入力をまとめた条件で、2 つの誤差の分布の重なり BC が[既定で 0.99](https://github.com/vllm-project/vllm-neuron/blob/a080ebf48074048abd9574a3cb5a3ee9068a4958/vllm_neuron/accuracy/testing.py#L355) 以上か、Neuron の誤差の RMS を CPU の誤差の RMS で割った比が 1 以下であることです。2 つ目は入力ごとの条件で、同じく Neuron の誤差を CPU の誤差で割った比が、既定では最大値で 5 未満、L2 で 3 未満であることです。

この指針は vllm-neuron の部品のテストのためのものです。ただ、物差しが同じ型の CPU の誤差なので、筆者はほかのエンジンの部品にも使えると考えます。ビットをそろえる代わりに部品の**誤差が同じ型の CPU と同じ程度に収まるかを確かめる**ことで、実装が並んでも、部品の数値の精度を同じ物差しで比べられます。

## vllm-neuron の寄稿は始まったばかり

[contrib/README.md](https://github.com/vllm-project/vllm-neuron/blob/a080ebf48074048abd9574a3cb5a3ee9068a4958/contrib/README.md#L214-L232) は、モデル専用のコードとカーネルを寄稿のフォルダの中に置くよう求めています。共有してよいのは functional や nn のような安定した部品と vLLM の公開 API で、2 つのモデルが同じ補助関数を使いたいときは、それぞれに写すか、共有の部品への格上げを Neuron チームに相談します。寄稿のモデルはプラグインが起動時に登録する[一覧に入らず](https://github.com/vllm-project/vllm-neuron/blob/a080ebf48074048abd9574a3cb5a3ee9068a4958/contrib/README.md#L40-L46)、PR には Neuron の上の vLLM で出力を確かめる[精度のテスト](https://github.com/vllm-project/vllm-neuron/blob/a080ebf48074048abd9574a3cb5a3ee9068a4958/contrib/README.md#L159-L190)と README が必須です。[CONTRIBUTING.md](https://github.com/vllm-project/vllm-neuron/blob/a080ebf48074048abd9574a3cb5a3ee9068a4958/CONTRIBUTING.md#L49-L62) は、始める前に既存の contrib と PR を確かめるよう求めています。contrib にすでにあるモデルについて、元の寄稿者と協力できず、特定の最適化や機能を加えるときは、別の実装を出すことも認めています。

[vllm-neuron の PR](https://github.com/vllm-project/vllm-neuron/pulls?q=is%3Apr) では、仕組みが入った翌日からの 3 日間 (2026 年 10 月 21〜23 日) に寄稿の PR が 6 件作られ、10 月 31 日の時点でマージされたものはありません。重なりも、すでに見えています。

- 同じモデルを扱う PR が、開いたまま並んでいます。Qwen3-MoE では、仕組みが入る前に別々の寄稿者が出した [#39](https://github.com/vllm-project/vllm-neuron/pull/39) と [#56](https://github.com/vllm-project/vllm-neuron/pull/56) が、どちらも公式のモデルの場所に実装を加えようとしています。Hy3-FP8 では、仕組みの前に出た [#59](https://github.com/vllm-project/vllm-neuron/pull/59) と、contrib に置いた [#73](https://github.com/vllm-project/vllm-neuron/pull/73) が両方開いています。
- 既存のカーネルと重なる寄稿があります。Qwen3.5 の [#68](https://github.com/vllm-project/vllm-neuron/pull/68) は寄稿のフォルダに独自の DeltaNet のカーネルを持ちますが、nkilib にも [Gated DeltaNet のカーネル](https://github.com/aws-neuron/nki-library/tree/ad2f1b921d8e5949fa3b9a186e5f9130269353dc/src/nkilib_src/nkilib/experimental/gdn)があります。両者が置き換えられるかどうかは、測らなければ分かりません。
- 文書に無い条件の話が出ています。#68 のコメントでは、寄稿者の 1 人が、Neuron チームから聞いた理解として、新しい寄稿は Model Runner v2 の上に書く必要があると書いています。contrib/README.md と PR テンプレートには、その条件はありません。

nkilib には、外から変更を提案できます。[README](https://github.com/aws-neuron/nki-library/blob/ad2f1b921d8e5949fa3b9a186e5f9130269353dc/README.md#L80) も、カーネルの変更を寄稿したい人に向けた使い方を案内しています。ただ、[nki-library の PR](https://github.com/aws-neuron/nki-library/pulls?q=is%3Apr) では、外部の修正 PR の多くが閉じられ、[内部で取り込んで次のリリースで出す](https://github.com/aws-neuron/nki-library/pull/14)、[内部のレビューに移す](https://github.com/aws-neuron/nki-library/pull/21)と返されています。寄稿者からは採否と公開の時期を追いにくく、手元で手を加えたいときは写すことになりがちです。

## GPU のコミュニティは担当とレビューの役割を決めている

vLLM は、[CODEOWNERS](https://github.com/vllm-project/vllm/blob/d0d3005affa38e16dbd60092f0af4e314743d586/.github/CODEOWNERS#L196-L247) でファイルごとの担当者を決めています。担当はモデルごと (DeepSeek V4 や Qwen) にも、ハードごと (各モデルの amd のフォルダ) にも置かれ、モデルとハードが交わるフォルダには両方が並びます。PR には少なくとも 1 人の committer のレビューと承認が要り、[CODEOWNERS の対象のコードなら担当者がレビューします](https://github.com/vllm-project/vllm/blob/d0d3005affa38e16dbd60092f0af4e314743d586/docs/governance/process.md#L137)。軽微な変更や緊急の修正には例外があります。vllm-neuron と nki-library、以前の vllm-neuron が土台にしていた推論ライブラリ NxD Inference のリポジトリには、CODEOWNERS のファイルがありません。[vllm-neuron](https://github.com/vllm-project/vllm-neuron/blob/a080ebf48074048abd9574a3cb5a3ee9068a4958/contrib/README.md#L189-L190) と [NxD Inference](https://github.com/aws-neuron/neuronx-distributed-inference/blob/5b509a8996f42071d9d34e4d83a748270437324f/contrib/CONTRIBUTING.md#L40) の寄稿の文書は、Neuron チームがレビューすると書いています。

vLLM には、マージの権限を持つ committer のほかに、[Reviewer という役割](https://github.com/vllm-project/vllm/blob/d0d3005affa38e16dbd60092f0af4e314743d586/docs/community/reviewers.md#L1-L55)があります。この役割は [RFC #58253](https://github.com/vllm-project/vllm/issues/58253) で作られました。Reviewer は PR を承認し、重複を閉じ、設計の問題を担当者に上げ、committer の最終確認に回します。Reviewer には、レビューの実績を積んだ人が、別々の組織に属する 2 人の committer の推薦でなります。必須ではない目安として、15 件のマージと 30 件のレビュー、または 45 件のレビューが挙げられています。実績を積めばこの役割に就ける手順が、文書になっています。

## 足りない仕組みを RFC で提案する

![RFC で決めたいことは、nkilib へ変更が届く経路、置き場所と契約の版、レビューする人の 3 つ](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/686da5f92f511f/zenn/articles/686da5f92f511f/proposal.png)

ここからは筆者の提案です。2026 年 10 月 31 日時点で、[vllm-neuron の issue](https://github.com/vllm-project/vllm-neuron/issues?q=is%3Aissue) の 33 件と [nki-library の issue](https://github.com/aws-neuron/nki-library/issues?q=is%3Aissue) の 5 件に、タイトルに RFC を含むものはありません。あるのは、Qwen3.5 の対応の提案のような、モデル単位の issue です。ここまでの問題を扱う RFC が無いなら、作ることを提案します。中身は次の 3 つです。

1 つ目は、nkilib へ変更が届く経路です。共有できる演算は nkilib に集め、vLLM と SGLang の両方のプラグインが同じものを使う形を目指します。そのためには、外からの変更がどの経路で取り込まれ、どの SDK の版で届くかを、寄稿者が追える形で公開する必要があります。届くまでの写しは、出どころの nkilib のコミットと、消す基準の SDK の版を書いた一時的なものにします。意図して分けた写しは、次の 2 つ目の特化したカーネルとして扱います。nkilib に何があるかを寄稿者が探せる一覧も要ります。

2 つ目は、置き場所と契約の版です。共有の演算とモデル専用の実装の境界を、RFC で決めます。nkilib の GPT-OSS のように、モデル専用でも nkilib に置く例があるので、名前ではなく、依存、使い回す範囲、保守する人で決めるのがよいと考えます。モデル専用の処理をプラグインに置くなら、vLLM の vllm/models/<model>/<vendor>/ のようにモデルの隣に置きます。寄稿が従う契約は、モデルランナーの版、nkilib の版、SDK の版を README とテンプレートに書き、変えるときは、すでに開いている PR の扱いも書きます。NVIDIA と AMD の外部のカーネル集を載せる SGLang の [plugin_kernels](https://github.com/sgl-project/sglang/blob/b572b8ea827fc236786cf64d025337f60895d16d/python/sglang/kernels/plugin_kernels/README.md#L13-L42) も、契約の [API の版](https://github.com/sgl-project/sglang/blob/b572b8ea827fc236786cf64d025337f60895d16d/python/sglang/kernels/plugin_kernels/README.md#L15-L16)を持ち、起動時に条件を確かめて、合わなければ理由を並べて止まります。

3 つ目は、レビューする人の仕組みです。いまの Neuron チームのレビューを補う形で、寄稿者のコミュニティから、モデルやアーキテクチャごとにレビューする人のグループを作ります。Neuron チームはマージの判断と契約を受け持ち、グループは一次のレビュー、重複の整理、測った記録の確認を受け持ちます。グループに加わるのは、寄稿とレビューの実績を積んだ人です。vLLM の Reviewer にならって、推薦の手順と、レビューと最終のマージの権限の分け方を文書にします。実績の件数の目安は、いまの寄稿の規模に合わせて決め、最初は必須にしない方がよいと考えます。担当はモデルだけで切らず、カーネルと共有部分を見る人も置きます。寄稿のフォルダの外に触れる PR は、必ず Neuron チームのレビューを通るようにします。

物差しも、この RFC でそろえます。部品には three-way の比較を、モデル全体には Transformers との出力の比較を、共通の確かめ方の候補とします。いまは vllm-neuron でも three-way は任意で、Transformers との比較の扱いも vLLM と SGLang でそろっていないので、どこまで必須にするかと、どこで実行するかを RFC で決めます。Trainium の実機を持たない寄稿者も多いので、PR には測った環境と結果を添えてもらいます。環境は、SDK の版、nkilib の版、インスタンスの種類です。性能のための 2 つ目の実装なら、どの段階、テンソルの形、重みの形式で速くなったかと、その数値も書いてもらいます。

## まとめ

GPU でも、1 つの演算に多くのカーネルがあり、モデルのコードはエンジンごと、ハードごとに分かれていて、実装の違いによる差分は出えます。vLLM は、置き場所に加えて、担当者と、実績を積んだ人がレビューする役割を文書にしています。筆者は、Trainium でも nkilib へ変更が届く経路、置き場所と契約の版、レビューする人のグループを RFC として提案し、コミュニティの中で実績を積み重ねていくことを提案します。
