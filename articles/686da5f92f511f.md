## はじめに

2026 年 10 月 22 日に、LMSYS が [SGLang の Trainium 対応のベータ](https://www.lmsys.org/blog/2026-10-22-sglang-trainium-beta)を発表しました。vLLM には [vLLM Neuron プラグイン](https://github.com/vllm-project/vllm-neuron/blob/a080ebf48074048abd9574a3cb5a3ee9068a4958/README.md) (以下 vllm-neuron) がすでにあり、コミュニティからモデルの寄稿を受け付けています。Neuron は Trainium 向けの AWS の SDK とコンパイラです。NKI (Neuron Kernel Interface) は、Trainium のカーネルを Python で書くための仕組みです。AWS の Neuron チームは、NKI で書いたカーネルを [NKI Library](https://github.com/aws-neuron/nki-library/blob/ad2f1b921d8e5949fa3b9a186e5f9130269353dc/README.md) (以下 nkilib) として公開しています。カーネルは、アクセラレータの上で 1 つ、またはまとめた複数の演算を実行するプログラムです。

ここで気になるのは、nkilib、vllm-neuron、SGLang、寄稿者の手元のそれぞれで同じ演算のカーネルが書かれ、食い違っていくことです。この記事では、GPU の vLLM と SGLang がこの問題をどう扱っているかをソースで確かめ、Trainium ではどうあるべきかを提案します。内容は 2026 年 10 月 30 日時点のもので、コードへのリンクはそのときのコミットに固定しています。

| 疑問 | GPU での事実 | Trainium での筆者の見立て |
|---|---|---|
| エンジンやモデルごとに差分は出るか | 出ることがあります。カーネルが違うと足し算の順番が変わり、ビットが変わりえます | エンジンをまたぐビット一致は前提にせず、何と比べてどこまで許すかを決めます |
| 1 モデルに 1 つのカーネルになるか | なりません。1 つの演算に多くの実装の候補があり、エンジンが条件で選びます | 段階、テンソルの形、重みの形式、世代ごとに複数のカーネルが並ぶのは自然です |
| 寄稿をどう受け付けるか | モデルのコードはエンジンごとに書きます。カーネルは共通のライブラリと各エンジンの自前の実装の両方から取ります | 演算、特化、モデルの 3 段で、共有の仕方を分けます |

## コードはどこに置かれているか

![vllm-neuron の中に公式のモデル、寄稿のモデル、共有の演算があり、その下に nkilib がある。SGLang のプラグインは中身が公開されていない](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/686da5f92f511f/zenn/articles/686da5f92f511f/places.png)

vllm-neuron では、公式のモデルが [vllm_neuron/model/](https://github.com/vllm-project/vllm-neuron/tree/a080ebf48074048abd9574a3cb5a3ee9068a4958/vllm_neuron/model) に、寄稿のモデルが [contrib/models/](https://github.com/vllm-project/vllm-neuron/tree/a080ebf48074048abd9574a3cb5a3ee9068a4958/contrib/models) に置かれます。モデル間で共有する演算は [functional/](https://github.com/vllm-project/vllm-neuron/tree/a080ebf48074048abd9574a3cb5a3ee9068a4958/vllm_neuron/functional) にあります。`__init__.py` を除く 50 のファイルのうち 36 が、[MoE の prefill](https://github.com/vllm-project/vllm-neuron/blob/a080ebf48074048abd9574a3cb5a3ee9068a4958/vllm_neuron/functional/moe/moe_cte.py#L5-L12) のように nkilib を import しています。プラグインが自分で書いた NKI カーネルは [_kernels/](https://github.com/vllm-project/vllm-neuron/blob/a080ebf48074048abd9574a3cb5a3ee9068a4958/vllm_neuron/_kernels/__init__.py#L1-L17) にあり、`qwen3_32b_sp` や `glm_5_3` のようにモデルの名前の付いたものもあります。

nkilib には、[コンパイラに同梱された版と、pip で入れる版](https://github.com/aws-neuron/nki-library/blob/ad2f1b921d8e5949fa3b9a186e5f9130269353dc/README.md#L76-L108)があります。同梱の版は、そのコンパイラで確かめられています。pip の版を入れると、通常はそちらが優先されます。pip の版は最新のコンパイラで動くとは限らず、README はコンパイラの版に対応するブランチから始めるよう勧めています。

プラグインには、nkilib から写したカーネルもあります。Qwen3-32B 向けの QKV のカーネルのファイルは、[nkilib の版を写して手を加えた](https://github.com/vllm-project/vllm-neuron/blob/a080ebf48074048abd9574a3cb5a3ee9068a4958/vllm_neuron/_kernels/qwen3_32b_sp/qwen3_32b_qkv_tkg_projection_mxfp_preloaded.py#L1-L9)と冒頭に記しています。[vendored_kernels/](https://github.com/vllm-project/vllm-neuron/blob/a080ebf48074048abd9574a3cb5a3ee9068a4958/vllm_neuron/functional/vendored_kernels/__init__.py#L1-L8) には、依存先のイメージにまだ入っていない版のカーネルが写されていて、上流の版が入ったら消すとされています。

SGLang の発表は、プラグインが TorchNeuron の上に作られたと述べています。TorchNeuron は Trainium 向けの PyTorch のバックエンドで、発表によると SGLang のモデルの部品と中心の抽象は大きく変えずに Trainium に移せました。独自のカーネルには NKI を使います。発表にはリポジトリへのリンクが無いので、この記事ではプラグインの中身には踏み込みません。

## GPU では、エンジンがカーネルを選ぶ

![vLLM と SGLang では、モデルのコードが演算の層や入り口を呼び、どのカーネルで実行するかはエンジンが条件から選ぶ](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/686da5f92f511f/zenn/articles/686da5f92f511f/gpu-select.png)

vLLM のモデル追加のガイドは、[契約が合う限り Attention や MoE などの共有の層を使う](https://github.com/vllm-project/vllm/blob/d0d3005affa38e16dbd60092f0af4e314743d586/docs/contributing/model/basic.md#L80-L88)よう求めています。契約は、層が受け取る入力と返す出力の約束です。共有の層を使う場合、どのカーネルで実行するかはエンジンが決めます。新しい種類の attention なら、層から作ります。

層の下には多くの候補があります。attention のバックエンドの一覧には、使わないことを表す NO_ATTENTION なども含めて [52 個の名前](https://github.com/vllm-project/vllm/blob/d0d3005affa38e16dbd60092f0af4e314743d586/vllm/v1/attention/backends/registry.py#L34-L251)が並びます。MoE の実装を集めた [experts/](https://github.com/vllm-project/vllm/tree/d0d3005affa38e16dbd60092f0af4e314743d586/vllm/model_executor/layers/fused_moe/experts) には、`__init__.py` を除いて 40 のファイルがあります。FP8 の MoE では、[プラットフォームや設定に応じて候補の優先順位](https://github.com/vllm-project/vllm/blob/d0d3005affa38e16dbd60092f0af4e314743d586/vllm/model_executor/layers/fused_moe/oracle/fp8.py#L83-L150)が決まります。

SGLang は、呼び出せるカーネルの公開の入り口として [sglang.kernels](https://github.com/sgl-project/sglang/blob/b572b8ea827fc236786cf64d025337f60895d16d/python/sglang/kernels/README.md#L1-L12) を用意しています。ここに登録する 1 つの実装は [KernelSpec](https://github.com/sgl-project/sglang/blob/b572b8ea827fc236786cf64d025337f60895d16d/python/sglang/kernels/spec.py#L203-L215) で表され、[動ける装置の条件](https://github.com/sgl-project/sglang/blob/b572b8ea827fc236786cf64d025337f60895d16d/python/sglang/kernels/spec.py#L126-L137)を持てます。AMD の GPU 向けのカーネル集 aiter や、Huawei の Ascend 向けの torch_npu も、[実装の出どころの 1 つ](https://github.com/sgl-project/sglang/blob/b572b8ea827fc236786cf64d025337f60895d16d/python/sglang/kernels/spec.py#L29-L54)として区別されます。

GPU でも、モデルの名前の付いたカーネルはあります。vLLM の [csrc/](https://github.com/vllm-project/vllm/tree/d0d3005affa38e16dbd60092f0af4e314743d586/csrc) には、DeepSeek V4 や Kimi K3 向けに複数の処理をまとめたカーネルがあります。SGLang は、ops/ の下では、そうした実装も [attention や MoE などの演算の分類の中に置く](https://github.com/sgl-project/sglang/blob/b572b8ea827fc236786cf64d025337f60895d16d/python/sglang/kernels/README.md#L40-L42)と決めています。

## GPU では、モデルのコードはエンジンごとに書く

SGLang の新しいモデルのガイドには、[vLLM のモデルを SGLang に移す手順](https://github.com/sgl-project/sglang/blob/b572b8ea827fc236786cf64d025337f60895d16d/docs/docs/supported-models/support_new_models.mdx#L86-L105)があります。SGLang は vLLM のインタフェースと一部の層を引き継いでいるので、移すのは易しいと書かれています。そのうえで、vLLM の Attention を SGLang の RadixAttention に置き換え、最後は SGLang の部品だけで動くよう求めています。同じモデルのコードが、vLLM と SGLang に別々にある前提です。

カーネルは、共通のライブラリからも取ります。2 つのエンジンはどちらも CUDA 向けに FlashInfer に依存し、版はそれぞれが [vLLM は 0.7.2.post1](https://github.com/vllm-project/vllm/blob/d0d3005affa38e16dbd60092f0af4e314743d586/requirements/cuda.txt#L13)、[SGLang は 0.7.2](https://github.com/sgl-project/sglang/blob/b572b8ea827fc236786cf64d025337f60895d16d/python/pyproject.toml#L41) に固定しています。

正しさを確かめる方法として、2 つのガイドはどちらも Hugging Face Transformers との比較を案内しています。vLLM のガイドで必須なのはダミーの重みで初期化できるテストで、[Transformers との出力の比較](https://github.com/vllm-project/vllm/blob/d0d3005affa38e16dbd60092f0af4e314743d586/docs/contributing/model/tests.md#L5-L36)は任意です。SGLang のガイドは、比較と[ベンチマークの結果を PR に書く](https://github.com/sgl-project/sglang/blob/b572b8ea827fc236786cf64d025337f60895d16d/docs/docs/supported-models/support_new_models.mdx#L49-L84)よう求めています。

vllm-neuron も、モデルの実装をプラグインの中に持ちます。Llama 3 の実装が vLLM から読み込むのは、[テンソル並列のグループと 1 つのインタフェース](https://github.com/vllm-project/vllm-neuron/blob/a080ebf48074048abd9574a3cb5a3ee9068a4958/vllm_neuron/model/llama3/model.py#L25-L29)です。層の計算は functional と nkilib から取り、プラグインの[モデルの契約](https://github.com/vllm-project/vllm-neuron/blob/a080ebf48074048abd9574a3cb5a3ee9068a4958/contrib/README.md#L195-L212)に合わせて書かれています。

## GPU でも差分は出うる

同じモデルと同じ重みでも、カーネルが違えば結果のビットが変わることがあります。浮動小数点の足し算は順番で結果が変わり、足す順番はカーネルの作りで決まるからです。Thinking Machines の「[Defeating Nondeterminism in LLM Inference](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/)」は、推論サービスの出力が揺れる主な原因を、負荷によって一緒に処理するリクエストの数が変わることだとしています。

vLLM には、一緒に処理するリクエストの構成によらない結果を目指す [VLLM_BATCH_INVARIANT](https://github.com/vllm-project/vllm/blob/d0d3005affa38e16dbd60092f0af4e314743d586/vllm/envs.py#L642-L644) があり、compute capability 9.0 以上の NVIDIA GPU が必要です。SGLang には、Thinking Machines の実装を[もとにした](https://github.com/sgl-project/sglang/blob/b572b8ea827fc236786cf64d025337f60895d16d/python/sglang/srt/batch_invariant_ops/__init__.py#L1) batch_invariant_ops があります。どちらも、一緒に処理するリクエストによる揺れへの対策です。エンジンやハードウェアをまたいでビットをそろえるものではありません。

Neuron の中でも、実装はすでに意図して分かれています。nkilib の GPT-OSS 向けの decode のカーネルの 1 つは、依存するライブラリのコードごと写した、別に保守するコード一式です。その [README](https://github.com/aws-neuron/nki-library/blob/ad2f1b921d8e5949fa3b9a186e5f9130269353dc/src/nkilib_src/nkilib/models/gpt_oss/README.md#L1-L27) は、GPT-OSS 向けの調整を、他のモデルが使う共通のカーネルから隔離するためにわざと分けたと述べています。attention の実装が共通の版と違うことも書いています。実装が分かれた以上、同じ計算の順番やビット一致は、確かめずには前提にできません。

## 1 モデルに 1 つのカーネルにはならない

![GPT-OSS には、段階ごと、decode のカーネル一式ごと、重みの形式と目的ごとに別のコードがある](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/686da5f92f511f/zenn/articles/686da5f92f511f/neuron-variants.png)

推論には、入力をまとめて処理する prefill と、1 トークンずつ作る decode の 2 つの段階があります。nkilib の attention は、Context Encoding の略で prefill 向けの [attention_cte](https://github.com/aws-neuron/nki-library/blob/ad2f1b921d8e5949fa3b9a186e5f9130269353dc/src/nkilib_src/nkilib/core/attention/attention_cte.py) と、Token Generation の略で decode 向けの [attention_tkg](https://github.com/aws-neuron/nki-library/blob/ad2f1b921d8e5949fa3b9a186e5f9130269353dc/src/nkilib_src/nkilib/core/attention/attention_tkg.py) に大きく分かれ、それぞれに派生もあります。prefill は多くのトークンをまとめて計算し、decode は 1 トークンごとに重みと KV キャッシュを読むので、良いカーネルの形が違います。

GPT-OSS では、さらに [decode 向けのカーネル一式が 3 つ](https://github.com/aws-neuron/nki-library/tree/ad2f1b921d8e5949fa3b9a186e5f9130269353dc/src/nkilib_src/nkilib/models/gpt_oss)並びます。vllm-neuron のモデルも、[BF16 向け、MXFP4 向け、MXFP4 の性能向けの 3 つの実装](https://github.com/vllm-project/vllm-neuron/tree/a080ebf48074048abd9574a3cb5a3ee9068a4958/vllm_neuron/model/gpt_oss)を持ちます。チップの世代でも分かれ、nkilib には [Trainium3 向けの FlashAttention-2](https://github.com/aws-neuron/nki-library/blob/ad2f1b921d8e5949fa3b9a186e5f9130269353dc/README.md#L44) があります。筆者は、カーネルの本数をモデルの数から見積もることはできないと考えます。

## 部品の誤差は FP32 を基準に比べる

![FP32 の CPU の結果を基準に、BF16 の CPU と BF16 の Neuron の誤差を比べ、分布の条件と入力ごとの条件の両方で合否を決める](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/686da5f92f511f/zenn/articles/686da5f92f511f/three-way.png)

差分が出る前提に立つなら、何と比べるかが大事です。vllm-neuron の[部品のテストの指針](https://github.com/vllm-project/vllm-neuron/blob/a080ebf48074048abd9574a3cb5a3ee9068a4958/docs/design/accuracy/module_test_guidelines.md#L58-L83)は、同じ入力を FP32 の CPU、BF16 の CPU、BF16 の Neuron で計算します。FP32 の結果からの誤差を、BF16 の CPU と BF16 の Neuron のそれぞれで測り、2 つの誤差を比べます。3 つの結果を使うので、指針はこれを three-way の比較と呼んでいます。

[合格の条件](https://github.com/vllm-project/vllm-neuron/blob/a080ebf48074048abd9574a3cb5a3ee9068a4958/docs/design/accuracy/module_test_guidelines.md#L105-L134)は 2 つで、両方を満たす必要があります。1 つ目は全入力をまとめた条件で、2 つの誤差の分布の重なり BC が[既定で 0.99](https://github.com/vllm-project/vllm-neuron/blob/a080ebf48074048abd9574a3cb5a3ee9068a4958/vllm_neuron/accuracy/testing.py#L355) 以上か、Neuron の誤差の RMS を CPU の誤差の RMS で割った比が 1 以下であることです。2 つ目は入力ごとの条件で、同じく Neuron の誤差を CPU の誤差で割った比が、既定では最大値で 5 未満、L2 で 3 未満であることです。2 つ目は、1 つの入力だけが大きく外れることを防ぎます。

この指針は vllm-neuron の部品のテストのためのものです。ただ、物差しが同じ型の CPU の誤差なので、筆者はほかのエンジンの部品にも使えると考えます。ビットをそろえる代わりに部品の**誤差が同じ型の CPU と同じ程度に収まるかを確かめる**ことで、実装が並んでも、部品の数値の精度を同じ物差しで比べられます。

## vllm-neuron は寄稿をフォルダに閉じ込める

[contrib/README.md](https://github.com/vllm-project/vllm-neuron/blob/a080ebf48074048abd9574a3cb5a3ee9068a4958/contrib/README.md#L214-L232) は、寄稿のモデルを自分のフォルダの中で完結させるよう求めています。そのモデル専用のカーネルはフォルダの中に置き、共有してよいのは functional や nn のような安定した部品と vLLM の公開 API だけです。2 つのモデルが同じ補助関数を使いたいときは、それぞれに写すか、共有の部品への格上げを Neuron チームに相談します。理由は、寄稿を切り離し、レビューしやすく、アプリへ写しやすくするためとされています。

寄稿のモデルは、プラグインが起動時に登録する[一覧に入りません](https://github.com/vllm-project/vllm-neuron/blob/a080ebf48074048abd9574a3cb5a3ee9068a4958/contrib/README.md#L40-L46)。使う人がモデルを自分で登録する形で、既定では有効になりません。PR には、Neuron の上の vLLM を通して出力を確かめる[精度のテスト](https://github.com/vllm-project/vllm-neuron/blob/a080ebf48074048abd9574a3cb5a3ee9068a4958/contrib/README.md#L159-L190)と README が必須です。README には、使い方、試したインスタンスと SDK の版の表、チェックポイント、テストの動かし方を書きます。寄稿のモデルは[コミュニティが保守する](https://github.com/vllm-project/vllm-neuron/blob/a080ebf48074048abd9574a3cb5a3ee9068a4958/CONTRIBUTING.md#L69-L72)ものとされ、寄稿者には新しい版のプラグインで動かし続けることが勧められています。

[CONTRIBUTING.md](https://github.com/vllm-project/vllm-neuron/blob/a080ebf48074048abd9574a3cb5a3ee9068a4958/CONTRIBUTING.md#L49-L62) は、始める前に既存の contrib と PR を確かめ、元の寄稿者と協力できるなら既存の実装を良くするよう勧めています。協力できず、特定の最適化や機能を加えるときは、既存の実装を書き換えずに別の実装を出してよく、何が違うかを PR に書きます。モデルに必要なフレームワークの変更は同じ PR に入れてよく、Neuron チームがその部分の分割や先送りを求めることがあります。筆者は、この決まりのもとでは、補助関数やカーネルの写しと、同じモデルの別の実装が増えうると考えます。受け付け方は[いまは意図して軽くしている](https://github.com/vllm-project/vllm-neuron/blob/a080ebf48074048abd9574a3cb5a3ee9068a4958/CONTRIBUTING.md#L43-L47)とされ、プラグインもまだ Beta なので、決まりは変わりえます。

PR の要件は、以前の vllm-neuron が土台にしていた推論ライブラリ NxD Inference の [contrib の決まり](https://github.com/aws-neuron/neuronx-distributed-inference/blob/5b509a8996f42071d9d34e4d83a748270437324f/contrib/CONTRIBUTING.md#L1-L45)とほぼ同じです。ただ、NxD Inference の [68 の寄稿のモデル](https://github.com/aws-neuron/neuronx-distributed-inference/tree/5b509a8996f42071d9d34e4d83a748270437324f/contrib/models)は、[NxD Inference に依存しない](https://github.com/vllm-project/vllm-neuron/blob/a080ebf48074048abd9574a3cb5a3ee9068a4958/README.md#L135-L141)いまの vllm-neuron では[作り直しが要り](https://github.com/vllm-project/vllm-neuron/blob/a080ebf48074048abd9574a3cb5a3ee9068a4958/docs/getting-started/migration-nxdi-to-vllm-neuron.md#L19-L21)、vllm-neuron の contrib/models/ にはまだ template しかありません。

## どう収めるべきか

![共有の仕方を、変わりにくい演算のカーネル、特化したカーネル、モデルのコードの 3 段に分ける](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/686da5f92f511f/zenn/articles/686da5f92f511f/proposal.png)

ここからは筆者の提案です。乱立を避けるには、何を 1 つにするかを、変わりにくさで分けるのがよいと考えます。

1 段目は、attention、MoE、正規化、集団通信のような演算のカーネルです。筆者は、共有できる演算は nkilib に集め、vLLM と SGLang の両方のプラグインが import して使う形を提案します。GPU では FlashInfer のほかに [DeepGEMM や aiter などの供給元](https://github.com/vllm-project/vllm/blob/d0d3005affa38e16dbd60092f0af4e314743d586/vllm/model_executor/layers/fused_moe/oracle/fp8.py#L92-L108)が並んでいますが、Trainium では初めから 1 つの上流に寄せておく方が、写しが増えにくいと考えます。写すのは、vendored_kernels のように出どころと消す条件を書いた一時的なものに限ります。

上流を 1 つにしても、同じ版のカーネルが動くとは限りません。同梱の nkilib はそのコンパイラの版で確かめられたもので、vllm-neuron は[プラグインの版ごとに Neuron SDK の版](https://github.com/vllm-project/vllm-neuron/blob/a080ebf48074048abd9574a3cb5a3ee9068a4958/README.md#L137-L141)を 1 つに決めています。2 つのプラグインが別の SDK の版を使えば、動く nkilib の版も違いえます。GPU でも、FlashInfer の版は 2 つのエンジンで違いました。そのため、上流を 1 つにすることに加えて、どの SDK の版で測ったかを書くことも求めます。

2 段目は、特定のモデル、設定、段階、世代に絞ったカーネルです。この層は数が増えてよく、代わりに載せ方を決めます。参考になるのは、NVIDIA と AMD の外部のカーネル集を載せる SGLang の [plugin_kernels](https://github.com/sgl-project/sglang/blob/b572b8ea827fc236786cf64d025337f60895d16d/python/sglang/kernels/plugin_kernels/README.md#L13-L42) です。有効にすると、SGLang は重みを読む前に設定がカーネルの条件に合うかを確かめ、合わなければ理由を並べてサーバーを止めます。合えば、カーネルが受け持つ段階だけモデルの処理を差し替え、ほかの段階はモデル自身の処理で動かします。カーネル本体は外のライブラリに置き、SGLang の側は契約と、起動時の確認や処理の振り分けを受け持ちます。

筆者は、Trainium で同じことをするなら、プラグインごとに契約と振り分けの処理を用意することになると考えます。カーネル本体の置き場所には、nkilib の models/ が候補になります。ただ、GPT-OSS 向けの decode のカーネルの 1 つは、[VLLM_NEURON_MEGA_ で始まる環境変数](https://github.com/aws-neuron/nki-library/blob/ad2f1b921d8e5949fa3b9a186e5f9130269353dc/src/nkilib_src/nkilib/models/gpt_oss/README.md#L35-L45)で、既定で有効な性能と数値の設定を切り替えます。その 1 つは、重みのスケールの HBM 上の並べ方も変えます。SGLang からも使うなら、設定の渡し方をエンジンの名前から切り離す方がよいと考えます。

3 段目は、モデルのコードです。モデルとエンジンの契約はエンジンごとに違うので、GPU と同じくエンジンごとに書くことになります。ただし書き方は 2 つのプラグインで違います。発表によれば、SGLang のモデルの部品と中心の抽象は、大きく変えずに Trainium に移せました。vllm-neuron は、vLLM 本体とは別にプラグインのモデルを書いています。GPU 向けのコードと共有するかどうかで、保守の手間も変わります。

その代わり、物差しをそろえます。筆者は、部品には three-way の比較を、モデル全体には Transformers との出力の比較を、共通の確かめ方として提案します。three-way は vllm-neuron でも任意のテストで、Transformers との比較も、vLLM のガイドでは任意、SGLang のガイドでは正解率の比較が必須と、扱いがそろっていません。three-way には CPU での 2 回の計算と Neuron の実機が要るので、PR に測った環境と結果を添えてもらうのが現実的です。性能のための 2 つ目の実装なら、どの段階、テンソルの形、重みの形式、インスタンス、SDK の版で速くなったかと、その数値も書いてもらいます。利用者は、その記録から、どの組み合わせで確かめられた実装かを判断できます。

## まとめ

GPU でも、1 つの演算に多くのカーネルがあり、モデルのコードはエンジンごとに書かれていて、実装の違いによる差分は出えます。筆者は、Trainium では演算のカーネルを nkilib に集め、特化したカーネルは条件が合うときだけ差し替え、モデルのコードは共通の物差しで測る形を提案します。
