## はじめに

MoE のモデルを複数の GPU で動かすと、GPU どうしがトークンを送り合います。この記事では、その送り合いに関わるソフトウェアの層が、それぞれ何を受け持っているかを図で見ていきます。コードには踏み込みません。

全体の流れは次の動画にまとめています。記事の図は、この動画から切り出したものです。

## 登場する層

![1 台の GPU ノードの上の層。下から EC2 インスタンス、DLAMI、コンテナ](/images/a0f5ff21eed405-stack.png)

1 台の GPU ノードには、下から 3 つの段が載っています。

| 段 | 中身 | 入れる場所 |
|---|---|---|
| EC2 インスタンス | GPU と、ノードの外へ送る EFA | 機器そのもの |
| DLAMI | Ubuntu と、EFA と GPU のドライバ、gdrcopy のドライバである gdrdrv | ホスト |
| コンテナ | rdma-core、libfabric、aws-ofi-nccl、NCCL、DeepEP。V1 では NVSHMEM も | コンテナイメージ |

カーネルのドライバは OS のカーネルの中で動くので、ホストに入れます。そのほかのライブラリはコンテナに入れます。

## all-to-all: トークンを担当の GPU へ送る

MoE では、トークンごとに使うエキスパートが決まります。エキスパートを複数の GPU に分けて置く方法を、エキスパート並列、略して EP と呼びます。EP では、各 GPU が持つトークンを、担当のエキスパートがいる GPU へ送る必要があります。

![4 つの GPU が、トークンを担当のエキスパートの GPU へ送り、計算し、元の GPU へ戻す](/images/a0f5ff21eed405-alltoall.gif)

トークンの色は、そのトークンを処理するエキスパートの色です。送る処理を dispatch、結果を戻す処理を combine と呼びます。どの GPU も、ほかのどの GPU へでも送りうるので、この通信を all-to-all と呼びます。図では、各トークンが 1 つのエキスパートだけを使う場合を描いています。

MoE の仕組みそのものは「[MoE 推論を理解する](https://zenn.dev/tosshi/articles/431977b09a79bd)」で説明しています。

## ノードの中は NVLink、外は EFA

![同じノードの GPU へは NVLink で送る](/images/a0f5ff21eed405-nvlink.png)

p5 のような GPU インスタンスでは、ノードの中の GPU どうしが NVLink でつながっています。同じノードの GPU へは、NVLink を通ります。

![別のノードの GPU へは EFA を通り、複数の経路に散らして送る](/images/a0f5ff21eed405-across-nodes.png)

別のノードの GPU へは、EFA を通ります。この記事で見ていくのは、こちらの道です。

## GPUDirect RDMA: EFA が GPU のメモリを直接読む

![EFA が GPU のメモリからトークンを直接読む](/images/a0f5ff21eed405-gpudirect.png)

EFA は、GPU のメモリにあるトークンを直接読み、相手の GPU のメモリに直接書き込みます。途中で CPU のメモリにコピーしません。この仕組みを GPUDirect RDMA と呼びます。EFA が GPU のメモリを読み書きするには、そのメモリを前もって登録しておく必要があります。

GPUDirect RDMA の仕組みは「[GPUDirect RDMA 入門](https://zenn.dev/tosshi/articles/42f0ee03b328a4)」で詳しく説明しています。

## SRD: EFA の送り方

![SRD は 1 つの通信のパケットを複数の経路に散らす](/images/a0f5ff21eed405-srd.png)

EFA は、SRD という方式でパケットを送ります。SRD は、1 つの通信のパケットを複数の経路に散らして送ります。そのため、パケットの届く順番が入れ替わることがあります。SRD の動きは「[AWS EFA と Nitro System の仕組みを理解する](https://zenn.dev/tosshi/articles/0eeb53ca63f8b2)」で説明しています。

## EFA で送る合図を誰が出すか: NVSHMEM と NCCL GIN

トークンの中身は、EFA が GPU のメモリから直接読みます。では、EFA に「これを送って」と頼むのは誰でしょうか。ここは、DeepEP V1 が使う NVSHMEM と、V2 が使う NCCL GIN で違います。

![EFA では、DeepEP V1 は CPU の代理役を通して頼み、V2 は EFA-GDA を選ぶと GPU が自分で頼む](/images/a0f5ff21eed405-v1-v2.png)

DeepEP V1 は、NVSHMEM の上で動きます。NVSHMEM は、GPU のカーネルから、ほかの GPU のメモリへ直接読み書きできるようにするライブラリです。NVSHMEM には、GPU がネットワークカードを直接操作する IBGDA という道があり、DeepEP V1 のノードをまたぐ通信は、この道を使うように書かれています。ただし IBGDA は NVIDIA のネットワークカード向けで、EFA では使えません。そこで awsome-distributed-ai の V1 のベンチマークでは、DeepEP に手直しを加え、NVSHMEM の CPU の代理役のスレッドを通して、libfabric から EFA に頼みます。NVSHMEM は「[NVSHMEM 入門](https://zenn.dev/tosshi/articles/228e4225b659f7)」で説明しています。

DeepEP V2 は、NCCL GIN の上で動きます。GIN は、GPU のカーネルから通信を頼むための、NCCL の中の仕組みです。NVSHMEM が独立したライブラリなのに対して、GIN は NCCL の一部です。GIN が実際に EFA へ頼む方法には、GPU が自分で頼むものと、CPU の代理役を通すものの 2 種類があります。代理役のスレッドそのものは NCCL の中にあります。NCCL のプラグインである aws-ofi-nccl は、代理役を通す方式では EFA への通信の処理を、GPU が自分で頼む方式では送る前の準備を受け持ちます。GPU が自分で頼む方式を、EFA-GDA と呼びます。

EFA-GDA を使うには、対応した版の NCCL、EFA installer が入れる libfabric と aws-ofi-nccl、ホストの EFA のドライバ、gdrdrv をそろえたうえで、設定で選ぶ必要があります。必要な版のドライバが DLAMI に入っていないときは、ホストで EFA installer を実行して入れ替えます。選ばないと、V2 でも CPU の代理役を通す方式になります。必要な版は、参考に挙げた V2 のベンチマークにまとまっています。

## aws-ofi-nccl: 送る前の準備を受け持つ

![aws-ofi-nccl が libfabric とドライバを通して、EFA の中に送信キューを作らせる](/images/a0f5ff21eed405-setup.png)

ここからは、DeepEP V2 で EFA-GDA を選んだ場合を見ていきます。aws-ofi-nccl は、NCCL を EFA につなぐプラグインです。EFA-GDA では、aws-ofi-nccl が送る前の準備を受け持ちます。まず、libfabric に頼み、libfabric が rdma-core とドライバを通して、EFA の中に送信キュー、呼び鈴、カウンタを作らせます。送信キューは依頼を並べる場所、呼び鈴は依頼を書いたことを EFA に知らせる場所です。カウンタは、自分が出した依頼のうち終わった数や、相手から届いた合図の数を数える場所です。この組は、データ用と合図用に分けて作ります。

![送信キューと呼び鈴は libfabric が作り、窓と宛先表は aws-ofi-nccl が用意する](/images/a0f5ff21eed405-owners.png)

次に、送信キューと呼び鈴を GPU から直接触れるように登録します。図の窓がこれにあたります。さらに、GPU のメモリを EFA に登録し、相手と鍵を交換して、宛先表を GPU のメモリに置きます。

## 1 回の送信

![NCCL GIN が窓から送信キューに依頼を書く](/images/a0f5ff21eed405-send.png)

準備が終わると、1 回の送信は次の順に進みます。

1. DeepEP のカーネルが、データと一緒に、届いたことを知らせる合図も送るよう NCCL GIN に頼みます。
2. GPU の上の NCCL GIN が、宛先表を見て、窓から送信キューに依頼を書き、呼び鈴を鳴らします。合図は、合図用の送信キューを通る小さな書き込みです。
3. EFA が GPU のメモリからトークンを読み、SRD で送ります。受け側の EFA が、相手の GPU のメモリに書き込みます。
4. 送り側では、自分の依頼が終わった数のカウンタが進みます。受け側では、合図の数のカウンタが進み、受け側の GPU はそれを見てトークンが届いたことを知ります。

EFA-GDA では、この手順の中に CPU と OS のカーネルは出てきません。ただし、GPU のカーネルを起動するのは CPU です。

## 各層の受け持ち

![転送中に動くのは DeepEP、NCCL GIN、EFA。aws-ofi-nccl と libfabric は準備で働く](/images/a0f5ff21eed405-who-works.png)

DeepEP V2 で EFA-GDA を選んだとき、DeepEP のトークンの転送での分担は次のとおりです。CPU の代理役を通す方式や、NCCL のふつうの集団通信では、aws-ofi-nccl と libfabric も転送中に働きます。

| 層 | 受け持ち | 働くとき |
|---|---|---|
| DeepEP | トークンを宛先ごとにまとめ、送り、集め戻す | 転送中 |
| NCCL GIN | GPU の上で、EFA に依頼を書き、呼び鈴を鳴らす | 転送中 |
| aws-ofi-nccl | NCCL を EFA につなぎ、EFA-GDA の準備をする | 準備 |
| libfabric と rdma-core | EFA を操作するライブラリ。送信キューなどを作る | 準備 |
| ドライバ | OS のカーネルの中で EFA と GPU を動かす | 準備 |
| EFA と SRD | GPU のメモリを直接読み書きし、複数の経路で送る | 転送中 |

## まとめ

EFA-GDA を選んだ DeepEP V2 では、送る準備を aws-ofi-nccl が、送る合図を GPU の上の NCCL GIN が、データを運ぶ仕事を EFA が受け持ちます。
