## はじめに

AWS で大規模な分散学習や HPC を動かすと、ノードの間の通信の待ち時間が全体の速さを決めることがあります。AWS はこの通信のために、EFA（Elastic Fabric Adapter）というネットワークの装置と、その中で動く SRD（Scalable Reliable Datagram）という通信の約束ごとを作りました。この記事では、EFA が何を受け持ち、SRD がなぜ TCP と違う作りになっているのかを、図で順に見ていきます。

:::message alert
この記事は、2020 年の IEEE Micro の論文「[A Cloud-Optimized Transport Protocol for Elastic and Scalable HPC](https://ieeexplore.ieee.org/document/9167399)」（Shalev ほか）と AWS の公開ドキュメントにもとづいています。AWS の内部の実装は公開されておらず、更新も続いているので、いまの実装と違う点があり得ます。
:::

## 全体の地図

![NCCL は aws-ofi-nccl を、MPI は直接 libfabric を通り、EFA provider と rdma-core を経て Nitro カードの EFA デバイスに届く。efa.ko はキューの作成やメモリの登録を受け持ち、データはカーネルを通らずにカードへ渡る](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/0eeb53ca63f8b2/zenn/articles/0eeb53ca63f8b2/stack.png)

libfabric は高性能な通信のための共通の API で、EFA provider はその中で EFA 向けの処理を実装する部分です。EFA を使う通信は、上から次の層を通ります。NCCL は aws-ofi-nccl を通り、Open MPI や Intel MPI は libfabric を直接使います。論文によると、libfabric を使わずに、装置をそのまま見せる user-space driver の上に作る経路もあります。

| 層 | すること | 入っている場所 |
| --- | --- | --- |
| NCCL、MPI | 集合通信と 1 対 1 の通信をアプリに提供する | アプリのライブラリ |
| aws-ofi-nccl | NCCL の通信の口を libfabric につなぐ | [aws-ofi-nccl](https://github.com/aws/aws-ofi-nccl/tree/13328683bd65) |
| libfabric の EFA provider | efa fabric の場合、SRD の上で、順番、大きなメッセージ、同じノードの中の通信を受け持つ | [libfabric](https://github.com/ofiwg/libfabric/tree/7a494bde871a/prov/efa) |
| rdma-core（libibverbs と efa） | キューへの書き込みと doorbell（装置への合図）を、ユーザー空間から直接行う | [rdma-core](https://github.com/linux-rdma/rdma-core/tree/bd3282a1cf10/providers/efa) |
| efa.ko | キューの作成やメモリの登録といった準備を受け持つ | [amzn-drivers](https://github.com/amzn/amzn-drivers/tree/8a8b6f29ba67/kernel/linux/efa) |
| Nitro カードの EFA デバイス | SRD を動かし、パケットを複数の経路に分散し、再送と輻輳の制御をする | ハードウェア |

データの経路でカーネルを通らない作り（OS バイパス）なので、送るたびのシステムコールを避けられ、カーネルを経由するコピーも減ります。各層の中身は、最後の「EFA ソフトウェアスタックの実装の詳細」で説明します。

## Nitro: I/O をカードに移す

![EC2 インスタンスの CPU や GPU はワークロードを動かし、ネットワークとストレージは PCIe でつながった Nitro カードが受け持つ。ゲストのドライバは SR-IOV の仮想機能でカードに直接つながり、ホストの Nitro Hypervisor は CPU とメモリだけを受け持つ](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/0eeb53ca63f8b2/zenn/articles/0eeb53ca63f8b2/nitro.png)

[Nitro System](https://aws.amazon.com/ec2/nitro/) は、ネットワーク、ストレージ、セキュリティの処理を、ホストの CPU から専用の Nitro カードに移す仕組みです。ゲストの OS は、SR-IOV（1 つの装置を複数の仮想的な装置に見せる PCIe の仕組み）で、カードの仮想機能に直接つながります。Nitro Hypervisor は CPU とメモリの割り当てだけを受け持つので、ホストの資源のほとんどをワークロードに使えます。EFA は、ネットワークを受け持つ Card for VPC の機能の 1 つです（[Security Design of the AWS Nitro System](https://docs.aws.amazon.com/whitepapers/latest/security-design-of-aws-nitro-system/security-design-of-aws-nitro-system.html)）。

## TCP がクラウドのネットワークで苦しむ理由

AWS のデータセンターは、普通の Ethernet スイッチで組んだ Folded Clos 型のネットワークで、2 台のサーバーの間に何本もの経路があります（図は 2 段 4 本に簡略化しています）。スイッチは ECMP で、フローごとに宛先やポート番号のハッシュから経路を 1 本に決めます。TCP はこの方式で順番を保てますが、大きなフローどうしが同じ経路に重なると、そこだけが詰まります。

![失ったパケットの回復に再送のタイマーが要る場合、TCP はタイマーが切れるまで待って同じ経路で送り直す。SRD はすぐに送り直し、元の経路が使えなければ別の経路に回す。論文の TCP の実験では、再送のタイマーの最小値は 50 ms だった](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/0eeb53ca63f8b2/zenn/articles/0eeb53ca63f8b2/loss-recovery.png)

論文によると、データセンターの TCP では、混雑やリンクの故障のときの外れ値が 50 ms から数秒に達し、空いた別の経路があっても避けられません。その主な原因は、失ったパケットの再送です。論文の実験では、再送のタイマーの最小値が 50 ms で、50 ms を超える遅れは再送によるものでした。論文は、検討した RoCEv2 についても、パケットを落とさないために PFC（スイッチが送り手を一時停止させる仕組み）が必要で、PFC は大規模なネットワークでは停止の連鎖やデッドロックの問題を起こすこと、PFC を使っても ECMP のハッシュの衝突は残ることを、採らなかった理由に挙げています（[Shalev ほか](https://ieeexplore.ieee.org/document/9167399)）。

## SRD: 1 つの通信を複数の経路に分散する

![A と B の間にはスパインとリーフのスイッチを通る 4 本の経路があり、SRD は 1 つの通信のパケットを 4 本に分散する](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/0eeb53ca63f8b2/zenn/articles/0eeb53ca63f8b2/srd-multipath.gif)

![SRD は 1 つの通信のパケットを 4 本に分散する。TCP 側は、ECMP のハッシュで大きなフローが同じスパインに重なった場合で、流れが増えるとそのスパインの手前に列ができ、SRD は流れ続ける](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/0eeb53ca63f8b2/zenn/articles/0eeb53ca63f8b2/srd-vs-tcp.gif)

SRD は、1 つの通信のパケットを、混んだ経路を避けながら、できるだけ多くの経路に分散して送ります（packet spraying）。1 本の経路が詰まっても、他の経路で流れ続けます。

![送り手の Nitro カードがパケットのカプセル化のヘッダーを変え、スイッチは普段どおりハッシュで経路を選ぶので、パケットが別々のスパインを通る。経路ごとの往復時間を見て遅い経路を避け、壊れた経路からは再送を別の経路に回し、接続ごとに送る速さを抑える](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/0eeb53ca63f8b2/zenn/articles/0eeb53ca63f8b2/srd-paths.png)

スイッチは普通の ECMP のままです。送り手の Nitro カードがパケットのカプセル化のヘッダーを変えることで、スイッチが選ぶ経路を送り手の側から決めます。カードは経路ごとの往復時間（RTT）を集めて混んだ経路を避け、経路が壊れたときは、ネットワーク全体の経路の更新を待たずに再送のパケットを別の経路に回します。論文によると、ネットワーク全体の経路の更新がそろうまでには、SRD が再送を別の経路に回すより 2〜3 桁長い時間がかかります。SRD を Nitro カードに置いたのは、ホストの OS やハイパーバイザーが入れる揺らぎを避け、失ったパケットの再送と、混雑したときに送る速さを抑える輻輳制御を、すぐに行うためです。

複数の経路に分散するだけでは、多くの送り手が 1 台の受け手に集まる incast は解消しません。論文は、分散することでかえって受け手の手前に同時に届き、incast を悪くすることもあると書いています。そこで SRD は、ACK の届く間隔と RTT の変化から送れる速さを見積もり、接続ごとの送る速さと、届いていないデータの量を抑えます。大半の経路で RTT が伸びたとき、または見積もった速さが送っている速さを下回ったときに、接続全体が混んでいると判断します。論文の言葉では「BBR に少し似た」（somewhat similar to BBR）方式に、複数の経路の考慮を加えたものです。

## 順番は受け側の上の層で並べ直す

![4 本の経路は速さがばらばらなので B には順番が崩れて届き、efa fabric の場合は EFA provider が送り手ごとの窓で番号順に並べ直してからアプリに渡す](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/0eeb53ca63f8b2/zenn/articles/0eeb53ca63f8b2/srd-reorder.gif)

経路ごとに遅れが違うので、パケットは順番が崩れて届きます。論文は、ネットワークカードで順番をそろえるとメモリの帯域やバッファの大きさに縛られ、1 つの欠けたパケットのために無関係なパケットまで待たせることになると説明しています。そこで **Nitro カードの SRD は、失ったパケットを再送して届けることを受け持ち、届いた順のまま上の層に渡します**。順番が要るかどうかは上の層が知っているので、並べ直しは上の層が行います。たとえば MPI では、同じタグのメッセージだけが順番を守れば足ります。libfabric の efa fabric を使う場合は、EFA provider が送り手ごとに並べ直しの窓を持ち、その大きさは `FI_EFA_RECVWIN_SIZE` で決まります。efa-direct fabric を使う場合はこの並べ直しが無く、送った順に届く保証（SAS）もありません（[fi_efa(7)](https://ofiwg.github.io/libfabric/main/man/fi_efa.7.html)）。

## 性能: 論文の 2 つの実験

![48 本のフローを 1 本の 100 Gb/s のリンクに集めた実験では、最大の完了時間が SRD はほぼ理想どおりで TCP は理想の 3〜20 倍。ラックをまたぐ 8 組の実験では、SRD の中央値は理想の 15% 増し、TCP の平均は 50% 増し、TCP の裾は 10〜100 倍で、SRD の最大は TCP の平均より短い](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/0eeb53ca63f8b2/zenn/articles/0eeb53ca63f8b2/results.png)

論文は、同じサーバーの組を使い、EFA を通した SRD と標準設定の TCP のノード間の通信を比べています（[Shalev ほか](https://ieeexplore.ieee.org/document/9167399)）。OS バイパスによる差は分析しておらず、混雑したときの転送方式の振る舞いの差に比べて小さいと述べています。

上の実験では、4 台のサーバーが 12 プロセスずつ、計 48 本のフローを 1 台の受け手に同時に送り始め、転送の大きさを変えて最大の完了時間を測ります。理想は、受け手の 100 Gb/s のリンクを 48 本で均等に分けたときの完了時間です。下の実験では、1 つのラックの 8 台と別のラックの 8 台を 1 対 1 に組み、各サーバーの 16 プロセスが相手と別々のフローで通信します。1 台の受け手に送るのは 1 台だけなので、下りのリンクは混みません。上りのリンクの利用率は 50% で、経路が均等に分かれれば混雑しない条件です。図の値は 8 台のうち 1 台の送り手のフローで、他の送り手も同様だと論文は書いています。図の下段は、論文の本文にある SRD の中央値と、TCP の平均と裾の値で、同じ統計量どうしの比較ではありません。SRD の最大の完了時間は、TCP の平均より短くなりました。

## 使うときの決まり

| 決まり | 中身 |
| --- | --- |
| 同じ Availability Zone の中だけ | EFA のトラフィックは AZ と VPC をまたげず、ルーティングもされない。同じ口の ENA の IP 通信は普段どおり使える（[EFA](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/efa.html)） |
| セキュリティグループで自分自身を許可する | EFA には、同じセキュリティグループとのすべての受信と送信を許可するルールが必須。無いとインスタンスの間の EFA の通信が止まる（[Get started with EFA](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/efa-start.html)） |
| cluster placement group を勧める | 1 つの AZ の中で、遅延の小さいまとまりにインスタンスを置ける（[Get started with EFA](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/efa-start.html)） |
| 口の種類を選ぶ | EFA と ENA の両方を作る口と、EFA だけを作る口がある（[EFA](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/efa.html)） |

## SRD は EFA の外でも使われている

[ENA Express](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ena-express.html) は、普通の TCP や UDP の通信に、アプリを変えずに SRD を使う機能です。同じ AZ の対応するインスタンスの間で効き、そうでない相手とは自動で普段の通信に戻ります。

## InfiniBand との違い

ここでは、AWS の共有の Ethernet の上の EFA と SRD を、HPC 専用に作った InfiniBand のネットワークと比べます。順番と接続の数は、InfiniBand の RC（信頼できる接続）と比べます（[Shalev ほか](https://ieeexplore.ieee.org/document/9167399)、[OSU、HOTI 2019](https://pdfs.semanticscholar.org/07f4/0e3f05b00225e51f5b8abcdf5260269d2df9.pdf)）。

| 観点 | EFA と SRD | InfiniBand（専用のネットワーク、RC） |
| --- | --- | --- |
| ネットワーク | 多くの利用者が共有する Clos 型の Ethernet | 計算ノードのために作った専用のネットワーク |
| 経路と順番 | パケットを複数の経路に分散し、順番は上の層でそろえる | 接続ごとに届いた順番を守る |
| 接続の数 | 1 つの SRD の QP（送受信のキューの組）で多くの相手と通信でき、全対全の接続に要る QP の数が少ない | 相手ごとに QP が要る |

論文は、InfiniBand のような専用のネットワークをクラウドで使うと、費用がかかり、規模を広げにくく、新しい装置への更新も遅れると述べています。

:::::details EFA ソフトウェアスタックの実装の詳細

![キューの作成やメモリの登録が要るときは、libibverbs から /dev/infiniband/uverbs を通って efa.ko を呼ぶ。準備済みのキューを使うデータの転送では、ユーザー空間がキューに書き、doorbell を鳴らし、装置が登録済みのメモリから DMA で読み、完了をユーザー空間で受け取る](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/0eeb53ca63f8b2/zenn/articles/0eeb53ca63f8b2/control-data-path.png)

EFA の通信には、制御の経路とデータの経路があります。制御の経路は、キューやメモリの登録が必要になったときに通ります。制御の経路では、libibverbs がカーネルの efa.ko を呼び、キューの作成、メモリの登録（ページを固定し、装置が使う鍵を受け取る）、キューと doorbell のユーザー空間への割り当て（mmap）を行います。データの経路では、ユーザー空間がそのキューに直接書き込み、doorbell のレジスタに書いて装置に知らせ、完了もユーザー空間で受け取ります。データの経路にシステムコールが入らないことが、OS バイパスの中身です。

![SRD は届くことを保証するが順番を守らない小さなデータグラムで、libfabric の EFA provider の efa fabric がその上に、送り手ごとの並べ直し、大きなメッセージのプロトコル、同じノードの中の shm、GPU や Trainium のメモリへの直接の転送を足す](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/0eeb53ca63f8b2/zenn/articles/0eeb53ca63f8b2/efa-provider.png)

SRD は、届くことを保証するが順番を守らない、小さなデータグラムの通信です。メッセージを分割しないために、1 つのメッセージの大きさを制限しています（論文）。論文によると、EFA のユーザー空間のソフトウェアには、装置の振る舞いをそのまま見せる「user-space driver」と、その上でパケットの並べ直し、メッセージの分割、MPI のタグの照合を行う libfabric の provider の 2 種類があります。libfabric の EFA provider の efa fabric は次のものを足し、最大メッセージサイズの制限を無くします（[fi_efa(7)](https://ofiwg.github.io/libfabric/main/man/fi_efa.7.html)）。

- 並べ直し: 送り手ごとの窓（`FI_EFA_RECVWIN_SIZE`）でメッセージの順番をそろえる
- 大きなメッセージ: 1 パケットに収まるものは eager、それより大きいものは medium、さらに大きいものは受け手の準備を待つ CTS 方式で送る（環境変数 `FI_EFA_INTER_MAX_MEDIUM_MESSAGE_SIZE` の説明）
- 同じノードの中: NIC を使わず、shm provider で共有メモリを使う
- GPU や Trainium、Inferentia のメモリ: HMEM として、装置がアクセラレータのメモリに直接 DMA する。AWS Neuron のバッファでは peer to peer の転送が必須（`FI_HMEM` の説明）

libfabric には、こうしたプロトコルを使わずにデータの経路を装置に直接渡す `efa-direct` という fabric もあります。できることが減り、MSG の最大の大きさは EFA デバイスの MTU（約 8 KiB）になります（[fi_efa(7)](https://ofiwg.github.io/libfabric/main/man/fi_efa.7.html)）。

カーネルのドライバ efa.ko の主な部品は次のとおりです（[amzn-drivers](https://github.com/amzn/amzn-drivers/tree/8a8b6f29ba67/kernel/linux/efa)）。

| 部品 | 主なファイル | 役割 |
| --- | --- | --- |
| コア | `efa_main.c`、`efa.h` | PCIe の装置を見つけて登録する |
| Verbs の実装 | `efa_verbs.c`、`efa_data_verbs.c` | キュー、完了キュー、メモリの登録などの Verbs の操作を EFA 向けに実装する |
| 管理の通信 | `efa_com.c`、`efa_com_cmd.c` | Admin Queue で装置に管理のコマンドを送る |
| 装置の定義 | `efa_regs_defs.h`、`efa_io_defs.h`、`efa-abi.h` | レジスタ、データの経路の形式、ユーザー空間との約束（ABI） |
| アクセラレータ | `efa_p2p.c`、`efa_nvmem_*.c`、`efa_neuronmem.c` | NVIDIA の GPU と AWS Neuron のメモリへの直接の転送 |

:::::

::::details インスタンスから EFA を確かめる

EC2 インスタンスの中で `lspci` を実行すると、Nitro カードが提供する EFA が PCIe の装置として見えます。次の出力は実行例で、実行したインスタンスの種類は記録していません。

```
# 実際に実行した例
lspci | grep -i "Amazon.*Elastic Fabric Adapter"
00:1a.0 Ethernet controller: Amazon.com, Inc. Elastic Fabric Adapter (EFA)
```

::::

## まとめ

EFA は、Nitro カードの SRD でパケットを複数の経路に分散し、再送と輻輳の制御まで受け持ち、順番は libfabric の EFA provider（efa fabric の場合）などの上の層でそろえることで、共有の Ethernet の上で待ち時間の揺れを小さくしています。
