# はじめに

NemotronH は、Mamba2、Mixture of Experts（MoE）、Attention の 3 種類の層を組み合わせて積んだハイブリッドな言語モデルです。この記事では、NemotronH の 30B 版（[nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-BF16](https://huggingface.co/nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-BF16)）を、vLLM の Neuron plugin に組み込んで AWS Trainium2 上で動かした方法をまとめます。

最初に、モデルを plugin の決まりごとに沿って実装し、正しく動くことを確かめました。次に NKI（Trainium 向けのカーネル記述言語）で重い部分を書き直し、最後に複数のリクエストを同時に処理できるようにしました。測った環境は trn2.3xlarge です。Trainium2 のチップ 1 個に物理コアが 8 個あり、2 個ずつ束ねた 4 個の論理コア（LNC=2 の設定）に、モデルを 4 分割するテンソル並列（TP=4）で載せています。結果は次のとおりです。

| 項目 | NKI 最適化なし | NKI + Serving 最適化 |
|---|---|---|
| 1 トークンの生成時間（1 リクエスト） | 72.5 ms | 9.2 ms |
| プロンプトの読み込み速度 | 約 800 トークン/秒 | 約 2,600 トークン/秒 |
| 8 リクエスト同時の生成速度 | 非対応 | 合計 216 トークン/秒 |
| 事実・計算・長文の確認問題 12 問 | 12/12 | 12/12（12 問を一度に投入しても 12/12） |

コードは vLLM Neuron plugin のフォーク [littlemex/vllm-neuron の release-0.24.0.1.1.0 ブランチ](https://github.com/littlemex/vllm-neuron/tree/fdc980267b8ecd247d84d959658adaceb5c47a18/vllm_neuron/model/nemotron_h)にあります。plugin はベータ版なので、ここで触れる内部のインタフェースは今後変わる可能性があります。

# 全体像

![vLLM は変えず、plugin の枠にモデルを足す](/images/162e5225ba1c9b-overview.png)

vLLM の Neuron plugin は、vLLM 本体には手を入れません。vLLM の platform plugin という仕組みを使って、外から部品を差し替えます。API サーバー、リクエスト管理、KV キャッシュのブロック管理といった vLLM の中核はそのまま動きます。plugin が差し替えるのは、スケジューラと、計算グラフを Trainium 用の実行形式（NEFF）にコンパイルして動かす ModelRunner です。

NemotronH を足すために新しく作ったのは、`vllm_neuron/model/nemotron_h/` のモデル一式とそのテストです。plugin にもともとあるファイルで変更したのは、モデルを登録する `vllm_neuron/model/registry.py` の 2 行（import と、登録の一覧への 1 行）だけで、runner やスケジューラ、KV キャッシュの処理には手を入れていません。モデル一式には、plugin が求める 5 つのメソッド（次の節で説明します）を実装する本体、リクエストごとの Mamba の状態を置く状態プール、そして NKI カーネル 4 本が入っています。

3 者がどう連携するかを、起動時と毎ステップに分けて見ます。図の 3 本の帯が vLLM、plugin、自分で書くモデル（BYOM、Bring Your Own Model）で、番号は呼ばれる順番です。

![起動時は、plugin が自前のモデルを組み立て、KV キャッシュを結線する](/images/162e5225ba1c9b-relations-startup.png)

起動時は、まず vLLM が plugin を読み込み（1）、plugin がワーカーとスケジューラを Trainium 向けに差し替えます（2）。そのあと plugin の ModelRunner が、モデルのメソッドを順に呼びます。`from_configs` でモデルを組み立て（3）、`load_weights` で重みを 4 つのランクに分けて読み込みます（4）。続いて `get_kv_spec` で、どの層が KV キャッシュを使うかを問い合わせます（5）。plugin は空いているメモリから KV キャッシュの量を決めて確保し（6）、`bind_kv_cache` でモデルに渡します（7）。最後に、`forward` をあらかじめ決めた入力の長さごとに 1 回ずつ流して、Trainium で動く形（NEFF）にコンパイルします（8）。モデルの側から vLLM や plugin を呼ぶことはありません。KV キャッシュについては、各リクエストにどのブロックを割り当てるかを vLLM が決め、メモリそのものは plugin が持ち、モデルはそこを読み書きするだけ、という分担です。

![毎ステップは、vLLM が何を計算するかを決め、自前のモデルが計算する](/images/162e5225ba1c9b-relations-step.png)

毎ステップでは、vLLM がリクエストを受け取り、各リクエストに KV のブロックを割り当てます（1）。Neuron のスケジューラは、このステップで 1 リクエストの prefill をするか、実行中の全リクエストの decode をするかを決めます（2）。plugin はトークン、位置、そして各リクエストのブロック番号の表を入力にまとめ（3）、モデルの `forward` を呼びます（4）。モデルは、リクエストごとの Mamba の状態の行を探し、52 層を計算して、KV キャッシュに書き込みます。plugin がその出力から次のトークンをデバイス上で選び（5）、vLLM が結果を返します（6）。毎ステップモデルに渡るのは、トークンの番号、位置、層ごとのメタデータ（ブロックの表と、各トークンを KV のどこに書くかの対応表）だけです。

# plugin の枠にどう入れたか

![契約は 5 つ。難所は KV キャッシュを持つ層の指定と状態の置き場](/images/162e5225ba1c9b-contract.png)

呼ばれる順番は前の図のとおりで、表にすると、モデル側が書くことと plugin が受け持つことは上のように分かれます。

ハイブリッドモデルで悩ましいのは、KV キャッシュを持つ層の指定と、Mamba の状態の置き場です。NemotronH の 52 層のうち、KV キャッシュを持つのは Attention の 6 層だけです。そこで `get_kv_spec` は Attention の 6 層だけを返し、Mamba2 と MoE の層は含めません。こうすると ModelRunner の KV 管理には何も足さずに済みます。

一方、Mamba2 の層も、リクエストごとに状態を次のステップへ持ち越します。持ち越すのは、直前 3 トークン分の畳み込みの入力と、状態空間モデル（SSM）の内部状態の 2 つです。これらを TP の 1 ランクのデバイスメモリのどこに置いているかを図にしました。

![1 ランクのデバイスメモリには、重み、plugin が持つ KV キャッシュ、モデルが持つ Mamba の状態プールがある](/images/162e5225ba1c9b-memory.png)

デバイスメモリには 3 種類のデータがあります。

- 重み：約 15 GB で、`load_weights` が起動時に 1 回だけ読み込みます。
- KV キャッシュ：Attention の 6 層だけが使います。KV はトークンが増えるたびに増えるので、32 トークンずつのブロックに区切って管理します。どのリクエストにどのブロックを渡すかは vLLM が決め、メモリの確保は plugin が行います。モデルは、各トークンの KV を指定された場所に書き込むだけです。図では、リクエスト A がブロック 7、8、9 を、リクエスト B がブロック 41、42 を持っています。
- Mamba の状態：KV キャッシュとは違い、文章がどれだけ長くなっても 1 リクエストあたりの大きさが変わりません。そのためブロックに区切る必要がなく、plugin の KV の仕組みには乗せていません。plugin はこの状態の存在を知らないので、モデルが自分のバッファとして持ちます。

Mamba の状態は、23 層それぞれに「1 リクエスト 1 行」の表（状態プール）として置いています。1 行には、SSM の状態（16 ヘッド × 64 × 128 の値）と、畳み込み用の直前 3 トークン分の入力が入ります。行数は、最大同時数 $N$ に対して $2N+1$ で、$N = 8$ なら全層で約 200 MB です。どの行がどのリクエストのものかは、行ごとに記録した「持ち主」で区別します。持ち主には、そのリクエストが持つ最初の KV ブロックの番号を使います（図では A が 7、B が 41）。モデルは毎ステップ、計算グラフの中で自分の行を探し、その行を読み、計算した新しい状態で上書きします。バッファへの書き込みはグラフの実行が終わっても残るので、次のステップは更新された状態から始まります。行の探し方の詳しい仕組みは、後の「サービング側の工夫」で説明します。

:::details 状態をモデルの中にどう持っているか
![Mamba2 の層は、重みとは別に、register_buffer で登録したバッファに 1 リクエスト 1 行の状態を持つ。毎ステップ、自分の行を探して読み、計算した新しい状態を同じ行に書き戻し、その値はデバイスの上に残って次のステップで使われる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/162e5225ba1c9b/zenn/articles/162e5225ba1c9b/state-buffer.png)

PyTorch の機能です。nn.Module の `register_buffer` で、Mamba2 の層ごとに `ssm_state` と `conv_state` という 2 つのテンソルをモデルに登録しています（[model_bf16.py](https://github.com/littlemex/vllm-neuron/blob/fdc980267b8ecd247d84d959658adaceb5c47a18/vllm_neuron/model/nemotron_h/model_bf16.py#L645-L656)）。バッファは重みと同じようにモデルと一緒にデバイスへ載りますが、学習の対象にはなりません。`persistent=False` を付けているので、チェックポイントにも保存されません。

テンソルの先頭の次元が行で、1 行が 1 リクエストの状態です。毎ステップ、自分の行の番号で読み出し（`index_select`）、計算した新しい状態を同じ行にその場で書き戻します（`index_put_`、[書き戻す行](https://github.com/littlemex/vllm-neuron/blob/fdc980267b8ecd247d84d959658adaceb5c47a18/vllm_neuron/model/nemotron_h/model_bf16.py#L938)）。どの行が誰のものかも、同じく `register_buffer` で持つ `state_owner` に記録しています。
:::

# NemotronH 固有の部品をどう作ったか

![52 層は 3 種類。Mamba2 と MoE を Trainium で動く形に書き直す](/images/162e5225ba1c9b-layers.png)

52 層は `hybrid_override_pattern` という設定で、Mamba2（23 層）、MoE（23 層）、Attention（6 層）のどれかに振り分けられます。図の帯がその並びです。Trainium のコンパイラは、長い逐次ループと、データの値によって読み書きする場所が変わる処理が苦手です。そのため Mamba2 と MoE は、同じ計算を別の形に書き直しました。

Mamba2 の prefill（プロンプトの読み込み）は、本来は 1 トークンずつ状態を更新する逐次ループで、そのままではコンパイルできません。そこで、128 トークンの塊ごとの行列演算と、塊から塊への状態の受け渡しに書き直しました（chunked SSD）。

::::details chunked SSD の詳細
![Mamba2 の prefill は、逐次・1 枚の行列・chunked SSD の 3 通りで同じ値を計算できる。出荷しているのは chunked SSD](/images/162e5225ba1c9b-k-prefill-ways.png)

Mamba2 の prefill は、同じ値を 3 通りの形で計算できます。1 つ目は 1 トークンずつ状態を更新する逐次の形で、512 トークンなら前の結果に依存する 512 回の計算が一列に並びます。Trainium のコンパイラはこの長いループを扱えず、コンパイルに通りませんでした。

**何を計算しているか**

![バケツは毎回少し漏れ、入力を注ぎ、水位を読む。行列の各行は、それまでの入力がどれだけ残っているかで、階段の形になる。斜線のマスは 1 つ目の塊の入力が 2 つ目の塊に残っている分で、バケツ全体が一緒に漏れるので、水位 1 つを渡せば済む](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/162e5225ba1c9b/zenn/articles/162e5225ba1c9b/bucket.gif)

Mamba2 の状態は、少しずつ水が漏れるバケツのようなものです。トークンが来るたびに、少し漏れ、新しい入力を注ぎ、水位を出力として読みます。出力には、それまでに注いだ入力の残りだけが入るので、行ごとに 1 マスずつ増えて階段の形になります。この階段を全部作って 1 回の行列積で計算するのが 2 つ目の形です。ループはなくなりますが、マスの数はトークン数の 2 乗で、128k トークンでは約 170 億マスになり、作れません。

**塊をまたぐマスを作らずに済む理由**

塊をまたぐマス（図では斜線のマス）は、1 つ目の塊の入力が、2 つ目の塊の出力に残っている分です。1 つ目の塊が終わったときのバケツ $h_3$ には、その残りがすべて入っています。2 つ目の塊で掛かる減衰は、どの入力の水にも同じなので、y4 の行は $h_3$ を 1 回、y5 の行は 2 回漏らしたものになります。だから塊をまたぐマスは作らず、$h_3$ を次の塊に渡せば同じ結果になります。これが 3 つ目の chunked SSD です。

![h3 = 8 の中には x1 の分が 4、x2 の分が 3、x3 の分が 1 入っている。塊をまたぐ 9 マスは、どれも h3 の中のその入力の分に、2 つ目の塊の減衰 a4、a5、a6 を順に掛けたもので、行を足すと h3 に同じ減衰を掛けた値になる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/162e5225ba1c9b/zenn/articles/162e5225ba1c9b/h3-block.gif)

数で見ると次のとおりです（入力は 16、6、1、減衰はすべて 0.5、入力と読み出しの係数は 1）。$h_3 = 8$ の中には、x1 の分が 4、x2 の分が 3、x3 の分が 1 入っています。たとえば y5 の x1 のマスは $4 \times a_4 \times a_5 = 1$ で、y5 の行を足すと $h_3 \times a_4 \times a_5 = 2$ になります。

**1 枚の行列との比べ方**

![左は 12 トークン分の下三角をすべて計算し、右は塊ごとの三角形だけを計算して状態 h を次の塊へ渡す](/images/162e5225ba1c9b-chunked-ssd.gif)

左の 1 枚の行列は、12 トークン分の下三角をすべて計算します。右の chunked SSD は、4 トークンの塊ごとに三角形だけを計算し、塊が終わるたびに状態 $h$ を次の塊に渡します。出力は同じで、計算するマスは 78 個から 30 個に減ります。実際の塊は 128 トークンなので、作るマスはトークン数 $\times$ 128 程度で済みます。

:::details Mamba2 の減衰とマルコフ性
Mamba2 の状態の更新は、次の 1 行だけです。

$$
h_t = a_t \, h_{t-1} + b_t \, x_t
$$

減衰は $a_t$ です。0 と 1 の間の数で（$a_t = \exp(\Delta_t A)$、$A$ は負、$\Delta_t$ はトークンごとの時間刻み）、毎ステップ前の状態に掛けます。バケツの「少し漏れる」にあたり、古い入力ほど何回も掛けられて小さくなります。

マルコフ性は、次の状態 $h_t$ を決めるのが、今の状態 $h_{t-1}$ と今の入力 $x_t$ だけ、という性質です。過去の入力の影響はすべて $h_{t-1}$ に入っているので、それより前の入力を 1 つずつ覚えておく必要はありません。chunked SSD が塊の終わりの状態 1 つを渡せば済むのは、この性質のおかげです。
:::

:::details 式で確かめる
状態が 1 つの数だけの小さな例で、トークン $t$ ごとに減衰 $a_t$、入力の係数 $b_t$、出力の係数 $c_t$ が決まっているとします。

$$
h_t = a_t \, h_{t-1} + b_t \, x_t, \qquad y_t = c_t \, h_t
$$

![1 枚の行列 M の各マスには、トークン j の入力がトークン i の出力に届く割合が入る。塊をまたぐ部分は、塊の終わりの状態 h3 を通るので作らずに済む](/images/162e5225ba1c9b-k-ssd-matrix.png)

この漸化式を展開すると、出力は入力の重み付きの和になります。たとえば次のとおりです。

$$
y_3 = c_3 a_3 a_2 b_1 \, x_1 + c_3 a_3 b_2 \, x_2 + c_3 b_3 \, x_3
$$

重みを、行を出力 $y_i$、列を入力 $x_j$ にして並べたのが図の行列 $M$ です。マス $(i, j)$ は「トークン $j$ の入力が、トークン $i$ の出力にどれだけ届くか」で、未来のトークンは過去の出力に影響しないので $j > i$ は 0 です。

$$
M_{ij} = c_i \left( \prod_{k=j+1}^{i} a_k \right) b_j \quad (j \le i), \qquad M_{ij} = 0 \quad (j > i)
$$

塊をまたぐマスのうち $y_4$ に届く分を $x_1$ から $x_3$ まで足すと、括弧の中が 1 つ目の塊の終わりの状態 $h_3$ になります。

$$
c_4 a_4 \left( a_3 a_2 b_1 \, x_1 + a_3 b_2 \, x_2 + b_3 \, x_3 \right) = c_4 a_4 \, h_3
$$

実際の Mamba2 では、$a_t = \exp(\Delta_t A)$、$b_t = \Delta_t B_t$、$c_t = C_t$ に当たります。$x$ と $h$ がヘッドごとのベクトルや行列になるだけで、構造は同じです。
:::

**実機での動き**

これで 128k トークンの設定でも動き、長文の中の事実を答えさせる問題は 87.7k トークンまで通りました（112k では 2 問中 1 問が外れました）。長いプロンプトは、vLLM の設定で 512 トークンずつのセグメントに分けて読み込みます。セグメントの区切りでは、SSM の状態と、畳み込み用の直前 3 トークン分の入力を次のセグメントへ引き継ぎ、最初のセグメントではこの引き継ぎ分を 0 にします。この切り替えは Python の分岐ではなく、「すでに読んだトークン数が 0 かどうか」で 0 か 1 をかける計算で書いてあるので、1 つのコンパイル済みグラフがどのセグメントにも使えます。

最後のセグメントは、コンパイル済みグラフの長さに合わせて末尾に詰め物のトークンが足されます。詰め物のトークンでは時間刻み $\Delta_t$ を 0 にします。$\Delta_t = 0$ だと $a_t = 1$、$b_t = 0$ になるので、状態は変わりません。畳み込み用に引き継ぐ入力も、詰め物ではなく最後の本物のトークンから取ります。3 つの形が同じ値を出すこと、セグメントに分けても一度に計算しても同じになることは、畳み込みの引き継ぎと詰め物の扱いも含めて CPU 上のテストで確かめています。
::::

MoE は、128 個の専門家から各トークンが 6 個を選び、常に使う 1 個（共有専門家）を足す形です。活性化関数は ReLU の 2 乗で、このチェックポイントの設定には、専門家の入力を低い次元に落とす（latent の）射影はありません。

課題は、専門家を選ぶルーターでした。ふつうの書き方では、`torch.topk` で上位 6 個の専門家の番号を求め、その番号を使って表の中の場所を取り出したり書き込んだりします（`gather` と `scatter`）。読み書きするメモリの場所が、計算の途中で出た番号によって毎回変わる処理です。Trainium はこれを、メモリを番号で間接的に読み書きする仕組み（DGE）で実行します。ところが MoE の層を 4 つ以上重ねると、neuronx-cc のコンパイル結果が範囲の外のメモリを読みに行き、実行の準備の段階で止まりました（3 層までは動き、Mamba2 や Attention だけを同じ深さに重ねても動きました。[model_bf16.py](https://github.com/littlemex/vllm-neuron/blob/fdc980267b8ecd247d84d959658adaceb5c47a18/vllm_neuron/model/nemotron_h/model_bf16.py#L509-L528)）。

そこで、番号で場所を選ぶ処理をやめ、128 個すべての専門家に同じ計算をする形に書き直しました。「一番大きい値を探し、その専門家に印を付け、その値を大きく減らす」を 6 回繰り返すと、選んだ 6 個の位置が 1、それ以外が 0 の表ができます（[ops.py](https://github.com/littlemex/vllm-neuron/blob/fdc980267b8ecd247d84d959658adaceb5c47a18/vllm_neuron/model/nemotron_h/ops.py#L27-L50)）。使うのは最大値と比較と掛け算だけなので、読み書きする場所は値によって変わりません。選ばれる専門家は `torch.topk` と同じで、同じ値のときに小さい番号を選ぶ決まりも同じなので、出力は変わりません。

:::details ルーターの詳細
![MoE のルーターは、最大値を探して印を付け、その専門家を大きく減点する、を 6 回繰り返して選ぶ](/images/162e5225ba1c9b-k-router.png)

ルーターは、トークンごとに 128 個の専門家のスコア（シグモイドを通した値に補正のバイアスを足したもの）から、上位 6 個を選びます。素直に書くと「上位 6 個の番号を求めて、その番号の場所に重みを書き込む」処理になります。この、値によって読み書きする場所が変わる処理（gather や scatter）を使うと、MoE 層を何層も重ねた構成で、実行時にメモリの範囲外アクセスのエラーが出ました。

そこで、どのトークンでも同じ手順になる形に書き直しました。図は分かりやすさのために 8 個から 2 個を選ぶ例です。まず全専門家のスコアの最大値を求めます。最大値と同じスコアの専門家が複数あるときは、番号の小さい方を 1 つ選び、その位置だけ 1、ほかは 0 の印を作ります。次に、選んだ専門家のスコアを大きく引いて、二度と選ばれないようにします。これを 6 回繰り返し、6 回分の印を足すと、選ばれた 6 個の位置だけが 1 の表ができます。

専門家にかける重みは、この表にシグモイドを通した元のスコア（補正のバイアスを足す前の値）をかけ、6 個の合計が 1 になるように割ってから、2.5 倍したものです。どの計算も、全専門家に対する最大値、比較、引き算だけなので、値によって読み書きする場所が変わりません。同点のときに小さい番号を選ぶ扱いまで含めて、Hugging Face の実装と同じ結果になることを CPU 上のテストで確かめています。

重みは専門家ごとにまとめて並べ直しています。prefill では専門家を 16 個ずつのグループにして全トークンとまとめて行列演算し、decode では選ばれた 6 個の重みだけを読みます。
:::

Attention は回転位置埋め込みを持たない形です。位置の情報は Mamba2 の層が運ぶ設計なので、Attention は書き直さず、既存の部品をそのまま使っています。

# NKI カーネルで速くする

![1 トークンの生成 72.5 ms → 9.0 ms（同時処理対応前）](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/162e5225ba1c9b/zenn/articles/162e5225ba1c9b/decode.png)

速くする作業は、実機のプロファイラで時間の内訳を測り、一番大きい部分から順に手を入れる、という繰り返しでした。NKI 最適化なしの版では 1 トークンの生成に 72.5 ms かかっていました。主な原因は、MoE の 128 個の専門家の重みを、1 トークンを作るたびにすべて HBM から読み出して計算していたことです（1 層あたり約 640 MB）。decode は計算よりも重みを運ぶ量で時間が決まるので、ルーターが選んだ 6 個の番号で、その 6 個の重みだけを HBM から読むように変えると（`torch.topk` と `torch.index_select`）、14 ms になりました。Attention は複数の query ヘッドが 1 つの KV ヘッドを共有する形（GQA）なので、KV をヘッド数分に複製せずに計算し、さらに文脈の長さ別にグラフを分けると 12.8 ms です。MoE の decode を NKI カーネルにしても 12.6 ms とほとんど変わりませんでした。効いたのは Mamba2 の decode の NKI カーネル（10.0 ms）と、各層の入出力の射影を行列ベクトル積の NKI カーネルにしたこと（9.0 ms）です。同時処理に対応した最終版は 9.2 ms です。

![NKI カーネルの作り方：2 コアで分け、DMA をまとめる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/162e5225ba1c9b/zenn/articles/162e5225ba1c9b/kernels.png)

カーネルは Mamba2 の decode、Mamba2 の prefill（chunked SSD）、MoE の decode、行列ベクトル積の 4 本で、共通の方針は 2 つです。

![trn2.3xlarge の Trainium2 チップには物理コアが 8 個あり、LNC=2 で 2 個ずつが 1 つの論理コアになり、TP=4 で論理コア 1 つが 1 ランクを受け持つ。Mamba2 の 64 ヘッドは 8 ヘッドずつ B と C を共有するグループに分かれ、1 ランクの 16 ヘッドは 2 グループなので、物理コア 1 つに 1 グループを割り当てるとコアの間でデータをやり取りせずに済む。MoE と行列ベクトル積は半分ずつに分ける](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/162e5225ba1c9b/zenn/articles/162e5225ba1c9b/cores.gif)

1 つ目は、2 つの物理コアに、データのやり取りが要らない単位で仕事を分けることです。trn2.3xlarge の Trainium2 チップには物理コアが 8 個あり、LNC=2 では 2 個ずつが 1 つの論理コアになります。TP=4 では、論理コア 1 つが TP の 1 ランクを受け持ち、Mamba2 の 64 ヘッドのうち 16 ヘッドを計算します。Mamba2 では 8 ヘッドが同じ B と C を共有していて、このまとまりをグループと呼びます。グループは Mamba2 の層の中の分け方で、MoE の専門家とは関係ありません。B と C は重みではなく、トークンごとに入力から作られる係数で、Attention の GQA で複数の query ヘッドが 1 つの KV ヘッドを共有するのと似た形です。1 ランクの 16 ヘッドはちょうど 2 グループなので、論理コアの中の 2 つの物理コアに 1 グループずつ割り当てます。ヘッドが使うのは自分のグループの B と C だけなので、2 つの物理コアの間でデータをやり取りする必要がありません。MoE と行列ベクトル積も、2 つの物理コアで半分ずつに分けます。MoE は専門家の中間の次元を分けて最後に 2 つを足し、行列ベクトル積は出力の列を分けます。

2 つ目は、メモリとのデータ転送（DMA）を大きく、少なくすることです。MoE の decode カーネルは、専門家の番号を使って重みをメモリから直接読み、選ばれた専門家の分だけを転送します。Mamba2 の decode カーネルは、1 回の転送でバッチ全員分の入力を読み込みます。ヘッドごとに 1 つある値をそのヘッドの全要素に広げる処理も、小さな転送を繰り返す代わりに行列積 1 回で済ませます。

4 本それぞれの中身は、下の折りたたみで図と一緒に説明します。その前に、カーネルを読むための前提を 3 つだけ押さえておきます。

- Trainium のチップには、大きいけれど遠いメモリ（HBM）と、小さいけれど計算器のすぐそばにあるメモリ（SBUF）があります。計算は SBUF に置いたデータに対してしか行えないので、HBM から SBUF へデータを運ぶ転送（DMA）が必ず要ります。転送は 1 回ごとに準備の手間がかかるので、小さな転送を何度も繰り返すと、運ぶ量が少なくても時間がかかります。
- SBUF のデータは 128 行の表のように並んでいて、128 行を同時に計算します。1 行に何を置くかを決めることが、カーネルの設計の中心になります。
- 行列積は専用の計算器（Tensor Engine）が担当します。片方の行列を計算器に固定し、もう片方を流し込む形で計算します。

:::details Mamba2 の decode カーネル：全リクエストを 1 枚のタイルにまとめる
![Mamba2 の decode カーネルは、全リクエストの同じ 128 チャネルを 1 枚のタイルに並べて一度に計算する](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/162e5225ba1c9b/zenn/articles/162e5225ba1c9b/k-mamba-decode.png)

decode では、各リクエストが 1 トークンずつ進みます。Mamba2 の層は、そのトークンの入力と、そのリクエストが持ち越してきた状態から、次の状態と出力を計算します。

最初の作り方では、リクエストを 1 件ずつループで処理していました。さらに、ヘッドごとに 1 つしかない値（dt など）を、そのヘッドの 64 行に配るために、小さな転送を何度も出していました。8 リクエストのときは、この小さな転送の繰り返しが時間の大半を占めていました。

作り直したカーネルの並べ方を説明する前に、ヘッドとチャネルという言葉を決めておきます。Mamba2 の層は、1 トークン分の入力を長い数の並びとして持ち、それを 64 個ずつに区切って計算します。この 64 個のまとまりをヘッド、その中の 1 つ 1 つの数をチャネルと呼びます。1 つの物理コアは 1 グループの 8 ヘッド（8 × 64 = 512 チャネル）を受け持ちます。SBUF に置く表（タイル）の行は 128 までなので、2 ヘッド分（2 × 64 = 128 チャネル）ずつ、4 枚のタイルに分けて計算します。GIF の head 0 はタイルの上の 64 行、head 1 は下の 64 行です。タイルの列には、リクエストを 8 件並べます。1 トークン分の計算は、下の GIF の 1〜6 の 6 ステップです（[mamba_decode_kernel.py](https://github.com/littlemex/vllm-neuron/blob/fdc980267b8ecd247d84d959658adaceb5c47a18/vllm_neuron/model/nemotron_h/mamba_decode_kernel.py)）。

![タイルの行は 128 チャネル（2 ヘッド × 64）、列は 8 リクエスト。1 で全リクエストの入力を 1 回の転送でタイルに入れ、2 で畳み込みと SiLU を全列まとめて計算し、3 でヘッドごとの dt と減衰を 0/1 の表との行列積で 64 行に配り、4 で状態の更新だけを 1 リクエストずつ行い、5 で出力を求め、6 で正規化して HBM に書き出す](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/162e5225ba1c9b/zenn/articles/162e5225ba1c9b/mamba-decode.gif)

1. 全リクエストの入力を、1 回の転送でタイルに入れます。
2. Mamba2 は SSM の前に、チャネルごとに「直前 3 トークンの入力と今のトークンの入力」の 4 つを重み付きで足す短い畳み込み（幅 4 の 1 次元の畳み込み）をかけ、そのあと SiLU をかけます。直前 3 トークン分の入力は、chunked SSD の塊とは関係なく、リクエストごとの状態プール（`conv_state`、状態 $h$ と同じくモデルのバッファ）に持ち越してあります。畳み込みのあと、`conv_state` は 1 トークン分ずらして今の入力を加え、書き戻します。列ごとに同じ計算なので、8 リクエスト分を一度に行います。
3. ヘッドごとの時間刻み $\Delta$ と減衰 $dA = \exp(\Delta A)$ を求め、どのヘッドがどの行に当たるかを 0 と 1 で表した表との行列積 1 回で、各ヘッドの 64 行に配ります。
4. 状態の更新 $h \leftarrow h \, dA + \Delta \, x \, B$ だけは、リクエストごとに状態が違うので 1 件ずつ行います。状態は、HBM の状態プールにあるそのリクエストの行です。
5. 出力 $y = h \cdot C + D x$ を求めます。
6. $\mathrm{SiLU}(\text{gate})$ を掛けて正規化し、HBM に書き出します。

Mamba2 では、いくつかのヘッドが B と C という係数を共有していて、その単位をグループと呼びます。2 つの物理コアには、このグループを 1 つずつ割り当てます。グループをまたぐ計算はないので、2 つのコアの間でデータをやり取りする必要がありません。実機のプロファイラで測ると、この作り直しで、8 リクエストのときの decode 1 ステップのうち Mamba2 の分が 9.0 ms から 3.0 ms になりました。
:::

:::details SSD の prefill カーネル：128 トークンの塊ごとに行列演算をして、状態を次へ渡す
![SSD の prefill カーネルは、128 トークンの塊の中を三角形の行列演算で計算し、状態を次の塊へ渡す](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/162e5225ba1c9b/zenn/articles/162e5225ba1c9b/k-ssd-prefill.png)

prefill では、プロンプトのトークンをまとめて読み込みます。Mamba2 の本来の計算は 1 トークンずつ状態を更新する逐次の計算ですが、これをそのままカーネルにすると、128 行を同時に計算できる計算器がほとんど遊んでしまいます。そこで、トークンを 128 個ずつの塊に区切ります。

![1 つの塊を NeuronCore で計算する流れ。HBM から SBUF に塊の入力を運び、Tensor Engine で C と B の積から階段の形を作り、Scalar Engine の exp で漏れを、Vector Engine で掛け合わせて重みにし、塊の中の出力を求める。前の塊からの分は状態 h から求めて足し、出力を HBM に書き出し、新しい h は SBUF に置いたまま次の塊へ渡す](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/162e5225ba1c9b/zenn/articles/162e5225ba1c9b/ssd-hw.gif)

上の「chunked SSD の詳細」のバケツの説明を、NeuronCore の上でどう計算するかに置き換えると、GIF の 7 ステップになります（[ssd_prefill_kernel.py](https://github.com/littlemex/vllm-neuron/blob/fdc980267b8ecd247d84d959658adaceb5c47a18/vllm_neuron/model/nemotron_h/ssd_prefill_kernel.py)）。HBM は遠くて大きいメモリ、SBUF は計算器のそばの小さいメモリです。Tensor Engine は、片方の行列を固定し、もう片方を流し込んで行列積を計算します。

式の $i$ と $j$ は塊の中のトークンの番号（1〜128）で、$cs_i = \sum_{k \le i} \Delta_k A$ は塊の先頭から $i$ までの減衰の指数を足したものです。$\exp(cs_i - cs_j)$ が、バケツの説明の「$j$ から $i$ までにどれだけ漏れたか」にあたります。

1. 塊の 128 トークン分の $x$、$\Delta$（dt）、$B$、$C$ を、HBM から SBUF に運びます。状態 $h$ は SBUF に置いたままです。
2. Tensor Engine で $G_{ij} = C_i \cdot B_j$ を 128 × 128 まとめて作り、$j \le i$ の階段の形（三角形）だけを残します。
3. Scalar Engine の exp で漏れ $L_{ij} = \exp(cs_i - cs_j)$ を作り、Vector Engine で $M_{ij} = G_{ij} L_{ij}$ にします。
4. Tensor Engine で $y_i = \sum_j M_{ij} \, \Delta_j x_j$ を求めます。塊の中の分の出力です。
5. 前の塊からの分 $\exp(cs_i) \, C_i \cdot h$ と、$D x_i$ を足します。バケツの説明の、$h$ に減衰を掛けるだけで済む部分です。
6. 出力 $y$ を HBM に書き出します。
7. 新しい状態 $h \leftarrow \exp(cs_Q) \, h + \sum_j \exp(cs_Q - cs_j) \, \Delta_j x_j B_j$（$Q = 128$）を Tensor Engine で作り、SBUF に置いたまま次の塊へ渡します。$h$ は最後の塊まで HBM に戻りません。

1 つのコアは 1 つの SSM グループを受け持ち、その中のヘッドを順に計算します。2 つのコアは別々のグループを受け持つので、データをやり取りしません。

1 つ注意がいるのは減衰の計算です。減衰は $\exp\left(A \sum_{k=j+1}^{i} \Delta_k\right)$ で、$A$ は負なので、$j \le i$ の部分の値は 1 以下に収まります。ところが三角形の反対側（$j > i$）では指数が正になり、塊が長いと指数関数の値があふれます。そこで、反対側の指数は 0 に切り詰めてから指数関数に通し、結果はマスクで捨てます。prefill をこのカーネルにしたことで、読み込みは約 800 から約 2,600 トークン/秒になりました。
:::

:::details MoE の decode カーネル：選ばれた 6 個の専門家の重みだけを運ぶ
![MoE の decode カーネルは、ルーターが選んだ 6 個の専門家の重みだけを番号で取りに行く](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/162e5225ba1c9b/zenn/articles/162e5225ba1c9b/k-moe-decode.png)

MoE の層には 128 個の専門家（それぞれが小さな MLP）があり、ルーターが各トークンに使う 6 個を選びます。このほかに、全トークンが必ず通る共有専門家が 1 個あります。最初の版は、128 個すべてを計算してから、選ばれなかった専門家の結果に 0 をかけていました。decode で効いてくるのは計算量よりも、HBM から重みを運ぶ量です。専門家 1 個の重みは TP の 1 ランクあたり約 5 MB あるので、128 個すべてを運ぶと 1 層で約 640 MB になります。

まず PyTorch の段階で、選ばれた 6 個の重みだけを読む形に変えました。これだけで、1 トークンの生成が 72.5 ms から 14 ms になりました。NKI カーネルでは、ルーターが出した専門家の番号をそのまま転送の位置の指定に使い、HBM からその専門家の重みを直接 SBUF へ運びます。6 個分の転送を先にまとめて出しておき、計算と重なるようにしています。計算は、up の重みとの積に ReLU をかけてから 2 乗し、ルーターの重みをかけ、down の重みとの積を 6 個分足し合わせる、という順です。

2 つの物理コアは、各専門家の中間の次元を半分ずつ受け持ち、それぞれの部分和を最後に足します。ただし、このカーネルの効果は小さく、12.8 ms が 12.6 ms になった程度でした。運ぶ重みの量は PyTorch の段階ですでに 6 個分に減っていて、カーネルにしても運ぶ量そのものは変わらないためだと考えています。
:::

:::details 行列ベクトル積のカーネル：トークンを固定し、重みを流し込む
![行列ベクトル積のカーネルは、トークンの側を計算器に固定し、重みを 512 列ずつ流し込む](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/162e5225ba1c9b/zenn/articles/162e5225ba1c9b/k-matvec.png)

decode では、各層の入出力の射影（Mamba2 の入力と出力、Attention の q, k, v と出力、最後の語彙への射影）が、「数トークンの行ベクトル × 大きな重み行列」の形になります。行列積の計算器は、片方の行列を固定し、もう片方を流し込んで計算します。普通は重みのほうを固定しますが、そうすると、重みを 128 × 128 の小片に切るたびに計算器へ載せ直すことになります。トークンが 1 つしかない decode では、載せ直しの時間に比べて計算がほとんどなく、計算器が待ってばかりになります。

このカーネルでは逆に、数トークン分の行ベクトル x のほうを計算器に固定します。x は重みの 128 行ごとに 1 回載せるだけで済み、重みは 512 列ずつの帯にして流し込みます。2 つの物理コアは、出力の列を左右半分ずつ受け持ち、それぞれ自分の担当の列の重みだけを読みます。この変更で、1 トークンの生成が 10.0 ms から 9.0 ms になりました。共有専門家の射影だけは、計測するとコンパイラが作る通常の行列積のほうが速かったので、このカーネルを使っていません。
:::

prefill の chunked SSD を NKI カーネルにしたことで、プロンプトの読み込みは約 800 から約 2,600 トークン/秒になりました。Mamba2 の状態は $\exp\left(A \sum \Delta\right)$（$A$ は負の減衰係数、$\Delta$ はトークンごとの時間刻み）で減衰するので、そのまま計算すると塊が長いときに指数関数があふれます。カーネルでは累積和どうしの差を取り、上限で切ってから指数関数に渡すので、$|A| \sum \Delta$ が大きくてもあふれません。

一方、効果がなかった試みもあります。prefill の MoE を、選ばれた専門家だけ計算する方式（AWS が公開する NKI カーネル集 nkilib の blockwise MoE）に替えると、2,596 から 1,695 トークン/秒に逆に遅くなりました。512 トークンの塊では 128 個の専門家のほぼ全員が使われるので、どの方式でも 1 層・1 ランクあたり約 640 MB の重みを読みます。プロファイルでは MoE 層ごとに約 3.5 ms の待ちが出ており、ここが今の prefill のいちばん大きな待ち時間です。

# サービング側の工夫：同時リクエスト

![同時リクエスト：状態の行を「先頭 KV ブロック番号」で引く](/images/162e5225ba1c9b-concurrency.png)

1 リクエストずつの処理では、Mamba2 の状態は層ごとに 1 本のバッファで足ります。複数のリクエストを同時に扱うと、リクエストごとに別の状態が必要になります。ここで問題が 2 つあります。1 つは、ModelRunner がモデルに「これは何番目のリクエストか」を渡さないことです。もう 1 つは、終わったリクエストが抜けると、decode バッチの中の行の並びがステップごとに入れ替わることです。

そこで、各リクエストが最初に確保した KV ブロックの番号を目印にしました。このブロックは、リクエストが終わるまで同じ番号のままで、他のリクエストと共有されません。ただし、プロンプトの先頭の KV を複数のリクエストで共有する prefix caching を有効にすると共有が起きるので、無効のまま使う必要があります（この構成では既定で無効です）。モデル側には、最大同時数 $N$ に対して $2N+1$ 行の状態プールを用意し、各行の持ち主のブロック番号を記録します。$2N+1$ は、実行中の $N$ 本、終わってもまだ空いていない最大 $N$ 本、詰め物用の作業行 1 本の合計です。

- prefill の最初の塊では、空いている一番小さい行を取ります。
- 以後の塊や decode では、持ち主の番号が一致する行を引きます。
- decode バッチに現れなかった行は、終わったリクエストのものとして空けます。
- 詰め物の行は、最後の作業用の行に書き込みます。

行の検索は比較と最大値だけで書いているので、1 つのコンパイル済みグラフが毎ステップそのまま使えます。

この仕組みは、Neuron のスケジューラの 2 つの性質を前提にしています。1 つは、1 リクエストの prefill か、実行中の全リクエストの decode のどちらか一方しか 1 ステップに入れないことです。もう 1 つは、非同期のスケジューラでは、最初のトークンで終わるリクエストも直後の decode ステップに一度は載ることです。載らないと、そのリクエストの行を空けるきっかけがなく、行が残り続けます。実機では行が残る現象は再現しませんでしたが、前提としてモデルの [README](https://github.com/littlemex/vllm-neuron/blob/fdc980267b8ecd247d84d959658adaceb5c47a18/vllm_neuron/model/nemotron_h/README.md) に書いてあります。

生成速度は、1 リクエストでは 91〜94 トークン/秒、8 リクエスト同時では合計 216 トークン/秒です。同時に処理するぶん、1 リクエストあたりの速さは約 27 トークン/秒に下がります。確認問題 12 問を一度に投入したとき（8 問を同時に処理し、残り 4 問は待ち）も 12/12 でした。あるリクエストの出力は、同じバッチに入る相手を替えても 1 ビットも変わりませんでした（相手を 3 通りに替えて計 5 回試しました）。ただし、単独で流したときの出力とは途中から変わることがあります。バッチ幅ごとに別のグラフがコンパイルされ、bf16 の丸めが変わるためと考えています。

# 動かし方

起動は、aws-neuron-samples のフォーク [littlemex/aws-neuron-samples](https://github.com/littlemex/aws-neuron-samples) の `setup/multi-node/eks` にある `up.sh` で行います。前提として、Trainium のノードプールと Neuron デバイスプラグインを持つ EKS クラスタが要ります。この記事の設定をプリセット `models/nemotron-h.yaml` に書くと、次のようになります。

```yaml
model: nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-BF16
tpSize: 4
maxModelLen: 8192
maxNumSeqs: 8
extraArgs: ["--max-num-batched-tokens=512", "--num-gpu-blocks-override=2400"]
plugin:
  install: true
  repo: littlemex/vllm-neuron
  ref: release-0.24.0.1.1.0
  modelDir: nemotron_h
  registerClass: NemotronHForCausalLM
```

`plugin.install` を有効にすると、公開されている vLLM Neuron のイメージのまま起動し、Pod の起動時にフォークからモデルのコードを取ってきて plugin に組み込みます。`--num-gpu-blocks-override`（名前に gpu とありますが、Neuron でも KV ブロック数の指定に使います）は、8 リクエスト分の最大長の KV（$8 \times 8192 \div 32 = 2048$ ブロック。1 ブロックは 32 トークン）より多めにしています。KV の見積もりが同時数に足りないと、スケジューラが新しいリクエストを待たせるので、同時数が上がりません。

`--volume` には、コンパイル結果のキャッシュを置く PersistentVolume の名前を渡します。

```bash
export PV_NAME=my-neuron-cache
./up.sh nemotron-h --pool trn2 --namespace serving --volume "$PV_NAME"
```

手元では、キャッシュのない初回は NEFF へのコンパイルに 20〜40 分ほどかかりました。2 回目以降はキャッシュが効いて短くなります。

:::message alert
起動時にブランチからコードを取ってくるのは検証用の割り切りです。実際に運用するときは、コミットを固定し、モデルを組み込んだイメージをビルドしてください。
:::

# まとめ

vLLM Neuron plugin は、vLLM 本体を変えずに、スケジューラと ModelRunner を Trainium 向けに差し替える仕組みでした。NemotronH はその枠に、5 つの契約メソッドを実装したモデル一式として入れました。KV キャッシュは Attention の 6 層だけに割り当て、Mamba2 の状態はモデル側に置いています。Mamba2 は chunked SSD に、MoE の専門家選びは最大値と比較だけの形に書き直しました。そのうえで、プロファイラで測った大きい部分から NKI カーネルに置き換え、生成は 72.5 から 9.2 ms/トークン、読み込みは約 800 から約 2,600 トークン/秒になりました。最後に、先頭 KV ブロック番号でリクエストごとの状態の行を引く状態プールを作り、8 リクエストの同時処理で合計 216 トークン/秒まで伸ばしました。
