# はじめに

NemotronH は、Mamba2、Mixture of Experts（MoE）、Attention の 3 種類の層を組み合わせて積んだハイブリッドな言語モデルです。この記事では、NemotronH の 30B 版（[nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-BF16](https://huggingface.co/nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-BF16)）を、vLLM の Neuron plugin に組み込んで AWS Trainium2 上で動かした方法をまとめます。

最初に、モデルを plugin の決まりごとに沿って実装し、正しく動くことを確かめました。次に NKI（Trainium 向けのカーネル記述言語）で重い部分を書き直し、最後に複数のリクエストを同時に処理できるようにしました。測った環境は trn2.3xlarge です。Trainium2 のチップ 1 個に物理コアが 8 個あり、2 個ずつ束ねた 4 個の論理コア（LNC=2 の設定）に、モデルを 4 分割するテンソル並列（TP=4）で載せています。結果は次のとおりです。

| 項目 | NKI 最適化なし | NKI + Serving 最適化 |
|---|---|---|
| 1 トークンの生成時間（1 リクエスト） | 72.5 ms | 9.2 ms |
| プロンプトの読み込み速度 | 約 800 トークン/秒 | 約 2,600 トークン/秒 |
| 8 リクエスト同時の生成速度 | 非対応 | 合計 216 トークン/秒 |
| 事実・計算・長文の確認問題 12 問 | 12/12 | 12/12（12 問を一度に投入しても 12/12） |

コードは vLLM Neuron plugin のフォーク [littlemex/vllm-neuron の release-0.24.0.1.1.0 ブランチ](https://github.com/littlemex/vllm-neuron/tree/fdc980267b8ecd247d84d959658adaceb5c47a18/vllm_neuron/model/nemotron_h)にあります。plugin はベータ版なので、ここで触れる内部のインタフェースは今後変わる可能性があります。

# 全体像

![vLLM は変えず、plugin の枠にモデルを足す](/images/162e5225ba1c9b-overview.png)

vLLM の Neuron plugin は、vLLM 本体には手を入れません。vLLM の platform plugin という仕組みを使って、外から部品を差し替えます。API サーバー、リクエスト管理、KV キャッシュのブロック管理といった vLLM の中核はそのまま動きます。plugin が差し替えるのは、スケジューラと、計算グラフを Trainium 用の実行形式（NEFF）にコンパイルして動かす ModelRunner です。

NemotronH を足すために新しく作ったのは、`vllm_neuron/model/nemotron_h/` のモデル一式とそのテストです。plugin にもともとあるファイルで変更したのは、モデルを登録する `vllm_neuron/model/registry.py` の 2 行（import と、登録の一覧への 1 行）だけで、runner やスケジューラ、KV キャッシュの処理には手を入れていません。モデル一式には、plugin が求める 5 つのメソッド（次の節で説明します）を実装する本体、リクエストごとの Mamba の状態を置く状態プール、そして NKI カーネル 4 本が入っています。

3 者がどう連携するかを、起動時と毎ステップに分けて見ます。図の 3 本の帯が vLLM、plugin、自分で書くモデル（BYOM、Bring Your Own Model）で、番号は呼ばれる順番です。

![起動時は、plugin が自前のモデルを組み立て、KV キャッシュを結線する](/images/162e5225ba1c9b-relations-startup.png)

起動時は、まず vLLM が plugin を読み込み（1）、plugin がワーカーとスケジューラを Trainium 向けに差し替えます（2）。そのあと plugin の ModelRunner が、モデルのメソッドを順に呼びます。`from_configs` でモデルを組み立て（3）、`load_weights` で重みを 4 つのランクに分けて読み込みます（4）。続いて `get_kv_spec` で、どの層が KV キャッシュを使うかを問い合わせます（5）。plugin は空いているメモリから KV キャッシュの量を決めて確保し（6）、`bind_kv_cache` でモデルに渡します（7）。最後に、`forward` を長さの段ごとに 1 回ずつ流して、Trainium で動く形（NEFF）にコンパイルします（8）。モデルの側から vLLM や plugin を呼ぶことはありません。KV キャッシュについては、各リクエストにどのブロックを割り当てるかを vLLM が決め、メモリそのものは plugin が持ち、モデルはそこを読み書きするだけ、という分担です。

![毎ステップは、vLLM が何を計算するかを決め、自前のモデルが計算する](/images/162e5225ba1c9b-relations-step.png)

毎ステップでは、vLLM がリクエストを受け取り、各リクエストに KV のブロックを割り当てます（1）。Neuron のスケジューラは、このステップで 1 リクエストの prefill をするか、実行中の全リクエストの decode をするかを決めます（2）。plugin はトークン、位置、そして各リクエストのブロック番号の表を入力にまとめ（3）、モデルの `forward` を呼びます（4）。モデルは、リクエストごとの Mamba の状態の行を探し、52 層を計算して、KV キャッシュに書き込みます。plugin がその出力から次のトークンをデバイス上で選び（5）、vLLM が結果を返します（6）。毎ステップモデルに渡るのは、トークンの番号、位置、層ごとのメタデータ（ブロックの表と、各トークンを KV のどこに書くかの対応表）だけです。

# plugin の枠にどう入れたか

![契約は 5 つ。難所は KV の申告と状態の置き場](/images/162e5225ba1c9b-contract.png)

呼ばれる順番は前の図のとおりで、表にすると、モデル側が書くことと plugin が受け持つことは上のように分かれます。

ハイブリッドモデルで悩ましいのは、KV の申告と、Mamba の状態の置き場です。NemotronH の 52 層のうち、KV キャッシュを持つのは Attention の 6 層だけです。そこで `get_kv_spec` は Attention の 6 層だけを申告し、Mamba2 と MoE の層は申告しません。こうすると ModelRunner の KV 管理には何も足さずに済みます。

一方、Mamba2 の層も、リクエストごとに状態を次のステップへ持ち越します。持ち越すのは、直前 3 トークン分の畳み込みの入力と、状態空間モデル（SSM）の内部状態の 2 つです。これらを TP の 1 ランクのデバイスメモリのどこに置いているかを図にしました。

![1 ランクのデバイスメモリには、重み、plugin が持つ KV キャッシュ、モデルが持つ Mamba の状態プールがある](/images/162e5225ba1c9b-memory.png)

デバイスメモリには 3 種類のデータがあります。

- 重み：約 15 GB で、`load_weights` が起動時に 1 回だけ読み込みます。
- KV キャッシュ：Attention の 6 層だけが使います。KV はトークンが増えるたびに増えるので、32 トークンずつのブロックに区切って管理します。どのリクエストにどのブロックを渡すかは vLLM が決め、メモリの確保は plugin が行います。モデルは、各トークンの KV を指定された場所に書き込むだけです。図では、リクエスト A がブロック 7、8、9 を、リクエスト B がブロック 41、42 を持っています。
- Mamba の状態：KV キャッシュとは違い、文章がどれだけ長くなっても 1 リクエストあたりの大きさが変わりません。そのためブロックに区切る必要がなく、plugin の KV の仕組みには乗せていません。plugin はこの状態の存在を知らないので、モデルが自分のバッファとして持ちます。

Mamba の状態は、23 層それぞれに「1 リクエスト 1 行」の表（状態プール）として置いています。1 行には、SSM の状態（16 ヘッド × 64 × 128 の値）と、畳み込み用の直前 3 トークン分の入力が入ります。行数は、最大同時数 N に対して 2N+1 で、N = 8 なら全層で約 200 MB です。どの行がどのリクエストのものかは、行ごとに記録した「持ち主」で区別します。持ち主には、そのリクエストが持つ最初の KV ブロックの番号を使います（図では A が 7、B が 41）。モデルは毎ステップ、計算グラフの中で自分の行を探し、その行を読み、計算した新しい状態で上書きします。バッファへの書き込みはグラフの実行が終わっても残るので、次のステップは更新された状態から始まります。行の探し方の詳しい仕組みは、後の「サービング側の工夫」で説明します。

# NemotronH 固有の部品をどう作ったか

![52 層は 3 種類。Mamba2 と MoE を Trainium で動く形に書き直す](/images/162e5225ba1c9b-layers.png)

52 層は `hybrid_override_pattern` という設定で、Mamba2（23 層）、MoE（23 層）、Attention（6 層）のどれかに振り分けられます。図の帯がその並びです。Trainium のコンパイラは、データの値によって動きが変わる処理や長い逐次ループが苦手です。そのため Mamba2 と MoE は、Trainium で正しく動く形に書き直す必要がありました。

**Mamba2** の prefill（プロンプトの読み込み）は、本来は 1 トークンずつ状態を更新する逐次ループです。これはそのままではコンパイルに通りません。そこで数学的に同じ計算を、行列演算の組み合わせで書き直しました。全トークンを一度に行列演算にすると、計算量は系列長の 2 乗で増えます。そこで 128 トークンの塊に区切り、塊の中は行列演算、塊の間は状態の受け渡しで計算する chunked SSD という形にしました（SSD は Mamba2 の計算を行列演算として書く定式化の名前です）。これで計算量は系列長にほぼ比例する程度に収まります。別に試した最大長 128k トークンの設定では、長文の中の事実を答えさせる問題が 87.7k トークンまで通りました。112k では 2 問中 1 問が外れ、これは書き直し前と同じ結果です。また、長いプロンプトは vLLM の設定で 512 トークン（塊 4 つ分）ずつに分けて読み込むので、その区切りをまたいでも状態を引き継ぎます。また、コンパイル済みグラフの長さに合わせて末尾に足される詰め物のトークンは、状態に影響しないようにマスクしています。

**MoE** は、128 個の専門家から各トークンが 6 個を選び、それに常に使う 1 個（共有専門家）を足す形です。活性化関数は ReLU の 2 乗です。このチェックポイントの設定には、専門家の入力を低い次元に落とす（latent の）射影はありません。専門家を選ぶ処理を、値に応じて場所を読み書きする gather や scatter で素直に書くと、MoE 層を何層も重ねた構成で、実行時にメモリの範囲外アクセスのエラーが出ました。そこで、各専門家のスコアを他の全専門家と比べ、その結果を足して順位を数え、上位 6 個を選ぶ形に書き直しました。比較と和しか使わないので、値に応じた読み書きがありません。同点のときに小さい番号を優先する扱いまで、元の実装と一致させています。重みは専門家ごとに並べ直し、decode（1 トークンずつの生成）では選ばれた 6 個の重みだけを読みます。

**Attention** は回転位置埋め込みを持たない形です。位置の情報は Mamba2 の層が運ぶ設計なので、Attention は書き直さず、既存の部品をそのまま使っています。

書き直した計算は、どれも CPU 上のテストで逐次の参照実装や Hugging Face の実装と突き合わせて、一致することを確かめ、テストとして残しています。

# NKI カーネルで速くする

![1 トークンの生成 72.5 ms → 9.0 ms（同時処理対応前）](/images/162e5225ba1c9b-decode.png)

速くする作業は、実機のプロファイラで時間の内訳を測り、一番大きい部分から順に手を入れる、という繰り返しでした。NKI 最適化なしの版では 1 トークンの生成に 72.5 ms かかっていました。主な原因は、MoE の 128 個の専門家を毎回すべて計算していたことです。選ばれた 6 個の重みだけを読むように変えると 14 ms になりました。Attention は複数の query ヘッドが 1 つの KV ヘッドを共有する形（GQA）なので、KV をヘッド数分に複製せずに計算し、さらに文脈の長さ別にグラフを分けると 12.8 ms です。MoE の decode を NKI カーネルにしても 12.6 ms とほとんど変わりませんでした。効いたのは Mamba2 の decode の NKI カーネル（10.0 ms）と、各層の入出力の射影を行列ベクトル積の NKI カーネルにしたこと（9.0 ms）です。同時処理に対応した最終版は 9.2 ms です。

![NKI カーネルの作り方：2 コアで分け、DMA をまとめる](/images/162e5225ba1c9b-kernels.png)

カーネルは Mamba2 の decode、Mamba2 の prefill（chunked SSD）、MoE の decode、行列ベクトル積の 4 本で、共通の方針は 2 つです。

1 つ目は、Trainium2 の論理コアを構成する 2 つの物理コアに、やり取りが要らない単位で仕事を分けることです。Mamba2 のヘッドは、B と C という係数を共有するグループにまとまっています。TP で 4 分割したうちの 1 つが担当する 2 グループを、物理コアに 1 つずつ割り当て、コア間の通信をなくしました。MoE と行列ベクトル積は、中間の次元や出力の列を半分ずつ分けます。

2 つ目は、メモリとのデータ転送（DMA）を大きく、少なくすることです。MoE の decode カーネルは、専門家の番号を使って重みをメモリから直接読み、選ばれた専門家の分だけを転送します。Mamba2 の decode カーネルは、1 回の転送でバッチ全員分の入力を読み込みます。ヘッドごとに 1 つある値をそのヘッドの全要素に広げる処理も、小さな転送を繰り返す代わりに行列積 1 回で済ませます。

4 本それぞれの中身は、下の折りたたみで図と一緒に説明します。その前に、カーネルを読むための前提を 3 つだけ押さえておきます。

- Trainium のチップには、大きいけれど遠いメモリ（HBM）と、小さいけれど計算器のすぐそばにあるメモリ（SBUF）があります。計算は SBUF に置いたデータに対してしか行えないので、HBM から SBUF へデータを運ぶ転送（DMA）が必ず要ります。転送は 1 回ごとに準備の手間がかかるので、小さな転送を何度も繰り返すと、運ぶ量が少なくても時間がかかります。
- SBUF のデータは 128 行の表のように並んでいて、128 行を同時に計算します。1 行に何を置くかを決めることが、カーネルの設計の中心になります。
- 行列積は専用の計算器（Tensor Engine）が担当します。片方の行列を計算器に固定し、もう片方を流し込む形で計算します。

:::details Mamba2 の decode カーネル：全リクエストを 1 枚のタイルにまとめる
![Mamba2 の decode カーネルは、全リクエストの同じ 128 チャネルを 1 枚のタイルに並べて一度に計算する](/images/162e5225ba1c9b-k-mamba-decode.png)

decode では、各リクエストが 1 トークンずつ進みます。Mamba2 の層は、そのトークンの入力と、そのリクエストが持ち越してきた状態から、次の状態と出力を計算します。計算は図の右の 4 段です。まず直前 3 トークンと今のトークンの 4 つで畳み込みをして SiLU をかけます。次に、ヘッドごとの時間刻み dt と減衰の係数を求めます。そのあと、状態を「状態 × 減衰 + dt × B × 入力」で更新します。最後に、出力を「状態と C の内積 + D × 入力」で求めてから正規化します。

最初の作り方では、リクエストを 1 件ずつループで処理していました。さらに、ヘッドごとに 1 つしかない値（dt など）を、そのヘッドの 64 行に配るために、小さな転送を何度も出していました。8 リクエストのときは、この小さな転送の繰り返しが時間の大半を占めていました。

作り直したカーネルでは、タイルの行に 128 チャネル（2 ヘッド × 64）を、列にリクエストを並べます。こうすると、全リクエストの同じチャネルの入力が 1 回の転送で SBUF に入り、畳み込みのような計算も全リクエスト分を一度に行えます。ヘッドごとの値は、どのヘッドがどの行に当たるかを 0 と 1 で表した表と行列積を 1 回するだけで、64 行に配れます。状態の更新だけは、リクエストごとに状態の中身が違うので 1 件ずつ行います。

Mamba2 では、いくつかのヘッドが B と C という係数を共有していて、その単位をグループと呼びます。2 つの物理コアには、このグループを 1 つずつ割り当てます。グループをまたぐ計算はないので、2 つのコアの間でデータをやり取りする必要がありません。実機のプロファイラで測ると、この作り直しで、8 リクエストのときの decode 1 ステップのうち Mamba2 の分が 9.0 ms から 3.0 ms になりました。
:::

:::details SSD の prefill カーネル：128 トークンの塊ごとに行列演算をして、状態を次へ渡す
![SSD の prefill カーネルは、128 トークンの塊の中を三角形の行列演算で計算し、状態を次の塊へ渡す](/images/162e5225ba1c9b-k-ssd-prefill.png)

prefill では、プロンプトのトークンをまとめて読み込みます。Mamba2 の本来の計算は 1 トークンずつ状態を更新する逐次の計算ですが、これをそのままカーネルにすると、128 行を同時に計算できる計算器がほとんど遊んでしまいます。そこで、トークンを 128 個ずつの塊に区切ります。

塊の中では、トークン i の出力は、それより前のトークン j（j ≤ i）の入力の重み付きの和として書けます。重みは「C_i と B_j の内積 × j から i までの減衰 × dt_j」です。この重みを並べると図の左のような三角形の行列になり、塊の中の出力は、この行列と入力の行列積 1 回で求まります。逐次のループが行列演算に置き換わるので、計算器を有効に使えます。

塊をまたぐ影響は状態で受け渡します。各塊は、前の塊から受け取った状態の影響を出力に足し、自分の入力を加えた新しい状態を次の塊へ渡します。こうすると、計算量は系列の長さにほぼ比例して増えるだけで済みます。

1 つ注意がいるのは減衰の計算です。減衰は「A × dt の和」の指数関数で、A は負なので、j ≤ i の部分の値は 1 以下に収まります。ところが三角形の反対側（j > i）では指数が正になり、塊が長いと指数関数の値があふれます。そこで、反対側の指数は 0 に切り詰めてから指数関数に通し、結果はマスクで捨てます。prefill をこのカーネルにしたことで、読み込みは約 800 から約 2,600 トークン/秒になりました。
:::

:::details MoE の decode カーネル：選ばれた 6 個の専門家の重みだけを運ぶ
![MoE の decode カーネルは、ルーターが選んだ 6 個の専門家の重みだけを番号で取りに行く](/images/162e5225ba1c9b-k-moe-decode.png)

MoE の層には 128 個の専門家（それぞれが小さな MLP）があり、ルーターが各トークンに使う 6 個を選びます。このほかに、全トークンが必ず通る共有専門家が 1 個あります。最初の版は、128 個すべてを計算してから、選ばれなかった専門家の結果に 0 をかけていました。decode で効いてくるのは計算量よりも、HBM から重みを運ぶ量です。専門家 1 個の重みは TP の 1 ランクあたり約 5 MB あるので、128 個すべてを運ぶと 1 層で約 640 MB になります。

まず PyTorch の段階で、選ばれた 6 個の重みだけを読む形に変えました。これだけで、1 トークンの生成が 72.5 ms から 14 ms になりました。NKI カーネルでは、ルーターが出した専門家の番号をそのまま転送の位置の指定に使い、HBM からその専門家の重みを直接 SBUF へ運びます。6 個分の転送を先にまとめて出しておき、計算と重なるようにしています。計算は、up の重みとの積に ReLU をかけてから 2 乗し、ルーターの重みをかけ、down の重みとの積を 6 個分足し合わせる、という順です。

2 つの物理コアは、各専門家の中間の次元を半分ずつ受け持ち、それぞれの部分和を最後に足します。ただし、このカーネルの効果は小さく、12.8 ms が 12.6 ms になった程度でした。運ぶ重みの量は PyTorch の段階ですでに 6 個分に減っていて、カーネルにしても運ぶ量そのものは変わらないためだと考えています。
:::

:::details 行列ベクトル積のカーネル：トークンを固定し、重みを流し込む
![行列ベクトル積のカーネルは、トークンの側を計算器に固定し、重みを 512 列ずつ流し込む](/images/162e5225ba1c9b-k-matvec.png)

decode では、各層の入出力の射影（Mamba2 の入力と出力、Attention の q, k, v と出力、最後の語彙への射影）が、「数トークンの行ベクトル × 大きな重み行列」の形になります。行列積の計算器は、片方の行列を固定し、もう片方を流し込んで計算します。普通は重みのほうを固定しますが、そうすると、重みを 128 × 128 の小片に切るたびに計算器へ載せ直すことになります。トークンが 1 つしかない decode では、載せ直しの時間に比べて計算がほとんどなく、計算器が待ってばかりになります。

このカーネルでは逆に、数トークン分の行ベクトル x のほうを計算器に固定します。x は重みの 128 行ごとに 1 回載せるだけで済み、重みは 512 列ずつの帯にして流し込みます。2 つの物理コアは、出力の列を左右半分ずつ受け持ち、それぞれ自分の担当の列の重みだけを読みます。この変更で、1 トークンの生成が 10.0 ms から 9.0 ms になりました。共有専門家の射影だけは、計測するとコンパイラが作る通常の行列積のほうが速かったので、このカーネルを使っていません。
:::

prefill の chunked SSD を NKI カーネルにしたことで、プロンプトの読み込みは約 800 から約 2,600 トークン/秒になりました。Mamba2 の状態は `exp(A * sum(dt))`（A は負の減衰係数、dt はトークンごとの時間刻み、sum(dt) はその累積和）で減衰するので、そのまま計算すると塊が長いときに指数関数があふれます。カーネルでは累積和どうしの差を取り、上限で切ってから指数関数に渡すので、`|A| * sum(dt)` が大きくてもあふれません。

一方、効果がなかった試みもあります。prefill の MoE を、選ばれた専門家だけ計算する方式（AWS が公開する NKI カーネル集 nkilib の blockwise MoE）に替えると、2,596 から 1,695 トークン/秒に逆に遅くなりました。512 トークンの塊では 128 個の専門家のほぼ全員が使われるので、どの方式でも 1 層・1 ランクあたり約 640 MB の重みを読みます。プロファイルでは MoE 層ごとに約 3.5 ms の待ちが出ており、ここが今の prefill のいちばん大きな待ち時間です。

# サービング側の工夫：同時リクエスト

![同時リクエスト：状態の行を「先頭 KV ブロック番号」で引く](/images/162e5225ba1c9b-concurrency.png)

1 リクエストずつの処理では、Mamba2 の状態は層ごとに 1 本のバッファで足ります。複数のリクエストを同時に扱うと、リクエストごとに別の状態が必要になります。ここで問題が 2 つあります。1 つは、ModelRunner がモデルに「これは何番目のリクエストか」を渡さないことです。もう 1 つは、終わったリクエストが抜けると、decode バッチの中の行の並びがステップごとに入れ替わることです。

そこで、各リクエストが最初に確保した KV ブロックの番号を目印にしました。このブロックは、リクエストが終わるまで同じ番号のままで、他のリクエストと共有されません。ただし、プロンプトの先頭の KV を複数のリクエストで共有する prefix caching を有効にすると共有が起きるので、無効のまま使う必要があります（この構成では既定で無効です）。モデル側には、最大同時数 N に対して 2N+1 行の状態プールを用意し、各行の持ち主のブロック番号を記録します。2N+1 は、実行中の N 本、終わってもまだ空いていない最大 N 本、詰め物用の作業行 1 本の合計です。

- prefill の最初の塊では、空いている一番小さい行を取ります。
- 以後の塊や decode では、持ち主の番号が一致する行を引きます。
- decode バッチに現れなかった行は、終わったリクエストのものとして空けます。
- 詰め物の行は、最後の作業用の行に書き込みます。

行の検索は比較と最大値だけで書いているので、1 つのコンパイル済みグラフが毎ステップそのまま使えます。

この仕組みは、Neuron のスケジューラの 2 つの性質を前提にしています。1 つは、1 リクエストの prefill か、実行中の全リクエストの decode のどちらか一方しか 1 ステップに入れないことです。もう 1 つは、非同期のスケジューラでは、最初のトークンで終わるリクエストも直後の decode ステップに一度は載ることです。載らないと、そのリクエストの行を空けるきっかけがなく、行が残り続けます。実機では行が残る現象は再現しませんでしたが、前提としてモデルの [README](https://github.com/littlemex/vllm-neuron/blob/fdc980267b8ecd247d84d959658adaceb5c47a18/vllm_neuron/model/nemotron_h/README.md) に書いてあります。

生成速度は、1 リクエストでは 91〜94 トークン/秒、8 リクエスト同時では合計 216 トークン/秒です。同時に処理するぶん、1 リクエストあたりの速さは約 27 トークン/秒に下がります。確認問題 12 問を一度に投入したとき（8 問を同時に処理し、残り 4 問は待ち）も 12/12 でした。あるリクエストの出力は、同じバッチに入る相手を替えても 1 ビットも変わりませんでした（相手を 3 通りに替えて計 5 回試しました）。ただし、単独で流したときの出力とは途中から変わることがあります。バッチ幅ごとに別のグラフがコンパイルされ、bf16 の丸めが変わるためと考えています。

# 動かし方

起動は、aws-neuron-samples のフォーク [littlemex/aws-neuron-samples](https://github.com/littlemex/aws-neuron-samples) の `setup/multi-node/eks` にある `up.sh` で行います。前提として、Trainium のノードプールと Neuron デバイスプラグインを持つ EKS クラスタが要ります。この記事の設定をプリセット `models/nemotron-h.yaml` に書くと、次のようになります。

```yaml
model: nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-BF16
tpSize: 4
maxModelLen: 8192
maxNumSeqs: 8
extraArgs: ["--max-num-batched-tokens=512", "--num-gpu-blocks-override=2400"]
plugin:
  install: true
  repo: littlemex/vllm-neuron
  ref: release-0.24.0.1.1.0
  modelDir: nemotron_h
  registerClass: NemotronHForCausalLM
```

`plugin.install` を有効にすると、公開されている vLLM Neuron のイメージのまま起動し、Pod の起動時にフォークからモデルのコードを取ってきて plugin に組み込みます。`--num-gpu-blocks-override`（名前に gpu とありますが、Neuron でも KV ブロック数の指定に使います）は、8 リクエスト分の最大長の KV（8 × 8192 トークン ÷ 32 トークン/ブロック = 2,048 ブロック）より多めにしています。KV の見積もりが同時数に足りないと、スケジューラが新しいリクエストを待たせるので、同時数が上がりません。

`--volume` には、コンパイル結果のキャッシュを置く PersistentVolume の名前を渡します。

```bash
export PV_NAME=my-neuron-cache
./up.sh nemotron-h --pool trn2 --namespace serving --volume "$PV_NAME"
```

手元では、キャッシュのない初回は NEFF へのコンパイルに 20〜40 分ほどかかりました。2 回目以降はキャッシュが効いて短くなります。

:::message alert
起動時にブランチからコードを取ってくるのは検証用の割り切りです。実際に運用するときは、コミットを固定し、モデルを組み込んだイメージをビルドしてください。
:::

# まとめ

vLLM Neuron plugin は、vLLM 本体を変えずに、スケジューラと ModelRunner を Trainium 向けに差し替える仕組みでした。NemotronH はその枠に、5 つの契約メソッドを実装したモデル一式として入れました。KV は Attention の 6 層だけを申告し、Mamba2 の状態はモデル側に置いています。Mamba2 は chunked SSD に、MoE の専門家選びは比較と和だけの形に書き直しました。そのうえで、プロファイラで測った大きい部分から NKI カーネルに置き換え、生成は 72.5 から 9.2 ms/トークン、読み込みは約 800 から約 2,600 トークン/秒になりました。最後に、先頭 KV ブロック番号でリクエストごとの状態の行を引く状態プールを作り、8 リクエストの同時処理で合計 216 トークン/秒まで伸ばしました。
