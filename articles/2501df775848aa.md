## はじめに

[Prismyra](https://github.com/littlemex/Prismyra) は、1 つの文書に対して「はい/いいえ」や「選択肢のどれか」のような決まった形の質問に、何度も速く答えるための推論エンジンです。文章を新しく作る(生成する)ことはせず、モデルがすでに持っている確率を読み出すだけで答えを決めます。この記事では、Prismyra がその答えをどう速く出すか、そして検証した構成でどう同じ答えを返し続けるか、サービング(モデルを動かして応答を返す側)の仕組みに絞って見ていきます。質問が 4 件を下回るならふつうの生成エンジンのほうが速いこと、同じ系列の `autotrust/JEV-35B` との比較で初めて明確な差が出ることも、あとで数字とともに説明します。学習でどう精度を上げたかは、別の記事で扱います。紹介するモデルは商用利用できるデータだけで学習した [`littlemex/prismyra-decision-35b-a3b-fp8`](https://huggingface.co/littlemex/prismyra-decision-35b-a3b-fp8) と [`littlemex/prismyra-decision-35b-a3b-nvfp4`](https://huggingface.co/littlemex/prismyra-decision-35b-a3b-nvfp4) の 2 つです。

## Decision Model とは何か

Prismyra が属する Decision Model(決定モデル)は、共有された 1 つの文書について、閉じた選択肢を持つ質問に答える専用のモデルです。文章を 1 字も生成しないので、出力は常に宣言した選択肢のどれかになります。この形のおかげで、文書を 1 回読んだあとの質問 1 件あたりのコストが、ふつうの文章生成エンジンより大きく下がります。[`README.md`](https://github.com/littlemex/Prismyra/blob/e617f059f86c94560f025d19ba931e4c8b70d575/README.md) にある、質問数ごとの応答時間の比較です(条件は README に明記されていませんが、Prismyra 側はこの記事が扱う FP8 のチェックポイントです)。

| 質問数 | Prismyra | vLLM(文章生成) |
|---|---:|---:|
| 1 | 226 ms | **134 ms** |
| 2 | 227 ms | 181 ms |
| 3 | 228 ms | 228 ms |
| 4 | 229 ms | 275 ms |
| 16 | 228 ms | 839 ms |
| 64 | 320 ms | 3,095 ms |
| 128 | 503 ms | 6,103 ms |

3 件まではほぼ互角で、4 件から Prismyra が明確に速くなります。文章を生成するエンジンは質問が増えるたびにほぼ同じコストを払い直すのに対し、Prismyra は文書を読む分だけ先に払い、質問はそこに相乗りするからです。**質問が 4 件を下回るなら、この比較ではふつうの生成エンジンを使うべきです。**

最小限の呼び方はこれだけです。文書と質問を渡すと、宣言した選択肢ごとの確率が返ります。

```python
from prismyra import Prismyra, Boolean

engine = Prismyra("Qwen/Qwen3.6-35B-A3B-FP8")
result = engine.ask(
    context="Returns are accepted within thirty days of delivery.",
    questions=[Boolean(id="within_30", prompt="Is there a thirty day limit?")],
)
result["within_30"].value  # True
```

## 読み出しを使う理由

Prismyra に、質問用の分類ヘッド(head)は既定で付いていません。答えは、質問で宣言した選択肢を綴る 1 トークンを、モデル自身の出力埋め込み(`lm_head` の重み)でそのまま採点して出します。実装を見ると、選択肢のトークン ID 分だけ埋め込み行列から行を取り出し、隠れ状態と内積を取っているだけです([`prismyra/readout.py`](https://github.com/littlemex/Prismyra/blob/e617f059f86c94560f025d19ba931e4c8b70d575/prismyra/readout.py#L211-L228) の `logits_for`)。この読み出し自体のために新しく学習した重みは無いという意味で、答えはゼロショットです(紹介する 2 つのチェックポイントの本体がどう学習されているかは、後述します)。

```python
return [
    (hidden[row : row + 1].float() @ unembedding[ids].to(hidden.device).float().t())[0]
    for row, ids in enumerate(token_ids)
]
```

一回の forward で宣言した選択肢の行だけに触れて答えが決まるので、文章を 1 トークンずつ生成するループが要りません。これが次の章で見る、文書を 1 回読めば質問は相乗りできるという設計の土台になります。

得た点数は、宣言した選択肢だけを対象に softmax します。だからこの確率は「あなたが並べた選択肢のうちどれを好むか」という相対的な好みです。「はい」が 80%と出ても「この答えが 80%の確率で正しい」という意味ではありません。キャリブレーションされておらず、別の選択肢の組で出した確率とは比較もできません。[`docs/READOUT.md`](https://github.com/littlemex/Prismyra/blob/e617f059f86c94560f025d19ba931e4c8b70d575/docs/READOUT.md) はこれを明文化し、意図的に `confidence` という名前のフィールドを持たせていません。

一方で、毎回まったく同じ選択肢の組で聞かれる質問だけに使える `heads.py` という仕組みも用意されています([`docs/HEADS.md`](https://github.com/littlemex/Prismyra/blob/e617f059f86c94560f025d19ba931e4c8b70d575/docs/HEADS.md))。既定では登録されておらず、opt-in で別途学習した小さな行列に差し替える機能です。使われた答えには、その head の名前が入った `read_by` フィールドが付き、対象外の質問はいつもの読み出しにビット単位で一致したまま戻ります。

## 文書を 1 回読む fork の仕組み

質問が増えても文書を読み直さない理由は、モデルが文脈を読んだあとに持つ 3 種類の状態の扱いの違いにあります。

| 状態 | 書き込まれるか | 結果 |
|---|---|---|
| 文脈の key/value | 読まれるだけ | 1 回書けば全部の枝に使える |
| 再帰・畳み込みの状態(漸化式の中間値) | 枝ごとに進む | 枝ごとに**コピー**が必要 |
| 枝自身のトークン | 枝ごとに書く | 最初から枝専用 |

[`prismyra/cache.py`](https://github.com/littlemex/Prismyra/blob/e617f059f86c94560f025d19ba931e4c8b70d575/prismyra/cache.py#L57-L75) の `ForkLayer` は、文脈 1 行分の書き込みを枝の数だけある全ての行に書き、読むときは呼び出し元が持ってきた行だけを返します。文脈の key/value については、この方法で枝ごとのコピーが要らなくなります(再帰・畳み込みの状態は、表のとおり枝ごとにコピーします)。以前は重みと並べて 48 GiB のカードに文脈を 3 個しか載せられませんでしたが、今は 19 個載ります。

枝どうしが互いを見られないのは、2 つの仕組みによります。1 つは枝ごとに状態を別々に書くこと、もう 1 つは枝のトークンが文脈より後ろに置かれ、注意機構(attention)が自分より前のトークンしか見ないことです。一方、文脈側にパディングを足すのは安全ではありません。再帰状態はこの仕組みで止められないため、文脈に詰め物を足すと答えが最大 1.08e-01 動くと計測されています(バッチの形だけを変えた場合の 2.4e-02 より大きな動きです)。

![文脈の key/value は 1 回だけ書き、質問ごとの枝は自分の再帰状態とトークンだけを書く](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/2501df775848aa/zenn/articles/2501df775848aa/fig1-fork.png)
*文脈は 1 回だけ読み、質問ごとの枝(fork)がそれぞれ答えを持って帰る。*

コストの見積もりはこの形のまま式になります。

$$
\text{total} \approx \text{context} + \text{per\_group} \times \left\lceil \frac{\text{questions}}{\text{group}} \right\rceil
$$

1 回の traversal(モデルの重みを 1 通り読む処理)が運べる質問の数(`group`)を超えると、もう 1 回 traversal が走ります。あとで見る約 5,000 トークン・L40S の構成では `group` は 32 で、33 番目の質問が高くつき、32 番目がほぼ無料になるのはこのためです。

## 並列の処理と文書キャッシュ

複数の質問が同じタイミングで届くと、1 つの worker にそのまま積むだけでは「全員まとめて遅くなる」という形で遅くなります。8 件が同時に届いた場合、まとめて処理する(interleaved)と中央値 2,113 ms・最初の答えも 2,113 ms かかるのに対し、順番に答える(queued)と中央値 945 ms・最初の答えは 214 ms で返ります。

同じ文書に複数の質問が別々の HTTP リクエストで届く場合は、`open_shelf` で文書の key/value を device 上に残しておく「shelf(棚)」が使えます。RACE の 80 文書で検証したところ、`ask()` と完全に一致する答えが得られています。`Batcher(lanes=N)` は、この shelf を複数本の CUDA ストリームで同時に走らせる仕組みです。文書の内容のハッシュで常に同じレーンへ送るので、そのレーンの棚にキャッシュが残り続け、使い続けられます。[`prismyra/schedule.py`](https://github.com/littlemex/Prismyra/blob/e617f059f86c94560f025d19ba931e4c8b70d575/prismyra/schedule.py#L165) の `Batcher` がその実装です。

`autotrust/JEV-27B` 系が持つ `/v1/decide` という判定専用の API も、この shelf を使えるようになっています(JEV 自体との速さの比較は後述しますが、こちらはその API 形式だけを真似た機能です)。fp8 チェックポイント・L40S・3,446 トークンの文書で、毎回新しい文書を使う場合と、同じ文書を繰り返して棚のキャッシュに当てる場合を比べた実測です。

| 質問数 | `/v1/decide`(毎回新しい文書、棚なし) | `/v1/decide`(同じ文書を繰り返す、棚から) |
|---|---:|---:|
| 1 | 289.4 ms | 100.0 ms |
| 2 | 291.4 ms | 102.2 ms |
| 16 | 321.7 ms | 130.4 ms |

棚に乗った文書への 2 回目以降の質問は、読み直しが無いぶん 2.4〜2.9 倍速く答えます。ただし `--batcher` を有効にすると `paged=True` の保存方式になり、既定の保存方式(joined)とは答えが完全には一致しない場合があります。1,893 件の開発用データセットで調べると 1.69% の答えが入れ替わりますが、全体の正解率の差は +0.21 ポイントで有意ではありません。`--batcher` 無しの経路とビット単位で同じ答えが必要な場面では外す、文書をまとめて速く答えたい場面では付ける、という使い分けです。

![文書ごとの shelf が key/value を device 上に残し、同じ文書は常に同じレーンに送られて読み直されない](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/2501df775848aa/zenn/articles/2501df775848aa/fig2-shelf.png)
*同じ文書への 2 回目以降の質問は、棚(shelf)に残った key/value を読み直さずに答える。*

## カーネルの工夫と決定性

Prismyra はモデルの forward 処理そのものを書き換えず、特定のモジュールだけを fused kernel(複数の処理を 1 回の起動にまとめたもの)で置き換えます。約 5,000 トークンの文脈で、置き換え前後を直接比べた測定です。

| 工夫 | 何をするか | 速さの効果 |
|---|---|---|
| ルーティング先の専門家(routed experts)を 1 本のカーネルに | トークンを専門家ごとに並べ替えるコピーを無くす | 288.1 ms → 208.3 ms |
| 密な射影(dense projection)を vLLM と別の FP8 block 量子化カーネルに | `q/k/v` などの射影を別のカーネルで実行する | 204.5 ms → 185.7 ms(量子化の丸め方が変わるだけで、float32 を基準にした精度への距離は変化せず) |
| 同じ入力を使う射影をまとめて 1 回の行列積に(dense fusion) | `q/k/v` や共有エキスパートの gate/up などをまとめて実行 | branch 幅(16〜32 行)で 32〜54% 速い。それぞれ別に呼ぶ場合とビット単位で一致 |
| 正規化と出力ゲートを 1 つのカーネルに融合 | elementwise の複数回起動を 1 回に | 792 ms → 712 ms(64 質問)、検証用の入力に対して誤差 0.0 |
| rope の回転とゲートの乗算を融合 | 複数回の乗算・加算を 1 回のカーネル起動に | 1〜64 問で 0.5〜0.7% 速い。eager 実装とビット単位で一致 |

ここからが決定性の話です。問題になりやすいのは「同じ入力でも、一緒に走る他の行の数や、プロセスが変わると答えが変わってしまう」ことです。Prismyra はこれを何重かのチェックで塞いでいます。まず Triton の autotuning(カーネルの設定を実行時に計測して選ぶ仕組み)は、コールドスタートのたびに違う設定を選びやすく、ある Triton カーネルはコールドスタートの約 5 回に 1 回だけ `num_warps=2` を選び(他は 4)、確率が最大 0.59 動いていました。これを GPU の世代ごとに 1 つの設定へ固定することで止めています。さらに、`aten::mm`・`addmm`・`matmul`・`linear` という行列積全般に固定タイル幅のカーネルを登録する仕組み(batch invariance、同時に走る行数が変わっても答えが変わらないようにする仕組み)を入れたところ、companion(同時に読む他の文書)と質問数を全組み合わせで振った監査が、RTX PRO 4500 の最初の実行での 4,392 件中 1,692 件の不一致から、両対応カード(L40S・RTX PRO 4500)で 4,392 件中 0 件まで減りました。

専門家混合(MoE)のカーネルでは、K 方向の積み上げに使う `BLOCK_SIZE_K` と `SPLIT_K` を固定すれば積算の順序が変わらないため、出力側のタイル形(`BLOCK_SIZE_M`・`BLOCK_SIZE_N`・`GROUP_SIZE_M`・`num_warps`・`num_stages`)は候補どうしの一致を確認した範囲で自由に変えられます。この自由を使って、1 問だけの一発読み(one-pass)経路のタイルを「M が 64 を超える全部で 1 つに固定」からバケットごとに選ぶ方式へ作り直したところ、3,401 トークンと 5,315 トークンの実文書でそれぞれ +16.3%・+14.1% 速くなりました。

融合カーネルを作る過程で見つかった罠が、Triton の bfloat16 への変換です。`x.to(tl.bfloat16)` は、このビルドでは最近接偶数への丸め(round-to-nearest-even:PyTorch/CUDA のどの bfloat16 カーネルも使う丸め方)ではなく、ゼロ方向への切り捨てになっていました。rope とゲートの融合カーネルは、eager 実装が同じ計算を 3 回の別々のカーネル起動に分けて丸めていたのと同じ結果をビット単位で再現する必要があったため、ビットを直接操作して最近接偶数への丸めをやり直す関数([`prismyra/kernels/qwen3_moe.py`](https://github.com/littlemex/Prismyra/blob/e617f059f86c94560f025d19ba931e4c8b70d575/prismyra/kernels/qwen3_moe.py#L469-L492) の `_round_bf16_rne`)を自前で書いて差し込んでいます。

1 問だけの短い質問は、カーネル自体の実行時間より起動そのものの回数が負担になります。232 トークンの文脈で計測すると壁時計で 92 ms かかる一方、カーネルの実行時間は 39.9 ms しかなく、差は 2,564 回のカーネル起動そのものです。この形は、文脈の長さごとに一度録画(CUDA graph)して後は再生するだけで縮められ、HTTP 経由の中央値で 98.1 ms から 44.7 ms まで落ちています。録画をそのまま使うと答えが変わる場合があったため、行数によって計算のやり方が変わる少数の射影(ルーター、共有エキスパートの gate、再帰の小さい射影)だけを録画の切れ目にして毎回その場で実行し、残りだけを録画区間として繋いでいます。各録画区間はその長さの範囲でもっとも短い入力と長い入力の両方で eager 実装とビット単位で一致することを確認しています。

![同じ入力は、量子化・自動チューニング・録画のどれを通っても同じビット列を返す。決定性を守る仕組みはカーネルごとではなくプロセス全体にかかる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/2501df775848aa/zenn/articles/2501df775848aa/fig3-determinism.png)
*速くするためのカーネル(緑)と、それらを一緒に支える決定性の仕組み(黄、プロセス全体にかかる)。*

NVIDIA の Blackwell 世代(sm_120、例えば RTX PRO 4500)では、専門家の重みを NVFP4(4 bit の浮動小数点)に変換する経路も選べます。36 層の専門家の重みは FP8 だと約 29 GB あり、32 GB のカードには載りません。NVFP4 に変換すると約 16 GB になり、同じ 36 層がそのまま載ります。この変換による精度差は、変換前の FP8 の重みと比べてノイズと区別できない範囲でした(1,400 問のデータセットで −0.07 点、95% 区間 [−0.86, +0.79]。この記事が紹介するサービング経路とは別の経路で計測した数字です)。密な射影の一部(`self_attn` と共有エキスパート)も NVFP4 に変換する設定(`PRISMYRA_DENSE=nvfp4`、実験的機能)は、RTX PRO 4500・1 問の計測で 4.4〜6.3% 追加で速くなります。再帰の射影まで変換すると 15.6〜19.4% まで伸びますが、4 つの精度評価セットのうち少なくとも 1 つで有意に精度が落ちたため、既定では再帰の射影は FP8 のまま残しています。

## 2 つのモデルの紹介と使い方

Prismyra が配布しているチェックポイントのうち、商用利用できるデータだけで学習した系列が [`littlemex/prismyra-decision-35b-a3b-fp8`](https://huggingface.co/littlemex/prismyra-decision-35b-a3b-fp8) と [`littlemex/prismyra-decision-35b-a3b-nvfp4`](https://huggingface.co/littlemex/prismyra-decision-35b-a3b-nvfp4) です。どちらを選ぶかは GPU の世代とメモリで決まります。`fp8` はこのプロジェクトのカーネルが動く GPU なら動き、`nvfp4` は前の章の NVFP4 変換が要るため Blackwell 限定ですが、同じ 36 層をより小さいカードに載せられます。

学習データは、商用利用と派生モデルの学習が明確に許可されている素材だけで作られており、教師信号(ラベル付けや蒸留のもとになる出力)もオープンな重みのモデル(Kimi K3、DeepSeek V3.2)かこのプロジェクト自身の出力しか使っていません。閉じた独自モデルの出力は、学習データのどこにも使われていません([`docs/DATA_PROVENANCE.md`](https://github.com/littlemex/Prismyra/blob/e617f059f86c94560f025d19ba931e4c8b70d575/docs/DATA_PROVENANCE.md))。この記事は学習そのものには踏み込みませんが、サービングの土台になっている事実として押さえておいてください。

サーバーとして動かす場合は次の通りです。

```bash
pip install -e ".[server,fast]"
prismyra-serve --host 127.0.0.1 --port 8000
curl -s localhost:8000/health
```

既存システムが `autotrust/JEV-27B` の `/v1/decide` という形で判定を受け取っている場合は、Prismyra も同じ入出力の形でそのまま差し替えられます。同じ `autotrust` 系列のより新しいモデルである JEV-35B 系との速さの比較は、次の章で扱います。

## 速さの実測

速さの比較で一番大事なのは、測り方がどちらにも公平かどうかです。最初の計測では、JEV-35B-NVFP4 のサーバーが `enable_prefix_caching=True` で同じ文書を使い回すキャッシュを持っていたのに対し、Prismyra の `ask()` は呼ぶたびに文書を新しく読む作りだったため、2 回の空撃ちと 7 回の計測をすべて同じ文書で行う測り方は JEV 側だけにキャッシュの得をさせていました。実際、JEV-35B-NVFP4 は 2 回目以降の呼び出しで文書の 3,168 / 3,446 トークンがキャッシュに当たっていたことが確認されています。

毎回ちがう文書を使う(どちらにもキャッシュの得が無い)測り方で、同じ日・同じハードウェアで取り直した結果です(3,446 トークンの文書、2 回の空撃ちのあと 7 回の中央値)。この「公平」はキャッシュ利用の非対称性を取り除いたという意味で、GPU の機種・枚数・量子化の精度まで揃えたものではありません。

| 質問数 | `fp8`(L40S 1 枚) | `nvfp4`(RTX PRO 4500 1 枚) | JEV-35B(L40S 2 枚、TP=2) | JEV-35B-NVFP4(RTX PRO 4500 1 枚) |
|---|---:|---:|---:|---:|
| 1 | **154.0 ms** | **155.1 ms** | 447.1 ms | 231.3 ms |
| 16 | **254.6 ms** | **199.1 ms** | 1,040.3 ms | 595.1 ms |
| 64 | **373.5 ms** | **331.0 ms** | 3,119.8 ms | 1,882.5 ms |

この条件では、Prismyra の 2 つのチェックポイントは質問 1 件の時点からすでに速く、`fp8` は JEV-35B の 2.9 倍、`nvfp4` は JEV-35B-NVFP4 の 1.5 倍です。64 件まで増やすと差はさらに開き、8.4 倍・5.7 倍になります。参考までに、文書を開いたまま `open_context` を再利用して質問を重ねる場合は、1 問の応答が `fp8` で 91.3 ms、`nvfp4` で 67.0 ms まで縮みます。これは、最初の(キャッシュの非対称性が残っていた)測定で JEV 側がキャッシュ有りで出した最良の数字(99.2 ms・82.3 ms)より速い値ですが、測定回が異なる参考比較です。

もう 1 つ、決定性の面でも差があります。JEV-35B-NVFP4 は、同じ入力を 1 つのプロセスで 11 回聞いても 8 通りの異なる確率を返しましたが、`fp8`・`nvfp4`・JEV-35B(bf16)はいずれも 11 回とも同じ値を返しています。前章のカーネルの工夫が守っているのは、まさにこの「同じ入力に同じ答え」です。

約 5,000 トークンの文脈における L40S 上のコストモデルは次の式に近づきます。

$$
\text{total} \approx 138\,\text{ms} + 92\,\text{ms} \times \left\lceil \frac{\text{questions}}{32} \right\rceil
$$

ここまでに見た個々の工夫は、それぞれ別の条件で測ったものなので単純に足し算はできませんが、同じ方向に効きます。1 問を一発読みする経路の録画で HTTP 経由の中央値が 98.1 ms から 44.7 ms に、`interleaved_fork`(文脈読みと最初の枝をまとめて読む設定、既定で有効)で L40S の 16 問が 15.2%・64 問が 9.6% 速くなり(RTX PRO 4500 では 5.9%・1.3%)、rope とゲートの融合でさらに 0.5〜0.7% 縮みます。どれも答えのビット列を変えない前提で積まれているので、速さのための設定を増やしても精度の計測結果は使い続けられます。

## まとめ

Prismyra の背骨になっているのは、文脈の key/value を 1 回だけ書き、質問を枝として相乗りさせるという 1 点です。そこから、質問が増えても traversal は `group` 単位でしか増えないコスト構造、HTTP をまたいで文書のキャッシュを使い続ける棚とレーン、そして答えのビット列を変えずに速くするカーネルの工夫が、同じ設計の上に積まれています。商用利用できるデータだけで学習した `fp8` と `nvfp4` は、5 つの評価セットをプールした比較で、同じデータの制約から先行の研究用チェックポイントに 2.43 ポイント劣ります(5 セットのうち 2 セットで負け、3 セットは互角)。一方、同じ `autotrust` 系列の JEV-35B との比較では `fp8` がプールで +0.68 ポイント、`nvfp4` は JEV-35B-NVFP4 自身の量子化による精度低下も効いてプールで +7.10 ポイントと、互角以上の精度を保ったまま、公平な条件で測った速さでは質問 1 件の時点から明確に勝っています。学習データをどう増やし、精度をどう上げてきたかは、別の記事で扱います。
