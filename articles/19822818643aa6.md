## はじめに

SGLang で prefill エンジンと decode エンジンを分けて動かすと、2 つのエンジンの間で KV キャッシュ(それまでに読んだ文脈の attention 計算の途中結果)を転送します。この転送には NIXL を使い、バックエンドに `LIBFABRIC` を選んで `FI_PROVIDER=efa` で EFA(Elastic Fabric Adapter、AWS の低遅延ネットワークカード)を指定すれば、EFA を使って転送してくれるはずです。NIXL と EFA を使った分離推論環境そのものの作り方は「[AWS 上で NIXL と EFA を使って分離推論の検証環境を作る](https://zenn.dev/tosshi/articles/009bb138491dd1)」で説明されているので、本記事はそこから一歩進んで、同じノードの中での転送に絞ります。

| 想定していたこと | 今回の構成(SGLang 0.5.12.post1・NIXL 1.1.0・libfabric 2.4.0)で計測して分かったこと |
|---|---|
| `FI_PROVIDER=efa` を指定したので EFA デバイスを通る | 既定の設定では、同じノード内の相手には EFA デバイスを一度も通らない |
| EFA デバイスを通る経路は、孤立した 1 回の転送でも SGLang の実リクエストでも shm より遅いはずだ | 孤立した 1 回の転送では shm より遅いが、SGLang の実リクエストでは shm より明らかに速かった |

同じノードの中で prefill と decode を動かした場合、今回計測した条件では EFA デバイスを一度も通っていませんでした。libfabric の EFA プロバイダは、相手が同じノードにいることを検出すると、既定の設定では自動的に `shm` プロバイダ(shared memory の略で、同じノード内の通信を受け持つ libfabric のプロバイダ)に処理を渡すためです。

さらに、この shm 経由の転送は、孤立した 1 回だけの転送では最速なのに、SGLang の実リクエストで計測すると shm off や UCX より大幅に遅いという結果になりました。本記事では、同じノード内にある 3 つの転送経路(UCX、LIBFABRIC の既定動作、LIBFABRIC で shm を無効にした場合)がどんな通信をしているかをソースコードと実機ログで追い、どちらが速いかを計測した結果をまとめます。先に断っておくと、この「孤立した計測」と「SGLang の実リクエストでの計測」は転送の形も測り方も異なる 2 種類の実験であり、同じ条件のまま負荷だけを上げて逆転が起きる様子を直接確かめたものではありません。原因の内部構造まで完全に特定できたわけではない点も、推測の範囲として本文で区別します。

## 検証した環境と測り方

![SGLang が出すステージ別カウンタと EFA デバイスのハードウェアカウンタの両方を使う。ホストネットワークの Pod ではハードウェアカウンタを読めるが、ホストネットワークを使わない Pod の内側からはそのディレクトリ自体が見えない](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/19822818643aa6/zenn/articles/19822818643aa6/measurement-setup.png)
*測定は SGLang 側のステージ別カウンタと EFA デバイス自身のハードウェアカウンタの 2 本立てで行いました。*

計測の軸はこの 2 本です。SGLang の `--enable-metrics` が出すステージ別カウンタは、`prefill_transfer_kv_cache` などの区間ごとに転送にかかった時間を積み上げたもの、EFA デバイスのハードウェアカウンタは `sysfs` 配下の値を転送の前後で読んで差分を取ったものです。ホストネットワークを使わない Pod の内側からはハードウェアカウンタのディレクトリ自体が見えません。この「見えない」ことと、後述するハードウェアカウンタの差分が「0 だった」ことは別の事実なので、この記事のハードウェアカウンタの値はすべてホストネットワークを使う別の Pod から読んでいます。

| 項目 | 値(今回の構成) |
|---|---|
| モデル | DeepSeek-V2-Lite-Chat |
| 推論エンジン | SGLang 0.5.12.post1(prefill・decode とも TP 2) |
| KV キャッシュ転送ライブラリ | NIXL 1.1.0(一部の介入実験のみ一時的に 1.4.0) |
| ネットワークライブラリ | libfabric 2.4.0(EFA installer 1.47.0) |
| インスタンス | g7.48xlarge 1 台(prefill と decode を同居、EFA デバイス 2 枚) |
| リクエスト | 入力 8,192 トークン・出力 256 トークン、到着はポアソン過程 |

到着シードの本数は実験ごとに違います。後述する 3 シード平均と 1 シードの基準値、単発実行の値を区別して書くので、表やグラフの数値を見るときは、どの実験のものかを本文で確認してください。以降の数値はすべてこの環境での実測、ソースコードを読んで確認した事実、まだ確認できていない点をそれぞれ区別して書きます。

## 同じノード内にある 3 つの経路

![UCX・LIBFABRIC(既定)・LIBFABRIC(shm off)の 3 つの経路。どの層が SGLang・NIXL/UCX/libfabric・EFA ハードウェアのどれに属するかを色で示す](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/19822818643aa6/zenn/articles/19822818643aa6/overview-map.png)
*今回の構成では、NIXL が使う UCX または libfabric/EFA プロバイダが、それぞれ同じノード上の GPU 同士向けの安いコピー手段を選びました。中身は経路ごとに違います。*

LIBFABRIC はさらに `FI_EFA_ENABLE_SHM_TRANSFER` という設定で挙動が変わるので、合わせて 3 つの経路を見ていきます。UCX の経路(経路 1)は cuda_ipc という GPU 間の直接コピーを自動選択し、LIBFABRIC の既定動作(経路 2)は shm プロバイダという別の GPU 間直接コピーに処理を渡し、LIBFABRIC で shm を切った場合(経路 3)だけが実際に EFA デバイスへ到達します。今回確認した範囲では、実データそのものはどの経路でもホストメモリ上の一時バッファを経由しません(shm プロバイダの中身は次の節で見ます)。ただし、転送の発行・通知・完了の確認には CPU 上のソフトウェアが関わります。

| 経路 | 実データの経路 | EFA デバイスを使うか |
|---|---|---|
| 経路 1: UCX(既定) | cuda_ipc によるゼロコピー | 使わない |
| 経路 2: LIBFABRIC(既定、shm) | shm プロバイダによる直接コピー | 使わない |
| 経路 3: LIBFABRIC、shm off | EFA デバイスへの RDMA WRITE | 使う(同じ 1 枚にループバック) |

## 経路が決まる場所

![FI_PROVIDER=efa を指定しても、必ず EFA デバイスを通るとは限らない。libfabric の EFA プロバイダは、相手のアドレスを登録する時点で同じノードかどうかを判定し、shm プロバイダのアドレス表にも登録する](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/19822818643aa6/zenn/articles/19822818643aa6/decision-point.png)
*同じノードかどうかを判定して経路を切り替えているのは NIXL 自身ではなく、libfabric の EFA プロバイダです。*

:::message
よくある誤解: `FI_PROVIDER=efa` を指定すれば EFA デバイスを通る、というのは言い過ぎです。正確には、相手のアドレスを登録する時点で同じノードだと判定されると、既定では shm プロバイダに切り替わります。
:::

LIBFABRIC バックエンドでは、NIXL 自身は同じノードかどうかを特別扱いしません。相手のアドレスを登録するとき([`fi_av_insert()`](https://ofiwg.github.io/libfabric/main/man/fi_av.3.html) が呼ばれたとき)、EFA プロバイダの [`efa_conn_rdm_insert_shm_av()`](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/efa/src/efa_conn.c#L104-L148) が、内部で [`efa_is_local_peer()`](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/efa/src/efa_conn.c#L14-L31) を呼んで相手が同じノードかどうかを判定し、同じノードであれば(かつ shm 用の受け口があれば)その相手を shm プロバイダのアドレス表にも登録します。この判定は転送のたびに行われるわけではなく、接続の確立時に 1 回だけ行われます。以降のやり取りは shm プロバイダが処理し、EFA デバイス(ネットワークカード)の出番はありません。ログを詳しく出さないと気付けない挙動です。

## shm 経路: 送信から受信側の記帳まで

![送信側がコピーして即座に完了を確定し、write_async の通知をコマンドキューに積む。受信側の進行ループがそのキューを処理したときだけ受信カウンタが進む](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/19822818643aa6/zenn/articles/19822818643aa6/shm-write-sequence.png)
*shm プロバイダの中身は [`smr_rma_fast()`](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_rma.c#L58-L99) です。送信側プロセスが受信側のメモリへ直接バイト列をコピーします(CUDA IPC と同種の、相手のメモリへ直接書き込む方式で、ホストメモリを経由する一時バッファではありません)。*

以下は、遅さの原因を確定させる説明ではなく、候補となる仕組みをソースコードで調べた結果です。送信側はこのコピーが終わった時点で自分の完了を同期的に確定し、受信側の状況を待ちません。コピーと同時に、送信側プロセスは `write_async` という印の付いた通知を、受信側に宛てた共有メモリ上のコマンドキューに積みます。libfabric では、届いた通知の後片付け(カウンタの更新など)は自動では進まず、受信側プロセスが libfabric の関数を呼んだとき(本記事ではこれを「進行ループ」と呼びます。独立した常駐スレッドではなく、受信側が処理の中で呼ぶ関数です)にだけ、溜まっている処理をまとめて片付けます。コマンドキューに積まれた通知は、受信側が自分の進行ループ([`smr_progress_cmd()`](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/shm/src/smr_progress.c#L1213-L1266))を実行してそのキューを処理するまで、受信側自身の受信カウンタには反映されません。**送信側はコピーが終わった瞬間に完了しますが、受信側が「このデータが届いた」と記帳できるかどうかは、受信側自身がいつ進行ループを呼ぶかにかかっています。**

![通知が束で届くと、受信側の進行ループが動くまでコマンドキューに積み上がる。進行ループが動いた分だけ受信カウンタが追いついて増える](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/19822818643aa6/zenn/articles/19822818643aa6/shm-write-sequence.gif)
*GIF は上の図と同じ仕組みを時間方向に見せた概念図で、通知が束で届くとコマンドキューに積み上がり、進行ループが動いた分だけ受信カウンタが追いつく様子を描いています。実測のタイミングそのものではありません。*

この記帳の遅れが、実際に prefill 側の転送ステージの計測時間(送信側で測っている値)をどう遅くしているのか、内部の正確な経路までは今回確認できていません。送信側はコピーが終わった時点で受信側を待たない作りなので、受信側の記帳の遅れが送信側の計測時間を直接延ばすには、コマンドキューが満杯になって送信側が待たされる、といった受信側から送信側への逆方向の圧力が必要です。この逆方向の圧力があるかどうかも今回は確認できていません。確認できているのは、受信側の記帳が受信側自身のソフトウェアに依存する仕組みがソースコード上に存在することと、後述するように shm を無効にすると SGLang の計測時間が大きく減る実行があったことの 2 点で、両者を直接つなぐ内部の詳しい挙動は推測の範囲です。NIXL や SGLang の decode 側が、この受信カウンタの先でどう「KV が届いた」と判断しているかも、今回のソース読解の範囲外です。

::::details gdrcopy は使われていません
GPU のメモリに CPU 側から直接アクセスするための高速化ライブラリ gdrcopy も、ログ上では最初に試されます。ただしカーネル側のデバイスファイルがこの環境に存在しないため失敗し、常に gdrcopy なしの経路にフォールバックします。
::::

## shm off: EFA デバイスへの切り替え

![shm_ep が作られないため、書き込みは efa_rdm_rma_post_write() を経て本物の RDMA WRITE になり、ノードが選んだ 1 枚の EFA デバイスにループバックする](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/19822818643aa6/zenn/articles/19822818643aa6/shm-off-path.png)
*環境変数 `FI_EFA_ENABLE_SHM_TRANSFER` を 0 にすると、shm 用のエンドポイント(通信の受け口)が作られないため、同じノード宛てでも shm には振り分けられず、書き込みは EFA デバイス側の経路に進みます。*

shm を無効にすると、[`efa_shm_info_create()`](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/efa/src/efa_shm.c#L68-L77) がこの設定を見た時点で shm 用の情報を作らずに即座に戻るため、shm プロバイダの実体が一切作られません。その結果、EFA プロバイダ内の「相手がローカルで、かつ shm 用の受け口がある場合だけ shm を使う」という各種チェックは常に不成立になり、書き込みは本来のハードウェア経路に進みます。RDMA WRITE になるかどうかは別の条件判定で決まりますが、今回の実行ではその条件を満たし、本当の RDMA WRITE(ネットワークカードが相手の CPU を介さずに相手のメモリへ直接書き込む操作)が EFA デバイスに発行されていたことを、後述するバイト単位の裏取りで確認しました。今回の環境ではノードに EFA デバイスが 2 枚ありますが、ログで確認した限り、prefill と decode の両プロセスは同じ 1 枚のデバイスを選び、書き込みはそのデバイス自身に向けてループバックする形になります。

::::details ソースコードでの経路(関数の連鎖)
相手がローカルかどうかに関係なく、書き込みは本来のハードウェア経路である [`efa_rdm_rma_post_write()`](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/efa/src/rdm/efa_rdm_rma.c#L339-L404) に進み、条件を満たせば [`efa_rdm_rma_should_write_using_rdma()`](https://github.com/ofiwg/libfabric/blob/5a13558c2fcea15f1a6c4e8c06dc702e50724cf8/prov/efa/src/rdm/efa_rdm_rma.h#L30-L66) の判定を経て、本当の RDMA WRITE が発行されます。満たさない場合も、送信は eager/long message の送信プロトコルにフォールバックしますが、どちらの分岐でも EFA デバイスの QP(Queue Pair、送受信を管理する単位)に乗り、ホストメモリ経由の近道にはなりません。
::::

![RDMA WRITE が発行されてから EFA デバイスでループバックし、ハードウェアの完了が送信側の完了キューに届くまで](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/19822818643aa6/zenn/articles/19822818643aa6/shm-off-path.gif)
*これは送信側の完了の話です。送信側の完了は本物のハードウェア完了で、`ibv_cq`(ネットワークカードの完了キュー)から `IBV_WC_RDMA_WRITE` という完了種別を読み取って判定されます。*

受信側がこの書き込みの到着をどう把握するか(ハードウェア側の通知を使うのか、別の仕組みを使うのか)は、今回のソース読解では特定できておらず未確認です。

## UCX の cuda_ipc 自動選択

![UCX は何も設定しなくても同じノード上の GPU 同士の転送に cuda_ipc を自動選択する。実データはゼロコピーで動き、tcp や cma は制御メッセージのためだけに使われる](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/19822818643aa6/zenn/articles/19822818643aa6/ucx-cuda-ipc.png)
*今回の構成で UCX の転送方式を明示指定せずに実行したところ、起動ログ上は GPU バッファ間の書き込みに cuda_ipc の zero-copy が選ばれていました。*

UCX は、今回の構成では何も設定しなくても同じノード上の GPU 同士の転送に CUDA IPC(GPU のメモリを別プロセスから直接見える状態にする仕組み)を選びました。起動ログ上、実データも制御メッセージも EFA デバイスを経由していません。UCX がこの経路を選ぶ基準そのものはソースの読解対象にしていないため、起動ログで観測された挙動として扱います。UCX の送信側の完了の確定方法と、受信側がデータの到着をどう把握するかは、どちらも今回のソース読解の範囲外で未確認です。

## 3 つの経路を並べる

![同じ 1 件の転送が、UCX・LIBFABRIC(shm)・LIBFABRIC(shm off)のそれぞれでどの部品を経由するか](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/19822818643aa6/zenn/articles/19822818643aa6/three-paths-compare.png)
*shm プロバイダと UCX の cuda_ipc は、どちらも「ネットワークカードを使わない GPU 間の直接コピー」という点では同じ系統の方式です。実データの経路はこの図のとおり比較できますが、完了と記帳の仕組みまで比較できるのは経路 2(shm)だけです。*

今回ソース上で確認できた特徴の一つは、経路 2(shm)の受信カウンタ更新が受信側自身の進行ループに依存することです。経路 1(UCX)と経路 3(shm off)の受信側の記帳の仕組みは、今回のソース読解では確認できていません。そのため、3 つの経路のうちどこに本当の違いがあるのかは、経路 2 についてだけ言えることで、3 経路を横並びで「ここが違う」とまでは言えません。

| 項目 | 経路 1: UCX(既定) | 経路 2: LIBFABRIC(既定、shm) | 経路 3: LIBFABRIC、shm off |
|---|---|---|---|
| 完了の確定方法(送信側) | 未確認 | 同期的に即確定、受信側を待たない | ハードウェアの完了(`IBV_WC_RDMA_WRITE`) |
| 受信側の記帳の仕組み | 未確認 | 受信側自身の進行ループがキューを処理して初めて受信カウンタに反映 | 未確認 |

## バイト単位の裏取り

![EFA デバイスのハードウェアカウンタを転送の前後で読んだ差分。shm off のときだけカウンタが動き、期待値とほぼ一致する](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/19822818643aa6/zenn/articles/19822818643aa6/byte-proof.png)
*ログの文言だけでは「本当に EFA デバイスを通ったのか」は確証にならないため、EFA デバイスのハードウェアカウンタを転送の前後で読んで差分を取りました。*

今回の構成(TP 2・ページサイズ 1)で 17 リクエストぶんの転送を行ったとき、経路 2(shm)と経路 1(UCX)ではこのカウンタはどちらも 0 のままで、経路 3(shm off)のときだけ動きました。期待値は、1 リクエスト・1 ランクぶんの KV データ量を

$$
254{,}803{,}968 = 8{,}192 \times 27 \times 576 \times 2
$$

(トークン数 × 層数 × 値の数 × バイト数)として、それを 2 ランク × 17 リクエストぶん積み上げた値です。DeepSeek-V2 の MLA(Multi-head Latent Attention)が持つ潜在 KV は TP で分割されず各ランクに複製されるため、1 ランクあたりの量に単純にランク数を掛けられます。経路 3 の実測は $8{,}663{,}389{,}312$ バイトで、期待値 $8{,}663{,}334{,}912$ バイトとの比は $1.0000063$、差は約 0.0006 パーセント(約 54 KB)でした。このときの書き込み回数は 3,742 回(リクエスト・ランクあたり平均 110 回ほど)で、転送直前に 20 秒間トラフィックを止めた区間ではカウンタの動きは完全にゼロでした。

:::message alert
EFA のハードウェアカウンタは、Kubernetes の Pod がホストネットワークを使わない設定だと Pod の中からは見えず、どの転送方式を使っていてもバイト数が 0 だったという結果しか得られません。同じノードでホストネットワークを使う別の Pod から読むと、同じデバイスで正しくカウンタが見えました。この sysfs の見え方の違いがなぜ Pod のネットワーク namespace によって起きるのかは、カーネル側の正確な理由まで確認できていません。
:::

## 混雑時の転送時間

![到着レート 1・2 req/s での転送ステージ時間。経路 2(shm)の値は 1 req/s の 1 シードのみで、経路 3(shm off)はページサイズ 64 の方が短い](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/19822818643aa6/zenn/articles/19822818643aa6/transfer-stage-times.png)
*ステージ別カウンタで見た転送段階(prefill 側が KV キャッシュを送り出すのにかかった時間)の平均値です。経路 2(shm)の行だけは、別の回に 1 シードだけ取った基準値をそのまま引用しています。*

KV キャッシュの「ページサイズ」とは、SGLang の設定上の転送の単位のことで、小さいほど転送をまとめる塊が増えます。これは次節で見るディスクリプタ(libfabric が実際に発行する転送の単位)とは別の数え方で、ページサイズを 1 から 64 に変えてもディスクリプタ数自体は変わらないことを確認しています。経路 3(shm off)はページサイズ 1・到着レート 1 req/s で 196.2 ms、ページサイズを 64 に広げると 60.0 ms まで下がりました。到着レート 2 req/s でも、経路 3 はページサイズ 1 で 495.0 ms、ページサイズ 64 で 187.1 ms です。これらはいずれも 3 本の到着シードの平均です。

比較のための経路 2(shm)の値は、別の回に 1 シードだけ取った基準値で、ページサイズ 1・到着レート 1 req/s のとき 1,775.5 ms でした。これと上の 196.2 ms を比べると

$$
1{,}775.5 \div 196.2 \approx 9.0
$$

倍の差です。ただし、この shm の基準値は 3 シードで取り直したものではなく、比較できる 2 req/s の 3 シード平均もありません。別の回に単発実行(1 回の実行の中で 40 件前後のリクエストを平均したもの、到着レート 2 req/s・ページサイズ 1)で経路どうしを揃えて測った結果は、経路 2(shm)が 1,772.8 ms、経路 1(UCX)が 344.9 ms、経路 3(shm off)が 1 回目 17.1 ms・2 回目 218.5 ms でした。同じ条件を 2 回測ってこれだけ違う($1{,}772.8 \div 17.1 \approx 104$ 倍と $1{,}772.8 \div 218.5 \approx 8.1$ 倍)ため、17.1 ms は何らかの理由で待ちがほとんど発生しなかった実行だと考えられ、代表値としては扱いません。条件を揃えた比較としては、2 req/s・ページサイズ 1 の 3 シード平均どうし($1{,}772.8 \div 495.0 \approx 3.6$ 倍)と、ページサイズ 64 まで含めた比較($1{,}772.8 \div 187.1 \approx 9.5$ 倍)の 2 つが手元にあり、どちらも shm off の方が明らかに短いという方向は一致していますが、倍率は 3.6 倍から 9〜10 倍まで実行によって揺れています。

もう一つ注意したいのは、shm 自身が負荷に応じて遅くなっているかどうかです。1 req/s の基準値(1,775.5 ms)と 2 req/s の単発実行(1,772.8 ms)はほぼ同じ値で、この 2 点だけからは「shm は混雑するほど遅くなる」とは言えません。言えるのは、今回測った 1〜2 req/s の範囲ではいずれも shm が約 1.8 秒かかり、shm off や UCX の方が一貫して短かったという点です。

ここで気になるのは、孤立した 1 回の転送では shm の方が速いのに、SGLang の実リクエストでは逆に shm off や UCX の方が速かったという点です。1 回・16 MiB のデータだけを孤立させて測ると、経路 2(shm)は 0.165 ms(94.6 GiB/s)、経路 3(EFA デバイス)は 0.637 ms(24.5 GiB/s)、経路 1(UCX)は 1.10 ms(14.2 GiB/s)でした。1 リクエスト・1 ランクあたりの KV データは約 243 MiB(TP 2 なので合計は約 486 MiB)なので、この帯域で単純に換算すると、1 ランクぶんだけで shm で約 2.5 ms、EFA デバイスで約 10 ms、UCX で約 17 ms のはずです(あくまで単発計測の帯域をそのまま当てはめた目安で、同時に進む転送どうしの資源の奪い合いは含みません)。実測の数百〜1,700 ms 台はこの目安よりはるかに大きく、孤立したコピーの帯域だけでは SGLang 側の転送ステージ時間を説明できないと分かります。ただし、ここから「コピー以外の待ち時間が支配的だ」とまでは言えません。混雑時の実効的なコピー帯域の低下、転送の投入や同期にかかるコスト、ステージの計測区間に含まれる他の処理など、複数の候補が残っており、今回はそれらを分離して測っていません。前の節で見たとおり、shm の受信側の記帳は受信側自身の進行ループに依存する仕組みがソースコード上に存在するので、これが混雑時に詰まる候補の一因と考えられますが、送信側の計測時間を実際に伸ばすには受信側から送信側への逆方向の圧力が必要で、その経路も内部でどこが飽和するのかも特定できていません。UCX も shm off と同様に shm より速いままでしたが、この差を生む仕組みは今回のソース読解や次節の実験では特定できず、未解明のまま残っています。

## 棄却した仮説

![1 リクエストあたりのディスクリプタ数は低負荷から到着レート 2 req/s まで約 27 個のまま。進行スレッド数を変えた介入でも、所要時間は大きくは動かなかった](https://raw.githubusercontent.com/littlemex/figures/refs/heads/zenn/articles/19822818643aa6/zenn/articles/19822818643aa6/ruled-out-hypotheses.png)
*経路 2(LIBFABRIC、shm 既定)と経路 1(UCX)の速さの差を説明しようとして、追加で調べた 2 つの要因です。どちらも主な原因だとは確認できませんでした。*

転送の塊(ディスクリプタ)が負荷で増えて遅くなっているのではないかという仮説は、低負荷(到着レート 0.25〜1 req/s)でも、到着レート 2 req/s まで混雑させても、1 リクエストあたりのディスクリプタ数がほぼ 27 個(モデルの層数と同じ)のままだったことから、主な原因ではないと判断しました。ただし確認できたのは 1 リクエストぶんのディスクリプタ数だけで、同時に処理中のリクエストが増えたときの未完了ディスクリプタの総数までは数えていません。進行用のスレッドについては、UCX の進行スレッド数を既定の 8 本から 0 本に減らしても到着レート 1 req/s での所要時間はほとんど変わらず(130.0 ms と 132.9 ms)、検証用に NIXL を 1.4.0 へ一時的に上げて LIBFABRIC 側(経路 2、到着レート 1 req/s)の転送発行側のスレッドプールを有効にしても約 11 %の短縮にとどまりました(無効 434.6 ms、有効 388.5 ms)。どちらも、観測された経路どうしの差(数百~1,700 ms 台の差)を説明できる大きさの変化ではなかったため、主な原因としては棄却しましたが、この NIXL 1.4.0 でのスレッドプールは転送を発行する側を並列化するものであり、受信側の進行ループの実行頻度そのものに介入したわけではない点には注意してください。また、これらの数値は NIXL 1.1.0 の基準値(1,775.5 ms など)とは別の回に測ったもので、直接比較できる値ではありません。

## 分かったことと、分かっていないこと

前の節までの内容を、確定・推測・未解明の 3 段階に分けてまとめます。

| | 内容 | 根拠 |
|---|---|---|
| 確定 | 既定の LIBFABRIC は同じノード内では shm を使い、EFA デバイスを通らない | ログ、ハードウェアカウンタ |
| 確定 | 16 MiB の孤立した単発転送なら shm が最速 | 16 MiB 単発計測 |
| 確定 | 今回測った SGLang の実リクエストでは、shm off と UCX が shm より明らかに速かった(倍率は実行によって約 3.6〜104 倍まで揺れる) | ステージ別カウンタ |
| 確定 | shm は受信側の記帳が受信側自身の進行ループ任せになる作り | ソースコード |
| 推測 | shm の記帳の作りが、SGLang の実リクエストで shm が遅くなる一因 | 状況証拠のみ、送信側計測時間への経路も内部の飽和箇所も未確認 |
| 未解明 | UCX が shm より速い理由(shm off と同じ理由かは不明) | 進行スレッド数の介入では変化なし |
| 未確認 | 経路 1(UCX)の受信側の記帳の仕組み | 今回はソースの読解対象にしていない |
| 未確認 | 経路 3(shm off)の受信側の記帳の仕組み | ソースを読んだが、今回は特定できなかった |

## 実務での使い分け

今回計測した構成では、同じノードの中での KV キャッシュ転送は、UCX バックエンドを使って cuda_ipc の自動選択に任せるか、LIBFABRIC バックエンドのまま `FI_EFA_ENABLE_SHM_TRANSFER` を 0 にするかのどちらかを選ぶと、SGLang の実リクエストでは shm より遅くなりにくい結果でした。後者を選ぶ利点は、ノード内でもノード間でも同じバックエンド(LIBFABRIC)で統一できることです。もっとも、孤立した 1 回の転送だけを見れば shm 経由の方が速いこと、UCX が shm より速い理由は今回特定できていないこと、今回の倍率が実行によって約 3.6〜104 倍まで揺れていたことを踏まえると、どちらが適切かはモデルの形やトラフィックの混み方によって変わり得ます。また、ノード内のループバック通信も EFA デバイスの帯域を使うと考えられるため、ノード間通信と同時に流れる構成では競合の影響が出る可能性がありますが、これは今回検証していません。自分の環境に適用する前には、転送のステージ時間と、ホストネットワークから見える EFA のハードウェアカウンタの両方で、実際にどの経路を通り効果が出ているかを、できれば複数回・複数シードで確かめることをお勧めします。

## まとめ

- 同じノードの中では、`FI_PROVIDER=efa` を指定しても libfabric は既定で shm プロバイダに切り替わり、EFA デバイスを通りませんでした。
- shm は 16 MiB の孤立した単発転送では最速でしたが、今回測った SGLang の実リクエストでは shm off や UCX の方が明らかに速く、倍率は実行によって約 3.6〜104 倍まで揺れました。
- `FI_EFA_ENABLE_SHM_TRANSFER=0` にするか UCX を使うと、今回の構成では shm より遅くなりにくい結果でしたが、なぜ UCX が速いのかは特定できておらず、shm の記帳の仕組みが遅さの一因だという推測も内部までは確認できていません。
- 効果を自分の環境で確かめるときは、転送のステージ時間とホストネットワーク側の EFA ハードウェアカウンタの両方を、できれば複数回測ることをお勧めします。
