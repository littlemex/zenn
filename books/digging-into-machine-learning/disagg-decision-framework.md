## はじめに

:::message
本稿は全 4 回のシリーズの最終回である。「[(1) 割り勘と割り込みで読む、分離が速くなる理由](https://zenn.dev/littlemex/books/digging-into-machine-learning/viewer/disagg-queueing-basics)」「[(2) 平均では見えない裾と、約束を引数にした地図](https://zenn.dev/littlemex/books/digging-into-machine-learning/viewer/disagg-tail-promisemap)」「[(3) 実機で測る、道具が嘘をつく場所と分離が勝った条件](https://zenn.dev/littlemex/books/digging-into-machine-learning/viewer/disagg-real-validation)」で積んだ材料を、分離するかどうかを決める手順にまとめる。
:::

前 3 回で分かったことを 1 行ずつにすると、次のようになる。平均の式の上では、分離の得は書く係の相席を増やして重みの代金を割り勘にすることから来る。2 段に分けること自体の得には $(P+D)/\max(P,D)$ という天井があり、同じ台数の統合と比べると 1 を超えない。約束を分位点で書くと評価が大きく動き、TPOT の上限に沿って分離だけが守れる帯が現れる。測る道具は何度も嘘をつき、1 回の測定で見えた勝ちは繰り返すと消えた。

これらの材料には依存関係がある。約束を決めずに測ると、測った数字が何を意味するか決まらない。統合構成を最適化せずに分離と比べると、分離の勝ちは単に統合の設定不足を測ったものになる。判断には、約束を守れるかという性能の条件と、運用費用を許容できるかという費用の条件がある。本稿ではまず性能の条件を確かめる 7 段の順番を並べ、そのあとで費用の条件を重ねる。

## 判断は 7 段で、上の段が下の段の前提になる

![約束を決める段から始まり、繰り返しで確かめる段まで、上の段の結論が下の段の前提になる](/images/books/digging-into-machine-learning/dd-fig1-order.png)

### 1. 売る分位点と約束を先に決める

最初に決めるのは GPU の並べ方ではなく、利用者に約束する TTFT と TPOT の上限、判定の分位点、達成率の目標である。第 2 回の試算では、統合エンジンと分離の書く係エンジンの容量比が、p90 で判定すると 1.63 倍、p99 で判定すると 4.57 倍になった [試算]。これはエンジン 1 台どうしの比で、読む係の台数を含む配備全体の比ではないが、判定の規則だけで数字が大きく動くことは分かる。約束を決めないまま測ると、測った数字の意味が決まらない。

### 2. 間隔は ICL の分位点で測る

TPOT を要求ごとの平均 (AIPerf などの ITL) で測ると、応答の中で起きた詰まりは平均に薄められて見えない。間隔そのものの分布である ICL の分位点を測る。ICL がトークンの間隔になるのは、サーバが 1 トークンごとに断片を送る設定のときである。クライアントはエンジンと同じクラスタに置き、手元から port-forward 経由で測らない。間隔の合計を保ったまま配り直す経路は、平均を壊さずに分位点だけを壊すからである。

### 3. 実際の負荷の形で流す

固定長の入出力をでたらめな時刻に送る合成負荷は、結論を作ってしまうことがある。第 3 回の 32 GPU、EFA の比較で分離が勝ったのは多ターンで短い読みが高頻度に来る形で、単発の長い入力では大きく負けた [実機]。入出力長の分布、到着の突発性、会話の積み上がりと履歴の再利用、前の応答が終わるまで次が来ない性質を持った負荷で測る。多ターンの負荷では、前のターンの KV を読む係の側で再利用できるかで分離の代金が変わるので、キャッシュの再利用率も記録する。測定の入口では、送ったトークンの合計がエンジンの受け取った量と一致することを確かめる。

### 4. 統合構成を先に最適化する

分離と比べる相手は、最適化した統合構成でなければならない。第 3 回では、GPU 1 枚の統合に `long_prefill_token_threshold` を 1 行足すだけで、GPU 2 枚の分離に対してスループット 1.26 倍、TTFT p99 で 11 倍、ICL p99 で 3.8 倍良くなった [実機]。割り込みを分けて消すより、割り込み 1 回の大きさを縛る方が安い場合がある (第 3 回の負荷では入力の大半が閾値より短く、この設定がどの経路で効いたかは確かめていない)。この例は GPU 1 枚の統合でさえ GPU 2 枚の分離を上回った場合で、同じ GPU 数で比べるなら相手は複数レプリカの統合にする。ただしこの設定は、入力が極端に長く出力が数トークンの負荷では TTFT を悪化させた。

### 5. 天井と回線の上限を机の上で計算する

統合構成のエンジン 1 台で、1 要求あたりの読む時間 $P$ と書く時間 $D$ を測り、天井 $(P+D)/\max(P,D)$ を計算する。天井は統合エンジン 1 台に対して 2 台を使う比なので、同じ台数の統合と比べた容量比は天井 $\div 2$ になる。天井が 1.012 倍なら、2 段化だけでは容量は統合の約半分で、その差を割り勘か割り込みの解消で取り返せるかを次の段で確かめることになる [式]。第 3 回の L40S の測定では取り返せず、GPU 2 枚の分離は GPU 1 枚の統合と同じ量しか出さなかった。

回線についても 2 つ計算できる。運ぶか計算し直すかの境目の帯域は、1 トークンあたりの KV バイト数を読む係の 1 トークンあたりの時間で割った値である。そして転送経路が飽和する到着率 $\lambda_\text{max}$ は、回線の実効帯域 $W$ を 1 要求が運ぶ KV のバイト数 $S$ で割った値である [式]。

$$
\lambda_\text{max} = \frac{W}{S}
$$

筆者が測った UCX の TCP 経路は GPU メモリから 0.5 GiB/s 前後に張り付き、EFA は 256 MB 級の転送でその約 65 倍だった [実機]。予定している到着率が TCP の $\lambda_\text{max}$ に近いなら、TCP のままで分離を組むのは難しい。約束を守れる到着率は $\lambda_\text{max}$ より低くなりうることにも注意する。

### 6. 約束を引数にして、帯 2 を探す

ここで初めて分離構成を作って測る。測定は要求ごとの記録として残し、約束は後から当てる。そうすれば測定済みの到着率について、TPOT の上限を動かしたときに勝者が入れ替わる点が取れる。探すのは、分離だけが TPOT を守る帯 (第 2 回の帯 2) で、しかも分離の TTFT も約束の内側に収まる範囲である。帯 2 の幅は「統合の TPOT $-$ 分離の TPOT」で、統合の TPOT が負荷でどれだけ崩れるかで決まる。

比率 (読む係と書く係の台数比) はこの段で振る。第 2 回と同じ 16 GPU、テンソル並列 1、TCP の測定では、比率の最適は台地状で、外すと急に悪くなり、到着率によって動いた [実機]。入力 8,192 トークン、到着 3 タスク/s、TTFT 2,000 ms、TPOT 100 ms の約束では、読む係に寄せた比率 (6P+10D から 12P+4D へ) にすると達成率が 62.2% から 97.6% に上がった [実機]。ただし入力 24,576 トークンでは、測った比率のどれでも TTFT 2,000 ms の約束を守れなかった。受け渡しの代価が入力長に比例するので、長すぎる入力は比率では救えなかった。

### 7. 繰り返しで確かめる

最後に、勝ったマスを乱数シードを変えて繰り返す。判定は「繰り返したすべての回で、その到着率とそれより低い到着率がすべて合格すること」にする。第 3 回のラボでは、1 回目で 4 マスあった分離の勝ちが、2 回の追試を入れると 0 マスになった [実機]。達成率の目標の近くにある 1 回の結果は、どちら向きの交差の証拠にもならない。

## 負荷の形ごとの見立て

7 段を通した結果を、負荷の形ごとにまとめる。表の見立ては筆者の測定と試算の範囲でのものであり、モデル、GPU、回線、約束が変われば測り直す必要がある。

| 負荷の形 | 筆者の測定での見立て | 理由 |
|---|---|---|
| 書く係が時間を支配する (入力 1,500、出力 180 など) | 統合を出発点にする | 天井 $(P+D)/\max(P,D)$ が 1 に近い |
| 多ターンで短い読みが高頻度に来る | EFA なら既定の約束で、TCP なら TPOT を締めた約束で、分離が勝った (到着率が読む係の容量に収まる範囲) | 統合の TPOT が割り込みの回数で崩れ、分離の読む係は短い読みを楽に吸収する |
| 単発の長い入力 | 分離が負けた | 役割を固定すると総読み容量が減り、受け渡しの代価が入力長に比例する |
| 長短が混ざる | 読む係に寄せた比率を取れれば帯 2 が広い | 長い読みが短い要求の間隔を傷めるが、比率を振れなかった構成では負けた |
| 入力が数万、出力が数トークン | 入力 120,000、出力 12 では分離のスループットが 1.05 倍で TTFT p99 が 27% 悪化した。入力 28,000、出力 4 では閾値の設定が TTFT p99 を 1.26 倍悪化させた | 天井が 1 に潰れ、守るべき間隔がほとんどない |

## 費用の条件を重ねる

ここまでは性能の比較だった。実務の判断ではお金の軸が加わる。自前の GPU は時間で課金され、API はトークンで課金されるので、自前の 1 トークンの値段は機械の性質ではなく、借りた機械をどれだけ埋められるかで決まる。自前が API より安くなる負荷率 (実際に出したトークン $\div$ 約束を守って出せる最大のトークン) の境目は、次の形になる [式]。

$$
\text{損益分岐の負荷率} = \frac{\text{機械の時間単価}}{\text{API のトークン単価} \times \text{約束を守って出せるトークン/時}}
$$

境目は容量に反比例するので、約束を守って出せる容量が $r$ 倍になる配置は境目を $1/r$ 倍にし、容量が下がる配置は境目を上げる。70B モデルを H100 32 枚で動かす条件を試算した。GPU はオンデマンドの定価 (1 GPU 1 時間 3.99 ドル)、API を [Together AI の料金表](https://www.together.ai/pricing) の、入力と出力が同じ単価の公表価格 (100 万トークン 1.04 ドル) と置いた。入力を 2,048 から 32,768 トークン (出力 256) へ伸ばすと、統合の境目は 58.5 から 81.5%、分離は 74.0 から 102.6% になった [試算]。100% を超える境目は、どれだけ回しても API の方が安いことを意味する。入力と出力の単価が違う API では、それぞれの料金を別に計算する必要がある。またこの例は API のキャッシュ済み入力の割引を入れていない。境目は GPU の借り方と API の値付けで数倍動くので、並べ方より先に 2 つの価格を確かめる必要がある。

TPOT 10 ms のような厳しい約束では事情が変わる。比較に使った API の公表料金表には、トークン間隔の保証が見当たらなかった。その保証が必要なら、まず同等の契約を提供するサービスがあるかを確かめ、なければ自前の運用が候補になる。筆者の価格と負荷率の仮定では、TPOT 30 ms から 80 ms の約束で分離が安くなる例は得られなかった。分離の価値は、安さよりも、買えない間隔の保証を作れることにある場合が多い。

## 式で見積もれること、測るしかないこと

判断の順番に沿って、どの問いを何で答えるかを並べる。

| 問い | 答える道具 |
|---|---|
| 分離に得の余地があるか (天井、回線の境目、到着率の上限) | 式。統合のエンジン 1 台の測定から計算する |
| 帯 2 があるか、どちら側の約束で勝ちそうか | 要求ごとの記録に約束を後から当てた実機の測定 |
| 何 ms か、何倍か、近い 2 つの比率のどちらが良いか | 繰り返した実機の測定 |
| 崩壊がどこで始まるか | 実機の測定 |

式は測る範囲を絞る道具である。判断を代行する道具ではない。

## まとめ

分離するかどうかは、7 段の順番で決める。売る分位点と約束を決め、ICL で測り、実際の負荷の形で流し、統合を先に最適化し、天井と回線の上限を机の上で計算し、約束を引数にして分離だけが守れる帯を探し、最後に繰り返しで確かめる。上の段を飛ばすと、下の段の数字が何を意味するか決まらない。

そのうえで残る結論は 2 つである。筆者の測った範囲で分離が勝ったのは、統合の TPOT が割り込みで崩れ、分離の TTFT が約束の内側に収まる狭い領域だった。32 GPU、EFA の比較ではそれは長文脈ではなく短い読みが高頻度で来る負荷だった。16 GPU、TCP の比較では、多ターンの短い読みに TPOT 25 ms のような締めた約束を当てた場合と、長短が混ざる負荷に読む係へ寄せた比率を合わせた場合だった (いずれも 1 回の測定)。そして筆者の価格の仮定では、分離の価値は安さよりも、比較した API の料金表にない間隔の保証を作れることにあった。
