## はじめに

2026年の LLM 推論サービングをめぐる技術文書で、「分離 (disaggregation)」という語の登場頻度が急に上がった。ところがこの語が指す対象は一つではない。ある文書では Prefill と Decode を別クラスタに分ける Prefill/Decode 分離 (以下 P/D 分離) を指し、別の文書では同じ Decode 処理の中で Attention 層と FFN 層を別の GPU プールに分ける Attention-FFN 分離 (以下 AFD) を指す。さらに FlowPrefill のように、Prefill 内部のスケジューリングを「分けて」扱う手法もある。これらに Mixture-of-Experts (MoE) の Expert Parallelism (EP) まで加わると、初見の読者は競合する選択肢なのか同時に使えるのかを見失いやすい。

:::message
本稿は学習済みモデルを「どう提供するか」というサービングとシステムの側を扱う。アーキテクチャそのもの (MoE、Attention 圧縮、量子化など) が「どう作るか」の話であったのに対し、ここでは作ったモデルを GPU クラスタ上でどう分割配置し、どう通信させるかを整理する。帯域律速、ルーフライン、KV-Cache、MoE のアクティブ比、all-to-all 通信といった基礎概念は所与として進めるので、初出の概念は本書の別章へのリンクで補ってほしい。vLLM や SGLang の起動フラグとソースコードに踏み込むが、それらを触ったことがなくても構造の議論は追えるように書いた。
:::

本稿の主張は単純である。これらは競合する選択肢ではなく、互いに直交する分離の軸である。ここで「直交」という語は概念空間での意味で使う。すなわち分ける対象の軸が異なるという意味であって、実装の現場でいつでも自由に組み合わせられるという意味ではない。P/D 分離は時間軸 (推論のフェーズ) で分け、AFD は空間軸 (レイヤの種別) で分け、FlowPrefill は順序軸 (Prefill 内の実行順) で分ける。分ける対象が違うので、概念上はこの3つは直交する。ただし後で見るように、構成空間では依存や排他が生じる。AFD は Prefill の供給を P/D 分離に頼るし、ある実装では AFD と他の分離が排他になる。概念の直交性と実装の組み合わせ可能性は別物として扱う、というのが本稿の一貫した立場である。

そして MoE の EP は、これら3つの分離とは層の違う存在である。EP は「4つ目の分離軸」ではなく、3軸のいずれの内側にも現れる FFN 計算の下部構造、すなわち横断軸である。この見立てを最初に地図として描き、次に各軸を一つずつ掘り下げ、最後に vLLM と SGLang の実装でこれらが実際にどこまで同時に成立するのかをコードレベルで確定する、というのが本稿の道筋である。

なぜ「直交」と「横断」を最初に区別するかというと、この区別を誤ると設計判断を誤るからである。たとえば「AFD を入れれば P/D 分離は要らない」というのは誤りで、後述する通り AFD の代表的な実装はそもそも Decode 定常状態を主眼とし、Prefill の供給は別途 P/D 分離に委ねる前提で論じられる。逆に「EP を強くすれば AFD と同じ効果が得られる」というのも誤りで、EP は Attention と FFN を分離しない。軸が違うものを別の軸として描き分けることが、整理の出発点になる。

前提とする基礎概念は本書の他章に譲る。自己回帰デコードがなぜ帯域律速に張り付くのか、ルーフラインモデルにおける ridge point とは何かは本書の「[ハード制約から読む設計収束](https://zenn.dev/littlemex/books/digging-into-machine-learning/viewer/llm2026-overview)」で扱った。MoE がなぜ「知識の容量 (総パラメータ) と1トークンあたりのコスト (アクティブパラメータ) の分離」なのか、all-to-all 通信がなぜ MoE の並列度を縛るのかも同じ章にある。MLA などによる KV-Cache 圧縮の数理は「[要素技術を重要な順に](https://zenn.dev/littlemex/books/digging-into-machine-learning/viewer/llm2026-elements)」で扱った。本稿はこれらを既知として、サービングの構造だけに集中する。

:::message
本稿では根拠レベルを次のように表記する。[定理] は数学的に証明された保証を指す。[報告] は一次ソース (arXiv 本文、公式リポジトリの README・ソースコード、公式ブログなど) に原文で記載がある事実を指す。[仮説] は筆者による解釈であり、状況証拠に基づく推論を含む。実装の可否については、ソースコードのアサーションや公式レシピの有無という検証可能な事実に基づく場合は [報告] とし、そこからの一般化は [仮説] と区別する。
:::

軸と横断軸をどう線引きするかも先に決めておく。本稿では、律速の異なる断片を作る操作、すなわち計算を性質の違う資源プールへ切り分ける操作を分離軸と呼ぶ。P/D 分離は演算律速の Prefill と帯域律速の Decode を作り、AFD は帯域律速の Attention と演算律速の FFN を作る。いずれも切り分けた結果として性質の違う断片が生まれる。これに対し、律速を変えずに同種の計算を均質に分散する操作は横断軸と呼ぶ。EP はエキスパートを複数 GPU にばらまくが、ばらまいた先はどれも同じ FFN 計算であって律速は変わらない。この基準ではテンソル並列 (TP) も横断軸の側に落ちる。本稿が EP を取り上げて TP を主役にしないのは、MoE を扱う3軸すべてで EP が前面に出るからであって、TP を軸から外す特別な理由があるわけではない。

## 分離の4つの登場人物を1枚の地図に置く

まず全体像を1枚に置く。次の図は、本稿で扱う4つの登場人物を「何を分けるか」「なぜ分けると効くか」「代表技術」で並べたものである。

![分離の3つの直交軸と1つの横断軸](/images/books/digging-into-machine-learning/afd-fig1-axes.png)

上から3行が分離軸で、いずれも「何かを2つ以上に分けて別々に扱う」という操作だが、分ける対象の軸が異なる。最下行の EP だけは色を変えてある。分離軸ではなく、3つの分離軸がいずれも扱う FFN 計算の実体を指す横断軸だからである。詳細はそれぞれ専用の節で扱うので、ここでは軸が違うことだけを掴んでほしい。

軸1のフェーズ分離は、推論を時間的な2つの局面に分ける。演算律速の Prefill と帯域律速の Decode を別々の GPU クラスタに載せ、それぞれを律速に合わせて最適化する。DistServe や Splitwise、Mooncake がこの系譜にある。軸2のレイヤ種別分離は、同じ Decode の1回の順伝播を空間的に (どのレイヤを担うかで) 分ける。帯域律速の Attention と演算律速の FFN を別々の GPU プールに載せる。これが AFD であり、MegaScale-Infer や Step-3、FastAFD、そして後半で見る vLLM の afd-plugin がこの系譜にある。軸3の Prefill 内スケジューリングは、Prefill クラスタの内部で長短のプロンプトの実行順を分ける。長い Prefill が短いリクエストを待たせる先頭行ブロッキング (head-of-line blocking、以下 HoL blocking) を、実行粒度とスケジュール頻度の分離で緩和する。これが FlowPrefill である。

最下行の EP は色が違う。MoE のエキスパートを複数 GPU に分散し、各トークンを担当エキスパートへ送る all-to-all 通信を回すのが EP だが、EP が分けるのはエキスパートの配置先であって、フェーズでもレイヤ種別でも実行順でもない。むしろ EP は3軸がいずれも内部に抱える FFN 計算の並列化であり、P/D 分離した Decode クラスタの中でも、AFD で切り出した FFN プールの中でも回る。だから EP は分離軸と同列に並べず、3軸を縦に貫く横断軸として描くのが正確である。そのうえ後述するように、EP の通信のやり方はフェーズによって最適な形が変わり、軸1と強く相互作用する。この絡み合いが本稿後半の山場になる。

軸1から軸3は概念上は掛け合わせが可能で、「P/D 分離した Decode 側をさらに AFD で Attention と FFN に分け、その FFN プールの中で EP を回す」という入れ子が原理的には成立する。この時間軸 (P/D) と空間軸 (AFD) の二重分離を図にしたのが次の図で、後半で見る vLLM のレシピが実際にこの構造を取る。

![時間軸 (P/D) と空間軸 (AFD) の二重分離は入れ子にできる](/images/books/digging-into-machine-learning/afd-fig2-nesting.png)

縦がフェーズ分離、横がレイヤ種別分離である。P/D 分離で Decode を切り出したうえで、その Decode 行だけを Attention プールと FFN プールに再分割する。この二重の入れ子が実装でどこまで成立するかは最終節で確定するが、まずは4者が別々の軸に住んでいるという構図を頭に入れておいてほしい。

## 軸1: フェーズ分離 (P/D 分離) が時間で切る

最初の軸は Prefill と Decode の分離である。この軸を理解する鍵は、2つのフェーズが正反対の資源を食い尽くすという点にある。Prefill は入力プロンプト全体を一度に順伝播させるので、数千トークン分の行列積が並び、GPU の演算ユニットを飽和させる演算律速の処理になる。一方 Decode は既に生成したコンテキストをもとに1トークンずつ出力するので、1ステップあたりの計算量は小さく、代わりにモデル重みと KV-Cache をメモリから読み直す帯域が律速になる。この非対称は本書の設計収束の章で扱ったルーフライン議論そのもので、Prefill は ridge point の右 (演算律速)、Decode は左 (帯域律速) に位置する。

同居させると何が困るのか。両者を同じ GPU の同じバッチに混ぜると、演算律速の Prefill が実行されている間、帯域律速の Decode リクエストは待たされる。逆に Decode 中心にバッチを組めば演算ユニットが遊ぶ。しかも最適なバッチサイズも、テンソル並列度も、さらには最適な GPU 世代さえ両者で食い違う。Decode は帯域が命なので高帯域メモリを積んだ構成が効き、Prefill は演算が命なので演算スループットの高い構成が効く。ならばクラスタごと分けて、Prefill 専用ノードと Decode 専用ノードを別に用意し、Prefill が生成した KV-Cache だけをネットワーク越しに Decode ノードへ転送すればよい。これが P/D 分離であり、DistServe が定式化し、Splitwise や Mooncake が大規模実装として広めた。

P/D 分離の代償は KV-Cache の転送である。Prefill ノードで計算した KV を Decode ノードへ運ぶ必要があり、ここに RDMA や NVLink 越しの高速転送機構が要る。その転送機構が vLLM と SGLang で具体的にどう実装されているかは最終節で見る。転送のコストを、Prefill と Decode を分けたことによる利得が上回るかどうかが、P/D 分離を採るかの分岐点になる。長いコンテキストで Decode が長く続くワークロードほど、Prefill を切り離す利得が大きい。

ここで補足すると、P/D 分離は歴史的には MoE や EP と無関係に生まれた。DistServe や Splitwise は、Prefill が演算律速で Decode が帯域律速というルーフライン上の非対称と、初回トークン遅延 (TTFT) と後続トークン間隔 (TPOT) という別々の遅延目標を独立に最適化したいという動機から P/D 分離を定式化した。MoE の EP がフェーズと相互作用する話は、その後に重なってきた別のレイヤの論点である。この点は横断軸の節で扱う。

## 軸2: レイヤ種別分離 (AFD) が空間で切る

2つ目の軸は、同じ Decode の順伝播の内部を Attention 層と FFN 層で切り分ける AFD である。P/D 分離が推論を時間で切ったのに対し、AFD は1回の順伝播を空間 (レイヤの種別) で切る。ここが両者を直交させている核心なので、まず「なぜ Decode の内部にもう1本の律速の断層が走っているか」を押さえたい。

1トークンを生成する Decode ステップの中でも、Attention と FFN は資源の食い方が違う。Attention は蓄積した KV-Cache を読み直すので帯域律速で、バッチを大きくしても KV の読み出し量が線形に増えるため、演算ユニットはさほど埋まらない。対して FFN (MoE ではルーティングされたエキスパート) は重み行列との積なので、バッチ内のトークンを束ねるほど演算律速に近づき、GPU の演算ユニットを効率よく使える。つまり同じ Decode の中に、帯域が欲しい部分と演算が欲しい部分が同居している。P/D 分離で Decode を切り出してもなお、その内部にこの断層が残るのだ。

AFD はこの断層で GPU プールを2つに割る。Attention 専用の GPU プール (FastAFD の用語では AG、attention-generation) は KV-Cache を保持し、データ並列で台数を稼いで帯域を確保する。FFN 専用の GPU プール (同じく EG、expert-generation) はエキスパートだけを載せ、KV-Cache を一切持たず、EP でエキスパートを分散して演算効率を追う。両プールの間を隠れ状態ベクトルが往復する。この往復通信の名前が N2M と M2N である。

:::message
N2M と M2N の向きは資料により表記が揺れるが、本稿は FastAFD の公式リポジトリの README を一次ソースとして採る。論文本文とリポジトリで表記が食い違う場合、実際に動くコードの定義に従うのが安全だからである。README では N2M が Attention から FFN への dispatch (トークンを担当エキスパート側へ送る)、M2N が FFN から Attention への combine (エキスパートの計算結果を戻す) と定義されている。ある解説記事ではこの向きが逆に要約されているが、本稿は実装リポジトリの定義を優先する [報告]。
:::

ここで AFD の通信 N2M/M2N と、MoE の EP all-to-all の関係を1枚で見ておきたい。

![AFD の N2M/M2N は EP の all-to-all を非対称に一般化したもの](/images/books/digging-into-machine-learning/afd-fig3-comm.png)

左が通常の EP である。全 GPU が Attention とエキスパートの両方を持ち、各トークンを担当エキスパートのある GPU へ送って結果を戻す。送受信の相手が全 GPU で対称なので、これは対称な all-to-all になる。右が AFD である。Attention 専用 GPU 群と FFN 専用 GPU 群に役割が割れており、その間をトークンが往復する。ここで両群の台数は一致しなくてよい。FastAFD の代表構成では、データ並列の Attention GPU を多数並べる一方で FFN 側は1ノード (エキスパート並列 ep=4 の4 GPU) に絞り、Attention 対 FFN の台数比が最大で 17 対 1 に達する [報告]。この非対称性が AFD を特徴づける。

実装上の面白い点は、この非対称な往復を既存の EP 通信ライブラリに載せる工夫である。DeepEP は全ランクがエキスパートを持つ対称なワールドを前提とするため、Attention 専用ランク (エキスパートを持たない) をそのまま混ぜられない。そこで Attention ランクにダミーのエキスパート範囲を割り当て、非対称な往復を対称な all-to-all の見かけに押し込める [報告]。言い換えれば、AFD の N2M/M2N は EP の all-to-all を非対称な台数比へ一般化したものであり、両者は無関係な別技術ではなく、同じ all-to-all の対称版と非対称版なのだ。

この「AFD は EP の一般化」という見方は、逆に「なぜ AFD を軸と呼び EP を横断軸と呼ぶのか」という疑問を呼ぶ。答えは先に定めた基準に戻る。AFD は KV を持つ帯域律速の Attention プールと、KV を持たない演算律速の FFN プールという、律速の違う断片を作る。だから分離軸である。EP はエキスパートをばらまくだけで律速の違う断片を作らない。だから横断軸である。通信の形が一般化の関係にあることと、両者が異なる軸に属することは矛盾しない。この対称版と非対称版という関係は、後で AFD と MoE の EP が実装上どう衝突するかを理解する伏線になる。

AFD の利得が主に論じられるのは Decode 側である。代表的な実装 (MegaScale-Infer や FastAFD) はいずれも Decode の定常状態を測定対象とし、Prefill の供給は範囲外に置く。理由は律速の議論から推し量れる。Prefill は演算律速なので、Attention と FFN を分けても分離の利得が薄く、むしろ往復通信のオーバーヘッドが勝ちやすいと考えられる [仮説]。ただしこれは「Prefill に AFD が効かない」という断定ではない。長文脈 Prefill では Attention の計算量が系列長の二乗で効いてくるし、実際 vLLM の afd-plugin には Prefill 向けの非同期コネクタも用意されている。あくまで代表実装が Decode 定常状態を主眼に据えているという事実 [報告] と、その理由の推論 [仮説] は区別しておきたい。いずれにせよ、AFD が Decode を主眼とし Prefill の供給を P/D 分離に委ねる構図は、2つの軸が競合ではなく補完である様子をよく表す。FastAFD 自身、本番サービング化には P/D 分離や投機デコードなどとの合成がなお必要だと明言している [報告]。

## 軸3: Prefill 内スケジューリング (FlowPrefill) が順序で切る

3つ目の軸は毛色が違う。P/D 分離と AFD がハードウェアの配置 (どの GPU にどの計算を載せるか) を分けたのに対し、FlowPrefill が分けるのは実行の順序と粒度である。分ける対象がスケジューリングという別の次元なので、これは配置を分ける2軸と真に直交し、原理的にはどんな配置の上にも重ねられる。

問題設定は HoL blocking である。P/D 分離した Prefill クラスタには、短いプロンプトと非常に長いプロンプトが混在して届く。素朴なスケジューラは1つの Prefill を最後まで実行してから次に移るので、長大なプロンプトの Prefill が走っている間、後から来た短いリクエストはその完了を待たされる。待たされた側の初回トークンまでの遅延 (TTFT) が跳ね上がり、テールレイテンシが悪化する。これはネットワークの HoL blocking と同型の問題である。

この問題への既存の標準解が chunked prefill である。長い Prefill を固定長のチャンクに切り、チャンクの合間に他のリクエストを挟むことで待ち時間を均す手法で、vLLM でも SGLang でも標準的に使える。ただし chunked prefill にはジレンマがある。チャンクを小さくすると待ち時間は減るが、カーネル起動のオーバーヘッドが増え、Attention が過去の KV を再ロードする冗長メモリアクセスが嵩み、演算ユニットの利用率が落ちる。逆にチャンクを大きくすると効率は戻るが待ち時間が悪化する。FlowPrefill はこのジレンマを、実行の粒度とスケジュール判断の頻度という2つを別々に分離することで解こうとする [報告]。

第一に実行の粒度を分ける。リクエストをチャンクに切り分けるのではなく、1回のモデル前進の内部を qkv_proj、attention、o_proj、gate_up_proj、down_proj といった演算子 (operator) の境界に区切り、その境界で実行中の長い Prefill を中断できるようにする。第二にスケジュール判断の頻度を分ける。イベント駆動のスケジューラを置き、リクエストの到着と完了というイベントのときにだけ、次に何を走らせるかを判断し直す。固定間隔でのポーリングはしない。判断の優先度には slack を考慮した EDF (earliest-deadline-first) を使い、締め切りまでの余裕 (slack) が小さいリクエストを優先する。演算子境界はあくまで中断してよい地点であって、スケジュール判断のトリガではない。中断できる粒度は細かく、判断を下す頻度は到着と完了に絞る、という2つの分離が FlowPrefill の核心である。

論文の報告では、この演算子粒度のプリエンプションとイベント駆動スケジューリングにより、DistServe に対して最大 5.6 倍の goodput (応答遅延の目標である SLO を満たしたリクエストのスループット) を達成したとされる。実装は vLLM 0.11.2 の上に構築されている [報告]。本稿の関心にとって重要なのは2点ある。1つは、FlowPrefill が「P/D 分離に自然に適用できる」と論文自身が述べている点で、FlowPrefill が P/D 分離の Prefill クラスタ内部のスケジューラとして働くことを意味する [報告]。もう1つは、論文が MoE を扱ってはいるものの、EP や AFD には踏み込んでいない点である。MoE の評価は Section 6.5 で Qwen3-30B-A3B を単一ノードで測り、gate と experts の演算子境界にプリエンプション点を足すだけで 1.6 倍の goodput 改善を報告する。しかしそこに EP や AFD のような分散配置は登場しない [報告]。

この2点目は、FlowPrefill が他の軸とどう関わるかを正直に示す。FlowPrefill は Prefill 側の実行順を扱い、AFD は Decode 側の配置を扱うので、両者は効く局面がそもそも重ならない。分ける対象が違うという意味で直交する。ただし、局面が重ならないことは干渉しないことの証明ではない。P/D 分離構成では、FlowPrefill の演算子粒度プリエンプションが Prefill 側の KV 転送のタイミングや、Prefill 用 EP (高スループット型) のバッチ形成と相互作用しうる。この相互作用を測った報告は現時点で見当たらない。したがって正確には、設計上は直交するが、他の軸と同時に回した実測はまだ無い、という状態である [仮説]。

## 横断軸: MoE と Expert Parallelism は3軸すべてを貫く

ここまでの3軸はいずれも「何かを分けて別々に扱う」分離だった。EP はそのどれとも軸が違う。EP が分けるのはエキスパートの配置先であって、フェーズでもレイヤ種別でも実行順でもない。この節では、ここまで予告してきた EP の横断性を具体化し、さらに EP がフェーズ分離 (軸1) と強く相互作用するという、本稿の山場を扱う。

横断性は、EP の実体がどの分離軸の内側にも現れる点に尽きる。P/D 分離した Decode クラスタの中にも FFN はあるし、AFD で切り出した FFN プールの中身はまさに EP そのものだし、FlowPrefill が刻む演算子の中の gate_up_proj と down_proj はエキスパートの計算である。つまり EP は分離軸と並ぶのではなく、分離軸が切り出したどの断片の中でも回る下部構造なのだ。図1で EP だけ色を変え、縦に貫く軸として描いたのはこの理由による。

次が本題の相互作用である。EP は横断軸でありながら、その最適な通信の形がフェーズ (軸1) によって変わる。この事実を2つの一次ソースで確認する。

1つ目は arXiv:2603.13606 の NCCL ベース EP の研究である。この論文では EP の通信カーネルが2つのモードに分かれると報告されている [報告]。低遅延を狙う LL (low latency) モードは、1トークンずつを速く捌く Decode 向けである。高スループットを狙う HT (high throughput) モードは、大量トークンをまとめて捌く Prefill 向けである。同じ EP の all-to-all でありながら、レイテンシ最適化とスループット最適化で通信カーネルの実装そのものが別物になる。2つ目は SGLang の DeepEP 実装で、これはソースコードで確認できる。`--deepep-mode` は `auto`、`normal`、`low_latency` を取り、内部の `DeepEPMode.resolve()` が Prefill では NORMAL を、Decode では LOW_LATENCY を選ぶ [報告]。NORMAL は高スループット型、LOW_LATENCY は低遅延型で、NCCL EP の HT/LL とちょうど対応する。フェーズの区別が EP 通信カーネルの選択を規定する構図が、独立な2つのソースで裏づけられる。

では、この HT/LL の非対称と P/D 分離はどういう関係にあるのか。ここは慎重に述べたい。歴史的な因果としては、P/D 分離は前述の通り MoE や EP と無関係にルーフラインと遅延目標から生まれたので、EP 通信モードの非対称が P/D 分離を生んだわけではない。両者はむしろ「Prefill は演算律速、Decode は帯域律速」という共通の原因から出た別々の帰結である。そのうえで、EP 通信の非対称は P/D 分離に強い追加の動機を与える。SGLang の大規模 EP の公式ブログは、auto モードでは normal と low_latency を1つの通信グループの中で同時にはサポートできないと指摘する [報告]。この制約は DeepEP のバッファ設計に由来する特定実装の制約であって物理法則ではないが、この制約下では、Prefill と Decode を P/D 分離しておけば Prefill 側は normal (HT)、Decode 側は low_latency (LL) と各フェーズに最適な通信モードを別々に固定できる。すでに P/D 分離を採用している構成にとって、これは分離の追加の利得になる。分離が律速の非対称だけでなく通信ライブラリの都合からも後押しされる、という重なりがここで見える。次節では、この重なりが vLLM と SGLang の実装でどこまで実際に成立するのかを、コードとレシピの事実で確定する。

## 交差の実装: vLLM と SGLang でどこまで重ねられるか

概念上の掛け合わせが、実在するコードでどこまで成立しているのかを確定する。この節では vLLM と SGLang の2つの実装を、起動フラグとソースコードのアサーション、公式レシピの有無という検証可能な事実に基づいて突き合わせる。結論から言えば、両者は執筆時点で正反対の得意分野を持っている。まず全体像を1枚の対照表で示す。

![vLLM と SGLang で分離をどこまで重ねられるかの対照表](/images/books/digging-into-machine-learning/afd-fig4-impl.png)

表の記号は、○が同時利用の実在レシピあり、△が起動は通るが公式レシピや CI に同時構成が見当たらない、×が実装が同時利用を明示的に禁止する (アサートで弾く)、ハイフンが該当機能が本体に無い、を表す。数値やクラス名は執筆時点 (2026年7月) のソースに基づく。ここで大事な前置きを2つ置く。1つは評価範囲の非対称である。vLLM は本体に加えてプラグイン (afd-plugin) まで含めて評価し、SGLang は本体 main と未マージの draft PR を分けて評価する。両者でエコシステムの取り方が揃っていない点は、表を読むときに割り引いてほしい。もう1つは○の強さである。後で留保するが、○は「レシピが存在し起動する」ことを意味するのであって、「本番相当の負荷で精度と性能が検証済み」を意味しない。以下、行ごとに事実を追う。

### P/D 分離と EP と MoE は両者とも素直に成立する

まず土台になる P/D 分離、EP、MoE の3点セットは、vLLM でも SGLang でも確立している。vLLM では KVConnector 抽象 (NixlConnector など) が P/D 間の KV-Cache 転送を担い、EP は `--enable-expert-parallel` で有効になる。SGLang では `--disaggregation-mode {prefill,decode}` が P/D 分離を、`--ep-size` と `--moe-a2a-backend` が EP を担う [報告]。ここは争いがない。

そして前節で予告した「フェーズが EP 通信モードを規定する」という点も、両者で成立している。とりわけ SGLang では `DeepEPMode.resolve()` が Prefill で NORMAL (高スループット型)、Decode で LOW_LATENCY (低遅延型) を自動選択し、NCCL EP の HT/LL 二分と対応する [報告]。この自動選択があるからこそ、P/D 分離が「各フェーズに最適な EP 通信モードを固定する」という具体的な意味を持つ。表ではこれを P/D 分離が EP 通信モードを変える行として独立に立て、両者○とした。

### AFD の有無で明暗が分かれる

差がつくのは AFD である。vLLM 側は本体ではなくプラグイン `vllm-project/afd-plugin` として AFD を実装している。DeepSeek 系アーキテクチャを別名登録する entry point 機構で本体を無改変のまま拡張し、`VllmConfig.additional_config["afd"]` の存在を起動シグナルにする [報告]。Attention ワーカー (`AFDAttentionWorker`) は KV-Cache とスケジューラを保持し、FFN ワーカー (`AFDFFNWorker`) は `get_kv_cache_spec()` が空辞書を返す、すなわち KV-Cache を一切持たない構造になっている [報告]。前節で見た AFD の設計 (Attention プールが KV を持ち、FFN プールは持たない) が、そのままコードに現れている。

一方 SGLang 本体の main には AFD が無い。存在するのは未マージの草案 PR #10900 (RFC、作者 LPhgh) だけである。この草案は転送バックエンドに StepMesh (Step-3 由来の GPU 間通信ライブラリ) を使い、`--afd-role {attn,ffn}` フラグを導入する設計だが、現時点で draft のまま main には入っていない [報告]。したがって表では vLLM を○ (2p1a1f レシピが実在)、SGLang を△ (未マージ草案) とした。

### AFD を他の分離と重ねられるかで両者は正反対になる

ここが本節の核心である。AFD をさらに P/D 分離や MoE の EP と同時に使えるか。この問いに対し、vLLM と SGLang は正反対の答えを返す。

vLLM 側には AFD と P/D 分離と EP と MoE を1つのレシピに同居させた実例がある。`recipe/gpu/P2pNcclAFDConnector/deepseek_v2_lite/prefill_decode_disaggregation/2p1a1f_eager_dbo.sh` がそれである。ファイル名の 2p1a1f は、2 台の Prefill、1 台の Decode Attention、1 台の Decode FFN という構成を表す。5つのプロセスの役割は次の通りである。

- Prefill プロデューサ 2 台。NixlConnector の kv_producer として KV-Cache を生成する。
- Decode Attention ワーカー 1 台。NixlConnector の kv_consumer であると同時に AFD role=attention でもあり、KV-Cache を保持する。
- Decode FFN ワーカー 1 台。AFD role=ffn でエキスパートだけを担い、KV 転送には関与しない。
- NIXL ロードバランスプロキシ 1 台。リクエストを振り分ける。

この構成では、KVConnector による P/D 分離と、AFD Connector による Attention/FFN 分離が、Decode の Attention プロセス上に同居する。地図の節で図示した時間軸と空間軸の二重の入れ子が、ここで実物になっている。ただし信頼性には留保が要る。このレシピは当初 Attention と FFN が実際には分離されず Attention GPU の利用率が 0% になるバグを抱えており、修正されたばかりの新しい構成である [報告]。

対照的に SGLang の AFD 草案は、他の分離との同時利用を明示的に禁止する。起動時に走る `check_afd_server_args()` が、次のアサートを課す [報告]。

- `disaggregation_mode == "null"` を要求する。すなわち P/D 分離との併用を弾く。
- `moe_a2a_backend == "none"` を要求する。すなわち DeepEP などの MoE all-to-all との併用を弾く。
- `enable_two_batch_overlap` を不可とする。
- CUDA graph、overlap schedule、マルチノード、パイプライン並列 (PP) をいずれも不可とする。

つまり AFD を使うなら他の分離は全部切れ、という限定的な実験段階にある。ただしこれは未マージ draft のアサートであって、SGLang というプロジェクト全体が AFD を排他的に設計しているという意味ではない点は注意したい。この対比は、表の AFD+P/D 分離の行 (vLLM ○だが小規模のみ、SGLang ×) と AFD+MoE-A2A の行 (vLLM ○、SGLang ×) にそのまま出る。

### バッチ overlap は両者とも慎重に扱う

バッチ overlap と P/D 分離の併用を見る。ここでいうバッチ overlap は、1回のステップを2つのマイクロバッチに割り、片方が通信している間にもう片方を計算させて、通信を計算の陰に隠す最適化である。vLLM ではこれを DBO (Dual Batch Overlap)、SGLang では TBO (Two-Batch Overlap) と呼ぶ。vLLM の DBO は AFD プラグイン側の機構で、厳密に2マイクロバッチに限定される [報告]。前掲の 2p1a1f レシピにも eager_dbo 版があり、DBO と P/D 分離の同時レシピは vLLM に実在する。よって表では vLLM を○ (ただし DeepSeek-V2-Lite 小規模のみ) とした。一方 SGLang の TBO は、P/D 分離との併用を禁止するアサートこそ無いものの、公式の P/D デプロイマニフェスト (`lws_pd_deploy.mdx`) では decode ワーカーの TBO フラグがコメントアウトされており、CI でも P/D 分離と TBO を同時に回す構成は見当たらない [報告]。ここから、SGLang の TBO は P/D 分離なしの単一サーバ構成を主用途とする運用だと推測できる [仮説]。よって SGLang は△とした。

### 表から2つの結論を導く

この対照表から2つのことが言える。1つは、vLLM と SGLang が執筆時点で正反対の得意分野を持つという事実である。vLLM は AFD を核に据え、その上に P/D 分離と EP を薄く重ねた小規模実証を持つ。SGLang は AFD 以外の技術 (P/D 分離、EP、DP attention すなわち Attention 層をデータ並列で複製する構成、TBO) を大規模に実運用する一方、AFD だけは他の分離と排他の実験段階にある。理想の全部盛りに対して、vLLM は AFD 側から、SGLang は AFD 以外の側から、それぞれ異なる方向で接近している。ただしこれは執筆時点のスナップショットにすぎず、SGLang の AFD 草案がマージされれば容易に変わりうる。

もう1つは、両者に共通する壁の正体である。SGLang の AFD 草案が MoE の all-to-all を禁止するのも、大規模 EP で Prefill と Decode を P/D 分離するのも、根には同じ「Prefill (HT) と Decode (LL) で EP の通信が別物」という非対称がある。この非対称が「1つの通信グループでは両立しない」という制約 (前述の通り DeepEP のバッファ設計に由来する) を生み、その制約を避けるために分離が後押しされる。本稿が概念上の「直交する軸」として整理した4者は、この非対称という1点で実装の現実に接地する。分離とは、律速の非対称と EP 通信の HT/LL 非対称という制約に、システムの構造で応える営みなのだ。

なお FlowPrefill (軸3) は、この対照表には現れない。研究実装が vLLM 0.11.2 上のプロトタイプであり本体にマージされていないため、他の軸との同時構成を持つ公式レシピが存在しないからである。軸3が他の3者と同時に成立した実装は、vLLM でも SGLang でも執筆時点では確認できない [報告]。3つの分離軸が概念上は掛け合わせられるという主張に対し、実装で検証できたのは P/D 分離と AFD と EP の重なりまでであって、そこに FlowPrefill を加えた4者同時はまだ誰も回していない、というのが正直な現状である。

### 実測数値を読むときの留保を明記する

これらの実装が謳う性能数値を鵜呑みにしないための留保を明記しておく。vLLM の AFD プラグインの公式ブログは、Attention 64 台と FFN 16 台の構成 (64A16F) で 16K 入力時に +11.3% のスループット改善を掲げるが、この数値には裏がある。ベンチマークの全ケースが `enable_force_load_balance=true` を使っており、これは実際のルーティングを合成的なエキスパート割り当てに置き換える設定である [報告]。プラグインの README 自身が「これはモデル出力を変えるので、精度評価や本番サービング評価に使ってはならない」と明記している [報告]。さらに Decode の KV も実データではなく合成コネクタで供給される。つまり +11.3% は合成負荷分散下のマイクロベンチであって本番数値ではない [報告]。加えて自動 E2E テストが通っているのは DeepSeek-V2-Lite という小規模モデルのみで、大規模構成での P/D と AFD の同時実測は公開範囲に無い [報告]。同様に FastAFD の 1.35 倍から 1.45 倍という主張も Decode 定常状態に限った測定で、Prefill の供給は P/D 分離に委ねる前提であり、次世代ハードウェアの数値は実測ではなく投影である [報告]。技術の可能性と実証済みの範囲は、慎重に切り分けて読む必要がある。

## まとめ

本稿は「分離」という一語に詰め込まれた複数の技術を、直交する軸として解きほぐすことを試みた。要点を改めて並べる。P/D 分離は推論を時間軸 (Prefill と Decode) で切り、AFD は Decode の順伝播を空間軸 (Attention と FFN) で切り、FlowPrefill は Prefill クラスタ内部を順序軸 (実行の粒度とスケジュール頻度) で切る。この3つは分ける対象の軸が異なるので互いに直交し、原理的には掛け合わせられる。そして MoE の EP は4つ目の分離軸ではなく、3軸のいずれの内側にも現れる FFN 計算の実体、すなわち横断軸である。この見立てを持てば、似た語感の技術を同じ平面で比較して取り違える混乱から抜け出せる。

概念の直交性は、実装の現場で「Prefill (HT) と Decode (LL) で EP の通信が別物」という1つの非対称に接地する。この非対称が「1つの通信グループでは両立しない」制約を生み、フェーズ分離を技術的必然として要請する。NCCL EP の LL/HT 二分と、SGLang の DeepEP auto モードが Prefill で normal、Decode で low_latency を選ぶ挙動は、この非対称を2つの独立な一次ソースから裏づけている。

実装の到達点は、vLLM と SGLang で正反対だった。vLLM は AFD をプラグインとして実装し、その上に P/D 分離と EP を薄く重ねた 2p1a1f レシピという小規模実証を持つ。SGLang は AFD 以外の技術 (P/D 分離、EP、DP attention、TBO) を大規模に実運用する一方、AFD だけは `check_afd_server_args()` が他の分離との併用を明示的に禁止する実験段階にある。理想の「全部盛り」に対し、両者は逆方向から接近している。そして公表される性能数値の多くが合成負荷や小規模モデルや定常状態に限った条件下のものである点は、技術の可能性と実証済みの範囲を切り分けて読むべき理由になる。

分離という設計思想の本質は、ハードウェアの物理的制約 (律速点の非対称、通信カーネルの HT/LL 非対称) に対して、計算をどの軸で切り分ければ各断片を最適化できるかを問うことにある。軸が違えば独立に選べるという直交性の視点は、今後さらに増えるであろう新しい「分離」を、既存の軸の掛け合わせなのか、それとも本当に新しい軸なのかという物差しで読み解く助けになるはずである。
