### SGLang-Neuron: Trainium で SGLang を動かすプラグイン

> 参照元: [Deploy frontier AI models on AWS Trainium with SGLang-Neuron](https://aws.amazon.com/blogs/machine-learning/deploy-frontier-ai-models-on-aws-trainium-with-sglang-neuron/)、[SGLang-Neuron v0.1.0: SGLang's Serving Stack on AWS Trainium](https://www.lmsys.org/blog/2026-11-12-sglang-neuron-v0.1.0/)

SGLang は、オープンソースの LLM の推論エンジンです。Trainium は AWS が作った機械学習向けのチップです。この AWS と LMSYS のブログは、RadixArk が Amazon の Annapurna Labs と共同で、SGLang の本体を書き換えずに Trainium で動かせるプラグイン SGLang-Neuron を一般公開したことを伝えるもので、AWS の記事は使い方の案内、LMSYS の記事は仕組みと実測の説明です。GPU で SGLang を使っている人が、同じ使い方のまま Trainium で推論や強化学習のロールアウトの生成をできるようになります。

:::message
**コメント**: SGLang の本体はそのままで、API サーバー、スケジューラ、radix cache、PD 分離の取り決めは SGLang の側に残し、モデルの実装、attention や MoE の NKI のカーネル、グラフの実行、KV の置き場といった Trainium に固有の部分をプラグインが持つ、という vLLM Neuron Plugin と同じ形で SGLang も使えるようになったのは待望のリリースですね。Miles など SGLang 向けの強化学習ライブラリの利用も、今後検証してみたいです。
:::

#### 参照元からの抜粋と要約

- **課題**: GPU で SGLang を使っている人が、同じ使い方のまま Trainium を使いたい、という場面に向けた公開の告知です。
- **ねらい**: SGLang の使い方を変えずに Trainium で推論できるようにすること。
- **やったこと**: 記事では、SGLang-Neuron を本体の外のプラグインとして作り、環境変数 `SGLANG_PLATFORM=neuron` で選べるようにしたと説明しています。コードは [sgl-project/sglang-neuron](https://github.com/sgl-project/sglang-neuron) で公開されています。
- **結果**: 記事によると、10 月の非公開のベータに続く v0.1.0 として一般公開されました。GPU と比べてどれくらい速いかは、まだ示されていません。

### Muse Spark Open の megakernel: 1 層を 1 回の起動にまとめる融合カーネル

> 参照元: [Muse Spark Open Ultrafast: Pushing beyond 1,000 Tokens per second](https://www.lmsys.org/blog/2026-11-05-muse-spark-open-ultrafast/)

Muse Spark Open は Meta が重みを公開した MoE のモデルです。1 人のリクエストに速く答える場面では、GPU は重みを読み出しては小さな演算をこなすことを繰り返すので、演算ごとにカーネル、つまり GPU に投げる 1 まとまりの処理を起動し直すたびに手が止まることが、速さの壁になります。この LMSYS のブログは、SGLang のチームの立場の著者が、Muse Spark Open の 1 層分の attention と MoE を 1 回の起動で動かす megakernel を CUDA C++ と PTX で書き、GB300 で 1 人のリクエストのデコードを約 2 倍に速くした記録です。

:::message
**コメント**: 最近 megakernel が流行っていますが、これまでは人が部品ごとに、あるいはよく出てくる決まった連続の処理を fused kernel にまとめるのが一般的でした。生成 AI の進化に伴って、1 つのモデルのために処理の全体を通した最適化を個別に作っても、費用対効果の面で問題がなくなってきていることが背景にありそうです。今回も本体のモデルの分だけで約 8,000 行の CUDA C++ と PTX を書いていて、モデルごとにここまで作り込む形が当たり前になっていくのかもしれません。
:::

![1 人のリクエストのデコードのスループットが、これまでの SGLang の 毎秒 517 トークンから megakernel で毎秒 1,109 トークン になることを示す図](https://www.lmsys.org/images/blog/muse-spark-open-ultrafast/fig_tps.png)
*出典: [Muse Spark Open Ultrafast](https://www.lmsys.org/blog/2026-11-05-muse-spark-open-ultrafast/) の図*

#### 参照元からの抜粋と要約

- **課題**: SGLang は 1 人のリクエストのデコードの 1 ステップで約 1,450 個のカーネルを順に起動していて、切れ目ごとに GPU が止まり、メモリの帯域を使い切れていません。
- **ねらい**: 1 層分の演算を 1 回の起動にまとめて GPU を止めずに動かし、デコードを毎秒 1,000 トークンより速くすること。
- **やったこと**: 記事では、1 層分を受け持つ常駐のカーネルの中で、ワープ (GPU の中で一緒に動く 32 スレッドの組) ごとに重みの読み込み、計算、通信の役割を固定し、いまの演算を計算している間に次の演算の重みを読み始めるようにしたと説明しています。カーネルの切れ目が無くなるので、読み込みと計算が途切れずに重なります。コードは [facebookresearch/sgl-muse-mega](https://github.com/facebookresearch/sgl-muse-mega) で公開されています。
- **結果**: 記事によると、GB300 8 枚で 1 リクエストを流すと、デコードは従来の SGLang の毎秒 517 トークンから 1,109 トークンへ 2.1 倍になり、ねらいの毎秒 1,000 トークンを超えました。対応しているのはバッチ 1 の場合だけです。

### SGLang の unified memory: KV と状態をまとめた共有の置き場

> 参照元: [Unified Memory in SGLang: One Arena for Every Token Lifetime](https://www.lmsys.org/blog/2026-11-11-unified-memory/)

最近のモデルには、文脈が長いほど KV キャッシュが伸び続ける attention の層と、直近だけを見る層や固定の大きさの状態を持つ層を混ぜたハイブリッドなものが増えています。SGLang はこれまで、この 2 種類に別々の置き場を用意し、その割合を起動時に決め打ちしていたので、負荷によって片方だけが足りなくなりました。この LMSYS のブログは、著者らがこれらを GPU のメモリの 1 つの置き場にまとめ、使う量を需要に合わせて動かす unified memory を SGLang に入れ、同時に動かせるリクエストを増やした話です。ここでの unified memory は、CUDA の Unified Memory とは別のものです。

:::message
**コメント**: attention と、Mamba の SSD のように状態を持ち回る層を混ぜたモデルの KV のメモリ管理は難しい問題で、それをうまく扱う手法には注目しています。割合を決め打ちせずに 1 つの置き場で需要に合わせる、という考え方は素直で、まだ実験的な機能ですが、複数の GPU や PD 分離の構成でどう振る舞うかを見ていきたいです。また、Trainium で SGLang を動かす SGLang-Neuron はまだ unified memory に対応していませんが、ハイブリッドなモデルで KV と状態の割合を決め打ちする問題は Trainium でも同じように起きるはずなので、入れられると良さそうです。
:::

![長い文脈のときも短いリクエストが多いときも、全体を見る attention の KV と上限のある状態が、1 つのアリーナの同じバイトを分け合う様子を示す図](https://www.lmsys.org/images/blog/unified-memory/fig2-one-arena.svg)
*出典: [Unified Memory in SGLang](https://www.lmsys.org/blog/2026-11-11-unified-memory/) の図*

#### 参照元からの抜粋と要約

- **課題**: ハイブリッドなモデルのメモリを種類ごとに固定の比率で分けると、比率が負荷に合わないときに、メモリが余っているのにリクエストを受け入れられません。
- **ねらい**: 置き場を 1 つにまとめても既定の構成と同じ以上の性能を保ち、より多くのリクエストを収容すること。
- **やったこと**: 記事では、全部の層の KV と状態を 1 つの連続した領域の中の帯として確保し、受け入れる前に、最後まで動かすのに必要なメモリがあるかを判定するようにしたと説明しています。使い方は [SGLang のドキュメント](https://docs.sglang.io/docs/advanced_features/unified_memory) にあります。
- **結果**: 記事によると、H200 1 枚で GPT-OSS-20B を同時 1,024 の負荷で動かすと、同時に動かせたリクエストは既定の構成の 618 件から約 1,000 件へ約 1.6 倍になり、ねらいに届きました。まだ実験的な機能で、ハイブリッドなモデルだけが対象です。

### vLLM の DeepSeek-V4.1-Flash on Vera Rubin: 同じ interactivity で GB300 の 58 倍

> 参照元: [DeepSeek-V4.1-Flash on Vera Rubin NVL72: 58x Throughput vs. GB300 NVL72 at 387 tokens/s](https://vllm.ai/blog/2026-11-12-deepseek-v41-flash-vera-rubin)

推論の性能は、ふつう TTFT や TPOT、両方の目標を満たしたリクエストだけを数える goodput で語られます。この記事は、SemiAnalysis のベンチマーク InferenceX の流儀で、横軸に interactivity、縦軸に GPU 1 枚あたりのスループットをとった曲線で比べます。interactivity は 1 人の利用者に毎秒何トークン届くかを表す値で、同じ interactivity の点どうしで比べると、利用者の体感をそろえたまま、ハードウェアがどれだけ多くの仕事をさばけるかが分かります。この vLLM のブログは、Inferact と vLLM のチームが、GB300 NVL72 で組んだ DeepSeek-V4.1-Flash の構成を、次の世代のラックの Vera Rubin NVL72 に移して作り直した記録です。

:::message
**コメント**: interactivity は聞き馴染みのない言葉です。InferenceX の[資料](https://github.com/SemiAnalysisAI/InferenceX/blob/3253e6572bb6dfe6255629a50210a48a0c0c36e1/inferencex-e2e/docs/MODELS.md)によると、エージェントの会話を再生する AgentX の既定の interactivity は、リクエストごとに TTFT を含む全体の時間を出力のトークン数で割り、その P90 を取ってから逆数にしたもので、およそ 1 ÷ (TPOT + TTFT ÷ 出力のトークン数) になります。最初のトークンが出るまでの待ちも罰として入るので、トークンの間の時間だけから求める 1 ÷ TPOT より小さく出ます。TTFT と TPOT を別々の目標で切る goodput と違い、1 本の数で利用者の体感を表そうとしている点が面白いと思いました。ただ、前の GB300 の記事の図は TTFT を含まない 1 ÷ TPOT の表示を引いていて、今回どちらで比べたかは書かれていません。58 倍には Rubin 向けにカーネルを作り直した分も入り、スループットにはキャッシュに当たった入力のトークンも数えているので、世代の差そのものとは読まないほうがよさそうです。一番面白かったのは、計算が速くなった結果、ボトルネックがメモリと割り振りに移ったことです。1 つのラックがさばく同時のセッションが増え、GPU ごとに KV を持ち、セッションを GPU に固定する GB300 のときのやり方では追いつかなくなりました。KV の置き場をまとめて需要に合わせる点は、今週の unified memory の話とも似ています。
:::

![Vera Rubin NVL72 の GPU 1 枚あたりのスループットが、同じ interactivity の点で、Dynamo と vLLM で動かした GB300 NVL72 の 58 倍になることを示す図](https://vllm.ai/blog-assets/figures/2026-11-12-deepseek-v41-flash-vera-rubin/hero.png?v=20261112)
*出典: [DeepSeek-V4.1-Flash on Vera Rubin NVL72](https://vllm.ai/blog/2026-11-12-deepseek-v41-flash-vera-rubin) の図*

#### 参照元からの抜粋と要約

- **課題**: GB300 NVL72 向けの構成を Rubin に移すと同時のセッションが大きく増え、GPU ごとに KV を持ちセッションを GPU に固定するやり方では、キャッシュが足りず、負荷も偏ります。
- **ねらい**: GB300 の構成の形を保ったまま、カーネルとメモリの使い方を Rubin に合わせて作り直し、同じ interactivity でさばける量を増やすこと。
- **やったこと**: 記事では、Rubin の GPU 1 枚に 2 つあるメモリの領域のうち、計算の部品が速く読める自分の側に重みなどを置くようにカーネルを作り直し、KV キャッシュをラック全体で 1 つの Mooncake の置き場にまとめ、負荷の少ない GPU にリクエストを送る割り振りに変えたと説明しています。変更は vLLM 本体の [PR #54371](https://github.com/vllm-project/vllm/pull/54371) などに入っています。
- **結果**: 記事によると、AgentX の負荷で、同じ interactivity の点の GPU 1 枚あたりの処理量は GB300 NVL72 の 58 倍になり、ねらいに届きました。共有の置き場と割り振りの変更で、TTFT の中央値も 29.8 秒から 4.2 秒へ約 7 分の 1 になっています。

## カーネルと開発の道具

### TLX: ワープの役割分担を書ける Triton の拡張

> 参照元: [How We Built TLX: A Hardware-Native GPU Compiler for Production ML at Scale](https://engineering.fb.com/2026/11/10/open-source/tlx-a-hardware-native-gpu-compiler-for-production-ml/)

Triton は GPU のカーネルを Python から書ける言語で、Meta の社内でも広く使われています。ところが Hopper や Blackwell では、データを運ぶ係と計算する係にワープを分ける warp specialization や専用の転送の仕組みといった段取りが性能の鍵になり、Triton ではそれがコンパイラの裏に隠れているので、新しい GPU が出るたびにコンパイラの対応を待つことになっていました。この Meta のブログは、Triton の書き方を残したまま、ワープの組ごとの役割分担と同期を書ける拡張の TLX を作り、広告や推薦、LLM の学習の本番で使った経験をまとめたものです。

:::message
**コメント**: 記事は、TLX はたいてい手で調整した CUDA と同等の性能が出て、開発はずっと速いと述べています。ただ、CUDA と比べた数字は載っておらず、Triton の DSL を拡張して書くと、CUDA でそのまま書くより行数がどのくらい減り、性能がどこまで並ぶのか、私にはまだ体感がないので、同じカーネルを両方で書いて今後確かめたいです。
:::

![1 つのスレッドを単位にする CUDA と、塊を単位にする Triton の間に、ワープの組を単位にする段が抜けていて、TLX がそこを埋める構成図](https://engineering.fb.com/wp-content/uploads/2026/11/Meta-TLX-Figure-3.png)
*出典: [How We Built TLX](https://engineering.fb.com/2026/11/10/open-source/tlx-a-hardware-native-gpu-compiler-for-production-ml/) の図*

#### 参照元からの抜粋と要約

- **課題**: 新しい GPU が求める実行の段取りは、CUDA なら書けても手間が大きく、Triton ではコンパイラの裏に隠れるので、新しいハードウェアへの対応が遅れます。
- **ねらい**: Triton の書き方を保ったまま、ワープの組を単位に段取りを書けるようにし、新しいハードウェアの機能をコンパイラを待たずに使えるようにすること。
- **やったこと**: 記事では、ワープの組への役割の割り当て、組どうしの同期、専用の転送の仕組みと記憶領域への直接の読み書きなどを Triton に足したと説明しています。Hopper 以降の GPU がもともとワープの組の単位で動くことに合わせた形です。コードは [facebookexperimental/triton](https://github.com/facebookexperimental/triton) で公開されています。
- **結果**: 記事によると、広告の生成モデルの学習では attention を 1 つのカーネルにまとめたものが、まとめる前より順伝播で最大 2 倍速く、推薦の推論では H100 で以前のカーネルの 4 倍のスループットになり、ねらいどおりハードウェアの機能を使い切れました。LLM の事前学習の MoE の事例には、速さの比較がありません。

### LLDB で CPU と GPU を 1 つのセッションでデバッグする拡張

> 参照元: [Extending LLDB to Debug Applications That Span CPUs and GPUs](https://engineering.fb.com/2026/11/09/developer-tools/extending-lldb-to-debug-applications-that-span-cpus-and-gpus/)

いまの AI のプログラムは CPU のコードと GPU のカーネルを行き来するので、不具合も CPU と GPU の境目をまたいで起きます。ところが GPU は CPU と命令の種類もメモリの使い方も違うので、ふつうのデバッガでは 1 つのプロセスとして調べられず、これまでは AMD の ROCgdb や NVIDIA の CUDA-GDB のような会社ごとの専用のデバッガが、共通の機能まで別々に作ってきました。この Meta のブログは、Meta のチームが、デバッガ LLDB に特定の会社に依存しない GPU のためのプラグインの土台を作り、その大部分を本家の LLVM に取り込んだことを説明したものです。

:::message
**コメント**: エージェントが流行っている今は、ツールの呼び出しやシミュレーションで、GPU と比べた CPU の使われ方の比率が戻ってきているので、CPU と GPU をまとめて 1 つのセッションで調べられるのは、とても大事になりそうです。今後ぜひ確かめてみたいです。
:::

![CPU と GPU が別々の LLDB のターゲットのままで、lldb-server の中のプラグインが CPU 側と GPU 側のデバッグを協調させる構成図](https://engineering.fb.com/wp-content/uploads/2026/11/Extending-LLDB.png)
*出典: [Extending LLDB to Debug Applications That Span CPUs and GPUs](https://engineering.fb.com/2026/11/09/developer-tools/extending-lldb-to-debug-applications-that-span-cpus-and-gpus/) の図*

#### 参照元からの抜粋と要約

- **課題**: ふつうのデバッガは 1 つのプロセスが 1 つの命令の種類とメモリの見方を持つことを前提にしていて、GPU はこれに合わないため、会社ごとの専用のデバッガが同じ機能を別々に保守しています。
- **ねらい**: LLDB に会社に依存しない共通の土台を作り、新しいハードウェアの対応を、その会社のプラグインを書くだけで済ませること。
- **やったこと**: 記事では、CPU と GPU を別々のデバッグの対象として表し、それぞれが自分の命令の種類やアドレスの空間を持つようにしたと説明しています。1 つのプロセスに押し込めると、すべての操作が CPU 向けか GPU 向けかの分岐になるからです。土台の大部分は LLVM の本家に取り込み済みです。
- **結果**: 記事によると、AMD の HIP のカーネルで、CPU と GPU の対象が並び、GPU 側のブレークポイントとバックトレースが動くことを確かめ、Meta の社内では構成の違う複数の GPU の取り組みが同じ仕組みを使っています。共通の土台というねらいには届いていますが、比べられる数字は無く、残りの機能の本家への取り込みも終わっていません。

### GC-MoE on SM120: ワークステーションの Blackwell での MoE デコードの重ね合わせ

> 参照元: [GC-MoE on SM120: Overlapping Expert-Parallel Token Dispatch with Warp-Level FP8xFP4 Block-Scaled MMA on Consumer Blackwell](https://arxiv.org/html/2611.16219)

MoE のモデルを複数の GPU で動かすときは、専門家を GPU ごとに分けて持つ専門家並列がよく使われ、デコードの 1 層ごとに、トークンを担当の GPU へ送る dispatch、専門家ごとの行列の掛け算、結果を戻して足し合わせる combine の 3 段が順に起きます。著者らの前作の GC-MoE は、この 3 段を GPU の中で重ねて動かして待ち時間を減らしましたが、データセンター向けの Blackwell の専用の機能と NVLink に頼っていました。このプレプリントは、Alibaba の研究者が、その機能も高速な GPU 間の接続も無いワークステーション向けの Blackwell の SM120 で同じ重ね合わせを作り直し、既存の手法より約 1.4〜1.5 倍速くしたものです。

:::message
**コメント**: SM の一部だけを使う区画を作る CUDA の Green Context で SM を分け、段を重ねて動かす話です。データセンター向けの Blackwell に合わせて作られた MoE のカーネルが、ワークステーション向けの Blackwell では命令の種類からして使えず、作り直しになるというのは、同じ Blackwell という名前でも中身がかなり違うことを示していて覚えておきたいです。PCIe では結果を戻す側の転送が最も大きくなるので、バイト数よりも転送の回数を減らす、という考え方も、NVLink の無い環境で MoE を動かすときの参考になりそうです。ただし評価は 8 枚の RTX PRO 5000 の 1 台だけで、複数のノードは試しておらず、バッチ 256 の GLM5.2 では Cake との差が 1.017 倍まで縮み、著者らも未解決の課題としています。コードの公開先もプレプリントには書かれていないので、PCIe の GPU で MoE を動かす機会があれば、FlashInfer のカーネルとの差を自分で見てみたいです。
:::

![GLM5.2 の形の MoE で、バッチの大きさを 1 から 256 まで変えたときのデコードのレイテンシーを、GC-MoE と、FlashInfer の CuTe DSL で書いた実装と、Cake で比べると、どのバッチでも GC-MoE が最も速いことを示す図](https://arxiv.org/html/2611.16219v1/pro5000_glm52_gc_moe.png)
*出典: [GC-MoE on SM120](https://arxiv.org/html/2611.16219) の Figure 3*

#### 参照元からの抜粋と要約

- **課題**: ワークステーション向けの SM120 には前作が頼った専用の機能が無く、GPU の間も PCIe でつながるので、前作の作り方は使えません。
- **ねらい**: SM120 と PCIe の制約の中で、3 段を重ねて動かす利点を、仕組みの作り直しで取り戻すこと。
- **やったこと**: 著者らは、SM120 のテンソルコアがワープ単位の命令でしか低いビット数の計算を扱えないので、行列の掛け算を 1 つのワープで完結する形に組み直しました。PCIe の上で一番重い戻りの転送は、連続した区間ごとにまとめて 1 回でコピーする専用の係に任せています。コードの公開先は書かれていません。
- **結果**: 著者らによると、8 枚の RTX PRO 5000 で、2 つのモデルの形と 18 通りのバッチの条件のすべてで既存の 2 つの手法より速く、レイテンシーの倍率の平均は FlashInfer の実装に対して 1.522 倍、Cake に対して 1.387 倍で、ねらいに届きました。ただし、バッチを 256 まで増やすと、Cake との差は 1.017 倍まで縮みます。

## 学習の並列化

### AutoParallel: 並列化の計画の自動探索

> 参照元: [AutoParallel: Composable, PyTorch-Native Automatic Parallelism for Production Training](https://arxiv.org/html/2611.08660)

大きなモデルの学習では、1 枚の GPU に載らない重みや計算を何枚もの GPU に分ける並列化が必要で、重みを分割する FSDP や、1 つの演算を分担する TP などを組み合わせます。どれをどう組み合わせるかはこれまで専門家が手で書いていて、モデルや GPU の台数が変わるたびに書き直しが必要でした。このプレプリントは、Meta Superintelligence Labs の研究者が、PyTorch の中だけで動き、結果を普通の PyTorch のプログラムとして出す自動の計画ツール AutoParallel を作り、多くの構成で専門家の手書きに並ぶか上回る計画を見つけたものです。

:::message
**コメント**: 学習は、モデルや系列長などの条件が変わらない限り、一度決めた並列化を固定して回せるので、見積もりやすいのかもしれません。それでも、多様なモデルやメモリの状況まで考えて並列化を自動で用意するのは難しそうに感じました。この手法が最小にするのは所要時間の見積もりで、大きな構成では近似で解いており、実測での比較相手も手書きの計画だけなので、どこまで最適なのかは気になりました。
:::

![AutoParallel が学習の計算全体をグラフとして取り出し、演算ごとの分け方の候補から 1 つずつ選び、普通の PyTorch のモジュールとして出力する構成図](https://arxiv.org/html/2611.08660v1/overview.svg)
*出典: [AutoParallel](https://arxiv.org/html/2611.08660) の Figure 1*

#### 参照元からの抜粋と要約

- **課題**: 並列化のやり方は専門家が手で書いていて、モデルやハードウェアが変わるたびに調整し直す必要があり、先行する自動化の研究は PyTorch とは別の実行環境に頼るなどの理由で、手書きを置き換えられていません。
- **ねらい**: PyTorch の外の実行環境を使わずに、演算ごとの分け方を学習の計算全体で同時に探し、専門家の手書きに並ぶか上回る計画を自動で見つけること。
- **やったこと**: 著者らは、順伝播と逆伝播の計算をグラフとして取り出し、演算ごとに正しく動く分け方の候補を並べて、所要時間の見積もりで全体の組み合わせを選ぶ探索を作りました。同じ層の繰り返しをまとめて解くことで、大きな構成でも短時間で解けます。コードは meta-pytorch/autoparallel で公開されています。
- **結果**: 著者らによると、H100 最大 128 枚の 14 の構成のうち 9 つで TorchTitan の手書きの計画を上回り、DeepSeek-V3 の構造の 16B の MoE を H100 8 枚で学習したときは、1 秒あたりのトークン数が手書きの 1.18 倍になりました。ねらいにはおおむね届きましたが、残りの 5 つの構成では手書きを最大 3.6% 下回りました。

### SS-HSDP: 計算の並べ方と更新の単位の分離

> 参照元: [SS-HSDP: Efficient and Flexible Sharded Data Parallelism via Runtime-Update Decoupling](https://arxiv.org/html/2611.16467)

大きなモデルの学習では、重みや勾配を GPU ごとに分割して持ち、計算の直前だけ集める PyTorch の FSDP2 のような方法が広く使われています。ところが、8 ビットの数でブロックごとに倍率を共有する MXFP8 のような形式や、行列全体を単位に更新する Muon のようなオプティマイザが出てきて、計算に都合の良い重みの並べ方と、更新に都合の良い単位が食い違うようになりました。このプレプリントは、Tsinghua University と Shengshu Technology の研究者が、計算用と更新用の重みを別物として扱い、コピーを増やさずに両方の都合を満たす SS-HSDP を作ったものです。

:::message
**コメント**: これも AutoParallel と同じく、並列化を決め打ちのレシピから柔軟なものへ移していく流れの一つだと読みました。AutoParallel は演算ごとの分け方を探すほうで、SS-HSDP は計算と更新という役割の違いで分け方を切り離すほうなので、自動化と分離が両方から進んでいるのが面白いです。プレプリントの関連研究には、DeepSeek-V4 や Kimi K3 や GLM-5 が Muon をヘッド単位で使う例が挙がっていて、行列単位の更新が実験ではなく大規模な事前学習の道具になってきたことが、この仕組みが出てきた理由だと感じます。気になるのは、主な比較で使った GPU の機種が書かれていないこと、比較相手の veScale-FSDP が著者らの作り直しであること、入力が合成データであること、そしてコードがまだ公開されていないことです。公開されたら、プレプリントが報告する Muon と AdamW の差を手元で再現し、FSDP2 でヘッド単位の Muon がそもそも組めるのかもあわせて確かめたいです。
:::

![MXFP8 での学習の MFU とピークのメモリを 4 つのモデルと 32 枚から 128 枚の GPU で比べると、SS-HSDP がどの構成でも MFU が最も高いことを示す図](https://arxiv.org/html/2611.16467v1/x5.svg)
*出典: [SS-HSDP](https://arxiv.org/html/2611.16467) の Figure 6*

#### 参照元からの抜粋と要約

- **課題**: FSDP2 などは、計算が求める並べ方と更新が求める単位を同じ分割に結びつけているので、新しい形式やオプティマイザでは、計算の効率か更新の柔軟さのどちらかが落ちます。
- **ねらい**: 計算に使う重みと更新に使う重みを分け、余分なデータの移動なしに両方の都合を満たすこと。
- **やったこと**: 著者らは、同じメモリを形の違う複数の見方で共有し、分割の段ごとにどの断片がどの GPU にあるかを記録する仕組みを作って、計算用と更新用の重みをコピーなしで両立させました。通信は GPU の計算の部品を使わない専用の転送で行い、計算と奪い合わないようにしています。コードは将来公開の予定です。
- **結果**: 著者らによると、MXFP8 で 128 枚の GPU を使って MiMo を学習すると、GPU の理論上の性能を使えた割合 (MFU) が、最も速い既存の方法の約 1.22 倍になり、ねらいに届きました。ただし、Qwen3-30B-A3B では MXFP8 の効果は 1% 未満でした。

## 強化学習の数値

### BF16 の強化学習の遅さの原因: 丸めで消える小さな更新

> 参照元: [Closing the BF16-FP16 Convergence Speed Gap in RL Post-Training with Stochastic Rounding](https://arxiv.org/html/2611.13545)

LLM の学習では、重みの元の値を 32 ビットで持ち、計算には 16 ビットに丸めた写しを使う混合精度がふつうです。16 ビットの形式のうち BF16 は事前学習では問題なく収束しますが、正解を自動判定して報酬を与える強化学習の RLVR では学習率をとても小さくするため、同じ学習率の FP16 より収束が遅くなります。このプレプリントは、NVIDIA の研究者が、先行研究の説明だった推論側と学習側の確率のずれを取り除いても遅さが残ることを示し、小さな更新が丸めで消えて BF16 の写しが変わらない重みの固着という本当の原因を突き止めて、丸め方を変えて直したものです。

:::message
**コメント**: 先行研究は、BF16 の強化学習の遅さを推論側と学習側の確率のずれのせいだとしていました。このプレプリントは、先行研究の Qi らが報告した BF16 の GRPO の崩壊が、著者らの環境では vLLM の TorchInductor の最適化を有効にしたときだけ起きたとしたうえで、ずれをビット単位でなくしても BF16 が遅いことを示していて、原因が少なくとも 2 層あることが見えてくるのが面白いです。学習率がとても小さいと更新が丸めで消える、というのは言われてみれば当然ですが、最初の 4 回の更新の後に変わらず残った重みの割合を BF16 と FP16 で数えて、仮数のビット数を 1 つずつ増やした擬似の形式で収束が FP16 に近づくことまで確かめている、という詰め方がよいと思いました。学習のテーマの SS-HSDP にも、GPU の間の集計を BF16 の確率的丸めで行う方式が出てきたので、低精度で集計や更新をするところで確率的丸めが標準の道具になっていく気がします。ただ、丸めのカーネル自体のコストは数字がなく、複数のモデルでの主な比較は、推論と学習の確率をビット単位でそろえた状態ではなく TorchInductor を切っただけの状態で行われています。手元の RL の基盤でも、最初の数回の更新で BF16 の重みがどれだけ変わらないかは安く数えられるので、まずそこを測ってみたいです。
:::

![確率的丸めを使う BF16 が、3 つのモデルと 2 つのデータセットで FP16 とほぼ同じ報酬の伸び方をし、ふつうの BF16 より速く報酬が上がることを示す図](https://arxiv.org/html/2611.13545v1/reward_trajectory.svg)
*出典: [Closing the BF16-FP16 Convergence Speed Gap in RL Post-Training with Stochastic Rounding](https://arxiv.org/html/2611.13545) の Figure 1*

#### 参照元からの抜粋と要約

- **課題**: 学習率がとても小さい RLVR では BF16 が FP16 より多くの学習の回数を要し、推論側と学習側の確率のずれを取り除いてもこの差は残るので、これまでの説明では足りません。
- **ねらい**: 遅さの原因を突き止め、参照のモデルからの離れ方を増やさずに、BF16 のまま FP16 と同じ速さで収束させること。
- **やったこと**: 著者らは、最初の数回の更新の後に変わらず残った重みの割合を数え、BF16 では 98.84%、FP16 では 90.79% だったことから、更新が BF16 の刻みの半分に届かないうちは丸めで打ち消される重みの固着が原因だと突き止めました。そこで、BF16 の写しを作る丸めを、値の近さに応じた確率で上下に丸める確率的丸めに替えました。
- **結果**: 著者らによると、確率的丸めの BF16 は、試したすべてのモデルとデータセットの組み合わせで FP16 とほぼ同じ報酬の伸び方になり、学習率を 2 倍にして補う方法のように参照からの離れ方が約 1.5 倍に増えることもなく、ねらいに届きました。ただし、Qwen3-30B-A3B では答えの長さが約 25% 短いまま残り、原因は分かっていません。

## モデルの調整と圧縮

### 前向きの計算による削る重みの探し方

> 参照元: [Efficient LLM Adaptation with Forward-Only Passes](https://arxiv.org/html/2611.10610)

学習を終えたモデルを特定の課題向けに調整するには、ふつう勾配を求める逆伝播で重みを更新しますが、そのぶんメモリと時間がかかります。先行研究の LASER は、重み行列を特異値分解で重要度の順の成分に分け、重要度の低い成分を削ると正答率が上がる現象を見つけましたが、削る行列を全部試して決めるので遅いままでした。このプレプリントは、Lund University の研究者が、逆伝播を使わず、入力から出力を求めるふだんの前向きの計算だけで、削る重み行列を探す方法を提案したものです。

:::message
**コメント**: 今回の中ではインフラから一番遠い話ですが、サービングで毎日大量に回っている前向きの計算をそのままモデルの調整に使えないか、という問いの立て方が気になって入れました。逆伝播が要らないので、推論用の GPU や推論エンジンのままで調整の候補を探せるようになれば、学習用の環境を別に用意する手間が減りそうです。一方で、実験は課題ごとの検証データで候補を選んで正答率を測るもので、実際のサービングのリクエストを使ったわけではありません。GPT-J-6B では、8 つのデータセットのうち Bios Profession で正答率が LASER より 3.0 ポイント、LASER-Grad より 1.4 ポイント低く、WikidataQA でも LASER-Grad より 1.2 ポイント低く、最大 57B とされるモデルも一度に使う重みは 14B の MoE です。コードの公開先もプレプリントには書かれていないので、まずは削った後のモデルが推論エンジンでスループットや正答率をどう変えるかを見てみたいです。
:::

![重み行列を SVD で成分に分け、前向きの計算で各成分の角度の集中度を測り、散らばりを生む重み行列だけを削る手順を示す図](https://arxiv.org/html/2611.10610v1/main_camera.png)
*出典: [Efficient LLM Adaptation with Forward-Only Passes](https://arxiv.org/html/2611.10610) の Figure 1*

#### 参照元からの抜粋と要約

- **課題**: LASER の全部を試す探索は時間がかかり、勾配を使う LASER-Grad は逆伝播のぶんメモリと時間がかかります。
- **ねらい**: 逆伝播を使わず、前向きの計算だけで、削るべき重み行列を効率よく見つけること。
- **やったこと**: 著者らは、各成分が作る途中の値がトークンどうしでどれだけ同じ向きを向いているかを測り、向きが散らばっている成分の多い行列ほど削る候補として点数を付け、点数の高い候補だけを実際に削って確かめました。ファインチューニングでは向きが集中していくという先行研究の知見に対して、逆の状態にある行列を選ぶ考え方です。
- **結果**: 著者らによると、GPT-J-6B では探索の時間が LASER-Grad の平均 18.4 分の 1 になり、8 つのデータセットのうち 4 つで最も高い正答率を出して、ねらいに届きました。ただし、Bios Profession では LASER と LASER-Grad の両方より正答率が低くなりました。

### 大きいモデルほど補えない圧縮の傷

> 参照元: [When Bigger Becomes Brittle: Why Compression Hurts More as Language Models Scale](https://arxiv.org/html/2611.07891)

量子化や枝刈りでモデルを軽くしたときの良し悪しは、ふつうベンチマークの点数で測りますが、点数に表れるのは出力に残った悪化だけです。中で大きく壊れても、残りの部分が補えば点数は下がらないので、点数だけでは、壊れていないのか、壊れたが補えたのかを区別できません。このプレプリントは、IIIT-Delhi を中心とする研究者が、文章の中から答えの名前を探す役目の注意のヘッドを止めたときの悪化を、補われた分と出力に残った分に分けて測り、モデルが大きいほど補いの割合が下がって傷が出力に残りやすいことを示したものです。

:::message
**コメント**: 同じテーマの前のプレプリントが、重みを削ると正答率が上がる場合を探していたのに対して、こちらは削ったときに大きいモデルほど傷が素通りする、という逆向きの話で、並べて読むと面白いです。小さいモデルではほぼ無害だった圧縮が、大きいモデルでは高くつくことがありうる、という著者らの示唆を、点数ではなく中で何が起きているかの測定から導いている点が気になりました。ただ、調べた能力はひな形の文で名前を当てる 1 種類だけで、量子化も 32 ビットの浮動小数点の推論の中で重みだけを 4 ビット相当に丸めた模擬で、実際の量子化のカーネルを使ったものではありません。著者らのコードの公開先も見当たりません。それでも、点数が下がらないことと中が壊れていないことは別だ、という見方は、圧縮した推論の構成を評価するときの測り方として覚えておきたいと思いました。
:::

![Pythia-410M は検索のヘッドを止めた傷のほとんどを、抑えのゆるみと残りの部品の補いと正規化の変化の合計で取り戻すが、Pythia-12B はごく一部しか取り戻せず、傷が出力に残ることを比べた図](https://arxiv.org/html/2611.07891v1/fig_repair_bands_pythia_410m_12b.svg)
*出典: [When Bigger Becomes Brittle](https://arxiv.org/html/2611.07891) の Figure 3*

#### 参照元からの抜粋と要約

- **課題**: 圧縮の効果は出力に残った悪化だけで報告され、中でどれだけ傷つき、どれだけ補われたかも、それがモデルの大きさでどう変わるかも分かっていませんでした。
- **ねらい**: 出力に残った悪化を補いの分と厳密に分け、その割合が Pythia の 410M から 12B でどう変わるかを明らかにすること。
- **やったこと**: 著者らは、答えの名前を探すヘッドの出力を 0 にして、正解の名前と紛らわしい名前の点数の差の変化を、各部品が直接足している量に分ける恒等式を組みました。後ろのヘッドが答えの点数をもともとどれだけ抑えているかがモデルの大きさで変わることが、補いの割合が変わる一因だと確かめています。4 ビットの模擬の量子化と枝刈りでも同じ分け方をしました。
- **結果**: 著者らによると、同じ大きさの傷に対して、残りの attention の部品が補った割合は Pythia-410M の約 80% から Pythia-12B の約 9% に下がり、4 ビットの模擬の量子化でも出力に残る割合は 0.55 から 0.91 に上がって、ねらいの答えが得られました。ただし、調べたのはひな形の文での名前の検索だけです。

## ベクトル検索とクラスタリング

### GINGER: 粗くも細かくも使う 1 つの符号

> 参照元: [GINGER: Spicing Up Graph-Based Vector Search](https://arxiv.org/html/2611.08306)

RAG や推薦では、文章や画像を数のベクトルに変えた埋め込みを大量に持ち、問い合わせに近いベクトルを探します。全部と比べると遅いので、近いベクトルどうしをつないだグラフをたどって速く探す方法が使われ、たどる間は少ないビット数の粗い符号で比べ、最後に残った候補だけを細かい表現で並べ直します。これまでのライブラリは、粗い符号と細かい表現を別々に持つのでメモリを多く使いました。このプレプリントは、Google Research の研究者が、1 つの符号の上位のビットを粗い比較に、全体を並べ直しに使うライブラリ Ginger を作り、既存のライブラリより問い合わせを平均 1.8 倍速く処理できるようにしたものです。

:::message
**コメント**: 普段の推論や学習の話とは離れますが、RAG の裏側で毎回動く部分の話です。GPU を使わず CPU の SIMD だけで、再現率 95% での QPS が 14 のデータセットのうち 13 で、データセットごとの最速の既存のライブラリの平均 1.8 倍になった点が目を引きました。上位の 4 ビットだけ読めばグラフをたどれて、続きのビットまで読めば並べ直しに使える、という符号の作り方は、別々の表現を 2 つ持つより素直で、メモリの量と読み出す量を同時に減らせるのがうまいと思います。比べ方も、データセットごとの最速の相手との比較と、1 つのライブラリに固定した比較を分けて書いていて、どちらで見ても速いと言えるようにしているのが誠実だと感じました。一方で、8 ビットの整数の BigANN では SVS のほうが 4% 速く、小さいデータセットでは索引の構築で ParlayANN に、GloVe では Faiss に負けています。コードは公開されているので、手元の RAG の埋め込みの次元と件数で、いま使っている Faiss などとメモリと QPS を比べてみたいです。
:::

![14 のデータセットの幾何平均で、Ginger が再現率 95% でのクエリのスループットが既存のライブラリより高く、MS-MARCO での索引の構築も速いことを示す図](https://arxiv.org/html/2611.08306v1/teaser.svg)
*出典: [GINGER](https://arxiv.org/html/2611.08306) の Figure 1*

#### 参照元からの抜粋と要約

- **課題**: 既存のライブラリは、たどるための粗い符号と並べ直しのための細かい表現を別々に持つので、メモリを無駄に使い、グラフの辺の一覧もメモリを圧迫します。
- **ねらい**: 1 つの符号で粗い比較と細かい並べ直しを両立させ、グラフも圧縮して、速さ、メモリ、索引を作る時間の 3 つを同時に良くすること。
- **やったこと**: 著者らは、4 ビットの符号の各区間をさらに細かく分けて 10 ビットや 12 ビットにし、上位の 4 ビットを粗い比較に使いました。座標をランダムに回転してなめらかな分布に整えておくと、細かく分けても精度が落ちないので、1 つの符号で両方を兼ねられます。グラフの辺は損失なく詰めて保存します。コードは [google/ginger](https://github.com/google/ginger) で公開されています。
- **結果**: 著者らによると、7 つの既存のライブラリと比べ、本当に近い上位 10 件のうち 95% を見つける条件で、1 秒あたりの問い合わせの数は 14 のデータセットのうち 13 で、最も速い相手の平均 1.8 倍になりました。10 億件の索引を作る時間は最も速い Faiss の約 2 分の 1 で、ねらいに届きました。ただし、GloVe では Faiss が 2.1 倍速いままです。

### e-means: 指数移動平均による Lloyd の 10 分の 1 のエポックでの k-means の解き方

> 参照元: [e-means: outperforming k-means (in one-tenth the epochs)](https://arxiv.org/html/2611.09501)

k-means は、データの点を k 個のまとまりに分け、各点とそのまとまりの中心との距離が小さくなるように中心を決める方法で、ベクトル検索の索引づくりなどに広く使われています。標準の Lloyd のアルゴリズムは、全部の点を最も近い中心に割り当て直してから中心を置き直す 1 周を何十回も繰り返すので、点が多いと重くなります。このプレプリントは、FAIR at Meta の研究者が、新しい値を一定の割合で混ぜていく指数移動平均で中心を少しずつ動かす e-means を提案し、その設定を式で決められるようにして、Lloyd と同じかそれより小さい誤差に、約 10 分の 1 の周回の数で届かせたものです。

:::message
**コメント**: k-means はあまりに当たり前の道具なので、まだこんなに速くなる余地があったことにまず驚きました。深層学習で当たり前になったミニバッチ、中心を動かす幅をコサインで減らしていくやり方、スケーリング則でハイパーパラメータを決めるやり方を、そのまま古典的なアルゴリズムに持ち込んでいて、学習の側で育った道具が古い問題に戻ってくる流れが面白いです。プレプリントも IVF というクラスタに分けて探す検索の索引で評価していて、そうした索引は中で k-means を回して作るので、k-means の GPU の計算量が Faiss-GPU や Flash-KMeans と比べて約 10 分の 1 になるなら、索引の作り直しの頻度も変えられそうです。ただ、スケーリング則は DEEP という比較的高次元のデータセットで当てはめたもので、低次元で小さいデータには最適ではないと著者らも書いており、合成データの 140 の実験のうち 10 では、学習に使わない点での誤差が Lloyd に負けています。コードは Faiss の中に入っているので、手元の埋め込みで、いま使っている Faiss の k-means と時間と誤差を比べてみたいです。
:::

![DINO10B の 1 億点で、e-means が 2 エポックで Faiss-GPU と Flash-KMeans の 25 エポック目の誤差を下回ることを示す図](https://arxiv.org/html/2611.09501v1/robustness_tstar.svg)
*出典: [e-means](https://arxiv.org/html/2611.09501) の Figure 1 の左*

#### 参照元からの抜粋と要約

- **課題**: Lloyd の方法は 1 周ごとにデータ全体をなめるので重く、データの一部だけで中心を動かす既存の速い方法は、誤差が大きく、設定を問題ごとに手で探す必要がありました。
- **ねらい**: 設定を探索なしで決める式を与え、Lloyd より少ない周回と短い時間で同じかそれより小さい誤差に届くこと。
- **やったこと**: 著者らは、クラスタごとの点の数と和を指数移動平均で更新して中心を読み出すようにしました。Lloyd は 1 周に 1 回しか中心を動かせませんが、これはデータの一部を見るたびに動かせるので、少ない周回で収束します。コードは [Faiss の contrib/e_means](https://github.com/facebookresearch/faiss/tree/main/contrib/e_means) で公開されています。
- **結果**: 著者らによると、100 億件のデータを約 1,670 万のクラスタに分ける実験で、e-means は Lloyd より 0.014% 小さい誤差に、Lloyd の約 8.7 分の 1 の GPU 時間で届き、ねらいを満たしました。4 つのデータセットでも、既存の GPU の実装より 9.5〜45.5 倍速く同じ誤差に届いています。ただし、低次元の小さいデータでは、式の設定が最適ではありません。
