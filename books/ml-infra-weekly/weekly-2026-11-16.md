## 推論とサービング

### SGLang-Neuron: Trainium で SGLang を動かすプラグイン

> 参照元: [Deploy frontier AI models on AWS Trainium with SGLang-Neuron](https://aws.amazon.com/blogs/machine-learning/deploy-frontier-ai-models-on-aws-trainium-with-sglang-neuron/)、[SGLang-Neuron v0.1.0: SGLang's Serving Stack on AWS Trainium](https://www.lmsys.org/blog/2026-11-12-sglang-neuron-v0.1.0/)

SGLang は、プロンプトの先頭が同じリクエストどうしで KV キャッシュを使い回す prefix cache を、RadixAttention という木の形の仕組みで持つ、オープンソースの LLM の推論エンジンです。Trainium は AWS が作った機械学習向けのチップで、その上でモデルを動かすための道具一式を Neuron SDK と呼びます。この AWS と LMSYS のブログは、RadixArk が Amazon の Annapurna Labs と共同で、SGLang の本体を書き換えずに外から差し込むプラグイン SGLang-Neuron を一般公開したことを伝えるもので、AWS の記事は使い方の案内、LMSYS の記事は仕組みと実測の説明です。抜粋に出てくる PD 分離は、プロンプトを読む prefill とトークンを 1 つずつ作る decode を別のサーバーに分けて動かす構成のことで、その間の KV キャッシュのやり取りには通信ライブラリの NIXL と AWS の高速な通信装置の EFA を使い、GPU から追い出したキャッシュをホストのメモリに残す HiCache という仕組みも使えます。LMSYS の記事はこのリリースを v0.1.0 と呼び、10 月の非公開ベータの後継だとしています。

:::message
**コメント**: SGLang の本体はそのままで、API サーバー、スケジューラ、radix cache、PD 分離の取り決めは SGLang の側に残し、モデルの実装、attention や MoE の NKI のカーネル、グラフの実行、KV の置き場といった Trainium に固有の部分をプラグインが持つ、という vLLM Neuron Plugin と同じ形で SGLang も使えるようになったのは待望のリリースですね。Miles など SGLang 向けの強化学習ライブラリの利用も、今後検証してみたいです。
:::

#### 参照元からの抜粋と要約

- **課題**: GPU で SGLang を使っている人が、同じ使い方のまま Trainium で推論とロールアウトの生成をしたい、という場面に向けた公開の告知です。LMSYS の記事は、10 月の closed beta で持ち込めることは示せたので、次はそれを速くすることが課題だとしています。
- **ねらい**: SGLang の使い方を変えずに Trainium を使えるようにし、Trainium への対応と SGLang の本体の開発を切り離すこと。
- **やったこと**: 記事では、SGLang-Neuron を本体の外のプラグインとして作り、`SGLANG_PLATFORM=neuron` で選べるようにしたと説明しています。PyTorch の演算と NKI のカーネルを torch.compile でまとめて動かし、PD 分離では KV キャッシュを NIXL で EFA を通して送ります。コードは [sgl-project/sglang-neuron](https://github.com/sgl-project/sglang-neuron) で公開されています。
- **結果**: 記事によると、gpt-oss-120b を TP8・コンテキスト長 32K で動かした場合、HiCache を有効にすると出力のスループットが無効時の 1.72〜1.75 倍になり、これは「速くする」というねらいの方向に沿う結果です。ただし Kimi-K3 の 1 人あたり毎秒 67 トークンという数字には比較対象がなく、GPU との比較や本番の負荷でどこまで速いかは、この記事にはまだ示されていません。

### Muse Spark Open の megakernel: 1 層を 1 回の起動にまとめる融合カーネル

> 参照元: [Muse Spark Open Ultrafast: Pushing beyond 1,000 Tokens per second](https://www.lmsys.org/blog/2026-11-05-muse-spark-open-ultrafast/)

Muse Spark Open は Meta が重みを公開した MoE のモデルで、全体は 816B、1 トークンあたりに使う重みは約 42B、トークンごとに 256 の専門家のうち 8 つを選びます。1 人のリクエストに速く答える場面では、GPU の仕事は大きな計算より、重みを読み出しては小さな演算をこなすことの繰り返しになります。そのため、演算ごとにカーネル (GPU に投げる 1 まとまりの処理) を起動し直すたびに GPU の手が止まることが、速さの壁になります。megakernel は、多くの演算を 1 つの常駐するカーネルにまとめ、その中で読み込みと計算を重ねて、この止まる時間を無くす作り方です。この LMSYS のブログは、著者が SGLang のチームの立場から、Muse Spark Open の 1 層分の attention と MoE を 1 回の起動で動かす megakernel を CUDA C++ と PTX (NVIDIA の GPU の命令に近い言葉) で書き、GB300 で 1 人のリクエストのデコードを従来の SGLang の約 2 倍に速くした記録です。抜粋に出てくる SM は GPU の中の計算の単位、ワープはその中で同じ命令を一緒に実行する 32 スレッドの組、投機的デコードは小さい draft モデルが先に数トークンを予想し本体がまとめて確かめる方法です。

:::message
**コメント**: 最近 megakernel が流行っていますが、これまでは人が部品ごとに、あるいはよく出てくる決まった連続の処理を fused kernel にまとめるのが一般的でした。生成 AI の進化に伴って、1 つのモデルのために処理の全体を通した最適化を個別に作っても、費用対効果の面で問題がなくなってきていることが背景にありそうです。今回も本体のモデルの分だけで約 8,000 行の CUDA C++ と PTX を書いていて、モデルごとにここまで作り込む形が当たり前になっていくのかもしれません。
:::

*出典: [Muse Spark Open Ultrafast](https://www.lmsys.org/blog/2026-11-05-muse-spark-open-ultrafast/) の図*

#### 参照元からの抜粋と要約

- **課題**: 1 人のリクエストのデコードで、SGLang は 1 ステップに約 1,450 個のカーネルを順に起動していて、カーネルの切れ目ごとに SM やワープが止まるので、メモリの帯域を使い切れていません。
- **ねらい**: 1 層分の attention と MoE を 1 回の起動にまとめて GPU を止めずに動かし、1 人のリクエストのデコードを毎秒 1,000 トークンより速くすること。
- **やったこと**: 記事では、ある層の attention から次の層の qkv の射影と KV の書き込みまでを 1 回の起動で受け持つ megakernel を、本体のモデルの分だけで約 8,000 行書いたと説明しています。attention が読む過去の KV はすでに書き込まれているので、前の層の終わりを待たずに読み始められる、というのがこの区切り方の理由です。GB300 の 144 個の SM それぞれに 12 のワープを置き、KV の読み込み、重みの読み込み、テンソルコアの演算、送受信などの役割をワープごとに固定して、前の演算の計算中に次の演算の重みを読み始められるようにしました。8 枚の GPU で MoE の 2 つの行列の掛け算を分けて持つ方法は、両方とも出力の向きで分け、1 つ目の後に FP4、2 つ目の後に BF16 の all-gather を置く形に変えました。通信は 1 回増えますが、送る量は減ります。また、1 つの SM の命令のキャッシュは約 128 KB しかなく、215〜314 KB ある megakernel は入りきらずにコードを読み直すことを確かめ (100 KB のコードを単独で回すと 1 回 12.4 マイクロ秒、別の 100 KB と続けると 19.5 マイクロ秒)、対策しました。GPU どうしの受け渡しでは、データそのものを合図にして、1 回 3.6〜4.0 マイクロ秒かかるメモリのフェンスを毎層の待ちから外しました。draft モデル (DFlash V2) も megakernel にしました。重みを共有メモリと L2 のどこに置くかなどは、1 つのやり方がどこでも効くわけではないので、演算ごとに試して最も速い版を選んでいます。コードは [facebookresearch/sgl-muse-mega](https://github.com/facebookresearch/sgl-muse-mega) で公開されています。
- **結果**: 記事によると、GB300 8 枚で GSM8K の 1 リクエストを投機的デコードありで流し、20 ステップの中央値をとると、デコードは従来の SGLang の毎秒 517 トークンから毎秒 1,109 トークンへ 2.1 倍になり、ねらいの毎秒 1,000 トークンを超えました。1 ステップの時間は 12.9 ミリ秒から 5.9 ミリ秒へ約 2.2 倍速くなり、起動するカーネルは 1,450 個から 97 個へ約 15 分の 1 に減りました。このうち draft モデルの 1 ステップは 1.16 ミリ秒から 0.44 ミリ秒へ 2.6 倍速くなっています。ただし、GPU が止まる時間は無くなってはいません。記事が示す 1 層の実測では、2 つ目の行列の掛け算から層の終わりまでに平均約 12.5 マイクロ秒の空きが残り、これが止まっている時間全体のほぼ半分です。また、解決したのはバッチ 1 で投機的デコードを使う場合だけで、複数のリクエストをまとめて流す場合はまだ扱っていません。

### SGLang の unified memory: KV と状態をまとめた共有の置き場

> 参照元: [Unified Memory in SGLang: One Arena for Every Token Lifetime](https://www.lmsys.org/blog/2026-11-11-unified-memory/)

最近のモデルには、全部の文脈を見る attention の層と、直近の一定の長さだけを見るスライディングウィンドウの attention の層や、Mamba や線形の attention のように固定の大きさの状態を持ち回る層を混ぜたハイブリッドなものが増えています。前者の KV キャッシュは文脈が長くなるほど伸び続けますが、後者のウィンドウの KV や状態は 1 リクエストあたりの大きさに上限があり、2 つは同じようには伸び縮みしません。SGLang はこれまで、それぞれに別の置き場を用意し、その割合を起動時の設定で決め打ちしていたので、長い文脈が多いと一方が足りなくなり、短いリクエストが多いと他方が足りなくなり、空いているメモリがあっても別の置き場からは使えませんでした。この LMSYS のブログは、著者らがこれらを GPU のメモリの 1 つの置き場にまとめ、使う量を実行中の需要に合わせて動かす unified memory を SGLang に入れ、H200 1 枚での検証で既定の構成と遜色ない結果を報告した話をまとめたものです。ここでの unified memory は、Grace Hopper の CPU と GPU の共有メモリや CUDA の Unified Memory とは別のもので、SGLang の中のメモリの置き場の作り方のことです。抜粋に出てくるアリーナは 1 つの連続した GPU のメモリの領域のことで、retraction はメモリが足りなくなったときに実行中のリクエストをいったん巻き戻して後でやり直すことです。

:::message
**コメント**: attention と、Mamba の SSD のように状態を持ち回る層を混ぜたモデルの KV のメモリ管理は難しい問題で、それをうまく扱う手法には注目しています。割合を決め打ちせずに 1 つの置き場で需要に合わせる、という考え方は素直で、まだ実験的な機能ですが、複数の GPU や PD 分離の構成でどう振る舞うかを見ていきたいです。
:::

#### 参照元からの抜粋と要約

- **課題**: ハイブリッドなモデルのメモリを状態の種類ごとに起動時の固定比率で分けると、負荷に合わない比率を選んだときにスループットが落ちたり、同時に動かせるリクエスト数が不必要に絞られたりします。適切な比率は負荷に依存するため事前の測定が要り、負荷が変わるとメモリが余ったまま使われません。
- **ねらい**: 比率を固定せず 1 つのアリーナにまとめても、既定の比率構成と同等以上の性能を保ち、比率が負荷に合わない場面でより多くのリクエストを収容できることを示すこと。
- **やったこと**: 記事では、全部の層の KV をトークンごとの 1 つの項目にまとめる新しい並べ方にし、全体を見る attention の KV と上限のある状態を同じアリーナの中の帯として確保したと説明しています。リクエストを受け入れる前に、最後まで動かしたときに必要なメモリが確保できるかを判定し、実行中の処理を壊さずにページを動かすため、解放したページや移したページの古いバイトをしばらく守る仕組みを入れました。評価は H200 1 枚で、Qwen3.5-4B と GPT-OSS-20B を使い、SGLang の既定の、種類ごとに置き場を分ける構成と比べました(各条件は 2 回の平均)。コードは SGLang の該当コミット ([daa171846f](https://github.com/sgl-project/sglang/commit/daa171846f)) に含まれ、使い方は [SGLang のドキュメント](https://docs.sglang.io/docs/advanced_features/unified_memory) にあります。
- **結果**: 記事によると、GPT-OSS-20B の入力 512・出力 1,536 トークン・同時 1,024 の負荷で、既定の比率の構成が同時に動かせたリクエストは 618 件だったのに対し、unified memory は約 1,000 件で、約 1.6 倍でした。既定の比率と同じかそれ以上の性能を保ちながら、比率が負荷に合わない場面でより多く収容するというねらいには届いています。一方、まだ実験的な機能で、ハイブリッドなモデルだけが対象であり、優先度による割り込みや LMCache・FP4 KV との組み合わせには対応していません。

### vLLM の DeepSeek-V4.1-Flash on Vera Rubin: 同じ interactivity で GB300 の 58 倍

> 参照元: [DeepSeek-V4.1-Flash on Vera Rubin NVL72: 58x Throughput vs. GB300 NVL72 at 387 tokens/s](https://vllm.ai/blog/2026-11-12-deepseek-v41-flash-vera-rubin)

推論の性能は、1 人の利用者に毎秒何トークン返せるかという interactivity と、GPU 1 枚が全体で毎秒何トークン処理できるかというスループットの、2 つの釣り合いで決まります。同じハードウェアでも同時に受けるリクエストを増やせばスループットは上がり interactivity は下がるため、異なる構成を比べるときは同じ interactivity の点どうしで比べるのが筋です。Vera Rubin NVL72 は、NVIDIA の Blackwell の次の世代 Rubin の GPU 72 枚を 1 つの NVLink でつないだラックで、1 枚の GPU の中にメモリ領域が 2 つあることと、FP8・FP4 の新しい行列演算の命令を持つことが、GB300 NVL72 との違いです。この vLLM のブログは、Inferact と vLLM のチームが、GB300 NVL72 で組んだ DeepSeek-V4.1-Flash の提供構成を Vera Rubin NVL72 に移し、Rubin の特徴に合わせてカーネルとメモリの使い方を作り直し、同じ interactivity で GPU 1 枚あたりの処理量を GB300 の約 58 倍にした記録です。抜粋に出てくる DEP はデータ並列の attention と専門家並列を組み合わせた構成で、数字はまとめる GPU の枚数を指し、AgentX は SemiAnalysis が公開するエージェントの会話を再生する負荷のベンチマーク、Mooncake は KV キャッシュを複数サーバーで共有する置き場です。

:::message
**コメント**: interactivity は聞き馴染みのない言葉ですが、SemiAnalysis の InferenceX の AgentX では、1 人の利用者に毎秒何トークン届いたかを表す値です。[資料](https://github.com/SemiAnalysisAI/InferenceX/blob/3253e6572bb6dfe6255629a50210a48a0c0c36e1/inferencex-e2e/docs/MODELS.md)によると、AgentX の既定の値はリクエストごとに TTFT を含む全体の時間を出力のトークン数で割り、その P90 を取ってから逆数にしたもので、およそ 1 ÷ (TPOT + TTFT ÷ 出力のトークン数) になり、トークンの間の時間だけから求める 1 ÷ TPOT より小さく出ます。TTFT と TPOT にそれぞれ SLO を置いて両方を満たしたリクエストだけを数える goodput とは、書き方の流儀が異なります。記事の 387 トークンが、この AgentX の既定の値と 1 ÷ TPOT のどちらで測ったものかは書かれていません。見出しの 58 倍は、GB300 の結果と、利用者 1 人あたり毎秒 387 トークンという同じ interactivity の点どうしで比べた数字で、比べ方としては筋が通っています。ただ、58 倍には Rubin 向けにカーネルとメモリの使い方を作り直した分も入っていて、トークンにはキャッシュに当たった入力も数えているので、世代の差そのものとは読まないほうがよいと思いました。387 トークンが GB300 の曲線のどのあたりの点かによっても、倍率は大きく変わるはずです。それよりも面白かったのは、Rubin で計算が速くなった結果、1 つのラックがさばく同時のセッションが増え、GB300 のときの GPU ごとの KV の置き場とセッションを GPU に固定する割り振りでは追いつかなくなった、という話です。速いハードウェアが次はメモリと割り振りを問題にする流れで、KV の置き場をまとめて需要に合わせる点は今週の unified memory の話とも似ています。prefill の GPU の空いた HBM を共有の KV の置き場に出す仕組みはまだ実験的で、ピークの数字や 1 人向けの最速の数字には比べる相手が書かれていません。手元で Rubin を試せる見込みはまだないので、まずは GB300 の曲線の上で、interactivity を変えたときに倍率がどう動くかを記事の図から読み取ってみたいです。
:::

#### 参照元からの抜粋と要約

- **課題**: GB300 NVL72 で作った DeepSeek-V4.1-Flash の prefill とデコードを分けた構成と専門家並列の構成を、Vera Rubin NVL72 に移し、Rubin の 2 つのメモリ領域、新しい行列演算の命令、72 枚の NVLink のつながりを使って性能を伸ばしたいとしています。Rubin では 1 つのラックがさばく同時セッションが大きく増え、GB300 のときの GPU ごとの CPU 側 prefix cache とセッション固定の割り振りでは、キャッシュ不足と GPU 間の負荷の偏りが起きます。
- **ねらい**: GB300 の構成の形を保ったまま、カーネルとラック全体のメモリの使い方を Rubin に合わせて作り直し、スループットと interactivity の曲線を押し上げること。
- **やったこと**: 記事では、GB300 で使った DEP2 の prefill、DEP16 か DEP32 のデコード、最もレイテンシーの短い TP8 のデコードという 3 つの形をそのまま使い、中のカーネルを Rubin の 2 つのメモリ領域と新しい命令に合わせて作り直したと説明しています。MoE の dispatch では、各トークンが必要とする遠くの GPU からの読み込みを自分の GPU への書き込みより先にすべて出すようにし、KV キャッシュを DRAM と空いた HBM まで広げた 1 つの Mooncake の置き場にまとめ、セッションを GPU に固定しない負荷を見た割り振りに切り替えました。これらの変更は vLLM 本体の [PR #54371](https://github.com/vllm-project/vllm/pull/54371) と [PR #66552](https://github.com/vllm-project/vllm/pull/66552) などで実装されています。
- **結果**: 記事によると、Vera Rubin NVL72 の 1 ラックで SemiAnalysis AgentX を流すと、利用者 1 人あたり P90 で毎秒 387 トークンという同じ interactivity の点で、GPU 1 枚あたりの処理量は GB300 NVL72 (Dynamo + vLLM) の 58 倍でした。これは、GB300 の構成を保ったままカーネルとメモリの使い方を Rubin 向けに作り直すというねらいに沿う結果です。ただし、ピークの毎秒 252 万トークンや 1 人向け最速構成の P90 毎秒 1,810 トークンには比較対象が書かれておらず、58 倍という倍率自体もカーネルの作り直し分を含むため、ハードウェア世代の差だけを表す数字ではありません。

### Detent: カーネルの選び方の固定によるバッチ不変

> 参照元: [Detent: Batch-Invariant LLM Serving and RL Rollouts at Near-Stock Speed](https://arxiv.org/html/2611.10611)

LLM の推論エンジンは、GPU を効率よく使うために複数のリクエストをまとめたバッチで処理します。ところが、同じリクエストでも、一緒にバッチに入った他のリクエストによって出力がビット単位で変わることがあります。小数の足し算は足す順番を変えると結果がわずかに変わるので、バッチの大きさに応じて足し方の違う計算を選ぶと、結果も変わってしまうからです。評価の再現や、強化学習でロールアウトと呼ぶ「今のモデルで答えを生成する段階」を学習側で計算し直して一致させたい場面では、これが問題になります。vLLM や SGLang には、どんなバッチでも同じ結果を返すバッチ不変のモードがすでにありますが、計算ごとに 1 種類の保守的なカーネルに固定するので遅くなります。このプレプリントは、独立研究者と Boston University、Google、Princeton University などの研究者が、カーネルそのものではなく、どのカーネルをどの設定で選ぶかの判断のほうを固定する Detent を作り、既存の決定的なモードよりもずっと、バッチ不変を求めない既定の設定 (記事では Stock) に近い速さでバッチ不変性を達成したと報告したものです。抜粋に出てくる split は長い入力を分けて並列に計算し最後に足し合わせるやり方で、GRPO は同じ問題への複数の答えの報酬を比べてモデルを更新する強化学習の手法、KL はロールアウト側と学習側の確率のずれの大きさを表す量です。

:::message
**コメント**: 前号では学習側から同じ問題に取り組む TitanRL の batch-invariant モードを取り上げ、本の章 [[26/10/29:#3] 学習と推論の確率は本当に一致するか](https://zenn.dev/tosshi/books/ml-distributed-experiment-collection/viewer/exp-titanrl-batch-invariant) でも確かめました。Detent はそれを推論エンジンの側から、しかも「カーネル自体はバッチ不変でも、選び方がバッチを読んでいる」という見方で解いていて、固定する対象をカーネルから選び方に移し、固定する値をワークロードごとに測って決めると、H100 4 枚の構成で既定の構成と比べた遅さが、既存の決定的なモードの 1.67〜10.3 倍から 1.04〜1.17 倍まで縮むのが面白いと思いました。BF16 の GRPO で、既定の構成だと報酬が途中で崩れたのに Detent では崩れなかった、という結果は、学習と推論の確率のずれが実際に学習を壊すことを示す例として覚えておきたいです。ただ、カーネルの選び方を SelIR という専用の言語で書き直す手間がカーネルごとにかかり、動的な FP8 の倍率のようにバッチ全体で決まる値は対象外で、コードもプレプリントには載っていません。最速の設定は流れてくるリクエストの形で変わり、Qwen3-30B-A3B では別の形の負荷向けの設定を当てると、その負荷に合わせた設定と比べて最大 4.17 倍遅くなるとも書かれているので、本番でこの設定をどう保つかが一番の課題だと感じます。
:::

![Detent がワークロードごとに設定を決めることで、Qwen3-30B-A3B と Llama-3.1-70B のどちらでも既定の構成に近いレイテンシーでバッチ不変を保つことを示す図](https://arxiv.org/html/2611.10611v1/fig_headline.svg)
*出典: [Detent](https://arxiv.org/html/2611.10611) の Figure 1*

#### 参照元からの抜粋と要約

- **課題**: 推論エンジンは、同じバッチに乗る他のリクエストの組み合わせによって、attention の split の数とタイルの幅、MoE の融合カーネルの設定の行、TP の all-reduce のアルゴリズムを切り替えるので、カーネル自体がバッチ不変でもエンジン全体ではバッチ不変になりません。既存の決定的なモードである SGLang-Det と vLLM-Det は、計算ごとに 1 種類の保守的なカーネルに固定するため、出力トークン 1 個あたりのレイテンシーが既定の構成の 1.67〜10.3 倍になります。
- **ねらい**: カーネル自体は変えずに、カーネルの選び方だけをバッチ不変にして、既定の構成に近いレイテンシーでバッチ不変を実現すること。
- **やったこと**: 著者らは、FA3 の attention、融合 MoE、all-reduce、GEMM のカーネルの選び方を SelIR という Python の一部からなる言語で書き直し、バッチに依存する入力から選択までのすべての経路を塞ぐ最小の値の組を最大流の計算で求めました。固定する値はワークロードごとに測って決め、カーネルの種類ごとに独立に探すことで、Qwen3-30B-A3B では 1,607,040 通りの組み合わせを 3,020 通りに減らしました。vLLM と SGLang に組み込み、Llama-3.1-70B と MoE の Qwen3-30B-A3B を H100 4 枚の TP 構成で、ShareGPT の会話と 8K トークンの arXiv の文書など 3 種類の負荷で評価しました。プレプリントには Detent 自身のコードの公開先は書かれていません。
- **結果**: 著者らによると、H100 4 枚で Llama-3.1-70B と Qwen3-30B-A3B を動かした場合、出力トークン 1 個あたりのレイテンシーは、ワークロードごとに調整した Detent が Stock の 1.04〜1.17 倍で済み、既存の決定的なモードの Stock 比 1.67〜10.3 倍と比べて p50 で 2.4〜5.7 倍速く、BF16 の GRPO 学習で Stock の報酬が崩壊する場面も Detent では崩壊しませんでした。カーネル自体は変えずに選び方だけ固定し、既定の構成に近い速さでバッチ不変を実現するというねらいには届いています。一方、ワークロードが変わると事前にチューニングした設定の速さが最大 4.17 倍まで落ちるなど、トラフィックの変化への追従はまだ解決していません。

### SubGPU Pipelining: 1 枚の GPU の中の流れ作業

> 参照元: [SubGPU Pipelining: Intra-GPU Fine-Grained Spatial Parallelism for LLM Inference](https://arxiv.org/html/2611.14904)

LLM が答えを 1 トークンずつ生成するデコードの段階では、1 ステップの中で正規化、attention、行列の掛け算、MoE の専門家の計算などの何十個もカーネルを順番に呼びます。B200 のような強力な GPU では、1 つのカーネルがマイクロ秒単位で終わってしまい、起動の待ち時間が目立ったり、メモリの帯域が上限に当たって GPU の計算の部品が余ったりします。GPU の中には SM と呼ぶ計算の部品が 148 個並んでいて、ふつうはどのカーネルも全部の SM を使って 1 つずつ順に動きます。GPU を増やしても、この 1 枚の中の無駄は残ります。このプレプリントは、NVIDIA の研究者が、1 枚の GPU の中を SM のまとまりに分けて、計算の区間を流れ作業で重ねる SubGPU Pipelining を提案し、シミュレーションと 1 枚の B200 を使った実機の両方で、全 SM を使って順に動かす方式より速くなることを確認したものです。抜粋に出てくるマイクロバッチはバッチをさらに小さく分けたもので、Green Context は SM の一部だけを使う区画を作る CUDA の機能です。ユーザーあたりのスループットは 1 人の利用者に 1 秒あたり何トークン返せるか、GPU あたりのスループットは GPU 1 枚が 1 秒あたり全体で何トークン生成できるかを表します。

:::message
**コメント**: 並列化というと GPU を何枚にどう分けるかの話になりがちですが、これは 1 枚の GPU の中をさらに分ける話で、学習のテーマの並列化と並べると、分ける単位がどんどん細かくなっているのが面白いです。既存のカーネルには手を入れず、Green Context と CUDA Graph という CUDA の既存の仕組みで組んでいる点はよいと思いましたが、区間の切り方と SM の割り当てを決める探索のコードは見当たらないので、同じことを試すには割り当てを自分で決める必要があります。ただ、全部の SM で順に動かす方式と比べてユーザーあたりのスループットが最大 2.2 倍、GPU あたりのスループットが最大 1.9 倍という見出しの数字はシミュレーションのもので、実機は 1 枚の B200 で 32 枚構成の 1 枚分の仕事を、GPU 間の通信を見積もりの待ち時間で置き換えて再現したものです。実機では、full attention のカーネルの合計時間は延び SM の稼働率も下がっていますが、重ねた結果として、全部の SM で順に動かす場合と比べて 1 ステップは 10.33% 短くなっています。vLLM や SGLang のような実際のエンジンの中で、ほかの並列化と組み合わせたときにどこまで残るかを見たいです。
:::

![ふつうの実行ではどのカーネルも 148 個の SM を全部使って順番に動くが、SubGPU では full attention を 68 SM、残りを 80 SM に割り当てて重ねて動かす様子を比べた図](https://arxiv.org/html/2611.14904v1/figures/fig3_kernel_timeline.png)
*出典: [SubGPU Pipelining](https://arxiv.org/html/2611.14904) の Figure 6*

#### 参照元からの抜粋と要約

- **課題**: LLM のデコードは、短くメモリの読み出しに縛られがちなカーネルが何十個も連続するので、GPU の計算の部品とメモリの読み出しを一時的にしか使い切れません。GPU の間で分ける TP、DP、EP、CP、パイプライン並列のどれを使っても、この GPU 1 枚の中の無駄は解決しません。
- **ねらい**: 1 層分の計算のつながりを連続した区間に切って互いに重ならない SM のまとまりに固定し、マイクロバッチを流し込んで、必要な資源の違う区間を同時に動かすこと。
- **やったこと**: 著者らは、区間の切り方、SM の割り当て、マイクロバッチの大きさをまとめて決める最適化の問題を定式化し、出来事を順に追うシミュレータと、動的計画法で切り方の案を出してから SM を 2 つの区間の間で移し替えて磨く探索を作りました。シミュレーションでは GPT-OSS 120B のデコードを入力長 32,768、32 枚の B200 想定で評価し、実機では 1 枚の B200 で 32 枚構成の 1 枚分の仕事を再現し、TensorRT-LLM の既存カーネルを CUDA の Green Context と CUDA Graph で組み合わせてバッチ 2,048 で測りました。GPU 間の通信は 3 マイクロ秒と転送量を 900GB/s で割った時間を待つだけの仮のカーネルで置き換えました。論文中に著者ら自身のコードの公開先への言及はありません。
- **結果**: 著者らによると、1 枚の B200 で 32 枚構成の 1 ランク分を再現した実機の計測では、36 層の GPT-OSS 120B デコード 1 ステップの時間が、全 SM を使って順に動かす方式の 14.970ms から SubGPU の 13.424ms へ、約 1.12 倍速くなりました。シミュレーションで予測していた 6.6% の短縮(約 1.07 倍)を上回り、GPU 内の空き時間を減らして資源を同時に使うというねらいには届いています。一方、この実機の確認はシミュレーションで示した「GPU あたりスループットを揃えたときユーザーあたり最大 2.2 倍」という範囲の一部でしかなく、バッチが小さすぎる場合や既に計算に縛られている場合には利得がほぼ消えるなど、効果が出る条件はまだ限られています。

### Cairn: 共有と前もった準備によるコールドスタートの短縮

> 参照元: [Fast Serverless LLM Cold Starts by Sharing and Prewarming Startup Work](https://arxiv.org/html/2611.16180)

サーバーレスの LLM 推論は、リクエストが来たときだけプロセスを立ち上げるコールドスタートの遅さが課題で、これまでの研究は重みの読み込みを速くすることに注目してきました。ところが実際に測ると、遅さの大半は重みの読み込みではなく、torch.compile によるコンパイルやメモリの使用量を確認する作業など、サーバーが違っても同じ結果になるか、モデルが何であっても必要になる準備作業でした。このプレプリントは、KAIST と SK hynix の研究者が、こうした重複した作業をサーバーの間で共有したり前もって済ませたりする Cairn という仕組みを作り、コールドスタートを大きく短くした記録です。抜粋に出てくる CXL は、CPU が別の装置のメモリを普通のメモリと同じ命令で読み書きできるようにする接続の規格で、複数のサーバーが共有して読み書きできる領域をメモリプールと呼びます。ウォームコンテナは、モデルがまだ決まっていない段階で、モデルに依存しない準備だけを済ませて待っている 2 つ 1 組のプロセスのことです。

:::message
**コメント**: コールドスタートというと重みの転送の帯域の話になりがちですが、重みは 1 割程度で、残りの多くはサーバー間で結果が同じか、モデルに依存しない作業のやり直しだった、という切り分けが一番の収穫でした。共有できるもの、前もってできるもの、記録したプロセスから離せない CUDA Graph の 3 つに分ける見方は、サーバーレスに限らず、Kubernetes で推論の Pod をスケールさせるときの立ち上げの時間を見直すときにも使えそうです。ただ、共有の CXL のメモリプールは実機ではなく、1 台のホストの上の 2 台の仮想マシンでリモートの NUMA のメモリを共有させて真似したもので、GPU も RTX A6000 が 1 枚ずつです。16 台の規模の結果はシミュレーションで、GPU が埋まり切る負荷では差が縮むとも書かれています。CXL が無い環境でも、vLLM の compile のキャッシュを共有のストレージに置くだけでどこまで縮むかは、手元で確かめられそうです。
:::

![一度もそのモデルを動かしたことのないサーバーで最小と最大のモデルのコールドスタートを段階ごとに分けると、重みの読み込みはごく一部で、残りをコンパイルやメモリの確認、起動の処理が占めることを示す図](https://arxiv.org/html/2611.16180v1/fig1_breakdown.svg)
*出典: [Fast Serverless LLM Cold Starts by Sharing and Prewarming Startup Work](https://arxiv.org/html/2611.16180) の Figure 1*

#### 参照元からの抜粋と要約

- **課題**: サーバーレスの LLM 推論は、リクエストが来てからプロセスを立ち上げるコールドスタートが長く、著者らが 1B から 14B のモデルで測ると 57〜85 秒かかり、そのうち重みの読み込みは一部にすぎませんでした。残りのコンパイルやメモリの確認、起動の処理は、サーバーが違っても同じ結果になるか、モデルが何であっても必要な作業なのに、サーバーごとに毎回やり直されていました。
- **ねらい**: サーバー間で結果が同じになる作業はクラスタで一度だけ行って共有し、モデルに依存しない準備はモデルが決まる前にウォームコンテナで済ませておくことで、コールドスタートを短くすること。
- **やったこと**: 記事では、最初にモデルを立ち上げたサーバーが、重みやコンパイルのキャッシュ、CUDA Graph のメモリの見積もりなどを CXL のメモリプールに書き込み、他のサーバーは一から作り直す代わりにそれをその場で読むだけにしたと説明しています。これらの情報はどのサーバーで作っても同じ結果になることを著者らが先に確かめたため、共有しても安全だと判断しました。モデルに依存しない起動処理は、CUDA をまだ初期化していないひな形のプロセスを fork して複製するウォームコンテナで先に済ませ、記録したプロセスから離せない CUDA Graph の記録だけは毎回そのまま行います。コードは出版時に公開するとされており、いまは公開されていません。
- **結果**: 著者らによると、一度もそのモデルを動かしたことがなく自分のチェックポイントも持たないサーバーで、Cairn のコールドスタートは既存手法 (ServerlessLLM と vLLM の組み合わせ) の 57〜85 秒に比べて 11.0〜21.0 秒になり、6 つのモデルすべてで 4.1〜5.2 倍速くなりました。これは「サーバー間の共有と事前の準備でコールドスタートを短くする」というねらいに届いた結果です。ただし、GPU が埋まり切るほど負荷が高い場面では、この短縮効果が大きく縮むとされています。

## カーネルと開発の道具

### TLX: ワープの役割分担を書ける Triton の拡張

> 参照元: [How We Built TLX: A Hardware-Native GPU Compiler for Production ML at Scale](https://engineering.fb.com/2026/11/10/open-source/tlx-a-hardware-native-gpu-compiler-for-production-ml/)

Triton は行列の塊をまとめて扱う書き方で GPU のカーネルを Python から書ける言語で、Meta の社内でも広く使われるようになっています。ところが Hopper や Blackwell の GPU では、データを運ぶ係と計算する係にワープを分ける warp specialization や、専用の転送機構 TMA、専用の記憶領域 TMEM などの実行の段取りが性能の鍵になり、これらはカーネルの組み立て方そのものを変えます。CUDA ならこうした段取りを書けますが手間が大きく、Triton では多くがコンパイラの裏に隠れていて、新しい GPU が出るたびにコンパイラの対応を待つことになっていました。この Meta のブログは、Meta のチームが、Triton の書き方を残したまま、ワープの組ごとの役割分担と同期をはっきり書ける拡張の TLX を作り、広告や推薦、LLM の学習など複数の本番システムで使った経験をまとめたものです。抜粋に出てくる mbarrier は、ワープの組の間で準備ができたことを知らせ合う軽い同期の仕組みで、MFU は GPU が理論上出せる演算のスループットのうち実際に使えた割合です。

:::message
**コメント**: 同じテーマの GC-MoE が、warp specialization や非同期の段の重ね合わせを CuTe DSL で一から組んでいたのを見ると、それを Triton の書き方のまま書けるようにする、という TLX の狙いはよく分かります。Triton は何を計算するかを、TLX はそれをどう段取りするかを書く、という役割の分け方は、学習のテーマの SS-HSDP が計算の都合と更新の都合を分けたのと似た発想で、今週は分け方の設計の話が多いと感じました。記事の Blackwell の GEMM の例では、データを読む組、テンソルコアで計算する組、結果を書く組をそれぞれ書いていて、ふつうの Triton より段取りが見えます。CUDA で同じことを書いた場合との長さの比較は記事にはありません。ただ、スループットとレイテンシーの数字はどれも Meta の社内の事例で、GEMM や attention の形状をそろえた CUTLASS や cuBLAS との比較の表はなく、MoE の grouped GEMM の事例には数字がありません。コードは Meta の Triton のフォークにあり、本家の Triton にプラグインとして足す配り方もあるので、手元の Hopper で attention のカーネルを書いて、ふつうの Triton と比べてみたいです。
:::

![1 つのスレッドを単位にする CUDA と、塊を単位にする Triton の間に、ワープの組を単位にする段が抜けていて、TLX がそこを埋める構成図](https://engineering.fb.com/wp-content/uploads/2026/11/Meta-TLX-Figure-3.png)
*出典: [How We Built TLX](https://engineering.fb.com/2026/11/10/open-source/tlx-a-hardware-native-gpu-compiler-for-production-ml/) の図*

#### 参照元からの抜粋と要約

- **課題**: Hopper と Blackwell は、warp specialization、TMA、TMEM、クラスタの実行といった実行の段取りを求めますが、CUDA は書けても手間が大きく、Triton は生産的でも実行の構造をコンパイラの裏に隠すため、新しいハードウェアへの対応が常に遅れます。
- **ねらい**: Triton の生産的な書き方を保ったまま、ワープの組を実行の基本の単位として扱える段を用意し、新しいハードウェアの機能をコンパイラを待たずに使えるようにすること。
- **やったこと**: 記事では、Triton に warp-group orchestration、mbarrier による同期、TMA や TMEM への直接アクセス、クラスタの実行、レイアウトの自動推論という 5 つの機能を足したと説明しています。ワープの組に送り手・計算役・後処理役のような役割を割り当てられるようにしたのは、Hopper 以降のハードウェアがもともとこの単位で動くことに合わせたためで、レイアウトを自動推論する機能は、カーネルを融合するときに手動でレイアウトを調整する手間を減らすために加えたとしています。対象は NVIDIA の Hopper と Blackwell、AMD の MI300 と MI350x で、広告の生成モデルの学習、推薦の推論、LLM の事前学習の MoE という 3 つの本番ワークロードに使っています。コードは [facebookexperimental/triton](https://github.com/facebookexperimental/triton) で MIT ライセンスで公開されています。
- **結果**: 記事によると、広告の生成モデルの学習では、attention の演算を 1 つのカーネルに統合した GDPA が、統合前の複数カーネル構成に比べて順伝播で最大 2 倍速くなりました。推薦の推論では、linear compression のカーネルを TLX で書き直すと、H100 上でそれ以前のカーネルの 4 倍のスループットになりました。いずれもねらいどおり、ハードウェアの機能を使い切る高速化が得られたことを示しています。もう一つの事例である LLM 事前学習の MoE の grouped GEMM は、本番で長期間動いているとだけ書かれ、速度の比較はされていません。

### LLDB で CPU と GPU を 1 つのセッションでデバッグする拡張

> 参照元: [Extending LLDB to Debug Applications That Span CPUs and GPUs](https://engineering.fb.com/2026/11/09/developer-tools/extending-lldb-to-debug-applications-that-span-cpus-and-gpus/)

いまの AI のプログラムは、高レベルのフレームワークから CPU のネイティブのコードを通って GPU のカーネルまで往復するので、不具合も CPU と GPU の境目をまたいで起きます。ところが CPU と GPU は命令の種類やメモリの使い方が違い、GPU は CPU 側のプロセスの中のランタイムとドライバを通して動くので、ふつうのデバッガのように 1 つのプロセスとして調べることができません。これまでは GPU を作る会社がそれぞれ、AMD の ROCgdb や NVIDIA の CUDA-GDB のような専用のデバッガを作ってきましたが、ブレークポイントのような共通の機能まで会社ごとに作って保守することになっていました。この Meta のブログは、Meta のチームが、デバッガ LLDB に、特定の会社に依存しないアクセラレーターのためのプラグインの土台を作り、その大部分を本家の LLVM に取り込んだことを説明したものです。抜粋に出てくる lldb-server は、デバッグする対象のそばで動いて、プロセスの起動や停止、メモリの読み出しを LLDB の代わりに行う相棒のプロセスで、ターゲットは LLDB がデバッグする 1 つの対象のことです。upstream は、こうした変更を本家のリポジトリに取り込んでもらうことを指します。

:::message
**コメント**: CPU と GPU を 1 つのプロセスに無理にまとめず、別々のターゲットのまま 1 つのセッションに並べ、つなぎ役をプラグインに任せる、という分け方は、推論のテーマの SGLang-Neuron が本体と Trainium の部分を分けたのとよく似ていると思いました。同じテーマの GPU のカーネルのライブラリの不具合の調査では、結果が誤りになる不具合が 17.67% あったので、CPU 側の呼び出しから GPU のカーネルの中まで同じ道具で追えるのは、こうした不具合を調べるときにありがたいはずです。本物の GPU を使わずにプラグインの流れを確かめる模擬のプラグインを LLVM のテストに入れている点も、共有の土台を保守していくための手当てとしてよいと感じました。一方で、記事に数字はなく、例は AMD の HIP のカーネル 1 つで、PyTorch や Triton のカーネルのデバッグとどうつながるかは書かれていません。記事にはリンクがありませんでしたが、LLVM のリポジトリを探すと、たとえば[プラグインの基底のクラスを足す PR](https://github.com/llvm/llvm-project/pull/198907) が見つかりました。手元では Triton のカーネルの中でブレークポイントが止まるかを、まず試してみたいです。
:::

![CPU と GPU が別々の LLDB のターゲットのままで、lldb-server の中のプラグインが CPU 側と GPU 側のデバッグを協調させる構成図](https://engineering.fb.com/wp-content/uploads/2026/11/Extending-LLDB.png)
*出典: [Extending LLDB to Debug Applications That Span CPUs and GPUs](https://engineering.fb.com/2026/11/09/developer-tools/extending-lldb-to-debug-applications-that-span-cpus-and-gpus/) の図*

#### 参照元からの抜粋と要約

- **課題**: CPU と GPU の境目をまたぐ不具合を調べたいのに、ふつうのデバッガは 1 つのプロセスが 1 つの命令の種類と 1 つのメモリの見方を持つことを前提にしています。GPU は CPU と違う命令を使い、何千もの実行の単位を同時に進めるため、この前提に合わず、会社ごとの専用のデバッガは共通の機能まで別々に作って保守しています。
- **ねらい**: LLDB の lldb-server に会社に依存しない共通のプラグインの仕組みを作り、新しいハードウェアを LLDB に足す作業が、デバッガを一から作るのではなく、その会社のプラグインを書くだけで済むようにすること。
- **やったこと**: 記事では、CPU と GPU を別々の LLDB のターゲットとして表し、それぞれが自分の命令の種類やレジスタ、アドレスの空間を持つようにしたと説明しています。これは、1 つのプロセスモデルに無理に押し込めると、すべての操作が CPU 向けか GPU 向けかを判定する分岐になってしまうため、境界をあいまいにせず最初から分けて扱う方針です。プラグインは CPU 側のプロセスに内部のブレークポイントを置くよう LLDB に頼み、GPU のデバッグを始められる時点でその会社のデバッグ API を初期化し、LLDB がそこに GPU 側の 2 つ目のターゲットを作って接続します。専用のハードウェアなしでこの流れを確かめる模擬のプラグインも作り、GPU のコアダンプを後から調べる仕組みも同じ土台に載せました。この共通フレームワークの大部分は LLVM の本家に取り込み済みです。
- **結果**: 記事によると、AMD の HIP で書いたベクトルの内積のカーネルで、CPU のターゲットと GPU のターゲットが一覧に並び、保留になっていたブレークポイントが GPU のモジュールの読み込みで有効になり、GPU 側のバックトレースが取れることを確かめています。Meta の社内では、ハードウェアとソフトウェアの構成が違う複数の GPU の取り組みが、すでに同じ仕組みを使っているとされ、これはねらいだった共通の土台を複数のハードウェアで使い回せることを裏付けています。ただし、性能や対応モデル数を示す数値は記事に書かれておらず、残りの機能のアップストリーム化もまだ完了していません。

### GPU カーネルのライブラリの不具合 300 件の分類

> 参照元: [An Empirical Study of Issues in GPU Kernel Libraries for LLM Systems](https://arxiv.org/html/2611.09280)

LLM の学習と推論のスループットは、attention や行列の掛け算を GPU の上で速く計算するカーネルのライブラリに大きく頼っていて、FlashAttention、FlashInfer、Triton、CUTLASS などがその代表です。これらのライブラリは、テンソルの形や数の形式ごとに専用に作り分けたカーネルを利用者の環境でコンパイルして動かすことが多く、エラーを出さずに結果だけが間違う不具合や、GPU の処理が止まったまま進まないハングが起きると原因を突き止めるのが難しくなります。それでも、こうした不具合がどこから来るのかを体系的に整理した研究はありませんでした。このプレプリントは、Microsoft Research Asia と Tsinghua University の研究者が、7 つのライブラリの GitHub の issue から 300 件を選び、症状、原因、直し方、テストのやり方を手作業で分類したものです。抜粋に出てくるメモリのエイリアシングは、別々であるはずの入力と出力が同じメモリを指してしまうことで、ABI はコンパイル済みのプログラムどうしをつなぐ約束事のこと、低精度は FP16 や FP8、INT8 のように、ふつうの 32 ビットより少ないビット数で数を表す形式のことです。

:::message
**コメント**: GPU のカーネルというと、計算の中身の誤りや性能の話を想像しますが、原因の 6 割がコンパイラ、ビルド、実行環境の側だったというのが一番の発見でした。症状でも、そもそもインストールや配布で失敗したものとビルドで失敗したものが合わせて半分を超えていて、GPU の上で動く前に壊れている、というのが実態に近いと感じました。前のテーマの Detent が「カーネルの選び方」に原因を置き直したのと同じく、ここでも問題はカーネル本体の外側に多い、という見方がそろってきているのが面白いです。一方で、エラーを出さずに結果だけが間違う例が 17.67% あり、FP16 の参照値と合わないのは参照側の丸めが原因だった例のように、テストの参照値そのものが怪しい場合もあると書かれています。データや分類の表の公開先は見当たらないので、自分たちが使っているカーネルの issue を同じ分類で数えてみると、どこにテストを足すべきかが見えそうです。
:::

|---|---|---|
| インストールや配布の失敗 | 82 | 27.33% |
| ビルドの失敗 | 73 | 24.33% |
| クラッシュ | 63 | 21.00% |
| エラーを出さずに誤った結果 | 53 | 17.67% |

#### 参照元からの抜粋と要約

- **課題**: GPU のカーネルのライブラリの不具合は、エラーを出さずに結果を壊したり、GPU をハングさせたり、デプロイの食い違いを起こしたりしますが、どんな症状がどんな原因で起き、どう直され、どうテストされているかを体系的に整理した研究がありませんでした。
- **ねらい**: FlashInfer、FlashAttention、Triton、CUTLASS、DeepGEMM、xFormers、bitsandbytes の 7 つのライブラリについて、GitHub の issue を通して症状、原因、直し方、テストとデバッグのやり方を初めて体系的に整理すること。
- **やったこと**: 著者らは、issue 9,099 件を集め、失敗に関する語とラベルで 3,181 件に絞り、ライブラリごとの件数に比例して 300 件を選びました。2 人の著者が 300 件すべてに症状と原因のラベルを独立に付け、一致の度合いを表す Cohen's kappa は 0.87 でした。症状だけでなく原因まで分けたのは、同じ症状でも直し方が違う場合があり、原因が分からないと対策につながらないと考えたためです。データの公開先はプレプリントに書かれていません。
- **結果**: 著者らによると、300 件のうち、原因がコンパイラやビルド、実行環境の側だったのは合わせて 181 件で、カーネルのライブラリそのものの原因だった 119 件の約 1.5 倍でした。これは、カーネルの計算そのものよりも、その手前の環境やビルドの食い違いのほうが不具合の主な原因だという、この調査のねらいに対する答えになっています。一方で、エラーを出さずに結果だけが間違う不具合も 53 件あり、低精度の数値の誤差やハードウェア固有の失敗は、今のテストのやり方では見つけにくいままだと結論づけています。

### GC-MoE on SM120: ワークステーションの Blackwell での MoE デコードの重ね合わせ

> 参照元: [GC-MoE on SM120: Overlapping Expert-Parallel Token Dispatch with Warp-Level FP8xFP4 Block-Scaled MMA on Consumer Blackwell](https://arxiv.org/html/2611.16219)

MoE のモデルを複数の GPU で動かすときは、専門の部品である専門家を GPU ごとに分けて持つ専門家並列がよく使われます。デコードの 1 層ごとに、トークンを担当の専門家の GPU へ送る dispatch、専門家ごとの行列の掛け算をまとめて行う grouped GEMM、結果を元の GPU へ戻して足し合わせる combine の 3 段が順番に起き、1 回に流れるトークンが少ないので待ち時間がそのまま遅さになります。著者らの前作の GC-MoE は、この 3 段を、SM の一部だけを使う区画を作る CUDA の Green Context で SM を分け、1 つの CUDA Graph の中で重ねて動かすことでこの遅さに対処していましたが、データセンター向けの Blackwell である SM100 の専用の機能や NVLink の帯域に頼った作りでした。このプレプリントは、Alibaba の研究者が、こうした専用の機能も高速な GPU 間の接続も無い、ワークステーション向けの Blackwell である SM120 で、同じ重ね合わせの利点を作り直したものです。抜粋に出てくるワープは GPU の中で 32 本のスレッドがそろって動く単位で、CTA はそのワープを束ねたスレッドのまとまり、ブロックスケールは一定の数の値ごとに倍率を共有して少ないビット数で数を表す形式のことです。

:::message
**コメント**: 推論のテーマの SubGPU Pipelining と同じく Green Context で SM を分けて段を重ねる話で、同じ週に NVIDIA と Alibaba からこの使い方が出てきたのは偶然ではない気がします。データセンター向けの Blackwell に合わせて作られた MoE のカーネルが、ワークステーション向けの Blackwell では命令の種類からして使えず、作り直しになるというのは、同じ Blackwell という名前でも中身がかなり違うことを示していて覚えておきたいです。PCIe では結果を戻す側の転送が最も大きくなるので、バイト数よりも転送の回数を減らす、という考え方も、NVLink の無い環境で MoE を動かすときの参考になりそうです。ただし評価は 8 枚の RTX PRO 5000 の 1 台だけで、複数のノードは試しておらず、バッチ 256 の GLM5.2 では Cake との差が 1.017 倍まで縮み、著者らも未解決の課題としています。コードの公開先もプレプリントには書かれていないので、PCIe の GPU で MoE を動かす機会があれば、FlashInfer のカーネルとの差を自分で見てみたいです。
:::

![GLM5.2 の形の MoE で、バッチの大きさを 1 から 256 まで変えたときのデコードのレイテンシーを、GC-MoE と、FlashInfer の CuTe DSL で書いた実装と、Cake で比べると、どのバッチでも GC-MoE が最も速いことを示す図](https://arxiv.org/html/2611.16219v1/pro5000_glm52_gc_moe.png)
*出典: [GC-MoE on SM120](https://arxiv.org/html/2611.16219) の Figure 3*

#### 参照元からの抜粋と要約

- **課題**: 専門家並列の MoE のデコードは、dispatch、grouped GEMM、combine の 3 段が 1 層ごとに順番に起き、各 GPU に同時に流れるトークンも少ないので、レイテンシーが問題になります。前作が頼っていたデータセンター向け Blackwell の機能 (テンソルメモリ、2 つの CTA で協力する行列の掛け算、クラスタの中での一斉配信) はワークステーション向けの SM120 には無く、GPU の間も NVLink ではなく PCIe でつながるため、同じ作り方は使えません。
- **ねらい**: SM120 と PCIe の制約の中で、3 段を重ねて動かす利点を、設定の調整ではなく仕組みの作り直しで取り戻すこと。
- **やったこと**: 著者らは、FP4 の重みを行列の掛け算の命令の A の側に、FP8 の値を B の側に置く形でメインのループを作り直しました。これは、SM120 のテンソルコアがワープ単位の命令でしか block-scaled の計算を扱えず、専用のメモリや複数 CTA の協調が無いため、1 つのワープで完結する組み立てに変える必要があったからです。dispatch では専門家ごとに準備ができ次第知らせて同じ行を二重に読まないキャッシュを持たせ、combine にあたる戻りの転送は PCIe 上で最も大きくなる部分だったため、BF16 のまま連続した区間ごとに 1 回でまとめてコピーする専用のコピー役を置きました。カーネルは CuTe DSL で書き、FlashInfer の CuTe DSL の実装と Cake という 2 つの既存手法と比べました。コードの公開先はプレプリントに書かれていません。
- **結果**: 著者らによると、8 枚の RTX PRO 5000 で GLM5.2 と DSV4.1-Flash の 2 つの形について、バッチを変えた 18 通りの条件すべてで両方の既存手法より速く、レイテンシーで比べた倍率の平均は FlashInfer の CuTe DSL に対して 1.522 倍、Cake に対して 1.387 倍でした。これは「3 段を重ねて動かす利点を仕組みの作り直しで取り戻す」というねらいに届いた結果です。ただし、GLM5.2 でバッチを最大の 256 まで増やすと Cake との差は 1.017 倍まで縮み、著者ら自身がこの条件を未解決の課題としています。

### SPMW: 格子をそのまま書ける FPGA 回路のプログラミングモデル

> 参照元: [SPMW: A Grid-Based Programming Model for Scalable Accelerator Design](https://arxiv.org/html/2611.12944)

FPGA で行列の掛け算のような規則正しい計算を速くする専用回路では、PE (計算の最小単位) を格子状に並べて隣どうしでデータを渡すシストリックアレイがよく使われますが、これを書く既存の HLS (C++ で動作を書いて回路に変換する高位合成) は、PE の並べ方や接続の規則をコードのあちこちに分散させてしまい、同じ形の PE でも何度も別々に変換し直してしまいます。このプレプリントは、Cornell University の研究者が、格子の並べ方と PE どうしのつながりをプログラムの中で直接書ける SPMW (Single Program, Multiple Connected Work Units) というモデルを作ったもので、PE の中身は HLS、格子とつながりは RTL (回路の配線レベルの記述) で組み立て、同じ設定の PE は 1 回だけ変換して使い回します。GEMM (行列の掛け算) や FFT (信号を周波数成分に分ける計算) の設計例に加え、コーディングエージェントに同じ回路を書かせる実験も行い、同じ形の部品を何度も作り直す手間を大きく減らせることを示しました。U280 は Xilinx の FPGA のボードです。

:::message
**コメント**: GPU の話ではありませんが、学習のテーマの AutoParallel と同じく、人が手で書き分けていた規則性を、ツールが理解できる形に持ち上げて自動で扱う方向の話として読みました。同じ PE は 1 回だけ変換して使い回すので、変換の時間が格子の大きさではなく PE の種類の数で決まる、というのは素直でうまい考え方だと思います。面白かったのは、5 つのコーディングエージェントに同じ 8×8 の回路を作らせると、SPMW で書かせたときの課金されたトークン数の中央値が SystemVerilog の 7.51 分の 1 だった実験で、エージェントに書かせるならどんな抽象が向いているかを測る、という評価の仕方は今後増えそうです。一方で、FPGA の配置配線にかかる時間は変わらず、最大の配列では 89.3 分のうち HLS は 2.1% にすぎないとされ、小さい配列では回路の資源が元の RTL の実装より多く、FFT では DSP を多く使います。コードは Allo のリポジトリへの取り込みが進んでいる段階なので、まずはそこで例を動かしてみたいです。
:::

![コーディングエージェントに 8×8 のシストリックアレイを作らせると、SPMW で書かせたときのトークン数の中央値は HLS や SystemVerilog で書かせたときより少ないことを示す図](https://arxiv.org/html/2611.12944v1/agent_study.svg)
*出典: [SPMW](https://arxiv.org/html/2611.12944) の Figure 14*

#### 参照元からの抜粋と要約

- **課題**: 既存の HLS/RTL ツールは PE の複製・並べ方・データ供給をコードのあちこちに分散して書くため、同じ形の PE という規則性がコンパイラに見えず、同じ処理を何度も作り直してしまいます。
- **ねらい**: 格子の規則性をプログラミングモデルの中心に置き、同じ設計の PE を 1 回だけコンパイルして多くのハードウェアの部品に使い回せるようにすること。
- **やったこと**: 記事では、著者らが PE の振る舞いとポート、格子の形、型の付いた接続の規則を書き分けるモデルを Allo の上に実装し、各格子座標の特殊化キー (選ばれる本体・ポートのつなぎ方・座標依存の定数の組) が同じ座標どうしは 1 つの HLS 設計だけを合成して RTL の組み立て時に複製する、という仕組みで変換の手間を PE の種類の数だけに抑えたと説明しています。評価は Xilinx U280 の FPGA で、GEMM・FFT・mini-TPU・FEATHER の 4 つの設計例と、5 つのコーディングエージェントに同じ 8×8 のシストリックアレイを SPMW・C++ HLS・SystemVerilog で書かせる実験で行いました。コードは Allo のリポジトリへの統合を進めている段階です。
- **結果**: 記事によると、U280 FPGA で測った 32×32 の GEMM の kernel-to-RTL コンパイル時間は、SPMW が AutoSA (Vitis HLS 版) より 619 倍短く、ねらいである「1 回のコンパイルで多くの部品に使い回す」効果を裏付けました。ただし FPGA 全体の配置配線にかかる時間は変わらないままで、最大の配列ではビルド時間全体の 89.3 分のうち HLS 部分はわずか 2.1% にすぎません。
