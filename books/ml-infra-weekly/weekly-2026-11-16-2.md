## 学習の並列化

### AutoParallel: 並列化の計画の自動探索

> 参照元: [AutoParallel: Composable, PyTorch-Native Automatic Parallelism for Production Training](https://arxiv.org/html/2611.08660)

大きなモデルを学習するときは、1 枚の GPU に載らない重みや計算を何枚もの GPU に分けて持たせる並列化が必要で、重みを分割する FSDP、1 つの演算を分担する TP、長い入力を分ける CP、モデルを前後に区切るパイプライン並列などを組み合わせます。どれをどう組み合わせるかはこれまで専門家が手で書いていて、モデルや GPU の台数が変わるたびに書き直しが必要でした。このプレプリントは、Meta Superintelligence Labs の研究者が、PyTorch の中だけで動き、結果を普通の PyTorch のプログラムとして出す自動の計画ツール AutoParallel を作ったもので、専門家の手書きに並ぶか上回る並列化の計画を自動で見つけました。メッシュは GPU を格子状に並べた座標、DTensor はテンソルがその格子上でどう分割されているかを覚える PyTorch のデータ型です。

:::message
**コメント**: 並列化の決め方を人の手作業から自動の探索へ移そうとする流れがはっきり出てきたのは興味深いと思いました。次に紹介する SS-HSDP も、手で決め打ちしていた重みの分け方を柔軟にする方向で、向きは同じだと感じます。私が一番効いていると思ったのは、結果が独自の実行環境ではなく普通の PyTorch のプログラムとして出てくる点です。中身を人が読んで直せるなら、自動で作ったものを本番に入れる心理的なハードルがかなり下がりそうです。一方で、パイプライン並列は対象外で、MoE の振り分けや CP の attention は利用者が書いた部分をそのまま固定の条件として扱う作りなので、いちばん難しいところはまだ人の手に残っています。LLaMA 3 8B を H100 128 枚の CP 併用の 4 次元メッシュで学習した構成では、1 秒あたりのトークン数が手書きのレシピより 3.6% 少なく、著者らは CP が attention の大部分を利用者の書く部分に押し込むことを主な要因と推測しつつ、他の要因からは切り分けていないと書いています。自動で探せる範囲が CP や MoE の部分まで広がるかを見ていきたいです。
:::

![AutoParallel が学習の計算全体をグラフとして取り出し、演算ごとの分け方の候補から 1 つずつ選び、普通の PyTorch のモジュールとして出力する構成図](https://arxiv.org/html/2611.08660v1/overview.svg)
*出典: [AutoParallel](https://arxiv.org/html/2611.08660) の Figure 1*

#### 参照元からの抜粋と要約

- **課題**: 分散学習の並列化のレシピは専門家が手で書いていて、モデルや入力の形、ハードウェアの構成が変わるたびに調整し直す必要があります。先行する自動並列化の研究も、PyTorch とは別の実行環境に頼る、出力が読みにくいなどの理由で手書きのレシピを置き換えられていません。
- **ねらい**: PyTorch の外の実行環境を使わずに、演算子ごとの分け方を学習の計算全体で同時に探し、専門家の手書きに並ぶか上回る計画を自動で見つけること。
- **やったこと**: 著者らは、順伝播と逆伝播をまとめた計算のつながりをグラフとして取り出し、演算子ごとに DTensor の規則から正しく動く分け方の候補を並べ、ハードウェアに合わせた所要時間の見積もりで全体の組み合わせを選ぶ探索器を作りました。選び方の問題を演算子どうしの隣接関係だけでコストが決まる形に書き直し、同じ層の繰り返しをまとめる工夫とメッシュの軸ごとに先に解いて候補を絞る工夫で、4 次元のメッシュでも短時間で解けるようにしました。結果は DTensor の重みを持つ普通の nn.Module として出し、TorchTitan の GraphTrainer を通して Inductor でコンパイルします。MoE のルーティングや CP の attention のような動きの決まらない部分は local_map という仕組みで利用者が入口と出口の分け方を宣言し、探索ではその境界を固定の条件として扱います。評価は H100 最大 128 枚、最大 4 次元のメッシュで、LLaMA 3 8B/70B、Qwen3 32B、MuseGlimmer 30B、DeepSeek-V3 ベースの 16B MoE の計 14 構成を TorchTitan の手書きのレシピと比べました。コードは meta-pytorch/autoparallel で公開されています。
- **結果**: 著者らによると、DeepSeek-V3 の構造に基づく 16B の MoE を H100 8 枚で学習したとき、1 秒あたりのトークン数は手書きのレシピの 4.42 万に対し AutoParallel が 5.23 万で、18.3% 多くなりました。14 構成のうち 9 構成で手書きのレシピを上回り、ねらいである「専門家の手書きに並ぶか上回る」計画を自動で見つけられましたが、残り 5 構成は下回り、CP を併用した H100 128 枚の構成では最大 3.6% 少なくなりました。

### SS-HSDP: 計算の並べ方と更新の単位の分離

> 参照元: [SS-HSDP: Efficient and Flexible Sharded Data Parallelism via Runtime-Update Decoupling](https://arxiv.org/html/2611.16467)

大きなモデルの学習では、重みと勾配とオプティマイザの状態を GPU ごとに分割して持たせ、計算の直前だけ集めて使う方法 (PyTorch の FSDP2 など) が広く使われていますが、重みを 8 ビットの小さな数で持ちブロックごとに倍率を共有する MXFP8 のような形式や、行列全体を単位に更新する Muon のようなオプティマイザが出てきたことで、計算に都合の良い重みの並べ方と更新に都合の良い単位が食い違う問題が出てきました。このプレプリントは、Tsinghua University と動画生成の Shengshu Technology の研究者が、計算に使う重みと更新に使う重みを別物として扱い、コピーを増やさずに両方の都合を満たす SS-HSDP という仕組みを作ったものです。HSDP は少数の GPU の間だけで分割し複製することで通信を減らす方式、MFU は GPU の理論上の演算性能のうち実際に使えた割合、B200 は NVIDIA の GPU の機種名です。

:::message
**コメント**: これも AutoParallel と同じく、並列化を決め打ちのレシピから柔軟なものへ移していく流れの一つだと読みました。AutoParallel は演算ごとの分け方を探すほうで、SS-HSDP は計算と更新という役割の違いで分け方を切り離すほうなので、自動化と分離が両方から進んでいるのが面白いです。プレプリントの関連研究には、DeepSeek-V4 や Kimi K3 や GLM-5 が Muon をヘッド単位で使う例が挙がっていて、行列単位の更新が実験ではなく大規模な事前学習の道具になってきたことが、この仕組みが出てきた理由だと感じます。気になるのは、主な比較で使った GPU の機種が書かれていないこと、比較相手の veScale-FSDP が著者らの作り直しであること、入力が合成データであること、そしてコードがまだ公開されていないことです。公開されたら、プレプリントが報告する Muon と AdamW の差を手元で再現し、FSDP2 でヘッド単位の Muon がそもそも組めるのかもあわせて確かめたいです。
:::

![MXFP8 での学習の MFU とピークのメモリを 4 つのモデルと 32 枚から 128 枚の GPU で比べると、SS-HSDP がどの構成でも MFU が最も高いことを示す図](https://arxiv.org/html/2611.16467v1/x5.svg)
*出典: [SS-HSDP](https://arxiv.org/html/2611.16467) の Figure 6*

#### 参照元からの抜粋と要約

- **課題**: FSDP2 などの既存の仕組みは、計算が求める重みの並べ方とオプティマイザが求める更新の単位を同じ分割の構造に結びつけているため、Muon のような行列単位の更新や MXFP8 のようなブロック単位の倍率を満たそうとすると、計算の効率か更新の柔軟さのどちらかが落ちます。
- **ねらい**: 計算に使う重みと更新に使う重みを分け、追加のデータの移動なしに両方の都合を同時に満たすこと。
- **やったこと**: 著者らは、同じメモリを形の違う複数の見方で共有する data tree と、分割の段ごとにどの断片がどの GPU にあるかを記録する shard chain を作り、計算用と更新用の重みをコピーなしで両立させました。そのうえで、同じ種類の更新をまとめて実行する工夫と、GPU の計算ユニット (SM) を使わず専用の転送エンジンで通信する ZeroSM を加え、NCCL の通信カーネルが SM を奪い合って計算を遅らせる問題を避けました。社内の動画モデル 2 種、MoE の Qwen3-30B-A3B、12 層に縮めた MiMo の計 4 モデルを 32〜128 GPU で学習し、FSDP2・veScale-FSDP (著者らの再現実装)・Megatron-FSDP と比べました。コードは将来公開予定とされています。
- **結果**: 著者らによると、MXFP8 で 128 枚の GPU を使い MiMo を学習したとき、SS-HSDP の MFU は最も速いベースライン (FSDP2・veScale-FSDP・Megatron-FSDP のうち最速) より 21.7% 高くなり、ねらいである「計算と更新の両方の都合を同時に満たす」ことを達成しました。ただし Qwen3-30B-A3B では MXFP8 の効果が 1% 未満にとどまり、コードもまだ公開されていません。

## 強化学習の数値

### BF16 の強化学習の遅さの原因: 丸めで消える小さな更新

> 参照元: [Closing the BF16-FP16 Convergence Speed Gap in RL Post-Training with Stochastic Rounding](https://arxiv.org/html/2611.13545)

LLM の学習では重みの元の値を 32 ビットの FP32 で持ち、計算には 16 ビットに丸めた写し (BF16 か FP16) を使う混合精度がふつうで、BF16 は値があふれにくく事前学習では FP32 と同じように収束しますが、正解かどうかを自動判定して報酬を与える強化学習の RLVR では学習率をとても小さくすることが多く、この条件では BF16 が同じ学習率の FP16 より収束に時間がかかります。先行研究はこの遅さを推論側と学習側の確率のずれが原因だとしていましたが、このプレプリントは、NVIDIA の研究者が、そのずれを取り除いても遅さが残ることを示し、重みの固着という別の原因を突き止めたものです。重みの固着とは、FP32 の重みへの小さな更新が BF16 の刻みの半分に届かないうちは丸めで打ち消され、BF16 の写しが変わらないまま残る現象です。確率的丸めは、丸める値の近さに応じた確率で上下どちらかに丸め、平均すると元の値に一致する丸め方です。

:::message
**コメント**: 同じ週の Detent は、Qi らの手順の BF16 の GRPO で報酬が崩れるのを、推論と学習のずれをなくして防いでいました。このプレプリントは、Qi らが報告したその崩壊が著者らの環境では vLLM の TorchInductor の最適化を有効にしたときだけ起きたとしたうえで、ずれをビット単位でなくしても BF16 が遅いことを示していて、2 本を並べると原因が少なくとも 2 層あることが見えてくるのが面白いです。学習率がとても小さいと更新が丸めで消える、というのは言われてみれば当然ですが、最初の 4 回の更新の後に変わらず残った重みの割合を BF16 と FP16 で数えて、仮数のビット数を 1 つずつ増やした擬似の形式で収束が FP16 に近づくことまで確かめている、という詰め方がよいと思いました。学習のテーマの SS-HSDP にも、GPU の間の集計を BF16 の確率的丸めで行う方式が出てきたので、低精度で集計や更新をするところで確率的丸めが標準の道具になっていく気がします。ただ、丸めのカーネル自体のコストは数字がなく、複数のモデルでの主な比較は、推論と学習の確率をビット単位でそろえた状態ではなく TorchInductor を切っただけの状態で行われています。手元の RL の基盤でも、最初の数回の更新で BF16 の重みがどれだけ変わらないかは安く数えられるので、まずそこを測ってみたいです。
:::

![確率的丸めを使う BF16 が、3 つのモデルと 2 つのデータセットで FP16 とほぼ同じ報酬の伸び方をし、ふつうの BF16 より速く報酬が上がることを示す図](https://arxiv.org/html/2611.13545v1/reward_trajectory.svg)
*出典: [Closing the BF16-FP16 Convergence Speed Gap in RL Post-Training with Stochastic Rounding](https://arxiv.org/html/2611.13545) の Figure 1*

#### 参照元からの抜粋と要約

- **課題**: BF16 の混合精度の学習は事前学習では FP32 と同じように収束しますが、学習率がとても小さい RLVR では同じ学習率の FP16 より多くのイテレーションを要し、推論側と学習側の確率のずれを取り除いてもこの差は残るため、これまでの説明では足りません。
- **ねらい**: 収束の遅さの原因を突き止め、参照のモデルからの離れ方 (drift) を増やさずに、BF16 のまま FP16 と同じ収束の速さを得る方法を示すこと。
- **やったこと**: 著者らは、vLLM の TorchInductor コンパイラ最適化を無効にして推論側と学習側の確率のずれの影響を取り除いたうえで、DeepSeek-R1-Distill-Qwen-1.5B を MATH-1460 で学習し、最初の RL イテレーションの 4 回の更新の後に学習前の値のまま変わらない重みの割合を BF16 と FP16 で数えました。その結果、変わらず残った重みは BF16 で 98.84%、FP16 で 90.79% で、FP16 は BF16 の約 8 倍の重みを動かしていたことから、FP32 の重みへの小さな更新が BF16 の刻みの半分に届かないうちに丸めで打ち消される重みの固着が遅さの原因だと分かりました。そこで、FP32 から BF16 の写しを作る丸めを確率的丸めに替え、DeepSeek-R1-Distill-Qwen の 1.5B・14B と Qwen3-30B-A3B を MATH-1460 や DAPO-Math-17k で学習して比べました。
- **結果**: 著者らによると、学習率を 2 倍に上げて BF16 の遅さを補う方法は、参照モデルからの drift (KL ダイバージェンス) が同じ学習率の FP16 の約 1.5 倍に増えましたが、確率的丸めを使う BF16 は学習率を上げずに FP16 に近い drift のまま、試した全モデル・データセットの組み合わせで FP16 とほぼ同じ報酬の伸び方を再現し、ねらいである「drift を増やさずに BF16 のまま FP16 と同じ速さで収束させる」ことを達成しました。ただし Qwen3-30B-A3B では答えの長さが他の条件より約 25% 短いまま残り、原因は分かっていません。

## モデルの調整と圧縮

### 前向きの計算による削る重みの探し方

> 参照元: [Efficient LLM Adaptation with Forward-Only Passes](https://arxiv.org/html/2611.10610)

学習を終えたモデルを特定の課題向けに調整する適応は、ふつう勾配を求める逆伝播を使って重みを更新しますが、そのぶんメモリと時間がかかります。先行研究の LASER は、重み行列を SVD (特異値分解) で重要度順の成分に分け、重要度の低い成分を削ると正答率が上がる現象を見つけましたが、削る行列を全部試して決めるので遅く、勾配を使う LASER-Grad は逆伝播のぶんメモリを食います。このプレプリントは、Lund University の研究者が、Google DeepMind の研究者の助言を受けて、逆伝播を使わず前向きの計算 (入力から出力を求めるふだんの推論の計算) だけで削る重み行列を探す方法を提案したものです。角度の集中度は、ある成分が作る途中の値のベクトルがトークンどうしでどれだけ同じ向きを向いているかを、向きの近さを表すコサイン類似度の平均で測った指標で、この値だけで逆伝播なしに削る候補を絞り込めることを示しました。

:::message
**コメント**: 今回の中ではインフラから一番遠い話ですが、サービングで毎日大量に回っている前向きの計算をそのままモデルの調整に使えないか、という問いの立て方が気になって入れました。逆伝播が要らないので、推論用の GPU や推論エンジンのままで調整の候補を探せるようになれば、学習用の環境を別に用意する手間が減りそうです。一方で、実験は課題ごとの検証データで候補を選んで正答率を測るもので、実際のサービングのリクエストを使ったわけではありません。GPT-J-6B では、8 つのデータセットのうち Bios Profession で正答率が LASER より 3.0 ポイント、LASER-Grad より 1.4 ポイント低く、WikidataQA でも LASER-Grad より 1.2 ポイント低く、最大 57B とされるモデルも一度に使う重みは 14B の MoE です。コードの公開先もプレプリントには書かれていないので、まずは削った後のモデルが推論エンジンでスループットや正答率をどう変えるかを見てみたいです。
:::

![重み行列を SVD で成分に分け、前向きの計算で各成分の角度の集中度を測り、散らばりを生む重み行列だけを削る手順を示す図](https://arxiv.org/html/2611.10610v1/main_camera.png)
*出典: [Efficient LLM Adaptation with Forward-Only Passes](https://arxiv.org/html/2611.10610) の Figure 1*

#### 参照元からの抜粋と要約

- **課題**: LASER が示した、重み行列の重要度の低い成分を削ると正答率が上がる現象を使って課題ごとに適応したいのですが、LASER の全部を試す探索は時間がかかり、勾配を使う LASER-Grad は逆伝播のぶんメモリと時間がかかります。
- **ねらい**: 逆伝播を使わず、前向きの計算だけで、どの重み行列を削るべきかを効率よく見つけること。
- **やったこと**: 著者らは、重み行列の出力が SVD の成分ごとの出力の和に書けることを使い、各成分が生む活性化 (入力に対する出力の値) について、トークンどうしの向きの近さの平均を角度の集中度として測りました。全体より向きを散らしている成分を多く持つ重み行列ほど、ファインチューニングで向きが集中していくという先行研究の知見とは逆の状態にあると考え、こうした行列を削る候補として点数を付け、点数の高い候補だけを検証データで実際に削って残す成分の割合を決めました。評価は NVIDIA A100 40GB 1 枚で、GPT-J-6B と RoBERTa を中心に 8 つのデータセットで LASER と LASER-Grad と比べました。コードは補足資料に含むとされていますが、公開先は書かれていません。
- **結果**: 著者らによると、GPT-J-6B では、探索にかかる時間が平均で LASER-Grad の 18.4 倍短くなり、8 つのデータセットのうち 4 つで最も高い正答率を達成し、ねらいである「逆伝播を使わず効率よく削る重み行列を見つける」ことを達成しました。ただし Bios Profession では正答率が LASER と LASER-Grad の両方より低く、課題を完全には解決していません。

### 大きいモデルほど補えない圧縮の傷

> 参照元: [When Bigger Becomes Brittle: Why Compression Hurts More as Language Models Scale](https://arxiv.org/html/2611.07891)

量子化や枝刈りでモデルを軽くしたときの良し悪しは、ふつうベンチマークの点数で測りますが、点数に表れるのは出力に残った悪化だけで、モデルの中でどれだけ壊れ、残りの部分がそれをどれだけ補ったかは分かりません。補いが大きければ、中では大きく壊れていても点数は下がらないので、点数だけでは、壊れていないのか、壊れたが補えたのかを区別できません。このプレプリントは、IIIT-Delhi を中心とする研究者が、文章の中から答えの名前を探してくる役目の注意のヘッドを止めたときに、悪化を補いと出力に残った分に分けて測り、モデルが大きいほど補いの割合が下がって傷が出力に残りやすくなることを示したものです。注意のヘッドは attention の中で並んで働く小さな部品で、ここでの量子化は重みを少ないビット数の数で表すこと、枝刈りは部品の一部を取り除くことです。抜粋に出てくる logit はモデルが各単語に付ける点数で、ここでは正解の名前と、文中で繰り返されて紛らわしい名前の点数の差を悪化の物差しに使います。Pythia は同じデータを同じ順に同じ量だけ学習させた大きさ違いのモデルの一式で、大きさの違いだけを比べるのに使われます。

:::message
**コメント**: 同じテーマの前のプレプリントが、重みを削ると正答率が上がる場合を探していたのに対して、こちらは削ったときに大きいモデルほど傷が素通りする、という逆向きの話で、並べて読むと面白いです。小さいモデルではほぼ無害だった圧縮が、大きいモデルでは高くつくことがありうる、という著者らの示唆を、点数ではなく中で何が起きているかの測定から導いている点が気になりました。ただ、調べた能力はひな形の文で名前を当てる 1 種類だけで、量子化も 32 ビットの浮動小数点の推論の中で重みだけを 4 ビット相当に丸めた模擬で、実際の量子化のカーネルを使ったものではありません。著者らのコードの公開先も見当たりません。それでも、点数が下がらないことと中が壊れていないことは別だ、という見方は、圧縮した推論の構成を評価するときの測り方として覚えておきたいと思いました。
:::

![Pythia-410M は検索のヘッドを止めた傷のほとんどを、抑えのゆるみと残りの部品の補いと正規化の変化の合計で取り戻すが、Pythia-12B はごく一部しか取り戻せず、傷が出力に残ることを比べた図](https://arxiv.org/html/2611.07891v1/fig_repair_bands_pythia_410m_12b.svg)
*出典: [When Bigger Becomes Brittle](https://arxiv.org/html/2611.07891) の Figure 3*

#### 参照元からの抜粋と要約

- **課題**: 量子化や枝刈りの効果はベンチマークの点数、つまり出力に残った悪化だけで報告され、モデルの中でどれだけ傷つき、どれだけ補われたかが分かりません。この傷と補いのつり合いがモデルの大きさで変わるかも分かっていませんでした。
- **ねらい**: 文章の中から答えを探す役目のヘッドへの傷を例に、出力に残った悪化を補いの分と厳密に分け、その分け方が Pythia の 410M から 12B でどう変わるかを明らかにすること。
- **やったこと**: 著者らは、文中の 2 人の名前のうち繰り返されていないほうを答えさせる課題で、答えの名前に注意を向けて点数を上げるヘッドを検索のヘッドとして見つけ、その出力を 0 にしました。正解の名前と紛らわしい名前の点数の差について、各部品が直接足している量を使い、出力に残った悪化が、もとの傷から、検索のヘッドの後ろで同じ答えの名前の点数を下げるコピー抑制のヘッドの抑えがゆるんだ分、残りの部品が補った分、最後の正規化で変わった分を引いたものに一致する恒等式を組みました。さらに、このコピー抑制のヘッドがもともと答えの名前の点数をどれだけ抑えているかを測り、この抑えがモデルの大きさで変わることが、補いの割合がモデルの大きさで変わる一因であることを確かめました。Pythia の 410M、1B、1.4B、2.8B、6.9B、12B の 6 つを主に比べ、OPT の 4 つの大きさでも確かめました。さらに、検索のヘッドの重みを出力のチャンネルごとに 4 ビットの整数に丸めて戻す模擬の量子化と、ヘッドの半分を止める枝刈りでも同じ分け方をしました。計算はすべて 32 ビットの浮動小数点で行いました。
- **結果**: 著者らによると、同じ 0.5 logit の傷を与えたとき、Pythia-410M は約 0.55 logit を補って点数の差がもとより約 0.05 logit 高くなったのに対し、Pythia-12B では 0.5 logit のうち約 0.38 logit が出力に残りました。約 0.8 logit の傷をそろえて比べると、残りの attention の部品が補った割合は、Pythia-410M で約 80%、Pythia-12B で約 9% でした。4 ビットの模擬の量子化でも、出力に残った悪化をもとの傷で割った比は、Pythia で 410M の 0.55 から 12B の 0.91 に、OPT で 125M の 0.41 から 6.7B の 0.98 に上がり、枝刈りでも、上位の検索のヘッドを多く含む止め方では大きいモデルほど補いが減りました。モデルが大きいほど補いの割合が下がるという答えが得られ、ねらいに届きました。ただし、調べたのはひな形の文での名前の検索だけで、コピー抑制のヘッドは量子化と枝刈りの対象から外したので、実際の量子化のカーネルがそのヘッドも傷つける場合は結果が変わりうるとされ、著者らのコードの公開先も書かれていません。

## ベクトル検索とクラスタリング

### GINGER: 粗くも細かくも使う 1 つの符号

> 参照元: [GINGER: Spicing Up Graph-Based Vector Search](https://arxiv.org/html/2611.08306)

RAG や推薦では、文章や画像を意味の近さが距離に表れる数のベクトルに変えた埋め込みを大量に持ち、問い合わせに近いベクトルを探します。全部と比べると遅いので、多少の取りこぼしを許して速く探す近似最近傍探索が使われ、その代表が、近いベクトルどうしを辺でつないだグラフをたどって探すやり方です。グラフをたどる間はベクトルを少ないビット数に丸めた粗い符号で比べ、最後に残った候補だけを細かい表現で並べ直すことが多いのですが、これまでのライブラリは粗い符号と細かい表現を別々に持つか元の浮動小数点のベクトルを持ち続けるので、メモリを多く使います。このプレプリントは、Google Research の研究者が、1 つの符号の上位のビットを粗い比較に、残りのビットまで含めた全体を並べ直しに使う形にし、グラフも損失なく圧縮したライブラリ Ginger を作り、既存のライブラリと比べて再現率 95% でのクエリの速さを平均 1.8 倍にしたものです。抜粋に出てくる再現率は、本当に近い上位 10 件のうち何件を見つけられたかの割合で、QPS は 1 秒あたりに処理できる問い合わせの数です。

:::message
**コメント**: 普段の推論や学習の話とは離れますが、RAG の裏側で毎回動く部分の話です。GPU を使わず CPU の SIMD だけで、再現率 95% での QPS が 14 のデータセットのうち 13 で、データセットごとの最速の既存のライブラリの平均 1.8 倍になった点が目を引きました。上位の 4 ビットだけ読めばグラフをたどれて、続きのビットまで読めば並べ直しに使える、という符号の作り方は、別々の表現を 2 つ持つより素直で、メモリの量と読み出す量を同時に減らせるのがうまいと思います。比べ方も、データセットごとの最速の相手との比較と、1 つのライブラリに固定した比較を分けて書いていて、どちらで見ても速いと言えるようにしているのが誠実だと感じました。一方で、8 ビットの整数の BigANN では SVS のほうが 4% 速く、小さいデータセットでは索引の構築で ParlayANN に、GloVe では Faiss に負けています。コードは公開されているので、手元の RAG の埋め込みの次元と件数で、いま使っている Faiss などとメモリと QPS を比べてみたいです。
:::

![14 のデータセットの幾何平均で、Ginger が再現率 95% でのクエリのスループットが既存のライブラリより高く、MS-MARCO での索引の構築も速いことを示す図](https://arxiv.org/html/2611.08306v1/teaser.svg)
*出典: [GINGER](https://arxiv.org/html/2611.08306) の Figure 1*

#### 参照元からの抜粋と要約

- **課題**: グラフをたどる近似最近傍探索の既存のライブラリは、たどるための軽い符号と並べ直しのための細かい符号を別々に持つか、元の浮動小数点のベクトルを持ち続けるので、メモリを無駄に使います。グラフの辺の一覧もメモリを圧迫します。
- **ねらい**: 1 本の量子化の符号で粗い比較と細かい並べ直しを両立させ、グラフを損失なく圧縮して、問い合わせのスループット、メモリ、索引の構築時間の 3 つを同時に良くすること。
- **やったこと**: 著者らは、索引を作る PiPNN と量子化の TurboQuant という先行研究を土台に、TurboQuant の 4 ビットの各区間をさらに細かく分けて 10 ビットや 12 ビットの符号にする Nested TurboQuant を作り、符号の上位 4 ビットをグラフをたどる比較に、全体を並べ直しに使いました。各座標をランダムな回転でなめらかな分布に整えておくと、4 ビットの範囲を跨がずに少しずつ精度を上げても元の分布に近い符号になる性質があるため、1 本の符号で粗い比較と細かい並べ直しの両方を精度を落とさずに兼ねられました。グラフは頂点を並べ替えたうえで、辺の一覧をビット単位で詰める SIMD 向けの無損失圧縮の AdaptiveGap で圧縮し、辺あたりに読み出すバイト数を減らしてメモリと読み出しの両方を削りました。評価は Intel Xeon 6985P-C の 72 コアを 2 つ載せた CPU のマシンで、GPU は使わず、10 億件の BigANN や 768 次元から 4,096 次元の埋め込みを含む 14 のデータセットで比べました。コードは [google/ginger](https://github.com/google/ginger) で公開されています。
- **結果**: 著者らによると、DiskANN、ParlayANN、SVS、Hnswlib、SymphonyQG、Faiss、ScaNN の 7 つのライブラリと比べたとき、再現率 95% での QPS は 14 データセットのうち 13 で、データセットごとに最も速い相手の平均 1.8 倍でした。メモリを最も節約する SVS と比べても、高次元のデータセットでは再現率 95% での QPS が幾何平均で 2.9 倍でした。索引の構築時間は、10 億件の 5 つのデータセットで平均 35 分と、最も速い Faiss の平均 69 分の約 2 分の 1 でした。スループット・メモリ・索引構築時間の 3 つを同時に良くするというねらいに、この 3 つの結果で届きました。ただし、8 ビットの整数の BigANN では SVS が 4% 速く、とても小さいデータセットでは索引の構築で ParlayANN が最大 5.7 倍速く、GloVe では Faiss が 2.1 倍速いままです。

### e-means: 指数移動平均による Lloyd の 10 分の 1 のエポックでの k-means の解き方

> 参照元: [e-means: outperforming k-means (in one-tenth the epochs)](https://arxiv.org/html/2611.09501)

k-means は、データの点を k 個のまとまりであるクラスタに分け、各点と、そのクラスタの中心との距離の二乗の平均が小さくなるように中心を決める方法で、ベクトル検索の索引づくりやベクトルの量子化に広く使われています。標準の解き方である Lloyd のアルゴリズムは、全部の点を最も近い中心に割り当て直してから中心を割り当てられた点の平均に置き直す 1 周をエポックと呼び、これを何十回も繰り返すので、点の数が多いと重くなります。このプレプリントは、FAIR at Meta の研究者が、画像の生成モデルの VQ-VAE で使われてきた指数移動平均による中心の更新を k-means に持ち込み、その設定を式で決められるようにした e-means を提案し、Lloyd と同じかそれより小さい誤差に、Lloyd の約 10 分の 1 のエポック数で届かせたものです。指数移動平均は、新しい値を一定の割合で混ぜ、古い値ほど小さい重みで残していく平均のことで、その混ぜる割合を決めるのが減衰率です。抜粋に出てくる DINO10B は、画像を DINOv3 というモデルに通して作った 1,024 次元のベクトル 100 億件のデータセットです。

:::message
**コメント**: k-means はあまりに当たり前の道具なので、まだこんなに速くなる余地があったことにまず驚きました。深層学習で当たり前になったミニバッチ、中心を動かす幅をコサインで減らしていくやり方、スケーリング則でハイパーパラメータを決めるやり方を、そのまま古典的なアルゴリズムに持ち込んでいて、学習の側で育った道具が古い問題に戻ってくる流れが面白いです。プレプリントも IVF というクラスタに分けて探す検索の索引で評価していて、そうした索引は中で k-means を回して作るので、k-means の GPU の計算量が Faiss-GPU や Flash-KMeans と比べて約 10 分の 1 になるなら、索引の作り直しの頻度も変えられそうです。ただ、スケーリング則は DEEP という比較的高次元のデータセットで当てはめたもので、低次元で小さいデータには最適ではないと著者らも書いており、合成データの 140 の実験のうち 10 では、学習に使わない点での誤差が Lloyd に負けています。コードは Faiss の中に入っているので、手元の埋め込みで、いま使っている Faiss の k-means と時間と誤差を比べてみたいです。
:::

![DINO10B の 1 億点で、e-means が 2 エポックで Faiss-GPU と Flash-KMeans の 25 エポック目の誤差を下回ることを示す図](https://arxiv.org/html/2611.09501v1/robustness_tstar.svg)
*出典: [e-means](https://arxiv.org/html/2611.09501) の Figure 1 の左*

#### 参照元からの抜粋と要約

- **課題**: Lloyd の k-means はクラスタの質は高いのですが、エポックごとにデータ全体を走査するので重くなります。ミニバッチの k-means は速いのですが、収束先の誤差が高く、バッチの大きさと中心を動かす幅を問題ごとに手で探索して決める必要がありました。
- **ねらい**: 指数移動平均による中心の更新を k-means の誤差の最小化に合わせて作り直し、バッチの大きさと減衰率を探索なしで決める式を与えて、Lloyd より少ないエポックと短い時間で同じかそれより小さい誤差に届くこと。
- **やったこと**: 著者らは、クラスタごとに点の数と点の和を指数移動平均で更新し、中心をその比として読み出す更新式を作りました。Lloyd は 1 エポックに 1 回しか中心を動かせませんが、この更新はミニバッチのたびに動かせるので、1 エポックの中で中心を何十回も動かせることが少ないエポックで収束する理由です。動かす幅をコサインで減らしていく工夫、点の少ないクラスタを点の多いクラスタの中心を 2 つに割って復活させる工夫、最後のエポックの割り当てで中心を平均し直す仕上げを加え、誤差を Lloyd 並みまで落としました。さらに、バッチの大きさと最初に動かす幅を、点の数、クラスタの数、エポックの予算のべき乗の式で表し、DEEP のデータセットでの 75,000 回の実行に当てはめたことで、問題ごとに値を探索しなくても式に数を入れるだけで決まるようにしました。最も近い中心を探す計算は NVIDIA の CuTe DSL で GPU のカーネルとして書き、クラスタが非常に多い場合は中心の側に IVF の索引を作って近い中心だけを比べることで計算量を減らしました。コードは [Faiss の contrib/e_means](https://github.com/facebookresearch/faiss/tree/main/contrib/e_means) で公開されています。
- **結果**: 著者らによると、GPU の Flash-KMeans・Faiss-GPU・cuML や CPU の Faiss・SuperKMeans と比べ、DEEP、DINO10B、SPACEV、SimSearchNet++ の 4 つのデータセットで、Flash-KMeans の 25 エポック目の誤差に e-means は 1.4〜2.6 エポックで届き、実時間では 9.5〜45.5 倍速くなりました。DINO10B の 100 億件全部を約 1,670 万クラスタに分ける実験では、Lloyd が 25 エポック・H100 512 枚・6,784 GPU 時間で届いた誤差に、e-means は 2.5 エポック・H100 256 枚・779 GPU 時間、Lloyd の約 8.7 分の 1 の GPU 時間で、0.014% 小さい誤差で届きました。少ないエポックと短い時間で同じかそれより小さい誤差に届くというねらいは、どちらの規模でも届きました。ただし、スケーリング則は比較的高次元のデータで当てはめたもので、低次元で小さいデータには最適ではなく、合成データの 140 の実験のうち 10 では、学習に使わない点での誤差が Lloyd の 25 エポックより大きくなりました。
