## はじめに

この章は AIM345 ワークショップの冒頭である。あなたのチームは 2 台の GPU ノードでモデルを配信しており、長い文脈を使うリクエストが増えている。60 分の中で、すでに並べて動いている統合構成と分離構成を比較し、どちらを残すかを決める。

サービスレベル目標 (SLO) は、TTFT (最初の 1 文字が出るまでの時間) が 2000 ms 未満、TPOT (1 トークンあたりの生成時間) が 100 ms/トークン未満で、計画した呼び出しの 90 パーセント以上がこの両方を満たすことである。モデル・GPU 予算・ルーティング・キャッシュ設定はすべて両構成で揃え、測定結果だけで分割するかしないかを決める。

## 配信環境

Amazon EKS (Elastic Kubernetes Service) は Kubernetes クラスタを運用するマネージドサービスである。ワークショップの CloudFormation テンプレートがクラスタとデバイスプラグインを用意してくれる。両方の構成とも、SGLang という推論エンジンが DeepSeek-V2-Lite-Chat を配信する。

![CloudShell が別々のルータに届く。統合はノード A で動き、まとめて配置された prefill と decode はノード B で動いて、KV の受け渡しはノード内で完結する](/images/books/aim345-disaggregated-inference-workshop/diagram-architecture.png)

CloudShell からポートフォワード経由でそれぞれのルータへトラフィックを送る。統合側のルータはノード A 上の 2 つのエンジンプロセスから 1 つを選び、各プロセスが prefill と decode を両方担当する。ノード B では、分離側のルータが prefill 専用プロセスと decode 専用プロセスを連携させる。両構成は同じ GPU 割り当てを持ち、モデルはそれぞれのノードの NVMe キャッシュから読み込まれる。

EFA (Elastic Fabric Adapter) は、計算ノード間を高速に結ぶ AWS のネットワークインターフェースである。g7.48xlarge ノードは 1 台あたり GPU 8 枚と EFA デバイス 2 個を、g7.24xlarge ノードは GPU 4 枚と EFA デバイス 1 個を提供する。測定前に自分の割り当てを確認すること。小さい方の測定例は、制約を加えた g7.48xlarge ホストで取ったものなので **g7.24xlarge 相当の割り当て** と表記している。

## Prefill、ハンドオフ、decode

Prefill はプロンプトを処理して KV (key/value) キャッシュ、つまり続きのトークンを生成するために必要な注意機構の状態を作る。Decode はその状態とモデル重みを使って応答を生成する。統合エンジンは両方の処理を同じプロセスにまとめて持つが、分離構成ではプロセス間に KV のハンドオフが挟まる。NIXL (NVIDIA Inference Xfer Library) は、メモリ位置やデバイス間で推論データを転送するためのライブラリである。

![論理的な prefill、KV 転送、decode の各段階と、クライアントが見る TTFT・TPOT のタイミング。EFA 転送はエンジンが別ノードにあるときに発生する](/images/books/aim345-disaggregated-inference-workshop/diagram-prefill-decode.png)

今回のペア配置では prefill と decode がノード B を共有するので、KV のハンドオフはノード内で完結する。図にある別ノード経路では、KV は NIXL の LIBFABRIC バックエンドを使って EFA 経由で送られる。TTFT はリクエストを送った時点から最初のトークンを含むチャンクを受け取るまでの時間であり、TPOT は最初のチャンクから最後のチャンクまでの時間を、最初のチャンクより後に受け取ったトークン数で割った値である。

## このワークショップでできるようになること

- 稼働中の両方のスタック、揃えた GPU 割り当て、転送設定を確認する。
- キャッシュが効くエージェント的トラフィックと長文脈トラフィックについて、TTFT・TPOT・有効な calls/s/GPU を比較する。
- それぞれの構成が共通 SLO を満たす、測定した中で最も高い到着率を特定する。
- どちらの構成を残すかを決め、再度比較が必要になるワークロードの変化を 1 つ挙げる。

## 前提条件

LLM 配信、Kubernetes の Pod、レイテンシのパーセンタイルについて馴染みがあることが望ましい。使用するのはワークショップイベントに割り当てられた AWS アカウントとリージョンである。両方の配信スタックは開始前にデプロイ済みであり、[参考実装 (companion code)](https://github.com/awslabs/awsome-distributed-ai/tree/riv2026/aim345-content/examples/use-cases/disaggregated-inference-prefill-decode) がこれから実行するコマンドを提供する。

## まとめ

このワークショップは、分離推論が常に速いという前提を検証ではなく「測って決める」ことから始まる。次の「準備」の章では CloudShell を開いてクラスタに接続し、必要な環境変数を読み込む。60 分の本線が終わった後は、Optional の DeepSeek-V4-Flash の演習に進める。
